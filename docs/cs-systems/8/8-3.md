### 前節（8-2）の確認問題の解答

前節の最後に提示した3つの問いの解答を確認します。問3がそのまま本節（関係論理と関係完備）の導入になります。

1. **関係代数の手計算（選択・射影・自然結合）：**

    * **(a) $\pi_{\text{dept\_id}}(\text{Students})$：**
        `Students` の `dept_id` 列は `CS, EE, CS, ME` ですが、純粋な関係代数は集合（Set）を扱うため重複行が自動排除されます。したがって結果は **3 行：`{(CS), (EE), (ME)}`** です。

    * **(b) $\pi_{\text{name}}\Bigl(\sigma_{\text{bldg}=\text{'Bldg-B'}}(\text{Students} \bowtie \text{Depts})\Bigr)$：**
        `Depts` で `bldg = 'Bldg-B'` なのは `dept_id = 'ME'` だけであり、`Students` で `dept_id = 'ME'` に一致するのは `Dave` のみです。したがって結果は **1 行：`{(Dave)}`** です。

2. **スーパーキー・候補キー・整合性制約と 3 値論理：**

    * **(a) スーパーキーと候補キーの違い、および 2 つの整合性制約：**

        * **スーパーキー vs 候補キー：** タプルを一意に識別できる属性集合が**スーパーキー**であり、そのうち「どの属性を 1 個でも取り除くと一意性が失われる極小のスーパーキー」が**候補キー**です。
        * **実体整合性制約：** 主キーを構成するどの属性も `NULL` であってはならず、かつ値が重複してはならないという制約です。
        * **参照整合性制約：** 外部キーの値は、参照先テーブルの主キー（または候補キー）に実在する値であるか、あるいは `NULL` でなければならないという制約です。

    * **(b) `WHERE age = 20 OR age != 20` で `age` が `NULL` の行が出力されない理由：**
        SQL の 3 値論理では、`NULL` との比較（`NULL = 20` および `NULL != 20`）はいずれも `TRUE` でも `FALSE` でもない第 3 の真理値 **`UNKNOWN`** になります。その結果 `UNKNOWN OR UNKNOWN` も **`UNKNOWN`** と評価され、`WHERE` 句は厳密に `TRUE` となる行しか出力しないため抜け落ちます。

3. **「どう演算するか」ではなく「何が欲しいか」だけを論理学で書く（本節への接続）：**
    演算の手順を一切書かず、一階述語論理（$\exists, \forall$）を用いて「条件 $P(t)$ を満たすタプル $t$ の集合 $\{ t \mid P(t) \}$」として純粋に宣言的に書く体系が **関係論理（Relational Calculus）** です。無限集合を生まない「安全な関係論理」は、前節の関係代数と**表現力が完全に等価である（Codd の定理・関係完備）**ことが証明されています。

## 8-3. 関係論理（タプル／ドメイン関係論理・安全な式と関係完備）

### 1. 動機（Why）：関係代数があるのに、なぜ一階述語論理に基づく「関係論理」が必要なのか

前節（[8-2節](8-2.md)）で学んだ **関係代数（Relational Algebra）** は、$\sigma, \pi, \bowtie$ などの演算を組み合わせて新しい表を作り出す強力な体系でした。しかし、関係代数には **「手続き的（Procedural）」** という性格があります。すなわち、「まず `Students` と `Depts` を結合し、次に `bldg = 'Bldg-A'` で選択し、最後に `name` を射影せよ」という**計算の順番（How）**を人間が明示して式を組み立てる必要があります。

これに対し、[8-1節](8-1.md)で見た E. F. Codd の理想は、利用者が計算の手順（How）を一切気にせず **「自分が欲しいデータの条件（What）」だけを宣言的に書く** ことでした。数学の世界には、まさに「条件を満たす要素の集合を宣言的に記述する」ための完成された言語がすでに存在します。それが **一階述語論理（First-Order Predicate Logic）** の集合内包表記 $\{ x \mid P(x) \}$ です。

この一階述語論理をリレーショナルデータベースへ適用した問合せ言語の理論体系が **関係論理（Relational Calculus）** です。関係論理を学ぶことには、次の3つの重要な意義があります。

1. **宣言的言語 SQL の数学的母体：** 私たちが実務で書く SQL（特に `WHERE EXISTS (...)` や `NOT EXISTS` を含む相関副問合せ）は、関係代数よりもむしろ **タプル関係論理** の発想から直接生まれています。
2. **「無限の出力」を防ぐ安全性の理論：** 論理学の否定（$\neg$）を素朴に許すと、「学生テーブルに載っていない宇宙上のすべてのデータ」のような無限集合が書けてしまいます。データベースとして実行可能な **安全な式（Safe Formula）** の境界を厳密に定義する必要があります。
3. **問合せ言語の表現力のものさし（関係完備）：** 「新しい問合せ言語が十分な検索能力を持っているか」を測る国際的な基準が、関係代数・安全な関係論理と等価であることを示す **関係完備（Relationally Complete）** という概念です。

本節では、**タプル関係論理（TRC）** と **ドメイン関係論理（DRC）** の2形式を具体的な問合せで対比したうえで、**安全な式** の条件と **Codd の定理（関係完備）**、さらに一階述語論理の理論的限界までを整理します。

### 2. 具体例と動作イメージ（Toy Model）

形式的な構文規則に入る前に、前節（[8-2節](8-2.md)）と同じ大学データベースの 2 つの表 `Students(sid, name, dept_id)` と `Depts(dept_id, bldg)` を使い、同じ問合せを3通りの言語で書き比べてみます。

#### 実験A：「建物が `Bldg-A` にある学科の学生の名前」を 3 通りで書く

1. **関係代数（[8-2節](8-2.md)：手続き的・How を書く）：**

    $$\pi_{\text{name}}\Bigl(\sigma_{\text{bldg}=\text{'Bldg-A'}}\bigl(\text{Students} \bowtie \text{Depts}\bigr)\Bigr)$$

    「結合して → 選択して → 射影する」という演算パイプラインの順番を指定しています。

2. **タプル関係論理（TRC：行の変数 $t$ を使う・What だけを書く）：**

    $$\bigl\{\, t.\text{name} \;\big|\; \text{Students}(t) \land \exists d\,\bigl(\text{Depts}(d) \land d.\text{dept\_id} = t.\text{dept\_id} \land d.\text{bldg} = \text{'Bldg-A'}\bigr) \,\bigr\}$$

    日本語に直訳すると、**「`Students` に属するタプル $t$ の `name` であって、ある `Depts` のタプル $d$ が存在して（$\exists d$）、$d$ と $t$ の `dept_id` が等しく、かつ $d$ の `bldg` が `'Bldg-A'` であるようなものの集合」** となります。結合を先にやるか選択を先にやるかといった手順は一切書かれていません。

3. **ドメイン関係論理（DRC：列の値の変数 $s, n, k, b$ を使う・What だけを書く）：**

    $$\bigl\{\, \langle n \rangle \;\big|\; \exists s, k, b\,\bigl(\text{Students}(s, n, k) \land \text{Depts}(k, b) \land b = \text{'Bldg-A'}\bigr) \,\bigr\}$$

    行丸ごとの変数ではなく、各列のドメイン値（学籍番号 $s$、名前 $n$、学科 $k$、建物 $b$）を個別の変数として並べ、同じ変数名 $k$ を2箇所に書くことで自然に結合条件を表現しています。

#### 実験B：商演算（全称量化 $\forall$）の書きやすさと、「安全でない式」の問題

前節（[8-2節](8-2.md)コラム）では、「必修科目 `Required(cid)` を**すべて**履修している学生 `sid`（`Enroll(sid, cid) ÷ Required(cid)`）」を関係代数の基本 5 演算で書くために、二重否定を使った非常に複雑な式 $\pi_X(R) - \pi_X((\pi_X(R) \times S) - R)$ を組み立てなければなりませんでした。

ところが、全称量化子 **$\forall$（すべての〜について）** を持つタプル関係論理（TRC）なら、日本語の要求そのままの 1 行で直感的に書けます。

$$
\bigl\{\, e.\text{sid} \;\big|\; \text{Enroll}(e) \land \forall r\,\bigl(\text{Required}(r) \to \exists e'\,(\text{Enroll}(e') \land e'.\text{sid} = e.\text{sid} \land e'.\text{cid} = r.\text{cid})\bigr) \,\bigr\}
$$

（「すべての必修科目 $r$ について、その学生 $e.\text{sid}$ が $r.\text{cid}$ を履修している記録 $e'$ が存在する」）。

一方で、論理学の自由さには注意すべき危険もあります。たとえば「`Students` に**属さない**すべてのタプル $t$」を次のように書いたとします。

$$
\bigl\{\, t \;\big|\; \neg \text{Students}(t) \,\bigr\}
$$

文字列や整数の定義域（ドメイン）は無限にあるため、`Students` に載っていないタプルは **無限個** 存在します。この式を DBMS へ渡しても、答えを書き出すだけで永遠に処理が終わりません。これが後述する **安全でない式（Unsafe Formula）** です。

### 3. 構造・アルゴリズム・実装（What）

#### (1) タプル関係論理（TRC：Tuple Relational Calculus）の構文と SQL との対応

**タプル関係論理（TRC）** は、変数（タプル変数 $t, d, e$ 等）が**テーブルの1行（タプル）全体**を動く論理体系です。一般的な形は次の通りです。

$$
\bigl\{\, t.\text{attr}_1, \dots, t.\text{attr}_k \;\big|\; P(t) \,\bigr\}
$$

論理式（述語）$P$ は、以下の **原子式（Atom）** を論理結合子（$\land, \lor, \neg, \to$）と量化子（存在量化 $\exists$、全称量化 $\forall$）で再帰的に組み合わせて構成します。

1. **関係帰属原子式：** $R(t)$（タプル $t$ が関係 $R$ に属するとき真）
2. **属性と属性の比較：** $t.A \;\theta\; s.B$（$\theta \in \{=, \neq, <, \le, >, \ge\}$）
3. **属性と定数の比較：** $t.A \;\theta\; c$（$c$ は定数）

ここで重要なのが **自由変数（Free Variable）** と **束縛変数（Bound Variable）** の区別です。

* **束縛変数：** $\exists d\,(\dots)$ や $\forall r\,(\dots)$ のように量化子で縛られている変数（プログラムのループ変数のような局所変数）。
* **自由変数：** 量化子で縛られておらず、集合の外側（縦棒 `|` の左側）で出力対象として取り出される変数（実験Aの TRC では $t$ が自由変数、$d$ が束縛変数）。

実験Aの TRC の式と、標準 SQL を上下に並べて見比べると、**SQL の `SELECT ... FROM ... WHERE EXISTS (...)` が TRC の直接的な構文糖衣（シンタックスシュガー）である**ことがひと目で分かります（図8-3-1）。

```sql
-- 実験Aの TRC をそのまま SQL へ書き下したもの
SELECT DISTINCT t.name
FROM Students AS t
WHERE EXISTS (
    SELECT *
    FROM Depts AS d
    WHERE d.dept_id = t.dept_id AND d.bldg = 'Bldg-A'
);
```

`FROM Students AS t` が $\text{Students}(t)$ に対応し、`EXISTS (SELECT * FROM Depts AS d WHERE ...)` がまさに存在量化子 $\exists d\,(\text{Depts}(d) \land \dots)$ に対応しています。

#### (2) ドメイン関係論理（DRC：Domain Relational Calculus）と QBE

**ドメイン関係論理（DRC）** は、タプル全体ではなく**個々の属性値（スカラー値）**を動くドメイン変数 $x_1, x_2, \dots, x_n$ を用いて問合せを記述する体系です。

$$
\bigl\{\, \langle x_1, x_2, \dots, x_k \rangle \;\big|\; P(x_1, x_2, \dots, x_k) \,\bigr\}
$$

原子式は $R(v_1, v_2, \dots, v_m)$（各 $v_i$ はドメイン変数または定数）および $v_i \;\theta\; v_j$ です。実験Aのように、同じ変数名 $k$ を `Students(s, n, k)` と `Depts(k, b)` の両方の位置へ置くだけで「`dept_id` が等しい」という等結合条件を暗黙に表せます。

この DRC を表形式のグラフィカル UI へ落とし込んだのが、1970年代に IBM のモシェ・ズルーフ（Moshe Zloof）が開発した **QBE（Query-By-Example）** です（Microsoft Access のクエリデザイナ等の原型）。利用者は画面上の表の枠内に、出力したい列へ `P._n`（Print 変数 `n`）、結合したい列へ同じ変数 `_k`、条件列へ `'Bldg-A'` と例示するだけで DRC の式を直感的に作成できました。

| `Students` | `sid` | `name` | `dept_id` | | `Depts` | `dept_id` | `bldg` |
| :--- | :---: | :---: | :---: | :---: | :--- | :---: | :---: |
| | | `P._n` | `_k` | | | `_k` | `'Bldg-A'` |

#### (3) 安全な式（Safe Formula）とドメイン独立性

実験Bの最後で見た通り、関係論理では $\bigl\{\, t \;\big|\; \neg \text{Students}(t) \,\bigr\}$ のように**無限個のタプルを返してしまう式**を文法上書けてしまいます。さらに、たとえ有限個であっても、たとえば「`Students` に載っていないすべての 3 桁整数」のように**データベースの中身だけでなく「背後の定義域（ドメイン）全体の大きさ」に結果が依存してしまう式**は、データベースの問合せとして不適切です。

ある関係論理式 $Q$ が、データベースの現在の中身（インスタンス $I$）だけに依存し、背後の定義域をどれだけ広げても常に同じ**有限個の出力**を返す性質を **ドメイン独立（Domain Independent）** と呼びます。

出力が有限かつドメイン独立であることを保証するために定義されるのが **安全な式（Safe Formula）** です。一般の任意の論理式がドメイン独立かどうかを意味論的に自動判定する問題自体は決定不能ですが（4-(2)）、式 $P$ に現れる定数およびデータベース内の全テーブルに含まれる値の集合（**能動ドメイン：$\text{dom}(P)$**）へ結果と量化の範囲が収まることを要請するのが安全性の基準であり、実務の SQL 等では変数を必ず有限のテーブルで束縛する構文規則（レンジ制限：Range-Restricted）によって安全性を保証します。TRC 式 $\{ t \mid P(t) \}$ が安全であるための条件は次の 3 点です（図8-3-2）。

1. 出力されるすべてのタプル $t$ の各属性値は、必ず有限集合 $\text{dom}(P)$ に含まれること（例：$\neg \text{Students}(t)$ のように否定だけで放り出さず、必ず正の帰属条件 `AllPersons(t) ∧ ¬Students(t)` で範囲を縛る）。
2. $\exists u\,(Q(u))$ の部分式について、$Q(u)$ を真にする $u$ のすべての要素が $\text{dom}(Q)$ の中に収まること。
3. $\forall u\,(Q(u))$ の部分式について、$\text{dom}(Q)$ の**外側**にある任意の要素 $u$ に対して $Q(u)$ が常に真になること（例：$\forall r\,(\text{Required}(r) \to \dots)$ は、$r \notin \text{Required}$ なら前提が偽なので含意 $\to$ が自動的に真になり安全）。

#### (4) Codd の定理と「関係完備（Relationally Complete）」

1972年、E. F. Codd はデータベース理論の基礎となる次の定理（**Codd の定理**）を証明しました（図8-3-3）。

> **【Codd の定理】** 次の 3 つの問合せ言語の表現力（記述できる問合せの集合）は、数学的に**完全に等価**である。
>
> $$\text{関係代数（基本 5 演算 } \sigma, \pi, \cup, -, \times \text{）} \;\equiv\; \text{安全なタプル関係論理（TRC）} \;\equiv\; \text{安全なドメイン関係論理（DRC）}$$

証明の直感は明快です。

* **関係代数 $\implies$ 安全な TRC：** 関係代数の基本 5 演算はすべて 1 対 1 で安全な TRC へ翻訳できます。

    * 選択 $\sigma_P(R)$ $\mapsto$ $\{ t \mid R(t) \land P(t) \}$
    * 射影 $\pi_A(R)$ $\mapsto$ $\{ t.A \mid R(t) \}$
    * 和 $R \cup S$ $\mapsto$ $\{ t \mid R(t) \lor S(t) \}$
    * 差 $R - S$ $\mapsto$ $\{ t \mid R(t) \land \neg S(t) \}$
    * 直積 $R \times S$ $\mapsto$ $\{ t \mid \exists r, s\,(R(r) \land S(s) \land t = r \cdot s) \}$（ただし $r \cdot s$ はタプル $r$ と $s$ の連結を表す）

* **安全な TRC $\implies$ 関係代数：** 逆に、任意の安全な TRC 式では、全称量化子 $\forall x\,P(x)$ をド・モルガンの法則 $\neg \exists x\,\neg P(x)$ へ書き換え、否定 $\neg$ を差演算（$-$）、論理積 $\land$ を直積・選択（$\times, \sigma$）、論理和 $\lor$ を和演算（$\cup$）、存在量化 $\exists$ を射影（$\pi$）へ機械的に変換できます。

この定理に基づき、**「少なくとも標準関係代数（＝安全な関係論理）と同等以上の表現力を持つ問合せ言語」**のことを **関係完備（Relationally Complete）** と呼びます。SQL は基本 5 演算（および安全な TRC）をすべて表現できるうえ、さらに集計（`GROUP BY`）やソート（`ORDER BY`）、再帰問合せ（`WITH RECURSIVE`）まで備えているため、**関係完備（かつそれを超える表現力を持つ）** です。

> **【コラム：SQL・QUEL・QBE の三つ巴と、なぜ「宣言的な関係論理」が人間向け言語を制したのか】**
>
> 1970年代、Codd の論文に触発された研究者たちは、関係代数・TRC・DRC のそれぞれをベースにした実用言語を競って開発しました。
>
> * **QUEL（UC バークレー Ingres）：** 純粋な **TRC** に忠実な言語（`RETRIEVE (s.name) WHERE s.dept_id = d.dept_id AND d.bldg = "Bldg-A"`）で、論理的に一貫性がありました。
> * **QBE（IBM）：** **DRC** を表形式 GUI へ直結させた言語。
> * **SEQUEL → SQL（IBM System R）：** 「英語の文章のように読める宣言的言語」を目指し、**TRC** の構文（`SELECT ... FROM ... WHERE ...`）を土台にしつつ、関係代数の集合演算（`UNION`, `EXCEPT`）や集計（`GROUP BY`）を折衷した言語。
>
> 結果として、IBM の商用展開と ANSI/ISO 標準化によって **SQL** が世界標準を勝ち取りました。しかし重要なのは、どの言語も「人間が書く入口は **関係論理ベース（宣言的：What）**、DBMS の内部で最適化する中間表現は **関係代数木（手続き的：How）**」という分業を共通して採用している点です。Codd の定理による「両者の完全な等価性」こそが、この分業を数学的に保証しているのです。

### 4. 限界と補正（Critique & Adaptation）

#### (1) 一階述語論理（FO）の表現力の壁と Datalog / `WITH RECURSIVE` による補正

Codd の定理によって、関係代数と安全な関係論理はどちらも **一階述語論理（First-Order Logic：FO）** と表現力が一致します。これは、[8-2節](8-2.md)で触れた表現力の限界が「関係代数の記法のせい」ではなく、**一階述語論理そのものの数学的限界**であることを意味します。

* **グラフの到達性（推移閉包：Transitive Closure）が書けない：** 親子関係 `Parent(p, c)` から「Alice のすべての子孫（深さ無制限）」を求める問合せや、路線図 `Edge(u, v)` から「東京駅から横浜駅へ乗換回数無制限で到達可能か」は、どのような安全な TRC / DRC 式でも表現できません（有限モデル理論の Ehrenfeucht-Fraïssé ゲームや局所性定理で厳密に証明されています）。
* **集合の大きさの偶奇性や集計が書けない：** 「テーブルの行数が偶数か奇数か」や「平均値・合計値」も純粋な一階述語論理では記述できません。

この限界に対する理論・実務の両面からの補正が、次の2つです。

1. **Datalog（データログ）：** DRC の記法に**再帰ルール**を導入した論理プログラミング型問合せ言語です。たとえば到達性 `Reach(x, y)` は次のわずか 2 行の宣言的ルールで簡潔に書けます。
    ```prolog
    Reach(x, y) :- Edge(x, y).
    Reach(x, y) :- Edge(x, z), Reach(z, y).
    ```
    （※最小不動点へ収束するまでボトムアップに計算するため必ず有限回で停止します。）

2. **SQL の拡張（`GROUP BY` と `WITH RECURSIVE`）：** 現代の標準 SQL（SQL:1999 以降）は、集計関数と、まさに Datalog の再帰ルールに相当する **再帰共通テーブル式（`WITH RECURSIVE`：[8-6節](8-6.md)）** を導入することで、推移閉包や階層ツリー探索まで完全に扱えるようになっています。

#### (2) 関係論理は「そのままでは実行できない」（関係代数への翻訳の必然性）

関係論理は人間が要求（What）を正確に定義するには理想的ですが、**「どのテーブルを先に読み、どの順番で結合するか」という実行手順を一切含まない**ため、そのままでは CPU やディスク上で実行できません。また、一般の任意の論理式がドメイン独立（安全）であるかどうかを自動判定する問題自体は、実は**決定不能（Undecidable）**であることが知られています。

そのため実用 DBMS では、① SQL の構文自体に `FROM` 句で必ず有限のテーブル範囲を明示させることで安全性を構文レベルで保証し、② パーサが受け取った宣言的な SQL（TRC 系）を内部で **関係代数木（[8-2節](8-2.md)）へ自動変換** し、③ [9-4節](../9/9-4.md)の問合せ最適化器がコスト最小の実行手順（How）を選び出して実行する、という 2 段階パイプラインをとっています。
