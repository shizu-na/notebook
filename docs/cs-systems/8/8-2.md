### 前節（8-1）の確認問題の解答

前節の最後に提示した3つの問いの解答を確認します。問3がそのまま本節（リレーショナルデータモデルと関係代数）の導入になります。

1. **ANSI/SPARC 3 層スキーマと 2 つのデータ独立性：**

    * **(a) `dept` 列へ $\text{B}^+$ 木インデックスを追加し、ディスク上の格納順序を変更した場合：**

        * 性質：**物理データ独立性（Physical Data Independence）**
        * 変更された層：**内部スキーマ（物理層）**

    * **(b) `Students` テーブルへ `email` 列を追加したが、図書館システム向けのビュー定義を維持した場合：**

        * 性質：**論理データ独立性（Logical Data Independence）**
        * 変更された層：**概念スキーマ（論理層）**

2. **階層型・ネットワーク型から関係データモデルへの転換点：**
    先行する階層型やネットワーク型では、レコード同士を**物理ポインタ**で結び、プログラマがポインタを1本ずつ辿る手続き（How）を手書きする必要があったため、物理構造の変更に非常に弱いという欠点がありました。これに対し関係データモデルは、物理ポインタを完全に追放してデータを2次元の表（集合）へ統一し、表同士の関連を共通の**値（主キー・外部キー）**だけで論理的に結びつけます。その結果、利用者は「何が欲しいか（What）」だけを**宣言的**に記述すればよく、最適なアクセス手順（How）の決定を DBMS の最適化器へ任せられるようになりました。

3. **2次元の「表」を数学的な集合としてどう厳密に定義し、どう演算するか（本節への接続）：**
    関係データモデルでは、表（関係）を各属性の定義域（ドメイン）の直積の部分集合として厳密に定義し、**主キー**と**外部キー**で整合性を守ります。さらに、表を受け取って新しい表を返す閉じた演算体系である **関係代数（選択 $\sigma$・射影 $\pi$・結合 $\bowtie$ 等）** によって、複雑な検索や結合を数式のように厳密に記述・変形できます。

## 8-2. リレーショナルデータモデルと関係代数

### 1. 動機（Why）：なぜ「ただの表計算ソフト」ではなく、集合論に基づく厳密な「関係」と「代数」が必要なのか

前節（[8-1節](8-1.md)）では、物理ポインタを排除してデータを2次元の表だけで扱う **関係データモデル** が、データ独立性と宣言的問合せを実現する鍵であることを確認しました。

ここで素朴な疑問が湧きます。「2次元の表にデータを並べるだけなら、表計算ソフト（Excel 等）のシートと何が違うのか？」

決定的な違いは、関係データモデルが **離散数学の集合論（Set Theory）** の上に厳密に構築されている点にあります。表計算ソフトのセルは「3行目のB列」といった位置に依存し、同じ行を重複して書いたり、1つのセルにカンマ区切りで複数データを詰め込んだりしてもエラーになりません。しかし、何億件もの業務データを安全かつ自動で高速検索するには、次の **2つの数学的な土台** が不可欠です。

1. **データの構造と整合性の厳密定義（関係モデル）：**
    「行の順番は意味を持たない」「同じ行の重複を許さない」「各行を一意に識別するキー（**主キー**）と、別テーブルとの参照の整合性を守る制約（**外部キー**）を強制する」という厳格な枠組みによって、データの矛盾を未然に防ぎます。

2. **表を操作する閉じた演算体系（関係代数）：**
    「1つまたは2つの関係（表）を入力として受け取り、必ず新しい1つの関係（表）を返す」という**閉包性（Closure Property）**を持つ演算群を定義します。整数どうしの足し算・掛け算が常に整数を返し、$(a + b) \times c = a \times c + b \times c$ のような代数的変形ができるのと同様に、**関係代数**によって複雑な検索を演算の組み合わせ（木構造）で表現でき、さらに後述する DBMS の問合せ最適化器（[9-4節](../9/9-4.md)）が「結果を一切変えずに100倍速い計算順序へ自動変形する」ための数学的根拠が手に入ります。

本節では、関係データモデルの厳密な定義とキー制約を押さえたうえで、関係代数の基本演算・派生演算を手計算と図解で体系的に整理します。

---

### 2. 具体例と動作イメージ（Toy Model）

形式的な定義に入る前に、小さな大学の2つの表を題材に、関係代数の直感的な動きを確かめます。

#### 実験A：2つの表 `Students` と `Depts` から「工学部系（建物 A）の学生の名前」を取り出す

次の2つの関係（表）があるとします。

**関係 `Students(sid, name, dept_id)`：**

| `sid` | `name` | `dept_id` |
| :---: | :--- | :---: |
| `101` | Alice | `CS` |
| `102` | Bob | `EE` |
| `103` | Carol | `CS` |
| `104` | Dave | `ME` |

**関係 `Depts(dept_id, bldg)`：**

| `dept_id` | `bldg` |
| :---: | :---: |
| `CS` | `Bldg-A` |
| `EE` | `Bldg-A` |
| `ME` | `Bldg-B` |

ここから **「建物が `Bldg-A` にある学科の学生の `name` だけ」** を求めたいとき、関係代数では次の3つの基本操作を数珠つなぎ（合成）にして 1 本の式で書けます。

1. **結合（$\bowtie$）：** `Students` と `Depts` を共通の属性 `dept_id` の値が一致する行どうしで横に繋ぐ $\implies$ `(101, Alice, CS, Bldg-A)`, `(102, Bob, EE, Bldg-A)`, `(103, Carol, CS, Bldg-A)`, `(104, Dave, ME, Bldg-B)`。
2. **選択（$\sigma$）：** 繋いだ表から、条件 `bldg = 'Bldg-A'` を満たす**行だけ**を抜き出す $\implies$ `Dave` の行が落ち、3行が残る。
3. **射影（$\pi$）：** 残った3行から、`name` **列だけ**を切り出す $\implies$ `{(Alice), (Bob), (Carol)}`（1列3行の新しい関係が完成）。

これを関係代数の式 1 行で書くと、

$$
\pi_{\text{name}}\Bigl(\sigma_{\text{bldg}=\text{'Bldg-A'}}\bigl(\text{Students} \bowtie \text{Depts}\bigr)\Bigr)
$$

となります。各演算の出力が必ず「関係（表）」であるため、関数の合成のように何重にも入れ子にして複雑な問合せを組み立てられるのです。

### 3. 構造・アルゴリズム・実装（What）

#### (1) リレーショナルデータモデルの数学的定義と用語の対応

E. F. Codd の関係データモデルでは、日常語の「表・行・列」を集合論の言葉で次のように厳密定義します（図8-2-1）。

* **ドメイン（Domain：定義域 $D_i$）：** 属性が取り得る原子的な値（それ以上分割しない単一の値：[8-4節](8-4.md)の**第1正規形［1NF］**の前提）の集合です（例：整数型 `INT`、文字列型 `VARCHAR`、学科コード集合 `{'CS', 'EE', 'ME'}`）。
* **関係スキーマ（Relation Schema）：** 関係名 $R$ と、$n$ 個の属性名（Attribute）およびそのドメインの組 $R(A_1: D_1, A_2: D_2, \dots, A_n: D_n)$ です。属性の個数 $n$ を **次数（Degree / Arity）** と呼びます。
* **関係（Relation / インスタンス $r$）：** 各ドメインの直積（カルテシアン積）の部分集合です。

    $$r \subseteq D_1 \times D_2 \times \dots \times D_n$$

* **タプル（Tuple）：** 関係 $r$ に含まれる1つの要素（行）です。タプルの総数 $|r|$ を **濃度（Cardinality）** と呼びます。

関係は数学的な **集合（Set）** であるため、次の **2つの重要な性質** が自動的に成り立ちます。

1. **タプル（行）の順序は問わない：** `{t1, t2}` と `{t2, t1}` は同じ関係です。
2. **重複するタプル（完全に同じ行）は存在しない：** 集合なので同一の要素は高々1つしか含まれません。

| 数学的用語（関係モデル） | 実務・SQL での呼び方 | 実験Aの例（`Students`） |
| :--- | :--- | :--- |
| **関係（Relation）** | テーブル（表） | `Students` |
| **タプル（Tuple）** | 行（Row）／レコード | `(101, 'Alice', 'CS')` |
| **属性（Attribute）** | 列（Column）／フィールド | `sid`, `name`, `dept_id` |
| **ドメイン（Domain）** | データ型・値域 | `INT`, `VARCHAR` |
| **次数（Degree）** / **濃度（Cardinality）** | 列数 / 行数 | 次数 $3$ / 濃度 $4$ |

#### (2) キーの階層（スーパーキー・候補キー・主キー・外部キー）と 3 大整合性制約

関係の中の各タプルを一意に識別し、複数の関係どうしの矛盾を防ぐために、次の **キー（Key）** と **整合性制約（Integrity Constraints）** を定義します（図8-2-1）。

1. **スーパーキー（Superkey）：** その属性集合の値が決まれば、関係内のタプルを必ず一意に特定できる属性集合 $K$ です（例：`{sid}`、`{sid, name}`、`{sid, name, dept_id}` はすべてスーパーキーです）。
2. **候補キー（Candidate Key）：** スーパーキーのうち、**極小なもの**（どの属性を1個でも取り除くと一意性が失われる最小のスーパーキー）です。たとえば学生に学籍番号 `sid` とマイナンバー `ssn` があれば、`{sid}` と `{ssn}` の両方が候補キーになります。
3. **主キー（Primary Key：PK）：** 複数の候補キーの中から、設計者がテーブルの代表識別子として **1つだけ選んだキー** です（慣例で属性名に下線 $\underline{\text{sid}}$ を引きます）。残りの候補キーを代理キー（Alternate Key）と呼びます。
4. **外部キー（Foreign Key：FK）：** ある関係 $R_1$ の属性集合が、別の関係 $R_2$ の主キー（または候補キー）を参照するとき、その $R_1$ 側の属性集合を外部キーと呼びます（例：`Students.dept_id` は `Depts.dept_id` を参照する外部キーです）。

DBMS はデータ更新（`INSERT` / `UPDATE` / `DELETE`）のたびに、次の **3大整合性制約** が破られていないかを自動検査します。

* **ドメイン制約：** 各属性の値は必ず定義されたドメイン（型・`CHECK` 制約）に属さなければなりません。
* **実体整合性制約（Entity Integrity）：** **主キーを構成するどの属性も `NULL`（値なし）であってはならず**、かつ値が重複してはなりません。
* **参照整合性制約（Referential Integrity）：** 外部キーの値は、参照先テーブルの主キー（または候補キー）に**実在する値**であるか、あるいは `NULL` でなければなりません（存在しない学科 `dept_id = 'XX'` を持つ学生タプルは登録できません）。参照先の親行が削除されたときの挙動は、`RESTRICT`（削除拒否）、`CASCADE`（子行も連鎖削除）、`SET NULL`（外部キーを `NULL` へ変更）から選択します。

#### (3) 関係代数の 5 つの独立基本演算（Codd の基本演算）

**関係代数（Relational Algebra）** は、関係（表）から新しい関係（表）を生成するための**手続き的な**（どの順番でどの演算を適用するかを明示する）演算体系です。実は、あらゆる標準的な関係代数演算は、次の **たった 5 つの独立な基本演算**（＋名前変更 $\rho$）だけで表現できます（図8-2-2）。

1. **選択（Selection：$\sigma_P(R)$）［単項演算・行の絞り込み］：**
    関係 $R$ の中から、条件述語 $P$（比較 $=, \neq, <, \le, >, \ge$ と論理結合 $\land, \lor, \neg$）を満たす**タプル（行）だけ**を抽出します。出力の次数（列数）は $R$ と同じで、濃度は $|R|$ 以下です。

2. **射影（Projection：$\pi_{A_1, \dots, A_k}(R)$）［単項演算・列の絞り込み］：**
    関係 $R$ から指定した**属性（列）だけ**を切り出します。関係は集合なので、列を削った結果として**同じ行が生じた場合は自動的に重複排除**されます（例：$\pi_{\text{dept\_id}}(\text{Students}) = \{(\text{CS}), (\text{EE}), (\text{ME})\}$ の 3 行になります）。

3. **和（Union：$R \cup S$）［二項演算］：**
    $R$ または $S$ の少なくとも一方に属するタプル全体の集合です。ただし $R$ と $S$ は **和両立（Union-Compatible：次数が等しく、対応する各列のドメインが同じ）** でなければなりません。

4. **差（Set Difference：$R - S$）［二項演算］：**
    和両立な $R, S$ に対し、$R$ には属するが $S$ には属さないタプル全体の集合です。

5. **直積（Cartesian Product：$R \times S$）［二項演算］：**
    $R$ のすべてのタプルと $S$ のすべてのタプルの**あらゆる組み合わせ**を横に連結します。次数は $\text{deg}(R) + \text{deg}(S)$、濃度は $|R| \times |S|$ になります。

* **（補助）名前変更（Rename：$\rho_{S(B_1, \dots, B_n)}(R)$）：** 関係名や属性名を変更します。同じ表を自分自身と結合（自己結合）する際の名前の衝突を避けるために用います。

#### (4) 実務で頻出する派生演算（積・結合・外部結合・商）

上の 5 つの基本演算を組み合わせることで、表現力が増すわけではないものの、問合せを簡潔に書ける **派生演算（Derived Operators）** が定義されます（図8-2-2）。

1. **積（Intersection：$R \cap S$）：**
    $R$ と $S$ の両方に属するタプル集合です。差演算だけで等価に表せます。

    $$R \cap S \;=\; R - (R - S)$$

2. **$\theta$-結合（Theta Join：$R \bowtie_{\theta} S$）：**
    直積をとったあと条件 $\theta$ で選択する操作の省略形です。特に条件が等号（$=$）のみのものを **等結合（Equijoin）** と呼びます。

    $$R \bowtie_{\theta} S \;=\; \sigma_{\theta}(R \times S)$$

    結合は定義上、最悪で $|R| \times |S|$ 組を調べる直積の絞り込みにあたるため、関係代数の中でも計算コストが高くなりやすい演算です（実際の DBMS では索引・ハッシュ・ソート結合で高速化します：[9-3節](../9/9-3.md)）。

3. **自然結合（Natural Join：$R \bowtie S$）：**
    $R$ と $S$ のあいだで**同じ名前の共通属性すべてについて値が等しいタプル同士を結合**し、重複した共通属性列を1つにまとめる演算です（実験Aで使用しました）。共通属性が1つもない場合は直積 $R \times S$ と一致します。

4. **外部結合（Outer Join：左 ⟕・右 ⟖・完全 ⟗）：**
    通常の結合（内部結合）では、相手側に一致する行が存在しないタプルは結果から消えてしまいます。たとえば「まだ 1 人も学生が所属していない新設学科 `AI`」も結果へ残したいとき、一致相手がない行の不足列を **`NULL`** で埋めて残すのが外部結合です。

    * **左外部結合（Left Outer Join）：** 左表の全タプルを必ず残します。
    * **右外部結合（Right Outer Join）：** 右表の全タプルを必ず残します。
    * **完全外部結合（Full Outer Join）：** 左右両表の全タプルを必ず残します。

5. **商（Division：$R \div S$）：**
    「**$S$ のすべての要素と関連を持つ $R$ の要素（全称量化 $\forall$）**」を求める演算です。たとえば `Enroll(sid, cid)` と全必修科目表 `Required(cid)` があるとき、`Enroll` $\div$ `Required` は「必修科目を**すべて**履修している学生の `sid`」を返します。

> **【コラム：なぜ商演算（$\div$）は基本5演算だけで書けるのか（二重否定のトリック）】**
>
> 「必修科目 `Required(cid)` を **すべて** 履修している学生 `sid` を求めよ」という商演算 `Enroll(sid, cid) ÷ Required(cid)` は、一見すると $\sigma, \pi, \cup, -, \times$ の基本5演算だけでは書けなさそうに見えます。
>
> しかし、論理学の **二重否定「すべての必修を履修している $\iff$ 履修していない必修が 1 つも存在しない」** を使うと、次の 3 ステップ（差と直積と射影だけ）で厳密に表現できます。
>
> 1. **すべての理想ペアを作る：** 全学生 $\pi_{\text{sid}}(\text{Enroll})$ と全必修 $\text{Required}$ の直積 $\pi_{\text{sid}}(\text{Enroll}) \times \text{Required}$ を作ります。
> 2. **未履修ペアだけを残す（差演算 1 回目）：** 上の理想ペアから、実際の履修表 `Enroll` を引き算すると、「その学生が**まだ履修していない**必修科目」のペアだけが残ります。
> 3. **未履修が 1 つでもある学生を全員から引く（差演算 2 回目）：** 全学生から「未履修ペアに名前が出た学生」を引き算すれば、残った学生こそが**全必修を履修済みの学生**です。
>
> $$R(X, Y) \div S(Y) \;=\; \pi_X(R) \;-\; \pi_X\Bigl(\bigl(\pi_X(R) \times S\bigr) - R\Bigr)$$
>
> 実際の SQL には商演算子が存在しないため、まさにこの二重否定を `NOT EXISTS ( ... NOT EXISTS ... )` として書き下すのが定番のテクニックです。

#### (5) 関係代数木と等価変換（第9部・問合せ最適化への入口）

関係代数が「単なる理論記号」ではなく商用 RDBMS の心臓部として使われている理由は、**等価変換（同じ結果を保ったまま演算順序を入れ替える代数法則）** が成り立つためです（図8-2-3）。

実験Aの問合せ $\pi_{\text{name}}\bigl(\sigma_{\text{bldg}=\text{'Bldg-A'}}(\text{Students} \bowtie \text{Depts})\bigr)$ を考えてみます。もし `Students` が **100 万行**、`Depts` が **100 行**（そのうち `Bldg-A` は 2 学科だけ）だとします。

* **素朴な手順（結合してから選択）：** まず 100 万行と 100 行を結合して 100 万行の中間表を作り、その後で `bldg = 'Bldg-A'` に絞り込みます。
* **等価変換後（選択を結合の下へ押し下げる：Selection Pushdown）：**
    条件 `bldg = 'Bldg-A'` は `Depts` の属性だけを参照しているため、結合より先に `Depts` へ適用しても数学的に結果は完全に一致します。

    $$\pi_{\text{name}}\Bigl(\text{Students} \bowtie \sigma_{\text{bldg}=\text{'Bldg-A'}}(\text{Depts})\Bigr)$$

    まず `Depts` を 100 行から **たった 2 行** へ絞り込んでから `Students` と結合できるため、中間データ量とディスク I/O が大幅に削減されます。

### 4. 限界と補正（Critique & Adaptation）

純粋な数学モデルとしての関係データモデル・関係代数と、実際の商用 RDBMS（SQL）のあいだには、実務上の性能と表現力に由来する **3つの重要なギャップと補正** が存在します。

#### (1) 集合（Set）モデル vs 実務 SQL の多重集合（Bag / Multiset）モデル

数学の関係代数では、射影 $\pi_{\text{dept\_id}}(\text{Students})$ を実行すると**自動的に重複行が削除**されます。しかし、もし 1 億行のテーブルに対して `SELECT dept_id FROM Students` を実行するたびに DBMS が毎回全件ソートやハッシュ構築で重複排除を行っていたら、莫大な CPU とディスク I/O を浪費してしまいます。

* **補正：** 現実の SQL は、純粋な集合ではなく重複を許容する **多重集合（Bag / Multiset）** をデフォルトに採用しています。`SELECT` は重複をそのまま残して高速に出力し、重複排除が必要なときだけ利用者が明示的に **`SELECT DISTINCT`** や `UNION`（重複を残すなら `UNION ALL`）を指定する設計になっています。

#### (2) `NULL` と 3 値論理（Three-Valued Logic）の注意点

関係モデルの純粋な世界では各属性に必ず値が入っていますが、現実の業務データには「まだ未定」「不明」「該当なし」を表す特別な印 **`NULL`** が不可避です（外部結合でも `NULL` が生まれます）。

`NULL` を含む比較式（例：`age = 20` や `NULL = NULL`）は、真（`TRUE`）でも偽（`FALSE`）でもない第3の真理値 **`UNKNOWN`（不明）** を返します（**3 値論理**）。さらに SQL の **`WHERE` 句は評価結果が厳密に `TRUE` になった行だけを出力し、`FALSE` と `UNKNOWN` の行はいずれも除外する** 仕様になっているため、通常の2値論理の常識が崩れます。

* `WHERE age = 20 OR age != 20` と書いても、`age` が `NULL` の行は `UNKNOWN OR UNKNOWN = UNKNOWN` と評価され、`TRUE` にならないため**結果から抜け落ちます**（排中律の崩壊）。
* **補正：** `NULL` の判定には `=` ではなく専用の **`IS NULL` / `IS NOT NULL`** を必ず使い、さらにスキーマ設計段階では不要な `NULL` を許さない **`NOT NULL` 制約** を積極的に付与します。

#### (3) 標準関係代数の表現力の限界（集計・ソート・推移閉包）

Codd の標準的な関係代数（基本5演算）は強力ですが、実務で不可欠な次の3つは標準関係代数だけでは表現できません。

1. **集計とグルーピング：** 「学科ごとの平均点や人数（`SUM`, `AVG`, `COUNT`）」の計算は表現できません。
2. **並べ替え：** 集合に順序はないため、点数順のソート（`ORDER BY`）は表現できません。
3. **再帰問合せ（推移閉包：Transitive Closure）：** たとえば `Parent(parent, child)` という親子関係テーブルから「Alice の**すべての子孫**（深さが何代になるか事前に不明なグラフ到達性）」を求める操作は、有限個の結合 $\bowtie$ の組み合わせでは原理的に書けないことが数学的に証明されています。

* **補正：** これらに対応するため、現代の DBMS では **拡張関係代数**（グルーピング・集計演算 $\gamma$、ソート演算 $\tau$、重複排除 $\delta$）を内部に持ち、SQL では `GROUP BY`・`ORDER BY`、そして [8-6節](8-6.md)で扱う **再帰共通テーブル式（`WITH RECURSIVE`）** を標準機能として備えています。
