### 前節（8-6）の確認問題の解答

前節の最後に提示した3つの問いの解答を確認します。問3がそのまま本節（OLAP と RDB の拡張・グラフ DB）の導入になります。

1. **ER 図からリレーショナルテーブルへの変換（顧客 `Customer`・注文 `Order`・商品 `Product`）：**

    * 強い実体3つをそのままテーブルにし、`1 : N` の関連（顧客 $\to$ 注文）は多側（`Order`）へ `cid` を外部キーとして入れ、`M : N` の関連（注文 $\leftrightarrow$ 商品、属性 `qty`）は独立した中間テーブル `OrderItem` を新設します。
    * **`Customer`**(`PK: cid`, `name`)
    * **`Order`**(`PK: oid`, `order_date`, `FK: cid` $\to$ `Customer.cid`)
    * **`Product`**(`PK: pid`, `pname`, `price`)
    * **`OrderItem`**(`PK/FK: oid` $\to$ `Order.oid`, `PK/FK: pid` $\to$ `Product.pid`, `qty`)

2. **SQL の論理評価順序とビュー更新の制約：**

    * **(a) `WHERE` 句と `HAVING` 句の決定的な違い：**
        論理評価順序において、**`WHERE` は `GROUP BY` より前**に実行されて「個別の行」を絞り込むのに対し、**`HAVING` は `GROUP BY` より後**に実行されて「グループ化された集計結果（`COUNT(*) >= 10` 等）」を絞り込みます。そのため `WHERE` 句の中では集約関数を使えません。

    * **(b) `GROUP BY` や `JOIN` を含むビューへの直接更新が禁止される理由：**
        ビュー上の 1 行に対する `UPDATE` や `DELETE` を、「元の基底表のどの行をどう書き換えるべきか」へ**数学的に一意に逆写像（翻訳）できない**（あるいは結合表の片側を書き換えることで無関係な他の行まで波及して矛盾する）ためです。

3. **日常業務の更新（OLTP）とは異なる「経営分析（OLAP）」と「グラフ探索」（本節への接続）：**
    3NF / BCNF に正規化されたテーブルと行指向ストレージは日々の注文処理（OLTP）には最適ですが、数億件の過去データから特定列だけを集計する経営分析（**OLAP**）では、意図的に非正規化した **スタースキーマ**・**多次元データキューブ**・**列指向ストレージ** が高い性能を発揮します。また、SNS のような多段ホップの関係探索には **グラフデータベース**、複雑なデータ型には **ORDB（オブジェクト関係 DB）** という拡張が進化してきました。

## 8-7. OLAP（スタースキーマ・データキューブ）と RDB の拡張（ORDB・グラフ DB）

### 1. 動機（Why）：なぜ 3NF / BCNF の RDB だけでは「大規模分析」と「多段グラフ探索」が苦しいのか

[8-1節](8-1.md)から [8-6節](8-6.md)まで、私たちは「データの重複をなくし、更新時異常を防ぎ、宣言的言語 SQL で正確に操作する」という関係データベースの基礎理論を積み上げてきました。銀行の振込処理や EC サイトの注文登録のように、**少数の行を毎秒何千〜何万回も高頻度で読み書きする日常業務（OLTP：Online Transaction Processing）** において、BCNF / 3NF の RDB は強力な基盤です。

ところが、現実のシステムでは OLTP とは正反対の性質を持つ **2つの巨大なワークロード** が現れます。

1. **大量データの多次元経営分析（OLAP：Online Analytical Processing）：**
    「過去 5 年間の全店舗の売上 10 億件から、東日本エリアにおける電子機器カテゴリの月別売上合計と前年比を出せ」という分析クエリを考えます。

    * ここで読むのは「特定の 1 行」ではなく「**10 億行のうちのたった 3 列（日付・カテゴリ・金額）**」です。
    * もし OLTP 用の BCNF テーブル群の上でそのまま実行すると、① 毎回 6〜8 枚のテーブルを結合（`JOIN`）する重いコストがかかり、② 全列が横に並んだ行データから不要な 20 列まで丸ごとディスクから読み込んでしまい、③ さらに分析クエリがディスク I/O とロックを占有して**肝心の注文処理（OLTP）が止まってしまいます**。

2. **深い多段ホップのグラフ探索と非構造・複合データ：**

    * SNS で「Alice の友達の友達の友達（4 ホップ先）のうち、同じ映画を好む人」を探したり、金融の不正送金リングを検知したりするとき、RDB で中間テーブル `Follows(from_id, to_id)` を 4 回自己結合（`JOIN`）すると、ホップ数が増えるにつれて中間結果とインデックス探索コストが爆発します。
    * また、地理空間データ（緯度経度・ポリゴン）、入れ子の JSON、AI の高次元埋め込みベクトルなど、単純な 1NF の数値・文字列だけでは扱いにくいデータも急増しています。

本節では、[第8部](../index.md#part-8)の締めくくりとして、分析系データベースの設計論である **OLAP（スタースキーマ・データキューブ・列指向ストレージ）** を整理したうえで、RDB 自身の進化である **ORDB（オブジェクト関係 DB）** と、関係探索に特化した **グラフデータベース** の内部構造までを対比します。

### 2. 具体例と動作イメージ（Toy Model）

体系的な分類に入る前に、2つの小さな具体例で「スタースキーマの明快さ」と「RDB 結合 vs グラフ DB 探索のコスト差」を体感します。

#### 実験A：売上 1 億件を「時間 × 商品 × 店舗」の 3 軸で切り刻む（スタースキーマ）

全国に展開する小売チェーンの分析用データベース（**データウェアハウス：DWH**）を設計します。

* 中央に、日々の売上明細 1 億行が並ぶ **ファクトテーブル `SalesFact(date_id, prod_id, store_id, qty, amount)`** を置きます。ここには集計対象となる数値（**メジャー**：`qty`, `amount`）と、各分析軸への外部キーだけを入れます。
* その周囲を、分析の切り口となる 3 つの **ディメンションテーブル** で星型に囲みます。

    * **`DimDate(date_id, year, quarter, month, day_of_week)`**
    * **`DimProduct(prod_id, prod_name, category, brand)`**
    * **`DimStore(store_id, store_name, city, region)`**

注目すべきは、`DimStore` の中に `store_id → city → region` という **3NF 違反の推移関数従属をあえて残している（意図的な非正規化：[8-5節](8-5.md)）** 点です。店舗マスタはせいぜい数千行しかなく更新も稀なため、あえて 1 枚にまとめておくことで、「地域別売上」を出すときの `JOIN` を `SalesFact ⋈ DimStore` の **たった 1 回** で完結させられるのです。

#### 実験B：SNS で 4 ホップ先の友人を辿る（RDB の索引探索 vs グラフ DB の直接ポインタ）

1,000 万人のユーザと平均 100 人のフォロー関係（計 10 億エッジ）がある SNS で、あるユーザから **4 ホップ先** の友人集合を辿るとします。

* **RDB（`Follows(src, dst)` の $\text{B}^+$ 木索引）：**
    1 人のフォロー先を引くたびに、10 億エッジ（$|E| = 10^9$）を収めた巨大なグローバル索引木（高さ $O(\log |E|)$）を根から葉まで毎回辿る必要があります。平均次数 100 の場合、重複を省かない素朴な探索では 4 ホップ目の展開だけで最大 $100^3 = 100$ 万回（1〜4 ホップ合計で約 101 万回）もの索引木探索とランダム I/O が発生します。

* **グラフ DB（インデックスフリー隣接：Index-Free Adjacency）：**
    各ユーザノードの物理メモリ／ディスク構造の中に、**隣接するエッジへの直接ポインタ（物理参照）** をあらかじめ持たせておきます。最初の 1 人だけ索引で見つければ、あとは「次のノードへポインタを 1 発辿る」だけの **$O(1)$ の局所ホップ** を繰り返せばよく、グラフ全体の総ユーザ数が 1,000 万人でも 10 億人でも、1 ホップあたりのコストが全体サイズ $N$ に一切依存しません。

### 3. 構造・アルゴリズム・実装（What）

#### (1) OLTP vs OLAP の徹底対比とデータウェアハウス（ETL / ELT）

日常業務のデータベース（OLTP）と、経営分析用のデータウェアハウス（OLAP）は、同じ「データベース」という名前でも最適化の方向性が 180 度異なります。

| 比較項目 | OLTP（オンライン処理） | OLAP（オンライン分析処理） |
| :--- | :--- | :--- |
| **主な目的** | 注文・決済・在庫更新などの日常業務 | 傾向分析・経営意思決定・レポート集計 |
| **典型的なクエリ** | 単純な 1〜数行の `SELECT` / `INSERT` / `UPDATE` | 数百万〜数十億行を走査する複雑な `SUM` / `AVG` / `GROUP BY` |
| **正規化レベル** | **3NF / BCNF**（更新時異常の徹底排除） | **意図的な非正規化**（スタースキーマ等、`JOIN` 削減） |
| **データ鮮度・範囲** | 最新の現在状態（ミリ秒単位の整合性・ACID 必須） | 過去数年〜数十年分の履歴スナップショット（追記中心） |
| **ストレージ物理配置** | **行指向（Row-oriented）**（1 行の挿入・更新が高速） | **列指向（Column-oriented）**（特定列の大量集計・圧縮が高速） |
| **代表システム** | PostgreSQL, MySQL, Oracle, SQL Server | BigQuery, Snowflake, Redshift, ClickHouse, DuckDB |

実務では、OLTP データベースへ負荷をかけないよう、OLTP から分析用データウェアハウス（DWH）へデータを複製・変換して取り込む **ETL（Extract → Transform → Load）** または **ELT（Extract → Load → Transform）** パイプラインを構築して両者を分離運用します。

#### (2) スタースキーマ（Star Schema）とスノーフレークスキーマ（Snowflake Schema）

データウェアハウスにおける多次元スキーマ設計の 2 大パターンを比較します（図8-7-1）。

1. **スタースキーマ（Star Schema：標準）：**

    * 中央の **ファクトテーブル**（巨大・細長い：外部キー群＋数値メジャーのみ）と、周囲の **ディメンションテーブル**（小規模・幅広：2NF 相当へ意図的に非正規化された階層属性）で構成されます。
    * **長所：** SQL がシンプルになり、`JOIN` の段数が常に 1 ホップ（ファクト $\bowtie$ 各ディメンション）で済むためクエリが非常に高速です。

2. **スノーフレークスキーマ（Snowflake Schema）：**

    * スタースキーマのディメンションテーブルをさらに 3NF へ正規化し、`DimProduct → DimCategory → DimDepartment` のように雪の結晶状に枝分かれさせたスキーマです。
    * **トレードオフ：** ディメンション側の重複は減りますが、分析クエリごとに追加の `JOIN` が増えるため、現代の高速な列指向ストレージ環境では、ストレージ節約より読み取り速度と単純さを優先して **スタースキーマ（あるいは 1 枚へ完全展開したワイドテーブル）** が好まれます。

#### (3) 多次元データキューブ（Data Cube）と OLAP 操作・SQL 拡張

スタースキーマのファクトデータを、各ディメンション（時間・商品・地域など）を座標軸とする多次元の直方体として捉えた概念モデルが **データキューブ（Data Cube）** です（図8-7-2）。各セルの中に売上金額などの集計値が入ります。また、$d$ 個の軸それぞれについて「個別値で分ける」か「全合計（`ALL`）へまとめる」かを選んだ全 $2^d$ 通りの集計粒度は、集約の包含関係に基づく **束（ラティス：Lattice）構造** を成します。

分析者はこのキューブに対して、次の代表的な **OLAP 操作** を対話的に行います。

* **ロールアップ（Roll-up）：** 粒度を粗くして上位階層へまとめる操作です（例：「日別 → 月別 → 年別」や「店舗別 → 地域別 → 全国合計」へ集計を上げます）。
* **ドリルダウン（Drill-down）：** ロールアップの逆で、全体を細かい粒度へ掘り下げる操作です（例：「2026 年全体 → Q1〜Q4 → 1 月〜12 月」へ展開します）。
* **スライス（Slice）：** 特定の 1 次元の値を 1 つに固定し、キューブを薄く切り出す操作です（例：`year = 2026` だけに固定した 2 次元の「商品 × 地域」表）。
* **ダイス（Dice）：** 複数の次元でそれぞれ部分範囲を指定し、小さな部分キューブを切り出す操作です（例：`year IN (2025, 2026)` かつ `region IN ('関東', '関西')`）。
* **ピボット（Pivot）：** 行と列の表示軸を入れ替えてクロス集計表の視点を回転させる操作です。

現代の SQL には、これらの小計・総計を一発で計算する **`ROLLUP`** と **`CUBE`** 拡張が標準で組み込まれています。

```sql
-- ① ROLLUP：階層順の集計（(region, category), (region, ALL), (ALL, ALL) の 3 段階）
SELECT region, category, SUM(amount)
FROM SalesView
GROUP BY ROLLUP(region, category);

-- ② CUBE：全組み合わせ（2^2 = 4 通り：両軸、region別、category別、総計）を一括計算
SELECT region, category, SUM(amount)
FROM SalesView
GROUP BY CUBE(region, category);
```

> **【コラム：行指向 vs 列指向：なぜ分析 DB（BigQuery / Snowflake / DuckDB）は表を「縦」に保存するのか】**
>
> 図8-7-1右に示した通り、伝統的な OLTP 向け RDB（PostgreSQL や MySQL InnoDB）は、1 行の全列を隣り合わせてディスクページへ格納する **行指向（Row-oriented）ストレージ** です。1 件の注文を `INSERT` したり特定ユーザの全プロフィールを読んだりするとき、1 ページだけアクセスすれば済むため OLTP に最適です。
>
> これに対し、現代の分析 DB（BigQuery, Snowflake, ClickHouse, Apache Parquet, DuckDB 等）は例外なく **列指向（Column-oriented）ストレージ** を採用しています。同じ 1 列の値だけを連続させて格納することで、OLAP に対して次の **3 つの大きな高速化** が生まれます。
>
> 1. **ディスク I/O の大幅削減：** 50 列あるテーブルから `SUM(amount)` を求めるとき、必要な `amount` 列のファイルだけを読めばよく、残り 49 列分のディスク読み込みが **ゼロ** になります。
> 2. **高いデータ圧縮率：** 同じ列には同じ型・似た値（例：`region` 列に `"関東"` が 100 万回連続する）が並ぶため、ランレングス符号化（RLE）や辞書圧縮がよく効き、データサイズが 5 分の 1 〜 10 分の 1 に縮みます。
> 3. **CPU キャッシュ効率と SIMD ベクトル化実行：** [0-7節](../0/0-7.md)の空間的局所性が最大化し、連続した数値配列に対して CPU の AVX / NEON といった **SIMD 命令** で 1 クロックあたり 4〜16 個の要素を一括加算できます。

#### (4) RDB の拡張（ORDB）とグラフデータベース（Graph DB）

純粋な 1NF の関係モデルだけでは扱いにくい現代のデータ要件に対し、データベース技術は **「RDB 自身の拡張（ORDB）」** と **「専用モデルへの特化（グラフ DB 等）」** の 2 方向へ発展しました。

1. **ORDB（Object-Relational Database：オブジェクト関係 DB）：**
    リレーショナルモデルの数学的基盤・SQL・ACID トランザクションを維持したまま、データ型と索引の枠組みを拡張したモデルです。代表的な **PostgreSQL** はもともと ORDB として設計されており、次のような拡張を標準または公式拡張で備えています。

    * **ユーザ定義型（UDT）・配列・複合型**
    * **半構造化 JSONB 型：** バイナリ化された JSON を格納し、内部キーへ汎用転置索引（**GIN**）を張って高速検索できます。
    * **地理空間データ（PostGIS）：** 緯度経度の点・ポリゴン型と、空間近傍検索を高速化する **R 木（GiST：汎用探索木）索引**を備えます。
    * **高次元ベクトル（pgvector）：** 生成 AI の埋め込みベクトル同士のコサイン類似度を高速検索する近似最近傍（**HNSW**：階層的近傍グラフ等）索引を備えます。

2. **グラフデータベース（Graph Database：プロパティグラフと RDF）：**
    SNS の人間関係、知識グラフ、レコメンデーション、マネーロンダリング（不正送金リング）検知のように、**「データそのものよりも、データ同士の多段の繋がり（関係性）のパターン」** を主役とする領域では、**プロパティグラフ（Property Graph）** を採用するグラフ DB（Neo4j 等）が威力を発揮します（図8-7-3）。

    * **データモデル：** **ノード（頂点：ラベルと Key-Value プロパティを持つ）** と **エッジ（有向辺：関係種別とプロパティを持つ）** の 2 要素で構成されます。
    * **インデックスフリー隣接（Index-Free Adjacency）：** 実験Bで見た通り、各ノードが隣接エッジへの直接の物理ポインタを保持しているため、1 ホップ辿る計算量がグラフ全体のノード数 $N$ に依存せず、そのノード自身の次数 $d$ だけで済みます（$O(d)$）。
    * **宣言的グラフ問合せ言語（Cypher / ISO 標準 GQL）：** ASCII アートのように視覚的にグラフパターンを書けます。
        ```cypher
        // Alice から 1〜3 ホップのフォロー関係で到達し、同じ都市に住む他人を探す
        MATCH (a:User {name: 'Alice'})-[:FOLLOWS*1..3]->(f:User)
        WHERE f.city = a.city AND f <> a
        RETURN DISTINCT f.name;
        ```

    * **RDF（トリプルストア）と SPARQL：** プロパティグラフと並び、データを「主語・述語・目的語」の 3 つ組（トリプル）として表現する **RDF（Resource Description Framework）** と標準問合せ言語 **SPARQL** も、セマンティック Web やオープンな知識グラフの基盤として広く用いられます。

### 4. 限界と補正（Critique & Adaptation）

#### (1) データキューブの「次元の呪い（組み合わせ爆発）」

$d$ 個のディメンション（軸）を持つデータキューブに対して、すべての集計粒度（`CUBE` の全組み合わせ）を事前に計算して保存（マテリアライズ）しようとすると、必要な集計テーブルの数は **$2^d$ 通り** に膨らみます（さらに各軸に階層［年→月→日等］があると $\prod (L_i + 1)$ 通り）。たとえば $d = 20$ 個の分析軸があるだけで $2^{20} \approx 100\text{ 万通り}$ もの集計表が必要になり、ストレージと更新コストが破綻します（**次元の呪い**）。

**補正：** すべての組み合わせを事前計算せず、アクセス頻度の高い少数の組み合わせだけを選択的にマテリアライズドビューとして保持し、残りのアドホックな切り口は **列指向ストレージ＋分散並列実行＋SIMD ベクトル化** によって生のファクトテーブルから数秒でオンザフライ集計するのが現代のクラウド DWH の主流です。ただし、マテリアライズドビューを増やしすぎると、元テーブル更新時の再計算（リフレッシュ／差分更新）コストと鮮度遅延が重くなるため、事前計算の対象は慎重に選定します。

#### (2) ETL 遅延による鮮度の壁と HTAP（Hybrid Transactional/Analytical Processing）

OLTP と OLAP を別システムへ分離し、毎晩深夜に ETL バッチでデータをコピーする構成は安全ですが、「たった 5 秒前の売上や在庫の変化をリアルタイムでダッシュボード分析したい」という現代の要求には応えられません。

**補正：**

* **CDC（Change Data Capture）：** OLTP データベースの WAL ログ（[9-8節](../9/9-8.md)）から変更イベントだけをリアルタイムに吸い上げ、数秒の遅延で OLAP 側へストリーミング反映します。
* **HTAP（TiDB / AlloyDB 等）：** 1 つのデータベースシステム内部で「更新用の行指向レプリカ」と「分析用の列指向レプリカ」を自動同期して並存させ、トランザクション処理とリアルタイム分析を 1 基盤で両立させるアーキテクチャも実用化されています。

#### (3) グラフ DB の分散スケーリングの壁とポリグロット永続化の運用コスト

グラフ DB の強みである「インデックスフリー隣接（直接ポインタ）」は、グラフ全体が 1 台のマシンのメモリやローカル SSD に収まっている間は非常に高速です。しかし、グラフが数十億ノードへ膨らんで複数台のサーバへ分割（シャーディング）しなければならなくなると、**各サーバへ頂点数を均等に割り当てつつマシン境界を跨ぐ（ネットワーク通信が発生する）エッジ数を最小化する「均衡グラフ分割問題（Balanced Graph Partitioning）」が NP 困難**であるため、結局ホップごとにネットワーク往復遅延が発生して性能優位が急減します。また、RDB・列指向 DWH・グラフ DB・検索エンジンなど複数種のデータストアを用途別に併用する **ポリグロット永続化（Polyglot Persistence）** では、データ同期や整合性・バックアップの運用複雑性が大きく増すため、データ規模・更新頻度・ホップ数を見極めて RDB（ORDB）と専用 DB を使い分ける判断が重要です。

### 理解度チェック（次節・第9部へ進む前の確認）

本節の OLTP vs OLAP・スタースキーマ・列指向ストレージ・グラフ DB の仕組みを確認し、[第9部](../index.md#part-9)（DBMS の内部構造）へ繋ぐ問いを置きます。

> **【確認の問い】**
>
> 1. **（OLTP vs OLAP とスタースキーマ・列指向ストレージ）**
>
>     * (a) 分析系データベース（OLAP）の **スタースキーマ** において、ディメンションテーブルを 3NF へ完全正規化せず、あえて推移関数従属を残した非正規化状態（2NF 相当）にすることが多いのはなぜでしょうか。
>     * (b) 50 列ある 1 億行の売上テーブルに対して `SELECT SUM(amount) FROM SalesFact;` を実行するとき、行指向ストレージに比べて **列指向ストレージ** が大きく高速になる理由を 2 点挙げてください。
>
> 2. **（データキューブ操作とグラフ DB のインデックスフリー隣接）**
>     次の 2 つの問いに簡潔に答えてください。
>
>     * (a) 売上データキューブ（時間 × 商品 × 地域）において、「2026 年のデータだけに固定して 2 次元の表を切り出す操作」と、「日別の売上を月別・年別へと上位階層へまとめて集計する操作」を、OLAP 用語でそれぞれ何と呼ぶでしょうか。
>     * (b) グラフデータベースが採用する **インデックスフリー隣接（Index-Free Adjacency）** により、多段ホップの探索が RDB の多段 `JOIN` に比べて高速になる仕組みを説明してください。
>
> 3. **（[第9部](../index.md#part-9)への伏線：テーブルの「行」は物理ディスクの固定長ページの上へどう並んでいるのか）**
>     [第8部](../index.md#part-8)を通じて、テーブルの論理設計と SQL のすべてが揃いました。では、実際に `INSERT` された可変長の文字列（`VARCHAR` 等）を含むタプル（行）は、DBMS のストレージエンジン内部で **$8\text{ KiB}$ の固定長ディスクページ** の中へどのように配置され、途中の行が削除・更新されたときの断片化を防ぎつつ、RAM 上の **バッファプール** でどうキャッシュ管理されているのでしょうか。
