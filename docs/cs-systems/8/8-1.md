### 前節（7-7）の確認問題の解答

前節の最後に提示した3つの問いの解答を確認します。問3がそのまま[第8部](../index.md#part-8)（関係データモデル・正規化と SQL）の導入になります。

1. **Diffie-Hellman 鍵交換の手計算と前方秘匿性（$p = 11,\; g = 2,\; a = 3,\; b = 4$）：**

    * **(a) 公開値 $A, B$ と共有秘密鍵 $S$：**

        * Alice の公開値：$A = 2^3 \bmod 11 = \mathbf{8}$
        * Bob の公開値：$B = 2^4 \bmod 11 = 16 \bmod 11 = \mathbf{5}$
        * 共有秘密鍵 $S$：

            * Alice の計算：$B^a \bmod 11 = 5^3 \bmod 11 = 125 \bmod 11 = \mathbf{4}$（$11 \times 11 = 121$ より余り $4$）
            * Bob の計算：$A^b \bmod 11 = 8^4 \bmod 11 \equiv (-3)^4 = 81 \bmod 11 = \mathbf{4}$（$11 \times 7 = 77$ より余り $4$）
            よって 2 人が共有する秘密鍵は **$S = 4$** です。

    * **(b) 前方秘匿性（PFS：Perfect Forward Secrecy）の性質：**
        将来サーバの長期秘密鍵が盗まれても、過去の通信セッションで使われた使い捨てのセッション鍵（$g^{ab}$）は復元できないため、攻撃者が過去に録画していた暗号化通信を遡って解読できない性質です。

2. **デジタル署名・PKI と TLS vs IPsec：**

    * **(a) ブラウザによる公開鍵の正当性検証：**
        ブラウザ（OS）にあらかじめ内蔵されている信頼された **ルート CA の公開鍵** を起点に、信頼の連鎖（Chain of Trust）を辿って中間 CA およびサーバの **X.509 証明書に付与されたデジタル署名** を検証し、さらに証明書に記載されたドメイン名（SAN）と有効期限が一致することを確認することで、証明書内の公開鍵が攻撃者の偽物ではないと保証します。

    * **(b) TLS（HTTPS）と IPsec（トンネルモード）の動作層と用途：**

        * **TLS（HTTPS）：** 第 4 層（TCP / QUIC）のすぐ上で動作し、Web ブラウザやメールなど**アプリケーション単位のエンドツーエンド暗号化**に向きます。
        * **IPsec（トンネルモード）：** 第 3 層（IP 層）で動作し、元の IP ヘッダごとパケット全体を暗号化して新しい外部 IP ヘッダで包むため、**本社と支社を結ぶ拠点間 VPN** のようにネットワーク全体の通信をアプリ非依存で透過的に保護する用途に向きます。

3. **データを「ただのファイル」で管理する限界と DBMS（本節への接続）：**
    業務データを手書きの CSV や固定長ファイルで直接管理すると、データの重複による不整合、複数ユーザ同時更新によるデータ破損、停電時の途中書き込み、毎回ファイル全体を読み込む検索の遅さ、さらにデータ形式変更のたびに全プログラムを書き直す手間が噴出します。これらを汎用ソフトウェアとして一手に引き受ける基盤が **DBMS（データベース管理システム）** であり、その論理的な土台が **関係データモデル** です。

## 8-1. ファイルベースの限界とDBMSの役割・データモデル

### 1. 動機（Why）：第5部のファイルシステムがあるのに、なぜさらに「DBMS」が必要なのか

[第0部](../index.md#part-0)から[第7部](../index.md#part-7)までを通じて、1台のコンピュータの内部（ハードウェア・コンパイラ・OS・並行性・ファイルシステム・保護）と、世界中の計算機を安全に結ぶネットワーク（リンク・IP・TCP/QUIC・TLS）の全構造が揃いました。

ここで素朴な疑問が湧きます。「[第5部](../index.md#part-5)で、電源が落ちても壊れないジャーナリング付きのファイルシステム（ext4 等）を手に入れたのだから、銀行の口座残高や EC サイトの在庫、大学の履修登録データも、**ただのテキストファイル（CSV）やバイナリファイルへ直接 `read()` / `write()` して管理すれば十分なのではないか？**」

小規模な設定ファイルやログ出力なら、それで十分です。しかし、数万〜数億件のレコードを多数のユーザやアプリケーションから同時に読み書きする業務システムを「ファイルベース」で直接組もうとすると、すぐに次の **5つの壁** に突き当たって破綻します。

1. **データの冗長性と不整合：** 部署ごとに別々の CSV ファイル（例：`学生名簿.csv` と `履修登録.csv`）を持つと、同じ学生の住所が複数箇所に重複し、片方だけ更新した瞬間に矛盾（不整合）が生じます。
2. **データ構造とアプリの癒着（データ独立性の欠如）：** バイナリファイルのレコードに「電話番号」フィールドを 1 個追加したり、検索を速くするためにファイル内部をソート構造へ変えたりしただけで、そのファイルを読む **すべてのアプリケーションコードを書き直して再コンパイル** しなければなりません。
3. **検索と集計の遅さ・開発の手間：** 「2026年度に単位を20以上取得した工学部生を成績順に並べよ」といった新しい条件の集計が欲しくなるたびに、毎回 $O(N)$ で全ファイルをなめる専用プログラムを一から書く羽目になります。
4. **同時更新（並行性）の破綻：** 銀行口座 A から B へ送金する処理と、別の ATM からの引き出しが同時に同じファイルへ `write()` すると、[4-1節](../4/4-1.md)で見た **更新の消失（Lost Update）** や残高の矛盾が起きます。
5. **複合操作の途中停電（部分的な永続化）：** [第5部](../index.md#part-5)のファイルシステム・ジャーナリング（[5-6節](../5/5-6.md)）が守ってくれるのは「1回のファイルシステム操作（メタデータ等）の整合性」までであり、「口座 A のファイルから 1 万円引き、口座 B のファイルへ 1 万円足す」という **アプリケーション側の複数操作をまとめた原子性（All-or-Nothing）** は守ってくれません。

これらの共通課題を、個別のアプリケーションごとに毎回車輪の再発明をするのではなく、**汎用的なデータ管理基盤ソフトウェア** として一括提供するのが **DBMS（Database Management System：データベース管理システム）** です。本節では、DBMS の 3 層スキーマ設計とデータモデルの進化、そして第8〜9部全体を見通す DBMS 内部アーキテクチャの地図を描きます。

### 2. 具体例と動作イメージ（Toy Model）

抽象的な役割の一覧に入る前に、大学システムを題材にした小さな実験で「ファイルベース管理の破綻」と「DBMS による分離」を比べてみます。

#### 実験A：手書きの固定長ファイルが「1列追加」と「同時送金」で破綻する瞬間

ある大学のシステムが、学生データを1レコードちょうど 64 バイトの固定長バイナリファイル `students.dat` に保存しているとします。

```c
// アプリA（教務課）もアプリB（図書館）も、この物理構造を直書きして読んでいる
struct StudentRecord {
    int  id;          // offset 0  (4B)
    char name[32];    // offset 4  (32B)
    char dept[28];    // offset 36 (28B)
};
```

* **破綻1（物理変更の波及）：** 翌年、学生データに `email[64]` を追加してレコード長が 128 バイトになった瞬間、`sizeof(struct StudentRecord) == 64` を前提に `lseek(fd, i * 64, SEEK_SET)` で読んでいた**教務課・図書館・保健室の全プログラムが一斉に壊れてゴミデータを読み込み始めます**。
* **破綻2（検索性能と書き換え）：** 10万人の学生から `dept == "CS"` を探すには毎回全 10 万件を線形走査するしかありません。高速化しようとファイルを B木（索引）形式へ変えようとすれば、また全アプリを全面書き直しです。
* **破綻3（複数更新の途中停電）：** 履修登録で「定員残り枠ファイルから `1` 減らす」直後にサーバが停電すると、「履修者リストファイルへ学生を追加する」処理が実行されず、**誰も登録していないのに定員枠だけが永久に 1 減った状態**で固定されてしまいます。

#### 実験B：DBMS を使うとアプリは何だけを書けばよいか

同じシステムを **RDBMS（関係データベース管理システム）** の上に載せると、アプリケーションは「ファイルのバイト位置」「B木の辿り方」「ロックの取り方」「停電時のログ回復」を**1行も書かなくなります**。

```sql
-- 1. 欲しい結果（What）だけを宣言的に書く（どうやって探すか How は DBMS 任せ）
SELECT id, name FROM Students WHERE dept = 'CS';

-- 2. 複数更新を 1 つの原子的なまとまり（トランザクション）で囲む
BEGIN TRANSACTION;
    UPDATE Courses SET seats = seats - 1 WHERE course_id = 'CS101';
    INSERT INTO Enrollments VALUES (2026001, 'CS101');
COMMIT;
```

裏側で DBMS が `Students` テーブルに `email` 列を追加しても、検索高速化のために内部へ $\text{B}^+$ 木インデックスを追加しても、上の `SELECT` 文を 1 文字も書き換える必要はありません。この「アプリから物理構造を切り離す力」こそが、本節 3-(1) で整理する **データ独立性** です。

### 3. 構造・アルゴリズム・実装（What）

#### (1) ANSI/SPARC 3層スキーマアーキテクチャと「データ独立性」

DBMS がアプリケーションと物理ストレージの癒着を断ち切るために採用している標準的な設計モデルが、1975年に米国規格協会の委員会が提唱した **ANSI/SPARC 3層スキーマアーキテクチャ** です（図8-1-1）。

ここで **スキーマ（Schema）** とはデータの「構造の定義（型や表の設計図）」を指し、実際に格納されているその時点のデータの塊を **インスタンス（Instance）** と呼びます（プログラミング言語における「型定義」と「変数の実行時値」の対応と同じです）。

DBMS はデータベースの設計図（スキーマ）を次の **3つの層** へ分離します。

1. **外部スキーマ（External Schema / ビュー層）：**
    個々のアプリケーションやユーザグループごとに見せる「専用の切り口（ビュー：View）」です。たとえば、図書館システムには学生の `(id, name, dept)` だけを見せ、成績や住所は隠蔽します（[5-7節](../5/5-7.md)の最小権限の原則にも合致します）。

2. **概念スキーマ（Conceptual Schema / 論理層）：**
    組織全体のデータを統一的に記述する論理的な設計図（テーブル定義、属性の型、主キー・外部キー制約など）です。「どんなデータがあり、互いにどう関係しているか」を定義し、ディスク上の物理配置には一切触れません。

3. **内部スキーマ（Internal Schema / 物理層）：**
    ディスク上のどのファイルへ、どのページ編成（[9-1節](../9/9-1.md)）・どの索引構造（$\text{B}^+$ 木やハッシュ：[9-2節](../9/9-2.md)）・どの圧縮形式で格納するかを定義する物理的な実装設計です。

この3層分離によって、DBMS 最大の価値である **2種類のデータ独立性（Data Independence）** が実現されます。

* **物理データ独立性（Physical Data Independence）：** 内部スキーマ（索引の追加・削除、ハッシュから $\text{B}^+$ 木への変更、ストレージの HDD から SSD への移行、パーティショニング）を変更しても、概念スキーマやアプリケーションの SQL を一切変更せずに済む性質です。
* **論理データ独立性（Logical Data Independence）：** 概念スキーマ（新しい列の追加、テーブルの正規化分割など）を変更しても、外部スキーマ（ビュー）の定義を調整するだけで既存のアプリケーションへの影響を遮断できる性質です。

#### (2) データモデルの進化と 4 分類：なぜ「関係データモデル」が主流になったのか

現実世界の複雑な情報をどのような抽象構造で表現するかという枠組みを **データモデル（Data Model）** と呼びます。実務ではまず業務の「実体と関連」を実装非依存で整理する**概念モデリング（ER モデル：[8-6節](8-6.md)）**を行い、それを具体的な論理データモデルへ落とし込みます。論理データモデルは歴史的に次の流れで進化してきました（図8-1-2）。

1. **階層データモデル（Hierarchical Model：1960年代、IBM IMS 等）：**
    データを「親から子へ」の **1本の木構造（1対多）** で表現するモデルです。フォルダ構造のように直感的で、あらかじめ決められた親子経路の検索は非常に高速ですが、**「多対多」の関係（例：1人の学生が複数講義を履修し、1つの講義に複数学生が登録する）を木構造では自然に表現できず**、データの重複や複雑なダミー参照が必要になります。

2. **ネットワークデータモデル（Network Model：1969年 CODASYL）：**
    木構造を一般の **有向グラフ（多対多を許容）** へ拡張したモデルです。表現力は高まりましたが、データを検索するプログラムが**レコード同士を結ぶ物理的なポインタ（リンク）を手続き的に1本ずつ辿って書かなければならず**（ナビゲーショナルアクセス）、物理配置を変えるとプログラムが壊れ、物理データ独立性が著しく低かったです。

3. **関係データモデル（Relational Model：1970年 E. F. Codd）：**
    物理的なポインタをすべて追放し、あらゆるデータを数学の集合論に基づく **「行と列からなる2次元の表（関係：Relation）」** だけで表現するモデルです。表同士の関連は物理ポインタではなく**共通の値（主キーと外部キー）**で論理的に結びつけます。これにより、利用者は「どう辿るか（How）」を一切書かず「何が欲しいか（What）」だけを宣言的言語（SQL）で書けばよくなり、高い物理データ独立性と自動最適化への道が開かれました。

4. **NoSQL / 非リレーショナルモデル（2000年代後半〜）：**
    Web スケールの大規模分散や非構造化データに対応するため、キーバリュー型（Redis / DynamoDB）、ドキュメント型（MongoDB：JSON ネスト構造）、カラムファミリ型（Cassandra）、グラフ型（Neo4j：[8-7節](8-7.md)）など、特定用途へ特化したモデルが RDB を補完する形で発展しました。

> **【コラム：1970年 E. F. Codd の先駆的論文と「What」と「How」の分離】**
>
> 1970年、IBM サンノゼ研究所の数学者 **エドガー・F・コッド（Edgar F. Codd）** は、計算機科学の歴史を大きく変えた論文 *"A Relational Model of Data for Large Shared Data Banks"* を発表しました。当時の商用データベース（階層型・ネットワーク型）では、プログラマがディスク上のポインタ構造を知り尽くして「親レコードを読み、次ポインタを辿り…」という手続き（**How**）を手書きするのが常識でした。
>
> コッドはこれを根本から覆し、「データの論理構造を数学の集合論（直積の部分集合＝関係）だけに統一すれば、利用者は『何が欲しいか（**What**）』だけを宣言すればよく、最適なアクセス手順（**How**）の決定はすべて DBMS の問合せ最適化器へ任せられる」と提唱しました。当初は「そんな抽象的な仕組みは遅すぎて実用にならない」と懐疑論も根強かったものの、IBM の **System R**（SQL の原型とコストベース最適化を実証）と UC バークレーの **Ingres**（後の PostgreSQL の源流）の成功によってその実用性が証明され、関係データベースは今日まで半世紀以上にわたり計算機システムの中心的な基盤であり続けています。

#### (3) DBMS の内部アーキテクチャ全体見取り図（第8〜9部の学習ロードマップ）

アプリケーションから SQL クエリが 1 本届いたとき、DBMS の内部ではどのようなコンポーネントが協調して答えを返すのでしょうか。ここからの[第8部](../index.md#part-8)・[第9部](../index.md#part-9)で詳しく解き明かす **DBMS の内部構造の全体見取り図** を図8-1-3に示します（各専門用語の詳細は[第9部](../index.md#part-9)の該当節で順に定義します）。

1. **問合せ処理系（Query Processor：上層）：**

    * **パーサ＆意味解析（[第2部](../index.md#part-2)と同型）：** SQL 文を字句・構文解析して抽象構文木へ変換し、システムカタログ（テーブル・列・型の定義表）と照合します。
    * **問合せ最適化器（Query Optimizer：[9-4節](../9/9-4.md)）：** 宣言的な SQL（関係代数木：[8-2節](8-2.md)）を等価変換し、統計情報をもとに「$\text{B}^+$ 木索引を使うか全表走査するか」「どの結合順序が最速か」という実行計画を自動決定します。
    * **問合せ実行エンジン（Execution Engine：[9-3節](../9/9-3.md)）：** 決定された実行計画に従って、外部マージソートやハッシュ結合などを実行します。

2. **ストレージエンジン（Storage Engine：下層）：**

    * **索引マネージャ（Index Manager：[9-2節](../9/9-2.md)）：** $\text{B}^+$ 木や動的ハッシュ、**LSM-Tree**（書き込みを追記ログ構造で高速化する索引）によって $O(\log N)$ で目的のレコード位置を特定します。
    * **バッファプールマネージャ（Buffer Pool Manager：[9-1節](../9/9-1.md)）：** [5-5節](../5/5-5.md)の OS バッファキャッシュと同型です。ディスクページを RAM 上へキャッシュし、LRU（追い出し置換）・**PIN 管理**（参照中ページの追い出し禁止）・**ダーティページ**（更新済みで未書き戻しのページ）の書き戻しを制御します。
    * **ファイル・ページマネージャ（[9-1節](../9/9-1.md)）：** スロット配列と **TID**（ページ番号＋スロット番号のレコード識別子）を使って、固定長ページ（$8\text{ KiB}$ 等）の中へ可変長レコードを格納します。

3. **トランザクション管理（横断コンポーネント）：**

    * **並行性制御マネージャ（Concurrency Control：[9-5](../9/9-5.md)〜[9-7節](../9/9-7.md)）：** **2PL**（2相ロック）・時刻印（TO）・**OCC**（楽観的制御）・**MVCC**（複数バージョン保持による非ブロッキング読み取り）によって、同時実行される複数トランザクションの隔離性（**ACID**＝原子性・一貫性・隔離性・永続性の I）を守ります。
    * **障害回復マネージャ（Recovery Manager：[9-8節](../9/9-8.md)）：** [5-6節](../5/5-6.md)のジャーナリングを発展させた **WAL**（先行書き込みログ）・**LSN**（ログ順序番号）・チェックポイント・**CLR**（取り消し処理用の補償ログ）によって、停電時の原子性（A）と永続性（D）を守り抜きます。

### 4. 限界と補正（Critique & Adaptation）

DBMS（特に RDBMS）は非常に強力な基盤ですが、あらゆるデータ保存を無条件にサーバ型 RDBMS へ載せればよいわけではありません。実務では次の4つの限界と補正を見極めます。

#### (1) サーバ型 RDBMS のオーバーヘッドと「ファイル／組み込み DB」の使い分け

RDBMS は、SQL の構文解析・最適化、ロック管理、WAL ログ書き込み、クライアント／サーバ間のネットワーク通信（TCP/IP）という多層処理を経由するため、単純なファイル `read()`/`write()` に比べて一定の CPU・メモリ・運用のオーバーヘッドがかかります。

* **ファイルシステムを直接使うべき場面：** 巨大な画像・動画・音声などのバイナリ大規模データ（**BLOB**）の保管（通常はファイル本体をオブジェクトストレージやファイルシステムへ置き、そのパスやメタデータだけを DB に格納します）、あるいは単純な追記のみのアプリケーションログです。
* **組み込み型 RDBMS（SQLite / DuckDB）という中間解：** 別のデータベースサーバプロセスを立てず、アプリケーション自身のプロセス内にライブラリとしてリンクして単一ファイル上で完全な SQL と ACID トランザクションを提供する **SQLite**（スマートフォンアプリやブラウザ内部の標準）は、運用コストゼロで DBMS の利点を得られる強力な補正です。

#### (2) スキーマ固定（Schema-on-Write）の硬直性と半構造化データの補正

伝統的な RDBMS は「データを書き込む前に必ず厳格な列定義（スキーマ）を決める（**Schema-on-Write**）」設計です。整合性を保つには最適ですが、ログ解析や IoT センサーデータ、頻繁に仕様が変わる商品属性のように「レコードごとに項目がバラバラな半構造化データ」には窮屈です。

* **補正：** ドキュメント型 NoSQL（MongoDB 等：読み出し時に構造を解釈する **Schema-on-Read**）を使い分けるほか、現代の PostgreSQL や MySQL などの RDBMS 自身も **JSON / JSONB 型**（バイナリ形式で格納し検索可能にした JSON）とその内部フィールドへのインデックスを標準搭載し、厳格なスキーマと柔軟な半構造化データの利点を両立しています。

#### (3) 単一サーバ（スケールアップ）の限界と分散データベースへの展望

古典的な RDBMS は 1 台のマシン上の共有メモリとローカルディスクを前提として設計されており、Web サービスのように毎秒数百万リクエスト・ペタバイト級データに達すると 1 台の性能上限（スケールアップの壁）にぶつかります。これに対する補正（参照専用の複製である**リードレプリカ**、データを複数台へ水平分割する**シャーディング**、分散環境でも SQL と強整合性を目指す **NewSQL** と分散システムの制約である **CAP 定理**）は、[第9部](../index.md#part-9)の最終節（[9-9節](../9/9-9.md)）で改めて掘り下げます。

#### (4) データ独立性の代償：物理構造を意識しない SQL による性能劣化

高いデータ独立性によってアプリケーション開発者は物理配置や索引を意識せずに SQL を書けるようになりましたが、その裏返しとして、索引が効かない条件式や不要な全表走査・多段結合を無自覚に書いてしまい、実運用で深刻な性能劣化を招くことがあります。実行計画の確認と、DBMS 内部のページ編成・索引・結合・最適化の仕組みを理解することが不可欠であり、これこそが[第9部](../index.md#part-9)で内部構造へ踏み込む直接の動機になります。
