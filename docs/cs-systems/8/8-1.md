### 前節（7-7）の確認問題の解答

前節の最後に提示した3つの問いの解答を確認します。問3がそのまま[第8部](../index.md#part-8)（データベース基礎とリレーショナルモデル）の導入になります。

1. **未認証 Diffie-Hellman への MITM 実数値計算と TLS 1.3 の防御機構（$p = 23,\; g = 5,\; a = 6,\; b = 15,\; A = 8,\; B = 19,\; m = 2$）：**

    * **(a) 攻撃者 Mallory の公開値 $M$ と 2 つの共有鍵 $S_{AM},\; S_{BM}$：**

        * **Mallory の公開値 $M$：**

            $$M = g^m \bmod 23 = 5^2 \bmod 23 = 25 \bmod 23 = \mathbf{2}$$

        * **Alice と Mallory の共有鍵 $S_{AM}$：** Mallory は $A = 8$ から $A^m \bmod 23$ を、Alice は受け取った $M = 2$ から $M^a \bmod 23$ を計算し、一致します。

            $$S_{AM} = A^m \bmod 23 = 8^2 \bmod 23 = 64 \bmod 23 = \mathbf{18} \qquad \bigl(M^a = 2^6 = 64 \equiv 18 \pmod{23}\bigr)$$

        * **Bob と Mallory の共有鍵 $S_{BM}$：** Mallory は $B = 19 \equiv -4 \pmod{23}$ から $B^m \bmod 23$ を、Bob は受け取った $M = 2$ から $M^b \bmod 23$ を計算し、一致します。

            $$S_{BM} = B^m \bmod 23 = 19^2 \bmod 23 \equiv (-4)^2 = \mathbf{16} \qquad \bigl(M^b = 2^{15} = (2^5)^3 \equiv 9^3 = 729 \equiv 16 \pmod{23}\bigr)$$

        正規の共有鍵 $S = 2$ ではなく、Alice 側とは $S_{AM} = 18$、Bob 側とは $S_{BM} = 16$ という異なる 2 本の鍵が成立するため、Mallory は Alice からの暗号文を鍵 $18$ で復号して盗聴・改ざんし、鍵 $16$ で再暗号化して Bob へ中継できます。

    * **(b) TLS 1.3 が `CertificateVerify` 署名で MITM を防ぐ仕組み：**
        TLS 1.3 では、サーバが自身の ECDHE 公開値 $g^b$ を含むハンドシェイク全体のハッシュ値に対し、**サーバの長期秘密鍵で生成したデジタル署名（`CertificateVerify`）** と、信頼された認証局（CA）が署名した **X.509 証明書** をセットで返します。クライアントは内蔵のルート CA 公開鍵から信頼の連鎖を辿って証明書の正当性を検証し、証明書内のサーバ公開鍵で `CertificateVerify` を確認します。Mallory はサーバの長期秘密鍵を持たないため、自身の偽公開値 $g^m$ を含むハンドシェイクに対する正当な署名を偽造できず、MITM 攻撃は即座に検知・遮断されます。

2. **否認防止における HMAC vs デジタル署名、および Kerberos・PKI の運用診断：**

    * **(a) HMAC で否認防止を実現できない理由：**
        HMAC は送信者（Alice）と受信者（Bob）が **同一の秘密鍵 $K$** を共有する共通鍵方式であるため、受信者 Bob 自身も正しい HMAC タグを自力で作成できます。そのため、後日 Alice が「そのデータとタグは Bob が自分で偽造した」と主張しても第三者へ反証できません。一方、デジタル署名は送信者のみが保持する秘密鍵でしか生成できず、誰でも公開鍵で検証できるため、否認防止が成立します。

    * **(b) 2 つの運用トラブルの原因：**

        1. **Kerberos における 15 分の時刻ズレ：** Kerberos は盗聴されたチケットや認証子（Authenticator）の使い回し（リプレイ攻撃）を防ぐため、両者に現在時刻のタイムスタンプを埋め込み、KDC・サービス側と数分以内（標準 5 分以内）の時刻一致を要求します。時計が 15 分ずれると許容時間窓から外れるため、正しいパスワードでも認証がすべて拒否されます。
        2. **正規 CA 署名済みの `evil.example.net` 証明書が拒否される理由：** ブラウザは X.509 証明書の CA 署名（信頼の連鎖）と有効期限だけでなく、証明書内の許可ドメイン名一覧（**SAN**：Subject Alternative Name）が接続先ホスト名 `bank.example.com` と一致するかを必ず照合します。`evil.example.net` の証明書は SAN に `bank.example.com` を含まないため、正規 CA の署名があってもドメイン不一致で接続を拒否します。

3. **TLS で保護されたステートレス Web サーバ群と共有 CSV ファイルの限界（本節・[第8部](../index.md#part-8)への接続）：**
    TLS 1.3 が保護するのは「通信路上の盗聴・改ざん・なりすまし」だけであり、サーバ背後のデータ整合性は保証しません。複数台のステートレスな Web サーバが 1 つの共有 CSV ファイルを直接同時読み書きすると、次の 3 つの問題が生じます。

    1. **同時更新による競合とデータ破損：** 複数サーバが同時に同じ在庫行を読み取って減算・上書きすると、売り越し（ロストアップデート）や書き込み途中の行の混在によるファイル破損が起きます（単一 OS 内のロックだけでは複数台に跨る排他制御ができません）。
    2. **障害時の不整合（原子性の欠如）：** 「在庫を減らして注文履歴を追記する」処理の途中でサーバが停止すると、片方だけが反映された矛盾状態が残ります。
    3. **検索・更新性能の悪化：** CSV ファイルでは対象商品の検索に毎回先頭からの線形探索（$O(N)$）が必要となり、行サイズが変わる更新ではファイル全体の書き換えが発生します。

    これら「同時実行制御・障害復旧・高速索引・データ整合性」を体系的に解決するのが、本節（[第8部](../index.md#part-8)）から学ぶ **データベース管理システム（DBMS）** です。

## 8-1. ファイルベースの限界とDBMSの役割・データモデル

### 1. 動機（Why）：第5部のファイルシステムがあるのに、なぜさらに「DBMS」が必要なのか

[第0部](../index.md#part-0)から[第7部](../index.md#part-7)までを通じて、1台のコンピュータの内部（ハードウェア・コンパイラ・OS・並行性・ファイルシステム・保護）と、世界中の計算機を安全に結ぶネットワーク（リンク・IP・TCP/QUIC・TLS）の全構造が揃いました。

ここで素朴な疑問が湧きます。「[第5部](../index.md#part-5)で、電源が落ちても壊れないジャーナリング付きのファイルシステム（ext4 等）を手に入れたのだから、銀行の口座残高や EC サイトの在庫、大学の履修登録データも、**ただのテキストファイル（CSV）やバイナリファイルへ直接 `read()` / `write()` して管理すれば十分なのではないか？**」

小規模な設定ファイルやログ出力なら、それで十分です。しかし、数万〜数億件のレコードを多数のユーザやアプリケーションから同時に読み書きする業務システムを「ファイルベース」で直接組もうとすると、すぐに次の **5つの壁** に突き当たって破綻します。

1. **データの冗長性と不整合：** 部署ごとに別々の CSV ファイル（例：`学生名簿.csv` と `履修登録.csv`）を持つと、同じ学生の住所が複数箇所に重複し、片方だけ更新した瞬間に矛盾（不整合）が生じます。
2. **データ構造とアプリの癒着（データ独立性の欠如）：** バイナリファイルのレコードに「電話番号」フィールドを 1 個追加したり、検索を速くするためにファイル内部をソート構造へ変えたりしただけで、そのファイルを読む **すべてのアプリケーションコードを書き直して再コンパイル** しなければなりません。
3. **検索と集計の遅さ・開発の手間：** 「2026年度に単位を20以上取得した工学部生を成績順に並べよ」といった新しい条件の集計が必要になるたびに、毎回 $O(N)$ で全ファイルを走査する専用プログラムを一から書く必要が生じます。
4. **同時更新（並行性）の破綻：** 銀行口座 A から B へ送金する処理と、別の ATM からの引き出しが同時に同じファイルへ `write()` すると、[4-1節](../4/4-1.md)で見た **更新の消失（Lost Update）** や残高の矛盾が起きます。
5. **複合操作の途中停電（部分的な永続化）：** [第5部](../index.md#part-5)のファイルシステム・ジャーナリング（[5-6節](../5/5-6.md)）が守ってくれるのは「1回のファイルシステム操作（メタデータ等）の整合性」までであり、「口座 A のファイルから 1 万円引き、口座 B のファイルへ 1 万円足す」という **アプリケーション側の複数操作をまとめた原子性（All-or-Nothing）** は守ってくれません。

これらの共通課題を、個別のアプリケーションごとに毎回一から作り直すのではなく、**汎用的なデータ管理基盤ソフトウェア** として一括提供するのが **DBMS（Database Management System：データベース管理システム）** です。本節では、DBMS の 3 層スキーマ設計とデータモデルの進化、そして第8〜9部全体を見通す DBMS 内部アーキテクチャの地図を描きます。

### 2. 具体例と動作イメージ（Toy Model）

抽象的な役割の一覧に入る前に、大学システムを題材にした小さな実験で「ファイルベース管理の破綻」と「DBMS による分離」を比べてみます。

#### 実験A：手書きの固定長ファイルが「1列追加」と「同時送金」で破綻する瞬間

ある大学のシステムが、学生データを1レコードちょうど 64 バイトの固定長バイナリファイル `students.dat` に保存しているとします。

```c
// アプリA（教務課）もアプリB（図書館）も、この物理構造を直書きして読んでいる
struct StudentRecord {
    int  id;          // offset 0  (4B)
    char name[32];    // offset 4  (32B)
    char dept[28];    // offset 36 (28B)
};
```

* **破綻1（物理変更の波及）：** 翌年、学生データに `email[64]` を追加してレコード長が 128 バイトになった瞬間、`sizeof(struct StudentRecord) == 64` を前提に `lseek(fd, i * 64, SEEK_SET)` で読んでいた**教務課・図書館・保健室の全プログラムが誤ったオフセットからデータを読み込み始め、正常に動作しなくなります**。
* **破綻2（検索性能と書き換え）：** 10万人の学生から `dept == "CS"` を探すには毎回全 10 万件を線形走査するしかありません。高速化しようとファイルを B木（索引）形式へ変えようとすれば、再び全アプリケーションを書き直す必要が生じます。
* **破綻3（複数更新の途中停電）：** 履修登録で「定員残り枠ファイルから `1` 減らす」直後にサーバが停電すると、「履修者リストファイルへ学生を追加する」処理が実行されず、**誰も登録していないのに定員枠だけが永久に 1 減った状態**で固定されてしまいます。

#### 実験B：DBMS を使うとアプリは何だけを書けばよいか

同じシステムを **RDBMS（関係データベース管理システム）** の上に載せると、アプリケーションは「ファイルのバイト位置」「B木の辿り方」「ロックの取り方」「停電時のログ回復」を**自分で記述する必要がなくなります**。

```sql
-- 1. 欲しい結果（What）だけを宣言的に書く（どうやって探すか How は DBMS 任せ）
SELECT id, name FROM Students WHERE dept = 'CS';

-- 2. 複数更新を 1 つの原子的なまとまり（トランザクション）で囲む
BEGIN TRANSACTION;
    UPDATE Courses SET seats = seats - 1 WHERE course_id = 'CS101';
    INSERT INTO Enrollments VALUES (2026001, 'CS101');
COMMIT;
```

裏側で DBMS が `Students` テーブルに `email` 列を追加しても、検索高速化のために内部へ $\text{B}^+$ 木インデックスを追加しても、上の `SELECT` 文を 1 文字も書き換える必要はありません。この「アプリから物理構造を切り離す力」こそが、本節 3-(1) で整理する **データ独立性** です。

### 3. 構造・アルゴリズム・実装（What）

#### (1) ANSI/SPARC 3層スキーマアーキテクチャと「データ独立性」

DBMS がアプリケーションと物理ストレージの癒着を断ち切るために採用している標準的な設計モデルが、1975年に米国規格協会の委員会が提唱した **ANSI/SPARC 3層スキーマアーキテクチャ** です（図8-1-1）。

ここで **スキーマ（Schema）** とはデータの「構造の定義（型や表の設計図）」を指し、実際に格納されているその時点のデータの塊を **インスタンス（Instance）** と呼びます（プログラミング言語における「型定義」と「変数の実行時値」の対応と同じです）。

DBMS はデータベースの設計図（スキーマ）を次の **3つの層** へ分離します。

1. **外部スキーマ（External Schema / ビュー層）：**
    個々のアプリケーションやユーザグループごとに見せる「専用の切り口（ビュー：View）」です。たとえば、図書館システムには学生の `(id, name, dept)` だけを見せ、成績や住所は隠蔽します（[5-7節](../5/5-7.md)の最小権限の原則にも合致します）。

2. **概念スキーマ（Conceptual Schema / 論理層）：**
    組織全体のデータを統一的に記述する論理的な設計図（テーブル定義、属性の型、主キー・外部キー制約など）です。「どんなデータがあり、互いにどう関係しているか」を定義し、ディスク上の物理配置には一切触れません。

3. **内部スキーマ（Internal Schema / 物理層）：**
    ディスク上のどのファイルへ、どのページ編成（[9-1節](../9/9-1.md)）・どの索引構造（$\text{B}^+$ 木やハッシュ：[9-2節](../9/9-2.md)）・どの圧縮形式で格納するかを定義する物理的な実装設計です。

この3層分離によって、DBMS の中核的な価値である **2種類のデータ独立性（Data Independence）** が実現されます。

* **物理データ独立性（Physical Data Independence）：** 内部スキーマ（索引の追加・削除、ハッシュから $\text{B}^+$ 木への変更、ストレージの HDD から SSD への移行、パーティショニング）を変更しても、概念スキーマやアプリケーションの SQL を一切変更せずに済む性質です。
* **論理データ独立性（Logical Data Independence）：** 概念スキーマ（新しい列の追加、テーブルの正規化分割など）を変更しても、外部スキーマ（ビュー）の定義を調整するだけで既存のアプリケーションへの影響を遮断できる性質です（参照用ビューでは実現しやすい一方、集約や結合を含むビューを介した更新には制約があります。このビュー更新問題は [8-6節](8-6.md)で詳述します）。

#### (2) データモデルの進化と 4 分類：なぜ「関係データモデル」が主流になったのか

現実世界の複雑な情報をどのような抽象構造で表現するかという枠組みを **データモデル（Data Model）** と呼びます。実務ではまず業務の「実体と関連」を実装非依存で整理する**概念モデリング（ER モデル：[8-6節](8-6.md)）**を行い、それを具体的な論理データモデルへ落とし込みます。論理データモデルは歴史的に次の流れで進化してきました（図8-1-2）。

1. **階層データモデル（Hierarchical Model：1960年代、IBM IMS 等）：**
    データを「親から子へ」の **1本の木構造（1対多）** で表現するモデルです。フォルダ構造のように直感的で、あらかじめ決められた親子経路の検索は高速ですが、**「多対多」の関係（例：1人の学生が複数講義を履修し、1つの講義に複数学生が登録する）を木構造では自然に表現できず**、データの重複や複雑なダミー参照が必要になります。

2. **ネットワークデータモデル（Network Model：1969年 CODASYL）：**
    木構造を一般の **有向グラフ（多対多を許容）** へ拡張したモデルです。表現力は高まりましたが、データを検索するプログラムが**レコード同士を結ぶ物理的なポインタ（リンク）を手続き的に1本ずつ辿って書かなければならず**（ナビゲーショナルアクセス）、物理配置を変えるとプログラムが壊れ、物理データ独立性が低いという課題がありました。

3. **関係データモデル（Relational Model：1970年 E. F. Codd）：**
    物理的なポインタをすべて排除し、あらゆるデータを数学の集合論に基づく **「行と列からなる2次元の表（関係：Relation）」** だけで表現するモデルです。表同士の関連は物理ポインタではなく**共通の値（主キーと外部キー）**で論理的に結びつけます。これにより、利用者は「どう辿るか（How）」を一切書かず「何が欲しいか（What）」だけを宣言的言語（SQL）で書けばよくなり、高い物理データ独立性と自動最適化への道が開かれました。

4. **NoSQL / 非リレーショナルモデル（2000年代後半〜）：**
    Web スケールの大規模分散や非構造化データに対応するため、キーバリュー型（Redis / DynamoDB）、ドキュメント型（MongoDB：JSON ネスト構造）、カラムファミリ型（Cassandra）、グラフ型（Neo4j：[8-7節](8-7.md)）など、特定用途へ特化したモデルが RDB を補完する形で発展しました。

> **【コラム：1970年 E. F. Codd の先駆的論文と「What」と「How」の分離】**
>
> 1970年、IBM サンノゼ研究所の数学者 **エドガー・F・コッド（Edgar F. Codd）** は、データベース理論の礎となった論文 *"A Relational Model of Data for Large Shared Data Banks"* を発表しました。当時の商用データベース（階層型・ネットワーク型）では、プログラマがディスク上のポインタ構造を知り尽くして「親レコードを読み、次ポインタを辿り…」という手続き（**How**）を手書きするのが常識でした。
>
> コッドはこれを大きく転換し、「データの論理構造を数学の集合論（直積の部分集合＝関係）だけに統一すれば、利用者は『何が欲しいか（**What**）』だけを宣言すればよく、最適なアクセス手順（**How**）の決定はすべて DBMS の問合せ最適化器へ任せられる」と提唱しました。当初は「そんな抽象的な仕組みは遅すぎて実用にならない」と懐疑論も根強かったものの、IBM の **System R**（SQL の原型とコストベース最適化を実証）と UC バークレーの **Ingres**（後の PostgreSQL の源流）の成功によってその実用性が証明され、関係データベースは今日まで半世紀以上にわたり計算機システムの中心的な基盤であり続けています。

#### (3) DBMS の内部アーキテクチャ全体見取り図（第8〜9部の学習ロードマップ）

アプリケーションから SQL クエリが 1 本届いたとき、DBMS の内部ではどのようなコンポーネントが協調して答えを返すのでしょうか。ここからの[第8部](../index.md#part-8)・[第9部](../index.md#part-9)で詳しく解き明かす **DBMS の内部構造の全体見取り図** を図8-1-3に示します（各仕組みの詳細は[第9部](../index.md#part-9)の該当節で順に定義します）。

1. **問合せ処理系（Query Processor：上層）：**

    * **パーサ＆意味解析（[第2部](../index.md#part-2)と同型）：** SQL 文を字句・構文解析して抽象構文木へ変換し、システムカタログ（テーブル・列・型の定義表）と照合します。
    * **問合せ最適化器（Query Optimizer：[9-4節](../9/9-4.md)）：** 宣言的な SQL（関係代数木：[8-2節](8-2.md)）を等価変換し、統計情報をもとに「$\text{B}^+$ 木索引を使うか全表走査するか」「どの結合順序が最速か」という実行計画を自動決定します。
    * **問合せ実行エンジン（Execution Engine：[9-3節](../9/9-3.md)）：** 決定された実行計画に従って、外部マージソートやハッシュ結合などを実行し、下層のストレージエンジンへページ読み書きを要求します。

2. **ストレージエンジン（Storage Engine：下層）：**

    * **索引マネージャ（Index Manager：[9-2節](../9/9-2.md)）：** 範囲検索に強い $\text{B}^+$ 木、等値検索に強い動的ハッシュ、追記型の構成で大量書き込みを高速化する **LSM-Tree**（Log-Structured Merge-Tree）といった索引構造を使い、全件走査を避けて目的のレコード位置を高速に特定します。
    * **バッファプールマネージャ（Buffer Pool Manager：[9-1節](../9/9-1.md)）：** [5-5節](../5/5-5.md)の OS バッファキャッシュと同型です。ディスク上のページを主記憶（RAM）上へキャッシュし、追い出し方針（LRU など）、参照中ページの追い出しを禁じる **PIN 管理**（固定化）、および更新済みでディスクへ未反映の **ダーティページ** の書き戻しを制御します。
    * **ファイル・ページマネージャ（[9-1節](../9/9-1.md)）：** ページ内の配置表（スロット配列）と、ページ番号・スロット番号の組であるレコード識別子（**TID**／RID）を用いて、固定長ページ（$8\text{ KiB}$ 等）の中へ可変長レコードを格納します。

3. **トランザクション管理（横断コンポーネント）：**

    * **並行性制御マネージャ（Concurrency Control：[9-5](../9/9-5.md)〜[9-7節](../9/9-7.md)）：** トランザクションの基本特性である **ACID**（原子性・一貫性・隔離性・永続性）のうち、同時実行される処理が互いに干渉しない性質（隔離性：I）を守ります。ロックの獲得と解放を 2 段階に分ける **2PL**（2相ロック）、開始時刻で順序づける **時刻印制御**（TO）、衝突が少ない前提でコミット時に検証する **OCC**（楽観的並行性制御）、データの過去版を保持して読み取りの待ち合わせを減らす **MVCC**（多版並行性制御）といった手法を使い分けます。
    * **障害回復マネージャ（Recovery Manager：[9-8節](../9/9-8.md)）：** [5-6節](../5/5-6.md)のジャーナリングを発展させ、停電やクラッシュ時に ACID の原子性（A）と永続性（D）を保証します。データ本体より先に変更履歴を書き出す **WAL**（先行書き込みログ）、各ログに振る通し番号である **LSN**（ログ順序番号）、回復の起点を作るチェックポイント、取り消し処理の進行自体を記録する **CLR**（補償ログレコード）を組み合わせて整合状態を復元します。

### 4. 限界と補正（Critique & Adaptation）

DBMS（特に RDBMS）は強力な基盤ですが、あらゆるデータ保存を無条件にサーバ型 RDBMS へ載せればよいわけではありません。実務では次の4つの限界と補正を見極めます。

#### (1) サーバ型 RDBMS のオーバーヘッドと「ファイル／組み込み DB」の使い分け

RDBMS は、SQL の構文解析・最適化、ロック管理、WAL ログ書き込み、クライアント／サーバ間のネットワーク通信（TCP/IP）という多層処理を経由するため、単純なファイル `read()`/`write()` に比べて一定の CPU・メモリ・運用のオーバーヘッドがかかります。

* **ファイルシステムを直接使うべき場面：** 巨大な画像・動画・音声などのバイナリ大規模データ（**BLOB**）の保管（通常はファイル本体をオブジェクトストレージやファイルシステムへ置き、そのパスやメタデータだけを DB に格納します）、あるいは単純な追記のみのアプリケーションログです。
* **組み込み型 RDBMS（SQLite / DuckDB）という中間解：** 独立したデータベースサーバプロセスを立てず、アプリケーション自身のプロセス内にライブラリとしてリンクして動作する DBMS です。単一ファイル上で完全な SQL と ACID トランザクションを提供する行指向の **SQLite**（スマートフォンアプリやブラウザ内部で広く採用）や、ローカル上の大容量ファイルに対して列指向の高速集計を行う分析向けの **DuckDB**（[8-7節](8-7.md)）は、サーバ運用コストを抑えつつ DBMS の利点を得られる実用的な選択肢です。

#### (2) スキーマ固定（Schema-on-Write）の硬直性と半構造化データの補正

伝統的な RDBMS は「データを書き込む前に必ず厳格な列定義（スキーマ）を決める（**Schema-on-Write**）」設計です。整合性を保つには最適ですが、ログ解析や IoT センサーデータ、頻繁に仕様が変わる商品属性のように「レコードごとに項目がバラバラな半構造化データ」には窮屈です。

* **補正：** ドキュメント型 NoSQL（MongoDB 等：読み出し時に構造を解釈する **Schema-on-Read**）を使い分けるほか、現代の PostgreSQL や MySQL などの RDBMS 自身も **JSON / JSONB 型**（バイナリ形式で格納し検索可能にした JSON）とその内部フィールドへのインデックスを標準搭載し、厳格なスキーマと柔軟な半構造化データの利点を両立しています。

#### (3) 単一サーバ（スケールアップ）の限界と分散データベースへの展望

古典的な RDBMS は 1 台のマシン上の共有メモリとローカルディスクを前提として設計されており、Web サービスのように毎秒数百万リクエスト・ペタバイト級データに達すると 1 台の性能上限（スケールアップの壁）にぶつかります。これに対する補正（参照専用の複製である**リードレプリカ**、データを複数台へ水平分割する**シャーディング**、分散環境でも SQL と強整合性を目指す **NewSQL** と分散システムの制約である **CAP 定理**）は、[第9部](../index.md#part-9)の最終節（[9-9節](../9/9-9.md)）で改めて掘り下げます。

#### (4) データ独立性の代償：物理構造を意識しない SQL による性能劣化

高いデータ独立性によってアプリケーション開発者は物理配置や索引を意識せずに SQL を書けるようになりましたが、その裏返しとして、索引が効かない条件式や不要な全表走査・多段結合を無自覚に書いてしまい、実運用で深刻な性能劣化を招くことがあります。実行計画の確認と、DBMS 内部のページ編成・索引・結合・最適化の仕組みを理解することが不可欠であり、これこそが[第9部](../index.md#part-9)で内部構造へ踏み込む直接の動機になります。

### 理解度チェック（次節へ進む前の確認）

本節の3層スキーマ・データ独立性・トランザクションの役割とデータストアの使い分けを確認し、次節（[8-2節](8-2.md)：リレーショナルデータモデルと関係代数）へ繋ぐ問いを置きます。

> **【確認の問い】**
>
> 1. **（DBMS が提供する性質の診断：4 つの運用シナリオ）**
>     ある EC サイトを運用する中で、次の (a)〜(d) の事象や構成変更が発生しました。それぞれ、DBMS が提供する **物理データ独立性**・**論理データ独立性**・**原子性（トランザクション）**・**同時実行制御（隔離性）** のどれが問題を解決・吸収しているかを対応づけ、簡潔な理由を添えて答えてください。
>
>     * (a) 商品検索を高速化するため、`Items` テーブルに $\text{B}^+$ 木インデックスを追加し、ディスク上の格納構成を変更しましたが、アプリ側の SQL は修正しませんでした。
>     * (b) `Customers` テーブルへ新たに `loyalty_rank` 列を追加しましたが、配送管理アプリが参照している外部ビューの定義を維持したため、配送管理アプリを改修せずに済みました。
>     * (c) 注文確定時に「在庫数を 1 減算し、注文明細を 1 行挿入する」処理の途中でサーバが停電しましたが、再起動後に「在庫だけ減って注文が存在しない」状態にはなりませんでした。
>     * (d) 残り在庫 1 個の商品を 2 人のユーザが同時に購入しようとした際、両者が同じ在庫 1 個を読み込んで二重販売してしまう更新の消失を防ぎました。
>
> 2. **（ワークロードに応じたデータストア選定）**
>     次の (a)〜(d) のワークロードに対し、本節で扱ったデータ管理基盤（サーバ型 RDBMS／組み込み型 RDBMS［SQLite・DuckDB］／NoSQL［キーバリュー型・ドキュメント型］／ファイルシステム・オブジェクトストレージ）の中から適した選択肢を選び、選定理由を 1〜2 文で説明してください。
>
>     * (a) 複数端末から同時に残高が更新され、厳格なスキーマと ACID による整合性が必須となる決済台帳。
>     * (b) サービスや機器ごとに項目構造が頻繁に増減する大規模な分析用ログの蓄積と集計。
>     * (c) スマートフォンやデスクトップの単一アプリ内で、別サーバを立てずに設定や履歴データを安全に保存するローカル記憶領域。
>     * (d) Web ログイン中ユーザの一時的なセッション情報を、キー指定でミリ秒未満の低遅延に読み書きするキャッシュ。
>
> 3. **（次節への伏線：表計算シートや CSV で業務データを管理する際の構造的限界）**
>     「2 次元の表形式でデータを並べるだけなら、表計算ソフトや CSV ファイルでも関係データモデルと同じではないか」という主張に対し、**列位置番号への依存**・**重複行の許容**・**他表との参照整合性の欠如** の 3 点から、大規模な業務データでどのような不整合や運用上の問題が生じるかを説明してください。
