### 前節（8-5）の確認問題の解答

前節の最後に提示した3つの問いの解答を確認します。問3がそのまま本節（ER モデリングと宣言的言語 SQL）の導入になります。

1. **2 つのスキーマに対する BCNF 分解・従属性保存の比較と違反データ反例：**

    * **(a) 候補キー・BCNF 分解・従属性保存の比較：**

        * **スキーマ A（`StudentAdvisor(sid, major, advisor)`）：**
            候補キーは **`{sid, major}` と `{sid, advisor}`** の 2 つ（重なり合う候補キー）です。違反 FD `advisor → major` で分解すると **`R1(PK: advisor, major)`** と **`R2(PK: sid, advisor)`** になります。どちらも BCNF かつ無損失結合ですが、元の FD **`(sid, major) → advisor` が 2 表に分断されるため従属性保存は保たれません**。

        * **スキーマ B（`ExamRoom(course, time, room, capacity)`）：**
            候補キーは **`{course, time}`** のみです。違反 FD `room → capacity` で分解すると **`R1(PK: room, capacity)`** と **`R2(PK: course, time, room)`** になります。`R1` が `room → capacity`、`R2` が `(course, time) → room` をそれぞれ単表内で保持するため、無損失結合・BCNF に加えて**従属性保存も保たれます**。

    * **(b) スキーマ A の分解結果に対する違反データの具体例：**
        `R1(advisor, major)` に `(ProfA, CS)` と `(ProfB, CS)`（`advisor` は一意）、`R2(sid, advisor)` に `(101, ProfA)` と `(101, ProfB)`（`(sid, advisor)` は一意）を挿入します。各表の主キー制約には違反しませんが、自然結合 `R1 ⋈ R2` は `(101, CS, ProfA)` と `(101, CS, ProfB)` を返し、同じ `(101, CS)` に 2 人の指導教員が紐づいて元の `(sid, major) → advisor` に違反します。

2. **4NF 分解の適用境界と、スナップショット vs キャッシュの設計区別：**

    * **(a) `ShopInfo(shop, menu, area)` の 4NF 分解と独立でない場合の反例：**

        * **① 独立な場合：** 非自明な MVD は **$\text{shop} \twoheadrightarrow \text{menu} \mid \text{area}$** です。1 枚の表のままでは直積により $10 \times 8 = \mathbf{80\text{ 行}}$ 必要ですが、4NF 分解（`ShopMenu(shop, menu)` 10 行と `ShopArea(shop, area)` 8 行）では合計 $10 + 8 = \mathbf{18\text{ 行}}$ に圧縮されます。
        * **② 独立でない場合の反例：** `{(ShopA, Ramen, Area1), (ShopA, Curry, Area2)}` を誤って `ShopMenu = {(ShopA, Ramen), (ShopA, Curry)}` と `ShopArea = {(ShopA, Area1), (ShopA, Area2)}` へ分解して自然結合すると、元の 2 行に加えて **`(ShopA, Ramen, Area2)` と `(ShopA, Curry, Area1)` の 2 行の偽タプル**が発生します。MVD が成り立たない（相互に依存する）表を 4NF 分解すると損失結合になるため、分解してはいけません。

    * **(b) スナップショット（`unit_price_at_order`）vs キャッシュ（`like_count`）：**

        * **`unit_price_at_order`（履歴スナップショット）：** 後日商品マスタの単価が変わっても過去注文の請求額は変えてはならないため、元マスタ更新時に**同期追従してはいけません**。時間軸を含めれば `(order_id, item_id)` に完全従属する業務固有の事実であり、実質的に正規化違反ではありません。
        * **`like_count`（集計キャッシュ）：** `Likes` テーブルの件数から導出可能な冗長列（意図的な非正規化）であり、`Likes` への挿入・削除のたびに**必ず同期追従させる必要があります**。

3. **アプリ層だけでの非正規化キャッシュ同期リスクとトリガのトレードオフ（本節への接続）：**
    アプリ層だけで `like_count` を同期すると、別のマイクロサービス・管理画面・手動 SQL バッチのいずれか 1 か所で更新処理を書き漏らした瞬間に件数の不整合（更新異常）が発生します。これに対し、DBMS 側でイベントに応じて自動発動する **トリガ** を導入すれば同期漏れを防げますが、逆にアプリコードからは見えにくい隠れた副作用やトリガ同士の連鎖・ロック競合が生まれやすくなるという保守上のトレードオフがあります。本節では、実務の概念設計（ER モデリング）と合わせて、SQL のビュー・トリガ・再帰問合せの仕組みと注意点を整理します。

## 8-6. ERモデリングと宣言的言語SQL（ビュー更新の制約・トリガ・再帰問合せ）

### 1. 動機（Why）：なぜ「ER 図で描いてから正規化で検算」し、SQL には単なる `SELECT` 以上の仕組みが要るのか

前節まで（[8-2](8-2.md)〜[8-5節](8-5.md)）を通じて、関係データモデルの数学的基盤（関係代数・関係論理）と、更新時異常を排除する正規化理論（1NF〜5NF）がすべて揃いました。

しかし、実際のシステム開発の現場で「新しい EC サイトや大学の履修システムを設計してください」と依頼されたとき、最初から 50 列の巨大な 1 枚の表を書いて関数従属性を並べる人はいません。人間はまず業務の世界を**「モノ（実体：学生、講義、学科）」**と**「モノ同士の結びつき（関連：履修する、所属する）」**として頭の中で整理します。この人間の認識をそのまま図面化し、機械的なルールで最初からほぼ 3NF/BCNF に近いテーブル群へ変換する手法が **ER モデリング（Entity-Relationship Modeling）** です。

そして、設計したテーブルを実際の DBMS 上で動かし始めると、基本的な `SELECT / INSERT / UPDATE / DELETE` だけでは済まない次の **3つの実務上の要求** に直面します。

1. **見せ方の抽象化とアクセス制御（ビューと更新の制約）：** [8-1節](8-1.md)の外部スキーマを実現する「ビュー（仮想表）」は、参照するだけでなく `UPDATE` もできるのか、どこまでが更新可能でなぜ結合や集計を含むビューは更新できないのかを判断する必要があります。
2. **データ整合性や非正規化キャッシュの自動化（トリガ）：** [8-5節](8-5.md)で触れた `like_count` の自動更新や監査ログの記録を、アプリ側の書き忘れに頼らず DBMS 側で自動発動させる仕組みが求められます。
3. **階層データ・グラフデータの探索（再帰問合せ）：** [8-2](8-2.md)・[8-3節](8-3.md)で「一階述語論理（標準関係代数・関係論理）では表現できない」と証明された **推移閉包（組織の上司→部下ツリー、部品表 BOM）** を SQL でどのように解くのでしょうか。

本節では、**ER モデリングとテーブル変換規則**、**SQL の論理評価順序とウィンドウ関数**、**ビュー更新の制約**、**トリガ（ECA モデル）**、そして **再帰問合せ（`WITH RECURSIVE`）** を実践的な例と図解で整理します。

### 2. 具体例と動作イメージ（Toy Model）

規則の網羅に入る前に、2つの小さな例で「ER 図からテーブルへの自然な変換」と「SQL の評価順序によるよくあるエラー」を確かめます。

#### 実験A：大学の業務ルールを 3 つの要素（実体・関連・多重度）で整理する

ある大学の業務要件が次のように与えられたとします。

* **学科（`Dept`）** には複数の **学生（`Student`）** が所属し、各学生は必ず 1 つの学科に所属します（**1 対多：`1 : N`**、学生側は **全参加**）。
* 1 人の **学生（`Student`）** は複数の **講義（`Course`）** を履修でき、1 つの講義も複数の学生に履修されます（**多 対 多：`M : N`**）。履修ごとに成績 `grade` が付きます（ここでは同一学生が同一講義を重複履修しない 1 回限りの履修という簡略化前提を置きます。再履修を許す場合は開講年度・学期等も主キーに含めます）。
* 1 つの **講義（`Course`）** には、年度と学期ごとに複数の **開講クラス（`Section`）** が開かれますが、`Section` は親の `Course` がなければ単独では識別できません（**弱実体**）。

これを ER 図として描いた瞬間、後述の機械的ルールによって「`Dept`」「`Student`（`NOT NULL` の外部キー `dept_id` を持つ）」「`Course`」「`Enroll`（`sid, cid, grade` の中間テーブル）」「`Section`（`cid, year, term` の複合主キー）」という **最初から BCNF を満たす 5 枚のテーブル** が迷わず導き出せます。

#### 実験B：なぜ `WHERE` 句で `SELECT` の別名や `COUNT(*)` を使うとエラーになるのか

次の SQL クエリは、SQL の学習中に初学者が頻繁に遭遇するエラーコードです。

```sql
-- 失敗例：構文エラー（または列未定義エラー）になる
SELECT dept_id, COUNT(*) AS cnt
FROM Students
WHERE cnt >= 10           -- エラー：WHERE で SELECT の別名 cnt や COUNT(*) は使えない
GROUP BY dept_id;
```

なぜエラーになるのでしょうか。英語の語順に合わせて **`SELECT` を一番上に書く** のはあくまで見た目の記述順であり、DBMS がクエリを評価する **論理的な実行順序** では、**`WHERE` が `GROUP BY` や `SELECT` よりもずっと先に実行される** からです。

1. まず `FROM Students` でテーブル全体を用意します。
2. 次に `WHERE` で **個別の行** を絞り込みます（この時点ではまだグループ化も `COUNT(*)` も別名 `cnt` の付与も起きていません）。
3. 次に `GROUP BY dept_id` で学科ごとのグループへ束ね、`COUNT(*)` を計算します。
4. **グループ化した後の絞り込み** を行うのが **`HAVING COUNT(*) >= 10`** です。
5. 最後に `SELECT` で出力列を選び、`ORDER BY` で並べ替えます。

この論理評価順序を頭に入れておけば、`WHERE` と `HAVING` の使い分けや複雑な SQL の挙動に迷うことがなくなります。

### 3. 構造・アルゴリズム・実装（What）

#### (1) ER モデリング（実体関連モデル）と関係スキーマへの変換規則

1976年にピーター・チェン（Peter Chen）が提唱した **ER モデル（Entity-Relationship Model）** は、現実世界のデータ構造を次の構成要素で図式化します（図8-6-1左）。

* **実体集合（Entity Set：長方形）：** 独立して識別できる対象です（例：`Dept`, `Student`, `Course`）。主キー属性に下線を引きます。
* **関連集合（Relationship Set：ひし形）：** 実体同士の結びつきです（例：`所属`, `履修`）。関連自身が属性（例：`grade`）を持つこともできます。
* **多重度（Cardinality：カーディナリティ）：** 関連に参加する実体の個数比です（**`1 : 1`**、**`1 : N`**、**`M : N`**）。また、すべての実体が必ず関連に参加しなければならない制約を **全参加（Total Participation：二重線）** と呼びます（`1 : N` の多側が全参加のとき、対応する外部キーには `NOT NULL` 制約を付与します）。
* **弱実体集合（Weak Entity Set：二重長方形）：** 自分自身の属性だけでは一意に識別できず、親となる所有者実体の主キーと自分の **部分キー（破線下線）** を組み合わせて初めて識別できる実体です（例：講義 `CS101` の「2026年・春学期」クラス `Section`）。親との識別関連は二重ひし形で表し、弱実体側は必ず全参加（二重線）になります。

なお、実務の設計ツールでは、ひし形を省いて実体間の線の端に多重度を「一本線（1）」や「三叉（多＝カラスの足）」で表す **カラスの足記法（Crow's Foot / IE 記法）** も広く使われます。

描いた ER 図をリレーショナルデータベースのテーブル（概念スキーマ）へ変換する手順は、次の **4 つの機械的ルール** で体系化されています（図8-6-1右）。

1. **強い実体集合：** そのまま 1 枚のテーブルにし、主キーを設定します（例：`Dept(dept_id, bldg)`、`Student(sid, name)`、`Course(cid, title)`）。
2. **`1 : N`（1 対多）の関連：** 新しいテーブルを作らず、**「多（`N`）側」のテーブルへ「1 側」の主キーを外部キー（FK）として追加**します（例：`Student` テーブルへ `dept_id` を追加します。`Student` は全参加なので `NOT NULL` を付与します）。関連の属性も多側へ入れます。
3. **`M : N`（多 対 多）の関連：** **新しい中間テーブル（関連テーブル）を 1 枚作成**し、両側の主キーを外部キーかつ**複合主キー**として入れ、関連自身の属性（`grade`）もそこへ置きます（例：`Enroll(sid, cid, grade)`）。
4. **弱実体集合：** 弱実体用のテーブルを作成し、**所有者（親）の主キー（FK）＋ 自身の部分キー** を合わせて複合主キーとします（例：`Section(cid, year, term, room)`）。親削除時は `ON DELETE CASCADE` を設定します。

（※`1 : 1` の関連は、全参加側またはどちらか一方のテーブルへ相手の主キーを `UNIQUE` 制約付きの外部キーとして追加します。）

#### (2) 宣言的言語 SQL の構成と論理評価順序・ウィンドウ関数

* **DDL（データ定義言語）：** `CREATE TABLE`, `ALTER TABLE`, `DROP TABLE`, `CREATE INDEX`, `CREATE VIEW`（スキーマと整合性制約の定義）。

ここで、`GROUP BY` と混同しやすい **ウィンドウ関数（Window Function）** との違いを整理しておきます。`GROUP BY` は同じグループに属する複数行を **1 行へ集約（圧縮）** するのに対し、ウィンドウ関数（`SUM(score) OVER (PARTITION BY dept_id ORDER BY sid)` や `RANK() OVER (PARTITION BY dept_id ORDER BY score DESC)` など）は **元の全行を潰さずに残したまま**、各行へ部門内順位・累積和・移動平均といった計算列を付加します。

| 比較項目 | `GROUP BY`（集約） | ウィンドウ関数（`OVER (...)`） |
| :--- | :--- | :--- |
| **出力の行数** | グループごとに 1 行へ圧縮される | 元の全行がそのまま残る |
| **主な用途** | 学科別平均点・件数などグループ単位の要約 | 学科内ランキング（`RANK()`）、累計、移動平均、前行比較（`LAG()`） |
| **論理評価段階** | ステップ ③（`HAVING` で絞り込み可能） | ステップ ⑤（`SELECT` 段階；絞り込むには副問合せや CTE で包む） |

#### (3) ビュー（View）と「ビュー更新の制約（View Update Problem）」

**ビュー（View）** は、`CREATE VIEW` で名前を付けて保存した `SELECT` クエリ（仮想テーブル）です。通常のビューはデータを物理的にコピーせず、参照されるたびに元のテーブル（基底表）に対するクエリへ展開されます（[8-1節](8-1.md)の **外部スキーマ** と **論理データ独立性**、および機密列を隠すセキュリティ保護を実現します）。

```sql
-- 成績や住所を隠して、図書館向けに学生の基本情報だけを見せるビュー
CREATE VIEW LibraryStudents AS
SELECT sid, name, dept_id FROM Students WHERE dept_id = 'CS';
```

ここで重要な理論的・実務的課題が **ビュー更新問題（View Update Problem）** です。「ビューに対して `INSERT` や `UPDATE` や `DELETE` を実行したら、元の基底表をどう書き換えるべきか？」という問いです。

* **更新可能なビュー（単純な単表ビュー）：**
    上の `LibraryStudents` のように、**単一の基底表**に対する単純な選択（`WHERE`）と射影だけで作られたビューであれば、操作種別ごとに次の条件を満たす範囲で基底表への更新へ一意に翻訳できます（※`WITH CHECK OPTION` を付けておけば、ビューの `WHERE dept_id = 'CS'` 条件を外れるような不正な更新も弾けます）。

    * **`UPDATE` / `DELETE` の条件：** ビュー上の 1 行から基底表の 1 行を**一意に特定できる**こと（典型的には、基底表の**主キーとの 1 対 1 対応**が保たれていること）が必要です。
    * **`INSERT` の条件：** 上記に加えて、基底表における **`NOT NULL` かつデフォルト値を持たないすべての列（主キーを含む）** をビューが含んでいる必要があります（含まない必須列があると、基底表への挿入時に値を埋められないためです）。

* **更新不可能なビュー（逆写像が一意に定まらないケース）：**
    次のいずれかを含むビューは、基底表への翻訳先が数学的に一意に定まらない（あるいは矛盾する）ため、標準 SQL では原則として直接更新が禁止されています。

    1. **集約・`GROUP BY`・`DISTINCT` を含むビュー：** たとえば `DeptAvg(dept_id, avg_gpa)` の平均値 `avg_gpa` を `3.2 → 3.5` に書き換えよと言われても、どの学生の成績をどれだけ変えればよいか無限の候補があり一意に決まりません。
    2. **複数テーブルの結合（`JOIN`）を含むビュー：** `StudentDept(sid, name, dept_id, bldg)` に対して 1 行 `DELETE` したとき、`Students` の行だけ消すのか `Depts` の学科ごと消すのかが一意に決まらず、さらに `bldg` を書き換えると他の全 CS 学生の建物まで波及してしまいます。
    3. **計算式・定数・副問合せで導出された列への更新：** 元の基底表のどの列へ書き戻すべきかが一意に定まりません。

#### (4) トリガ（Trigger：ECA モデル）とストアドプロシジャ

**トリガ（Trigger）** は、テーブルへの特定イベント（`INSERT` / `UPDATE` / `DELETE`）が発生した瞬間に、DBMS が自動的に指定した処理を実行する能動的な仕組みです。構造は次の **ECA モデル（Event - Condition - Action）** で整理されます。

* **Event（事象）：** いつ発動するかを指定します（例：`AFTER INSERT ON Likes`、`BEFORE UPDATE ON Accounts`）。
* **Condition（条件）：** どの条件を満たすとき実行するかを指定します（例：`WHEN (NEW.balance < 0)`）。
* **Action（動作）：** 何を実行するかを指定します（`FOR EACH ROW`＝変更された各行ごと、または `FOR EACH STATEMENT`＝SQL 1 文につき 1 回）。

[8-5節](8-5.md)で学んだ「意図的な非正規化キャッシュ（`Posts.like_count`）」をトリガで自動同期する例は次の通りです。

```sql
CREATE TRIGGER inc_like_count
AFTER INSERT ON Likes
FOR EACH ROW
BEGIN
    UPDATE Posts SET like_count = like_count + 1
    WHERE post_id = NEW.post_id;
END;
```

これにより、どのアプリケーションから `Likes` へ `INSERT` されても、同一トランザクション内で自動的に `like_count` が `+1` され、更新時異常を防げます。

なお、イベント駆動で自動発動するトリガに対し、複数の SQL 文と分岐・ループ処理を名前付き手続きとして DBMS 内部へ事前登録し、アプリケーションから明示的に呼び出す仕組みを **ストアドプロシジャ（Stored Procedure）** と呼びます。クライアントとの通信往復を減らせる利点がある一方、トリガと同様に業務ロジックが DB 側とアプリ側へ分散する保守上のトレードオフがあります。

#### (5) 共通テーブル式（CTE）と再帰問合せ（`WITH RECURSIVE`）

複雑な副問合せに名前を付けて一時的な仮想表として見通しよく記述する構文が **共通テーブル式（CTE：Common Table Expression、`WITH` 句）** です。さらに [8-2節](8-2.md)・[8-3節](8-3.md)で確認した「標準の関係代数や一階述語論理では深さが事前に分からない階層構造（推移閉包）を検索できない」という壁を超えるため、CTE を自己参照へ拡張したのが **再帰共通テーブル式（Recursive CTE：`WITH RECURSIVE`）** です（図8-6-3）。

従業員と直属上司の表 `Emp(emp_id, name, mgr_id)` に対して、「社長（`emp_id = 1`）の配下にいる**すべての部下（孫・ひ孫を含む全員）**と階層深さ」を求めるクエリは次の 2 部構成で書きます。

```sql
WITH RECURSIVE Subordinates(emp_id, name, depth) AS (
    -- ① 基底部（アンカーメンバ）：再帰の出発点（深さ 0 の社長本人）
    SELECT emp_id, name, 0
    FROM Emp
    WHERE emp_id = 1

    UNION ALL

    -- ② 再帰部（リカーシブメンバ）：直前のステップで見つかった人の部下を結合
    SELECT e.emp_id, e.name, s.depth + 1
    FROM Emp AS e
    JOIN Subordinates AS s ON e.mgr_id = s.emp_id
)
SELECT * FROM Subordinates;
```

DBMS はこれを **幅優先の反復不動点計算** として実行します（[8-3節](8-3.md)の Datalog のボトムアップ評価と同型です）。

1. まず基底部を実行して作業テーブル $W_0 = \{ (1, \text{社長}, 0) \}$ を作り、結果集合 $R$ へ追加します。
2. 次に再帰部で $W_0$ と `Emp` を結合し、社長の直属部下 $W_1 = \{ (2, \text{部長A}, 1), (3, \text{部長B}, 1) \}$ を得て $R$ へ追加します。
3. 同様に $W_1$ から $W_2$（課長ら）を得て $R$ へ追加し、次の反復で**新しく見つかる行が空（図8-6-3の例では $W_3 = \emptyset$：不動点に到達）** になった瞬間に停止して全体の $R$ を返します（さらに深い階層があれば $W_k = \emptyset$ になるまで反復が続きます）。

> **【コラム：SQL インジェクションとプリペアドステートメント：「構文木（AST）」と「データ」の分離】**
>
> Web アプリケーションにおける代表的かつ深刻な脆弱性の 1 つが **SQL インジェクション** です。アプリ側でユーザ入力 `name` を文字列結合して
>
> ```sql
> "SELECT * FROM Users WHERE name = '" + user_input + "';"
> ```
>
> のように SQL 文を組み立てると、攻撃者が `user_input` に **`' OR '1'='1`** や **`'; DROP TABLE Users; --`** を入力した瞬間、本来「データ（文字列リテラル）」であるはずの入力が **SQL の構文（命令）として構文解析されてしまい**、認証突破や全データ流出・テーブル破壊が起きます。
>
> これに対する根本的な対策が **プリペアドステートメント（Prepared Statement / バインド変数）** です。
>
> ```sql
> PREPARE stmt FROM 'SELECT * FROM Users WHERE name = ?';
> EXECUTE stmt USING @user_input;
> ```
>
> なぜこれで SQL インジェクションを原理的に防げるのかは、**[第2部](../index.md#part-2)（[2-3節](../2/2-3.md)：構文解析と AST）** の知識で明快に理解できます。プリペアドステートメントでは、ユーザ入力を受け取る**より前**に `SELECT ... WHERE name = ?` だけを字句解析・構文解析して **抽象構文木（AST）と実行計画を確定** してしまいます。あとから渡される `@user_input` は、すでに完成した AST の葉ノード `?` へ「ただの文字列値」として流し込まれるだけで二度と構文解析されないため、中に `'` や `OR` や `;` が含まれていても命令へ解釈されることはありません。
>
> なお、プリペアドステートメントのプレースホルダ `?` は `WHERE` 句の値などの **リテラル値（データ）をバインドするための仕組み** であり、テーブル名・列名・`ORDER BY` の昇順／降順（`ASC`/`DESC`）といった **動的な識別子や SQL キーワードの位置には使えません**。ユーザ入力に応じて並び替え対象列などを切り替える必要がある場合は、アプリ側で許可された候補一覧（**ホワイトリスト**）と厳密一致を検証したうえで固定の識別子文字列を選択することが必須です。

### 4. 限界と補正（Critique & Adaptation）

#### (1) トリガの乱用が招く「隠れた副作用と連鎖爆発」

トリガは便利ですが、大規模なシステムで業務ロジックを大量にトリガへ書き込むと、次の深刻な保守性・性能問題を引き起こします。

* アプリケーションコードを読んでも「なぜ `INSERT INTO Likes` しただけで別の 3 テーブルまで書き換わったのか」が見えず、バグの原因追跡が難しくなります。
* テーブル A のトリガがテーブル B を更新し、B のトリガが再び A を更新する **無限カスケードループ** や予期せぬロック競合・デッドロックを生みます。

**補正：** 単純な制約や計算列にはトリガを使わず、宣言的な **`CHECK` 制約・`FOREIGN KEY (ON DELETE CASCADE)`・生成列（`GENERATED ALWAYS AS (...) STORED`）** を優先します。業務上の複雑なワークフローはアプリケーション層のトランザクション内で明示的に記述し、トリガは監査ログや小規模な不変条件の維持など最小限の用途へ限定するのが実務の定石です。

#### (2) 再帰問合せにおける「循環グラフの無限ループ」と「DAG での結果爆発」

図8-6-3の組織図のように閉路のない木構造（または有向非巡回グラフ：DAG）であれば `WITH RECURSIVE` は必ず有限回で停止します。ただし、一般のグラフでは次の 2 つの問題が生じます。

* **循環（サイクル）による無限ループ：** SNS のフォロー関係や道路網グラフのように **`A → B → C → A` という閉路** を含むデータへ `UNION ALL` の再帰クエリを実行すると、同じノードを回り続けてメモリ枯渇やタイムアウトに陥ります。
* **合流経路を持つ DAG での結果爆発：** 閉路がなくても、部品表（BOM）のように複数経路が合流する一般の DAG では、`UNION ALL` を使うと同じノードが経路の組み合わせ数だけ重複展開され、行数が指数的に膨らむことがあります。

**補正：** 循環や合流があり得るデータでは、次のいずれかを必ず組み込みます。

1. `UNION ALL` の代わりに **`UNION`**（重複行を自動排除）を使い、すでに訪れた頂点を再展開しないようにします（ただし `depth` のように毎回変わる列を出力に含めると重複とみなされず止まらない点に注意します）。
2. PostgreSQL 14+ や標準 SQL:1999 の **`CYCLE emp_id SET is_cycle USING path`** 句（または訪問済み ID 配列 `NOT (e.emp_id = ANY(s.path))`）および **深さ上限 `WHERE s.depth < 100`** を明示します。

#### (3) インピーダンス・ミスマッチ（ORM と N+1 問題）

オブジェクト指向言語（Java, Python, TypeScript 等）のメモリ上ではデータはポインタで結ばれた複雑なオブジェクトグラフですが、RDBMS の世界は平坦な 2 次元テーブルの集合です。この表現モデルのズレを **オブジェクト・リレーショナル・インピーダンス・ミスマッチ** と呼びます。

このズレを埋める **ORM（Object-Relational Mapping）** を使うと、ループの中で関連オブジェクトを遅延読み込みしてしまい、「1 回の親リスト取得 `SELECT` のあとに、子要素を取得する `SELECT` を $N$ 回連続発行して極端に遅くなる（**N+1 問題**）」が頻発します。補正として、最初から SQL の `JOIN` や `WHERE id IN (...)` で 1〜2 回のクエリへまとめる（Eager Loading）意識が不可欠です。
