### 前節（8-5）の確認問題の解答

前節の最後に提示した3つの問いの解答を確認します。問3がそのまま本節（ER モデリングと宣言的言語 SQL）の導入になります。

1. **3NF だが BCNF でない関係の判定と分解（`StudentAdvisor(sid, major, advisor)`、FD：`(sid, major) → advisor` および `advisor → major`）：**

    * **(a) 候補キーと 3NF / BCNF の判定：**

        * $\{\text{sid}, \text{major}\}^+ = \{\text{sid}, \text{major}, \text{advisor}\}$、また $\{\text{sid}, \text{advisor}\}^+ = \{\text{sid}, \text{advisor}, \text{major}\}$ であり、どの 1 属性だけでは全属性が決まらないため、候補キーは **`{sid, major}`** と **`{sid, advisor}`** の 2 つです。
        * したがって全 3 属性（`sid`, `major`, `advisor`）がすべて **素属性** です。`advisor → major` の左辺 `advisor` はスーパーキーではありませんが、右辺 `major` が素属性であるため **3NF の例外条項により 3NF は満たします**。一方、BCNF は「すべての非自明な FD の左辺がスーパーキーであること」を要求するため、**BCNF には違反** します。

    * **(b) BCNF 分解と従属性保存の判定：**
        違反している FD `advisor → major`（$X = \{\text{advisor}\}, Y = \{\text{major}\}$）で分解すると、次の 2 表（無損失結合）になります。

        * $R_1(\underline{\text{advisor}},\; \text{major})$（FD：`advisor → major` を保存）
        * $R_2(\underline{\text{sid},\; \text{advisor}})$
        
        しかし、元の重要な業務ルール **`(sid, major) → advisor` が $R_1$ と $R_2$ に分断されてしまうため、従属性保存は保たれません**。

2. **多値従属性（MVD）と 4NF 分解（`ShopInfo(shop, menu, area)`）：**

    * **(a) 成り立つ非自明な MVD：**

        $$\text{shop} \twoheadrightarrow \text{menu} \quad \text{および} \quad \text{shop} \twoheadrightarrow \text{area} \qquad (\text{まとめて } \text{shop} \twoheadrightarrow \text{menu} \mid \text{area})$$

    * **(b) 行数の比較（10 種類の料理 × 8 つの配達地域）：**

        * 1 枚の表のまま（直積）：$10 \times 8 = \mathbf{80\text{ 行}}$
        * 4NF へ分解後（`ShopMenu(shop, menu)` と `ShopArea(shop, area)`）：$10 + 8 = \mathbf{18\text{ 行}}$

3. **真っ白な業務要件からの ER モデリングと宣言的言語 SQL（本節への接続）：**
    正規化理論（[8-4](8-4.md)・[8-5節](8-5.md)）はテーブルの良さを数学的に検証・分解する道具です。実務でゼロから概念スキーマを設計する出発点となるのが **ER モデリング（実体関連モデル）** であり、それを実際の DBMS 上で定義・操作・自動化・階層検索するのが宣言的言語 **SQL** です。

## 8-6. ERモデリングと宣言的言語SQL（ビュー更新の制約・トリガ・再帰問合せ）

### 1. 動機（Why）：なぜ「ER 図で描いてから正規化で検算」し、SQL には単なる `SELECT` 以上の仕組みが要るのか

前節まで（[8-2](8-2.md)〜[8-5節](8-5.md)）を通じて、関係データモデルの数学的基盤（関係代数・関係論理）と、更新時異常を排除する正規化理論（1NF〜5NF）がすべて揃いました。

しかし、実際のシステム開発の現場で「新しいECサイトや大学の履修システムを設計してください」と依頼されたとき、最初から 50 列の巨大な 1 枚の表を書いて関数従属性を並べる人はいません。人間はまず業務の世界を**「モノ（実体：学生、講義、学科）」**と**「モノ同士の結びつき（関連：履修する、所属する）」**として頭の中で整理します。この人間の認識をそのまま図面化し、機械的なルールで最初からほぼ 3NF/BCNF に近いテーブル群へ変換する手法が **ER モデリング（Entity-Relationship Modeling）** です。

そして、設計したテーブルを実際の DBMS 上で動かし始めると、基本的な `SELECT / INSERT / UPDATE / DELETE` だけでは済まない次の **3つの実務上の要求** に直面します。

1. **見せ方の抽象化とアクセス制御（ビューと更新の制約）：** [8-1節](8-1.md)の外部スキーマを実現する「ビュー（仮想表）」は、参照するだけでなく `UPDATE` もできるのか？ どこまでが更新可能で、なぜ結合や集計を含むビューは更新できないのか。
2. **データ整合性や非正規化キャッシュの自動化（トリガ）：** [8-5節](8-5.md)で触れた `like_count` の自動更新や監査ログの記録を、アプリ側の書き忘れに頼らず DBMS 側で自動発動させるにはどうするか。
3. **階層データ・グラフデータの探索（再帰問合せ）：** [8-2](8-2.md)・[8-3節](8-3.md)で「一階述語論理（標準関係代数・関係論理）では表現できない」と証明された **推移閉包（組織の上司→部下ツリー、部品表 BOM）** を SQL でどう解くのか。

本節では、**ER モデリングとテーブル変換規則**、**SQL の論理評価順序**、**ビュー更新の制約**、**トリガ（ECA モデル）**、そして **再帰問合せ（`WITH RECURSIVE`）** を実践的な例と図解で整理します。

### 2. 具体例と動作イメージ（Toy Model）

規則の網羅に入る前に、2つの小さな例で「ER 図からテーブルへの自然な変換」と「SQL の評価順序によるよくあるエラー」を確かめます。

#### 実験A：大学の業務ルールを 3 つの要素（実体・関連・多重度）で整理する

ある大学の業務要件が次のように与えられたとします。

* **学科（`Dept`）** には複数の **学生（`Student`）** が所属するが、各学生は必ず 1 つの学科に所属する（**1 対多：`1 : N`**）。
* 1 人の **学生（`Student`）** は複数の **講義（`Course`）** を履修でき、1 つの講義も複数の学生に履修される（**多 対 多：`M : N`**）。履修ごとに成績 `grade` が付く。
* 1 つの **講義（`Course`）** には、年度と学期ごとに複数の **開講クラス（`Section`）** が開かれるが、`Section` は親の `Course` がなければ単独では識別できない（**弱実体**）。

これを ER 図として描いた瞬間、後述の機械的ルールによって「`Dept`」「`Student`（外部キー `dept_id` を持つ）」「`Course`」「`Enroll`（`sid, cid, grade` の中間テーブル）」「`Section`（`cid, year, term` の複合主キー）」という **最初から BCNF を満たす 5 枚のテーブル** が迷わず導き出せます。

#### 実験B：なぜ `WHERE` 句で `SELECT` の別名や `COUNT(*)` を使うとエラーになるのか

次の SQL クエリは、SQL を学び始めた人がほぼ全員一度は書くエラーコードです。

```sql
-- 失敗例：構文エラー（または列未定義エラー）になる
SELECT dept_id, COUNT(*) AS cnt
FROM Students
WHERE cnt >= 10           -- エラー：WHERE で SELECT の別名 cnt や COUNT(*) は使えない
GROUP BY dept_id;
```

なぜエラーになるのでしょうか。英語の語順に合わせて **`SELECT` を一番上に書く** のはあくまで見た目の記述順であり、DBMS がクエリを評価する **論理的な実行順序** では、**`WHERE` が `GROUP BY` や `SELECT` よりもずっと先に実行される** からです。

1. まず `FROM Students` でテーブル全体を用意します。
2. 次に `WHERE` で **個別の行** を絞り込みます（この時点ではまだグループ化も `COUNT(*)` も別名 `cnt` の付与も起きていません）。
3. 次に `GROUP BY dept_id` で学科ごとのグループへ束ね、`COUNT(*)` を計算します。
4. **グループ化した後の絞り込み** を行うのが **`HAVING COUNT(*) >= 10`** です。
5. 最後に `SELECT` で出力列を選び、`ORDER BY` で並べ替えます。

この論理評価順序を頭に入れておけば、`WHERE` と `HAVING` の使い分けや複雑な SQL の挙動に迷うことがなくなります。

### 3. 構造・アルゴリズム・実装（What）

#### (1) ER モデリング（実体関連モデル）と関係スキーマへの変換規則

1976年にピーター・チェン（Peter Chen）が提唱した **ER モデル（Entity-Relationship Model）** は、現実世界のデータ構造を次の構成要素で図式化します（図8-6-1左）。

* **実体集合（Entity Set：長方形）：** 独立して識別できる対象です（例：`Dept`, `Student`, `Course`）。主キー属性に下線を引きます。
* **関連集合（Relationship Set：ひし形）：** 実体同士の結びつきです（例：`BelongsTo`, `Enroll`）。関連自身が属性（例：`grade`）を持つこともできます。
* **多重度（Cardinality：カーディナリティ）：** 関連に参加する実体の個数比です（**`1 : 1`**、**`1 : N`**、**`M : N`**）。また、すべての実体が必ず関連に参加しなければならない制約を **全参加（Total Participation：二重線）** と呼びます。
* **弱実体集合（Weak Entity Set：二重長方形）：** 自分自身の属性だけでは一意に識別できず、親となる所有者実体の主キーと自分の **部分キー（破線下線）** を組み合わせて初めて識別できる実体です（例：講義 `CS101` の「2026年・春学期」クラス `Section`）。親との識別関連は二重ひし形で表します。

なお、実務の設計ツールでは、ひし形を省いて実体間の線の端に多重度を「一本線（1）」や「三叉（多＝カラスの足）」で表す **カラスの足記法（Crow's Foot / IE 記法）** も広く使われます。

描いた ER 図をリレーショナルデータベースのテーブル（概念スキーマ）へ変換する手順は、次の **4 つの機械的ルール** で体系化されています（図8-6-1右）。

1. **強い実体集合：** そのまま 1 枚のテーブルにし、主キーを設定します（例：`Dept(dept_id, bldg)`、`Student(sid, name)`、`Course(cid, title)`）。
2. **`1 : N`（1 対多）の関連：** 新しいテーブルを作らず、**「多（`N`）側」のテーブルへ「1 側」の主キーを外部キー（FK）として追加**します（例：`Student` テーブルへ `dept_id` を追加）。関連の属性も多側へ入れます。
3. **`M : N`（多 対 多）の関連：** **新しい中間テーブル（関連テーブル）を 1 枚作成**し、両側の主キーを外部キーかつ**複合主キー**として入れ、関連自身の属性（`grade`）もそこへ置きます（例：`Enroll(sid, cid, grade)`）。
4. **弱実体集合：** 弱実体用のテーブルを作成し、**所有者（親）の主キー（FK）＋ 自身の部分キー** を合わせて複合主キーとします（例：`Section(cid, year, term, room)`）。親削除時は `ON DELETE CASCADE` を設定します。

（※`1 : 1` の関連は、全参加側またはどちらか一方のテーブルへ相手の主キーを `UNIQUE` 制約付きの外部キーとして追加します。）

#### (2) 宣言的言語 SQL の構成と論理評価順序

**SQL（Structured Query Language）** は、次の3つのサブ言語で構成されます。

* **DDL（データ定義言語）：** `CREATE TABLE`, `ALTER TABLE`, `DROP TABLE`, `CREATE INDEX`, `CREATE VIEW`（スキーマと整合性制約の定義）。
* **DML（データ操作言語）：** `SELECT`, `INSERT`, `UPDATE`, `DELETE`（データの検索と更新）。
* **DCL / TCL（制御言語）：** `GRANT`, `REVOKE`（権限管理：[5-7節](../5/5-7.md)）、`BEGIN`, `COMMIT`, `ROLLBACK`（トランザクション制御：[第9部](../index.md#part-9)）。

なお、現代 SQL で広く活用される **ウィンドウ関数（Window Function：例として部門内累積和を求める `SUM(score) OVER (PARTITION BY dept_id ORDER BY sid)` や部門内順位を付ける `RANK() OVER (PARTITION BY dept_id ORDER BY score DESC)` など）** は、`GROUP BY` と違って行を 1 行へ潰さず、**元の全行を残したまま**各行へ累積和・ランキング・移動平均を付加できる機能であり、論理評価順序のステップ⑤（`SELECT` 段階）で評価されます。

#### (3) ビュー（View）と「ビュー更新の制約（View Update Problem）」

**ビュー（View）** は、`CREATE VIEW` で名前を付けて保存した `SELECT` クエリ（仮想テーブル）です。通常のビューはデータを物理的にコピーせず、参照されるたびに元のテーブル（基底表）に対するクエリへ展開されます（[8-1節](8-1.md)の **外部スキーマ** と **論理データ独立性**、および機密列を隠すセキュリティ保護を実現します）。

```sql
-- 成績や住所を隠して、図書館向けに学生の基本情報だけを見せるビュー
CREATE VIEW LibraryStudents AS
SELECT sid, name, dept_id FROM Students WHERE dept_id = 'CS';
```

ここで重要な理論的・実務的課題が **ビュー更新問題（View Update Problem）** です。「ビューに対して `INSERT` や `UPDATE` や `DELETE` を実行したら、元の基底表をどう書き換えるべきか？」という問いです。

* **更新可能なビュー（単純な単表ビュー）：**
    上の `LibraryStudents` のように、**単一の基底表**に対する単純な選択（`WHERE`）と射影（主キーを含む列）だけで作られたビューであれば、ビュー上の 1 行が基底表の 1 行へ 1 対 1 で一意に対応するため、`UPDATE LibraryStudents SET name = 'Alicia' WHERE sid = 101;` を基底表 `Students` への更新へ一意に翻訳できます（※`WITH CHECK OPTION` を付けておけば、ビューの `WHERE dept_id = 'CS'` 条件を外れるような不正な更新も弾けます）。

* **更新不可能なビュー（逆写像が一意に定まらないケース）：**
    次のいずれかを含むビューは、基底表への翻訳先が数学的に一意に定まらない（あるいは矛盾する）ため、標準 SQL では原則として直接更新が禁止されています。

    1. **集約・`GROUP BY`・`DISTINCT` を含むビュー：** たとえば `DeptAvg(dept_id, avg_gpa)` の平均値 `avg_gpa` を `3.2 → 3.5` に書き換えよと言われても、どの学生の成績をどれだけ変えればよいか無限の候補があり一意に決まりません。
    2. **複数テーブルの結合（`JOIN`）を含むビュー：** `StudentDept(sid, name, dept_id, bldg)` に対して 1 行 `DELETE` したとき、`Students` の行だけ消すのか `Depts` の学科ごと消すのかが一意に決まらず、さらに `bldg` を書き換えると他の全 CS 学生の建物まで波及してしまいます。
    3. **基底表の `NOT NULL` かつデフォルト値のない列（特に主キー）を含まないビューへの `INSERT`：** 基底表へ挿入する際に必須列を埋められません。

#### (4) トリガ（Trigger：ECA モデル）とストアドプロシジャ

**トリガ（Trigger）** は、テーブルへの特定イベント（`INSERT` / `UPDATE` / `DELETE`）が発生した瞬間に、DBMS が自動的に指定した処理を実行する能動的な仕組みです。構造は次の **ECA モデル（Event - Condition - Action）** で整理されます。

* **Event（事象）：** いつ発動するかを指定します（例：`AFTER INSERT ON Likes`、`BEFORE UPDATE ON Accounts`）。
* **Condition（条件）：** どの条件を満たすとき実行するかを指定します（例：`WHEN (NEW.balance < 0)`）。
* **Action（動作）：** 何を実行するかを指定します（`FOR EACH ROW`＝変更された各行ごと、または `FOR EACH STATEMENT`＝SQL 1 文につき 1 回）。

[8-5節](8-5.md)で学んだ「意図的な非正規化キャッシュ（`Posts.like_count`）」をトリガで自動同期する例は次の通りです。

```sql
CREATE TRIGGER inc_like_count
AFTER INSERT ON Likes
FOR EACH ROW
BEGIN
    UPDATE Posts SET like_count = like_count + 1
    WHERE post_id = NEW.post_id;
END;
```

これにより、どのアプリケーションから `Likes` へ `INSERT` されても、同一トランザクション内で確実に `like_count` が `+1` され、更新時異常を防げます。

なお、イベント駆動で自動発動するトリガに対し、複数の SQL 文と分岐・ループ処理を名前付き手続きとして DBMS 内部へ事前登録し、アプリケーションから明示的に呼び出す仕組みを **ストアドプロシジャ（Stored Procedure）** と呼びます。クライアントとの通信往復を減らせる利点がある一方、トリガと同様に業務ロジックが DB 側とアプリ側へ分散する保守上のトレードオフがあります。

#### (5) 共通テーブル式（CTE）と再帰問合せ（`WITH RECURSIVE`）

複雑な副問合せに名前を付けて一時的な仮想表として見通しよく記述する構文が **共通テーブル式（CTE：Common Table Expression、`WITH` 句）** です。さらに [8-2節](8-2.md)・[8-3節](8-3.md)で確認した「標準の関係代数や一階述語論理では深さが事前に分からない階層構造（推移閉包）を検索できない」という壁を超えるため、CTE を自己参照へ拡張したのが **再帰共通テーブル式（Recursive CTE：`WITH RECURSIVE`）** です（図8-6-3）。

従業員と直属上司の表 `Emp(emp_id, name, mgr_id)` に対して、「社長（`emp_id = 1`）の配下にいる**すべての部下（孫・ひ孫を含む全員）**と階層深さ」を求めるクエリは次の 2 部構成で書きます。

```sql
WITH RECURSIVE Subordinates(emp_id, name, depth) AS (
    -- ① 基底部（アンカーメンバ）：再帰の出発点（深さ 0 の社長本人）
    SELECT emp_id, name, 0
    FROM Emp
    WHERE emp_id = 1

    UNION ALL

    -- ② 再帰部（リカーシブメンバ）：直前のステップで見つかった人の部下を結合
    SELECT e.emp_id, e.name, s.depth + 1
    FROM Emp AS e
    JOIN Subordinates AS s ON e.mgr_id = s.emp_id
)
SELECT * FROM Subordinates;
```

DBMS はこれを **幅優先の反復不動点計算** として実行します（[8-3節](8-3.md)の Datalog のボトムアップ評価と完全に同型です）。

1. まず基底部を実行して作業テーブル $W_0 = \{ (1, \text{社長}, 0) \}$ を作り、結果集合 $R$ へ追加します。
2. 次に再帰部で $W_0$ と `Emp` を結合し、社長の直属部下 $W_1 = \{ (2, \text{部長A}, 1), (3, \text{部長B}, 1) \}$ を得て $R$ へ追加します。
3. 同様に $W_1$ から $W_2$（課長ら）を得て $R$ へ追加し、次の反復で**新しく見つかる行が空（図8-6-3の例では $W_3 = \emptyset$：不動点に到達）** になった瞬間に停止して全体の $R$ を返します（さらに深い階層があれば $W_k = \emptyset$ になるまで反復が続きます）。

> **【コラム：SQL インジェクションとプリペアドステートメント：「構文木（AST）」と「データ」の分離】**
>
> Web アプリケーションで最も深刻かつ古典的な脆弱性の 1 つが **SQL インジェクション** です。アプリ側でユーザ入力 `name` を文字列結合して
> ```sql
> "SELECT * FROM Users WHERE name = '" + user_input + "';"
> ```
> のように SQL 文を組み立てると、攻撃者が `user_input` に **`' OR '1'='1`** や **`'; DROP TABLE Users; --`** を入力した瞬間、本来「データ（文字列リテラル）」であるはずの入力が **SQL の構文（命令）として構文解析されてしまい**、認証突破や全データ流出・テーブル破壊が起きます。
>
> これに対する根本的かつ完全な対策が **プリペアドステートメント（Prepared Statement / バインド変数）** です。
> ```sql
> PREPARE stmt FROM 'SELECT * FROM Users WHERE name = ?';
> EXECUTE stmt USING @user_input;
> ```
> なぜこれで SQL インジェクションが 100% 不可能になるのかは、**[第2部](../index.md#part-2)（[2-3節](../2/2-3.md)：構文解析と AST）** を学んだ今なら明快に理解できます。プリペアドステートメントでは、ユーザ入力を受け取る**より前**に `SELECT ... WHERE name = ?` だけを字句解析・構文解析して **抽象構文木（AST）と実行計画を確定** してしまいます。あとから渡される `@user_input` は、すでに完成した AST の葉ノード `?` へ「ただの文字列値」として流し込まれるだけで二度と構文解析されないため、中に `'` や `OR` や `;` が何個入っていようと絶対に命令へ化けることがないのです。

### 4. 限界と補正（Critique & Adaptation）

#### (1) トリガの乱用が招く「隠れた副作用と連鎖爆発」

トリガは便利ですが、大規模なシステムで業務ロジックを大量にトリガへ書き込むと、次の深刻な保守性・性能問題を引き起こします。

* アプリケーションコードを読んでも「なぜ `INSERT INTO Likes` しただけで別の 3 テーブルまで書き換わったのか」が見えず、バグの原因追跡が非常に難しくなります。
* テーブル A のトリガがテーブル B を更新し、B のトリガが再び A を更新する **無限カスケードループ** や予期せぬロック競合・デッドロックを生みます。

**補正：** 単純な制約や計算列にはトリガを使わず、宣言的な **`CHECK` 制約・`FOREIGN KEY (ON DELETE CASCADE)`・生成列（`GENERATED ALWAYS AS (...) STORED`）** を優先します。業務上の複雑なワークフローはアプリケーション層のトランザクション内で明示的に記述し、トリガは監査ログや小規模な不変条件の維持など最小限の用途へ限定するのが実務の定石です。

#### (2) 再帰問合せにおける「循環グラフの無限ループ」と「DAG での結果爆発」

図8-6-3の組織図のように閉路のない木構造（または有向非巡回グラフ：DAG）であれば `WITH RECURSIVE` は必ず有限回で停止します。ただし、一般のグラフでは次の 2 つの問題が生じます。

* **循環（サイクル）による無限ループ：** SNS のフォロー関係や道路網グラフのように **`A → B → C → A` という閉路** を含むデータへ `UNION ALL` の再帰クエリを実行すると、永遠に同じノードを回り続けてメモリ枯渇やタイムアウトに陥ります。
* **合流経路を持つ DAG での結果爆発：** 閉路がなくても、部品表（BOM）のように複数経路が合流する一般の DAG では、`UNION ALL` を使うと同じノードが経路の組み合わせ数だけ重複展開され、行数が指数的に膨らむことがあります。

**補正：** 循環や合流があり得るデータでは、次のいずれかを必ず組み込みます。

1. `UNION ALL` の代わりに **`UNION`**（重複行を自動排除）を使い、すでに訪れた頂点を再展開しないようにします（ただし `depth` のように毎回変わる列を出力に含めると重複とみなされず止まらない点に注意します）。
2. PostgreSQL 14+ や標準 SQL:1999 の **`CYCLE emp_id SET is_cycle USING path`** 句（または訪問済み ID 配列 `NOT (e.emp_id = ANY(s.path))`）および **深さ上限 `WHERE s.depth < 100`** を明示します。

#### (3) インピーダンス・ミスマッチ（ORM と N+1 問題）

オブジェクト指向言語（Java, Python, TypeScript 等）のメモリ上ではデータはポインタで結ばれた複雑なオブジェクトグラフですが、RDBMS の世界は平坦な 2 次元テーブルの集合です。この表現モデルのズレを **オブジェクト・リレーショナル・インピーダンス・ミスマッチ** と呼びます。

このズレを埋める **ORM（Object-Relational Mapping）** を使うと、うっかりループの中で関連オブジェクトを遅延読み込みしてしまい、「1 回の親リスト取得 `SELECT` のあとに、子要素を取得する `SELECT` を $N$ 回連続発行して極端に遅くなる（**N+1 問題**）」が頻発します。補正として、最初から SQL の `JOIN` や `WHERE id IN (...)` で 1〜2 回のクエリへまとめる（Eager Loading）意識が不可欠です。
