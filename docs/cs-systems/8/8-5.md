### 前節（8-4）の確認問題の解答

前節の最後に提示した3つの問いの解答を確認します。問3がそのまま本節（BCNF・4NF・5NF と非正規化）の導入になります。

1. **複数候補キーの導出と 2NF・3NF の精密判定（$R(A, B, C, D, E)$、$F = \{\, AB \to C,\; C \to D,\; D \to B,\; A \to E \,\}$）：**

    * **(a) 候補キーの導出（3 つ）：**
        与えられた FD の右辺に現れる属性は $\{B, C, D, E\}$ であり、**$A$ はどの FD の右辺にも一度も現れません**。したがって $A$ はすべての候補キーに必ず含まれます。まず $\{A\}^+ = \{A, E\} \neq R$ なので $A$ 単体では候補キーにならず、残りの属性から 1 つ補って閉包を計算します（$E$ はどの左辺にも現れないため補っても増えません）。

        * $\{A, B\}^+$：$\{A, B\} \xrightarrow{AB \to C} \{A, B, C\} \xrightarrow{C \to D} \{A, B, C, D\} \xrightarrow{A \to E} \{A, B, C, D, E\} = R$（極小）
        * $\{A, C\}^+$：$\{A, C\} \xrightarrow{C \to D} \{A, C, D\} \xrightarrow{D \to B} \{A, B, C, D\} \xrightarrow{A \to E} \{A, B, C, D, E\} = R$（極小）
        * $\{A, D\}^+$：$\{A, D\} \xrightarrow{D \to B} \{A, B, D\} \xrightarrow{AB \to C} \{A, B, C, D\} \xrightarrow{A \to E} \{A, B, C, D, E\} = R$（極小）

        よって、$R$ の候補キーは **`{A, B}`, `{A, C}`, `{A, D}`** の 3 つです。

    * **(b) 2NF 違反と、$D \to B$ が 3NF に違反しない理由：**
        素属性（いずれかの候補キーに含まれる属性）は $A, B, C, D$ の 4 つで、非素属性は **$E$ のみ**です。

        * **2NF に違反する部分関数従属：** **`A → E`** です。非素属性 $E$ が、候補キー（`{A, B}` 等）の真部分集合である $A$ だけに従属しています。
        * **$D \to B$ が 3NF の一般定義に違反しない理由：** 3NF の一般定義は「すべての非自明な FD $X \to Y$ について、① $X$ がスーパーキーである、または ② $Y$ が素属性である」の少なくとも一方を満たすことです。$D \to B$ の左辺 $D$ はスーパーキーではありません（$D^+ = \{D, B\} \neq R$）が、右辺の **$B$ が候補キー `{A, B}` の一部である素属性**なので条件 ② を満たし、3NF には違反しません。

2. **`OrderDetail` の 3NF 分解・履歴データの業務判断・損失結合の反例構成：**

    * **(a) 3NF の 4 テーブル分解と履歴保持の業務判断：**

        * **① 3NF の 4 テーブル（無損失・従属性保存）：**

            * **`OrderItems`**(`PK: order_id, item_id`, `FK: order_id -> Orders.order_id`, `FK: item_id -> Items.item_id`, `qty`)
            * **`Items`**(`PK: item_id`, `item_name`, `unit_price`)
            * **`Orders`**(`PK: order_id`, `FK: cust_id -> Customers.cust_id`, `ship_city`)
            * **`Customers`**(`PK: cust_id`, `cust_city`)

        * **② 注文時点の単価や `ship_city` を注文側へ保持すべき理由：**
            後日、商品マスタの価格改定（値上げ・値下げ）や顧客の引っ越し（`cust_city` の更新）が起きても、過去の注文の請求額や実際に配送した住所が書き換わってはなりません。注文時点の単価や配送先 `ship_city` はマスタの現在値ではなく「その注文・明細時点に固有の事実」であり、時間軸を含めた業務上の意味では注文キー（または明細キー）に完全関数従属しているため、注文側へ保持する設計が妥当です。

    * **(b) $R(A, B, C)$（$A \to B$ のみ）に対する損失結合の 2 行反例：**
        たとえば $r = \{(a_1, b_1, c_1),\; (a_2, b_1, c_2)\}$ とおきます（$A$ の値が相異なるため $A \to B$ を満たします）。このとき $\pi_{A, B}(r) = \{(a_1, b_1),\; (a_2, b_1)\}$、$\pi_{B, C}(r) = \{(b_1, c_1),\; (b_1, c_2)\}$ となり、自然結合をとると

        $$\pi_{A, B}(r) \bowtie \pi_{B, C}(r) = \bigl\{\, (a_1, b_1, c_1),\; (a_2, b_1, c_2),\; \mathbf{(a_1, b_1, c_2)},\; \mathbf{(a_2, b_1, c_1)} \,\bigr\}$$

        となって元の $r$ に存在しない 2 行の偽タプルが生じます。

3. **`Addr(zip, city, street)` の分解で関数従属性が失われる具体反例（本節への接続）：**
    `R1(PK: zip, city)` に `(220-0012, 横浜)` と `(220-9999, 横浜)`、`R2(PK: zip, street)` に `(220-0012, みなとみらい1丁目)` と `(220-9999, みなとみらい1丁目)` を格納します。`R1` では `zip` が重複せず、`R2` でも `(zip, street)` が重複しないため各表の主キー制約は満たしますが、自然結合 `R1 ⋈ R2` をとると `(220-0012, 横浜, みなとみらい1丁目)` と `(220-9999, 横浜, みなとみらい1丁目)` が得られ、同じ `(横浜, みなとみらい1丁目)` に 2 つの郵便番号が対応して元の制約 `(city, street) → zip` に違反します。このように 3NF からさらに冗長性を断つ **BCNF** と従属性保存のトレードオフが、本節の最初のテーマです。

## 8-5. 正規化②：BCNF・多値従属性（4NF）・結合従属性（5NF）と非正規化

### 1. 動機（Why）：なぜ「3NF で終わり」ではなく BCNF・4NF・5NF があり、逆に「あえて崩す」こともあるのか

前節（[8-4節](8-4.md)）では、関数従属性（FD）を武器にして 1NF → 2NF → 3NF へとテーブルを無損失分解し、典型的な3大更新時異常（更新・挿入・削除）を解消しました。

しかし、データベース設計の理論には、3NF の先になお **2つの見落としやすい盲点** が残っています。

1. **盲点1（複数の候補キーが重なるとき）：** 3NF の定義には「右辺 $A$ が素属性（いずれかの候補キーの一部）なら、左辺 $X$ がスーパーキーでなくても許す」という例外条項がありました。そのため、複数の候補キーが属性を共有して重なり合う表では、**3NF を満たしているのに更新時異常がそのまま残る**ケースがあります（$\implies$ **BCNF** による解決）。
2. **盲点2（関数従属性が 1 本もないのに起きる直積爆発）：** 1つの表の中に「互いに無関係な 2 つの多値（1対多）の事実」を同居させると、非自明な FD は 1 本も存在しない（したがって BCNF すら合格する）にもかかわらず、組み合わせの直積によって行数が爆発し、深刻な更新時異常が起きます（$\implies$ **4NF・5NF** による解決）。

そしてもう1つ、理論を整理した直後に必ず直面する**実務上の逆向きの問い**があります。
「高次の BCNF や 5NF まで細分化すれば、どんなシステムでも常に最良なのか？」
答えは「いいえ」です。表を細かく分けるほど、検索のたびに何枚もの表を結合（$\bowtie$）しなければならず、アクセスが集中する画面や集計クエリが遅くなることがあります。

本節では、まず **BCNF・4NF・5NF** によって正規化の包含階層 $\text{5NF} \subset \text{4NF} \subset \text{BCNF} \subset \text{3NF} \subset \text{2NF} \subset \text{1NF}$ を完成させたうえで、実務で求められる **意図的な非正規化** の判断基準と安全に運用するための補正策を整理します。

---

### 2. 具体例と動作イメージ（Toy Model）

厳密な定義に入る前に、前節の最後で予告した「3NF の盲点」と「BCNF の盲点」を 2 つの小さなテーブルで直接確かめます。

#### 実験A：3NF には合格するのに更新時異常が残る表 `Addr(city, street, zip)`

前節のコラムで登場した住所テーブル `Addr(city, street, zip)` をもう一度詳しく観察します。この表には次の2本の関数従属性（FD）が成り立っています。

* $f_1$：`city, street → zip`（市と通りの組が決まれば、郵便番号が一意に決まります）
* $f_2$：`zip → city`（郵便番号が決まれば、市が一意に決まります）

| `city` | `street` | `zip` |
| :--- | :--- | :---: |
| 横浜 | みなとみらい1丁目 | `220-0012` |
| 横浜 | みなとみらい2丁目 | `220-0012` |
| 横浜 | みなとみらい3丁目 | `220-0012` |
| 東京 | 丸の内1丁目 | `100-0005` |

この表の候補キーは **`{city, street}`** と **`{zip, street}`** の 2 つです（どちらの閉包も全 3 属性になります）。したがって、全属性 `city`, `street`, `zip` がすべて **素属性**（候補キーの一部）であり、非素属性が 1 個も存在しません。

* **3NF の判定：** 3NF の条件「すべての非自明な FD $X \to A$ について、$X$ がスーパーキー **または $A$ が素属性**」を照合すると、`zip → city` の右辺 `city` が素属性なので **3NF 合格** になります。
* **しかし残る異常：** 表を見れば明らかな通り、`zip = 220-0012` に属する通りが 50 本あれば、「`220-0012` は `横浜` である」という事実が 50 回も重複します。市町村合併で市名が変わったときに 1 行でも更新漏れがあれば矛盾（更新異常）が起き、通りのない郵便番号は登録できません（挿入異常）。

原因は、**「スーパーキーではない `zip` が決定項（左辺）になっている FD（`zip → city`）」**を 3NF が見逃したことにあります。

#### 実験B：BCNF にすら合格するのに「直積」で崩壊する表 `ProfInfo(prof, course, book)`

次に、大学教員 `prof` について「担当している講義 `course`」と「執筆した書籍 `book`」を 1 枚の表 `ProfInfo(prof, course, book)` にまとめたとします。ただし、担当講義と執筆書籍は**互いに独立**（どの本もどの講義にも縛られない）とします。

もし教員 `Sato` が 2 科目（`OS`, `DB`）を担当し、3 冊の本（`Book1`, `Book2`, `Book3`）を執筆していると、どの組み合わせも等価なため、表の中には $2 \times 3 = \mathbf{6\text{ 行}}$ の直積を入れざるを得なくなります。

| `prof` | `course` | `book` |
| :--- | :---: | :--- |
| Sato | `OS` | `Book1` |
| Sato | `OS` | `Book2` |
| Sato | `OS` | `Book3` |
| Sato | `DB` | `Book1` |
| Sato | `DB` | `Book2` |
| Sato | `DB` | `Book3` |

* **BCNF の判定：** 1 人の教員が複数科目を担当し複数書籍を執筆するため、`prof → course` も `prof → book` も成り立ちません。この表には**非自明な関数従属性が 1 本も存在せず**、唯一の候補キーは全 3 属性 `{prof, course, book}` です。したがって、この表は **3NF どころか BCNF すら無条件で合格** します。
* **しかし起きる深刻な異常：** もし `Sato` が新しく 4 冊目の本 `Book4` を出版したら、担当科目すべてに対して `(Sato, OS, Book4)` と `(Sato, DB, Book4)` の **2 行を漏れなく同時挿入**しなければならず、1 行でも抜けると「`Book4` は `OS` だけに関係するのか？」という偽の相関が生まれて矛盾します。もし担当科目が 5 個・書籍が 10 冊なら $5 \times 10 = 50$ 行に膨らみますが、2 つの表 `Teaches(prof, course)`（5 行）と `Authors(prof, book)`（10 行）へ分ければ合計わずか **15 行** になり、異常も解消されます。

### 3. 構造・アルゴリズム・実装（What）

#### (1) ボイス＝コッド正規形（BCNF）と「従属性保存」のトレードオフ

実験Aの異常を排除するために、1974年にレイモンド・ボイスと E. F. Codd が定義したのが、3NF から例外条項を取り除いた **ボイス＝コッド正規形（BCNF：Boyce-Codd Normal Form）** です。

> **【定義：BCNF】**
> 関係 $R$ が **BCNF** であるとは、$R$ 上で成り立つすべての非自明な関数従属性 $X \to A$（$A \notin X$）について、必ず **「$X$ が $R$ のスーパーキーである」** ことである。

**BCNF 分解アルゴリズム（常に無損失結合）：**
もし BCNF に違反する非自明な FD $X \to Y$（$X$ がスーパーキーでない）が見つかったら、$R$ を次の 2 表へ分解します（違反がなくなるまで繰り返します）。

$$
R_1 = X \cup Y, \qquad R_2 = (R \setminus Y) \cup X
$$

2 表の共通属性は $R_1 \cap R_2 = X$ であり、$X \to Y$ より $X \to R_1$ が成り立つため、[8-4節](8-4.md)の無損失条件を満たし、**BCNF 分解は常に無損失結合分解になる**ことが保証されます。なお、分解後の各部分表 $R_i$ が BCNF を満たすかを再検査する際は、元の入力 $F$ に直接書かれた FD だけでなく、**閉包 $F^+$ から $R_i$ の属性だけへ射影して得られるすべての非自明な FD（$F_i = \{\, U \to V \in F^+ \mid UV \subseteq R_i \,\}$）**を検査する必要があります（推移的に導かれる FD が $R_i$ 内部で BCNF 違反を起こすことがあるためです）。

では、実験Aの `Addr(city, street, zip)` に BCNF 分解を適用してみます（図8-5-1）。
違反している FD は `zip → city`（$X = \{\text{zip}\}, Y = \{\text{city}\}$）なので、次の 2 表へ分解されます。

* $R_1(\underline{\text{zip}},\; \text{city})$（FD：`zip → city` を保持します）
* $R_2(\underline{\text{zip},\; \text{street}})$（非自明な FD はありません）

どちらも BCNF を満たし、「`220-0012`＝`横浜`」の重複は解消され、自然結合 $R_1 \bowtie R_2$ で元の表も完全に復元（無損失）できます。

しかしここで、[8-4節](8-4.md)の問い 3 で確認した **「BCNF の代償」** が現れます。元の表にあったもう 1 本の重要な業務ルール **`(city, street) → zip` が、$R_1$ の中にも $R_2$ の中にも収まらなくなり、従属性保存（Dependency Preservation）が壊れてしまった** のです。
そのため、`R_1` に `(220-0012, 横浜)` と `(220-9999, 横浜)` が入っている状態で、`R_2` へ `(220-0012, みなとみらい1丁目)` と `(220-9999, みなとみらい1丁目)` の 2 行を挿入すると、それぞれの表の主キー制約には違反しないのに、自然結合した瞬間に「同じ `(横浜, みなとみらい1丁目)` に 2 つの郵便番号が存在する」という **`(city, street) → zip` 違反がすり抜けてしまいます**。

このように、**「無損失結合」「従属性保存」「FD 冗長性ゼロ（BCNF）」の 3 つは、一般には同時達成できない**ことが数学的に知られています。したがって実務では、まず BCNF 分解を試し、もし重要な業務ルール（FD）の従属性保存が壊れてしまう場合だけ、あえて **3NF に留める** という設計判断を行います。

#### (2) 第4正規形（4NF）と多値従属性（MVD：$X \twoheadrightarrow Y$）

次に、実験Bの `ProfInfo(prof, course, book)` のように、BCNF を満たしているのに直積で爆発する異常を扱うのが **多値従属性（MVD：Multivalued Dependency）** と **第4正規形（4NF）** です（1977年 Ronald Fagin）。

> **【定義：多値従属性 $X \twoheadrightarrow Y$】**
> 関係 $R(X, Y, Z)$（$Z = R \setminus (X \cup Y)$）において、ある $X$ の値に対して決まる $Y$ の値の集合が、残りの属性 $Z$ の値と**完全に独立**であるとき（すなわち、同じ $X$ の値を持つ任意の 2 タプル $(x, y_1, z_1), (x, y_2, z_2) \in r$ に対し、$Y$ と $Z$ を入れ替えた $(x, y_1, z_2)$ と $(x, y_2, z_1)$ も必ず $r$ に存在するとき）、**$X$ が $Y$ を多値決定する**といい、**$X \twoheadrightarrow Y$** と書く。

定義の対称性から、$X \twoheadrightarrow Y$ が成り立つとき必ず相方の **$X \twoheadrightarrow Z$** も同時に成り立ちます（まとめて $X \twoheadrightarrow Y \mid Z$ と書くことも多いです）。また、通常の関数従属性 $X \to Y$ は「$X$ に対して $Y$ の集合の要素数が常に 1 個である」特殊なケースなので、**すべての FD は MVD の一種（$X \to Y \implies X \twoheadrightarrow Y$）** です。

ここで重要なのは、多値従属性 $X \twoheadrightarrow Y$（ただし $Z = R \setminus (X \cup Y)$）が成り立つことと、2 表への射影分解 $R = \pi_{X \cup Y}(R) \bowtie \pi_{X \cup Z}(R)$ が**無損失結合分解になることが数学的に必要十分（同値）である**という性質です。

$$
X \twoheadrightarrow Y \quad \iff \quad R \;=\; \pi_{X \cup Y}(R) \bowtie \pi_{X \cup Z}(R)
$$

実験Bでは、`prof` に対して `course` の集合と `book` の集合が独立なので、**`prof` $\twoheadrightarrow$ `course`** および **`prof` $\twoheadrightarrow$ `book`** が成り立ちます。

> **【定義：第4正規形（4NF）】**
> 関係 $R$ が **4NF** であるとは、$R$ 上で成り立つすべての **非自明な多値従属性** $X \twoheadrightarrow Y$（ここで「自明」とは $Y \subseteq X$ または $X \cup Y = R$ のこと）について、**$X$ が $R$ のスーパーキーである** ことである。

実験Bでは `prof` $\twoheadrightarrow$ `course` が非自明（`course` $\not\subseteq$ `prof` かつ `prof` $\cup$ `course` $\neq$ 全3属性）なのに、`prof` がスーパーキーではないため **4NF 違反** となります。上の同値性より、4NF 分解によって `Teaches(prof, course)` と `Authors(prof, book)` へ切り分ければ無損失結合が保証され、直積 6 行が 2 行＋3 行の 5 行へ分離されて更新異常が解消されます（図8-5-2）。

#### (3) 第5正規形（5NF / PJNF）と結合従属性（JD）および正規形の包含階層

前項で見た通り、4NF までは多値従属性 $X \twoheadrightarrow Y$ に基づいて「1枚の表を **2 枚の表** へ無損失分解する」枠組みでした。

ところが稀に、**「どの 2 枚の表へ切っても損失分解（偽タプル発生）になってしまうが、3 枚の表へ切って自然結合すれば完全に無損失復元できる」** という特殊な 3 項関係が存在します。

典型例が、`AgentCompanyProduct(agent, company, product)`（代理店 `agent`、メーカー `company`、製品 `product`）であり、次の循環的な業務ルールが成り立つケースです。

> 「代理店 $a$ がメーカー $c$ の特約店であり、かつメーカー $c$ が製品 $p$ を製造しており、かつ代理店 $a$ が製品 $p$ の取扱資格を持つならば、必ず代理店 $a$ はメーカー $c$ の製品 $p$ を販売する。」

次の **4 行の具体テーブル $R$** で、2 表分解の失敗と 3 表分解の成功を直接確認してみます。

| `agent` | `company` | `product` |
| :---: | :---: | :---: |
| `A1` | `C1` | `P1` |
| `A1` | `C2` | `P2` |
| `A2` | `C1` | `P2` |
| `A1` | `C1` | `P2` |

この 4 行を 3 つの 2 列射影へ分けます。

* $R_1 = \pi_{\text{agent, company}}(R) = \{(\text{A1, C1}),\; (\text{A1, C2}),\; (\text{A2, C1})\}$
* $R_2 = \pi_{\text{company, product}}(R) = \{(\text{C1, P1}),\; (\text{C2, P2}),\; (\text{C1, P2})\}$
* $R_3 = \pi_{\text{agent, product}}(R) = \{(\text{A1, P1}),\; (\text{A1, P2}),\; (\text{A2, P2})\}$

まず **任意の 2 表の自然結合** を計算すると、いずれも元の 4 行に存在しない **偽タプルが 1 行ずつ混入（5 行）** してしまいます。

* $R_1 \bowtie R_2$：`company = C1` で `(A2, C1)` と `(C1, P1)` が結びつき、偽タプル **`(A2, C1, P1)`** が発生します（`A2` は `P1` の取扱資格がありません）。
* $R_2 \bowtie R_3$：`product = P2` で `(C2, P2)` と `(A2, P2)` が結びつき、偽タプル **`(A2, C2, P2)`** が発生します（`A2` は `C2` の特約店ではありません）。
* $R_1 \bowtie R_3$：`agent = A1` で `(A1, C2)` と `(A1, P1)` が結びつき、偽タプル **`(A1, C2, P1)`** が発生します（`C2` は `P1` を製造していません）。

どの 2 表分解も損失結合になるため非自明な MVD は存在せず、この表は **4NF を満たしています**。ところが、$R_1 \bowtie R_2$ の 5 行へさらに **$R_3$ を自然結合**すると、`(A2, P1)` は $R_3$ に存在しないため偽タプル `(A2, C1, P1)` が綺麗に弾かれ、**元の 4 行と完全に一致**します。

$$
R \;=\; R_1 \bowtie R_2 \bowtie R_3
$$

このような「複数の射影の自然結合で元と完全に一致する」という一般化された制約を **結合従属性（JD：Join Dependency：$\bowtie(R_1, R_2, \dots, R_n)$）** と呼びます。そして、**「すべての非自明な結合従属性が候補キーによって論理的に含意されている（すなわち、これ以上射影分解して情報重複を減らせる余地がない）」** 状態が **第5正規形（5NF：射影結合正規形［PJNF］）** です。

こうして、関係データベース理論における **正規形の厳密な包含階層** が完成します（図8-5-3）。

$$
\text{5NF} \;\subset\; \text{4NF} \;\subset\; \text{BCNF} \;\subset\; \text{3NF} \;\subset\; \text{2NF} \;\subset\; \text{1NF}
$$

> **【コラム：有名な法廷宣誓の暗記法「The Key, the Whole Key, and Nothing but the Key」】**
>
> データベース設計の現場で、1NF〜BCNF のエッセンスを一瞬で思い出すために広く知られている英語のフレーズがあります（ウィリアム・ケント、1983年。米国の法廷証言の誓い *"the truth, the whole truth, and nothing but the truth, so help me God"* のもじりです）。
>
> > 「すべての非キー属性は、**キー**（1NF）、**キー全体**（2NF：部分従属の禁止）、**そしてキーのみ**（3NF/BCNF：推移従属および非スーパーキー決定項の禁止）に従属しなければならない、**コッドにかけて（so help me Codd）**。」
>
> この 1 文が表している通り、正規化の本質は「**1 つの事実はデータベース内のたった 1 箇所にだけ記録する（Single Source of Truth）**」というソフトウェア工学の原則を、数学的な関数従属性・多値従属性として定式化したものです。

### 4. 限界と補正（Critique & Adaptation）

#### (1) 過度な正規化の代償：読み取り時の `JOIN` コスト増大

BCNF や 4NF まで徹底的に正規化すると、データの重複がゼロになり、`INSERT` / `UPDATE` / `DELETE` の整合性管理は一貫して保ちやすくなります。

ところが、**読み取り（`SELECT`）の性能**という視点で見ると、正規化には明確な代償があります。もともと 1 枚の表にまとまっていた情報が 5 枚・6 枚の表へ分割されるため、画面を 1 回表示するたびに毎回 **5 表の `JOIN`（結合演算）** を実行しなければならなくなるのです。アクセスが毎秒数万回集中する EC サイトのトップページや SNS のタイムラインでは、毎回巨大なテーブル同士を `JOIN` して集計していては CPU とディスク I/O がボトルネックとなり処理が滞ります。

#### (2) 意図的な非正規化（Denormalization）の 3 パターンと補正策

そこで実務のデータベース設計では、**「まず BCNF / 3NF で正規化したスキーマを設計し、実際のボトルネックを計測した箇所に限り、性能要件を満たすためにあえて冗長なデータを持たせる」** という **意図的な非正規化（Denormalization）** を行います。代表的なパターンは次の 3 つです。

1. **集計値のキャッシュ列：** SNS の投稿テーブル `Posts` に、毎回 `Likes` テーブルを `COUNT(*)` する代わりに `like_count` 列を直接持たせます。
2. **歴史的スナップショットの保持（業務上の固有事実）：** 注文明細テーブル `OrderItems` に、商品マスタ `Items` の `price` を参照するだけでなく、**注文時点の単価 `unit_price_at_order`** をコピーして持ちます。これは単なる性能目的ではなく、「後日商品の定価が値上げされても過去の請求額が変わってはならない」という業務上の不変要件でもあります（時間軸を含めれば `unit_price_at_order` は `(order_id, item_id)` に完全関数従属しており、実質的に正規化違反ではありません）。
3. **事前結合テーブル・読み取り専用サマリ表：** 頻繁に参照される複数表の結合結果を、あらかじめ 1 枚の表へ展開しておきます。

**非正規化の代償に対する補正：**
非正規化を行うと、当然ながら **[8-4節](8-4.md)の更新時異常（重複データの矛盾）が復活** します。そのため、非正規化を安全に運用するには必ず次のいずれかの補正とセットにします。

* **トランザクション（[第9部](../index.md#part-9)）＋トリガ（[8-6節](8-6.md)）：** `Likes` へ 1 行 `INSERT` するのと同じトランザクション内で `Posts.like_count` を `+1` する処理を自動化し、不整合を防ぎます。
* **マテリアライズドビュー（Materialized View）：** 元の正規化テーブルを「唯一の正（Single Source of Truth）」として保ったまま、DBMS 側が結合・集計済みの結果を物理テーブルとして自動キャッシュ・定期更新します。
* **OLTP と OLAP の分離（CQRS［コマンドクエリ責務分離：更新用と参照用のモデルを分離する設計］／データウェアハウス）：** 日常の更新処理（OLTP：オンライン決済や在庫更新）は **BCNF / 3NF** で整合性を守り、大量データの過去分析（OLAP：売上レポート）は別系統の **スタースキーマ（意図的に非正規化された分析用スキーマ：[8-7節](8-7.md)）** へコピーして高速集計します。
