### 前節（0-5）の確認問題の解答

前節の最後に提示した3つの問いの解答を確認します。問3がそのまま本節（データハザードの解決）の導入になります。

1. **1ビット予測器 vs 2ビット飽和カウンタのトレース比較（実際の結果：`T, T, N, T, T, N`）：**

    * **(a) 1ビット予測器（初期状態：`T`）：**

        3回目のループ脱出（`N`）で1ビット予測器は即座に予測を `N` へ反転するため、4回目（次周ループ開始の `T`）でも連続ミスが起きます。一方、2ビット飽和カウンタは `11 → 10` に留まって予測を `T` のまま維持するため、4回目を的中させて再び `11` へ復帰できます。

2. **5段 vs 10段パイプラインの分岐ミス率による性能比較：**
    分岐命令割合は $b = 0.20$ であり、$\text{CPI} = 1.0 + (b \times m) \times \text{分岐ペナルティ}$、実効スループットは $f / \text{CPI}$ で求めます。

    * **(a) 分岐予測ミス率 $m = 30\%$（$b \times m = 0.20 \times 0.30 = 0.06$）のとき：**

        * **設計A（5段・$2.0\text{ GHz}$・ペナルティ2）：** $\text{CPI}_A = 1.0 + 0.06 \times 2 = \mathbf{1.12}$、スループット $= 2.0 / 1.12 \approx \mathbf{1.79\text{ GIPS}}$ です。
        * **設計B（10段・$2.5\text{ GHz}$・ペナルティ8）：** $\text{CPI}_B = 1.0 + 0.06 \times 8 = \mathbf{1.48}$、スループット $= 2.5 / 1.48 \approx \mathbf{1.69\text{ GIPS}}$ です。

        クロック周波数が高い設計Bよりも、ペナルティの小さい5段の**設計Aの方が高速**になります。

    * **(b) 分岐予測ミス率 $m = 5\%$（$b \times m = 0.20 \times 0.05 = 0.01$）のとき：**

        * **設計A（5段）：** $\text{CPI}_A = 1.0 + 0.01 \times 2 = \mathbf{1.02}$、スループット $= 2.0 / 1.02 \approx \mathbf{1.96\text{ GIPS}}$ です。
        * **設計B（10段）：** $\text{CPI}_B = 1.0 + 0.01 \times 8 = \mathbf{1.08}$、スループット $= 2.5 / 1.08 \approx \mathbf{2.31\text{ GIPS}}$ です。

        性能が逆転し、**設計Bが設計Aを約18%上回ります**。パイプラインを深くするほど1回のミスあたりの損失が急増するため、高精度な分岐予測があって初めて高クロックの利点を引き出せます。

3. **連続する命令のレジスタ依存と必要な `NOP` 挿入数（本節への接続）：**

    * **(a) 読み書きのタイミングと問題：**
        命令1（`addi x5, x0, 4`）が `x5` の新しい値 `4` をレジスタファイルへ書き込むのは **CC5（WBステージ）** です。一方、直後の命令2（`add x6, x5, x1`）が `x5` をレジスタファイルから読み出すのは **CC3（IDステージ）** です。何の対策もせずに動かすと、命令2は `x5` が更新される前の古い値を読み込んでしまい、誤った計算結果になります（**データハザード**）。

    * **(b) 必要な `NOP` 挿入数：**
        命令1のWB（CC5）が終わった次のサイクルである **CC6** に命令2のIDを置くには、命令2のIFを **CC5** にする必要があります。命令1のIF（CC1）と命令2のIF（CC5）のあいだ（CC2・CC3・CC4）を埋めるため、**`NOP` 命令を3個**挿入する必要があります。

## 0-6. データハザードの解決（バイパス・フォワーディング・ストール）

### 1. 動機（Why）：前の命令の答えが出る前に、後ろの命令がそれを欲しがる問題

前節（[0-5節](0-5.md)）では、5段パイプラインによって周波数 $f$ と $\text{IPC} \approx 1.0$ を両立できることを確認し、構造ハザードと制御ハザードの対処法を整理しました。しかし、実際のプログラムにはもう1つ、分岐命令よりもはるかに頻繁に現れる障壁があります。それが **データハザード（Data Hazard）** です。

普段私たちが書くプログラムを振り返ってみてください。

```c
int a = b + 4;
int c = a + d;
```

1行目の計算結果 `a` を、すぐ次の2行目で使うという書き方はごく当たり前です。ところが5段パイプラインでは、1行目の命令が計算結果をレジスタへ書き戻す（WB：5段目）のを待たずに、2行目の命令がレジスタを読み出す（ID：2段目）ため、そのままでは**前の命令が書いた新しい値ではなく、レジスタに残っていた古い値を読んでしまいます**。

もし毎回「前の命令がWBを終えるまで3サイクル待つ（NOPを3個挟む）」とすれば正しい結果は得られますが、$\text{IPC}$ はマルチサイクル方式並みに急落し、パイプライン化の利点が失われてしまいます。

よく観察すると、1行目の加算結果自体は5段目のWBを待たなくても、**3段目のEXステージが終わった瞬間にすでにALUの出力として手元に出ています**。本節では、この「計算済みの値をレジスタへ戻す前に近道で届ける」仕組み（**バイパス**と**フォワーディング**）と、それでも間に合わない唯一の例外（**ロード・ユースハザード**）の解決策を整理します。

### 2. 具体例と動作イメージ（Toy Model）

回路の設計に入る前に、先行命令が書いたレジスタ `x5` を後続命令が読み出すまでの「距離（間に挟まる無関係な命令の数）」によって何が起きるかを、4つの小さなパターンで確かめます。

#### 実験A：`addi x5, x0, 4` と `add x30, x5, x0` の距離を詰めていく

先行命令1 `addi x5, x0, 4`（`x5` に `4` を代入）と、その結果を使う後続命令 `add x30, x5, x0`（`x5 + 0` を `x30` へ代入）の間に、無関係な命令（ここでは `NOP`）が何個挟まるかを3個から0個まで減らして観察します（図0-6-1）。

1. **間に3命令（`NOP` 3個）以上ある場合：ハザードなし**
    命令1が CC5（WB）で `x5 = 4` をレジスタファイルへ書き込み終えた後、後続命令は CC6（ID）でレジスタファイルから `x5` を読み出します。普通のレジスタ読み書きだけで正しく `4` が得られます。

2. **間に2命令（`NOP` 2個）ある場合：WBとIDが同じサイクルに重なる**
    命令1の **WB** と後続命令の **ID** が、どちらも **CC5** に重なります。通常の順序回路のレジスタファイルでは、書き込みが反映されるのはCC5の終わり（次のクロック立ち上がり）なので、CC5の途中でIDがレジスタ配列を読むと古い値が出てしまいます。

3. **間に1命令（`NOP` 1個）ある場合：後続のEXと先行のWBが重なる**
    後続命令が ID（CC4）でレジスタを読んだ時点では、命令1はまだ MEM ステージにおり、レジスタには古い値しかありません。しかし、後続命令が実際にALUで `x5` の値を使うのは次の **EX（CC5）** です。このCC5の瞬間、命令1はちょうど **WBステージ** にあり、書き戻す直前の新しい値 `4` を持っています。

4. **間に0命令（連続実行）の場合：後続のEXと先行のMEMが重なる**
    後続命令が **EX（CC4）** でALUの計算を始めようとする瞬間、命令1はちょうど **MEMステージ（CC4）** にあります。`addi` の計算結果 `4` は前のサイクル（CC3のEX）ですでに確定しており、`ExMe` パイプラインレジスタに保持されています。

この4ケースを並べると、**「後続命令がIDで古い値を読んでしまっても、EXで実際にALUへ入力する瞬間に、MEMやWBにある新しい値へ差し替えれば1サイクルも止めずに計算を続けられる」**という見通しが立ちます。

### 3. 構造・アルゴリズム・実装（What）

#### (1) データ依存の分類とRAW（真の依存）

データハザードを正確に議論するため、2つの命令間のレジスタ依存関係は読み書きの順序によって3種類に分類されます。

* **RAW（Read After Write：書き込み後の読み出し）：** 先行命令が書き込んだ値を、後続命令が読み出す依存関係です（実験Aの `addi x5, ...` → `add x30, x5, ...`）。計算の本質的な流れを表すため**真の依存**と呼ばれ、5段のインオーダ（命令順）パイプラインで発生するのはこのRAWハザードです。
* **WAR（Write After Read）と WAW（Write After Write）：** 読み出し後に別命令が上書きする関係（WAR）や、同じレジスタへ2命令が続けて書く関係（WAW）です。これらは「たまたま同じ名前のレジスタを再利用した」だけの見かけ上の依存です。5段のインオーダパイプラインではすべての命令が必ず **IDステージ（2段目）で読み出し、WBステージ（5段目）で書き込み** を行うため、後続命令の書き込みが先行命令の読み出しを追い越すこと（WAR）も、後続命令の書き込みが先行命令の書き込みを追い越すこと（WAW）も物理的に発生しません（後述のコラムで触れるアウトオブオーダ実行で重要になります）。

#### (2) レジスタバイパス（WBとIDの同時衝突の解決）

実験Aのケース2（間に2命令）のように、同じクロックサイクル内で WB が書き込み先レジスタ番号（`w_wr`）へデータ（`w_wdata`）を書き込もうとしており（書き込み許可 `w_we == 1`）、同時に ID が同じレジスタ番号（`w_rr1` または `w_rr2`）を読み出そうとする場合を考えます。

この衝突は、レジスタファイル自身の読み出し出力（`w_rdata1`）に小さなバイパス回路（MUX）を1段足すだけで解決できます。

```text
w_rdata1 = (w_rr1 == 0)                ? 0       :   // x0 は常に 0
           (w_rr1 == w_wr && w_we)     ? w_wdata :   // 同じ番号へ書込み中なら直送
           reg_array[w_rr1];                         // 通常はレジスタ配列から読出し
```

この仕組みを **レジスタバイパス（Register Bypass / 内部フォワーディング）** と呼びます。書き込む予定のデータをレジスタ配列へ保存するのと並行して、そのままIDの読み出し出力へ素通しさせることで、同一サイクル内でも新しい値がIDステージへ渡ります。

#### (3) フォワーディング（WB→EX・MEM→EX）と優先順位制御

次に、実験Aのケース3（WB→EX）とケース4（MEM→EX）を実現するのが **フォワーディング（Forwarding：データ転送）** です。EXステージのALUの2つの入力（`rs1` 側と `rs2` 側）の直前に、それぞれマルチプレクサ（MUX）を配置し、次の候補から正しい値を選びます（図0-6-2）。

ここで見落としやすいのが、**「直前の命令（MEM）と2つ前の命令（WB）の両方が、同じレジスタへ書き込む場合」**です。たとえば次の3命令を連続実行したとします。

```asm
addi x5, x0, 10    # 命令1：x5 = 10  （CC5でWBステージ）
addi x5, x5, 5     # 命令2：x5 = 15  （CC5でMEMステージ）
add  x6, x5, x1    # 命令3：x6 = x5 + x1 （CC5でEXステージ）
```

CC5の時点で、命令3（EX）が参照したい `x5` は、命令1の結果 `10` ではなく、より新しい**命令2の結果 `15`（MEMステージ側）**でなければなりません。また、書き込み先が `x0`（常に `0`）の命令から `0` 以外の値をフォワーディングしてもいけません。

したがって、EXステージの `rs1` 側フォワーディング制御は必ず次の**優先順位**で値を選択します（括弧内は対応する内部信号名です）。

1. **最優先（`x0` の保護）：** EXで読むレジスタ番号が `x0`（`Ex_rs1 == 0`）なら、常に `0` を選びます。
2. **第2優先（1つ前の命令・MEMフォワーディング）：** EXで読む番号がMEMの書き込み先と一致し（`Ex_rs1 == Me_rd`）、かつMEMの命令がレジスタ書込みを行う（`Me_we == 1`）なら、MEMにあるALU演算結果（`ExMe_rslt`）を選びます。
3. **第3優先（2つ前の命令・WBフォワーディング）：** 上に該当せず、EXで読む番号がWBの書き込み先と一致し（`Ex_rs1 == Wb_rd`）、かつWBの命令がレジスタ書込みを行う（`Wb_we == 1`）なら、WBの最終書き戻し値（`Wb_rslt2`：ALU結果またはデータメモリ読出し値からWBのMUXで選ばれた値）を選びます。
4. **通常経路：** いずれにも該当しなければ、IDステージで読み出して運んできた値（`IdEx_rrs1`）をそのまま使います。

`rs2` 側についてもまったく同じ優先順位のフォワーディングMUXを配置し、その出力をさらに「即値 `imm` との選択MUX」へ通してALUの第2入力（`Ex_ain2`）を作ります。`rs2` のフォワーディングMUXを即値選択MUXより**手前**に置くのは、ストア命令（`sw`）ではALUの第2入力にオフセット即値 `imm` を使う一方で、データメモリへ書き込む値としてフォワーディング済みの最新の `rs2` が必要になるためです。

### 4. 限界と補正（Critique & Adaptation）

#### (1) フォワーディングだけでは解けない「ロード・ユースハザード」

ここまでのバイパスとフォワーディングによって、`add` や `addi` のようなALU演算命令どうしのデータ依存は、間に1つもNOPを挟まずに連続実行できるようになりました。

しかし、**ロード命令（`lw`）の直後に、その読み出したレジスタを使う命令が続く場合**だけは事情が異なります。次の2命令を見てください。

```asm
lw   x5, 16(x0)    # 命令1：メモリから x5 を読み出す
addi x6, x5, 4     # 命令2：直後に x5 を使って計算する
```

タイムチャートで時間を追ってみます（図0-6-3上）。

* 命令1（`lw`）がデータメモリから `x5` の値を取り出し終えるのは、**CC4（MEMステージ）の終わり**です。
* 一方、命令2（`addi`）が `x5` をALUへ入れて足し算を始めるのは、**CC4（EXステージ）の初め**です。

つまり、必要なデータが確定する時刻（CC4の終わり）が、データを使いたい時刻（CC4の初め）より1サイクル後ろになってしまいます。時間を過去へ戻す配線は物理的に作れないため、**フォワーディングだけではこのハザードを解決できません**。この特殊なデータハザードを **ロード・ユースハザード（Load-Use Hazard）** と呼びます。

#### (2) 2つの補正策：ハードウェア・ストールと命令スケジューリング

ロード・ユースハザードに対する補正は、ハードウェア側とソフトウェア（コンパイラ）側の2方向から行います。

1. **ハードウェアによる1サイクル・ストール（バブル挿入）：**
    IDステージに「ハザード検出ユニット」を置き、前の命令（`IdEx` にある命令）が `lw` であり、かつその書き込み先 `IdEx_rd` が **`x0` 以外（`IdEx_rd != 0`）** であって、現在の命令（`IfId`）が**実際にソースとして読み出すレジスタ（`rs1` または `rs2`）**と一致しているかを検査します（たとえば `addi` や `lw` のように `rs2` を使わない命令では、命令ビット列の `rs2` 相当位置にたまたま同じ番号が入っていても検査対象外にして不要なストールを防ぎます。また `x0` へのロードは結果が捨てられるためストールは不要です）。一致を検出したら、次の3つの操作を1サイクルだけ同時に行います（図0-6-3下）。

    * `PC` と `IfId` レジスタの更新を止め、命令2をもう1サイクルだけIDステージに留め置きます（**ストール：Stall**）。
    * `IdEx` レジスタへは `NOP` を流し込みます（パイプラインに1サイクル分の空き＝**バブル：Bubble** を挿入します）。
    * 1サイクルずれた次のCC5で、命令1は WB ステージ（メモリ読出し値 `Wb_rslt2` を保持）、命令2は EX ステージへ進むため、**WBフォワーディング**によって正しく新しい値を受け取って計算できます。

2. **コンパイラによる命令スケジューリング（ソフトウェアでの隠蔽）：**
    ハードウェアでストールすれば正しさは保証されますが、1サイクルの性能損失が発生します。そこでコンパイラは、プログラムの意味を変えない範囲で**`lw` の直後に依存関係のない別の命令を1つ滑り込ませる**並べ替え（命令スケジューリング）を行います。たとえば `a = x + y; b = z + w;` のような計算では、素朴に `x, y` をロードしてすぐ `a` を計算し、続けて `z, w` をロードしてすぐ `b` を計算すると、`y` と `w` の直後で計2回のストールが起きます。ここで、**`x, y, z, w` の4つすべてを先にロードしてから `a = x + y` と `b = z + w` の2つの加算を後続させる**順番へ並べ替えると、`y` と `a` の間にも、`w` と `b` の間にも無関係な命令が挟まるため、ストールを0サイクルへ消すことができます。

> **【コラム：アウトオブオーダ実行（Out-of-Order Execution）の3段階と精密例外】**
>
> コンパイラによる静的な命令スケジューリングには限界があります。たとえばロード命令が主記憶からデータを読み込むのに何十サイクルも待たされたとき、順番通り（インオーダ）にしか命令を実行できないCPUでは、後ろに「まったく無関係ですぐ計算できる命令」が控えていても、パイプライン全体が詰まって止まってしまいます。
>
> 現代の高性能CPUは、この詰まりをハードウェア自身で動的に解消する **アウトオブオーダ実行（Out-of-Order Execution, OoO）** を備えています。その仕組みは大きく次の3段階で成り立っています。
>
> 1. **材料が揃った命令から実行する待合室（リザベーション・ステーション）：** デコード後の命令を待ちプールへ入れ、入力データが揃った命令からプログラムの記述順を追い越して演算器へ投入します。
> 2. **名前衝突を避ける予備レジスタへの付け替え（レジスタ・リネーミング）：** プログラム上では同じレジスタ名を使い回していても、内部に用意した多数の物理レジスタ（`p1`, `p2`, ...）へ動的に名前を付け替えることで、WAR・WAWといった見かけ上の依存を取り除きます。たとえば次の4命令を考えます。
>
>     ```asm
>     lw   x1, 0(x10)   # 命令1：x1(→ p1) へロード（主記憶待ちで遅い）
>     add  x2, x1, x3   # 命令2：p1 を待つ（真の依存 RAW）
>     addi x1, x4, 1    # 命令3：x1(→ p2) へ新規書込み（命令1・2とは無関係な別名へ）
>     add  x5, x1, x6   # 命令4：p2 を使う
>     ```
>
>     前半の `x1` を `p1`、後半の `x1` を別名の `p2` へ付け替えれば、命令3と命令4は遅い命令1の完了を待たずに追い越して先に計算を終えられます。
>
> 3. **出口で元の順番に戻して確定（リオーダ・バッファ：ROB とリタイア）：** 追い越し計算が終わった命令はすぐには結果を確定せず、ROBに一時保管して**元のプログラム順に整列し直してから確定（リタイア）**させます。順番通りに戻す理由は2つあります。第1に、分岐予測ミスが起きたときに後続の投機命令をきれいに取り消すためです。第2に、途中の命令で**ページフォールト**（仮想記憶で必要なデータ領域が主記憶上に未配置のときに起きる例外；詳細は[第3部](../index.md#part-3) [3-5節](../3/3-5.md)）やゼロ除算などの例外が起きたとき、「例外を起こした命令より前はすべて完了し、後ろの命令は一切実行されていない」という**精密例外（Precise Exception）**をOSに対して保証するためです。
>
> こうして外から見れば順番通りに実行されたように見せながら、CPU内部の空きサイクルを最大限に活用します。

### 5. 接続と展望（Bridge）：本節の内容が後半のどの部に繋がるか

2. **[第2部](../index.md#part-2)（[2-7](../2/2-7.md)・[2-8節](../2/2-8.md)：コード最適化とレジスタ割当）：**

3. **[第4部](../index.md#part-4)（[4-3節](../4/4-3.md)：メモリ一貫性モデルとメモリバリア）：**
