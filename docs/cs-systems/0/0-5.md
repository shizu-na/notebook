### 前節（0-4）の確認問題の解答

前節の最後に提示した3つの問いの解答を確認します。問3がそのまま本節（パイプラインとハザード）の導入になります。

1. **各命令が通るステージの整理：**

    * **(a) 4番目のステージ MEM（データメモリ）を使用する命令：**
        メモリから読み出す **`lw`** と、メモリへ書き込む **`sw`** の2つです（`add`, `addi`, `beq` はデータメモリを使用しません）。

    * **(b) 5番目のステージ WB（レジスタファイルへの書き戻し）を使用する命令：**
        演算結果をレジスタへ書く **`add`**, **`addi`** と、メモリ読出し結果をレジスタへ書く **`lw`** の3つです（`sw` と `beq` はレジスタへ書き戻しません）。

2. **性能式 $\text{Performance} = f \times \text{IPC}$ の計算：**
    各ステージの遅延は IF: $4\text{ ns}$、ID: $2\text{ ns}$、EX: $4\text{ ns}$、MEM: $6\text{ ns}$、WB: $4\text{ ns}$ です。

    * **(a) シングルサイクル方式：**

        * クロック周期：$T_{\text{clk}} = 4 + 2 + 4 + 6 + 4 = \mathbf{20\text{ ns}}$
        * 動作周波数：$f = \dfrac{1}{20 \times 10^{-9}\text{ s}} = \mathbf{50\text{ MHz}}$
        * 性能：$\text{IPC} = 1.0$ より、$\text{Performance} = 50 \times 1.0 = \mathbf{50\text{ MIPS}}$

    * **(b) 5段固定マルチサイクル方式：**

        * クロック周期：$T_{\text{clk}} = \max(4, 2, 4, 6, 4) = \mathbf{6\text{ ns}}$
        * 動作周波数：$f = \dfrac{1}{6 \times 10^{-9}\text{ s}} \approx \mathbf{166.7\text{ MHz}}$
        * $\text{IPC}$：1命令に5サイクルかかるため $\text{IPC} = \dfrac{1}{5} = \mathbf{0.2}$
        * 性能：$\text{Performance} = 166.7 \times 0.2 \approx \mathbf{33.3\text{ MIPS}}$

    周波数は約3.3倍に上がりますが、1命令あたりの実行時間が $20\text{ ns}$ から $6 \times 5 = 30\text{ ns}$ へ伸び、かつ各回路が5サイクル中4サイクル遊休となるため、性能はシングルサイクル（$50\text{ MIPS}$）より低下します。

3. **流れ作業にしたときに何がぶつかるか（本節への接続）：**
    前の命令が終わる前に次の命令を重ねて流し込むと、主に2つの衝突が起きます。1つは「前の命令が計算結果をレジスタへ書き戻す前に、後ろの命令が古いレジスタ値を読んでしまう」問題（**データハザード**）、もう1つは「条件分岐（`beq`）がジャンプするかどうか決まる前に、後ろの命令を誤って読み込んでしまう」問題（**制御ハザード**）です。

## 0-5. 5段パイプラインと構造・制御ハザード（分岐予測の直感）

### 1. 動機（Why）：なぜ「流れ作業」にすると周波数と $\text{IPC}$ を両立できるのか

前節（[0-4節](0-4.md)）で見た通り、プロセッサの性能は $\text{Performance} = f \times \text{IPC}$ で決まります。シングルサイクル方式は $\text{IPC} = 1.0$ を保てますが、全5ステップを1クロックに押し込むため周波数 $f$ を上げられません。一方、マルチサイクル方式はステージを分けて周波数 $f$ を数倍に引き上げられますが、1命令ずつ順番に処理するため $\text{IPC}$ が $0.2$ 前後まで落ちてしまいました。

このジレンマを解消する考え方は、工場の組み立てライン（流れ作業）とまったく同じです。自動車を1台ずつ最初から最後まで作り終えてから次の車に着手するのではなく、「1台目が塗装工程へ進んだ瞬間に、空いた溶接工程へ2台目を入れる」ようにすれば、すべての工程が毎サイクル休まず稼働します。

CPUの5つのステージ（IF・ID・EX・MEM・WB）にこの流れ作業を適用した仕組みが **5段パイプライン（5-stage pipeline）** です。ただし、命令同士は独立した自動車とは違い、同じメモリを奪い合ったり、直前の分岐結果で次に実行すべき命令が変わったりします。本節では、5段パイプラインの基本構造を組み立てたうえで、並列実行を妨げる **ハザード（Hazard）** のうち**構造ハザード**と**制御ハザード**、さらに現代CPUに不可欠な**分岐予測**の仕組みを整理します。

### 2. 具体例と動作イメージ（Toy Model）

パイプラインの動作と性能向上の仕組みを、前節（[0-4節](0-4.md)）と同じ遅延時間の数値例で確かめます。

#### 実験A：5つの命令を流れ作業で重ねて実行する

前節と同じく、各ステージの物理遅延が IF: $5\text{ ns}$、ID: $4\text{ ns}$、EX: $4\text{ ns}$、MEM: $5\text{ ns}$、WB: $2\text{ ns}$ であるプロセッサを考えます。最も遅いステージが $5\text{ ns}$ なので、クロック周期は $T_{\text{clk}} = \mathbf{5\text{ ns}}$（動作周波数 $f = \mathbf{200\text{ MHz}}$）に設定できます。

ここで、互いに依存関係のない5つの命令（命令1〜命令5）を連続して流し込みます。クロックサイクル（CC1, CC2, ...）ごとの各ステージの担当は次のようになります（図0-5-1）。

* **CC1（$0 \sim 5\text{ ns}$）：** 命令1が IF に入る。
* **CC2（$5 \sim 10\text{ ns}$）：** 命令1が ID へ進み、同時に空いた IF へ命令2が入る。
* **CC3（$10 \sim 15\text{ ns}$）：** 命令1は EX、命令2は ID、命令3は IF。
* **CC4（$15 \sim 20\text{ ns}$）：** 命令1は MEM、命令2は EX、命令3は ID、命令4は IF。
* **CC5（$20 \sim 25\text{ ns}$）：** 命令1が WB を終えて**完了**する。この瞬間、全5ステージが同時に稼働している（命令1: WB、命令2: MEM、命令3: EX、命令4: ID、命令5: IF）。
* **CC6〜CC9：** 以降、**毎クロックサイクル（$5\text{ ns}$ ごと）に1命令ずつ完了**し、CC9（$45\text{ ns}$ 時点）で全5命令が完了する。

前節の2方式と5命令の総実行時間を比べると、大きな差が生じます。

* **シングルサイクル（$20\text{ ns}$/命令）：** 5命令で $20 \times 5 = \mathbf{100\text{ ns}}$
* **5段固定マルチサイクル（$25\text{ ns}$/命令）：** 5命令で $25 \times 5 = \mathbf{125\text{ ns}}$
* **5段パイプライン（$5\text{ ns}$/サイクル）：** 5命令で $9 \times 5 = \mathbf{45\text{ ns}}$

さらに1,000命令を実行すれば、パイプラインが満たされるまでの最初の4サイクル（$20\text{ ns}$）の遅れは全体のわずか $0.4\%$ に過ぎなくなり、実質的に $5\text{ ns}$ ごとに1命令が完了します。

### 3. 構造・アルゴリズム・実装（What）

#### (1) パイプラインレジスタによるステージ分離

5つの命令が同じデータパス上に同時に存在するためには、あるステージで計算している命令の信号が、隣のステージにある別命令の信号と混ざらないように仕切る必要があります。この仕切りが、各ステージ間に配置される **パイプラインレジスタ（Pipeline Register）** です。

5段パイプラインでは、4組のパイプラインレジスタを配置します。

```text
[ IF ] ──▶ | IfId | ──▶ [ ID ] ──▶ | IdEx | ──▶ [ EX ] ──▶ | ExMe | ──▶ [ MEM ] ──▶ | MeWb | ──▶ [ WB ]
```

それぞれのレジスタは、クロックの立ち上がりで左側のステージの出力をまとめて取り込み、次の1サイクル間、右側のステージへ安定して供給します。なお、本節および次節のハードウェア信号名では、先頭の接頭辞で所属ステージやパイプラインレジスタ（`Ex_` はEXステージ、`IdEx_` は `IdEx` レジスタ等）を示し、`ir` は命令レジスタ（Instruction Register）、`rrs1`/`rrs2` は読み出したレジスタ値、`tpc` は分岐先アドレス（Target PC）、`rslt` は演算結果、`ldd` はメモリ読出し値（Load Data）、`we` は書き込み許可（Write Enable）を表します。

| パイプラインレジスタ | 主に保持して次ステージへ渡す情報 |
| :--- | :--- |
| **`IfId`** | 命令メモリから読み出した32ビット命令（`ir`）、その命令の `pc` |
| **`IdEx`** | レジスタ読出し値（`rrs1`, `rrs2`）、符号拡張即値（`imm`）、分岐先アドレス（`tpc = pc + imm`）、書戻し先番号 `rd`、制御信号 |
| **`ExMe`** | ALU演算結果（`rslt`）、ストア用データ（`rrs2`）、`rd`、メモリ制御信号 |
| **`MeWb`** | ALU演算結果（`rslt`）、データメモリ読出し値（`ldd`）、`rd`、書戻し制御信号 |

重要なのは、**書き込み先レジスタ番号 `rd` や制御信号もデータと一緒にパイプラインレジスタをバケツリレーで運ぶ**点です。命令1がWBに到達したとき、IDステージにはすでに命令4が入っています。もしWBがIDの信号線を見てしまうと命令4の書き込み先へ誤って書いてしまうため、命令1自身の `rd` を `IdEx → ExMe → MeWb` と最後まで運び届ける必要があるのです。

#### (2) レイテンシとスループットの区別

実験Aから、計算機システム全般で繰り返し現れる2つの性能指標の違いがくっきり見えます。

* **レイテンシ（Latency：遅延時間）：** 1つの命令が開始してから完了するまでの所要時間です。パイプライン化しても1命令のレイテンシは短くなりません（むしろ各ステージを最遅ステージに揃える分、$20\text{ ns} \to 25\text{ ns}$ へとわずかに伸びます）。
* **スループット（Throughput：処理能力）：** 単位時間あたりに完了する命令数です。5段パイプラインで $N$ 個の命令をハザードなしで流すと、最初の1命令が完了するまでに5サイクルかかり、残りの $(N - 1)$ 命令が毎サイクル1命令ずつ完了するため、総サイクル数は $5 + (N - 1) = (N + 4)$ サイクルになります（一般に $k$ 段パイプラインでは $N + k - 1$ サイクル）。$N$ が十分大きいとき $\text{IPC} = \frac{N}{N + 4} \to 1.0$ となり、スループットは $50\text{ MIPS} \to 200\text{ MIPS}$ へと**4倍**に向上します。

パイプライン処理とは、**個別のレイテンシを少し犠牲にする代わりに、並列度を高めてスループットを大幅に引き上げる**設計手法です。

#### (3) 並列実行を阻む3つのハザード

現実のプログラムでは、理想通りの $\text{IPC} = 1.0$ を常に維持することはできません。後続命令を次のクロックサイクルで予定通り実行できなくなる状況を **ハザード（Hazard）** と呼び、次の3種類に分類されます。

1. **構造ハザード（Structural Hazard）：** 異なるステージにある複数命令が、同じハードウェア資源を同時に使おうとして衝突する問題です。
2. **制御ハザード（Control Hazard）：** 条件分岐やジャンプ命令の行き先が確定する前に、後続の命令をフェッチしてしまう問題です。
3. **データハザード（Data Hazard）：** 先行命令が書き込む予定のレジスタ値を、書き込みが終わる前に後続命令が読もうとして起きる依存関係の問題です（※データハザードの詳しい解決策は、次節 [0-6節](0-6.md)で独立して扱います）。

#### (4) 構造ハザードとハードウェア設計による回避

図0-5-1の CC4 や CC5 をよく見ると、同じサイクルの中で次の2組の同時アクセスが起きています。

* **IF（命令読出し）と MEM（データ読み書き）が同時：** もし命令とデータを1つの単一メモリ（1ポート）にまとめて置いていると、命令4のIFと命令1のMEMが衝突し、どちらかを1サイクル待たせなければなりません。そこでパイプラインプロセッサでは、**命令メモリとデータメモリを物理的に分離**する（実CPUではL1命令キャッシュとL1データキャッシュを分離する；詳細は[0-7節](0-7.md)）ことでこの構造ハザードを根本から回避します。
* **ID（レジスタ読出し）と WB（レジスタ書込み）が同時：** 同じサイクルで命令1がWBでレジスタを書き、命令4がIDでレジスタを読みます。[0-4節](0-4.md)で構成したレジスタファイルは「2ポート読み出し＋1ポート書き込み」とポートが独立しているため、別々のレジスタ番号であれば衝突せずに同時実行できます（※同じレジスタ番号に当たった場合の扱いは次節 [0-6節](0-6.md)のレジスタバイパスで扱います）。

#### (5) 制御ハザードと「不成立仮定＋2ステージ同時フラッシュ」

次に、条件分岐命令 `beq x1, x2, Target` がパイプラインへ入った場面を考えます。

`beq` が IF でフェッチされた直後の次のサイクル（CC2）では、まだ `beq` は ID ステージにあり、`x1 == x2` が成り立つかどうかは分かりません。分岐の成否（`Ex_taken`）が確定するのは、ALUで2つのレジスタを比較する **EXステージ（CC3）** です。その間に、IFステージは止まらずに後続の命令（`PC + 4` の命令2、`PC + 8` の命令3）を次々とフェッチしてしまいます。

この制御ハザードに対する素朴な対処法は2つあります。

* **戦略1：ストール（分岐のたびに待つ）：** 分岐命令の後ろに2サイクル分の空き（NOP）を入れて、EXで結果が出るまでフェッチを止めます。実装は単純ですが、分岐が不成立のときでも毎回2サイクルの無駄が生じます。
* **戦略2：不成立仮定＋成立時フラッシュ（Predict-Not-Taken）：** 「分岐は成立しない（次の `PC + 4` へ進む）」と仮定して、止めずに命令2・命令3をそのまま流し続けます。

    * **分岐が不成立だった場合：** すでに流し込んだ命令2・命令3がそのまま正解なので、**ペナルティは 0 サイクル**です。
    * **分岐が成立した場合（`Ex_taken == 1`）：** 誤って流し込んでしまった **IDステージの命令2（`IdEx`）と IFステージの命令3（`IfId`）を、次のクロック立ち上がりで同時に無効化（フラッシュ：Flush）** し、何もしない命令 `NOP`（RISC-Vでは `addi x0, x0, 0`）へ書き換えます。同時に `PC` を分岐先アドレス `Target` へ更新します（図0-5-2）。このとき、2サイクル分の仕事が捨てられるため**分岐ペナルティは 2 サイクル**になります。

> **【コラム：パイプラインを深くするほど速くなるのか：最適段数の数式モデルとスーパースカラ】**
>
> 「5段に分割したら周波数が4倍になったのなら、20段、40段とさらに細かく分割すればもっと速くなるのではないか」と考えるのは自然です。実際に2000年代前半には、クロック周波数を競うためにパイプラインを20段〜31段まで深くしたCPU（Intel Pentium 4 など、スーパーパイプラインと呼ばれます）が製品化されました。
>
> しかし、段数 $k$ を増やすと次の2つのコストが急速に膨らみます。
>
> 1. **パイプラインレジスタのオーバーヘッド：** 段数を増やすたびにレジスタのセットアップ時間（[0-3節](0-3.md)）とクロック遅延 $t_{\text{reg}}$ が毎段にかかり、純粋な組合せ回路の時間 $T / k$ が短くなるほどレジスタ自身の遅延が割合として大きくなります。
> 2. **分岐予測ミス時のペナルティ増大：** 5段なら分岐確定まで2サイクル（2命令の破棄）で済みますが、$k$ 段パイプラインでは分岐確定までの段数もおよそ $k$ に比例して伸び（たとえば $k/2$ 段前後）、予測が1回外れるだけで十数サイクル分の命令が丸ごと無駄になります。
>
> 1命令の組合せ遅延を $T$、全命令中の分岐割合を $b$、分岐予測ミス率を $m$ とすると、$k$ 段パイプラインの実効スループットは簡易モデルで次のように表せます。
>
> $$\text{Throughput}(k) \propto \frac{1}{\left(\dfrac{T}{k} + t_{\text{reg}}\right)\left(1 + b \cdot m \cdot \dfrac{k}{2}\right)}$$
>
> $k$ を増やすと前半のクロック周期 $(T/k + t_{\text{reg}})$ は縮みますが、後半の分岐ペナルティ項 $(1 + bmk/2)$ が直線的に増えるため、スループットは $k$ に対して上に凸の曲線を描き、ある最適段数を超えると逆に低下します。さらに[0-3節](0-3.md)で見た「電力の壁（デナード則の終焉）」も重なり、Intel自身も31段の Pentium 4 路線を撤回して14段前後の Core 系アーキテクチャへ転換しました。
>
> その後の現代CPUでは、パイプラインの段数（深さ）を **14〜19段前後** に抑える代わりに、命令のフェッチ・デコード・演算器を複数系統並列に並べて1サイクルに複数命令を同時実行する **スーパースカラ（Superscalar：$\text{IPC} > 1$）** によって性能を伸ばす方向へ進化しています。

### 4. 限界と補正（Critique & Adaptation）

#### (1) 不成立仮定の限界と「分岐予測（Branch Prediction）」

3-(5)の「常に不成立と仮定する」方式は、プログラムの中で最も多く実行される**ループ処理**と相性がよくありません。`for` ループや `while` ループの末尾にある分岐命令は、たとえば1,000回繰り返すループなら**999回は「成立（ループ先頭へ戻る）」**、最後の1回だけ「不成立（ループを抜ける）」になるからです。常に不成立を仮定すると、1,000回のうち999回も2サイクルのフラッシュペナルティを払うことになります。

この限界を補正するのが、分岐の方向を事前に推測してフェッチを進める **分岐予測（Branch Prediction）** です。

1. **静的分岐予測（Static Branch Prediction）：**
    実行時の履歴を使わず、命令の形だけで予測します。最も代表的な規則は **BTFN（Backward Taken, Forward Not-taken）** です。分岐先アドレスが現在より後ろ（負のオフセット）ならループの戻り先なので「成立」、前（正のオフセット）なら `if` のスキップなので「不成立」と予測します。

2. **動的分岐予測（Dynamic Branch Prediction）と2ビット飽和カウンタ：**
    ハードウェア内に小さな履歴表（分岐予測テーブル）を持ち、直近の実行結果から学習します。単純に「前回の結果と同じと予測する（1ビット予測器）」と、**二重ループの内側ループへ再突入する場面**で2回連続ミスが起きます（内側ループを抜ける最後の1回で「成立」と予測して外し履歴が「不成立」に書き換わるため、外側ループの次周で再び内側ループへ入った1回目も「不成立」と予測して外してしまいます）。そこで広く使われるのが、$0$ 未満にも $3$ 超にもならず両端で止まる（飽和する）4段階の「確信度メーター」である **2ビット飽和カウンタ（2-bit saturating counter）** です（図0-5-3）。

    * 4つの状態（`00`: 強く不成立、`01`: 弱く不成立、`10`: 弱く成立、`11`: 強く成立）を持ち、上位ビットが `1` なら「成立」、`0` なら「不成立」と予測します。
    * 分岐が成立したらカウンタを $+1$（最大 `11` で飽和）、不成立なら $-1$（最小 `00` で飽和）します。
    * 「強く成立（`11`）」の状態なら、ループ脱出時に1回だけ不成立になっても「弱く成立（`10`）」へ移るだけで予測は「成立」のまま保たれるため、次のループ開始時の1回目も正しく予測できます。

3. **分岐ターゲットバッファ（BTB：Branch Target Buffer）：**
    仮にIFステージで「成立する」と予測できても、分岐先アドレス `PC + imm` がまだ分かっていなければ次のサイクルで分岐先をフェッチできません。そこで、過去に実行した分岐命令のアドレス（`PC`）と「その分岐先アドレス（`Target`）」の組を小さな「行き先メモ帳」のようなキャッシュ表（BTB）に覚えておき、IFステージの段階で即座に分岐先へ飛べるようにします。

分岐ミス（予測外れ）がプロセッサ全体の性能へ与える影響は、基本の $\text{CPI} = 1.0$ に「1命令あたりの分岐ミス発生率 $\times$ 分岐ペナルティ」を足した平均 $\text{CPI}$ で定量評価できます。

$$\text{CPI} = 1.0 + (\text{全命令中の分岐命令の割合} \times \text{分岐予測ミス率}) \times \text{分岐ペナルティ}$$

たとえば全命令の $25\%$ が分岐命令で、予測ミス率が $20\%$、分岐ペナルティが $2$ サイクルであれば、1命令あたりのミス発生率は $0.25 \times 0.20 = 0.05$ となり、平均 $\text{CPI} = 1.0 + 0.05 \times 2 = 1.10$（実効 $\text{IPC} \approx 0.91$）と計算できます。分岐予測の的中率を高めることは、そのまま平均 $\text{CPI}$ を理想値 $1.0$ へ近づけることに直結します。

> **【コラム：分岐予測とソフトウェア性能（ソート済み配列の速度差と `cmov` による分岐レス化）】**
>
> 分岐予測の挙動は、私たちが書く普通のプログラムの実行速度にもはっきり現れます。たとえば `0`〜`255` の乱数が入った大きな配列 `a[]` に対して、「`if (a[i] >= 128) sum += a[i];`」を全要素で回す処理を考えます。
>
> 配列が**ランダム順**のままだと、`a[i] >= 128` の真偽は毎回コイントスと同じ約50%の確率で入れ替わるため、2ビット飽和カウンタでも予測が約半分の確率で外れ、そのたびに十数サイクルのフラッシュペナルティが発生します。ところが、同じ配列を**あらかじめ昇順にソート**してからまったく同じループを回すと、前半はずっと不成立、後半はずっと成立と切り替わりが1回しか起きないため、分岐予測的中率がほぼ100%になり、**処理時間が数倍速く終わる**ことが知られています。
>
> ランダムな入力でもペナルティを避けたい場合、コンパイラやプログラマは条件分岐命令を使わずに「条件が真のときだけレジスタへ値を転送する」専用命令（x86-64の **`cmov`** 命令など；[第1部](../index.md#part-1) [1-2節](../1/1-2.md)で詳述）やビットマスク演算へ書き換える**分岐レス化（Branchless）**を行います。分岐自体を消せば予測ミスは原理的にゼロになります。

#### (2) 投機実行の功罪

分岐予測に基づいて、結果が確定する前に先の命令を先行実行する仕組みを **投機実行（Speculative Execution）** と呼びます。予測が外れたときは、フラッシュによって途中の結果をすべて捨て、レジスタや主記憶といった「プログラムから見える状態」には一切影響を残さないように制御されます。

しかし、投機実行には見落とされやすい副作用があります。予測が外れて命令が取り消されても、**投機的に読み込んだデータがCPU内部の高速キャッシュ（[0-7節](0-7.md)）へ載った痕跡までは完全には消えない**ことがある点です。このアクセス時間のわずかな差といった副次的な痕跡から秘密データを推測する**サイドチャネル攻撃**（Spectre 等）が2018年に発見され、現代のCPU・OS・コンパイラでは投機実行の境界に制御命令を挟むなどの補正が行われています。

### 5. 接続と展望（Bridge）：本節の内容が後半のどの部に繋がるか

1. **次節（[0-6節](0-6.md)：データハザードの解決）：**
    本節で後回しにした3つ目のハザードである**データハザード**を取り上げ、レジスタバイパス・フォワーディング・ストールによって連続した依存命令をどう捌くかを追います。

2. **[第0部](../index.md#part-0)（[0-7節](0-7.md)：記憶階層とCPUキャッシュ）：**
    本節の3-(4)で触れた「命令メモリとデータメモリの分離」は、実際のCPUではL1命令キャッシュとL1データキャッシュの分離として実装されます。

3. **[第2部](../index.md#part-2)（[2-7節](../2/2-7.md)：コード最適化①）：**
    コンパイラが行う「ループ展開（loop unrolling）」は、ループ本体の命令を複数回並べることで条件分岐命令の実行回数そのものを減らし、本節の制御ハザードを軽減する最適化です。

4. **[第7部](../index.md#part-7)（[7-1](../7/7-1.md)・[7-2節](../7/7-2.md)：ARQとスライディングウィンドウ）：**
    「1つ終わるのを待ってから次を送る（Stop-and-Wait / マルチサイクル）」と遅いため、「確認を待たずに連続して流し込み、異常が起きたら巻き戻す（Go-Back-$n$ / パイプライン＋フラッシュ）」という発想は、CPU内部とネットワーク通信のプロトコルでまったく同型に現れます。

### 理解度チェック（次節へ進む前の確認）

本節のパイプライン実行時間と制御ハザードのペナルティ計算を確認し、次節（[0-6節](0-6.md)）へ繋ぐ問いを置きます。

> **【確認の問い】**
>
> 1. **（パイプラインの総サイクル数と実効 $\text{IPC}$）**
>     ハザードが一切発生しない5段パイプラインプロセッサにおいて、$N$ 個の命令をすべて完了するのに必要な総サイクル数は $(N + 4)$ サイクルです。
>
>     * (a) $N = 10$ 命令を実行したときの総サイクル数と実効 $\text{IPC} = N / (N + 4)$ を求めてください（小数第2位まで）。
>     * (b) $N = 1{,}000$ 命令を実行したときの実効 $\text{IPC}$ を求め（小数第3位まで）、命令数が増えるほど理想値 $1.0$ に近づくことを確かめてください。
>
> 2. **（制御ハザードのペナルティと分岐予測の効果）**
>     あるプログラムでは、実行される全命令の $20\%$ が条件分岐命令であり、そのうち $70\%$ が実際に分岐成立するとします。分岐予測ミス（または不成立仮定で成立した場合）の分岐ペナルティは $2$ サイクル、それ以外のハザードはないものとします。
>
>     * (a) 「常に不成立と仮定する」方式のときの平均 $\text{CPI}$ を求めてください。
>     * (b) 動的分岐予測を導入して予測的中率が $90\%$（ミス率 $10\%$）になったときの平均 $\text{CPI}$ を求め、(a) と比較してください。
>
> 3. **（次節への伏線：連続する命令のレジスタ依存）**
>     5段パイプラインに次の2命令を連続して投入したとします。
>
>     ```asm
>     addi x5, x0, 4    # 命令1：x5 に 4 を書き込む
>     add  x6, x5, x1   # 命令2：x5 と x1 を足して x6 に書き込む
>     ```
>
>     命令1が `x5` の新しい値 `4` をレジスタファイルへ書き込むのは何サイクル目（どのステージ）でしょうか。一方、命令2が `x5` の値をレジスタファイルから読み出すのは何サイクル目（どのステージ）でしょうか。このまま何の対策もせずに動かすと何が起きるでしょうか。
