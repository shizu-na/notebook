### 前節（0-7）の確認問題の解答

前節の最後に提示した3つの問いの解答を確認します。本節では[第0部](../index.md#part-0)の締めくくりとして、CPU 単体のパイプライン・キャッシュの先にある **SIMD・GPU・メモリ帯域の物理制約（Roofline モデル）** へ進みます。

1. **8-way キャッシュのアドレス分割と競合ミスの診断（32ビットアドレス・$32\text{ KiB}$・ライン $64\text{ B}$・8-way）：**

    * **(a) 総ライン数・セット数とアドレスのビット分割：**

        * 総ライン数：$\dfrac{32\text{ KiB}}{64\text{ B}} = \dfrac{2^{15}}{2^6} = 2^9 = \mathbf{512\text{ ライン}}$ です。
        * セット数（1セットに8ウェイ）：$\dfrac{512}{8} = \mathbf{64\text{ セット}}\ (= 2^6)$ です。
        * **オフセット：** 1ライン $64\text{ B} = 2^6\text{ B}$ より、**$6$ ビット**（下位ビット `5..0`）です。
        * **インデックス：** $64\text{ セット} = 2^6$ より、**$6$ ビット**（中位ビット `11..6`）です。
        * **タグ：** 残り $32 - 6 - 6 = \mathbf{20\text{ ビット}}$（上位ビット `31..12`、検算：$20 + 6 + 6 = 32$ ビット）です。

    * **(b) `0x1000` と `0x2000` の交互アクセスと競合ミス診断：**
        下位12ビット（オフセット6ビット＋インデックス6ビット）がちょうど $2^{12}\text{ B} = 4\text{ KiB} = \texttt{0x1000}$ に相当するため、両アドレスの分割は次の通りになります。

        * `0x1000`：オフセット `0`、**インデックス `0`**、**タグ `0x00001`** です。
        * `0x2000`：オフセット `0`、**インデックス `0`**、**タグ `0x00002`** です。

        両者は同じセット `0` に入りますが、この 8-way キャッシュではセット `0` に8個の格納枠があるため同時に共存できます。したがって初回の強制ミス（計2回）のあとはすべてヒットし、**競合ミスは起きません（0回）**。
        対照的に、同じ64セット構成の**直接写像キャッシュ（1-way・容量 $4\text{ KiB}$）**ではセット `0` の枠が1個しかないため、`0x1000` と `0x2000` の2種類を交互に読むだけで毎回追い出し合い（競合ミス）が発生します。また、8-way キャッシュであっても `0x1000`〜`0x9000` の**9種類**を循環アクセスするとすべてセット `0` へ集中して8ウェイを超えるため、他の63セットが空いたまま毎回追い出しが連発する競合ミス（スラッシング）が起きます。

2. **2階層 AMAT：ハードウェアの L2 追加 vs ソフトウェアの局所性改善：**

    * **(a) ハードウェア案（L2キャッシュ追加）：**
        まず L1 ミス時に到達する L2 キャッシュの AMAT（L1 から見たミスペナルティ）を求め、再帰式へ代入します。

        $$\text{AMAT}_{\text{L2}} = T_{\text{hit,L2}} + m_{\text{L2}} \times T_{\text{penalty,L2}} = 10 + 0.20 \times 100 = 30\text{ ns}$$

        $$\text{AMAT}_{\text{L1}} = T_{\text{hit,L1}} + m_{\text{L1}} \times \text{AMAT}_{\text{L2}} = 1 + 0.05 \times 30 = 1 + 1.5 = \mathbf{2.5\text{ ns}}$$

    * **(b) ソフトウェア案（L1ミス率を $1\%$ へ改善）：**

        $$\text{AMAT} = 1 + 0.01 \times 100 = 1 + 1.0 = \mathbf{2.0\text{ ns}}$$

        ハードウェア案（L2追加）はミス1回あたりのペナルティを $100\text{ ns} \to 30\text{ ns}$ へ緩和して AMAT を $6.0\text{ ns} \to 2.5\text{ ns}$ に短縮します。一方、ソフトウェア案は L1 ミス率そのものを $5\% \to 1\%$ へ削減することで、追加ハードウェアなしに **`2.0 ns`** と L2 追加を上回る短縮を実現できます（両者を併用すれば $1 + 0.01 \times 30 = 1.3\text{ ns}$ までさらに縮まります）。

3. **False Sharing の MESI 状態遷移診断とパディングによる修正：**

    * **(a) False Sharing の原因と MESI 状態遷移（1往復）：**
        64ビットLP64環境では `c0`（オフセット `0..7`）と `c1`（オフセット `8..15`）が連続して**同一の64バイト・キャッシュライン**に載ります。キャッシュコヒーレンシは64バイトのライン単位で管理されるため、両コアが最初にこのラインを `S`（共有）状態で持っている場面から次の遷移が往復します。

        1. **コア0が `c0` へ書込み：** コア0は共有バス経由で他コアへ無効化（Invalidate）メッセージを送り、コア1のラインを **`S → I`**（無効）へ遷移させてから自身を **`S → M`**（変更済み）にして書き込みます。
        2. **コア1が `c1` へ書込み：** コア1のラインは `I` 状態のためキャッシュミスとなり、書込み用の所有権要求をバスへ送ります。コア0は最新のラインをコア1へ供給して自身を **`M → I`** へ落とし、受け取ったコア1が **`I → M`** へ遷移して `c1` を書き込みます。

        ループ内で両コアが更新を繰り返すたびに無効化とライン転送（キャッシュライン・ピンポン）が往復し続けるため、論理的には独立した変数であっても著しい性能劣化（**False Sharing**）が生じます。

    * **(b) `_Alignas(64)` による修正例と解消される理由：**
        [0-2節](0-2.md)のアラインメント制御を用い、2つのメンバを別々の64バイト・キャッシュラインへ分離します。

        ```c
        struct Counter {
            _Alignas(64) long c0;  // オフセット 0..7（1本目の64Bライン）
            _Alignas(64) long c1;  // オフセット 64..71（2本目の64Bライン）
        };
        ```

        `c0` と `c1` が異なるキャッシュラインへ分離されることで、コア0は `c0` のラインを、コア1は `c1` のラインをそれぞれ単独で `E → M` のまま保持し続けられるようになり、無効化やライン往復が消えて False Sharing が解消されます。

## 0-8. GPU・SIMD と並列ハードウェアの物理制約（SIMT・メモリ帯域・Roofline）

### 1. 動機（Why）：なぜ汎用 CPU だけでは AI や画像・集計処理の計算量に追いつけないのか

[0-3節](0-3.md)から [0-7節](0-7.md)までを通じて、現代の汎用 CPU が「パイプライン化・分岐予測・アウトオブオーダ実行・多階層キャッシュ」という精巧な仕掛けを総動員し、1 本の複雑なプログラムをできる限り低遅延（低レイテンシ）で動かす仕組みを学びました。

ところが、現代の計算機システムで比重が急速に増しているワークロード（**3D グラフィックス、動画エンコード、列指向データベースの集計（[8-7節](../8/8-7.md)）、そして深層学習・生成 AI［LLM］の行列計算**）には、従来の事務処理や OS カーネルとはまったく異なる特徴があります。

* 分岐（`if`）やポインタ追跡はほとんどなく、**「同じ足し算や掛け算を、何百万個もの配列要素や画素へ一斉に適用する（データ並列性：Data-Level Parallelism）」** 処理が大半を占めます。
* 汎用 CPU コアは、複雑な分岐予測器、リオーダバッファ（ROB）、巨大な L1/L2/L3 キャッシュといった「1 スレッドの待ち時間を削る制御回路」にシリコン面積の大部分を割いており、実際に数値計算を行う演算器（ALU / FPU）が占める面積はチップ全体のごく一部に過ぎません。

この構造的な非効率を打破し、同じシリコン面積・同じ消費電力の中で桁違いの演算スループットを引き出すために発展したのが、**CPU 内部の SIMD（ベクトル演算）** と **スループット特化型プロセッサである GPU（Graphics Processing Unit）** です。

本節では、[第0部](../index.md#part-0)の集大成として、**SIMD の仕組み**、**GPU の SIMT アーキテクチャとワープ分岐・コアレスアクセス**、そして並列ハードウェアの性能上限を 1 枚のグラフで統一的に説明する **Roofline モデル（演算律速 vs メモリ帯域律速）** を整理します。

---

### 2. 具体例と動作イメージ（Toy Model）

アーキテクチャの詳細に入る前に、2 つの具体的な対比で「SIMD の威力」と「CPU と GPU の設計思想の正反対さ」を確かめます。

#### 実験A：1,024 個の配列加算を「1 個ずつ（スカラ）」vs「8 個同時（SIMD）」で行う

32 ビット浮動小数点数（`float`：4 バイト）の配列 `a[1024]` と `b[1024]` を要素ごとに足して `c[1024]` へ書き込むループを考えます。

```c
for (int i = 0; i < 1024; i++) {
    c[i] = a[i] + b[i];
}
```

* **通常のスカラ演算（SISD）：**
    1 回の加算命令（`addss`）で 1 個の `float` だけを足すため、ループは **1,024 回** 回り、ロード 2,048 回・加算 1,024 回・ストア 1,024 回・分岐 1,024 回の計 5,000 命令以上が発行されます。

* **256 ビット SIMD 演算（x86-64 AVX2）：**
    CPU 内部の 256 ビット幅ベクトルレジスタ（`%ymm0`〜`%ymm15`）には、32 ビット `float` がちょうど **$256 \div 32 = \mathbf{8\text{ 個}}$** まとめて入ります。`vaddps %ymm0, %ymm1, %ymm2` という **1 命令** をフェッチ・デコードするだけで、8 組の加算が 1 クロックで同時実行されます。ループ回数は $1024 \div 8 = \mathbf{128\text{ 回}}$（8 分の 1）へ減少します。

#### 実験B：「フェラーリ数台（CPU）」vs「大型バス数百台（GPU）」

CPU と GPU の違いは、東京から大阪へ乗客を運ぶ乗り物の比喩で直感的に理解できます。

* **CPU（レイテンシ志向：フェラーリ 8 台）：**
    1 人の VIP 客（単一スレッドの複雑な処理）を最速で目的地へ届けるため、最高速度（高クロック）、先読みナビ（高精度な分岐予測）、途中の渋滞回避（アウトオブオーダ実行・大容量キャッシュ）にコストを集中します。

* **GPU（スループット志向：大型バス 100 台）：**
    1 台あたりの速度（クロック）は控えめで先読みナビも簡素ですが、チップ面積の大部分を座席（数千個の単純な演算器）へ割り当てます。1 人の客を運ぶ時間（レイテンシ）は CPU より遅くても、**10 万人の乗客をまとめて運ぶ総輸送量（スループット）では CPU を 1 桁〜2 桁上回ります**。

### 3. 構造・アルゴリズム・実装（What）

#### (1) フリンの分類と CPU の SIMD（ベクトル拡張命令）

コンピュータの並列実行方式は、命令の流れ（Instruction Stream）とデータの流れ（Data Stream）が単一か複数かによって **フリンの分類（Flynn's Taxonomy）** の 4 つに整理されます。

| 分類 | 意味 | 代表例 |
| :--- | :--- | :--- |
| **SISD** | 単一命令・単一データ | 古典的な単一コアのスカラ CPU |
| **SIMD** | 単一命令・複数データ | CPU のベクトル命令（x86 AVX2/AVX-512, ARM NEON/SVE, RISC-V V 拡張） |
| **MIMD** | 複数命令・複数データ | マルチコア CPU、マルチノード分散システム |
| **MISD** | 複数命令・単一データ | 航空宇宙の多重冗長フォールトトレラント計算機など特殊な用途 |

CPU の **SIMD（Single Instruction, Multiple Data）** は、命令フェッチ・デコード・分岐予測の回路を 1 系統だけ共有し、その 1 つの命令で複数の並列 ALU（レーン）を一斉に動かすことで、制御回路の電力と面積を増やさずに演算スループットを 4〜16 倍（実験Aの AVX2 なら 8 レーンで 8 倍）へ引き上げます（図0-8-1左）。

* **固定幅 SIMD（x86-64 SSE / AVX2 / AVX-512、ARM NEON）：** レジスタ幅が 128 / 256 / 512 ビットと命令セット（ISA）に固定されており、世代が上がって幅が倍になるたびに新しい命令群とバイナリの再コンパイルが必要になります。
* **可変長ベクトル（RISC-V V 拡張［RVV］・ARM SVE）：** 命令セットにベクトル幅を固定せず、実行時にハードウェアが持つ物理幅（`vlen`）を自動取得してループを回す **VLA（Vector-Length Agnostic）** 設計です。同じバイナリが将来 2 倍幅の CPU へ載っても、再コンパイルなしで新しいベクトル幅を活用できます（演算律速であれば理論上 2 倍の演算スループットを得られます）。

#### (2) GPU の内部構造：SIMT・ワープ（Warp）とレイテンシ隠蔽

GPU は、SIMD の発想をさらに押し広げた **SIMT（Single Instruction, Multiple Threads）** モデルを採用しています。プログラマは「1 本のスレッドが配列の 1 要素を担当する普通の関数（カーネル関数）」を書き、それを GPU 上で数万〜数百万スレッド同時起動します。

GPU ハードウェア（NVIDIA アーキテクチャ用語での説明。AMD でも構造は同型）は次の階層で構成されます。

* **SM（Streaming Multiprocessor）：** GPU 内に数十〜百数十個並ぶ独立した計算クラスタです。各 SM には多数の単純な演算コア（FP32/INT32 コア、行列演算用の Tensor Core）、少量の高速オンチップ SRAM（Shared Memory / L1 キャッシュ）、そして**大容量のレジスタファイル**が搭載されています。
* **ワープ（Warp：32 スレッドの実行単位）：** SM のスケジューラは、スレッドを 1 本ずつではなく **32 スレッドを 1 組（ワープ）** として束ね、1 つの命令フェッチユニットから同じ命令を 32 スレッドへ一斉に配信（ロックステップ実行）します。
* **0 サイクルのワープ切替によるレイテンシ隠蔽：**
    GPU は CPU のような巨大な L3 キャッシュを持たないため、グローバルメモリ（VRAM）からの読み込みには数百サイクルかかります。しかし SM の大容量レジスタファイルには、**数十個のワープ（千数百スレッド分）のレジスタ状態が最初から常駐**しています。あるワープ 0 がメモリ読込み待ちに入ると、SM スケジューラはレジスタのメモリ退避を行わず **0〜1 サイクルで別の準備完了ワープ 1 へ切り替え**、ワープ 0 のデータが返るあいだも他のワープで演算器を稼働させ続けます。

#### (3) GPU 性能を左右する 2 大制約：ワープ分岐とコアレスアクセス

GPU で理論性能を引き出すには、SIMT とメモリバスの物理制約に由来する次の 2 つの制約に注意する必要があります（図0-8-2）。

1. **ワープ分岐（Warp Divergence）：**
    同じワープ内の 32 スレッドは 1 つの命令を共有しています。もしワープの中で `if (tid % 2 == 0) { A(); } else { B(); }` のように偶数スレッドが `A`、奇数スレッドが `B` へ分岐すると、ハードウェアは 2 つを同時には実行できません。代わりに実行マスクを使い、**① 偶数スレッドだけ有効にして `A()` を実行（奇数スレッドは遊休）→ ② 奇数スレッドだけ有効にして `B()` を実行（偶数スレッドは遊休）** と直列化されるため、実行時間が 2 倍に伸びて実効スループットが半減します。

2. **メモリ・コアレッシング（Coalesced Memory Access）：**
    ワープ内の 32 スレッドが一斉にメモリロード命令を実行したとき、32 スレッドが参照するアドレスが**連続した 1 本の 128 バイト・キャッシュライン（`float` 4B × 32 ＝ 128B）**へ収まっていれば、ハードウェアは 32 個の要求を **1 回のメモリトランザクションへ統合（コアレス）** します。逆に、32 スレッドが飛び飛びの不連続なアドレスへアクセスすると、最大 32 回の個別メモリアクセスへ分裂し、実効メモリ帯域が数十分の 1 へ急落します（[0-7節](0-7.md)の空間的局所性の GPU 版です）。このため、メモリ配置は構造体の配列（**AoS**：`struct { float x, y, z; } p[N]`）よりも、属性ごとの配列（**SoA**：`struct { float x[N], y[N], z[N]; }`）に並べ替えると、32 スレッドが同じ属性 `x[tid]` を読むときにアドレスが連続してコアレス化しやすくなります。

#### (4) 演算性能とメモリ帯域の物理法則：Roofline モデル

SIMD や GPU を導入したとき、「理論上のピーク性能が $50\text{ TFLOPS}$ の GPU なのに、実際のプログラムでは $1\text{ TFLOPS}$ しか出ない」という現象が頻繁に起きます。その原因が「演算器不足」なのか「メモリ帯域不足」なのかを 1 本の式とグラフで診断できる枠組みが **Roofline モデル（Williams ら、2009年）** です（図0-8-3）。

まず、あるアルゴリズム（カーネル）が「主記憶から 1 バイト読み書きするあいだに、何回浮動小数点演算（FLOP）を行うか」を表す比率を **算術強度（Arithmetic Intensity：$I$）** と定義します。

$$
I = \frac{\text{総演算回数 [FLOP]}}{\text{主記憶との総転送バイト数 [Byte]}} \qquad [\text{FLOP/Byte}]
$$

ハードウェアのピーク演算性能を $P_{\text{peak}}\text{ [FLOP/s]}$、主記憶の最大帯域幅を $B_{\text{mem}}\text{ [Byte/s]}$ とすると、どんなに最適化しても達成可能な性能 $P\text{ [FLOP/s]}$ には次の上界（屋根＝Roofline）が存在します。

$$
P \;\le\; \min\bigl(\, P_{\text{peak}},\;\; B_{\text{mem}} \times I \,\bigr)
$$

2 つの上限が交わる境界の算術強度を **リッジポイント（Ridge Point：$I^* = P_{\text{peak}} / B_{\text{mem}}$）** と呼びます。

* **$I < I^*$（メモリ律速：Memory-Bound）：** 演算器はガラ空きなのに、主記憶からデータを運ぶパイプの太さ（$B_{\text{mem}}$）が詰まって性能が頭打ちになります。たとえば実験Aのベクトル加算 `c[i] = a[i] + b[i]` は、`a[i]`（4B 読込）＋`b[i]`（4B 読込）＋`c[i]`（4B 書込）の計 $12\text{ B}$ の転送に対して演算は加算 **1 FLOP** だけなので、算術強度はわずか $I = 1 / 12 \approx \mathbf{0.083\text{ FLOP/B}}$ です。
* **$I \ge I^*$（演算律速：Compute-Bound）：** 一度読み込んだデータをキャッシュや共有メモリ上で何十回・何百回も再利用するため、メモリ帯域に余裕が生まれ、ハードウェアのピーク演算性能 $P_{\text{peak}}$ を使い切れます。代表例が大きな $N \times N$ **行列積（GEMM）** であり、32 ビット `float` では総演算回数 $2N^3$ FLOP に対して入出力 3 行列の最小転送量が $3 \times 4N^2 = 12N^2\text{ B}$ であるため、ブロッキング（[0-7節](0-7.md)）と組み合わせることで算術強度 $I$ を $N/6$ に比例する数十〜数百 $\text{FLOP/B}$ まで引き上げられます。

> **【コラム：なぜ生成 AI 時代の GPU は「HBM（広帯域メモリ）」と「Tensor Core / TPU」へ進化したのか】**
>
> 大規模言語モデル（LLM）の推論には、Roofline モデル上で正反対の 2 つのフェーズが存在します。
>
> 1. **Prefill（プロンプト一括処理）：** 入力された数百〜数千トークンをまとめて巨大な行列積（行列 × 行列）として計算するため算術強度 $I$ が非常に高く、**演算律速** になります。これを高速化するのが、行列積和（$D = A \times B + C$）を低精度浮動小数点（FP16 / BF16 / FP8）で 1 サイクルに数百回実行する専用回路 **Tensor Core** や Google の **TPU（シストリックアレイ）** です。
> 2. **Decode（1 トークンずつの生成）：** 新しい単語を 1 個生成するたびに、モデルの数十 GB の重みパラメータすべてを VRAM から読み込み直して「行列 × ベクトル」の計算を行うため、算術強度が非常に低くなり **メモリ帯域律速** になります。そのため現代の AI 向け GPU（H100 / B200 等）は、通常の DDR メモリ（数十 GB/s）ではなく、DRAM チップを垂直に積層して数千本の広幅バスで GPU 直横に繋ぐ **HBM（High Bandwidth Memory：$3\text{〜}8\text{ TB/s}$）** を搭載し、「斜めの屋根（$B_{\text{mem}}$）」そのものを押し上げています。

### 4. 限界と補正（Critique & Adaptation）

#### (1) ホスト（CPU）⇄ デバイス（GPU）間のデータ転送ボトルネック

独立した GPU カードは CPU の主記憶（DDR）とは別の VRAM を持っており、両者は **PCIe バス**（例：PCIe Gen5 x16 で片道約 $64\text{ GB/s}$）で結ばれています。GPU 内部の HBM 帯域（数 $\text{TB/s}$）に比べて PCIe は 50 倍以上も細いため、「小さな配列を CPU から GPU へ転送して 1 回だけ加算して戻す」と、**データ転送時間だけで CPU 単体より何倍も遅くなります**。

* **補正：** データを一度 GPU の VRAM 上へ置いたら、多数の演算ステップを連続して GPU 側で完結させ（バッチ化）、あるいは Apple Silicon（M シリーズ）のように CPU と GPU が同一の物理メモリを直接共有する **ユニファイドメモリ（Unified Memory）**、データセンターでは複数 GPU 間を数百 GB/s で直結する **NVLink** を用います。

#### (2) アムダールの法則（Amdahl's Law）：逐次部分が並列化の天井を決める

どれほど強力な SIMD や数千コアの GPU を投入しても、プログラム全体に「並列化できない逐次処理（ファイル読込、初期化、結果の集約等）」の割合 $s$（$0 < s < 1$）が残っている限り、元の実行時間を $1$ とすると、並列度 $N$ を増やしても逐次部分 $s$ は変わらず並列部分 $(1 - s)$ だけが $(1 - s) / N$ に縮みます。そのため全体の高速化倍率 $S(N)$ は次式（**アムダールの法則**、[4-1節](../4/4-1.md)で詳述）で頭打ちになります。

$$
S(N) = \frac{1}{s + \dfrac{1 - s}{N}} \;<\; \frac{1}{s}
$$

たとえばプログラムの $10\%$（$s = 0.1$）が逐次処理のまま残っていると、たとえ並列化可能な $90\%$ を 10,000 コアの GPU で 0 秒に短縮しても、全体の高速化は最大 **$1 / 0.1 = 10\text{ 倍}$** を超えることはできません。並列ハードウェアを使いこなすには、演算器を並べるだけでなく逐次ボトルネックとデータ転送を徹底的に削る全体設計が不可欠です。

### 理解度チェック（第1部へ進む前の確認）

本節の Roofline モデル計算・GPU の SIMT 制約・アムダールの法則を確認し、[第1部](../index.md#part-1)（機械語と ISA）へ繋ぐ問いを置きます。

> **【確認の問い】**
>
> 1. **（Roofline モデルによる算術強度と律速判定の定量計算）**
>     ピーク演算性能 $P_{\text{peak}} = 20\text{ TFLOPS}$（$= 20 \times 10^{12}\text{ FLOP/s}$）、メモリ帯域幅 $B_{\text{mem}} = 1{,}000\text{ GB/s}$（$= 10^{12}\text{ Byte/s}$）の GPU を考えます。
>
>     * (a) この GPU の **リッジポイント** $I^* = P_{\text{peak}} / B_{\text{mem}}$（$\text{FLOP/Byte}$）を求めてください。
>     * (b) この GPU 上で次の 2 つの処理を実行するとき、それぞれ **メモリ律速** か **演算律速** かを判定し、Roofline モデルから得られる理論上の最大性能（$\text{TFLOPS}$）を計算してください。
>
>         * **処理①（ベクトル加算 `c[i] = a[i] + b[i]`）：** 32 ビット `float`（$4\text{ B}$）を 2 要素読込み・1 要素書込み（計 $12\text{ B}$）あたり $1\text{ FLOP}$（算術強度 $I_1 = 1 / 12\text{ FLOP/B}$）。
>         * **処理②（大規模行列積 GEMM）：** ブロック化により算術強度 $I_2 = 50\text{ FLOP/B}$ を達成。
>
> 2. **（ワープ分岐の境界判定と、アムダールの法則による並列化上限の検証）**
>
>     * (a) ワープサイズが 32 スレッドの GPU 上で、`tid = 0..63` の 64 スレッド（2 ワープ）を起動したとき、次の 2 つの分岐コードのうち**ワープ分岐（Warp Divergence）**が発生するのはどちらで、発生しないのはどちらかを判定し、その理由を説明してください。
>
>         * **コード①：** `if (tid % 2 == 0) { A(); } else { B(); }`
>         * **コード②：** `if (tid < 32) { A(); } else { B(); }`
>
>     * (b) あるプログラムの実行時間の $80\%$ を並列化可能な行列計算が占め、残り $20\%$ は並列化できない逐次処理（ファイル読込や CPU ⇄ GPU 間のデータ転送など）であるとします。ある開発者が「行列計算部分を GPU で 100 倍高速化すれば、プログラム全体も数十倍は速くなるはずだ」と主張しています。アムダールの法則を用いて実際の全体高速化倍率 $S(100)$ と理論上限（$N \to \infty$）を計算し、この主張がなぜ誤りかを説明してください。
>
> 3. **（[第1部](../index.md#part-1)への伏線：ハードウェアの世代交代とバイナリ互換性を両立する境界仕様）**
>     本節では、固定幅 SIMD（x86-64 AVX2 など）はベクトル幅が変わるたびに新しい命令群と再コンパイルが必要になる一方、可変長ベクトル（RVV / SVE）は同一バイナリのまま新しい物理幅を活かせることを見ました。同様に、5 年前の CPU と最新の CPU ではパイプライン段数・キャッシュ容量・アウトオブオーダ実行の規模が大きく異なります。もしコンパイラが生成する機械語バイナリがこれらの物理実装の詳細へ直接依存していたら、ソフトウェア配布や CPU の世代交代でどのような問題が起きるでしょうか。また、両者を切り離すための「共通の境界仕様（契約）」には、最低限どのような情報（命令・レジスタ・メモリなど）だけを定め、何を隠蔽すべきか考えてみてください。
