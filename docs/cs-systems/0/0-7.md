### 前節（0-6）の確認問題の解答

前節の最後に提示した3つの問いの解答を確認します。

1. **フォワーディング優先順位と `x0` 書き込み保護漏れバグの診断：**

    * **(a) 3命令連続実行時の候補値と `x7` の結果：**
        命令2（`addi x5, x5, 8`）はMEMフォワーディングで命令1の `12` を受け取り $12 + 8 = 20$ を計算します。命令3（`add x7, x5, x5`）がEXステージにあるとき、**MEMステージ（命令2）が `20`**、**WBステージ（命令1）が `12`** をそれぞれ `x5` の候補値として保持しています。より新しい **MEMステージ側が優先** されるため `20` が選択され、`x7` は $20 + 20 = \mathbf{40}$ になります。

    * **(b) `x0` 書き込み保護チェック漏れによるバグ：**
        命令1（`addi x0, x0, 99`）はALUで $0 + 99 = 99$ を計算し、`ExMe_rslt = 99`・`Me_rd = 0`・`Me_we = 1` の状態でMEMステージへ進みます。フォワーディング制御で `x0` の保護（`Ex_rs1 != 0` または `Me_rd != 0` の確認）が抜けていると、直後の命令2（`addi x6, x0, 1`）のEXステージで `Ex_rs1 == Me_rd`（`0 == 0`）が一致と誤判定され、MEMから `99` がフォワーディングされてしまいます。その結果、`x6` には本来の `1` ではなく $99 + 1 = \mathbf{100}$ という誤った値が入ります。

2. **ロード・ユースハザードの命令スケジューリングと総サイクル数短縮：**

    * **(a) そのまま実行した場合のストール回数と総サイクル数：**
        `lw x1` の直後の `add x2` で1回、`lw x3` の直後の `add x4` で1回、**合計 `2` 回**の1サイクル・ストールが発生します。5段パイプラインで4命令を流す基本サイクル数は $4 + 4 = 8$ サイクルであるため、ストール2回を加えて総サイクル数は $8 + 2 = \mathbf{10\text{ サイクル}}$ になります。

    * **(b) ストールを `0` 回にする並べ替えと短縮後の総サイクル数：**
        2つのロード命令を先にまとめ、その後に2つの加算命令を並べます。

        ```asm
        lw  x1, 0(x10)
        lw  x3, 4(x10)
        add x2, x1, x5
        add x4, x3, x6
        ```

        この順序であれば、`lw x1` と `add x2` の間に `lw x3` が、`lw x3` と `add x4` の間に `add x2` が挟まるため、どちらも **WB→EX フォワーディング** で間に合いストールは **`0` 回** になります。総クロックサイクル数は $4 + 4 = \mathbf{8\text{ サイクル}}$（2サイクル＝20%短縮）になります。

3. **命令ペア別のハザード判定と `sw` のフォワーディング経路：**

    * **(a) `addi x5, x1, 10` → `sw x5, 0(x10)`：**
        **ストールは不要（`0` 回）** です。`sw` のEXステージで `rs2`（`x5`）へ **MEM→EX フォワーディング**（`ExMe_rslt`）から最新値が届きます。`rs2` のフォワーディングMUXが即値 `imm` との選択MUXより手前に必要なのは、`sw` ではALUの第2入力にオフセット即値 `imm`（`0`）を選んでメモリアドレスを計算しつつ、データメモリへ書き込むストアデータとしてフォワーディング済みの最新の `rs2`（`x5`）を別に `ExMe` へ運ぶ必要があるためです。

    * **(b) `lw x5, 0(x10)` → `add x6, x7, x8` → `add x9, x5, x1`：**
        **ストールは不要（`0` 回）** です。間に無関係な1命令が挟まるため、`add x9` がEXステージにあるとき `lw` はちょうどWBステージにおり、**WB→EX フォワーディング**（`Wb_rslt2`）で最新値を受け取れます。

    * **(c) `lw x5, 0(x10)` → `sw x5, 8(x10)` と `sw` の優先順位：**
        EXステージ入力へのフォワーディングのみを持つ本節の標準設計では、`sw` がEXで `rs2` を受け取る時点で `lw` がまだMEMの途中にあるため、**`1` 回の1サイクル・ストール** が必要になります（1サイクル待ってWB→EXフォワーディングで受け取ります；※ストアデータはMEMステージまで使われないため、専用のMEM→MEMフォワーディング経路を追加すればストールを0にできる拡張もあります）。また、連続する2命令がともに `x5` を更新した直後の `sw` では、ストアデータ側の `rs2` フォワーディングMUXでも `rs1` 側と同じく、より新しい **MEMステージ側（`ExMe_rslt`）をWBステージ側（`Wb_rslt2`）より優先** します。

## 0-7. 記憶階層とCPUキャッシュ（局所性・セット連想・コヒーレンシ）

### 1. 動機（Why）：なぜCPUと主記憶の「約200倍の速度差」を放置できないのか

前節（[0-6節](0-6.md)）まで、私たちは「命令メモリやデータメモリへアクセスすれば、1クロックサイクルで必ず値が返ってくる」という理想化された前提のもとでパイプラインを設計してきました。

しかし、現実のハードウェアには深刻な物理的ギャップがあります。CPU内部のレジスタや演算器の速度が半導体微細化とともに大きく向上した一方で、大容量を安く作るための主記憶（**DRAM**：コンデンサに電荷を蓄えて記憶するメモリ）のアクセス速度はそれほど速くなりませんでした。その結果、現代のコンピュータでは、CPUが1命令を実行する時間（約 $0.3\text{〜}0.5\text{ ns}$）に対し、主記憶DRAMからデータを1回読み出す時間（約 $100\text{ ns}$）のあいだに**約200〜300倍もの速度差**が開いています（この乖離は**メモリの壁：Memory Wall**と呼ばれます）。

もしCPUの演算性能をどれだけ高めても、データを1つ読むたびに300サイクル待たされていれば、CPUは99%以上の時間を待ちぼうけで過ごすことになります。だからといって、主記憶の数十ギガバイトすべてをレジスタ並みに高速な回路（**SRAM**：フリップフロップ構造で高速だが高価なメモリ；物理構造の差は後述のコラム参照）で作ろうとすると、チップ面積・消費電力・製造コストのすべてが現実的な範囲を超えてしまいます。

「速くて小さい記憶装置」と「遅くて大きい記憶装置」のトレードオフを乗り越え、**あたかも「大容量かつ高速な1つのメモリ」があるかのように見せる仕組み**が、**記憶階層（Memory Hierarchy）**と **CPUキャッシュ（Cache）** です。本節では、キャッシュが機能する根拠となる「局所性」、ハードウェア内部の検索・書き込み構造、そしてマルチコア環境で生じる一貫性の問題までを整理します。

> **【コラム：SRAMとDRAMの物理構造差が「メモリの壁」を生む理由】**
>
> キャッシュに使う **SRAM（Static RAM）** と主記憶に使う **DRAM（Dynamic RAM）** の速度差とコスト差は、1ビットを記憶する物理セルの構造そのものから生じています。
>
> * **SRAM（6トランジスタ・フリップフロップ構造）：** [0-3節](0-3.md)の順序回路と同様に、複数のトランジスタ（標準的に6個）を組み合わせて電源が入っている限り値を静的に保持し続けます。読み出し時に電荷の充放電を待つ必要が少なく $1\text{ ns}$ 前後で応答できますが、1ビットあたりのシリコン面積が大きく消費電力も高いため、数十 MiB 程度が限界です。
> * **DRAM（1トランジスタ＋1コンデンサ構造：1T1C）：** 微小なコンデンサ（蓄電器）に電荷が溜まっているか否かで `1/0` を表します。素子数が少なく高密度・低コストに数十 GiB を作れる反面、2つの物理的制約を伴います。第1に、コンデンサの電荷は数ミリ秒で自然放電してしまうため、定期的に全セルを読み直して再充電する**リフレッシュ**が必要です。第2に、読み出し動作そのものがコンデンサの電荷を信号線へ放出する**破壊読み出し**であるため、読み出すたびに元の値を書き戻す手順が必要になり、アクセス遅延が $100\text{ ns}$ 近くまで大きくなります。
>
> この物理的トレードオフがある限り、「速くて小さいSRAM」と「遅くて大きいDRAM」を階層で組み合わせる設計は避けられません。

#### 実験B：配列の先頭を読んだら「隣の15個」も一緒に机へ運ばれる

`int a[16];` という4バイト整数16個（合計64バイト）の配列が、**先頭 `a[0]` が64バイト境界に整列した状態で**主記憶に並んでいるとします（配列全体がちょうど1本の64バイト・キャッシュラインに収まる前提です）。プログラムが `a[0]` を読み出すとき、CPUキャッシュは `a[0]` の4バイトだけを主記憶から運ぶのではなく、**`a[0]` を含む連続した64バイトのかたまり（`a[0]`〜`a[15]` すべて）** を一気にL1キャッシュへコピーします。

すると、ループで `a[0]`, `a[1]`, `a[2]`, ..., `a[15]` と順に読むとき、最初の `a[0]` だけは主記憶まで取りに行くため $100\text{ ns}$ かかります（**キャッシュミス**）が、残りの `a[1]`〜`a[15]` の15回はすべてL1キャッシュにすでに載っているため各 $1\text{ ns}$ で返ってきます（**キャッシュヒット**）。16回平均すれば、1回あたりわずか $(100 + 15 \times 1) / 16 \approx 7.2\text{ ns}$ まで待ち時間を縮められるのです。

### 3. 構造・アルゴリズム・実装（What）

#### (1) キャッシュが機能する根拠：参照の局所性（Locality）

もしプログラムが主記憶のあらゆる番地を毎回一様にランダムアクセスするなら、小さなキャッシュを置いてもほとんど当たらず意味がありません。キャッシュが高い確率（通常 $95\% \sim 99\%$ 以上）でヒットするのは、現実のプログラムが次の2種類の **参照の局所性（Locality of Reference）** を強く持つためです。

1. **時間的局所性（Temporal Locality）：** 「ついさっきアクセスしたデータや命令は、近い将来もう一度アクセスされる可能性が高い」という性質です。ループのカウンタ変数 `i` やループ本体の命令列、頻繁に呼ばれる関数が典型例です。
2. **空間的局所性（Spatial Locality）：** 「あるアドレスにアクセスした直後は、そのすぐ近くのアドレスにもアクセスされる可能性が高い」という性質です。配列の連続走査や、構造体の隣接メンバへのアクセス、順番に実行される命令列が典型例です。

キャッシュは、一度使ったデータを手元に残すことで**時間的局所性**を活かし、実験Bのように連続する64バイト（**キャッシュライン**）をまとめて読み込むことで**空間的局所性**を活かします。

#### (2) キャッシュラインとメモリアドレスの3分割

主記憶とキャッシュの間でデータをやり取りする固定長の最小単位を **キャッシュライン（Cache Line / キャッシュブロック）** と呼びます。現代の一般的なCPU（x86-64やRISC-Vの標準構成）では **64バイト** です。

CPUがあるメモリアドレスを読み出そうとするとき、キャッシュハードウェアはそのアドレスがキャッシュ内のどこにあるかを1サイクル程度で判定しなければなりません。そのために、メモリアドレスのビット列を次の3つのフィールドに分割して解釈します。

```text
+-----------------------------------+-------------------+--------------------+
|            タグ (Tag)             | インデックス(Index) | オフセット (Offset) |
+-----------------------------------+-------------------+--------------------+
         上位ビット                       中位ビット            下位ビット
  「主記憶のどの領域のデータか照合」   「キャッシュの何番の組か」 「64B内の何バイト目か」
```

具体例として、**32ビットアドレス**、キャッシュラインサイズ **$64\text{ B} = 2^6\text{ B}$**、キャッシュ内の組（セット）数が **$64\text{ 組} = 2^6$** の小さなキャッシュを考えます。

* **オフセット（6ビット）：** 64バイトのキャッシュラインの中の何バイト目かを指定します（$2^6 = 64$）。
* **インデックス（6ビット）：** キャッシュに用意された64個の組（セット `0`〜`63`）のうち、どの組を見に行くかを指定します（$2^6 = 64$）。
* **タグ（残り $32 - 6 - 6 = 20$ ビット）：** 同じインデックスへ割り当てられる主記憶上の候補は多数あるため、「今その場所に入っているデータが、本当に自分の探しているアドレスのものか」を照合するための識別子です。

さらに各キャッシュラインには、そのエントリに有効なデータが入っているかを示す **有効ビット（Valid bit, `V`）** が付いています。`V == 1` かつ `保存されているタグ == アドレスのタグ` であれば**キャッシュヒット**、そうでなければ**キャッシュミス**です。

#### (3) 配置方式の比較：直接写像 vs セット連想

主記憶のデータをキャッシュのどの位置へ置けるかには、代表的な3つの方式があります（座席に例えると、直接写像は「完全指定席」、$N$-wayセット連想は「決まった棚に $N$ 枠」、完全連想は「全席自由席」にあたります）。

1. **直接写像方式（Direct-Mapped Cache）：**
    各インデックスにつき格納場所（スロット）が**1個だけ**の方式です（図0-7-2左）。回路が単純で検索が速い反面、異なるアドレスでもインデックスが同じ2つのデータを交互に使うと、キャッシュ全体に空きが余っていても互いに追い出し合ってしまう弱点があります（後述の**競合ミス**）。

2. **$N$-way セット連想方式（$N$-way Set-Associative Cache）：**
    各インデックス（セット）につき格納場所を **$N$ 個（$N$ ウェイ、例：4-way や 8-way）** 用意する方式です（図0-7-2右）。インデックスで選んだセット内の $N$ 個のタグを**並列に同時比較**します。同じインデックスのデータが最大 $N$ 個まで共存できるため競合ミスが大きく減り、現代のCPUのL1/L2/L3キャッシュで標準的に採用されています。セットが満杯のときにどのウェイを追い出すかには、**LRU（Least Recently Used：最も長く使われていないものを追い出す）** またはその近似アルゴリズムが用いられます。

3. **完全連想方式（Fully Associative Cache）：**
    インデックスを設けず、キャッシュ内のどこにでも自由に置ける方式（セット数1、ウェイ数＝全ライン数）です。競合ミスは起きませんが、入力されたタグと全エントリを1サイクルで一斉比較する特殊な連想メモリ（**CAM**：Content Addressable Memory）の回路コストと消費電力が大きいため、エントリ数が数十〜数百個と少ない特殊なキャッシュ（仮想アドレスから物理アドレスへの変換結果をキャッシュする **TLB：Translation Lookaside Buffer** 等；詳細は[第3部](../index.md#part-3) [3-5節](../3/3-5.md)）に限って使われます。

ここで、キャッシュ容量・キャッシュラインサイズ・ウェイ数 $N$ からセット数とアドレス分割ビット数を求める関係式を確認しておきます。

$$\text{総キャッシュライン数} = \frac{\text{キャッシュ容量}}{\text{キャッシュラインサイズ}}, \qquad \text{セット数} = \frac{\text{総キャッシュライン数}}{\text{ウェイ数 } N}$$

たとえば、32ビットアドレスで容量 $16\text{ KiB}$（$2^{14}\text{ B}$）、ラインサイズ $64\text{ B}$（$2^6\text{ B}$）、**2-way セット連想**のキャッシュなら、総ライン数は $2^{14} / 2^6 = 2^8 = 256$ 本、セット数は $256 / 2 = 128 = 2^7$ 組になります。したがってアドレスのビット分割は、オフセット **6ビット**（$2^6 = 64$）、インデックス **7ビット**（$2^7 = 128$）、タグ **19ビット**（$32 - 7 - 6$）と一意に決まります。

#### (4) 書き込みポリシー：ライトスルー vs ライトバック

CPUがキャッシュ上のデータを**書き換えた**とき、その変更をいつ下位の主記憶へ反映するかには2つの方式があります。

* **ライトスルー（Write-Through）：** キャッシュへ書き込むのと同時に、下位の主記憶（または下位キャッシュ）へも毎回即座に書き込みます。主記憶の内容が常に最新に保たれるため管理は単純ですが、書き込みのたびに低速な下位記憶へのトラフィックが発生します。
* **ライトバック（Write-Back）：** キャッシュ上のデータだけを書き換え、そのラインに「変更済み・下位未反映」を示す **ダーティビット（Dirty bit）** を立てます。下位記憶への書き戻しは、そのラインがキャッシュから追い出される瞬間まで遅延させます。同じ変数をループ内で何百回も書き換えるような処理では、下位記憶への書き込みが最後の1回だけで済むため、現代のCPUキャッシュではライトバックが広く採用されています。

> **【コラム：2次元配列の「行優先走査」と「列優先走査」で実行時間が大きく変わる理由】**
>
> C言語の2次元配列 `int A[4096][4096];` の全要素の合計を求める2つのループを比べてみます。
>
> ```c
> // パターン1：行優先（内側ループで j を動かす）
> for (int i = 0; i < 4096; i++)
>     for (int j = 0; j < 4096; j++)
>         sum += A[i][j];
>
> // パターン2：列優先（内側ループで i を動かす）
> for (int j = 0; j < 4096; j++)
>     for (int i = 0; i < 4096; i++)
>         sum += A[i][j];
> ```
>
> 数学的にはまったく同じ足し算を同じ回数（約1,678万回）行っています。ところが実際に実行すると、パターン1の方がパターン2より**数倍〜10倍以上速く終わります**。
>
> 理由は、C言語が2次元配列を「行ごと（`A[0][0], A[0][1], A[0][2], ...`）」にメモリ上へ連続配置していることにあります。パターン1では隣り合う要素を順に読むため、1回のキャッシュミスで64バイト（`int` 16個分）を読み込めば続く15回がすべてL1ヒットになります（空間的局所性が最大）。一方、パターン2では1ステップごとに $4096 \times 4\text{ B} = 16\text{ KiB}$ も離れた番地へ飛び越えてアクセスするため、せっかく運んだ64バイトのうち4バイトしか使わずに次のラインへ移ってしまい、**ほぼ毎回キャッシュミス**が起きます。
>
> さらに、配列幅が `4096`（1行 $= 16\text{ KiB} = 2^{14}\text{ B}$）という**2のべき乗**であることも劣化に拍車をかけます。たとえば典型的な 32 KiB・8-way・64 BラインのL1キャッシュではセット数が $64$（$64 \times 64\text{ B} = 4\text{ KiB}$ 周期で同じインデックスへ戻る）であるため、$16\text{ KiB}$ 飛びでアクセスする列優先走査は、すべての要素が **`Index = 0` の同じ1つのセットへ集中**します。その結果、8行目までは8ウェイに収まっても9行目を読んだ瞬間に追い出しが連発し（次項3Cモデルの**競合ミス**）、キャッシュ全体の大半が空いたまま極端な性能低下（スラッシング）を起こします。
>
> 同じ原理は、数値計算の中核である**行列積** $C[i][j] = \sum_k A[i][k] \cdot B[k][j]$ でも顕著に現れます。素朴な3重ループ `i → j → k` 順では内側で `B[k][j]` を列方向へ飛び越しアクセスしてしまいますが、ループ順序を `i → k → j` に変えるだけで `B[k][j]` と `C[i][j]` の両方が行方向の連続アクセスになり大きく高速化します。さらに大きな行列では、行列全体をキャッシュに収まる小さな正方形ブロック（例：$32 \times 32$）に分割して小ブロック単位で積和を完結させる**ブロッキング（タイリング）**を行うことで、キャッシュ容量の限界による追い出し（容量ミス）も抑えられます。アルゴリズムの計算量（どちらも $O(N^2)$ や $O(N^3)$）が同じでも、キャッシュの仕組みを意識したデータアクセス順だけで実測性能は大きく変わるのです。

### 4. 限界と補正（Critique & Adaptation）

#### (1) キャッシュミスの3分類（3Cモデル）と平均メモリアクセス時間（AMAT）

キャッシュの性能を定量的に評価する基本指標が、**平均メモリアクセス時間（AMAT：Average Memory Access Time）**です。ヒット時の時間を $T_{\text{hit}}$、ミス率を $m$、ミスしたときに下位記憶から読み込む追加時間（ミスペナルティ）を $T_{\text{penalty}}$ とすると、

$$\text{AMAT} = T_{\text{hit}} + m \times T_{\text{penalty}}$$

で表されます。たとえば $T_{\text{hit}} = 1\text{ ns}$、$T_{\text{penalty}} = 100\text{ ns}$ のとき、ミス率 $m$ が $10\%$（$0.10$）だと $\text{AMAT} = 1 + 0.10 \times 100 = 11\text{ ns}$ ですが、ミス率を $1\%$（$0.01$）へ下げれば $\text{AMAT} = 2\text{ ns}$ まで縮まります。なお、L1・L2・L3のように多段キャッシュを構成している場合は、下位キャッシュの AMAT が再帰的にミスペナルティへ入ります（2段なら $\text{AMAT}_{\text{L1}} = T_{\text{hit,L1}} + m_{\text{L1}} \times (T_{\text{hit,L2}} + m_{\text{L2}} \times T_{\text{penalty,L2}})$ となります。ここで $m_{\text{L2}}$ は全メモリアクセスに対する割合ではなく、**L1でミスしてL2へ到達したアクセスのうちL2でもミスする割合［局所ミス率：Local Miss Rate］**である点に注意します）。キャッシュミスは原因別に次の3種類（**3Cモデル**）に分類されます。

1. **強制ミス（Compulsory Miss）：** プログラム開始後に初めてそのキャッシュラインへアクセスしたときに必ず起きるミスです。先読み（ハードウェアプリフェッチ）で緩和します。
2. **容量ミス（Capacity Miss）：** プログラムが同時に必要とするデータ量（ワーキングセット）がキャッシュの総容量を超えているために起きるミスです。キャッシュ容量の拡大や、データを小さなブロックに分割して処理するアルゴリズム（前項コラムで触れた行列積のブロッキング等）で補正します。
3. **競合ミス（Conflict Miss）：** キャッシュ全体に空きがあるのに、同じインデックスへ複数のデータが集中して追い出し合うことで起きるミスです。セット連想度 $N$ を増やすことで補正します。

#### (2) マルチコア環境のキャッシュコヒーレンシ（MESIプロトコル）

[0-3節](0-3.md)で確認した通り、現代のCPUは複数のコアを搭載しています。各コアはそれぞれ専用の高速なL1/L2キャッシュを持っているため、ここで新たな問題が生じます。

コア0とコア1の両方が、主記憶の同じアドレス `X`（初期値 `0`）を自身のL1キャッシュへ読み込んだとします。その後、コア0が自身のL1キャッシュ（ライトバック方式）で `X` を `1` に書き換えました。もし何の調整もしなければ、コア1が自分のL1キャッシュにある `X` を読んだとき、**古い値 `0` がそのまま返ってきてしまいます**。

このように複数のコアのキャッシュ間で同じアドレスの内容が矛盾しないように保つ仕組みを **キャッシュコヒーレンシ（Cache Coherency：キャッシュ一貫性）** と呼びます。代表的なハードウェア制御が、各キャッシュラインに4つの状態を持たせる **MESI プロトコル** です（図0-7-3左）。

* **M（Modified：変更済み／自分だけの変更済み原本）：** 自コアのキャッシュにだけ存在し、主記憶より新しい値へ書き換えられた状態（ダーティ）です。
* **E（Exclusive：排他／自分だけの未変更コピー）：** 自コアのキャッシュにだけ存在し、主記憶と一致している状態です。他コアに通知せず静かに `M` へ書き換えられます。
* **S（Shared：共有／他コアと共有中の未変更コピー）：** 他のコアのキャッシュにも同じラインが存在する可能性があり、主記憶と一致している状態です。
* **I（Invalid：無効／古くて使えないデータ）：** このキャッシュラインのデータは無効であり、次に使う際には再取得が必要です。

ここで **`E`（排他）状態** をわざわざ設けている理由は、バス通信の無駄を省くためです。もし `M, S, I` の3状態しかないプロトコル（MSI）だと、シングルスレッド（1本の処理の流れである**スレッド**だけで動くプログラム；詳細は[第4部](../index.md#part-4)）のように自コアしか使っていないデータを読み込んだ直後に書き換えるだけでも、「他コアにコピーがあるかもしれない」と考えて毎回バスへ無効化メッセージを送らなければなりません。`E` 状態によって「他コアは持っていない」と分かっていれば、初回書き込み時にバス通信を一切発生させず静かに `E → M` へ遷移できます。

一方、コア0とコア1がともに `X` を **S（共有）** 状態で持っているとき、コア0が `X` へ書き込みを行うと、コア0はバス（相互接続網）経由で他コアへ「`X` を書き換えるので手元のコピーを無効化せよ（Invalidate）」というメッセージを送り、コア1の `X` を **I（無効）** 状態へ遷移させてから自身を **M（変更済み）** にします。続いてコア1が `X` を読み出そうとすると、自キャッシュが `I` 状態であるためバス経由で読み出し要求を出します。これを監視していたコア0は最新の値 `1` をコア1（および主記憶側）へ供給して自身の状態を **`M → S`** へ下げ、データを受け取ったコア1も **`I → S`** へ遷移することで、両コアが最新の値 `1` を共有する状態へ戻ります。

#### (3) False Sharing（偽共有）とパディングによる補正

MESIプロトコルはキャッシュの一貫性を正しく守ってくれますが、コヒーレンシの管理が「1バイト単位」ではなく **「64バイトのキャッシュライン単位」** で行われるために、思わぬ性能劣化を引き起こすことがあります。それが **False Sharing（偽共有）** です（図0-7-3右）。

たとえばマルチスレッドプログラムで、コア0専用のカウンタ `count0`（4バイト）とコア1専用のカウンタ `count1`（4バイト）が、メモリ上で隣り合って**同じ64バイトのキャッシュライン**に載っていたとします。

* プログラムの論理上、コア0は `count0` しか触らず、コア1は `count1` しか触らないため、2つのスレッドは互いに独立しているように見えます。
* しかしハードウェアから見ると、同じキャッシュラインに対してコア0とコア1が交互に書き込みを行うため、**毎回「無効化 → ライン転送 → 無効化 → ライン転送」がコア間で延々と往復**します（キャッシュライン・ピンポン）。その結果、2コアで並列化したのに1コアで実行するより遅くなる現象が起きます。

この限界に対する実務上の補正は、[0-2節](0-2.md)で学んだパディングを逆手に取ることです。独立したスレッドが頻繁に書き換える変数同士の間にパディングを挟み（C11の `_Alignas(64)` やC++17の `alignas(64)` 等）、**別々の64バイト・キャッシュラインへ意図的に引き離す**ことで False Sharing を解消できます。

3. **[第4部](../index.md#part-4)（[4-3](../4/4-3.md)・[4-4節](../4/4-4.md)：メモリ一貫性モデルとスピンロック）：**

4. **[第5部](../index.md#part-5)（[5-5節](../5/5-5.md)：OSバッファキャッシュ）および[第9部](../index.md#part-9)（[9-1](../9/9-1.md)・[9-9節](../9/9-9.md)：DBバッファプールと分散一貫性）：**

### 理解度チェック（次節へ進む前の確認）

本節のセット連想キャッシュのアドレス分割・2階層 AMAT 比較・False Sharing の MESI 診断を具体的な計算とコードで確認します。

> **【確認の問い】**
>
> 1. **（8-way キャッシュのアドレス分割と競合ミスの診断）**
>     32ビットのメモリアドレスを使うコンピュータにおいて、容量 $32\text{ KiB}$（$2^{15}\text{ B}$）、キャッシュラインサイズ $64\text{ B}$（$2^6\text{ B}$）、**8-way セット連想方式**のL1キャッシュを考えます。
>
>     * (a) このキャッシュの総ライン数、セット数、および32ビットアドレスの「タグ」「インデックス」「オフセット」のビット幅をそれぞれ求めてください。
>     * (b) この8-wayキャッシュで、メモリアドレス `0x1000` と `0x2000`（$4\text{ KiB} = 2^{12}\text{ B}$ 間隔）へ交互に繰り返しアクセスしたとき、両者のインデックスとタグを求めたうえで、初回以降に競合ミスが起きるか判定してください。さらに、同じ64セット構成の直接写像キャッシュ（1-way・容量 $4\text{ KiB}$）での交互アクセスや、8-wayキャッシュで `0x1000`, `0x2000`, ..., `0x9000` の9種類を循環アクセスした場合と対比してください。
>
> 2. **（2階層 AMAT：ハードウェアの L2 追加 vs ソフトウェアの局所性改善）**
>     初期構成として、L1キャッシュのみ（ヒット時間 $T_{\text{hit,L1}} = 1\text{ ns}$、ミス率 $m_{\text{L1}} = 5\%$、主記憶へのミスペナルティ $100\text{ ns}$）のシステムがあり、このときの AMAT は $1 + 0.05 \times 100 = 6.0\text{ ns}$ です。これを改善する次の2案の AMAT を計算して比較してください。
>
>     * (a) **ハードウェア案（L2キャッシュ追加）：** L1の下位に L2キャッシュ（ヒット時間 $T_{\text{hit,L2}} = 10\text{ ns}$、L2の**局所ミス率** $m_{\text{L2}} = 20\%$、L2ミス時の主記憶ペナルティ $T_{\text{penalty,L2}} = 100\text{ ns}$）を追加した場合の $\text{AMAT}_{\text{L1}}$。
>     * (b) **ソフトウェア案（局所性改善）：** ハードウェアはL1のみのままで、配列の走査順やブロッキングを改善して L1ミス率を $m_{\text{L1}} = 1\%$ へ下げた場合の AMAT。両案の数値結果を比べ、性能改善におけるハードウェアとソフトウェアそれぞれの効果を述べてください。
>
> 3. **（False Sharing の MESI 状態遷移診断とパディングによる修正）**
>     64ビットLP64環境（`long` は8バイト、キャッシュラインは64バイト）のデュアルコアCPU上で、次の構造体が64バイト境界の先頭に配置されているとします。
>
>     ```c
>     struct Counter {
>         long c0;  // コア0のスレッドだけがループ内でインクリメント
>         long c1;  // コア1のスレッドだけがループ内でインクリメント
>     };
>     ```
>
>     * (a) コア0は `c0` だけ、コア1は `c1` だけを別々に更新しているのに並列実行すると著しく遅くなる理由（**False Sharing**）を、両コアが最初にこのラインを `S`（共有）状態で持っている場面から始め、「コア0が `c0` へ書込み → コア1が `c1` へ書込み」の1往復における **MESI 状態遷移**（`S`, `M`, `I` の変化とバス上の無効化）を使って説明してください。
>     * (b) [0-2節](0-2.md)のアラインメント知識を活かし、C11の `_Alignas(64)`（または明示的なパディング配列）を使ってこの構造体を修正した定義例を示し、なぜそれで問題が解消されるかを説明してください。
