### 前節（0-1）の確認問題の解答

前節の最後に提示した3つの問いの解答を確認します。問3-(b) がそのまま本節（バイトオーダとアラインメント）の導入になります。

1. **2の補数と符号拡張・ゼロ拡張の比較（`0xD6`）：**

    * **(a) 符号なし解釈 $U$・符号あり解釈 $S$ と橋渡し式の検算：**
        `0xD6` は2進数で $\texttt{11010110}_2$（MSB は $b_7 = 1$）です。

        * 符号なし整数：$U = 128 + 64 + 16 + 4 + 2 = \mathbf{214}$（16進数からも $13 \times 16 + 6 = 214$）です。
        * 符号あり整数（2の補数）：$S = -128 + 64 + 16 + 4 + 2 = -128 + 86 = \mathbf{-42}$ です。
        * 橋渡し式の確認：$U - S = 214 - (-42) = 256 = 1 \cdot 2^8 = b_7 \cdot 2^8$ となり一致します。

    * **(b) 16ビットへの拡張（ゼロ拡張 vs 符号拡張）：**

        * **ゼロ拡張：** 上位8ビットを `0` で埋めるため **`0x00D6`** になります。符号なし16ビット整数として解釈すると $13 \times 16 + 6 = \mathbf{214}$ となり、元の値が保たれます。
        * **符号拡張：** 元のMSBが `1` なので上位8ビットを `1` で埋め、**`0xFFD6`** になります。符号あり16ビット整数として解釈すると、符号なし値 $65{,}494$（$= 65{,}535 - 41$）から橋渡し式より $65{,}494 - 2^{16} = 65{,}494 - 65{,}536 = \mathbf{-42}$ となり、元の負の値が保たれます。

2. **オーバーフロー・暗黙変換・浮動小数点誤差の診断：**

    * **(a) 8ビット加算 $(-100) + (-50)$（$\texttt{10011100}_2 + \texttt{11001110}_2$）：**
        8ビット同士を加算すると、最上位から桁上がりが生じて次の結果になります。

        $$
        \begin{aligned}
          &\phantom{1\,}\texttt{10011100}_2 \quad (\texttt{0x9C}:\ \text{符号なし } 156\text{ ／ 符号あり } -100) \\
          +{}&\phantom{1\,}\texttt{11001110}_2 \quad (\texttt{0xCE}:\ \text{符号なし } 206\text{ ／ 符号あり } -50) \\
          \hline
          &\texttt{1\,01101010}_2 \quad (\text{下位8ビット } \texttt{0x6A})
        \end{aligned}
        $$

        下位8ビット $\texttt{01101010}_2$（**`0x6A`**）は、符号なし解釈でも符号あり解釈でも **$106$（$+106$）** です。最上位からの桁上がりがあるため **`CF = 1`**（符号なしオーバーフロー：$156 + 206 = 362 > 255$）、さらに負の数同士を足して非負の $+106$ になったため **`OF = 1`**（符号ありオーバーフロー：$-100 + (-50) = -150 < -128$）となり、**両方のフラグが同時に `1`** になります。

    * **(b) `delta < len` が偽になる理由：**
        C言語の通常の算術型変換により、符号ありの `int delta = -4` が比較相手の `unsigned int`（32ビット）へ暗黙変換されます。$-4$ の2の補数ビット列 `0xFFFFFFFC` は符号なし整数として $2^{32} - 4 = 4{,}294{,}967{,}292$ と解釈されるため、$4{,}294{,}967{,}292 < 16$ は偽（`0`）になります。

    * **(c) `double` 型の金額誤差と回避策：**
        $0.1 = \frac{1}{2 \times 5}$ は分母に素因数 $5$ を含むため2進数では無限循環小数（$0.000110011\dots_2$）になり、有限桁の仮数部へ丸める際に微小な誤差が生じます。10回加算すると誤差が累積して厳密な `1.0` と一致しない場合があるため、実務では最小通貨単位（円やセント）を**整数型**で扱うか、10進固定小数点型（`DECIMAL` 型等）を用います。

3. **UTF-8 のバイト境界分類と多バイト整数の格納順（本節への接続）：**

    * **(a) `41 E3 81 82 C3 A9` の分類：**
        各バイトを2進数にして先頭パターンを確認すると、次の通り合計 **3文字**（1バイト＋3バイト＋2バイト）から成ります。

        * `0x41`（`01000001`）：先頭 `0` → **1バイト文字（ASCII `'A'`）**
        * `0xE3`（`11100011`）：先頭 `1110` → **3バイト文字の先頭**
        * `0x81`（`10000001`）：先頭 `10` → **継続バイト**（2文字目の2バイト目）
        * `0x82`（`10000010`）：先頭 `10` → **継続バイト**（2文字目の3バイト目、`E3 81 82` で「あ」）
        * `0xC3`（`11000011`）：先頭 `110` → **2バイト文字の先頭**
        * `0xA9`（`10101001`）：先頭 `10` → **継続バイト**（3文字目の2バイト目、`C3 A9` で `U+00E9` `'é'`）

    * **(b) 多バイト整数で格納順の約束事が必要になる理由：**
        UTF-8 のバイト列は1バイトごとに先頭・継続の役割と並び順が仕様で固定されているため、機種をまたいでもバイト順の食い違いが起きません（バイトオーダに依存しません）。一方、4バイト整数 `0x11223344` の各バイトには順番を示す目印が付いていないため、1バイトごとに番地が付いたメモリへ置く際に「最上位バイト `0x11` から並べるか、最下位バイト `0x44` から並べるか」という規約（**バイトオーダ／エンディアン**）が不可欠になります。本節ではこの規則とアラインメント制約を整理します。

## 0-2. バイトオーダ（エンディアン）・アラインメントとパディング

### 1. 動機（Why）：なぜ1バイトごとのメモリ上で「並べる向き」と「置く番地」が問題になるのか

現代のコンピュータの主記憶（メインメモリ）は、**バイトアドレッシング（Byte addressing）**という方式をとっています。これは、メモリ全体を「1バイト（8ビット）の箱が一列に並んだ巨大な配列」とみなし、先頭から `0`, `1`, `2`, `3`, ... と1バイトごとに番地（アドレス）を振る仕組みです。

1バイトの文字（`char` 型など）を格納するだけなら、1つの番地にそのまま収まるため迷う余地はありません。ところが、32ビット整数（4バイト）や64ビット整数・**ポインタ**（メモリ上の番地を格納する変数。現代の64ビット環境では8バイト、32ビット環境では4バイト）といった**多バイトデータ**をメモリへ格納しようとすると、必ず次の2つの設計問題に直面します。

1. **どの順番でバイトを並べるか（バイトオーダ／エンディアン）：** たとえば4バイトの整数 `0x11223344` を `1000`〜`1003` 番地の連続した4箱に入れるとき、`1000` 番地に最上位の `0x11` を置くのか、最下位の `0x44` を置くのかを決めなければ、読み出したときに元の数値へ復元できません。
2. **どの番地から置き始めてよいか（アラインメントとパディング）：** CPUとメモリをつなぐデータ転送路（バス）は、効率のために1バイトずつではなく4バイトや8バイトといったまとまった幅で一気に読み書きします。もし4バイトの整数が区切りをまたいだ位置に置かれていると、ハードウェアが2回に分けて読み出して結合する処理が必要になったり、そもそもアクセスを拒否したりします。

この2つの制約は、メモリやファイルの中身を1バイトずつ16進数で一覧表示した**16進ダンプ**を読むとき、C言語の構造体のメモリ使用量を見積もるとき、そして異なるコンピュータ同士がネットワーク越しにデータをやり取りするときに必ず顔を出します。

### 2. 具体例と動作イメージ（Toy Model）

規則の整理に入る前に、2つの小さな例でエンディアンとパディングの振る舞いを確かめます。

#### 実験A：4バイト整数 `0x11223344` を `1000`〜`1003` 番地へ格納する

4バイトの16進数 `0x11223344` を1バイトずつ4つに分解すると、`0x11`、`0x22`、`0x33`、`0x44` になります。左端の `0x11` が最も桁の重みが大きい**最上位バイト（MSB：Most Significant Byte）**、右端の `0x44` が最も桁の重みが小さい**最下位バイト（LSB：Least Significant Byte）**です（※前節のビット単位のMSB/LSBと同じ略語なので、文脈でビットかバイトかを区別します）。

これをメモリの `1000`〜`1003` 番地へ並べる方法は、大きく次の2通りです。

* **ビッグエンディアン（Big-endian）：** 最上位バイト（`0x11`）を先頭（最小アドレス `1000`）に置きます。人間の読み書きする向きと同じ `11 22 33 44` の順になります。
* **リトルエンディアン（Little-endian）：** 最下位バイト（`0x44`）を先頭（最小アドレス `1000`）に置きます。メモリ上には逆順に見える `44 33 22 11` の順で並びます。

#### 実験B：`char`（1バイト）と `int`（4バイト）を持つ構造体のサイズ

次に、C言語で次の構造体を定義したとします。

```c
struct Item {
    char tag;   // 1 バイト
    int  price; // 4 バイト
};
```

素朴に足し算すれば、`sizeof(struct Item)` は $1 + 4 = 5$ バイトになりそうです。しかし、実際に一般的な64ビット環境（x86-64やRISC-V）でコンパイルしてサイズを測ると、結果は **$5$ バイトではなく $8$ バイト**になります。

理由は、4バイトの `int` 型メンバ `price` を「4の倍数の番地」から配置しなければならないためです。`tag` がオフセット `0`（1バイト）を占めたあと、オフセット `1`, `2`, `3` の **3バイト分が未使用の詰め物（パディング）** として空けられ、`price` はオフセット `4`〜`7` に置かれます。その結果、合計サイズは $1 + 3 + 4 = 8$ バイトになるのです。

### 3. 構造・アルゴリズム・実装（What）

#### (1) エンディアンの特徴と使い分け

現在広く使われている **x86-64、RISC-V、ARM** といったCPUアーキテクチャは、いずれも原則として**リトルエンディアン**を採用しています（ARMやRISC-Vは仕様上ビッグエンディアンモードも持ちますが、LinuxやWindowsなどの汎用OS上ではリトルエンディアンが標準です）。一方、かつてのPowerPCやSPARCなどの一部アーキテクチャ、そしてインターネットの通信プロトコル（IP・TCPヘッダ等）では**ビッグエンディアン**が採用されています。

両者にはそれぞれ実装上の小さな利点があります。

* **リトルエンディアンの利点：** 値が十分に小さいとき、同じ先頭アドレスから「4バイトとして読む」「2バイトとして読む」「1バイトとして読む」のいずれでも同じ数値が得られます。たとえば値 `0x00000012`（10進の18）をリトルエンディアンで `1000` 番地から置くと `12 00 00 00` となるため、`1000` 番地から1バイトだけ読んでも `0x12`（18）が得られます。また、多倍長整数の加算を下の桁から順に処理するとき、先頭からアドレスを1ずつ増やしながら下位桁から上位桁へ桁上げを伝播できるため、アドレスの進行方向と計算の向きが一致します。
* **ビッグエンディアンの利点：** 16進ダンプを人間が左から右へそのまま読める点に加え、先頭バイトを見るだけで符号ビット（MSB）がすぐ分かり、符号なし整数であれば先頭バイトからそのまま大小比較できます。

> **【コラム：「エンディアン」という名称の由来と、リトルエンディアンへの収斂】**
>
> 「エンディアン（Endian）」という言葉は、コンピュータ工学の造語ではなく、ジョナサン・スウィフトの風刺小説『ガリバー旅行記』（1726年）に由来します。物語の中で、小人国の住人たちが「ゆで卵の殻は丸い大きい方（Big End）から割るべきか、尖った小さい方（Little End）から割るべきか」という些細な違いをめぐって激しい対立を繰り広げ、それぞれ Big-Endian、Little-Endian と呼ばれます。
>
> 1980年、計算機科学者のダニー・コーエン（Danny Cohen）が、ネットワーク上でバイト順の統一をめぐる論争を風刺して書いた著名な論文 *"On Holy Wars and a Plea for Peace"* の中でこの言葉を引用したことから、技術用語として世界中に定着しました。
>
> 歴史的には、IBMのメインフレームや Motorola 68000系、初期のワークステーション（SPARC等）およびインターネットプロトコルがビッグエンディアンを採る一方、DEC VAX や Intel x86系がリトルエンディアンを採り、長らく両陣営が並立していました。現在では、PC・サーバの x86-64 がリトルエンディアンであるのに加え、仕様上は両モードを切り替えられる（バイエンディアンの）ARM や RISC-V でも、Linux・Windows・Android・iOS などの汎用OSはすべてリトルエンディアンを標準としており、ソフトウェア資産の互換性を背景に実務上はリトルエンディアンへほぼ収斂しています。なお、ビッグエンディアンのネットワークパケットを扱う際も、現代のCPUはバイト順を1命令で反転する専用命令（x86-64 の `bswap`、ARM の `rev` など）を備えているため、変換に伴う実行コストはごく小さく抑えられています。

#### (2) アラインメント制約とハードウェアの理由

**アラインメント（Alignment：境界調整）**とは、サイズ $k$ バイトのデータを「$k$ の倍数のメモリアドレス（**$k$ バイト境界**）」に配置する規則です。Linux等のx86-64環境で採用されるバイナリ規約（**System V AMD64 ABI**、詳細は[1-3節](../1/1-3.md)）における標準的なアラインメント要件は次の通りです（表中の **LP64** は `long` とポインタが64ビット、`int` が32ビットであるデータモデルを指します）。

| データ型（LP64環境） | サイズ | アラインメント要件（配置すべきアドレス） |
| :--- | :---: | :--- |
| `char` / `int8_t` | 1 バイト | 1 の倍数（任意のアドレス） |
| `short` / `int16_t` | 2 バイト | 2 の倍数（末尾ビットが `0`） |
| `int` / `int32_t` / `float` | 4 バイト | 4 の倍数（下位2ビットが `00`） |
| `long` / `int64_t` / `double` / ポインタ | 8 バイト | 8 の倍数（下位3ビットが `000`） |
| 16バイト整数（`__int128`）・128ビットSIMD型 | 16 バイト | 16 の倍数（下位4ビットが `0000`） |

なお、System V AMD64 ABI では個々のデータ型だけでなく、関数呼び出し時のスタックポインタ（[第1部](../index.md#part-1) [1-3節](../1/1-3.md)で詳述）も16バイト境界へ揃える規約が定められています。

なぜハードウェアはこのような制約を求めるのでしょうか。メモリはソフトウェアから見ると1バイト単位で番地が付いていますが、物理的なメモリコントローラやデータバスは、たとえば「4バイトごと（`0..3`, `4..7`, `8..11`, ...）」あるいは「8バイトごと」の固定された区切り（ワード境界）で一気にデータを転送する構造になっているためです。

* **整列されている場合（例：4バイト値を `1004` 番地から配置）：** `1004`〜`1007` は1つの4バイト区切りに丸ごと収まるため、**1回のメモリアクセス**でそのままレジスタへ読み込めます。
* **整列されていない場合（例：4バイト値を `1002` 番地から配置）：** `1002`〜`1003` が手前の区切り（`1000..1003`）に、`1004`〜`1005` が次の区切り（`1004..1007`）にまたがります。そのためCPUは**2回のメモリアクセス**を行い、不要な部分のビットを `0` で隠し（**ビットマスク**）、必要なバイトの位置を左右にずらして（**ビットシフト**）1つの数値へ繋ぎ合わせる余計な処理が必要になります（図0-2-2）。

#### (3) 構造体のパディング規則と配列の連続配置

C言語などのコンパイラは、プログラム中のすべてのデータがこのアラインメント制約を満たすように、構造体の内部や末尾へ自動的に未使用バイト（**パディング：Padding**）を挿入します。パディングの配置は次の2つの規則で一意に決まります。

1. **メンバ間のパディング（内部アラインメント）：** 構造体の各メンバは、構造体先頭からのオフセットが「そのメンバ自身のアラインメント要件の倍数」になる位置へ置かれます。満たさない場合は直前にパディングを詰めます（先頭メンバは常にオフセット `0` なので、構造体の先頭にパディングが入ることはありません）。なお、構造体の中に `char buf[5]` のような**配列メンバ**が含まれる場合、そのアラインメント要件は配列全体の合計サイズ（5バイト）ではなく、**要素型（`char` なら1バイト、`int arr[3]` なら4バイト）のアラインメント要件**に従います。
2. **構造体末尾のパディング（全体サイズの切り上げ）：** 構造体全体のアラインメント要件は「含まれるメンバの中で最大のアラインメント要件」に一致し、構造体全体のサイズ（`sizeof`）も**その最大アラインメント要件の倍数**になるよう末尾にパディングが足されます。

なぜ「末尾」にもパディングが必要なのでしょうか。それは**配列の規則**と噛み合わせるためです。配列では要素同士のあいだにパディングを入れず、メモリ上へ隙間なく連続配置する決まりになっています（要素 `a[i]` のアドレスを単純な `先頭 + i * sizeof(要素)` で計算するためです）。

たとえば実験Bの順序を逆にした `struct Item2 { int price; char tag; };` を考えます。`price` はオフセット `0..3`、`tag` はオフセット `4` なので、これだけで $5$ バイトに収まりそうです。しかし、配列 `struct Item2 arr[2];` は構造体全体のアラインメント要件に従って先頭 `arr[0]` が4の倍数の番地（たとえばオフセット `0`）に置かれます。もし `sizeof(struct Item2)` が `5` のままだと、2要素目 `arr[1]` の先頭がオフセット `5` になってしまい、`arr[1].price` が4バイト境界に違反します。末尾に3バイトのパディングを入れて全体サイズを `8` バイトに揃えておくことで、配列の全要素が常にアラインメント制約を満たせるようになるのです（図0-2-3）。

> **【コラム：構造体パディングと未初期化データによる `memcmp` バグ・カーネル情報漏洩】**
>
> 構造体のメンバ間や末尾に挿入されたパディング領域は、プログラムから明示的に名前を付けてアクセスできない「見えない隙間」です。この領域の中身は、C言語の仕様上、個別のメンバへ代入しただけでは初期化されず、**以前にそのメモリ領域を使っていた別の処理の残骸（不定値）**がそのまま残ります。
>
> この性質は、実務で2種類の深刻な問題を引き起こします。
>
> 1. **`memcmp` による構造体比較の不一致：** たとえば `struct Item x, y;` に対して `x.tag = 'A'; x.price = 100;` および `y.tag = 'A'; y.price = 100;` と全メンバへまったく同じ値を代入しても、パディングの3バイトに入っているゴミデータが異なっていれば、`memcmp(&x, &y, sizeof(struct Item))` は `0`（一致）を返しません。構造体同士の比較はメンバ単位で行うか、事前に `memset(&x, 0, sizeof(x))` でパディングを含めて全バイトをゼロ初期化しておく必要があります。
> 2. **OSカーネルからの情報漏洩脆弱性：** OSの中核であるカーネル（[第3部](../index.md#part-3)・[第5部](../index.md#part-5)で詳述）が、一般プログラム（ユーザ空間）からの依頼（システムコール）に対する応答を構造体へ詰めて返すとき、パディング領域をゼロクリアし忘れると、**カーネル内部の一時記憶領域（スタックやヒープ）に残っていた機密データ（他の実行中プログラムのデータやカーネルのアドレス配置など）がパディング経由で一般プログラム側へ漏洩**してしまいます。Linuxカーネル等の実務開発では、ユーザ空間へ渡す構造体は必ず `memset` でゼロ初期化するか、明示的なダミーメンバで隙間を埋める規約が徹底されています。

### 4. 限界と補正（Critique & Adaptation）

エンディアンとアラインメントの規則は、単純なプログラムではコンパイラが裏側で面倒を見てくれますが、システムレベルの設計や性能チューニングでは次の3つの課題に直面します。

#### (1) アラインメント違反が招く性能劣化とクラッシュ

通常のCコードを書いている限りコンパイラが自動でパディングを入れてくれますが、バイト配列へのポインタを直接 `int *` 等へ型変換（キャスト）したり、コンパイラ拡張（GCCの `__attribute__((packed))` 等）でパディングを強制禁止したりすると、非整列アドレスへのアクセスが発生します。

このとき何が起きるかはCPUアーキテクチャと命令の種類によって異なります。x86-64の通常の整数ロード命令ではハードウェアが2回アクセスを代行してくれるため「遅くなるだけで動く」ことが多い一方、1命令で16バイトや32バイトの複数データを並列演算する高速なベクトル命令（**SIMD命令**の `movdqa` 等）や、単純な固定長命令を基本とする一部の **RISC** 環境ではアラインメント違反が起きた瞬間にハードウェア例外が発生し、**OSによってプログラムが即座に強制終了（不正メモリアクセスを示す Segmentation fault や、境界違反等を示す Bus error）**します。ネットワークパケットの解析などで非整列データを安全に読み出す場合は、ポインタの直接キャストを避け、`memcpy` を使って整列されたローカル変数へコピーするのが移植性の高い補正です（現代のコンパイラは固定サイズの `memcpy` を効率的なロード命令へ最適化します）。

#### (2) 構造体メンバの宣言順序によるメモリ消費量の差

コンパイラはC言語の規格上、プログラマが書いた構造体メンバの順序を勝手に並べ替えることができません。そのため、**同じメンバを持つ構造体でも、宣言する順番が違うだけでメモリ消費量が大きく変わります**（図0-2-4）。

```c
// 宣言順が悪い例：合計 12 バイト（パディング 6 バイト）
struct BadOrder {
    char a;   // offset 0 (1B) + padding 3B
    int  b;   // offset 4 (4B)
    char c;   // offset 8 (1B) + tail padding 3B
};

// 大きい型から並べた例：合計 8 バイト（パディング 2 バイト）
struct GoodOrder {
    int  b;   // offset 0 (4B)
    char a;   // offset 4 (1B)
    char c;   // offset 5 (1B) + tail padding 2B
};
```

#### (3) 異機種間・ネットワーク通信でのエンディアン不一致

リトルエンディアンのマシンがメモリ上の `0x11223344`（バイト列 `44 33 22 11`）をそのままネットワークや共有ファイルへ書き出し、ビッグエンディアンのマシンがそれをそのまま読み込むと、値が `0x44332211` に化けてしまいます。

この不一致を防ぐため、インターネットプロトコル（TCP/IP）では**通信路上の標準バイトオーダ（ネットワークバイトオーダ）をビッグエンディアンに統一する**規約が定められています。プログラムは送信前に自機の形式（ホストバイトオーダ）からネットワークバイトオーダへ変換し、受信後に逆変換を行います（UNIX系OSの標準API規格である **POSIX** の `htons` / `htonl` / `ntohs` / `ntohl` 関数など。それぞれ `h`＝host、`n`＝network、`s`＝16ビット値 `uint16_t`、`l`＝32ビット値 `uint32_t` を指します。`l` は16ビット〜32ビット時代に `long` が32ビットだった歴史的命名の名残であり、64ビットのLP64環境で `long` が8バイトになった現在でも `htonl` / `ntohl` は常に32ビット値 `uint32_t` を変換する点に注意してください）。また、ファイル形式やAPI設計でも、エンディアンを仕様で明記するか、UTF-8テキスト（JSON等）のようにバイトオーダに依存しない形式を選ぶことで問題を回避します。

### 理解度チェック（次節へ進む前の確認）

本節のエンディアン変換・構造体アラインメント・実務バグ診断を具体的な計算とコードで確認します。

> **【確認の問い】**
>
> 1. **（エンディアンと `htons` 変換忘れによるポート誤認）**
>     リトルエンディアンのマシン上で、Webサーバの待受ポート番号 `80`（16ビット符号なし整数 `uint16_t`、16進表記で `0x0050`）をネットワークへ送る場面を考えます。
>
>     * (a) 変数 `port = 80` がメモリの `2000`〜`2001` 番地に置かれたとき、リトルエンディアン環境で `2000` 番地と `2001` 番地に入るバイト値をそれぞれ16進数で答えてください。
>     * (b) `htons(80)` を呼び忘れてこの2バイト列をそのままネットワーク（ビッグエンディアン規約）へ送った場合、受信側の機器はこの2バイトを何番のポート（16進数および10進数）として誤認するでしょうか。
>
> 2. **（配列メンバを含む構造体のオフセット計算・並べ替えと末尾パディング）**
>     64ビットLP64環境（`char`: 1B・1B境界、`int`: 4B・4B境界、`double`: 8B・8B境界）において、次の構造体 `struct RecordA` を考えます。
>
>     ```c
>     struct RecordA {
>         char   tag[3];
>         double value;
>         int    id;
>     };
>     ```
>
>     * (a) `struct RecordA` の各メンバのオフセットと、構造体全体のサイズ（`sizeof(struct RecordA)`）を求めてください（メンバ間パディングと末尾パディングのバイト数も明記してください）。
>     * (b) 同じ3つのメンバをアラインメント要件の大きい型から順に並べ替えた `struct RecordB` を示し、そのサイズと、なお末尾パディングが必要になる理由（配列 `struct RecordB arr[2]` を例に）を説明してください。
>
> 3. **（パディング領域と非整列アクセスに由来する実務バグの診断）**
>     次の2つのCコード片には、アラインメントとパディングに起因する実務上の問題が潜んでいます。それぞれの原因と安全な修正方法を答えてください。
>
>     * (a) 実験Bの構造体 `struct Item { char tag; int price; };` の変数 `a`, `b` に対し、各メンバへ同じ値を代入したあと `memcmp(&a, &b, sizeof(struct Item)) == 0` で等価判定したところ、一致しないことがある。
>     * (b) ネットワークから受信したバイト配列 `uint8_t buf[16]` の先頭から1バイト目（`buf + 1`）に入っている4バイト整数を読み出すため、`int x = *(int *)(buf + 1);` と書いたところ、あるCPU環境やSIMD命令使用時に異常終了（Bus error 等）が起きた。
