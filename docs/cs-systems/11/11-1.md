### 前節（10-3）の確認問題の解答

前節の最後に提示した3つの問いの解答を確認します。問3がそのまま[第11部](../index.md#part-11)（分散システムと信頼性工学）の本節の導入になります。

1. **L4 ロードバランサ（DSR）vs L7 リバースプロキシの仕組みと診断：**

    * **(a) 巨大な動画配信における DSR 方式の帯域回避と、ARP 応答無効化忘れによる破綻：**
        DSR（Direct Server Return）方式では、**往路**（小さなリクエスト）だけを L4 ロードバランサが宛先 MAC アドレスの書き換えによってバックエンドへ転送し、**復路**（巨大な動画レスポンス）はバックエンドがループバックインタフェース（`lo`）に保持する VIP を送信元 IP にセットしてクライアントへ直接返却するため、ロードバランサの帯域ボトルネックを回避できます。
        もしバックエンドの `lo` で VIP に対する **ARP 応答の無効化を忘れる**と、上流ルータが VIP の MAC アドレスを問い合わせた際にバックエンド自身も応答してしまいます。その結果、ルータの ARP テーブルが特定のバックエンドの MAC アドレスへ書き換わり、以降のトラヒックが L4 ロードバランサを迂回してその 1 台へ直接集中してしまい、負荷分散が破綻します。

    * **(b) 単一ドメイン HTTPS のパス別振分で L7 が必要な理由と `X-Forwarded-For`：**
        L4 ロードバランサはトランスポート層の 5 つ組（IP・ポート・プロトコル）だけを見て転送し、TLS の暗号化ペイロードを復号しないため、HTTP の URL パス（`/api/*` や `/images/*`）を読み取れません。パス別に振り分けるには、TLS を終端してアプリケーション層（HTTP）を解釈できる **L7 リバースプロキシ** が必要です。
        また、L7 プロキシが接続を終端するとバックエンドから見た TCP の送信元 IP がすべてプロキシの IP になってしまうため、元のクライアント IP を後段へ引き継ぐ目的で **`X-Forwarded-For`**（または標準の `Forwarded`）ヘッダを付与します。

2. **CDN のキャッシュスタンピード対策と安全なキャッシュヘッダ設計：**

    * **(a) 毎秒 10,000 リクエスト・オリジン処理 100 ms 時の比較：**
        期限切れ後の 100 ms のあいだに $10{,}000 \times 0.1 = \mathbf{1{,}000}$ 件のリクエストが到着します。

        * **対策なし：** 到着した **1,000 件すべて** がキャッシュミスとして一斉にオリジンへ到達し、オリジンを過負荷に追い込みます。ユーザは全員が 100 ms 以上（過負荷によりさらに長期）待たされます。
        * **① Request Collapsing：** オリジンへ転送されるのは先頭の **1 件のみ** に抑えられます。ただし、同時に到着した 1,000 人のユーザはその 1 件の応答が返るまで、到着タイミングに応じて最大 **100 ms** 待たされます。
        * **② `stale-while-revalidate`：** オリジンへ届くリクエストは裏側の非同期再取得の **1 件のみ** に抑えられ、かつ期限切れ後の猶予期間内であれば、1,000 人のユーザ全員へ古いキャッシュが **数 ms で即答** されるため待ち時間がほぼゼロになります。

    * **(b) 2 種類のコンテンツに対する `Cache-Control` 方針と、ハッシュなし `bundle.js` の障害：**

        * **① 注文履歴ページ（個人データ）：** **`Cache-Control: private, no-store`** とし、CDN などの共有キャッシュへ保存して他ユーザへ個人情報が誤配信される事故を防ぎます。
        * **② コンテンツハッシュ付き `bundle.3a9f1c.js`：** 内容変更時に URL 自体が変わるため、**`Cache-Control: public, max-age=31536000, immutable`** を設定して長期間キャッシュさせ、更新時は新しいハッシュの URL へ切り替える（キャッシュバスティング）ことで高いキャッシュヒット率と即時反映を両立します。
        * **ハッシュなしの `bundle.js` に `max-age=31536000, immutable` を誤設定した場合の障害：** 新バージョンを同じ URL のままデプロイしても、ブラウザや CDN が最大 1 年間オリジンへの再検証（`If-None-Match` 等）すら行わず古い `bundle.js` を返し続けてしまい、バグ修正や新機能がユーザへ反映されない・更新後のバックエンド API と旧 JS の仕様不整合で画面が壊れるといった障害が発生します。

3. **物理時計による因果順序逆転と論理時計の導入（本節への接続）：**
    各サーバの水晶発振子の個体差や温度変化によるクロックドリフトと、NTP のネットワーク遅延・非対称性により、物理時計はサーバ間で数ミリ秒〜数十ミリ秒ずれるため、「送信時刻より受信時刻の方が小さい」という因果の逆転が起きます。物理時計だけに頼らず、「原因となるイベントの番号が必ず結果となるイベントの番号より小さくなる」順序を保証するには、メッセージ送受信に同期してカウンタを更新する **論理時計（Lamport の論理時計やベクタクロック）** を導入します。本節では、分散システムにおける「時間と因果順序」の仕組みを体系的に学びます。

## 11-1. 分散システムの時間と順序（論理時計と因果関係）

### 1. 動機（Why）：なぜ分散システムでは「時計の時刻」ではなく「因果の前後関係」が重要なのか

[第10部](../index.md#part-10)（[10-1](../10/10-1.md)〜[10-3節](../10/10-3.md)）までで、仮想マシン・コンテナ・ロードバランサ・CDN を組み合わせて現代の Web インフラをスケールさせる仕組みを学びました。ここからの最終部 **[第11部](../index.md#part-11)** では、複数台のノードが協調して状態を維持・合意する **分散システムと信頼性工学** の核心へ進みます。

単一マシンの OS 上では、CPU のクロックやタイマ割り込み、共有メモリ上の順序（[4-3節](../4/4-3.md)）によって「どちらの出来事が先に起きたか」を 1 つの基準で扱えました。しかし、複数の独立したマシンがネットワーク越しにメッセージをやり取りする分散システムでは、次の 3 つの理由から「絶対的な共通時刻」を前提にできません。

1. **物理時計は必ずズレる（クロックドリフトとクロックスキュー）：** 各サーバのハードウェア時計（RTC / 水晶発振子）はわずかな周波数誤差や温度変化で少しずつ進んだり遅れたりし（**クロックドリフト**）、ある瞬間におけるノード間の時刻差（**クロックスキュー**）を生みます。NTP（Network Time Protocol）で定期補正しても、ネットワーク遅延の揺らぎや往路・復路の非対称性があるため、LAN 内でも数ミリ秒、広域網では数十ミリ秒の誤差が残るうえ、補正時に時計が過去へ巻き戻ることさえあります。
2. **「同時刻」の定義が曖昧：** 光速やネットワーク遅延がある以上、「東京のサーバで 14:00:00.100 に起きた出来事」と「大阪のサーバで 14:00:00.100 に起きた出来事」が、相対的な因果関係を持つのか、まったく無関係に並行して起きたのかを物理タイムスタンプだけでは判別できません。
3. **分散ログ・分散 DB の整合性への直結：** 分散データベースで 2 つの更新が競合したときや、分散トレース・障害調査で複数ノードのイベントを並べるとき、「原因（送信・先行更新）が必ず結果（受信・後続更新）より前に並んでいること」を保証する仕組みが必要です。

本節では、レスリー・ランポート（Leslie Lamport）が 1978 年に定式化した **Happens-Before（先行発生）関係** と **Lamport の論理時計**、因果関係の有無を正確に区別できる **ベクタクロック**、そして物理時計の誤差上限を明示的に扱う現代的なアプローチまでを整理します。

### 2. 具体例と動作イメージ（Toy Model）

数式に入る前に、2 つの小さな例で「物理時計の逆転による誤解」と「論理カウンタの受け渡しによる順序保証」を確かめます。

#### 実験A：物理時計が 10 ms ずれている 2 台のサーバで起きるログの食い違い

ノード $N_1$（時計が 5 ms 進んでいる）と、ノード $N_2$（時計が 5 ms 遅れている）の 2 台（両者のクロックスキューは合計 10 ms）があるとします。

1. $N_1$ がローカル時計 `12:00:00.005`（実際の時刻は `12:00:00.000`）に「残高を 100 万円へ更新」というイベント $e_1$ を起こし、$N_2$ へ通知メッセージを送ります。
2. $N_2$ が 2 ms 後（実際の時刻は `12:00:00.002`）にメッセージを受信し、ローカル時計 `11:59:59.997` に「残高を 80 万円へ更新」というイベント $e_2$ を起こします。
3. その後、監視システムが各ノードのローカルタイムスタンプだけで全イベントを並べると、**「$e_2$（`11:59:59.997`）が $e_1$（`12:00:00.005`）より先に起きた」** という**原因と結果が逆転した順序**になってしまいます。

#### 実験B：メッセージへ「今のカウンタ値」を同封して渡す（論理時計の直感）

物理時計を見るのをやめ、各ノードが「自分だけの整数カウンタ $L$（初期値 `0`）」を持ち、次の単純な 2 ルールだけを守ってみます。

* 自分が何かイベントを起こすたびに、自分のカウンタを **$L \leftarrow L + 1$** します。
* 他ノードへメッセージを送るときは、**更新後の自分のカウンタ値 $L$ をメッセージへ一緒に書き込んで送ります**。
* メッセージ（相手が送ったカウンタ値 $m$ を含む）を受け取った側は、自分のカウンタを **$\max(L, m) + 1$** に更新してから受信イベントを記録します。

実験Aと同じ「$N_1$ が送信 $\to$ $N_2$ が受信して後続処理」をこのルールで追ってみます。

1. $N_1$ が送信イベントを起こす $\implies$ $L_1$ が `0 → 1` になり、値 **`1`** を添えてメッセージを送ります。
2. $N_2$ がメッセージ（`m = 1`）を受け取る $\implies$ $L_2 = \max(0, 1) + 1 = \mathbf{2}$ へ進みます。

どんなにネットワークが遅れても、物理時計が何秒ズレていても、**「受信側のカウンタ（`2`）は必ず送信側のカウンタ（`1`）より大きくなる」** ことが常に保証されます。

### 3. 構造・アルゴリズム・実装（What）

#### (1) Happens-Before（先行発生）関係 $\to$ と並行関係 $\parallel$

Lamport（1978年）は、分散システム内のイベント集合における因果的な前後関係を **Happens-Before 関係（$a \to b$：「$a$ は $b$ に先行して発生する」）** として次の 3 規則で厳密に定義しました（[4-3節](../4/4-3.md)のメモリモデルで登場した Happens-Before の分散システム版です）。

1. **同一プロセス（ノード）内の順序：** イベント $a$ と $b$ が同じノード内で発生し、$a$ が $b$ より先に実行されたならば、**$a \to b$**。
2. **メッセージ送受信の因果順序：** イベント $a$ が「メッセージ $m$ の送信」であり、イベント $b$ が「同じメッセージ $m$ の受信」であるならば、**$a \to b$**。
3. **推移律：** $a \to b$ かつ $b \to c$ ならば、**$a \to c$**。

また、非反射性（どのイベント $a$ についても $a \to a$ ではない）と非対称性（$a \to b$ ならば $b \not\to a$）を満たす半順序（厳密半順序）です。

ここで、任意の 2 つの異なるイベント $a, b$ について、**$a \to b$ でもなく、$b \to a$ でもないとき**、両者は互いに因果的な影響を与え合わない **並行（Concurrent）** なイベントであるといい、**$a \parallel b$** と書きます（図11-1-1）。

#### (2) Lamport の論理時計（Lamport Logical Clock）と「時計条件」

各ノード $P_i$ が保持する論理時計 $C_i$（初期値 $0$）は、次の 2 つの更新規則に従います。実験Bの $L_1: 0 \to 1$ は規則 1 に、$L_2 = \max(0, 1) + 1 = 2$ は規則 2 に対応しています。

* **規則 1（内部・送信イベント）：** ノード $P_i$ でイベント $a$ が発生する直前に、$C_i$ を $1$ 増やし、その値をイベントのタイムスタンプ $C(a)$ とします。

    $$C_i \leftarrow C_i + 1,\qquad C(a) = C_i$$

* **規則 2（メッセージ受信イベント）：** ノード $P_i$ がタイムスタンプ $t_m = C(m_{\text{send}})$ 付きメッセージを受信するイベント $b$ の直前に、自ノードの時計と受信タイムスタンプの大きい方をとったうえで $1$ を増やし、その値を $C(b)$ とします。

    $$C_i \leftarrow \max\bigl(C_i,\; t_m\bigr) + 1,\qquad C(b) = C_i$$

これにより、次の **時計条件（Clock Condition）** が常に成り立ちます。

> **【Lamport の時計条件】**
> 任意の 2 つのイベント $a, b$ について、**$a \to b$ ならば、必ず $C(a) < C(b)$ が成り立つ**。

> **【重要な注意点：逆は必ずしも成り立たない】**
> $a \to b \implies C(a) < C(b)$ は**常に真**ですが、その**逆「$C(a) < C(b)$ ならば必ず $a \to b$ である」は成り立ちません**。たとえば図11-1-1 の $c$（$C(c) = 1$）と $b$（$C(b) = 2$）は互いに通信していない並行イベント（$c \parallel b$）ですが、$C(c) < C(b)$ となっています。したがって、Lamport 論理時計のタイムスタンプの大小だけでは「原因と結果なのか、単なる無関係な並行イベントなのか」を区別できません。

また、Lamport 論理時計の値を使って全イベントに全順序 $a \prec b$ を与えるには、たとえば「$C(a) < C(b)$、または $C(a) = C(b)$ かつノード識別子 $\text{id}(P_i) < \text{id}(P_j)$」のようにタイブレーカを付ければ一意の全順序を作れますが、その全順序はあくまで「因果順序（$a \to b \implies a \prec b$）と矛盾しない並べ方の一例」に過ぎず、並行イベントの前後関係に因果的意味はありません。

#### (3) ベクタクロック（Vector Clock）：因果関係と並行性の同値判定

Lamport の論理時計は「$a \to b$ なら $C(a) < C(b)$」を満たしますが、$C(a) < C(b)$ だけでは $a \to b$ か $a \parallel b$ かを区別できません。これを**双方向（必要十分）に判別できる**ように拡張したのが **ベクタクロック（Vector Clock：Fidge / Mattern、1988〜1989年）** です。

システムに $N$ 個のノード $P_1, \dots, P_N$ があるとき、各ノード $P_i$ は長さ $N$ の整数配列（ベクトル）$\mathbf{V}_i[1 \dots N]$（初期値はすべて `0`）を保持します。$\mathbf{V}_i[k]$ は、「$P_i$ 自身がこれまでに認識している、ノード $P_k$ 上で発生したイベント数」を表します。

* **更新規則：**

    1. **自ノードのイベント（内部・送信）：** イベント $a$ の直前に、自ノードの成分だけを $+1$ します。

        $$\mathbf{V}_i[i] \leftarrow \mathbf{V}_i[i] + 1$$

        メッセージ送信時は、更新後のベクトル $\mathbf{V}_i$ 全体をメッセージへ同封します。

    2. **メッセージ受信イベント $b$：** 相手からベクトル $\mathbf{V}_{\text{msg}}$ を受け取ったとき、各成分 $k = 1 \dots N$ について要素ごとの最大値をとり、そのうえで自ノードの成分 $i$ だけを $+1$ します。

        $$\mathbf{V}_i[k] \leftarrow \max\bigl(\mathbf{V}_i[k],\; \mathbf{V}_{\text{msg}}[k]\bigr) \quad (\forall k),\qquad \mathbf{V}_i[i] \leftarrow \mathbf{V}_i[i] + 1$$

* **2 つのベクタクロック $\mathbf{u}, \mathbf{v}$ の比較と因果・並行の同値定理：**
    2 つの長さ $N$ のベクトル $\mathbf{u} = (u_1, \dots, u_N)$ と $\mathbf{v} = (v_1, \dots, v_N)$ について、

    * **$\mathbf{u} \le \mathbf{v}$：** すべての $k \in \{1, \dots, N\}$ に対して $u_k \le v_k$ が成り立つこと。
    * **$\mathbf{u} < \mathbf{v}$：** $\mathbf{u} \le \mathbf{v}$ であり、かつ**少なくとも 1 つの $k$ について厳密に $u_k < v_k$** が成り立つこと。

    このとき、任意の異なる 2 つのイベント $a$（ベクタ $\mathbf{u}$）と $b$（ベクタ $\mathbf{v}$）について（各イベントで発生ノードの自成分が増えるため $a \neq b$ なら $\mathbf{u} \neq \mathbf{v}$ です）、次の **同値関係** が成り立ちます。

    $$a \to b \quad \Longleftrightarrow \quad \mathbf{u} < \mathbf{v}$$

    $$a \parallel b \quad \Longleftrightarrow \quad \neg(\mathbf{u} < \mathbf{v}) \;\land\; \neg(\mathbf{v} < \mathbf{u}) \quad \bigl(\text{すなわち } (\mathbf{u} \not\le \mathbf{v}) \;\land\; (\mathbf{v} \not\le \mathbf{u})\bigr)$$

    図11-1-1 で確かめると、$a:(1,0,0) < b:(2,0,0) < d:(2,2,0) < g:(2,3,0) < f:(2,3,2)$ と成分ごとに単調増加して因果連鎖 $a \to b \to d \to g \to f$ が一目で分かり、一方 $c:(0,1,0)$ と $b:(2,0,0)$ は第 1 成分（$0 < 2$）と第 2 成分（$1 > 0$）が互いに逆転しているため **$c \parallel b$（並行・無関係）** と一意に判定できます。

#### (4) 物理時計の限界を超えるアプローチ：HLC と TrueTime

純粋な論理時計は「事象の前後関係」を正確に捉えますが、「現実世界の何時何分に起きたか（外部の物理時刻との対応や、リースの有効期限）」を扱うには物理時計も必要になります。現代の分散データベースでは、物理時計のズレを前提とした次の 2 つの方式が使われます。

* **HLC（Hybrid Logical Clock：ハイブリッド論理時計）：**
    物理時刻（NTP 等）を上位に、論理カウンタを下位に組み合わせ、「物理時計がずれても常に因果順序 $a \to b \implies \text{HLC}(a) < \text{HLC}(b)$ を壊さず、かつ物理時刻からの乖離を小さく保つ」実用的な時刻表現です（CockroachDB, YugabyteDB 等）。

* **Google Spanner の TrueTime API：**
    GPS 受信機と原子時計を各データセンターへ配備し、現在時刻を単一の点 $t$ ではなく **「真の時刻 $t_{\text{abs}}$ は必ず区間 $[t_{\text{earliest}},\, t_{\text{latest}}]$ の中にある（片側誤差の上限 $\varepsilon$、区間幅 $2\varepsilon$ を保証）」** という不確実性区間として返す API です（図11-1-2）。
    トランザクション $T_1$ はコミット時刻として区間の上端 $s_1 = t_{\text{latest}}$ を選び、真の時刻が確実に $s_1$ を過ぎる（`TT.now().earliest > s_1` が成り立つ）まで最大 **$2\varepsilon$** だけ待機してからコミットを完了します（**Commit Wait**）。もし片側分の $\varepsilon$ しか待たないと、$T_1$ のノード時計が $+\varepsilon$ 進んでいて直後の $T_2$ のノード時計が $-\varepsilon$ 遅れている最悪ケースで $s_2 < s_1$ と逆転し得ますが、最大 **$2\varepsilon$** 待つことで $s_1 < t_{\text{abs}}(T_1\text{完了}) < t_{\text{abs}}(T_2\text{開始}) \le s_2$ が必ず成立し、物理時計のズレによらない厳密な外部一貫性（線形化可能性）を分散トランザクションへ与えています。

### 4. 限界と補正（Critique & Adaptation）

#### (1) ベクタクロックのスケーラビリティ限界（ノード数 $N$ の増大と動的メンバーシップ）

ベクタクロックは因果関係と並行性を正確に判定できますが、**ベクトル長がシステム全体のノード総数 $N$ に比例（$O(N)$）** します。ノード数が 3〜10 台程度なら問題ありませんが、数千〜数万台規模の分散システムや、ノードが頻繁に参加・離脱する環境では、毎回のメッセージへ数千個の整数を載せる通信オーバーヘッドと $N$ の動的変化の管理が重くなります。

* **補正：** 大規模な分散システムでは、全ノードのベクトルを毎回送る代わりに、「因果履歴が必要な因果一貫性（Causal Consistency：[11-2節](11-2.md)）を限られたクライアント／レプリカ群で追跡する」、あるいは次節（[11-2節](11-2.md)）で学ぶ **単一リーダーと任期番号（Term）・インデックス番号（Index）** によって順序を一元化する合意プロトコル（Raft 等）を採用します。

#### (2) 「順序が分かること」と「全員が同じ状態へ合意すること」の違い（次節への動機）

Lamport 時計やベクタクロックは、「あるイベントが別のイベントに先行したか」という **因果の順序** を教えてくれます。しかし、ネットワーク分断やノードクラッシュが起きている中で、「**複数台のレプリカが、どの更新をどの順番で確定させるかについて全員で合意する**」という問題には、順序だけでは足りず **合意アルゴリズム（Consensus）** が必要になります。次節（[11-2節](11-2.md)）では、その中核である **Raft** と **データ複製・一貫性モデル** へ進みます。
