### 前節（3-2）の確認問題の解答

前節の最後に提示した3つの問いの解答を確認します。問3がそのまま本節（スケジューリングとコンテクストスイッチ）の導入になります。

1. **`fork()` のプロセス数と戻り値のトレース：**

    * **`"hello\n"` の出力回数：** **合計 4 回** です。最初の `fork()` でプロセスが 1 個から 2 個（親と子1）に増え、その両方が2回目の `fork()` を実行するため合計 $2 \times 2 = 4$ 個のプロセスになり、4個すべてが `printf("hello\n")` を実行します。
    * **最初の `fork()` の戻り値：** 親プロセスには **新しく生まれた子プロセスの PID（正の整数）** が返り、子プロセスには **`0`** が返ります。

2. **`fork` と `exec` の分離、および `cd` が組み込みコマンドである理由：**

    * **(a) `ls > out.txt` における `fork` と `exec` 分離の利点：**
        `fork()` で作られた子プロセスが `exec("ls")` を呼ぶ**直前の隙間**で、`close(1)` と `open("out.txt", ...)` を実行して標準出力（FD 1）だけをファイルへ差し替えられる点にあります。親シェルのFDテーブルは一切汚れず、`ls` 本体のコードもリダイレクトを意識せずに済みます。

    * **(b) `cd` を親シェル自身が直接実行しなければならない理由：**
        カレントディレクトリは各プロセス固有の状態です。もし `cd` を子プロセスで実行すると子プロセスのディレクトリだけが変わって直後に終了してしまい、親シェルの作業ディレクトリは元のまま変わらないため、`cd` はシェルの組み込みコマンドとして親自身が `chdir()` を呼ぶ必要があります。

3. **複数の `RUNNABLE` プロセスを1個のCPUでどう切り替えるか（本節への接続）：**
    OSカーネルは、**スケジューラ**が一定の基準（公平性・応答性・スループット）に従って次に実行するプロセスを選び、**コンテクストスイッチ**によって現在のプロセスのCPU状態（RISC-Vでは14本の callee-saved レジスタ群）をメモリへ退避して次のプロセスの状態へ差し替えることで、1個のCPUを多数のプロセスで安全に分け合います。

## 3-3. マルチタスキング・スケジューリングとコンテクストスイッチ

### 1. 動機（Why）：1個のCPUコアで「多数のプログラムが同時に動いている」ように見せるには

前節（[3-2節](3-2.md)）の `fork()` によって、システムの中には複数の実行可能なプロセス（`RUNNABLE`）が同時に存在するようになりました。しかし、CPUコアが1個しかない場合、ある瞬間に物理的に命令を実行できるプロセスは常に **1つだけ** です。

それでも私たちがパソコンを使うとき、エディタで文字を打ちながら裏でコンパイルを走らせ、さらに音楽を再生するといった作業がすべて同時進行しているように見えます。これを実現するのが、1個のCPUを数ミリ秒単位の細かい時間枠（**タイムスライス／タイムクォンタム**）で高速に切り替え続ける **時分割マルチタスキング（Time-Sharing Multitasking）** です。

この仕組みをOSカーネルに実装するには、性格の異なる次の2つの層を分けて設計する必要があります。

1. **ポリシー（Policy：誰を次に選ぶか＝スケジューリング）：**
    重い計算を続けるバッチ処理と、キー入力へ即座に反応してほしい対話アプリが同時に待っているとき、どの順番でどれだけの時間CPUを渡すべきでしょうか。性能指標（スループット・ターンアラウンド時間・応答時間）の間には明確なトレードオフが存在します。

2. **メカニズム（Mechanism：どうやって切り替えるか＝コンテクストスイッチ）：**
    実行中のプロセスAからプロセスBへCPUを移すとき、Aの計算途中のレジスタやスタックを一切壊さずに凍結し、後から戻ってきたときに何事もなかったかのように再開させるには、アセンブリレベルでどのレジスタをどう退避・復元すればよいでしょうか。

本節では、小さな3ジョブの手計算でスケジューリング方式のトレードオフを確かめたうえで、RISC-V（xv6モデル）におけるコンテクストスイッチ関数 `swtch` の実装構造までを一貫して整理します。

### 2. 具体例と動作イメージ（Toy Model）

スケジューリングの理論に入る前に、同じ3つのジョブを3種類のルールで実行し、待ち時間の違いを手計算で確かめます。

#### 実験A：3つのジョブ（A: 10ms, B: 2ms, C: 2ms）を3方式でスケジュールする

時刻 $t = 0$ に、次の3つのプロセスが同時に `RUNNABLE` 状態になったとします（切替自体のコストは $0\text{ ms}$ と仮定します）。

* **プロセス A：** 重い計算処理（必要なCPU時間 **$10\text{ ms}$**）
* **プロセス B：** 軽い対話処理（必要なCPU時間 **$2\text{ ms}$**）
* **プロセス C：** 軽い対話処理（必要なCPU時間 **$2\text{ ms}$**）

スケジューリングの良さを測る代表的な2つの指標で評価します。

* **ターンアラウンド時間（Turnaround Time）：** 到着してから処理が完了するまでの総時間（$T_{\text{完了}} - T_{\text{到着}}$）。全体の仕事のはけ具合を表します。
* **応答時間（Response Time）：** 到着してから**初めてCPUをもらえるまで**の待ち時間（$T_{\text{初回実行}} - T_{\text{到着}}$）。対話アプリの体感の軽快さを表します。

3つの代表的なアルゴリズムでガントチャートを描いて計算してみます（図3-3-1）。

1. **FCFS（First-Come, First-Served：到着順 `A → B → C`）：**

    * 実行順：A（$0 \sim 10$）→ B（$10 \sim 12$）→ C（$12 \sim 14$）
    * ターンアラウンド時間：A $= 10$, B $= 12$, C $= 14$ $\implies$ 平均 $\dfrac{10 + 12 + 14}{3} = \mathbf{12.0\text{ ms}}$
    * 応答時間：A $= 0$, B $= 10$, C $= 12$ $\implies$ 平均 $\dfrac{0 + 10 + 12}{3} \approx \mathbf{7.33\text{ ms}}$
    * **問題点：** 先頭に来た重いプロセスAが終わるまで、すぐ終わるBとCが延々と待たされます（**コンボイ効果：Convoy Effect**）。

2. **SJF（Shortest Job First：最短ジョブ優先 `B → C → A`）：**

    * 実行順：B（$0 \sim 2$）→ C（$2 \sim 4$）→ A（$4 \sim 14$）
    * ターンアラウンド時間：B $= 2$, C $= 4$, A $= 14$ $\implies$ 平均 $\dfrac{2 + 4 + 14}{3} \approx \mathbf{6.67\text{ ms}}$
    * 応答時間：B $= 0$, C $= 2$, A $= 4$ $\implies$ 平均 $\dfrac{0 + 2 + 4}{3} = \mathbf{2.0\text{ ms}}$
    * **特徴：** 同時到着の条件では平均ターンアラウンド時間が**数学的に最小**になりますが、現実のOSは「各プロセスがあと何ミリ秒で終わるか」を事前に知ることができません。

3. **ラウンドロビン（RR：タイムクォンタム $q = 2\text{ ms}$、`A → B → C → A...`）：**

    * 実行順：A（$0 \sim 2$、残り8）→ B（$2 \sim 4$、完了）→ C（$4 \sim 6$、完了）→ A（$6 \sim 14$、完了）
    * ターンアラウンド時間：A $= 14$, B $= 4$, C $= 6$ $\implies$ 平均 $\dfrac{14 + 4 + 6}{3} = \mathbf{8.0\text{ ms}}$
    * 応答時間：A $= 0$, B $= 2$, C $= 4$ $\implies$ 平均 $\dfrac{0 + 2 + 4}{3} = \mathbf{2.0\text{ ms}}$
    * **特徴：** 処理時間を事前に知らなくても、2msごとに順番を回すだけでコンボイ効果を解消し、高い応答性を確保できます。

### 3. 構造・アルゴリズム・実装（What）

#### (1) 非プリエンプティブ vs プリエンプティブ・マルチタスキング

プロセスを切り替えるタイミングの制御方式には2種類あります。

* **非プリエンプティブ（協調的：Cooperative）：** 実行中のプロセスが自分からシステムコール（I/O待ちや `yield` 等）を呼んでCPUを手放すまで、OSは強制的に切り替えません。実装は単純ですが、1つのプロセスが無限ループに陥るとシステム全体が止まります。
* **プリエンプティブ（横取り型：Preemptive）：** [3-1節](3-1.md)で見た**タイマ割り込み**を使い、タイムクォンタム（たとえば $1\text{〜}10\text{ ms}$）が経過するたびにOSカーネルが実行中のプロセスからCPUを強制的に取り上げ（`yield`）、別の `RUNNABLE` プロセスへ切り替えます。Linux・macOS・Windows・xv6 といった現代の汎用OSはすべてプリエンプティブ方式を採用しています。

#### (2) コンテクストスイッチの実装（RISC-V `swtch` と14本の callee-saved レジスタ）

では、プリエンプティブにプロセスAからプロセスBへ切り替える瞬間、OSカーネルの内部ではどのような機械語が実行されているのでしょうか。ここが、**[1-3節](../1/1-3.md)で学んだ関数呼び出し規約（ABI）の仕組みが直接活かされる場面**です。

xv6（RISC-V）では、コンテクストスイッチの本体は **`swtch(struct context *old, struct context *new)`** というわずか約30命令のアセンブリ関数として実装されています。ここで注目すべきは、**`swtch` が退避・復元するレジスタは全32本の汎用レジスタではなく、`ra`, `sp`, `s0`〜`s11` のたった14本だけ**であるという事実です。

```asm
# void swtch(struct context *old, struct context *new);
# a0 = old（退避先構造体）, a1 = new（復元元構造体）
swtch:
    sd ra, 0(a0)      # 1. 現在の戻り番地・スタックポインタ・s0〜s11 を old へ退避
    sd sp, 8(a0)
    sd s0, 16(a0)
    ...               # (s1 〜 s10 の退避)
    sd s11, 104(a0)

    ld ra, 0(a1)      # 2. 次のコンテクストの ra・sp・s0〜s11 を new から復元
    ld sp, 8(a1)
    ld s0, 16(a1)
    ...               # (s1 〜 s10 の復元)
    ld s11, 104(a1)

    ret               # 3. 復元された「新しい ra」のアドレスへ戻る
```

なぜ `t0`〜`t6` や `a0`〜`a7`（caller-saved レジスタ）を退避しなくてよいのでしょうか。理由は単純です。`swtch` はカーネル内のC言語コードから**通常の関数呼び出し**として呼ばれるため、コンパイラはABIの約束に従って「`swtch` を呼び出した後にまだ使いたい caller-saved レジスタは、あらかじめ呼び出し元のカーネルスタック上へ退避しておく」コードを自動生成しているからです。したがって、`swtch` 自身は **callee-saved レジスタ（`s0`〜`s11`）** と **スタックポインタ `sp`**、そして **戻り番地 `ra`** の14本だけを切り替えれば完全に安全なのです（なお、U-mode で動いていたユーザプログラムの全32本レジスタは、カーネルへ入った直後のトラップ入口で `trapframe` へすでに退避済みです：[3-6節](3-6.md)）。

最後の `ret` 命令の振る舞いこそがコンテクストスイッチの核心です。`ld ra, 0(a1)` と `ld sp, 8(a1)` を実行した瞬間に**カーネルスタックと戻り番地が別人のものへすり替わっている**ため、`ret` 命令は呼び出し元（プロセスA）ではなく、**`new` が前回 `swtch` を呼んで止まった場所**へ復帰します。

#### (3) スケジューラ経由の2段階切替（プロセスA → スケジューラ → プロセスB）

さらに xv6 の実装では、プロセスAのカーネルスタックから直接プロセスBへ飛び移るのではなく、各CPUコアに専用の **スケジューラ・コンテクスト（`cpu->context`）** を用意し、常に **「プロセスA → スケジューラ → プロセスB」** という2段階のスイッチを行います（図3-3-2）。

1. **プロセスAの停止（`yield` → `sched`）：** タイマ割り込みを受けたプロセスAは、自分のカーネルスタック上で `state = RUNNABLE` とし、`swtch(&pA->context, &cpu->context)` を呼んでスケジューラへCPUを戻します。
2. **次プロセスの選択（`scheduler` ループ）：** 動き出したスケジューラはプロセス表を順に走査し、`RUNNABLE` なプロセスBを見つけると、`pB->state = RUNNING` にして `swtch(&cpu->context, &pB->context)` を呼びます。
3. **プロセスBの再開：** プロセスBは、前回自分が `sched` の中で `swtch` を呼んで眠った直後の行から目覚め、トラップ復帰（`sret`）を経てユーザ空間の実行を再開します。

#### (4) 実用スケジューリングへの発展：MLFQ と Linux CFS

実験Aの単純なラウンドロビン（RR）は公平ですが、「CPUをほとんど使わずキー入力だけ待つ対話アプリ」も「CPUを100%使い続ける動画エンコード」も同じ優先度で並ぶため、対話アプリの数ミリ秒の反応が遅れがちです。そこで現実のOSでは、次の2つの発展的な設計が広く使われています。

1. **MLFQ（Multi-Level Feedback Queue：多段フィードバックキュー）：**
    「ジョブの長さを事前に知らなくても、**過去の振る舞いからSJF（短いジョブ優先）を自動近似する**」巧みなアルゴリズムです（図3-3-3）。優先度の異なる複数のキュー（例：高・中・低）を用意し、次の規則で運用します。

    * 新規プロセスはまず**最高優先度キュー**に入れます。
    * 与えられたタイムクォンタムを**最後まで使い切った**プロセス（CPUバウンドな重い計算）は、1段低い優先度キューへ**降格**させます。
    * クォンタムを使い切る前に**I/O待ち等で自らCPUを手放した**プロセス（対話アプリ等）は、同じ高い優先度を**維持**します。
    * 低いキューに落ちたプロセスが永久に実行されない飢餓（スターベーション）を防ぐため、一定周期 $S$ ごとに**全プロセスを最高優先度キューへ引き上げます（プライオリティブースト）**。

2. **CFS（Completely Fair Scheduler：完全公平スケジューラ）と EEVDF：**
    Linuxカーネルで長らく標準採用されてきた **CFS**（および近年の後継 **EEVDF**）は、各プロセスがこれまでに消費したCPU時間を優先度（`nice` 値）で重み付けした **仮想実行時間（`vruntime`）** として記録し、**常に `vruntime` が最も小さい（これまで一番CPUをもらえていない）プロセス**を赤黒木（平衡二分探索木）から $O(\log n)$ で選んで実行します。優先度の高いプロセスは `vruntime` の進み方が遅くなるように重み付けされるため、飢餓を起こさずに滑らかな公平配分を実現できます。

> **【コラム：プロセスとスレッドの違い：仮想アドレス空間を「分けるか、共有するか」】**
>
> マルチタスキングを学ぶとき、必ず登場するのが **プロセス（Process）** と **スレッド（Thread）** の違いです。
>
> * **プロセス：** それぞれが**独立した仮想アドレス空間**（コード・データ・ヒープ・スタック）とファイル記述子テーブルを持ちます。あるプロセスがバグでメモリを破壊しても他のプロセスは安全（高い隔離性）ですが、プロセス間でデータを共有するにはパイプや共有メモリといった仕組みが必要です。
> * **スレッド（同一プロセス内の複数実行フロー）：** 1つのプロセスの中で、**コード・大域変数・ヒープ・開いたファイルはすべて共有**しつつ、**プログラムカウンタ・レジスタ・スタック（実行コンテクスト）だけ**をスレッドごとに独立して持ちます。
>
> スケジューラの目線から見ると、現代のOS（Linux等）が実際にCPUコアへ割り当てて `swtch` で切り替えている最小の実行単位は**スレッド**です。同じプロセス内のスレッド同士を切り替えるときは、仮想アドレス空間（ページテーブル：[3-5節](3-5.md)）を切り替える必要がなく、アドレス変換キャッシュ（TLB）もそのまま活かせるため、別プロセス間の切替より軽量に動作します。ただし、メモリを共有しているぶん、[第4部](../index.md#part-4)で扱う競合状態や同期制御が不可欠になります。

### 4. 限界と補正（Critique & Adaptation）

スケジューリングとコンテクストスイッチを現実のマルチコアCPU上で動かすとき、次の3つの物理的・構造的な限界に対処する必要があります。

#### (1) タイムクォンタムの長さとコンテクストスイッチのオーバーヘッド

タイムクォンタム $q$ の設定には明確なトレードオフがあります。

* **$q$ が短すぎる場合（例：$0.05\text{ ms}$）：** 応答時間は短くなりますが、切替のたびに発生する直接コスト（レジスタ退避・復元・スケジューラ実行）に加えて、もっと重い**間接コスト（キャッシュとTLBの汚染）**が効いてきます。[0-7節](../0/0-7.md)で見た通り、プロセスAがせっかくL1/L2キャッシュへ温めておいたデータがプロセスBの実行で追い出されてしまうため、Aへ戻った直後は大量のキャッシュミスが発生し、CPU全体のスループットが大きく低下します。
* **$q$ が長すぎる場合（例：$500\text{ ms}$）：** キャッシュ効率は良くなりますが、実質的にFCFSへ近づき、マウス操作やキーボード入力の反応がカクついて対話性が損なわれます。

そのため実用OSでは、切替コストが全体の数%以下に収まりつつ人間の知覚（約 $50\text{〜}100\text{ ms}$）より十分短い **$1\text{〜}10\text{ ms}$ 程度** を基準にクォンタムを設定します。

#### (2) マルチコア環境でのキャッシュ親和性（CPU Affinity）と負荷分散

CPUコアが複数（4コア、16コアなど）あるシステムで、全コアが1つの共通レディキューを奪い合うと、キューのロック競合（[第4部](../index.md#part-4)）がボトルネックになります。また、プロセスAがさっきまでコア0で動いていたのに、次のクォンタムでコア3へ移されると、コア0のL1/L2キャッシュに残っていたAのデータがすべて無駄になります。

この限界に対する現代OSの補正が、次の2つの組み合わせです。

1. **コアごとのレディキュー（Per-CPU Queue）とキャッシュ親和性（CPU Affinity）：** 各CPUコアに専用の実行待ちキューを持たせ、同じプロセスはなるべく前回動いていたのと同じコアへ優先して戻すことでキャッシュヒット率を維持します。
2. **ワークスティーリング（Work Stealing：負荷分散）：** あるコアのキューが空になって暇になったとき、忙しい他のコアのキューから `RUNNABLE` プロセスを一部引き抜いて実行し、全コアの利用率を均等に保ちます。

#### (3) 優先度逆転（Priority Inversion）と優先度継承

優先度付きスケジューラ（リアルタイムOSやMLFQ等）で資源の排他制御（ロック）を組み合わせると、**優先度逆転（Priority Inversion）** という有名な現象が起きます。

* 低優先度プロセス $L$ が共有ロックを握っている最中に、高優先度プロセス $H$ がそのロックを待って `SLEEPING` に入る。
* その間に、ロックとは無関係な中優先度プロセス $M$ が動き出すと、$M$ は $L$ より優先度が高いため $L$ からCPUを奪い続ける。
* 結果として、$L$ がロックを解放できず、**最高優先度のはずの $H$ が中優先度の $M$ に延々と待たされる**逆転現象が起きます（1997年の火星探査機マーズ・パスファインダーがリセットを繰り返した実例が有名です）。

これに対する代表的な補正が **優先度継承（Priority Inheritance）** です。高優先度プロセス $H$ がロックを待ってブロックしたとき、そのロックを現在保持している低優先度プロセス $L$ の優先度を一時的に $H$ と同じ高さまで引き上げ、$L$ に素早くクリティカルセクションを終わらせてロックを解放させます。
