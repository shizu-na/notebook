### 前節（3-4）の確認問題の解答

前節の最後に提示した3つの問いの解答を確認します。問3がそのまま本節（仮想記憶と多段ページテーブル）の導入になります。

1. **可変サイズ割当（First-Fit と Best-Fit の成否分岐と弱点）：**
    初期の空きリストは `[30 KiB] → [100 KiB] → [50 KiB] → [20 KiB]` です。

    * **(a) First-Fit と Best-Fit の比較：**

        * **First-Fit：**

            * 要求1（$40\text{ KiB}$）：最初に収まる **`[100 KiB]`** から切り出し、残りは `[30] → [60] → [50] → [20]` になります。
            * 要求2（$25\text{ KiB}$）：最初に収まる **`[30 KiB]`** から切り出し、残りは `[5] → [60] → [50] → [20]` になります。
            * 要求3（$70\text{ KiB}$）：最大の空きが $60\text{ KiB}$ しかないため **確保に失敗** します（最終空きリスト：**`[5 KiB] → [60 KiB] → [50 KiB] → [20 KiB]`**）。

        * **Best-Fit：**

            * 要求1（$40\text{ KiB}$）：$40\text{ KiB}$ 以上で最小の **`[50 KiB]`** から切り出し、残りは `[30] → [100] → [10] → [20]` になります。
            * 要求2（$25\text{ KiB}$）：$25\text{ KiB}$ 以上で最小の **`[30 KiB]`** から切り出し、残りは `[5] → [100] → [10] → [20]` になります。
            * 要求3（$70\text{ KiB}$）：温存しておいた **`[100 KiB]`** から切り出して **確保に成功** します（最終空きリスト：**`[5 KiB] → [30 KiB] → [10 KiB] → [20 KiB]`**）。

    * **(b) 一般の運用で Best-Fit が不利になりやすい2つの理由：**
        ① ちょうど収まる空きを探して切り出すため、再利用しにくい**極小の断片が大量に蓄積しやすい**点、② 最適な空きを見つけるために原則として**フリーリスト全体を走査する必要があり探索コストが大きい**点、の2つです。

2. **バディシステムの非バディ隣接ブロックと内部断片化率：**

    * **(a) `0x4000` と `0x8000` が合体できない理由（ブロックサイズ $B = 16\text{ KiB} = \texttt{0x4000}$）：**
        それぞれの相棒（バディ）を式 $\text{buddy\_addr} = \text{addr} \oplus B$ で計算します。

        $$
        \texttt{0x4000} \oplus \texttt{0x4000} = \texttt{0x0000}, \qquad \texttt{0x8000} \oplus \texttt{0x4000} = \texttt{0xC000}
        $$

        `0x4000` の相棒は使用中の `0x0000`、`0x8000` の相棒は使用中の `0xC000` であり、**`0x4000` と `0x8000` は物理的に隣接していてもバディ関係にない**（前者は下位 $32\text{ KiB}$ 半分、後者は上位 $32\text{ KiB}$ 半分に属する）ため合体できません。

    * **(b) $33\text{ KiB}$ 要求時の割当サイズと内部断片化率：**
        $33\text{ KiB}$ 以上で最小の2のべき乗は **$64\text{ KiB}$** です。未使用となる領域は $64 - 33 = 31\text{ KiB}$ であるため、内部断片化率は $\dfrac{31}{64} = 0.484375 \approx \mathbf{48.4\%}$ です。

3. **固定サイズページ割当の限界とアドレス変換の必要性（本節への接続）：**
    物理アドレスを直接使う設計のままでは、`kalloc` で確保された $4\text{ KiB}$ の空きページが物理 RAM 上に飛び飛びで散らばっている場合、それらを束ねてプロセスから見た 1 本の連続した $100\text{ KiB}$ 配列として扱うことができず、他プロセスからの誤書き込みも防げません。この制約を解消するには、CPU が使う**仮想アドレス**と RAM の**物理アドレス**を切り離し、両者の間にハードウェアの変換装置（**MMU**）とプロセスごとの変換表（**ページテーブル**）を挟む必要があります。

## 3-5. 仮想記憶と多段ページテーブル・TLB

### 1. 動機（Why）：なぜCPUが使うアドレスと物理RAMの番地を分離する必要があるのか

前節（[3-4節](3-4.md)）で、OSカーネルが物理メモリ（RAM）を $4\text{ KiB}$ 単位の固定ページとして $O(1)$ で確保・解放できる仕組みを整えました。しかし、もしユーザプログラムが物理アドレスを直接指定してメモリへアクセスするままだと、次の3つの問題が解決できません。

1. **プロセス間の隔離（保護）：** プロセスAが誤って（あるいは悪意を持って）プロセスBやOSカーネルの物理番地へ書き込もうとしたとき、物理アドレス直結ではそれを止める手立てがありません。
2. **アドレス空間の衝突：** コンパイル済みの実行ファイルは、たとえば「コードは `0x0000_1000` から始まる」といった同じアドレス前提で作られます。物理メモリ上では同じ番地に2つのプロセスを同時に置けません。
3. **不連続な物理ページの連続化：** 固定ページ割当（`kalloc`）で確保された2枚の物理ページ（例：`0x8000_5000` と `0x8000_F000`）は物理RAM上で離れ離れです。これをアプリケーションから見て「隙間なく連続した $8\text{ KiB}$ の配列」として見せる必要があります。

これらの課題をまとめて解決するのが、OSとCPUハードウェアが協調して実現する **仮想記憶（Virtual Memory）** です。CPUがプログラムの命令を実行するときに扱う **仮想アドレス（VA：Virtual Address）** を、CPU内部の専用ハードウェアである **MMU（Memory Management Unit）** が、プロセスごとに用意された変換表（**ページテーブル：Page Table**）を引いて **物理アドレス（PA：Physical Address）** へ毎回自動変換します。

本節では、小さなモデルで仮想アドレス変換の原理を押さえたうえで、64ビット時代の巨大な空間で素朴な単段テーブルが破綻する理由を計算で確かめ、RISC-V（Sv39）の **3段ページテーブル** と、変換速度を支える専用キャッシュ **TLB** の構造を整理します。

---

### 2. 具体例と動作イメージ（Toy Model）

多段構造に入る前に、2つの小さな計算実験で「ページテーブルによる隔離」と「単段テーブルのメモリ爆発」を確かめます。

#### 実験A：プロセスAとBが「同じ仮想アドレス `0x1040`」を読んでも別データになる

ページサイズを $4\text{ KiB}$（$4096 = 2^{12}\text{ B}$）とし、16ビットの小さな仮想アドレス空間を考えます。アドレスの下位12ビット（16進数3桁）は「$4\text{ KiB}$ ページの中の何バイト目か（**ページ内オフセット**）」、残りの上位ビットは「何番目のページか（**仮想ページ番号：VPN**）」を表します。

今、プロセスAとプロセスBがどちらもまったく同じ仮想アドレス **`0x1040`**（$\text{VPN} = \texttt{0x1}$、オフセット $= \texttt{0x040}$）へアクセスしたとします。

* **プロセスAのページテーブル：** $\text{VPN } \texttt{1} \mapsto \text{PPN（物理ページ番号） } \texttt{5}$ と登録されているため、MMUは物理アドレス **`0x5040`** へ変換します。
* **プロセスBのページテーブル：** $\text{VPN } \texttt{1} \mapsto \text{PPN } \texttt{9}$ と登録されているため、MMUは物理アドレス **`0x9040`** へ変換します。

両プロセスは同じ番地 `0x1040` を使っているにもかかわらず、物理RAM上ではまったく別の場所へ隔離されています。しかも、プロセスAのページテーブルに物理ページ `9` へのエントリが存在しない限り、**プロセスAはどんなポインタ操作をしてもプロセスBのメモリへ到達する手段自体を物理的に持てません**。

#### 実験B：素朴な「単段ページテーブル」を64ビットOSへ載せると破綻する

実験Aのような1枚の配列（**単段ページテーブル**）を、RISC-V（xv6モデル）が採用する **Sv39（39ビット仮想アドレス空間：$2^{39}\text{ B} = 512\text{ GiB}$）** へそのまま当てはめてみます。

* ページサイズ：$4\text{ KiB} = 2^{12}\text{ B}$（オフセット12ビット）です。
* 仮想ページ番号（VPN）のビット幅：$39 - 12 = 27\text{ ビット}$ であり、エントリ総数は $2^{27} = 134{,}217{,}728$ 個です。
* 1エントリ（PTE：Page Table Entry）のサイズ：$8\text{ バイト}$（64ビット）です。

したがって、**たった1つのプロセス**の単段ページテーブルを保持するためだけに、

$$
2^{27} \times 8\text{ B} = 2^{30}\text{ B} = \mathbf{1\text{ GiB}}
$$

もの連続した物理メモリが必要になってしまいます。もしシステム上に100個のプロセスが動けば、中身のデータ以前に**変換表だけで $100\text{ GiB}$ のRAMが消費される**計算です。

現実のプロセスが実際に使うメモリは、広大な $512\text{ GiB}$ 空間のうちのほんの一部（コード・ヒープ・スタックの数 MiB 程度）だけであり、残りの 99.99% は未使用のスカスカな領域（スパース空間）です。未使用の領域には変換表そのものを作らずに済ませるデータ構造が、次項（3-(1)）の **多段ページテーブル** です。

---

### 3. 構造・アルゴリズム・実装（What）

#### (1) RISC-V Sv39 の 3段ページテーブルと `satp` レジスタ

多段ページテーブルの発想は、巨大な1次元配列を**木構造（トライ木）**へ折り畳むことです。RISC-V の標準仮想記憶方式 **Sv39** では、27ビットの仮想ページ番号（VPN）を **9ビット × 3段** に均等分割します（図3-5-1）。

$$
39\text{ ビット仮想アドレス} = \underbrace{\text{VPN}[2]}_{9\text{ bit}} \;\mid\; \underbrace{\text{VPN}[1]}_{9\text{ bit}} \;\mid\; \underbrace{\text{VPN}[0]}_{9\text{ bit}} \;\mid\; \underbrace{\text{Offset}}_{12\text{ bit}}
$$

なぜ「9ビット」なのかに注目してください。$2^9 = 512$ エントリであり、1つのエントリ（PTE）は $8\text{ バイト}$ です。掛け合わせると、

$$
512 \times 8\text{ B} = \mathbf{4096\text{ B} = 4\text{ KiB}}
$$

となり、**1つのページテーブルノードがちょうど物理ページ1枚（$4\text{ KiB}$）に1バイトの過不足もなくぴったり収まります**。そのためOSカーネルは、[3-4節](3-4.md)で作った `kalloc()` を1回呼ぶだけで新しいページテーブルノードをそのまま確保できます。

CPUの制御レジスタ **`satp`（Supervisor Address Translation and Protection）** は、上位から変換モードを指定する **`MODE`（4ビット：Sv39 では `8`）**、アドレス空間識別子 **`ASID`（16ビット）**、そして現在実行中プロセスの最上位テーブル（L2ページテーブル）の物理ページ番号 **`PPN`（44ビット）** で構成されています。MMUが仮想アドレスを物理アドレスへ変換する手順（**ページテーブル・ウォーク**）は次の3ステップで進みます。

1. `satp` が指す L2 テーブルから `VPN[2]` 番目の PTE を読み、次の L1 テーブルの物理番地を得ます。
2. L1 テーブルから `VPN[1]` 番目の PTE を読み、次の L0 テーブルの物理番地を得ます。
3. L0 テーブルから `VPN[0]` 番目の PTE を読んで目的の物理ページの先頭番地（44ビットの PPN）を得て、元の仮想アドレスの下位12ビット（オフセット）をそのまま貼り付けて **56ビット物理アドレス**（$44 + 12$ ビット）が完成します。

もし L2 や L1 の途中で「未使用（有効ビット `V = 0`）」のエントリに当たれば、その配下にある下位テーブル（L1・L0）をそもそも物理メモリ上に確保する必要がありません。これにより、数 MiB しか使わないプロセスならページテーブル全体の消費量もわずか **数枚〜数十枚（数十 KiB）** に大きく圧縮されます。

具体的な64ビット仮想アドレス **`0x0000_0000_4020_3456`** を Sv39 で手計算して3段ウォークの流れを確かめてみます。下位39ビットを `0x4000_0000 + 0x0020_0000 + 0x0000_3000 + 0x0456` と重みごとに分解すると、各フィールドは次の通りになります。

* **Offset（ビット 11..0）：** 下位12ビット（16進3桁）そのまま取り出して **`0x456`** です。
* **VPN[0]（ビット 20..12）：** 右へ12ビットシフトした `0x40203` の下位9ビット（`& 0x1FF`）を取り、`0x003` ＝ **`3`** です（$3 \times 4\text{ KiB} = \texttt{0x3000}$）。
* **VPN[1]（ビット 29..21）：** 右へ21ビットシフトした `0x201` の下位9ビット（`& 0x1FF`）を取り、`0x001` ＝ **`1`** です（$1 \times 2\text{ MiB} = \texttt{0x20\_0000}$）。
* **VPN[2]（ビット 38..30）：** 右へ30ビットシフトした値を取り、`0x001` ＝ **`1`** です（$1 \times 1\text{ GiB} = \texttt{0x4000\_0000}$）。

MMUは `satp` の指す L2 テーブルの **`1` 番目** → その先にある L1 テーブルの **`1` 番目** → さらにその先の L0 テーブルの **`3` 番目** の PTE を順に読みます。仮に L0[3] の PTE に `PPN = 0x80123`（物理ページ `0x8012_3000`）が登録されていた場合、そこにオフセット `0x456` を貼り付けた物理アドレス **`0x0000_0000_8012_3456`** が得られます。

#### (3) アドレス変換の速度の壁と TLB（Translation Lookaside Buffer）

3段ページテーブルによってメモリ消費量の爆発は解決しましたが、今度は深刻な**実行速度の壁**が立ちはだかります。

プログラムが `ld x5, 0(x6)` でメモリをたった1回読み出そうとするたびに、MMUが L2 → L1 → L0 と3回も主記憶へページテーブルを読みに行っていたら、**1回のメモリアクセスが実質4回（約4倍遅い）**に膨れ上がってしまいます（4段ページテーブルのx86-64では5回）。

この速度の壁を緩和するのが、CPUのMMU内部に内蔵されたアドレス変換専用の高速キャッシュである **TLB（Translation Lookaside Buffer）** です（図3-5-3）。

* **仕組み：** 最近変換した「仮想ページ番号（VPN）$\to$ 物理ページ番号（PPN）＋保護フラグ（`R/W/X/U`）」の組を、数十〜数千エントリだけSRAM上に記憶しておきます。[0-7節](../0/0-7.md)で予告した通り、L1 TLB は競合ミスを避けるため **完全連想方式**（または高いセット連想度）で構成され、1サイクル以内で全エントリを並列検索します。
* **TLB ヒット（通常 99% 以上）：** 仮想ページ番号がTLBに見つかれば、3段ページテーブルを一切辿らず、即座に物理アドレスを得てL1キャッシュへアクセスします。同じ $4\text{ KiB}$ ページ内の連続アクセス（空間的局所性）やループ内の繰り返しアクセス（時間的局所性）はすべて1個のTLBエントリでヒットするため、非常に高いヒット率が出ます。
* **TLB ミス：** TLBに見つからない場合だけ、ハードウェアのページテーブル・ウォーカーが主記憶上の L2 → L1 → L0 を辿ってPTEを取得し、その変換結果をTLBへ登録してから命令を続行します。

TLB の性能効果を定量的に表すため、**実効アクセス時間（EAT：Effective Access Time）** を導出します。TLB 検索時間を $t_{\text{TLB}}$、主記憶アクセス時間を $t_{\text{mem}}$、ページテーブル段数を $d$（Sv39 では $d = 3$）、TLB ヒット率を $h$ とすると、ヒット時は「TLB 検索＋データ本体1回」（$t_{\text{TLB}} + t_{\text{mem}}$）、ミス時は「TLB 検索＋ページテーブル $d$ 回＋データ本体1回」（$t_{\text{TLB}} + (d + 1)t_{\text{mem}}$）がかかるため、期待値である EAT は次式で与えられます。

$$
\text{EAT} = h(t_{\text{TLB}} + t_{\text{mem}}) + (1 - h)\bigl(t_{\text{TLB}} + (d + 1)t_{\text{mem}}\bigr) = t_{\text{TLB}} + \bigl(1 + d(1 - h)\bigr)t_{\text{mem}}
$$

たとえば $t_{\text{TLB}} = 1\text{ ns},\; t_{\text{mem}} = 100\text{ ns},\; d = 3$ の Sv39 環境で比較してみます。

* **$h = 0.99$（99% ヒット）のとき：** $\text{EAT} = 1 + (1 + 3 \times 0.01) \times 100 = \mathbf{104\text{ ns}}$（裸の主記憶アクセス $100\text{ ns}$ に対する遅延はわずか 4% 増に収まります）。
* **$h = 0.80$（80% ヒット）のとき：** $\text{EAT} = 1 + (1 + 3 \times 0.20) \times 100 = \mathbf{161\text{ ns}}$（約 1.55 倍遅くなり、TLB ヒット率の低下がそのまま性能劣化へ直結します）。

> **【コラム：なぜ 64 ビットCPUなのに仮想アドレスは 39 ビットや 48 ビットしか使わないのか】**
>
> 64ビットのポインタ変数（`void *`）は64ビット幅なのに、RISC-V Sv39 は下位 **39ビット（$512\text{ GiB}$）**、一般的な x86-64 は下位 **48ビット（$256\text{ TiB}$：4段ページテーブル）** までしか実際のアドレス変換に使いません。なぜ最初から64ビット全部を使わないのでしょうか。
>
> 理由は2つあります。第1に、$2^{64}\text{ B} = 16\text{ エクサバイト}$ は現代の物理RAM容量に比べて桁違いに大きく、もし64ビットすべてを9ビットずつ分割すると **6段ものページテーブル** が必要になり、TLBミス時のウォーク時間とメモリ消費が無駄に増えるためです。第2に、使っていない上位ビット（Sv39ではビット63..39）を「自由にゴミの値を入れてよい領域」にしてしまうと、将来のCPUがビット数を拡張（Sv48や57ビットの5段ページングへ）した瞬間に、上位ビットをタグなどに流用していた古いプログラムがすべて壊れてしまいます。そこでハードウェアは、未使用の上位ビットが最上位有効ビット（Sv39ではビット38）と同じ値で符号拡張されていること（**カノニカルアドレス：Canonical Address**）を厳格に強制し、将来の安全な拡張余地を守っています。

### 4. 限界と補正（Critique & Adaptation）

多段ページテーブルとTLBの組み合わせは非常に強力ですが、OSが複数プロセスを切り替えたり、数十 GiB もの大規模データを扱ったりする場面では次の2つの限界が現れます。

#### (1) プロセス切替・PTE更新時の TLB 一貫性問題（`sfence.vma` と ASID）

TLBが記憶している「`VPN 0x1 → PPN 0x5`」という対応表は、**現在実行中のプロセスAのページテーブル**から引いたものです。ここで[3-3節](3-3.md)のコンテクストスイッチが起きてプロセスBへ切り替わり、`satp` レジスタをプロセスBのページテーブルへ差し替えたとします。

もしTLBの中にプロセスAのエントリが残ったままだと、プロセスBが同じ `VPN 0x1` へアクセスした瞬間にTLBが誤ってヒットし、**プロセスAの物理ページ `0x5` を読んでしまう**という致命的な隔離違反が起きます。

これに対する2段階の補正があります（図3-5-4左）。

1. **TLB フラッシュ（`sfence.vma` 命令）：** xv6 などの基本設計では、`satp` を書き換えた直後に専用命令 `sfence.vma` を実行してTLBの全エントリを一括破棄（フラッシュ）します。また、プロセス切替時だけでなく、**同一プロセス内で有効な PTE の権限を変更したとき**（[3-7節](3-7.md)の Copy-on-Write で書込み許可 `PTE_W` を落とす場合や、ページを解放して `V=0` にする場合）にも、古い権限が TLB に残らないよう `sfence.vma` の実行が必須になります。安全ですが、一括フラッシュの直後は TLB が空（コールド状態）になり、しばらく TLB ミスが増えて性能が落ちます。
2. **ASID（Address Space Identifier：アドレス空間識別子）：** 現代のCPU（RISC-Vの `satp` 内のASIDフィールドや、x86-64の **PCID**）では、各プロセスへ固有のタグ番号（ASID）を割り当て、TLBの各エントリにも `(ASID, VPN) → PPN` とタグを併記します。すると、プロセスAとプロセスBのエントリがTLB上で安全に共存でき、プロセス切替のたびにTLBをフラッシュする必要がなくなります。

#### (2) TLB リーチの限界とスーパーページ（Huge Page）

TLBのエントリ数は物理的なチップ面積と電力の制約から大きくできません（L1 TLBで64〜128個、L2 TLBでも1,000〜2,000個程度）。1エントリがカバーする $4\text{ KiB}$ ページが1,024個あっても、TLB全体でカバーできるメモリ総量（**TLB リーチ**）はわずか $1024 \times 4\text{ KiB} = \mathbf{4\text{ MiB}}$ に過ぎません。データベースや大規模行列計算のように数十 GiB のメモリをランダムにアクセスするアプリでは、TLBミスが頻発して性能が大きく低下します。

この限界に対するハードウェア・OS協調の補正が、[3-4節](3-4.md)でも触れた **スーパーページ（Huge Page：巨大ページ）** です（図3-5-4右）。Sv39 の3段ページテーブルでは、L0まで降りずに **L1 の PTE で `R/W/X` ビットを立てて葉ノードにするだけ** で、下位21ビット（`VPN[0]` 9bit + `Offset` 12bit）をそのままオフセットとする **$2\text{ MiB}$ ページ**（L2で止めれば **$1\text{ GiB}$ ページ**）を即座に作れます。

* 1個のTLBエントリが $4\text{ KiB}$ ではなく $2\text{ MiB}$（**512倍**）をカバーできるため、TLBリーチが512倍へ拡大します。
* しかもTLBミス時のウォーク段数も3段から2段へ短縮されます。
* 一方でトレードオフも存在します。小さな領域に $2\text{ MiB}$ ページを使うと**内部断片化が大きく増える**点、物理メモリが断片化していると**連続した $2\text{ MiB}$ 物理フレームの確保が難しくなる**点、さらに[3-7節](3-7.md)の Copy-on-Write で書込みフォルトが起きた際の**コピー量が通常の512倍（$2\text{ MiB}$）へ膨らむ**（そのため書込み時に $4\text{ KiB}$ へ分割する処理が必要になる）点に注意が必要です。

### 5. 接続と展望（Bridge）：本節の内容が後半のどの部に繋がるか

1. **次節（[3-6節](3-6.md)：トラップ処理の実装とカーネル／ユーザ空間の切替）：**
    本節で、ユーザプロセスとOSカーネルがそれぞれ別のページテーブル（`satp`）を持つ構造が分かりました。次節では、システムコールや割り込みが発生した瞬間に「どうやって安全に `satp` を切り替え、ユーザの全32レジスタを退避するか」という最も繊細な実装（`trampoline` と `trapframe`）へ踏み込みます。

2. **[第3部](../index.md#part-3)（[3-7節](3-7.md)：ページフォルトの応用）：**
    PTEの有効ビット `V=0` や書込許可 `W=0` をあえて利用してハードウェアにページフォルトを起こさせ、OSが裏側で動的にページを割り当てる **遅延割当・デマンドページング・Copy-on-Write・`mmap`** へと発展します。

3. **[第1部](../index.md#part-1)（[1-5節](../1/1-5.md)：共有ライブラリ）および[第5部](../index.md#part-5)（[5-8節](../5/5-8.md)：NXビット）との回収：**
    [1-5節](../1/1-5.md)で見た「同じ `libc.so` の物理ページを、異なるプロセスが別々の仮想アドレスで共有する仕組み」は、まさに2つのプロセスのページテーブルから同じ PPN を指すことで実現されています。また、PTEの `W` と `X` を同時に立てない制御（W^X）は[第5部](../index.md#part-5)のメモリ破壊攻撃防御の中核になります。

### 理解度チェック（次節へ進む前の確認）

本節の Sv39 ビット分割・ページテーブル消費量・TLB の EAT とリーチを確認し、次節（[3-6節](3-6.md)）へ繋ぐ問いを置きます。

> **【確認の問い】**
>
> 1. **（Sv39 の仮想アドレス分解と3段ページテーブルの必要枚数）**
>     RISC-V の Sv39（仮想アドレス39ビット、ページサイズ $4\text{ KiB}$、1 PTE = 8バイト、9+9+9+12ビット分割）において、**仮想アドレス `0x0000_0000_0000_1000` と `0x0000_003F_FFFF_E000` の2ページだけ**を使用するプロセスを考えます。
>
>     * (a) この2つの仮想アドレスをそれぞれ `(VPN[2], VPN[1], VPN[0], Offset)` へ分解してください（10進または16進のどちらでも可）。
>     * (b) このプロセスに必要なページテーブル（L2・L1・L0）の合計枚数と総容量（KiB）を求めてください。また、もし2ページ目が `0x0000_0000_0000_2000` であった場合、必要なページテーブルが合計3枚で済む理由を説明してください。
>
> 2. **（TLB の実効アクセス時間 EAT と TLB リーチの計算）**
>     次の2つの計算を行ってください。
>
>     * (a) $t_{\text{TLB}} = 1\text{ ns}$、主記憶アクセス時間 $t_{\text{mem}} = 100\text{ ns}$ の Sv39 環境（ページテーブル段数 $d = 3$）において、TLB ヒット率が $h = 99\%$ の場合と $h = 90\%$ の場合の実効アクセス時間（EAT）をそれぞれ求めてください。
>     * (b) エントリ数が 64 個の L1 TLB を持つ CPU で $64\text{ MiB}$ の配列をランダムにアクセスするとき、通常ページ（$4\text{ KiB}$）とスーパーページ（$2\text{ MiB}$）のそれぞれで TLB リーチ（TLB 全体がカバーできる容量）がいくらになるか計算し、ミス率の違いを説明してください。
>
> 3. **（アドレス変換機構から考える `satp` 切替時のコード配置条件）**
>     ユーザ空間からカーネル空間へ切り替える際、S-mode のトラップハンドラが `csrw satp, kernel_pagetable` を実行した直後、CPU は新しいページテーブルのもとで次の命令（`pc + 4`）をフェッチします。このとき命令フェッチが暴走やページフォルトを起こさずに次の命令へ繋がるためには、切替命令を含むコードページがユーザページテーブルとカーネルページテーブルの双方でどのような仮想アドレス配置になっている必要があるでしょうか。
