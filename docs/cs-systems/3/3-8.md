### 前節（3-7）の確認問題の解答

前節の最後に提示した3つの問いの解答を確認します。本節（起動シーケンスとマルチコア初期化）をもって[第3部](../index.md#part-3)が完結します。

1. **Copy-on-Write の参照カウント追跡と `copyout` バグ診断（初期 `refcount[A] = 3`）：**
    P・C1・C2 の3プロセスが物理ページ A を `W=0, COW=1` で共有している状態から順に辿ります。

    * **① 子プロセス C1 が書き込み：** 共有中（`refcount[A] = 3 >= 2`）のため、新たな物理ページの**複製が発生します**。C1 の PTE を新ページ（`W=1, COW=0`）へ付け替え、元のページ A の参照カウントは **`refcount[A] = 2`** になります。
    * **② 子プロセス C2 が書き込まずに `exit()`：** 書き込みは起きていないため**複製は発生しません**。C2 のメモリ解放処理で参照カウントが 1 減り、**`refcount[A] = 1`** になります（まだ 0 ではないためページ A は解放されません）。
    * **③ 親プロセス P が書き込み：** ストアページフォルトが起きますが、この時点で **`refcount[A] == 1`**（共有相手が誰もいない）であるため、**新たな複製は発生しません**。P の PTE をそのまま `W=1, COW=0` へ書き戻すだけで完了し、**`refcount[A] = 1`** のままになります。
    * **④ `copyout()` が `PTE_COW` を検査しないバグ：** `copyout()` は S-mode でソフトウェアにより `p->pagetable` を辿り、直接マップされた物理ページ A へ直接データを書き込みます（U-mode の MMU 書込みフォルトが起きません）。そのため CoW 複製が行われず、C1 がファイルから読み込んだデータによって**共有中の物理ページ A が直接上書きされ、親 P や兄弟 C2 のメモリ内容まで静かに破壊されてしまいます**。

2. **Clock アルゴリズムのトレースと `PTE_COW` フラグの必要性：**

    * **(a) Clock アルゴリズムのトレース（開始時の針＝枠0）：**
        枠0（`P1`, `A=1`）→ `A` を `0` にして次へ、枠1（`P2`, `A=1`）→ `A` を `0` にして次へ、枠2（`P3`, `A=0`）→ ここで停止して置換対象とします。

        * ① 追い出されるページ：**`P3`**（枠2）です。
        * ② 走査後の各枠の `A` ビット：枠0（`P1`）は **`A=0`**、枠1（`P2`）は **`A=0`**、枠3（`P4`）は未走査のため **`A=1` のまま** です（枠2には新ページが読み込まれます）。
        * ③ 針の次の位置：**枠3（`P4`）** です。
        * ④ `D=1` による追加処理：`P3` はメモリ上で変更済み（ダーティ）のため、枠2を上書き再利用する前に **`P3` の内容をディスク（スワップ領域等）へ書き戻す処理** が必要になります。

    * **(b) `PTE_W == 0` だけで CoW 判定してはならない理由：**
        `.text`（機械語コード）や `.rodata`（定数データ）など、本来から書込み禁止（`PTE_W == 0`）で保護すべきページも存在します。`PTE_COW == 1` を確認せず `PTE_W == 0` だけで複製・書込み許可をしてしまうと、バグや攻撃によるコード領域・定数領域への不正書込みが強制終了されず通り抜けてしまい、メモリ保護が破綻するためです。

3. **ページフォルト復帰時の `sepc` と CoW における `sfence.vma` 忘れのバグ：**

    * **(a) `sepc += 4` してはならない理由と CSR 名：**
        ページフォルトはロード／ストア命令がメモリアクセスを完了できずに中断された例外であり、物理ページの用意後に**失敗したその命令自身を再実行する**必要があるため `sepc` を進めてはなりません（`+4` するとその読み書き命令が丸ごと飛ばされます）。フォルトを起こした仮想アドレスは **`stval`** レジスタから読み取ります。

    * **(b) 親側で `sfence.vma` を実行し忘れたときのデータ破壊バグ：**
        親プロセスの PTE を `PTE_W = 0` に書き換えても、CPU の TLB に以前の `PTE_W = 1` のエントリがキャッシュされたまま残ります。そのまま親がページへ書き込むと TLB にヒットしてストアページフォルトが起きず、親が共有中の物理ページを直接書き換えてしまい、子プロセスのメモリ内容が破壊されます。

## 3-8. 起動シーケンス（ブート）・リンカスクリプトとマルチコア初期化

### 1. 動機（Why）：OS自身がまだ動いていない状態から、どうやってOSを立ち上げるのか

[3-1節](3-1.md)から[3-7節](3-7.md)までを通じて、OSカーネルが特権モード・プロセス・スケジューラ・多段ページテーブル・ページフォルトを駆使してシステム全体を統括する姿を見てきました。

ここで時間を一番最初へ巻き戻し、**「コンピュータの電源スイッチを押した直後の1マイクロ秒目」**を想像してみてください。この瞬間、システムは次のような真っさらな状態にあります。

1. **OSカーネル自身がまだメモリ上で動いていない：** [3-2節](3-2.md)で見たように、通常のプログラムは親プロセス（シェル）が `fork()` と `exec()` で起動します。しかし、最初の1つ目のOSカーネルを起動してくれる親プロセスは存在しません（**ブートストラップ問題**）。
2. **C言語を動かすための前提条件すら整っていない：** [1-3節](../1/1-3.md)で確認した通り、C言語の関数を1つ呼ぶだけでも「有効なスタックポインタ（`sp`）」と「ゼロ初期化された `.bss` 領域」が必要です。しかし電源オン直後のレジスタやRAMには不定な値しか入っていません。
3. **複数コアが同時に同じ番地から走り出す：** マルチコアCPUでは、電源が入るとコア0・コア1・コア2・コア3のすべてが一斉に動き出します。もし全コアが同時にカーネルのメモリ管理表やページテーブルを初期化し始めたら、互いの書き込みを上書きし合って即座に破綻します。

本節では、[第3部](../index.md#part-3)の締めくくりとして、RISC-V（xv6モデル）を題材に**「電源オン → アセンブリ入口（`entry.S`） → リンカスクリプトによる配置（`kernel.ld`） → M-mode 初期化（`start.c`） → S-mode 初期化とマルチコア同期（`main.c`） → 最初のプロセス `init`（PID 1）」**という起動（ブート）の全工程を1本の線で結びます。

---

### 2. 具体例と動作イメージ（Toy Model）

細部の実装に入る前に、2つの小さな視点で起動の流れとメモリ配置の必然性を確かめます。

#### 実験A：電源オンから `init` プロセスが動き出すまでの5段階

RISC-V（QEMU `virt` マシン上の xv6 モデル）に電源を入れると、特権モードは **M-mode（最高権限）→ S-mode（カーネル）→ U-mode（ユーザ）** と階段を降りるように切り替わりながら、次の5段階でシステムが立ち上がります（図3-8-1）。

1. **ファームウェア／ブートローダ（M-mode）：** 電源オン直後、CPUはROM上の固定アドレスから起動コードを実行し、OSカーネルのバイナリを物理RAMの **`0x80000000`** 番地へ読み込んでそこへジャンプします。
2. **アセンブリ入口 `entry.S`（M-mode）：** C言語の関数を呼ぶため、各CPUコアに自分専用の初期スタック（$4\text{ KiB}$）を割り当てて `sp` を設定し、C言語の `start()` 関数を呼び出します。
3. **ハードウェア基盤の初期化 `start.c`（M-mode）：** ページングを一旦無効（`satp = 0`）にし、例外や割り込みを S-mode のOSへ委譲する設定とタイマ割り込みの初期化を行ったうえで、**`mret` 命令を使って S-mode の `main()` へ降格**します。
4. **OSカーネル初期化とマルチコア同期 `main.c`（S-mode）：** コア0だけが物理メモリアロケータ（`kinit`）、カーネルページテーブル（`kvminit`）、プロセス表、割り込みコントローラ、最初のユーザプロセス（`userinit`）を初期化します。他コアは完了まで待機し、揃ったら全コアが `main()` 内で `kvminithart()` により `satp`（ページング）を有効化してから `scheduler()` へ入ります。
5. **最初のユーザプロセス `init`（U-mode）：** スケジューラが `userinit()` で作られた PID 1 のプロセスを選び、`sret` で U-mode へ降りてシェルを起動します。

#### 実験B：なぜOSカーネルには専用の「リンカスクリプト」が必要なのか

[1-4節](../1/1-4.md)で見た通常のユーザプログラムは、リンカ（`ld`）のデフォルト設定のままビルドしてもOSのローダが適切にメモリへ配置してくれます。しかし、**OSカーネル自身のELFファイル**には次の3つの厳格な物理配置の要求があります。

1. **先頭命令 `_entry` を必ず物理アドレス `0x80000000` のちょうど先頭に置くこと：** ファームウェアは決め打ちで `0x80000000` へジャンプするため、1バイトでもズレたら起動しません。これを保証するため、リンカの入力順で `entry.o` を先頭に指定するか、`*(.text.entry)` のような専用セクションを `.text` の最初に配置します。
2. **`TRAMPOLINE` コード（[3-6節](3-6.md)）をちょうど $4\text{ KiB}$ ページ境界に揃えて1ページへ収めること：** ユーザページテーブルとカーネルページテーブルで1ページ単位で共有マップするためです。
3. **カーネルの `.bss` セクションの直後のアドレスを記号 `end` としてエクスポートすること：** 物理メモリアロケータ（`kinit`）は、「`end` 番地から物理RAMの上限 `PHYSTOP` まで」を空きページとしてフリーリストへ登録します。もしカーネル自身の終端番地を知らなければ、空きページと勘違いしてカーネル自身のコードや変数を上書きしてしまいます。

こうした「どのセクションをどの物理アドレスへ、どの境界揃えで配置し、境界にどのシンボル名を付けるか」をリンカへ直接命令する設計図が **リンカスクリプト（`kernel.ld`）** です。

### 3. 構造・アルゴリズム・実装（What）

#### (1) リンカスクリプト（`kernel.ld`）の構造と物理メモリ地図

xv6 のリンカスクリプト `kernel.ld` の骨格を抜き出すと、その意図がひと目で分かります（図3-8-2）。

```ld
OUTPUT_ARCH( "riscv" )
ENTRY( _entry )

SECTIONS
{
    . = 0x80000000;                  /* ロケーションカウンタを RAM 先頭へ設定 */

    .text : {
        *(.text .text.*)             /* entry.o を先頭にリンク（または *(.text.entry) を先頭配置） */
        . = ALIGN(0x1000);           /* 次のセクションを 4KiB ページ境界へ揃える */
        _trampoline = .;
        *(trampsec)                  /* trampoline.S のコードをここへ配置 */
        . = ALIGN(0x1000);
        PROVIDE(etext = .);          /* コード領域の終端シンボル（以降 R/W 用） */
    }
    .rodata : { *(.rodata .rodata.*) }
    .data   : { *(.data .data.*) }
    .bss    : { *(.bss .bss.*) }

    PROVIDE(end = .);                /* カーネル終端 = 空き物理メモリの開始点 */
}
```

ここでドット「`.`」は[1-4節](../1/1-4.md)のアセンブラで登場したロケーションカウンタ（現在の配置アドレス）を意味します。`etext` の前後で「読み取り＋実行専用（`R, X`）」と「読み書き可能・実行禁止（`R, W`）」のページ境界を綺麗に分け、`end` から物理RAMの上限 `PHYSTOP`（たとえば `0x88000000`：128 MiB）までを `kinit()` が $4\text{ KiB}$ ずつ `kfree()` してフリーリスト（[3-4節](3-4.md)）へ登録する構造になっています。なお、教育用OSの xv6 では実装を簡略化するため `.rodata` を `.data`・`.bss` とまとめて `(R, W)` でマップしていますが、Linux などの実用OSでは `.rodata` を別のページ境界に揃えて読取り専用（`R` のみ）で保護します。

#### (2) 最小アセンブリ入口（`entry.S`）：コアごとの初期スタック構築と `.bss` 初期化

物理アドレス `0x80000000` の先頭に置かれたアセンブリ関数 `_entry` は、マルチコアの全CPUが一斉に実行する最初のコードです。やるべき仕事は、**「各CPUコアが互いにぶつからない自分専用の初期スタックポインタ `sp` を設定して、C言語の `start()` を呼ぶこと」**です。

```asm
_entry:
    la   sp, stack0       # カーネル .bss に確保された初期スタック配列の先頭
    li   a0, 4096         # 1コアあたり 4 KiB
    csrr a1, mhartid      # 自分の CPU コア番号 (0, 1, 2, ...) を取得
    addi a1, a1, 1        # スタックは下向きに伸びるので末尾を指すため +1
    mul  a0, a0, a1       # (hartid + 1) * 4096
    add  sp, sp, a0       # sp = stack0 + (hartid + 1) * 4096
    call start            # C言語の start() 関数へ
```

スタックは高位アドレスから低位アドレスへ向かって成長する（[1-3節](../1/1-3.md)）ため、コア0には `stack0 + 4096`、コア1には `stack0 + 8192` という具合に、各コアの $4\text{ KiB}$ 領域の上端を `sp` に設定します。この数命令でC言語のコードが安全に動き出します。

なお、冒頭で挙げたもう1つの前提条件である **`.bss` 領域のゼロ初期化** について、QEMU の `-kernel` オプションで起動する仮想環境では QEMU 側のローダがカーネル ELF を読み込む際に `.bss` をゼロ初期化してくれるため、xv6 の `entry.S` では省略されています。これに対し、実機のベアメタル環境（ファームウェアやブートローダ経由で起動する環境）では RAM の初期値が不定のため、リンカスクリプトで定義した `__bss_start` から `__bss_end` までを `entry.S` 内のループでゼロ埋めしてから `call start` を実行します。

#### (3) M-mode から S-mode への降格トリック（`start.c`）

`entry.S` から呼ばれた `start()` は、まだ最高権限の **M-mode** で動いています。RISC-Vの仕様上、M-mode から S-mode へ直接切り替える「降格命令」は存在しません。そこでカーネルは、**「まるで S-mode からトラップで M-mode へ入ってきたかのようにCSRを偽装し、トラップ復帰命令 `mret` を実行する」**という巧みな手順をとります。

1. **`mstatus` の設定：** 直前の特権モードを記録する `MPP`（Machine Previous Privilege）フィールドを **`S-mode`** に書き換えます。
2. **`mepc` の設定：** 復帰先プログラムカウンタ `mepc` に、C言語の **`main` 関数のアドレス** を書き込みます。
3. **ページングの一時無効化：** `satp` に `0` を書き込み、初期は物理アドレス直結のまま動かします。
4. **例外・割り込みの委譲（Delegation）：** `medeleg = 0xffff`、`mideleg = 0xffff` を設定し、システムコール（`ecall`）やページフォルト、外部割り込みが M-mode ではなく直接 **S-mode のOSカーネル** へ届くように委譲します。
5. **物理メモリ保護（PMP）の許可とコア番号退避：** RISC-V では PMP が未設定のままだと S-mode 以降のメモリアクセスがデフォルトで拒否されるため、S-mode から物理アドレス全体へアクセスできるよう PMP レジスタを設定します。また S-mode では `mhartid` を直接読めないため、汎用レジスタ **`tp`（Thread Pointer）** へ自コア番号をコピーしておきます。
6. **タイマ初期化と `mret` 実行：** タイマ割り込みの初期設定を済ませて **`mret`** を実行すると、CPUハードウェアは `mstatus.MPP`（S-mode）へ権限を降格し、`mepc`（`main()` の先頭）へジャンプします。

#### (4) マルチコア初期化の同期と最初のプロセス `init`（`main.c`）

`mret` によって全CPUコアが S-mode の `main()` へ飛び込んできます。ここで、システム全体で1回だけ行えばよい初期化（物理メモリのフリーリスト作成、カーネルページテーブル作成、プロセス表・ディスク・割り込みコントローラ初期化）と、各CPUコアがそれぞれ行う初期化（自コアの `satp` と `stvec` の設定）を明確に分離します（図3-8-3）。

```c
volatile static int started = 0;   // コア0の初期化完了を他コアへ伝えるフラグ

void main(void) {
    if (cpuid() == 0) {
        consoleinit();             // コンソール初期化
        kinit();                   // end..PHYSTOP を空きページリストへ登録
        kvminit();                 // カーネルページテーブル構築
        kvminithart();             // コア0の satp 有効化（ここから仮想記憶オン）
        procinit();                // プロセス表・kstack 準備
        trapinithart();            // コア0の stvec = kernelvec 設定
        plicinit(); plicinithart();// 割り込みコントローラ設定
        binit(); iinit(); fileinit(); // バッファキャッシュ・ファイルシステム初期化
        userinit();                // 最初のユーザプロセス (PID 1) を生成
        __sync_synchronize();      // メモリバリア：上の全書込みを他コアへ可視化
        started = 1;               // 他コアへ「準備完了」を通知
    } else {
        while (started == 0)       // コア1以降はここで待機
            ;
        __sync_synchronize();      // メモリバリア：started==1 観測前の投機読込を防止
        kvminithart();             // 自コアの satp を有効化
        trapinithart();            // 自コアの stvec を設定
        plicinithart();            // 自コアの割り込み受付を有効化
    }
    scheduler();                   // 全コアが一斉にスケジューラループへ突入
}
```

ここで注目すべきは、`kvminithart()` が `satp` へカーネルページテーブルを書き込んで仮想記憶を有効化した瞬間、[3-6節](3-6.md)の `TRAMPOLINE` のような特別な共通ページを介さなくてもクラッシュしない点です。これはカーネルページテーブルが物理アドレスと仮想アドレスを1対1に一致させる**直接マッピング（`VA == PA`）**になっているため、`satp` 有効化の前後で次の命令アドレス `pc + 4` が物理的にまったく同じ命令を指し続けるからです。

最後の仕上げが **`userinit()`** による最初のユーザプロセス（PID 1）の誕生です。まだユーザプロセスが1つも存在しないため `fork()` は使えません。そこでカーネルは、手作業でPCBを1つ確保し、ごく小さな機械語（`exec("/init", argv)` を呼ぶだけの数命令のバイナリ）を1ページ分だけユーザ空間の先頭 `0x0` へコピーし、`trapframe->epc = 0`、`state = RUNNABLE` としてプロセス表へ登録します。

あとは全コアが `scheduler()` へ入った瞬間に、いずれかのコアがこの PID 1 プロセスを見つけて `swtch()` → `forkret()` → `usertrapret()` → `sret` と実行し、ついに U-mode で `/init` が動き出してシェルが立ち上がります。

> **【コラム：x86 PCのブートシーケンス（512バイトの MBR から現代の UEFI・Secure Boot へ）】**
>
> RISC-V の xv6 はシンプルに `0x80000000` から64ビットモードで起動しますが、私たちが普段使う x86-64 PC では、1981年の初代 IBM PC からの後方互換性を引きずった長い歴史があります。
>
> * **旧来の BIOS / MBR ブート：** 電源オン直後、最新の64ビットCPUであっても最初は1978年の 8086 と同じ **16ビット・リアルモード**（仮想記憶なし、メモリ1 MiB制限）で目覚めます。BIOS はディスク先頭セクタのわずか **512バイト（MBR：Master Boot Record、末尾2バイトが署名 `0x55 0xAA`）** を物理アドレス `0x7C00` へ読み込みます。この512バイトの小さなコードが、より大きなブートローダ（GRUB等）を読み込み、16ビット → 32ビット保護モード → 64ビットロングモード（4段ページング有効化）へと段階的にCPUのモードを切り替えながらLinuxやWindowsのカーネルを起動します。
> * **現代の UEFI と Secure Boot：** 2010年代以降、16ビット互換の煩雑さを脱ぎ捨てた **UEFI（Unified Extensible Firmware Interface）** が標準になりました。UEFI は最初から32/64ビットモードで動作し、FATファイルシステムを直接読んでブートローダやOSカーネル（PE形式）を直接起動できます。さらに **Secure Boot** 機能により、公開鍵暗号（[第7部](../index.md#part-7) [7-7節](../7/7-7.md)）のデジタル署名を検証し、改ざんされたブートローダやマルウェア（ブートキット）がOSより先に起動するのを防いでいます。

### 4. 限界と補正（Critique & Adaptation）

#### (1) マルチコア起動における最適化・並べ替えの危険（`volatile` と `__sync_synchronize`）

`main.c` のマルチコア待機コードをよく見ると、次の2つの特別な記述が入っています。

1. **`volatile static int started = 0;`：** [2-7節](../2/2-7.md)で確認した通り、もし `volatile` を付けずに `-O2` でコンパイルすると、他コアの `while (started == 0) ;` ループは「ループ内で `started` を書き換えていない」と判断され、無限ループへ最適化されて他コアが永遠に目覚めなくなります。
2. **`__sync_synchronize();`（メモリバリア命令）：** [2-7節](../2/2-7.md)の最後で注意した通り、`volatile` だけでは現代のアウトオブオーダCPU（[0-6節](../0/0-6.md)）やストアバッファによる**ハードウェアレベルの命令並べ替え**を防げません。もしコア0が `kvminit()` でページテーブルを書き終えるより先に `started = 1` の書き込みが他コアへ見えてしまうと、コア1は**まだ作りかけの壊れたページテーブル**を `satp` へ読み込んでクラッシュします。また同様に、他コア側（`while (started == 0) ;` の直後）にも `__sync_synchronize()` を置いているのは、`started == 1` を観測するよりも前に後続の `kvminithart()` などが参照するページテーブル等の読み込みが投機的に先行してしまう順序逆転を防ぐためです。双方に `__sync_synchronize()`（RISC-V の `fence` 命令）を挟むことで、コア0の初期化完了結果が他コアへ確実に可視化されてから処理が進む順序をハードウェアに強制しています。

#### (2) ハードコードされた物理アドレスの限界とデバイスツリー（DTB）・ACPI

xv6 のような教育用OSでは、「物理RAMは `0x80000000` から $128\text{ MiB}$」「UART（シリアル通信）は `0x10000000`」「PLIC（割り込みコントローラ）は `0x0C000000`」というように、ハードウェアの物理アドレスをソースコードとリンカスクリプトへ固定値で書き込んでいます（ハードコード）。

しかし現実の商用OS（Linux等）は、メモリ容量が $4\text{ GiB}$ のマシンでも $256\text{ GiB}$ のマシンでも、また異なるメーカーのボード上でも、**同じ1つのカーネルバイナリ**で動かなければなりません。

この限界に対する実システム上の補正が、**ハードウェア構成情報の動的な受け渡し**です。

* **RISC-V / ARM 環境のデバイスツリー（DTB：Device Tree Blob）：** ブートローダ（OpenSBI や U-Boot）が、「このボードにはCPUコアが何個あり、RAMが何番地から何GBあり、どの番地にどのデバイスが繋がっているか」を記述したバイナリデータ（DTB）のアドレスをレジスタ（RISC-Vでは `a1`）へ入れてカーネルへ渡します。
* **x86-64 PC 環境の ACPI（Advanced Configuration and Power Interface）：** UEFIファームウェアがメモリ上に配置した標準テーブル群（ACPIテーブル）をOSカーネルが起動時に解析し、CPUコア数・割り込み配線・電源管理機能を動的に発見して初期化します。

> **【確認の問い】**
>
> 1. **（初期スタック計算とリンカスクリプトの配置制約）**
>     次の2点に答えてください。
>
>     * (a) `entry.S` において、`stack0` の先頭アドレスが `0x8001_0000`（1コアあたり $4\text{ KiB} = \texttt{0x1000}$）のとき、コア0（`mhartid = 0`）とコア2（`mhartid = 2`）の初期スタックポインタ `sp` はそれぞれ何番地になるでしょうか。また、もし `addi a1, a1, 1` の1行を削除した状態でコア0が `call start` を実行すると、どの領域が破壊されるかをスタックの成長方向から説明してください。
>     * (b) `kernel.ld` で `*(trampsec)` の直前に書かれた `. = ALIGN(0x1000);` を削除した場合、仮想記憶（[3-6節](3-6.md)）の動作にどのような不具合が生じるでしょうか。

> 2. **（直接マッピング・コア0限定初期化・メモリバリアの役割）**
>     `main.c` の起動処理について、次の2点に答えてください。
>
>     * (a) `kvminithart()` で `satp` を書き換えて仮想記憶を有効化した瞬間、[3-6節](3-6.md)の `TRAMPOLINE` のような共通ページを介さなくても次の命令（`pc + 4`）でクラッシュしないのはなぜでしょうか。
>     * (b) `if (cpuid() == 0)` の分岐を省いて全コアが `kinit()` や `kvminit()` を同時実行してしまった場合の障害と、コア0・他コア双方の `__sync_synchronize()` を省いた場合にコア1がクラッシュし得る命令並べ替えシナリオをそれぞれ説明してください。
>
> 3. **（複数コアの同時実行で生じる共有変数の更新欠損）**
>     本節の `main()` の最後で、全 CPU コアが同時に `scheduler()` へ入り、複数のコアが並列に命令を実行する状態が始まりました。ここで、コア0とコア1がメモリ上の同じ共有カウンタ `count`（初期値 `0`）に対して同時に `count = count + 1;` を実行したとします。[第1部](../index.md#part-1)で学んだロード・加算・ストアの3命令への分解を踏まえ、なぜ最終結果が `2` ではなく `1` になってしまうことがあるのか、2つのコアの命令の交錯順序を具体的に示して説明してください。
