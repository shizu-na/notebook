### 前節（3-3）の確認問題の解答

前節の最後に提示した3つの問いの解答を確認します。問3がそのまま本節（物理メモリ管理と断片化）の導入になります。

1. **スケジューリング方式の比較計算（P1: $6\text{ ms}$, P2: $3\text{ ms}$, P3: $3\text{ ms}$）：**

    * **(a) FCFS（P1 → P2 → P3）：**

        * 実行順：P1（$0 \sim 6$）→ P2（$6 \sim 9$）→ P3（$9 \sim 12$）
        * 完了時刻：P1 $= 6\text{ ms}$、P2 $= 9\text{ ms}$、P3 $= 12\text{ ms}$
        * 平均ターンアラウンド時間：$\dfrac{6 + 9 + 12}{3} = \mathbf{9.0\text{ ms}}$

    * **(b) ラウンドロビン（$q = 3\text{ ms}$、P1 → P2 → P3 → P1）：**

        * 実行順：P1（$0 \sim 3$、残 $3$）→ P2（$3 \sim 6$、完了）→ P3（$6 \sim 9$、完了）→ P1（$9 \sim 12$、完了）
        * 完了時刻：P1 $= 12\text{ ms}$、P2 $= 6\text{ ms}$、P3 $= 9\text{ ms}$
        * 平均ターンアラウンド時間：$\dfrac{12 + 6 + 9}{3} = \mathbf{9.0\text{ ms}}$
        * 応答時間：P1 $= 0\text{ ms}$、P2 $= 3\text{ ms}$、P3 $= 6\text{ ms}$ $\implies$ 平均応答時間 $\dfrac{0 + 3 + 6}{3} = \mathbf{3.0\text{ ms}}$（FCFS の平均応答時間 $5.0\text{ ms}$ から改善しています）

2. **`swtch` が14本のレジスタしか退避しない理由と2段階切替：**

    * **(a) `ra, sp, s0`〜`s11` の14本だけで安全な理由：**
        `swtch` はカーネル内のC言語コードから通常の関数呼び出しとして呼ばれるため、ABI（[1-3節](../1/1-3.md)）の規約に従い、caller-saved レジスタは呼び出し元が必要に応じてカーネルスタックへ退避済みです。また、ユーザプログラム側の全レジスタもトラップ入口で退避済みのため、`swtch` 自身は callee-saved レジスタ（`s0`〜`s11`）と `ra`, `sp` の14本だけを切り替えれば完全に安全です。

    * **(b) 最後の `ret` 命令で別のコンテクストへ復帰する理由：**
        `ret` の直前に `ld ra, 0(a1)` と `ld sp, 8(a1)` を実行して、戻り番地レジスタ `ra` とスタックポインタ `sp` をすでに `new` 側の値へすり替えているため、`ret` は元のプロセスAではなく `new` が前回 `swtch` を呼んだ直後の場所へジャンプします。

3. **複数プロセスへ物理メモリをどう切り分けて渡すか（本節への接続）：**
    有限の物理メモリを複数プロセスへ可変サイズで切り出して解放・再利用を繰り返すと、メモリのあちこちに細かな空き領域が散らばり、合計では十分な空きがあるのに連続した塊が取れなくなる**外部断片化**が生じます。本節では、物理メモリの割当方式（可変サイズ・固定ページ・バディシステム）とそのトレードオフを整理します。

## 3-4. 物理メモリ管理と断片化（可変・固定割当・バディシステム）

### 1. 動機（Why）：なぜメモリを使い回すだけで「空きはあるのに確保できない」現象が起きるのか

前節（[3-1](3-1.md)〜[3-3節](3-3.md)）までで、1個のCPUコアを複数のプロセスで時間分割して分け合う仕組み（**CPUの仮想化**）が整いました。ここからはOSのもう1つの柱である **メモリの管理と仮想化** へ入ります。

システム上に多数のプロセスが同時に存在するとき、OSカーネルは限られた物理メモリ（RAM）を各プロセスやカーネル自身のデータ構造へ切り分けて貸し出し、プロセスが終了したり不要になったりした領域を回収して再利用しなければなりません。

ここで、一見すると単純に思える「メモリの貸し出しと回収（**物理メモリ管理**）」には、次の3つの厄介な設計課題が潜んでいます。

1. **断片化（Fragmentation）：** プロセスごとに必要なサイズ（$10\text{ KiB}$、$128\text{ KiB}$、$2\text{ MiB}$ 等）はばらばらで、終了する順番も予測できません。確保と解放を繰り返すうちに、メモリ全体が虫食い状になって使えない隙間が増えていきます。
2. **割当・解放の速度と管理オーバーヘッド：** メモリ確保はシステムコールやカーネル内部で毎秒何十万回も呼ばれます。空き領域を探すのに毎回長いリストを端から走査していては遅すぎますし、管理用のメタデータ自体がメモリを大量に消費しても本末転倒です。
3. **連続領域の要求と、小さな領域の要求の混在：** I/Oデバイスのバッファ（[5-1節](../5/5-1.md)のDMA等）のように物理的に連続した大きな塊が欲しい場面もあれば、PCB（`struct proc`）のように数百バイトの小さな構造体を大量に確保・解放する場面もあります。

本節では、まず素朴な可変サイズ割当がなぜ破綻するのかを具体例で確かめたうえで、OSカーネルが実際に採用している **固定サイズページ割当（xv6モデル）** と **バディシステム（Linux等の物理ページアロケータ）** の仕組みを整理します。

### 2. 具体例と動作イメージ（Toy Model）

アルゴリズムの分類に入る前に、総容量 $128\text{ KiB}$ の小さな物理メモリを舞台にした2つの実験で、**外部断片化**と**内部断片化**の違いを体感します。

#### 実験A：可変サイズ割当で起きる「外部断片化」

総容量 $128\text{ KiB}$ の物理メモリがあり、4つのプロセス A, B, C, D がそれぞれ $32\text{ KiB}$ ずつ連続領域を確保したとします。メモリは隙間なく `[A:32][B:32][C:32][D:32]` と埋まります。

1. ここで、**プロセス B と D が終了**してメモリを解放しました。メモリは `[A:32][空:32][C:32][空:32]` の状態になります。
2. 空きメモリの合計は $32 + 32 = \mathbf{64\text{ KiB}}$ もあります。
3. そこへ新しく **プロセス E が $48\text{ KiB}$ の連続領域** を要求しました。

合計では $64\text{ KiB}$ も空いているにもかかわらず、個々の空き領域は $32\text{ KiB}$ ずつ分断されているため、**プロセス E の $48\text{ KiB}$ を確保することができません**（図3-4-1左）。このように、割り当て済み領域の「外側」に細切れの空きが散らばって再利用できなくなる現象を **外部断片化（External Fragmentation）** と呼びます。

#### 実験B：固定サイズ割当（$4\text{ KiB}$ ページ）で起きる「内部断片化」

外部断片化を根本からなくす発想はシンプルです。「あらゆるサイズを自由に切り出すのをやめ、物理メモリ全体を最初から **$4\text{ KiB}$ の固定サイズ（ページフレーム）** に等分してしまい、常に $4\text{ KiB}$ 単位で貸し出す」方式にします。

* どの空きブロックもすべて同じ $4\text{ KiB}$ なので、どの空き枠を選んでも形がぴったり合い、**外部断片化は原理的にゼロ**になります。
* 一方、ある処理が $5\text{ KiB}$ だけメモリを欲しがった場合、$4\text{ KiB}$ を2枠（合計 $8\text{ KiB}$）割り当てる必要があり、2枠目の残りの **$3\text{ KiB}$ は使われないまま無駄**になります（図3-4-1右）。このように、割り当てた枠の「内側」に生じる余り領域を **内部断片化（Internal Fragmentation）** と呼びます。

### 3. 構造・アルゴリズム・実装（What）

#### (1) 可変サイズ割当の戦略とフリーリストの結合（Coalescing）

ユーザ空間の `malloc` / `free` や、仮想記憶を持たない組込みOSなどでは、要求サイズちょうどを切り出す **可変サイズ割当** が使われます。未割り当ての空き領域を連結リスト（**フリーリスト：Free List**）で管理し、要求サイズ $S$ が来たときにどの空きブロックから切り出すか（**分割：Splitting**）には代表的な4戦略があります。

| 割当戦略 | 選び方 | 特徴とトレードオフ |
| :--- | :--- | :--- |
| **First-Fit**（最初適合） | リスト先頭から探して**最初に見つかった** $S$ 以上の空きを使う | 探索が速いが、リスト先頭付近に細かな断片が溜まりやすい |
| **Next-Fit**（次回適合） | 前回割り当てた位置の**次から**循環探索する | First-Fit の先頭集中を緩和し、メモリ全体へ均等に分散させる |
| **Best-Fit**（最良適合） | 全空きの中で $S$ 以上かつ**最小の**空きを選ぶ | 大きな空きを温存できるが、全探索が必要で極小の使えない欠片が増えやすい |
| **Worst-Fit**（最悪適合） | 全空きの中で**最大の**空きから切り出す | 切り出した残りがまだ再利用可能な大きさを保ちやすいが、大きな連続領域を早く消費する |

また、ブロックが解放（`free`）されたとき、**物理アドレス上で隣り合う空きブロック同士を1つの大きな空きへ合体させる処理（結合：Coalescing）**が不可欠です。もし結合を行わなければ、一度細かく分割されたメモリは二度と元の大きなサイズへ戻れず、急速に枯渇してしまいます。なお、実験Aの `[A][空][C][空]` のように使用中ブロック `C` が間に挟まっている場合は結合できないため、可変サイズ割当で外部断片化を完全に防ぐことはできません。

#### (2) 固定サイズ割当と xv6 のページアロケータ（`kalloc` / `kfree`）

OSカーネルが物理メモリを管理する最もシンプルで高速な実装が、**固定サイズ（$4\text{ KiB} = 4096\text{ B}$）のページフレーム単位のフリーリスト**です。RISC-V 版 xv6 の物理メモリアロケータ（`kalloc.c`）では、驚くほど巧みな省メモリ実装が使われています（図3-4-2）。

空きページ一覧を管理するための専用配列を別途用意するのではなく、**「空きページ自身の先頭8バイトに、次の空きページへのポインタ（`struct run *next`）を直接書き込んで単方向連結リストにする」**のです。

```c
struct run {
    struct run *next;   // 空きページ自身の先頭8バイトをポインタとして流用
};

void kfree(void *pa) {
    struct run *r = (struct run *)pa;
    // フリーリストの先頭へ O(1) で差し込む（push）
    r->next = kmem.freelist;
    kmem.freelist = r;
}

void *kalloc(void) {
    struct run *r = kmem.freelist;
    if (r)
        kmem.freelist = r->next;   // 先頭から O(1) で1ページ取り出す（pop）
    return (void *)r;
}
```

この方式は、管理用の追加メモリを `kmem.freelist` のポインタ1個（8バイト）しか消費せず、しかも確保も解放も **常に定数時間 $O(1)$**、外部断片化もゼロという優れた性質を持ちます。

#### (3) バディシステム（Buddy System）：2のべき乗分割と XOR による高速結合

xv6 の固定ページ方式は $4\text{ KiB}$ を1ページずつ配るだけなら完璧ですが、**「物理的に連続した $16\text{ KiB}$（4ページ分）や $64\text{ KiB}$（16ページ分）の塊が欲しい」**という要求（DMAバッファや大きなカーネルデータ構造、Huge Page など）には応えられません。

そこで、Linuxカーネルをはじめ多くの実用OSの物理ページ管理で採用されているのが **バディシステム（Buddy System）** です。

バディシステムは、メモリブロックのサイズを **$2^k$（2のべき乗）単位**（最小 $4\text{ KiB} = 2^0$ ページ、$8\text{ KiB} = 2^1$ ページ、$16\text{ KiB} = 2^2$ ページ、…）に限定し、サイズ（次数 $k$）ごとに独立したフリーリスト `free_list[k]` を持ちます。

* **確保（分割：Splitting）の手順：**
    要求サイズ $S$ を満たす最小の2のべき乗サイズ $2^k$ を決めます。もし `free_list[k]` に空きがあればそれを返します。空いていなければ、1段大きい `free_list[k+1]` からブロックを1つ取り出し、**ちょうど半分（2つの $2^k$ ブロック＝「相棒：Buddy」同士）に分割**して、片方を `free_list[k]` へ戻し、もう片方を使います（必要なサイズになるまで再帰的に分割）。

* **解放（結合：Coalescing）の手順と XOR 計算：**
    サイズ $2^k$ のブロックを解放するとき、相棒（バディ）のブロックも現在空き状態であれば、2つを合体させて1段大きい $2^{k+1}$ ブロックに戻します（相棒が空きである限り連鎖的に合体）。

ここで、バディシステム最大の実装上の美しさが **「相棒のアドレスをビットの排他的論理和（XOR）1命令で即座に求められる」** 点にあります。

ベースアドレスを `0` としたとき、バイトサイズ $B = 2^m$ のブロック（例：$16\text{ KiB} = 2^{14}\text{ B}$ なら $m = 14$）は必ず $B$ の倍数アドレスに配置され、ペアとなる2つのバディはアドレスの **$m$ ビット目（サイズ $B$ の位置のビット）だけが `0` と `1` で異なり、他のビットはすべて同一**です。したがって、任意のブロック（アドレス `addr`、バイトサイズ `B`）のバディのアドレスは常に次式で計算できます。

$$
\text{buddy\_addr} = \text{addr} \oplus B
$$

具体例として、全体 $64\text{ KiB}$（アドレス `0x0000`〜`0xFFFF`）のメモリから $16\text{ KiB}$（`0x4000`）を要求し、その後解放する流れを追ってみます（図3-4-3）。

1. 最初は `0x0000` に $64\text{ KiB}$ の塊が1つだけあります。
2. $16\text{ KiB}$ が必要なので、$64\text{ KiB}$ を2分割（`0x0000` と `0x8000` の各 $32\text{ KiB}$）し、さらに左の $32\text{ KiB}$ を2分割（`0x0000` と `0x4000` の各 $16\text{ KiB}$）して、`0x0000` の $16\text{ KiB}$ を割り当てます。
3. 解放時：`0x0000`（サイズ `0x4000`）のバディは $\texttt{0x0000} \oplus \texttt{0x4000} = \mathbf{\texttt{0x4000}}$ です。`0x4000` は空きなので合体して `0x0000`（サイズ $32\text{ KiB} = \texttt{0x8000}$）へ戻ります。
4. 続けて `0x0000`（サイズ `0x8000`）のバディは $\texttt{0x0000} \oplus \texttt{0x8000} = \mathbf{\texttt{0x8000}}$ です。こちらも空きなので合体し、元の $64\text{ KiB}$ が完全に復元されます。

バディシステムは、サイズの種類を $\log_2 N$ 段階だけに絞ることで、連続した複数ページの確保と高速な $O(\log N)$ 結合を両立しています。

> **【コラム：スラブアロケータ（Slab Allocator）：ページ単位と「数十バイトの構造体」の隙間を埋める】**
>
> バディシステムや xv6 の `kalloc` が配る最小単位は $4\text{ KiB}$（$4096\text{ B}$）です。しかしOSカーネルの内部では、ファイル記述子やi-node、ネットワークパケット管理ヘッダといった **64バイト〜256バイト程度の小さな構造体** が毎秒何万個も生成・破棄されます。もし64バイトの構造体を1個作るたびに毎回 $4\text{ KiB}$ の物理ページを丸ごと渡していたら、98%以上が内部断片化で無駄になってしまいます。
>
> この隙間を埋めるために Linux や BSD カーネルが採用しているのが、バディシステムの上にもう1層載せる **スラブアロケータ（Slab Allocator：SLAB / SLUB）** です。スラブアロケータはバディシステムから $4\text{ KiB}$ ページ（スラブ）を1枚まとめて借り受け、その中を「`inode` 専用（128B 刻み）」「`task_struct` 専用」のように**同じサイズの小さなスロットへ等分**してオブジェクトキャッシュを作ります。これにより、外部断片化も内部断片化もほぼゼロに抑えつつ、構造体の初期化コストまで再利用して超高速に割り当てられます。

### 4. 限界と補正（Critique & Adaptation）

#### (1) ページサイズ（$4\text{ KiB}$）のバランスと Huge Page

固定サイズページ割当の内部断片化は、平均して「1プロセス（または1領域）あたり $0.5$ ページ分」になります。ページサイズを $512\text{ B}$ のように小さくすれば内部断片化は減りますが、次節（[3-5節](3-5.md)）で学ぶアドレス変換表（ページテーブル）のエントリ数が8倍に膨らんで管理コストが増えます。逆に $1\text{ MiB}$ にすると小さなプロセスでメモリ浪費が激しくなります。

歴史的に **$4\text{ KiB}$（4096バイト）** が両者のバランス点としてほぼ全CPUの標準となりましたが、現代のサーバのように数百 GiB のRAMを搭載する環境では $4\text{ KiB}$ ページだけでは管理対象が数千万ページに達します。これに対する補正として、データベースや機械学習のように巨大な連続メモリを使うアプリ向けに、$2\text{ MiB}$ や $1\text{ GiB}$ の大きなページを併用する **Huge Page（ラージページ）** が現代OSで広く使われています。

#### (2) バディシステムの内部断片化と階層的アロケータ構造

バディシステムは高速で外部断片化を抑えられる反面、サイズが2のべき乗に限定されるため、**要求サイズが2のべき乗をわずかに超えたときに大きな内部断片化が生じる**という弱点があります。たとえば $65\text{ KiB}$ を要求すると、$64\text{ KiB}$ に入りきらないため次の $128\text{ KiB}$ ブロックが割り当てられ、**$63\text{ KiB}$（約49%）が未使用**になります。

したがって現代のOSとアプリケーションでは、単一の方式に頼るのではなく、用途に応じた **3階層のメモリ管理** で互いの弱点を補っています。

1. **最下層（OS物理ページ管理）：** バディシステム（$4\text{ KiB} \times 2^k$ のページ群を管理）。
2. **中層（OSカーネル内オブジェクト管理）：** スラブアロケータ（小さな固定長構造体を高速管理）。
3. **上層（ユーザ空間のヒープ管理）：** C標準ライブラリの `malloc` / `free`（OSから `sbrk` や `mmap` でページ単位の塊を借り、内部でサイズ別ビンやフリーリストを管理して任意バイト数をアプリへ配る）。

#### (3) 物理メモリ管理だけでは解けない「2つの根本的な壁」（次節への動機）

ここまでの仕組みで、物理メモリを効率よく切り出して使い回す方法は揃いました。しかし、**物理アドレスをそのままユーザプログラムへ渡して動かす設計には、どうしても越えられない2つの壁**が残ります。

1. **保護・隔離の壁：** プロセスAとプロセスBが同じ物理メモリ空間に同居しているだけでは、プロセスAがポインタの計算ミスでプロセスBの物理番地へ書き込むのを防げません。
2. **連続性と固定アドレスの壁：** コンパイル済みの複数プログラムが「どちらも先頭アドレス `0x0000`（あるいは同じ仮想アドレス）から配置されたい」と期待していても、物理メモリの同じ番地に2つのプロセスを同時に置くことはできません。さらに、固定ページ割当で飛び飛びに空いた2枚の物理ページ（例：`0x8000_5000` と `0x8000_F000`）を、プロセスから見て1本の連続した $8\text{ KiB}$ 配列として見せることもできません。

この2つの壁を一挙に打ち破るのが、次節（[3-5節](3-5.md)）で導入する **仮想記憶（Virtual Memory）と多段ページテーブル** です。

### 5. 接続と展望（Bridge）：本節の内容が後半のどの部に繋がるか

1. **次節（[3-5節](3-5.md)：仮想記憶と多段ページテーブル・TLB）：**
    本節で「飛び飛びの $4\text{ KiB}$ 物理ページフレーム」を $O(1)$ で確保する土台（`kalloc`）が整いました。次節では、CPUのMMUと多段ページテーブルという「間接参照の地図」を挟むことで、飛び飛びの物理ページを各プロセス専用の連続した仮想アドレス空間へ見せる仕組みへ進みます。

2. **[第3部](../index.md#part-3)（[3-7節](3-7.md)：ページフォルトの応用）：**
    本節で触れた `malloc` の背後にある遅延割当（Lazy Allocation）や、参照カウントを用いた物理ページの共有（Copy-on-Write）へ接続します。

3. **[第4部](../index.md#part-4)（[4-4節](../4/4-4.md)：スピンロック）：**
    マルチコア環境では、2つのCPUコアが同時に `kalloc()` を呼ぶと `kmem.freelist` のポインタ付け替えが競合してリストが破壊されます。そのため xv6 の実装では `kmem.lock` というスピンロックで `kalloc`/`kfree` を保護します。

4. **[第9部](../index.md#part-9)（[9-1節](../9/9-1.md)：DBMSのページ編成）：**
    「固定長のページ（$4\text{ KiB}$ / $8\text{ KiB}$）単位で管理しつつ、ページ内部の可変長データの削除で生じる断片化をどう扱うか」という課題は、データベースのディスクページ編成（スロッテッドページとコンパクション）でも再び登場します。

### 理解度チェック（次節へ進む前の確認）

本節の可変割当（First-Fit / Best-Fit）とバディシステムの計算を確認し、次節（[3-5節](3-5.md)）へ繋ぐ問いを置きます。

> **【確認の問い】**
>
> 1. **（可変サイズ割当：First-Fit と Best-Fit の比較）**
>     空き領域のフリーリストに、先頭から順に **`[30 KiB] → [100 KiB] → [50 KiB] → [20 KiB]`** の4つの空きブロックが並んでいるとします。ここへ順に **要求1：$40\text{ KiB}$**、**要求2：$25\text{ KiB}$** が到着しました。
>
>     * (a) **First-Fit** で割り当てた場合、要求1と要求2はそれぞれどのブロックから切り出され、残りの空きブロックはどうなるでしょうか。
>     * (b) **Best-Fit** で割り当てた場合はどうなるでしょうか。
> 2. **（バディシステムの分割と XOR 結合計算）**
>     全体 $128\text{ KiB}$（アドレス `0x00000`〜`0x1FFFF`）のバディシステムから、まず $32\text{ KiB}$（`0x08000`）のブロックを1つ確保し、続けて $16\text{ KiB}$（`0x04000`）のブロックを1つ確保しました（常にアドレスの小さい左側から割り当てるものとします）。
>
>     * (a) $32\text{ KiB}$ のブロックと $16\text{ KiB}$ のブロックは、それぞれどの先頭アドレスへ割り当てられるでしょうか。
>     * (b) $16\text{ KiB}$ のブロックを解放するとき、相棒（バディ）のアドレスを式 $\text{addr} \oplus B$ で計算してください。また、その時点でバディと合体できるか否かを答えてください。
> 3. **（次節への伏線：飛び飛びの物理ページを「連続かつ隔離された専用メモリ」に見せるには）**
>     本節の固定ページ割当（$4\text{ KiB}$）によって外部断片化はゼロになりましたが、確保された物理ページはRAM上のあちこちに飛び飛びに散らばっており、しかも他プロセスと同じ物理空間に同居しています。各プロセスに「自分だけの独立した連続メモリ空間」を見せ、かつ他プロセスの物理ページへ絶対に触れられないようにするには、CPUと主記憶の間にどのようなアドレス変換の仕組みを挟めばよいでしょうか。
