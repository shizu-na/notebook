### 前節（2-9）の確認問題の解答

前節の最後に提示した3つの問いの解答を確認します。問3がそのまま[第3部](../index.md#part-3)（OS の仮想化：プロセスと仮想記憶）の本節の導入になります。

1. **参照カウントの手動トレースと、コピー GC 対 マーク＆コンパクトの適用判断：**

    * **(a) 参照カウントのトレース（`p → A → B → C → B`）と循環参照の解消：**

        * ① `p` が消滅する直前の参照カウントは **`A: 1`**（`p` から）、**`B: 2`**（`A` と `C` から）、**`C: 1`**（`B` から）です。`p` が消滅すると `A` のカウントが $1 \to 0$ になり、**`A` は即座に解放**されます。`A` が解放されると `A → B` の参照も消えるため `B` のカウントは $2 \to 1$ に減りますが、その後は **`B: 1`**（`C` から）、**`C: 1`**（`B` から）のまま互いに支え合って `0` にならず、**`B` と `C` がメモリリーク**します。
        * ② 参照カウントのままリークを防ぐには、循環を構成する辺の片方（たとえば `C → B`）をカウントを増やさない**弱参照（`weak`）**へ変更します。すると初期カウントが `B: 1`（`A` からのみ）となり、`A` 解放時に `B` が $1 \to 0$ で解放され、連鎖して `C` も $1 \to 0$ で正しく解放されます。

    * **(b) 総容量 $200\text{ MiB}$ におけるコピー GC の適用比較：**
        コピー GC は領域を From / To の 2 つに分けるため、実際に使える空間は半分（**$100\text{ MiB}$、空間効率 50%**）に限られます。

        * **① 生存率 $1\%$ の若世代：** コピー対象は $100\text{ MiB} \times 1\% = \mathbf{1\text{ MiB}}$ のみで非常に高速に終わり、外部断片化もゼロでバンプポインタ割当の恩恵が最大化されます。
        * **② 生存率 $80\%$ の旧世代：** 毎回 $100\text{ MiB} \times 80\% = \mathbf{80\text{ MiB}}$ をコピーする負荷が大きいうえ、大きな旧世代の半分（$100\text{ MiB}$）を常に空きとして遊ばせる空間ロスが大きすぎます。そのため世代別 GC では、若世代にコピー GC、旧世代に空間効率 **100%** のマーク＆スイープ／コンパクトを組み合わせます。

2. **並行 GC の三色マーキング誤回収トレースと、外部資源管理の誤解検証：**

    * **(a) ライトバリア無効時の誤回収と、有効時の防止メカニズム：**
        ライトバリアが無効だと、`A` はすでに黒（子ポインタの探索完了済み）のため再走査されず、`B → C` の参照も消えているため、`C` はルートから `A` 経由で生存しているにもかかわらず**白のまま取り残され、スイープ時に誤回収（Use-After-Free の原因）**されます。ライトバリアを有効にしておけば、`A.ref = C`（挿入バリア）または `B.ref = null`（削除バリア／SATB）の瞬間に `C` を強制的に **白 → 灰** へ塗って探索キューへ積むため、`C` とその子孫が確実にマークされます。

    * **(b) ファイルや DB 接続を GC 任せにしてはいけない理由と対処法：**
        GC が監視・回収するのはヒープメモリだけであり、ヒープに十分な空きがあるあいだは GC が発動しません。OS のファイル記述子（FD）や DB 接続は上限が厳しく有限な資源であるため、GC 任せにするとメモリが余っている状態で FD 枯渇（`EMFILE`）や接続枯渇による障害を起こします。Java の `try-with-resources`、Python の `with`、Go の `defer` 等を用い、スコープ脱出時に決定的かつ即座に明示クローズする必要があります。

3. **複数プロセス間の隔離と CPU ハードウェア機能（本節への接続）：**
    OS の保護なしで複数アプリがハードウェアを直接操作すると、① 1 つのアプリのポインタバグが他アプリのメモリを壊す **メモリの相互破壊**、② 無限ループで他アプリへ実行権が渡らない **CPU の独占**、③ 機種差の吸収不能や同時書込みによる **デバイス・ファイル破損**、の 3 つが起きます。これをソフトウェアの約束事だけでなく強制するには、CPU ハードウェア側が **特権モード（U-mode / S-mode）** と **トラップ（タイマ割り込み・例外・システムコール）** を備える必要があり、これが本節の主題になります。

## 3-1. OSの役割（抽象化と保護）と特権モード・割り込み・システムコール

### 1. 動機（Why）：なぜアプリケーションにハードウェアを直接触らせてはならないのか

[第0部](../index.md#part-0)から[第2部](../index.md#part-2)までを通じて、1つのCプログラムがコンパイル・最適化され、ELFバイナリとしてCPUのパイプラインとキャッシュ上で動くまでの道筋がすべて繋がりました。

しかし、私たちが日常的に使うコンピュータの上では、エディタ、Webブラウザ、コンパイラ、音楽再生ソフトといった多数のプログラムが**同時に**動いています。もしここにOS（オペレーティングシステム）が存在せず、それぞれのプログラムがCPU・主記憶・ディスクといった生のハードウェアを直接操作できるとしたら、次の3つの破綻が即座に起きます。

1. **メモリの相互破壊：** あるプログラムにポインタのバグがあり、誤った番地へデータを書き込んだ瞬間、隣で動いている別プログラムのデータやシステム全体の管理情報まで破壊してしまいます。
2. **CPUの独占：** 1つのプログラムが `while (1) {}` のような無限ループに陥ると、他のすべてのプログラムへ二度とCPUが回ってこなくなり、コンピュータ全体がフリーズします。
3. **デバイス操作の複雑さと衝突：** ディスクや画面、キーボードは機種ごとに異なる細かな制御手順を持ちます。すべてのアプリに全メーカーのハードウェア制御コードを書かせるわけにはいかず、2つのアプリが同時にディスクへ書き込めばファイルが破損します。

これらの問題を解決するために、ハードウェアとアプリケーションの間に常駐してシステム全体を統括する特別なソフトウェアが **OS（オペレーティングシステム）**、特にその中核部分が **カーネル（Kernel）** です。

重要なのは、**「OSによる保護と隔離は、ソフトウェアの約束事だけでは実現できない」**という点です。悪意ある（あるいはバグのある）プログラムがOSの監視を無視して勝手にメモリやデバイスを触れないようにするため、CPUハードウェア自体が **特権モード** と **トラップ（割り込み・例外・システムコール）** という専用の仕掛けを備えています。本節では、構造の見通しがよい **RISC-V（RV64GC：教育用OS xv6 の設計モデル）** を具体例として、OSの役割とユーザ／カーネル境界の仕組みを整理します。

### 2. 具体例と動作イメージ（Toy Model）

抽象的な分類に入る前に、ユーザプログラムがOSの力を借りる場面と、OSが強制的にCPUを取り戻す場面の2つの小さな実験を辿ってみます。

#### 実験A：画面へ `"Hi\n"` を出力する `write` システムコールの旅

ユーザプログラムが画面（標準出力：OSが開いた入出力先を整数番号で識別する**ファイル記述子** `1`）へ3バイトの文字列 `"Hi\n"` を出力したいとします。アプリは画面ハードウェアの制御レジスタを直接触る権限を持たないため、OSへ「代わりに書いてほしい」と依頼します。この依頼窓口が **システムコール（System Call）** です。

RISC-V環境でCコードから `write(1, "Hi\n", 3);` を呼び出すと、裏側では次の手順でユーザ空間からカーネル空間へ境界を越えます。

1. **引数の準備（ユーザ空間）：** [1-1節](../1/1-1.md)のレジスタ対応表の通り、RISC-Vの引数レジスタへ `a0 = 1`（出力先）、`a1 = "Hi\n"の先頭アドレス`、`a2 = 3`（バイト数）を入れ、さらにシステムコール番号レジスタ **`a7`** に `write` を表す番号（例：`SYS_write = 16`）をセットします。
2. **境界を越える専用命令 `ecall` の実行：** ユーザプログラムが **`ecall`（Environment Call）** 命令を実行すると、CPUハードウェアが自動的に動作モードを「ユーザモード」から特権のある「カーネルモード」へ切り替え、あらかじめOSが登録しておいたカーネルの入口番地へ強制ジャンプします。
3. **カーネルによる検証と実行（カーネル空間）：** OSカーネルは `a7` の番号を検査して `sys_write` 関数を呼び出します。渡されたアドレスやサイズが不正でないかを検証したうえで、特権を使って出力デバイスへ `"Hi\n"` を書き出し、戻り値（書き込んだバイト数 `3`）をユーザ復帰用の `a0` へ設定します。
4. **ユーザ空間への帰還（`sret`）：** カーネルが **`sret`** 命令を実行すると、CPUは動作モードを再びユーザモードへ戻し、`ecall` のすぐ次の命令からアプリの処理を再開します。

#### 実験B：無限ループと不正アクセスをハードウェアが止める瞬間

では、ユーザプログラムが自分から `ecall` を呼ばず、お行儀悪く振る舞った場合はどうなるでしょうか。

* **ケース1（無限ループによるCPU独占）：** アプリが `while (1) {}` に陥っても、マザーボードやCPUに内蔵された**タイマハードウェア**が一定間隔（たとえば数ミリ秒〜10ミリ秒ごと）で強制的に電気信号（**タイマ割り込み**）をCPUへ送り込みます。CPUはその瞬間にアプリの実行を強制中断してカーネルモードへ切り替えるため、OSはいつでも確実にCPUの主導権を奪い返して別のアプリへ切り替えられます。
* **ケース2（特権命令や他人のメモリへの不正アクセス）：** ユーザモードのアプリが、許可されていないハードウェア制御命令を実行したり、自分に割り当てられていないメモリアドレスへ書き込んだりした瞬間、CPUハードウェアが**例外（Exception）**を発生させて即座にカーネルへ制御を移します。OSは違反を起こしたそのプロセスだけを強制終了させ、他のアプリやOS自身を無傷で守り抜きます。

### 3. 構造・アルゴリズム・実装（What）

#### (1) OSの2大役割：抽象化（Abstraction）と保護・多重化（Isolation & Multiplexing）

OSがアプリケーションへ提供している価値は、次の2つの柱に整理できます（図3-1-1左）。

1. **ハードウェアの抽象化と仮想化：** 扱いにくい生の物理資源を、アプリから見て使いやすく独立した「仮想的な資源」へ変換して見せます。

    * **限られた物理CPUコア** $\implies$ 各プログラムがCPUを専有しているように見える **プロセス（Process）**（[3-2](3-2.md)・[3-3節](3-3.md)）
    * **1枚の物理主記憶（RAM）** $\implies$ 各プロセスが広大で独立した自分専用のメモリを持つように見える **仮想アドレス空間**（[3-5節](3-5.md)）
    * **セクタの羅列であるストレージやI/O機器** $\implies$ 階層的な名前とバイト列で統一的に読み書きできる **ファイル（File）**（[第5部](../index.md#part-5)）

2. **多重化（Multiplexing）と保護・隔離（Isolation）：** 複数のプロセスが1台のハードウェア資源を時間・空間で分け合いながら、あるプロセスのバグや攻撃が他のプロセスやOSカーネルへ波及しないように隔離します。

#### (2) CPUの特権モード（Privilege Modes）と制御ステータスレジスタ（CSR）

OSによる隔離をハードウェアレベルで強制する仕組みが、CPUの **特権モード（Privilege Mode）** です。現在のCPUがどのモードで動いているかに応じて、実行できる命令やアクセスできるメモリ領域がハードウェアによって厳格に制限されます（図3-1-1右）。

RISC-V（RV64）には、権限の強さに応じて次の3つの特権モードがあります。

| モード名 | 略称 | 主な実行主体 | できること |
| :--- | :---: | :--- | :--- |
| **マシンモード**（Machine Mode） | **M-mode** | ブートローダ・ファームウェア | 最高権限。起動直後の初期化や低レベルハードウェア制御（[3-8節](3-8.md)） |
| **スーパーバイザモード**（Supervisor Mode） | **S-mode** | **OSカーネル** | ページテーブル（仮想と物理の対応表）設定、割り込み制御、I/Oデバイス操作などの特権命令 |
| **ユーザモード**（User Mode） | **U-mode** | **一般アプリケーション** | 通常の演算・分岐・自プロセス内メモリ参照のみ。特権命令は即座に例外 |

（※x86-64ではプロテクションリングと呼ばれ、**Ring 0** がカーネルモード［S-mode相当］、**Ring 3** がユーザモード［U-mode相当］に対応します。基本的な役割分担は同じですが、x86-64 ではトラップ時にハードウェアが TSS 経由でカーネルスタックを自動切替するなど、細部には実装差があります。）

S-mode のOSカーネルは、通常の汎用レジスタ（`x0`〜`x31`）とは別に用意された **CSR（Control and Status Registers：制御ステータスレジスタ）** を専用命令（`csrr` / `csrw`）で読み書きしてCPUの動作を制御します。本節で押さえるべき基本の4つのCSRは次の通りです。

* **`stvec`（Supervisor Trap Vector）：** トラップが起きたときにCPUが自動的にジャンプする、カーネル側のハンドラ先頭アドレスを事前に登録しておくレジスタです。
* **`sepc`（Supervisor Exception Program Counter）：** トラップ発生時のユーザ側プログラムカウンタ（`pc`）をハードウェアが自動退避しておくレジスタであり、`sret` でここへ戻ります。
* **`scause`（Supervisor Cause）：** 「何が原因でトラップが起きたか」（システムコールか、タイマ割り込みか、不正メモリアクセスか）をハードウェアが番号で記録するレジスタです。
* **`sstatus`（Supervisor Status）：** トラップ直前の動作モード（U-modeだったかS-modeだったか）や、割り込みの許可／禁止ビットを保持するレジスタです。

#### (3) トラップ（Trap）の3分類：システムコール・例外・割り込み

実行中の処理を一時中断し、CPUハードウェアが自動的に特権モード（S-mode）へ切り替えてカーネルのハンドラ（`stvec`）へ制御を移す仕組みを総称して **トラップ（Trap）** と呼びます。トラップは、発生原因と「命令の実行と同期しているか」の観点から次の3つに明確に分類されます。

| 分類 | 同期／非同期 | 意図 | 主な具体例 | 復帰先 `sepc` の扱い |
| :--- | :---: | :---: | :--- | :--- |
| **システムコール**（System Call） | **同期** | 意図的 | `ecall`（`read`, `write`, `fork`, `exit` 等） | **`sepc + 4`**（`ecall` の次の命令へ進む） |
| **例外**（Exception） | **同期** | 非意図的 | 不正命令、ページフォルト（未割当・権限違反のメモリ参照）、不正アドレス参照 | 原則 **`sepc` のまま**（修復後に再実行）または強制終了 |
| **割り込み**（Interrupt） | **非同期** | 外部事象 | タイマ割り込み、キーボード入力、ディスクI/O完了 | **`sepc` のまま**（中断された命令からそのまま再開） |

「同期（Synchronous）」とは、ある特定の機械語命令を実行した直接の結果としてその命令のタイミングで起きることを意味します。一方、「非同期（Asynchronous）」は、CPUが今どの命令を実行しているかとは無関係に、外部のタイマやデバイスからの電気信号によって任意のタイミングで発生するイベントです。

1. **ユーザ側の薄いラッパー関数：** C言語からは普通の関数 `write(1, "Hi\n", 3)` に見えますが、標準ライブラリ内の実体（xv6では `usys.S`）は、`li a7, SYS_write; ecall; ret` というわずか3命令のスタブです。3命令だけで済むのは、Cの関数呼び出し規約（ABI：[1-3節](../1/1-3.md)）により呼び出し元がすでに引数レジスタ `a0`〜`a2` へ引数を配置した状態でこのスタブを呼んでおり、スタブ自身はシステムコール番号を `a7` へ設定して `ecall` を実行し、`a0` に返った値をそのまま返すだけでよいためです。
2. **CPUハードウェアによる原子的なモード遷移：** `ecall` を実行した瞬間、CPUは次の処理を不可分（1ステップ）に行います。

    * 現在の `pc`（`ecall` 命令自身のアドレス）を `sepc` へ退避します。
    * 原因コード `8`（U-mode からの環境呼び出し）を `scause` へ書き込みます。
    * 割り込みを一時禁止し、直前のモード（U-mode）を `sstatus` へ記録したうえで、動作モードを **S-mode** へ昇格させます。
    * `pc` を `stvec` に登録されたカーネルのトラップ入口へジャンプさせます。

3. **カーネルのディスパッチと `sepc += 4`：** カーネルはユーザの全レジスタを退避したあと、`usertrap()` 内で `scause == 8`（システムコール）であることを確認します。ここで重要なのが **`sepc` に `4`（`ecall` 命令のサイズ4バイト）を加算する処理** です。もし加算しないと、`sret` で戻った瞬間に同じ `ecall` をもう一度実行して無限ループに陥ります。続いて、不正なシステムコール番号による配列外参照（カーネルの任意アドレスジャンプ）を防ぐため、必ず **`num > 0 && num < NELEM(syscalls)` の境界検査** を行ったうえで関数ポインタ配列 `syscalls[a7]()` を通じて `sys_write` を呼び出します（範囲外ならエラー値 `-1` を返します）。処理が終わると、返り値を退避領域の `a0` へ書き込みます。現在のCPUレジスタ `a0` へ直接書かずに退避領域の `a0` へ書くのは、ステップ4の復帰時に退避領域から全ユーザレジスタを一括復元した際、現在の `a0` が上書きされて消えてしまうためです。
4. **`sret` による復帰：** 退避していたユーザレジスタを復元し、`sret` 命令を実行すると、ハードウェアが `mode` を U-mode へ降格させ、`pc` を更新済みの `sepc`（`ecall` の次の `ret` 命令）へ戻します。

> **【コラム：モノリシックカーネル vs マイクロカーネル：保護の境界をどこに引くか】**
>
> OSのカーネル（S-mode）の中に「どの機能までを入れるか」という設計思想には、古典的な2つの流派があります（図3-1-3）。
>
> * **モノリシックカーネル（Monolithic Kernel：Linux, xv6, FreeBSD 等）：** プロセス管理、仮想記憶、ファイルシステム、ネットワークプロトコル、デバイスドライバといったOSの全機能を1つのカーネル空間（S-mode）へ同居させます。機能同士が通常の関数呼び出しだけで低オーバーヘッドに連携できる反面、デバイスドライバの1行のバグ（ヌルポインタ参照等）がカーネル全体を停止（カーネルパニック）させてしまう弱点があります。
> * **マイクロカーネル（Microkernel：seL4, QNX, Minix 等）：** S-mode のカーネルには「プロセス切替・最小限のメモリ保護・プロセス間通信（IPC）」という必要最小限の中核機能だけを残し、ファイルシステムやドライバはすべて**U-mode の独立したユーザプロセス**として隔離して動かします。ドライバがクラッシュしてもOS全体は落ちず再起動できる高い堅牢性を持つ一方、ファイル読出しのたびにプロセス間通信とモード切替が何度も発生するため性能面のオーバーヘッドが課題になります。
>
> 現実のシステムでは、Linux（モノリシック）がドライバを動的に着脱できるカーネルモジュールやユーザ空間ドライバを取り入れ、macOS / Windows が両者の中間（ハイブリッド構成）をとるなど、性能と堅牢性のバランスを追求しています。

### 4. 限界と補正（Critique & Adaptation）

特権モードとシステムコールによる厳格な境界分離は計算機の安全性を支えますが、実運用では次の2つのコストとリスクに対処する必要があります。

#### (1) システムコールのオーバーヘッドと回数削減の工夫

普通のC関数呼び出し（`call` / `ret`）は数サイクル（数ナノ秒）で完了します。これに対し、システムコール（`ecall` / `sret`）では特権モード切替、ユーザレジスタ全体の退避と復元、アドレス空間の切替（[3-6節](3-6.md)）、さらにCPUパイプラインのフラッシュやキャッシュ汚染が伴うため、**通常の関数呼び出しの数十倍〜数百倍のコスト**がかかります。

もし1バイト出力するたびに毎回 `write(1, &c, 1)` システムコールを呼ぶと、処理時間の大半がモード切替で消えてしまいます。これに対する実システム上の補正は次の3方向です。

1. **ユーザ空間でのバッファリング（[5-2節](../5/5-2.md)）：** C標準ライブラリ（`stdio.h` の `printf` や `fwrite`）は、ユーザ空間のメモリに4 KiBなどのバッファを溜め込み、満杯になったときや改行時だけまとめて1回の `write` システムコールを発行します。
2. **読取り専用カーネルデータの共有（`vDSO`：[1-5節](../1/1-5.md)コラム）：** 時刻取得（`clock_gettime`）のように権限チェックが不要な処理は、カーネルが時刻ページをユーザ空間へ共有マップすることでシステムコール自体を回避します。
3. **非同期バッチI/O（Linux の `io_uring` 等）：** ユーザ空間とカーネル空間で**リングバッファ**（先頭と末尾が繋がった環状の共有キュー）を共有し、多数のI/O要求を1回のシステムコール、あるいは**ポーリング**（割り込みを待たず定期的に状態を確認する方式）でまとめて受け渡します。

#### (2) ユーザから渡される引数への不信と防御（Confused Deputy の防止）

システムコールの境界でOSカーネルが最も警戒すべきなのが、**「ユーザプログラムが渡してくるポインタやサイズ引数をそのまま信用してはならない」**という原則です。

たとえば、悪意ある（またはバグのある）ユーザプロセスが、`write(fd, 0x80000000, 4096)` のように**カーネル空間の秘密データ（他人のパスワードやカーネルの鍵）のアドレス**をバッファポインタとして渡してきたとします。カーネル自身は S-mode で動いているため、もしカーネル自身のアドレス空間のままユーザから渡されたポインタを直接逆参照してファイルへ書き出してしまうと、本来読めないはずのカーネルの秘密をユーザへ漏洩させてしまいます（権限を持つ代理人を騙して悪用する **Confused Deputy 問題**）。

このため、OSカーネルはユーザ空間とのデータ受け渡しに必ず専用の検査付きコピー関数（xv6の `copyin` / `copyout`、Linuxの `copy_from_user` / `copy_to_user`）を使い、「その仮想アドレスが本当にそのユーザプロセス自身の有効なユーザページに属しているか」「アクセス権限（読取り／書込み）を満たしているか」を検証してからコピーする補正を徹底しています。

### 5. 接続と展望（Bridge）：本節の内容が後半のどの部に繋がるか

1. **次節（[3-2節](3-2.md)：プロセスのライフサイクルとシェルの仕組み）：**
    本節でシステムコールの実行メカニズムを押さえたので、次節ではOSが提供する代表的なプロセス制御システムコール群（`fork`, `exec`, `wait`, `exit`）を組み合わせて、普段使うシェル（コマンドインタプリタ）がどう動いているかを組み立てます。

2. **[第3部](../index.md#part-3)（[3-3節](3-3.md)：スケジューリングとコンテクストスイッチ）：**
    本節の実験Bで触れた**タイマ割り込み**をきっかけに、OSが実行中のプロセスからCPUを強制的に取り上げて別のプロセスへ切り替える（プリエンプティブ・マルチタスキング）仕組みへ進みます。

3. **[第3部](../index.md#part-3)（[3-6節](3-6.md)：トラップ処理の実装と空間切替）：**
    本節では `ecall` から `sret` までの流れを概念レベルで追いました。[3-5節](3-5.md)で仮想記憶（多段ページテーブル）を学んだあと、[3-6節](3-6.md)では「ページテーブルが切り替わる瞬間にどうやって安全にカーネルへ飛び込むか（`trampoline` と `trapframe`）」の低レベル実装へ踏み込みます。

4. **[第5部](../index.md#part-5)（[5-1](../5/5-1.md)・[5-2節](../5/5-2.md)：デバイス割り込みとバッファリング）：**
    外部デバイスからの非同期割り込みを統括する割り込みコントローラ（PLIC）の仕組み（[5-1節](../5/5-1.md)）や、システムコール回数を減らす標準I/Oのバッファリング（[5-2節](../5/5-2.md)）へ直結します。

### 理解度チェック（次節へ進む前の確認）

本節の特権モード・`sepc` の扱い・システムコールのコストと境界防御を確認し、次節（[3-2節](3-2.md)）へ繋ぐ問いを置きます。

> **【確認の問い】**
>
> 1. **（`sepc` 更新の違いとシステムコール境界のセキュリティ診断）**
>     次の2点について簡潔に説明してください。
>
>     * (a) システムコール（`ecall`）の処理後にカーネルが `sepc += 4` を行うのに対し、タイマ割り込みや修復可能な例外（ページフォルト等）の復帰時に `sepc` へ `4` を加えてはならないのはなぜでしょうか。
>     * (b) カーネルのシステムコール実装において、① `syscalls[a7]()` を呼び出す前の範囲検査（`num > 0 && num < NELEM(syscalls)`）を省いた場合と、② `copyin` を介さずにカーネル自身のアドレス空間のままユーザ提供ポインタを直接逆参照した場合に、それぞれどのようなセキュリティ上の問題が生じるでしょうか。
>
> 2. **（システムコールのコスト比較と `vDSO` の適用条件）**
>     通常の関数呼び出しのコストを $5\text{ ns}$、システムコール1回のモード切替コストを $500\text{ ns}$ と仮定します（実際のデータ転送時間は無視します）。
>
>     * (a) $4\text{ KiB}$（$4096\text{ B}$）のデータを、①1バイトずつ `write` システムコールで書き出した場合と、②1バイトずつ通常の関数呼び出しでユーザ空間バッファへ書き込み、最後に1回だけ `write` システムコールで一括出力した場合のそれぞれの合計時間を計算し、比較してください。
>     * (b) 時刻取得（`clock_gettime`）は `vDSO` によってシステムコールを省けますが、ファイル書込み（`write`）は `vDSO` 化できません。この違いが生じる理由を権限と保護の観点から説明してください。
>
> 3. **（保護境界から考える複数コマンドの起動と制御）**
>     本節で見た特権モードとトラップ機構により、すでに動作中の1つのプロセスがOSへ処理を依頼して安全に動く土台が整いました。では、端末上で動作するシェルが別のコマンド（例：`ls` や `gcc`）を起動して実行し、その完了後にシェル自身へ制御を戻すとき、なぜ「現在のシェルプロセスの中でコマンドを直接関数呼び出しする」だけでは不十分であり、OS側にどのような空間の複製・切替・待機機能が必要になるでしょうか。
