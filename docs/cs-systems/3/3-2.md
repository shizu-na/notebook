### 前節（3-1）の確認問題の解答

前節の最後に提示した3つの問いの解答を確認します。問3がそのまま本節（プロセスのライフサイクルとシェルの仕組み）の導入になります。

1. **`sepc` 更新の違いとシステムコール境界のセキュリティ診断：**

    * **(a) `ecall` では `sepc += 4` するのに割り込み・例外で `+4` してはいけない理由：**
        `ecall` はカーネルがシステムコール処理を代行し終えたため、同じ `ecall` を再実行して無限ループになるのを防ぐ目的で `sepc + 4`（次の命令）へ進めます。一方、タイマ割り込みや修復可能な例外（ページフォルト等）では、`sepc` が指す元の命令はまだ完了せずに中断された状態であるため、`+4` するとその1命令が丸ごと飛ばされてプログラムの計算結果が壊れてしまいます。

    * **(b) システムコール実装における2つのセキュリティ上の問題：**
        ① `syscalls[a7]()` の範囲検査を省くと、ユーザが負数や配列外の大きな番号を `a7` へ渡した際にカーネルが関数ポインタ配列の領域外を読み出し、意図しないアドレスへ S-mode のままジャンプしてクラッシュや任意コード実行を引き起こします。② `copyin` を使わずにカーネル自身のアドレス空間のままユーザ提供ポインタを直接逆参照すると、悪意あるユーザがカーネル領域の秘密データのアドレスを渡すことで、特権を持つカーネルに秘密を読み出させてしまう Confused Deputy 問題が生じます。

2. **システムコールのコスト比較と `vDSO` の適用条件：**

    * **(a) $4\text{ KiB}$（$4096\text{ B}$）出力時の合計時間比較：**

        * ① 1バイトずつ `write` システムコールを発行した場合：$4096 \times 500\text{ ns} = 2{,}048{,}000\text{ ns} = \mathbf{2.048\text{ ms}}$ です。
        * ② 1バイトずつ関数呼び出し（$5\text{ ns}$）でユーザ空間バッファへ書き込み、最後に1回だけ `write` を発行した場合：$4096 \times 5\text{ ns} + 1 \times 500\text{ ns} = 20{,}480 + 500 = \mathbf{20{,}980\text{ ns}}$（約 $0.021\text{ ms}$）です。
        * 比較すると、ユーザ空間バッファリングを挟むことで合計時間は約 **98 倍**（モード切替コスト単体では 4,096 倍）短縮されます。

    * **(b) `clock_gettime` は `vDSO` 化でき、`write` はできない理由：**
        時刻取得はカーネルが更新する読取り専用ページをユーザ空間から参照するだけで完結し、権限検査や状態変更を伴わないため `vDSO` で安全に回避できます。一方、`write` は他プロセスと共有するファイルシステムや出力デバイスへ変更を加える操作であり、ファイル記述子の正当性やアクセス権限の検証、排他制御を S-mode のカーネル側で強制する必要があるため `vDSO` 化できません。

3. **保護境界から考える複数コマンドの起動と制御（本節への接続）：**
    現在のシェルプロセス内で別コマンドを直接呼び出すと、コマンドとシェルが同じメモリ空間を共有してしまい、コマンド側のバグや強制終了がシェル本体まで巻き添えにするうえ、シェル自身のコードや変数を別の実行ファイルへ差し替えることもできません。したがって OS 側には、独立したメモリ空間を持つ新プロセスを生成し、別プログラムへ入れ替え、終了まで親が待機できる仕組み（UNIX 系の `fork`・`exec`・`wait`・`exit`）が必要になります。

## 3-2. プロセスのライフサイクル（`fork`・`exec`・`wait`）とシェルの仕組み

### 1. 動機（Why）：なぜ「プロセスを作る」と「別プログラムを実行する」をわざわざ2つに分けたのか

前節（[3-1節](3-1.md)）では、OSがCPUの特権モードとトラップを用いてアプリケーションを隔離し、システムコールという安全な窓口を提供していることを確認しました。

では、私たちが端末（シェル）に `ls` や `gcc` と打ち込んだとき、OSはどのようにして新しいプログラムを起動するのでしょうか。素朴に考えれば、「`create_process("ls", args, stdin, stdout, ...)` のような1つの万能システムコールを用意すれば分かりやすいのではないか」と思えるかもしれません。

ところが、UNIX系OS（Linux、macOS、xv6 等）の設計者たちはあえてその道を選ばず、プログラムの起動を次の **2つの独立したシステムコール** へ分離しました。

1. **`fork()`：** 呼び出したプロセスと**まったく同じ中身を持つ分身（子プロセス）**をもう1つ複製します。
2. **`exec(path, argv)`：** 現在のプロセスの中身（コード・データ・スタック）を、**指定された別プログラム（ELFファイル）で丸ごと上書き**して最初から実行します。

一見すると、「どうせ直後に `ls` で上書きしてしまうのに、わざわざシェルの分身を作るのは二度手間ではないか」と感じるかもしれません。しかし、この **「`fork` と `exec` の分離」** こそが、UNIXのシェルがわずか数十行のコードで入出力リダイレクト（`ls > out.txt`）やパイプ（`ls | grep foo`）、作業ディレクトリ変更、環境変数設定をすべて自在にこなせる最大の理由です。

本節では、OSが管理する「プロセス」という抽象化の実体と状態遷移を押さえたうえで、`fork`・`exec`・`wait`・`exit` の4大システムコールとシェルの動作原理を1ステップずつ解き明かします。

---

### 2. 具体例と動作イメージ（Toy Model）

データ構造の整理に入る前に、UNIXのプロセス制御を象徴する2つの小さな実験を辿ってみます。

#### 実験A：1回呼ぶと「2回返ってくる」不思議なシステムコール `fork()`

次の短いCプログラムを実行すると、画面には何が表示されるでしょうか。

```c
int pid = fork();
if (pid > 0) {
    // 親プロセス側：fork() の戻り値は「生まれた子プロセスの PID」
    printf("parent: child=%d\n", pid);
    pid = wait(0);   // 引数 0 (NULL) は子の終了ステータスを受け取らず破棄する指定
    printf("child %d is done\n", pid);
} else if (pid == 0) {
    // 子プロセス側：fork() の戻り値は「0」
    printf("child: exiting\n");
    exit(0);
} else {
    printf("fork error\n");
}
```

プログラムが `fork()` を1回呼び出した瞬間、OSカーネルは現在のプロセス（親）のメモリ空間とレジスタを丸ごと複製し、新しいプロセス（子）を1つ増やします。そして、**親と子の両方が `fork()` の直後の行から別々に動き出します**。

このとき、親と子が「自分が親なのか子なのか」を見分けるための唯一の目印が、`fork()` の戻り値（RISC-V では `a0` レジスタ）の違いです。

* **親プロセスへ返る値：** 新しく生まれた子プロセスの識別番号（**PID**：正の整数、たとえば `4`）です。
* **子プロセスへ返る値：** **`0`** です。

これによって、親は `if (pid > 0)` の側へ進み、`wait(0)`（引数 `0` は終了ステータスを破棄する指定）を呼んで子が終了するまで待機します。一方、子は `else if (pid == 0)` の側へ進み、自分の仕事をして `exit(0)` で終了します。ここで重要な点として、`parent: child=4` と `child: exiting` の**出力順序は非決定的**であり、OS のスケジューリング次第でどちらが先に出てもおかしくありません。これに対し、親の `wait(0)` は子が `exit(0)` を終えるまで返らないため、**`child 4 is done` は必ず `child: exiting` より後に出力されます**。

#### 実験B：シェルが `ls > out.txt` を実行する4ステップ

次に、シェルに `ls > out.txt`（`ls` の出力を画面ではなくファイル `out.txt` へ書き出すリダイレクト）と入力したときの動きを追ってみます。

1. **複製（`fork`）：** シェル（親）が `fork()` を呼び、シェルの分身（子）を作ります。この時点では親も子も標準出力（ファイル記述子 `1`）は画面に繋がっています。
2. **隙間の環境調整（子プロセスだけ）：** 子プロセスは `exec` を呼ぶ**直前の隙間**で、`close(1)` して画面との接続を切り、`open("out.txt", O_WRONLY | O_CREATE | O_TRUNC)`（`O_TRUNC` は既存ファイルの中身を空にして上書きするフラグ）を呼びます。OSは空いている最小の番号を自動で割り当てるため（詳細は3-(4)）、ファイル記述子 `1` が `out.txt` へ繋ぎ替わります。**親シェル側の標準出力は画面のまま一切汚れません。**
3. **置換（`exec`）：** 子プロセスが `exec("ls", argv)` を呼びます。子プロセスのメモリは `ls` のELFバイナリで丸ごと置き換わりますが、**ファイル記述子テーブル（`1` が `out.txt` を指している状態）だけはそのまま引き継がれます**。
4. **実行と回収（`wait`）：** `ls` はリダイレクトされていることすら知らずに普通に標準出力（`1`）へ書き出し、終わると `exit(0)` します。親シェルは `wait(0)` で完了を受け取り、次のプロンプト `$ ` を表示します。

もし `fork` と `exec` が1つに合体していたら、リダイレクトやパイプや作業ディレクトリ変更のすべてを巨大なシステムコールの引数オプションとしてOSカーネル側へ押し込まなければならなかったはずです。2つに分離したことで、**子プロセス自身の通常のCコードで自由に環境を整えてから `exec` へ飛び込める**という簡潔で拡張性の高い設計が生まれました。

### 3. 構造・アルゴリズム・実装（What）

#### (1) プロセスの正体：プログラムとの違いと PCB（`struct proc`）

まず、よく混同される **プログラム（Program）** と **プロセス（Process）** の違いを明確にします。

* **プログラム：** ディスク上に置かれた静的なファイル（ELFバイナリ：[1-4節](../1/1-4.md)）そのものです。
* **プロセス：** プログラムがメモリへ読み込まれて**実行中にある動的な実体**です。同じプログラム `ls` を2つの端末で同時に起動すれば、プログラムは1つでもプロセスは独立して2つ存在します。

OSカーネルの内部では、1つのプロセスを管理するための構造体（**PCB：Process Control Block**、xv6では `struct proc`、Linuxでは `task_struct`）がプロセス配列として保持されています。PCBには主に次の情報が格納されます。

| PCB（`struct proc`）の主なフィールド | 役割 |
| :--- | :--- |
| **識別子（`pid`, `parent`）** | プロセスID（一意な整数）と、親プロセスへのポインタ |
| **状態（`state`）** | 現在の実行状態（`UNUSED`, `USED`, `RUNNABLE`, `RUNNING`, `SLEEPING`, `ZOMBIE`） |
| **仮想アドレス空間（`pagetable`, `sz`）** | このプロセス専用のメモリ地図（ページテーブル：[3-5節](3-5.md)）とサイズ |
| **レジスタ退避領域（`trapframe`, `context`）** | ユーザ実行中の全レジスタ退避枠と、カーネル切替用の退避枠（[3-3](3-3.md)・[3-6節](3-6.md)） |
| **カーネルスタック（`kstack`）** | このプロセスがシステムコールや割り込みで S-mode に入ったときに使う専用スタック |
| **開いているファイル一覧（`ofile[]`）** | ファイル記述子（FD：`0`=標準入力, `1`=標準出力, `2`=標準エラー等）の配列 |
| **終了情報（`xstate`, `killed`）** | `exit(status)` で渡された終了ステータスと、強制終了フラグ |

ここで重要なのが、**各プロセスは「ユーザスタック」とは別に、自分専用の「カーネルスタック（`kstack`）」を持っている**点です。ユーザスタックは U-mode のアプリが自由に書き換えられるため、S-mode のカーネルがそこに自分の戻り番地や局所変数を置くのは危険です。また、プロセスAがディスクI/O待ちでカーネル内部で眠っているあいだに、プロセスBが別のシステムコールでカーネルへ入ってくることもあるため、プロセスごとに独立したカーネルスタックが不可欠になります。

* **`RUNNABLE`（実行可能）：** 実行準備はできているものの、今は他のプロセスがCPUを使っているため順番待ちをしている状態です。
* **`RUNNING`（実行中）：** 今まさにCPUコア上で命令を実行している状態です。タイマ割り込みなどで時間枠が切れると `RUNNABLE` へ戻ります（[3-3節](3-3.md)）。
* **`SLEEPING`（待機中／ブロック）：** ディスク読出しやキーボード入力、子プロセスの終了（`wait`）などのイベントを待っている状態です。CPUを無駄に消費しないようスケジューラの対象から外れ、イベント完了時に `RUNNABLE` へ起こされます。
* **`ZOMBIE`（終了済み・未回収）：** `exit()` で処理を終え、親プロセスが `wait()` で終了ステータスを受け取るのを待っている状態です。なお、ユーザ空間メモリの解放タイミングは OS によって異なり、Linux などの実用 OS では `exit()` 時点でユーザメモリを解放して PCB のみ残すのに対し、教育用 OS の xv6 では実装を簡潔にするため親の `wait()` 内の `freeproc()` でユーザメモリと PCB を一括解放して `UNUSED` へ戻します。

#### (3) 4大システムコール（`fork`・`exec`・`wait`・`exit`）の内部動作

実験A・Bで触れた4つのシステムコールが、カーネル内部でPCBとメモリをどう操作するかを整理します（図3-2-2）。

1. **`fork()`（複製）：**

    * 未使用のPCBスロットを1つ確保（`UNUSED` → `USED`）し、新しいPIDを割り当て、`parent` に親プロセスを記録します。
    * 親のユーザ仮想メモリ空間（コード・データ・ヒープ・スタック）の内容を、子プロセス用の新しいメモリ領域へ複製します。
    * 親のレジスタ退避枠（`trapframe`）をそのまま子へコピーし、**子側の戻り値レジスタ `a0` だけを `0` に書き換えます**（親側の `a0` には子のPIDが入ります）。
    * 親が開いているファイル記述子テーブル（`ofile[]`）を子へコピーし、ファイルの参照カウントを増やします。
    * 子の状態を `RUNNABLE` にして完了します。

2. **`exec(path, argv)`（プログラム置換）：**

    * パス `path` で指定されたELF実行ファイルをディスクから開き、ELFヘッダとプログラムヘッダ（[1-4節](../1/1-4.md)）を検証します。
    * 新しい仮想アドレス空間を用意し、ELFの `.text` / `.data` セクションを読み込み、新しいユーザスタックを確保して引数文字列 `argv` をスタック上へ積みます。
    * 現在のプロセスの古い仮想アドレス空間を破棄して新しい空間へ差し替え、プログラムカウンタ `sepc` をELFのエントリポイントへ、スタックポインタ `sp` を新スタックへ設定します。
    * **成功した場合、`exec` は元のプログラムへ二度と戻りません**（新しいプログラムの `main` から実行が始まります）。失敗した場合（ファイルが存在しない等）だけ `-1` を返して元のプログラムへ戻ります。なお、**PID と開いているファイル記述子テーブルはそのまま維持されます**。

3. **`exit(status)`（終了）：**

    * 開いているファイルをすべて閉じ、終了ステータス `status` を自身の `xstate` へ記録します（Linux ではこの時点でユーザ空間メモリも解放します）。
    * もし自分にまだ生きている子プロセスが残っていれば、それらの親を `init`（PID 1）へ付け替えます。
    * 親プロセスが `wait()` で眠っているかもしれないので親を起こし（`wakeup`）、自身の状態を **`ZOMBIE`** にしてスケジューラへCPUを明け渡します（二度と戻りません）。

4. **`wait(&status)`（待機と回収）：**

    * 自分の子プロセスの中に `ZOMBIE` 状態のものがいないか探します。
    * 見つかれば、子の `xstate` を引数ポインタ先へコピーし（引数が `0` の場合は破棄）、子の残存資源（xv6 ではユーザメモリを含む `freeproc()` 全体、Linux では PCB 等）を解放して `UNUSED` へ戻し、子のPIDを返します。
    * まだ全子が実行中であれば、親自身を `SLEEPING` 状態にして眠り、子が `exit()` で起こしてくれるのを待ちます。子が1つも存在しなければ即座に `-1` を返します。

#### (4) シェルの仕組み：ユーザプログラムとしてのコマンドインタプリタ

多くの人が誤解しやすい点ですが、**シェル（`sh`、`bash`、`zsh` 等）はOSカーネルの一部ではなく、単なる普通のユーザプログラム（U-mode）** です。シェルは、まさに上で見た `fork`, `exec`, `wait`, `open`, `close` などのシステムコールを組み合わせた、次のような簡潔なループとして実装されています。

```c
while (getcmd(buf, sizeof(buf)) >= 0) {
    // 例外：cd（作業ディレクトリ変更）だけは親シェル自身で実行する
    if (buf[0] == 'c' && buf[1] == 'd' && buf[2] == ' ') {
        chdir(buf + 3);
        continue;
    }
    if (fork() == 0) {
        runcmd(parsecmd(buf));  // 子プロセス：リダイレクト設定後に exec
    }
    wait(0);                    // 親シェル：コマンド完了まで待機
}
```

ここで注目すべき細部が **`cd`（ディレクトリ変更）コマンド** です。`ls` や `grep` と違って、`cd` は子プロセスの中で `exec` してはなりません。もし子プロセスの中で `chdir()` を呼んでも、子プロセスが終了した瞬間にその変更は消えてしまい、**親シェルのカレントディレクトリが元のまま変わらない**からです。そのため `cd` や `exit` のようなコマンドは、外部実行ファイルではなくシェルの **組み込みコマンド（Built-in Command）** として親プロセス自身が直接システムコールを実行します。

さらに、リダイレクト（`ls > out.txt`）が動く仕組みは、OSが新しいファイルを開くときの「**現在空いている最小のファイル記述子番号を割り当てる**」という単純な規則に基づいています（図3-2-3）。子プロセスが `close(1)` で1番を空けた直後に `open("out.txt", ...)` を呼べば、必ず空いたばかりの **1番（標準出力）** が `out.txt` へ割り当てられます。しかも、各プロセスの FD テーブルは独立しているため、子プロセスが自分の FD 1 を差し替えても、親シェルの FD テーブルとカーネル内のオープンファイル構造体の参照関係には影響しません。

> **【コラム：ゾンビプロセスと孤児プロセス：なぜ `init`（PID 1）が必要なのか】**
>
> すべてのプロセスは親プロセスから `fork()` によって生まれ、プロセス全体の親子関係は1本の木構造（プロセスツリー）をなします。その根（ルート）にいるのが、OS起動時にカーネルが最初に生み出す **`init` プロセス（PID 1）** です。
>
> 親子関係が崩れたとき、OSには2つの特殊な状態が生じます。
>
> * **ゾンビプロセス（Zombie Process）：** 子プロセスが先に `exit()` で終了したのに、親プロセスがまだ `wait()` を呼んで回収していない状態です。実行自体は終わっていますが（Linux ではユーザメモリも解放済み、xv6 では `wait()` 時の `freeproc()` まで保持）、「終了ステータス（`xstate`）とPID」を親へ伝えるために **PCBの1スロット** が `ZOMBIE` 状態のまま残ります。すでに実行を終えているため `kill -9` を送っても消えず、親が `wait()` するか、親自身が終了して `init` に引き取られることで消滅します。
> * **孤児プロセス（Orphan Process）：** 逆に、子プロセスがまだ動いているのに親プロセスが先に `exit()` で終了してしまった状態です。親がいなくなると、将来その子が終了したときに誰も `wait()` で回収できなくなってしまいます。そこでOSは、親の `exit()` 処理の中で**残された子プロセスの親ポインタをすべて `init`（PID 1）へ付け替えます（reparent）**。`init` は無限ループで常に `wait()` を呼び続けているため、孤児になったプロセスが終了しても確実に回収され、システムに未回収の PCB が残らない仕組みになっています。

### 4. 限界と補正（Critique & Adaptation）

`fork` と `exec` の分離は UNIX の柔軟な設計基盤ですが、大規模なシステムやセキュリティ、標準ライブラリの利用においては次の3つの限界と補正が重要になります。

#### (1) 素朴な `fork()` のメモリコピー浪費と Copy-on-Write（CoW）・`posix_spawn`

もし親プロセスがWebブラウザや大規模なデータベースのように **4 GiB ものメモリ** を使っているとき、小さな補助コマンド（たとえば数 KiB の `date`）を起動するためだけに `fork()` → `exec()` を実行すると何が起きるでしょうか。

素朴な `fork()` の実装（xv6の初期実装等）では、親の4 GiBの物理メモリを子へ丸ごとコピーします。ところが子プロセスはその直後に `exec("date")` を呼んで、コピーしたばかりの4 GiBをほとんど使わずに全部捨ててしまいます。これは時間と物理メモリの大きな浪費です。

この限界に対するOSの代表的な補正が2つあります。

1. **Copy-on-Write（CoW：書き込み時コピー）：** 現代のLinuxやmacOSの `fork()` は、実行時点では物理メモリをコピーしません。親と子で同じ物理ページを読み取り専用として**共有**させておき、どちらかが実際にページへ書き込もうとした瞬間だけハードウェア例外（ページフォルト）を起こしてその1ページだけを複製します（実装の詳細は[3-7節](3-7.md)で扱います）。これにより、直後に `exec()` する場合はコピーコストがほぼゼロになります。
2. **`posix_spawn()`：** 同一プロセス内でメモリ空間を共有する実行単位である**スレッド**（[3-3節](3-3.md)コラム）が複数動くプログラムの中で `fork()` を呼ぶと、「他スレッドが排他制御用の**ロック**（[第4部](../index.md#part-4)）を握ったまま複製され、誰も解放できず永久停止する（**デッドロック**）」という難題が生じます。また、仮想記憶を持たない組込みOSでは `fork()` 自体が困難です。そのため現代のPOSIXでは、一般的な外部コマンド起動をより安全かつ高速に行える統合API **`posix_spawn()`**（および内部的に親のメモリを複製せず子の `exec` まで親を停止させる軽量版 `vfork`）も併用されます。

#### (2) ゾンビの蓄積・フォークボム（Fork Bomb）と資源上限（`rlimit`）

OSが管理できるプロセス数（PCB配列のサイズやPIDの上限）は有限です。もし長時間動き続けるサーバプログラムが `fork()` した子プロセスに対して `wait()` を呼び忘れると、`ZOMBIE` 状態のPCBスロットが際限なく溜まり、やがてシステム全体で新しいプロセスを1つも作れなくなります。

また、悪意ある（あるいはバグのある）プログラムが `while (1) fork();` を実行すると、プロセス数が $1 \to 2 \to 4 \to 8 \to \dots$ と指数関数的に増殖し、数秒でシステムのプロセス枠とメモリを食い尽くして停止させてしまいます（**フォークボム：Fork Bomb**）。

これらに対する実システム上の補正は次の2点です。

* **非同期回収（`SIGCHLD`）：** サーバのように親が `wait()` でブロックして止まるわけにはいかないプログラムでは、子が終了したときにOSから親へ届く非同期通知（**シグナル** `SIGCHLD`：[4-7節](../4/4-7.md)）を契機にノンブロッキングの `waitpid(-1, &status, WNOHANG)` を呼んでゾンビを確実に回収します。
* **ユーザ・コンテナごとのプロセス数制限：** LinuxなどのOSは、ユーザ単位の資源制限（`RLIMIT_NPROC` / `ulimit -u`）や、隔離実行環境である**コンテナ**単位の資源制限機構（**cgroups** の `pids.max`）をカーネル側で強制し、1つの暴走プログラムがシステム全体のPCB枠を枯渇させるのを防ぎます。

#### (3) `fork()` 直前のユーザ空間バッファ未フラッシュによる出力重複

[3-1節](3-1.md) 4-(1) で見た通り、C標準ライブラリ（`stdio.h` の `printf` 等）はシステムコール回数を減らすために出力データを**ユーザ空間メモリ内のバッファ**へ一時的に溜め込みます。もし `printf("hello");` のように改行がないまま、あるいは出力先がファイルやパイプ（完全バッファリング）でまだ `write` システムコールが発行されていない状態で `fork()` を呼ぶと、**未出力の `"hello"` が入ったユーザ空間バッファごと子プロセスへ複製**されます。

その結果、親と子がそれぞれ終了時に自分のバッファを書き出した瞬間、本来1回だけ実行したはずの `printf("hello")` が画面やファイルへ **2回重複して出力される** 落とし穴が生じます。これを防ぐには、`fork()` の直前に `fflush(stdout)`（または `fflush(NULL)`）でユーザ空間バッファを明示的に掃き出しておく補正が必要です。

### 理解度チェック（次節へ進む前の確認）

本節の `fork`・`exec`・`wait`・リダイレクト・バッファの挙動を確認し、次節（[3-3節](3-3.md)）へ繋ぐ問いを置きます。

> **【確認の問い】**
>
> 1. **（条件分岐を伴う `fork()` の出力回数と実行順）**
>     次のCプログラムを実行したとき（すべての `fork()` は成功し、標準出力は改行ごとに即座に出力されるものとします）、以下の問いに答えてください。
>
>     ```c
>     if (fork() == 0) {
>         fork();
>         printf("A\n");
>         exit(0);
>     }
>     wait(0);
>     printf("B\n");
>     ```
>
>     * (a) 画面に `"A"` と `"B"` はそれぞれ合計何回出力されるでしょうか。
>     * (b) 実行のタイミングによっては、`"B"` が2回目の `"A"` より先に出力されることがあります。その理由を、親の `wait(0)` が待つ対象と孫プロセスの親子関係から説明してください。
>
> 2. **（シェル実装の誤り診断とゾンビプロセスの挙動）**
>     次の2点に答えてください。
>
>     * (a) シェルが `ls > out.txt` を実装する際、次の2つの誤った実装はそれぞれどのような不具合を引き起こすでしょうか。① `fork()` の**前**に親シェル側で `close(1); open("out.txt", ...);` を実行した場合、② 子プロセスで `exec("ls", argv)` を呼んだ**後**に `close(1); open("out.txt", ...);` を書いた場合。
>     * (b) `ZOMBIE` 状態になったプロセスへ強制終了シグナル（`kill -9`）を送っても消えない理由と、長時間稼働するサーバが `wait()` を呼び忘れたときに起きる障害を説明してください。
>
> 3. **（`fork()` とユーザ空間バッファの落とし穴、および単一 CPU 上の同時実行）**
>     次の2点に答えてください。
>
>     * (a) `printf("hello"); fork();` のように改行なしで出力した直後に `fork()` を呼ぶと、プログラム終了時に `"hello"` が2回出力されることがあるのはなぜでしょうか。また、これを防ぐにはどうすればよいでしょうか。
>     * (b) `fork()` によって複数の `RUNNABLE` なプロセスが同時に存在するようになったとき、単一 CPU コア上でこれらが見かけ上同時に動くようにするには、OS は[3-1節](3-1.md)のタイマ割り込みと本節の状態遷移をどのように組み合わせて実行権を切り替える必要があるでしょうか。
