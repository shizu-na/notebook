### 前節（3-5）の確認問題の解答

前節の最後に提示した3つの問いの解答を確認します。問3がそのまま本節（トラップ処理の実装と空間切替）の導入になります。

1. **Sv39 の仮想アドレス分解と3段ページテーブルの必要枚数：**

    * **(a) 2つの仮想アドレスの `(VPN[2], VPN[1], VPN[0], Offset)` 分解：**

        * `0x0000_0000_0000_1000`：`(VPN[2] = 0, VPN[1] = 0, VPN[0] = 1, Offset = 0x000)` です。
        * `0x0000_003F_FFFF_E000`：下位12ビットが `0x000`、右へ12ビットシフトした `0x3F_FFFFE` を9ビットずつ切り出すと `0x1FE = 510`、`0x1FF = 511`、`0x0FF = 255` となるため、**`(VPN[2] = 255, VPN[1] = 511, VPN[0] = 510, Offset = 0x000)`** です（検算：$255 \times 2^{30} + 511 \times 2^{21} + 510 \times 2^{12} = \texttt{0x3F\_C000\_0000} + \texttt{0x00\_3FE0\_0000} + \texttt{0x00\_001F\_E000} = \texttt{0x3F\_FFFF\_E000}$）。

    * **(b) 必要なページテーブル枚数と総容量、および近接アドレスの場合：**
        根の L2 テーブルは1枚を共有しますが、`VPN[2]` が `0` と `255` で異なるため、L1 テーブルが2枚、L0 テーブルも2枚必要になり、合計 **$1 + 2 + 2 = \mathbf{5\text{ 枚}}$（$5 \times 4\text{ KiB} = \mathbf{20\text{ KiB}}$）** です。一方、2ページ目が `0x0000_0000_0000_2000` であれば `(0, 0, 2, 0x000)` となり、`VPN[2] = 0` と `VPN[1] = 0` が一致して L2・L1 だけでなく**同じ L0 テーブルの隣のエントリを共有できる**ため、合計 $1 + 1 + 1 = \mathbf{3\text{ 枚}}$（$12\text{ KiB}$）だけで済みます。

2. **TLB の実効アクセス時間 EAT と TLB リーチの計算：**

    * **(a) Sv39（$d = 3, t_{\text{TLB}} = 1\text{ ns}, t_{\text{mem}} = 100\text{ ns}$）の EAT：**
        $\text{EAT} = h(t_{\text{TLB}} + t_{\text{mem}}) + (1 - h)(t_{\text{TLB}} + (d + 1)t_{\text{mem}})$ に代入します。

        * $h = 99\%$（$0.99$）：$0.99 \times 101 + 0.01 \times 401 = 99.99 + 4.01 = \mathbf{104\text{ ns}}$ です。
        * $h = 90\%$（$0.90$）：$0.90 \times 101 + 0.10 \times 401 = 90.9 + 40.1 = \mathbf{131\text{ ns}}$ です（ヒット率が 9 ポイント下がるだけで実効アクセス時間が約 26% 悪化します）。

    * **(b) 64エントリ L1 TLB における $64\text{ MiB}$ 配列ランダム参照時の TLB リーチ：**

        * $4\text{ KiB}$ ページ：$64 \times 4\text{ KiB} = \mathbf{256\text{ KiB}}$（$0.25\text{ MiB}$）です。$64\text{ MiB}$ 配列のわずか $1/256$（約 $0.39\%$）しかカバーできないため、ランダムアクセスではほぼ毎回 TLB ミスが発生します。
        * $2\text{ MiB}$ スーパーページ：$64 \times 2\text{ MiB} = \mathbf{128\text{ MiB}}$ です。配列全体（32 ページ分）が余裕をもって TLB に収まり切るため、初回参照以降はほぼ 100% ヒットします。

3. **`satp` 切替時のコード配置条件（本節への接続）：**
    `csrw satp` の直後に CPU がフェッチする仮想アドレス `pc + 4` が、新旧2つのページテーブルで**まったく同じ物理ページ内の次の命令**を指し続けている必要があります。すなわち、切替命令を含むコードページは、ユーザページテーブルとカーネルページテーブルの双方で**同じ仮想アドレスから同じ物理アドレスへマップ**されていなければなりません。この共通の足場が、本節で学ぶ **`TRAMPOLINE` ページ** です。

## 3-6. トラップ処理の実装とカーネル／ユーザ空間の切替

### 1. 動機（Why）：なぜ「ユーザ空間からカーネル空間への扉」の実装がOSで最も繊細なのか

[3-1節](3-1.md)では、ユーザプログラムが `ecall` を実行したりタイマ割り込みが発生したりすると、CPUが S-mode へ昇格してカーネルのトラップハンドラへジャンプする概念を学びました。さらに[3-5節](3-5.md)では、ユーザプロセスとOSカーネルが**互いに異なるページテーブル（`satp`）**で隔離されていることを確認しました。

ここで、この2つを組み合わせて実際のカーネルコードを書こうとすると、OS設計の中で最も繊細な「**3つの同時制約**」に直面します。RISC-Vのハードウェアがトラップ発生時に自動でやってくれるのは、「`sepc`・`scause`・`sstatus` の設定」「S-mode への昇格」「`stvec` へのジャンプ」という最小限の処理だけだからです。

1. **空きレジスタが1本もない：**
    `stvec` へ飛んできた瞬間、31本の汎用レジスタ（`x1`〜`x31`）には**ユーザプログラムが計算途中だった大切な値**がすべて詰まっています。メモリへ退避しようにも、「退避先アドレスを入れる作業用レジスタ」を1本書き換えただけでユーザの値が壊れてしまいます。

2. **まだユーザのページテーブルのままである：**
    ハードウェアは `satp` を自動では切り替えません。そのため、トラップ入口へ飛び込んだ直後は**カーネルのC関数も、カーネルスタックも、まだ仮想アドレス空間に見えていない**状態です。

3. **`satp` を切り替える瞬間に「自分の足元」が消えてはならない：**
    前節の問3で確認した通り、`satp` をカーネル用へ切り替えた次の1命令（`pc + 4`）を安全にフェッチし続けるための仕組みが必要です。

本節では、RISC-V（xv6モデル）が **`sscratch` レジスタ**、**`TRAPFRAME`（プロセス固有の退避枠）**、そして **`TRAMPOLINE`（共通の飛び石ページ）** の3つを組み合わせて、この繊細な空間切替をわずか数十行のアセンブリで破綻なく実装している構造を1命令ずつ追っていきます。

---

### 2. 具体例と動作イメージ（Toy Model）

全体のシーケンスを見る前に、上の難題を解く2つの巧妙な仕掛けを小さな例で確認します。

#### 実験A：空きレジスタ0本から最初の1本を捻り出す `csrrw` 交換トリック

ユーザプログラムの全31本（`x0` 除く）のレジスタに、1本も壊せない値が入っていると想像してください。この状態で「退避先メモリの番地 `TRAPFRAME`」をレジスタ `a0` へ読み込みたいのですが、普通に `li a0, TRAPFRAME` と書くと元の `a0` が消えてしまいます。

そこでRISC-Vは、S-mode専用の1本の予備レジスタ **`sscratch`** と、汎用レジスタとCSRの値を**1命令で同時に入れ替える交換命令 `csrrw`** を用意しています。

1. 事前にカーネルが、ユーザ空間へ戻る直前に `sscratch = TRAPFRAME`（退避先アドレス）を仕込んでおきます。
2. トラップ入口の**最初の1命令目**で **`csrrw a0, sscratch, a0`** を実行します。
3. この1命令の直後、**`a0` には退避先アドレス `TRAPFRAME` が入り、`sscratch` にはユーザの元の `a0` が無傷で避難している**状態になります。
4. あとは `a0` を基準に残り30本（`ra`, `sp`, `gp`, ..., `t6`）を `sd ra, 40(a0)` のように `TRAPFRAME` へすべて退避し、最後に `csrr t0, sscratch; sd t0, 112(a0)` で避難させていた元の `a0` も保存すれば、**31本すべてのレジスタを1ビットも壊さずに退避完了**です。

#### 実験B：橋の途中で地図を取り替える「共通の飛び石（`TRAMPOLINE`）」

次に、`satp` をユーザページテーブルからカーネルページテーブルへ切り替える瞬間を考えます。

トラップ入口の機械語コード（`uservec`）が、仮想アドレスの上限 `MAXVA`（`0x40_0000_0000`）のすぐ下に位置する最上位1ページ（`TRAMPOLINE = MAXVA - PGSIZE = 0x3F_FFFF_F000`）に置かれているとします。そしてOSカーネルは、**すべてのユーザプロセスのページテーブル**と**カーネル自身のページテーブル**の両方で、**まったく同じ仮想アドレス `0x3F_FFFF_F000` が、まったく同じ物理ページ（`uservec` の機械語実体）を指すように**マップしておきます。

すると、CPUが `0x3F_FFFF_F080` 番地で `csrw satp, kernel_satp` を実行した直後、新しいカーネルページテーブルのもとで次の命令 `0x3F_FFFF_F084` をフェッチしても、**物理的にはまったく同じコードページの次の1命令へ綺麗に着地**できます。こうして足元を崩さずにカーネル空間へ移行できるのです。

### 3. 構造・アルゴリズム・実装（What）

#### (1) ユーザ仮想アドレス空間とカーネル仮想アドレス空間の配置

実験Bの仕組みを支えるのが、ユーザ空間とカーネル空間の仮想メモリレイアウト設計です（図3-6-1）。Sv39 の非負アドレス空間の上限は定数 **`MAXVA`**（$2^{38} = \texttt{0x40\_0000\_0000}$）で定義されます。

* **ユーザ仮想アドレス空間（プロセスごとに独立）：**

    * 下位（`0x0` から）：プログラムのコード（`.text`）・データ（`.data`）に続き、1枚の**ガードページ（`V=0`）**と下向きに伸びる1ページ分のユーザスタックが置かれ、その上からヒープ（`sbrk`）が上向きに伸びます（なお Linux などの実用 OS では、ユーザスタックを仮想空間の上端付近へ配置してヒープと向かい合うように伸ばす構成が一般的であり、xv6 の低位固定スタック配置とは異なります）。
    * `MAXVA` 直下の最上位2ページ（全プロセス共通の固定仮想アドレス）：

        1. **`TRAMPOLINE`（`0x3F_FFFF_F000`）：** 空間切替コード（`uservec` / `userret`）を格納します。権限は `R=1, X=1` かつ **`U=0`（カーネル専用）** です。
        2. **`TRAPFRAME`（`0x3F_FFFF_E000`）：** このプロセス固有の31レジスタ退避枠とカーネル復帰情報を格納します。権限は `R=1, W=1` かつ **`U=0`（カーネル専用）** です。

* **カーネル仮想アドレス空間（カーネル全体で1つ）：**

    * 物理アドレスと仮想アドレスを1対1で一致させる **直接マッピング（Direct Mapping）** を採用し、カーネルのコード・データ・物理RAM全体・I/Oデバイス（UART, VirtIO, PLIC 等）をそのまま参照できるようにします。
    * 上位に各プロセス専用の **カーネルスタック（`kstack`）** を、互いに1枚ずつ未使用の **ガードページ（`V=0`）** を挟んで配置します。
    * 最上位ページ（`0x3F_FFFF_F000`）には、ユーザ空間と**まったく同じ仮想アドレス**に **`TRAMPOLINE`** をマップします。

ここで注目すべきセキュリティ設計が、**ユーザページテーブルに載っている `TRAMPOLINE` と `TRAPFRAME` の両方に `U=0`（ユーザアクセス禁止）が設定されている**点です。U-mode で動いているユーザプログラムは、たとえ `TRAMPOLINE` や `TRAPFRAME` の仮想アドレスを知っていても読み書き・実行がMMUによって即座に拒否されます。一方、トラップが起きてCPUが **S-mode へ昇格した瞬間** から、同じユーザページテーブルのまま `TRAMPOLINE` の実行と `TRAPFRAME` への退避が可能になるのです。

#### (2) ユーザ空間 → カーネル空間（`uservec` → `usertrap`）の完全な流れ

`ecall`・例外・割り込みが U-mode で発生してから、C言語のトラップ処理関数 `usertrap()` が動き出すまでの全ステップを辿ります（図3-6-2）。

1. **ハードウェア遷移：** CPUが `sepc ← pc`、`scause ← 原因`、`sstatus` 更新（割り込み禁止＋S-mode昇格）を行い、`stvec` に登録された `TRAMPOLINE` 上の **`uservec`** へジャンプします。
2. **レジスタ全退避（`uservec` 前半）：**

    * `csrrw a0, sscratch, a0` で `a0` に `TRAPFRAME` のアドレスを得つつ元の `a0` を `sscratch` へ避難させます。
    * ユーザの全31汎用レジスタ（避難させた元の `a0` を含む）を `TRAPFRAME`（固定オフセット）へ保存します。

3. **カーネル環境への切替（`uservec` 後半）：**
    `TRAPFRAME` の先頭には、前回の復帰時にカーネルが書き込んでおいたカーネル側の設定値が保存されています。これを読み出して切り替えます。

    * `ld sp, 8(a0)`：スタックポインタをこのプロセス専用の **カーネルスタック（`kstack`）** へ切り替えます。
    * `ld tp, 32(a0)`：現在実行中のCPUコア番号（`hartid`）を復元します。
    * `ld t0, 16(a0)`：C言語関数 `usertrap()` のアドレスを `t0` へ読み込みます。
    * `ld t1, 0(a0)`：カーネルページテーブルの値を `t1` へ読み込み、ページテーブルを切り替えて `usertrap()` へジャンプします。

        ```asm
        sfence.vma zero, zero   # 進行中のメモリアクセス完了とTLB同期
        csrw satp, t1           # ここでカーネルページテーブルへ切替
        sfence.vma zero, zero   # ユーザ側の古いTLBエントリをフラッシュ
        jr t0                   # C言語の usertrap() へジャンプ
        ```

4. **C言語での本体処理（`usertrap`）：**
    ここからは通常のC言語の世界になります。まずカーネル実行中の割り込みに備えて `stvec` をカーネル用ハンドラ（`kernelvec`）へ切り替え、`sepc` を `p->trapframe->epc` へ保存します。続いて `scause` を判定し、システムコール（`8`）なら `epc += 4` して割り込みを許可したうえで `syscall()` を実行し、タイマ割り込みなら `yield()` でコンテクストスイッチ（[3-3節](3-3.md)）を行います。

#### (3) カーネル空間 → ユーザ空間（`usertrapret` → `userret`）の復帰手順

`usertrap()` の仕事が終わると、行き道とちょうど逆順の鏡像操作でユーザ空間へ戻ります。特に **`a0` と `sscratch` の交換手順** には見落としやすい重要ポイントがあります（図3-6-3）。

1. **`usertrapret()`（C言語での準備）：**

    * 復帰準備の途中で割り込みが入って `stvec` 等が不整合になるのを防ぐため、まず割り込みを禁止します（`intr_off()`）。
    * 次にU-modeからトラップが起きたときに備え、`stvec` を `TRAMPOLINE` 上の `uservec` へ戻し、カーネルページテーブル・カーネルスタック・`usertrap` の番地・CPU番号を `p->trapframe` へ書き込んでおきます。
    * `sstatus` レジスタの **SPP ビットを `0`（復帰先は U-mode）**、**SPIE ビットを `1`（`sret` 実行と同時に割り込みを再許可）** に設定し、`sepc` に `p->trapframe->epc` を戻します（`sret` より前に割り込みを許可するとカーネル復帰途中に割り込みが入ってしまうため、`SPIE` を経由して U-mode への降格と原子的に再許可します）。
    * ユーザページテーブルの値 `satp` を引数 `a1`、`TRAPFRAME` を `a0` に渡し、`TRAMPOLINE` 上の **`userret`** へジャンプします。

2. **`userret`（アセンブリでの空間復帰）：**

    * `csrw satp, a1` と `sfence.vma` で、ページテーブルをユーザプロセス用へ戻します（この瞬間も `TRAMPOLINE` 上にいるため安全です）。
    * **更新済み `a0` の `sscratch` への仕込み：** システムコールの戻り値などで更新された新しいユーザの `a0`（`TRAPFRAME` オフセット `112`）を、**`ld t0, 112(a0)`** で取り出して **`csrw sscratch, t0`** によりあらかじめ `sscratch` へ入れておきます（カーネル実行中に別プロセスへ切り替わったり `TRAPFRAME->a0` が書き換わったりしているため、トラップ入口で避難させた古い `sscratch` の値をそのまま戻してはなりません）。
    * **残り30本の復元と最後の交換：** `a0`（`TRAPFRAME`）をベースポインタとして残り30本の汎用レジスタ（`ra`, `sp`, `gp`, ..., `t6`）を復元し、最後に **`csrrw a0, sscratch, a0`** を実行します。この1命令で、`a0` に新しいユーザ `a0`（戻り値等）が復元されると同時に、次回のトラップ入口で使う `TRAPFRAME` のアドレスが `sscratch` へ再び仕込まれます。
    * **`sret`** を実行し、U-mode の元の実行箇所へ帰還します。

#### (4) カーネル実行中のトラップ（`kernelvec` → `kerneltrap`）との違い

システムコール処理の途中など、**すでに S-mode（カーネル空間）で動いている最中**にタイマ割り込みやディスク完了割り込みが発生することもあります。このとき `stvec` は `uservec` ではなく **`kernelvec`** を指しています。

`kernelvec` は `uservec` よりはるかに単純です。なぜなら、すでに S-mode であり、**カーネルページテーブルもカーネルスタックも有効な状態**だからです。そのため `satp` の切替も `TRAMPOLINE` も不要であり、現在のカーネルスタック上へ caller-saved レジスタを退避してC言語の `kerneltrap()` を呼び、終わったら復元して `sret` で元のカーネルコードへ戻るだけで完結します（[3-3節](3-3.md)の `swtch` とは逆に caller-saved レジスタを退避するのは、非同期割り込みがカーネル実行の任意の命令間に割り込むため、呼び出されるC関数 `kerneltrap()` が ABI に従って自由に上書きできる caller-saved レジスタを入口側で保護する必要があるからです。callee-saved レジスタは `kerneltrap()` 側が保存・復元します）。なお、カーネル内で起きるべきでない例外（ヌルポインタ参照等）であれば、システム破損を防ぐため **カーネルパニック** として停止させます。

> **【コラム：なぜカーネルとユーザでページテーブルを分けるのか：Meltdown 脆弱性と KPTI の歴史】**
>
> xv6 のように「ユーザ空間とカーネル空間でページテーブルを完全に分け、システムコールのたびに `satp` を切り替える」設計は安全で分かりやすい反面、`satp` 切替に伴う TLB フラッシュのコストがかかるため、2017年頃までの Linux や Windows、macOS といった実用OSでは別の設計が一般的でした。
>
> 従来の実用OSは、**「ユーザプロセスのページテーブルの上位半分に、カーネル空間全体を `U=0` で常駐マップしておく」**方式をとっていたのです。`U=0` なのでU-modeからは触れないはずであり、しかもシステムコールのたびに `satp` を切り替える必要がないため高速でした。
>
> ところが **2018年に公表された脆弱性（Meltdown）** によって、CPUの投機実行（[0-5節](../0/0-5.md)）において**`U=0` の権限例外が確定するよりも先にカーネルメモリが投機的にロードされ、その値に応じたキャッシュ状態の痕跡（アクセス時間差というサイドチャネル）から秘密データをユーザ空間へ読み出せてしまう**問題が明らかになりました。これに対するOS側の根本的な補正が **KPTI（Kernel Page-Table Isolation）** です。KPTI はまさに本節で学んだ xv6 と同じように、**「ユーザ空間のページテーブルには最小限の `trampoline` 相当だけを残してカーネル本体を取り除き、トラップ入口でページテーブルを切り替える」**構造へと現代のLinuxカーネルを戻したのです。教育用OSの単純明快な分離設計が、最先端のセキュリティ対策とそのまま合致した象徴的な出来事と言えます。

### 4. 限界と補正（Critique & Adaptation）

#### (1) カーネルスタック溢れと「ガードページ（Guard Page）」による早期検知

図3-6-1右に示した通り、各プロセスのカーネルスタック（`kstack`）は有限のサイズしかありません（xv6 ではわずか $4\text{ KiB}$、Linux x86-64 でも通常 $16\text{ KiB}$ 程度です）。ユーザ空間のスタックと違って自動で大きく伸びるわけではないため、もしカーネルコードの中で深い再帰呼び出しや大きな局所配列（例：`char buf[4096];`）を宣言すると、カーネルスタックがあっという間に底を突き抜けます（**カーネルスタックオーバーフロー**）。

もし隣り合うプロセスの `kstack` 同士を隙間なく並べて配置していたら、プロセス0のスタックが溢れた瞬間にプロセス1のカーネルスタックを静かに上書きしてしまい、原因不明のシステム破壊を引き起こします。

この限界に対する仮想記憶を活かした補正が、図3-6-1右の **ガードページ（Guard Page）** です。カーネルスタックのすぐ下（低位アドレス側）に、物理ページを1枚も割り当てていない **`V=0`（無効）の仮想ページ** を1枚挟んでおきます。すると、スタックが1バイトでも底を突き抜けた瞬間にMMUが即座にページフォルト例外を起こし、他のメモリを破壊する前にカーネルパニックで正確に異常を検知できます（同じ仕組みは図3-6-1左の通りユーザスタックの底にも使われます）。

#### (2) ページテーブル分離に伴うデータコピーコスト（`copyin` / `copyout`）

ユーザ空間とカーネル空間のページテーブルを完全に分離すると、セキュリティと隔離性は高まりますが、1つの手間が増えます。たとえばユーザが `write(fd, buf, 100)` を呼んだとき、引数 `buf` は**ユーザ仮想アドレス**です。しかし `sys_write` が動いている時点の `satp` は**カーネルページテーブル**に切り替わっているため、カーネルが `*buf` とそのまま逆参照してもユーザのデータには届きません。

したがってカーネルは、[3-1節](3-1.md)でも触れた専用関数 **`copyin`（ユーザ → カーネル）** および **`copyout`（カーネル → ユーザ）** を通じ、ソフトウェアで対象プロセスのユーザページテーブル（`p->pagetable`）を3段辿って（`walkaddr`）、**`PTE_V == 1` かつ `PTE_U == 1`（さらに書込み時は `PTE_W == 1`）** であることを検証したうえで、対応する物理アドレス（カーネルでは直接マップされている）へコピーします。このソフトウェア・ウォークは少しコストがかかるものの、悪意あるポインタ指定を確実に遮断する安全弁として機能します。

### 5. 接続と展望（Bridge）：本節の内容が後半のどの部に繋がるか

1. **次節（[3-7節](3-7.md)：ページフォルトの応用［遅延割当・デマンドページング・CoW・`mmap`］）：**
    本節では、`usertrap()` がシステムコールと割り込みを処理し、ページフォルトのような例外が起きたらプロセスを終了させる基本形を見ました。次節では、この `usertrap()` のページフォルト処理に「必要な物理ページをその場で確保してPTEを書き換え、`sepc` の命令を再実行させる」仕組みを組み込み、仮想記憶の応用技術へ発展させます。

> **【確認の問い】**
>
> 1. **（トラップ実装の2つのバグ診断）**
>     次の2つの実装ミスが起きたとき、それぞれどのような破綻や異常が生じるかを説明してください。
>
>     * (a) `usertrapret()` で `stvec` を `uservec` に書き換えた直後、まだ S-mode（カーネルページテーブル）で動いている最中に `intr_on()` で割り込みを許可してしまい、そこへタイマ割り込みが入った場合。
>     * (b) `userret` の復帰手順で、`ld t0, 112(a0); csrw sscratch, t0`（`TRAPFRAME` 内の更新済み `a0` を `sscratch` へ移す処理）を省いたまま最後に `csrrw a0, sscratch, a0` を実行した場合、ユーザ空間へ戻る `a0` レジスタには何が入り、システムコールの結果はどうなるでしょうか。
>
> 2. **（`kernelvec` の設計と KPTI による Meltdown 防御）**
>     次の2点に簡潔に答えてください。
>
>     * (a) カーネル実行中の割り込みを受ける `kernelvec` では、なぜ `TRAMPOLINE` や `satp` の切替が不要なのでしょうか。また、[3-3節](3-3.md)の `swtch` とは逆に caller-saved レジスタを退避する理由も説明してください。
>     * (b) KPTI（カーネルページテーブル分離）が Meltdown 攻撃を防げる原理と、それに伴う性能上の代償を説明してください。
>
> 3. **（トラップ復帰手順から考えるページフォルトの修復構造）**
>     ユーザプログラムが未割り当ての仮想アドレス（`V=0`）へアクセスしてページフォルト例外（`scause = 13` または `15`）を起こし、`usertrap()` へ制御が移ったとします。プロセスを強制終了させる代わりに「後から物理ページを用意して処理を続行させる」には、例外時にハードウェアが記録した `stval`（失敗した仮想アドレス）と `sepc`（失敗した命令のアドレス）を使って、`usertrap()` と復帰手順でそれぞれ何を行えばよいでしょうか。
