### 前節（0-7）の確認問題の解答

前節の最後に提示した3つの問いの解答を確認します。これで[第0部](../index.md#part-0)（計算機の土台とハードウェアの制約）が完結し、本節からは[第1部](../index.md#part-1)（機械語・ABI・バイナリとリンク）へ進みます。

1. **8-way キャッシュのアドレス分割と競合ミスの診断（32ビットアドレス・$32\text{ KiB}$・ライン $64\text{ B}$・8-way）：**

    * **(a) 総ライン数・セット数とアドレスのビット分割：**

        * 総ライン数：$\dfrac{32\text{ KiB}}{64\text{ B}} = \dfrac{2^{15}}{2^6} = 2^9 = \mathbf{512\text{ ライン}}$ です。
        * セット数（1セットに8ウェイ）：$\dfrac{512}{8} = \mathbf{64\text{ セット}}\ (= 2^6)$ です。
        * **オフセット：** 1ライン $64\text{ B} = 2^6\text{ B}$ より、**$6$ ビット**（下位ビット `5..0`）です。
        * **インデックス：** $64\text{ セット} = 2^6$ より、**$6$ ビット**（中位ビット `11..6`）です。
        * **タグ：** 残り $32 - 6 - 6 = \mathbf{20\text{ ビット}}$（上位ビット `31..12`、検算：$20 + 6 + 6 = 32$ ビット）です。

    * **(b) `0x1000` と `0x2000` の交互アクセスと競合ミス診断：**
        下位12ビット（オフセット6ビット＋インデックス6ビット）がちょうど $2^{12}\text{ B} = 4\text{ KiB} = \texttt{0x1000}$ に相当するため、両アドレスの分割は次の通りになります。

        * `0x1000`：オフセット `0`、**インデックス `0`**、**タグ `0x00001`** です。
        * `0x2000`：オフセット `0`、**インデックス `0`**、**タグ `0x00002`** です。

        両者は同じセット `0` に入りますが、この 8-way キャッシュではセット `0` に8個の格納枠があるため同時に共存できます。したがって初回の強制ミス（計2回）のあとはすべてヒットし、**競合ミスは起きません（0回）**。
        対照的に、同じ64セット構成の**直接写像キャッシュ（1-way・容量 $4\text{ KiB}$）**ではセット `0` の枠が1個しかないため、`0x1000` と `0x2000` の2種類を交互に読むだけで毎回追い出し合い（競合ミス）が発生します。また、8-way キャッシュであっても `0x1000`〜`0x9000` の**9種類**を循環アクセスするとすべてセット `0` へ集中して8ウェイを超えるため、他の63セットが空いたまま毎回追い出しが連発する競合ミス（スラッシング）が起きます。

2. **2階層 AMAT：ハードウェアの L2 追加 vs ソフトウェアの局所性改善：**

    * **(a) ハードウェア案（L2キャッシュ追加）：**
        まず L1 ミス時に到達する L2 キャッシュの AMAT（L1 から見たミスペナルティ）を求め、再帰式へ代入します。

        $$\text{AMAT}_{\text{L2}} = T_{\text{hit,L2}} + m_{\text{L2}} \times T_{\text{penalty,L2}} = 10 + 0.20 \times 100 = 30\text{ ns}$$

        $$\text{AMAT}_{\text{L1}} = T_{\text{hit,L1}} + m_{\text{L1}} \times \text{AMAT}_{\text{L2}} = 1 + 0.05 \times 30 = 1 + 1.5 = \mathbf{2.5\text{ ns}}$$

    * **(b) ソフトウェア案（L1ミス率を $1\%$ へ改善）：**

        $$\text{AMAT} = 1 + 0.01 \times 100 = 1 + 1.0 = \mathbf{2.0\text{ ns}}$$

        ハードウェア案（L2追加）はミス1回あたりのペナルティを $100\text{ ns} \to 30\text{ ns}$ へ緩和して AMAT を $6.0\text{ ns} \to 2.5\text{ ns}$ に短縮します。一方、ソフトウェア案は L1 ミス率そのものを $5\% \to 1\%$ へ削減することで、追加ハードウェアなしに **`2.0 ns`** と L2 追加を上回る短縮を実現できます（両者を併用すれば $1 + 0.01 \times 30 = 1.3\text{ ns}$ までさらに縮まります）。

3. **False Sharing の MESI 状態遷移診断とパディングによる修正：**

    * **(a) False Sharing の原因と MESI 状態遷移（1往復）：**
        64ビットLP64環境では `c0`（オフセット `0..7`）と `c1`（オフセット `8..15`）が連続して**同一の64バイト・キャッシュライン**に載ります。キャッシュコヒーレンシは64バイトのライン単位で管理されるため、両コアが最初にこのラインを `S`（共有）状態で持っている場面から次の遷移が往復します。

        1. **コア0が `c0` へ書込み：** コア0は共有バス経由で他コアへ無効化（Invalidate）メッセージを送り、コア1のラインを **`S → I`**（無効）へ遷移させてから自身を **`S → M`**（変更済み）にして書き込みます。
        2. **コア1が `c1` へ書込み：** コア1のラインは `I` 状態のためキャッシュミスとなり、書込み用の所有権要求をバスへ送ります。コア0は最新のラインをコア1へ供給して自身を **`M → I`** へ落とし、受け取ったコア1が **`I → M`** へ遷移して `c1` を書き込みます。

        ループ内で両コアが更新を繰り返すたびに無効化とライン転送（キャッシュライン・ピンポン）が往復し続けるため、論理的には独立した変数であっても著しい性能劣化（**False Sharing**）が生じます。

    * **(b) `_Alignas(64)` による修正例と解消される理由：**
        [0-2節](../0/0-2.md)のアラインメント制御を用い、2つのメンバを別々の64バイト・キャッシュラインへ分離します。

        ```c
        struct Counter {
            _Alignas(64) long c0;  // オフセット 0..7（1本目の64Bライン）
            _Alignas(64) long c1;  // オフセット 64..71（2本目の64Bライン）
        };
        ```

        （構造体先頭が64バイト整列する前提で `long c0; char pad[56]; long c1;` と明示パディングを入れても分離できますが、`_Alignas(64)` なら構造体全体のアラインメントも64バイト・全体サイズ128バイトへ揃うため配列化しても安全です。）
        `c0` と `c1` が異なるキャッシュラインへ分離されることで、コア0は `c0` のラインを、コア1は `c1` のラインをそれぞれ単独で `E → M` のまま保持し続けられるようになり、無効化やライン往復が消えて False Sharing が解消されます。

## 1-1. ISAの設計思想（RISC vs CISC）と2つのアーキテクチャの対応

### 1. 動機（Why）：なぜハードウェアとソフトウェアの間に「契約（ISA）」を挟み、2つの流派が生まれたのか

[第0部](../index.md#part-0)では、論理ゲートから5段パイプライン、CPUキャッシュに至るハードウェアの内部構造を追ってきました。しかし、私たちがC言語で書いたプログラムをコンパイルして作った実行ファイルは、5年前に買ったPCでも、最新世代のパイプラインや巨大なキャッシュを搭載したPCでも、同じようにそのまま動作します。

これが可能なのは、ハードウェアの内部実装（**マイクロアーキテクチャ**）と、ソフトウェアから見える命令・レジスタの仕様（**ISA：Instruction Set Architecture／命令セットアーキテクチャ**）が明確に分離されているためです。ISAは「このビット列の命令を渡せば、CPUは必ずこのレジスタやメモリをこう更新する」という**ハードウェアとソフトウェアの間の契約書**に相当します（図1-1-1）。契約（ISA）さえ守っていれば、ハードウェア設計者はパイプラインの段数を変えたりアウトオブオーダ実行を導入したりと内部を自由に高速化でき、逆にソフトウェア側は既存のバイナリ資産をそのまま動かし続けられます。

では、その「契約（ISA）」自体はどのように設計すべきでしょうか。コンピュータの歴史の中で、ISAの設計思想は大きく2つの対照的な流派に分かれました。

1. **CISC（Complex Instruction Set Computer）：** 1つの命令に複雑な処理を詰め込み、少ない命令数（小さいコードサイズ）でプログラムを書けるようにする思想です。代表例が **x86-64** です。
2. **RISC（Reduced Instruction Set Computer）：** 命令を少数・単純・固定長に絞り、ハードウェアのデコードとパイプライン実行を単純化する思想です。代表例が **RISC-V** や ARM です。

本ノートでは、構成の見通しがよい **RISC-V** を[第0部](../index.md#part-0)（CPU）と第3〜5部（OS）の具体例に用い、現実のLinuxバイナリやCISCならではの工夫が見えやすい **x86-64** を[第1部](../index.md#part-1)（ABI・バイナリ）と[第2部](../index.md#part-2)（コンパイラ）に用います。本節では、両者の設計思想の違いとレジスタ・命令の対応関係を最初に整理し、以降の章を行き来するための共通の地図を作ります。

### 2. 具体例と動作イメージ（Toy Model）

RISCとCISCの思想の違いは、1行のC言語の計算を機械語へ翻訳して並べるだけでよく見えます。

#### 実験A：メモリ上の変数に `5` を足す（`mem[addr] += 5`）

メモリのある番地に置かれた64ビット整数へ `5` を足して書き戻す処理（たとえばC言語の `*p += 5;`）を、RISC-V（64ビット基本整数命令セット：**RV64I**）と **x86-64** で比べてみます。

ここで最初に、両者のアセンブリ表記の最小限の読み方だけ確認しておきます（レジスタの完全な対応表と記法の詳細は第3節で整理します）。

* **RISC-V（RV64I）：** [第0部](../index.md#part-0)では32ビット版（RV32I）の `lw`/`sw` と番号名 `x0`〜`x31` を使いましたが、64ビット版の **RV64I** では8バイトの読み書きに `ld`（Load Doubleword）／`sd`（Store Doubleword）を使い、レジスタも役割名（一時用 `t0`、第1引数 `a0` 等）で書きます。
* **x86-64（AT&T記法）：** レジスタ名に `%`、定数（即値）に `$`、64ビット演算の命令末尾に `q` を付け、左のオペランドから右のオペランドへ作用します。`(%rdi)` は「レジスタ `%rdi` の番地が指すメモリの中身」を意味します。

これを踏まえて、`*p += 5;` に対応する機械語列を並べてみます。

* **RISC-V（RV64I・ロード・ストア型）の機械語列（3命令・合計12バイト）：**

    ```asm
    ld   t0, 0(a0)      # 1. メモリ [a0] からレジスタ t0 へ読み込む（4バイト）
    addi t0, t0, 5      # 2. レジスタ t0 に 5 を足す（4バイト）
    sd   t0, 0(a0)      # 3. レジスタ t0 の結果をメモリ [a0] へ書き戻す（4バイト）
    ```

* **x86-64（メモリ直アクセス型）の機械語列（1命令・合計4バイト）：**

    ```asm
    addq $5, (%rdi)     # メモリ [%rdi] の値に直接 5 を足して書き戻す（4バイト）
    ```

    機械語のバイト列は `48 83 07 05` の4バイトです（先頭から順に、64ビット演算を指定する `REX` プリフィクス `48`、8ビット即値演算のオペコード `83`、加算および `(%rdi)` を指定する ModR/M バイト `07`、即値 `5` を表す `05`）。

この対比に、両者の設計方針の違いがよく表れています。

* **RISC-V（RV64I）** は「メモリへアクセスするのは専用のロード（`ld`）とストア（`sd`）命令だけ、演算は必ずレジスタ同士で行う」という **ロード・ストアアーキテクチャ** を採用しています。命令数は3個に増えますが、どの命令も4バイト固定長で動作が単純なため、[第0部](../index.md#part-0)で見た5段パイプラインへそのまま素直に乗ります。
* **x86-64** は1つの `addq` 命令の中に「メモリ読出し → 加算 → メモリ書戻し」を丸ごと詰め込みます。命令数は1個、バイト数も4バイトで済みますが、1命令の内部でメモリアクセスと演算を両方こなすため、命令フォーマットも制御回路も複雑になります。

### 3. 構造・アルゴリズム・実装（What）

#### (1) RISC と CISC の設計思想の対比

歴史的に、1970年代は主記憶の容量が小さく高価であり、さらに人間が直接アセンブリ言語を書く機会も多かったため、「メモリを節約し、1命令で高機能な処理ができる」**CISC**（DEC VAXやIntel x86）が主流でした。しかし1980年代に入り、コンパイラが生成する命令を統計的に分析すると、実際には単純なロード・ストア・加減算・分岐が実行時間の大部分を占めており、複雑な命令はかえってデコード回路を肥大化させパイプライン化を妨げていることが判明しました。そこから生まれたのが **RISC** です。

| 比較項目 | RISC（代表例：RISC-V, ARM） | CISC（代表例：x86-64） |
| :--- | :--- | :--- |
| **命令セットの規模** | 少数・単純な命令が中心 | 多数・高機能な命令（ストリング命令等を含む） |
| **命令長** | 原則として固定長（RV64I 基本は32ビット＝4B） | 可変長（x86-64は **1バイト〜15バイト**） |
| **メモリアクセス** | ロード／ストア命令のみ（演算命令はレジスタ限定） | 演算命令のオペランドにメモリを直接指定可能 |
| **汎用レジスタ数** | 多い（RISC-Vは32本：`x0`〜`x31`） | 比較的少ない（x86-64は16本：`%rax`〜`%rsp` の8本と `%r8`〜`%r15` の8本） |
| **条件分岐の仕組み** | レジスタ同士を直接比較して分岐（`beq`, `blt`） | 比較結果（ゼロ・符号・桁上がり等）を記録するステータスフラグ（`CF/OF/ZF/SF`、[1-2節](1-2.md)）を参照して分岐 |
| **関数呼び出しの戻り番地** | 専用レジスタ `ra`（リンクレジスタ）へ格納 | `call` 命令が自動的にメモリ（スタック）へプッシュ |
| **主な設計目標** | デコードの簡素化・パイプライン効率・電力効率 | コードサイズ削減・過去世代との後方互換性 |

#### (2) 機械語命令の符号化フォーマットの対比

両者の違いがハードウェア設計に最も強く表れるのが、命令を2進数へ符号化するフォーマットです（図1-1-2）。

* **RISC-V（RV64I・固定32ビット・位置固定設計）：**
    基本命令はすべてちょうど32ビット（4バイト）です。しかもデコード回路を簡略化するため、命令種別（`opcode`: ビット6..0）は全フォーマットで固定されており、**ソースレジスタ番号（`rs1`: ビット19..15、`rs2`: ビット24..20）や書き込み先レジスタ番号（`rd`: ビット11..7）も、それぞれのフィールドを持つすべての命令形式において同じビット位置に固定**されています（加算と減算のように同じ `opcode` を共有する命令の細かい区別は、補助オペコードの `funct3`・`funct7` で指定します）。命令の種類を解析し終える前でも、ハードウェアは決め打ちでビット19..15と24..20をレジスタファイルへ繋いで読み出しを始められます。さらに符号ビットは常に最上位ビット（ビット31）に置かれるため、即値の符号拡張も即座に開始できます。

* **x86-64（可変長1〜15バイト・歴史的拡張の積み重ね）：**
    16ビットの8086（1978年）→ 32ビットのIA-32 → 64ビットのx86-64へと後方互換性を保ちながら拡張されてきたため、命令フォーマットは階層的な可変長になっています。先頭から順に次の要素が並び、命令全体の長さは最大15バイトです。

    1. **レガシープリフィクス（Legacy Prefix：0〜4バイト）と `REX` プリフィクス（0〜1バイト）：** マルチコア環境で他コアの割り込みを許さず不可分に実行（アトミック実行）させる `LOCK` プリフィクスやオペランド幅切替などのレガシープリフィクス（任意・最大4バイト）に続き、64ビット演算や追加レジスタ（`%r8`〜`%r15`）を指定する1バイトの **`REX` プリフィクス**（任意・0〜1バイト）を置きます。
    2. **オペコード（Opcode：1〜3バイト・必須）：** 命令の種類（`mov`, `add` 等）と転送方向ビットを指定します。
    3. **ModR/M バイト（0〜1バイト）と SIB バイト（0〜1バイト）：** アドレッシングモード（レジスタかメモリか）を指定する ModR/M バイトと、「ベース＋インデックス $\times$ スケール」の配列参照を指定する SIB バイトを任意で付加します。
    4. **変位（Displacement：0, 1, 4バイト）と即値（Immediate：0, 1, 2, 4, 一部8バイト）：** メモリ基準番地からのずらし幅（変位）や、命令内に直書きする定数（即値）を任意で並べます。

    たとえば `nop` 命令や `ret` 命令はわずか **1バイト**（`0x90`, `0xC3`）ですが、複雑なメモリアクセスと定数を含む命令は10バイト以上に伸びます。可変長命令がデコードで難しい本質は、**1命令目の先頭から順に解析して長さが確定するまで、2命令目がどのバイトから始まるか（命令境界）すら分からない**点にあります。32ビット固定長のRISC-Vなら「0バイト目、4バイト目、8バイト目、…」から複数命令を一斉に並列デコードできますが、x86-64では命令境界を切り出すだけでも複雑な解析ハードウェアと電力が必要になります。

#### (3) 本ノート全体で参照する2つのアーキテクチャのレジスタ対応表

本ノートでは、第1〜2部で **x86-64（System V AMD64 ABI）**、第3〜5部で **RISC-V（RV64GC）** を具体例として用います。レジスタの名前や書き方は異なりますが、果たしている役割は次のように1対1に対応しています。

| 役割 | RISC-V（RV64） | x86-64（Linux / System V ABI） | 補足 |
| :--- | :--- | :--- | :--- |
| **プログラムカウンタ** | `pc` | `%rip` | 次に実行する命令のアドレス |
| **スタックポインタ** | `sp` (`x2`) | `%rsp` | 現在のスタックトップを指す |
| **フレーム／ベースポインタ** | `s0` / `fp` (`x8`) | `%rbp` | 現在のスタックフレームの基準 |
| **関数の戻り番地** | `ra` (`x1`) | スタックトップに自動プッシュ | RISC-Vはレジスタ、x86-64はメモリへ保存 |
| **関数の引数** | `a0`〜`a7`（8個） | `%rdi, %rsi, %rdx, %rcx, %r8, %r9`（6個） | 入りきらない引数はスタック渡し |
| **関数の返り値** | `a0`, `a1` | `%rax`, `%rdx` | 整数・ポインタの戻り値 |
| **定数ゼロ専用** | `zero` (`x0`) | なし（`xorl %eax, %eax` 等で代用） | 32ビット命令の上位ゼロ拡張で `%rax=0`（詳細は[1-2節](1-2.md)） |
| **一時レジスタ（caller-saved）** | `t0`〜`t6`, `a0`〜`a7`, `ra` | `%rax, %rcx, %rdx, %rsi, %rdi, %r8`〜`%r11` | 呼び出し側が必要に応じて退避 |
| **保存レジスタ（callee-saved）** | `s0`〜`s11`, `sp` | `%rbx, %rbp, %rsp, %r12`〜`%r15` | 呼ばれた関数側が元の値を復元 |
| **システムコール番号** | `a7`（命令：`ecall`） | `%rax`（命令：`syscall`） | OSカーネルへのサービス要求 |

以降の章でどちらのアーキテクチャのコードが出てきても、「今はスタックポインタを動かしている」「今は第1引数を渡している」とこの対応表に引き当てて読めば、本質的な構造が同じであることが分かります。

> **【コラム：x86-64アセンブリの2つの記法（AT&T記法 vs Intel記法）】**
>
> x86-64のアセンブリ言語には、同じ機械語命令に対して **AT&T記法**（GNUアセンブラ `as` や `gcc` のデフォルト）と **Intel記法**（Intel公式マニュアル、Windowsツールチェイン、NASMの標準）という2種類の方言が存在します。歴史的には、UNIXが初期に動いていた PDP-11 や VAX のアセンブラの伝統を AT&T ベル研究所経由で GNU `as` が受け継いだのに対し、Intelは自社のCPU仕様書で独自の記法を定めたため、2つの流儀が並存するようになりました。最大の違いは**オペランド（引数）の向きが逆**である点です。
>
> | 項目 | AT&T記法（本ノートで使用） | Intel記法 | 意味 |
> | :--- | :--- | :--- | :--- |
> | **代入の向き** | 左 → 右（`movq %rsp, %rbp`） | 右 → 左（`mov rbp, rsp`） | `%rbp = %rsp` |
> | **レジスタと即値** | レジスタに `%`、即値に `$`（`addq $5, %rax`） | 記号なし（`add rax, 5`） | `%rax += 5` |
> | **サイズ指定** | 命令末尾の文字（`b/w/l/q`） | `BYTE/WORD/DWORD/QWORD PTR` | 1 / 2 / 4 / 8 バイト |
> | **メモリ参照** | `-8(%rbp)` | `[rbp - 8]` | `%rbp - 8` 番地のメモリ |
>
> AT&T記法を読む際に最も誤読しやすいのは、次の2点です。
>
> 1. **減算・比較命令の向き：** `subq %rbx, %rax` は `%rax = %rax - %rbx`、`cmpq %rbx, %rax` は `%rax - %rbx` の結果でフラグを更新します。つまり、**右（第2オペランド）から左（第1オペランド）を引く**向きになる点に注意が必要です。
> 2. **即値プレフィックスの有無による意味の違い：** `$` の付いた `movq $0x100, %rax` は定数 `0x100` をレジスタへ入れる即値参照ですが、`$` を落として `movq 0x100, %rax` と書くと「`0x100` 番地のメモリの中身を読み込む」直接メモリ参照になってしまい、通常は不正なメモリアクセスで即座にクラッシュします。
>
> なお、RISC-V や ARM64 のアセンブリは Intel記法と同じく「左が書き込み先（`addi t0, t0, 5`）」です。本ノートの第1〜2部では Linux の標準ツールチェイン（`gcc -S` や `objdump -d`）の出力とそのまま照合できるよう **AT&T記法** で統一し、[第0部](../index.md#part-0)・第3〜5部の RISC-V と行き来するときはオペランドの向きを意識して読み分けます（`gcc -S -masm=intel` や `objdump -d -M intel` と指定すれば Intel記法で出力させることもできます）。

### 4. 限界と補正（Critique & Adaptation）

RISCとCISCは1980〜90年代に激しく優劣が議論されましたが、現代のプロセッサ設計では、両者が互いの弱点を補い合う形で**実務上の収斂（コンバージェンス）**が進んでいます。

#### (1) CISC（x86-64）側の補正：内部でのマイクロオペレーション（$\mu\text{op}$）分解

実験Aで見た `addq $5, (%rdi)` のような複雑なCISC命令は、そのままでは現代の深いパイプラインやアウトオブオーダ実行（[0-6節](../0/0-6.md)）に載せにくいという限界があります。

そこで現代のx86-64プロセッサ（Intel Core や AMD Ryzen など）は、**「外側の契約（ISA）はx86-64のまま守りつつ、CPUの入口（デコーダ）で複雑なx86-64命令を複数の単純なRISC風命令（マイクロオペレーション：$\mu\text{op}$）へ動的に分解し、内部のRISC風アウトオブオーダ実行コアで処理する」**という二層構造をとっています（図1-1-3）。たとえば `addq $5, (%rdi)` は、内部的には「ロード $\mu\text{op}$ → 加算 $\mu\text{op}$ → ストア $\mu\text{op}$」へ分解されて実行されます。

もっとも、「毎回重いデコーダで $\mu\text{op}$ へ分解するなら、最初から単純なRISC命令を実行するより遅くなるのではないか」と疑問に思うかもしれません。現代のx86-64がそれでも高い実行効率を保てる主な理由は2つあります。第1に、一度変換した $\mu\text{op}$ 列を保存しておく専用の **$\mu\text{op}$ キャッシュ**（Intel の Decoded Stream Buffer［DSB］や AMD の Op Cache など、各社のプロセッサで広く採用されている機構）を備えており、ループのように繰り返し実行される箇所では重い可変長デコーダを迂回して直接 $\mu\text{op}$ を供給できることです。第2に、可変長命令はコード密度が高いため、同じ容量のL1命令キャッシュにより多くの命令を収められる点です。デコーダの回路規模と消費電力というコストは払うものの、膨大な既存ソフトウェアの互換性とRISC並みの実行効率を両立させる現実的な折衷案です。

#### (2) RISC（RISC-V）側の補正：圧縮命令拡張（RV64C）と命令拡張のモジュール化

一方、純粋なRISCには「全命令を32ビット固定長にすると、頻繁に現れる単純な命令まで4バイトを消費し、プログラム全体のサイズ（コードサイズ）が大きくなってL1命令キャッシュの利用効率が落ちる」という限界がありました。

これに対するRISC-Vの補正が、標準拡張の **C拡張（RV64C／Compressed Instructions：16ビット圧縮命令）** です。よく使われるレジスタ加算やロード・ストア・分岐に2バイト（16ビット）の短縮版を用意し、命令の最下位2ビットを見るだけで「`11` なら32ビット命令、それ以外なら16ビット圧縮命令」と即座に判別できる **語頭符号（Prefix Code：どの符号も他の符号の先頭と重ならず、先頭から読むだけで区切りが一意に決まる符号）** を採用しています。RISC-V はリトルエンディアン（[0-2節](../0/0-2.md)）で命令を配置するため、命令の最下位2ビットは常にメモリ上の**先頭バイトのビット1..0**に現れ、命令フェッチ回路は先頭バイトを読んだ瞬間に命令長を確定できます。これにより、デコードの単純さを損なわずにコードサイズを約 $25\% \sim 30\%$ 削減し、命令キャッシュのヒット率を高めています。また、乗除算（`M`）、マルチコア間で不可分に読み書きするアトミック命令（`A`）、浮動小数点（`F`/`D`）、ベクトル演算（`V`）を用途に応じて選べるモジュール設計も現代RISCの特徴です。

> **【コラム：ARM64（AArch64）に見る現実的な折衷設計】**
>
> RISCとCISCは完全な二項対立ではなく、用途と時代に応じた連続的なスペクトラムとして設計されます。その代表例が、スマートフォンから Apple Silicon、クラウドサーバまで広く使われている **ARM64（AArch64）** です。
>
> ARM64は、すべての命令を32ビット固定長とし、演算をレジスタ同士に限るロード・ストア型を採用し、31本の64ビット汎用レジスタ（`x0`〜`x30`）とゼロレジスタ（`xzr`）を備える点で、明確にRISCの骨格を持っています。その一方で、条件分岐にはRISC-Vのようなレジスタ直接比較ではなく、x86-64と同様の**ステータスフラグ（`NZCV`：Negative, Zero, Carry, Overflow）** を採用しています。さらに、ロード／ストアと同時にベースレジスタを更新するプリ／ポストインクリメント（例：`ldr x0, [sp], #16` でメモリから読み出しつつ `sp` を16バイト進める）や、2本のレジスタを一括で読み書きする `ldp`/`stp` 命令も持ちます。
>
> 固定長命令による高速な並列デコードの利点を守りつつ、コンパイラが多用する配列走査やスタック操作の命令数を減らす工夫を取り入れたARM64は、RISC-Vの「単純さを重視した設計」とx86-64の「後方互換と高密度」の中間に位置する現実的な設計例といえます。

### 理解度チェック（次節へ進む前の確認）

本節の AT&T 記法・命令フォーマット・レジスタ対応と RISC/CISC の収斂設計を確認し、次節（[1-2節](1-2.md)）へ繋ぐ問いを置きます。

> **【確認の問い】**
>
> 1. **（AT&T 記法の誤読診断と固定長 vs 可変長命令の並列デコード）**
>
>     * (a) 64ビットレジスタに `%rax = 10`、`%rbx = 3` が入っている状態で、AT&T 記法の命令 `subq %rbx, %rax` を実行しました。実行後の `%rax` の値はいくらになるでしょうか。また、別の箇所で定数 `0x200` をレジスタ `%rcx` へ入れようとして、誤って `$` を落とし `movq 0x200, %rcx` と書いてしまいました。この命令はどのように動作し、なぜバグになるでしょうか。
>     * (b) RISC-V（RV64I 基本命令）の32ビット固定長フォーマットと、x86-64 の1〜15バイト可変長フォーマットを比べたとき、CPU が複数命令を同時に並列デコードするうえで可変長命令側が抱える本質的な難しさは何か説明してください。
>
> 2. **（RISC-V から x86-64 への変換と現代の収斂設計）**
>
>     * (a) RISC-V（RV64）で「8個の整数引数を受け取り、戻り番地をレジスタ `ra` に保持して動作する関数」を、x86-64（Linux / System V AMD64 ABI）へ対応づけて実装するとき、① 第7・第8引数の渡し方、② 戻り番地の保存場所、③ 汎用レジスタ本数の違い（32本 vs 16本）の3点はどう変わるでしょうか。
>     * (b) 現代の x86-64 プロセッサは複雑な可変長命令を内部で $\mu\text{op}$ へ分解して実行しますが、ループのように繰り返し実行される箇所でデコード負荷を抑えるためにどのような機構を備えているでしょうか。また、RISC-V の C拡張（16ビット圧縮命令）が先頭バイトを読むだけで32ビット命令か16ビット命令かを即座に判別できる理由（エンディアンとの関係を含む）も答えてください。
>
> 3. **（符号あり／なし比較におけるフラグ方式と直接比較方式の設計対比）**
>     8ビットのビット列 `0xFF` と `0x01` を比べるとき、2の補数の符号あり整数としては $-1 < 1$ ですが、符号なし整数としては $255 > 1$ となり大小関係が逆転します。
>
>     * (a) ステータスフラグを持たずレジスタ同士を直接比較して分岐する RISC-V の設計で、符号あり比較と符号なし比較を区別するには命令セット側でどのような工夫が必要でしょうか。
>     * (b) 一方、x86-64 のように「比較命令でステータスフラグ（`CF/OF/ZF/SF`）を更新し、続く条件付きジャンプ命令でフラグを参照する」二段階方式には、1回の比較から符号あり／なし双方の条件を判定できる利点がある反面、パイプラインやアウトオブオーダ実行の観点ではどのような制約（依存関係）が生じやすいでしょうか。本節および[第0部](../index.md#part-0)の内容をもとに考察してください。
