### 前節（1-5）の確認問題の解答

前節の最後に提示した3つの問いの解答を確認します。

1. **PIC の `%rip` 相対ディスプレイスメント計算と非 PIC 共有ライブラリの問題：**

    * **(a) 両プロセスでの `%rip` 相対ディスプレイスメントの計算：**
        命令長は 7 バイトなので、次の命令のモジュール内オフセットは $\texttt{0x1200} + 7 = \texttt{0x1207}$ です。

        * **プロセスA（ベース `0x7f10_0000_0000`）：**
            次の命令 `%rip` $= \texttt{0x7f10\_0000\_1207}$、`GOT[g]` $= \texttt{0x7f10\_0000\_3FE8}$ より、相対ディスプレイスメントは

            $$\texttt{0x7f10\_0000\_3FE8} - \texttt{0x7f10\_0000\_1207} = \mathbf{\texttt{0x2DE1}}$$

            です。

        * **プロセスB（ベース `0x7f82_0000_0000`）：**
            次の命令 `%rip` $= \texttt{0x7f82\_0000\_1207}$、`GOT[g]` $= \texttt{0x7f82\_0000\_3FE8}$ より、相対ディスプレイスメントは

            $$\texttt{0x7f82\_0000\_3FE8} - \texttt{0x7f82\_0000\_1207} = \mathbf{\texttt{0x2DE1}}$$

            です（検算：$\texttt{0x1207} + \texttt{0x2DE1} = \texttt{0x3FE8}$）。ベースアドレスが引き算で相殺されるため、両プロセスで同一の相対値 **`0x2DE1`** がそのまま使えます。

    * **(b) 非 PIC 共有ライブラリが物理メモリ共有を壊す理由：**
        起動時に動的リンカが `.text` セクション内の機械語へプロセスごとの絶対アドレスを直接書き込むと、OS の**コピーオンライト（Copy-on-Write）**機構が働いてその書き込みページがプロセスごとに別々の物理ページとして複製されてしまいます。結果として、本来1枚で共有できたはずの `.text` がプロセス数だけ物理メモリを消費するようになり、共有ライブラリのメモリ節約効果が失われます（また書き換えのために一時的に `.text` へ書き込み許可を与える必要も生じます）。

2. **遅延バインディング初回呼び出しの復帰と Full RELRO のトレードオフ：**

    * **(a) `printf` が直接 `main` へ戻れる理由：**
        `main` が実行した `call printf@plt` によって `main` への戻り番地がスタックへ1度だけ積まれたあと、`printf@plt` → `PLT[0]` → `_dl_runtime_resolve` → `printf` 本体の移動はすべて **`jmp` 命令** で行われます。途中でスタックへ積まれた識別番号と `link_map`、および退避した引数レジスタも、`_dl_runtime_resolve` が `printf` 本体へジャンプする直前にすべて復元・解放するため、`printf` 実行時のスタックトップには **`main` への戻り番地がそのまま残っています**。したがって `printf` の `ret` 命令は直接 `main` へ戻れます。

    * **(b) Full RELRO（`BIND_NOW`）のトレードオフ：**

        * **プログラム起動時間：** 遅延バインディングが無効化され、起動時にすべての外部関数シンボルを一括解決する必要があるため、Partial RELRO に比べて**起動時間はわずかに増加**します。
        * **実行中のセキュリティ：** 起動時の解決直後に `.got` と `.got.plt` を含む GOT 全体が**読み取り専用（`r--`）**へ凍結されるため、実行中に脆弱性で `GOT[printf]` 等を書き換える **GOT Overwrite 攻撃をハードウェアのメモリ保護で防止**できます。

3. **`LD_PRELOAD` が効かない条件と `vDSO` で高速化できる境界：**

    * **(a) `LD_PRELOAD` が効かない2つの理由：**

        * **① `-static` 静的リンクの場合：** 動的リンカ（`ld-linux`）自体が使われず、`malloc` の実体もリンク時にバイナリ本体へ直接結合済みのため、動的リンカの機能である `LD_PRELOAD` が介入する余地がありません。
        * **② `setuid` バイナリの場合：** 特権昇格の悪用を防ぐため、起動時にカーネルが補助ベクトル（`auxv`）へ **`AT_SECURE = 1`** を設定して渡し、これを受け取った**動的リンカが `LD_PRELOAD` を意図的に無視**します。

    * **(b) `vDSO` 化できる処理とできない処理の境界：**
        `vDSO` 化できるのは、`clock_gettime` や `getcpu` のように**「カーネルが読み取り専用ページとしてユーザ空間へ公開したデータを参照するだけで完結する処理」**に限られます。一方、`open`・`write`・`fork` のように**権限検査やファイルシステム・プロセス表などカーネル内部状態の変更を伴う処理**はユーザ空間だけでは安全に実行できないため、通常のシステムコール命令（`syscall`）で特権モードへ遷移する必要があります。

## 1-6. デバッグ情報（DWARF）・デバッガの動作原理とインラインアセンブラ

### 1. 動機（Why）：なぜ機械語だけの世界から「ソースコードの行」や「CPU固有の命令」を扱えるのか

前節（[1-5節](1-5.md)）までで、C言語のプログラムがコンパイル・アセンブル・リンク（静的／動的）を経て、実行可能なELFバイナリとしてメモリ上で動き出すまでの全体像が揃いました。

ここで、[第1部](../index.md#part-1)の締めくくりとして「高級言語（C言語）と機械語（ELFバイナリ）の境界を行き来する」ための2つの実用的な仕組みを確認します。

1. **機械語からソースコードへ逆引きして観察する仕組み（DWARF とデバッガ）：**
    プログラムにバグが起きたとき、私たちはGDBなどのデバッガ上で「`main.c` の12行目で止めよ」「局所変数 `x` の値を表示せよ」と操作します。しかし実行中のCPUが知っているのは `%rip` のメモリアドレスとレジスタ・スタックのビット列だけです。どのようにしてアドレスと行番号・変数型を結びつけ、しかも動き続けているCPUを1命令単位で止めているのでしょうか。

2. **高級言語の中から直接機械語を操る仕組み（インラインアセンブラ）：**
    逆にOSカーネルや低レベルライブラリを書く場面では、C言語の標準構文では表現できないCPU固有の命令（システム制御レジスタの読み書き、特殊なアトミック命令、割り込み禁止など）を実行したいことがあります。C言語の関数の中に直接アセンブリ命令を安全に埋め込むには、コンパイラの最適化器とどう協調すればよいのでしょうか。

本節では、**DWARF デバッグ情報**、**デバッガの動作原理（`ptrace` と `int 3`）**、そして **GCC拡張インラインアセンブラ** の3つを順に整理し、[第1部](../index.md#part-1)を完結させます。

### 2. 具体例と動作イメージ（Toy Model）

仕組みの細部に入る前に、2つの小さな実験で「`-g` オプションがELFに何を追加するか」と「ブレークポイントがメモリをどう書き換えるか」を確かめます。

#### 実験A：`-g` オプションの有無でバイナリに何が加わるか

次の短いプログラム `dbg.c` を、通常の `gcc dbg.c -o a_no_g` と、デバッグ情報付きの `gcc -g dbg.c -o a_with_g` でコンパイルして比べてみます。

```c
int add(int a, int b) {
    int sum = a + b;
    return sum;
}
int main(void) {
    return add(3, 4);
}
```

両者のセクション一覧（`readelf -S`）を見比べると、実行される機械語（`.text`）の中身自体は同じである一方、`-g` を付けた `a_with_g` には **`.debug_info`**（関数や変数の定義本体）、**`.debug_abbrev`**（`.debug_info` 内で使うタグと属性の並びを短い番号へ省略定義する辞書）、**`.debug_line`**（機械語アドレスとソース行番号の対応表）、**`.debug_str`**（関数名やファイル名などの長い文字列を集約して重複を省く文字列テーブル）といった `.debug_*` セクション群が追加されています。

* これらのセクションは実行時にメモリへロードされる必要がないため、プログラムヘッダ（セグメント）には含まれません。
* デバッガ（GDB）が `a_with_g` を開くと、`.debug_line` の対応表から「`dbg.c` の2行目は仮想アドレス `0x1135`」、`.debug_info` から「関数 `add` の局所変数 `sum` は `int` 型（4バイト符号あり整数）で、フレーム基準位置から `-4` バイトにある」という情報を読み取ります。

#### 実験B：ブレークポイントを張った瞬間、メモリ上の機械語が `0xCC` に変わる

GDB上で `break add` と入力して `dbg.c` の `add` 関数先頭（アドレス `0x1129`）にブレークポイントを張ったとします。元のメモリ上の機械語の先頭バイトは `pushq %rbp` を表す **`0x55`** でした。

この瞬間、GDBはOSのシステムコール経由で対象プロセスのメモリ `0x1129` 番地を覗き、元の1バイト `0x55` を自分自身のメモへ退避したうえで、そこへ **`0xCC`** という1バイトの機械語命令を上書きします。ここで「`.text` セクションは書き込み禁止（`r-x`）のはずでは？」と疑問に思うかもしれません。GDBが後述の `ptrace` システムコール経由で依頼すると、**OSカーネルが特権によってページ保護を一時的に迂回して書き込みを行います**（もしその `.text` ページが別プロセスと物理メモリを共有している場合は、対象プロセス専用のプライベートコピーを作ってから書き換えるため、他プロセスには影響しません）。

* `0xCC` は x86-64 の **`int 3`（ブレークポイント用トラップ命令）** です。
* プログラムを実行してCPUの `%rip` が `0x1129` へ到達すると、CPUは `0xCC` を実行して即座に例外を発生させ、OSが対象プロセスを一時停止させてGDBへ「トラップで止まりました（ブレークポイント等の発生を知らせるOSシグナル **`SIGTRAP`**）」と通知します。

私たちが「ブレークポイントで止まった」と見ている現象の正体は、**デバッガが対象プロセスの `.text` メモリを一時的に `0xCC` へ書き換え、止まった後に元の `0x55` へ戻して再開させる**という仕組みです。

### 3. 構造・アルゴリズム・実装（What）

#### (1) DWARF デバッグ情報の構造（DIEの木構造と LEB128）

LinuxなどのELF環境で標準的に使われているデバッグ情報フォーマットが **DWARF（Debugging With Attributed Record Formats）** です（※バイナリ形式がファンタジー世界の「エルフ［ELF］」と読めることにちなみ、対になる「ドワーフ［DWARF］」と名付けられました）。

DWARFは主に次のセクションに分けて情報を格納します（図1-6-1）。

* **`.debug_info`（DIEの木構造）：** HTMLやJSONのように「ファイル ＞ 関数 ＞ ブロック ＞ 変数」という親子関係を、**DIE（Debugging Information Entry）** と呼ばれるノードの木構造で表現します。各DIEは種類を表す **タグ**（`DW_TAG_compile_unit`＝翻訳単位、`DW_TAG_subprogram`＝関数、`DW_TAG_variable`＝変数、`DW_TAG_base_type`＝基本型など）と、詳細な **属性**（名前、型への参照、開始・終了アドレス、スタック上の位置計算式など。図1-6-1の `fbreg(-4)` はフレーム基準位置から `-4` バイトを意味します）を持ちます。タグと属性の型一覧は **`.debug_abbrev`** に共通の雛形として定義しておき、長い識別子文字列は **`.debug_str`** にまとめて参照することでサイズを圧縮しています。
* **`.debug_line`（行番号プログラム）：** 機械語アドレスと「ソースファイル名・行番号・列番号」の対応表です。全命令1つずつにファイル名と行番号をベタ書きすると容量が膨大になるため、「前の行からアドレスを $+4$ バイト、行番号を $+1$ 進めよ」といった小さな差分コマンド列（状態機械）として圧縮記録されています。
* **`.debug_frame` / `.eh_frame`（呼び出しフレーム情報）：** [1-3節](1-3.md)で触れた `-fomit-frame-pointer` で `%rbp` が省略されていてもバックトレースできるよう、各命令アドレスにおける呼び出し元フレームとの境界アドレス（**CFA：Canonical Frame Address**）の復元手順を記録します。

DWARFのファイルサイズを抑えるために随所で使われているのが、**LEB128（Little Endian Base 128）** という可変長整数符号化です。デバッグ情報に現れるオフセットや行番号差分の大半は小さな整数なので、毎回4バイトや8バイト固定で書くのは無駄が大きくなります。

符号なし版（**ULEB128**）の手順は次の2段階です。

1. 対象の整数を2進数で表し、最下位ビット（LSB）側から **7ビットずつ** のかたまりに分割します。
2. 下位のかたまりから順番に並べ、各バイトの最上位ビット（MSB：ビット7）に**継続フラグ**を付けます（後ろにまだバイトが続くなら `1`、最後のバイトなら `0`）。

たとえば整数 $300 = \texttt{100101100}_2$ を下位から7ビットずつ分けると、下位が `0101100`（$44$）、上位が `0000010`（$2$）になります。1バイト目は継続するのでMSBに `1` を付けて `10101100`（`0xAC`）、2バイト目は終了なのでMSBに `0` を付けて `00000010`（`0x02`）となり、合計2バイトで表現できます（復号は $44 + 2 \times 2^7 = 44 + 256 = 300$）。[0-1節](../0/0-1.md)で見たUTF-8と同じく、「頻出する小さな値を少ないバイト数で表す」可変長符号化の好例です。

一方、図1-6-1の `fbreg(-4)` のように**負のオフセット**を表す必要がある箇所では、符号あり版の **SLEB128（Signed LEB128）** が使われます。手順は ULEB128 とほぼ同じですが、2の補数表現を下位から7ビットずつ切り出し、**最終バイトのビット6（`0x40`：7ビットデータ部の最上位ビット）** が `1` なら負数として上位を `1` で符号拡張します（たとえば `-4` は7ビットの2の補数で `1111100` なので、ビット6が `1` で符号が確定しており、終了ビット `0` をビット7に付けた1バイト `01111100` ＝ `0x7C` だけで表せます。1バイトで表せる SLEB128 の範囲は $-64 \sim +63$ です）。

#### (2) デバッガの動作原理：`ptrace` とブレークポイント／ウォッチポイント

DWARFによって「`dbg.c` の2行目は `0x1135` だ」と分かっても、デバッガ（GDB）自体は普通のユーザプログラムに過ぎません。通常、OSのメモリ保護によって、あるプロセスが別プロセスのメモリやレジスタを勝手に覗き見たり書き換えたりすることは禁止されています。

そこでLinuxなどのOSがデバッガ用に用意している特別なシステムコールが **`ptrace`（Process Trace）** です（システムコールの詳細は[第3部](../index.md#part-3) [3-1節](../3/3-1.md)で扱います）。デバッガは `ptrace` を通じてOSカーネルへ依頼することで、デバッグ対象プロセス（子プロセス等）のレジスタ読み書き、メモリ読み書き、停止・再開、1命令だけの実行（シングルステップ）を制御できます。

1. **設定時：** デバッガが対象アドレスの元の1バイト（例：`0x55` や `0x48`）を退避し、`0xCC`（`int 3`）へ書き換えます。
2. **停止時：** 対象プロセスが `0xCC` を実行すると例外が発生し、OSが対象プロセスを止めてデバッガへ通知します。このとき、ユーザは変数やスタックを自由に観察できます。
3. **復元と巻き戻し（再開準備）：** ユーザが「続行（`continue`）」を指示すると、デバッガは退避していた元の1バイトを戻し、すでに1バイト先へ進んでいる **`%rip` を `1` 減らして**元の命令の先頭へ戻します。
4. **1命令だけの実行（シングルステップ）：** そのまま通常再開すると `0xCC` が消えたままになり2回目以降止まらなくなってしまいます。そこで、CPUのステータスレジスタ内の **トラップフラグ（TF）** を立てて「元の1命令だけ」を実行させ、直後に再び止めます。
5. **再設定と通常再開：** 元の1命令が通過した直後に再び `0xCC` を埋め戻し、通常の高速実行を再開します。

また、特定の命令アドレスではなく「変数 `x` の中身が書き換わった瞬間に止める」機能を **ウォッチポイント（Watchpoint）** と呼びます。x86-64 CPUにはアドレス監視専用の **ハードウェア・デバッグレジスタ（`DR0`〜`DR3` の4本）** が内蔵されており、ここに変数 `x` のアドレスを登録しておけば、CPUが毎回のメモリアクセスをハードウェアで自動比較して速度低下なしで書き込みを検知できます。

> **【コラム：クラッシュの瞬間を凍結保存する「コアダンプ」と分離デバッグ情報】**
>
> 本番環境で数日に1回しか起きないクラッシュは、あらかじめデバッガを繋いで再現させることが困難です。このようなときに役立つのが **コアダンプ（Core Dump）** です。
>
> プログラムが不正なメモリアクセス（`SIGSEGV`）などで異常終了した瞬間、OSカーネルはそのプロセスのメモリイメージ全体（スタック、`malloc` 等で動的に確保したヒープ、`.data` 等）と全レジスタの値（`%rip`, `%rsp`, `%rbp` 等）を1つのファイル（`core` ファイル）としてディスクへ書き出します。実は `core` ファイル自身も [1-4節](1-4.md)で学んだ **ELF 形式（ファイル種別 `ET_CORE`）** で作られており、各メモリ領域は `PT_LOAD` セグメント、レジスタ群・停止原因のシグナル・補助ベクトル（`auxv`）は `PT_NOTE` セグメントとして格納されています。開発者は後から `gdb ./a.out core` と開くだけで、DWARF情報と照合しながら「クラッシュした瞬間にどの関数の何行目にいて、各変数に何が入っていたか」をそのまま調査できます（事後デバッグ / Post-mortem Debugging）。
>
> 実務の本番運用では、巨大な DWARF 情報を含めたままバイナリを配布せず、リンク後のバイナリから `objcopy --only-keep-debug` 等でデバッグ情報だけを別ファイルへ切り出し、実行ファイル本体は `strip` して軽量化する **分離デバッグ情報（Separate Debug Info）** が広く使われます。実行ファイル側には対応ファイル名を記す `.gnu_debuglink` セクションや、ビルド時固有のハッシュ値である **`.note.gnu.build-id`（Build ID）** が埋め込まれており、事後デバッグ時に正確なデバッグ情報ファイルを自動照合できます。なお、これと混同しやすい仕組みに **Split DWARF（`-gsplit-dwarf`）** がありますが、こちらはビルド・リンクの高速化を目的として、各オブジェクトファイル分の DWARF 情報をコンパイル段階から別ファイル（`.dwo`）へ分けて出力し、リンカが巨大なデバッグ情報を読み込み・結合する負荷を省く仕組みです。
>
> また、コアダンプにはメモリ上の秘密鍵や個人情報が含まれ得るうえ大容量のディスクを消費するため、本番サーバでは `ulimit -c` や `systemd-coredump` で出力サイズ・保存先・アクセス権限を厳格に管理します（なお、「コア（core）」という名前は、半導体メモリ以前に小さな磁性体の輪［磁気コア］を並べて主記憶を作っていた時代の名残です）。

#### (3) インラインアセンブラの仕組み（GCC拡張構文）

最後に、C言語のソースコードの中から特定の機械語命令を直接呼び出す **インラインアセンブラ（Inline Assembly）** の構造を押さえます。Cの標準仕様には含まれませんが、GCCやClangでは次の **拡張インラインアセンブラ構文** が広く使われます（図1-6-3）。

```c
int a = 10, b = 20, result;
asm volatile (
    "movl %1, %0\n\t"      // アセンブリテンプレート（%0=result, %1=a, %2=b）
    "addl %2, %0"
    : "=&r" (result)       // [出力オペランド] =書込専用, &早期破壊, r汎用レジスタ
    : "r" (a), "r" (b)     // [入力オペランド] r汎用レジスタ
    : "cc"                 // [破壊リスト（clobber list）] フラグレジスタ変化
);
```

さらに、C言語の標準構文では書けないCPU固有命令の実例として、x86-64 のCPUクロックカウンタ（64ビット値）を `%edx`（上位32ビット）と `%eax`（下位32ビット）へ読み出す **`rdtsc`** 命令の呼び出し方を見てみます。

```c
uint32_t lo, hi;
asm volatile (
    "rdtsc\n\t"
    "movl %%eax, %0\n\t"   // 拡張構文内で物理レジスタ名を書くときは %% と重ねる
    "movl %%edx, %1"
    : "=r" (lo), "=r" (hi) // [出力] 任意の汎用レジスタへ受け取る
    :                      // [入力] なし
    : "eax", "edx"         // [破壊リスト] rdtsc が暗黙に上書きするレジスタを申告
);
```

ここで、拡張インラインアセンブラのテンプレート文字列内では `%0`, `%1` がオペランド番号の参照に使われるため、物理レジスタ名を直接書くときは **`%%eax`, `%%edx` のように `%` を2つ重ねる** 決まりになっています（出力制約 `"=a"(lo), "=d"(hi)` を使って `%eax`/`%edx` へ直接結びつける書き方もよく使われます）。

なぜこのような細かい制約指定が必要なのでしょうか。コンパイラは `asm` ブロックの中に書かれた文字列（アセンブリ命令）の意味を解釈せず、ただのブラックボックスとしてそのままアセンブラへ渡します。そのため、プログラマが「どの変数を読み、どの変数を書き換え、どのレジスタやメモリを壊すか」を正確に申告しないと、コンパイラのレジスタ割当や最適化が破綻するのです。

* **早期破壊修飾子（`&`：earlyclobber）：** 入力を使い終わる前に出力へ書き込むため、「入力と出力に同じレジスタを使い回してはならない」と念押しする印です。コンパイラは通常「入力を全部読み終えてから出力へ書くのだろう」と仮定して、入力と出力に**同じ物理レジスタ**を割り当てることがあります。たとえば上の `movl %1, %0; addl %2, %0` で `&` を書き忘れると、`a = 10 (%edi), b = 20 (%esi)` のときに出力 `%0` にも `%esi` が使い回され、1行目の `movl %edi, %esi` で `b` の値 `20` が `10` に上書きされてしまい、2行目の `addl %esi, %esi` が誤答 `20` を返します（図1-6-3下）。同様に、`2 * a + b` を計算する関数 `calc(a, b)` へ `calc(a, a)` のように同じ変数を2つの引数へ渡した場合も、`&` がないと入力 `a` と出力が同一レジスタで衝突し、途中で出力レジスタを加工した瞬間に未読の入力側まで破壊されてしまいます。出力に `&` を付けて `"=&r"` と書けば、入力とは別のレジスタを確実に割り当ててくれます。
* **`volatile` と `"memory"`：** `asm volatile` を付けると「出力変数が使われていなくてもこの命令を削除・ループ外移動してはならない」と指示でき、破壊リストに `"memory"` を入れると「このブロックの前後にまたがってメモリ読み書きを並べ替えてはならない（コンパイラレベルのメモリバリア）」と指示できます。

### 4. 限界と補正（Critique & Adaptation）

#### (1) コンパイラ最適化（`-O2` 等）とデバッグの衝突、および `-Og` の役割

実務でデバッガを使うときに最も頻繁に直面するのが、**最適化オプション（`-O2` や `-O3`）を付けてビルドしたバイナリはデバッグしにくい**という問題です。

最適化器（[第2部](../index.md#part-2) [2-7節](../2/2-7.md)）はプログラムを速くするために、関数のインライン展開、ループの並べ替え、不要な一時変数の削除、同じレジスタの使い回しを積極的に行います。その結果、GDBでステップ実行するとソースコードの行番号が上下に飛び跳ねたり、変数の値を表示しようとしても `<optimized out>`（レジスタやメモリに実体が残っていない）と表示されたりします。

この限界に対する現実的な補正が、GCCやClangが用意している **`-Og`** オプションです。`-Og` はデバッグ体験を損なわない範囲の安全な最適化だけを有効にするため、「`-O0`（最適化なし）ほど遅くはなく、しかも行番号の対応や変数の観察がほぼ壊れない」という開発時の中間解を提供します。

#### (2) ソフトウェア・ウォッチポイントの低速さとハードウェア支援の個数制限

変数の中身が書き換わった瞬間に止めるウォッチポイントには、ハードウェア方式とソフトウェア方式の2種類があります。

* **ハードウェア・ウォッチポイント：** CPU内蔵のデバッグレジスタ（x86-64の `DR0`〜`DR3`）を使うため実行速度がほぼ落ちませんが、**同時に監視できる箇所が最大4箇所**（かつサイズ上限あり）に限られます。
* **ソフトウェア・ウォッチポイント：** ハードウェアの枠を超えた場合、GDBは1命令実行するたびにプロセスを止め（シングルステップ）、毎回対象メモリの値が変化したかを確認します。監視個数に制限はありませんが、実行速度が**数百倍〜数千倍も遅くなる**という厳しい限界があります。

そのため実務では、まずハードウェア・ウォッチポイントの枠内に収まるよう監視対象を絞り、さらに複雑な条件監視にはプログラム側へアサーション（`assert`）や、実行時にメモリ破壊・未定義動作を自動検出する検査機構である **サニタイザ**（AddressSanitizer 等、[第5部](../index.md#part-5) [5-8節](../5/5-8.md)）を組み込む方法で補います。

> **【コラム：固定長ISAのブレークポイントと、マルチスレッド環境での「取り逃し」問題】**
>
> x86-64 では最短命令長が1バイトであるため、1バイトの `int 3`（`0xCC`）を上書きしてブレークポイントを実現しました。同じ発想は RISC-V や ARM64 のような固定長ISAでも使われます。ARM64 では4バイトの `brk` 命令、RISC-V では4バイトの `ebreak`（16ビット圧縮命令 C拡張が有効な環境では2バイトの `c.ebreak`）を対象命令の先頭へ上書きしてトラップを発生させます。
>
> ただし、第3節で見た「元の命令を復元 → 1命令シングルステップ → 再び `0xCC` を埋め戻す」という手順には、**マルチスレッド環境特有の注意点**があります。スレッドAがブレークポイントから再開するために一時的に `0xCC` を元の命令へ戻しているわずかな隙間に、**別のコアで走るスレッドBが同じ番地を通過すると、ブレークポイントに気づかず素通り（取り逃し）してしまう**のです。この問題を回避するため、現代のデバッガ（GDB の displaced stepping 等）では、`.text` 上の `0xCC` は置いたまま、元の1命令だけを別の退避メモリ領域へコピーしてスレッドAに実行させる **アウトオブライン実行（Out-of-line Single Stepping）** という手法が使われます（PC相対参照を含む命令はアドレスを補正してコピーします）。

#### (3) インラインアセンブラの保守性・移植性の限界と現代的な代替手段

インラインアセンブラは直接的な制御に有用ですが、次のような大きなリスクを伴います。

* 特定のISA（x86-64等）に強く依存するため、ARMやRISC-Vへ移植できなくなります。
* 早期破壊 `&` や `"memory"` の破壊リスト（clobber list）を1つ書き忘れただけで、`-O0` では動いたのに `-O2` でだけ壊れる再現困難なバグを生みます。

このため現代のシステムプログラミングでは、**「OSカーネルのシステム制御レジスタ操作やコンテクストスイッチなど、本当に代替不能な最小限の箇所だけ」**にインラインアセンブラを限定し、SIMD並列演算にはコンパイラの **組み込み関数（Intrinsics）**、マルチスレッドのアトミック操作には **C11 / C++11 の標準アトミックライブラリ（`<stdatomic.h>`）** を使うことが標準的な補正になっています。

>
> 3. **（インラインアセンブラの契約違反とコンパイラ最適化事故：[第2部](../index.md#part-2)への橋渡し）**
>     あるプログラマが、2つの整数 `a`, `b` から `2 * a + b` を計算する拡張インラインアセンブラを次のように書きました。
>
>     ```c
>     int calc(int a, int b) {
>         int out;
>         asm (
>             "movl %1, %0\n\t"
>             "shll $1, %0\n\t"
>             "addl %2, %0"
>             : "=r" (out)          // 早期破壊 '&' を付け忘れ

>

>     * (b) CPU のタイムスタンプカウンタを読む `rdtsc` のような計測・副作用目的のインラインアセンブラで **`volatile`** を省いたり、共有メモリ上のロック変数を操作する命令で破壊リストの **`"memory"`** を省いたりすると、`-O2` 等のコンパイラ最適化によってどのような誤動作（削除・移動・並べ替え）が起こり得るでしょうか。コンパイラが `asm` ブロックをどう扱うかに着目して説明してください。
