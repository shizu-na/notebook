### 前節（1-5）の確認問題の解答

前節の最後に提示した3つの問いの解答を確認します。問3がそのまま本節（デバッグ情報とデバッガの動作原理）の導入になります。

1. **PIC と GOT が `.text` を書き換えずに済む理由：**
    共有ライブラリ `libfoo.so` のロード先仮想アドレスがプロセスAとプロセスBで異なっていても、同一モジュール内における `.text` と **プロセス固有の GOT** の相対距離はリンク時に固定されます。そのため、`.text` 側の機械語は **`%rip` 相対の固定距離** で `GOT[g]` のスロットだけを参照すればよく、実アドレスの書き込みは各プロセス専用の `GOT[g]` だけに閉じ込められます。結果として `.text` を1バイトも書き換えずに全プロセスで物理メモリを共有できます。

2. **PLT と GOT による遅延バインディングのトレース：**

    * **(a) 1回目の `call printf@plt`：**
        呼び出し直前、`GOT[printf]` には `printf` 本体のアドレスではなく、すぐ次の命令である **`printf@plt` の2行目（`pushq $index`）のアドレス** が初期値として入っています。1回目の呼び出しでは `PLT[0]` を経由して動的リンカ（`_dl_runtime_resolve`）が起動され、`libc.so.6` の記号表から `printf` の実アドレスを検索して **`GOT[printf]` をその実アドレスへ書き換えたうえで** `printf` 本体へジャンプします。

    * **(b) 2回目・3回目の呼び出しと Full RELRO：**
        2回目・3回目の呼び出しでは `GOT[printf]` がすでに実アドレスへ書き換わっているため、**動的リンカは呼ばれず**、`jmpq *GOT[printf](%rip)` で直接 `printf` 本体へ飛びます。なお、**Full RELRO** を有効にした場合は遅延バインディングが無効化され、プログラム起動時に動的リンカがすべての関数アドレスを一括解決した直後に、GOT全体が**読み取り専用（`r--`）**へ変更されます。

3. **実行中の機械語とソースコード行番号をどう結びつけるか（本節への接続）：**
    機械語のバイト列そのものには、元のC言語のファイル名・行番号・局所変数の名前や型といった情報は残っていません。それらをELFファイル内の専用セクションへ体系的に保存するのが **DWARF デバッグ情報** です。さらにデバッガは、OSのプロセス監視機能（`ptrace`）とCPUの専用トラップ命令（`int 3`）を組み合わせることで、実行中のプログラムを任意の1命令で一時停止させて内部を観察しています。

## 1-6. デバッグ情報（DWARF）・デバッガの動作原理とインラインアセンブラ

### 1. 動機（Why）：なぜ機械語だけの世界から「ソースコードの行」や「CPU固有の命令」を扱えるのか

前節（1-5節）までで、C言語のプログラムがコンパイル・アセンブル・リンク（静的／動的）を経て、実行可能なELFバイナリとしてメモリ上で動き出すまでの全体像が揃いました。

ここで、第1部の締めくくりとして「高級言語（C言語）と機械語（ELFバイナリ）の境界を行き来する」ための2つの実用的な仕組みを確認します。

1. **機械語からソースコードへ逆引きして観察する仕組み（DWARF とデバッガ）：**
    プログラムにバグが起きたとき、私たちはGDBなどのデバッガ上で「`main.c` の12行目で止めよ」「局所変数 `x` の値を表示せよ」と操作します。しかし実行中のCPUが知っているのは `%rip` のメモリアドレスとレジスタ・スタックのビット列だけです。どのようにしてアドレスと行番号・変数型を結びつけ、しかも動き続けているCPUを1命令単位で止めているのでしょうか。
2. **高級言語の中から直接機械語を操る仕組み（インラインアセンブラ）：**
    逆にOSカーネルや低レベルライブラリを書く場面では、C言語の標準構文では表現できないCPU固有の命令（システム制御レジスタの読み書き、特殊なアトミック命令、割り込み禁止など）を実行したいことがあります。C言語の関数の中に直接アセンブリ命令を安全に埋め込むには、コンパイラの最適化器とどう協調すればよいのでしょうか。

本節では、**DWARF デバッグ情報**、**デバッガの動作原理（`ptrace` と `int 3`）**、そして **GCC拡張インラインアセンブラ** の3つを順に整理し、第1部を完結させます。

### 2. 具体例と動作イメージ（Toy Model）

仕組みの細部に入る前に、2つの小さな実験で「`-g` オプションがELFに何を追加するか」と「ブレークポイントがメモリをどう書き換えるか」を確かめます。

#### 実験A：`-g` オプションの有無でバイナリに何が加わるか

次の短いプログラム `dbg.c` を、通常の `gcc dbg.c -o a_no_g` と、デバッグ情報付きの `gcc -g dbg.c -o a_with_g` でコンパイルして比べてみます。

```c
int add(int a, int b) {
    int sum = a + b;
    return sum;
}
int main(void) {
    return add(3, 4);
}
```

両者のセクション一覧（`readelf -S`）を見比べると、実行される機械語（`.text`）の中身自体は同じである一方、`-g` を付けた `a_with_g` には **`.debug_info`、`.debug_abbrev`、`.debug_line`、`.debug_str`** といった `.debug_*` セクション群が追加されています。

* これらのセクションは実行時にメモリへロードされる必要がないため、プログラムヘッダ（セグメント）には含まれません。
* デバッガ（GDB）が `a_with_g` を開くと、`.debug_line` の対応表から「`dbg.c` の2行目は仮想アドレス `0x1135`」、`.debug_info` から「関数 `add` の局所変数 `sum` は `int` 型（4バイト符号あり整数）で、フレーム基準位置から `-4` バイトにある」という情報を読み取ります。

#### 実験B：ブレークポイントを張った瞬間、メモリ上の機械語が `0xCC` に変わる

GDB上で `break add` と入力して `dbg.c` の `add` 関数先頭（アドレス `0x1129`）にブレークポイントを張ったとします。元のメモリ上の機械語の先頭バイトは `pushq %rbp` を表す **`0x55`** でした。

この瞬間、GDBはOSのシステムコール経由で対象プロセスのメモリ `0x1129` 番地を覗き、元の1バイト `0x55` を自分自身のメモへ退避したうえで、そこへ **`0xCC`** という1バイトの機械語命令を上書きします。

* `0xCC` は x86-64 の **`int 3`（ブレークポイント用トラップ命令）** です。
* プログラムを実行してCPUの `%rip` が `0x1129` へ到達すると、CPUは `0xCC` を実行して即座に例外を発生させ、OSが対象プロセスを一時停止させてGDBへ「トラップで止まりました（`SIGTRAP`）」と通知します。

私たちが「ブレークポイントで止まった」と見ている現象の正体は、**デバッガが対象プロセスの `.text` メモリを一時的に `0xCC` へ書き換え、止まった後に元の `0x55` へこっそり戻して再開させる**という巧妙な手品なのです。

### 3. 構造・アルゴリズム・実装（What）

#### (1) DWARF デバッグ情報の構造（DIEの木構造と LEB128）

LinuxなどのELF環境で標準的に使われているデバッグ情報フォーマットが **DWARF（Debugging With Attributed Record Formats）** です（※バイナリ形式がファンタジー世界の「エルフ［ELF］」と読めることにちなみ、対になる「ドワーフ［DWARF］」と名付けられました）。

DWARFは主に次のセクションに分けて情報を格納します（図1-6-1）。

* **`.debug_info`（DIEの木構造）：** ソースファイル、関数、ブロック、変数、データ型といったプログラムの全要素を、**DIE（Debugging Information Entry）** と呼ばれるノードの木構造で表現します。各DIEは種類を表す **タグ**（`DW_TAG_compile_unit`＝翻訳単位、`DW_TAG_subprogram`＝関数、`DW_TAG_variable`＝変数、`DW_TAG_base_type`＝基本型など）と、詳細な **属性**（名前、型への参照、開始・終了アドレス、スタック上の位置計算式など）を持ちます。
* **`.debug_line`（行番号プログラム）：** 機械語アドレスと「ソースファイル名・行番号・列番号」の対応表です。全命令1つずつにファイル名と行番号をベタ書きすると容量が膨大になるため、「アドレスを $+4$、行番号を $+1$ 進めよ」といった小さなバイトコード（状態機械）として圧縮記録されています。
* **`.debug_frame` / `.eh_frame`（呼び出しフレーム情報）：** 1-3節で触れた `-fomit-frame-pointer` で `%rbp` が省略されていてもバックトレースできるよう、各命令アドレスにおけるフレーム基準位置（CFA）の復元手順を記録します。

DWARFのファイルサイズを抑えるために随所で使われているのが、**LEB128（Little Endian Base 128）** という可変長整数符号化です。デバッグ情報に現れるオフセットや行番号差分の大半は小さな整数なので、毎回4バイトや8バイト固定で書くのは無駄が大きくなります。

符号なし版（**ULEB128**）の手順は非常にシンプルです。

1. 対象の整数を2進数で表し、下位（LSB側）から **7ビットずつ** のかたまりに分割します。
2. 下位のかたまりから順番に並べ、各バイトの最上位ビット（MSB）に**継続フラグ**を付けます（後ろにまだバイトが続くなら `1`、最後のバイトなら `0`）。

たとえば整数 $300 = \texttt{100101100}_2$ を下位から7ビットずつ分けると、下位が `0101100`（$44$）、上位が `0000010`（$2$）になります。1バイト目は継続するのでMSBに `1` を付けて `10101100`（`0xAC`）、2バイト目は終了なのでMSBに `0` を付けて `00000010`（`0x02`）となり、合計2バイトで表現できます（復号は $44 + 2 \times 2^7 = 44 + 256 = 300$）。0-1節で見たUTF-8と同じく、「頻出する小さな値を少ないバイト数で表す」可変長符号化の好例です。

#### (2) デバッガの動作原理：`ptrace` とブレークポイント／ウォッチポイント

DWARFによって「`dbg.c` の2行目は `0x1135` だ」と分かっても、デバッガ（GDB）自体は普通のユーザプログラムに過ぎません。通常、OSのメモリ保護によって、あるプロセスが別プロセスのメモリやレジスタを勝手に覗き見たり書き換えたりすることは禁止されています。

そこでLinuxなどのOSがデバッガ用に用意している特別なシステムコールが **`ptrace`（Process Trace）** です（システムコールの詳細は第3部 3-1節で扱います）。デバッガは `ptrace` を通じてOSカーネルへ依頼することで、デバッグ対象プロセス（子プロセス等）のレジスタ読み書き、メモリ読み書き、停止・再開、1命令だけの実行（シングルステップ）を制御できます。

1. **設定時：** デバッガが対象アドレスの元の1バイト（例：`0x55`）を退避し、`0xCC`（`int 3`）へ書き換えます。
2. **停止時：** 対象プロセスが `0xCC` を実行すると例外が発生し、OSが対象プロセスを止めてデバッガへ通知します。このとき、ユーザは変数やスタックを自由に観察できます。
3. **復元と巻き戻し（再開準備）：** ユーザが「続行（`continue`）」を指示すると、デバッガは退避していた `0x55` を元のアドレスへ戻し、すでに1バイト先へ進んでいる **`%rip` を `1` 減らして**元の命令の先頭へ戻します。
4. **1命令だけの実行（シングルステップ）：** そのまま通常再開すると `0xCC` が消えたままになり2回目以降止まらなくなってしまいます。そこで、CPUのステータスレジスタ内の **トラップフラグ（TF）** を立てて「元の1命令（`pushq %rbp`）だけ」を実行させ、直後に再び止めます。
5. **再設定と通常再開：** 元の1命令が通過した直後に再び `0xCC` を埋め戻し、通常の高速実行を再開します。

また、特定の命令アドレスではなく「変数 `x` の中身が書き換わった瞬間に止める」機能を **ウォッチポイント（Watchpoint）** と呼びます。x86-64 CPUにはアドレス監視専用の **ハードウェア・デバッグレジスタ（`DR0`〜`DR3` の4本）** が内蔵されており、ここに変数 `x` のアドレスを登録しておけば、CPUが毎回のメモリアクセスをハードウェアで自動比較して速度低下なしで書き込みを検知できます。

> **【コラム：クラッシュの瞬間を凍結保存する「コアダンプ」による事後デバッグ】**
>
> 本番環境で数日に1回しか起きないクラッシュは、あらかじめデバッガを繋いで再現させることが困難です。このようなときに力を発揮するのが **コアダンプ（Core Dump）** です。
>
> プログラムが不正なメモリアクセス（`SIGSEGV`）などで異常終了した瞬間、OSカーネルはそのプロセスのメモリイメージ全体（スタック・ヒープ・`.data` 等）と全レジスタの値（`%rip`, `%rsp`, `%rbp` 等）を1つのELFファイル（`core` ファイル）としてディスクへ書き出します。開発者は後から `gdb ./a.out core` と開くだけで、DWARF情報と照合しながら「クラッシュした瞬間にどの関数の何行目にいて、各変数に何が入っていたか」をそのまま調査できます（事後デバッグ / Post-mortem Debugging）。なお、「コア（core）」という名前は、半導体メモリ（DRAM）以前に小さな磁性体の輪（磁気コア）を並べて主記憶を作っていた時代の名残です。

#### (3) インラインアセンブラの仕組み（GCC拡張構文）

最後に、C言語のソースコードの中から特定の機械語命令を直接呼び出す **インラインアセンブラ（Inline Assembly）** の構造を押さえます。Cの標準仕様には含まれませんが、GCCやClangでは次の **拡張インラインアセンブラ構文** が広く使われます（図1-6-3）。

```c
int a = 10, b = 20, result;
asm volatile (
    "movl %1, %0\n\t"      // アセンブリテンプレート（%0=result, %1=a, %2=b）
    "addl %2, %0"
    : "=&r" (result)       // [出力オペランド] =書込専用, &早期破壊, r汎用レジスタ
    : "r" (a), "r" (b)     // [入力オペランド] r汎用レジスタ
    : "cc"                 // [破壊レジスタ列（clobber list）] フラグレジスタ変化
);
```

コロン `:` で区切られた4つのブロックが、プログラマとコンパイラ最適化器の間の契約書になります。

* **早期破壊修飾子（`&`：earlyclobber）：** コンパイラは通常「入力を全部読み終えてから出力へ書くのだろう」と仮定して、入力 `%2` と出力 `%0` に**同じ物理レジスタ**を割り当てることがあります。しかし上の例のように、1行目の `movl %1, %0` で出力 `%0` を先に書き換えてから2行目で入力 `%2` を読む場合、もし `%0` と `%2` が同じレジスタだと `b` の値が壊れてしまいます。出力に `&` を付けて `"=&r"` と書けば、入力とは別のレジスタを割り当ててくれます。
* **`volatile` と `"memory"`：** `asm volatile` を付けると「出力変数が使われていなくてもこの命令を削除・ループ外移動してはならない」と指示でき、破壊リストに `"memory"` を入れると「このブロックの前後にまたがってメモリ読み書きを並べ替えてはならない（コンパイラレベルのメモリバリア）」と指示できます。

### 4. 限界と補正（Critique & Adaptation）

#### (1) コンパイラ最適化（`-O2` 等）とデバッグの衝突、および `-Og` の役割

実務でデバッガを使うときに最も頻繁に直面するのが、**最適化オプション（`-O2` や `-O3`）を付けてビルドしたバイナリはデバッグしにくい**という問題です。

最適化器（第2部 2-7節）はプログラムを速くするために、関数のインライン展開、ループの並べ替え、不要な一時変数の削除、同じレジスタの使い回しを積極的に行います。その結果、GDBでステップ実行するとソースコードの行番号が上下に飛び跳ねたり、変数の値を表示しようとしても `<optimized out>`（レジスタやメモリに実体が残っていない）と表示されたりします。

この限界に対する現実的な補正が、GCCやClangが用意している **`-Og`** オプションです。`-Og` はデバッグ体験を損なわない範囲の安全な最適化だけを有効にするため、「`-O0`（最適化なし）ほど遅くはなく、しかも行番号の対応や変数の観察がほぼ壊れない」という開発時の中間解を提供します。

#### (2) ソフトウェア・ウォッチポイントの低速さとハードウェア支援の個数制限

変数の中身が書き換わった瞬間に止めるウォッチポイントには、ハードウェア方式とソフトウェア方式の2種類があります。

* **ハードウェア・ウォッチポイント：** CPU内蔵のデバッグレジスタ（x86-64の `DR0`〜`DR3`）を使うため実行速度がほぼ落ちませんが、**同時に監視できる箇所が最大4箇所**（かつサイズ上限あり）に限られます。
* **ソフトウェア・ウォッチポイント：** ハードウェアの枠を超えた場合、GDBは1命令実行するたびにプロセスを止め（シングルステップ）、毎回対象メモリの値が変化したかを確認します。監視個数に制限はありませんが、実行速度が**数百倍〜数千倍も遅くなる**という厳しい限界があります。

そのため実務では、まずハードウェア・ウォッチポイントの枠内に収まるよう監視対象を絞り、さらに複雑な条件監視にはプログラム側へアサーション（`assert`）やサニタイザ（第5部 5-8節）を組み込む方法で補います。

#### (3) インラインアセンブラの保守性・移植性の限界と現代的な代替手段

インラインアセンブラは強力ですが、次のような大きなリスクを伴います。

* 特定のISA（x86-64等）に完全に固定され、ARMやRISC-Vへ移植できなくなります。
* 早期破壊 `&` や `"memory"` クローバーを1つ書き忘れただけで、`-O0` では動いたのに `-O2` でだけ壊れる再現困難なバグを生みます。

このため現代のシステムプログラミングでは、**「OSカーネルのシステム制御レジスタ操作やコンテクストスイッチなど、本当に代替不能な最小限の箇所だけ」**にインラインアセンブラを限定し、SIMD並列演算にはコンパイラの **組み込み関数（Intrinsics）**、マルチスレッドのアトミック操作には **C11 / C++11 の標準アトミックライブラリ（`<stdatomic.h>`）** を使うことが標準的な補正になっています。

> **【確認の問い】**
>
> 1. **（ULEB128 による可変長整数符号化の手計算）**
>     DWARF デバッグ情報で使われる符号なし可変長整数符号化（ULEB128）を用いて、10進数の整数 **`200`**（2進数で $\texttt{11001000}_2$）をバイト列へ変換してください。また、変換した2バイトを16進数で表し、各バイトのMSB（継続ビット）の意味とあわせて検算してください。
> 2. **（ソフトウェア・ブレークポイントの動作原理）**
>     x86-64 環境でデバッガがソフトウェア・ブレークポイント（`int 3` = `0xCC`）を使って対象プロセスを停止させたあと、処理を続行（`continue`）するとき、次の2つの手順が不可欠である理由をそれぞれ簡潔に説明してください。
>
>     * (a) 元の命令の先頭1バイトを復元したうえで、`%rip` の値を `1` 減らす理由。
>     * (b) そのまま通常再開せず、まず1命令だけシングルステップ実行してから再び `0xCC` を埋め戻す理由。
> 3. **（第2部への伏線：高級言語から機械語への翻訳パイプライン）**
>     第1部を通じて、C言語のプログラムが x86-64 の機械語命令・スタックフレーム・ELFセクションへ落ちた姿を見てきました。では、コンパイラは人間が書いたテキスト（ソースコード）を受け取ったとき、どのような段階（フェーズ）に分けて文字列を解析し、型をチェックし、無駄のない機械語命令列へ自動変換しているのでしょうか。
