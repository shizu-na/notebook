### 前節（1-3）の確認問題の解答

前節の最後に提示した3つの問いの解答を確認します。

1. **16バイト境界アラインメント違反のデバッグとパディング配置：**

    * **(a) `movaps` による強制終了の原因：**
        System V AMD64 ABI では **`call` 命令の実行直前に `%rsp` が16の倍数（16バイト境界）** である必要があります。`wrapper` に入った直後の `%rsp` は `0x7fffffffe008`（16の倍数 $+ 8$）であり、調整せずにそのまま `call printf` を実行すると、`printf` 入口で `%rsp = 0x7fffffffe000`（16の倍数）、さらに `printf` 内部の `pushq %rbp` 後に16バイト境界から8バイトずれた状態になります。その結果、16バイト整列を要求する SSE 命令（`movaps`）が境界違反を起こして強制終了（Segmentation Fault）します。

    * **(b) パディングを置く位置（`push` の前 vs 後）：**
        8バイトのパディング（`subq $8, %rsp`）は、**第7引数を `push` する「前」** に置く必要があります。

        * **前に置く場合（正解）：** `subq $8, %rsp`（`%rsp = 0x7fffffffdff8`）→ `pushq arg7`（`%rsp = 0x7fffffffdff0`、16バイト境界で `arg7` は `0x...dff0` に配置）→ `call g`（戻り番地を `0x...dfe8` へ積む）→ `g` のプロローグ（`%rbp = 0x...dfe0`）。このとき `g` 側が参照する `16(%rbp)` は `0x...dfe0 + 0x10 = 0x...dff0` となり、正確に第7引数 `arg7` を読めます。
        * **後に置く場合（誤り）：** `pushq arg7`（`0x...dff8`）→ `subq $8, %rsp`（`0x...dff0`）の順だと、`16(%rbp)`（`0x...dff0`）にはダミーのパディングが置かれてしまい、`arg7` が `24(%rbp)` へずれてしまいます。

2. **TCO の可否判定・カーネルでの Red Zone 禁止・レジスタ選択：**

    * **(a) 局所配列のアドレスを渡す場合の TCO 可否：**
        **適用できません。** TCO で `jmp B` を実行する前に関数 `A` のスタックフレームを解放すると、`buf` が置かれていたメモリ領域が未確保領域となり、`B` の実行中（スタック使用や割り込み）で上書きされて壊れてしまうためです。

    * **(b) カーネルビルドで `-mno-red-zone` が必須になる理由：**
        ユーザ空間では、OS カーネルがシグナルを配送する際に `%rsp` 下位128バイト（Red Zone）を飛び越えてシグナルフレームを作ることが保証されています。一方、カーネルモード実行中にハードウェア割り込みが発生すると、**CPU 自身が現在のカーネル `%rsp` の直下へ例外フレームを直接プッシュ**するため、Red Zone に置いていた局所データが即座に破壊されてしまいます。そのためカーネルでは Red Zone の使用を禁止する必要があります。

    * **(c) ループカウンタに選ぶべきレジスタ：**
        **`%r12`（callee-saved）** を選ぶ方が効率的です。`%r12` であれば関数のプロローグとエピローグで**各1回（合計2回）**退避・復元するだけでループ内は `helper()` を何度呼んでも値が保たれます。一方、`%r10`（caller-saved）を使うと `helper()` に上書きされる恐れがあるため、1000回の呼び出しのたびに退避と復元（合計2000回のメモリアクセス）が必要になってしまいます。

3. **`%rbp` チェーンからのバックトレース復元と `-fomit-frame-pointer`：**

    * **(a) 復元される戻り番地（近い順）：**
        各フレームにおいて `0(%rbp)` が1つ前の `%rbp`、`8(%rbp)` が戻り番地です。

        1. 現在のフレーム（`%rbp = 0x7000`）：`0x7008` より戻り番地は **`0x401184`**、呼び出し元の `%rbp` は `0x7000` の値 **`0x7030`** です。
        2. 1つ前のフレーム（`%rbp = 0x7030`）：`0x7038` より戻り番地は **`0x401120`**、さらに前の `%rbp` は `0x7030` の値 **`0x7060`** です。
        3. 2つ前のフレーム（`%rbp = 0x7060`）：`0x7068` より戻り番地は **`0x401050`**、次の `%rbp` は終端 `0x0000` のため終了です。

        したがって、戻り番地は順に **`0x401184` → `0x401120` → `0x401050`** となります。

    * **(b) `-fomit-frame-pointer` 時に参照するセクションと復元方法：**
        ELF バイナリ内の **`.eh_frame`**（または DWARF デバッグ情報の `.debug_frame`）を参照します。そこには各命令アドレスごとに「現在の `%rsp` から何バイト戻れば呼び出し元のフレーム境界（**CFA：Canonical Frame Address**）に到達するか」という逆算表が記録されており、それを使ってフレームを遡ります。

## 1-4. ELFバイナリ構造・セクションと記号表・再配置

### 1. 動機（Why）：なぜ機械語をただ並べるだけでは実行できず、バイナリ形式と再配置が必要なのか

前節（[1-3節](1-3.md)）までで、C言語の計算や分岐・関数呼び出しが1つひとつの機械語命令へ翻訳される仕組みを見てきました。ここで「それなら、機械語のバイト列をファイルにベタ書きすればそのまま実行できるのではないか」と思えるかもしれません。

しかし、現実のソフトウェア開発では、1つのプログラムを何十・何百ものソースファイル（`main.c`, `util.c`, `math.c`, ...）に分けて**分割コンパイル**するのが普通です。すると、単純な機械語の羅列では解決できない次の3つの課題が生じます。

1. **命令とデータを区別して配置する枠組みが必要：** [0-1節](../0/0-1.md)で確認した通り、ビット列そのものには「これは実行すべき命令か、書き換え可能な変数か、書き換え禁止の文字列定数か」という区別がありません。用途ごとに領域（**セクション**）を分けて管理するファイル形式が必要です。
2. **別ファイルの関数や変数のアドレスがコンパイル時には分からない：** `main.c` をコンパイルして `main.o` を作るとき、別ファイル `sub.c` にある大域変数 `x` や関数 `foo` が最終的にメモリの何番地へ置かれるかはまだ未定です。
3. **リンク時の配置単位と、OSが実行時にメモリへ載せる単位が異なる：** 複数のオブジェクトファイルを合体させて1つの実行ファイルへまとめる際、用途別のセクションを並べ直して住所を確定し、さらにOSが読み取り専用や実行可能といったメモリ保護権限を一括設定できる形へ整える必要があります。

Linuxをはじめとする多くのUNIX系OSでは、これらを統一的に扱うバイナリ形式として **ELF（Executable and Linkable Format）** を採用しています。本節では、ソースコードから実行ファイルができるまでの4段階の流れを押さえたうえで、ELFの内部構造・記号表・再配置の仕組みを具体的なアドレス計算で追っていきます。

### 2. 具体例と動作イメージ（Toy Model）

ELFの細かい構造に入る前に、2つの小さな実験で「ビルドの全体像」と「未確定アドレスがリンク時に埋まる瞬間」を確かめます。

#### 実験A：広義のコンパイルの4段階とオブジェクトファイルの結合

普段私たちが `gcc main.c sub.c` と1行打つだけで実行可能ファイル `a.out` が生成されますが、内部では次の4つの処理が順番に動いています（図1-4-1）。

1. **前処理（プリプロセス：`gcc -E`）：** `#include` でヘッダファイルを取り込み、`#define` マクロを展開します。
2. **狭義のコンパイル（`gcc -S` / 内部のコンパイラ本体 `cc1`）：** C言語のソースコードをアセンブリコード（`*.s`）へ翻訳します。
3. **アセンブル（`gcc -c` / `as`）：** アセンブリコードを機械語のバイト列へ変換し、**再配置可能オブジェクトファイル（`*.o`）** を生成します。
4. **リンク（`ld`）：** 複数の `*.o` や標準ライブラリ、さらにプログラムの開始点 `_start` から `main` を呼び終了処理を行うCランタイム起動コード（`crt*.o`）を合体させ、最終的な**実行可能ファイル（`a.out`）** を作ります。

#### 実験B：仮アドレス `00 00 00 00` がリンクで埋まる様子

次の2つのごく短いCファイルを別々にコンパイルしてみます。

```c
// main.c
extern int x;
int main(void) {
    return x;
}
```

```c
// sub.c
int x = 999;
```

現代のLinux環境のGCCはデフォルトで位置独立実行ファイル（PIE：[1-5節](1-5.md)）向けの間接参照を生成するため、ここでは直接の `%rip` 相対再配置が見えやすい **`-fno-pie`** 指定を前提にします。`gcc -fno-pie -c main.c` で `main.o` を作った直後に逆アセンブル（`objdump -dr main.o`）すると、`return x;` に対応する `%rip` 相対のロード命令は次のようになっています。

```text
   8:  8b 05 00 00 00 00    mov    0x0(%rip), %eax
          a: R_X86_64_PC32  x-0x4
```

`main.o` の段階では `x` の住所が不明なため、先頭2バイトのオペコード・ModR/M（`8b 05`）に続く変位4バイト（開始オフセット `0x8 + 2 = 0xa`）には **仮の値 `00 00 00 00`** が入っており、直下に「オフセット `0xa` の4バイトを、あとでシンボル `x` の `%rip` 相対値で埋めよ」というメモ（再配置情報）が添えられています。

続いて `main.o` と `sub.o` をリンクして `a.out` を作り、再び逆アセンブルすると、仮の `00 00 00 00` が次のように具体的な相対距離へ書き換わります（アドレス `0x1151`・`0x4010` は仕組みを見やすくした代表的な配置例です）。

```text
1151:  8b 05 b9 2e 00 00    mov    0x2eb9(%rip), %eax   # 0x4010 <x>
1157:  ... (次の命令)
```

この命令は6バイト長なので、次の命令の先頭アドレスは `0x1151 + 6 = 0x1157` です。そこに相対距離 `0x2eb9` を足すと `0x1157 + 0x2eb9 = 0x4010` となり、正確に `sub.o` から持ち込まれた変数 `x` の最終住所 `0x4010` を指しています（バイト列が `b9 2e 00 00` と逆順なのは[0-2節](../0/0-2.md)のリトルエンディアンによるものです）。

### 3. 構造・アルゴリズム・実装（What）

#### (1) ELF バイナリの3つのヘッダと「セクション vs セグメント」

Linuxのオブジェクトファイル（`*.o`）、実行可能ファイル（`a.out`）、共有ライブラリ（`lib*.so`）は、すべて共通の **ELF** 形式で書かれています。ファイルの先頭4バイトには、ELFファイルであることを示す識別子（マジックナンバー `0x7F 'E' 'L' 'F'`）が入っています。

ELFファイルには、目次の役割を果たす **3種類のヘッダ** があります（図1-4-2）。

| ヘッダの種類 | 主な確認コマンド | 役割 |
| :--- | :--- | :--- |
| **ELF ヘッダ** | `readelf -h` | ファイル先頭に必ず存在。64ビット/リトルエンディアン、エントリポイント（プログラム全体の真の開始点 `_start` の番地）、他ヘッダの位置を記す。 |
| **セクションヘッダ** | `readelf -S` / `objdump -h` | **リンク時の見方（Linking View）：** `.text` や `.data`、記号表、再配置情報など各セクションの位置・サイズ・属性の目次。 |
| **プログラムヘッダ** | `readelf -l` | **実行時の見方（Execution View）：** OSがメモリへロードするまとまりである**セグメント**の目次（実行可能ファイルだけでなく、共有ライブラリ `.so` やコアダンプファイルにも存在）。 |

ここで混同しやすい **セクション（Section）** と **セグメント（Segment）** の違いを押さえておきます。

* **セクション**は、アセンブラやリンカが扱う「用途別の細かい区分」です（`.text`, `.rodata`, `.data`, `.bss`, `.symtab` 等）。記号表やデバッグ情報など実行に直接不要なセクションは、ファイルサイズを小さくするため `strip` コマンドで後から削除することもできます。
* **セグメント**は、OSが実行ファイルをメモリへ読み込むときに「同じメモリ保護権限（読み・書き・実行）を持つ隣接セクションを1つに束ねたロード単位」です。たとえば実行可能かつ書き込み禁止（`r-x`）の `.text` 系はコードセグメントへ、読み取り専用（`r--`）の `.rodata` 系は読み取り専用セグメントへ、読み書き可能かつ実行禁止（`rw-`）の `.data` と `.bss` はデータセグメントへそれぞれまとめられ、OSがメモリ保護権限を管理する最小区画である **ページ（通常 4 KiB）** の境界に整列して配置されます。

#### (2) 4つの基本セクションとC言語の変数の配置

アセンブラ（`as`）は、ソースコード中の配置先切り替え指示（**ディレクティブ**：`.text`, `.data`, `.bss`, `.section .rodata`）に従い、各セクションごとの **ロケーションカウンタ**（先頭から何バイト目まで書き出したかを数えるしおり）を進めながら2進数データを書き出します。C言語の各要素は、次の4つの基本セクションへ振り分けられます。

| セクション名 | 格納されるもの | C言語の具体例 | 実行時のメモリ権限 |
| :--- | :--- | :--- | :---: |
| **`.text`** | CPUが実行する機械語命令列 | 関数本体（`main`, `add5` 等） | `r-x`（読込・実行） |
| **`.rodata`** | 読み取り専用データ（Read-Only Data） | 文字列リテラル `"hello\n"`、`switch` のジャンプテーブル | `r--`（読込専用） |
| **`.data`** | 初期値ありの静的変数（非ゼロ） | `int g1 = 999;`、`static int s1 = 888;` | `rw-`（読込・書込） |
| **`.bss`** | 未初期化（または0初期化）の静的変数 | `int g2;`、`static int a[1024];` | `rw-`（読込・書込） |

一方、関数内の普通の局所変数（`static` の付かない**自動変数**）は、関数が呼ばれるたびにスタックフレーム上（[1-3節](1-3.md)）へ動的に確保されるため、上記の4セクションのいずれにも実体を持ちません。

#### (3) 記号表（Symbol Table）の役割と読み方

アセンブラは、関数名や大域変数名などのラベルを見つけるたびに、その名前・セクション・仮アドレス（セクション先頭からのオフセット）・サイズ・公開範囲（グローバルかファイルローカルか）をまとめた **記号表（Symbol Table：`.symtab` セクション）** をオブジェクトファイルへ記録します。

記号表は `nm` コマンドで一覧表示できます。記号のアルファベットは配置セクションを、**大文字／小文字の別はスコープ**（大文字＝他ファイルから参照できるグローバル、小文字＝そのファイル内限定の `static` ローカル）を表します。

```c
int g1 = 999;          // 初期化済みグローバル → D (.data, global)
int g2;                // 未初期化グローバル   → B (.bss,  global)
static int s1 = 888;   // 初期化済みローカル   → d (.data, local)
static int s2;         // 未初期化ローカル     → b (.bss,  local)
extern int ext_var;    // 他ファイルで定義     → U (Undefined: 未定義参照)
int main(void) { ... } // グローバル関数       → T (.text, global)
```

関数内の自動変数が記号表に一切現れないのは、実行時に `%rbp` や `%rsp` からの相対オフセットでアクセスされるため、固定のメモリアドレスを持たないからです。なお、関数内の `static` 変数（例：`main` 内の `static int s3 = 777;`）は実行中ずっとメモリに残り続けるため `.data` に置かれますが、他関数の同名 `static` 変数と衝突しないよう、コンパイラが自動的に `s3.0` のように連番を付けて記号表へ登録します。

#### (4) 再配置（Relocation）のアルゴリズムと `S + A - P`

実験Bで見た通り、リンカ（`ld`）は次の2ステップで複数のオブジェクトファイルを1つの実行可能ファイルへ仕上げます。

1. **シンボル解決とセクション配置：** 全オブジェクトファイルの同種セクション（`.text` 同士、`.data` 同士など）を1列に連結し、すべてのグローバルシンボル（`T`, `D`, `B`）の最終的な **仮想アドレス**（プロセスごとに独立して割り当てられる見かけのメモリアドレス、詳細は[1-5節](1-5.md)および[第3部](../index.md#part-3)）を確定します。未定義シンボル（`U`）に対応する定義がどのファイルやライブラリにも見つからなければ、ここで **リンクエラー（`undefined reference to ...`）** になります。
2. **再配置（Relocation）：** 各オブジェクトファイルの再配置テーブル（`.rela.text` 等）を1行ずつ読み込み、機械語命令の中に仮置きされていた `00 00 00 00` を、確定した最終アドレスから計算した値へ書き換えます。

実験Bの `a: R_X86_64_PC32  x-0x4` を、System V AMD64 ABI の計算式で検算してみます（図1-4-3）。`R_X86_64_PC32`（32ビットのPC相対再配置）の埋め込み値は、次の式で厳密に定義されています。

$$\text{書き込む値} = S + A - P$$

* **$S$（Symbol）：** 対象シンボル `x` の最終確定アドレスであり、実験Bのリンク後では **`0x4010`** です。
* **$A$（Addend：調整値）：** 再配置エントリに記された補正値であり、`x-0x4` より **`-4`**（`-0x4`）です。
* **$P$（Place）：** 仮アドレスを書き換える場所の最終アドレスです。`mov 0x0(%rip), %eax`（`8b 05 00 00 00 00`）は先頭が `0x1151`、オペコード2バイトの直後が仮アドレス欄なので **`P = 0x1153`** です。

ここでなぜ `A = -4` が付くのかに注目してください。x86-64の `%rip` 相対アドレッシングの起点は、仮アドレス欄の先頭 `P = 0x1153` ではなく、**その4バイト先にある「次の命令の先頭アドレス `0x1157`」** です。`P` から `4` を足した `P + 4`（$= \texttt{0x1157}$）を基準にするには、式の上で $S - (P + 4) = S + (-4) - P$ とすれば一致します。なお、仮アドレス欄の後ろにさらに1バイトの即値が付く命令（たとえば `addl $1, x(%rip)`：機械語 `83 05 <4バイト変位> 01` や `movb $1, x(%rip)`：機械語 `c6 05 <4バイト変位> 01`）では、次の命令の先頭が `P + 4 + 1 = P + 5` になるため **`A = -5`** が記録されます（4バイト即値が付く `movl $1, x(%rip)` なら `A = -8` です）。このように命令ごとのオフセット差を統一的に吸収できるため、再配置エントリは独立した調整値 `A` を持っています。実際に実験Bの値を代入すると、

$$S + A - P = \texttt{0x4010} + (-4) - \texttt{0x1153} = \texttt{0x4010} - \texttt{0x1157} = \mathbf{\texttt{0x2EB9}}$$

となり、リトルエンディアンで4バイト **`b9 2e 00 00`** が `0x1153`〜`0x1156` へ書き込まれます。実行時、CPUは `%rip (0x1157) + 0x2EB9 = 0x4010` を計算し、正確に変数 `x` の値 `999` を読み出せるのです。

> **【コラム：機械語も文字も同じビット列：セクションの役割・W^X原則と命令キャッシュ同期】**
>
> [0-1節](../0/0-1.md)で、同じ1バイト `01010101`（`0x55`）がASCIIでは文字 `'U'`、x86-64の機械語では `pushq %rbp` になることを確認しました。この性質はELFバイナリの上でそのまま実験できます。アセンブリコードの `.text` セクションに、命令のニモニックではなく生データとして `.byte 0x55` と書いてアセンブルすると、逆アセンブラ（`objdump -d`）はそれを機械語命令 `push %rbp` として表示し、CPUもそのまま実行します。
>
> つまり、アセンブラにとっても主記憶にとっても「命令」と「データ」は同じバイト列に過ぎません（フォン・ノイマン型アーキテクチャ）。両者を厳格に区別しているのは、**「書き込み可能（`w`）と実行可能（`x`）を同じメモリページへ同時に与えない」という W^X（Write XOR Execute）原則** に基づくELFのセグメント設計（`.text` は `r-x`、`.data` は `rw-`）と、それをハードウェアで強制するOSのページ保護（[第3部](../index.md#part-3)・[第5部](../index.md#part-5)）です。もしこの境界が曖昧であれば、入力データとして読み込んだ文字列を機械語として誤実行させる攻撃（[5-8節](../5/5-8.md)）が容易に成立してしまいます。
>
> ここで興味深い例外が、プログラムの実行中に新しい機械語を生成して動かす **JIT コンパイラ**（JavaScript V8 や JVM、[2-1節](../2/2-1.md)）です。JIT コンパイラは W^X 原則を守るため、まずメモリ領域を `rw-`（読み書き可・実行禁止）で確保して機械語のバイト列を書き込み、生成が終わった段階で OS の `mprotect` システムコールを使って権限を `r-x`（読み取り・実行可・書き込み禁止）へ切り替えてからジャンプします。
>
> さらにハードウェアの観点でも、主記憶上では命令とデータが一体である一方、CPU内部のL1キャッシュは高速化のため **L1命令キャッシュ（L1I）と L1データキャッシュ（L1D）に分離** されています（[0-5節](../0/0-5.md)で触れた修正ハーバード構造）。そのため、JIT や自己書き換えコードでメモリへ機械語を書き込んだ直後は、新しいバイト列が L1D 側にあって L1I 側に古い内容が残っている可能性があります。x86-64 ではハードウェアが両者の整合性を自動で保ちますが、RISC-V（`fence.i` 命令）や ARM64 では、データとして書き込んだ機械語を実行する前にソフトウェアから明示的に命令キャッシュ同期命令を発行する必要があります（[1-6節](1-6.md)で扱うデバッガによる命令書き換えでも同様の仕組みが関わります）。

### 4. 限界と補正（Critique & Adaptation）

#### (1) 未初期化の巨大配列によるファイル肥大化と `.bss` セクションの工夫

C言語で `int buf[1024 * 1024];`（4 MiBの未初期化大域配列）を宣言したとします。もしアセンブラが4 MiB分の `0x00` をそのままオブジェクトファイルや実行ファイルへ書き込んでしまうと、わずか数行のプログラムなのにディスク上のファイルサイズが4 MiBも膨らみ、ロード時のディスク読み込み時間も浪費してしまいます。

この限界に対するELFの補正が、**`.bss` セクションの特殊扱い（`NOBITS` 属性）** です。`.bss` は「中身はすべて `0` なのでファイルには一切書かず、『起動時に 4 MiB 分の空き地を用意せよ』というサイズメモだけ残す」という特別扱いになっており、セクションヘッダに**実行時に必要なバイトサイズ（4 MiB）とアラインメントというメタ情報だけ**を記録します。そのため、ファイル上の `.bss` の占有サイズは **0 バイト** です。プログラムを起動するとき、OSのローダがこのサイズ情報を見てメモリ上に4 MiBの領域を確保し、ゼロで初期化して渡します（[第3部](../index.md#part-3) [3-7節](../3/3-7.md)の遅延割当により、実際には書き込まれるまでRAM上の実区画である物理ページすら消費しない最適化も働きます）。

#### (2) 大規模開発におけるシンボル衝突とスコープ制御（`static`・`weak`・`.L`）

数十人・数百人で開発する大規模プログラムでは、別々のファイルに書いた補助関数や大域変数の名前が偶然かぶる（**シンボルの多重定義エラー**）問題が頻発します。また、関数内の `if` や `while` ごとに生成される大量のジャンプ先ラベルをすべて記号表へ入れると、記号表自体が肥大化してリンクが遅くなります。

ELFとツールチェインでは、次の3つの仕組みでこれを補正しています。

1. **ローカルシンボル（`static`）：** C言語で関数や大域変数に `static` を付けると、ELF記号表で `LOCAL`（`nm` で小文字 `t`, `d`, `b`）としてマークされ、他ファイルから隠蔽されます。別ファイルに同名の `static` 関数があっても衝突しません。
2. **Weak シンボル（`.weak` / `__attribute__((weak))`）：** 「他に通常の（強い）定義があればそちらを優先し、なければこのデフォルト定義を使う」という弱いシンボルを定義できます。組込みシステムのデフォルト割り込みハンドラや、ライブラリのフック関数をユーザが上書きしたい場面で広く使われます。
3. **`.L` プレフィックスによる記号表からの除外：** コンパイラが制御フロー用に自動生成する一時ラベルには `.L2` のように先頭へ `.L` を付けます。関数内の `if` や `while` の分岐先は同じ関数内での相対距離がアセンブル段階で確定し、別ファイルのリンカから名前で参照されることがないため、記号表へ載せる必要がありません。ELFのアセンブラは `.L` で始まるラベルを記号表（`.symtab`）へ出力しない規則になっており、記号表のサイズを小さく保ちます。

### 5. 接続と展望（Bridge）：本節の内容が後半のどの部に繋がるか

1. **次節（[1-5節](1-5.md)：静的リンクと動的リンク［PIC・PIE・GOT/PLT］）：**
    本節では、`main.o` と `sub.o` のようにリンク時にすべての住所が確定するケースを見ました。次節では、`printf` のような標準ライブラリを全実行ファイルへ毎回コピーする無駄を省く**動的リンク**と、実行時まで住所が決まらない関数を呼び出す **GOT / PLT** の仕組みへ進みます。

2. **[第2部](../index.md#part-2)（[2-5](../2/2-5.md)・[2-6節](../2/2-6.md)：コンパイラの記号表とコード生成）：**
    コンパイラ自身がソースコード解析のために持つ記号表（[2-5節](../2/2-5.md)）と、コード生成器が `.text`/`.data`/`.rodata` セクションや `.L` ラベルを実際に出力する手順（[2-6節](../2/2-6.md)）へ直結します。

3. **[第3部](../index.md#part-3)（[3-8節](../3/3-8.md)：OSのブートとリンカスクリプト）：**
    OSカーネル自身のELFファイルを作るときは、通常のプログラムと違い「`.text` を物理アドレス `0x80000000` から配置し、`trampoline` をページ境界に揃えよ」といった厳密な配置指定が必要になります。これをリンカへ指示するのが**リンカスクリプト**です。

4. **[第5部](../index.md#part-5)（[5-8節](../5/5-8.md)：メモリ破壊攻撃と多層防御）：**
    本節コラムで触れた「コードセグメントは `r-x`、データ／スタックは `rw-`（実行禁止＝NXビット）」という権限分離が、現代のセキュリティ防御の土台として再登場します。

### 理解度チェック（次節へ進む前の確認）

本節のセクション配置・`.bss` の仕組み・`R_X86_64_PC32` 再配置計算・シンボル解決を具体的な問題で確認します。

> **【確認の問い】**
>
> 1. **（セクション配置・記号表と `.bss` が実行ファイルサイズを増やさない理由）**
>     ある C ファイルに次の3つの宣言があります。
>
>     ```c
>     static int cnt = 0;         // ①
>     const char *msg = "hi";     // ② ポインタ変数 msg と文字列リテラル "hi"
>     int big_buf[1024 * 1024];   // ③（4 MiB の未初期化大域配列）
>     ```
>
>     * (a) ① `cnt`、② 文字列リテラル `"hi"` 本体およびポインタ変数 `msg`、③ `big_buf` は、それぞれどの ELF セクション（`.text`, `.rodata`, `.data`, `.bss`）へ配置され、`nm` ではどの記号（`D`, `d`, `B`, `b` 等）で表されるでしょうか（文字列リテラル `"hi"` 本体はセクション名のみで構いません）。
>     * (b) ③ の配列は実行時に 4 MiB のメモリを消費しますが、ビルドしてできる実行ファイルのディスクサイズはほとんど増えません。ELF が `.bss` に対して行っている工夫（`NOBITS` 属性と起動時の動作）を説明してください。
>
> 2. **（`A = -5` と負のオフセットを含む `R_X86_64_PC32` 再配置の手計算）**
>
>     * (a) あるオブジェクトファイルの `.text` に、大域変数 `flag` に `1` を足す7バイト命令 `addl $1, flag(%rip)`（機械語 `83 05 00 00 00 00 01`：先頭2バイトがオペコードと ModR/M、続く4バイトが仮変位欄、末尾1バイトが即値 `01`）が含まれており、再配置エントリは `R_X86_64_PC32  flag - 5` です。リンク後、この命令の先頭が `0x2000`、`flag` の最終アドレスが `0x5010` に決まったとき、書き換え位置 $P$、式 $S + A - P$ で計算される32ビット相対値（16進数）、リトルエンディアンで埋め込まれる4バイト列、および加数 $A$ が `-4` でなく `-5` になる理由を答えてください。
>     * (b) 別の6バイト命令 `mov 0x0(%rip), %eax`（`8b 05 00 00 00 00`、再配置 `R_X86_64_PC32  table - 4`）で、命令の先頭が `0x3000`、参照先シンボル `table` が命令より低位アドレスの `0x2FF0` に配置された場合、書き込まれる32ビット符号あり相対値（16進数8桁）とリトルエンディアンの4バイト列はどうなるでしょうか。
>
> 3. **（複数ファイル間のシンボル解決・弱シンボル・未定義参照エラーの診断）**
>     2つのオブジェクトファイル `a.o` と `b.o` を `ld` でリンクします。次の3つのケースについて、リンクが成功するかエラーになるかを判定し、その理由を答えてください。
>
>     * (a) `a.o` と `b.o` の両方に `static void helper(void)` が定義されている場合。
>     * (b) `a.o` に `__attribute__((weak)) void hook(void)` が定義され、`b.o` に通常の（強い）`void hook(void)` が定義されている場合。
>     * (c) `a.o` に `extern int calc(int);` を呼び出すコードがあり、`b.o` には `static int calc(int)` が定義されている場合。
