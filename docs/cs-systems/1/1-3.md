### 前節（1-2）の確認問題の解答

前節の最後に提示した3つの問いの解答を確認します。

1. **`movw` vs `movl` の上位ビット挙動と `leaq` による整数演算：**

    * **(a) `movw` と `movl` 実行後の `%rax` の値と理由：**

        * **`movw $0x00FF, %ax` 実行後：** 16ビットレジスタへの書き込みでは上位48ビットがそのまま保持されるため、`%rax` は **`0x11223344556600FF`** になります。
        * **`movl $0x000000FF, %eax` 実行後：** x86-64 では32ビットレジスタへ書き込むと上位32ビットが自動的にすべて `0` クリアされるため、`%rax` は **`0x00000000000000FF`** になります。これは、古い上位ビットへの依存によるアウトオブオーダ実行の詰まり（部分レジスタ・ストール）を防ぎ、短い32ビット命令で64ビット定数を安全に初期化できるようにする設計規則です。

    * **(b) `leaq 16(%rdi, %rdi, 8), %rax` の計算結果と副作用：**
        実効アドレス計算式 $\text{base} + \text{index} \times \text{scale} + \text{disp}$ に当てはめると、$x + x \times 8 + 16 = \mathbf{9x + 16}$ を計算しています。`%rdi = 10` のときは $9 \times 10 + 16 = \mathbf{106}$ になります。また、`leaq` はアドレス値のみを計算してレジスタへ格納する命令であり、**メモリ参照もステータスフラグ（`%rflags`）の更新も一切行いません**。

2. **`cmpb` の4フラグ判定と符号あり／なし分岐の食い違い（`%al = 0x80`, `%bl = 0x7F`）：**

    * **(a) 整数解釈と4つのステータスフラグ：**

        * **符号あり8ビット整数（2の補数）：** `%al` $= \mathbf{-128}$、`%bl` $= \mathbf{+127}$ です。
        * **符号なし8ビット整数：** `%al` $= \mathbf{128}$、`%bl` $= \mathbf{127}$ です。
        * **`cmpb %bl, %al`（`%al - %bl`）の結果とフラグ：** $\texttt{0x80} - \texttt{0x7F} = \mathbf{\texttt{0x01}}$ となり、**`ZF = 0`**（結果が0でない）、**`SF = 0`**（結果の最上位ビットが0）、**`CF = 0`**（符号なし $128 - 127 = 1$ で繰り下げなし）、**`OF = 1`**（符号あり $(-128) - (+127) = -255$ は範囲外で、負数から正数を引いて正数になったためオーバーフロー発生）になります。

    * **(b) `jg` と `ja` の分岐判定：**

        * **符号あり `jg`（`ZF == 0 && SF == OF`）：** `ZF == 0` は満たしますが、`SF (0) != OF (1)` となるため**ジャンプしません**（$-128 > +127$ は偽）。
        * **符号なし `ja`（`CF == 0 && ZF == 0`）：** `CF == 0` かつ `ZF == 0` をともに満たすため**ジャンプします**（$128 > 127$ は真）。

3. **`switch` 文の範囲チェック `subl`＋`ja` と疎な `case` 値の翻訳判断：**

    * **(a) `subl $10, %eax`＋`cmpl $4, %eax`＋`ja .L_default` で上下限を同時に弾ける理由：**

        * **`x = 9`（下限未満）のとき：** `subl $10, %eax` の結果は $9 - 10 = -1$（32ビット2の補数で **`0xFFFFFFFF`**）になります。これを符号なし32ビット整数として解釈すると $2^{32} - 1 = 4{,}294{,}967{,}295 > 4$ となるため、符号なし比較の `ja` で `.L_default` へジャンプします。
        * **`x = 15`（上限超過）のとき：** `subl $10, %eax` の結果は $15 - 10 = 5 > 4$ となるため、同じく `ja` で `.L_default` へジャンプします。
        * 一方、`10`〜`14` の範囲内の値だけが `0`〜`4` へ移り、そのままジャンプテーブルの添字として使えます。こうして負数への折り返しを利用することで、1回の `ja` だけで下限未満と上限超過を同時に弾けます。

    * **(b) 飛び飛び（疎）な `case` 値の問題とコンパイラの翻訳戦略：**
        `1`〜`10000000` の範囲に単純なジャンプテーブルを作ると、間の約1,000万個分のダミーエントリ（4バイト相対オフセット方式でも約40 MB、8バイト方式なら約80 MB）を `.rodata` に確保することになり、メモリとバイナリサイズを著しく浪費します。そのため現代のコンパイラは、このような疎な `case` 値に対しては**比較による二分探索木（$O(\log n)$）**（`case` 数がごく少ない場合は単純比較列 $O(n)$、密な塊がある部分だけ局所的にジャンプテーブルを併用するハイブリッド戦略）を選択します。

## 1-3. スタックフレームと関数呼び出し規約（ABI）

### 1. 動機（Why）：なぜ「関数を呼んで戻る」ために詳細な約束事（ABI）が必要なのか

C言語などの高級言語では、`y = add5(10);` のように関数を呼び出すのはごく自然な操作です。しかし、CPUの機械語の世界には「関数」という高級な概念はなく、あるのは「レジスタ」「一直線のメモリ」「プログラムカウンタ `%rip` を書き換えるジャンプ命令」だけです。

複数の関数、さらには別々のファイルや別々のコンパイラで作成されたライブラリ関数（たとえば `printf`）同士が、互いに中身を知らないまま正しく連携するためには、次の4つの問題をすべて解決しなければなりません。

1. **どこへ戻るか：** 関数 `add5` が `main` の3行目から呼ばれたのか、別の関数 `foo` の12行目から呼ばれたのかを記憶し、終わったら正しい場所へ戻る仕組みが必要です。
2. **引数と返り値をどこで受け渡すか：** 呼び出す側（**caller**）が引数を置いた場所と、呼ばれた側（**callee**）が引数を取りに行く場所が1バイトでもずれていれば計算が破綻します。
3. **局所変数をどこへ置くか：** 再帰関数 `fact(5) → fact(4) → ...` のように同じ関数が同時に何重にも動き出したとき、それぞれの呼び出しが持つ局所変数 `n` が上書きし合わない隔離場所が必要です。
4. **有限のレジスタを誰が守るか：** x86-64の汎用レジスタは16本しかありません。呼び出した先の関数が勝手にすべてのレジスタを上書きしてしまったら、呼び出し元の計算途中の値が消えてしまいます。

これらをバイナリレベルで統一した約束事が **ABI（Application Binary Interface）** の中核である **関数呼び出し規約（Calling Convention）** です。本節では、Linuxの標準規格である **System V AMD64 ABI** を題材に、`call`/`ret` とスタックフレームの動作を1命令ずつ追っていきます。

---

### 2. 具体例と動作イメージ（Toy Model）

規約の全体像に入る前に、最も小さな関数呼び出しの2つの実験で「戻り番地の出し入れ」と「スタックフレームの積み下ろし」を確認します。

#### 実験A：`main` → `foo` → `bar` の入れ子呼び出しとコールスタック

`main` が `foo` を呼び、`foo` がさらに `bar` を呼ぶ状況を考えます。関数の実行が終わって戻る順番は、`bar → foo → main` と**呼び出した順番のちょうど逆**になります。

この「最後に積んだものを最初に取り出す（LIFO：Last In, First Out）」動きにそのまま噛み合うのが、メモリ上に確保される **コールスタック（Call Stack）** です。x86-64のスタックは、**高位アドレス（大きな番地）から低位アドレス（小さな番地）に向かって下向きに成長**し、スタックポインタ **`%rsp`** が常にスタックの一番上（最も小さい使用中番地）を指します。

x86-64の `call` 命令と `ret` 命令は、このスタックを使って次の複合動作を1命令で行います（図1-3-1）。

* **`call foo` の動作：**

    1. 次に実行すべき命令のアドレス（`call` 命令自身の番地ではなく、**`call` のすぐ次の命令の番地**＝**戻り番地**）をスタックへプッシュします（命令フェッチ完了時点で `%rip` はすでに次の命令を指しているため、`%rsp -= 8; *(%rsp) = %rip;` がそのまま次の命令の番地を積みます）。
    2. `%rip` を `foo` の先頭番地へ書き換えてジャンプします。

* **`ret` の動作：**

    1. スタックトップから8バイトの戻り番地をポップします（`%rip = *(%rsp); %rsp += 8;`）。
    2. 取り出した戻り番地から実行を再開します。

たとえば `main`（`0x401107`）で `call foo` を実行すると、次の命令 `0x40110C` がスタックに積まれます。さらに `foo` の中で `call bar` を実行すると、`foo` 内の次の命令がさらにその上へ積まれます。`bar` が `ret` を実行すれば `foo` へ戻り、`foo` が `ret` を実行すれば `main` の `0x40110C` へ正確に戻れるのです。

#### 実験B：小さな関数 `add5(int n)` のプロローグとエピローグ

小さな関数 `int add5(int n) { return n + 5; }` を最適化なし（`gcc -S`）でコンパイルすると、本体の計算の前後に定型の準備コードと後片付けコードが付きます。

```asm
add5:
    pushq %rbp            # [プロローグ 1] 呼び出し元の %rbp をスタックへ退避
    movq  %rsp, %rbp      # [プロローグ 2] 今の %rsp を、この関数の基準 %rbp に設定
    movl  %edi, -4(%rbp)  # 引数 n (%edi) を自フレームの局所領域へ保存
    movl  -4(%rbp), %eax  # n を取り出し
    addl  $5, %eax        # n + 5 を返り値レジスタ %eax へ
    popq  %rbp            # [エピローグ 1] 呼び出し元の %rbp を復元
    ret                   # [エピローグ 2] 戻り番地をポップして呼び出し元へ戻る
```

`pushq %rbp` と `movq %rsp, %rbp` の2命令で「自分の関数専用の作業台」の基準点を確立し、終わったら `popq %rbp` と `ret` で元へ戻しています（なお、ここで `subq` で `%rsp` を下げずに `-4(%rbp)` へ書き込んでいるのは、他の関数を呼ばない関数だけに許された **Red Zone** の利用によるものです。詳細は4-(3)で後述します）。次の第3節で、この構造を一般の関数へ広げます。

---

### 3. 構造・アルゴリズム・実装（What）

#### (1) API と ABI の違い

どちらも互換性を保つための規格ですが、対象とするレイヤが異なります。

* **API（Application Programming Interface）：** **ソースコード**レベルの規格です（例：UNIX系OSの標準API規格である POSIX の `open` や `printf` の関数名・引数の型・戻り値の意味）。同じAPIを満たすOS同士なら、ソースコードを書き換えずに**再コンパイルすれば**動きます。
* **ABI（Application Binary Interface）：** **機械語バイナリ**レベルの規格です。関数呼び出し規約（引数レジスタ・スタック配置・レジスタ退避規則）、データ型のサイズとアラインメント、エンディアン、バイナリ形式（ELF：[1-4節](1-4.md)）を定めます。同じABIに従っていれば、別々のコンパイラ（たとえばGCCとClang、あるいはCとRust）で作られたコンパイル済みの部品ファイル（**オブジェクトファイル**）同士を**再コンパイルなしで**そのままリンクして呼び出せます。

#### (2) スタックフレームと関数プロローグ・エピローグ

関数呼び出し1回分に対してスタック上に割り当てられる領域を **スタックフレーム（Stack Frame）** と呼びます。スタックフレームには、戻り番地、退避された呼び出し元の `%rbp`、退避されたレジスタ、局所変数、さらにレジスタに入りきらない引数などが収められます。

関数の実行中は `push`/`pop` でスタックポインタ `%rsp` が動くことがあるため、局所変数へ毎回 `%rsp` からの距離でアクセスしようとするとオフセットが変動して管理が煩雑になります。そこで、関数の入口で **ベースポインタ（フレームポインタ）`%rbp`** をスタックフレームの基準位置に固定しておけば、関数内で `%rsp` がどれだけ動いても、局所変数は常に `-8(%rbp)`, `-16(%rbp)` のように一定の負オフセットで参照できます。

局所変数に32バイトを使う一般的な関数の入口（**関数プロローグ**）と出口（**関数エピローグ**）は次の形をとります（図1-3-2）。

```asm
# 関数プロローグ（入口）
    pushq %rbp            # 1. 呼び出し元の %rbp を退避
    movq  %rsp, %rbp      # 2. 新しい基準点 %rbp を設定
    subq  $32, %rsp       # 3. 局所変数用にスタックを 32 バイト伸ばす（低位へ減算）

    ... （関数本体の処理） ...

# 関数エピローグ（出口）
    leave                 # movq %rbp, %rsp; popq %rbp と同じ（局所領域解放＋旧 %rbp 復元）
    ret                   # スタックトップの戻り番地へ戻る
```

なお、x86-64にはプロローグの3命令を1命令で行う `enter $32, $0` 命令も歴史的に用意されていますが、入れ子関数のレキシカルスコープ（ディスプレイポインタ）を扱う汎用仕様を含むため、CPU内部のマイクロコードで多数のマイクロオペレーションへ展開されてしまい、個別の3命令より大幅に遅延が大きくなります（現代のCPUでも10サイクル前後を要することがあります）。そのため現代のコンパイラは `enter` を避けて上の3命令を出力し、出口だけ高速な `leave` 命令を使うのが一般的です。

また、各フレームの `%rbp` が指す番地には「1つ前の関数の `%rbp`」が入っているため、**メモリ上のすべてのスタックフレームは `%rbp` を辿る連結リスト（数珠つなぎ）** になっています。デバッガのバックトレース（関数呼び出し履歴の表示）は、この連結リストを順に遡ることで実現されます。

#### (3) System V AMD64 ABI の引数渡しと返り値

System V AMD64 ABI では、メモリへの読み書きを減らして高速化するため、整数・ポインタ型の引数は最初の6個までを**レジスタ渡し**にします。

* **第1〜第6引数：** `%rdi`, `%rsi`, `%rdx`, `%rcx`, `%r8`, `%r9` の順に渡します（浮動小数点引数は別の128ビット浮動小数点・SIMD用レジスタ `%xmm0`〜`%xmm7` で最大8個渡します）。
* **第7引数以降：** 入りきらない引数は、呼び出し元が**右から左の逆順**でスタックへプッシュしてから `call` を実行します。逆順に積むことで、可変長引数関数のように引数の総数が呼び出しごとに変わる場合でも、第7引数が常に固定位置 **`16(%rbp)`**、第8引数が **`24(%rbp)`**（戻り番地 `8(%rbp)` と古い `%rbp` `0(%rbp)` のすぐ高位側）に配置され、先頭から順に取り出せます（図1-3-3）。
* **返り値：** 8バイト以下の整数・ポインタは **`%rax`** へ入れて返します。整数クラスに分類されるメンバからなる16バイト以下の小さな構造体も `%rax` と `%rdx` の2本で返せます（浮動小数点メンバは `%xmm0`・`%xmm1` を使い、16バイトを超える大きな構造体は呼び出し側が確保したメモリ領域へ書き戻します）。
* **可変長引数関数の隠しルール：** `printf` のように引数の個数が不定の関数を呼ぶときは、呼び出し前に **`%al` レジスタへ「使用した浮動小数点（XMM）レジスタの個数」**（使わなければ `0`）を入れておく決まりになっています。これは、`printf` のように浮動小数点引数を1つも渡さない呼び出しが多い関数で、先頭で `%al` を見て必要な本数だけ XMM レジスタを退避することで、未使用の8本をすべてメモリへ退避するコストを省くためです。

#### (4) caller-saved レジスタと callee-saved レジスタの役割分担

関数呼び出しをまたいで16本のレジスタの値をどう守るかについて、ABIはレジスタを2つのグループに厳密に分けています。

| 分類 | 対象レジスタ（x86-64） | 誰が値を守る責任を持つか | 使い分けの考え方 |
| :--- | :--- | :--- | :--- |
| **caller-saved**<br>（揮発性：関数を呼ぶと上書きされてよい一時メモ用） | `%rax`, `%rcx`, `%rdx`, `%rsi`, `%rdi`, `%r8`〜`%r11` | **呼び出し側（caller）** | 呼ばれた関数が自由に上書きしてよい。呼び出し元が `call` の後も値を使いたい場合は、`call` の前に自分でスタックへ退避する。 |
| **callee-saved**<br>（不揮発性：関数を呼んでも値が保たれる長期保持用） | `%rbx`, `%rbp`, `%rsp`, `%r12`〜`%r15` | **呼ばれた側（callee）** | 呼ばれた関数が使う場合は、プロローグでスタックへ退避し、エピローグで必ず元の値へ復元してから戻る。 |

この2分法は、無駄なメモリ退避を最小限に抑えるための合理的な設計です。他の関数を呼ばない短い関数（葉関数）は **caller-saved レジスタだけ** を使えば退避・復元が一切不要になります。一方、ループの中で何度も別の関数を呼ぶ関数は、ループカウンタなどを **callee-saved レジスタ** へ置いておけば、`call` のたびに退避し直さずに済みます。

> **【コラム：末尾コール最適化（TCO）で戻り番地が変化する仕組み】**
>
> 関数 `A` の最後の処理が「別の関数 `B` を呼んで、その戻り値をそのまま自分の戻り値として返す（`return B(x);`）」であるような呼び出しを **末尾呼び出し（Tail Call）** と呼びます。
>
> 普通に翻訳すると、`A` は `call B` で戻り番地をスタックへ積み、`B` から戻ってきた直後に何もせずすぐ `ret` で `main` へ戻ります。ここでコンパイラは、`A` のスタックフレームを先に片付けたうえで `call B` を **無条件ジャンプ `jmp B`** へ置き換えることがあります（**末尾コール最適化：Tail Call Optimization, TCO**）。すると、`B` が実行されているときのスタックトップには `A` への戻り番地ではなく **`main` への戻り番地** がそのまま残っており、`B` の `ret` 命令は `A` を飛び越して直接 `main` へ帰還します。
>
> たとえば1から $n$ の総和を末尾再帰で書く `long sum_tail(long n, long acc)`（`n == 0` なら `acc`、そうでなければ `return sum_tail(n - 1, acc + n);`）を比べてみます（`n` が `%rdi`、`acc` が `%rsi`）。通常版では `call` 実行前に `%rsp` を16バイト境界へ揃えるための8バイト調整（詳細は4-(1)）も必要になります。
>
> ```asm
> # 通常版（毎回 call でスタックフレームを積む：n が大きいとスタック溢れ）
> sum_tail:
>     testq %rdi, %rdi
>     je    .L_ret
>     addq  %rdi, %rsi
>     subq  $1, %rdi
>     subq  $8, %rsp        # 16バイト境界合わせ（入口では %rsp が 16の倍数 + 8）
>     call  sum_tail        # 戻り番地を積んで再帰呼出し
>     addq  $8, %rsp        # スタック復元
>     ret
> .L_ret:
>     movq  %rsi, %rax
>     ret
> ```
>
> ```asm
> # TCO 適用版（call の代わりに jmp で先頭へ戻る：スタック消費 O(1)）
> sum_tail:
>     testq %rdi, %rdi
>     je    .L_ret
>     addq  %rdi, %rsi
>     subq  $1, %rdi
>     jmp   sum_tail        # 戻り番地を積まずに直接ジャンプ（実質 while ループ）
> .L_ret:
>     movq  %rsi, %rax
>     ret
> ```
>
> ただし、TCO はいつでも適用できるわけではありません。① 自分の局所変数のアドレスを `B` へ渡している場合（フレームを片付けるとその局所変数が壊れる）、② `B` の引数が7個以上で自分のフレームより多くのスタック引数領域を必要とする場合、③ C++ の局所オブジェクトのデストラクタなど `B` から戻ったあとに実行すべき後処理が残っている場合は、TCO を適用できません。また、TCO が効くとスタック上に `A` のフレームが残らなくなるため、クラッシュ時のバックトレース（[1-6節](1-6.md)）から関数 `A` が消えて原因調査が難しくなるというデバッグ上の副作用もあります。

### 4. 限界と補正（Critique & Adaptation）

ABIの標準ルールを現実の高速実行や特殊な環境へ当てはめると、次の3つの制約と工夫が現れます。

#### (1) `call` 時の16バイト境界アラインメント制約

System V AMD64 ABIでは、**`call` 命令を実行する直前の時点で、スタックポインタ `%rsp` が必ず16の倍数（16バイト境界）になっていなければならない**と定められています（図1-3-3）。

理由は、呼ばれた関数（特にC標準ライブラリ `libc` の `printf` や `memcpy` など）の内部で、16バイト境界を厳格に要求する高速な128/256ビットベクトル命令（SSE/AVX の `movaps` 等）が使われるためです。スタックは低位アドレスへ減算方向に伸びるため、`call` 命令で8バイトの戻り番地がプッシュされると、16の倍数から $8$ を引いた値（16進数表記の末尾が `8`、すなわち16の倍数 $+ 8$）になります。そこにプロローグの `pushq %rbp` でさらに8バイト引かれると、合計16バイト減算されてちょうど再び16の倍数へ戻ります。

もし手書きのアセンブリや自作コンパイラで、第7引数を1個（8バイト）だけ積んだまま `call` を実行してしまうと、`%rsp` が16の倍数から8バイトずれた状態でライブラリ関数へ突入し、不正なメモリアクセスによる強制終了（Segmentation Fault）でクラッシュすることがあります。これを防ぐため、奇数個の8バイト引数をスタックへ積む前には、ダミーの8バイト調整（`subq $8, %rsp`）を挟んで16バイト境界を揃えます。

#### (2) `-fomit-frame-pointer` とバックトレースの難化

プロローグとエピローグで毎回 `%rbp` を退避・更新するのは、小さな関数ほど相対的なオーバーヘッドになり、しかも貴重な汎用レジスタを1本潰してしまいます。そこで現代のコンパイラは、最適化オプション（`-O1` 以上）を付けるとデフォルトで **`-fomit-frame-pointer`** を有効にし、`%rbp` をフレームポインタとして使わず普通の汎用レジスタへ解放します（局所変数はすべて `%rsp` からの固定オフセットで参照します）。

しかしこの最適化には副作用があります。図1-3-2で見た「古い `%rbp` の連結リスト」がメモリ上から消えてしまうため、クラッシュ時やプロファイリング時にスタックを辿って関数呼び出し履歴（バックトレース）を復元できなくなるのです。この限界に対する補正が、`%rbp` の数珠つなぎを省く代わりに「この命令位置では `%rsp` から何バイト戻れば呼び出し元のフレーム境界か」を逆算表として記録しておく仕組みです。この表はELFバイナリ内の専用セクション **`.eh_frame`（Exception Handling Frame）** や DWARF デバッグ情報（[1-6節](1-6.md)）に格納され、フレーム境界の基準アドレスは **CFA（Canonical Frame Address）** と呼ばれます（近年ではプロファイラ高速化のために、OSディストリビューション全体で `-fno-omit-frame-pointer` へ戻す動きもあります）。

#### (3) Red Zone（レッドゾーン）の前提条件とカーネルでの禁止

実験Bの `add5` のアセンブリをよく見返すと、`-4(%rbp)`（すなわち `%rsp - 4`）へ書き込んでいるのに、事前に `subq` で `%rsp` を下げていません。通常なら `%rsp` より低位（未使用領域）へ書くと、その瞬間に割り込みやシグナルが起きたとき上書きされて壊れそうです。

これが許されるのは、System V AMD64 ABIが **`%rsp` より低位128バイトの領域を Red Zone（レッドゾーン）** として保護しているためです（図1-3-3）。Linuxカーネルはユーザプロセスへシグナルを配送する際、この128バイトを飛び越えてさらに下へシグナル用フレームを作ることを保証しています。そのため、他の関数を呼ばない葉関数は `subq`/`addq` の2命令を省いて高速に局所変数を使えます。

ただし、この前提が成り立たない場所があります。**OSカーネル内部のコード**です。カーネルモード実行中にハードウェア割り込みが入ると、CPU自身が現在のカーネルスタックポインタ `%rsp` のすぐ下へ例外フレームを直接プッシュしてしまうため、Red Zone は即座に破壊されます。そのためLinuxカーネル等のビルドでは必ず **`-mno-red-zone`** オプションを付けて Red Zone の使用を禁止する補正を行います。

> **【コラム：OS が違えば同じ x86-64 でも ABI が異なる（System V AMD64 vs Windows x64 / RISC-V）】**
>
> ABIはCPU（ISA）だけで決まるものではなく、OSとコンパイラ・ツールチェインを含めたプラットフォーム全体の契約です。そのため、まったく同じ x86-64 CPU の上で動くプログラムでも、Linux / macOS の **System V AMD64 ABI** と、Windows の **Windows x64 ABI** では関数呼び出し規約が大きく異なります。
>
> | 項目 | System V AMD64（Linux / macOS） | Windows x64 | RISC-V（RV64 LP64D） |
> | :--- | :--- | :--- | :--- |
> | **整数引数レジスタ** | 6個（`%rdi, %rsi, %rdx, %rcx, %r8, %r9`） | 4個（`%rcx, %rdx, %r8, %r9`） | 8個（`a0`〜`a7`） |
> | **callee-saved（主なもの）** | `%rbx, %rbp, %rsp, %r12`〜`%r15` | 左記に加え **`%rdi, %rsi`** も保存対象 | `s0`〜`s11`, `sp` |
> | **Red Zone** | あり（`%rsp` 下位 128 バイト） | **なし** | **なし** |
> | **Shadow Space（Home Space）** | なし | **あり（呼び出し側が毎回 32 バイト確保）** | なし |
> | **スタック境界** | `call` 前に 16 バイト境界 | `call` 前に 16 バイト境界 | 常に 16 バイト境界 |
>
> Windows x64 特有の **Shadow Space（32バイト）** は、引数が4個以下であっても、呼び出し側が毎回スタック上に「レジスタ渡しした4引数（$8\text{ B} \times 4 = 32\text{ B}$）をいつでも退避できる空き枠」を予約しておく規約です。これにより、可変長引数関数やデバッグビルドで引数をスタックへ書き戻す処理が単純化されます。同じ機械語命令セットを共有していても ABI が違えばバイナリはそのままリンクできないため、異なるOS間でライブラリを動かすには、ABIの変換層（Wine 等）や各プラットフォーム向けの再ビルドが必要になります。

### 5. 接続と展望（Bridge）：本節の内容が後半のどの部に繋がるか

1. **次節（[1-4節](1-4.md)：ELFバイナリ構造・セクションと記号表・再配置）：**
    本節では1つの関数から別の関数を `call foo` で呼ぶ仕組みを見ました。次節では、別のファイルに定義された `foo` のアドレスをリンカがどう探し出して機械語へ埋め込むか（ELF構造と再配置）へ進みます。

2. **[第2部](../index.md#part-2)（[2-6節](../2/2-6.md)：コンパイラのコード生成）：**
    本節の System V AMD64 ABI（6レジスタ引数、第7引数以降のスタック渡し、16バイト境界調整、プロローグ／エピローグ）は、コンパイラのコード生成器が実際に守るべき仕様そのものとして再登場します。

3. **[第3部](../index.md#part-3)（[3-3節](../3/3-3.md)：コンテクストスイッチ）：**
    OSカーネルの `swtch` 関数（RISC-V）が、全32本のレジスタではなく **`ra`, `sp`, `s0`〜`s11` の callee-saved レジスタだけ** を退避・復元するだけでプロセス切替を完結できる理由は、本節3-(4)の「caller-saved レジスタは呼び出し側が責任を持つ」というABIの約束があるからです。

4. **[第5部](../index.md#part-5)（[5-8節](../5/5-8.md)：メモリ破壊攻撃と多層防御）：**
    図1-3-3の通り、局所配列（`-32(%rbp)` 等）のすぐ高位アドレス側には「古い `%rbp`」と「**戻り番地（`+8(%rbp)`）**」が並んでいます。配列の境界を超えて書き込むとこの戻り番地を上書きできてしまう構造こそが、バッファオーバーフロー攻撃の物理的な原因です。

### 理解度チェック（次節へ進む前の確認）

本節の16バイト境界アラインメント・TCO・Red Zone・レジスタ退避規約・`%rbp` バックトレースを具体的な問題で確認します。

> **【確認の問い】**
>
> 1. **（16バイト境界アラインメント違反のデバッグとパディング配置）**
>     手書きアセンブリで作成した関数 `wrapper` の先頭（呼び出し元の `call wrapper` 直後なので `%rsp = 0x7fffffffe008`）において、次の2つのケースを考えます。
>
>     * (a) `wrapper` がプロローグ（`pushq %rbp` 等）も `%rsp` の調整も一切行わず、そのまま `call printf` を実行したところ、`libc` 内部の SSE 命令（`movaps`）で強制終了しました。その原因を System V AMD64 ABI の16バイト境界ルールから説明してください。
>     * (b) 今度は `wrapper` が標準のプロローグ（`pushq %rbp; movq %rsp, %rbp`）を実行して `%rsp = 0x7fffffffe000` になったあと、第7引数1個（8バイト）をスタック渡しで別関数 `g` へ渡そうとしています。`call g` 前に `%rsp` を16バイト境界へ揃えるための8バイトパディング（`subq $8, %rsp`）は、「第7引数を `push` する**前**」と「`push` した**後**」のどちらに置くべきでしょうか。`%rsp` の値の変化と、`g` 側が第7引数を参照する位置（`16(%rbp)`）を追って理由を答えてください。
>
> 2. **（TCO の可否判定・カーネルでの Red Zone 禁止・レジスタ選択）**
>
>     * (a) 関数 `A` が自身の局所配列 `int buf[4];` の先頭アドレスを子関数 `B` へ渡し、`return B(buf);` で終了するとき、コンパイラは末尾コール最適化（TCO）を適用できるでしょうか。理由を答えてください。
>     * (b) OS カーネルのビルドで `-mno-red-zone` オプションが必須になる理由を、ユーザ空間のシグナル配送とカーネル空間のハードウェア割り込みの違いから説明してください。
>     * (c) 1000回繰り返すループの内部で毎回別関数 `helper()` を呼び出すとき、ループカウンタ `i` を保持するレジスタとして `%r12`（callee-saved）と `%r10`（caller-saved）のどちらを選ぶ方が効率的でしょうか。メモリ退避・復元の回数に着目して答えてください。
>
> 3. **（`%rbp` チェーンからのバックトレース復元と `-fomit-frame-pointer`）**
>     フレームポインタ（`%rbp`）を有効にしてビルドされたプログラムが関数 `bar` 内で停止し、現在の `%rbp = 0x7000`、`%rip = 0x401208` でした。スタックメモリ（各エントリ8バイト）には次の値が入っていました（`0x0000` はスタック底の終端とします）。
>
>     | アドレス | 格納値（8バイト） |
>     | :--- | :--- |
>     | `0x7000` | `0x7030` |
>     | `0x7008` | `0x401184` |
>     | `0x7030` | `0x7060` |
>     | `0x7038` | `0x401120` |
>     | `0x7060` | `0x0000` |
>     | `0x7068` | `0x401050` |
>
>     * (a) 現在の `%rbp = 0x7000` から古い `%rbp` の連結リストを順に辿り、各呼び出し元の「戻り番地」を近い順（`bar` の直前の呼び出し元から順）にすべて列挙してください。
>     * (b) 最適化ビルドで `-fomit-frame-pointer` が有効になると上の連結リストが使えなくなります。その代わりにデバッガや例外処理が呼び出し履歴を復元するために参照する ELF セクション名と、基準アドレス（CFA）の復元方法を簡潔に答えてください。
