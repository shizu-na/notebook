### 前節（1-1）の確認問題の解答

前節の最後に提示した3つの問いの解答を確認します。問3がそのまま本節（レジスタ・アドレッシングモード・制御フロー）の導入になります。

1. **AT&T 記法の誤読診断と固定長 vs 可変長命令の並列デコード：**

    * **(a) `subq %rbx, %rax` の結果と `movq 0x200, %rcx` のバグ：**
        AT&T 記法の減算命令は「第2オペランド（右）から第1オペランド（左）を引く」向きのため、`subq %rbx, %rax` は `%rax = %rax - %rbx = 10 - 3 =` **`7`** になります。また、`$` を落とした `movq 0x200, %rcx` は定数 `0x200` の代入（即値参照）ではなく、**「メモリの `0x200` 番地に置かれた8バイトを読み込む」直接メモリ参照**として解釈されます。通常のユーザ空間では `0x200` 番地はアクセス禁止領域のため、不正なメモリアクセスで即座にクラッシュするバグになります（正しくは `movq $0x200, %rcx`）。

    * **(b) 可変長命令における並列デコードの難しさ：**
        32ビット固定長の RISC-V（RV64I）では命令境界が常に4バイト間隔（0, 4, 8, …バイト目）に確定しているため、複数命令を一斉に並列デコードできます。一方、1〜15バイト可変長の x86-64 では、**1命令目を先頭から順に解析して長さが確定するまで、2命令目がどのバイトから始まるか（命令境界）が分からない**ため、並列に命令を切り出すだけでも複雑な解析回路と電力が必要になります。

2. **RISC-V から x86-64 への変換と現代の収斂設計：**

    * **(a) 3点の設計上の違い：**

        * **① 第7・第8引数の渡し方：** RISC-V は8個の引数レジスタ（`a0`〜`a7`）へすべて収まりますが、x86-64（System V AMD64 ABI）の整数引数レジスタは6個（`%rdi`, `%rsi`, `%rdx`, `%rcx`, `%r8`, `%r9`）のみのため、第7・第8引数は**スタック経由**で渡します（詳細は[1-3節](1-3.md)）。
        * **② 戻り番地の保存場所：** RISC-V はリンクレジスタ `ra` へ保持しますが、x86-64 では `call` 命令が自動的に**スタックトップ（メモリ）へプッシュ**します。
        * **③ 汎用レジスタ本数の違い：** RISC-V（32本）より x86-64（16本）の方が少ないため、x86-64 側ではレジスタに収まりきらない一時値をスタックへ退避（スピル）する機会や、メモリ直接参照オペランドを活用する場面が増えます。

    * **(b) $\mu\text{op}$ キャッシュと RV64C の命令長判別：**
        現代の x86-64 プロセッサは、一度デコードした $\mu\text{op}$ 列を保存する **$\mu\text{op}$ キャッシュ**（Intel の DSB や AMD の Op Cache 等）を備えており、ループ等の反復実行時は重い可変長デコーダを迂回して直接 $\mu\text{op}$ を供給します。また、RISC-V の C拡張（RV64C）は命令の最下位2ビットが `11` か否かで32ビット／16ビットを区別する語頭符号を採用しており、RISC-V がリトルエンディアンであるため最下位2ビットは常にメモリ上の**先頭バイトのビット1..0**に現れます。そのため先頭バイトを読み込んだ瞬間に命令長を即座に判別できます。

3. **符号あり／なし比較におけるフラグ方式と直接比較方式の設計対比（本節への接続）：**

    * **(a) RISC-V（フラグなし方式）での区別：**
        ステータスフラグを持たないため、命令セット側で**符号あり用の分岐命令（`blt`, `bge`）と符号なし用の分岐命令（`bltu`, `bgeu`）を別々のオペコードとして用意**し、1命令の中で指定した解釈に基づき比較と分岐を同時に行います。

    * **(b) x86-64（フラグ方式）の制約：**
        比較命令や多くの算術命令が単一の共有ステータスフラグレジスタへ結果を書き込むため、比較命令と直後の条件分岐命令の間に暗黙のデータ依存関係が生じ、アウトオブオーダ実行でフラグを書き換える命令同士を自由に並べ替えにくくなる制約があります（ハードウェア側でフラグレジスタにもリネーミングを行うなどの補正が必要になります）。本節では、このステータスフラグと条件付きジャンプの具体的な対応を詳しく追います。

## 1-2. レジスタ・アドレッシングモードと制御フローの機械語表現

### 1. 動機（Why）：C言語の「配列」や「`if` / `switch`」は、どのように機械語の1命令へ落ちるのか

前節（[1-1節](1-1.md)）では、ソフトウェアとハードウェアの契約であるISAについて、RISC（RISC-V）とCISC（x86-64）の設計思想を対比しました。ここからは実際のLinuxバイナリやコンパイラの出力を読み解くために、x86-64の機械語命令がC言語の要素をどう表現しているのかを具体的に見ていきます。

C言語で書かれたプログラムを逆アセンブル（機械語をアセンブリ表記へ戻すこと）して眺めると、最初は慣れない記号が並んで見えます。しかし、実際に押さえるべき仕組みは次の3点に集約されます。

1. **同じレジスタを異なるビット幅で呼ぶ仕組み：** 64ビットレジスタ `%rax` の下位32ビットを `%eax`、下位8ビットを `%al` と呼ぶ別名ルールと、32ビット演算時に上位32ビットがどう振る舞うかを確認します。
2. **メモリ上の場所を1命令で指定する仕組み（アドレッシングモード）：** 構造体のメンバ（オフセット加算）や配列の要素（インデックス $\times$ 要素サイズ）を、CPUがどのような記法で参照するかを整理します。
3. **条件分岐と多方向分岐の仕組み：** 比較結果を一時保持するステータスフラグと条件付きジャンプ、さらに `switch` 文を $O(1)$ で飛ばすジャンプテーブルの構造を理解します。

本節では、これら3つの仕組みを小さな具体例から順に整理します。なお、アセンブリ記法は前節の約束通り、Linuxの標準ツールチェイン（`gcc` / `objdump`）と同じ **AT&T記法（左から右へ代入）** で統一します。

### 2. 具体例と動作イメージ（Toy Model）

規則の網羅に入る前に、x86-64らしさが最もよく表れる2つの小さな例で動作を確かめます。

#### 実験A：配列アクセス `a[i]` を1命令で読む

C言語で、`int` 型（4バイト）の配列 `int a[]` の先頭アドレスが `%rdi` に、添字 `i`（64ビット整数）が `%rsi` に入っているとします。要素 `a[i]` の値を読み出して返り値レジスタ `%eax` へ入れる処理は、x86-64では次の**1命令**だけで書けます。

```asm
movl (%rdi, %rsi, 4), %eax
```

ここで `(%rdi, %rsi, 4)` は、「`%rdi`（配列の先頭アドレス）$+ \texttt{\%rsi}$（添字 `i`）$\times 4$（`sizeof(int)`）で計算される番地のメモリから、4バイト（`movl` の `l`）を読み出す」という意味です。RISC-Vであれば「`i` を左に2ビットシフトして4倍 → 先頭アドレスに加算 → ロード」と3命令かかるところを、x86-64はハードウェアのアドレッシング機能（SIBバイト）によって1命令へ畳み込んでいます。

#### 実験B：同じビット列の比較で「符号あり」と「符号なし」が分かれる瞬間

8ビットレジスタ `%al` に `0xFF`、`%bl` に `0x01` が入っているとします。[0-1節](../0/0-1.md)で確認した通り、同じ `0xFF` でも符号あり整数なら **`-1`**、符号なし整数なら **`255`** です。

ここで比較命令 `cmpb %bl, %al` を実行します（AT&T記法では、**第2オペランドから第1オペランドを引く** `%al - %bl` の計算を行い、結果の値は捨ててステータスフラグだけを更新します）。

$$\texttt{0xFF} - \texttt{0x01} = \texttt{0xFE} \quad (\texttt{11111110}_2)$$

この1回の引き算で、ステータスフラグは次のように更新されます。

* **ゼロフラグ `ZF = 0`：** 結果 `0xFE` は `0` ではないため `0` になります。
* **符号フラグ `SF = 1`：** 結果 `0xFE` の最上位ビット（MSB）が `1`（負数）のため `1` になります。
* **キャリーフラグ `CF = 0`：** 符号なし計算 $255 - 1 = 254$ では繰り下げ（ボロー）が起きないため `0` になります。
* **オーバーフローフラグ `OF = 0`：** 符号あり計算 $(-1) - 1 = -2$ は8ビット符号ありの範囲内なのでオーバーフローせず `0` になります。

この直後にどの条件付きジャンプ命令を置くかで、プログラムの解釈が分かれます。

* **符号ありの「より大きい（`>`）」を判定する `jg`（Jump if Greater）：** 条件は `ZF == 0 && SF == OF` です。今 `SF = 1`, `OF = 0` で一致しないため**ジャンプしません**（$-1 > 1$ は偽）。
* **符号なしの「より大きい（`>`）」を判定する `ja`（Jump if Above）：** 条件は `CF == 0 && ZF == 0` です。今どちらも `0` で条件を満たすため**ジャンプします**（$255 > 1$ は真）。

CPUの比較命令 `cmp` 自体は符号の有無を区別せず1通りに計算し、**直後のジャンプ命令の種類で符号あり／符号なしを切り替える**のがx86-64の基本構造です。

### 3. 構造・アルゴリズム・実装（What）

#### (1) x86-64 の汎用レジスタと別名・上位32ビットゼロクリア

x86-64には16本の64ビット汎用レジスタがあります。歴史的な経緯（16ビットの8086 → 32ビットのIA-32 → 64ビットのx86-64への拡張）により、同じ1本の物理レジスタの下位部分に対して、サイズ別の別名が付けられています（図1-2-1左）。

| 64ビット（`q`：8B） | 32ビット（`l`：4B） | 16ビット（`w`：2B） | 下位8ビット（`b`：1B） | 備考 |
| :--- | :--- | :--- | :--- | :--- |
| `%rax`, `%rbx`, `%rcx`, `%rdx` | `%eax`, `%ebx`, `%ecx`, `%edx` | `%ax`, `%bx`, `%cx`, `%dx` | `%al`, `%bl`, `%cl`, `%dl` | ビット15..8（下位16ビットの上位側）を指す別名 `%ah`〜`%dh` もある |
| `%rsi`, `%rdi`, `%rbp`, `%rsp` | `%esi`, `%edi`, `%ebp`, `%esp` | `%si`, `%di`, `%bp`, `%sp` | `%sil`, `%dil`, `%bpl`, `%spl` | 64ビット化で下位8ビット名が追加 |
| `%r8`〜`%r15` | `%r8d`〜`%r15d` | `%r8w`〜`%r15w` | `%r8b`〜`%r15b` | x86-64で新設された8本 |

ここで、アセンブリを読むときに必ず押さえておくべきx86-64特有の重要ルールがあります。それは、**「32ビットレジスタ（`%eax` 等）へ値を書き込むと、対応する64ビットレジスタ（`%rax` 等）の上位32ビットが自動的にすべて `0` でクリアされる」**という規則です（図1-2-1右）。

たとえば `%rax` に `0x1122334455667788` が入っている状態で `movl $0xAABBCCDD, %eax` を実行すると、`%rax` 全体は `0x00000000AABBCCDD` になります。一方、16ビット（`%ax`）や8ビット（`%al`）への書き込みでは上位ビットは保持されたまま変化しません。

なぜ32ビット書き込みだけ上位をゼロクリアするのでしょうか。理由は2つあります。第1に、古い上位32ビットの値を残すと、CPUが「前の命令が書き終えるまで待たなければならない」という依存関係があるとみなしてしまい、アウトオブオーダ実行（[0-6節](../0/0-6.md)）の並列処理が詰まります（**部分レジスタ・ストール**）。上位を一律 `0` でクリアすれば、古い値への依存を断ち切れます。第2に、64ビットレジスタへ小さな正の定数を入れたいとき、`movq $10, %rdi`（7バイト）の代わりに命令長が短い `movl $10, %edi`（5バイト）を使うだけで上位32ビットも確実にゼロ初期化できるため、コンパイラは頻繁に `movl` や `xorl %eax, %eax`（`%rax = 0` の慣用句、わずか2バイト）を出力します。

#### (2) 4つのアドレッシングモードとメモリ参照の一般形

機械語命令がオペランド（引数）の値をどこから取得するかを定める記法を **アドレッシングモード（Addressing Mode）** と呼びます。x86-64のオペランドは次の4種類に分類されます。

| アドレッシングモード | 表記例（AT&T記法） | 意味（参照される値） |
| :--- | :--- | :--- |
| **1. 即値（Immediate）** | `$100`, `$foo` | 定数 `100` やラベルのアドレス値そのもの（`$` が付く） |
| **2. レジスタ参照** | `%rbx` | レジスタ `%rbx` の中身 |
| **3. 直接メモリ参照** | `0x1000`, `foo` | 定数番地 `0x1000` やラベル `foo` の指す**メモリの中身**（※現代の PIE 環境では絶対番地埋め込みを避け `%rip` 相対参照を使う） |
| **4. 間接メモリ参照** | `(%rsp)`, `-8(%rbp)`, `(%rdi, %rsi, 4)`, `x(%rip)` | レジスタの値等から計算した番地の**メモリの中身** |

特に重要なのが4番目の**間接メモリ参照**です。x86-64のメモリ参照には、次の2つの一般形があります（図1-2-2）。

1. **通常のメモリ参照：`disp(base, index, scale)`**
    計算される実効アドレス（Effective Address）は次で与えられます。

    $$\text{Address} = \text{base} + \text{index} \times \text{scale} + \text{disp}$$

    * `disp`（変位）：符号あり定数を指定します（省略可。変位には `$` を付けません）。
    * `base`：任意の64ビット汎用レジスタを指定します（省略可）。
    * `index`：`%rsp` 以外の任意の64ビット汎用レジスタを指定します（省略可。機械語の SIB バイトでは、`%rsp` に相当する3ビットの符号 `100` が「インデックスレジスタを使用しない」という意味に割り当てられているため、`%rsp` は `index` に指定できません）。
    * `scale`：乗数として **`1`, `2`, `4`, `8`** のいずれかのみ指定できます（省略時は `1`）。C言語の基本データ型サイズ（`char`=1, `short`=2, `int`=4, `long`/ポインタ=8）にちょうど一致するよう設計されています。

    たとえば構造体のメンバ参照 `p->x2`（オフセット4）は `4(%rax)`、配列要素 `a[i]`（要素サイズ4）は `(%rdi, %rsi, 4)`、8バイト構造体 `struct Pair { int a; int b; };` の配列におけるメンバ参照 `p[i].b`（要素サイズ8、`int b` のオフセット4）は **`4(%rdi, %rsi, 8)`** とすべて1つの記法で表現できます。

2. **`%rip` 相対アドレッシング：`disp(%rip)`**
    現在のプログラムカウンタ `%rip`（次に実行する命令のアドレス）を基準に `Address = %rip + disp` で大域変数や文字列定数を参照します。たとえば `movl x(%rip), %eax` は、大域変数 `x` の絶対番地を命令に埋め込まず、「この命令から何バイト先にあるか」という相対距離だけでアクセスします。現代の Linux 環境では実行ファイル自身を任意の番地へロードできる **PIE（位置独立実行ファイル：[1-5節](1-5.md)）** が標準となっているため、大域変数や定数へのアクセスは直接メモリ参照ではなく `%rip` 相対アドレッシングで生成されます。

なお、x86-64の `mov` や `add` などの2オペランド命令では、**メモリからメモリへの直接転送（例：`movq (%rax), (%rbx)`）は禁止**されており、少なくとも片方はレジスタまたは即値である必要があります。

#### (3) ステータスフラグと `cmp`・`test`・条件付きジャンプ

[0-1節](../0/0-1.md)で見たキャリーフラグ（`CF`）とオーバーフローフラグ（`OF`）を含め、x86-64は演算結果を記録する専用の**ステータスレジスタ（`%rflags`）**を持ちます。条件分岐で主に参照するのは次の4ビットです。

* **`ZF`（Zero Flag）：** 演算結果がちょうど `0` のときに `1` になります。
* **`SF`（Sign Flag）：** 演算結果のMSB（符号ビット）をそのままコピーし、負数なら `1` になります。
* **`CF`（Carry Flag）：** 符号なし加減算で桁上がり／借り（符号なしオーバーフロー）が起きたときに `1` になります。
* **`OF`（Overflow Flag）：** 符号あり加減算で符号が矛盾（符号ありオーバーフロー）したときに `1` になります。

分岐の直前では、レジスタやメモリの値を壊さずにフラグだけを更新する2つの比較命令を使います。

* **`cmpq op1, op2`：** 引き算 `op2 - op1` のフラグ変化だけを計算します。
* **`testq op1, op2`：** ビット積 `op2 & op1` のフラグ変化だけを計算します。特に `%rax` が `0` かどうかを調べるとき、コンパイラは `cmpq $0, %rax`（4バイト）ではなく命令長が短い `testq %rax, %rax`（3バイト、`%rax == 0` のときだけ `ZF = 1`）を好んで生成します。

続く条件付きジャンプ命令は、**符号ありには `g/l`（greater / less）**、**符号なしには `a/b`（above / below）** を使い分けます。

| 条件（`cmp op1, op2` に対する `op2` と `op1` の関係） | 符号あり整数用 | フラグ条件（符号あり） | 符号なし整数用 | フラグ条件（符号なし） |
| :--- | :---: | :---: | :---: | :---: |
| 等しい（`==`） / 等しくない（`!=`） | `je` (`jz`) / `jne` (`jnz`) | `ZF==1` / `ZF==0` | `je` (`jz`) / `jne` (`jnz`) | `ZF==1` / `ZF==0` |
| より大きい（`>`） | `jg` | `ZF==0 && SF==OF` | `ja` | `CF==0 && ZF==0` |
| 以上（`>=`） | `jge` | `SF==OF` | `jae` | `CF==0` |
| より小さい（`<`） | `jl` | `SF!=OF` | `jb` | `CF==1` |
| 以下（`<=`） | `jle` | <code>ZF==1 &#124;&#124; SF!=OF</code> | `jbe` | <code>CF==1 &#124;&#124; ZF==1</code> |

ここで符号ありの `>=` 条件が「`SF == 0`」ではなく **`SF == OF`** になっている理由は、オーバーフローの有無で場合分けすると理解できます。引き算 `op2 - op1` の結果を見るとき、オーバーフローが起きていなければ（`OF == 0`）符号ビットがそのまま正しい向きを示すため、結果が0以上（`SF == 0`）のとき `op2 >= op1` です。一方、オーバーフローが起きたとき（`OF == 1`）は結果の符号ビットが反転するため、見かけ上は負（`SF == 1`）のときこそ本当は `op2 >= op1` になります（例：8ビットで $(+64) - (-64) = -128$ となり `OF = 1, SF = 1`）。この2つを合わせた条件 `(OF==0 && SF==0) || (OF==1 && SF==1)` が、ちょうど `SF == OF` に一致します。

また、ジャンプせずに比較の真偽（`1` または `0`）を値として得たいときは、`setg %al` のような `set` 系命令でフラグ条件を1バイトへ取り出し、`movzbl %al, %eax`（`mov`＋ゼロ拡張 `z`＋1バイト `b` から4バイト `l` へ転送）で32ビットへゼロ拡張します（32ビットレジスタ `%eax` への書き込みにより上位32ビットも `0` になるため、結果として64ビットの `%rax` 全体が `0` または `1` になります）。

#### (4) Cの制御文（`if`・`while`・`switch`）の機械語表現

C言語の構造化された制御文は、機械語レベルではすべて「比較＋条件付きジャンプ＋無条件ジャンプ（`jmp`）＋ラベル」の組み合わせへ翻訳されます。

* **`if-else` 文：** コンパイラは条件を反転して判定し、偽なら `else` 側ラベルへ飛ばす形をよく生成します。

    ```asm
    cmpl  $100, %eax     # x と 100 を比較
    jle   .L_else        # x <= 100 なら else 側へジャンプ
    addl  $1, %eax       # then 本体
    jmp   .L_end         # else を飛び越す
    .L_else:
    subl  $1, %eax       # else 本体
    .L_end:
    ```

* **`while` ループ（素朴な先頭判定版 vs 末尾条件版）：**
    たとえば `while (i < n) { sum += i; i++; }` を素直に先頭判定で書くと、1周ごとに「ループを抜ける条件分岐（`jge`）」と「先頭へ戻る無条件ジャンプ（`jmp`）」の**2回のジャンプ**が必要になります。一方、最初に条件判定ラベルへ1度だけ `jmp` してループ本体の末尾に条件判定を置く形にすると、ループ内では**1周あたり条件付きジャンプ1回だけ**で済み、命令キャッシュや分岐予測の効率が上がります（`i` を `%eax`、`n` を `%edi`、`sum` を `%edx` とします）。

    ```asm
    # 素朴な先頭判定版（1周あたりジャンプ2回）
    .L_loop:
        cmpl  %edi, %eax     # i と n を比較
        jge   .L_done        # i >= n なら終了
        addl  %eax, %edx     # sum += i
        addl  $1, %eax       # i++
        jmp   .L_loop        # 先頭へ戻る
    .L_done:
    ```

    ```asm
    # 末尾条件版（1周あたりジャンプ1回）
        jmp   .L_cond        # 初回だけ条件判定へ飛ぶ
    .L_body:
        addl  %eax, %edx     # sum += i
        addl  $1, %eax       # i++
    .L_cond:
        cmpl  %edi, %eax     # i と n を比較
        jl    .L_body        # i < n なら本体先頭へ戻る
    ```

* **`switch` 文の2つの翻訳戦略（単純比較 vs ジャンプテーブル）：**
    `case` の数が少ない場合、コンパイラは `if-else if` の連鎖と同じく上から1つずつ `cmpl` と `je` を並べます（探索時間は $O(n)$）。一方、`case 0:`〜`case 4:` のように値が連続して密に並んでいる場合、コンパイラは各 `case` の飛び先情報を配列としてメモリ（読み取り専用データ領域の `.rodata` セクション、詳細は[1-4節](1-4.md)）に並べた **ジャンプテーブル（Jump Table）** を生成します（図1-2-3）。まず基本構造が見えやすい絶対アドレス表の例を見てみます。

    ```asm
    # x (%eax) が 0〜4 の範囲内か1回で検査
    cmpl  $4, %eax
    ja    .L_default
    leaq  .L_table(%rip), %rdx      # ジャンプテーブルの先頭アドレスを取得
    movq  (%rdx, %rax, 8), %rax     # table[x] から飛び先アドレスを取得
    jmp   *%rax                     # レジスタ間接ジャンプ（O(1)）
    ```

    この5命令には、x86-64の重要な性質が3つ使われています。

    * **`ja` 1回で負数も同時に弾ける理由：** もし `x` が負数であれば、2の補数表現では最上位ビット（MSB）が `1` になるため、符号なし整数として解釈すると $2^{31}$ 以上の大きな正数になります。したがって符号なし比較の `ja`（`> 4`）を1回行うだけで、「$x > 4$」と「$x < 0$」の両方を同時に `.L_default` へ弾けます（もし下限が `0` でなく `10`〜`14` のようにずれている場合は、直前に `subl $10, %eax` で `0`〜`4` へ平行移動してから `cmpl $4, %eax`＋`ja` を実行します）。
    * **`%eax` 検査後に `%rax` をそのまま添字に使える前提：** 直前の命令で `%eax` へ32ビット値が書き込まれた時点で `%rax` の上位32ビットはすでに `0` にクリアされている（3-(1)）ため、非負の範囲 `0`〜`4` に収まった `%eax` はそのまま64ビット添字 `%rax` として安全に使えます。
    * **`leaq` と間接ジャンプ `*` の記法：** 3行目の `leaq` はメモリの中身を読まずにアドレス値だけを計算してレジスタへ入れる命令です（詳細は後述のコラム）。5行目の `jmp *%rax` に付く **`*`** は、AT&T記法で「ラベルへの直接ジャンプではなく、レジスタやメモリの中身を飛び先にする間接ジャンプ」であることを示す記号です（なお、`movq` と `jmp` を `jmp *(%rdx, %rax, 8)` の1命令にまとめる書き方もあります）。

    なお、現代の Linux 環境で標準となっている **PIE / PIC（位置独立コード：[1-5節](1-5.md)）** では、読み取り専用の `.rodata` へ64ビットの絶対アドレスを書き込むと配置先が変わったときに動かなくなるため、コンパイラはテーブルの各要素に「テーブル先頭 `.L_table` からの**32ビット符号あり相対オフセット**」を格納します。その場合は `movslq (%rdx, %rax, 4), %rax`（符号拡張ロード）でオフセットを読み、`addq %rdx, %rax` でテーブル基準番地を足してから `jmp *%rax` で飛びます（テーブル容量も半分で済みます）。いずれの方式でも、`case` が何十個あっても境界チェック1回・配列参照1回・間接ジャンプ1回の **$O(1)$** で目的の処理へ直行できます。

> **【コラム：アドレス計算命令 `lea` が「フラグを汚さない高速な積和算」として流用される理由】**
>
> GCCなどの最適化されたアセンブリを読むと、ポインタや配列を一切使っていない普通の整数計算なのに **`leaq`**（Load Effective Address：実効アドレスの計算）命令が頻繁に現れます。たとえばC言語の `y = x * 5 + 4;` をコンパイルすると、乗算命令 `imulq` と加算命令 `addq` の代わりに、次の1命令が出力されることがあります（`x` が `%rdi` にある場合）。
>
> ```asm
> leaq 4(%rdi, %rdi, 4), %rax    # %rax = %rdi + %rdi * 4 + 4 = 5 * x + 4
> ```
>
> `lea` は本来、`disp(base, index, scale)` のアドレスを計算してレジスタへ入れるだけの命令であり、**メモリへは一切アクセスしません**。この性質をコンパイラが「整数の積和算（`a + b * {1,2,4,8} + c`）」として流用する理由は3つあります。第1に、`imul` や複数回の `add`/`shl` より**1命令かつ低レイテンシ**で済むこと。第2に、出力先レジスタ `%rax` を入力 `%rdi` とは別に指定できる（非破壊の3オペランド演算になる）こと。そして第3に、**ステータスフラグ（`CF/OF/ZF/SF`）を一切書き換えない**ため、直前の `cmp` の結果を壊さずに計算を挟み込めることです。
>
> 具体的には、`base` と `index × {1, 2, 4, 8}` の組み合わせにより、**`×2`, `×3`, `×4`, `×5`, `×8`, `×9`** の定数倍を1命令で作れます。さらに `leaq` を2命令連結すれば、`×10`（`×5` のあと `×2`）、`×15`（`×3` のあと `×5`）、`×25`（`×5` を2回）といった乗算も乗算器を使わずに合成できます（[第2部](../index.md#part-2) [2-7節](../2/2-7.md)の「強さの軽減」で再登場します）。この技法は、要素サイズが2の累乗ではない構造体配列（たとえば24バイト構造体 `struct S` の配列 `s[i]`）のアドレス計算でも多用されます。`24 = 3 × 8` なので、まず `leaq (%rsi, %rsi, 2), %rax` で `3 * i` を作り、続けて `(%rdi, %rax, 8)` で `base + 24 * i` へアクセスできます。
>
> 一方、現代のx86-64 CPUの内部では、`lea` は専用のアドレス計算器（AGU）やALUで実行されますが、`base`・`index`・`disp` の3成分をすべて使う形式（例：`leaq 4(%rdi, %rsi, 4), %rax`）は、Intelの一部マイクロアーキテクチャではレイテンシが1サイクルではなく**3サイクルかかる「スローLEA（Slow LEA）」**になることが知られています。そのため、最適化コンパイラは対象CPUのモデルに応じて、3成分 `lea` を避けて2成分 `lea` や `add`/`shl` に分解する使い分けも行います。

### 4. 限界と補正（Critique & Adaptation）

#### (1) ジャンプテーブルの空間コストとコンパイラの使い分け

ジャンプテーブルは定数時間 $O(1)$ で分岐できる高速な手法ですが、**`case` の値が飛び飛び（疎：sparse）な場合にはメモリを浪費する**という明確な限界があります。たとえば `case 1:`, `case 1000:`, `case 1000000:` の3つしかない `switch` 文に単純なジャンプテーブルを作ろうとすると、間の999,997個分のダミーエントリ（8MB近く）を `.rodata` に確保しなければならず非現実的です。

そのため現代のコンパイラ（GCCやClang）は、`case` の個数と値の密度（範囲に対する占有率）を解析し、次の3つを自動で使い分けます。

* **`case` が数個と少ない場合：** 単純な比較列（$O(n)$）を生成します。分岐予測が当たりやすくコードサイズも小さく抑えられます。
* **`case` が多く値が密に並んでいる場合：** ジャンプテーブル（$O(1)$）を生成します。
* **`case` が多く値が疎に散らばっている場合：** 比較による**二分探索木（$O(\log n)$）**を生成し、さらに密な塊がある部分範囲だけ部分的にジャンプテーブルを併用するハイブリッド戦略をとります。

> **【コラム：分岐予測ミスを回避する条件付き転送命令 `cmov`】**
>
> [0-5節](../0/0-5.md)で見た通り、パイプラインプロセッサでは条件分岐の予測が外れると、投機実行していた命令列をすべて破棄する大きなペナルティ（15〜20サイクル程度）が発生します。たとえば `int max = (x > y) ? x : y;` のような単純な条件代入で、`x` と `y` の大小がランダムに入れ替わるデータを扱うと、通常の `cmp`＋`jle` では約50%の確率で予測ミスが起きます。
>
> これに対するx86-64の対策が、条件が真のときだけレジスタ転送を行う **条件付き転送命令 `cmov`（Conditional Move）** です。上の式は分岐命令を1つも使わずに次のように翻訳できます（`x` が `%edi`、`y` が `%esi` の場合）。
>
> ```asm
> movl   %esi, %eax     # まず y を仮の結果として %eax へ入れる
> cmpl   %esi, %edi     # x と y を比較
> cmovgl %edi, %eax     # x > y（Greater）なら %eax を x で上書き（偽なら何もしない）
> ```
>
> このように分岐を消す手法を**ブランチレス化（Branchless）**と呼びます。制御の流れが一直線になるため分岐予測ミスは一切起きません。ただし万能ではなく、① 常に両方の枝の値を計算しておく必要があること、② 転送命令がデータ依存チェーンを伸ばすこと、というコストがあります。そのため、分岐の向きが99%以上偏っていて分岐予測がほぼ当たる場面では通常の条件ジャンプの方が速く、コンパイラは分岐の予測しやすさと計算コストを見積もって `cmov` と条件ジャンプを使い分けます。

#### (2) 間接ジャンプの脆弱性とハードウェア保護（`endbr64` / Intel CET）

ジャンプテーブルの `jmp *%rax` や、C言語の関数ポインタ呼び出し `call *%rax` のように、レジスタやメモリの中身を飛び先にする**間接ジャンプ／間接コール**は、プログラムに柔軟性と速度をもたらします。

しかしセキュリティの視点では、間接ジャンプは攻撃者にとって主な標的になります。もしバッファオーバーフローなどのバグ（[第5部](../index.md#part-5) [5-8節](../5/5-8.md)）でメモリ上の関数ポインタやテーブル値が書き換えられると、CPUが関数の途中にある意図しない機械語バイト列へジャンプさせられ、任意の処理を実行されてしまうためです。

この限界に対する現代ハードウェアの補正の1つが、正規の着地点（関数の先頭やジャンプテーブルの各入口）にだけ「ここなら着地してよい」という目印命令（**`endbr64`**）を置いておき、目印のない途中番地へ飛ばされたらCPUが即座に停止する仕組みです。Intel CET（Control-flow Enforcement Technology）に含まれる **IBT（Indirect Branch Tracking）** がこれを実装しており、GCCは対応ビルド時に関数の先頭やジャンプテーブルの着地点へ `endbr64` を自動挿入します。

* CET対応CPUでは、間接ジャンプ（`jmp *%rax` 等）や間接コール（`call *%rax`）を実行した直後の**飛び先にある最初の命令が必ず `endbr64` でなければならない**と強制されます。もし関数の途中など `endbr64` 以外の命令へ飛ばされると、CPUが即座に例外を発生させてプロセスを停止します。
* 一方、CETに未対応の古いCPUでは、`endbr64` のバイト列（`F3 0F 1E FA`）は単なる「何もしない命令（`nop`）」として解釈されるよう意図的に符号化されており、後方互換性を保ったままセキュリティ保護を導入できるようになっています。

### 理解度チェック（次節へ進む前の確認）

本節のレジスタ上位ビット挙動・`leaq`・ステータスフラグ判定・`switch` 翻訳戦略を具体的な問題で確認します。

> **【確認の問い】**
>
> 1. **（`movw` vs `movl` の上位ビット挙動と `leaq` による整数演算）**
>     64ビットレジスタに `%rax = 0x1122334455667788`、`%rdi = 10` が入っているとします。
>
>     * (a) 初期状態から16ビット書き込み `movw $0x00FF, %ax` を実行した場合と、同じ初期状態から32ビット書き込み `movl $0x000000FF, %eax` を実行した場合で、それぞれ実行後の `%rax` の値は16進数でいくらになるでしょうか。違いが生まれる理由（x86-64 の設計規則）も簡潔に答えてください。
>     * (b) 命令 `leaq 16(%rdi, %rdi, 8), %rax` を実行すると、`%rax` は `%rdi`（$= x$）に対するどのような数式を計算したことになるでしょうか。`%rdi = 10` のときの具体的な値（10進数）と、この命令がメモリ参照およびステータスフラグ更新を行うか否かも答えてください。
>
> 2. **（`cmpb` の4フラグ判定と符号あり／なし分岐の食い違い）**
>     8ビットレジスタに `%al = 0x80`、`%bl = 0x7F` が入っている状態で `cmpb %bl, %al`（`%al - %bl`）を実行します。
>
>     * (a) `%al` と `%bl` をそれぞれ「符号あり8ビット整数（2の補数）」および「符号なし8ビット整数」として解釈した10進数の値を答えたうえで、`cmpb %bl, %al` の計算結果（16進数）と4つのステータスフラグ（`ZF`, `SF`, `CF`, `OF`）の値をすべて求めてください。
>     * (b) この直後に符号ありの `jg`（条件：`ZF == 0 && SF == OF`）と符号なしの `ja`（条件：`CF == 0 && ZF == 0`）をそれぞれ置いたとき、ジャンプするか否かをフラグ条件へ当てはめて説明してください。
>
> 3. **（`switch` 文の範囲チェック `subl`＋`ja` と疎な `case` 値の翻訳判断）**
>
>     * (a) `case 10:`〜`case 14:` の5つの連番を扱う `switch (x)` 文（`x` は32ビット `int` 型で `%eax` にあるとします）をジャンプテーブルへ翻訳するとき、コンパイラは `subl $10, %eax` に続けて `cmpl $4, %eax` と符号なしジャンプ `ja .L_default` を生成します。`x = 9`（下限未満）と `x = 15`（上限超過）のそれぞれについて、`subl $10, %eax` 後の `%eax` の値（符号なし32ビット整数としての解釈を含む）を追い、1回の `ja` だけで下限・上限を同時に弾ける理由を説明してください。
>     * (b) 一方、`case` の値が `1, 500, 10000, 500000, 10000000` のように飛び飛び（疎）である場合、単純なジャンプテーブルを使うとどのような問題が生じ、現代のコンパイラは代わりにどの翻訳戦略を選ぶでしょうか。
