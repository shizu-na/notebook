### 前節（1-4）の確認問題の解答

前節の最後に提示した3つの問いの解答を確認します。

1. **セクション配置・記号表と `.bss` が実行ファイルサイズを増やさない理由：**

    * **(a) ELF セクション名と `nm` の記号：**

        * **① `static int cnt = 0;`：** 初期値が `0` のファイルローカル静的変数のため **`.bss`**、`nm` では **`b`**（小文字）になります。
        * **② `const char *msg = "hi";`：** 文字列リテラル **`"hi"` 本体** は読み取り専用データのため **`.rodata`** に置かれます。一方、**ポインタ変数 `msg` 自体** は `"hi"` の先頭アドレスという非ゼロ値で初期化された書き換え可能なグローバル変数であるため **`.data`** に置かれ、`nm` では **`D`**（大文字）になります（※ポインタ自体も書き換え禁止にする `const char * const msg` であれば `.rodata`／`R` になります）。
        * **③ `int big_buf[1024 * 1024];`：** 未初期化のグローバル配列のため **`.bss`**、`nm` では **`B`**（大文字）になります。

    * **(b) `.bss` がディスク上の実行ファイルサイズを増やさない理由：**
        `.bss` セクションには **`NOBITS` 属性** が与えられており、ファイル内部には `0x00` の実データを一切書き込まず（ファイル上の占有サイズは **0 バイト**）、セクションヘッダに「実行時に必要なバイトサイズ（4 MiB）とアラインメント」というメタ情報だけを記録します。プログラム起動時に OS のローダがそのサイズ分のメモリ領域を確保してゼロ初期化するため、巨大な未初期化配列を宣言してもディスク上のファイルサイズはほとんど増えません。

2. **`A = -5` と負のオフセットを含む `R_X86_64_PC32` 再配置の手計算：**

    * **(a) `addl $1, flag(%rip)`（`A = -5`）の計算と理由：**
        7バイト命令 `83 05 00 00 00 00 01` の先頭が `0x2000` なので、オペコード・ModR/M（2バイト）の直後にある仮変位欄の先頭は $P = \mathbf{\texttt{0x2002}}$ です。また $S = \texttt{0x5010}$、$A = -5$ なので、

        $$S + A - P = \texttt{0x5010} + (-5) - \texttt{0x2002} = \texttt{0x5010} - \texttt{0x2007} = \mathbf{\texttt{0x3009}}$$

        となります（検算：次の命令の先頭 `%rip` は `0x2000 + 7 = 0x2007` であり、`0x2007 + 0x3009 = 0x5010` で `flag` のアドレスと一致します）。リトルエンディアンで埋め込まれる4バイト列は **`09 30 00 00`** です。
        また、加数 $A$ が `-4` ではなく **`-5`** になる理由は、4バイトの仮変位欄の後ろにさらに1バイトの即値（`01`）が続くため、相対参照の起点となる次の命令 `%rip` が $P + 4 + 1 = P + 5$ の位置に来るからです。これを $S - (P + 5) = S + (-5) - P$ と表すために `A = -5` が記録されます。

    * **(b) 低位アドレスへの負の相対オフセット（`table` = `0x2FF0`）：**
        6バイト命令の先頭が `0x3000` なので $P = \texttt{0x3002}$、$A = -4$（次の命令 `%rip = 0x3006`）、$S = \texttt{0x2FF0}$ です。

        $$S + A - P = \texttt{0x2FF0} + (-4) - \texttt{0x3002} = \texttt{0x2FF0} - \texttt{0x3006} = -\texttt{0x16} \quad (-22)$$

        これを32ビット符号あり整数（2の補数）で表すと $\texttt{0x100000000} - \texttt{0x16} = \mathbf{\texttt{0xFFFFFFEA}}$ となり、リトルエンディアンでの4バイト列は **`ea ff ff ff`** になります（検算：$\texttt{0x3006} + (-\texttt{0x16}) = \texttt{0x2FF0}$）。

3. **複数ファイル間のシンボル解決・弱シンボル・未定義参照エラーの診断：**

    * **(a) 両方に `static void helper(void)` がある場合：** **リンク成功します。** `static` を付けた関数は ELF 記号表で `LOCAL`（`t`）として扱われ各ファイル内に隠蔽されるため、同名であっても衝突しません。
    * **(b) `a.o` に `weak`、`b.o` に強い `hook` がある場合：** **リンク成功します。** 弱シンボル（`weak`）は他に通常の強い定義が存在すればそちらを優先する規則のため、多重定義エラーにならず `b.o` の `hook` が採用されます。
    * **(c) `a.o` が `extern int calc(int)` を呼び、`b.o` に `static int calc(int)` がある場合：** **リンクエラー（`undefined reference to 'calc'`）になります。** `a.o` は外部定義を求める未定義参照（`U`）を持ちますが、`b.o` 側の `calc` は `static` によるローカルシンボル（`t`）のため他ファイルから参照できず、リンカが実体を見つけられないためです。

## 1-5. 静的リンクと動的リンク（PIC・PIE・GOT/PLT）

### 1. 動機（Why）：共有ライブラリを「1バイトも書き換えずに」複数プロセスで共有する難題

前節（[1-4節](1-4.md)）では、複数のオブジェクトファイル（`main.o`, `sub.o`）をリンカが結合し、未確定だったアドレスを確定値へ書き換えて1つの実行可能ファイルへまとめる仕組み（**静的リンク**の基本）を見ました。

ところが、現実のシステムでは `ls`、`cat`、`grep`、Webサーバなど何百ものプログラムが、いずれも同じ標準Cライブラリ（`libc`）の `printf` や `malloc` を使います。もし全プログラムへ `libc` の機械語を丸ごとコピーして埋め込むと、ディスクも主記憶も大量に浪費され、ライブラリを1行修正するだけで全プログラムの再ビルドが必要になります。

そこで登場したのが、ライブラリの機械語を独立した1つのファイル（**共有ライブラリ：`lib*.so`**）として置き、プログラムの**実行時**にメモリへ読み込んで全プロセスで共有する **動的リンク（Dynamic Linking）** です。

しかし、動的リンクを実現しようとすると、すぐに2つの厄介な設計課題にぶつかります。

1. **共有ライブラリがメモリの何番地に置かれるか、コンパイル時には分からない：**
    プロセスAが `libA.so` と `libc.so` を読み込み、プロセスBが `libB.so` と `libc.so` を読み込むとき、`libc.so` が置かれる仮想アドレスはプロセスごとに変わり得ます。もし前節のように `.text` の機械語の中に確定アドレスを直接書き換えてしまうと、書き込み時にプロセス専用の物理ページが複製（**コピーオンライト：Copy-on-Write**）されてしまい、プロセスAとプロセスBで物理メモリを共有できなくなります（しかも `.text` は本来書き込み禁止 `r-x` です）。

2. **起動時に数千個のライブラリ関数をすべて解決すると起動が遅い：**
    大きな共有ライブラリには何千もの関数が含まれますが、1回の実行で実際に呼ばれるのはそのうちの数個だけということも珍しくありません。

本節では、静的リンクと動的リンクのトレードオフを比較したうえで、上の2つの難題を「**間接参照（Indirection）**」の工夫で効率よく解決する **PIC / PIE** と **GOT / PLT** の仕組みを1ステップずつ追っていきます。

---

### 2. 具体例と動作イメージ（Toy Model）

仕組みの細部に入る前に、同じ1行の Hello World プログラムを「静的リンク」と「動的リンク」の2通りでビルドして比べてみます。

#### 実験A：Hello World のファイルサイズと依存ライブラリの違い

次の短いCプログラム `hello.c` を、GCCのデフォルト（動的リンク）と `-static` オプション（静的リンク）でそれぞれコンパイルします。

```c
#include <stdio.h>
int main(void) {
    printf("Hello %d\n", 1); // %d を入れて GCC による puts への自動置換を避ける
    return 0;
}
```

典型的な64ビットLinux環境での出力サイズと `ldd`（依存する共有ライブラリの一覧表示）の結果は、およそ次のようになります。

| ビルド方法 | 実行ファイルサイズ（目安） | `ldd` の結果 | 特徴 |
| :--- | :---: | :--- | :--- |
| **動的リンク**（`gcc hello.c`） | **約 16 KiB** | `libc.so.6`, `ld-linux-x86-64.so.2`, `linux-vdso.so.1` | 実行ファイル本体には `printf` の実体が入っていない |
| **静的リンク**（`gcc -static hello.c`） | **約 800 KiB〜1 MiB** | `not a dynamic executable` | `printf` や関連する `libc` のコードがすべて埋め込まれている |

わずか数行のプログラムでも、静的リンクでは実行ファイルサイズが **50倍以上** に膨らみます。一方、動的リンクで作ったファイルは `16 KiB` しかなく、起動時に外部の `libc.so.6` を探して接続する構造になっています。

#### 実験B：同じ `libc.so.6` がプロセスごとに異なる番地へ載る様子

動的リンクされた2つのプログラムを同時に動かしたとき、同じ `libc.so.6` の機械語本体は、物理メモリ（RAM）上では**たった1つのコピー**を両プロセスで共有します。しかし、それぞれのプロセスから見た仮想アドレス（[第3部](../index.md#part-3)で詳述するプロセスごとの住所空間）は、たとえば次のように異なる番地へ配置されます。

* プロセスAから見た `libc.so.6` の先頭は `0x7f10_0000_0000` です。
* プロセスBから見た `libc.so.6` の先頭は `0x7f82_0000_0000` です。

つまり、`libc.so.6` の `.text` セクションに書かれた機械語は、**「自分の先頭番地が `0x7f10...` であっても `0x7f82...` であっても、1バイトも書き換えずにそのまま正しく動く」** ように作られていなければなりません。これを可能にするのが、次の第3節で説明する **PIC** と **GOT / PLT** です。

---

### 3. 構造・アルゴリズム・実装（What）

#### (1) 静的リンクと動的リンクの比較

まず、ライブラリ形式とリンク方式の違いを整理します。

* **静的ライブラリ（アーカイブ：`lib*.a`）：** 複数のオブジェクトファイル（`*.o`）を `ar` コマンドで1つに束ねた書庫です。リンク時に必要な `*.o` だけが取り出され、実行ファイルへ丸ごとコピーされます。
* **共有ライブラリ（Shared Object：`lib*.so`）：** 動的リンク用にコンパイルされたELFバイナリです。実行ファイルには「`libc.so.6` が必要」という名前情報だけを記録し、実体は実行時にメモリへ読み込みます。

| 比較項目 | 静的リンク（`lib*.a`） | 動的リンク（`lib*.so`） |
| :--- | :--- | :--- |
| **ディスク・RAM効率** | 各バイナリに重複コピーされ消費が大きい | `.text` を全プロセスで1つに共有でき効率的 |
| **起動・呼出の速度** | 実行時の解決が不要でわずかに速い | 起動時の読み込みと初回解決のオーバーヘッドがある |
| **セキュリティ更新** | ライブラリ修正後、全アプリの**再リンク**が必要 | 共有ライブラリ（`.so`）の差し替えだけで全アプリへ反映 |
| **配布の容易さ** | 単一バイナリで他環境へコピーするだけで動く | 実行環境に適切なバージョンの `.so` が揃っている必要がある |

#### (2) 動的リンカ（ELFインタプリタ）の起動フロー

動的リンクされた実行ファイルを起動するとき、OSのカーネルはいきなり `main`（や `_start`）へ飛びません。カーネルは実行ファイルのELFプログラムヘッダに含まれる **`PT_INTERP` セグメント**（実体は `.interp` セクションに書かれたパス文字列）を解釈し、そこに指定された **動的リンカ**（Linux x86-64では `/lib64/ld-linux-x86-64.so.2`）を先にメモリへ読み込んで制御を渡します。

動的リンカは次の3ステップを実行してから、本来のプログラムを開始します。

1. 実行ファイルの **`.dynamic` セクション（必要な共有ライブラリの部品リスト）** を読み、必要な共有ライブラリ（`libc.so.6` 等）をファイルシステムから探してメモリへ **マップ**（ファイル内容をプロセス空間へそのまま割り当てること、詳細は[第3部](../index.md#part-3) [3-7節](../3/3-7.md)の `mmap`）します。
2. 共有ライブラリ内のデータ参照先などを、プロセス固有のテーブル（GOT）へ書き込んで解決します。
3. 準備が整ったら、本来の実行ファイルのエントリポイント（`_start` → `main`）へジャンプします。

#### (3) 位置独立コード（PIC / PIE）と GOT（Global Offset Table）

では、共有ライブラリの `.text` セクションを1バイトも書き換えずに、どの仮想アドレスに置かれても大域変数へアクセスできるようにするにはどうすればよいでしょうか。

鍵になるのは、**「OSがモジュール全体のセグメントを同じベースアドレスへ一括で平行移動（スライド配置）するため、`.text`（コード）と `.data`（データ）がメモリ全体のどこへ載るかは実行時まで不明でも、同じモジュール内における `.text` と `.data` の間の相対距離（バイト差）はリンク時に固定されたまま変化しない」** という事実です（図1-5-1）。

これを利用した設計が **位置独立コード（PIC：Position-Independent Code、`-fPIC` オプション）** です。

1. **同一モジュール内の参照：** 実行可能ファイル内や、共有ライブラリ内の `static` 変数・隠蔽（hidden）シンボルであれば、[1-2節](1-2.md)で見た `%rip` 相対アドレッシング（`movl x(%rip), %eax`）を使って絶対アドレスを埋め込まずに直接アクセスできます（※共有ライブラリ内の非 `static` 大域変数は、ELFの **シンボル割り込み（Symbol Interposition）** により実行ファイル側の同名変数で上書きされ得るため、デフォルトでは次の GOT 経由で参照されます）。
2. **別モジュール（他の `.so` 等）の変数参照：** 相手がどの番地に載るか分からないため、各モジュールのデータ領域（プロセスごとに独立した `rw-` 領域）に **GOT（Global Offset Table）** というポインタの配列を用意します。

    * `.text` の機械語は、`%rip` 相対の固定距離で `GOT[g]` のスロットを読み出し（図1-5-1の `movq g@GOTPCREL(%rip), %rax` は「`GOT[g]` のスロットを `%rip` 相対で読み出して64ビット実アドレスを `%rax` へ得る」命令です）、そこに入っている実アドレスを経由して変数 `g` へアクセスします。
    * 起動時に動的リンカが、各プロセス固有の `GOT[g]` だけへ正しい仮想アドレスを書き込みます。

この「1段の間接参照」を挟むだけで、書き換えが発生するのはごく小さなプロセス固有の GOT だけになり、**巨大な `.text` セクションは1バイトも書き換えずに全プロセスで物理メモリを共有できる**ようになります。なお、共有ライブラリだけでなく実行可能ファイル本体も位置独立コードとしてビルドしたものを **PIE（Position-Independent Executable）** と呼びます。現代のLinuxでは、実行のたびにプログラムの配置番地をランダム化して攻撃を防ぐ仕組み（[第5部](../index.md#part-5) [5-8節](../5/5-8.md)の ASLR）と組み合わせるため、PIE がデフォルトになっています。

#### (4) 関数の遅延バインディング（Lazy Binding）：PLT と GOT の2段階ジャンプ

大域変数と同じように、外部ライブラリ関数（たとえば `printf`）のアドレスも GOT に置きます。しかし、もしプログラム起動時に `libc.so` や他の共有ライブラリにある何千もの関数のアドレスをすべて探して GOT へ埋めてしまうと、プログラムの起動に時間がかかってしまいます。

そこで ELF（System V AMD64 ABI）が採用している工夫が、**「その関数がプログラム中で初めて呼ばれた瞬間にだけアドレスを解決し、2回目以降は直接ジャンプする」** という **遅延バインディング（Lazy Binding）** です。これを実現するのが **PLT（Procedure Linkage Table）** と **GOT（関数用：`.got.plt`）** の2段階ジャンプ構造です（図1-5-2）。

実行ファイルの `.text` にある `call printf` は、実際には `.plt` セクション内の小さな中継コード **`printf@plt`** を呼び出します。`printf@plt` の中身はわずか3命令です。

```asm
printf@plt:
    jmpq  *GOT[printf](%rip)   # 1. GOT[printf] に書かれた番地へ間接ジャンプ
    pushq $0                   # 2. printf の識別番号（再配置インデックス）を積む
    jmpq  PLT[0]               # 3. 動的リンカの解決ルーチンを呼び出す共通口へ
```

また、`.got.plt` の先頭3エントリは動的リンク用の予約領域になっており、**`GOT[0]`** には `.dynamic` セクションのアドレス、**`GOT[1]`** にはこのモジュール自身の識別情報（`link_map` 構造体へのポインタ）、**`GOT[2]`** には動的リンカの解決ルーチン（`_dl_runtime_resolve`）のアドレスが格納されます。ここからの動きが遅延バインディングの核心です。

* **1回目の呼び出し：**
    プログラム起動直後、`GOT[printf]` の中身には `printf` の実アドレスではなく、**すぐ次の命令である `printf@plt` の2行目（`pushq $0`）のアドレス**が仮に書き込まれています。

    1. `main` が `printf@plt` を呼ぶと、1行目の `jmpq *GOT[printf](%rip)` はすぐ下の2行目へ着地します。
    2. 2行目で関数の識別番号をスタックへ積み、3行目で共通入口 `PLT[0]` へジャンプします。`PLT[0]` はさらに `GOT[1]`（`link_map`）をスタックへ積み、`GOT[2]` に登録された解決ルーチン（`_dl_runtime_resolve`）へジャンプします。
    3. `_dl_runtime_resolve` の入口では、`main` がすでに `printf` 向けにセット済みの引数レジスタ（`%rdi`, `%rsi`, `%rdx`, `%rcx`, `%r8`, `%r9` や `%rax`, `%xmm0`〜`%xmm7`）を壊さないよう、これらをすべてスタックへ退避します。そのうえで `libc.so.6` の記号表から `printf` の実アドレスを検索して **`GOT[printf]` を実アドレスへ書き換え**、退避していた引数レジスタを元通り復元し、先ほど積んだ2つの識別情報をスタックから片付けて `printf` 本体へジャンプします。

    ここで、`main` の `call printf@plt` から `printf` 本体へ到達するまでの経路はすべて `jmp` であり、スタック上の **`main` への戻り番地はそのまま最上部に保たれています**（[1-3節](1-3.md)の末尾コール最適化［TCO］と同じ原理です）。そのため、1回目の呼び出しであっても `printf` が `ret` を実行すれば、`_dl_runtime_resolve` へ戻らずに直接 `main` へ正しく戻れます。

* **2回目以降の呼び出し：**
    すでに `GOT[printf]` が `printf` 本体の実アドレスへ書き換わっているため、`printf@plt` の1行目 `jmpq *GOT[printf](%rip)` を実行した瞬間に、**動的リンカを一切経由せず直接 `printf` 本体へ1回で飛びます**。

このように、「使われない関数の解決コストをゼロにする」ことと「2回目以降の呼び出しオーバーヘッドを間接ジャンプ1命令だけに抑える」こと、さらに「`.text` と `.plt` を一切書き換えずに共有する」ことの3つを同時に満たしています。ここまで見てきた PIC と GOT / PLT を組み合わせたとき、2つのプロセスが物理メモリ上の共有 `.text` と各自の独立した `.got` / `.data` ページをどう参照しているかをまとめたのが図1-5-3です。

> **【コラム：システムコールを共有ライブラリのように呼び出す `vDSO` の仕組み】**
>
> 実験Aで `ldd` を実行すると、自分がリンクした覚えのない **`linux-vdso.so.1`** という共有ライブラリが一覧に現れます。しかもディスク上のどこを探してもこのファイルは存在しません。
>
> `vDSO`（virtual Dynamic Shared Object）は、OSカーネルがすべてのプロセス起動時にメモリ空間へ自動的にマップする「仮想的な共有ライブラリ」です。現在時刻を取得する `gettimeofday` や `clock_gettime` のような関数は、本来ならOSカーネルへ問い合わせるシステムコール（[第3部](../index.md#part-3) [3-1節](../3/3-1.md)）を呼ぶ必要がありますが、特権モード切替には数百 ns〜1 $\mu$s 程度のオーバーヘッドがかかります。
>
> そこでLinuxカーネルは、最新の時刻データを「読み取り専用ページ」としてユーザ空間へ公開し、それを読むだけの小さな関数群を `vDSO` として通常の共有ライブラリと同じ ELF 形式で提供しています。プロセス起動時、カーネルはスタック上に積む **補助ベクトル（`auxv`：`AT_SYSINFO_EHDR` エントリ）** で `vDSO` の配置アドレスを動的リンカや `libc` へ渡します。`clock_gettime` を呼ぶと、CPUのタイムスタンプカウンタ（`rdtsc` 等）と公開ページの基準時刻から、**20〜30 ns 程度**で現在時刻を計算できます。カーネルが基準時刻を更新している最中でもロックなしで整合した値を読むため、更新前後でカウンタ値が一致するまで読み直す軽量な同期手法（**`seqlock`**、[第4部](../index.md#part-4)の並行性制御でも重要な技法）が使われています。
>
> なお、`vDSO` 化できるのは `clock_gettime` や `getcpu` のように「カーネルが公開する読み取り専用データを参照するだけの処理」に限られます。ファイル操作（`open`/`read`）やプロセス生成（`fork`）のように権限検査やカーネル状態の変更を伴う処理は、依然として通常のシステムコール命令（`syscall` / `ecall`）でカーネルへ遷移する必要があります。

### 4. 限界と補正（Critique & Adaptation）

#### (1) 依存関係の不整合（DLL地獄）と静的リンク・コンテナによる再評価

動的リンクはメモリとディスクを節約し、OS全体のライブラリを一括更新できる優れた仕組みですが、運用面では **依存ライブラリのバージョン不整合（いわゆる DLL 地獄 / 依存関係地獄）** という弱点を抱えています。開発環境では `libfoo.so.2` 向けにビルドしたのに、本番サーバには `libfoo.so.1` しか入っていないと起動時にクラッシュします。また、アプリAは古いバージョン、アプリBは新しいバージョンを要求するような衝突も起こり得ます。

現代のソフトウェア開発では、ストレージやメモリが安価になった背景もあり、用途に応じた2つの補正が広く使われています。

* **単一バイナリの再評価：** Go言語やRustなどでは、標準ライブラリを含めて静的リンク（あるいは `libc` 以外の依存をすべて静的リンク）し、1ファイルをコピーするだけでどのLinux環境でも動く配布性を優先する設計が増えています。
* **コンテナによる依存環境の封じ込め：** Dockerなどのコンテナ技術では、アプリ本体と特定のバージョンの共有ライブラリ群を1つのファイルシステムイメージにまとめて隔離することで、動的リンクの仕組みを保ったままホスト環境とのバージョン衝突を解消しています。

#### (2) GOT 書き換え攻撃と RELRO（Relocation Read-Only）

遅延バインディングを成立させるために、`.got.plt` セクションは**実行中も書き込み可能（`rw-`）**にしておく必要がありました。ところがセキュリティの視点から見ると、「関数を呼び出すたびに必ずジャンプ先として参照されるテーブル（GOT）が、プログラム実行中に書き換え可能である」ことは大きな弱点になります。もしバッファオーバーフロー等の脆弱性で `GOT[printf]` の中身を攻撃者の用意したアドレスへ書き換えられると、次にプログラムが `printf` を呼んだ瞬間に乗っ取られてしまいます（**GOT Overwrite 攻撃**）。

また、動的リンカの検索順序を上書きする環境変数 `LD_LIBRARY_PATH` や、任意の共有ライブラリを先に読み込ませる `LD_PRELOAD` も、デバッグやテストには便利な反面、一般ユーザが実行してもファイル所有者の特権で動くプログラム（[第5部](../index.md#part-5) [5-7節](../5/5-7.md)の `setuid` 等）では悪用を防ぐ安全機構が働きます。具体的には、`setuid` バイナリの起動時にカーネルが補助ベクトル（`auxv`）へ **`AT_SECURE = 1`** を設定して渡し、これを受け取った**動的リンカ側が `LD_PRELOAD` や `LD_LIBRARY_PATH` を無視する**仕組みになっています。

GOT書き換えに対する現代の標準的な補正が、**RELRO（Relocation Read-Only）** です。

* **Partial RELRO（部分的保護）：** データ用の `.got` などを保護しつつ、関数用の `.got.plt` だけは遅延バインディングのため書き込み可能に残します。
* **Full RELRO（完全保護：`-Wl,-z,relro,-z,now`；`-Wl,` は後続オプションをリンカ `ld` へそのまま渡す指定で、`now` は起動時一括解決フラグ `BIND_NOW` を有効化）：** **遅延バインディングをあえて無効化**し、起動時に少し待ってでも動的リンカがすべての関数アドレスを一括解決した直後に、**GOT全体を OS のメモリ保護機能で読み取り専用（`r--`）へ凍結**する安全策です。起動時間はわずかに増えますが、実行中のGOT書き換えをハードウェアのメモリ保護で防げるため、セキュリティ重視のバイナリでは広く採用されています。

> **【コラム：`LD_PRELOAD` によるシンボル割り込み（Symbol Interposition）と実務応用】**
>
> 3-(3) で触れた通り、ELF の動的リンカはシンボルを検索するとき、ロードされた順序で最初に見つかった定義を採用します。この仕組みを積極的に活用するのが、指定した共有ライブラリを `libc.so.6` 等より先に読み込ませる環境変数 **`LD_PRELOAD`** です。
>
> たとえば、既存の実行ファイルを1行も再コンパイルせず、起動時に `LD_PRELOAD=/usr/lib/libjemalloc.so ./server` と指定するだけで、プログラム中の `malloc` / `free` 呼び出しをすべて標準の `libc` 実装から高速なアロケータ（**`jemalloc`** や **`tcmalloc`**）へ丸ごと差し替えられます。また、独自に `malloc` 関数を定義した共有ライブラリを `LD_PRELOAD` で差し込み、呼び出し履歴をログへ記録してから `dlsym(RTLD_NEXT, "malloc")` で本来の `libc` 側 `malloc` を呼ぶラッパを作れば、本番バイナリのメモリリーク検査や I/O のトレースにも応用できます。動的リンクの「間接参照と実行時解決」という設計が生む、実務上広く活用されている機能です。

### 理解度チェック（次節へ進む前の確認）

本節の PIC の相対計算・遅延バインディングの復帰機構・Full RELRO・`LD_PRELOAD`・`vDSO` を具体的な問題で確認します。

> **【確認の問い】**
>
> 1. **（PIC の `%rip` 相対ディスプレイスメント計算と非 PIC 共有ライブラリの問題）**
>     共有ライブラリ `libcalc.so` の `.text` 内に、7バイト命令 `movq g@GOTPCREL(%rip), %rax` がモジュール先頭からのオフセット `0x1200` に置かれており、同じモジュール内の `GOT[g]` がオフセット `0x3FE8` に置かれています。
>
>     * (a) このライブラリがプロセスAではベース `0x7f10_0000_0000`、プロセスBではベース `0x7f82_0000_0000` にロードされたとき、それぞれのプロセスにおける「次の命令の `%rip`」と「`GOT[g]` の仮想アドレス」を求め、命令内に埋め込まれる `%rip` 相対ディスプレイスメント（16進数）が両プロセスで一致することを計算で確かめてください。
>     * (b) もし共有ライブラリを `-fPIC` なしでビルドし、起動時に動的リンカが `.text` 内の絶対アドレスを直接書き換える方式をとると、複数プロセス間の物理メモリ共有が壊れてしまう理由をコピーオンライトの仕組みから説明してください。
>
> 2. **（遅延バインディング初回呼び出しの復帰と Full RELRO のトレードオフ）**
>
>     * (a) 遅延バインディング有効時の1回目の `call printf@plt` では、`printf@plt` → `PLT[0]` → `_dl_runtime_resolve` → `printf` 本体と複数の中継先を経由します。それでも `printf` 本体が `ret` を実行するだけで（`_dl_runtime_resolve` へ戻らずに）直接 `main` へ正しく戻れる理由を、`call`/`jmp` の使い分けとスタック上の戻り番地・一時情報の扱いから説明してください。
>     * (b) Full RELRO（`-Wl,-z,relro,-z,now`）を有効にした場合、Partial RELRO（遅延バインディング有効）と比べて「プログラム起動時間」と「実行中のセキュリティ（GOT 書き換え耐性）」がそれぞれどう変化するか整理してください。
>
> 3. **（`LD_PRELOAD` が効かない条件と `vDSO` で高速化できる境界）**
>
>     * (a) `LD_PRELOAD=./my_malloc.so ./app` を実行して `malloc` を差し替えようとしたところ、① `./app` が `gcc -static` で静的リンクされていた場合、② `./app` に `setuid` ビットが設定されていた場合、のどちらでも `my_malloc.so` の関数は呼ばれませんでした。それぞれ効かない理由を答えてください。
>     * (b) `vDSO` は `clock_gettime` や `getcpu` を数十 ns へ高速化できる一方、`open`・`write`・`fork` は `vDSO` 化できず通常のシステムコール命令（`syscall`）でカーネルへ遷移する必要があります。`vDSO` 化できる処理とできない処理の境界はどこにあるでしょうか。
