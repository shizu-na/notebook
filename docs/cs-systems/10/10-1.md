### 前節（9-9）の確認問題の解答

前節の最後に提示した3つの問いの解答を確認します。問3がそのまま[第10部](../index.md#part-10)（仮想化・コンテナと Web インフラ）の本節の導入になります。

1. **2 相コミット（2PC）の障害タイミング別トレースとブロッキング問題：**

    * **(a) $P_2$ が投票前にクラッシュした場合（ブロックしない）：**
        コーディネータ $C$ は $P_2$ からの応答タイムアウトを検知した時点で「全員一致の `VOTE_COMMIT` が揃わなかった」と判断し、自身の WAL へ `ABORT` を記録して **`GLOBAL_ABORT`** を決定し、$P_1$ へ送信します。$P_1$ はそれを受け取ってローカルで UNDO アボートし、保持していた X ロックを即座に解放できるため、システム全体はブロックしません。

    * **(b) 両参加者が `PREPARED` になった後に $C$ がクラッシュした場合（ブロックする）：**
        $P_1$ と $P_2$ が「双方とも `PREPARED` である」と確認できても、**$C$ が「自身の WAL へ `COMMIT` を書き終えた直後（送信前）に落ちた」のか、「まだ決定を WAL へ書く前（復旧後に `ABORT` になる可能性あり）に落ちた」のかを参加者側から判別できません**。勝手な判断は他ノードや復旧後の $C$ と矛盾するリスクがあるため、ACID の分離性を保つべく X ロックを解放できず、$C$ の復旧まで無期限にブロックします。

2. **シャーディングと同期／非同期レプリケーションのトレードオフ：**

    * **(a) シャーディングが突破する限界と新たな課題：**
        単一サーバの CPU・RAM・ディスク容量の上限（スケールアップの壁）を、データをキー範囲やハッシュで複数ノードへ水平分割することで突破します。一方で、複数ノードにまたがる結合（`JOIN`）やトランザクション（2PC）のコストが増大します。

    * **(b) 同期レプリケーション vs 非同期レプリケーション：**
        **同期レプリケーション**は、スタンバイノードへの WAL 複製と永続化を待ってからクライアントへコミット応答を返すため、プライマリ障害時のデータ損失（RPO＝0）を防げますが、ノード間のネットワーク往復遅延（RTT）がそのまま書き込み遅延へ上乗せされます。**非同期レプリケーション**はローカル永続化だけで即答するため低遅延ですが、複製が追いつく前にプライマリが故障すると直近のコミット済みデータが失われるリスクがあります。

3. **1 台の物理サーバへ複数サービスを安全に相乗りさせる課題（本節への接続）：**
    単一 OS 上のプロセス隔離（[3-2](../3/3-2.md)・[3-5節](../3/3-5.md)）では、すべてのプロセスが **たった 1 つの OS カーネル** を共有しているため、① 異なる OS（Linux と Windows、あるいは異なるカーネルバージョン）を同時に動かせない、② カーネルに 1 箇所でも権限昇格脆弱性があると同居する他顧客の全データが危険に晒される、③ CPU・メモリ・I/O 帯域の厳密な割り当てやサーバ丸ごとの停止・移動が難しい、という限界があります。これらをハードウェア資源そのものの仮想化によって解決するのが、本節で学ぶ **ハードウェア仮想化とハイパーバイザ** です。

## 10-1. ハードウェア仮想化とハイパーバイザ（VT-x・2段ページテーブル・VirtIO）

### 1. 動機（Why）：なぜ「OS の下にさらに OS のような層（ハイパーバイザ）」を挟むのか

[第3部](../index.md#part-3)から[第5部](../index.md#part-5)を通じて、OS カーネルが 1 台のコンピュータの CPU・メモリ・I/O デバイスを仮想化し、多数のプロセスへ安全に分配する仕組みを学びました。

しかし現代のクラウド（AWS EC2、Google Compute Engine 等）や企業データセンターでは、1 台の物理サーバに **64〜128 コアの CPU と数百 $\text{GiB}$ 〜数 $\text{TiB}$ の RAM** が搭載されています。この巨大な物理マシンをたった 1 つのサービスや 1 社の顧客だけで占有すると、CPU 利用率が 5% 未満のまま電力と設備費が浪費されてしまいます。

かといって、不特定多数の顧客のアプリケーションを「同じ 1 つの Linux カーネル上の別々のプロセス」として相乗りさせると、次の 3 つの壁に突き当たります。

1. **OS 環境の多様性：** 顧客 A は Ubuntu Linux、顧客 B は Windows Server、顧客 C は古いカーネルの検証環境を動かしたいとき、単一 OS では応えられません。
2. **カーネル共有によるセキュリティ境界の脆弱さ：** OS カーネルは数千万行の巨大コードであり、システムコール層に 1 つでもバグがあれば、悪意ある顧客が同居する他社のメモリへ侵入するリスクがあります。
3. **インフラ運用の柔軟性（保守・移行）：** 物理ハードウェアの故障予兆が出たとき、稼働中のサービスを止めずに別の物理サーバへ丸ごと引っ越せる仕組みが求められます。

これらの課題に対処する仕組みが **ハードウェア仮想化** です。物理ハードウェアの直上に **ハイパーバイザ（Hypervisor / VMM：Virtual Machine Monitor）** を配置し、その上で「自分専用の物理 CPU・物理メモリ・物理ディスクを占有している」と認識する複数の **仮想マシン（VM：Virtual Machine）** と **ゲスト OS** を同時に稼働させます。

本節では、CPU・メモリ・I/O の 3 大資源をどうやって高速かつ安全に仮想化しているのか（**VT-x / 2段ページテーブル / VirtIO と IOMMU**）を、[第3部](../index.md#part-3)・[第5部](../index.md#part-5)の知識と直結させて解き明かします。

---

### 2. 具体例と動作イメージ（Toy Model）

アーキテクチャの詳細に入る前に、仮想化の本質的な難しさを表す 2 つの具体例を手計算で確かめます。

#### 実験A：ゲスト OS が「特権命令」を実行した瞬間に何が起きるか

[3-1節](../3/3-1.md)で確認した通り、OS カーネルは「自分が CPU の最高特権（S-mode / Ring 0）を独占している」という前提で書かれています。そのため、ゲスト OS は起動時やコンテクストスイッチのたびに、ページテーブルを切り替える命令（RISC-V の `csrw satp, ...` や x86 の `mov cr3, ...`）や、割り込み禁止命令（`cli`）をそのまま実行します。

もしハイパーバイザがゲスト OS に本当に物理 CPU の最高特権を与えてしまったら、ゲスト OS は物理マシン全体のメモリを書き換えて他の顧客の VM やハイパーバイザ自身を乗っ取ってしまいます。

そこでハイパーバイザは、**[3-1節](../3/3-1.md)で OS がユーザプロセスに対して行ったのと同じ手口（トラップ＆エミュレート）** をもう 1 段深く適用します。

1. ゲスト OS は物理的には「権限を一段落とした状態（非特権／仮想化ゲストモード）」で動かします。
2. ゲスト OS が `hlt`（CPU 停止）などの特権命令を実行した瞬間（さらに後述の 2 段ページテーブル［EPT］が無効なシャドウページテーブル方式では `cr3` 書換え時も）、CPU ハードウェアが自動的に実行を中断して **ハイパーバイザへトラップ（VM Exit）** します（なお、EPT を有効化した現代の環境では `cr3` 書換えによる VM Exit は不要になります）。
3. ハイパーバイザは「ゲスト OS が何をしたかったのか」を読み取り、その VM 専用の仮想状態だけを安全に更新して（エミュレートして）、再びゲスト OS の次の命令へ戻します（**VM Entry**）。

ゲスト OS の目線からは、何事もなかったかのように自分が物理マシンを支配しているように見え続けます。

#### 実験B：2 段ページテーブルによる TLB ミスの「2 次元ページウォーク（24 回アクセス）」

[3-5節](../3/3-5.md)で学んだ通り、通常の 64 ビット環境（4 段ページテーブル）では、TLB ミスが 1 回起きると仮想アドレス（VA）から物理アドレス（PA）を引くために **4 回** のメモリアクセスが必要です。

では、仮想マシン上では何が起きるでしょうか。VM の中ではアドレス空間が次の **3 段階** に増えます。

* **GVA（Guest Virtual Address）：** ゲスト OS 上のアプリが使う仮想アドレス
* **GPA（Guest Physical Address）：** ゲスト OS が「物理メモリだと思い込んでいる」アドレス
* **HPA（Host Physical Address）：** 物理マシンの DRAM 上の本物の物理アドレス

ゲスト OS のページテーブルが「GVA → GPA」を変換し、ハイパーバイザの 2 段目ページテーブル（**EPT / NPT：Extended / Nested Page Tables**）が「GPA → HPA」を変換します。ここで **TLB ミスが 1 回起きたとき**、ハードウェア MMU が行うメモリアクセス回数を数えてみましょう。

前提として、ゲストの `cr3` が指すページテーブル先頭アドレス自体も GPA であるため、ゲストの 4 段ページテーブル（L4, L3, L2, L1）を辿るには、各段のテーブルアドレス（GPA）を 1 段ごとに EPT で HPA へ変換する必要があります。

1. ゲストの 4 段ページテーブル（L4, L3, L2, L1）の **各テーブルの GPA を HPA へ変換するために、毎回ホスト側の 4 段 EPT を辿ります**（$4 \times 4 = 16$ 回）。
2. 各段のゲスト PTE（ページテーブルエントリ）自体を読み出すアクセスが **$4$ 回** あります。
3. 最後に L1 のゲスト PTE から得られた目的データページの GPA を本物の HPA へ変換するため、もう 1 回ホスト側の 4 段 EPT を辿ります（**$4$ 回**）。

つまり、4 つのゲストテーブル GPA と 1 つの最終データページ GPA の計 5 回の EPT ウォーク（$5 \times 4 = 20$ 回）に 4 回のゲスト PTE 読み出しを加えて、たった 1 回の TLB ミスを解決するために

$$
(4 \times 4) + 4 + 4 = (4 + 1)(4 + 1) - 1 = \mathbf{24\text{ 回のメモリアクセス}}
$$

が発生します。一般に、ゲスト側が $g$ 段・ホスト側 EPT が $h$ 段であれば、テーブル GPA の EPT 変換（$g \times h$ 回）、ゲスト PTE 読み出し（$g$ 回）、最終データページの EPT 変換（$h$ 回）の合計で $(g \times h) + g + h = (g + 1)(h + 1) - 1$ 回となります（目的データ本体のアクセス 1 回を除いた変換コストだけで、非仮想化環境の **6 倍** です）。この重さが、仮想化環境で Huge Pages（$2\text{ MiB} / 1\text{ GiB}$ ページ）が重視される直接の物理的理由です（$2\text{ MiB} / 4\text{ KiB} = 512 = 2^9$ より、9 ビット分のページテーブル 1 段を省略でき、4 段から 3 段へ減らせます）。

### 3. 構造・アルゴリズム・実装（What）

#### (1) ハイパーバイザの分類と Popek-Goldberg の仮想化要件

ハイパーバイザは、物理ハードウェアとの配置関係によって 2 つに分類されます。

* **Type 1（ベアメタル型）：** 物理ハードウェアの上へホスト OS を挟まず直接ハイパーバイザが載る構成です。オーバーヘッドが小さく、クラウドやデータセンターの標準です（例：VMware ESXi, Xen, Hyper-V, AWS Nitro）。
* **Type 2（ホスト型）：** Windows や macOS などの既存ホスト OS の上で、通常アプリケーションの 1 つとしてハイパーバイザが動く構成です。開発・検証用途で手軽に使われます（例：VirtualBox, VMware Workstation）。
* **Linux KVM（Kernel-based Virtual Machine）の位置づけ：** Linux カーネル自身のモジュールとして組み込まれ、Linux カーネルそのものを Type 1 ハイパーバイザへ変身させます。CPU スケジューリングやメモリ管理は成熟した Linux カーネルに任せつつ、ユーザ空間の **QEMU** と協調してデバイスエミュレーションを行うハイブリッド構成であり、現在のクラウド基盤（GCP, OpenStack 等）で広く使われています。

1974年、ポペックとゴールドバーグ（Popek & Goldberg）は、ある CPU アーキテクチャが「単純なトラップ＆エミュレートだけで効率よく仮想化可能であるための数学的条件」を示しました。

> **【Popek-Goldberg の定理】**
> CPU の命令のうち、ハードウェア構成を変更したり特権状態に依存して挙動が変わったりする **機微命令（Sensitive Instructions）** の集合が、非特権モードで実行すると必ずトラップを起こす **特権命令（Privileged Instructions）** の集合の部分集合であるとき、その ISA は単純なトラップ＆エミュレートで仮想化可能である。

ところが、かつての **x86 アーキテクチャ** には「非特権モードで実行してもトラップを起こさず、黙って失敗したり現在の特権レベル（Ring 番号）をそのまま漏らしてしまったりする 17 個の非特権機微命令（例：フラグレジスタを書き換える `POPF`、システムテーブルのアドレスを読み出す `SGDT`）」が存在し、Popek-Goldberg の条件を満たしていませんでした。初期の VMware は、ゲストの機械語を実行直前にスキャンして危険な命令を安全なコードへ置き換える **バイナリ変換（Binary Translation）** による動的書き換えでこれを回避しました。

#### (2) CPU のハードウェア支援仮想化（Intel VT-x / AMD-V / RISC-V H 拡張）

バイナリ変換の複雑さとオーバーヘッドを根本から解消するため、2005〜2006年に Intel と AMD は CPU ハードウェア自体へ仮想化専用モードを追加しました（**Intel VT-x / AMD-V**。ARM の **EL2［Exception Level 2］**、RISC-V の **H 拡張［Hypervisor Extension］** も同型の仕組みです）。

Intel VT-x の構造を図10-1-1に示します。従来の Ring 0〜3 の縦軸とは直交する形で、CPU に **2 つの動作モード** を新設しました。

1. **VMX Root モード（ハイパーバイザ用）：** 物理ハードウェアの全権限を持つモードであり、ハイパーバイザがここで動作します。
2. **VMX Non-Root モード（ゲスト VM 用）：** ゲスト OS（Ring 0）とゲストアプリ（Ring 3）がそのままの特権階層で動作できる専用モードです。ゲスト OS は自分では Ring 0 で動いているように見えますが、特定の特権操作や割り込み・I/O 命令を実行した瞬間だけ、ハードウェアが自動的に **VM Exit** を起こして VMX Root モードのハイパーバイザへ制御を渡します。

各仮想 CPU（vCPU）のレジスタ状態・トラップ条件（どの命令で VM Exit を起こすか）・ホスト復帰先アドレスは、RAM 上の専用制御構造体 **VMCS（Virtual Machine Control Structure）** へ一括保存され、`VMLAUNCH` / `VMRESUME` の 1 命令で **VM Entry**（ゲストへの復帰）が完了します。

#### (3) メモリ仮想化：シャドウページテーブルから 2 段ページテーブル（EPT / NPT）へ

実験Bで確認した **GVA → GPA → HPA** の 2 段階アドレス変換を実現する方法は、歴史的に 2 世代へ進化しました。

1. **シャドウページテーブル（ソフトウェア方式・第 1 世代）：**
    ハイパーバイザが、ゲスト OS のページテーブル（GVA → GPA）とホストの割り当て表（GPA → HPA）をあらかじめ合成した「直結テーブル（GVA → HPA）」をソフトウェアで管理し、物理 MMU へ設定します。TLB ミス自体は通常の 4 回アクセスで済みますが、**ゲスト OS が自分のページテーブルを 1 エントリ書き換えるたびに必ず VM Exit が発生** してハイパーバイザが同期を取り直す必要があり、プロセス生成（`fork`）やページフォルトが多いワークロードで性能が大きく低下しました。

2. **2 段ページテーブル（ハードウェア方式：Intel EPT / AMD NPT / RISC-V `hgatp`・現代標準）：**
    物理 MMU ハードウェア自体が、ゲスト側のページテーブル（`cr3`：GVA → GPA）と、ハイパーバイザ側の **拡張ページテーブル（EPT：GPA → HPA）** の両方を直接認識して 2 次元ウォークを行います（図10-1-2）。これにより、**ゲスト OS がプロセスを切り替えたり自ページテーブルを書き換えたりしても VM Exit が一切起きなくなり**、さらに一度変換結果（GVA → HPA）が CPU の TLB へキャッシュされれば、次からは非仮想化環境と完全に同じ 1 サイクルでメモリアクセスできます。

#### (4) I/O 仮想化の 3 段階（完全エミュレーション・VirtIO 準仮想化・SR-IOV パススルー）

CPU とメモリが高速化されると、最後にボトルネックとして残るのがディスクや NIC の **I/O 仮想化** です。I/O 仮想化には性能と汎用性のトレードオフに応じた 3 段階の方式があります（図10-1-3）。

1. **完全エミュレーション（Full Emulation）：**
    ハイパーバイザ（QEMU 等）が、実在する古い物理ハードウェア（例：Intel e1000 NIC や IDE ディスク）の MMIO レジスタを 1 つずつソフトウェアで模倣します。ゲスト OS のドライバを一切変えずに動く高い互換性がある反面、**ゲストが制御レジスタへ 1 回書き込むたびに毎回 VM Exit が発生**するため、大きく低速化します。

2. **準仮想化 I/O（Paravirtualization：VirtIO — [5-1節](../5/5-1.md)の回収）：**
    [5-1節](../5/5-1.md)で xv6 のディスクドライバとして詳しく学んだ **VirtIO** こそ、現代クラウドにおける I/O 仮想化の標準仕様です。ゲスト OS へ「自分が VM 上にいることを知っている専用ドライバ（VirtIO ドライバ）」を入れることで、無駄なレジスタ操作を排し、RAM 上の **共有リングバッファ（Virtqueue）** へ多数の読み書き要求をまとめて積んでから 1 回の通知（VM Exit）で一括処理します。これにより VM Exit 回数を数十分の 1 へ減らし、高いスループットを実現します。

3. **ハードウェアパススルー（SR-IOV ＋ IOMMU — [5-1節](../5/5-1.md)の回収）：**
    100 Gbps NIC や機械学習用 GPU のように高い性能が求められる場合、ハイパーバイザを完全にバイパスして物理デバイスをゲスト VM へ直接割り当てます。1 枚の物理 NIC をハードウェア側で複数の仮想 NIC（VF：Virtual Function）へ分割する **SR-IOV（Single Root I/O Virtualization）** を用いると、複数 VM へ物理 NIC を直接分配できます。ここで注意すべきは、**DMA コントローラは CPU のページテーブル（EPT）を通らず物理メモリ（HPA）へ直接アクセスする** 点です。そのため、[5-1節](../5/5-1.md)で学んだ **IOMMU**（デバイスからの DMA アドレスを GPA → HPA へ変換・隔離し、他 VM のメモリへの不正 DMA 攻撃を物理遮断する MMU）を組み合わせることで、ベアメタルと同等の性能と隔離を両立します。

> **【コラム：無停止で物理サーバを引っ越す「ライブマイグレーション（Live Migration）」】**
>
> 仮想化がクラウド運用にもたらした象徴的な機能が、**稼働中の VM を止めずに別の物理ホストへ丸ごと移動させるライブマイグレーション** です。共有ストレージ上にディスクがあるとき、移動させるべき実体は「VM の全 RAM ページ（例：$16\text{ GiB}$）」と「vCPU のレジスタ状態（数 $\text{KiB}$）」です。
>
> もし VM を止めてから $16\text{ GiB}$ をネットワーク転送すると十数秒もサービスが止まってしまいます。そこで標準の **Pre-copy（事前コピー）方式** では、**VM を動かしたまま** まず全 RAM ページを新ホストへコピーします。そのコピー中にゲスト OS が書き換えたページ（ダーティページ：EPT の Dirty ビット［書込済み変更フラグ］で検知）だけを第 2 ラウンド、第 3 ラウンドと繰り返し差分転送し、残りダーティページが数 $\text{MiB}$ まで縮まった最後の瞬間だけ **数十ミリ秒だけ VM を一時停止（ダウンタイム）** して残りの差分と vCPU レジスタを送り、新ホストで再開させます。TCP 接続すら切れずに物理マシンのメンテナンスが完了します。

### 4. 限界と補正（Critique & Adaptation）

#### (1) 2 次元ページウォークと TLB フラッシュのコストに対するハードウェア補正

実験Bで見た通り、EPT（2 段ページテーブル）では TLB ミス 1 回あたりのメモリアクセスが最大 **24 回** に膨らみます。さらに初期の VT-x では、VM Exit と VM Entry が起きるたびに CPU の TLB 全体がフラッシュ（全消去）されていたため、ゲストへ戻った直後に大量の 24 回ウォークが発生していました。

* **補正①：VPID（Virtual Processor ID）による TLB タグ付け：** [3-5節](../3/3-5.md)のプロセス用 ASID / PCID と同じく、TLB の各エントリへ「どの VM の変換結果か」を示す識別子（VPID）を付与することで、VM Exit / Entry のたびに TLB を全消去せずに済むようにしました。
* **補正②：Huge Pages（$2\text{ MiB} / 1\text{ GiB}$ ページ）の活用：** ゲストとホストの双方で $4\text{ KiB}$ ではなく $2\text{ MiB}$ や $1\text{ GiB}$ の巨大ページを使うと、$2\text{ MiB} / 4\text{ KiB} = 512 = 2^9$ に相当する 9 ビット分（1 段分）のテーブル参照を省略でき、ページテーブルの段数自体が 4 段 → 3 段（$1\text{ GiB}$ では 2 段）へ減ります。さらに TLB がカバーできるメモリ範囲（TLB Reach）も 512 倍以上に広がるため、2 次元ページウォークの頻度を大幅に抑えられます。

#### (2) サイドチャネル攻撃とマルチテナント隔離の限界

ハイパーバイザと EPT・IOMMU は、異なる顧客の VM 同士をソフトウェア的・論理的に完全に隔離します。しかし、同じ物理 CPU ソケット上で 2 つの顧客 VM が共有 L3 キャッシュや分岐予測器・SMT（ハイパースレッディング）を物理的に共有していると、[3-5節](../3/3-5.md)コラムで触れた **Meltdown / Spectre** などの投機実行サイドチャネル攻撃によって、別 VM の秘密鍵がキャッシュのタイミング差から盗み見られるリスクが生じます。

* **補正：** クラウド事業者は次の多層的なハードウェア対策を導入しています。

    * CPU マイクロコード更新やコア単位の SMT 隔離により、共有物理資源を通じた情報漏えいを抑えます。
    * ハイパーバイザの I/O・ネットワーク処理を専用ハードウェアカードへオフロードする設計（**AWS Nitro System** のような専用 SoC 化）でホスト CPU の負担と攻撃対象面を縮小します。
    * メモリ内容自体を CPU ハードウェアで VM ごとに暗号化してクラウド管理者からも読めなくする **コンフィデンシャルコンピューティング（AMD SEV / Intel TDX）** も普及しています。

#### (3) VM の「起動の遅さと重さ」の壁（次節コンテナへの動機）

ハードウェア仮想化は強固な隔離を提供しますが、1 つのアプリを動かすためだけに **専用のゲスト OS カーネル、ブート処理、システムサービス一式を丸ごと起動する** 構造上、どうしても次の重さが残ります。

* 起動に数秒〜数十秒かかり、急なアクセス増への瞬時のスケールアウトが難しいです。
* 同じ物理ホスト上で 50 個のマイクロサービスを動かすと、50 個分のゲスト OS カーネルとページキャッシュが RAM を重複消費します。

この課題に対し、「**1 つの Linux カーネルを共有したまま、OS の隔離機能だけでミリ秒単位に軽量な隔離環境を立ち上げる**」アプローチが、次節（[10-2節](10-2.md)）で学ぶ **コンテナ（Namespace・cgroup・OverlayFS）** です。なお、強固な VM 隔離を保ったまま不要なデバイスエミュレーションを削ぎ落として約 125 ミリ秒で起動する **MicroVM（AWS Firecracker）** のように、VM とコンテナの中間領域もサーバレス基盤で広く使われています。

> **【確認の問い】**
>
> 1. **（2 段ページテーブルのメモリアクセス回数導出と方式比較）**
>
>     * (a) 2 次元ページウォークの構造（`cr3`〜L1 の各テーブル GPA と最終データページの GPA をそれぞれ EPT で変換する構造）を用い、ゲストが 4 段（$4\text{ KiB}$）のままホスト側 EPT を **$2\text{ MiB}$ Huge Page（3 段）** にした場合の最悪変換メモリアクセス回数を導出してください。さらに、双方 4 段（24 回）および双方 3 段（15 回）と比較し、どの項が減ったことで総回数が縮まったかを述べてください。
>     * (b) ゲスト OS が自分のページテーブルを書き換えるとき、従来のソフトウェア方式（シャドウページテーブル）では毎回 VM Exit が発生したのに対し、ハードウェア方式（EPT / NPT）で VM Exit が不要になった理由を説明してください。あわせて、`fork` やコンテクストスイッチが多発するワークロードと、大容量メモリへのランダムアクセスが多いワークロードのそれぞれで両方式の得失がどう表れるか考えてみてください。
>
> 2. **（I/O 仮想化の 3 方式選定と IOMMU の役割）**
>
>     * (a) ① 1990 年代の古いレガシー OS を未改変のまま動かしたい、② 一般的なクラウド VM で高速なディスク／ネットワーク性能とライブマイグレーションを両立したい、③ 機械学習の学習ノードで物理 GPU や 100 Gbps NIC の性能を最大限に引き出したい、の 3 つの要件に対して、本節の I/O 仮想化 3 方式（完全エミュレーション・VirtIO 準仮想化・SR-IOV パススルー）をそれぞれ割り当て、選定理由を簡潔に述べてください。さらに、SR-IOV パススルーを選ぶとライブマイグレーションが難しくなる理由も説明してください。
>     * (b) パススルー方式で物理デバイスをゲスト VM へ直接割り当てるとき、**IOMMU** を有効化しないとどのような深刻なセキュリティ事故が起き得るでしょうか。
>
> 3. **（次節への伏線：VM の重さを避けて「1 つの Linux カーネル上」でアプリを隔離するには）**
>     1 台の Linux ホスト上で 50 個のマイクロサービスを通常のプロセスとして直接相乗りさせた場合、① ネットワークポート・ファイルパス・プロセス一覧の衝突、② 1 サービスがメモリを食いつぶす暴走、③ 50 個分の共通ライブラリのディスク重複、の 3 点で具体的に何が破綻し、OS カーネルにどのような隔離・制限・共有の仕組みが求められるか説明してください。
