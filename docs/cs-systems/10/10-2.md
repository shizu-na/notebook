### 前節（10-1）の確認問題の解答

前節の最後に提示した3つの問いの解答を確認します。問3がそのまま本節（コンテナの内部構造）の導入になります。

1. **2 段ページテーブルのメモリアクセス回数導出と方式比較：**

    * **(a) 2 次元ページウォークの構造からの導出と比較：**
        ゲストが 4 段（$4\text{ KiB}$）、ホスト側 EPT が 3 段（$2\text{ MiB}$ Huge Page）のとき、ゲストの L4〜L1 テーブルの 4 つの GPA と最終データページの 1 つの GPA（計 5 つの GPA）をそれぞれ 3 段の EPT で変換するため $5 \times 3 = 15$ 回かかり、そこに各段のゲスト PTE 読み出し 4 回を加えて

        $$
        (4 \times 3) + 4 + 3 = \mathbf{19\text{ 回}}
        $$

        となります。双方 4 段（$(4 \times 4) + 4 + 4 = 24$ 回）と比べると、ホスト側 EPT の 1 段削減によりテーブル変換（$16 \to 12$ 回）と最終データページ変換（$4 \to 3$ 回）の計 5 回が減りました。さらにゲスト側も $2\text{ MiB}$（3 段）にすると、ゲスト PTE 読み出し（$4 \to 3$ 回）と対応する EPT ウォーク 1 列分（$12 \to 9$ 回）が減り、$(3 \times 3) + 3 + 3 = \mathbf{15\text{ 回}}$ まで縮みます（あわせて TLB 1 エントリのカバー範囲も 512 倍に広がり、TLB ミス頻度自体も下がります）。

    * **(b) シャドウページテーブルと EPT / NPT の仕組みとワークロード別の得失：**
        シャドウページテーブル方式ではハイパーバイザが合成表（GVA → HPA）をソフトウェアで同期し続ける必要があり、ゲスト OS が自ページテーブルを書き換えるたびに VM Exit が発生しました。一方、EPT / NPT では CPU の MMU ハードウェア自体がゲスト表（GVA → GPA）とホスト EPT（GPA → HPA）の 2 段を直接辿るため、ゲスト OS のページテーブル操作で VM Exit が不要になります。そのため、`fork` やコンテクストスイッチ・ページフォルトが多発するワークロードでは EPT が大きく有利です。逆に、大容量メモリへのランダムアクセスで TLB ミスが頻発するワークロードでは EPT の 2 次元ウォーク（最大 24 回）が重くなるため、Huge Pages や VPID による補正が重要になります。

2. **I/O 仮想化の 3 方式選定と IOMMU の役割：**

    * **(a) 3 要件への方式割り当てと SR-IOV におけるライブマイグレーションの課題：**

        * **① 1990 年代の古いレガシー OS を未改変で動作 → 完全エミュレーション：** ゲスト OS へ新規ドライバを追加できないため、実在した古いハードウェアの MMIO レジスタをそのまま模倣する必要があります。
        * **② 一般的なクラウド VM で高速性能とライブマイグレーションを両立 → 準仮想化（VirtIO）：** 共有リングバッファで VM Exit を大幅に減らして高速化しつつ、物理ハードウェア固有の状態へ依存しないため別ホストへのライブマイグレーションも容易です。
        * **③ 機械学習の GPU や 100 Gbps NIC の性能を最大限に引き出す → パススルー（SR-IOV）：** ハイパーバイザの介入をバイパスして物理デバイス（または VF）を VM へ直結し、ベアメタル並みの帯域と低遅延を引き出します。
        * **SR-IOV でライブマイグレーションが難しくなる理由：** VM が物理 NIC（VF）や GPU といった物理ハードウェア固有の内部状態や DMA マッピングへ直接結び付いているため、ハイパーバイザ側でデバイス状態を丸ごとシリアライズして別ホストへ引き継ぐことが難しく、移行前にデバイス切り離しや仮想 NIC へのフェイルオーバーが必要になるためです。

    * **(b) パススルー時に IOMMU を有効化しない場合のセキュリティ事故：**
        DMA コントローラは CPU のページテーブル（EPT）を通らず物理アドレス（HPA）へ直接アクセスできます。IOMMU が無効だと、悪意あるゲスト OS がデバイスの DMA 先に他の顧客 VM やハイパーバイザ自身の物理メモリアドレスを指定して読み書きする **DMA 攻撃** が成立してしまいます。

3. **1 つの Linux ホスト上で 50 個のサービスを通常プロセスとして相乗りさせた場合の破綻（本節への接続）：**
    ① 同じ 80 番ポートの `bind()` 衝突や設定ファイルパスの競合、他サービスのプロセスが見えることによる干渉が起きるため、見え方を隔離する仕組み（**Linux Namespace**）が求められます。② 1 つのサービスがメモリリークを起こすとホスト全体の RAM を食い尽くして他サービスまで OOM や性能低下に巻き込むため、プロセス群ごとに資源上限を課す仕組み（**cgroup**）が求められます。③ 50 個分の共通ライブラリやベース環境を個別に複製するとディスク容量が肥大化するため、共通部分を読み取り専用で共有しつつ書き込み差分だけ分離する仕組み（**OverlayFS**）が求められます。本節では、これら 3 つのカーネル機構を組み合わせて作られる **コンテナ** の正体を解き明かします。

## 10-2. コンテナの内部構造（Namespace・cgroup・OverlayFS）

### 1. 動機（Why）：なぜ「コンテナは軽量な仮想マシン」ではなく「隔離されたただの Linux プロセス」なのか

前節（[10-1節](10-1.md)）で学んだハードウェア仮想化（VM）は、強固な隔離と異なる OS の同時稼働を実現しました。しかし、同じ Linux アプリケーションを 1 台のサーバ上で 50 個・100 個と高密度に動かしたり、開発者の PC と本番サーバでまったく同じ実行環境を再現したりしたい場面では、VM の「毎回ゲスト OS カーネルごと丸ごと起動する重さ」が足かせになります。

この課題を解決し、現代のソフトウェア開発・クラウド運用の標準となった技術が **コンテナ（Container：Docker / containerd / Podman 等）** です。

コンテナを理解するうえで最も重要な事実が 1 つあります。それは、**Linux カーネルの中に「コンテナ」という独立した単一の機能やオブジェクトは存在しない** ということです。コンテナの正体は、**ホストの Linux カーネル上で動いている「ただの通常のプロセス」に対し、次の 3 つのカーネル機構を組み合わせて「隔離の壁」と「資源の上限」を被せたもの** に過ぎません。

1. **Linux Namespace（名前空間）：** そのプロセスから「何が見えるか（PID、ファイルツリー、IP アドレス等）」を隔離します。
2. **cgroup（Control Groups）：** そのプロセスが「どれだけ資源を使えるか（CPU、メモリ、プロセス数、I/O）」を制限します。
3. **Union File System（OverlayFS）：** 複数のコンテナで共通のベース OS イメージを読み取り専用で共有しつつ、書き込み差分だけを CoW（Copy-on-Write）で分離します。

本節では、VM とコンテナの決定的な構造差を押さえたうえで、これら 3 本柱の内部動作と、カーネル共有ゆえのセキュリティ限界・補正策を整理します。

---

### 2. 具体例と動作イメージ（Toy Model）

抽象的な仕様に入る前に、2 つの小さな実験で「コンテナがただの Linux プロセスであること」と「イメージ共有によるディスク節約」を確かめます。

#### 実験A：Docker なしで、Linux 標準コマンド 1 行から「ミニコンテナ」を作る

Linux マシン上で、Docker を一切使わずに標準の `unshare` コマンドを 1 行実行してみます。

```sh
sudo unshare --pid --fork --mount-proc --uts /bin/sh
```

ここで `--pid` と `--uts` は新しい PID・ホスト名空間を作成し、`--fork` はその新しい PID 空間内の先頭子プロセス（PID 1）として `/bin/sh` を起動します。また `--mount-proc` は新しい PID 空間に対応した `/proc` をマウントし直すことで、`ps` コマンドの表示を新空間へ一致させています。

この新しく開いたシェルの中で `hostname mini-box` や `ps aux` を実行すると、次のような結果が返ってきます。

* シェルの中から見ると、自分自身のプロセス ID は **`PID = 1`**（init プロセス）であり、ホスト側で動いている何百個もの他プロセスは **1 つも見えません**。ホスト名も `mini-box` に変わっています。
* しかし、**別の端末（ホスト側）から `ps aux` を実行すると**、その `/bin/sh` はホスト上のただの 1 プロセス（例：`PID = 18432`）として丸見えです。

これが **Namespace による「見え方の隔離」** です。ゲスト OS もハイパーバイザも一切起動していないため、起動時間は **数ミリ秒** で完了します。

#### 実験B：同じ $200\text{ MiB}$ イメージから 50 個のコンテナを起動したときのディスク消費量

Ubuntu のコンテナイメージ（サイズ $200\text{ MiB}$）から、50 個の Web アプリコンテナを同時に起動したとします。

* **VM 方式（フルクローン）：** 仮想ディスクを 50 個複製すると $200\text{ MiB} \times 50 = 10{,}000\text{ MiB}$（約 $9.8\text{ GiB}$）を消費します。
* **コンテナ方式（OverlayFS）：** 50 個のコンテナはすべて、ディスク上にある **たった 1 つの読み取り専用ベースイメージ（$200\text{ MiB}$）** を共有して参照します。各コンテナに用意されるのは、起動後にアプリが書き込んだ差分ファイル（例：ログ $2\text{ MiB}$）だけを収める薄い書き込み層だけです。したがって 50 個合計のディスク消費量は

    $$200\text{ MiB} + 50 \times 2\text{ MiB} = \mathbf{300\text{ MiB}}$$

    （フルクローン比で約 3%）に収まります。さらに RAM 上でも、共有ライブラリ（`libc.so` 等）の読み取り専用ページがホストの統合ページキャッシュ（[5-5節](../5/5-5.md)）で自然に共有されます。

#### (2) Linux Namespace（見え方の隔離）

**Namespace** は、本来システム全体で 1 つしかないグローバルなカーネル資源を、プロセスグループごとに独立した仮想的な名前空間へ複製して見せる仕組みです。新しいプロセス生成時の `clone()` フラグ、既存プロセスの分離 `unshare()`、あるいは別コンテナの名前空間へ入る `setns()`（`docker exec` の正体）で操作します。

現代の Linux カーネルには以下の主要な Namespace があります。

| Namespace | 隔離する対象 | コンテナ内での具体的な効果 |
| :--- | :--- | :--- |
| **`pid`** | プロセス ID 空間 | コンテナの先頭プロセスが **`PID 1`** となり、ホストや他コンテナのプロセスが見えなくなる。 |
| **`mnt`** | ファイルシステムのマウント点 | コンテナ独自のルートディレクトリ `/`（ルート切替の `pivot_root` で設定）を持ち、ホストの `/etc` 等が見えない。 |
| **`net`** | ネットワークスタック全体 | 独立した仮想 NIC・IP アドレス・ポート番号（各コンテナが同じ `80` 番ポートを衝突せず開ける）・ルーティング表・`iptables`（パケットフィルタ・NAT ルール）を持つ。 |
| **`uts`** | ホスト名・ドメイン名 | コンテナごとに独自の `hostname` を持てる。 |
| **`ipc`** | System V IPC・POSIX メッセージキュー | 共有メモリやセマフォをコンテナ内へ閉じる。 |
| **`user`** | UID / GID の対応付け | コンテナ内では `UID 0`（`root`）として振る舞わせつつ、**ホスト側では一般ユーザ（例：`UID 100000`）へマッピング**する（Rootless コンテナの核）。 |
| **`cgroup`** | cgroup ツリーの見え方 | コンテナ内からホスト側の他コンテナの cgroup 階層を隠す。 |

ここで、`net` Namespace で隔離されたコンテナがどうやって外部インターネットと通信するのか（[第6部](../index.md#part-6)の回収）を確認しておきます。コンテナランタイムは、両端が仮想的な LAN ケーブルで直結された 1 組の仮想インタフェース **`veth` ペア（Virtual Ethernet Pair）** を作成します。片端（`eth0`）をコンテナの `net` Namespace 内へ差し込み、もう片端をホスト側の仮想 L2 スイッチ（**Linux Bridge：`docker0`**）へ接続します。各コンテナは `docker0` をデフォルトゲートウェイとしてパケットを送り出し、ホスト側の **NAPT（[6-6節](../6/6-6.md)）** を介して外部ネットワークへ中継します。

#### (3) cgroup（Control Groups v2：計算資源の制限と会計）

Namespace だけでは「隣人は見えなくなったが、1 つの暴走コンテナがホストの全 CPU と全 RAM を食い尽くして他のコンテナを動作不能に陥らせる（Noisy Neighbor 問題）」を防げません。これを制御するのが **cgroup（Control Groups）** です（図10-2-2）。

現在の標準である **cgroup v2** は、プロセス群を単一の階層ディレクトリツリー（`/sys/fs/cgroup/...` の仮想ファイルシステム）として管理し、配下の設定ファイルへ数値を書き込むだけでカーネルのスケジューラやメモリマネージャへ上限を課します。

* **CPU 制限（`cpu.max` / `cpu.weight`）：** [3-3節](../3/3-3.md)の Linux スケジューラと連動し、たとえば `cpu.max = "50000 100000"` と設定すると「100 ms 周期のうち最大 50 ms（＝ 0.5 コア相当）までしか CPU を与えない」ハード上限（スロットリング）を課します。
* **メモリ制限（`memory.max`）：** [3-7節](../3/3-7.md)で触れた通り、コンテナ内の匿名メモリ（ヒープ・スタックなどファイルに紐付かない領域）＋ページキャッシュの合計が `memory.max`（例：`512M`）を超えると、カーネルはホスト全体ではなく**その cgroup の内部だけを対象に OOM Killer を発動**し、暴走コンテナだけを停止させてホストと他コンテナを守ります。
* **プロセス数制限（`pids.max`）：** [3-2節](../3/3-2.md)で触れた **フォークボム（`while(1) fork();`）** によってホスト全体の PID テーブルが枯渇するのを防ぐため、コンテナ内の最大プロセス・スレッド数を制限します。
* **I/O 制限（`io.max`）：** ディスクごとの最大読み書き帯域（MB/s）や IOPS を制限します。

#### (4) OverlayFS（Union File System）とコンテナイメージの階層構造

コンテナイメージ（Dockerfile の各命令 `FROM`, `RUN`, `COPY` から作られる **OCI［Open Container Initiative］** 標準形式のイメージ）は、複数の **不変（読み取り専用）レイヤ** を重ね合わせた構造をしています。これを 1 つの統合されたディレクトリツリーとしてコンテナへ見せる Linux カーネルのファイルシステムが **OverlayFS** です（図10-2-3）。

OverlayFS は次の 4 つのディレクトリを組み合わせてマウントします。

1. **`lowerdir`（読み取り専用レイヤ群）：** ベース OS（Ubuntu 等）やランタイム、アプリバイナリの不変レイヤ群です。複数のコンテナで完全に共有されます（実験Bの $200\text{ MiB}$ のベースイメージに対応します）。
2. **`upperdir`（書き込み可能レイヤ）：** コンテナ起動時に 1 個だけ作られる空のディレクトリです。コンテナ内での新規作成・変更・削除はすべてここへ記録されます（実験Bの各コンテナが書き込む $2\text{ MiB}$ の差分に対応します）。
3. **`workdir`（内部作業用ディレクトリ）：** `upperdir` と同じファイルシステム上に配置する空の作業領域です。Copy-up や名前変更を原子的に（途中で壊れた状態を見せずに）行うため、カーネルが内部的に一時ファイルを作成・移動する用途で使います（内部作業用のため図10-2-3では省略しています）。
4. **`merged`（統合ビュー）：** コンテナのルート `/` として見える仮想ビューです。同名のファイルがあれば常に上の層（`upperdir`）が優先して見えます。

**OverlayFS の 3 つの基本動作：**

* **読取り（Read）：** `upperdir` にファイルがあればそれを読み、なければ `lowerdir` をそのまま直接読みます（コピー不要）。
* **既存ファイルの書換え（Copy-up：CoW）：** `lowerdir` にある既存ファイル（例：`/etc/app.conf`）をコンテナが書き換えようとすると、OverlayFS はその瞬間に `lowerdir` から `upperdir` へファイルを丸ごとコピー（**Copy-up**）し、以降の書き込みは `upperdir` 側のコピーへ適用します。`lowerdir` の原本は 1 ビットも傷つきません（[3-7](../3/3-7.md)・[5-6節](../5/5-6.md)の Copy-on-Write と同型です）。
* **既存ファイルの削除（Whiteout）：** `lowerdir` にあるファイル（例：`/tmp/old.txt`）をコンテナが `rm` しても、読み取り専用の `lowerdir` から直接消すことはできません。そこで OverlayFS は `upperdir` の同じパスへ、削除済みを示す特殊な空マーカーファイル（デバイス番号 `0/0` のキャラクタデバイス）である **Whiteout（白塗り）** を作成し、`merged` ビューから見えなくします。

> **【コラム：なぜ macOS や Windows で Docker を動かすと、裏側で軽量な Linux VM が起動するのか】**
>
> 「コンテナは VM 不要で動くはずなのに、なぜ自分の MacBook（macOS）や Windows PC で Docker Desktop を起動するとメモリを数 GiB 消費する仮想マシンが裏で動いているのか？」という疑問が生じることがあります。
>
> 答えは本節の冒頭で述べた通り、**Linux コンテナは Linux カーネルのシステムコール（Namespace・cgroup・OverlayFS・`epoll` 等）に直接依存しているから** です。macOS の XNU カーネルや Windows カーネルは Linux のシステムコール ABI をそのまま実行できません。そのため macOS / Windows 上の Docker Desktop は、まず前節（[10-1節](10-1.md)）のハードウェア仮想化（Apple Virtualization.framework や Windows WSL2 / Hyper-V）で **1 台の軽量な Linux VM を裏側に立ち上げ、その Linux カーネルの上で多数の Linux コンテナを動かしている** のです。

### 4. 限界と補正（Critique & Adaptation）

#### (1) カーネル共有によるセキュリティ境界の弱さ（コンテナ脱出）と多層防御

コンテナの最大の利点（1 つの Linux カーネルの共有）は、セキュリティ面ではそのまま最大の弱点になります。VM ならゲスト OS カーネルが侵害されてもハイパーバイザ（VT-x / EPT）の壁で止まりますが、コンテナでは **ホストと共有している Linux カーネルのシステムコール（数百種類）に 1 箇所でも権限昇格脆弱性があると、コンテナの壁を突き破ってホスト全体と全同居コンテナを乗っ取る「コンテナ脱出（Container Escape）」** が成立し得ます。

* **補正①（最小権限の徹底 — [5-7節](../5/5-7.md)の回収）：**

    1. コンテナ内プロセスを非 `root` ユーザ（`USER appuser`）で動かし、`CAP_SYS_ADMIN`（マウント等の広範な管理権限）や `CAP_NET_RAW`（生ソケット操作権限）など不要な **Linux ケイパビリティ** をすべて剥奪します。
    2. **`seccomp-bpf`** プロファイルで、コンテナに不要な危険システムコール（`mount`, `kexec_load`, `ptrace` 等）をカーネル入口で遮断します。
    3. **User Namespace（Rootless コンテナ）** を有効化し、コンテナ内の `root` をホスト側の非特権 UID へ写像します。

* **補正②（マルチテナント環境でのサンドボックス・MicroVM 併用）：**
    不特定多数の第三者が書いた信頼できないコード（サーバレス関数やクラウドビルド環境など）を同一物理ホストで実行する場合は、通常のコンテナだけでは隔離が不足するため、システムコールをユーザ空間の独自カーネルで受け止める **gVisor** や、コンテナの使い勝手のまま 1 コンテナごとに軽量な VM を被せる **Kata Containers / AWS Firecracker（MicroVM）** を使います。

#### (2) OverlayFS の Copy-up 負荷とステートフルデータ（Volume マウント）

OverlayFS でデータベースファイル（例：$1\text{ GiB}$ のデータファイル）を `lowerdir` に置いて 1 バイトだけ更新すると、**Copy-up によってファイル全体（$1\text{ GiB}$）が丸ごと `upperdir` へコピーされる** という大きな書き込み遅延が発生します。さらに、コンテナを削除すると `upperdir` ごとデータが消滅します。

* **補正：** PostgreSQL や MySQL などのステートフルな永続データはコンテナの OverlayFS レイヤへ置かず、ランタイム管理の永続領域である **Volume** や、ホスト側の任意ディレクトリを直接割り当てる **Bind Mount** を使用して OverlayFS をバイパスします。

#### (3) 単一ホストの限界から「Web インフラと分散配置」へ（次節への動機）

コンテナと Kubernetes などのオーケストレータを使えば、同じ Web アプリのコンテナを複数台のホストへ 10 個・100 個と短時間で並べることができます。しかし、利用者のブラウザがアクセスする入り口は **`https://example.com` という 1 つの URL** です。

背後に何十個ものコンテナやサーバが動いているとき、外部からの膨大なトラヒックをどうやって健全なコンテナへ振り分け、TLS 暗号の復号や静的ファイルのキャッシュ配信を効率よく捌くのでしょうか。次節（[10-3節](10-3.md)）では、現代の Web サービスを前面で支える **Web インフラ構成要素（ロードバランサ・リバースプロキシ・CDN）** の仕組みを解き明かします。

### 理解度チェック（次節へ進む前の確認）

本節の Namespace・cgroup・OverlayFS・セキュリティ境界の性質を確認し、次節（[10-3節](10-3.md)）へ繋ぐ問いを置きます。

> **【確認の問い】**
>
> 1. **（コンテナの 3 本柱による障害診断）**
>     1 台の Linux ホスト上で複数のコンテナを運用しているとき、次の (a)〜(c) の現象が発生しました。それぞれ Linux カーネルのどの仕組み（**Namespace**［具体的な種別名も］・**cgroup**［具体的なパラメータも］）が作用しているか、あるいは設定漏れが原因かを答えてください。
>
>     * (a) 同じ物理ホスト上で 2 つの Web サーバコンテナ A・B が、どちらも自分のポート `80` 番で `bind()` して同時起動できた。
>     * (b) コンテナ A のアプリがメモリリークを起こして $512\text{ MiB}$ を超えた瞬間に、ホスト全体やコンテナ B に影響せずコンテナ A 内のプロセスだけが `SIGKILL`（OOM）で終了した。
>     * (c) コンテナ B 内で無限に `fork()` を繰り返すバグが発火したところ、コンテナ B だけでなくホスト上の他のコンテナでも新規プロセスを起動できなくなった。

> 2. **（OverlayFS の動作とデータベース格納の注意点、および VM との隔離差）**
>
>     * (a) OverlayFS において、`lowerdir`（読み取り専用）に置かれた $500\text{ MiB}$ のデータベースファイルをコンテナが 1 バイトだけ書き換えたとき、および `rm` で削除したときに、`upperdir` でそれぞれ何が起きるか（**Copy-up** と **Whiteout** の用語を用いて）説明し、DB の永続データをコンテナレイヤへ置いてはいけない理由を述べてください。さらに、`rm` でそのファイルを削除してもホスト側ディスク使用量が $500\text{ MiB}$ 減らない理由を Whiteout の仕組みから説明してください。
>     * (b) 不特定多数の顧客が任意のコードを提出して実行するオンラインコード実行サービス（またはサーバレス基盤）において、通常の Docker コンテナ単体ではなく **MicroVM（Firecracker 等）** や **gVisor** が好まれる理由を、「カーネル共有と攻撃対象面」の観点から説明してください。
>
> 3. **（次節への伏線：複数ホスト上のコンテナ群へ外部アクセスを振り分ける課題）**
>     コンテナ 20 個を 3 台のホストに並べた Web サービスへ、世界中のクライアントが各コンテナの IP へ直接アクセスする構成を採った場合、① コンテナ障害・増減時の追従、② HTTPS の証明書管理・URL パス単位の振分、③ 欧州ユーザからの $150\text{ ms}$ 以上の地理的遅延とオリジン負荷、の 3 点で何が破綻するか説明してください。
