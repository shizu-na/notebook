### 前節（10-2）の確認問題の解答

前節の最後に提示した3つの問いの解答を確認します。問3がそのまま本節（Web インフラ構成要素）の導入になります。

1. **コンテナの 3 本柱による障害診断：**

    * **(a) 同一ホスト上で 2 コンテナが両方ポート `80` 番で `bind()` できた理由：**
        **`net` Namespace（ネットワーク名前空間）** によって各コンテナが独立したネットワークスタック（独自の IP アドレスとポート空間）を持っているため、同じ物理ホスト上でもポート `80` 番が衝突しません。

    * **(b) メモリリークしたコンテナ A だけが `SIGKILL`（OOM）で終了した理由：**
        **cgroup v2 の `memory.max`（$= 512\text{ MiB}$）** によってコンテナ A 専用のメモリ上限が設定されており、超過時にホスト全体ではなくその cgroup 内だけを対象に OOM Killer が発動したためです。

    * **(c) コンテナ B のフォークボムでホスト全体の新規プロセス起動が止まった原因：**
        **cgroup v2 の `pids.max`** がコンテナ B へ設定されていなかった（設定漏れ）ため、コンテナ B 内の無限 `fork()` がホストカーネル全体の PID テーブルを枯渇させてしまったことが原因です。

2. **OverlayFS の動作とデータベース格納の注意点、および VM との隔離差：**

    * **(a) `500 MiB` ファイルの 1 バイト更新・削除時の動作と DB 格納を避ける理由：**

        * **1 バイト更新時（Copy-up）：** OverlayFS は読み取り専用の `lowerdir` を直接書き換えられないため、$500\text{ MiB}$ のファイル全体を `upperdir` へ丸ごとコピー（Copy-up）してから 1 バイトを更新します。
        * **`rm` 削除時（Whiteout）とディスク容量が減らない理由：** `lowerdir` からは消去せず、`upperdir` の同パスへ削除済みを示す特殊な空マーカー（Whiteout）を配置して `merged` ビューから非表示にします。読み取り専用の `lowerdir` 上にある $500\text{ MiB}$ の原本ファイル自体はそのまま残存するため、`rm` してもホスト側のディスク使用量は $500\text{ MiB}$ 減りません。
        * **DB をコンテナレイヤへ置いてはいけない理由：** わずかな更新でも巨大な Copy-up 遅延と書き込み増幅が起きるうえ、コンテナを削除すると `upperdir` ごと永続データが消失するためです（永続データは必ず Volume / Bind Mount で OverlayFS をバイパスします）。

    * **(b) マルチテナントのコード実行基盤で MicroVM や gVisor が好まれる理由：**
        通常のコンテナはホストの Linux カーネル（数百種類のシステムコール）を全コンテナで共有するため、カーネルに 1 箇所でも権限昇格バグがあるとホストや他顧客へ侵入される「コンテナ脱出」のリスクがあります。MicroVM（Firecracker 等）はハードウェア仮想化（VT-x / EPT）の壁を追加し、gVisor はユーザ空間の独立カーネルでシステムコールを受け止めることで、共有カーネルへの攻撃対象面を大幅に縮小できます。

3. **複数ホスト上のコンテナ群へクライアントが直接 IP アクセスした場合の破綻（本節への接続）：**
    ① コンテナが障害で停止したり増減して IP が変わるたびにクライアント側が追従できず接続失敗が起きるため、単一入口で健全ノードへ振り分ける **ロードバランサ（L4 / L7）** が必要になります。② 全 20 コンテナへ TLS 証明書と秘密鍵を配って更新・復号する負担が大きく、URL パス単位で別サービスへ振り分けることもできないため、前段で TLS 終端と経路振分を行う **リバースプロキシ** が必要になります。③ 欧州など遠隔地のユーザが毎回 $150\text{ ms}$ 以上の RTT をかけて東京のオリジンへ接続し、画像や動画のトラヒックもオリジンへ集中して飽和するため、世界各拠点へキャッシュを配置する **CDN（Content Delivery Network）** が必要になります。本節では、これら現代 Web インフラの中核要素の内部構造を解き明かします。

## 10-3. Web インフラ構成要素（ロードバランサ・リバースプロキシ・CDN）

### 1. 動機（Why）：なぜ Web アプリサーバをそのままインターネットへ直接公開しないのか

[10-1節](10-1.md)（VM）と [10-2節](10-2.md)（コンテナ）によって、アプリケーションを複数台のサーバへ水平スケール（スケールアウト）して並べる基盤が整いました。しかし、実運用の Web サービスでアプリケーションサーバ（Node.js、Go、Python、Java 等）をそのままインターネットへ直接公開することはほとんどありません。

大規模なトラヒックと故障・攻撃に耐えるためには、クライアントとバックエンドアプリ群のあいだに専門の中継インフラ層を挟み、次の **3 つの責務** をアプリから切り離す必要があります。

1. **単一入口からの負荷分散と障害切り離し（ロードバランサ）：**
    ユーザが接続する 1 つの IP アドレス／ドメインの背後へ数十〜数千台のバックエンドを隠蔽し、リクエストを均等に振り分けつつ、故障したサーバを数秒で自動除外します。

2. **TLS 終端と接続の吸収（リバースプロキシ）：**
    世界中の不安定なモバイル回線からの遅い TCP/TLS 接続や Keep-Alive を前段の専用プロキシ（Nginx / Envoy 等）で受け止め、暗号復号（TLS 終端）や HTTP/3 → HTTP/1.1 変換・圧縮を一括処理して、後段のアプリサーバを業務ロジックへ専念させます。

3. **地理的距離（光速の壁）の突破とオリジン保護（CDN）：**
    [6-1節](../6/6-1.md)で確認した通り、東京のサーバからロンドンのユーザへデータを送るだけで往復 $150\text{ ms}$ 以上の伝搬遅延がかかります。画像・動画・静的ファイルを世界中のユーザのすぐ近く（エッジ拠点）へキャッシュ配置することで、遅延を数ミリ秒へ縮めつつ、突発的なアクセス集中から本社（オリジン）サーバを守ります。

本節では、現代の Web サービスを前面で支える **L4 / L7 ロードバランサ**、**リバースプロキシ**、そして **CDN と多段キャッシュ** の動作原理と設計上の落とし穴を整理します。

---

### 2. 具体例と動作イメージ（Toy Model）

アーキテクチャの分類に入る前に、2 つの具体的なシナリオで「ロードバランサによる無停止運用」と「CDN による遅延と帯域の大幅な削減」を確かめます。

#### 実験A：バックエンド 10 台のうち 1 台がクラッシュした瞬間の自動切替

1 台のロードバランサ（**仮想 IP［VIP：Virtual IP］**：`203.0.113.10`）の背後に、同じ Web アプリコンテナが 10 台並んでいるとします。

* ロードバランサは 5 秒ごとに全 10 台の `/health` エンドポイントへ軽量な生存確認（**ヘルスチェック**）を送っています。
* ある瞬間、3 号機が OOM でクラッシュして応答が返らなくなりました。
* 2 回連続でタイムアウトを検知したロードバランサは、即座に 3 号機を振り分け対象リストから除外し、すべての新規リクエストを残りの健全な 9 台へ振り分けます。
* その裏側でオーケストレータ（Kubernetes 等）が新しい 3 号機コンテナを数秒で起動し直し、`/health` が `200 OK` を返し始めると、ロードバランサが自動的に 3 号機を振り分け対象へ復帰させます。ユーザは障害に一切気づきません。

#### 実験B：東京のオリジンサーバから世界中の 10 万人へ $1\text{ MB}$ の画像を配信する

東京のデータセンターに置かれたオリジンサーバへ、日本・欧州・北米の 10 万人のユーザが一斉にアクセスして $1\text{ MB}$ のトップページ画像を読み込むとします。

* **CDN なし（オリジン直接配信）：**

    * ロンドンやニューヨークのユーザは、TCP + TLS + HTTP の往復だけで **$300\text{〜}500\text{ ms}$** 以上待たされます（東京〜欧州・北米間の RTT 約 $150\text{ ms}$ に対し、TCP 1 RTT ＋ TLS 1.3 1 RTT ＋ HTTP 1 RTT $\approx 3\text{ RTT} \approx 450\text{ ms}$）。
    * 東京のオリジンサーバには合計 $100{,}000 \times 1\text{ MB} = \mathbf{100\text{ GB}}$ の送信トラヒックが集中し、回線帯域が飽和してダウンします。

* **CDN あり（世界 200 拠点のエッジキャッシュ）：**

    * ロンドンの最初の 1 人目がアクセスしたときだけ、ロンドン最寄りの CDN エッジ拠点が東京のオリジンから画像を 1 回（$1\text{ MB}$）取得してキャッシュします（**キャッシュミス**）。
    * ロンドン周辺からの 2 人目〜3 万人目のアクセスは、すべてロンドン拠点のキャッシュから数ミリ秒で返却されます（**キャッシュヒット**）。
    * 東京のオリジンサーバへ届くリクエストは世界中の拠点分（$200\text{ 拠点} \times 1\text{ MB} = 200\text{ MB}$）へ抑えられ、元の $100{,}000\text{ MB}$ から **99.8% 削減** されます。世界中のユーザも数ミリ秒で画面を表示できます。

### 3. 構造・アルゴリズム・実装（What）

#### (1) L4 ロードバランサ（NAT 型 vs DSR［Direct Server Return］）

**L4 ロードバランサ** は、TCP/IP モデルの **第 4 層（トランスポート層：送信元 IP・宛先 IP・送信元ポート・宛先ポート・プロトコル番号の 5 つ組）** だけを見てパケットをバックエンドサーバへ振り分けます。HTTP の中身や TLS の暗号化ペイロードを復号・解釈しないため、非常に高速（数百万〜数千万パケット/秒）に動作します。

L4 ロードバランサのパケット転送方式には、次の 2 つの代表構成があります（図10-3-1左）。

1. **NAT（DNAT / Full-NAT）方式：**
    ロードバランサが受信パケットの宛先 IP を仮想 IP（VIP）からバックエンドの実 IP へ書き換えて転送し（**DNAT**。さらに送信元 IP もロードバランサの IP へ書き換える方式を **Full-NAT** と呼びます）、**戻りパケット（レスポンス）も必ずロードバランサを経由**させて送信元 IP を VIP へ書き戻してからクライアントへ返します。仮にバックエンドがクライアントへ直接返送すると、送信元 IP がバックエンドの実 IP となり、VIP 宛てに張った TCP 接続と一致せずクライアント側で破棄されてしまうためです。設定が単純ですが、動画配信のように「リクエストは小さい（数百 B）が、レスポンスは巨大（数 MB）」な通信では、すべての巨大な戻りトラヒックがロードバランサの帯域を圧迫してボトルネックになります。

2. **DSR（Direct Server Return：ダイレクトサーバ返却）方式：**
    **往路（リクエスト）だけ** ロードバランサを通し、**復路（巨大なレスポンス）はバックエンドサーバからクライアントへ直接返す** 構成です（図10-3-1左。ヘッダ遷移は、往路 `DstIP=VIP, DstMAC=LB → DstMAC=B1`、復路 `SrcIP=VIP, DstIP=Client`）。

    * ロードバランサは IP ヘッダ（宛先 VIP）を書き換えず、**L2 の宛先 MAC アドレスだけ** を選んだバックエンドサーバのものへ書き換えて転送します（この L2 転送の前提として、原則ロードバランサとバックエンド群が **同一 L2 セグメント［VLAN］内** に配置されている必要があり、L3 ルータを越える環境では IP-in-IP カプセル化等を用います）。
    * 各バックエンドサーバはループバックインタフェース（`lo`）に VIP を設定しておき、VIP 宛てのパケットを自分宛てとして受理したうえで、応答パケットの送信元 IP に VIP をセットしてロードバランサを経由せず直接ルータ経由でクライアントへ返送します。このとき **各バックエンドの `lo` で VIP に対する ARP 応答を必ず無効化** しておきます（応答させてしまうと上流ルータがロードバランサを迂回して特定バックエンドへ直接送ってしまい、負荷分散が破綻するためです）。
    * これにより、ロードバランサの帯域負荷を大幅に減らし、巨大な下りトラヒックを捌くことができます。

#### (2) L7 ロードバランサとリバースプロキシ（TLS 終端・経路振分）

**L7 ロードバランサ**（および **リバースプロキシ**：Nginx, HAProxy, Envoy, AWS ALB 等）は、**第 7 層（アプリケーション層：HTTP/HTTPS）** まで終端してリクエストの中身を解釈する中継サーバです（図10-3-1右）。

* **2 本の独立した TCP 接続：** L4 が 1 本の TCP パケットをそのまま流すのに対し、L7 は **① クライアント ⇄ L7 プロキシ** と **② L7 プロキシ ⇄ バックエンド** の 2 本の独立した TCP 接続へ分割します。
* **L7 で実現できる高度な機能：**

    1. **TLS 終端（SSL/TLS Offloading）：** [7-7節](../7/7-7.md)で学んだ X.509 証明書の管理と重い暗号ハンドシェイクを L7 プロキシで一括処理し、安全な社内 LAN 内のバックエンドへは軽量な通信で中継します。
    2. **コンテンツベースルーティング：** URL パス（`/api/*` は API コンテナ群へ、`/static/*` は静的配信サーバへ）、`Host` ヘッダ、HTTP メソッド、Cookie に応じて柔軟に振り分け先を変えます。
    3. **プロトコル変換とコネクションプーリング：** クライアント側とは **HTTP/2 の多重化** や最新の **HTTP/3（QUIC）** で通信しつつ、バックエンド側とは再利用可能な長寿命 TCP 接続プール（Keep-Alive）を張ることで、[7-2節](../7/7-2.md)で見た `TIME_WAIT` 枯渇や毎回の 3-way ハンドシェイクを削減します。
    4. **送信元 IP の引き継ぎ（`X-Forwarded-For`）：** L7 が接続を終端すると、バックエンドから見た TCP の送信元 IP はすべて「L7 プロキシの IP」になってしまいます。そこで L7 は元のクライアント IP を HTTP ヘッダ **`X-Forwarded-For`**（または標準の `Forwarded` ヘッダ）へ追記して後段へ伝えます。

#### (3) 代表的な負荷分散アルゴリズム

ロードバランサが複数の健全なバックエンドから 1 台を選ぶ方式は、ワークロードの性質に応じて使い分けます。なお、いずれの方式でも前提となるのが実験Aで見た **ヘルスチェック** です。ロードバランサは `/health` への定期的な疎通確認（**アクティブヘルスチェック**）や、実リクエストの連続エラー・タイムアウト検知（**パッシブヘルスチェック**）によって異常ノードを自動で除外し、復旧確認後に振り分け対象へ戻します。

* **ラウンドロビン（Round Robin）＋ 重み付け（Weighted RR）：** サーバへ順番に均等配分します（スペックの異なるサーバが混ざる場合は重みを設定）。単純ですが、処理時間のばらつきが大きい（重いクエリと軽いクエリが混ざる）と特定のサーバだけ詰まります。
* **最小接続数（Least Connections）：** 現在処理中のアクティブ接続数が最も少ないサーバへ振り分けます。処理時間にばらつきがある場合に効果的です。さらに大規模環境では、ランダムに 2 台だけ選んで接続数が少ない方をとる **Power of Two Choices（2 択の力）** により、全サーバ走査なしで高い均等性を得ます。
* **ソース IP / キーハッシュ（Consistent Hashing：ノード増減時の再配置を最小限に抑えるハッシュ方式、11-3節で詳述）：** 送信元 IP や URL のハッシュ値で担当サーバを決めます。バックエンド側のインメモリキャッシュヒット率を高めたいときに有効です。

#### (4) CDN（Content Delivery Network）と多段キャッシュ階層

実験Bで見た **CDN（Cloudflare, Fastly, Amazon CloudFront, Akamai 等）** は、世界中の主要都市や ISP の内部に配置された **エッジ拠点（PoP：Point of Presence）** に大規模なリバースプロキシ・キャッシュ群を展開する分散配信網です（図10-3-2）。

1. **最寄りエッジへの誘導（[6-8](../6/6-8.md)・[7-5節](../7/7-5.md)の回収）：**

    * **BGP エニーキャスト方式：** 世界中の全エッジ拠点が同じ IP プレフィックスを広告し、インターネットの BGP 経路制御で最寄り拠点へ自動誘導します。
    * **GeoDNS 方式：** 権威 DNS サーバがクライアントのリゾルバ IP から地域を推定し、最寄りエッジ拠点の IP アドレスを `A`/`AAAA` レコードで返します。

2. **多段キャッシュとオリジンシールド（Origin Shield）：**
    世界 200 拠点のエッジそれぞれがキャッシュミスするたびに東京のオリジンサーバへ直接取りに行くと、200 回の重複取得が発生します。そこでエッジとオリジンの間にもう 1 層の中央キャッシュ拠点（**オリジンシールド / 階層キャッシュ**）を挟み、オリジンへの問い合わせを最大 1 回へ集約します。

3. **HTTP キャッシュ制御の 2 本柱（`Cache-Control` と条件付き `GET`）：**

    * **鮮度制御（`Cache-Control: public, max-age=3600`）：** 「1 時間（3600 秒）はオリジンへ確認せずキャッシュからそのまま返してよい」と宣言します。
    * **再検証（`ETag` ＋ `If-None-Match`）：** 期限が切れたあと、エッジはファイルの指紋（ハッシュ等）である **`ETag`** を `If-None-Match` ヘッダへ添えてオリジンへ問い合わせます。オリジン側でファイルが変わっていなければ、本体データを送らず空の **`304 Not Modified`** だけを返すため、帯域を節約してキャッシュ期限を延長できます。

> **【コラム：キャッシュ期限切れの瞬間にオリジンを過負荷に陥らせる「キャッシュスタンピード」と対策】**
>
> 毎秒 10,000 リクエストが集中する人気ページの CDN キャッシュ（`max-age=60`）が、ちょうど 60 秒経過して**期限切れになった瞬間**を想像してください。その 100 ミリ秒のあいだに届いた 1,000 件のリクエストすべてが「キャッシュミス」と判定され、1,000 本の同時リクエストが一斉に背後のオリジンサーバとデータベースへ雪崩れ込み、オリジンを応答不能に追い込んでしまいます。この現象を **キャッシュスタンピード（Cache Stampede / Dog-pile Effect）** と呼びます（[4-4節](../4/4-4.md)のサンダリング・ハードと同型です）。
>
> 現代の CDN やリバースプロキシは、次の 2 つの仕組みでこれを防ぎます。
>
> 1. **Request Collapsing（リクエスト統合）：** 同じ URL に対してキャッシュミスが同時に 1,000 件発生しても、オリジンへ転送するのは **最初の 1 件だけ** に絞り、残り 999 件はその 1 件の応答が返るのを数ミリ秒だけ待って結果を共有します。
> 2. **`stale-while-revalidate`：** `Cache-Control: max-age=60, stale-while-revalidate=30` と指定すると、期限切れ後の 30 秒間はユーザへ**少し古いキャッシュを即座に返して待たせず**、その裏側で CDN が非同期に 1 回だけオリジンから最新版を取り直してキャッシュを更新します。

### 4. 限界と補正（Critique & Adaptation）

#### (1) スティッキーセッションの課題とステートレス設計の徹底

ロードバランサには、特定のユーザの連続リクエストを常に同じバックエンドサーバへ送り続ける **スティッキーセッション（Session Affinity）** という機能があります。もしアプリサーバのローカル RAM にログインセッションを保存しているとスティッキーセッションが必須になりますが、① 特定のヘビーユーザが当たったサーバだけ過負荷になる（負荷偏り）、② そのサーバが落ちた瞬間に担当ユーザ全員のログインが強制切断される、という大きな欠点があります。

* **補正：** [7-5](../7/7-5.md)・[7-10節](../7/7-10.md)で確認した通り、セッション状態はバックエンドアプリ自身のメモリに置かず外部の共有ストア（Redis 等）または署名付きトークンへ逃がし、バックエンドを完全に **ステートレス** に保つことで、どのサーバへ振り分けても自由にスケール・故障切替できるようにします。

#### (2) キャッシュの鮮度・一貫性と「個人情報の誤キャッシュ」

CDN キャッシュの運用で最も危険な事故の 1 つが、**「ログイン済みユーザのマイページ（`Set-Cookie` や個人情報を含む動的応答）を誤って CDN がキャッシュしてしまい、別のユーザへ他人のマイページを配信してしまう」** 事故です。

* **補正：**

    1. 個人情報を含む動的ページには必ず **`Cache-Control: private, no-store`** を付与し、CDN などの共有キャッシュへの保存を明確に禁止します。
    2. 静的アセット（JS / CSS / 画像）には URL にコンテンツハッシュを埋め込み（例：`app.9f8a7b.js`）、`Cache-Control: public, max-age=31536000, immutable`（1 年間キャッシュ＋変更時は URL ごと切り替える **キャッシュバスティング**）を使うことで、「即時の最新反映」と「100% に近いキャッシュヒット率」を両立します。

#### (3) 多層 Web インフラの先にある「分散システムの根本問題」（第11部への接続）

本節をもって **[第10部](../index.md#part-10)（仮想化・コンテナと Web インフラ：全3節）は完結** です。VM・コンテナ・ロードバランサ・CDN によって、世界中のユーザへ大規模な Web サービスを届けるインフラ構造が一通り揃いました。

しかし、複数台のサーバが協調して**状態（データ・ログ・合意）**を管理しようとした瞬間、私たちは単一マシンでは決して起きなかった分散システムの核心問題に直面します。それは **「物理時計がずれる複数ノード間で『どちらが先に起きたか』をどう定義するか」「ネットワーク分断やノード故障の中で全員が矛盾なく合意するにはどうするか」「2PC のブロッキングを超え、障害が起きる前提でどう信頼性を測り守るか」** という問いです。

### 理解度チェック（第11部へ進む前の確認）

本節の L4 DSR vs L7 プロキシ・CDN キャッシュ制御とスタンピード対策を確認し、第11部（分散システムと信頼性工学）へ繋ぐ問いを置きます。

> **【確認の問い】**
>
> 1. **（L4 ロードバランサ［DSR］vs L7 リバースプロキシの仕組みと診断）**
>
>     * (a) 巨大な動画ストリーム配信で **DSR（Direct Server Return）方式** がロードバランサの帯域ボトルネックを回避できる理由を、往路・復路のパケット経路から説明してください。あわせて、バックエンドのループバックインタフェース（`lo`）で VIP に対する **ARP 応答の無効化を忘れた場合**、通信にどのような破綻が生じるか答えてください。
>     * (b) 単一ドメイン `https://example.com` への HTTPS リクエストを URL パス（`/api/*` は Go コンテナ群、`/images/*` は静的配信サーバ）で振り分けたいとき、L4 ロードバランサでは対応できず **L7 リバースプロキシ** が必要になる理由を説明してください。あわせて、L7 リバースプロキシが TLS 終端を行う際に **`X-Forwarded-For`** ヘッダを付与する理由も述べてください。
>
> 2. **（CDN のキャッシュスタンピード対策と安全なキャッシュヘッダ設計）**
>
>     * (a) 毎秒 10,000 リクエストが到着する人気ページのキャッシュが期限切れになり、オリジンが 1 件の応答生成に 100 ms かかる状況を考えます。キャッシュスタンピード対策が「なし」の場合と、① **Request Collapsing**、② **`stale-while-revalidate`** をそれぞれ有効にした場合で、オリジンへ届くリクエスト数とユーザの待ち時間がどう変わるか比較してください。
>     * (b) ① ログイン済みユーザ固有の「注文履歴ページ（HTML）」と、② ビルド時にファイル名へコンテンツハッシュを付与した「`bundle.3a9f1c.js`」のそれぞれについて、適切な `Cache-Control` ヘッダの方針とその理由を答えてください。さらに、ハッシュなしの `bundle.js` に誤って `max-age=31536000, immutable` を付けてしまった場合、デプロイ後にどのような障害が起きるか答えてください。

> 3. **（第11部への伏線：複数台のサーバに分散したイベントの「時刻と前後関係」）**
>     ロードバランサの背後に並ぶ 10 台のサーバ（Server 1〜10）が、それぞれ NTP で時刻同期しつつリクエスト処理ログへローカル時計のタイムスタンプ（例：`14:00:00.120`）を書き出しています。ある処理で「Server 1 がメッセージ $M$ を送信し、Server 2 が $M$ を受信して後続処理を行った」にもかかわらず、ログを集めてタイムスタンプ順に並べると **「Server 2 の受信時刻（`14:00:00.118`）の方が、Server 1 の送信時刻（`14:00:00.120`）より過去になっている」** という逆転現象が起きました。物理時計（NTP）だけに頼って分散イベントの因果順序を判定できない理由は何であり、物理時計の代わりにどのような「時計」を導入すれば「原因が必ず結果より小さい番号になる」順序を保証できるでしょうか。
