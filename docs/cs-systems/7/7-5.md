### 前節（7-4）の確認問題の解答

前節の最後に提示した3つの問いの解答を確認します。問3までで待ち行列の数理を定着させ、本節（アプリケーションプロトコル）へ進みます。

1. **負荷 2 倍時のスケール設計（独立 $M/M/1 \times 2$ vs 共有キュー $M/M/2$、$\mu = 100\text{ 件/秒}$、$1/\mu = 10\text{ ms}$、$\rho = 0.8$）：**

    * **(a) 独立 $M/M/1 \times 2$（各サーバ $\lambda = 80\text{ 件/秒}$）：**

        $$W_{q\,(M/M/1)} = \frac{\rho}{\mu(1 - \rho)} = \frac{0.8}{100(1 - 0.8)} = \frac{0.8}{20} = 0.04\text{ 秒} = \mathbf{40.0\text{ ms}}$$

        $$D_{(M/M/1)} = W_q + \frac{1}{\mu} = 40.0 + 10.0 = \mathbf{50.0\text{ ms}}$$

    * **(b) 共有キュー $M/M/2$（全体 $\lambda = 160\text{ 件/秒},\; S = 2$）と SLA 比較：**
        $M/M/2$ の平均待ち時間は独立 $M/M/1$ の $\dfrac{\rho}{1 + \rho}$ 倍となるため、

        $$W_{q\,(M/M/2)} = \frac{0.8}{1 + 0.8} \times 40.0 = \frac{160}{9} \approx \mathbf{17.8\text{ ms}}$$

        $$D_{(M/M/2)} = W_q + \frac{1}{\mu} = 17.8 + 10.0 = \mathbf{27.8\text{ ms}}$$

        同じサーバ 2 台・同じ利用率 $\rho = 0.8$ でも、独立 $M/M/1 \times 2$（$W_q = 40.0\text{ ms},\; D = 50.0\text{ ms}$）は SLA 基準を満たせないのに対し、共有キュー $M/M/2$（$W_q \approx 17.8\text{ ms},\; D \approx 27.8\text{ ms}$）は片側遊休をなくすことで SLA 基準を満たせます。

2. **アーラン B 式による最小回線数設計と P-K 公式による処理時間分散の影響：**

    * **(a) 呼量 $a = 1\text{ アーラン}$ で呼損率 $B(S, 1) \le 5\%$ を満たす最小回線数 $S$：**

        * $S = 3$ のとき：

            $$B(3, 1) = \frac{1^3 / 3!}{1 + \dfrac{1}{1!} + \dfrac{1}{2!} + \dfrac{1}{3!}} = \frac{1/6}{1 + 1 + 1/2 + 1/6} = \frac{1/6}{16/6} = \frac{1}{16} = \mathbf{6.25\%} > 5\%$$

        * $S = 4$ のとき：

            $$B(4, 1) = \frac{1^4 / 4!}{\dfrac{16}{6} + \dfrac{1}{24}} = \frac{1/24}{65/24} = \frac{1}{65} \approx \mathbf{1.54\%} \le 5\%$$

        したがって、必要な最小回線数は **$S = 4$ 本** です。

    * **(b) P-K 公式における $C_s = 0$（$M/D/1$）と $C_s = 3$（高分散 $M/G/1$）の平均待ち時間比：**
        P-K 公式 $W_q = \dfrac{\rho}{\mu(1-\rho)} \cdot \dfrac{1 + C_s^2}{2}$ において、$C_s = 0$ の係数は $\dfrac{1 + 0^2}{2} = 0.5$、$C_s = 3$ の係数は $\dfrac{1 + 3^2}{2} = 5.0$ となるため、平均待ち時間の比は $\dfrac{5.0}{0.5} = \mathbf{10\text{ 倍}}$ です。平均処理時間や利用率が同じでも処理時間のばらつき（分散）が大きいほど待ち時間が急激に悪化するため、重いジョブを別キューへ分離するなどで処理時間の分散を抑える設計が重要です。

3. **即時リトライによるリトライストームの機序と指数バックオフ＋ジッタの効果：**
    応答遅延でタイムアウトした多数のクライアントが即時一斉リトライを行うと、通常の新規到着率 $\lambda_{\text{new}}$ に再送到着率 $\lambda_{\text{retry}}$ が上乗せされて実効到着率 $\lambda = \lambda_{\text{new}} + \lambda_{\text{retry}}$ が急増します。その結果、利用率 $\rho = \lambda / \mu$ が $1$ へ迫り（やがて $\rho \ge 1$ へ突入し）、待ち行列遅延が発散してさらなるタイムアウトと再送を生む正のフィードバック（**リトライストーム**）に陥ります。これに対し **指数バックオフ** は連続失敗するほど再送間隔を 2 倍ずつ広げて単位時間あたりの再送到着率 $\lambda_{\text{retry}}$ を抑え、**ジッタ（ランダムな揺らぎ）** は全クライアントの再送時刻が同時刻に重なる同期バーストを分散させることで、$\rho < 1$ の安定領域へ回復させます。

## 7-5. アプリケーションプロトコル（DNS・HTTP・電子メール・SSH）

### 1. 動機（Why）：なぜトランスポート層の上に多様な「会話の作法（アプリケーションプロトコル）」が必要なのか

[7-1](7-1.md)〜[7-4節](7-4.md)を通じて、IP 網の上にプロセス間の通信口（ポート・ソケット）と信頼性・輻輳制御、そして待ち行列の数理基盤がすべて揃いました。しかし、TCP や UDP が提供してくれるのは、あくまで「意味を持たないただのバイト列（あるいはデータグラム）を相手のプロセスへ運ぶ土管」に過ぎません。

この土管を使って実際のサービスを実現するには、**「クライアントとサーバがどのような書式・手順で要求を送り、応答を返すか」**という会話の規約（**アプリケーションプロトコル**）を定める必要があります。このとき、サービスの性質によって次の設計上のトレードオフが生じます。

1. **UDP か TCP か（あるいは QUIC か）：**
    短い 1 往復の問い合わせで終わる名前解決（DNS）に毎回 TCP の 3-way ハンドシェイクを挟むのは遅延が大きすぎます。一方、Web ページの HTML や電子メール、リモート操作のコマンドでは 1 バイトの欠損も許されないため信頼性のある転送（TCP または QUIC）が必須です。

2. **ステートレス（状態を持たない）か、ステートフル（状態を保持する）か：**
    世界中の何百万人ものユーザがアクセスする Web サーバ（HTTP）が、全ユーザの途中状態をメモリへ抱え込むとスケールしません。逆に、対話的なリモートログイン（SSH）やメールボックス操作（IMAP）ではセッション状態の維持が不可欠です。

3. **人間にとっての読みやすさ vs 通信効率と安全性：**
    初期のインターネットプロトコル（HTTP/1.1 や SMTP）はデバッグのしやすさから ASCII テキストの平文で設計されましたが、高速化（バイナリ化・多重化）やセキュリティ強化（暗号化・認証）への進化が求められてきました。

本節では、現代のインターネットを支える4つの代表的なアプリケーションプロトコル（**DNS・HTTP・電子メール・SSH**）の設計思想と進化を整理します。

---

### 2. 具体例と動作イメージ（Toy Model）

各プロトコルの詳細に入る前に、私たちが日常的に行っている 1 回の操作の裏側で、複数のプロトコルがどう連携しているかを辿ってみます。

#### 実験A：ブラウザに `https://example.com/` と入力してから画面が表示されるまで

ブラウザのアドレスバーに `https://example.com/` と入力して Enter キーを押した瞬間、コンピュータは次の一連のプロトコルを連続実行します。

1. **名前解決（DNS：UDP ポート 53）：**
    IP パケットを送るには `example.com` という文字列ではなく IP アドレスが必要です。OS 内部の簡易 DNS クライアント（**スタブリゾルバ**）が DNS サーバへ「`example.com` の IPv4/IPv6 アドレスは？」と問い合わせ、`93.184.216.34` を取得します。

2. **トランスポート＆暗号接続（TCP ポート 443 ＋ TLS、または QUIC）：**
    取得した IP `93.184.216.34` のポート `443` へ接続を確立し、暗号通信の鍵を共有します（[7-7節](7-7.md)）。

3. **Web ページの要求と応答（HTTP）：**
    確立した暗号路の上で、ブラウザが HTTP リクエストを送信し、Web サーバが静的な HTML ファイルや、データベースから動的に生成した HTML 文書を返します。

    ```http
    GET / HTTP/1.1
    Host: example.com
    User-Agent: Mozilla/5.0 ...

    HTTP/1.1 200 OK
    Content-Type: text/html; charset=UTF-8
    Content-Length: 1256

    <!doctype html><html>...
    ```

4. **埋め込み資源の並列取得：**
    HTML を解析したブラウザは、その中に書かれた CSS・JavaScript・画像ファイルなどを同じ接続（HTTP/2・HTTP/3）上で並列に取得して画面を描画します。

#### 実験B：記憶喪失（ステートレス）な HTTP で「ログイン状態」を維持する Cookie

HTTP サーバは原則として**前のリクエストの内容を一切覚えていません（ステートレス）**。では、EC サイトでログインして商品をカートに入れたあと、別のページへ移動してもログイン状態が維持されるのはなぜでしょうか。

1. ログイン成功時、サーバは応答ヘッダに **`Set-Cookie: session_id=9f8a7b; HttpOnly; Secure`** という「名札」を添えて返します（`HttpOnly` は JavaScript からの盗み見禁止、`Secure` は HTTPS 通信限定で送信する安全属性です）。
2. ブラウザはこの名札をローカルへ保存し、以降同じサイトへ送る**すべての HTTP リクエスト**のヘッダへ自動的に **`Cookie: session_id=9f8a7b`** を貼り付けて送ります。
3. サーバは毎回送られてくる `session_id` を背後のセッションストア（Redis やデータベース）へ照合することで、「このリクエストはさっきログインした `alice` さんだ」と識別できます。

### 3. 構造・アルゴリズム・実装（What）

#### (1) DNS（Domain Name System）：インターネットの階層的分散電話帳

人間が覚えやすいドメイン名（`www.example.com`）と IP アドレス（`93.184.216.34`）を相互に結びつける仕組みが **DNS（RFC 1034 / 1035）** です。もし世界中の全ドメインをたった 1 台の中央サーバで管理すれば、単一障害点になり負荷も破綻します。そこで DNS は、**木構造の階層的分散データベース** と **キャッシュ** によって世界規模のスケーラビリティを実現しています（図7-5-1）。

* **3 階層の権威ネームサーバ：**

    1. **ルート（Root）ネームサーバ（`.`）：** 木の頂点です。世界に論理 13 系統（`a.root-servers.net`〜`m.root-servers.net`）あり、[6-8節](../6/6-8.md)の **BGP エニーキャスト** で世界中数百拠点へ分散配置されています。各 TLD サーバの住所を知っています。
    2. **TLD（Top-Level Domain）ネームサーバ：** `.com`, `.jp`, `.org` などのトップレベルドメインを管理し、各組織の権威サーバの住所を知っています。
    3. **権威（Authoritative）ネームサーバ：** `example.com` など個別のドメイン管理者が運用し、最終的な IP アドレスの原本（ゾーン情報）を保持します。

* **再帰問合せと反復問合せ：**

    * 端末（スタブリゾルバ）は、ISP やパブリック DNS（`8.8.8.8` / `1.1.1.1`）が提供する **フルサービスリゾルバ（キャッシュ DNS サーバ）** へ「最終結果の IP を調べて返してほしい」と **再帰問合せ（Recursive Query）** を 1 回だけ送ります。
    * フルサービスリゾルバは手元のキャッシュにない場合、ルート → TLD → 権威サーバへと順番に次の参照先を聞きながら辿る **反復問合せ（Iterative Query）** を代行し、得られた結果を **TTL（Time To Live：有効期限秒数）** のあいだキャッシュへ保存して端末へ返します。なお、DNS の TTL はキャッシュを保持する**秒単位の生存時間**であり、[6-5節](../6/6-5.md)の IP パケットの TTL（ルータを通過するたびに 1 減る**ホップ数上限**）とは名称が同じでも意味が異なります。

* **DNS の主要リソースレコード（RR）：**

    * **`A` / `AAAA`：** ドメイン名から IPv4（32bit）/ IPv6（128bit）アドレスへ対応付けます。
    * **`CNAME`：** 別名（エイリアス）を正規ドメイン名へ紐づけます（例：`www.example.com → cdn.provider.net`）。
    * **`NS`：** そのドメインを管理する権威ネームサーバ名を示します。
    * **`MX`：** そのドメイン宛ての電子メールを受け取るメールサーバ名と優先度を示します。
    * **`TXT`：** 任意のテキスト情報を格納します（後述の SPF / DKIM 等のメール認証や所有権確認に利用します）。

#### (2) HTTP の設計と進化（HTTP/1.1 → HTTP/2 → HTTP/3）

Web の基盤である **HTTP（HyperText Transfer Protocol）** は、クライアントが要求（リクエスト）を送り、サーバが応答（レスポンス）を返すシンプルなクライアント・サーバ型プロトコルです。

* **主なメソッドと性質：**

    * **`GET`（取得）：** サーバの状態を変更せず（**安全：Safe**）かつ何度繰り返しても結果が同じです（**べき等：Idempotent**）。ブラウザやプロキシがキャッシュ可能です。
    * **`PUT`（置換）・`DELETE`（削除）：** 状態を変更しますが、同じ要求を 2 回送っても最終状態は同じです（**べき等**）。
    * **`POST`（作成・送信）：** 決済や新規投稿のように、2 回送ると 2 件作られてしまいます（非べき等）。

* **ステータスコードの 5 分類：** `1xx`（情報）、`2xx`（成功：例 `200 OK`）、`3xx`（リダイレクト：例 `301 Moved Permanently`, `304 Not Modified`）、`4xx`（クライアント起因エラー：例 `400 Bad Request`, `403 Forbidden`, `404 Not Found`）、`5xx`（サーバ起因エラー：例 `500 Internal Server Error`, `503 Service Unavailable`）に分かれます。

Web ページが数十〜数百個の画像やスクリプトで構成される現代において、HTTP は **「どうすれば遅延（RTT）を削り、1本の接続を無駄なく使い切れるか」** という一点を軸に大きく 3 世代へ進化してきました（図7-5-2）。

1. **HTTP/1.1（1997年・テキストベース）：**

    * 初期の HTTP/1.0 は 1 ファイルごとに TCP 接続を開閉していたため大きな遅延が生じていました。HTTP/1.1 では 1 本の TCP 接続を使い回す **持続的接続（Keep-Alive）** を標準化しました。
    * しかし、1 本の TCP 接続上では「要求 1 の応答が完全に返るまで要求 2 の応答を送り始められない」という **アプリケーション層の HoL（Head-of-Line）ブロッキング** が起きます。これを回避するため、ブラウザは同じサーバへ **6 本もの TCP 接続を並列に張る** 工夫をしてきました。

2. **HTTP/2（2015年・バイナリ多重化）：**

    * メッセージをテキストではなく小さなバイナリの **フレーム** へ分割し、**たった 1 本の TCP 接続の中で複数ストリーム（HTML・CSS・画像）を同時にインターリーブ送信（ストリーム多重化）** できるようにしました。これによりアプリ層の HoL ブロッキングを解消します。
    * さらに、毎回のリクエストで重複する巨大な HTTP ヘッダ（Cookie や User-Agent 等）をハフマン符号と動的テーブルで圧縮する **HPACK** を導入しました。
    * **残された壁：** 下位が 1 本の TCP であるため、パケットが 1 個紛失すると **トランスポート層（TCP）の HoL ブロッキング**（[7-3節](7-3.md)）が起き、すべてのストリームが再送完了まで一斉に止まってしまいます。

3. **HTTP/3（2022年・QUIC ベース）：**

    * トランスポート層を TCP から **UDP 上の QUIC（[7-3節](7-3.md)）** へ刷新し、QUIC の独立ストリームに合わせて順序逆転でも詰まらないヘッダ圧縮方式 **QPACK** を採用しました。これにより **TCP 層の HoL ブロッキングまで解消** され、さらに TLS 1.3 統合による **1 RTT / 0 RTT 接続** と **コネクションマイグレーション**（Wi-Fi $\to$ 5G 切替でも切断されない）を実現しています。

> **【コラム：なぜ HTTP はあえて「ステートレス（記憶喪失）」に設計され、CDN や水平スケールを可能にしたのか】**
>
> Web サーバが「各クライアントが今どの画面を開いているか」を一切記憶しない **ステートレス設計** は、一見すると Cookie のような手間を増やしているように見えます。しかし、これこそが世界中の何億人ものアクセスを捌く現代の Web インフラ（クラウドと **CDN：Content Delivery Network**）を支える大きな利点です。
>
> * **水平スケール（ロードバランシング）が容易：** サーバが状態を持たないため、アクセスが急増したら同じ Web サーバを 10 台・100 台と横に並べるだけで、ロードバランサがリクエストをどのサーバへ振り分けてもまったく同じ結果が返ります。
> * **キャッシュと CDN の徹底活用：** 同じ URL に対する `GET` 応答が誰に対しても同じなら、世界中のエッジ拠点（[6-8節](../6/6-8.md)のエニーキャスト等）に配置した **CDN キャッシュサーバ** がオリジンサーバの代わりに画像や動画を即座に返却でき、遅延とバックボーン帯域を大きく削減できます。

#### (3) 電子メールのアーキテクチャ（SMTP・POP3・IMAP と MIME）

電子メールは、HTTP のように送信者と受信者が同時にオンラインである必要がない **非同期のストア＆フォワード型** システムです。「送信（プッシュ）」と「受信・閲覧（プル）」で別々のプロトコルを使い分けます（図7-5-3）。

1. **SMTP（Simple Mail Transfer Protocol：サーバ間転送 25 番／提出用 587 番［STARTTLS］・465 番［暗黙 TLS］）：**
    送信者のメールソフト（**MUA**：Mail User Agent）が自組織の提出受付サーバ（**MSA**：Mail Submission Agent）へメールを預け、送信側転送サーバ（**MTA**：Mail Transfer Agent）が DNS の **`MX` レコード** で宛先ドメインの受信側 MTA を探し出して直接 **プッシュ転送** します。コマンドは `HELO / EHLO`, `MAIL FROM:`, `RCPT TO:`, `DATA` といった ASCII テキスト対話です。

2. **POP3（平文 110 番 / TLS 暗号化 995 番）vs IMAP（平文 143 番 / TLS 暗号化 993 番）：**
    受信側 MTA がユーザのメールボックスへ格納したメールを、受信者の端末が好きなタイミングで **プル（取得）** するプロトコルです。

    * **POP3：** サーバからメールを端末へダウンロードし、原則サーバ側から削除する単純な方式です（1台のPCだけで読む時代向け）。
    * **IMAP：** メール本体とフォルダ構造・既読フラグを**サーバ側で一元管理**する方式です。PC・スマートフォン・タブレットの複数端末から常に同じメールボックスを同期閲覧できるため、現代の標準となっています。

3. **MIME（Multipurpose Internet Mail Extensions）：**
    1982年策定の SMTP は 7 ビット ASCII 英数字しか運べない前提でした。そこで日本語（UTF-8）や画像・PDF 添付ファイルを送るため、ヘッダに `Content-Type` を明記し、バイナリデータを 64 種類の ASCII 文字へ変換する **Base64 符号化** 等で安全に運ぶ拡張規格が **MIME** です（HTTP の `Content-Type` も MIME の仕組みを流用しています）。

#### (4) SSH（Secure Shell）：暗号化されたリモート操作とトンネリング

かつて遠隔サーバのシェルを操作するために使われていた **Telnet** は、パスワードも入力コマンドもすべて**平文**でネットワーク上へ流していたため、同じ LAN や経路上の盗聴者へパスワードが丸見えでした。これを置き換えたのが **SSH（TCP ポート 22）** です。

* **ホスト鍵の検証（TOFU：Trust On First Use）：** 初めて接続するサーバの公開鍵（指紋）を `~/.ssh/known_hosts` へ記録し、2回目以降に鍵が変わっていれば中間者攻撃（なりすましサーバ）の恐れがあるとして強く警告して接続を止めます。
* **暗号化通信路と公開鍵認証：** 接続直後に鍵交換でセッション鍵を確立して全通信を暗号化し（詳細は[7-6](7-6.md)・[7-7節](7-7.md)）、パスワード入力の代わりに手元の秘密鍵で署名を返す**公開鍵認証**によって総当たり攻撃（ブルートフォース）を防ぎます。
* **ポートフォワーディング（SSH トンネリング）：** SSH の暗号化接続を安全なトンネルとして流用し、外部から直接繋げない社内データベース等のポートへ安全に中継する機能も実務で広く使われます。

> **【補足：なぜ古典的な FTP は NAT・ファイアウォールと相性が悪く、SFTP / HTTPS へ置き換わったのか】**
>
> ファイル転送プロトコル **FTP** は、コマンド送信用（**TCP 21 番**）とファイル本体転送用（**TCP 20 番**）の **2 本の独立した TCP 接続** を分離する設計をとりました。標準のアクティブモードではサーバ側からクライアントの指定ポートへ逆向きにデータ接続を張り直すため、[6-6節](../6/6-6.md)の NAT やファイアウォール越しの通信が遮断されやすく、さらに認証情報も平文で流れる欠点がありました。現代では単一の暗号化接続で完結する **SFTP（SSH 上のファイル転送）** や **HTTPS** へ移行しています。

### 4. 限界と補正（Critique & Adaptation）

インターネット黎明期に設計された DNS・HTTP・SMTP は、**「善意の参加者だけで構成された学術網」を前提に平文かつ認証なしで設計された**ため、現代のインターネットでは深刻なセキュリティ上の限界が露呈し、多層的な補正が加えられています。

#### (1) DNS の盗聴・改ざんと補正（DNSSEC・DoH / DoT）

* **DNS キャッシュポイズニング（Kaminsky 攻撃等）：** 従来の DNS は UDP 53 番の平文で、問い合わせ ID もわずか 16 ビット（65,536 通り）でした。攻撃者が存在しないランダムなサブドメインを大量に問い合わせつつ偽の応答パケットを浴びせ（Kaminsky 攻撃）、キャッシュ DNS サーバへ「`bank.example.com` は攻撃者の IP だ」という偽レコードを覚え込ませると、利用者が本物の URL を打っても偽サイトへ誘導されます。
* **補正：**

    * **DNSSEC：** ルートから権威サーバまで公開鍵暗号のデジタル署名（[7-7節](7-7.md)）の連鎖を張り、DNS 応答が改ざんされていないことを暗号学的に検証します（ただし通信内容自体は暗号化されません）。
    * **DoT（DNS over TLS：ポート 853）と DoH（DNS over HTTPS：ポート 443）：** 端末とフルサービスリゾルバ間の DNS 問い合わせ自体を TLS / HTTPS で丸ごと暗号化し、カフェの Wi-Fi や ISP による閲覧先ドメインの盗聴・改ざんを防ぎます。

#### (2) HTTP の Cookie・セッション管理と電子メールのなりすまし対策

* **Cookie とセッション管理のセキュリティ課題：** 実験Bの Cookie はブラウザがリクエストごとに自動送信するため、平文通信での盗聴（**セッションハイジャック**）、悪意あるスクリプトで Cookie を抜き取る **XSS（クロスサイトスクリプティング）**、別サイトから意図しないリクエストを送りつける **CSRF（クロスサイトリクエストフォージェリ）** の標的になります。補正として、HTTPS 通信限定の `Secure` 属性、JavaScript からの読み出しを禁じる `HttpOnly` 属性、他サイト起点の送信を制限する `SameSite` 属性、および CSRF トークンを併用します。
* **電子メールのなりすましと送信ドメイン認証（SMTP AUTH・SPF・DKIM・DMARC）：** SMTP の `MAIL FROM:` ヘッダには誰でも他人のメールアドレス（例：`ceo@bank.com`）を書き込めてしまうため、フィッシング詐欺やスパムの温床になりました。これに対し、提出ポート（587 / 465 番）で送信者の認証を必須化する **SMTP 認証（SMTP AUTH）** に加え、次の 3 点セットの **送信ドメイン認証** で補正しています。

    1. **SPF（Sender Policy Framework）：** 送信元ドメインの DNS `TXT` レコードに「このドメインからメールを送ってよい正規の送信サーバの IP アドレス一覧」を公開し、受信側が接続元 IP と照合します。ただし、メーリングリストやメール転送（Forwarding）を経由すると接続元 IP が転送サーバのものへ変わるため、SPF は検証に失敗しやすい制約があります。
    2. **DKIM（DomainKeys Identified Mail）：** 送信側メールサーバがメール本文と主要ヘッダへ秘密鍵で**デジタル署名（[7-7節](7-7.md)）**を付与し、受信側が DNS `TXT` レコードの公開鍵で検証します。接続元 IP ではなくメール内容そのものに署名するため、本文が改変されない限りメール転送を経由しても検証に耐え、改ざんとなりすましを検知できます。
    3. **DMARC：** SPF と DKIM の検証に失敗したメールを受信側がどう扱うか（隔離・拒否・レポート通知）のポリシーを DNS で宣言します。

#### (3) 平文アプリケーションプロトコルの根本的限界（次節への動機）

ここまで見た DoH / DoT、HTTPS、SSH、DKIM、DNSSEC のすべてに共通しているのは、**「インターネットという盗聴・改ざん・なりすましが自在に起きる通信路の上で安全を保つには、暗号技術と認証プロトコルが不可欠である」**という事実です。では、盗聴されている回線の上でどうやって秘密の鍵を共有し、データを暗号化し、相手が本物であることを証明しているのでしょうか。残る[第7部](../index.md#part-7)の2節（[7-6](7-6.md)・[7-7節](7-7.md)）で、その暗号技術の数学的原理とプロトコル設計を解き明かします。

> **【確認の問い】**
>
> 1. **（DNS サーバ移行時の TTL キャッシュ残留と関連レコード診断）**
>     Web サイト `www.example.jp` の `A` レコードの TTL が `86400 秒`（24 時間）に設定されたまま、管理者が移行当日に突然 IP アドレスを旧サーバから新サーバへ書き換えました。
>
>     * (a) 切替直前に旧 IP アドレスをキャッシュしたフルサービスリゾルバが存在する場合、そのリゾルバを利用するユーザは最大でどれだけの時間、旧サーバへ接続し続けてしまうでしょうか。また、ダウンタイムを数分以内に抑えるために移行前日までに取るべき事前手順を答えてください。
>     * (b) Web サーバと同時にメールサーバも新ホスト名 `mail2.example.jp`（新 IP アドレス）へ移行したとき、`A` レコードの更新だけでは外部からのメール受信や外部への送信が失敗・迷惑メール判定される恐れがあります。あわせて更新・確認すべき DNS レコードの種類を 2 つ挙げ、それぞれの役割を説明してください。
>
> 2. **（HTTP メソッド設計・Cookie 保護属性および IMAP 暗号化と SSH ポートフォワーディングの比較）**
>     次の 2 つの問いに答えてください。
>
>     * (a) EC サイトの注文確定処理を `POST` ではなく `GET /checkout?item=123` として実装した場合、HTTP メソッドの性質（安全性・べき等性）に照らしてどのような実害が生じ得るか説明してください。また、セッション Cookie に **`HttpOnly`・`Secure`・`SameSite`** の 3 属性を付け忘れたとき、それぞれどのような攻撃・漏洩リスクが高まるかを簡潔に答えてください。
>     * (b) 社外から安全にメールボックスを閲覧する **TLS 暗号化付き IMAP（ポート 993）** と、外部非公開の社内データベースへ一時的に接続する **SSH ポートフォワーディング（ポート 22）** の仕組みと用途の違いを比較してください。
>
> 3. **（DNSSEC と DoH の防御レイヤの違い、および盗聴回線上の鍵配送ジレンマ）**
>     カフェの公衆 Wi-Fi 上でブラウザから Web サイトへアクセスする状況を考えます。
>
>     * (a) DNS に対する保護技術である **DNSSEC** と **DoH（DNS over HTTPS）** は、「盗聴防止（機密性）」と「応答データの改ざん検知（完全性・真正性）」のどちらを主に担っているか比較してください。
>     * (b) DoH・HTTPS・SSH のいずれも通信路を暗号化することで盗聴者からデータを守っていますが、初めて接続するクライアントと遠隔サーバが、盗聴者に見られている回線上で暗号化用の「秘密の鍵」を共有しようとするとき、どのような根本的なジレンマ（鍵配送問題）が生じるでしょうか。
