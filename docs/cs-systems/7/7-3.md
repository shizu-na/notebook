### 前節（7-2）の確認問題の解答

前節の最後に提示した3つの問いの解答を確認します。問3がそのまま本節（フロー制御・輻輳制御・QUIC）の導入になります。

1. **シーケンス番号・`Ack`・`rwnd`・SACK の実践トレース（バッファ総容量 `4000 B`、各セグメント `500 B`）：**

    * **(a) セグメント 1（バイト `1001..1500`）到着直後：**
        500 バイトが順番通り受信されてバッファに溜まるため、次に期待するバイト番号は **`Ack = 1501`**、残り空きバッファ容量は $4000 - 500 = \mathbf{3500}$ となり、**`rwnd = 3500`** を返します。

    * **(b) セグメント 2 紛失・セグメント 3 先着時、およびセグメント 2 再送到着後：**

        * **セグメント 3 先着時：** セグメント 2（`1501..2000`）が欠けているため、累積確認応答番号は欠損の先頭を指す **`Ack = 1501`** のままとなります。同時にサーバはセグメント 3 をバッファへ保存し、**SACK オプションでバイト `2001..2500`（RFC 2018 の右開区間表記では `2001..2501`）を受信済み** であることを通知します。
        * **セグメント 2 再送到着直後：** 欠損が埋まってバイト `1001..2500` の計 1,500 バイトが連続して揃うため、累積確認応答は **`Ack = 2501`** へ進みます。アプリはまだ `read()` していないため、残り空きバッファ容量は $4000 - 1500 = \mathbf{2500}$ となり、**`rwnd = 2500`** を返します。

2. **`TIME_WAIT` ポート枯渇と Nagle×遅延 ACK のデバッグ：**

    * **(a) リバースプロキシでの `TIME_WAIT` ポート枯渇の原因と対策：**
        能動クローズ側（プロキシ側）は 4-way 切断後に $2\text{ MSL}$（Linux では通常 60 秒）のあいだ 5 つ組を `TIME_WAIT` 状態で保持し続けます。接続先 `(バックエンドIP, ポート)` が同一であるため、毎秒数千回の短命接続をプロキシ側から閉じると、クライアント側エフェメラルポート（Linux 標準で約 28,000 個）がすべて `TIME_WAIT` で占有されて枯渇し、新規接続ができなくなります。対策としては、1 本の TCP 接続を使い回す **HTTP Keep-Alive（持続的接続）やコネクションプールの導入**（あるいは接続先バックエンド IP の分散やサーバ側クローズの回避）が有効です。

    * **(b) Nagle アルゴリズムと遅延 ACK による 40 ms 遅延の原因と対処：**
        送信側が 1 回目の小さな `write()` を送った直後、Nagle アルゴリズムが「未確認データが残っているため 1 発目の ACK が返るまで 2 回目の小さなデータを留保する」と動作します。一方、受信側は遅延 ACK により「返答データや後続セグメントに相乗りさせるため ACK の返送を最大 40 ms 程度待つ」と動作します。結果として双方が互いを待ち合うすれ違いが起き、遅延 ACK タイマが満了する約 40 ms が毎回上乗せされます。対処法としては、送信側ソケットに **`TCP_NODELAY`** を設定して Nagle アルゴリズムを無効化します（または 2 回の `write()` を 1 回のバッファ書き込みにまとめます）。

3. **RFC 6298 に基づく RTT 推定とパケットロス検知イベントの意味（本節への接続）：**

    * **(a) サンプル RTT 列 $80\text{ ms} \to 160\text{ ms} \to 90\text{ ms}$ の計算：**

        * **初回（$R_1 = 80\text{ ms}$）：** $\text{SRTT} = 80\text{ ms}$、$\text{RTTVAR} = 80 / 2 = 40\text{ ms}$（初期 $\text{RTO} = 240\text{ ms}$）となります。
        * **$R_2 = 160\text{ ms}$ 更新直後：** 更新前の $\text{SRTT} = 80\text{ ms}$ との差は $\vert 80 - 160 \vert = 80\text{ ms}$ なので、

            $$\text{RTTVAR} = \frac{3}{4} \times 40 + \frac{1}{4} \times 80 = 30 + 20 = \mathbf{50\text{ ms}}$$

            $$\text{SRTT} = \frac{7}{8} \times 80 + \frac{1}{8} \times 160 = 70 + 20 = \mathbf{90\text{ ms}}$$

            $$\text{RTO} = 90 + 4 \times 50 = \mathbf{290\text{ ms}}$$

        * **$R_3 = 90\text{ ms}$ 更新直後：** 更新前の $\text{SRTT} = 90\text{ ms}$ との差は $\vert 90 - 90 \vert = 0\text{ ms}$ なので、

            $$\text{RTTVAR} = \frac{3}{4} \times 50 + \frac{1}{4} \times 0 = \mathbf{37.5\text{ ms}}$$

            $$\text{SRTT} = \frac{7}{8} \times 90 + \frac{1}{8} \times 90 = \mathbf{90\text{ ms}}$$

            $$\text{RTO} = 90 + 4 \times 37.5 = \mathbf{240\text{ ms}}$$

    * **(b) 3 重重複 ACK と RTO タイムアウトの輻輳深刻度の違い：**
        **3 重重複 ACK** が返ってくるということは、ある 1 個のセグメントが失われた一方で、後続の 3 セグメントは正常に相手へ届き ACK も返っている（パイプ自体は流れ続けている）ことを意味するため、比較的軽度の輻輳と推定できます。これに対し **RTO タイムアウト** は一定時間以上まったく新しい ACK が届かず通信路が完全に詰まった状態を示すため、深刻な輻輳と推定できます。本節では、この差に応じて送信窓の絞り方を変える **TCP の輻輳制御** を学びます。

## 7-3. フロー制御と輻輳制御（スロースタート・AIMD・Tahoe/Reno・ECN・QUIC）

### 1. 動機（Why）：なぜ受信側の保護だけでは足りず、インターネット全体の「渋滞崩壊」を防ぐ仕組みが要るのか

前節（[7-2節](7-2.md)）では、TCP が 3-way ハンドシェイクで接続を確立し、バイト単位のスライディングウィンドウと適応的 RTT 推定によって信頼性のある転送を行う仕組みを学びました。

ここで残された最大の問いが、**「送信側が一度に回線上へ送り出してよい未確認データ量（送信ウィンドウサイズ $W$）を、いくつに決めるべきか」** です。$W$ が小さすぎれば広帯域回線を使い切れず（[7-1節](7-1.md)）、逆に $W$ を大きすぎる値に固定すると、次の **2つのまったく異なる場所** で破綻が起きます。

1. **受信ホストのパンク（1対1の問題 $\implies$ フロー制御）：**
    送信側が高速なサーバ、受信側が処理の遅い組込み機器や忙しいスマートフォンであるとき、受信側アプリの `read()` が追いつかない速度で送り続けると、受信 OS のソケットバッファが溢れて正常に届いたデータまで捨てられてしまいます。

2. **ネットワーク全体のパンク（多対多の問題 $\implies$ 輻輳制御）：**
    たとえ受信ホストに十分なメモリがあっても、途中の共有ルータ（ボトルネックリンク）へ世界中の送信者が一斉に大きなウィンドウでパケットを流し込むと、ルータの出力キューが溢れてパケット廃棄が連鎖します。さらに各送信者が「届かないから再送しよう」と追い打ちをかけた結果、回線上は再送パケットばかりで埋め尽くされ、**有効なスループットがほぼゼロへ転落する「輻輳崩壊（Congestion Collapse）」** が起きます。

しかも、[6-1節](../6/6-1.md)のエンドツーエンド原理のもとでは、途中のルータは原則として各送信者へ「今は何 Mbps で送れ」と指示してくれません。**世界中の送信ホストが互いの存在を知らないまま、自律的かつ公平に回線帯域を分け合う** ための制御アルゴリズムが、TCP の **輻輳制御（Congestion Control）** です。

本節では、**フロー制御（`rwnd`）** と **輻輳制御（`cwnd`：スロースタート・AIMD・Tahoe / Reno）** の原理を整理したうえで、現代の改良（**ECN・CUBIC・BBR**）、そして TCP 自体の構造的限界を超える次世代トランスポート **QUIC** へと進みます。

---

### 2. 具体例と動作イメージ（Toy Model）

アルゴリズムの細かい遷移に入る前に、2つの小さな例で「フロー制御のやり取り」と「AIMD が勝手に公平へ収束する不思議」を体感します。

#### 実験A：受信バッファの空き容量を毎回知らせる「フロー制御（`rwnd`）」

受信ホストの TCP 受信バッファの総容量が $4{,}096\text{ B}$ だとします。

1. 初期状態：バッファは空なので、受信側は ACK ヘッダのウィンドウサイズ欄に **`rwnd = 4096`** と書いて送信側へ通知します。
2. 送信側が $2{,}000\text{ B}$ 送信し、受信側のバッファへ到着します。まだ受信側アプリが `read()` を呼んでいないため、バッファの残り空きは $4{,}096 - 2{,}000 = 2{,}096\text{ B}$ になります。受信側は **`rwnd = 2096`** を返します。
3. 送信側がさらに $2{,}096\text{ B}$ 送ると、受信バッファが満杯になり、受信側は **`rwnd = 0`（ゼロウィンドウ）** を返します。これを見た送信側はデータ送信を一時停止します。
4. やがて受信側アプリが `read()` で $1{,}000\text{ B}$ 吸い出すと空きができますが、もし受信側から送る「空きができたよ（`rwnd = 1000`）」の通知が途中で紛失すると、双方待ちのデッドロックになります。そこで送信側は、`rwnd == 0` を受け取っているあいだも、一定間隔で 1 バイトだけの小さな確認パケット（**ゼロウィンドウプローブ**）を送り、空きが回復した瞬間に送信を再開します。

#### 実験B：なぜ「少しずつ増やし、ぶつかったら半分にする（AIMD）」と公平になるのか

容量 $100\text{ Mbps}$ の1本のボトルネック回線を、ホスト A とホスト B の2台が共有しているとします。最初は不公平に **A が $80\text{ Mbps}$、B が $20\text{ Mbps}$**（合計 $100\text{ Mbps}$）で流していたとします。ここで両者が互いに相談せず、次の単純なルール **AIMD（Additive Increase, Multiplicative Decrease：加法増加・乗法減少）** だけを守ってみます。

* **空いている間（ロスなし）：** 1 RTT ごとに両者とも同じ量 **$+10\text{ Mbps}$** ずつ増やします（加法増加）。
* **溢れた瞬間（ロス発生）：** 両者とも自分の現在速度を **半分（$\times 0.5$）** へ減らします（乗法減少）。

手計算で推移を追ってみましょう。

1. 初期状態：`(A, B) = (80, 20)`（合計 100、差は **60**）
2. 少し増えて溢れる $\to$ 両者半分にする：`(40, 10)`（差は **30** へ半減）
3. 合計 100 を超えるまで両者 $+10$ ずつ足す：`(50, 20) → (60, 30) → (70, 40)`（合計 110 で溢れ）
4. 両者半分にする：`(35, 20)`（差は **15** へさらに半減）
5. 再び $+10$ ずつ足して溢れる：`(45, 30) → (55, 40) → (65, 50)`（合計 115 で溢れ）$\to$ 半分にして `(32.5, 25)`（差は **7.5** へ半減）

このように、**A と B が一度も会話していないにもかかわらず、速度差が $60 \to 30 \to 15 \to 7.5 \to \dots \to 0$ と指数関数的に縮まり、自動的に公平な $(50, 50)$ へ収束**します（図7-3-2）。「たくさん使っている側ほど半減したときの譲歩幅が大きく、その後は同じ歩幅で増える」という非対称性が、インターネットの分散公平性を支える数理的な仕組みです。

### 3. 構造・アルゴリズム・実装（What）

#### (1) 送信ウィンドウの決定式：$W = \min(\text{rwnd},\; \text{cwnd})$

TCP の送信側は、常に次の2つの上限値のうち **小さい方** を実際の送信ウィンドウサイズ $W$ として採用します。

$$
\text{LastByteSent} - \text{LastByteAcked} \;\le\; \min(\text{rwnd},\; \text{cwnd})
$$

* **`rwnd`（受信ウィンドウ：フロー制御）：** 受信ホストが TCP ヘッダの 16 ビット Window フィールドで毎回通知してくる空きバッファ容量です。なお、16 ビットでは最大 $65{,}535\text{ B}$（$64\text{ KiB}$）までしか表せず現代の 1 Gbps〜10 Gbps 回線の帯域遅延積を満たせないため、3-way ハンドシェイク時に **ウィンドウスケーリング・オプション（RFC 7323）** でシフト量（最大 $2^{14}$ 倍＝約 $1\text{ GiB}$）を合意します。
* **`cwnd`（輻輳ウィンドウ：輻輳制御）：** 送信ホスト自身がネットワークの混雑度を推測して内部で管理する上限値です（通常は **MSS：最大セグメント長**、イーサネット標準で約 $1{,}460\text{ B}$ の整数倍で数えます）。

#### (2) TCP 輻輳制御の 3 フェーズ（スロースタート・輻輳回避・高速リカバリ）

送信側は、現在の通信路の適正帯域をまったく知らない状態から通信を始めます。そこで、**閾値 `ssthresh`（Slow Start Threshold）** を境界として、次の3つのフェーズを切り替えます（図7-3-1）。

1. **スロースタート（Slow Start：`cwnd < ssthresh`）：**

    * 接続直後は小さな初期値（古典的には $1\text{ MSS}$、現代の RFC 6928 では $10\text{ MSS}$）から出発し、**ACK を 1 個受け取るたびに `cwnd` を $+1\text{ MSS}$ 増やします**。
    * 1 RTT の間に送った $N$ 個すべての ACK が返ってくると `cwnd` は $2N$ になるため、**1 RTT ごとに `cwnd` が 2 倍へ指数関数的に増加**します（$1 \to 2 \to 4 \to 8 \to 16 \dots$）。名前は「スロー（ゆっくり）」ですが、これは「最初から最大ウィンドウで一気に送らない」という意味であり、立ち上がり自体は指数関数的に素早く適正帯域へ迫ります。

2. **輻輳回避（Congestion Avoidance：`cwnd >= ssthresh`）：**

    * `cwnd` が `ssthresh` に達したら、もうすぐボトルネック帯域にぶつかる警戒域に入るため、増加ペースを **AIMD の加法増加（1 RTT あたり $+1\text{ MSS}$ の線形増加）** へ落とします（実装上は ACK を 1 個受けるたびに $\text{cwnd} \mathrel{+}= \text{MSS} \times \dfrac{\text{MSS}}{\text{cwnd}}$ と加算します。1 RTT の間に約 $\text{cwnd}/\text{MSS}$ 個の ACK が返るため、1 RTT 合計でちょうど $+1\text{ MSS}$ 増える計算です）。

3. **パケットロス検知時の減速（Tahoe vs Reno の決定的な違い）：**
    TCP は「パケット紛失＝途中ルータのキューが溢れたサイン」と解釈して `cwnd` を絞りますが、**紛失の検知方法（重度のタイムアウトか、軽度の 3 重重複 ACK か）** に対する反応の違いが **TCP Tahoe（1988年）** と **TCP Reno（1990年）** を分けます。

| ロス検知イベント | ネットワーク状態の解釈 | **TCP Tahoe** の動作 | **TCP Reno** の動作 |
| :--- | :--- | :--- | :--- |
| **RTO タイムアウト** | **重度の輻輳**（ACK 自体が完全に途絶えた） | `ssthresh = cwnd / 2`<br>**`cwnd = 1 MSS`**（スロースタートからやり直し） | `ssthresh = cwnd / 2`<br>**`cwnd = 1 MSS`**（スロースタートからやり直し） |
| **3 重重複 ACK**（[7-2節](7-2.md)） | **軽度の輻輳**（後続の 3 パケットは相手に届いておりパイプは流れている） | `ssthresh = cwnd / 2`<br>**`cwnd = 1 MSS`**（タイムアウトと同じく 1 まで急落） | `ssthresh = cwnd / 2`<br>**`cwnd = ssthresh`**（半分に留めてすぐ線形増加へ＝**高速リカバリ：Fast Recovery**） |

図7-3-1の通り、TCP Tahoe は 3 重重複 ACK でも毎回 `cwnd = 1` まで急降下してしまうため帯域を大きく取りこぼします。一方、**TCP Reno** は 3 重重複 ACK 時に `cwnd` を半分（`cwnd / 2`）に留めてそのまま輻輳回避の線形増加へ戻る（**高速リカバリ**）ため、定常状態では `cwnd` が $W/2$ と $W$ の間を行き来する特徴的な **鋸歯状（ノコギリ波：Sawtooth）** を描き、高い平均スループットを維持します。なお、RFC 5681 の厳密な高速リカバリ実装では、3 重重複 ACK 検知時に `ssthresh = cwnd / 2` としたあと一時的に `cwnd = ssthresh + 3 MSS` へ設定し、さらに追加の重複 ACK が届くごとに `cwnd` を `+1 MSS` ずつ一時的にインフレさせて新規セグメントの送出を維持し、再送に対する新しい ACK が届いた時点で `cwnd = ssthresh` へ収縮（デフレート）して輻輳回避へ移行します。

#### (3) AIMD の公平性収束とスループットの近似式（Mathis の式）

実験Bで確かめた AIMD の公平性収束は、横軸をフロー1の速度 $x_1$、縦軸をフロー2の速度 $x_2$ にとった平面グラフ（**Chiu-Jain モデル**）で幾何学的に理解できます（図7-3-2）。

* 合計帯域 $x_1 + x_2 = R$ の直線（**効率線**）より下にある間は、両者が同じ傾き $45^\circ$（$+1, +1$）で右上へ進みます。
* 効率線を超えた瞬間にパケットロスが起き、両者が原点 $(0, 0)$ に向かって一直線に半分（$\times 0.5$）へ縮みます。
* この「$45^\circ$ 上昇 $\to$ 原点方向へ半減」を繰り返すだけで、どんな不公平な初期点から始めても、軌跡は必ず直線 $x_1 = x_2$（**公平線**）と効率線の交点 $(R/2, R/2)$ へ吸い込まれていきます。

また、定常状態で TCP Reno が $W/2$ と $W$ の間を鋸歯状に往復しているとき、1サイクル（$W/2 \to W$ に $W/2$ RTT かかります）の平均ウィンドウ幅は $\dfrac{W/2 + W}{2} = \dfrac{3}{4}W$ であり、1サイクル中に送信される総セグメント数は $\dfrac{3}{4}W \times \dfrac{W}{2} = \dfrac{3}{8}W^2$ 個です。各サイクルの末尾でちょうど 1 パケット紛失するため、パケット紛失率は $p \approx \dfrac{1}{(3/8)W^2}$、すなわち $W \approx \sqrt{\dfrac{8}{3p}}$ となります。これを 1 サイクルの平均スループットへ代入すると、有名な **TCP スループット近似式（Mathis の式）** が導かれます。

$$
\begin{aligned}
\text{Throughput} &\approx \frac{3}{4}W \cdot \frac{\text{MSS}}{\text{RTT}} \approx \frac{3}{4}\sqrt{\frac{8}{3p}} \cdot \frac{\text{MSS}}{\text{RTT}} \\
                  &= \sqrt{\frac{3}{2}} \cdot \frac{\text{MSS}}{\text{RTT}\sqrt{p}} \approx \frac{1.22 \cdot \text{MSS}}{\text{RTT}\sqrt{p}}
\end{aligned}
$$

この式は実践的な意味を持ちます。たとえば $\text{RTT} = 100\text{ ms}$（$= 0.1\text{ s}$）、$\text{MSS} = 1{,}460\text{ B} = 11{,}680\text{ bit}$ の長距離回線で $10\text{ Gbps}$（$= 10^{10}\text{ bit/s}$）を出し続けるには、許容されるパケット紛失率が $p \approx \left(\dfrac{1.22 \times 11{,}680}{0.1 \times 10^{10}}\right)^2 \approx \mathbf{2.0 \times 10^{-10}}$（約 50 億パケットに 1 個未満）という非現実的なほど低い値でなければならず、これが後述する CUBIC や BBR への進化を促しました。

> **【コラム：1986 年の「輻輳崩壊（Congestion Collapse）」と Van Jacobson の救済】**
>
> 1981年に策定された初期の TCP 仕様（RFC 793）には、受信側を守る「フロー制御（`rwnd`）」はありましたが、**「輻輳制御（`cwnd`）」は一切存在しませんでした**。そのため送信ホストは、接続した瞬間にいきなり受信ウィンドウいっぱいのパケットを回線へ流し込んでいました。
>
> 1986年10月、インターネットの前身である ARPANET 上で、ローレンス・バークレー研究所とカリフォルニア大学バークレー校を結ぶ回線の実効スループットが、ある日突然 **$32\text{ kbps}$ からわずか $40\text{ bps}$（約 800 分の 1）** へ急落する大規模な障害が発生しました。途中のルータが溢れてパケットが落ちるたびに、全ホストがフルスピードで再送を繰り返し、回線上を重複した再送パケットが埋め尽くす **輻輳崩壊** が現実のものとなったのです。
>
> この危機を救ったのが、1988年にヴァン・ジェイコブソン（Van Jacobson）らが提案した **スロースタート・輻輳回避（AIMD）・適応的 RTT 推定（[7-2節](7-2.md)）** でした。既存のルータを1台も買い替えず、両端のホスト OS の TCP スタックへわずか数十行の輻輳制御コードを追加しただけで、インターネットの崩壊は大きく収束し、その後の世界規模の拡大が可能になりました。

#### (4) ECN（明示的輻輳通知）と次世代トランスポート QUIC

古典的な TCP Tahoe / Reno は「パケットが廃棄されて初めて混雑に気づく（暗黙の通知）」設計ですが、現代のインターネットではさらに次の2つの大きな進化が起きています。

1. **ECN（Explicit Congestion Notification：明示的輻輳通知・RFC 3168）：**
    途中のルータが「出力キューが 50% 以上埋まって混雑し始めた」と検知したとき、パケットを**廃棄して再送させる代わりに**、IP ヘッダの 2 ビットの ECN フィールドに **「混雑発生（CE：Congestion Experienced）」の印** を付けてそのまま宛先へ届けます。受信ホストは ACK の TCP ヘッダ（`ECE`：ECN-Echo ビット）で送信側へ混雑を知らせ、送信側は**パケットを1個も失うことなく**事前に `cwnd` を引き下げられます。

2. **QUIC（RFC 9000：HTTP/3 のトランスポート基盤）：**
    TCP は 1980年代からの遺産として OS カーネル内に固定されており、現代の Web やモバイル環境（Wi-Fi と 5G の切り替え等）で深刻な構造的制約が顕在化しました。Google が開発し IETF で標準化された **QUIC** は、**UDP の上に「信頼性・輻輳制御・TLS 1.3 暗号化・複数ストリーム多重化」を一体設計した次世代トランスポートプロトコル**です（図7-3-3）。

    * **接続遅延の大幅な短縮（1 RTT / 0 RTT）：** 従来の `TCP (3-way) + TLS (暗号)` では接続確立に 2 RTT（TLS 1.2 では 3 RTT）かかっていましたが、QUIC はトランスポートと TLS 1.3 のハンドシェイクを統合し、初回 **1 RTT**、再接続時は **0 RTT**（最初の1発目から暗号化済み HTTP リクエストを送信）を実現します。ただし、0-RTT データはサーバ側で新鮮な乱数交換を完了する前に送られるため、攻撃者がパケットを複製して再送する **リプレイ攻撃** のリスクを伴います。そのため 0-RTT で送る処理は、何度再実行されても状態が変わらない **べき等なリクエスト（`GET` による閲覧等）** に限定するのが原則です。
    * **トランスポート層での HoL（Head-of-Line）ブロッキング解消：** 1本の TCP 接続の上で複数ファイル（HTML・画像・CSS）を同時転送（HTTP/2）しているとき、**1パケット紛失するだけで TCP のバイトストリーム全体が再送完了まで停止し**、無関係な別ファイルの配信まで待たされます（HoL ブロッキング）。QUIC は 1 本の接続の中に**互いに独立した複数ストリーム**を持つため、ストリーム A のパケットが1個紛失しても、ストリーム B や C は一切止まらずそのまま受信・描画できます。
    * **コネクションマイグレーション（Connection Migration）：** TCP は 5 つ組（IP アドレスとポート）で接続を識別するため、スマホが玄関を出て Wi-Fi から 5G へ切り替わって IP アドレスが変わった瞬間に全 TCP 接続が切れます。QUIC は IP ではなくパケットヘッダ内の **接続 ID（Connection ID）** でセッションを識別するため、IP が変わっても通話やダウンロードを途切れさせずに継続できます。

### 4. 限界と補正（Critique & Adaptation）

#### (1) 損失ベース輻輳制御（Reno）の 3 つの限界と CUBIC・BBR への進化

TCP Reno はインターネットを何十年も支えましたが、現代の高速光回線や無線網では次の3つの限界が深刻化しました。

1. **高速・長距離回線での回復の遅さ：** 3-(3)の Mathis の式で見た通り、10 Gbps・RTT 100 ms の回線では `cwnd` が数万 MSS にも達するため、1回のロスで半減してから $+1\text{ MSS / RTT}$ の線形増加で元の速度へ戻るのに**数十分**かかってしまいます。

    * **補正（TCP CUBIC：Linux / Windows / macOS の現代標準）：** ウィンドウの増加関数を RTT 回数ではなく**直近のロスからの実経過時間 $t$ の 3 次関数（Cubic 関数）** に変え、ロス直後は急速に元の最高点付近まで回復し、最高点付近では慎重に平らに探り、それを超えたら再び急上昇させることで、高速・長距離回線での回復速度と異なる RTT 間の公平性を大きく改善しました。

2. **Bufferbloat（バッファ肥大化による高遅延）：** 現代の家庭用ルータや携帯電話網はメモリが安くなったため、巨大な出力バッファを積んでいます。Reno や CUBIC のような**損失ベース（Loss-based）**のアルゴリズムは「キューが満杯になってパケットが落ちるまで速度を上げ続ける」ため、巨大なバッファを常に 100% 満タンに詰まらせたまま通信し続け、**帯域は出ているのに RTT（遅延）が数百ミリ秒〜数秒へ跳ね上がる（Bufferbloat）** 現象を引き起こします。
3. **無線パケットロスの誤認：** Wi-Fi や 5G では、ルータがまったく混雑していなくても電波干渉でランダムにパケットが落ちます。損失ベースの TCP はこれを「輻輳だ」と誤認して不要に速度を半減させてしまいます。

    * **補正（BBR：Bottleneck Bandwidth and Round-trip propagation time）：** Google が開発した **BBR** は、パケット紛失を合図にするのをやめ、送信側が「現在のボトルネック帯域幅（BtlBw）」と「キューが空のときの最小伝搬遅延（RTprop）」を継続的に実測推定し、**ちょうどパイプを満たしつつルータのキューを溜めない最適な送信レート（ペーシング）** を直接維持します。これにより、Bufferbloat と無線ロス誤認の両方を大きく改善しています。

#### (2) QUIC の新たな課題（UDP 処理コストとネットワーク運用の可視性）

QUIC は優れた次世代プロトコルですが、実運用では次の2つのトレードオフが伴います。

* **CPU 負荷の増加：** TCP は数十年の歴史の中で NIC ハードウェア側での分割・結合オフロード（TSO / GRO）が高度に最適化されていますが、ユーザ空間で動く UDP ベースの QUIC はシステムコール回数や暗号化負荷が高くなりやすいです（補正：カーネルと NIC で複数 UDP パケットを一括分割・結合する Linux の `UDP GSO` / `GRO` や、1回のシステムコールで複数パケットをまとめて送る `sendmmsg` バッチ処理によって高速化します）。
* **ヘッダの暗号化と運用監視：** QUIC はパケット番号や ACK を含むトランスポート層の制御情報までほぼすべて暗号化するため、悪意ある監視やミドルボックスの干渉を防げる反面、企業ネットワークのトラブルシューティング（遅延やロス原因の切り分け）が難しくなる側面もあります。

> **【確認の問い】**
>
> 1. **（TCP Tahoe vs TCP Reno の 3 RTT 送信量比較と実効送信ウィンドウ）**
>     TCP 接続において `cwnd = 12 MSS` に達した直後の時点で **3 重重複 ACK** が発生したとします（`1 MSS = 1,460 B`）。
>
>     * (a) 受信ウィンドウ `rwnd` が十分大きいものとするとき、ロス検知直後に設定される `ssthresh`、およびロス検知直後の新しい `cwnd` による送信を 1 RTT 目として続く 2 RTT 目・3 RTT 目の **計 3 RTT 分の送信可能セグメント数** を、**TCP Tahoe** と **TCP Reno**（簡略モデル：高速リカバリ直後に `cwnd = ssthresh` へ移行し以降 $+1\text{ MSS/RTT}$）でそれぞれ計算して比較してください。
>     * (b) 上記 TCP Reno の 3 RTT 目（`cwnd = 8 MSS`）の時点で、受信ホストから通知された空きバッファ容量が `rwnd = 8,760 B` だったとします。この瞬間に送信側が未確認のまま回線上へ送り出せる実効送信ウィンドウ $W = \min(\text{rwnd}, \text{cwnd})$ をバイト数および MSS 単位で求めてください。
>
> 2. **（Bufferbloat と QUIC / HTTP/3 の構造診断）**
>     次の 2 つの運用上の現象について説明してください。
>
>     * (a) 巨大な出力バッファを持つルータ経由で損失ベース TCP（Reno / CUBIC）のダウンロードを行うと、スループットは出ているのに同時に行う音声通話や Web 応答の遅延が数百ミリ秒へ悪化する現象が起きます。この現象の名称と発生メカニズムを述べ、**ECN** および **BBR** がそれぞれどう改善するかを説明してください。
>     * (b) スマートフォンが Wi-Fi から 5G へ切り替わったとき、およびパケット損失率 1% の回線で複数ファイル（HTML・CSS・画像）を 1 本の接続上で同時取得するとき、従来の **TCP（HTTP/2）** と **QUIC（HTTP/3）** では挙動がどのように異なるでしょうか（「5 つ組と Connection ID」「単一ストリームと独立ストリーム」の観点から答えてください）。
>
> 3. **（AIMD の収束座標計算と高利用率リンクでのキュー滞留）**
>     帯域容量 $100\text{ Mbps}$ のボトルネックリンクを、同一 RTT の 2 つのフロー A・B が共有しており、初期レートが $(A, B) = (90, 10)\text{ Mbps}$ であるとします。
>
>     * (a) 初期状態 $(90, 10)$ で 1 回目の輻輳損失が起きて両者が $\times 0.5$ に半減し、その後は合計が $100\text{ Mbps}$ を超過するまで 1 ステップごとに両者 $+10\text{ Mbps}$ ずつ増加して再び超過した瞬間に 2 回目の半減が起きるものとします。**1 回目の半減直後**、**2 回目の超過発生時**、および **2 回目の半減直後** の座標 $(A, B)$ と両者のレート差 $\vert A - B \vert$ をそれぞれ計算してください。
>     * (b) このように複数フローがリンク容量 $100\text{ Mbps}$（利用率 $100\%$ 付近）に迫るまで送信を続けると、ルータの出力バッファには何が起き、エンドツーエンドの遅延（RTT）はどう変化するでしょうか。平均到着率とリンク処理能力のバランスの観点から簡潔に説明してください。
