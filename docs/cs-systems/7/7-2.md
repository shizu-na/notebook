### 前節（7-1）の確認問題の解答

前節の最後に提示した3つの問いの解答を確認します。問3がそのまま本節（TCPコネクション管理とスライディングウィンドウ）の導入になります。

1. **広帯域リンクにおける ARQ 3 方式の伝送効率と必要シーケンス番号ビット幅（$R = 100\text{ Mbps},\; \text{RTT} = 20\text{ ms},\; L = 1{,}250\text{ B} = 10{,}000\text{ bit}$）：**

    * **(a) 伝送遅延 $T_{\text{trans}}$、パラメータ $a$、$p = 0$ 時の効率と $W_{\min}$：**

        $$T_{\text{trans}} = \frac{10{,}000\text{ bit}}{10^8\text{ bit/s}} = \mathbf{0.1\text{ ms}}, \qquad a = \frac{T_{\text{prop}}}{T_{\text{trans}}} = \frac{10\text{ ms}}{0.1\text{ ms}} = \mathbf{100}$$

        したがって $1 + 2a = \mathbf{201}$ となり、誤り率 $p = 0$ のときの値は次の通りです。

        * **Stop-and-Wait：** $U_{\text{SW}} = \dfrac{1}{1 + 2a} = \dfrac{1}{201} \approx \mathbf{0.00498}$（約 **$0.50\%$**、実効スループット約 $0.50\text{ Mbps}$）となります。
        * **パイプライン型の最小ウィンドウサイズ：** 利用率 $100\%$（$U = 1$）を満たすには $W \ge 1 + 2a$ が必要なため、**$W_{\min} = 201$ フレーム** です。

    * **(b) 誤り率 $p = 0.01$ 時の性能比較と必要最小シーケンス番号ビット幅 $k$：**

        * **Selective Repeat：** $U_{\text{SR}} = 1 - p = 1 - 0.01 = \mathbf{0.99}$（**$99\%$**）です。
        * **Go-Back-$N$：** $U_{\text{GBN}} = \dfrac{1 - p}{1 + 2ap} = \dfrac{0.99}{1 + 2 \times 100 \times 0.01} = \dfrac{0.99}{3} = \mathbf{0.33}$（**$33\%$**）です。わずか $1\%$ のパケット損失であっても、GBN は $2ap = 2$ の再送ペナルティにより SR のちょうど $1/3$ まで効率が低下します。
        * **必要最小シーケンス番号ビット幅 $k$（$W = 201$）：**

            * **Go-Back-$N$：** $W \le 2^k - 1 \implies 2^k \ge 202$ であり、$2^7 = 128 < 202 \le 256 = 2^8$ より **$k = 8$ ビット**（最大 $255$）が必要です。
            * **Selective Repeat：** $W \le 2^{k-1} \implies 2^k \ge 402$ であり、$2^8 = 256 < 402 \le 512 = 2^9$ より **$k = 9$ ビット**（最大 $256$）が必要です。

2. **Selective Repeat のラップアラウンド破綻トレースと UDP / TCP の逆多重化比較：**

    * **(a) $k = 3$（番号 `0`〜`7`）、$W = 5$ でのラップアラウンド誤認トレース：**
        送信側が `0, 1, 2, 3, 4` を送信して受信側がすべて正常受理すると、受信側の待機ウィンドウは 5 枠ぶん前進して **`[5, 6, 7, 0, 1]`** になります。ところが `ACK 0`〜`ACK 4` がすべて紛失したため、送信側はタイムアウトして **古いパケット `0`** を再送します。受信側の新しい待機ウィンドウ `[5, 6, 7, 0, 1]` の中に番号 `0`（および `1`）が含まれてしまっているため、受信側は古い再送パケット `0` を一周回ってきた **新しいパケット `0` と誤認して受理** し、データ破損が起きます（$W + W = 10 > 8 = 2^3$ であるため重なりが生じます）。

    * **(b) UDP（2 つ組）と TCP（5 つ組）の逆多重化の違い：**
        **UDP** はコネクションレスであり、サーバ側ソケットは基本的に **`(宛先IP, 宛先ポート)` の 2 つ組** で識別されるため、クライアント A・B のどちらから届いたデータグラムも同じ 1 個のサーバソケットへ渡されます。一方 **TCP** はコネクション指向であり、OS は **`(プロトコル, 送信元IP, 送信元ポート, 宛先IP, 宛先ポート)` の 5 つ組** で識別するため、クライアント A 用とクライアント B 用にそれぞれ別々の接続済みソケットへ振り分けられます。

3. **2-way ハンドシェイクにおける遅延重複 `SYN` の危険性（本節への接続）：**
    サーバは遅れて届いた過去の `SYN` パケットを「新しい接続要求」とみなして `SYN+ACK` を返し、そのまま一方的に接続確立状態へ移行してメモリ（バッファや接続管理状態）を確保したままデータを待ち続けます。一方、クライアント側はその古い要求をすでに完了・破棄しているため接続を開いておらず、応答を無視または異常とみなします。結果として、サーバ側だけが片側で接続を開き続けて資源を占有する **半開接続（幽霊コネクション）** が発生します。これを防ぐためにクライアント側からの第 3 の確認応答を待つ **3-way ハンドシェイク** が、本節の主題となります。

## 7-2. TCPコネクション管理（3-way handshake・二つの軍隊問題）とスライディングウィンドウ

### 1. 動機（Why）：なぜ「接続の開始・終了」と「再送タイミング」がこれほど繊細なのか

前節（[7-1節](7-1.md)）では、パケットを連続投入して広帯域回線を使い切る ARQ（Go-Back-$N$ と Selective Repeat）の理論を学びました。しかし、現実のインターネット上で **TCP（Transmission Control Protocol）** を動かすには、ARQ の基本モデルだけでは片付かない3つの実務的な難題を解決しなければなりません。

1. **不確実な通信路での合意形成の限界：**
    パケットがいつ途中で消えるか分からない IP 網の上で、クライアントとサーバが「今からこの初期番号で通信を始めよう」「すべてのデータが届いたので綺麗に終了しよう」と互いに合意するには、何回メッセージを送ればよいのでしょうか。実は分散システム理論において、**「有限回のメッセージ交換で 100% 確実な同時合意は原理的に不可能である（二つの軍隊問題）」**ことが証明されています。TCP はこの理論的限界とどう折り合いをつけているのでしょうか。

2. **「パケット番号」ではなく「バイト単位のストリーム」の実装：**
    TCP は [5-3節](../5/5-3.md)のソケット API（`read`/`write`）へ「区切りのない連続したバイト列（バイトストリーム）」を提供します。実際の TCP は、GBN と SR の長所を組み合わせた **バイト単位のスライディングウィンドウ** として実装されています。

3. **ネットワーク遅延（RTT）の激しい変動：**
    再送タイマ（RTO）が短すぎると、まだ相手に届いている途中の正常パケットを早合点して無駄に再送してしまい、逆に長すぎると本当に紛失したときに通信が何秒も止まります。経路や混雑によって刻々と変わる RTT へ自律的に追従する仕組みが必要です。

本節では、まず **二つの軍隊問題** で合意の理論限界を確かめたうえで、TCP の **3-way ハンドシェイクと 4-way 切断（`TIME_WAIT`）**、**バイト単位のスライディングウィンドウと高速再送**、そして **適応的 RTT 推定** の仕組みを整理します。

---

### 2. 具体例と動作イメージ（Toy Model）

プロトコルの詳細に入る前に、2つの小さな例で「なぜ完全合意が不可能なのか」と「TCP のバイト単位シーケンス番号の進み方」を確かめます。

#### 実験A：二つの軍隊問題（Two-Army Problem / Two Generals' Problem）

深い谷を挟んだ左右の丘に、味方の**青軍 A** と **青軍 B** が陣取っており、谷底には敵の**赤軍**がいます。A と B が**まったく同じ時刻に同時攻撃**すれば勝利できますが、片方だけで攻撃すれば全滅してしまいます。連絡手段は、敵の谷底を駆け抜ける伝令（パケット）だけであり、伝令は途中で敵に捕まる（パケット紛失）かもしれません。

1. A が「明朝 6 時に攻撃する」と伝令を送ると、運よく B へ届きます。しかし **A には伝令が無事に着いたか分からない**ため、A は攻撃に踏み切れません。
2. B が「了解した（ACK）」と伝令を返すと、運よく A へ届きます。これで A は安心しますが、今度は **B に自分の「了解」が A へ届いたか分からない**ため、B が攻撃に踏み切れません。
3. A が「了解を受け取った（ACK の ACK）」と返しても、今度は A にそれが届いたか分かりません。

たとえ 100 回往復しても、**「最後にメッセージを送った側」は常にそれが相手へ届いたことを確信できない**ため、有限回のやり取りで「100% 確実に両者が合意するプロトコル」は数学的に存在しません（1975年 Akkoyunlu ら、1978年 Jim Gray による定式化）。

したがって TCP は、「100% の理論的同時合意」を追い求めるのではなく、**「タイムアウトと再送、および十分な待機時間（`TIME_WAIT`）を組み合わせることで、実用上問題ない十分に高い確率で整合を保つ」**という現実的な工学解をとっています。

#### 実験B：TCP のバイト単位シーケンス番号と累積 ACK の手計算

TCP のシーケンス番号（`Seq`）は「何番目のパケットか」ではなく、**「そのセグメントの先頭データバイトが、ストリーム全体の中で何バイト目か」**を表します。確認応答番号（`Ack`）は **「相手から次に受け取ることを期待しているバイト番号（＝その1つ前まではすべて正常に届いた）」** を表します。

クライアントが初期番号 `Seq = 1000` から順に、100 バイトのデータ（バイト `1000`〜`1099`）と 50 バイトのデータ（バイト `1100`〜`1149`）を2セグメント連続送信したとします。

1. セグメント1：`Seq = 1000`, `Len = 100`（バイト `1000..1099` を運ぶ）
2. セグメント2：`Seq = 1100`, `Len = 50`（バイト `1100..1149` を運ぶ）

サーバが両方とも正常に受信すると、サーバは **`Ack = 1150`**（「1149 バイト目まですべて揃った。次は 1150 バイト目を送れ」）と返信します。もしセグメント1だけが途中で紛失してセグメント2だけが先に届いた場合、サーバはセグメント2を捨てずに受信バッファへ一時保存しつつ、まだ欠けている先頭位置を指す **`Ack = 1000`** を返して「1000 番から先がまだ来ていない」ことを送信側へ知らせます。

### 3. 構造・アルゴリズム・実装（What）

#### (1) 3-way ハンドシェイク（接続確立）と ISN のランダム化

TCP コネクションを開始するとき、クライアント（能動オープン）とサーバ（受動オープン：`listen` 状態）は、次の **3 回のメッセージ交換（3-way ハンドシェイク）** を行います（図7-2-1左）。

1. **第1波 `SYN`（クライアント → サーバ）：**
    制御ビット `SYN = 1` を立て、クライアントが選んだランダムな初期シーケンス番号（**ISN**：Initial Sequence Number）`Seq = x` を通知します。クライアントは `SYN_SENT` 状態へ移ります。

2. **第2波 `SYN + ACK`（サーバ → クライアント）：**
    サーバは接続を受け入れると、`SYN = 1, ACK = 1` を立て、サーバ自身のランダムな初期番号 `Seq = y` と、クライアントの `SYN` を確認したことを示す **`Ack = x + 1`** を返します（`SYN` フラグ自身もシーケンス番号を仮想的に 1 バイト分消費する約束です）。サーバは `SYN_RCVD` 状態へ移ります。

3. **第3波 `ACK`（クライアント → サーバ）：**
    クライアントはサーバの `SYN` を確認する **`Ack = y + 1`**（`Seq = x + 1`）を返して **`ESTABLISHED`（接続確立）** 状態へ移ります。サーバもこの第3波を受け取った瞬間に `ESTABLISHED` 状態になり、[5-3節](../5/5-3.md)の `accept()` が返って双方向データ通信が始まります。

この3段階構造によって、ネットワーク上に長く滞留した古い接続要求（遅延重複 `SYN`）が後からサーバへ届いても安全に処理できます。サーバが古い `SYN` に応じて `SYN+ACK` を返したとしても、クライアント側には対応する接続要求が存在しないため、第3波の `ACK` ではなく **`RST`（Reset：異常・強制切断フラグ）** を返送します。`RST` を受け取ったサーバは直ちにその半開き接続を破棄できるため、2-way 方式のような不要な接続確立を防げます。

ここで、**ISN（`x` と `y`）を毎回 `0` から始めず暗号学的にランダムな 32 ビット値にする理由**は2つあります。第1に、古い接続の迷子パケットが新しい接続の有効な番号範囲へ誤って一致するのを防ぐためです。第2に、もし ISN が予測可能だと、盗聴していない第三者の攻撃者が送信元 IP を偽装して正しい `Ack` 番号を当てずっぽうで当て、コネクションを乗っ取る（**TCP シーケンス番号予測攻撃**）ことが可能になるため、予測不能な乱数化が必須となります。

#### (2) 4-way ハンドシェイク（全二重切断）と `TIME_WAIT`（2MSL）の 2 つの理由

TCP は双方向に独立してデータを流せる **全二重（Full-Duplex）** 通信です。そのため切断するときも、「クライアント → サーバ方向（送り終わった）」と「サーバ → クライアント方向（送り終わった）」を **それぞれ独立に閉じる（ハーフクローズ可能）** ため、原則 **4 回のやり取り（4-way ハンドシェイク）** になります（図7-2-1右）。

1. **第1波 `FIN`（クライアント → サーバ）：** 「こちらから送るデータは終わった」と宣言します（`FIN_WAIT_1`）。なお、`FIN` フラグも `SYN` フラグと同様にシーケンス番号を仮想的に 1 バイト分消費する約束になっているため、直後の確認応答は `Ack = u + 1` となります。
2. **第2波 `ACK`（サーバ → クライアント）：** サーバが `FIN` を確認します（サーバは `CLOSE_WAIT`、クライアントは `FIN_WAIT_2`）。この間、**サーバからクライアントへの残りデータ送信はまだ続けられます**。
3. **第3波 `FIN`（サーバ → クライアント）：** サーバ側も送り終えて `close()` を呼ぶと `FIN` を送ります（`LAST_ACK`）。この `FIN` も同様に 1 バイト分のシーケンス番号を消費します。
4. **第4波 `ACK`（クライアント → サーバ）：** クライアントが最後の `ACK` を返して **`TIME_WAIT`** 状態へ入り、サーバは `ACK` を受け取って `CLOSED` になります。

ここで、最初に `FIN` を送った側（能動クローズ側）が、最後の第4波 `ACK` を送った直後にすぐ `CLOSED` にならず、**$2 \times \text{MSL}$（MSL：Maximum Segment Lifetime＝パケットがネットワーク上に生存し得る最大時間。RFC 9293 では MSL の目安を 2 分［$2\text{MSL} = 4$ 分］としており、Linux 実装では `TIME_WAIT` 期間である $2\text{MSL}$ を通常 60 秒固定としています）のあいだ `TIME_WAIT` 状態で居座り続ける**理由が重要です。

1. **最後の `ACK` 紛失時の再応答（二つの軍隊問題への実用解）：**
    もし第4波の `ACK` が途中で紛失すると、`LAST_ACK` 状態のサーバはタイムアウトして第3波の `FIN` を再送してきます。クライアントが `TIME_WAIT` で待っていれば、再送された `FIN` を受け取って最後の `ACK` をもう一度返し、サーバを綺麗に `CLOSED` へ導けます（もしクライアントが即座に消えていたら `RST` が返ってエラー終了してしまいます）。

2. **古い迷子パケットの新接続への混入防止：**
    同じ 5 つ組 `(TCP, SrcIP, SrcPort, DstIP, DstPort)` を使って直後に新しい接続が張られたとき、前の接続でネットワーク内を迷走していた古い遅延パケットが後から届くと、新しい接続のデータが破壊されます。$2\text{ MSL}$ 待つことで、古い接続のすべてのパケットがネットワーク上から消滅（TTL 切れ等）したことを保証してから同じ 5 つ組を再利用できるようにしています。

> **【コラム：SYN フラッド攻撃と、メモリを1バイトも使わずに防ぐ「SYN Cookie」】**
>
> 3-way ハンドシェイクの仕様には、1つだけ悪用されやすい急所があります。サーバが第1波の `SYN` を受け取って第2波 `SYN+ACK` を返した時点（`SYN_RCVD` 状態）で、サーバは「この半開き接続のシーケンス番号やオプション」を記憶するためのカーネルメモリ（**TCB：Transmission Control Block**）を消費します。
>
> 攻撃者が偽造したランダムな送信元 IP から毎秒何十万発もの `SYN` パケットを送りつけ、第3波の `ACK` を一切返さずに放置すると、サーバの半開き接続キュー（`SYN backlog`）が短時間で溢れ、正規のユーザが誰も接続できなくなる DoS 攻撃が成立します（**SYN フラッド攻撃**）。
>
> この攻撃に対する実用的な対策が、ダニエル・バーンスタインらが考案した **SYN Cookie** です。サーバのキューが溢れそうになると、サーバは **`SYN` を受け取っても TCB メモリを一切確保しません**。代わりに、クライアントの IP・ポート・**MSS（Maximum Segment Size：1 TCP セグメントで運べる最大データ長、標準イーサネットで約 1,460 B）**・時刻・サーバ秘密鍵から暗号学的ハッシュ（[7-7節](7-7.md)で詳述）を計算します。サーバはこの値を **サーバ側の初期シーケンス番号 `y`（クッキー）** として埋め込んだ `SYN+ACK` を返し、半開き接続の状態はメモリへ保持せず破棄します。本物のクライアントから第3波 `ACK (Ack = y + 1)` が返ってきたときだけ、サーバは `Ack - 1` が正しいクッキーかをハッシュ検証し、正当な場合のみ初めてメモリ（TCB）を確保して `ESTABLISHED` へ進めます。

#### (3) TCP スライディングウィンドウと高速再送（3重重複 ACK）

接続が確立（`ESTABLISHED`）したあとのデータ転送を支えるのが、**バイト単位のスライディングウィンドウ** です（図7-2-2）。送信側が一度に未確認のまま送り出せる幅 $W$ は、受信側の空きバッファ容量 **`rwnd`** とネットワーク混雑度に応じた **`cwnd`** の小さい方 $\min(\text{rwnd}, \text{cwnd})$ で決まります（詳細は[7-3節](7-3.md)）。TCP は [7-1節](7-1.md)で学んだ Go-Back-$N$（GBN）と Selective Repeat（SR）の**ハイブリッド設計**になっています。

* **送信側の4領域：**

    1. **送信済み・ACK 確認済み（`< SendBase`）：** 相手へ確実に届いた領域であり、送信バッファから解放できます。
    2. **送信済み・未確認（`SendBase .. NextSeqNum - 1`）：** 今まさに回線上を飛行中（In-flight）のバイト群であり、紛失に備えて送信バッファに保持し続けます。
    3. **送信可能（ウィンドウ内空き）：** ACK を待たずに直ちに送り出せる領域です。
    4. **ウィンドウ外：** 現在のウィンドウサイズ $W$ を超えるため、左端 `SendBase` が右へスライドするまで送信できません。

* **GBN 的な側面（累積 ACK と単一タイマ）：**
    受信側が返す基本の `Ack` は「連続して受信済みの末尾 $+ 1$」を示す**累積 ACK** です。また送信側は、全セグメントに個別タイマを持つのではなく、最古の未確認バイト `SendBase` に対する**1個の再送タイマ**だけを管理します。

* **SR 的な側面（順序外バッファリングと SACK）：**
    受信側は、順序が飛んで届いた後続セグメントを捨てずに**受信バッファへ保存**します。さらに現代の TCP では **SACK（Selective ACK：RFC 2018）オプション** を使い、ヘッダのオプション欄へ「`1000` は欠けているが、`1100..1250` はすでに受け取った」と明記することで、送信側が欠損セグメントだけを選択的に再送できるようにしています。

* **高速再送（Fast Retransmit：3重重複 ACK）：**
    もしセグメントが1個紛失したとき、再送タイマ（RTO：数百ミリ秒）が切れるまで待っているとスループットが大きく落ちます。そこで送信側は、**同じ `Ack` 番号（例：`Ack = 1000`）が初回に加えてさらに 3 回連続して返ってきた（合計 4 回＝3 重重複 ACK）** とき、「後続の 3 セグメントは相手に届いたのに `1000` 番だけが消えたに違いない」と即座に判断し、**タイマ満了を待たずに直ちに `1000` 番のセグメントを再送**します。

#### (4) 適応的再送タイマ（RTT 推定：Jacobson-Karels アルゴリズム）

TCP の再送タイムアウト時間（**RTO：Retransmission Timeout**）は、現在のネットワークの往復遅延（**RTT**）より少しだけ大きく設定する必要があります。しかしインターネットの RTT は、接続先が東京か米国かで数ミリ秒から数百ミリ秒まで異なり、同じ接続中でも混雑で刻々と変動します。

そこで TCP は、送信してから ACK が返るまでの実測値 **`SampleRTT`**（再送セグメントは初回と再送のどちらの ACK か区別できないため除外：Karn のアルゴリズム）をもとに、**指数加重移動平均（EWMA）** で平均 RTT（RFC 6298 では `SRTT`）と揺らぎ・偏差（RFC 6298 では `RTTVAR`）を毎回収束推定します（図7-2-3）。初回の実測値を得た時点では $\text{EstimatedRTT} = \text{SampleRTT}$、$\text{DevRTT} = \text{SampleRTT} / 2$ として初期化します（RFC 6298）。なお、標準仕様 RFC 6298 では `RTTVAR` を更新する際に更新**前**の `SRTT` を使う手順（$\text{RTTVAR} \leftarrow (1-\beta)\text{RTTVAR} + \beta\vert\text{SRTT} - \text{SampleRTT}\vert$ のあとで $\text{SRTT}$ を更新）が規定されており、下記の教科書表記（平均更新後に偏差を更新）とは更新順がわずかに異なります。

$$
\begin{aligned}
\text{EstimatedRTT} &= (1 - \alpha)\,\text{EstimatedRTT} + \alpha\,\text{SampleRTT} \qquad (\alpha = 0.125 = 1/8) \\
\text{DevRTT}       &= (1 - \beta)\,\text{DevRTT} + \beta\,\bigl|\text{SampleRTT} - \text{EstimatedRTT}\bigr| \qquad (\beta = 0.25 = 1/4) \\
\text{RTO}          &= \text{EstimatedRTT} + 4 \times \text{DevRTT}
\end{aligned}
$$

たとえば初回実測が $100\text{ ms}$（初期値 $\text{EstimatedRTT} = 100\text{ ms}$、$\text{DevRTT} = 50\text{ ms}$）のあと、2回目の実測で $\text{SampleRTT} = 120\text{ ms}$ が得られたとすると、教科書順では $\text{EstimatedRTT} = 0.875 \times 100 + 0.125 \times 120 = 102.5\text{ ms}$、$\text{DevRTT} = 0.75 \times 50 + 0.25 \times |120 - 102.5| = 41.875\text{ ms}$、$\text{RTO} = 102.5 + 4 \times 41.875 = \mathbf{270\text{ ms}}$ となります（更新前の `SRTT = 100 ms` を使う RFC 6298 順では `RTTVAR = 0.75 × 50 + 0.25 × |100 - 120| = 42.5 ms`、`SRTT = 102.5 ms`、`RTO = 272.5 ms` となります）。

* RTT が安定している有線網では $\text{DevRTT}$ が小さくなるため、$\text{RTO}$ が $\text{EstimatedRTT}$ のすぐ上に密着して紛失を素早く検知できます。
* RTT の揺らぎが大きい無線網や混雑時では $\text{DevRTT}$ が自動的に大きくなり、十分な安全マージン（$4 \times \text{DevRTT}$）を確保して早合点による不要な再送を防ぎます。
* もしタイムアウトが連続して発生した場合は、[6-3節](../6/6-3.md)の CSMA/CD と同じように **RTO を毎回 2 倍へ引き伸ばす（指数バックオフ）** ことで、混雑したネットワークへ再送パケットを追い打ちするのを防ぎます。

### 4. 限界と補正（Critique & Adaptation）

#### (1) 3-way ハンドシェイクの 1 RTT 遅延と TCP Fast Open / QUIC

クライアントとサーバが東京〜米国間（$\text{RTT} = 150\text{ ms}$）で通信するとき、TCP の 3-way ハンドシェイクだけで最初に丸々 **1 RTT（$150\text{ ms}$）** を消費し、その上に暗号通信 TLS（[7-7節](7-7.md)）のハンドシェイクを乗せると、最初の Web ページ 1 バイトを受け取るまでに $300\text{〜}450\text{ ms}$ も待たされます。

これに対する補正として、初回接続時にサーバから受け取った暗号クッキーを2回目以降の `SYN` パケットへ添えることで **`SYN` と同時にアプリデータを送り出す TCP Fast Open（TFO）** が提案されましたが、途中の古いルータやファイアウォールに遮断されやすく普及が限定的でした。そのため現代の Web（HTTP/3）では、UDP の上でトランスポートと暗号ハンドシェイクを統合して **1 RTT（再接続時は 0 RTT）** を実現する **QUIC（[7-3節](7-3.md)）** への移行が進んでいます。

#### (2) `TIME_WAIT` 枯渇問題と `SO_REUSEADDR`

`TIME_WAIT` は安全な切断に不可欠ですが、毎秒何千もの短い TCP 接続を開閉する Web サーバやリバースプロキシでは、実務上の有名な2つの問題を引き起こします。

1. **サーバ再起動時の `Address already in use` エラー：** サーバ側が能動クローズして直後に再起動し `bind(8080)` を呼ぶと、古い接続が `TIME_WAIT` でポート `8080` を掴んだままになっているため起動に失敗します。

    * **補正：** サーバのソケットへ **`SO_REUSEADDR`** オプションを設定し、`TIME_WAIT` 中のポートへの再 `bind` を許可するのがネットワークプログラミングの定番です。

2. **プロキシ等のエフェメラルポート枯渇：** クライアント側（プロキシ等）が同じバックエンドサーバ `(S, 80)` へ毎秒 1,000 回接続して自分から `close()` すると、60 秒間で $60{,}000$ 本の `TIME_WAIT` ソケットが溜まり、エフェメラルポート（約 $28{,}000$ 個）を使い切って新規接続できなくなります。

    * **補正：** 1本の TCP 接続を使い回す **HTTP Keep-Alive（持続的接続：[7-5節](7-5.md)）** やコネクションプールの活用、あるいはサーバ側から先に閉じる設計を避けることで緩和します。

#### (3) 高速網の拡張オプション（WSOPT・TSOPT）と Nagle＋遅延 ACK の相互作用

1980年代に設計された TCP ヘッダの固定長フィールドは、現代の高速網や対話型アプリで2つの実務的制約を生みます。

* **高速網での 16 ビット窓と 32 ビット番号の枯渇（WSOPT・TSOPT）：** 従来の 16 ビットウィンドウ欄（最大 $64\text{ KiB}$）では 1 Gbps〜10 Gbps 網の帯域遅延積を満たせません。そこで、3-way ハンドシェイク時にビットシフト倍率を合意する **ウィンドウ・スケール・オプション（WSOPT：RFC 7323）** が使われます。また、数秒で 32 ビットシーケンス番号が一周してしまう問題（PAWS：[7-1節](7-1.md)）には、各セグメントへ送信時刻を添える **タイムスタンプ・オプション（TSOPT）** を併用して古い迷子パケットを排除します。
* **Nagle アルゴリズムと遅延 ACK（Delayed ACK）の相互作用：** 1 バイトずつ送る非効率な小パケットの乱発を抑えるため、TCP 送信側には「未確認データが残っている間は小データを溜めてまとめて送る」**Nagle アルゴリズム** が実装されています。一方、受信側には「ACK だけをすぐ返さず最大 40〜200 ms 待って返答データへ相乗りさせる」**遅延 ACK** が実装されています。ところが `write()` を 2 回続けて呼んでから応答を待つパターンでは、「送信側は 1 発目の ACK が来るまで 2 発目を留保し、受信側は 2 発目が来るまで遅延 ACK タイマを待つ」というすれ違いが起き、毎回の応答に 40 ms 程度の余分な遅延が乗ります。この補正として、低遅延が重要な RPC や対話型アプリではソケットへ `TCP_NODELAY` を設定して Nagle を無効化します。

#### (4) スライディングウィンドウのサイズ $W$ を「いくつに設定すべきか」（次節への動機）

図7-2-2で見た通り、送信側スライディングウィンドウの幅 $W$ が大きいほど高いスループットが出ます。しかし、$W$ を無制限に大きくすると、次の **2つの場所が同時にパンク** します。

1. **受信ホストのメモリ溢れ：** 受信側アプリの `read()` が追いついていないのに送り続けると、受信 OS のソケットバッファが溢れてデータが捨てられます（これを防ぐのが受信側の空き容量 **`rwnd`** に合わせる **フロー制御**）。
2. **途中のルータのキュー溢れ：** 受信ホストに余裕があっても、途中の共有リンクに世界中の送信者が一斉に大きなウィンドウで流し込むと、ルータが渋滞崩壊を起こします（これを防ぐのが送信側が自律的に探る **`cwnd`** による **輻輳制御**）。

次節（[7-3節](7-3.md)）では、TCP のウィンドウサイズを決定する式 $W = \min(\text{rwnd},\; \text{cwnd})$ の核心である **フロー制御と輻輳制御、そして次世代 QUIC** を詳しく整理します。

### 5. 接続と展望（Bridge）：本節の内容が後半のどの部に繋がるか

1. **次節（[7-3節](7-3.md)：フロー制御と輻輳制御［スロースタート・AIMD・Tahoe/Reno・ECN・QUIC］）：**

2. **[第5部](../index.md#part-5)（[5-3節](../5/5-3.md)：ソケット `listen` / `accept`）との回収：**

### 理解度チェック（次節へ進む前の確認）

本節のバイト単位 ACK・SACK・`TIME_WAIT`・Nagle＋遅延 ACK・RTT 推定を確認し、次節（[7-3節](7-3.md)）へ繋ぐ問いを置きます。

> **【確認の問い】**
>
> 1. **（シーケンス番号・`Ack`・`rwnd`・SACK の実践トレース）**
>     TCP 接続の確立後、サーバの受信バッファ総容量は `4000 B`（初期状態は空で `rwnd = 4000`）であり、クライアントは `Seq = 1001` から 1 セグメントあたり **500 バイト** のデータを 3 セグメント連続送信しました（セグメント 1：`Seq = 1001, Len = 500`、セグメント 2：`Seq = 1501, Len = 500`、セグメント 3：`Seq = 2001, Len = 500`）。受信側アプリはこの間まだ `read()` を呼んでいないものとします。
>
>     * (a) セグメント 1（バイト `1001..1500`）が正常に到着した直後、サーバが返す `Ack` 番号と `rwnd` の値をそれぞれ答えてください。
>     * (b) 続いてセグメント 2（バイト `1501..2000`）が途中で紛失し、セグメント 3（バイト `2001..2500`）だけが先に到着しました。この時点でサーバが返す累積 `Ack` 番号と SACK オプションで通知する受信済み範囲を答えてください。また、その後セグメント 2 が再送されて到着した直後にサーバが返す累積 `Ack` 番号と `rwnd` の値を答えてください。
>
> 2. **（`TIME_WAIT` ポート枯渇と Nagle×遅延 ACK のデバッグ）**
>     次の 2 つの実務障害について原因と対処法を答えてください。
>
>     * (a) 単一のバックエンドサーバへ毎秒数千回の短い HTTP リクエストを中継するリバースプロキシで、プロキシ側から毎回 `close()` を呼ぶ設計にしたところ、数十秒後に新規接続が失敗し始めました。`TIME_WAIT`（$2\text{ MSL}$）とエフェメラルポート数の関係から原因を説明し、有効な対策を 1 つ挙げてください。
>     * (b) 小さなリクエストを `write()` 2 回に分けて送信して応答を待つ RPC アプリで、回線 RTT は 1 ms 未満なのに毎回の処理に約 40 ms の遅延が乗る現象が起きました。**Nagle アルゴリズム** と **遅延 ACK** の相互作用から原因を説明し、最も簡潔なソケットオプション設定を答えてください。
>
> 3. **（RFC 6298 に基づく RTT 推定とパケットロス検知イベントの意味）**
>     次の 2 つの問いに答えてください。
>
>     * (a) RFC 6298 の手順（初回実測 $R_1$ で $\text{SRTT} = R_1,\; \text{RTTVAR} = R_1 / 2$ と初期化し、2 回目以降は更新**前**の `SRTT` を使って $\text{RTTVAR} \leftarrow (1-\beta)\text{RTTVAR} + \beta\vert\text{SRTT} - R\vert$、続けて $\text{SRTT} \leftarrow (1-\alpha)\text{SRTT} + \alpha R$ を計算。$\alpha = 1/8,\; \beta = 1/4$、$\text{RTO} = \text{SRTT} + 4 \times \text{RTTVAR}$）に従い、サンプル RTT が $R_1 = 80\text{ ms} \to R_2 = 160\text{ ms} \to R_3 = 90\text{ ms}$ と観測されたときの、$R_2$ 更新直後および $R_3$ 更新直後の `RTTVAR`・`SRTT`・`RTO` をそれぞれ計算してください。
>     * (b) パケット紛失を検知する 2 つの契機である「**3 重重複 ACK**」と「**RTO タイムアウト**」を比較したとき、なぜタイムアウトの方がネットワークの輻輳が深刻であると推定できるのか説明してください。
