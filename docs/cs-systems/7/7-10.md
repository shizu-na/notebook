### 前節（7-9）の確認問題の解答

前節の最後に提示した3つの問いの解答を確認します。問3がそのまま本節（Web 認証・認可の仕組み）の導入になります。

1. **標本化定理・エイリアシングと PCM ビットレート計算：**

    * **(a) 標本化定理の条件とエイリアシングの対策：**
        最高周波数 $f_{\max} = 4\text{ kHz}$ の音声を完全に復元するには、ナイキスト＝シャノンの標本化定理よりサンプリング周波数が **$f_s > 2 f_{\max} = 8\text{ kHz}$** である必要があります。$f_s = 10\text{ kHz}$ のときナイキスト周波数は $f_N = 5\text{ kHz}$ であり、これを超える $7\text{ kHz}$ の高周波成分が混入すると、$5\text{ kHz}$ を境に低周波側へ折り返して偽の信号（$10 - 7 = 3\text{ kHz}$ の偽音）が生じる **エイリアシング（折り返し雑音）** が発生します。対策として、標本化の直前に $f_s / 2$ 以上の高周波を遮断する**アンチエイリアシングフィルタ（ローパスフィルタ）**を通します。

    * **(b) $48\text{ kHz}$・$16\text{ bit}$・ステレオ・60 秒の未圧縮 PCM：**

        * **ビットレート：** $48{,}000 \times 16 \times 2 = 1{,}536{,}000\text{ bit/s} = \mathbf{1.536\text{ Mbps}}$。
        * **60 秒間のデータ量：** $1{,}536{,}000\text{ bit/s} \times 60\text{ s} \div 8 = 11{,}520{,}000\text{ B} = \mathbf{11.52\text{ MB}}$（$1\text{ MiB} = 2^{20}\text{ B}$ 換算では約 $10.99\text{ MiB}$）。

2. **JPEG パイプラインと動画 I / P / B フレームの設計トレードオフ：**

    * **(a) JPEG で情報が削減される段階とジグザグ走査の役割：**

        * **① 情報が不可逆的に削減される段階：** 第 1 段階の色空間変換に付随する **クロマサブサンプリング（4:2:0 間引き）** と、第 3 段階の **量子化（$\text{round}(F / Q)$ による丸め・高周波の 0 化）** です（DCT 自体は可逆変換です）。
        * **② ジグザグ走査の役割：** 量子化後の $8 \times 8$ 行列では左上の低周波に非ゼロ係数が集まり、右下の高周波には大量の `0` が並びます。左上から右下へ斜めにジグザグ順で 1 次元配列化することで、非ゼロを先頭に集めつつ後半に長い連続した `0` の列を作り出せるため、後段の RLE（および終了記号 EOB）とハフマン符号による圧縮効率が大きく高まります。

    * **(b) 動画の B フレームと I フレーム間隔（GOP 長）のトレードオフ：**

        * **① リアルタイム通話で B フレームを無効化する理由：** B フレームは過去と**未来**の両方のフレームを参照して予測するため、復号するには未来のフレームが到着して復号されるまで待たなければならず、エンドツーエンド遅延が大きく増加するためです。
        * **② シーク応答速度と I フレーム間隔の関係：** P/B フレームは直前の参照フレームがなければ単独で復号できないため、シーク先が GOP の途中にあると、プレーヤーは必ず直前の **I フレーム（キーフレーム）** まで遡ってそこから目的位置までの全フレームを順に復号し直す必要があります。したがって I フレーム間隔が長すぎるとシークの応答が遅くなります。

3. **単純な `SHA-256(password)` による DB 保存の危険性（本節への接続）：**
    ① **同一パスワードの露出と事前計算表（レインボーテーブル）：** 同じパスワードを使う複数ユーザのハッシュ値が完全に一致してしまうため、誰か 1 人のパスワードが割れれば同じハッシュを持つ他ユーザも一斉に判明します。さらに攻撃者は頻出パスワード群の `SHA-256` 値をあらかじめ巨大な辞書表として計算しておけば、照合だけで即座に元のパスワードを特定できます。
    ② **SHA-256 の計算が速すぎること：** SHA-256 は本来ファイルや通信の高速な改ざん検知のために設計されており、現代の GPU を使えば毎秒数十億〜数百億回ものハッシュ試行（総当たり・辞書攻撃）が可能です。本節では、これらを防ぐ**ソルトとストレッチング**から、ログイン状態の維持・**OAuth 2.0 / OIDC**・**パスキー**まで、Web アプリケーション層の認証・認可の仕組みを体系的に解き明かします。

## 7-10. Web 認証・認可の仕組み（パスワード・セッション/JWT・OAuth/OIDC・パスキー）

### 1. 動機（Why）：TLS 1.3 で通信路を暗号化しても、なぜ「Web の認証と認可」の設計が難しいのか

[7-7節](7-7.md)で学んだ **TLS 1.3（HTTPS）** によって、ブラウザと Web サーバ間の通信路は盗聴・改ざん・サーバなりすましから強力に保護されました。しかし、HTTPS が守ってくれるのは「通信路」と「サーバ側の本人確認」までです。実際の Web サービスを安全に動かすには、アプリケーション層で次の **4 つの異なる課題** を解かなければなりません。

1. **本人確認の秘密（パスワード）をサーバ側でどう守るか：**
    万が一データベースが漏洩しても、攻撃者がユーザの元のパスワードを復元できない保存方法が必要です。

2. **ステートレスな HTTP（[7-5節](7-5.md)）の上で、ログイン済み状態をどう維持するか：**
    毎回のページ遷移でパスワードを再入力させるわけにはいきません。サーバ側で状態を覚える「セッション方式」と、クライアント側へ署名付き証票を持たせる「トークン（JWT）方式」のトレードオフを見極める必要があります。

3. **別サービスへの権限委譲を「パスワードを渡さずに」どう行うか：**
    家計簿アプリが銀行の明細を読み取ったり、新興サービスへ「Google でログイン」したりするとき、ユーザの Google パスワードそのものを外部アプリへ渡すわけにはいきません。

4. **人間が騙される「フィッシング詐欺」をどう根本から防ぐか：**
    どれだけ強力なパスワードと多要素認証（SMS コード等）を使っても、本物そっくりの偽サイト（`examp1e.com`）へユーザ自身が入力してしまえば突破されます。

ここで最初に、混同されがちな 2 つの専門用語を厳密に区別しておきます。

* **認証（Authentication：AuthN）：** 「あなたは**誰**ですか？」を確認するプロセス（本人確認：パスワード、パスキー、OpenID Connect 等）。
* **認可（Authorization：AuthZ）：** 「あなたに**何の操作を許す**か？」を決定するプロセス（権限付与：[5-7節](../5/5-7.md)のアクセス制御、OAuth 2.0 等）。

本節では、現代の Web サービスを支える認証・認可の 4 段階の設計（**パスワードハッシュ化・セッション vs JWT・OAuth 2.0 / OIDC・パスキー［WebAuthn］**）を順に整理します。

### 2. 具体例と動作イメージ（Toy Model）

プロトコルの詳細に入る前に、2 つの身近な比喩と具体例で「ソルトとストレッチング」および「OAuth 2.0 のホテルカードキーモデル」を直感的に掴みます。

#### 実験A：同じパスワード `"P@ssword1"` でも DB 上は別物にする（ソルト＋ストレッチング）

Alice と Bob が偶然まったく同じパスワード `"P@ssword1"` を設定したとします。

* **単純ハッシュ（危険）：** Alice も Bob も同じ `SHA-256("P@ssword1") = 8f4e...` が保存されます。
* **ソルト（Salt）の追加：** ユーザ登録時に、ユーザごとに暗号学的乱数で生成した**異なるランダム文字列（ソルト、16 バイト以上）**を混ぜてハッシュし、`(ソルト, ハッシュ値)` をセットで DB に保存します。

    * Alice：ソルト `s_A = "9a3f..."` $\implies$ ハッシュ `H("9a3f..." || "P@ssword1") = 3c10...`
    * Bob：ソルト `s_B = "7b02..."` $\implies$ ハッシュ `H("7b02..." || "P@ssword1") = e94a...`

    ソルト自体は DB に平文で保存して構いません。ユーザごとに値が異なるため、**同じパスワードでもハッシュ値が一致せず、事前のレインボーテーブル（共通辞書）が完全に無力化**されます。

* **ストレッチング（鍵導出関数：KDF）：** さらに 1 回のハッシュ計算をわざと **数万〜数十万回繰り返し**、1 回の検証に約 $50\text{〜}200\text{ ms}$ かかるように遅くします。正規ユーザがログインするときは $0.1\text{ 秒}$ 待つだけで気になりませんが、100 万通りの辞書攻撃を試みる攻撃者にとっては $100{,}000\text{ 秒}$（1 日以上）かかる計算壁になります。

#### 実験B：ホテルの「マスターキー」ではなく「限定カードキー」を渡す（OAuth 2.0 の直感）

写真プリントサービス（外部アプリ）が、あなたの Google フォトから写真を印刷したい状況を想像してください。

* **最悪の方法（パスワード共有）：** Google の ID とパスワードを写真アプリへ直接教えます。写真アプリは写真だけでなく、あなたの Gmail も決済情報もすべて操作できてしまい、しかも後から写真アプリだけの権限を取り消すには Google のパスワード自体を変えるしかありません。
* **OAuth 2.0 の方法（限定トークン委譲）：** あなたは Google の画面上で本人確認したうえで、「この写真アプリに対して、**写真の読み取り権限（`scope=photos.read`）だけ**を **1 時間だけ** 許可する」という専用の**アクセストークン（ホテルの 302 号室だけ開く期限付きカードキー）**を発行してもらいます。写真アプリはあなたのパスワードを 1 文字も知ることなく、許可された範囲の写真だけを取得できます。

### 3. 構造・アルゴリズム・実装（What）

#### (1) パスワードの安全な保存：ソルト・ストレッチング・メモリハード関数（Argon2id）

現代のパスワード保存では、`SHA-256` のような汎用高速ハッシュではなく、意図的に計算コストを高めた専用の **パスワードハッシュ関数（KDF：Key Derivation Function）** を使用します（図7-10-1左）。

* **PBKDF2 / bcrypt：** 暗号学的ハッシュ（HMAC-SHA256 や Blowfish 暗号）をソルト付きで何万〜何十万回も反復計算（ストレッチング）します。
* **scrypt / Argon2id（現代の第一推奨：PHC 2015 優勝アルゴリズム）：**
    近年の攻撃者は、CPU ではなく数千コアを持つ **GPU や専用 ASIC** を使って PBKDF2 を並列総当たり攻撃します。GPU は算術演算は高速ですが、**コアあたりの大容量 RAM は高価で乏しい**という物理的弱点があります。そこで **Argon2id** は、「時間コスト（反復回数）」に加えて **「1 回のハッシュ計算に数十 MiB の RAM をランダムアクセスさせる（メモリハード性：Memory-Hard）」** 設計を採り、GPU/ASIC による超並列解読を物理的に抑制します。

* **ペッパー（Pepper）による多層防御（任意）：**
    ユーザごとのソルト（DB に保存）に加えて、アプリケーション全体で共通の秘密鍵（**ペッパー**）を DB とは別の安全な領域（HSM や環境変数・シークレット管理基盤）に保持し、パスワードへ HMAC 等で混ぜてから KDF にかける設計もあります。万が一 SQL インジェクション等で DB のみが丸ごと漏洩しても、ペッパーがなければオフライン辞書攻撃自体を開始できません。

#### (2) ログイン状態の維持：ステートフルセッション vs JWT（JSON Web Token）

認証に成功したあと、後続の HTTP リクエストで「ログイン済みの Alice だ」と認識し続ける方式には、大きく次の 2 種類があります（図7-10-1右）。

1. **ステートフル・セッション方式（Cookie ＋ サーバ側セッションストア）：**

    * ログイン成功時、サーバは予測不能なランダム文字列（**セッション ID**：128 ビット以上の乱数）を生成し、`session_id → {user_id: 101, role: "admin", expires: ...}` を背後の **セッションストア（Redis や RDBMS）** へ保存します。
    * ブラウザへは `Set-Cookie: sid=...; HttpOnly; Secure; SameSite=Lax` でセッション ID だけを返します（[7-5節](7-5.md)）。
    * **強み：** サーバ側でセッションストアから 1 行削除するだけで、**即座にログアウト・強制失効（Revocation）** できます。
    * **弱み：** リクエストのたびにセッションストアへのネットワーク参照（1 往復）が発生します。

2. **ステートレス・トークン方式（JWT：JSON Web Token、RFC 7519）：**

    * サーバ側に状態を保存せず、ユーザ情報（クレーム）そのものを JSON にして **HMAC（HS256）または公開鍵デジタル署名（RSA：RS256、EdDSA 等。[7-7節](7-7.md)）** を付けたトークンをクライアントへ渡します。
    * JWT はピリオド（`.`）で区切られた 3 つの Base64URL 文字列で構成されます。

        ```text
        Header（署名アルゴリズム: HS256 / RS256 / EdDSA 等） . Payload（sub, role, exp 等） . Signature（Header+Payload への署名）
        ```

    * **重要：JWT の Payload は暗号化されておらず、単なる Base64URL エンコード（誰でもデコードして読める平文）です。** したがってパスワードや機密個人情報は決して Payload に入れてはならず、JWT が保証するのは「署名鍵を持つ認証サーバが発行し、途中で 1 文字も改ざんされていないこと（完全性・真正性）」です。
    * **強み：** 各マイクロサービス（API サーバ）は認証サーバの公開鍵さえ持っていれば、**中央の DB / Redis へ問い合わせずに手元の署名検証だけで即座にユーザと権限を検証** できます。
    * **弱み：** 一度発行した JWT は有効期限（`exp`）が切れるまで有効であり、**途中で強制失効させることが困難** です（対策は 4-(1) で整理します）。

#### (3) OAuth 2.0（認可の委譲）と OpenID Connect（認証の拡張）

実験Bの「パスワードを渡さずに特定範囲の権限だけを外部アプリへ委譲する」世界標準プロトコルが **OAuth 2.0（RFC 6749）** です。OAuth 2.0 には次の 4 つの登場人物（ロール）があります。

* **リソースオーナー：** データの持ち主であるユーザ本人。
* **クライアント：** 権限を借りたい外部アプリ（例：写真プリントサービス）。
* **認可サーバ（Authorization Server）：** ユーザを認証し、同意を得てトークンを発行するサーバ（例：Google アカウント基盤）。
* **リソースサーバ：** 保護された API（例：Google フォト API）。

現在、Web・モバイル・SPA のすべてで推奨される唯一の標準フローが **認可コードフロー ＋ PKCE（Proof Key for Code Exchange：RFC 7636）** です（図7-10-2）。

1. **認可要求（ブラウザ経由のフロントチャネル）：** クライアントは一時乱数 **`code_verifier`** を生成し、そのハッシュ **`code_challenge = SHA-256(code_verifier)`** と権限範囲 `scope`、CSRF 防止乱数 `state` を添えて、ブラウザを認可サーバへリダイレクトします。
2. **ログインと同意：** ユーザは認可サーバ自身の安全な画面でログインし、「写真アプリに写真読取を許可する」へ同意します。
3. **認可コード（`code`）の返却：** 認可サーバはブラウザをクライアントの事前登録済みコールバック URL へリダイレクトし、短命・1 回限りの **認可コード `code`** だけを返します（**アクセストークン自体は URL へ流しません**）。
4. **トークン交換（バックチャネル直接通信）：** クライアントはサーバ間通信（またはアプリ内部の直接 HTTPS POST）で、`code` と最初に作った元の乱数 **`code_verifier`**（および機密クライアントなら `client_secret`）を認可サーバへ送ります。認可サーバは `SHA-256(code_verifier) == code_challenge` を検証して一致すれば、**アクセストークン**（＋必要に応じリフレッシュトークン）を返します。

ここで重要なのが、**OAuth 2.0 はあくまで「認可（権限委譲）」のプロトコルであり、本来「認証（誰がログインしたか）」のプロトコルではない** という点です。OAuth 2.0 のアクセストークンは「写真を読む権利がある」ことは示しても、クライアントアプリに対して標準化された形式で「このユーザは誰か」を証明しません。

そこで、OAuth 2.0 の上に **「認証（AuthN）」の層を標準化拡張したものが OpenID Connect（OIDC）** です。「Google でログイン」などのソーシャルログインの実体は OIDC です。OIDC では `scope=openid` を指定することで、ステップ 4 の応答にアクセストークンと並んで、認可サーバがデジタル署名した **ID トークン（JWT 形式：`sub`［ユーザ一意 ID］、`iss`［発行者］、`aud`［対象クライアント］、`exp`、`nonce`）** が返されます。クライアントは ID トークンの署名を検証することで、ユーザの本人確認を安全に完了できます。

#### (4) パスワードレス認証の到達点：パスキー（WebAuthn / FIDO2）

パスワードと多要素認証（TOTP アプリや SMS）には、依然として **「リアルタイム・フィッシング（中間者型フィッシング）」に弱い** という根本的限界があります。偽の銀行サイト `examp1e.com` にユーザがパスワードと 6 桁のワンタイムコードを入力すると、裏側の攻撃者プロキシがそれを本物の `example.com` へ即座に転送してログインを乗っ取れてしまうからです。

これを暗号技術とブラウザの協調で根本から解決した現代のパスワードレス標準が **パスキー（Passkey：WebAuthn / FIDO2）** です（図7-10-3）。パスキーは [7-7節](7-7.md)で学んだ **公開鍵暗号のデジタル署名** と **チャレンジ応答認証** をそのまま Web 認証へ適用しています。

1. **登録時：** ユーザ端末の安全なハードウェア領域（TPM / Secure Enclave）が、接続先サイト（**RP ID：ドメイン名 `example.com`**）専用の **公開鍵・秘密鍵ペア** を自動生成します。秘密鍵は絶対に端末の外へ出ず、**公開鍵だけ** をサーバの DB へ登録します（サーバから DB が漏洩しても秘密鍵は盗まれません）。
2. **ログイン時（フィッシング耐性の核心）：**

    * サーバは毎回ランダムな **チャレンジ（乱数）** をブラウザへ送ります。
    * ユーザが指紋・顔認証で端末の秘密鍵をロック解除すると、**ブラウザ自身が現在のアドレスバーの正規オリジン（`https://example.com`）を自動的に署名対象データへ混ぜ込み**、秘密鍵でデジタル署名を生成して返します。
    * 仮にユーザが偽サイト `https://examp1e.com` に騙されて開いても、ブラウザは `examp1e.com` のオリジンを検出して **`example.com` 用の秘密鍵をそもそも使用しない**（仮に別鍵で署名してもオリジン不一致で本物サーバが拒否する）ため、フィッシング攻撃が構造的に成立しません。

> **【コラム：なぜ JWT をブラウザの `localStorage` に保存する設計は危険なのか】**
>
> SPA（Single Page Application）の開発で、ログイン後に受け取った JWT をブラウザの `localStorage` へ保存し、JavaScript から `Authorization: Bearer <JWT>` ヘッダへ載せて送る実装をよく見かけます。しかし、`localStorage` は同じオリジン上で動く**あらゆる JavaScript から読み取り可能**であるため、もしサイト内のたった 1 箇所（あるいは読み込んだ外部ライブラリ）に次節で学ぶ **XSS（クロスサイトスクリプティング）** の脆弱性があると、攻撃者のスクリプト 1 行で JWT が丸ごと盗まれてしまいます。
>
> これに対し、`HttpOnly`・`Secure`・`SameSite` 属性を付けた Cookie へトークン（あるいはセッション ID）を格納する設計（あるいはバックエンド側でトークンを保持する **BFF：Backend for Frontend** パターン）を使えば、JavaScript 自体がトークン文字列に触れられないため、トークン抜き取りのリスクを大きく下げられます。

### 4. 限界と補正（Critique & Adaptation）

#### (1) JWT の「失効不能」問題とリフレッシュトークン・ローテーション

ステートレス JWT の最大の弱点は、ユーザがログアウトしたり端末を紛失したりアカウントを凍結したりしても、**すでに発行済みの JWT が有効期限（`exp`）までそのまま通り続けてしまう** 点です。

* **補正（短命アクセストークン ＋ リフレッシュトークン・ローテーション）：**
    アクセストークン（JWT）の有効期限を **5〜15 分程度の極短時間** に抑え、期限が切れたら別の長命な **リフレッシュトークン** を認証サーバへ送って新しいアクセストークンを再発行してもらいます。リフレッシュトークン自体はサーバ側の DB / Redis で状態管理（失効可能）にし、さらに 1 回使うたびに古いリフレッシュトークンを無効化して新しいものへ差し替える（**ローテーション**）ことで、万が一トークンが盗まれて再利用された瞬間に不正を検知し、そのセッション系統全体を即座に失効させます。

#### (2) OAuth 2.0 実装の典型的な落とし穴

OAuth 2.0 は仕様が広く柔軟な分、実装の 1 箇所を省略するだけで重大なアカウント乗っ取りに繋がります。

1. **`state` パラメータの検証漏れ（ログイン CSRF）：** 攻撃者が自分の認可コードを被害者のブラウザへ踏ませ、被害者のブラウザを攻撃者アカウントへ強制ログインさせてしまう攻撃（補正：ランダムな `state` をセッションと紐付けてコールバック時に厳密照合する）。
2. **`redirect_uri` の曖昧な部分一致チェック（オープンリダイレクト）：** 認可サーバ側がコールバック URL を完全一致で検証しないと、攻撃者サイトへ認可コード `code` を横流しされます（補正：事前登録 URL との厳密な完全一致検証）。
3. **旧 Implicit フローの廃止：** かつて SPA で使われた「URL フラグメントへ直接アクセストークンを返す Implicit フロー」はブラウザ履歴やリファラからトークンが漏洩しやすいため、現在は **認可コードフロー ＋ PKCE** へ統一されています。また、JWT 署名検証で `alg: none`（署名なし）を受け入れてしまう古いライブラリの設定ミスにも注意し、検証側で許可する署名アルゴリズムを必ず明示固定します。

#### (3) 認証を通過した後に待ち受ける「ブラウザ側の脅威」（次節への動機）

ここまでの仕組みで、「誰が正規のユーザか」を安全に確認してトークンや Cookie を発行できるようになりました。ところが Web の世界では、**ユーザが正規にログインして有効な Cookie やセッションをブラウザに持っている状態** を狙い撃ちする攻撃（**XSS・CSRF・クリックジャッキング**）が次々と発生します。次節（[7-11節](7-11.md)）では、これら Web アプリケーションの代表的な脆弱性と、ブラウザ自身が持つ防御機構（**同一オリジンポリシー・CORS・CSP**）を解き明かします。

### 理解度チェック（次節へ進む前の確認）

本節のパスワード保存・セッション vs JWT・OAuth 2.0 / OIDC・パスキーの仕組みを確認し、次節（[7-11節](7-11.md)）へ繋ぐ問いを置きます。

> **【確認の問い】**
>
> 1. **（パスワード保存と JWT 設計のバグ診断）**
>
>     * (a) パスワード保存において、① **ユーザ固有のソルト** を混ぜることで防げる攻撃、および ② **Argon2id のようなメモリハードなストレッチング関数** を使うことで防げる攻撃を、それぞれ区別して説明してください。
>     * (b) ある Web サービスが、有効期限 30 日間の JWT の Payload に `{ "user_id": 42, "role": "user", "credit_card_last4": "1234" }` を入れて発行しました。この設計に潜む 2 つの問題点（① 機密情報の扱い、② 端末紛失・アカウント凍結時の即時失効）を指摘し、それぞれどのように修正すべきか答えてください。
>
> 2. **（OAuth 2.0 ＋ PKCE・OIDC・パスキーの仕組み比較）**
>
>     * (a) OAuth 2.0 の認可コードフローにおいて、① なぜ「認可（OAuth 2.0）」だけでなく「認証（OpenID Connect）」のために **ID トークン** が別途必要なのか、および ② **PKCE（`code_challenge` と `code_verifier`）** が「認可コード横取り攻撃」をどうやって防いでいるのかを説明してください。
>     * (b) 従来の「パスワード ＋ 6 桁の SMS ワンタイムコード」では防げないリアルタイム・フィッシング攻撃に対し、**パスキー（WebAuthn）** が構造的に強い理由を、ブラウザとオリジン（ドメイン名）の働きから説明してください。
>
> 3. **（次節への伏線：ブラウザの Cookie 自動送信とサイト間の隔離境界）**
>     ユーザが銀行サイト `https://bank.example` にログインし、ブラウザがセッション Cookie（`sid=...`）を保持したまま、別のタブで攻撃者の悪意あるサイト `https://evil.example` を開いたとします。もしブラウザにサイト間の保護制限が一切なかった場合、`evil.example` 上の HTML フォームや JavaScript を使って、攻撃者はユーザの銀行口座から勝手に出金したり残高を盗み見たりできてしまいます。ブラウザが「異なるサイト間のデータ読み取り」を遮断する基本ルールは何と呼ばれ、逆に「別サイトからのフォーム送信に Cookie が自動でくっついて送られてしまう」現象が悪用される攻撃は何と呼ばれるでしょうか。
