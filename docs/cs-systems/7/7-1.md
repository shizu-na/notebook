### 前節（6-8）の確認問題の解答

前節の最後に提示した3つの問いの解答を確認します。これで[第6部](../index.md#part-6)（リンク・IP とルーティング）が完結し、本節からは上位の[第7部](../index.md#part-7)（トランスポート層・トラヒック数理・応用と暗号）へ進みます。

1. **BGP ベストパス選択アルゴリズムの優先順位トレースとホットポテト：**

    * **(a) ループ破棄される経路と最終ベストパスの特定：**
        各比較ステップを上から順に適用します。

        1. **ループ検査（`AS_PATH` に自 AS 番号 `100` を含む経路の除外）：** **経路 1** は `AS_PATH = [200, 100, 400]` に自 AS 番号 `100` を含むため、`LOCAL_PREF = 200` であっても受信直後に**ループと判定されて即座に破棄**されます。
        2. **`LOCAL_PREF` 最大：** 残る 4 経路のうち経路 2（`100`）は経路 3・4・5（いずれも `150`）より小さいため脱落します（`AS_PATH` が短くても `LOCAL_PREF` が優先されます）。
        3. **最短 `AS_PATH`：** 経路 3・4・5 はいずれも通過 AS 数が `3` で同点となります。
        4. **最小 `MED`：** 経路 3・4・5 はいずれも同一の隣接 AS（`AS 200`）から受信した経路のため `MED` を比較でき、`MED = 20` の経路 3 が脱落して経路 4・5（`MED = 10`）が残ります。
        5. **最小 IGP コスト（ホットポテト）：** 経路 4（IGP コスト `15`）と経路 5（IGP コスト `4`）を比較し、最小の **経路 5（出口ルータ E2）** が最終ベストパスに確定します。

    * **(b) ホットポテトルーティングの経済的・運用上の狙い：**
        他社宛てのトラヒックを自社 AS 内の幹線網へ長く抱え込まず、最小の内部コストで最寄りの出口ルータから速やかに隣接 AS へ渡すことで、自社の内部帯域消費と運用コストを抑える狙いがあります。

2. **バレーフリー原則の違反検出と、2008 年 YouTube BGP ハイジャック・RPKI 防御：**

    * **(a) 経路 `[AS 3, AS 2, AS 1]` がバレーフリー原則に違反する理由と不利益：**
        企業 `AS 2` は `AS 1`・`AS 3` の双方に利用料を支払う顧客（マルチホーミング）であり、一方のプロバイダ（`AS 1`）から学んだ経路を他方のプロバイダ（`AS 3`）へ再広告すると、プロバイダ同士の通信を顧客である `AS 2` が中継（トランジット）する谷型の経路が生じ、バレーフリー原則に違反します。その結果、`AS 2` は他社の膨大なトラヒックを自社の有料回線で運ばされ、両 ISP へ高額な通信費を支払う不利益を被ります。

    * **(b) 2008 年 YouTube BGP ハイジャックの波及機序と RPKI による防御：**
        誤って外部 eBGP へ漏れ出した `/24` プレフィックスは、YouTube 本家が広告していた `/22` よりプレフィックス長が長かったため、世界中のルータが [6-5節](../6/6-5.md)の **最長プレフィックス一致（LPM）** に従って `/24` を最優先し、トラヒックがパキスタン側へ吸い込まれました。これを防ぐ **RPKI** では、IP アドレスの正当な所有者が「プレフィックスと正規の発信元 AS 番号の組」を電子署名した証明書（**ROA**）を公開し、各 ISP のルータが受信した BGP 広告を ROA と照合して不正経路を自動破棄（**ROV**）します。

3. **MPLS の TE / L3VPN と、エニーキャスト下での TCP 切断問題：**

    * **(a) MPLS-TE と L3 VPN を実現する仕組み：**

        * **MPLS-TE（トラヒックエンジニアリング）：** 入口の LER で明示的なラベル経路（**LSP**）を指定してコア LSR にラベルスワップ転送させることで、OSPF の最短経路 1 本へ集中するトラヒックを空いている別ルートへ計画的に分散します。
        * **L3 VPN：** コア網転送用の外側ラベルと顧客識別用の内側ラベルを重ねる **ラベルスタック**（`S` ビットで最下層を識別）を用いることで、プライベート IP アドレス帯が重複する複数企業のネットワークを 1 つのキャリア網上で安全に分離収容します。

    * **(b) エニーキャスト下で TCP 接続が `RST` 切断される理由（UDP との対比）：**
        TCP は送信元・宛先間の接続状態（シーケンス番号や接続情報）をサーバ側のメモリに保持するステートフルなプロトコルであるため、通信途中で BGP 経路が揺らいでパケットが東京拠点から大阪拠点へ切り替わると、大阪拠点のサーバはその接続状態を知らず即座にリセット（`RST`）を返して通信が切断されます。一方、1 往復で完結する UDP ベースの DNS 問い合わせはサーバ側で継続的な接続状態を持たないステートレス通信であるため、別の問い合わせが別拠点へ届いても問題が起きにくくなります。

## 7-1. トランスポート層（ポート・5つ組・UDP/TCP）とARQ 3方式の伝送効率

### 1. 動機（Why）：なぜ「ホスト間（IP）」の上に「プロセス間・信頼性（トランスポート層）」が必要なのか

[第6部](../index.md#part-6)（[6-1](../6/6-1.md)〜[6-8節](../6/6-8.md)）を通じて、送信ホストからイーサネット・Wi-Fi・L2 スイッチ・世界中の L3 ルータ（OSPF・BGP）を越えて、受信ホストまで IP パケットを届ける全構造が完成しました。

しかし、IP 層（第3層）が提供しているサービスには、アプリケーションを動かすうえでまだ不足している要素が **2つ** あります。

1. **宛先が「マシン（ホスト）」単位であり、「プロセス（アプリ）」単位ではない：**
    1台の PC の中では、Web ブラウザの複数のタブ、SSH 端末、メールソフト、オンライン通話アプリが同時にネットワークを使っています。受信ホストの OS カーネルへ IP パケットが届いたとき、「このパケットをどのプロセスのソケット（[5-3節](../5/5-3.md)）へ渡すべきか」を識別する仕組みが必要です。

2. **IP はベストエフォートであり、欠損・破損・順序逆転を直さない：**
    [6-1節](../6/6-1.md)で確認した通り、IP 網ではルータのバッファ溢れによるパケット廃棄、ノイズによるビット反転、別経路通過による順序逆転が日常的に起きます。ファイル転送や Web 閲覧では 1 バイトの欠損も許されませんが、かといって途中で消えるたびに「1個送っては返事を待つ」素朴な再送方式を使うと、広帯域・長距離の回線では帯域の 99% 以上が遊休になってしまいます。

この2つの課題をエンドツーエンド（両端のホスト OS 内部）で解決するのが **トランスポート層（第4層）** です。本節では、プロセス識別を支える **ポート番号と 5 つ組**、軽量な **UDP** と高機能な **TCP** の役割分担を押さえたうえで、信頼性通信の数学的土台である **ARQ（自動再送要求）3方式の動作と伝送効率** を導出します。

---

### 2. 具体例と動作イメージ（Toy Model）

仕様と数式に入る前に、2つの小さな具体例で「5つ組によるソケット識別」と「素朴な再送方式（Stop-and-Wait）が広帯域で破綻する理由」を確かめます。

#### 実験A：同じ Web サーバ（ポート 443）へブラウザのタブを 2 つ同時に開く

自分の PC（IP `192.168.1.10`）の Web ブラウザで、同じ Web サーバ（IP `93.184.216.34`、HTTPS ポート `443`）の別々のページを **2つのタブ（ソケット1 とソケット2）** で同時に開いたとします。

サーバから PC へ2つの返信パケットが届いたとき、どちらも「送信元 IP = `93.184.216.34`」「送信元ポート = `443`」「宛先 IP = `192.168.1.10`」までは同じです。PC の OS はどうやってタブ1宛てとタブ2宛てを区別するのでしょうか。

答えは、OS が接続開始時にクライアント側へ自動割り当てする **エフェメラル（一時）ポート番号** です。

* タブ1の接続：`(TCP, 192.168.1.10, 52001, 93.184.216.34, 443)`
* タブ2の接続：`(TCP, 192.168.1.10, 52002, 93.184.216.34, 443)`

宛先ポートが `52001` ならタブ1のソケットへ、`52002` ならタブ2のソケットへ正確に振り分けられます。さらにサーバ側でも、世界中の多数のクライアントが同じ `443` 番へ繋いできますが、**`(プロトコル, 送信元IP, 送信元ポート, 宛先IP, 宛先ポート)` の 5 つ組（5-tuple）** を見れば、何万本もの TCP コネクションを 1 本ずつ区別できます。

#### 実験B：$1\text{ Gbps}$・往復 $30\text{ ms}$ の回線で「1個送って返事待ち」をすると何が起きるか

東京〜大阪間（あるいは国内遠距離）を結ぶ $R = 1\text{ Gbps}$（$= 10^9\text{ bit/s}$）、往復伝搬遅延 $\text{RTT} = 30\text{ ms}$ の光ファイバ回線を使って、$L = 1{,}000\text{ B}$（$= 8{,}000\text{ bit}$）のパケットを送ります。

* 1パケットを回線へ送り出す伝送遅延：$T_{\text{trans}} = \dfrac{L}{R} = \dfrac{8{,}000\text{ bit}}{10^9\text{ bit/s}} = \mathbf{0.008\text{ ms}}$（わずか $8\ \mu\text{s}$）

ここで、最も素朴な信頼性通信である **Stop-and-Wait（1個送ったら、相手から確認応答 ACK が返ってくるまで次を送らず待つ）** を使ってみます。

1. $0.008\text{ ms}$ かけて 1 パケットを送り出します。
2. そこから丸々 **$\text{RTT} = 30\text{ ms}$** のあいだ、何も送らずに ACK を待ちます。
3. 合計 $30.008\text{ ms}$ ごとにたった $0.008\text{ ms}$ 分しか回線を使えていないため、回線利用率（伝送効率）は

    $$U = \frac{0.008}{30.008} \approx \mathbf{0.000267} \quad (\mathbf{0.027\%})$$

    となります。せっかく $1\text{ Gbps}$ の高速回線を契約しているのに、実効スループットはわずか **$267\text{ kbps}$** しか出ません。この大きな浪費を解消するのが、返事を待たずに複数パケットを連続投入する **パイプライン型 ARQ** です。

### 3. 構造・アルゴリズム・実装（What）

#### (1) ポート番号・多重化／逆多重化と 5 つ組

トランスポート層が複数のアプリケーションプロセスからのデータを1本のネットワーク層（IP）へ束ねる処理を **多重化（Multiplexing）**、逆に受信した IP パケットのペイロードを宛先ポート番号に基づいて正しいソケットへ振り分ける処理を **逆多重化（Demultiplexing）** と呼びます。

ポート番号は **16 ビット符号なし整数（`0` 〜 `65,535`）** であり、IANA によって次の3範囲に区分されています。

* **ウェルノウンポート（`0` 〜 `1023`）：** 主要プロトコル用に予約されています（例：SSH=`22`, DNS=`53`, HTTP=`80`, HTTPS=`443`）。UNIX系OSでは [5-7節](../5/5-7.md)の通り特権（`root` または `CAP_NET_BIND_SERVICE`）が必要です。
* **登録済みポート（`1024` 〜 `49151`）：** データベースや各種アプリ用に登録されています（例：PostgreSQL=`5432`, MySQL=`3306`, Redis=`6379`）。
* **エフェメラル（動的／一時）ポート（`49152` 〜 `65535`、Linux デフォルトは `32768`〜`60999`）：** クライアントが `connect()` した際に OS が一時的に自動割り当てする番号です。

#### (2) UDP と TCP の対比

インターネットのトランスポート層は、対照的な性格を持つ2つの標準プロトコルを提供しています（図7-1-1）。

* **UDP（User Datagram Protocol：RFC 768）：**
    IP のベストエフォート通信へ「ポート番号（多重化）」と「簡易な誤り検出（チェックサム）」だけを足した最小限のプロトコルです。ヘッダ長はわずか **8 バイト**（送信元ポート 2B、宛先ポート 2B、データグラム長 2B、チェックサム 2B）で、事前接続を持たないためサーバ側ソケットは基本的に **宛先 IP と宛先ポートの 2 つ組** で識別されます（複数クライアントからのデータグラムを同じ 1 個のソケットで受け取れます）。ハンドシェイクも再送も順序保証も行わないため **低遅延・軽量** であり、DNS クエリ、DHCP、音声／動画通話（VoIP / WebRTC）、オンラインゲーム、そして次世代 Web 通信 **QUIC（[7-3節](7-3.md)で詳述）** の土台として使われます。なお、QUIC があえて UDP の上に構築されるのは、途中のルータやファイアウォールが TCP・UDP 以外の新しい IP プロトコル番号を遮断する「プロトコル硬直化」を回避し、OS カーネルを改修せずユーザ空間で柔軟に進化させるためです。

* **TCP（Transmission Control Protocol：RFC 9293）：**
    ベストエフォートな IP 網の上に、**「1バイトの欠損も重複も順序逆転もない、信頼性のある双方向バイトストリーム」** を築き上げる高機能プロトコルです。ヘッダ長は標準 **20 バイト**（オプションなし時）で、3-way ハンドシェイクによる接続管理、シーケンス番号と確認応答（ACK）、タイムアウト再送、フロー制御、輻輳制御を備えています（詳細は [7-2](7-2.md)・[7-3節](7-3.md)）。

#### (3) ARQ（自動再送要求）の 3 方式：Stop-and-Wait・Go-Back-$N$・Selective Repeat

破損や紛失が起きる下位ネットワーク上で信頼性を実現する基本メカニズムが **ARQ（Automatic Repeat reQuest：自動再送要求）** です。必要な道具は、**①誤り検出（チェックサム／CRC）**、**②シーケンス番号（重複と順序の識別）**、**③確認応答（ACK）**、**④再送タイマ（紛失時のタイムアウト検知）** の4つです。

ARQ は、返事（ACK）を待たずに連続して回線上へ送り出せる最大フレーム数（**ウィンドウサイズ $W$**）と、エラー発生時の再送範囲によって次の **3方式** に分類されます（図7-1-2）。

1. **Stop-and-Wait（待機型：$W = 1$）：**
    1パケット送信するたびにタイマを始動し、ACK が返るまで次のパケットを送りません。タイマが切れたら同じパケットを再送します。実装は最も単純（シーケンス番号も `0` と `1` の 1 ビット交互で足ります）ですが、実験Bの通り広帯域・長距離では効率が大きく低下します。

2. **Go-Back-$N$（GBN：累積 ACK・一括巻き戻し型、$W = N$）：**
    ACK を待たずに最大 $N$ 個のパケットをパイプライン状に連続送信します。

    * **受信側：** 期待通りの順番（`expectedseqnum`）で届いたパケットだけを受理して **累積 ACK**（「番号 $k$ まではすべて正常に届いた」という意味の `ACK k`）を返します。順序が飛んで届いたパケットは**バッファせずそのまま破棄**し、直前の正常番号の ACK を繰り返します。
    * **送信側：** 最古の未確認パケットに対するタイマを 1 個だけ持ちます。もしパケット `1` が紛失してタイムアウトすると、その後すでに送信済みだったパケット `2, 3, ...` も含めて **「`1` 以降の $N$ 個をすべて最初から再送（巻き戻し）」** します。

3. **Selective Repeat（SR：個別 ACK・選択再送型、$W = N$）：**
    GBN が「1個紛失しただけで後続の正常な $N - 1$ 個まで全部再送してしまう」無駄を省いた方式です。

    * **受信側：** 順序が飛んで届いた後続パケット（例：`1` が欠けた状態で届いた `2, 3`）も捨てずに **受信バッファへ一時保存** し、個々のパケットごとに **個別 ACK**（`ACK 2`, `ACK 3`）を返します。欠けていた `1` が届いた瞬間に `1, 2, 3` をまとめて上位アプリへ渡します。
    * **送信側：** 各パケットごとに独立したタイマを持ち、タイムアウトした **紛失パケット `1` だけを選択的に再送** します。

#### (4) ARQ 3方式の伝送効率（リンク利用率 $U$）の数理解析

3方式の性能差を定量的に比較するため、1フレームの伝送遅延を $T_{\text{trans}} = L / R$、片道の伝搬遅延を $T_{\text{prop}} = d / s$（往復 $\text{RTT} = 2 T_{\text{prop}}$、ACK の伝送時間と処理遅延は無視）とし、両者の比を無次元パラメータ

$$
a = \frac{T_{\text{prop}}}{T_{\text{trans}}} = \frac{\text{RTT}}{2 T_{\text{trans}}}
$$

と定義します（$a$ が大きいほど「細長いパイプ」＝広帯域・長距離リンクであることを意味します。実験Bでは $a = 15 / 0.008 = 1{,}875$ でした）。

1. **誤りがない理想回線（パケット誤り率 $p = 0$）での伝送効率 $U$：**

    * **Stop-and-Wait（$W = 1$）：** 1サイクルの長さは $T_{\text{trans}} + 2 T_{\text{prop}} = T_{\text{trans}}(1 + 2a)$、そのうち実際に送信している時間は $T_{\text{trans}}$ なので、

        $$U_{\text{SW}} = \frac{1}{1 + 2a}$$

    * **パイプライン型（GBN / SR、ウィンドウサイズ $W$）：** 1サイクル $T_{\text{trans}}(1 + 2a)$ の間に最大 $W$ フレームを連続送信できるため、

        $$U_{\text{pipe}} = \min\!\left(1,\;\; \frac{W}{1 + 2a}\right)$$

        特に、**$W \ge 1 + 2a$**（回線のパイプ全体を満たす **帯域遅延積 $R \times \text{RTT}$（$2a$ フレーム分）に送信中の 1 フレーム分を加えたウィンドウサイズ**）を確保できれば、**利用率 $U = 1$（100%）** を達成できます。

2. **独立なパケット誤り率 $p$（$0 \le p < 1$）が存在するときの伝送効率 $U$：**
    ここでは解析の見通しをよくするため、「ACK は紛失・破損せず、GBN は 1 往復（$1 + 2a$ スロット）で誤りを検知して巻き戻し再送する（追加のタイマ待ちなし）」と仮定します。1つのパケットが正常に届くまでの平均送信回数（成功確率 $1 - p$ の幾何分布の期待値）は $\dfrac{1}{1 - p}$ 回であり、初回送信の $1$ 回を差し引いた再送回数の期待値は $\dfrac{1}{1 - p} - 1 = \dfrac{p}{1 - p}$ 回です。

    * **Stop-and-Wait：** 1パケット成功させるのに平均 $\dfrac{1}{1 - p}$ サイクルかかるため、

        $$U_{\text{SW}} = \frac{1 - p}{1 + 2a}$$

    * **Selective Repeat（$W \ge 1 + 2a$ のとき）：** 壊れたフレーム**だけ**を再送し、他の正常フレームは無駄にしないため、1パケット成功あたりの消費スロット数はそのまま平均 $\dfrac{1}{1 - p}$ となり、

        $$U_{\text{SR}} = 1 - p$$

    * **Go-Back-$N$（$W \ge 1 + 2a$、再送幅 $N = 1 + 2a$ のとき）：** 初回送信の $1$ スロットに加え、平均 $\dfrac{p}{1 - p}$ 回の再送のたびに **1回あたり $N \approx 1 + 2a$ スロット分を丸ごと巻き戻して再消費** します。1パケット成功あたりの平均消費スロット数は $1 + \dfrac{p}{1 - p}(1 + 2a) = \dfrac{1 + 2ap}{1 - p}$ となるため、逆数をとって

        $$U_{\text{GBN}} = \frac{1 - p}{1 + 2ap}$$

この3つの式を並べてみると、3方式の優劣が明確に浮かび上がります（図7-1-3）。$a$（回線の広帯域・長距離度）が大きく、かつ無線のように誤り率 $p$ もある程度高い環境では、$2ap$ の項が効いて GBN の効率が急落するのに対し、Selective Repeat は $a$ の大きさに一切影響されず常に $(1 - p)$ を維持できることが分かります。

> **【コラム：なぜ UDP/TCP チェックサムは下位層の情報を含む「擬似ヘッダ」を仮付加するのか】**
>
> UDP や TCP のチェックサム計算には、自分自身のヘッダとペイロードだけでなく、1つ下の IP 層から借りてきた **送信元 IP・宛先 IP・プロトコル番号・長さ（IPv4 の場合は計 12 バイト、IPv6 の場合はアドレス長が大きいため計 40 バイト）** を仮想的に先頭へ付加した **擬似ヘッダ（Pseudo-Header）** が含まれます（実際の回線上には送信されません）。これは一見すると階層化の原則に反するようですが、もし途中のルータのバグで IP ヘッダの宛先 IP が書き換わって別ホストへ誤配達された場合でも、受信側のトランスポート層がチェックサム不一致で即座に検知できるようにするためのエンドツーエンドの安全策です。

### 4. 限界と補正（Critique & Adaptation）

#### (1) 有限ビットのシーケンス番号とウィンドウサイズの上限（ラップアラウンド問題）

現実のパケットヘッダでは、シーケンス番号は $k$ ビットの有限整数（$0 \sim 2^k - 1$ の $2^k$ 通り）であり、上限を超えると再び `0` へ折り返します（ラップアラウンド）。ここでウィンドウサイズ $W$ を大きくしすぎると、**「再送されてきた古いパケット」と「一周回ってきた新しいパケット」の区別がつかなくなる**バグが起きます。

たとえば $k = 2$ ビット（番号空間 `0, 1, 2, 3` の 4 通り）で **Selective Repeat** を使うとき、もし $W = 3$ にしてしまうと破綻します。

1. 送信側が `0, 1, 2` を送り、受信側がすべて正常に受け取って受信ウィンドウを `[3, 0, 1]` へ進めます。
2. ところが受信側が返した `ACK 0, 1, 2` がすべて途中で紛失します。
3. 送信側はタイムアウトして **古いパケット `0`** を再送します。
4. 受信側の待機窓 `[3, 0, 1]` の中に `0` が含まれているため、受信側は古い再送パケット `0` を **「一周回ってきた新しいパケット `0`」と誤認して受理** してしまい、データが破壊されます。

一般に Selective Repeat では、送信側のウィンドウ（未確認の $W$ 個）と受信側のウィンドウ（新たに受け入れ待機する $W$ 個）が、ACK 紛失時に最大 $W$ 個ぶん先行してずれます。古い再送パケットが受信側の新しいウィンドウと重ならないためには、**送信窓と受信窓の合計がシーケンス番号空間全体を超えないこと**、すなわち $W_{\text{send}} + W_{\text{recv}} = W + W \le 2^k$ が必要十分条件となります。

Go-Back-$N$ の場合も、受信側の待機窓は 1 点のみ（$W_{\text{recv}} = 1$）ですが、もし $W = 2^k$（例：$k = 2, W = 4$ で `0, 1, 2, 3` を送信）にすると、全 ACK が紛失した直後に受信側が次に期待する番号がちょうど `0` に戻るため、再送された古い `0` と新しい `0` を区別できなくなります。上限を $W + 1 \le 2^k$（すなわち $2^k - 1$）に抑えておけば、未確認の先頭番号と受信側の期待番号が一致しないため混同を防げます。

この混同を原理的に防ぐため、$k$ ビット（$2^k$ 通り）のシーケンス番号空間におけるウィンドウサイズ $W$ には次の数学的上界があります。

* **Go-Back-$N$：** $W \le 2^k - 1$
* **Selective Repeat：** $W + W \le 2^k \implies W \le \dfrac{2^k}{2} = 2^{k-1}$（番号空間のちょうど**半分以下**）

実際の TCP ではシーケンス番号に **32 ビット（約 42.9 億バイト）** を割り当て、さらに 10 Gbps 以上の高速回線で数秒で 4 GB を使い切って番号が一周する問題（**PAWS：Protect Against Wrapped Sequences**、折り返した古いシーケンス番号の誤認防止）には **TCP タイムスタンプオプション（TSOPT）** を併用して補正しています（[7-2節](7-2.md)でも補足）。

#### (2) ARQ だけでは足りない現実の課題（次節への動機）

本節の ARQ（GBN と SR）は、「1本のリンク上でパケット紛失を効率よく回復する」理論を完成させました。しかし、現実のインターネット上で TCP を動かすには、まだ次の3つの大きな課題が残っています。

1. **接続の開始と終了をどう安全に合意するか：** 信頼性のない回線上では「最後の ACK が届いたか」を確実に確認し合うことが原理的に不可能です（次節の **二つの軍隊問題** と **3-way ハンドシェイク**）。
2. **受信ホストのメモリ溢れをどう防ぐか：** 送信側がウィンドウサイズ $W$ を固定で大きくしすぎると、受信側アプリの読み取りが追いつかず受信バッファが溢れます（[7-3節](7-3.md)の **フロー制御**）。
3. **ネットワーク全体の混雑をどう防ぐか：** 受信側に余裕があっても、世界中の送信者が一斉に送り込むと途中のルータのキューが溢れて渋滞崩壊します（[7-3節](7-3.md)の **輻輳制御**）。

これらを次節（[7-2節](7-2.md)）と [7-3節](7-3.md)で順に解き明かします。

### 5. 接続と展望（Bridge）：本節の内容が後半のどの部に繋がるか

1. **次節（[7-2節](7-2.md)：TCP コネクション管理［3-way handshake・二つの軍隊問題］とスライディングウィンドウ）：**
    本節の ARQ（GBN と SR のハイブリッド）を実際のバイトストリームへ実装した **TCP スライディングウィンドウ**、および信頼性のない網上で接続を確立・切断する **3-way ハンドシェイクと 4-way 切断** へ進みます。

2. **[第0部](../index.md#part-0)（[0-5節](../0/0-5.md)：CPU パイプライン）との構造的回収：**
    「1命令終わるのを待ってから次を始める（マルチサイクル / Stop-and-Wait）」と遅延が大きくてスループットが出ないため、「確認を待たずに連続投入し、異常（分岐ミス／パケット紛失）が起きたらまとめて巻き戻す（パイプライン＋フラッシュ / Go-Back-$N$）」という構造は、CPU 内部とネットワークで同型です。

3. **[第5部](../index.md#part-5)（[5-3節](../5/5-3.md)：ソケット）との回収：**
    [5-3節](../5/5-3.md)でサーバが `accept()` するたびにクライアント別の専用 FD が返ってきた裏側には、本節の **5つ組（5-tuple）による逆多重化** があります。

### 理解度チェック（次節へ進む前の確認）

本節の 5 つ組・ARQ 3 方式の伝送効率計算・ウィンドウサイズ上限を確認し、次節（[7-2節](7-2.md)）へ繋ぐ問いを置きます。

> **【確認の問い】**
>
> 1. **（広帯域リンクにおける ARQ 3 方式の伝送効率と必要シーケンス番号ビット幅）**
>     帯域幅 $R = 100\text{ Mbps}$（$= 10^8\text{ bit/s}$）、往復伝搬遅延 $\text{RTT} = 20\text{ ms}$（片道 $T_{\text{prop}} = 10\text{ ms}$）の通信路で、サイズ $L = 1{,}250\text{ B}$ のパケットを連続送信します（ACK の伝送時間と処理遅延は無視します）。
>
>     * (a) 1 パケットの伝送遅延 $T_{\text{trans}}$ と無次元パラメータ $a = T_{\text{prop}} / T_{\text{trans}}$ を求めたうえで、誤り率 $p = 0$ のときの **Stop-and-Wait の伝送効率 $U_{\text{SW}}$**、およびパイプライン型（GBN / SR）で利用率 $100\%$（$U = 1$）を達成するために必要な最小ウィンドウサイズ $W_{\min} = 1 + 2a$ を求めてください。
>     * (b) ウィンドウサイズを $W = W_{\min}$ とし、パケット誤り率が $p = 0.01$（$1\%$）になったときの **Go-Back-$N$（$U_{\text{GBN}}$）** と **Selective Repeat（$U_{\text{SR}}$）** の伝送効率をそれぞれ求めて比較してください。さらに、この $W = W_{\min}$ をラップアラウンドによる誤認なく安全に運用するために必要な最小のシーケンス番号ビット幅 $k$ を、GBN と SR それぞれについて求めてください。
>
> 2. **（Selective Repeat のラップアラウンド破綻トレースと UDP / TCP の逆多重化比較）**
>     次の 2 つの問いに答えてください。
>
>     * (a) シーケンス番号が $k = 3$ ビット（番号 `0` 〜 `7` の 8 通り）の Selective Repeat で、上限（$2^{k-1} = 4$）を超えてウィンドウサイズを $W = 5$ に設定したとします。送信側が `0, 1, 2, 3, 4` を送信して受信側がすべて正常受理した直後に、それらの ACK がすべて紛失した場合、受信側の待機ウィンドウはどう移動し、送信側がタイムアウト再送した古いパケット `0` がなぜ「新しいパケット `0`」と取り違えられるかをトレースして説明してください。
>     * (b) 同じサーバの待ち受けポート（例：UDP 53 番と TCP 443 番）へ、異なる 2 台のクライアント A・B から同時にパケットが届いたとき、OS カーネルがソケットへ振り分ける（逆多重化する）仕組みは **UDP（2 つ組）** と **TCP（5 つ組）** でどう異なるでしょうか。
>
> 3. **（2-way ハンドシェイクの危険性：遅延重複 `SYN` による半開接続）**
>     IP 網ではパケットの紛失だけでなく、ネットワーク内に長く滞留して遅れて届く「遅延重複パケット」も発生します。ここで、クライアントが接続要求（`SYN`）を送り、サーバが了承（`SYN+ACK`）を返しただけで即座に接続確立とみなす **2 回だけのやり取り（2-way ハンドシェイク）** を仮定します。過去の通信で送信されて遅れて届いた古い `SYN` パケットをサーバが受信したとき、サーバ側とクライアント側の状態の間にどのような食い違い（半開接続／幽霊コネクション）が生じ、なぜそれが問題になるのか説明してください。
