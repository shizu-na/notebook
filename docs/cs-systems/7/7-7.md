### 前節（7-6）の確認問題の解答

前節の最後に提示した3つの問いの解答を確認します。問3(a)の中間者攻撃をどう防ぐかが、そのまま本節（認証・鍵交換とプロトコル保護）の導入になります。

1. **小さな素数での RSA 手計算と教科書 RSA への決定性攻撃（$p = 3,\; q = 11,\; e = 3$）：**

    * **(a) $n$、$\phi(n)$、秘密指数 $d$、および $M = 4$ の暗号化・復号：**

        * $n = 3 \times 11 = \mathbf{33}$、$\phi(n) = (3 - 1)(11 - 1) = \mathbf{20}$ です。
        * $3 \cdot d \equiv 1 \pmod{20}$ を満たす $d$ は、$3 \times 7 = 21 \equiv 1 \pmod{20}$ より **$d = 7$** です。
        * 暗号化：$C = 4^3 \bmod 33 = 64 \bmod 33 = \mathbf{31}$ となります。
        * 復号：$31 \equiv -2 \pmod{33}$ を用いると、

            $$31^7 \equiv (-2)^7 = -128 = -4 \times 33 + 4 \equiv \mathbf{4} \pmod{33}$$

            となり、元の平文 **$M = 4$** へ正確に戻ります。

    * **(b) 暗号文 $C = 26$ の特定と対策：**
        パディングなしの教科書 RSA は決定論的であるため、盗聴者は公開鍵 $(3, 33)$ で 2 つの候補を暗号化して照合します。$4^3 \bmod 33 = 31 \neq 26$ である一方、$5^3 \bmod 33 = 125 \bmod 33 = 125 - 99 = \mathbf{26} = C$ と一致するため、秘密鍵を知らなくても平文が **`"NO"`（$M = 5$）** であると即座に特定できます。実務では、毎回ランダムな詰め物を混ぜて確率的暗号にする **OAEP（Optimal Asymmetric Encryption Padding）** でこれを防ぎます。

2. **CTR モードの Nonce 再利用による平文復元と可鍛性・AES-GCM の検知：**

    * **(a) Nonce 再利用時の $P_2$ の復元：**
        同一鍵・同一 Nonce では同じ鍵ストリーム $S$ が使われるため $C_1 \oplus C_2 = (P_1 \oplus S) \oplus (P_2 \oplus S) = P_1 \oplus P_2$ となり、

        $$C_1 \oplus C_2 = \texttt{0x5A} \oplus \texttt{0x4F} = \texttt{0101\,1010}_2 \oplus \texttt{0100\,1111}_2 = \texttt{0001\,0101}_2 = \texttt{0x15}$$

        $$P_2 = (C_1 \oplus C_2) \oplus P_1 = \texttt{0x15} \oplus \texttt{0x41} = \texttt{0001\,0101}_2 \oplus \texttt{0100\,0001}_2 = \texttt{0101\,0100}_2 = \mathbf{\texttt{0x54}}$$

        と復元されます（ASCII 文字 **`'T'`**）。

    * **(b) CTR モードの可鍛性による改ざんと AES-GCM の防御：**
        受信側が改ざん後の $C' = C \oplus \texttt{0x09} = (\texttt{0x30} \oplus S) \oplus \texttt{0x09}$ を鍵ストリーム $S$ と XOR して復号すると、

        $$P' = C' \oplus S = \texttt{0x30} \oplus \texttt{0x09} = \texttt{0011\,0000}_2 \oplus \texttt{0000\,1001}_2 = \texttt{0011\,1001}_2 = \mathbf{\texttt{0x39}}$$

        となり、平文が ASCII 文字 **`'9'`** へ狙い通りに書き換わります。CTR モード単体では鍵ストリームとの線形 XOR のみで改ざん検知を持たないため、暗号文のビット反転が平文の同じ位置のビット反転へ直結します（可鍛性）。これに対し **AES-GCM（AEAD）** は暗号文とヘッダに対する GHASH 認証タグを付与しているため、1 ビットでも改ざんされるとタグ検証に失敗し復号前にパケットを拒否します。

3. **未認証公開鍵交換への MITM トレースと量子コンピュータの非対称な影響（本節への接続）：**

    * **(a) 未認証公開鍵交換に対する MITM 攻撃の 3 ステップ：**

        1. **公開鍵のすり替え：** 経路上の Mallory が Bob の公開鍵を横取りし、代わりに Mallory 自身の公開鍵を Alice へ渡します。
        2. **Alice からの送信データの解読：** Alice は偽物に気づかず Mallory の公開鍵でセッション鍵を暗号化して送るため、Mallory は自身の秘密鍵で復号してデータ本体を盗み見（または改ざん）できます。
        3. **Bob への再暗号化転送：** Mallory は本物の Bob の公開鍵でセッション鍵とデータを暗号化し直して Bob へ転送するため、両者は通信が正常に成立していると錯覚します。

    * **(b) Grover と Shor のアルゴリズムによる非対称な影響と対策：**
        共通鍵暗号（AES）は **Grover のアルゴリズム** によって探索計算量が平方根（$2^k \to 2^{k/2}$）へ縮みますが、**鍵長を 2 倍（AES-128 → AES-256）にするだけで十分な安全性（128 ビット相当）を維持**できます。一方、公開鍵暗号（RSA / ECC）は **Shor のアルゴリズム** により素因数分解や離散対数問題が多項式時間で解かれるため、鍵長を多少伸ばしても安全性が崩壊します。対策として、格子問題などに基づく **耐量子計算機暗号（PQC：ML-KEM・ML-DSA 等）** への移行が進められています。

## 7-7. 認証・鍵交換とプロトコル保護（署名・DH・Kerberos・TLS/HTTPS・IPsec）

### 1. 動機（Why）：ハイブリッド暗号にまだ残る「2つの大きな課題」をどう塞ぐのか

前節（[7-6節](7-6.md)）で、共通鍵暗号（AES-GCM）と公開鍵暗号（RSA/ECC）を組み合わせたハイブリッド暗号を学びました。しかし、インターネットの現実の脅威に対しては、まだ次の **2つの大きな課題** が残っています。

1. **なりすましと中間者攻撃（MITM）の課題：**
    「Bob の公開鍵」として回線越しに届いた数値 $(e, n)$ が、本当に Bob 本人の鍵である保証がどこにもありません。経路上の攻撃者 Mallory が自分の公開鍵へすり替えてしまえば、ハイブリッド暗号は丸ごと突破されます。必要なのは、メッセージや公開鍵が「間違いなく本人によって作られ、途中で 1 ビットも改ざんされていない」と証明する **認証（Authentication）** と **デジタル署名・証明書（PKI）** です。

2. **「今録画して、将来解読する」脅威（前方秘匿性の欠如）：**
    もし従来の RSA 鍵配送（サーバの長期公開鍵でセッション鍵 $K_s$ を直接暗号化して送る方式）を使っていると、攻撃者が今日流れた暗号化通信をすべてハードディスクへ録画しておき、3年後にサーバの長期秘密鍵を1度でも盗み出した瞬間、**過去3年分のすべての通信内容が一斉に解読されてしまいます**。長期秘密鍵が将来漏洩しても過去のセッション鍵だけは復元できない仕組み（**前方秘匿性：PFS**）が不可欠です。

本節では、[第7部](../index.md#part-7)の締めくくりとして、**暗号学的ハッシュ関数・HMAC・デジタル署名・チャレンジ応答認証**、**PKI（公開鍵基盤）と証明書**、**Diffie-Hellman（DH）鍵交換**、企業内認証の標準 **Kerberos**、そしてこれらを統合した **TLS 1.3 / HTTPS**・**IPsec（VPN）** および境界防御の全体像を1本の線で結びます。

---

### 2. 具体例と動作イメージ（Toy Model）

プロトコルの全体像に入る前に、**「盗聴者がすべてのやり取りを見ている回線の上で、2人が同じ秘密の数字を作り出す」** **Diffie-Hellman（ディフィー＝ヘルマン：DH）鍵交換** を、小さな数で手計算して確かめます。

#### 実験A：小さな素数 $p = 23,\; g = 5$ で Diffie-Hellman 鍵交換を手計算する

Alice と Bob は、盗聴者 Eve がすべてを盗み見ている公開回線上で、共通の秘密鍵 $S$ を作りたいとします。

1. **公開パラメータの合意（Eve にも丸見え）：**
    素数 **$p = 23$** と原始根（生成元）**$g = 5$** を公開で合意します。

2. **各自の秘密乱数を選んで公開値を計算・交換する：**
    まず繰り返し二乗法で $5^2 = 25 \equiv 2$、$5^4 \equiv 4$、$5^8 \equiv 16 \pmod{23}$ を求めておきます。

    * **Alice：** 秘密の整数 **$a = 6$** を選び（秘密保管）、公開値 $A$ を計算して Bob へ送ります。

        $$A = 5^6 = 5^4 \cdot 5^2 \equiv 4 \times 2 = \mathbf{8} \pmod{23}$$

    * **Bob：** 秘密の整数 **$b = 15$** を選び（秘密保管）、公開値 $B$ を計算して Alice へ送ります。

        $$B = 5^{15} = 5^8 \cdot 5^4 \cdot 5^2 \cdot 5^1 \equiv 16 \times 4 \times 2 \times 5 \equiv 18 \times 2 \times 5 \equiv 13 \times 5 = 65 \equiv \mathbf{19} \pmod{23}$$

    * 盗聴者 Eve が見られるのは $p = 23,\; g = 5,\; A = 8,\; B = 19$ の 4 つだけです。

3. **相手の公開値を自分の秘密数でべき乗する：**

    * **Alice の計算：** $19 \equiv -4 \pmod{23}$ なので $19^2 \equiv 16$、$19^4 \equiv 256 \equiv 3 \pmod{23}$ より、

        $$S_A = B^a \bmod 23 = 19^6 = 19^4 \cdot 19^2 \equiv 3 \times 16 = 48 \equiv \mathbf{2} \pmod{23}$$

    * **Bob の計算：** $8^2 = 64 \equiv 18 \equiv -5$、$8^4 \equiv (-5)^2 = 25 \equiv 2$、$8^8 \equiv 4 \pmod{23}$ より、

        $$S_B = A^b \bmod 23 = 8^{15} = 8^8 \cdot 8^4 \cdot 8^2 \cdot 8^1 \equiv 4 \times 2 \times (-5) \times 8 = -320 \equiv \mathbf{2} \pmod{23}$$

指数法則より、

$$B^a = (g^b)^a = g^{ab} = (g^a)^b = A^b \pmod{p}$$

となるため、**Alice も Bob も秘密の数 $a, b$ を一度も回線へ流していないのに、まったく同じ共有秘密 $S = 2$ を手に入れました**。一方、盗聴者 Eve が $g, p, g^a \bmod p$ から秘密の指数 $a$ を逆算する問題（**離散対数問題**）は、$p$ が 2048 ビット以上（あるいは楕円曲線上の点乗算 **ECDH**）になると現代のコンピュータでは事実上解けません。

しかも、Alice と Bob がこの $a, b$ を**今回の通信 1 回限りの使い捨て（Ephemeral）**にして通信終了後に即座にメモリから消去してしまえば、仮に将来サーバの長期秘密鍵が盗まれても、過去の通信で使われた $g^{ab}$ は二度と復元できません（**前方秘匿性：PFS**）。

ただし、素の（認証を伴わない）Diffie-Hellman 鍵交換には重大な弱点があります。交換される公開値 $A = g^a \bmod p$ と $B = g^b \bmod p$ には送信者の本人確認がないため、経路上の攻撃者 Mallory が自身の乱数 $m$ から作った公開値 $M = g^m \bmod p$ へすり替えて両者へ渡すと、Alice と Mallory は $S_{AM} = A^m = M^a \bmod p$ を、Bob と Mallory は $S_{BM} = B^m = M^b \bmod p$ をそれぞれ独立に共有してしまい、全通信を復号・中継される **中間者攻撃（MITM）** が成立します。したがって実運用（TLS 1.3 や IKEv2）では、次項で学ぶ **デジタル署名と証明書（PKI）** を組み合わせて公開値 $g^a, g^b$ の正当性を必ず認証します。

---

### 3. 構造・アルゴリズム・実装（What）

#### (1) 暗号学的ハッシュ関数（SHA-256）・HMAC・デジタル署名

認証と改ざん検知の土台となるのが、任意長の入力データ $M$ から固定長（例：256 ビット＝32 バイト）の指紋（ダイジェスト）$h = H(M)$ を計算する **暗号学的ハッシュ関数**（現代の標準は **SHA-256** や **SHA-3**）です。[6-2節](../6/6-2.md)の CRC とは異なり、次の **3つの厳格な一方向性** を満たします。

1. **原像計算困難性（一方向性）：** ハッシュ値 $h$ から元のデータ $M$ を逆算することが計算量的に不可能です。
2. **第2原像計算困難性（弱衝突耐性）：** あるデータ $M_1$ が与えられたとき、同じハッシュ値 $H(M_1) = H(M_2)$ になる別データ $M_2 \neq M_1$ を見つけることが困難です。
3. **衝突困難性（強衝突耐性）：** 同じハッシュ値 $H(M_1) = H(M_2)$ を持つ任意のペア $(M_1, M_2)$ 自体を見つけ出すことが困難です（※古い **MD5** や **SHA-1** はすでに衝突攻撃が実証され廃止されています）。

このハッシュ関数に「鍵」を組み合わせることで、次の認証部品が作られます（図7-7-1）。

* **HMAC（メッセージ認証コード：共通鍵ベース）：**
    送受信者が共有する秘密鍵 $K$ とメッセージ $M$ を 2 重にハッシュして認証タグを計算します（$\text{HMAC}(K, M) = H\bigl((K \oplus \text{opad}) \parallel H((K \oplus \text{ipad}) \parallel M)\bigr)$。ここで `opad`・`ipad` は固定バイト定数、`$\parallel$` はビット列の連結を表します）。この 2 重構造により、単純に鍵と平文を繋いだ $H(K \parallel M)$ で問題となる **長さ伸長攻撃（Length Extension Attack：鍵 $K$ を知らずに $H(K \parallel M)$ から $H(K \parallel M \parallel M')$ を偽造できる攻撃）** を防いでいます。高速に **完全性（改ざん検知）** と **認証（鍵を持つ相手からの送信）** を検証できますが、送受信者が同じ鍵 $K$ を持つため「相手が自分で偽造したのではないか」という第三者への証明（否認防止）はできません。

* **デジタル署名（Digital Signature：公開鍵ベース）：**
    公開鍵暗号の役割を**逆向き**に使う仕組みです（RSA-PSS や **ECDSA / Ed25519**）。

    1. **署名生成（送信者 Alice）：** 巨大なメッセージ $M$ へ直接署名すると遅いため、まず $h = \text{SHA-256}(M)$ を計算し、その 32 バイトのハッシュ値に対して **Alice 自身の秘密鍵** で署名 $\sigma = \text{Sign}_{\text{priv}_A}(h)$ を生成して $M$ と一緒に送ります。
    2. **署名検証（受信者 Bob や任意の第三者）：** 受け取った $M$ のハッシュ値 $h' = \text{SHA-256}(M)$ を自力で計算し、**Alice の公開鍵** で署名 $\sigma$ を検証して一致すれば受理します。
    3. **3つの保証：** ①**完全性**（1ビットでも改ざんされるとハッシュが不一致になります）、②**認証**（秘密鍵を持つ Alice 本人しか署名を作れません）、③**否認防止（Non-repudiation）**（Alice の秘密鍵は Alice しか持たないため、「自分は送っていない」と後から言い逃れできません）の 3 つを同時に満たします。

* **チャレンジ応答認証（Challenge-Response）と反射攻撃（Reflection Attack）の回避：**
    パスワードや鍵を回線へ直接流さずに本人確認するには、検証側が毎回使い捨ての乱数（チャレンジ $R$）を送り、相手が秘密鍵 $K$ で暗号化（または HMAC 計算）した応答 $E_K(R)$ を返す **チャレンジ応答認証** を使います。ただし、開始側と応答側で手順が対称な素朴な設計では、次のように **反射攻撃（Reflection Attack）** が成立します。

    1. 攻撃者 Trudy が Bob へセッション 1 を開き、「Alice だ」と名乗って乱数 $R_1$ を送ると、Bob は本人確認のため自身のチャレンジ $R_B$ を返します（Trudy は共有鍵 $K$ を持たないため $E_K(R_B)$ を計算できません）。
    2. Trudy はセッション 1 を保留したまま、**同じ Bob へ向けて別セッション 2 を開き**、さきほど Bob から受け取った $R_B$ をそのまま自分のチャレンジとして Bob へ送りつけます。
    3. 対称なプロトコルでは Bob 自身がセッション 2 で答え $E_K(R_B)$ を計算して返してしまうため、Trudy はその応答をセッション 1 へそのまま提出するだけで秘密鍵 $K$ なしで認証を突破できてしまいます。

    これを防ぐには、①開始側と応答側で異なる鍵を使う、②チャレンジの役割・番号（例：奇数／偶数）を分ける、③応答側に自身の識別子（ID）を含める、④相手が先に証明を完了するまで自分の応答を返さない（方向と手順の非対称性を設ける）、という設計原則を徹底します。

#### (2) 公開鍵基盤（PKI）と X.509 デジタル証明書：中間者攻撃の防止

前節の最後に残った「届いた公開鍵が本当に `bank.example.com` のものか？」という問いを解くのが、**公開鍵基盤（PKI：Public Key Infrastructure）** です。

* **デジタル証明書（X.509 証明書）：**
    「ドメイン名 `bank.example.com` の持ち主の公開鍵は `PK_bank` であり、有効期限は 2027年までである」という身分証データに対し、世界中で信頼されている第三者機関 **認証局（CA：Certificate Authority）** が **CA の秘密鍵でデジタル署名** を押した電子パスポートです。

* **信頼の連鎖（Chain of Trust）とルート CA：**
    ブラウザや OS には、あらかじめ厳選された信頼できる **ルート CA（Root CA）の公開鍵（ルート証明書）** が最初から内蔵（プリインストール）されています。

    1. ブラウザが `https://bank.example.com` へ接続すると、サーバは自分の証明書（および中間 CA の証明書）を提示します。
    2. ブラウザは内蔵のルート CA 公開鍵を使って中間 CA 証明書の署名を検証し、次に中間 CA の公開鍵を使って `bank.example.com` の証明書の署名を検証し、さらに証明書内の許可ドメイン名一覧（**SAN**：Subject Alternative Name）と有効期限が一致することを確認します。
    3. すべて検証に通れば、証明書の中の公開鍵 `PK_bank` が間違いなく本物の銀行のものであると確定し、攻撃者 Mallory による公開鍵のすり替え（中間者攻撃）が封じられます。

#### (3) 共通鍵ベースの集中認証：Kerberos（企業内シングルサインオン）

インターネット全体では公開鍵ベースの PKI が使われますが、企業の社内ネットワーク（Windows Active Directory 等）のように全ユーザと全サーバを 1 つの組織が管理できる環境では、計算の軽い **共通鍵暗号だけ** で認証と鍵配布を行う **Kerberos（ケルベロス）** が広く使われています。

Kerberos の中核には、全ユーザと全サーバの秘密鍵を知る信頼された中央機関 **KDC（Key Distribution Center：AS［認証サーバ］＋ TGS［チケット発行サーバ］）** があります。

1. **ログイン時（1回だけ：AS とのやり取り）：** ユーザがパスワードを入力すると、AS が認証を行い、**TGT（Ticket Granting Ticket：TGS の秘密鍵で暗号化された総合入場パス）** と TGS 用セッション鍵を、ユーザのパスワード由来の鍵で暗号化して返します（パスワード自体は平文で流しません）。
2. **各サービス利用時（TGS とのやり取り）：** ユーザがファイルサーバやメールサーバを使いたいとき、TGT とタイムスタンプ付き認証子を TGS へ提示し、対象サーバの秘密鍵で暗号化された **サービスチケット** とサービス用セッション鍵を発行してもらいます。
3. **サービスアクセス：** ユーザは、サービスチケットに加えて、サービス用セッション鍵で暗号化した現在時刻付きの **認証子（Authenticator）** をファイルサーバへ提示します。ファイルサーバは自分の秘密鍵でチケットを復号してセッション鍵を取り出し、認証子内のタイムスタンプが現在時刻と数分以内かつ未使用であることを検証してリプレイ攻撃（盗聴チケットの使い回し）を防ぎます。これにより、ユーザはパスワードを二度と入力せずに認証と暗号通信を完了できます（**シングルサインオン：SSO**）。

#### (4) すべてを統合したプロトコル保護①：TLS 1.3 / HTTPS

Web（HTTPS）・メール・DoT/DoH を守るトランスポート層上の暗号プロトコルが **TLS（Transport Layer Security）** です。最新の標準規格である **TLS 1.3（RFC 8446、2018年策定）** は、古い脆弱な暗号（RC4、SHA-1、CBC モード、静的な RSA 鍵配送）を全面廃止し、**「AEAD（AES-GCM / ChaCha20-Poly1305）＋ 一時的 Diffie-Hellman（ECDHE：前方秘匿性必須）＋ 1-RTT 高速ハンドシェイク」** へと洗練されました（図7-7-2。なお楕円曲線上の ECDHE では実際の公開値はスカラー倍 $aG, bG$ ですが、実験Aと対応づけるため図中では乗法記法 $g^a, g^b$ で示しています）。

1. **ClientHello（クライアント → サーバ）：**
    対応する暗号スイート一覧、乱数、さらに **接続先を待たずに先読みで生成したクライアント側 ECDHE 公開値 $g^a$（Key Share）** を最初の 1 発目で送ります。

2. **ServerHello ＋ 暗号化済み証明書・署名（サーバ → クライアント）：**
    サーバは自分の ECDHE 公開値 $g^b$ を選んで返送します。この瞬間にサーバ側はすでに共有秘密 $g^{ab}$ からセッション鍵を導出できるため、**続く「サーバ証明書（X.509）」と「ハンドシェイク全体へのサーバ秘密鍵によるデジタル署名（`CertificateVerify`）」「改ざん確認（`Finished`：HMAC）」のすべてを暗号化して一気に返します**。

3. **検証と即座の HTTP 通信開始（わずか 1 RTT）：**
    クライアントは $g^b$ から同じ共有秘密 $g^{ab}$ を計算し、サーバ証明書（PKI）とデジタル署名を検証します（これにより、$g^b$ が中間者 Mallory の偽物ではなく本物のサーバが作ったものであることが証明されます）。クライアントが `Finished` を返すと同時に、**同じ送信塊（フライト）で暗号化された HTTP リクエストを送信開始**できます（従来の TLS 1.2 の 2-RTT から半減し、さらに QUIC と統合すれば TCP の 1-RTT すら消えて全体 1-RTT［再接続 0-RTT］になります）。

#### (5) すべてを統合したプロトコル保護②：IPsec（VPN）と階層別暗号化・境界防御

TLS は第4層（TCP/QUIC）の上でアプリ単位の通信を守りますが、企業の本社と支社のネットワーク全体を丸ごとインターネット越しに安全に結ぶ **VPN（Virtual Private Network）** などでは、**第3層（IP 層）そのものを暗号化・認証する IPsec（IP Security）** が使われます（図7-7-3）。

IPsec は、鍵交換プロトコル **IKEv2**（DH 鍵交換＋相互認証）で共有したセキュリティ設定（**SA**：Security Association＝使用する鍵と暗号方式の組）のもと、次の2つのプロトコルと2つの動作モードを提供します。

* **プロトコルの種類：**

    * **AH（Authentication Header）：** 外側の IP ヘッダの一部とペイロードの認証・完全性のみを保証します（暗号化はしません。NAT による IP アドレス書き換えで認証検証が壊れるため現在はほぼ使われません）。
    * **ESP（Encapsulating Security Payload：主流）：** ペイロードと末尾の **ESP トレーラ**（パディング長と内包プロトコル番号）の **暗号化（機密性）** と、ESP ヘッダからトレーラまでの **認証（完全性）** の両方を AEAD 等で提供します。

* **2つの動作モード（図7-7-3）：**

    1. **トランスポートモード（ホスト対ホスト）：** 元の IP ヘッダはそのまま残し、IP ペイロード（TCP/UDP 以降）だけを ESP で暗号化します。
    2. **トンネルモード（VPN ゲートウェイ間：主流）：** **元の IP ヘッダごと IP パケット全体を丸ごと ESP で暗号化**し、その外側に「本社ゲートウェイ $\to$ 支社ゲートウェイ」宛ての**新しい外部 IP ヘッダ**を被せてカプセル化します。これにより、内部のプライベート IP アドレスや通信相手ホストの情報までインターネットから隠蔽できます。

暗号化を TCP/IP のどの階層で行うかによって、「隠蔽できる範囲」と「経路上に露出するヘッダ」が変わります。

| 階層 | 代表プロトコル | 保護・隠蔽される範囲 | 経路上に露出するヘッダ |
| :--- | :--- | :--- | :--- |
| **L2（リンク層）** | WPA2 / WPA3 | 端末〜アクセスポイント間の無線区間全体 | 有線側へ出た後の全パケット（無線区間のみ保護） |
| **L3（ネットワーク層）** | IPsec（トンネルモード） | 元の IP ヘッダを含む内部パケット全体 | ゲートウェイ間の新外部 IP ヘッダのみ |
| **L4/5（トランスポート上）** | TLS（HTTPS / DoT） | HTTP 本文・Cookie 等のアプリ層データ全体 | IP ヘッダ・TCP/UDP ポート（および未暗号化時の SNI） |
| **L7（アプリケーション層）** | SSH / S/MIME / PGP | 特定アプリのコマンドやメール本文そのもの | IP・TCP ポート・メール配送ヘッダ（宛先アドレス等） |

さらに企業・組織ネットワークでは、暗号プロトコルに加えて境界防御の仕組みを組み合わせます。具体的には、IP・ポートや通信状態に基づいて通信を制御する **ファイアウォール**、不正通信パターンを検知・自動遮断する **IDS / IPS**、および LAN 接続口での端末認証を行う **IEEE 802.1X** が代表例です。しかし、許可された 443 番ポート（HTTPS）経由の攻撃や、一度社内へ侵入された後の横展開は境界ファイアウォールだけでは防げません。そのため現代では、「社内網であっても無条件には信頼せず、通信ごとに認証と暗号化を検証する」**ゼロトラスト（Zero Trust）** 設計へ移行しています。

> **【コラム：Let's Encrypt と Certificate Transparency（CT）：全 Web 暗号化の立役者】**
>
> 2010年代前半まで、HTTPS（TLS）はネットバンキングや決済ページだけの特別な機能であり、通常の Web サイトの多くは平文の HTTP でした。なぜなら、認証局（CA）から X.509 証明書を買うのに年間数万円の費用と煩雑な手作業更新が必要だったためです。
>
> この状況を一変させたのが、2015年に稼働した非営利の自動認証局 **Let's Encrypt** と、ドメイン所有権確認から証明書発行・更新までを全自動化する **ACME プロトコル** です。無料かつ数コマンドで自動更新できるようになった結果、現在では世界の Web トラヒックの **90% 以上が HTTPS で暗号化** されています。
>
> 一方で、ブラウザが信頼するルート CA は世界に数百社存在するため、「そのうちたった 1 社の CA がハッキングされて、Google や銀行の偽証明書を不正発行したらどうなるか？」という PKI の弱点が残ります。これを防ぐ現代の仕組みが **Certificate Transparency（CT：証明書の透明性）** です。すべての CA に対し、発行した全証明書を改ざん不能な公開追記ログ（ハッシュを木状に束ねて追記改ざんを検知するマークル木構造）へ登録することを義務づけることで、ドメイン管理者が「自分のドメインに対して身に覚えのない偽証明書が発行された」ことを数分以内に自動検知・失効できるようにしています。

### 4. 限界と補正（Critique & Adaptation）

#### (1) 証明書の失効（Revocation）の難しさと短命証明書への移行

もし Web サーバの秘密鍵が漏洩したとき、その証明書は有効期限前であっても直ちに無効化（**失効：Revocation**）しなければなりません。古典的には CA が失効済み一覧表（**CRL**：Certificate Revocation List）を配布したり、ブラウザが接続のたびに CA へ「この証明書はまだ有効か？」と問い合わせたり（**OCSP**：Online Certificate Status Protocol）していましたが、CRL の肥大化、OCSP 問い合わせによる遅延・プライバシー漏洩、さらに「OCSP サーバに繋がらないときブラウザが接続を止められず素通りさせてしまう（Soft-Fail）」という弱点がありました。

* **補正：** サーバ自身が CA の署名付き有効証明を定期的に取得して TLS ハンドシェイクへ添える **OCSP Stapling** に加え、近年は Let's Encrypt 等の自動化を前提に**証明書自体の有効期限を短くする（90日 $\to$ 47 日以下・数日）**ことで、失効リストへの依存そのものを減らす方向へ進んでいます。

#### (2) Kerberos の単一障害点と時刻同期依存

Kerberos は高速かつ強力な集中認証ですが、① **KDC が停止すると組織全体で誰も認証できなくなる（単一障害点）**、② リプレイ攻撃（盗聴した過去のチケットの再送）を防ぐために全チケットへタイムスタンプを埋め込んでいるため、**全端末の時計が時刻同期プロトコル（NTP）等で数分以内に同期されていないと認証がすべて失敗する**、という運用上の制約があります（補正：KDC の冗長化と NTP 基盤の必須化）。

#### (3) トランスポート暗号化（TLS / IPsec）だけでは守れないもの

TLS 1.3 や IPsec は「通信路上の盗聴・改ざん・なりすまし」を数学的に防ぎますが、**セキュリティのすべてを解決する万能策ではありません**。

* **メタデータの露出（トラヒック解析）：** TLS で本文を暗号化しても、宛先 IP アドレス・通信量・パケットのタイミング、さらには従来の TLS の `ClientHello` に平文で載る接続先ドメイン名通知（**SNI**：Server Name Indication）は経路から見えます（SNI の漏洩に対しては、DNS 経由で得た公開鍵で ClientHello 自体を暗号化する **ECH：Encrypted Client Hello** による補正が進んでいます）。
* **エンドポイント自体の侵害：** 通信路がどれほど強固でも、通信の両端にあるクライアント PC やサーバ本体に [5-8節](../5/5-8.md)のメモリ破壊脆弱性やマルウェアが存在すれば、暗号化される前（あるいは復号された後）の平文データがそのまま盗まれます。システム全体の安全は、OS の保護（[第5部](../index.md#part-5)）とネットワーク暗号（[第7部](../index.md#part-7)）の両輪が揃って初めて成立します。

### 理解度チェック（次節へ進む前の確認）

本節の Diffie-Hellman MITM 数値トレース・HMAC 対デジタル署名・Kerberos と X.509 検証を確認し、次節（[7-8節](7-8.md)：情報理論と可逆圧縮）へ繋ぐ問いを置きます。

> **【確認の問い】**
>
> 1. **（未認証 Diffie-Hellman への MITM 実数値計算と TLS 1.3 の防御機構）**
>     実験Aと同じ公開パラメータ $p = 23,\; g = 5$ で、Alice が秘密数 $a = 6$（公開値 $A = 5^6 \bmod 23 = 8$）、Bob が秘密数 $b = 15$（公開値 $B = 5^{15} \bmod 23 = 19$）を選んで未認証の Diffie-Hellman 鍵交換を行います。ここへ経路上の攻撃者 Mallory が割り込み、自身の秘密数 $m = 2$ から公開値 $M = g^m \bmod 23$ を生成して Alice と Bob の双方へ送りつけました。
>
>     * (a) Mallory が送りつける公開値 $M$、Alice と Mallory が共有してしまう鍵 $S_{AM} = M^a \bmod 23 = A^m \bmod 23$、および Bob と Mallory が共有してしまう鍵 $S_{BM} = M^b \bmod 23 = B^m \bmod 23$ をそれぞれ計算してください（正規の共有鍵 $S = 2$ とは異なる 2 つの鍵が成立することを確かめてください）。
>     * (b) TLS 1.3 では、サーバが自身の ECDHE 公開値 $g^b$ をクライアントへ返す際、なぜこのような MITM 攻撃が成立しないのでしょうか。**X.509 証明書（PKI）** と **`CertificateVerify` デジタル署名** の役割から説明してください。
>
> 2. **（否認防止における HMAC vs デジタル署名、および Kerberos・PKI の運用診断）**
>     次の 2 つの問いに答えてください。
>
>     * (a) **HMAC** と **デジタル署名** はどちらもメッセージの改ざん検知（完全性）と送信元認証を行えますが、なぜ HMAC では **否認防止（Non-repudiation）** を実現できないのでしょうか。
>     * (b) 次の 2 つの運用トラブルの原因をそれぞれ簡潔に説明してください。
>
>         1. Kerberos を導入した社内ネットワークで、ある端末の時計が KDC より **15 分ずれた** ところ、正しいパスワードを入力しても認証がすべて失敗するようになりました。
>         2. 攻撃者が正規の認証局（CA）から自身のドメイン `evil.example.net` の有効な証明書を取得し、中間者として `https://bank.example.com` へ接続するブラウザへ提示しましたが、ブラウザに拒否されました。
>
> 3. **（次節への伏線：データ圧縮と暗号化の適用順序）**
>     大量のテキストや JSON を HTTPS（TLS 1.3 ＋ AES-GCM）で効率よく送りたいとき、①「**圧縮してから暗号化**する」場合と、②「**暗号化してから圧縮**する」場合では、通信データ量の削減効果はどう異なるでしょうか。優れた暗号方式が出力する暗号文の統計的性質（ランダム性・冗長性の有無）から説明してください。
