### 前節（7-5）の確認問題の解答

前節の最後に提示した3つの問いの解答を確認します。問3がそのまま本節（暗号技術の基礎）の導入になります。

1. **DNS サーバ移行時の TTL キャッシュ残留と関連レコード診断：**

    * **(a) キャッシュ残留の最大時間と事前の移行手順：**
        フルサービスリゾルバは取得した `A` レコードを TTL のあいだ権威サーバへ再問合せせず返し続けるため、切替直前にキャッシュされた場合、**最大 86,400 秒（24 時間）** のあいだ旧サーバの IP アドレスが返され続けます。対策として、移行の **24 時間以上前（元の TTL 以上前）にあらかじめ TTL を `60〜300 秒` 程度へ短縮** しておき、古い長時間キャッシュが期限切れになってから IP アドレスを切り替える必要があります。

    * **(b) メールサーバ移行時にあわせて更新・確認すべき DNS レコード 2 つ：**

        1. **`MX` レコード：** `example.jp` 宛てのメールを受け取る受信側 MTA のホスト名を指定するレコードであり、これを `mail2.example.jp` へ更新しないと外部からのメールが旧メールサーバへ配送されてしまいます。
        2. **`TXT` レコード（SPF 用）：** `example.jp` からメール送信を許可された正規送信サーバの IP アドレス一覧を宣言するレコードであり、新サーバの IP を反映しないと受信側で SPF 検証に失敗し、なりすましメールとして拒否・隔離される恐れがあります（DKIM 鍵も刷新する場合は DKIM 用の `TXT` レコードも更新します）。

2. **HTTP メソッド設計・Cookie 保護属性および IMAP 暗号化と SSH ポートフォワーディングの比較：**

    * **(a) `GET /checkout` の危険性と Cookie の 3 属性欠落リスク：**

        * **`GET /checkout` の危険性：** `GET` はサーバの状態を変えない（安全・べき等）前提のため、ブラウザの先読み機能（プリフェッチ）、検索クローラ、中間プロキシのキャッシュや自動再試行によってユーザの意図せずリクエストが実行・重複送信され、勝手な注文確定や二重決済が生じる危険があります。
        * **Cookie の 3 属性欠落リスク：** `HttpOnly` が欠けると悪意ある JavaScript（XSS）から `document.cookie` でセッション ID を盗まれるリスク、`Secure` が欠けると平文 HTTP 接続時にネットワーク上へ漏洩して盗聴（セッションハイジャック）されるリスク、`SameSite` が欠けると外部サイト起点の不正リクエストにも Cookie が自動送信されて CSRF の標的になるリスクが高まります。

    * **(b) TLS 暗号化付き IMAP（993 番）と SSH ポートフォワーディング（22 番）の違い：**
        TLS 暗号化付き **IMAP（993 番）** は、メールサーバ自身が公開ポートで暗号化接続を直接受け付け、複数端末からサーバ上のメールボックス（フォルダ・既読フラグ）を同期閲覧するための日常的なメールアクセスプロトコルです。一方、**SSH ポートフォワーディング** は、公開されている SSH サーバ（22 番）との間に確立した暗号化セッションをトンネル（中継路）として流用し、外部へポートを公開していない社内データベース等の任意 TCP ポートへ安全に中継接続するための管理・運用向け手法です。

3. **DNSSEC と DoH の防御レイヤの違い、および盗聴回線上の鍵配送ジレンマ（本節への接続）：**

    * **(a) DNSSEC と DoH の役割比較：**
        **DNSSEC** は権威サーバからの DNS 応答にデジタル署名を付与することで「正規の権威サーバ由来であり改ざんされていないこと（完全性・真正性）」を保証しますが、問い合わせ自体は暗号化しないため盗聴は防げません。一方、**DoH（DNS over HTTPS）** は端末とフルサービスリゾルバ間の通信経路を HTTPS（TLS）で暗号化することで、公衆 Wi-Fi 経路上の第三者による閲覧先ドメインの盗聴防止（機密性）と経路上の改ざん防止を担います。

    * **(b) 盗聴回線上の鍵配送問題：**
        送信側と受信側が同じ秘密鍵を使う方式では、最初の秘密鍵そのものを盗聴されている回線へそのまま送れば盗聴者にも鍵が知られてしまい暗号の意味がなくなるという **鍵配送問題** が生じます。このジレンマを解決するのが、本節で学ぶ **公開鍵暗号** と、それを高速な共通鍵暗号と組み合わせた **ハイブリッド暗号** です。

## 7-6. 暗号技術の基礎（共通鍵AES・暗号モード・公開鍵RSA・ハイブリッド暗号）

### 1. 動機（Why）：なぜ平文通信は危険で、なぜ「共通鍵」と「公開鍵」の両方が必要なのか

前節（[7-5節](7-5.md)）までで、世界中のコンピュータを繋ぐネットワークの全階層（物理・リンク・IP・TCP/QUIC・DNS・HTTP・メール・SSH）が完成しました。しかし、ここまでに学んだパケットは、特別な対策をしなければ**すべて平文（暗号化されていない生のデータ）**で流れています。

インターネット上のパケットは、カフェの Wi-Fi 電波、見知らぬ ISP のルータ、海底ケーブルなど、自分が管理できない無数の機器を通過します。平文のままでは、経路上の誰かがパケットを覗き見る（**盗聴**）だけでパスワードやクレジットカード番号が丸見えになり、途中で金額を書き換える（**改ざん**）ことも、正規の銀行サーバになりすます（**なりすまし**）ことも容易です。これらに対抗するため、ネットワークセキュリティでは **機密性（Confidentiality）・完全性（Integrity）・認証（Authentication）・否認防止（Non-repudiation）** の **4 要素** を暗号技術によって体系的に満たす必要があります（本節で機密性と完全性の基礎を扱い、次節 [7-7節](7-7.md)で認証と否認防止・プロトコル統合へ進みます）。

これを支えるのが **暗号技術（Cryptography）** です。しかし、暗号を現実のインターネットへ組み込むときには、次の2つの根本的なトレードオフに直面します。

1. **共通鍵暗号の「鍵配送問題」：**
    送信者と受信者が同じ 1 本の秘密鍵 $K$ を使う **共通鍵暗号（対称暗号）** は非常に高速ですが、「初めて接続する東京のブラウザと米国の Web サーバが、盗聴者が見ている回線の上で、どうやって最初の秘密鍵 $K$ を安全に共有するのか？」という鶏と卵のジレンマ（**鍵配送問題**）が解けません。

2. **公開鍵暗号の「計算コストの重さ」：**
    暗号化用の「公開鍵」と復号用の「秘密鍵」を分離する **公開鍵暗号（非対称暗号）** を使えば鍵配送問題はきれいに解けますが、巨大な整数のべき乗剰余演算を伴うため、共通鍵暗号に比べて **数百倍〜数千倍も遅い** という欠点があります。数 GiB の動画や Web ページ全体を直接暗号化するには重すぎます。

本節では、このジレンマを解決する現代暗号の骨格として、**共通鍵暗号（AES）とブロック暗号の利用モード（ECB・CBC・CTR・GCM）**、**公開鍵暗号（RSA）の数理**、そして両者の長所を統合する **ハイブリッド暗号** の仕組みを整理します。

---

### 2. 具体例と動作イメージ（Toy Model）

アルゴリズムの全体構造に入る前に、2つの小さな実験で「公開鍵暗号（RSA）が本当に別々の鍵で元に戻る不思議」と「ブロック暗号の使い方を誤ると何が起きるか」を手を動かして確かめます。

#### 実験A：小さな素数 $p = 5,\; q = 11$ で RSA の暗号化と復号を手計算する

公開鍵暗号 **RSA** は、「暗号化する鍵 $(e, n)$ は世界中に公開してよいのに、復号する鍵 $(d, n)$ は本人しか計算できない」という一見不思議な性質を持ちます。小さな数で実際に試してみましょう。

1. **鍵ペアの生成（受信者 Bob が秘密裏に行う）：**

    * 2つの素数 $p = 5,\; q = 11$ を選び、積 $n = p \times q = \mathbf{55}$ を計算します。
    * オイラーのトーシェント関数 $\phi(n) = (p - 1)(q - 1) = 4 \times 10 = \mathbf{40}$ を計算します。
    * $40$ と互いに素な公開指数として $e = \mathbf{3}$ を選びます（$\gcd(3, 40) = 1$）。
    * $e \cdot d \equiv 1 \pmod{40}$ を満たす秘密指数 $d$ を求めます（大きな整数では **拡張ユークリッドの互除法** で高速に求まります）。ここでは $3 \times 27 = 81 = 2 \times 40 + 1 \equiv 1 \pmod{40}$ なので $d = \mathbf{27}$ です。
    * **公開鍵：** $(e, n) = (3, 55)$ を世界中へ公開します。**秘密鍵：** $d = 27$（および $p, q, \phi(n)$）は厳重に秘密にします。

2. **暗号化（送信者 Alice が公開鍵 $(3, 55)$ を使って平文 $M = 7$ を暗号化）：**

    $$C = M^e \bmod n = 7^3 \bmod 55 = 343 \bmod 55 = \mathbf{13}$$

    （$55 \times 6 = 330$、$343 - 330 = 13$）。Alice は暗号文 $C = 13$ を盗聴回線へ送ります。

3. **復号（受信者 Bob が秘密鍵 $d = 27$ を使って暗号文 $C = 13$ を復号）：**
    $M' = C^d \bmod n = 13^{27} \bmod 55$ を、指数を2進展開（$27 = 16 + 8 + 2 + 1$）する **繰り返し二乗法** で計算します。

    * $13^1 \equiv 13 \pmod{55}$
    * $13^2 = 169 \equiv 4 \pmod{55}$
    * $13^4 \equiv 4^2 = 16 \pmod{55}$
    * $13^8 \equiv 16^2 = 256 \equiv 36 \pmod{55}$
    * $13^{16} \equiv 36^2 = 1296 \equiv 31 \pmod{55}$

    これらを掛け合わせると、

    $$13^{27} \equiv 31 \times 36 \times 4 \times 13 \equiv 16 \times 4 \times 13 \equiv 9 \times 13 = 117 \equiv \mathbf{7} \pmod{55}$$

    元の平文 **$M = 7$** が正確に復元されました。

#### 実験B：同じブロックをそのまま暗号化する「ECB モード」の破綻

共通鍵暗号（AES）は、一度に固定長（128 ビット $= 16$ バイト）のブロックを 1 個だけ暗号化する部品です。では、数メガバイトの画像ファイルを暗号化するとき、単純に先頭から 16 バイトずつ切り出して、**毎回同じ鍵 $K$ で独立に暗号化（ECB モード）** したらどうなるでしょうか。

同じ入力ブロック $P_i = P_j$ からは、必ず **まったく同じ暗号文ブロック $C_i = C_j$** が出力されます。そのため、たとえば背景が真っ白で中央に黒いペンギンが描かれた画像を ECB モードで暗号化すると、背景の白い 16 バイト群はすべて同じランダム模様になり、黒い領域は別のランダム模様になるため、**暗号文を画像として表示するだけでペンギンの輪郭がくっきり浮かび上がってしまいます（有名な ECB ペンギン問題）**。暗号部品（AES）自体がどれほど強固でも、長いデータへ適用する「利用モード」を誤ると機密性が破綻するのです。

### 3. 構造・アルゴリズム・実装（What）

#### (1) 共通鍵暗号（対称暗号）：DES からの移行と AES の内部構造

暗号化と復号に**同一の秘密鍵 $K$** を用いる方式を **共通鍵暗号（Symmetric-Key Cryptography）** と呼びます。1977年に標準化された **DES（Data Encryption Standard）** はブロック長 64 ビット・鍵長わずか **56 ビット**（約 $7.2 \times 10^{16}$ 通り）だったため、計算機性能の向上により 1990年代末には専用ハードウェアで数時間〜数日以内に総当たり解読が可能となりました。その代替として 2001年に米国標準技術研究所（NIST）が公募・採用した現代の世界標準が **AES（Advanced Encryption Standard）** です。

* **基本仕様：** ブロック長は常に **128 ビット（16 バイト）固定** です。鍵長は **128 / 192 / 256 ビット** の3種類があり、鍵長に応じて同じ変換処理（**ラウンド**）をそれぞれ **10 / 12 / 14 回** 繰り返します。
* **SPN（Substitution-Permutation Network）構造：** AES は 16 バイトのデータを $4 \times 4$ のバイト行列（ステート）として扱います。まず第 1 ラウンドの直前に、平文ブロックと初期ラウンド鍵の XOR をとる **初期 `AddRoundKey`（ホワイティング）** を 1 回行い、その後に各ラウンドで次の 4 ステップを繰り返すことで（ただし最終ラウンドのみ `MixColumns` を省略します）、平文の 1 ビットの変化が暗号文全体へ雪崩のように波及する **混乱（Confusion）** と **拡散（Diffusion）** を実現します。

    1. **`SubBytes`（バイト置換）：** 各バイトを非線形な変換表（S-Box）で別のバイトへ置き換えます（混乱）。
    2. **`ShiftRows`（行シフト）：** $4 \times 4$ 行列の 0〜3 行目をそれぞれ左へ 0, 1, 2, 3 バイト巡回シフトします（拡散）。
    3. **`MixColumns`（列混合）：** 各列の 4 バイトに、256 個の元からなる有限体 $\text{GF}(2^8)$ 上の固定行列を掛けて混ぜ合わせます（拡散）。
    4. **`AddRoundKey`（ラウンド鍵加算）：** 元の秘密鍵 $K$ から拡張生成したそのラウンド専用の鍵とビットごとの XOR をとります。

AES の各ステップは単純な表引き・シフト・XOR のみで構成されるためソフトウェアでも高速ですが、現代の x86-64 / ARM / RISC-V CPU には AES の 1 ラウンドをわずか 1 命令で実行する専用ハードウェア命令（**AES-NI** 等）が内蔵されており、**1 コアあたり数 GB/s** という主記憶帯域に迫る速度で暗号化できます。

#### (2) ブロック暗号の利用モード（ECB・CBC・CTR・GCM）

実験Bの「ECB ペンギン問題」を防ぎ、16 バイトより長い任意長メッセージや通信ストリームを安全に暗号化するための繋ぎ方を **暗号利用モード（Mode of Operation）** と呼びます。代表的な 4 方式を整理します（図7-6-1）。

1. **ECB（Electronic Codebook）モード【使用禁止】：**
    各ブロックを完全に独立に $C_i = E_K(P_i)$ で暗号化します。同じ平文ブロックが同じ暗号文ブロックになりパターンが漏洩するほか、ブロックの順序入れ替えや削除も検知できないため、実システムでは原則使用しません。

2. **CBC（Cipher Block Chaining）モード：**
    直前の暗号文ブロック $C_{i-1}$ と次の平文ブロック $P_i$ の **XOR** をとってから暗号化します（$C_i = E_K(P_i \oplus C_{i-1})$）。先頭ブロック $P_1$ には予測不能なランダム値である **IV（Initialization Vector：初期ベクトル）** を $C_0$ として用います。

    * **長所：** 同じ平文でも毎回 IV を変えればまったく異なる暗号文になります。
    * **短所：** $C_i$ の計算に $C_{i-1}$ が必要なため**暗号化を並列化できず**、16 バイトの倍数へ揃えるための末尾パディング（不足バイト数で埋める PKCS#7 等）が必要になります。

3. **CTR（Counter）モード：**
    平文ブロックを直接 AES へ入れず、毎回一意な **Nonce（Number used once）＋ 連番カウンタ（`Ctr = 1, 2, ...`）** を AES で暗号化して擬似乱数ストリームを作り、それと平文の XOR をとります（$C_i = P_i \oplus E_K(\text{Nonce} \parallel i)$、$i = 1, 2, \dots$）。

    * **長所：** ブロック暗号を **ストリーム暗号** のように扱えるためパディングが不要です。暗号化も復号も **全ブロック並列計算** でき、ランダムアクセスも可能です。

4. **GCM（Galois/Counter Mode）【現代の標準】：**
    高速・並列可能な **CTR モードによる暗号化（機密性）** に、128 ビット有限体 $\text{GF}(2^{128})$ 上の乗算ハッシュ（GHASH）による **認証タグ（改ざん検知：完全性）** を統合した **認証付き暗号（AEAD：Authenticated Encryption with Associated Data）** です。TLS 1.3 や HTTPS、QUIC の事実上の標準です（※厳密な AES-GCM 仕様［NIST SP 800-38D］では初期カウンタ値 $J_0 = \text{Nonce} \parallel 1$ を認証タグのマスク用に予約しデータ暗号化は $2$ 以降から進めますが、図7-6-1 では CTR との対応を明快に示すため `Ctr = 1, 2` で統一表記しています）。

#### (3) 公開鍵暗号（非対称暗号）と RSA の数学的根拠

1976年のディフィーとヘルマンの概念提唱に続き、1977年にリベスト＝シャミア＝エーデルマンの3氏が発明した **RSA** は、**「一方向性落とし戸関数（順方向の計算は簡単だが、秘密の『落とし戸』を知らない限り逆算が計算量的に困難な関数）」** を数論で構成しました（図7-6-2）。

* **正しさの証明（オイラーの定理）：**
    異なる2つの素数 $p, q$ の積 $n = pq$ に対して $\phi(n) = (p - 1)(q - 1)$ とし、$ed \equiv 1 \pmod{\phi(n)}$ を満たす整数 $e, d$ をとると、$ed = k\,\phi(n) + 1$（$k$ は整数）と書けます。平文 $0 \le M < n$ が $n$ と互いに素（$\gcd(M, n) = 1$）のとき、オイラーの定理 $M^{\phi(n)} \equiv 1 \pmod{n}$ より（$p$ または $q$ の倍数の場合も中国剰余定理から同様に成立します）、

    $$(M^e)^d = M^{ed} = M^{k\phi(n) + 1} = \bigl(M^{\phi(n)}\bigr)^k \cdot M \equiv 1^k \cdot M = M \pmod{n}$$

    となり、公開鍵 $e$ で暗号化したものを秘密鍵 $d$ で必ず元の平文 $M$ へ戻せます。

* **安全性の根拠（素因数分解問題の困難性）：**
    攻撃者が知っているのは公開鍵 $(e, n)$ だけです。ここから秘密鍵 $d$ を求めるには $\phi(n) = (p-1)(q-1)$ が必要であり、そのためには **$n$ を元の2つの素数 $p, q$ へ素因数分解** しなければなりません。掛け算 $p \times q = n$ は **1024 ビット（約 309 桁）の素数同士** でもマイクロ秒で終わりますが、逆にその積である **2048 ビット（約 617 桁）の合成数 $n$** を現代のスーパーコンピュータで素因数分解するには現実的な時間では解けません。

* **楕円曲線暗号（ECC：Elliptic Curve Cryptography）：**
    現代の TLS 1.3 や SSH では、RSA に代わって楕円曲線上の離散対数問題の困難性に基づく **ECC**（X25519 / Ed25519 / P-256 等）が主流になっています。RSA で 2048〜3072 ビットの鍵長が必要な安全性を、ECC はわずか **256 ビット** の短い鍵長で達成できるため、計算速度・通信量・モバイル端末の消費電力のすべてで大きく優れています。

> **【コラム：ケルクホフスの原理：なぜ暗号アルゴリズムは「秘密」ではなく「世界中へ公開」するのか】**
>
> 1883年、オランダの暗号学者オーギュスト・ケルクホフス（Auguste Kerckhoffs）は、現代暗号の基本原則となる **ケルクホフスの原理（Kerckhoffs's Principle）** を提唱しました。
>
> > 「暗号方式の安全性は、**アルゴリズム（仕組み）の秘密に依存してはならず、鍵の秘密だけに依存すべきである**。」
>
> 素朴に考えると、「計算手順（アルゴリズム）自体を社外秘にして隠せばもっと安全ではないか（隠蔽によるセキュリティ：Security through Obscurity）」と思えるかもしれません。しかし、アルゴリズムを隠すと世界中の専門家による厳しい脆弱性検証を受けられず、見落としのある弱い暗号になりがちです。さらに、ソフトウェアを逆アセンブルされたり内部から仕様が漏れたりした瞬間に全システムが破綻し、アルゴリズムごと総入れ替えする羽目になります。
>
> AES も RSA も SHA-256 も、その数式と設計図は**世界へ公開**され、世界中の暗号研究者が何十年も総掛かりで解読を試みた末に「それでも鍵を知らない限り破れない」と実証されたからこそ、銀行や政府の通信でも安心して利用できます。

#### (4) ハイブリッド暗号（Hybrid Cryptosystem）：共通鍵と公開鍵の融合

1節で見た通り、共通鍵暗号（AES）は高速ですが鍵配送ができず、公開鍵暗号（RSA/ECC）は鍵配送ができますが計算が重すぎます。現実の HTTPS / TLS・SSH・メール暗号化規格 PGP などの暗号プロトコルはすべて、両者の長所を組み合わせた **ハイブリッド暗号** を採用しています（図7-6-3）。

1. **セッション鍵の生成：** 送信者 Alice は、今回の通信 1 回限りで使い捨てるランダムな共通鍵（**セッション鍵 $K_s$**、例：AES-256 用の 256 ビット乱数）をローカルで生成します。
2. **データ本体の高速暗号化（共通鍵暗号）：** 何メガバイトもある巨大な平文データ本体 $M$ を、高速な **AES-GCM** とセッション鍵 $K_s$ で暗号化します。
3. **セッション鍵だけの保護（公開鍵暗号）：** たった 32 バイトしかないセッション鍵 $K_s$ だけを、受信者 Bob の **公開鍵** で暗号化します（あるいは次節の Diffie-Hellman 鍵交換で共有します）。
4. **送信と復号：** 暗号化されたデータ本体と暗号化されたセッション鍵をセットで送ります。Bob はまず自分の**秘密鍵**で 32 バイトのセッション鍵 $K_s$ を取り出し、続いて $K_s$ を使ってデータ本体を AES-GCM で高速に復号します。

### 4. 限界と補正（Critique & Adaptation）

暗号アルゴリズムの数式自体は数学的に堅牢でも、実際のシステムへ組み込む際には次の **4つの重大な注意点と補正** を押さえておく必要があります。

#### (1) 「暗号化だけ」では改ざんを防げない（AEAD の必須化と Nonce 再利用の危険性）

CBC や CTR のような純粋な暗号化モードが保証するのは **機密性（中身が読めないこと）だけ** であり、**完全性（途中で書き換えられていないこと）は保証しません**。たとえば CTR モードでは $C_i = P_i \oplus \text{KeyStream}_i$ であるため、攻撃者が暗号文の特定のビットを反転すると、復号後の平文の同じ位置のビットもそのまま狙い通りに反転してしまいます（**展性／可鍛性：Malleability**）。CBC でも、復号時のパディングエラーの有無をサーバの応答から覗き見て平文を1バイトずつ割り出す **パディングオラクル攻撃** が知られています。

* **補正：** 現代のシステムでは、暗号化と改ざん検知を1つの安全な部品へ統合した **AEAD（AES-GCM や ChaCha20-Poly1305）** を使うことが現在の標準です。
* **Nonce 再利用の禁止：** CTR や AES-GCM において、**同じ鍵 $K$ で同じ Nonce を 2 回使い回すことは重大な脆弱性になります**。2つの暗号文の XOR をとると $C_1 \oplus C_2 = (P_1 \oplus S) \oplus (P_2 \oplus S) = P_1 \oplus P_2$ と鍵ストリーム $S$ が消えて平文の情報が露出し、さらに GCM では認証鍵まで逆算されて偽造が可能になります。

#### (2) 素の RSA（教科書 RSA）の危険性と OAEP パディング

実験Aで計算した素の RSA（$C = M^e \bmod n$）をそのまま使うこと（**教科書 RSA**）は実務では使用できません。同じ平文 $M$ を送るたびに毎回同じ暗号文 $C$ になる（決定論的暗号）ため、たとえば送信候補が `"YES"` か `"NO"` の2択なら、攻撃者が両方を公開鍵で暗号化して比べるだけで中身を即座に判別できます。また、公開指数が小さいとき（例：$e = 3$）に平文も小さく $M^3 < n$ が成り立つと、法 $n$ の剰余が一度も折り返されないため、攻撃者は秘密鍵なしで暗号文 $C$ の単なる整数 3 乗根 $\sqrt[3]{C}$ をとるだけで平文を復元できてしまいます（小指数攻撃）。

* **補正：** 実際の RSA 暗号化では、平文 $M$ へ毎回新しいランダムな詰め物を混ぜてから暗号化する **OAEP（Optimal Asymmetric Encryption Padding）** を必ず適用し、同じ平文でも毎回まったく異なる暗号文になる（確率的暗号）ようにします。

#### (3) 量子コンピュータの脅威と耐量子計算機暗号（PQC）

現在実用化に向けた研究が進む大規模な **量子コンピュータ** は、現代暗号に対して非対称な影響を与えます。

* **共通鍵暗号（AES）への影響（Grover のアルゴリズム）：** 探索の計算量が平方根（$2^k \to 2^{k/2}$）へ縮むため、AES-128 の実質強度が 64 ビット相当へ落ちますが、**鍵長を 2 倍の AES-256 へ増やすだけで十分に耐えられます**。
* **公開鍵暗号（RSA / ECC）への影響（Shor のアルゴリズム）：** 素因数分解や離散対数問題を**多項式時間**で解けてしまうため、大規模量子コンピュータが実現すると **RSA も ECC も安全性が崩壊** します。
* **補正：** 量子コンピュータでも解くのが困難とされる格子問題などに基づく **耐量子計算機暗号（PQC：Post-Quantum Cryptography、NIST 標準化済みの ML-KEM［旧 Kyber］や ML-DSA［旧 Dilithium］等）** の導入が進んでおり、すでに Chrome や Cloudflare の TLS 1.3 では既存の ECC と ML-KEM を併用するハイブリッド鍵交換が実用化されています。

#### (4) 公開鍵暗号だけでは防げない「公開鍵のすり替え（中間者攻撃）」（次節への動機）

ハイブリッド暗号で整って見える通信にも、実は **1 つの大きな課題** が残っています。Alice が Bob の公開鍵 $(e, n)$ をインターネット越しに受け取るとき、**経路上に潜む攻撃者 Mallory が Bob の公開鍵を「Mallory 自身の公開鍵」へすり替えて Alice へ渡してしまったら** どうなるでしょうか。

Alice はそれが偽物だと気づかずに Mallory の公開鍵でセッション鍵を暗号化して送り、Mallory は自分の秘密鍵で中身をすべて盗み見たあと、本物の Bob の公開鍵で暗号化し直して転送します（**中間者攻撃：MITM**）。「目の前にあるこの公開鍵が、本当に本物の `bank.example.com` の持ち物であるとどうやって証明するか？」という最後のパズルを解くのが、[第7部](../index.md#part-7)の最終節となる次節（[7-7節](7-7.md)）の **デジタル署名・証明書（PKI）・TLS / HTTPS** です。

### 5. 接続と展望（Bridge）：本節の内容が後半のどの部に繋がるか

1. **次節（[7-7節](7-7.md)：認証・鍵交換とプロトコル保護［署名・DH・Kerberos・TLS/HTTPS・IPsec］）：**
    本節の最後で残った「公開鍵のすり替え（中間者攻撃）」を防ぐ **デジタル署名と公開鍵基盤（PKI・認証局 CA）**、前方秘匿性を実現する **Diffie-Hellman（ECDHE）鍵交換**、そしてこれらすべてを統合した **TLS 1.3 / HTTPS・IPsec** へ進み、[第7部](../index.md#part-7)を完結させます。

2. **[第6部](../index.md#part-6)（[6-2節](../6/6-2.md)：CRC の限界）との回収：**
    [6-2節](../6/6-2.md)で「CRC は偶然のノイズは検出できるが、暗号鍵を含まないため悪意ある改ざんは一切防げない」と確認した課題が、本節の **認証付き暗号（AES-GCM / AEAD）** と次節の HMAC・デジタル署名によって解決されます。

3. **[第5部](../index.md#part-5)（[5-7節](../5/5-7.md)：アクセス制御）との接続：**
    [5-7節](../5/5-7.md)のアクセス制御（認可）は「本人確認が済んでいる」前提でしたが、本節と次節の暗号・認証技術が揃うことで、ネットワーク越しのシステム全体で **機密性・完全性・認証・否認防止** の 4 要素が揃います。

### 理解度チェック（次節へ進む前の確認）

本節の RSA 手計算と決定性攻撃・CTR の Nonce 再利用と可鍛性・未認証公開鍵の MITM と耐量子影響を確認し、[第7部](../index.md#part-7)の最終節（[7-7節](7-7.md)）へ繋ぐ問いを置きます。

> **【確認の問い】**
>
> 1. **（小さな素数での RSA 手計算と教科書 RSA への決定性攻撃）**
>     素数 $p = 3,\; q = 11$、公開指数 $e = 3$ を使ってパディングなしの教科書 RSA の鍵ペアを作ります。
>
>     * (a) $n = pq$、$\phi(n) = (p - 1)(q - 1)$、および $e \cdot d \equiv 1 \pmod{\phi(n)}$ を満たす秘密指数 $d$（$1 < d < \phi(n)$）を求めたうえで、平文 $M = 4$ を暗号化した暗号文 $C = M^e \bmod n$ と、秘密鍵 $d$ による復号 $C^d \bmod n$ が元の $4$ に戻ることを検算してください（ヒント：$31 \equiv -2 \pmod{33}$）。
>     * (b) 送信者が `"YES"` を $M = 4$、`"NO"` を $M = 5$ に割り当てて上記の教科書 RSA で暗号化し、暗号文 $C = 26$ を送信しました。秘密鍵 $d$ を知らない盗聴者が、公開鍵 $(e, n) = (3, 33)$ だけを使って平文が `"YES"` と `"NO"` のどちらかを特定する計算を示し、実務の RSA でこれを防ぐパディング方式の名称を答えてください。
>
> 2. **（CTR モードの Nonce 再利用による平文復元と可鍛性・AES-GCM の検知）**
>     AES-CTR モード（認証タグなし）による 1 バイトの暗号化 $C = P \oplus S$（$S$ は鍵ストリーム）を考えます。
>
>     * (a) 同じ鍵 $K$ と同じ Nonce を誤って再利用し、2 つの暗号文バイト $C_1 = \texttt{0x5A},\; C_2 = \texttt{0x4F}$ が観測されたとします。盗聴者が $P_1 = \texttt{0x41}$（ASCII `'A'`）を知っているとき、鍵 $K$ を知らずに $P_2 = C_1 \oplus C_2 \oplus P_1$ を 16 進数で復元してください。
>     * (b) 送金金額の文字 `'0'`（ASCII `0x30`）を暗号化したバイト $C$ に対し、攻撃者が経路上で $C' = C \oplus \texttt{0x09}$ と改ざんしました。受信側が $C'$ を復号したときの平文バイト（16 進数と ASCII 文字）を求め、なぜこの改ざん（展性／可鍛性）が成立するか、また **AES-GCM** ではどう防がれるかを説明してください。
>
> 3. **（未認証公開鍵交換への MITM トレースと量子コンピュータの非対称な影響）**
>     次の 2 つの問いに答えてください。
>
>     * (a) ハイブリッド暗号で Alice が Bob の公開鍵を通信経路経由で受け取るとき、攻撃者 Mallory が公開鍵をすり替える **中間者攻撃（MITM）** がどのように成立するか、①公開鍵のすり替え、②Alice からの送信データの解読、③Bob への再暗号化転送の 3 ステップで簡潔にトレースしてください。
>     * (b) 大規模な量子コンピュータが実現した場合、共通鍵暗号（AES）と公開鍵暗号（RSA / ECC）では安全性への影響がどのように非対称になるでしょうか。**Grover のアルゴリズム** と **Shor のアルゴリズム** の違いおよびそれぞれの対策に触れて説明してください。
