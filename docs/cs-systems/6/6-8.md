### 前節（6-7）の確認問題の解答

前節の最後に提示した3つの問いの解答を確認します。

1. **OSPF 参照帯域設定ミスの診断と修正後の Dijkstra 法（`A–B: 100M`, `A–C: 10G`, `C–B: 10G`）：**

    * **(a) デフォルト参照帯域 $100\text{ Mbps}$ のときの各コストと選択経路：**

        * `A–B`（$100\text{ Mbps}$）：$\max(1, \lfloor 100/100 \rfloor) = \mathbf{1}$ です。
        * `A–C`（$10\text{ Gbps} = 10{,}000\text{ Mbps}$）：$\max(1, \lfloor 100/10{,}000 \rfloor) = \max(1, 0) = \mathbf{1}$ です。
        * `C–B`（$10\text{ Gbps}$）：$\max(1, \lfloor 100/10{,}000 \rfloor) = \mathbf{1}$ です。

        結果として 1 ホップ直結の `A → B` はコスト `1`、2 ホップの `A → C → B` はコスト `1 + 1 = 2` となるため、OSPF は **100 倍遅い `A → B`（$100\text{ Mbps}$）** を選んでしまいます。整数切り捨てかつ最小コスト 1 という規則のもとでは、参照帯域 $100\text{ Mbps}$ を超える高速リンクがすべてコスト `1` に丸められて帯域差が消えてしまうためです。

    * **(b) 参照帯域 $100\text{ Gbps}$ 修正後の各コストと Dijkstra 法の実行：**
        各リンクコストは `A–B` $= 100{,}000 / 100 = \mathbf{1{,}000}$、`A–C` $= 100 / 10 = \mathbf{10}$、`C–B` $= 100 / 10 = \mathbf{10}$ です。始点 A から Dijkstra 法を実行します。

        * **ステップ 0（確定集合 `{A}`）：** $D(\text{B}) = 1{,}000$（直前 A）、$D(\text{C}) = 10$（直前 A） $\implies$ 最小の **C（コスト `10`）** を確定します。
        * **ステップ 1（`{A, C}`）：** C 経由で更新すると $D(\text{B}) = \min(1{,}000,\; 10 + 10) = \mathbf{20}$（直前 C） $\implies$ **B（コスト `20`）** を確定します。

        よって最短経路は **C：コスト `10`（`A → C`）**、**B：コスト `20`（`A → C → B`）** となります。なお、Dijkstra 法が正しく動作するためには **すべてのリンクコストが非負（$c \ge 0$）であること** が前提条件です。

2. **3 ノード三角形トポロジでのポイズンリバース破綻トレース：**

    * **(a) `C–X` 断線直前に A が広告している距離：**
        A の宛先 X への次ホップは C（B ではない）であるため、ポイズンリバース規則に従い、A は **C へは $\infty$** を広告する一方、**B へは未毒化の距離 `2`** を広告しています。

    * **(b) `C–X` 断線後の無限カウントのステップトレース：**

        1. **B の更新：** B は C から $D_C(X) = \infty$ を受け取りますが、A の次ホップが B ではなかったために B の手元には A からの広告値 `2` が残っています。そのため B は $D_B(X) = 1 + 2 = \mathbf{3}$（次ホップ **A**）へ更新し、A へ $\infty$、次ホップでない **C へ `3`** を広告します。
        2. **C の更新：** C は B から `3` を受け取り、$D_C(X) = 1 + 3 = \mathbf{4}$（次ホップ **B**）へ更新して、B へ $\infty$、次ホップでない **A へ `4`** を広告します。
        3. **A の更新：** A は B から $\infty$、C から `4` を受け取り、$D_A(X) = 1 + 4 = \mathbf{5}$（次ホップ **C**）へ更新して、C へ $\infty$、次ホップでない **B へ `5`** を広告します。
        4. **B の再更新：** B は A から `5` を受け取り $D_B(X) = 1 + 5 = \mathbf{6}$（次ホップ **A**）へ更新して C へ `6` を広告します。

        このように 3 ノード循環（`B → A → C → B`）では各ルータが「自分の次ホップではないもう一方の隣人」へ距離を広告し続けるため、ポイズンリバースをすり抜けて無限カウントに陥ります。

3. **単一エリア OSPF 障害診断と IGP の限界：**

    * **(a) 単一エリア 2,000 台でのフラッピング障害と対策：**
        末端の 1 本のリンクが点滅するたびに LSA が 2,000 台すべてのルータへフラッディングされ（LSA の嵐）、全ルータが毎回巨大な LSDB 上で Dijkstra 法（SPF）を再計算し続けるため、制御帯域と全ルータの CPU が飽和してネットワーク全体が不安定になります。OSPF では **マルチエリア分割（エリア 0 バックボーンと通常エリアへの分割）** を行い、詳細な LSA を各エリア内に封じ込めて ABR から集約経路のみを伝えることで影響を局所化できます。

    * **(b) 世界中を 1 つの OSPF で運用できない 2 つの理由：**
        ① **規模の壁：** 世界中の数百万台のルータ間で LSA をフラッディングし全地図を同期するのは制御トラヒックと計算負荷の面で破綻するためです。② **自律性とポリシーの壁：** 異なる会社（ISP・企業・大学＝AS）間では物理的な最短コストよりも契約・課金・タダ乗り防止などの経済的・運用的ポリシーが最優先され、コスト最小化のみを行う IGP ではこれを表現できないためです。

## 6-8. 動的ルーティング②：AS間経路制御（BGP）・MPLSとエニーキャスト

### 1. 動機（Why）：なぜインターネットは「組織内の最短経路」と「組織間の契約経路」の 2 階層に分かれているのか

前節（[6-7節](6-7.md)）では、1つの大学や企業、あるいは1社のプロバイダ（ISP）の内部でルータが自律的に最短経路を計算するプロトコル（RIP と OSPF）を学びました。しかし、インターネットとは「単一の組織が運営する1つの巨大なネットワーク」ではなく、**世界中の 7 万以上の独立した組織（ISP、クラウド事業者、大学、通信キャリア、大企業）が運営するネットワーク同士が相互接続した「ネットワークのネットワーク」**です。

単一の管理主体のもとで運用されるネットワークの単位を **AS（Autonomous System：自律システム）** と呼び、各 AS には世界一意の **AS 番号（ASN：16ビットまたは32ビット）** が割り当てられます。

前節の最後で確認した通り、AS の内側（**IGP：Interior Gateway Protocol**、OSPF 等）と、AS 同士の外側（**EGP：Exterior Gateway Protocol**、**BGP**）では、経路選択の目的関数そのものがまったく異なります。

1. **AS の内側（IGP：OSPF）：** 同じ組織の所有物なので、目的は純粋な **性能（帯域幅・遅延の最小化）** です。
2. **AS の外側（EGP：BGP）：** 互いに独立した営利企業や国家間の接続なので、最優先されるのは物理的な最短距離ではなく **経済的・運用的なポリシー（契約・課金・セキュリティ）** です。たとえば「競合他社どうしの通信を自社回線でタダ乗り（トランジット）させたくない」「安く使える直接接続（ピアリング）を優先したい」といったルールを表現できなければなりません。

さらに、大規模な通信事業者（ISP）のコア網では、何十万行もの BGP 経路表を途中のすべてのルータで毎回 LPM 検索する負荷を避けて高速かつ柔軟にトラヒックを誘導する **MPLS** が広く使われています。また、BGP の経路広告の仕組みを応用して、世界中の利用者を自動的に最寄りのサーバ拠点へ導く **エニーキャスト（Anycast）** も現代の DNS や CDN に不可欠な技術です。

本節では、[第6部](../index.md#part-6)の集大成として **BGP（パスベクトル・eBGP/iBGP・ベストパス選択）**、**MPLS（ラベルスイッチング）**、そして **エニーキャスト** の3つを整理します。

---

### 2. 具体例と動作イメージ（Toy Model）

仕様の整理に入る前に、2つの小さなシナリオで「BGP のポリシー制御（タダ乗り防止）」と「エニーキャストの仕組み」を直感的に掴みます。

#### 実験A：なぜ「物理的に最短のルート」が BGP では使われないのか（バレーフリー原則）

3つの組織のネットワーク（`AS 1`・`AS 2`・`AS 3`）と、上位の大手プロバイダ（`AS 100`）があるとします。

* 企業 `AS 2` は、インターネットへ繋がるために、ISP である `AS 1` と `AS 3` の**両方と顧客契約（マルチホーミング）**を結んでおり、どちらの ISP へも利用料を払っています。
* ある日、`AS 1` の顧客から `AS 3` の顧客へパケットを送りたい状況が生まれました。物理的な配線を見ると **`AS 1 → AS 2 → AS 3`** がわずか 2 ホップで最短に見えます。

しかし、もし企業 `AS 2` が「`AS 3` 宛ては自分経由で行けますよ」と `AS 1` へ広告してしまったら何が起きるでしょうか。`AS 1` と `AS 3` のあいだの膨大な他人のトラヒックが、一般企業である `AS 2` の有料回線を勝手に通過（**トランジット**）し、`AS 2` は両方の ISP へ高額な通信費を払わされることになります。

そこで BGP では、**「あるプロバイダ（または対等なピア）から教わった経路を、別のプロバイダやピアへは再広告しない（自分自身のプレフィックスと自分の顧客のプレフィックスだけを広告する）」**という商業上の鉄則（**バレーフリー［Valley-Free］原則**）をポリシーとして設定します。その結果、`AS 1` から `AS 3` への通信は `AS 2` を通らず、上位の `AS 100` を経由する経路（または `AS 1`–`AS 3` 間の直接ピアリング）が選ばれます。

#### 実験B：同じ IP アドレス `1.1.1.1` が東京にもロンドンにも存在する仕組み

パブリック DNS サービス（例：Cloudflare の `1.1.1.1` や Google の `8.8.8.8`）へ `ping` を打つと、日本から打てば **数ミリ秒**（東京のサーバ）、ロンドンから打てば同じく **数ミリ秒**（ロンドンのサーバ）で応答が返ってきます。光ファイバ中の光速（約 $2 \times 10^8\text{ m/s}$）で計算しても東京〜ロンドン間（大圏距離約 $9{,}600\text{ km}$）の往復は理論上約 $96\text{ ms}$、実際の海底ケーブルや陸路の迂回・中継を含めると $150\text{ ms}$ 以上かかるはずなのに、なぜ同じ1つの IP アドレスが世界中で数ミリ秒で応答できるのでしょうか。

答えは **BGP エニーキャスト** です。東京のデータセンターもロンドンのデータセンターも、**まったく同じプレフィックス `1.1.1.0/24` を最寄りの ISP へ向かって BGP で同時広告**します。するとインターネット全体の BGP ルーティングが自動的に「東京の ISP ルータからは東京拠点が最短」「ロンドンの ISP ルータからはロンドン拠点が最短」と判断して転送表を作るため、利用者は何も意識せずに最寄りのサーバへ自動的に導かれます。

### 3. 構造・アルゴリズム・実装（What）

#### (1) BGP（Border Gateway Protocol）の仕組み：パスベクトルと eBGP / iBGP

現在のインターネット全体（バージョン 4：**BGP-4**）を束ねる **BGP** は、IP や UDP の上ではなく、信頼性のある **TCP（ポート 179）** の上でルータ同士が永続的なセッションを張って制御メッセージを交換します。

BGP が採用するアルゴリズムは、距離ベクトル（RIP）でもリンク状態（OSPF）でもない第3の方式である **パスベクトル型（Path Vector）** です（図6-8-1）。

* **広告する情報：** 単なるホップ数ではなく、**「宛先プレフィックス（例：`198.51.100.0/24`）」＋「パス属性（Path Attributes）」** の組を交換します。
* **最重要のパス属性 `AS_PATH`：** その経路情報が生成されてからこれまでに通過してきた **AS 番号のリスト**（例：`AS 300` が発信し `AS 200` を経て `AS 100` へ届いた場合は `[AS 200, AS 300]`）です。ある AS の境界ルータが別の AS へ経路を再広告するたびに、先頭へ自分自身の AS 番号を付け足します。なお、実際のデータパケットは経路広告とは**逆向き**（`AS 100 → AS 200 → AS 300`）に流れます。
* **ループ防止：** ルータは受信した経路の `AS_PATH` の中に **自分自身の AS 番号がすでに含まれていたら、即座にその経路を破棄します**。これにより、距離ベクトル型（RIP）を悩ませた**無限カウント問題が原理的に一切発生しません**。

また、BGP セッションには役割の異なる2種類があります（図6-8-1）。

1. **eBGP（External BGP）：** 異なる AS に属する境界ルータ同士のセッションです。組織間で到達可能なプレフィックスを交換し、再広告のたびに `AS_PATH` の先頭へ自 AS 番号を追加します。
2. **iBGP（Internal BGP）：** 同じ AS の内部にあるルータ同士のセッションです。eBGP で外部から学んだ経路情報を、自 AS 内の他の境界ルータやコアルータへ行き渡らせるために使います（※AS 内の次ホップまでの実際の最短経路は、[6-7節](6-7.md)の OSPF などの IGP が担当します）。ここで重要な規則として、**iBGP は同一 AS 内での転送のため `AS_PATH` に自 AS 番号を追加せず、`AS_PATH` によるループ検出が機能しません**。そのため iBGP には「別の iBGP ピアから学んだ経路を他の iBGP ピアへ再広告してはならない（iBGP スプリットホライズン）」という禁止規則が設けられており、基本構成では AS 内の全 BGP ルータ同士を 1 対 1 で直接結ぶ **iBGP フルメッシュ**（$N$ 台で $N(N-1)/2$ 本）が必要になります。大規模 AS でセッション数の爆発を避けるには、中心ルータが例外的に他ピアへ経路を反射中継する **ルートリフレクタ（Route Reflector：RR）** を導入して階層化します。

#### (2) BGP のパス属性とベストパス選択（ホットポテトルーティング）

ある宛先プレフィックスに対して複数の候補経路が届いたとき、BGP ルータは自 AS 番号を含むループ経路を除外したうえで、図6-8-1下段に示した厳密な優先順位で「たった1本のベストパス」を選びます。

1. **`LOCAL_PREF`（ローカルプリファレンス：最大値を優先）：** 管理者が自 AS 内のポリシーとして手動設定する優先度です。たとえば「無料の直接ピアリング回線は `LOCAL_PREF = 200`、有料のトランジット回線は `LOCAL_PREF = 100`」と設定すれば、たとえ AS ホップ数が少し長くても必ず安い回線が最優先されます。
2. **最短 `AS_PATH`（通過 AS 数が最小の経路を優先）：** `LOCAL_PREF` が同じなら、経由する AS の個数が少ない経路を選びます。
3. **`MED`（Multi-Exit Discriminator：最小値を優先）：** 2つの AS が複数地点（例：東京と大阪）で接続しているとき、受信側 AS が「どちらの入口から入れてほしいか」を相手へヒントとして伝える属性です。なお、異なる AS 間ではメトリックの尺度が統一されていないため、**`MED` は原則として同一の隣接 AS から受け取った複数経路の間でのみ比較**されます。
4. **ホットポテトルーティング（Hot-Potato Routing：最小 IGP コストを優先）：** 上の条件がすべて同じなら、自 AS 内の OSPF コストが最小となる**最も近い出口ルータ**へ即座にパケットを放り出します。熱いジャガイモ（他社宛てのパケット）を自社網の中に長く抱え込まず、一番近くの出口から早く他社へ渡して自社の幹線帯域を節約する合理的な経済行動です。

#### (3) MPLS（Multi-Protocol Label Switching）：Layer 2.5 の高速ラベル転送

大手通信キャリアや ISP のコア網（バックボーン）では、毎日膨大な量の顧客トラヒックが通過します。ここで、途中のすべてのコアルータに「約 100 万行の BGP フルルート」を持たせて毎回最長プレフィックス一致（LPM）を実行させる代わりに、**L2（イーサネット）ヘッダと L3（IP）ヘッダのちょうど間（Layer 2.5）にわずか 32 ビットの固定長「MPLS シムヘッダ（ラベル）」を差し込んで転送する**技術が **MPLS** です（図6-8-2）。

```text
+---------------+--------------------+-----------+-------------+
| L2 ヘッダ     | MPLS シムヘッダ(4B) | IP ヘッダ | ペイロード  |
+---------------+--------------------+-----------+-------------+
                  └─ Label(20bit) | TC(3bit) | S(1bit) | TTL(8bit)
```

MPLS シムヘッダ（32 ビット）の各フィールドは、`Label`（20 bit：転送経路を識別するラベル番号）、`TC`（3 bit：Traffic Class、優先制御 QoS や ECN のクラス識別）、`S`（1 bit：Bottom of Stack、ラベルを多段に重ねたときの最下層ラベルで `1`、まだ下にラベルが続くとき `0`）、`TTL`（8 bit：IP と同様にホップごとに減算して転送ループを防ぐ寿命カウンタ）の 4 つで構成されます。

MPLS 網のルータは役割によって2種類に分かれます。

* **入口／出口のエッジルータ（LER：Label Edge Router）：**

    * **入口（Ingress LER）：** 通常の IP パケットを受け取ると、宛先や転送等価クラス（**FEC**：Forwarding Equivalence Class、[6-2節](6-2.md)の前方誤り訂正とは別概念）を調べて先頭に MPLS ラベルを挿入（**Push**）してコア網へ送り出します。
    * **出口（Egress LER）：** MPLS ラベルを取り外し（**Pop**）、元の IP パケットとして外部ネットワークへ送り出します。

* **コアのラベルスイッチングルータ（LSR：Label Switch Router）：**

    * パケットを受け取ると、IP ヘッダを一切見ず、**20 ビットのラベル番号をラベル転送表（LFIB）で完全一致（Exact Match）検索するだけ**で、次の出力ポートと新しいラベル番号へ付け替え（**Swap**）て即座に転送します。

MPLS が現代のキャリア網で重宝される最大の理由は、単なる検索高速化（現代の ASIC/TCAM は IP LPM も十分高速）以上に、**トラヒックエンジニアリング（MPLS-TE）** と **L3 VPN** にあります。通常の IP ルーティング（OSPF）では最短経路1本へトラヒックが集中して混雑しても迂回させにくいですが、MPLS では入口ルータで明示的に「ラベル経路（**LSP：Label Switched Path**）」を指定できるため、空いている別ルートへトラヒックを計画的に分散したり、複数企業のプライベート IP 網（`192.168.1.0/24` が重複していても可）をラベルの多段重ね（ラベルスタック：`S` ビットで階層を区別）で安全に分離収容したりできます。

#### (4) 通信形態の 4 分類と BGP エニーキャスト（Anycast）

ネットワーク層のパケット配信形態は、宛先ホストの数と選び方によって次の **4種類** に分類されます。

1. **ユニキャスト（Unicast：1対1）：** 特定の1台のホスト宛てに届ける通常の通信方式です。
2. **ブロードキャスト（Broadcast：1対全員）：** 同一サブネット内の全ホストへ一斉に届ける方式です（IPv4 の ARP / DHCP 等で使われ、IPv6 では廃止されました）。
3. **マルチキャスト（Multicast：1対特定グループ）：** 特定のグループへ参加表明した複数ホスト全員へ効率よく複製配信する方式です（動画の一斉配信や OSPF の制御パケット等で使われます）。
4. **エニーキャスト（Anycast：1対「最寄りの1台」）：** 同じ1つの IP アドレスを地理的に離れた複数台のサーバへ割り当て、**ルーティング上最も近い1台**へ自動的に届ける方式です（図6-8-3）。

実験Bで触れた通り、インターネット上の **BGP エニーキャスト** では、特別なプロトコルを新設する必要はなく、**複数の拠点（東京・シンガポール・ロンドン・ニューヨーク等）からまったく同じ IP プレフィックス（例：`1.1.1.0/24`）を BGP で同時広告するだけ**で実現できます。なお、ここで選ばれる「最寄り」とは厳密な物理距離や最小 RTT（往復遅延）そのものではなく、**BGP のポリシー（`LOCAL_PREF` 等）や `AS_PATH` ホップ数に基づくルーティング上の近さ**であるため、ISP 間のピアリング構成によっては必ずしも地理的最近傍にならない場合もあります。

エニーキャストが世界のインフラ（DNS のルートサーバ、Cloudflare・Fastly 等の CDN）で標準採用されている理由は3つあります。

* **低遅延化：** ユーザは多くの場合、地理的・トポロジ的に近い拠点へ自動接続されます。
* **自動フェイルオーバー（高可用性）：** たとえば東京拠点が停電や障害で落ちると、東京からの BGP 広告が取り下げられ、日本のユーザのトラヒックは自動的に2番目に近い大阪やシンガポール拠点へ切り替わります。
* **DDoS 攻撃の局所吸収：** 世界中から大量の攻撃パケットが押し寄せても、各国の攻撃トラヒックはそれぞれの最寄り拠点へ分散吸収されるため、1箇所のサーバが集中砲火で落ちるのを防げます。

> **【コラム：BGP 経路ハイジャック（2008年 YouTube 事件）と RPKI による暗号学的防御】**
>
> BGP は 1989 年に「インターネットを構成する各組織は互いに善意で正しい経路を広告する」という**性善説（認証なし）**のもとで設計されました。そのため、どこか1社の ISP が誤設定（または悪意）で「他人のプレフィックスが自分の AS にある」と広告してしまうと、世界中のルータがそれを信じてトラヒックをそちらへ吸い込んでしまいます（**BGP 経路ハイジャック**）。
>
> 最も有名な実例が **2008年の YouTube 遮断事件** です。パキスタンの通信事業者が国内向けに YouTube をブロックしようと、自国内ルータへ YouTube のアドレス帯の一部を細かく切った **`/24` プレフィックス** としてブラックホール設定した際、誤ってそれが外部の eBGP へ漏れ出してしまいました。当時の YouTube 本家はより粗い `/22` を広告していたため、[6-5節](6-5.md)の **最長プレフィックス一致（LPM）** によって世界中のルータが `/24` を優先し、**約2時間にわたり世界中の YouTube トラヒックがパキスタンへ吸い込まれて閲覧不能**になったのです。
>
> この構造的な脆弱性に対する現代の補正が、公開鍵暗号（[第7部](../index.md#part-7) [7-7節](../7/7-7.md)）を用いた **RPKI（Resource Public Key Infrastructure）** です。IP アドレスの正当な所有者が「プレフィックス `X` を広告してよい正規の AS 番号は `AS Y` である」という電子署名付き証明書（**ROA：Route Origin Authorization**）を公開し、各 ISP のルータが受信した BGP 広告を ROA と照合して不正な経路を自動破棄（**ROV：Route Origin Validation**）する仕組みが世界中で普及しています。

### 4. 限界と補正（Critique & Adaptation）

#### (1) BGP の収束遅延・フラッピングと、エニーキャストにおける TCP 切断問題

BGP とエニーキャストには、実運用で見落とせない2つの限界があります。

1. **BGP の収束遅延とフラッピング：**
    あるリンクが不安定になって「接続 ⇄ 切断」を繰り返す（フラッピング）と、BGP の経路広告と撤回メッセージが世界中へ波及してルータの CPU を圧迫します。また、代替経路を順に試しながら探索するため、障害収束に数十秒〜数分かかることがあります（補正：短時間に何度も揺れる経路を一時的に抑制する **Route Flap Dampening** や、BGP ルートリフレクタによる iBGP フルメッシュの緩和）。

2. **エニーキャストとステートフルな TCP 通信の相性：**
    DNS のような 1 往復で完結するステートレスな UDP 通信ではエニーキャストは問題なく機能します。しかし、数分間続く **TCP 接続（[7-2節](../7/7-2.md)）** の途中で BGP の経路がわずかに揺らぎ、同じユーザからのパケットが突然「東京拠点」から「大阪拠点」へ切り替わると、大阪拠点のサーバはその TCP 接続の状態（シーケンス番号や接続情報）を保持していないため、即座にリセット（`RST`）を返して接続が切断されてしまいます。

    * **補正：** 大手 CDN では、BGP の経路揺らぎを抑える運用に加え、エッジ拠点間で状態を引き継ぐプロキシ設計や、IP アドレスではなく「接続 ID」でセッションを識別できる次世代トランスポート **QUIC（[7-3節](../7/7-3.md)）** の活用が進んでいます。

#### (2) 分散ルーティングの限界と SDN（Software-Defined Networking）への展望

[6-7節](6-7.md)（RIP・OSPF）と本節（BGP）で学んだ従来のルーティングは、**すべてのルータが独立してコントロールプレーン（経路計算の頭脳）とデータプレーン（パケット転送の手足）を両方内蔵し、互いにメッセージを交換して分散合意する**アーキテクチャでした。

しかし、大規模なクラウドデータセンターや世界規模の自社専用バックボーン（Google の B4 等）では、「各ルータがバラバラに分散計算するより、ネットワーク全体の混雑状況を1箇所で把握して最適経路を一括計算したい」という要求が強まります。この発想から生まれたのが **SDN（Software-Defined Networking）** です。SDN では、ルータからコントロールプレーンを切り離して論理的に集中化した **SDN コントローラ** へ集約し、各スイッチ／ルータへは計算済みの転送テーブル（フローテーブル）だけを配布することで、リンク利用率を大幅に高める柔軟な運用を実現しています。

> 1. **（BGP ベストパス選択アルゴリズムの優先順位トレースとホットポテト）**
>     AS 100 内部のルータ R1 が、宛先 `203.0.113.0/24` に対して次の 5 つの BGP 経路候補を受信しました（IGP コストは R1 から自 AS 内の出口境界ルータまでの OSPF コストを表します）。
>
>     * 経路 1：`LOCAL_PREF = 200`, `AS_PATH = [200, 100, 400]`, 隣接 AS = `AS 200`, `MED = 10`, IGP コスト = `5`
>     * 経路 2：`LOCAL_PREF = 100`, `AS_PATH = [300, 400]`, 隣接 AS = `AS 300`, `MED = 5`, IGP コスト = `2`
>     * 経路 3：`LOCAL_PREF = 150`, `AS_PATH = [200, 500, 400]`, 隣接 AS = `AS 200`, `MED = 20`, IGP コスト = `10`
>     * 経路 4：`LOCAL_PREF = 150`, `AS_PATH = [200, 600, 400]`, 隣接 AS = `AS 200`, `MED = 10`, IGP コスト = `15`（出口ルータ E1）
>     * 経路 5：`LOCAL_PREF = 150`, `AS_PATH = [200, 700, 400]`, 隣接 AS = `AS 200`, `MED = 10`, IGP コスト = `4`（出口ルータ E2）
>
>     * (a) これら 5 つのうち、ループ判定で即座に破棄される経路と、最終的に採用されるベストパスを、BGP の各比較ステップ（ループ検査 $\to$ `LOCAL_PREF` $\to$ `AS_PATH` 長 $\to$ `MED` $\to$ IGP コスト）の脱落理由を順に追って特定してください。
>     * (b) 最終決着に用いられた「最小 IGP コストを優先する」方針（ホットポテトルーティング）は、AS 100 にとってどのような経済的・運用上の狙いがあるか 1 文で説明してください。
>
> 2. **（バレーフリー原則の違反検出と、2008 年 YouTube BGP ハイジャック・RPKI 防御）**
>     次の 2 つの問いに答えてください。
>
>     * (a) 企業 `AS 2` が 2 つの上位 ISP（`AS 1`・`AS 3`）の双方と顧客契約（マルチホーミング）を結んでいるとき、`AS 2` が `AS 1` から学んだ経路を `AS 3` へ再広告した結果生まれる経路 `[AS 3, AS 2, AS 1]` は、なぜ商業上の鉄則（バレーフリー原則）に違反しており、`AS 2` にどのような不利益をもたらすでしょうか。
>     * (b) 2008 年の YouTube BGP ハイジャック事件において、誤広告された `/24` プレフィックスが YouTube 本家の `/22` より優先されて世界中へ波及した技術的機序（[6-5節](6-5.md)の転送規則と関連づけて）と、これを防ぐ **RPKI（ROA / ROV）** の仕組みを説明してください。
>
> 3. **（MPLS の TE / L3VPN と、エニーキャスト下での TCP 切断問題）**
>     次の 2 つの問いに答えてください。
>
>     * (a) 現代の通信事業者が単なる検索高速化以上に MPLS を重宝する 2 つの代表用途（**トラヒックエンジニアリング［MPLS-TE］** と **L3 VPN**）は、MPLS のどのような仕組み（LSP・ラベルスタック）によって実現されているでしょうか。
>     * (b) BGP エニーキャスト構成のサービスへ **TCP 接続** している最中に、BGP 経路が揺らいで宛先拠点が「東京」から「大阪」へ切り替わると、なぜ大阪拠点から `RST` が返されて通信が切断されるのでしょうか。1 往復で完結する UDP ベースの DNS 問い合わせと対比して説明してください。
