### 前節（6-7）の確認問題の解答

前節の最後に提示した3つの問いの解答を確認します。問3がそのまま本節（BGP・MPLS・エニーキャスト）の導入になります。

1. **Dijkstra 法による最短経路の手計算（始点 X：`X–Y(1), X–Z(4), Y–Z(2), Y–W(6), Z–W(1)`）：**

    * **ステップ 0（初期 `{X}`）：** $D(\text{Y}) = 1$（直前 X）、$D(\text{Z}) = 4$（直前 X）、$D(\text{W}) = \infty$ $\implies$ 最小の **Y（コスト 1）** を確定。
    * **ステップ 1（`{X, Y}`）：** Y 経由で更新すると $D(\text{Z}) = \min(4,\; 1 + 2) = \mathbf{3}$（直前 Y）、$D(\text{W}) = \min(\infty,\; 1 + 6) = 7$（直前 Y）$\implies$ 最小の **Z（コスト 3）** を確定。
    * **ステップ 2（`{X, Y, Z}`）：** Z 経由で更新すると $D(\text{W}) = \min(7,\; 3 + 1) = \mathbf{4}$（直前 Z）$\implies$ 残る **W（コスト 4）** を確定。
    
    したがって、各ノードへの **(a) 最小総コスト** と **(b) 最短経路** は次の通りです。

    * **Y：** コスト **`1`**、経路 **`X → Y`**
    * **Z：** コスト **`3`**、経路 **`X → Y → Z`**
    * **W：** コスト **`4`**、経路 **`X → Y → Z → W`**

2. **RIP の無限カウント問題と OSPF のエリア分割：**

    * **(a) 無限カウント問題の根本原因と RIP の2つの対策：**
        距離ベクトル型（RIP）では各ルータが全体の地図を持たず「隣人から聞いた距離の噂」だけを信じるため、リンク断線時に「実は自分を経由していた隣人の古い経路」を別の迂回路と誤認し、互いに距離を1ずつ増やしながら永遠に数え上げてしまいます。RIP はこれに対し、**最大ホップ数を 15 に制限（16 を到達不能 $\infty$ とみなして強制打ち切り）**することと、ある隣人経由で学んだ経路はその同じ隣人へ距離 $\infty$（16）と毒を盛って送り返す **ポイズンリバース** によって2ノード間のループを防いでいます。

    * **(b) OSPF でマルチエリア分割（エリア 0 バックボーン）を行う理由：**
        単一エリアのままルータ台数が数千台に増えると、末端のリンク障害のたびに全ルータへ LSA がフラッディングされ、巨大な LSDB の保持と重い Dijkstra 法の再計算で CPU と帯域が飽和します。エリアを分割して詳細な LSA を各エリア内に封じ込め、境界ルータ（ABR）からエリア 0 へ要約経路だけを伝えることで、障害の波及と計算負荷を大きく抑えられます。

3. **世界中の ISP 同士を繋ぐとき、なぜ OSPF ではなく BGP が必要か（本節への接続）：**
    異なる組織（AS）同士を結ぶインターネット全体では、規模の限界に加えて「契約やコストに基づくポリシー制御」が最優先されます。**BGP** は単なる距離ではなく「**宛先までに通過する AS 番号の完全な列（パスベクトル：`AS_PATH`）**」を交換することで、自分の AS 番号が含まれる経路を即座に弾いてループ（無限カウント）を原理的に防ぎつつ、組織ごとの柔軟なポリシー選択を実現しています。

## 6-8. 動的ルーティング②：AS間経路制御（BGP）・MPLSとエニーキャスト

### 1. 動機（Why）：なぜインターネットは「組織内の最短経路」と「組織間の契約経路」の 2 階層に分かれているのか

前節（[6-7節](6-7.md)）では、1つの大学や企業、あるいは1社のプロバイダ（ISP）の内部でルータが自律的に最短経路を計算するプロトコル（RIP と OSPF）を学びました。しかし、インターネットとは「単一の組織が運営する1つの巨大なネットワーク」ではなく、**世界中の 7 万以上の独立した組織（ISP、クラウド事業者、大学、通信キャリア、大企業）が運営するネットワーク同士が相互接続した「ネットワークのネットワーク」**です。

単一の管理主体のもとで運用されるネットワークの単位を **AS（Autonomous System：自律システム）** と呼び、各 AS には世界一意の **AS 番号（ASN：16ビットまたは32ビット）** が割り当てられます。

前節の最後で確認した通り、AS の内側（**IGP：Interior Gateway Protocol**、OSPF 等）と、AS 同士の外側（**EGP：Exterior Gateway Protocol**、**BGP**）では、経路選択の目的関数そのものがまったく異なります。

1. **AS の内側（IGP：OSPF）：** 同じ組織の所有物なので、目的は純粋な **性能（帯域幅・遅延の最小化）** です。
2. **AS の外側（EGP：BGP）：** 互いに独立した営利企業や国家間の接続なので、最優先されるのは物理的な最短距離ではなく **経済的・運用的なポリシー（契約・課金・セキュリティ）** です。たとえば「競合他社どうしの通信を自社回線でタダ乗り（トランジット）させたくない」「安く使える直接接続（ピアリング）を優先したい」といったルールを表現できなければなりません。

さらに、大規模な通信事業者（ISP）のコア網では、何十万行もの BGP 経路表を途中のすべてのルータで毎回 LPM 検索する負荷を避けて高速かつ柔軟にトラヒックを誘導する **MPLS** が広く使われています。また、BGP の経路広告の仕組みを応用して、世界中の利用者を自動的に最寄りのサーバ拠点へ導く **エニーキャスト（Anycast）** も現代の DNS や CDN に不可欠な技術です。

本節では、[第6部](../index.md#part-6)の集大成として **BGP（パスベクトル・eBGP/iBGP・ベストパス選択）**、**MPLS（ラベルスイッチング）**、そして **エニーキャスト** の3つを整理します。

---

### 2. 具体例と動作イメージ（Toy Model）

仕様の整理に入る前に、2つの小さなシナリオで「BGP のポリシー制御（タダ乗り防止）」と「エニーキャストの仕組み」を直感的に掴みます。

#### 実験A：なぜ「物理的に最短のルート」が BGP では使われないのか（バレーフリー原則）

3つの組織のネットワーク（`AS 1`・`AS 2`・`AS 3`）と、上位の大手プロバイダ（`AS 100`）があるとします。

* 企業 `AS 2` は、インターネットへ繋がるために、ISP である `AS 1` と `AS 3` の**両方と顧客契約（マルチホーミング）**を結んでおり、どちらの ISP へも利用料を払っています。
* ある日、`AS 1` の顧客から `AS 3` の顧客へパケットを送りたい状況が生まれました。物理的な配線を見ると **`AS 1 → AS 2 → AS 3`** がわずか 2 ホップで最短に見えます。

しかし、もし企業 `AS 2` が「`AS 3` 宛ては自分経由で行けますよ」と `AS 1` へ広告してしまったら何が起きるでしょうか。`AS 1` と `AS 3` のあいだの膨大な他人のトラヒックが、一般企業である `AS 2` の有料回線を勝手に通過（**トランジット**）し、`AS 2` は両方の ISP へ高額な通信費を払わされる羽目になります。

そこで BGP では、**「あるプロバイダ（または対等なピア）から教わった経路を、別のプロバイダへは再広告しない（自分自身のプレフィックスと自分の顧客のプレフィックスだけを広告する）」**という商業上の鉄則（**バレーフリー［Valley-Free］原則**）をポリシーとして設定します。その結果、`AS 1` から `AS 3` への通信は `AS 2` を通らず、上位の `AS 100` を経由する経路が選ばれます。

#### 実験B：同じ IP アドレス `1.1.1.1` が東京にもロンドンにも存在する不思議

パブリック DNS サービス（例：Cloudflare の `1.1.1.1` や Google の `8.8.8.8`）へ `ping` を打つと、日本から打てば **数ミリ秒**（東京のサーバ）、ロンドンから打てば同じく **数ミリ秒**（ロンドンのサーバ）で応答が返ってきます。光ファイバ中の光速（約 $2 \times 10^8\text{ m/s}$）で計算しても東京〜ロンドン間（大圏距離約 $9{,}600\text{ km}$）の往復は理論上約 $96\text{ ms}$、実際の海底ケーブルや陸路の迂回・中継を含めると $150\text{ ms}$ 以上かかるはずなのに、なぜ同じ1つの IP アドレスが世界中で数ミリ秒で応答できるのでしょうか。

答えは **BGP エニーキャスト** です。東京のデータセンターもロンドンのデータセンターも、**まったく同じプレフィックス `1.1.1.0/24` を最寄りの ISP へ向かって BGP で同時広告**します。するとインターネット全体の BGP ルーティングが自動的に「東京のルータからは東京拠点が最短」「ロンドンのルータからはロンドン拠点が最短」と判断して転送表を作るため、利用者は何も意識せずに最寄りのサーバへ自動的に吸い込まれるのです。

### 3. 構造・アルゴリズム・実装（What）

#### (1) BGP（Border Gateway Protocol）の仕組み：パスベクトルと eBGP / iBGP

現在のインターネット全体（バージョン 4：**BGP-4**）を束ねる **BGP** は、IP や UDP の上ではなく、信頼性のある **TCP（ポート 179）** の上でルータ同士が永続的なセッションを張って制御メッセージを交換します。

BGP が採用するアルゴリズムは、距離ベクトル（RIP）でもリンク状態（OSPF）でもない第3の方式である **パスベクトル型（Path Vector）** です（図6-8-1）。

* **広告する情報：** 単なるホップ数ではなく、**「宛先プレフィックス（例：`198.51.100.0/24`）」＋「パス属性（Path Attributes）」** の組を交換します。
* **最重要のパス属性 `AS_PATH`：** その経路情報が生成されてからこれまでに通過してきた **AS 番号のリスト**（例：`AS 300` が発信し `AS 200`・`AS 100` を経た場合は `[AS 100, AS 200, AS 300]`）です。ある AS の境界ルータが別の AS へ経路を再広告するたびに、先頭へ自分自身の AS 番号を付け足します。
* **完全なループ防止：** ルータは受信した経路の `AS_PATH` の中に **自分自身の AS 番号がすでに含まれていたら、即座にその経路を破棄します**。これにより、距離ベクトル型（RIP）を悩ませた**無限カウント問題が原理的に一切発生しません**。

また、BGP セッションには役割の異なる2種類があります（図6-8-1）。

1. **eBGP（External BGP）：** 異なる AS に属する境界ルータ同士のセッションです。組織間で到達可能なプレフィックスを交換します。
2. **iBGP（Internal BGP）：** 同じ AS の内部にあるルータ同士のセッションです。eBGP で外部から学んだ経路情報を、自 AS 内の他の境界ルータやコアルータへ行き渡らせるために使います（※AS 内の次ホップまでの実際の最短経路は、[6-7節](6-7.md)の OSPF などの IGP が担当します）。なお、iBGP は内部ループを防ぐために「別の iBGP ピアから学んだ経路を他の iBGP ピアへ再広告しない」規則を持つため、基本構成では AS 内の全 BGP ルータ同士を 1 対 1 で結ぶ **iBGP フルメッシュ** が必要になります。

#### (2) BGP のパス属性とベストパス選択（ホットポテトルーティング）

ある宛先プレフィックスに対して複数の候補経路が届いたとき、BGP ルータは図6-8-1下段に示した厳密な優先順位で「たった1本のベストパス」を選びます。

1. **`LOCAL_PREF`（ローカルプリファレンス：最大値を優先）：** 管理者が自 AS 内のポリシーとして手動設定する優先度。たとえば「無料の直接ピアリング回線は `LOCAL_PREF = 200`、有料のトランジット回線は `LOCAL_PREF = 100`」と設定すれば、たとえ AS ホップ数が少し長くても必ず安い回線が最優先されます。
2. **最短 `AS_PATH`（通過 AS 数が最小の経路を優先）：** `LOCAL_PREF` が同じなら、経由する AS の個数が少ない経路を選びます。
3. **`MED`（Multi-Exit Discriminator：最小値を優先）：** 2つの AS が複数地点（例：東京と大阪）で接続しているとき、受信側 AS が「どちらの入口から入れてほしいか」を相手へヒントとして伝える属性です。
4. **ホットポテトルーティング（Hot-Potato Routing：最小 IGP コストを優先）：** 上の条件がすべて同じなら、自 AS 内の OSPF コストが最小となる**最も近い出口ルータ**へ即座にパケットを放り出します。熱いジャガイモ（他社宛てのパケット）を自社網の中に長く抱え込まず、一番近くの出口から早く他社へ渡して自社の幹線帯域を節約する合理的な経済行動です。

#### (3) MPLS（Multi-Protocol Label Switching）：Layer 2.5 の高速ラベル転送

大手通信キャリアや ISP のコア網（バックボーン）では、毎日膨大な量の顧客トラヒックが通過します。ここで、途中のすべてのコアルータに「約 100 万行の BGP フルルート」を持たせて毎回最長プレフィックス一致（LPM）を実行させる代わりに、**L2（イーサネット）ヘッダと L3（IP）ヘッダのちょうど間（Layer 2.5）にわずか 32 ビットの固定長「MPLS ラベル」を差し込んで転送する**技術が **MPLS** です（図6-8-2）。

```text
+---------------+--------------------+-----------+-------------+
| L2 ヘッダ     | MPLS シムヘッダ(4B) | IP ヘッダ | ペイロード  |
+---------------+--------------------+-----------+-------------+
                  └─ Label(20bit) | TC(3bit) | S(1bit) | TTL(8bit)
```

MPLS 網のルータは役割によって2種類に分かれます。

* **入口／出口のエッジルータ（LER：Label Edge Router）：**

    * **入口（Ingress LER）：** 通常の IP パケットを受け取ると、宛先や転送等価クラス（**FEC**：Forwarding Equivalence Class、[6-2節](6-2.md)の前方誤り訂正とは別概念）を調べて先頭に MPLS ラベルを挿入（**Push**）してコア網へ送り出します。
    * **出口（Egress LER）：** MPLS ラベルを取り外し（**Pop**）、元の IP パケットとして外部ネットワークへ送り出します。

* **コアのラベルスイッチングルータ（LSR：Label Switch Router）：**

    * パケットを受け取ると、IP ヘッダを一切見ず、**20 ビットのラベル番号を配列の添字のように完全一致（Exact Match）で 1 回引くだけ**で、次の出力ポートと新しいラベル番号へ付け替え（**Swap**）て即座に転送します。

MPLS が現代のキャリア網で重宝される最大の理由は、単なる検索高速化（現代の ASIC/TCAM は IP LPM も十分高速）以上に、**トラヒックエンジニアリング（MPLS-TE）** と **L3 VPN** にあります。通常の IP ルーティング（OSPF）では最短経路1本へトラヒックが集中して混雑しても迂回させにくいですが、MPLS では入口ルータで明示的に「ラベル経路（**LSP：Label Switched Path**）」を指定できるため、空いている別ルートへトラヒックを計画的に分散したり、複数企業のプライベート IP 網（`192.168.1.0/24` が重複していても可）をラベルの多段重ね（ラベルスタック）で安全に分離収容したりできます。

#### (4) 通信形態の 4 分類と BGP エニーキャスト（Anycast）

ネットワーク層のパケット配信形態は、宛先ホストの数と選び方によって次の **4種類** に分類されます。

1. **ユニキャスト（Unicast：1対1）：** 特定の1台のホスト宛てに届ける通常の通信。
2. **ブロードキャスト（Broadcast：1対全員）：** 同一サブネット内の全ホストへ一斉に届ける（IPv4 の ARP / DHCP 等。IPv6 では廃止）。
3. **マルチキャスト（Multicast：1対特定グループ）：** 特定のグループへ参加表明した複数ホスト全員へ効率よく複製配信する（動画の一斉配信や OSPF の制御パケット等）。
4. **エニーキャスト（Anycast：1対「最寄りの1台」）：** 同じ1つの IP アドレスを地理的に離れた複数台のサーバへ割り当て、**ネットワークのルーティング距離が最も近い1台**へ自動的に届ける方式（図6-8-3）。

実験Bで触れた通り、インターネット上の **BGP エニーキャスト** では、特別なプロトコルを新設する必要はなく、**複数の拠点（東京・シンガポール・ロンドン・ニューヨーク等）からまったく同じ IP プレフィックス（例：`1.1.1.0/24`）を BGP で同時広告するだけ**で実現できます。

エニーキャストが世界のインフラ（DNS のルートサーバ、Cloudflare・Fastly 等の CDN）で標準採用されている理由は3つあります。

* **低遅延化：** ユーザは常に地理的・トポロジ的に最も近い拠点へ自動接続されます。
* **自動フェイルオーバー（高可用性）：** たとえば東京拠点が停電や障害で落ちると、東京からの BGP 広告が取り下げられ、日本のユーザのトラヒックは自動的に2番目に近い大阪やシンガポール拠点へ切り替わります。
* **DDoS 攻撃の局所吸収：** 世界中から大量の攻撃パケットが押し寄せても、各国の攻撃トラヒックはそれぞれの最寄り拠点へ分散吸収されるため、1箇所のサーバが集中砲火で落ちるのを防げます。

> **【コラム：BGP 経路ハイジャック（2008年 YouTube 事件）と RPKI による暗号学的防御】**
>
> BGP は 1989 年に「インターネットを構成する各組織は互いに善意で正しい経路を広告する」という**性善説（認証なし）**のもとで設計されました。そのため、どこか1社の ISP が誤設定（または悪意）で「他人のプレフィックスが自分の AS にある」と広告してしまうと、世界中のルータがそれを信じてトラヒックをそちらへ吸い込んでしまいます（**BGP 経路ハイジャック**）。
>
> 最も有名な実例が **2008年の YouTube 遮断事件** です。パキスタンの通信事業者が国内向けに YouTube をブロックしようと、自国内ルータへ YouTube のアドレス帯の一部を細かく切った **`/24` プレフィックス** としてブラックホール設定した際、誤ってそれが外部の eBGP へ漏れ出してしまいました。当時の YouTube 本家はより粗い `/22` を広告していたため、[6-5節](6-5.md)の **最長プレフィックス一致（LPM）** によって世界中のルータが `/24` を優先し、**約2時間にわたり世界中の YouTube トラヒックがパキスタンへ吸い込まれて閲覧不能**になったのです。
>
> この構造的な脆弱性に対する現代の補正が、公開鍵暗号（[第7部](../index.md#part-7) [7-7節](../7/7-7.md)）を用いた **RPKI（Resource Public Key Infrastructure）** です。IP アドレスの正当な所有者が「プレフィックス `X` を広告してよい正規の AS 番号は `AS Y` である」という電子署名付き証明書（**ROA：Route Origin Authorization**）を公開し、各 ISP のルータが受信した BGP 広告を ROA と照合して不正な経路を自動破棄（**ROV：Route Origin Validation**）する仕組みが世界中で急速に普及しています。

### 4. 限界と補正（Critique & Adaptation）

#### (1) BGP の収束遅延・フラッピングと、エニーキャストにおける TCP 切断問題

BGP とエニーキャストには、実運用で見落とせない2つの限界があります。

1. **BGP の収束遅延とフラッピング：**
    あるリンクが不安定になって「接続 ⇄ 切断」を繰り返す（フラッピング）と、BGP の経路広告と撤回メッセージが世界中へ波及してルータの CPU を圧迫します。また、代替経路を順に試しながら探索するため、障害収束に数十秒〜数分かかることがあります（補正：短時間に何度も揺れる経路を一時的に無視する **Route Flap Dampening** や、BGP ルートリフレクタによる iBGP フルメッシュの緩和）。

2. **エニーキャストとステートフルな TCP 通信の相性：**
    DNS のような 1 往復で終わる UDP 通信ではエニーキャストは問題なく機能します。しかし、数分間続く **TCP 接続（[7-2節](../7/7-2.md)）** の途中で BGP の経路がわずかに揺らぎ、同じユーザからのパケットが突然「東京拠点」から「大阪拠点」へ切り替わると、大阪拠点のサーバはその TCP 接続の状態（シーケンス番号等）を知らないため即座にリセット（`RST`）を返して接続が切れてしまいます。

    * **補正：** 大手 CDN では、BGP の経路揺らぎを抑える運用に加え、エッジ拠点間で状態を引き継ぐプロキシ設計や、IP アドレスではなく「接続 ID」でセッションを識別できる次世代トランスポート **QUIC（[7-3節](../7/7-3.md)）** の活用が進んでいます。

#### (2) 分散ルーティングの限界と SDN（Software-Defined Networking）への展望

[6-7節](6-7.md)（RIP・OSPF）と本節（BGP）で学んだ従来のルーティングは、**すべてのルータが独立してコントロールプレーン（経路計算の頭脳）とデータプレーン（パケット転送の手足）を両方内蔵し、互いにメッセージを交換して分散合意する**アーキテクチャでした。

しかし、大規模なクラウドデータセンターや世界規模の自社専用バックボーン（Google の B4 等）では、「各ルータがバラバラに分散計算するより、ネットワーク全体の混雑状況を1箇所で把握して最適経路を一括計算したい」という要求が強まります。この発想から生まれたのが **SDN（Software-Defined Networking）** です。SDN では、ルータからコントロールプレーンを切り離して論理的に集中化した **SDN コントローラ** へ集約し、各スイッチ／ルータへは計算済みの転送テーブル（フローテーブル）だけを配布することで、リンク利用率を大幅に高める柔軟な運用を実現しています。

> 3. **（[第7部](../index.md#part-7)への伏線：ホストまで届いたパケットを「正しいアプリへ・欠損なく」渡すには）**
