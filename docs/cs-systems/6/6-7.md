### 前節（6-6）の確認問題の解答

前節の最後に提示した3つの問いの解答を確認します。

1. **$\text{MTU} = 1{,}000\text{ B}$ での IPv4 フラグメンテーションと PMTUD ブラックホール診断：**

    * **(a) 最大ペイロード長が $976\text{ B}$ になる理由と 3 断片の計算：**
        IPv4 のフラグメントオフセットは 16 ビットの全長フィールドに対して 13 ビットしかないため **$2^{16-13} = 8$ バイト単位** で表現されます。したがって最終断片以外のペイロード長は必ず 8 の倍数でなければなりません。$\text{MTU} = 1{,}000\text{ B}$ からヘッダ $20\text{ B}$ を引いた $980\text{ B}$ は $980 = 8 \times 122 + 4$ で 8 の倍数ではないため、8 の倍数へ切り捨てた **$976\text{ B}$**（$8 \times 122$）が 1 断片の最大ペイロード長になります。ペイロード合計 $2{,}480\text{ B}$ の分割結果は次の通りです（残り $2{,}480 - 976 \times 2 = 528\text{ B}$）。

        * **断片 1：** (i) ペイロード **$976\text{ B}$**・全長 **$996\text{ B}$**、(ii) `MF = 1`、(iii) オフセット $0 / 8 = \mathbf{0}$ です。
        * **断片 2：** (i) ペイロード **$976\text{ B}$**・全長 **$996\text{ B}$**、(ii) `MF = 1`、(iii) オフセット $976 / 8 = \mathbf{122}$ です。
        * **断片 3：** (i) ペイロード **$528\text{ B}$**・全長 **$548\text{ B}$**、(ii) `MF = 0`、(iii) オフセット $1{,}952 / 8 = \mathbf{244}$ です。

    * **(b) PMTUD ブラックホールの原因と対策：**
        DF=1 で送ったパケットが途中の小 MTU リンクで破棄されても、ファイアウォールがすべての ICMP を遮断しているとルータからの `ICMP Fragmentation Needed`（IPv6 では `Packet Too Big`）が送信元へ届かず、送信元がサイズを下げられず同じ大きいパケットを送り続けてハングアップします。対策としては、① ファイアウォールで PMTUD に必要な ICMP エラー通知を通過させる、② ルータで TCP の最大セグメント長を下げる **MSS クランピング** や ICMP に依存しない **PLPMTUD** を併用する、などが有効です。

2. **LAN $\to$ NAPT ルータ $\to$ WAN 越えの L2/L3/L4 全ヘッダ書き換えトレース：**

    * **(a) 各区間のヘッダ変化と通常 L3 ルーティングとの対比：**

        * **① LAN 側（PC $\to$ NAPT ルータ）：** L2 MAC `AA → R1`、L3 IP `192.168.1.10 → 93.184.216.34`、L4 ポート `51000 → 443` です。
        * **② WAN 側（NAPT ルータ $\to$ ISP ルータ）：** L2 MAC `R2 → ISP`、L3 IP `203.0.113.5 → 93.184.216.34`、L4 ポート `40010 → 443` です。

        通常の（NAT なし）L3 ルーティングでは L2 MAC と TTL・チェックサムだけが変わり送信元・宛先 IP と L4 ポートは不変ですが、NAPT では送信元 IP と送信元ポートまで書き換える点が大きく異なります。

    * **(b) 外部からの事前通信なしの内向きパケットが遮断される理由：**
        NAPT 変換テーブルのエントリは LAN 内部から外部へ発信したときに初めて動的に生成されるため、外部から突然届いたパケットの宛先ポート番号に対応する内部ホストのエントリがテーブルに存在せず、ルータが転送先を特定できないため破棄されます。

3. **DHCP のブロードキャスト規則と `traceroute` の障害診断：**

    * **(a) `DHCP Request` もブロードキャストで送る理由：**
        同じ LAN 内に複数の DHCP サーバが存在して複数台から `Offer` が届いた場合でも、端末がどのサーバの提示 IP を採用したかを全 DHCP サーバへ同時に知らせ、選ばれなかった他サーバが提示済みの候補 IP を即座に空きプールへ戻せるようにするためです。

    * **(b) 3 ホップ目だけ `* * *` になる 2 つの原因：**
        ① 3 ホップ目のルータがセキュリティポリシーや負荷軽減のため **ICMP Time Exceeded（Type 11）の返送を無効化またはレート制限** している場合、② 3 ホップ目のルータが返送した ICMP Time Exceeded パケットが **戻り経路上のファイアウォールで遮断** されている場合、の 2 つが代表的です（いずれも通常のデータ転送自体は行われるため 4 ホップ目以降や最終通信は成功します）。

## 6-7. 動的ルーティング①：距離ベクトル（RIPの無限カウント）vs リンク状態（OSPF）

### 1. 動機（Why）：なぜルータの経路表を「自律的なグラフアルゴリズム」で自動構築する必要があるのか

前節まで（[6-5](6-5.md)・[6-6節](6-6.md)）では、各ルータの内部にすでに正しい転送表（ルーティングテーブル）が登録されている前提で、最長プレフィックス一致（LPM）や ARP・NAT によってパケットが目的地へ運ばれる流れを追いました。

小規模な家庭用ネットワークであれば、管理者が「デフォルトゲートウェイは `192.168.1.1`」と手動で設定する **静的ルーティング（Static Routing）** でも十分です。しかし、大学キャンパスや大企業、プロバイダ（ISP）のネットワークのようにルータが数十台〜数千台と連なる環境では、静的ルーティングは次の2つの理由で破綻します。

1. **トポロジ変更への追従不能：** 新しい部署のサブネットが増設されたり、配線が変更されたりするたびに、関連するすべてのルータの設定を人間が手作業で矛盾なく書き換えるのは非現実的です。
2. **障害時の自動迂回ができない：** 途中の光ファイバが工事で切断されたりルータが故障したりしたとき、静的ルートでは切れっぱなしのリンクへパケットを送り続けて通信が途絶えたままになります。

そこで、ネットワークを **「ルータ＝頂点 $V$、リンク＝コスト（重み）付きの辺 $E$」** からなる重み付きグラフ $G = (V, E)$ としてモデル化し、ルータ同士が自律的に最短経路を計算・更新する **動的ルーティングプロトコル** が不可欠になります。

自律的に最短経路を求める分散アルゴリズムには、情報共有の仕方がまったく異なる **2つの対照的なアプローチ** があります。

* **距離ベクトル型（Distance Vector：代表例 RIP）：** 全体の地図は持たず、「**隣人から聞いた『宛先までの距離の噂』**」だけを頼りに自分の経路表を少しずつ改善します（Bellman-Ford 法）。
* **リンク状態型（Link State：代表例 OSPF）：** 全ルータが「自分の隣接リンクの状態」をネットワーク全体へ配布して**全員が同じ全体地図**を持ち、各自が手元で最短経路木を計算します（Dijkstra 法）。

本節では、この2大アルゴリズムの動作とトレードオフを、手計算トレースと障害時の振る舞い（無限カウント問題）を通して詳しく対比します。

---

### 2. 具体例と動作イメージ（Toy Model）

数式とプロトコル仕様に入る前に、2つの小さな例で「距離ベクトルとリンク状態の考え方の違い」および「距離ベクトル特有の問題（無限カウント）」を体感します。

#### 実験A：見知らぬ街で駅へ行く 2 つの方法

見知らぬ街の交差点（ルータ）に立って、目的地（駅）までの最短ルートを探す状況を想像してください。

* **距離ベクトル型（道標・噂ベース）：** 街全体の地図は持っていません。隣の交差点にいる人へ「駅から何分かかりますか」と尋ね、北の隣人が「10分」、東の隣人が「5分」と答えたら、「東の交差点まで2分かかるから、東経由なら $2 + 5 = 7\text{ 分}$ が最短だ。次も東へ案内しよう」と記録します。
* **リンク状態型（全体地図ベース）：** 街中のすべての交差点から「どの道が何分で通行可能か」という最新情報を全員へ一斉配布し、全員が同じ街全体の地図（データベース）を手元に持ちます。あとは各自が地図上で最短ルートを一気に計算します。

#### 実験B：3台直列のネットワークで起きる「無限カウント（Count-to-Infinity）」

距離ベクトル型は実装がとても単純ですが、**「悪いニュース（リンク断線）の伝播が遅い」**という深刻な弱点を持っています。次の3台のルータが直列に繋がったネットワーク（各リンクのコスト＝1ホップ）を考えます（図6-7-1右）。

$$
\text{A} \;\overset{1}{\longleftrightarrow}\; \text{B} \;\overset{1}{\longleftrightarrow}\; \text{C}
$$

* **正常時：**

    * C は自分自身なので「C までの距離 $= 0$」です。
    * B は C と直結しているため「C までの距離 $= 1$（次ホップ C）」です。
    * A は B から「C まで距離 1」と聞いたため「C までの距離 $= 2$（次ホップ B）」です。

ここで、**B–C 間のケーブルが切断された**とします（コスト $= \infty$）。

1. **時刻 $t_1$：** B は C との直結リンクが切れたことを検知します。ところが、B が「C は到達不能（$\infty$）だ」と A へ伝える直前に、**まだ断線を知らない A が定期広告で「私は C まで距離 2 で行けます」と B へ報告**してきます（あるいは B が手元に保存していた A の直近の広告値 `2` を参照します）。
2. **時刻 $t_2$：** 全体の地図を持たない B は、A の経路が「実は自分（B）を経由していること」を知りません。そこで B は「A 経由なら C へ行ける」と誤解し、自分の距離を **$1 + 2 = 3$（次ホップ A）** へ更新します。
3. **時刻 $t_3$：** 今度は B が A へ「C まで距離 3 に変わりました」と広告します。A は自分の次ホップである B の距離が増えたので、自分の距離を **$1 + 3 = 4$** へ更新します。
4. **時刻 $t_4, t_5, \dots$：** B が `5`、A が `6`、B が `7`、A が `8` ……と、**2台が互いに存在しない経路を信じ合って距離を1ずつ増やし続け、無限大まで永遠に数え上げ続ける（無限カウント問題：Count-to-Infinity）**ことになります。しかもこの間、C 宛てのパケットは A と B の間を TTL が `0` になるまで延々と往復（ルーティングループ）し続けます。

### 3. 構造・アルゴリズム・実装（What）

#### (1) コントロールプレーンとデータプレーン（RIB vs FIB）

ルータの内部機能は、役割と処理速度の異なる次の **2つのプレーン（層）** に明確に分離されています。

* **コントロールプレーン（制御面：ソフトウェア／CPU処理）：**
    RIP や OSPF、BGP などの動的ルーティングプロトコルを動かし、隣接ルータと制御メッセージを交換して最短経路を計算し、**経路表（RIB：Routing Information Base）** を構築・維持する頭脳部分です（ミリ秒〜秒オーダー）。

* **データプレーン（転送面：専用ハードウェア ASIC / TCAM 処理）：**
    RIB から最適な転送先だけを抽出・最適化した **転送表（FIB：Forwarding Information Base）** を持ち、到着した個々の IP パケットを [6-5節](6-5.md)の **最長プレフィックス一致（LPM）** で数ナノ秒のうちに出力ポートへ送り出す手足部分です。

本節と次節（[6-8節](6-8.md)）で扱うのは、前者の **コントロールプレーン** のアルゴリズムです。

#### (2) 距離ベクトル型（Distance Vector）：Bellman-Ford 方程式と RIP

距離ベクトル型アルゴリズムの数学的基盤は、リチャード・ベルマンとレスター・フォードによる **Bellman-Ford（ベルマン＝フォード）方程式** です。

ノード $x$ から宛先ノード $y$ までの最小コストを $D_x(y)$、$x$ と隣接ノード $v$ の間の直接リンクコストを $c(x, v)$ とすると、最短経路の最適性原理より次式が成り立ちます。

$$
D_x(y) = \min_{v \in N(x)} \bigl\{\, c(x, v) + D_v(y) \,\bigr\}
$$

ここで $N(x)$ はノード $x$ の隣接ノード集合です。各ノード $x$ は、自分の距離ベクトル $\mathbf{D}_x$（全宛先 $y$ への推定最小コスト）に加えて、**各隣接ノード $v$ から直近に受け取った距離ベクトル $\mathbf{D}_v$ もそれぞれテーブルとして保持**しています。そのため、隣接リンクの断線やコスト変化を検知した瞬間に、次の定期広告を待たず手元の最新テーブルから即座に別経路の再計算をトリガできます（図6-7-1左）。

1. 自身のリンクコストが変化するか、隣接ノード $v$ から新しい距離ベクトル $\mathbf{D}_v$ を受信して手元の隣接テーブルを更新します。
2. 各宛先 $y$ について上式 $\min_v \{ c(x, v) + D_v(y) \}$ を再計算します。
3. 自分の距離ベクトル $\mathbf{D}_x$ の値が1つでも変化したら、更新後の $\mathbf{D}_x$ をすべての隣接ノードへ送信します。

これを実装した古典的なプロトコルが **RIP（Routing Information Protocol）** です。RIP は UDP ポート 520 を使い、30秒ごとに隣接ルータへ自分の経路表全体を広告します。メトリック（リンクコスト）には単純な **ホップ数（通過ルータ数）** を用います。

実験Bの **無限カウント問題** を緩和するため、RIP は次の3つの補正を組み込んでいます。

1. **最大ホップ数の制限（$\infty = 16$）：** ホップ数の上限を **15** と定め、**16 を到達不能（$\infty$）** とみなします。これにより、仮に無限カウントが起きても 16 で確実に打ち切られます（反面、直径 16 ホップ以上の大規模ネットワークでは RIP を使用できません）。
2. **スプリットホライズン（Split Horizon）：** 「ある隣接ルータ $B$ から教えてもらった経路情報は、その同じ $B$ へ向かっては広告しない」という規則です。実験Bの A が B へ「C まで距離 2」と送り返すのを防げます。
3. **ポイズンリバース（Poison Reverse）：** スプリットホライズンの強化版です。「$B$ 経由で到達している宛先 $C$ については、$B$ へ向かってあえて **『距離 $=\infty$（16）』と毒を盛って広告**する」規則で、2ノード間のループを即座に断ち切れます。

#### (3) リンク状態型（Link State）：LSA フラッディングと Dijkstra 法（OSPF）

RIP の「全体が見えないことによる収束の遅さとホップ数 15 の壁」を根本から解決し、現代の企業網・大学網・ISP 内部（AS内）で標準的に使われているのが **リンク状態型** の代表プロトコル **OSPF（Open Shortest Path First）** です（IP プロトコル番号 `89` で直接運ばれます）。

OSPF は、次の **3ステップ** で全ルータが正確かつ高速に最短経路表を構築します（図6-7-2）。

1. **近隣発見（Hello プロトコル）：** 各ルータは定期的に `Hello` パケットを全インタフェースへ送信し、隣接しているルータとリンクの生存（死活監視）およびリンクコストを把握します。
2. **LSA フラッディングと LSDB の同期：**
    各ルータは「自分の隣接ルータとそれぞれのリンクコスト」だけを記した小さな広告パケット **LSA（Link-State Advertisement）** を作成し、ネットワーク内の全ルータへ行き渡るように転送（**フラッディング**）します（シーケンス番号で重複転送を防止します）。その結果、ネットワーク内の**全ルータが同一の全体地図（LSDB：Link-State Database）**をメモリ上に保持します。

3. **Dijkstra（ダイクストラ）法による最短経路木（SPT）の計算：**
    各ルータは、手元の全体地図（LSDB）の上で自分自身を始点 $u$ とする **Dijkstra のアルゴリズム**（計算量：二分ヒープ使用時 $O((|V|+|E|)\log |V|)$）を独立して実行し、すべての宛先への最短経路と「最初に踏み出すべき次ホップ」を確定して転送表（FIB）へ書き込みます。なお、Dijkstra 法が最短経路の正当性を保証するための前提条件は、**すべてのリンクコストが非負（$c(u, v) \ge 0$）であること** です（負の辺コストがあると、一度確定したノードの距離が後からさらに縮まり得るため正しく動作しません）。

図6-7-2左の4ノードグラフ（双方向リンクのコスト：`A–B: 2`、`A–C: 5`、`B–C: 1`、`B–D: 4`、`C–D: 2`、始点 A）に対して、Dijkstra 法のステップを手計算で追ってみましょう。確定済み集合を $N'$ とします。

| ステップ | 確定集合 $N'$ | $D(\text{B})$ / 直前 | $D(\text{C})$ / 直前 | $D(\text{D})$ / 直前 | 次に確定する最小ノード |
| :---: | :--- | :---: | :---: | :---: | :--- |
| 0 (初期) | `{A}` | `2` (A) | `5` (A) | $\infty$ | **B**（コスト `2`） |
| 1 | `{A, B}` | `2` (A) | **`3` (B)** | `6` (B) | **C**（コスト `3`：$2+1 < 5$ で更新） |
| 2 | `{A, B, C}` | `2` (A) | `3` (B) | **`5` (C)** | **D**（コスト `5`：$3+2 < 6$ で更新） |
| 3 (完了) | `{A, B, C, D}` | `2` (A) | `3` (B) | `5` (C) | 全ノード確定 |

結果として、ルータ A の転送表には「B 宛て $\to$ B、C 宛て $\to$ B、D 宛て $\to$ B」と登録されます。もし途中で B–C 間のリンクが切れても、B と C が即座に「B–C 断線」の LSA をフラッディングし、全ルータが数秒以内に新しい地図で Dijkstra 法を再実行するため、**無限カウントは原理的に一切発生しません**。

#### (4) 距離ベクトル型（RIP）vs リンク状態型（OSPF）の総合比較

| 比較項目 | 距離ベクトル型（RIP） | リンク状態型（OSPF） |
| :--- | :--- | :--- |
| **基盤アルゴリズム** | Bellman-Ford 方程式（分散反復） | Dijkstra 法（全体グラフ上で独立計算） |
| **交換する情報** | 自分の経路表全体（全宛先への距離）を**隣人だけ**へ | 自分の隣接リンク情報（LSA）だけを**全ルータ**へ |
| **障害時の収束速度** | 遅い（無限カウント・ルーティングループの恐れ） | **速い**（変化した LSA だけ即座にフラッディング） |
| **メトリック（基準）** | ホップ数のみ（最大 15、16 は到達不能） | リンク帯域幅に基づくコスト（ECMP 等コスト複数経路も可） |
| **CPU・メモリ消費** | 非常に小さい（安価な機器でも動く） | 大きい（LSDB の保持と Dijkstra 計算が必要） |
| **適用規模** | 小規模ネットワークのみ | 中〜大規模の企業網・大学網・ISP 内部網（AS内標準） |

> **【コラム：OSPF の帯域幅コスト計算と「参照帯域デフォルト 100 Mbps」の落とし穴】**
>
> RIP のように「ホップ数」だけで経路を決めると、「A–B 直結の古い $10\text{ Mbps}$ 回線（1ホップ）」と「A → C → B を経由する $10\text{ Gbps}$ 光ファイバ（2ホップ）」があるとき、RIP はホップ数の少ない $10\text{ Mbps}$ 回線を選んでしまい、1,000 倍速い幹線ルートが遊休になります。
>
> そこで OSPF は、リンクコストを次式のように帯域幅の逆数（整数切り捨て・最小値 `1`）で定義します。
>
> $$\text{Cost} = \max\left(1,\; \left\lfloor \frac{\text{参照帯域幅}}{\text{リンク帯域幅}} \right\rfloor\right)$$
>
> ところが、ここで実務上有名な落とし穴があります。OSPF の初期規格では**参照帯域幅のデフォルト値が $100\text{ Mbps}$** に設定されているため、管理者がデフォルトのまま運用すると、**$100\text{ Mbps}$（$100/100 = 1$）、$1\text{ Gbps}$（$\lfloor 100/1000 \rfloor \to 1$）、$10\text{ Gbps}$（$\lfloor 100/10000 \rfloor \to 1$）のリンクがすべて同じコスト `1`** に丸められてしまいます。その結果、100 倍速い 2 ホップの $10\text{ Gbps}$ 経路（コスト $1+1=2$）より、遅い 1 ホップの $100\text{ Mbps}$ 直結回線（コスト `1`）が選ばれてしまいます。現代の高速網では、全ルータの参照帯域幅を $100\text{ Gbps}$ 等へ引き上げて（$10\text{ Gbps} \to 10$、$1\text{ Gbps} \to 100$、$100\text{ Mbps} \to 1{,}000$）、帯域差を正しく反映させる運用が必須です。なお、最小コストが同点となる複数経路があれば、両方にトラヒックを均等分散する **ECMP（Equal-Cost Multi-Path）** も標準でサポートしています。

### 4. 限界と補正（Critique & Adaptation）

#### (1) ポイズンリバースでも防げない「3ノード以上のループ」

3-(2)で、距離ベクトル型の無限カウント対策としてスプリットホライズンとポイズンリバースを紹介しました。これらは実験Bのような**2ノード間（A–B間）のピンポンループ**は確実に防ぎます。

しかし、**3ノード以上が三角形（閉路）に並んでいる場合、ポイズンリバースを有効にしていても無限カウントを防ぎ切れません**。たとえばコスト 1 のリンクで A–B–C が三角形に繋がり、C の先にコスト 1 で宛先 X がある（正常時は $D_C(X)=1$、$D_A(X)=2$［次ホップ C］、$D_B(X)=2$［次ホップ C］）状態を考えます。このとき **A の宛先 X への次ホップは B ではなく C であるため、A は C へは $\infty$ を広告しても、B へは $\infty$ ではなく距離 `2` を広告してしまいループが復活します**。実際に `C–X` が断線して C が $D_C(X) = \infty$ を広告すると、B は手元にある A の未毒化広告 `2` を使って $D_B(X) = 3$（次ホップ A）へ更新し、次ホップでない C へ `3` を広告します。すると C が $D_C(X) = 4$（次ホップ B）になって A へ `4` を広告し、さらに A が $D_A(X) = 5$（次ホップ C）になって B へ `5` を広告する 3 ノード循環（`B → A → C → B`）が生まれ、`3 → 4 → 5 → 6 …` と無限カウントに陥ります。

これをさらに抑える補正として、距離が増大した経路を一時的に更新凍結する **ホールドダウンタイマ** や、変化時に30秒待たず即通知する **トリガードアップデート** が併用されますが、中〜大規模網では最初から全体地図を持つ OSPF（または IS-IS）へ移行するのが根本解決です。

#### (2) OSPF のフラッディング爆発と「エリア分割（エリア0 バックボーン）」

一方、OSPF にも大規模化に伴う明確な限界があります。全ルータが LSA を全員へフラッディングして同じ LSDB を持つため、ルータ台数 $|V|$ が数千台に増えると、**どこかの端のリンクが1本点滅（フラッピング）しただけでネットワーク全体へ LSA が洪水のように飛び交い、全ルータが一斉に重い Dijkstra 計算を繰り返して CPU が飽和**してしまいます。

この限界に対する OSPF の構造的な補正が、ネットワーク全体を複数の論理グループへ分割する **階層化（エリア分割：Multi-Area OSPF）** です（図6-7-3）。

* 中央に必ず **バックボーンエリア（エリア 0）** を置き、その周囲へ通常エリア（エリア 1, エリア 2, …）を星型に接続します。
* エリア同士の境界に立つルータを **ABR（Area Border Router）** と呼びます。
* 詳細な LSA フラッディングと LSDB の同期は**各エリアの内部だけ**に封じ込め、ABR はエリア 0 へ向かって「エリア 1 の住所はまとめて `10.1.0.0/16`」という **集約された要約経路だけ** を伝えます。

これにより、エリア 1 の端でリンク障害が起きてもエリア 2 のルータは一切影響を受けず、LSDB サイズも Dijkstra 計算負荷も大きく抑えられます。

#### (3) IGP の限界：なぜ世界中のインターネット全体を 1 つの OSPF で繋げないのか（次節への動機）

RIP や OSPF は、単一の組織・管理主体が運営するネットワーク（**AS：自律システム**）の内部で使う **IGP（Interior Gateway Protocol）** です。では、世界中の何万ものプロバイダや企業をすべて 1 つの巨大な OSPF で繋げないのはなぜでしょうか。理由は次の **2つの壁** にあります。

1. **規模の壁：** 世界中の何百万台ものルータのリンク情報をフラッディングすれば、一瞬で制御トラヒックと LSDB・SPF 計算負荷が飽和して破綻します。
2. **自律性とポリシー（契約・コスト）の壁：** たとえ物理的に最短距離であっても、「競合他社の ISP の通信を自社回線でタダ乗り（トランジット）させたくない」「政治的・契約上の理由で特定経路を避けたい」という**経済的・運用的なポリシー**を最優先しなければなりません。純粋なコスト最小化だけを行う OSPF では、こうした組織間のポリシーを表現できないのです。

この2つの壁を越えてインターネット全体を1つに束ねる仕組みが、次節（[6-8節](6-8.md)）で学ぶ **BGP（Border Gateway Protocol）** です。

1. **次節（[6-8節](6-8.md)：動的ルーティング② AS間経路制御［BGP］・MPLSとエニーキャスト）：**
    本節4-(3)で提起した「組織（AS）同士をポリシーベースで結ぶ」ための **EGP（BGP：パスベクトル型）** へ進み、さらに[第6部](../index.md#part-6)の締めくくりとして、通信事業者の高速ラベル転送（MPLS）や DNS/CDN で活躍するエニーキャストを学びます。

2. **[第6部](../index.md#part-6)（[6-4節](6-4.md)：STP）との構造的対比：**
    [6-4節](6-4.md)の L2 **STP** はネットワーク全体で1本の木（ルートブリッジ中心の全域木）しか使えず予備リンクが遊休になっていましたが、本節の L3 **OSPF** は各ルータが自分中心の最短経路木と ECMP を使うため、ネットワーク内のすべてのリンク帯域を無駄なく活用できます。

### 理解度チェック（次節へ進む前の確認）

本節の OSPF 参照帯域設定と Dijkstra 法、三角形トポロジでのポイズンリバース破綻、および大規模 OSPF と IGP の限界を確認する問いを置きます。

> **【確認の問い】**
>
> 1. **（OSPF 参照帯域設定ミスの診断と修正後の Dijkstra 法）**
>     ルータ A, B, C が三角形に結ばれており、リンク帯域幅は `A–B` が **$100\text{ Mbps}$**、`A–C` と `C–B` がどちらも **$10\text{ Gbps}$** とします。OSPF のリンクコストは $\text{Cost} = \max\bigl(1,\; \lfloor \text{参照帯域幅} / \text{リンク帯域幅} \rfloor\bigr)$ で決まります。
>
>     * (a) 参照帯域幅がデフォルトの **$100\text{ Mbps}$** のままになっているとき、3 本のリンクのコストと、ルータ A が B 宛てに選んでしまう経路を求めてください（なぜ遅い回線が選ばれるのかも 1 文で説明すること）。
>     * (b) 参照帯域幅を **$100\text{ Gbps}$** へ修正したときの各リンクコストを求め、始点 A から Dijkstra 法を実行して C・B への最小総コストと最短経路を確定してください（あわせて、Dijkstra 法が正しく動作するためのリンクコストの前提条件も 1 句述べること）。
>
> 2. **（3 ノード三角形トポロジでのポイズンリバース破綻トレース）**
>     コスト 1 のリンクで三角形（`A–B`、`B–C`、`A–C`）に結ばれた 3 台のルータがあり、さらに C の先にコスト 1 で宛先 X が接続されています（`C–X`）。全ルータは距離ベクトル型（ポイズンリバース有効）で動作し、正常時は $D_C(X)=1$（次ホップ X）、$D_A(X)=2$（次ホップ C）、$D_B(X)=2$（次ホップ C）で収束しています。
>
>     * (a) `C–X` が断線する**直前**に、ルータ A は隣接する C と B それぞれに対して X までの距離をいくつと広告しているでしょうか。
>     * (b) `C–X` が断線して C が $D_C(X) = \infty$ を広告した直後、B がまず C からの $\infty$ を受信したとします。以降、B $\to$ C $\to$ A $\to$ B の順に更新が進むと、なぜポイズンリバースが有効でも距離が `3 → 4 → 5 → 6 …` と無限カウントに陥るのか、各ステップの「距離・次ホップ・広告値」をトレースして説明してください。
>
> 3. **（単一エリア OSPF 障害診断と IGP の限界）**
>     次の 2 つの問いに答えてください。
>
>     * (a) 2,000 台のルータを単一エリアの OSPF で運用しているネットワークで、末端の 1 本のリンクが頻繁に断続（フラッピング）したとき、ネットワーク全体にどのような障害が発生するでしょうか。また、OSPF のどの設計機能によってこの影響を局所化できるでしょうか。
>     * (b) OSPF などの IGP をそのまま世界中のプロバイダや企業へ広げてインターネット全体を 1 つの OSPF 網で運用できない 2 つの根本理由を挙げ、組織（AS）間の経路制御に別プロトコルが必要になる理由を説明してください。
