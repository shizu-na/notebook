### 前節（6-6）の確認問題の解答

前節の最後に提示した3つの問いの解答を確認します。問3がそのまま本節（動的ルーティング①）の導入になります。

1. **IPv4 フラグメンテーションの手計算（全長 $3{,}020\text{ B}$、ペイロード $3{,}000\text{ B}$、$\text{MTU} = 1{,}500\text{ B}$）：**
    IPv4 ヘッダは $20\text{ B}$ のため、1断片に入れられる最大データ長は $1{,}500 - 20 = 1{,}480\text{ B}$（$8 \times 185$ であり 8 の倍数）です。残り $3{,}000 - 2{,}960 = 40\text{ B}$ が断片3に入ります。

    * **断片 1：** (i) 全長 **$1{,}500\text{ B}$**（データ $1{,}480\text{ B}$）、(ii) `MF = 1`、(iii) オフセット $0 / 8 = \mathbf{0}$
    * **断片 2：** (i) 全長 **$1{,}500\text{ B}$**（データ $1{,}480\text{ B}$）、(ii) `MF = 1`、(iii) オフセット $1{,}480 / 8 = \mathbf{185}$
    * **断片 3：** (i) 全長 **$60\text{ B}$**（ヘッダ $20\text{ B}$ ＋ データ $40\text{ B}$）、(ii) `MF = 0`、(iii) オフセット $2{,}960 / 8 = \mathbf{370}$

2. **ARP の問い合わせ対象と `traceroute` の動作原理：**

    * **(a) ARP Request で問い合わせる対象：** **デフォルトゲートウェイ（`192.168.1.1`）** です。宛先 `93.184.216.34` は別サブネットにあり、ARP ブロードキャストは L3 ルータを越えられないため、ホスト A はまず同一 LAN 内で次にフレームを渡す相手であるデフォルトゲートウェイの MAC アドレスを問い合わせます。
    * **(b) `traceroute` が組み合わせている仕組み：** IP ヘッダの **TTL（Time To Live）** と、ICMP の **Time Exceeded（Type 11）** です。送信元が `TTL = 1, 2, 3, ...` と1ずつ増やしながら探索パケットを送ることで、ちょうど $k$ ホップ目のルータで `TTL = 0` になって破棄され、そのルータから返ってくる ICMP Time Exceeded の送信元 IP から各ホップのルータを順に特定します。

3. **世界中のルータの「経路表」は誰がどうやって作っているのか（本節への接続）：**
    大規模ネットワークでは人間が手作業で経路表（静的ルート）を書き換えることは不可能です。ルータ同士が制御メッセージを交換して自律的に最短経路を計算し、リンク断線時にも自動迂回する仕組みが**動的ルーティング**であり、組織内部（AS内）で使われる代表が **距離ベクトル型（RIP）** と **リンク状態型（OSPF）** です。

## 6-7. 動的ルーティング①：距離ベクトル（RIPの無限カウント）vs リンク状態（OSPF）

### 1. 動機（Why）：なぜルータの経路表を「自律的なグラフアルゴリズム」で自動構築する必要があるのか

前節まで（[6-5](6-5.md)・[6-6節](6-6.md)）では、各ルータの内部にすでに正しい転送表（ルーティングテーブル）が登録されている前提で、最長プレフィックス一致（LPM）や ARP・NAT によってパケットが目的地へ運ばれる流れを追いました。

小規模な家庭用ネットワークであれば、管理者が「デフォルトゲートウェイは `192.168.1.1`」と手動で設定する **静的ルーティング（Static Routing）** でも十分です。しかし、大学キャンパスや大企業、プロバイダ（ISP）のネットワークのようにルータが数十台〜数千台と連なる環境では、静的ルーティングは次の2つの理由で破綻します。

1. **トポロジ変更への追従不能：** 新しい部署のサブネットが増設されたり、配線が変更されたりするたびに、関連するすべてのルータの設定を人間が手作業で矛盾なく書き換えるのは非現実的です。
2. **障害時の自動迂回ができない：** 途中の光ファイバが工事で切断されたりルータが故障したりしたとき、静的ルートでは切れっぱなしのリンクへパケットを送り続けて通信が途絶えたままになります。

そこで、ネットワークを **「ルータ＝頂点 $V$、リンク＝コスト（重み）付きの辺 $E$」** からなる重み付きグラフ $G = (V, E)$ としてモデル化し、ルータ同士が自律的に最短経路を計算・更新する **動的ルーティングプロトコル** が不可欠になります。

自律的に最短経路を求める分散アルゴリズムには、情報共有の仕方がまったく異なる **2つの対照的なアプローチ** があります。

* **距離ベクトル型（Distance Vector：代表例 RIP）：** 全体の地図は持たず、「**隣人から聞いた『宛先までの距離の噂』**」だけを頼りに自分の経路表を少しずつ改善する（Bellman-Ford 法）。
* **リンク状態型（Link State：代表例 OSPF）：** 全ルータが「自分の隣接リンクの状態」をネットワーク全体へ配布して**全員が同じ完全な地図**を持ち、各自が手元で最短経路木を計算する（Dijkstra 法）。

本節では、この2大アルゴリズムの動作とトレードオフを、手計算トレースと障害時の振る舞い（無限カウント問題）を通して徹底的に対比します。

### 2. 具体例と動作イメージ（Toy Model）

数式とプロトコル仕様に入る前に、2つの小さな例で「距離ベクトルとリンク状態の考え方の違い」および「距離ベクトル特有の問題（無限カウント）」を体感します。

#### 実験A：見知らぬ街で駅へ行く 2 つの方法

見知らぬ街の交差点（ルータ）に立って、目的地（駅）までの最短ルートを探す状況を想像してください。

* **距離ベクトル型（道標・噂ベース）：** 街全体の地図は持っていません。隣の交差点にいる人へ「駅から何分かかりますか？」と尋ね、北の隣人が「10分」、東の隣人が「5分」と答えたら、「東の交差点まで2分かかるから、東経由なら $2 + 5 = 7\text{ 分}$ が最短だ。次も東へ案内しよう」と記録します。
* **リンク状態型（完全な地図ベース）：** 街中のすべての交差点から「どの道が何分で通行可能か」という最新情報を全員へ一斉配布し、全員が同じ街全体の地図（データベース）を手元に持ちます。あとは各自が地図上で最短ルートを一気に計算します。

#### 実験B：3台直列のネットワークで起きる「無限カウント（Count-to-Infinity）」

距離ベクトル型は実装がとても単純ですが、**「悪いニュース（リンク断線）の伝播が遅い」**という致命的な弱点を持っています。次の3台のルータが直列に繋がったネットワーク（各リンクのコスト＝1ホップ）を考えます（図6-7-1右）。

$$
\text{A} \;\overset{1}{\longleftrightarrow}\; \text{B} \;\overset{1}{\longleftrightarrow}\; \text{C}
$$

* **正常時：**

    * C は自分自身なので「C までの距離 $= 0$」。
    * B は C と直結しているため「C までの距離 $= 1$（次ホップ C）」。
    * A は B から「C まで距離 1」と聞いたため「C までの距離 $= 2$（次ホップ B）」。

ここで、**B–C 間のケーブルが切断された**とします（コスト $= \infty$）。

1. **時刻 $t_1$：** B は C との直結リンクが切れたことを検知します。ところが、B が「C は到達不能（$\infty$）だ」と A へ伝える直前に、**まだ断線を知らない A が定期広告で「私は C まで距離 2 で行けます」と B へ報告**してきます。
2. **時刻 $t_2$：** 全体の地図を持たない B は、A の経路が「実は自分（B）を経由していること」を知りません。そこで B は「A 経由なら C へ行ける」と誤解し、自分の距離を **$1 + 2 = 3$（次ホップ A）** へ更新します。
3. **時刻 $t_3$：** 今度は B が A へ「C まで距離 3 に変わりました」と広告します。A は自分の次ホップである B の距離が増えたので、自分の距離を **$1 + 3 = 4$** へ更新します。
4. **時刻 $t_4, t_5, \dots$：** B が `5`、A が `6`、B が `7`、A が `8` ……と、**2台が互いに存在しない経路を信じ合って距離を1ずつ増やし続け、無限大まで永遠に数え上げ続ける（無限カウント問題：Count-to-Infinity）**のです。しかもこの間、C 宛てのパケットは A と B の間を TTL が `0` になるまで延々と往復（ルーティングループ）し続けます。

### 3. 構造・アルゴリズム・実装（What）

#### (1) コントロールプレーンとデータプレーン（RIB vs FIB）

ルータの内部機能は、役割と処理速度の異なる次の **2つのプレーン（層）** に明確に分離されています。

* **コントロールプレーン（制御面：ソフトウェア／CPU処理）：**
    RIP や OSPF、BGP などの動的ルーティングプロトコルを動かし、隣接ルータと制御メッセージを交換して最短経路を計算し、**経路表（RIB：Routing Information Base）** を構築・維持する頭脳部分（ミリ秒〜秒オーダー）。

* **データプレーン（転送面：専用ハードウェア ASIC / TCAM 処理）：**
    RIB から最適な転送先だけを抽出・最適化した **転送表（FIB：Forwarding Information Base）** を持ち、到着した個々の IP パケットを [6-5節](6-5.md)の **最長プレフィックス一致（LPM）** で数ナノ秒のうちに出力ポートへ送り出す手足部分。

本節と次節（[6-8節](6-8.md)）で扱うのは、まさに前者の **コントロールプレーン** のアルゴリズムです。

#### (2) 距離ベクトル型（Distance Vector）：Bellman-Ford 方程式と RIP

距離ベクトル型アルゴリズムの数学的基盤は、リチャード・ベルマンとレスター・フォードによる **Bellman-Ford（ベルマン＝フォード）方程式** です。

ノード $x$ から宛先ノード $y$ までの最小コストを $D_x(y)$、$x$ と隣接ノード $v$ の間の直接リンクコストを $c(x, v)$ とすると、最短経路の最適性原理より次式が成り立ちます。

$$
D_x(y) = \min_{v \in N(x)} \bigl\{\, c(x, v) + D_v(y) \,\bigr\}
$$

ここで $N(x)$ はノード $x$ の隣接ノード集合です。各ノード $x$ は、すべての宛先 $y$ に対する現在の推定最小コストを並べた配列（**距離ベクトル** $\mathbf{D}_x$）を保持し、次の単純な分散ループを繰り返します（図6-7-1左）。

1. 自身のリンクコストが変化するか、隣接ノード $v$ から新しい距離ベクトル $\mathbf{D}_v$ を受信します。
2. 各宛先 $y$ について上式 $\min_v \{ c(x, v) + D_v(y) \}$ を再計算します。
3. 自分の距離ベクトル $\mathbf{D}_x$ の値が1つでも変化したら、更新後の $\mathbf{D}_x$ をすべての隣接ノードへ送信します。

これを実装した古典的なプロトコルが **RIP（Routing Information Protocol）** です。RIP は UDP ポート 520 を使い、30秒ごとに隣接ルータへ自分の経路表全体を広告します。メトリック（リンクコスト）には単純な **ホップ数（通過ルータ数）** を用います。

実験Bの **無限カウント問題** を緩和するため、RIP は次の3つの補正を組み込んでいます。

1. **最大ホップ数の制限（$\infty = 16$）：** ホップ数の上限を **15** と定め、**16 を到達不能（$\infty$）** とみなします。これにより、仮に無限カウントが起きても 16 で確実に打ち切られます（反面、直径 16 ホップ以上の大規模ネットワークでは RIP を使用できません）。
2. **スプリットホライズン（Split Horizon）：** 「ある隣接ルータ $B$ から教えてもらった経路情報は、その同じ $B$ へ向かっては広告しない」という規則です。実験Bの A が B へ「C まで距離 2」と送り返すのを防げます。
3. **ポイズンリバース（Poison Reverse）：** スプリットホライズンの強化版です。「$B$ 経由で到達している宛先 $C$ については、$B$ へ向かってあえて **『距離 $=\infty$（16）』と毒を盛って広告**する」規則で、2ノード間のループを即座に断ち切れます。

#### (3) リンク状態型（Link State）：LSA フラッディングと Dijkstra 法（OSPF）

RIP の「全体が見えないことによる収束の遅さとホップ数 15 の壁」を根本から解決し、現代の企業網・大学網・ISP 内部（AS内）で標準的に使われているのが **リンク状態型** の代表プロトコル **OSPF（Open Shortest Path First）** です（IP プロトコル番号 `89` で直接運ばれます）。

OSPF は、次の **3ステップ** で全ルータが正確かつ高速に最短経路表を構築します（図6-7-2）。

1. **近隣発見（Hello プロトコル）：** 各ルータは定期的に `Hello` パケットを全インタフェースへ送信し、隣接しているルータとリンクの生存（死活監視）およびリンクコストを把握します。
2. **LSA フラッディングと LSDB の完全同期：**
    各ルータは「自分の隣接ルータとそれぞれのリンクコスト」だけを記した小さな広告パケット **LSA（Link-State Advertisement）** を作成し、ネットワーク内の全ルータへ行き渡るように転送（**フラッディング**）します（シーケンス番号で重複転送を防止します）。その結果、ネットワーク内の**全ルータがまったく同一の全体地図（LSDB：Link-State Database）**をメモリ上に保持します。

3. **Dijkstra（ダイクストラ）法による最短経路木（SPT）の計算：**
    各ルータは、手元の完全な地図（LSDB）の上で自分自身を始点 $u$ とする **Dijkstra のアルゴリズム**（計算量：二分ヒープ使用時 $O((|V|+|E|)\log |V|)$）を独立して実行し、すべての宛先への最短経路と「最初に踏み出すべき次ホップ」を確定して転送表（FIB）へ書き込みます。

図6-7-2左の4ノードグラフ（双方向リンクのコスト：`A–B: 2`、`A–C: 5`、`B–C: 1`、`B–D: 4`、`C–D: 2`、始点 A）に対して、Dijkstra 法のステップを手計算で追ってみましょう。確定済み集合を $N'$ とします。

| ステップ | 確定集合 $N'$ | $D(\text{B})$ / 直前 | $D(\text{C})$ / 直前 | $D(\text{D})$ / 直前 | 次に確定する最小ノード |
| :---: | :--- | :---: | :---: | :---: | :--- |
| 0 (初期) | `{A}` | `2` (A) | `5` (A) | $\infty$ | **B**（コスト `2`） |
| 1 | `{A, B}` | `2` (A) | **`3` (B)** | `6` (B) | **C**（コスト `3`：$2+1 < 5$ で更新） |
| 2 | `{A, B, C}` | `2` (A) | `3` (B) | **`5` (C)** | **D**（コスト `5`：$3+2 < 6$ で更新） |
| 3 (完了) | `{A, B, C, D}` | `2` (A) | `3` (B) | `5` (C) | 全ノード確定 |

結果として、ルータ A の転送表には「B 宛て $\to$ B、C 宛て $\to$ B、D 宛て $\to$ B」と登録されます。もし途中で B–C 間のリンクが切れても、B と C が即座に「B–C 断線」の LSA をフラッディングし、全ルータが数秒以内に新しい地図で Dijkstra 法を再実行するため、**無限カウントは原理的に一切発生しません**。

#### (4) 距離ベクトル型（RIP）vs リンク状態型（OSPF）の総合比較

| 比較項目 | 距離ベクトル型（RIP） | リンク状態型（OSPF） |
| :--- | :--- | :--- |
| **基盤アルゴリズム** | Bellman-Ford 方程式（分散反復） | Dijkstra 法（全体グラフ上で独立計算） |
| **交換する情報** | 自分の経路表全体（全宛先への距離）を**隣人だけ**へ | 自分の隣接リンク情報（LSA）だけを**全ルータ**へ |
| **障害時の収束速度** | 遅い（無限カウント・ルーティングループの恐れ） | **速い**（変化した LSA だけ即座にフラッディング） |
| **メトリック（基準）** | ホップ数のみ（最大 15、16 は到達不能） | リンク帯域幅に基づくコスト（ECMP 等コスト複数経路も可） |
| **CPU・メモリ消費** | 非常に小さい（安価な機器でも動く） | 大きい（LSDB の保持と Dijkstra 計算が必要） |
| **適用規模** | 小規模ネットワークのみ | 中〜大規模の企業網・大学網・ISP 内部網（AS内標準） |

> **【コラム：なぜ OSPF のコストは「ホップ数」ではなく「帯域幅の逆数」なのか】**
>
> RIP のように「通過するルータの数（ホップ数）」だけで経路を決めると、現実のネットワークでは奇妙な選択が起きます。たとえば「A から B へ直結している古い $10\text{ Mbps}$ 回線（1ホップ）」と、「A → C → B を経由する最新の $10\text{ Gbps}$ 光ファイバ（2ホップ）」があるとき、RIP はホップ数の少ない $10\text{ Mbps}$ 回線を選んでしまい、**1,000 倍速い幹線ルートが完全に遊休**になります。
>
> そこで OSPF は、リンクのコストを $\text{Cost} = \dfrac{\text{基準帯域幅}}{\text{リンク帯域幅}}$（標準では基準帯域幅 $100\text{ Mbps}$、現代の 10G/100G 網では管理者が基準を $100\text{ Gbps}$ 等へ引き上げて設定）と定義します。太い回線ほどコストが小さくなるため、OSPF は自動的に $10\text{ Gbps}$ の2ホップ経路を最適ルートとして選びます。さらに最小コストが同じ経路が複数あれば、両方にトラヒックを均等分散する **ECMP（Equal-Cost Multi-Path）** も標準でサポートしています。

### 4. 限界と補正（Critique & Adaptation）

#### (1) スプリットホライズンでも防げない「3ノード以上のループ」

3-(2)で、距離ベクトル型の無限カウント対策としてスプリットホライズンとポイズンリバースを紹介しました。これらは実験Bのような**2ノード間（A–B間）のピンポンループ**は確実に防ぎます。

しかし、**3ノード以上が三角形（閉路）に並んでいる場合、ポイズンリバースを使っても無限カウントを完全には防げません**。たとえば A–B–C が三角形に繋がっており、C の先に宛先 X がある状態で C–X が断線したとき、C が X へ到達不能になった瞬間に A が「B経由で X へ行ける」、B が「A経由で X へ行ける」と3台の間で誤った噂が循環し始めてしまうためです。これをさらに抑える補正として、距離が増大した経路を一時的に更新凍結する **ホールドダウンタイマ** や、変化時に30秒待たず即通知する **トリガードアップデート** が併用されますが、中〜大規模網では最初から全体地図を持つ OSPF（または IS-IS）へ移行するのが根本解決です。

#### (2) OSPF のフラッディング爆発と「エリア分割（エリア0 バックボーン）」

一方、OSPF にも大規模化に伴う明確な限界があります。全ルータが LSA を全員へフラッディングして同じ LSDB を持つため、ルータ台数 $|V|$ が数千台に増えると、**どこかの端のリンクが1本点滅（フラッピング）しただけでネットワーク全体へ LSA が洪水のように飛び交い、全ルータが一斉に重い Dijkstra 計算を繰り返して CPU が飽和**してしまいます。

この限界に対する OSPF の構造的な補正が、ネットワーク全体を複数の論理グループへ分割する **階層化（エリア分割：Multi-Area OSPF）** です（図6-7-3）。

* 中央に必ず **バックボーンエリア（エリア 0）** を置き、その周囲へ通常エリア（エリア 1, エリア 2, …）を星型に接続します。
* エリア同士の境界に立つルータを **ABR（Area Border Router）** と呼びます。
* 詳細な LSA フラッディングと LSDB の同期は**各エリアの内部だけ**に封じ込め、ABR はエリア 0 へ向かって「エリア 1 の住所はまとめて `10.1.0.0/16`」という **集約された要約経路だけ** を伝えます。

これにより、エリア 1 の端でリンク障害が起きてもエリア 2 のルータは一切影響を受けず、LSDB サイズも Dijkstra 計算負荷も大きく抑えられます。

#### (3) IGP の限界：なぜ世界中のインターネット全体を 1 つの OSPF で繋げないのか（次節への動機）

RIP や OSPF は、単一の組織・管理主体が運営するネットワーク（**AS：自律システム**）の内部で使う **IGP（Interior Gateway Protocol）** です。では、世界中の何万ものプロバイダや企業をすべて 1 つの巨大な OSPF で繋げないのはなぜでしょうか。理由は次の **2つの壁** にあります。

1. **規模の壁：** 世界中の何百万台ものルータのリンク情報をフラッディングすれば、一瞬で制御トラヒックが飽和して破綻します。
2. **自律性とポリシー（契約・コスト）の壁：** たとえ物理的に最短距離であっても、「競合他社の ISP の通信を自社回線でタダ乗り（トランジット）させたくない」「政治的・契約上の理由で特定経路を避けたい」という**経済的・運用的なポリシー**を最優先しなければなりません。純粋なコスト最小化だけを行う OSPF では、こうした組織間のポリシーを表現できないのです。

この2つの壁を越えてインターネット全体を1つに束ねる仕組みが、次節（[6-8節](6-8.md)）で学ぶ **BGP（Border Gateway Protocol）** です。

> **【確認の問い】**
>
> 1. **（Dijkstra 法による最短経路の手計算）**
>     4つのルータ X, Y, Z, W が次の双方向リンク（括弧内はコスト）で結ばれています。
>
>     * `X–Y (1)`、`X–Z (4)`、`Y–Z (2)`、`Y–W (6)`、`Z–W (1)`
>     
>     始点 **X** から Dijkstra 法を実行し、Y, Z, W それぞれへの **(a) 最小総コスト** と **(b) 最短経路（例：`X → ...`）** を求めてください。
>
> 2. **（RIP の無限カウント問題と OSPF のエリア分割）**
>     次の 2 つの問いに簡潔に答えてください。
>
>     * (a) 距離ベクトル型（RIP）でリンク断線時に「無限カウント問題」が発生する根本原因と、RIP が導入している2つの対策（最大ホップ数制限とポイズンリバース）の仕組みを説明してください。
>     * (b) リンク状態型（OSPF）でネットワークが大規模になったとき、なぜ単一エリアのまま運用せず **エリア 0（バックボーン）と複数エリアへ分割** するのでしょうか。
>
> 3. **（次節への伏線：世界中の ISP 同士を繋ぐとき、なぜ OSPF ではなく BGP が必要か）**
>     本節4-(3)で、異なる会社（ISP やクラウド事業者＝AS）同士を繋ぐインターネット全体の経路制御には、純粋な最短距離だけを計算する OSPF は使えないと述べました。では、**BGP** は「無限カウント（ループ）」を防ぎつつ「契約に基づくポリシー制御」を実現するために、距離ベクトルやリンク状態とは異なるどのような情報（**パスベクトル**）を交換しているのでしょうか。
