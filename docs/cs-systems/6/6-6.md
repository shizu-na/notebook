### 前節（6-5）の確認問題の解答

前節の最後に提示した3つの問いの解答を確認します。問3がそのまま本節（IP の周辺プロトコル群）の導入になります。

1. **CIDR サブネットの手計算（`172.16.40.70/26`）：**
    先頭から 26 ビットがネットワーク部、残り $32 - 26 = 6$ ビットがホスト部です。第4オクテット `70` を2進数へ展開すると $70 = 64 + 4 + 2 = \texttt{01000110}_2$ となり、上位 2 ビット（`01`）がネットワーク部、下位 6 ビット（`000110`）がホスト部になります。

    * **(a) サブネットマスク：** 第4オクテットが $\texttt{11000000}_2 = 192$ なので **`255.255.255.192`**。
    * **(b) ネットワークアドレスとブロードキャストアドレス：**

        * ネットワークアドレス（下位6ビットすべて `0`）：$\texttt{01000000}_2 = 64 \implies$ **`172.16.40.64/26`**
        * ブロードキャストアドレス（下位6ビットすべて `1`）：$\texttt{01111111}_2 = 127 \implies$ **`172.16.40.127`**

    * **(c) 割り当て可能な最大ホスト台数：** $2^6 - 2 = 64 - 2 = \mathbf{62\text{ 台}}$（`172.16.40.65` 〜 `172.16.40.126`）。

2. **最長プレフィックス一致（LPM）の転送先判定：**

    * **(a) 宛先 `10.1.6.100`：** `0.0.0.0/0`（0 bit）、`10.1.0.0/16`（16 bit）、`10.1.4.0/22`（22 bit：`10.1.4.0` 〜 `10.1.7.255`）の3つすべてに一致します。最も一致ビット数が長い `/22` が選ばれるため、**`Link 2`** へ転送されます。
    * **(b) 宛先 `10.1.8.1`：** `/22` の範囲（第3オクテット `4`〜`7`）には一致せず、`/0`（0 bit）と `/16`（16 bit）に一致します。最長一致の `/16` が選ばれるため、**`Link 1`** へ転送されます。

3. **IP アドレスと MAC アドレスの橋渡し・プライベート IP の変換（本節への接続）：**

    * **(i) ルータの MAC アドレスの調べ方：** ホスト A は **ARP（Address Resolution Protocol）** を用い、LAN 内へブロードキャストで「`192.168.1.1` の MAC アドレスを教えてほしい」と問い合わせ、ルータから返ってくるユニキャスト応答で MAC アドレスを取得します。
    * **(ii) プライベート IP を外へ出す変換：** ルータは **NAT / NAPT（IPマスカレード）** を行い、パケットの送信元 IP（`192.168.1.10`）とポート番号を、ルータ自身のグローバル IP アドレスと割り当てたポート番号へ書き換えて変換表に記録したうえでインターネットへ送り出します。

## 6-6. フラグメンテーション・経路MTU探索と周辺プロトコル（ARP・ICMP・DHCP・NAT）

### 1. 動機（Why）：なぜ「IP アドレスとヘッダ」だけでは1個のパケットすら現場で動かせないのか

前節（[6-5節](6-5.md)）では、IPv4 と IPv6 のヘッダ構造、CIDR / VLSM による階層的なアドレス設計、そしてルータの最長プレフィックス一致（LPM）を学びました。しかし、IP というプロトコル本体だけでは、実際のネットワーク上で通信を成立させるために必要な次の **5つの現場のギャップ** が埋まりません。

1. **リンクごとに異なる最大サイズ（MTU）の壁：**
    イーサネットは1フレームあたり最大 $1{,}500\text{ B}$ まで運べますが、途中のトンネル回線（PPPoE や VPN）では $1{,}454\text{ B}$ や $1{,}280\text{ B}$ しか通せないことがあります。大きすぎる IP パケットをどう分割・調整するか（**フラグメンテーションと経路 MTU 探索**）。

2. **第3層（IP）と第2層（MAC）の断絶：**
    ホストやルータが「次は `192.168.1.1` へ渡せ」と知っていても、実際にイーサネットフレーム（[6-4節](6-4.md)）をケーブルへ流すには、相手の 48 ビット **MAC アドレス** が必須です（**ARP**）。

3. **端末の初期設定の手間：**
    カフェの Wi-Fi やオフィス LAN に PC・スマートフォンを繋ぐたびに、利用者が自分の IP アドレス・サブネットマスク・デフォルトゲートウェイを手入力するわけにはいきません（**DHCP**）。

4. **エラーの通知と障害の切り分け：**
    TTL が `0` になってパケットが破棄されたり、宛先ネットワークへ到達できなかったりしたとき、IP 本体には送信元へ異常を知らせる手段がありません（**ICMP**）。

5. **IPv4 アドレスの枯渇とプライベート網の接続：**
    家庭や企業内では無数の端末にプライベート IP（`192.168.x.x` 等）を配りますが、そのままではインターネット上の Web サーバと通信できません（**NAT / NAPT**）。

本節では、IP を現実のインターネットで動かすために密接に協調するこれら5つの仕組みを、具体的なパケットの数値例と図解で整理します。

---

### 2. 具体例と動作イメージ（Toy Model）

仕様の整理に入る前に、2つの小さな手計算とトレースで「パケット分割（フラグメンテーション）」と「ARP＋NAPT による住所書き換え」の動作を体感します。

#### 実験A：$4{,}000\text{ B}$ の IPv4 パケットを $\text{MTU} = 1{,}500\text{ B}$ のリンクへ通す

送信元が作った IPv4 パケットの全長が **$4{,}000\text{ B}$**（IPv4 ヘッダ $20\text{ B}$ ＋ ペイロード $3{,}980\text{ B}$、識別子 `ID = 777`）であり、途中のルータが出力するリンクの **MTU（Maximum Transmission Unit：最大転送単位）** が **$1{,}500\text{ B}$** だったとします。

1つの断片（フラグメント）に入れられる最大データ長は $1{,}500 - 20 = 1{,}480\text{ B}$ です。しかも IPv4 の仕様上、断片の開始位置（**フラグメントオフセット**）は **8 バイト単位** で表現するため、最後の断片以外のデータ長は必ず **8 の倍数** でなければなりません。$1{,}480 = 8 \times 185$ なのでちょうど8の倍数です。

したがって、ペイロード $3{,}980\text{ B}$ は次の **3つの断片** へ分割されます（図6-6-1左）。

| 断片 | 識別子 (`ID`) | データ長 | パケット全長（ヘッダ20B込） | `MF` フラグ（続きあり） | オフセット（8B単位） | 元のデータ範囲 |
| :---: | :---: | :---: | :---: | :---: | :---: | :---: |
| **断片 1** | `777` | $1{,}480\text{ B}$ | **$1{,}500\text{ B}$** | **`1`**（続く） | $0 / 8 = \mathbf{0}$ | `0` 〜 `1479` |
| **断片 2** | `777` | $1{,}480\text{ B}$ | **$1{,}500\text{ B}$** | **`1`**（続く） | $1480 / 8 = \mathbf{185}$ | `1480` 〜 `2959` |
| **断片 3** | `777` | $1{,}020\text{ B}$ | **$1{,}040\text{ B}$** | **`0`**（最後） | $2960 / 8 = \mathbf{370}$ | `2960` 〜 `3979` |

途中のルータはこれら3個の独立した IP パケットをそのまま別々に転送し、**最終目的地である受信ホストだけ**が同じ `ID = 777` の3断片を集め、オフセット順に並べて元の $3{,}980\text{ B}$ へ再構成（リアセンブリ）します。

#### 実験B：自宅の PC が外部 Web サーバへ1パケット送るまでの住所の二重変化

自宅 LAN の PC（プライベート IP `192.168.1.10`、MAC `AA`）が、家庭用ルータ（LAN側 IP `192.168.1.1`・MAC `RR`、WAN側グローバル IP `203.0.113.5`）を経由して、外部の Web サーバ（グローバル IP `93.184.216.34`、ポート `80`）へパケットを送る瞬間を追ってみます。

1. **PC の宛先判定と ARP：** PC は宛先 `93.184.216.34` が自分のサブネット（`192.168.1.0/24`）の外側にあると判断し、「まずデフォルトゲートウェイ `192.168.1.1` へ渡す」と決めます。そこで **ARP** で `192.168.1.1` の MAC アドレス `RR` を調べます。
2. **LAN 上のフレーム：**

    * L2 ヘッダ：送信元 MAC `AA` $\to$ **宛先 MAC `RR`（隣のルータ）**
    * L3 ヘッダ：送信元 IP `192.168.1.10`（ポート `50000`）$\to$ **宛先 IP `93.184.216.34`（ポート `80`）**

3. **ルータによる NAPT 変換：** ルータはフレームを受け取って L2 ヘッダを剥がし、送信元がプライベート IP であるため **NAPT 変換表** へ `(192.168.1.10, 50000) ⇄ (203.0.113.5, 40001)` を登録し、IP・TCP ヘッダの送信元を **`203.0.113.5 : 40001`** へ書き換えてインターネット側へ送り出します。
4. **返信パケットの逆変換：** Web サーバから `203.0.113.5 : 40001` 宛てに返信が戻ってくると、ルータは NAPT 変換表を逆引きして宛先を **`192.168.1.10 : 50000`** へ書き戻し、自宅 LAN の PC（MAC `AA`）へ届けます。

### 3. 構造・アルゴリズム・実装（What）

#### (1) フラグメンテーションと経路 MTU 探索（Path MTU Discovery: PMTUD）

実験Aのように、IPv4 では途中のルータがパケットを分割（フラグメンテーション）する仕様が用意されていましたが、ルータに重い負荷がかかるうえ、後述する再送効率の悪化（4-(1)）を引き起こします。そのため現代の IPv4 通信および **IPv6（途中ルータでの分割を全面禁止：[6-5節](6-5.md)）** では、最初から**経路上の最小 MTU を調べて分割せずに送る** **経路 MTU 探索（PMTUD：Path MTU Discovery）** が標準となっています（図6-6-1右）。

* **PMTUD の手順：**

    1. 送信ホストは、IPv4 ヘッダの **DF ビット（Don't Fragment：分割禁止フラグ）を `1`** に立てて（IPv6 では常に分割禁止）、自分のローカルリンクの MTU（例：$1{,}500\text{ B}$）のサイズでパケットを送信します。
    2. もし経路上に MTU が小さいリンク（例：$1{,}400\text{ B}$）を持つルータがあれば、ルータは DF=1 のため分割せずそのパケットを**破棄**し、送信元へ **ICMP エラー（IPv4: `Fragmentation Needed`、IPv6: `Packet Too Big`）** に「次のリンクの MTU は $1{,}400\text{ B}$ だ」という数値を添えて返送します。
    3. 送信ホストは通知を受け取ると、その宛先向けのキャッシュ済み経路 MTU を $1{,}400\text{ B}$ へ引き下げて再送します。

#### (2) ARP（Address Resolution Protocol）と IPv6 の NDP

同一 LAN（ブロードキャストドメイン）内で「相手の IPv4 アドレスから 48 ビットの MAC アドレスを引く」プロトコルが **ARP（RFC 826）** です（図6-6-2）。

1. **ARP キャッシュの検索：** ホスト A はまずOS内部の **ARP テーブル（`IP → MAC` のキャッシュ表、有効期限は数分〜20分程度）** を探します。ヒットすればそのまま送信します。
2. **ARP Request（ブロードキャスト）：** キャッシュにない場合、宛先 MAC を **`FF:FF:FF:FF:FF:FF`（全員宛て）**、EtherType を `0x0806` にして「`192.168.1.1` を持っている人は、私（`192.168.1.10`, `AA`）へ自分の MAC を教えて」という ARP 要求フレームを LAN 全体へ流します。
3. **ARP Reply（ユニキャスト）：** 全端末が受け取り、該当 IP を持つ機器（ルータ `192.168.1.1`）だけが「私です、MAC は `RR` です」という ARP 応答を **ホスト A の MAC `AA` 宛てのユニキャスト** で返します。ホスト A はこれを ARP テーブルへ登録します。

**重要：** 宛先 IP が**別サブネット（外部インターネット等）**にある場合、ARP で問い合わせるのは最終宛先（例：`93.184.216.34`）ではなく、**同じ LAN 内にいるデフォルトゲートウェイ（ルータ）の IP アドレス**です。ARP ブロードキャストは L3 ルータを越えられないため、各ホップごとに「次のルータの MAC アドレス」を ARP で解決しながらバケツリレーします。なお、IPv6 ではブロードキャストが廃止されたため、ARP の代わりに ICMPv6 のマルチキャストを用いる **NDP（Neighbor Discovery Protocol：近隣探索プロトコル）** が使われます。

#### (3) DHCP（Dynamic Host Configuration Protocol）

新しく LAN へ接続された端末へ、**①自身の IP アドレス、②サブネットマスク、③デフォルトゲートウェイ（ルータの IP）、④DNS サーバの IP** の4点セットを自動配布（期限付き貸与＝**リース**）するプロトコルが **DHCP** です。頭文字をとって **DORA** と呼ばれる次の4ステップ（UDP ポート 67/68 を使用）で完了します（図6-6-2右）。

1. **Discover（発見）：** まだ自分の IP を持たない端末が、送信元 `0.0.0.0`・宛先 `255.255.255.255`（ブロードキャスト）で「誰か DHCP サーバはいませんか？」と呼びかけます。
2. **Offer（提示）：** 受信した DHCP サーバが、空きプールから候補 IP（例：`192.168.1.50`）とリース期間（例：24時間）を提示します。
3. **Request（要求）：** 複数の DHCP サーバから Offer が届いた場合にも備え、端末は選んだ1台のサーバと IP をブロードキャストで「この IP を使います」と宣言します（選ばれなかった他サーバは候補を空きプールへ戻します）。
4. **Ack（確認）：** 選ばれた DHCP サーバが最終承認（`DHCP ACK`）を返し、端末がネットワーク設定を完了します。

#### (4) ICMP（Internet Control Message Protocol）

**ICMP（RFC 792、IP プロトコル番号 `1`）** は、IP パケットのペイロードとして運ばれる「ネットワーク層の制御・エラー報告プロトコル」です。主な役割はエラー通知と疎通診断の2つです。

| Type / Code | 名称 | 主な用途・発生条件 |
| :---: | :--- | :--- |
| Type `8` / `0` | **Echo Request / Echo Reply** | **`ping` コマンド**による到達性確認と往復遅延（RTT）の計測 |
| Type `3` | **Destination Unreachable** | 宛先ネットワーク・ホスト・ポートへの到達不能。Code `4` は PMTUD 用の **Fragmentation Needed** |
| Type `11` | **Time Exceeded** | 途中ルータで **TTL が `0`** になってパケットが破棄された（ループ検知および **`traceroute`**） |

> **【コラム：`traceroute` コマンドはどうやって途中の全ルータの IP を暴いているのか】**
>
> `traceroute example.com` を実行すると、自分の PC から宛先サーバまでの間にある 10〜20 台のルータの IP アドレスと応答時間（ms）が1ホップずつ一覧表示されます。IP パケット自体には「途中ルータへ自分のIPを名乗らせる」機能がないのに、どうやってこれを知っているのでしょうか。
>
> 答えは、[6-5節](6-5.md)の **TTL** と本節の **ICMP Time Exceeded** を組み合わせた巧みな仕掛けです。
>
> 1. まず送信ホストは、宛先 `example.com` に向けてあえて **`TTL = 1`** に設定した探索パケット（UDP や ICMP）を送ります。すると、**ちょうど 1 台目のルータ**で TTL が `1 → 0` になって破棄され、1台目のルータが送信元へ **ICMP Time Exceeded** を返してきます。その返信の送信元 IP を見れば「1ホップ目のルータの IP」が分かります。
> 2. 次に **`TTL = 2`** で送ります。1台目は `2 → 1` で通過し、**2台目のルータ**で `1 → 0` になって Time Exceeded が返るため、2ホップ目のルータが判明します。
> 3. 以降 `TTL = 3, 4, ...` と1ずつ増やし、ついに最終目的地のホストへ届くと（使用されていない高い UDP ポート宛てなら **ICMP Port Unreachable**、ICMP Echo なら **Echo Reply** が返る）、そこで探索完了となります。

#### (5) NAT と NAPT（IP マスカレード）・CGNAT

[6-5節](6-5.md)コラムで触れた通り、枯渇した IPv4 を現在まで延命させた最大の立役者が **NAT（Network Address Translation）**、特に1個のグローバル IPv4 アドレスを何百台ものプライベート IP 端末で同時共有する **NAPT（Network Address Port Translation / PAT / IPマスカレード）** です（図6-6-3）。

* **狭義の NAT（1対1変換）：** プライベート IP とグローバル IP を 1対1 で対応づけます。同時通信できる端末数がグローバル IP の個数に制限されるため、枯渇対策には向きません。
* **NAPT（多対1変換：家庭用・企業用ルータの標準）：** L3 の IP アドレスだけでなく、L4（TCP/UDP）の **ポート番号** まで同時に書き換えます。送信元 `(プライベートIP, 内部ポート)` と `(グローバルIP, 外部ポート)` の対応表（**NAT 変換テーブル**）をルータのメモリ上に動的に作成し、ポート番号（16ビット＝最大 65,535 通り）の違いでどの端末の通信かを識別します。
* **CGNAT（キャリアグレード NAT / 大規模 NAT）：** IPv4 アドレスのさらなる枯渇に伴い、ISP 側でも大規模な NAPT 装置を設置し、複数世帯で 1 個のグローバル IP を共有する多段 NAT（家庭用ルータ＋ISP 側 CGNAT）の構成も広く運用されています。

### 4. 限界と補正（Critique & Adaptation）

#### (1) フラグメンテーションの弱点と PMTUD ブラックホール

IPv4 の途中フラグメンテーションには深刻な欠点があります。1個の大きなパケットが 3 つの断片に割れたとき、**そのうちたった 1 断片でも途中で紛失すると、受信ホストは元のパケットを再構成できず残りの2断片も丸ごと破棄せざるを得ない**（送信元は元の大きなパケット全体を再送する羽目になる）のです。

だから現代は PMTUD が標準なのですが、今度は **PMTUD ブラックホール** という運用上の問題が起きます。途中のファイアウォール管理者がセキュリティのつもりで **すべての ICMP パケットを全面遮断** してしまうと、ルータが送った `ICMP Fragmentation Needed` が送信ホストへ届かなくなり、送信ホストは大きいパケットを送り続けて延々と無応答（ハングアップ）に陥ります。

* **補正：** ①ファイアウォールで ICMP のエラー通知（Type 3 Code 4 や IPv6 Packet Too Big）は遮断しないこと、②TCP 接続確立時にルータ側で最大セグメント長（**MSS**：TCP ペイロードの最大長、[7-2節](../7/7-2.md)）を小さく書き換える **MSS クランピング**、および③ICMP に頼らずサイズを変えたプローブパケットの到達確認で自律的に MTU を探る **PLPMTUD（RFC 4821）** を併用します。

#### (2) ARP スプーフィング（キャッシュポイズニング）と対策

ARP は1982年に設計されたステートレスな信頼ベースのプロトコルであり、**認証機能が一切ありません**。同じ LAN 内に悪意ある端末（攻撃者）が繋がっていると、リクエストもされていないのに「ゲートウェイ `192.168.1.1` の MAC は私（攻撃者）です」という偽の ARP Reply（Gratuitous ARP）を送りつけ、被害者 PC の ARP キャッシュを書き換えて通信をすべて自分経由で盗聴・改ざんする **ARP スプーフィング（中間者攻撃：MITM）** が成立してしまいます。

* **補正：** 企業 LAN の L2 スイッチでは、DHCP で配布した正規の `(IP, MAC, Port)` 対応表と照合して偽の ARP 応答を遮断する **DAI（Dynamic ARP Inspection）** を有効化し、さらに上位層では通信自体を **TLS / HTTPS（[7-7節](../7/7-7.md)）** でエンドツーエンド暗号化して盗聴・改ざんを無力化します。

#### (3) NAT が壊すエンドツーエンド原理と P2P 通信の壁

NAPT は IPv4 枯渇を救いましたが、[6-1節](6-1.md)コラムで学んだ **プロトコルの階層化とエンドツーエンド原理を正面から破っている** ことに注意が必要です。

* **階層違反：** L3 ルータであるはずの NAT 装置が、L4 の TCP/UDP ポート番号まで覗き見て書き換え、さらにコネクションごとの変換表（状態：ステート）をルータ内に保持しなければなりません（ルータが再起動すると全通信が即切断されます）。
* **外部からの着信不能（NAT 越え問題）：** LAN 内部から外へ発信したときだけ変換表へエントリが作られるため、外部のホストから NAT の内側にある端末へ直接接続を開始できません。Web 閲覧のようなクライアント・サーバ型では困りませんが、オンライン通話（WebRTC）やゲームのような **P2P（端末同士の直接通信）** では深刻な障壁になります。
* **補正：** 現在の IPv4 網では、外部の案内サーバと協調して NAT の穴開け（UDP ホールパンチング）や中継を行う **STUN / TURN / ICE** という複雑な仕組みで回避していますが、根本的な解決策はすべての端末がグローバルアドレスを直接持てる **IPv6 への移行** です。

>
> 2. **（ARP の問い合わせ対象と `traceroute` の動作原理）**
>     次の 2 つの問いに簡潔に答えてください。
>
>     * (a) ホスト A（`192.168.1.10/24`）が、別サブネットにある Web サーバ（`93.184.216.34`）へパケットを送ろうとするとき、ホスト A が ARP Request で問い合わせる対象 IP アドレスは `93.184.216.34` とデフォルトゲートウェイ（`192.168.1.1`）のどちらでしょうか。理由とあわせて答えてください。
>     * (b) `traceroute` コマンドが、宛先までの途中にあるルータの IP アドレスを1ホップ目から順に特定できるのは、IP ヘッダのどのフィールドと、ICMP のどのエラーメッセージを組み合わせているからでしょうか。

>     [6-5](6-5.md)・6-6節では、各ルータの内部にすでに正しい経路表（転送表）が登録されている前提でパケット転送を追いました。しかしインターネットには何百万台ものルータがあり、どこかで光ファイバが切れたり新しい回線が増設されたりするたびに、人間が手作業で経路表を書き換えることは不可能です。ルータ同士が自律的に最短経路を計算する 2 大アルゴリズム（**距離ベクトル型 RIP** vs **リンク状態型 OSPF**）は、それぞれどのように動作するでしょうか。
