### 前節（5-6）の確認問題の解答

前節の最後に提示した3つの問いの解答を確認します。前節まででファイルシステムの永続性とクラッシュ一貫性が整ったため、本節からは視点をシステム保護へ移し、誰にどの資源への操作を許すかを規定するアクセス制御モデルへ進みます。

1. **xv6 ジャーナリングの 3 バグ診断：**

    * **(a) `log_write(b)` で `bpin(b)` を呼び忘れた場合：**
        No-Steal 方針が崩れ、トランザクションのコミット前にバッファキャッシュの LRU 追い出しによって変更途中のブロック `b`（例：更新済みの i-node）だけがディスク本体へ書き出されてしまいます。その直後・コミット前に停電すると、再起動時はログヘッダ `n == 0` を見て何も修復しないため、本体に未コミットの半端な変更だけが残ってファイルシステムの一貫性（二重割当や迷子ブロック等）が壊れます。

    * **(b) フェーズ 1（`write_log()`）とフェーズ 2（`write_head(n > 0)`）のあいだで `CACHE FLUSH` を省略した場合：**
        ディスクコントローラ内蔵の揮発性キャッシュが書き込み順序を並べ替え、フェーズ 1 のログデータ本体が不揮発媒体へ届くより先に、フェーズ 2 のログヘッダ（`n > 0`）だけを物理媒体へ確定させてしまう恐れがあります。この状態で停電すると、再起動時のリカバリが「中身が未完成のゴミのままのログ領域」を本来のホーム位置へ丸ごと上書き（REDO）してしまい、ファイルシステム全体が破壊されます。

    * **(c) フェーズ 3（`install_trans()`）とフェーズ 4（`write_head(n = 0)`）の順序を逆にした場合：**
        本体への反映が終わる前にログヘッダが `n = 0` で消去されてしまいます。もし `install_trans()` が半分だけ進んだ時点で停電すると、再起動時にリカバリが `n == 0` を見て「未完了のコミットは存在しない」と判断してリプレイをスキップするため、ディスク本体に一部のブロックだけ更新された不整合な状態が放置されます。

2. **ext4 Writeback のゴミ露出シナリオと Ordered vs Data モード比較：**

    * **(a) Writeback モードで他人の旧ファイル内容が露出するシナリオ：**
        Writeback モードはメタデータのみをログへ記録し、データ本体の書き込み順序を制約しません。そのため、新ファイルへ新規データブロックを割り当てたメタデータ（ビットマップ・i-node）のログが先にコミットされ、新しいデータ本体がディスクへ書き込まれる前に停電すると、再起動後にメタデータだけが確定した新ファイルが未書込の物理ブロックを指すことになり、以前別のユーザが削除したファイルの古い中身（ゴミデータ）がそのまま読めてしまいます。

    * **(b) Ordered モードと Data モードの防止仕組みと違い：**

        * **Ordered モード（`data=ordered`）：** ログに書くのはメタデータのみですが、「新規割り当てデータブロックの本体を先にディスクへ書き終えてからメタデータログをコミットする」順序を強制してゴミ露出を防ぎます。データ本体は 1 回しか書かないため高速ですが、既存データブロックの上書き途中の不整合までは保護しません。
        * **Data モード（`data=journal`）：** メタデータとデータ本体の両方をログへ書いてコミットしてから本体へ反映するため、新規書込だけでなく既存ファイルの上書きも含めて最も広い範囲を保護できます。ただしデータ本体をログと本体へ 2 回書き込むため、書き込み性能が低下します。

3. **ログ空間予約不等式の計算と巨大 `write()` の分割理由：**

    * **(a) 同時実行可能なシステムコール上限数：**

        * **`log.lh.n = 0` のとき：** $0 + (\text{outstanding} + 1) \times 10 \le 30$ を満たすのは $\text{outstanding} = 0, 1, 2$ まで（3 個目で $30 \le 30$、4 個目で $40 > 30$ となり待機）のため、**最大 3 個** 同時並行で実行できます。
        * **`log.lh.n = 6`・`log.outstanding = 0` のとき：** $6 + (\text{outstanding} + 1) \times 10 \le 30$ を満たすのは $\text{outstanding} = 0, 1$ まで（2 個目で $26 \le 30$、3 個目で $36 > 30$ となり待機）のため、追加で同時受け入れできるのは **最大 2 個** です。

    * **(b) 巨大 `write()` を分割書き込みする理由とトレードオフ：**
        100 ブロック分の変更は有限のログ領域（`LOGSIZE = 30`）に入り切らず、1 つのトランザクションに収めようとするとログ溢れを起こすため、カーネルは数ブロックずつのチャンクに分割してチャンクごとに `begin_op()`〜`end_op()` を繰り返します。これによりファイルシステムのメタデータ一貫性は常に保たれますが、トレードオフとして「100 ブロック全部が書かれるか、1 バイトも書かれないか」という巨大な `write()` 全体の原子性はチャンク単位へ緩和され、途中停電時に先頭の数チャンクだけ書き込まれた状態になり得ます。

## 5-7. アクセス制御モデル（ACL・ケイパビリティ・Unix権限と `setuid`）

### 1. 動機（Why）：なぜ仮想記憶の隔離だけでは足りず、「権限の設計モデル」が必要なのか

[第3部](../index.md#part-3)では仮想記憶によってプロセス同士のメモリを隔離し、[5-4](5-4.md)〜[5-6節](5-6.md)ではディスク上のデータを電源断から守るファイルシステムの仕組みを整えました。しかし、1台のLinuxサーバやPCを複数の人間（`alice`, `bob`, 管理者 `root`）や、複数の常駐サービス（Webサーバ、データベース、メールサーバ）で共有するとき、メモリ隔離だけでは防げない新たなセキュリティ課題が現れます。

1. **永続資源の保護と共有の両立：**
    `alice` の秘密鍵ファイルは `bob` から読めないようにしたい一方で、プロジェクトの設計書は同じチームのメンバーだけが読み書きでき、さらに標準コマンド `/bin/ls` は全員が実行できるようにしたい場面があります。このように、資源ごとにきめ細かく「誰に何を許すか」を制御する枠組み（**認可：Authorization**）が必要です。

2. **「普段は低権限、特定の瞬間だけ特権」というジレンマ：**
    たとえば、すべてのユーザのパスワードハッシュが収められた `/etc/shadow` ファイルは、管理者 `root` しか読み書きできません。もし一般ユーザ `alice` に `/etc/shadow` への直接書き込みを許せば、`alice` は他人のパスワードまで勝手に書き換えられてしまいます。かといって一切触らせなければ、`alice` は自分自身のパスワード変更すらできません。「`passwd` プログラムの厳格な手順を通るとき**だけ**、一時的に特権で `/etc/shadow` を更新させる」という安全な権限昇格の仕組みが求められます。

本節では、アクセス制御の理論的な出発点である **アクセス制御行列** から **ACL** と **オブジェクトケーパビリティ** の2大モデルを対比したうえで、Unix の伝統的な権限（`rwx` と **`setuid`**）の実装と、その構造的な危うさを補う現代の防御機構（Linux ケイパビリティ・MAC・サンドボックス）までを整理します。

---

### 2. 具体例と動作イメージ（Toy Model）

理論の分類に入る前に、2つの小さな例で「ACLとケイパビリティの違い」および「`setuid` による権限切替」を具体的に確かめます。

#### 実験A：3人のユーザと3つのファイルを管理する「アクセス制御行列」

システム上に3人の主体（**Subject**：`alice`, `bob`, `root`）と、3つの客体（**Object**：`alice.txt`, `shared.txt`, `/etc/shadow`）があるとします。誰が何をしてよいか（`r`: 読取、`w`: 書込、`x`: 実行）をすべて1枚の表に書き出したものが **アクセス制御行列（Access Control Matrix）** です。

| 主体（Subject）＼ 客体（Object） | `alice.txt` | `shared.txt` | `/etc/shadow` |
| :--- | :---: | :---: | :---: |
| **`alice`** | `r, w` | `r, w` | （なし） |
| **`bob`** | （なし） | `r` | （なし） |
| **`root`** | `r, w` | `r, w` | `r, w` |

現実のシステムではユーザ数が数千、ファイル数が数百万に及ぶため、この巨大なスカスカの表をそのままメモリやディスクへ保存することはできません。そこで、表を **「縦（列）に切り分けて各ファイル側へ持たせる」** か、**「横（行）に切り分けて各ユーザ／プロセス側へ持たせる」** かの2通りの実装が生まれます。

* **列で切る $\implies$ ACL（アクセス制御リスト）：** `shared.txt` の側に「`alice: r,w`、`bob: r`、`root: r,w`」という入場者名簿を貼り付ける方式です（空港の搭乗者名簿チェックに近いです）。
* **行で切る $\implies$ オブジェクトケーパビリティ（Capability：権限証票）：** `bob` の側に「`shared.txt` を `r` できる偽造不能なチケット」を持たせる方式です（映画館の入場チケットや部屋の物理鍵に近いです）。

#### 実験B：一般ユーザ `alice` が `passwd` を実行する瞬間の権限変化

一般ユーザ `alice`（ユーザID：`UID = 1000`）が、自分のパスワードを変更するため `/usr/bin/passwd` を実行する流れを追ってみます。

1. `alice` のシェルは `UID = 1000` で動いています。このままでは `/etc/shadow`（所有者 `root`：`UID = 0`、権限 `rw-------`）を開こうとしても OS に拒否されます。
2. `/usr/bin/passwd` の実行ファイルには、所有者が `root`（`0`）であり、かつ **`setuid` ビット**（`ls -l` で `-rwsr-xr-x` と表示される **`s`**）が立っています。
3. シェルが `fork()` して子プロセスが `exec("/usr/bin/passwd")` を実行した瞬間、OSカーネルは `setuid` ビットを検知し、そのプロセスの **実効UID（EUID）** だけを `1000` からファイル所有者の **`0`（`root`）** へ一時昇格させます（元のユーザを示す **実UID：RUID** は `1000` のまま残ります）。
4. `passwd` はまず `RUID = 1000`（`alice` 本人）の現在のパスワードを照合し、正しければ `EUID = 0` の権限で `/etc/shadow` の `alice` の行**だけ**を安全に書き換えて終了します。

### 3. 構造・アルゴリズム・実装（What）

#### (1) ACL vs オブジェクトケーパビリティ：環境権限と Confused Deputy 問題

実験Aのアクセス制御行列を列・行のどちらで分割するかによって、権限の取り消しやすさや委譲のしやすさだけでなく、**Confused Deputy 問題（混乱した代理人問題）** への耐性が大きく変わります（図5-7-1）。

* **環境権限（Ambient Authority）と Confused Deputy 問題：**
    ACL 方式では、プロセスがパス名（例：`"/etc/shadow"`）を指定して `open()` を呼ぶたびに、そのプロセスに紐づく全権限が暗黙のうちに適用されます。この「操作対象と切り離されて主体全体へ暗黙に付与されている権限」を **環境権限（Ambient Authority）** と呼びます。もし高い権限を持つ代理プログラム（例：課金ログを書く権限を持つコンパイラや、`setuid root` プログラム）が、一般ユーザから出力先ファイル名を受け取ってそのまま開いてしまうと、攻撃者が課金ファイルや `/etc/shadow` のパス名を指定するだけで、代理プログラムが**自分の環境権限を使って攻撃者の意図したファイルを誤って上書きしてしまう**現象が起きます。これが **Confused Deputy 問題** です（具体例は 4-(1) でも確認します）。

* **オブジェクトケーパビリティ（Object Capability）による防止：**
    一方、オブジェクトケーパビリティ方式では、**「どの対象（客体）か」と「何の操作が許されるか」が 1 枚の偽造不能な権限チケット（Capability）に一体化**しています。呼び出し元が「自分が正当に持つ出力先ファイルのチケット」だけを代理プログラムへ渡せば、代理プログラムは渡されたチケット以外の対象へアクセスする手段を持たないため、環境権限の混同（Confused Deputy）が原理的に起きにくくなります。

> **【コラム：実は身近なオブジェクトケーパビリティ：UNIX のファイル記述子（FD）と `open()` 時の権限検査】**
>
> 「オブジェクトケーパビリティは特殊な研究用OSだけの概念だ」と思われがちですが、実は[5-2節](5-2.md)と[5-3節](5-3.md)で学んだ **UNIX のファイル記述子（FD）そのものが、OSカーネルによって保護されたオブジェクトケーパビリティ** として機能しています。
>
> * プロセスが `open("secret.txt", O_RDONLY)` を呼ぶとき、OSカーネルは i-node の **ACL（Unix権限）** を検査し、許可された場合だけ「どのファイル実体か」と「`readable = 1, writable = 0`」という権限情報を一体化した `struct file` へのハンドル（FD番号）をプロセスのFDテーブルへ発行します。
> * 以降の `read(fd, ...)` では、OSは毎回ファイル名やACLを再検査せず、**「有効な読取用FD（偽造不能なチケット）を持っていること」**だけでアクセスを許可します。
> * さらに、特権を持つ親プロセスが `secret.txt` を `O_RDONLY` で開いたあと、特権を捨てた子プロセスへそのFDだけを継承（または[5-3節](5-3.md)の UNIX ドメインソケットでFD渡し）すれば、子プロセスはファイルシステム全体へアクセスできないまま、**渡されたその1ファイルの読み出しだけ**を安全に実行できます。このように現代のUNIX/Linuxは、「ファイルシステム層に ACL、オープン後のプロセス層にオブジェクトケーパビリティ（FD）」を組み合わせたハイブリッド設計をとっています。

#### (2) Unix の伝統的権限モデル（`rwx` 9ビットと8進表記）

1970年代のUNIXは、i-node（[5-4節](5-4.md)）のメタデータを小さく保つため、完全な可変長 ACL ではなく、主体を **所有者（User / Owner：`u`）**、**所属グループ（Group：`g`）**、**その他全員（Other：`o`）** の3区分に圧縮し、各区分に `r`（4）・`w`（2）・`x`（1）の3ビット、合計 **9ビット（8進数3桁）** の権限モデルを採用しました。

ここで実務上よく誤解されるのが、**通常ファイルとディレクトリで `r`, `w`, `x` の意味が異なる**点です。

| 権限ビット | 8進数 | 通常ファイルに対する意味 | ディレクトリに対する意味 |
| :---: | :---: | :--- | :--- |
| **`r`** | `4` | ファイルの中身を読み出せる（`read`） | ディレクトリ内のファイル名一覧を取得できる（`ls`） |
| **`w`** | `2` | ファイルの中身を書き換えられる（`write`） | そのディレクトリ内でファイルの**作成・削除（`unlink`）・名前変更**ができる |
| **`x`** | `1` | プログラムとして実行できる（`exec`） | そのディレクトリを**通過・検索（`cd` や配下パスへの到達）**できる |

特に重要なのがディレクトリの `w` と `x` です。**あるファイルを削除（`unlink`）できるかどうかは、そのファイル自身の `w` 権限ではなく、そのファイルを含む親ディレクトリの `w` 権限と `x` 権限で決まります**（ディレクトリというテーブルから1行消す操作だからです）。また、ディレクトリの `r` がなくても `x` さえあれば、正確なファイル名を知っている配下のファイルを開くことができます。

#### (3) 特殊権限ビット（`setuid`・`setgid`・Sticky Bit）と 3 つの UID

Unix 権限の9ビットの上位には、さらに **3ビットの特殊権限**（合計12ビット＝8進数4桁）が設けられています。

* **`setuid`（`4000`、所有者 `x` 欄が `s`）：** 実行可能ファイルに付けると、実行中だけプロセスの**実効UID（EUID）**がファイル所有者のUIDへ切り替わります（実験Bの `/usr/bin/passwd` や `sudo`）。
* **`setgid`（`2000`、グループ `x` 欄が `s`）：** 実行ファイルでは実効GIDが切り替わり、ディレクトリに付けると配下に新規作成されるファイルのグループが親ディレクトリと同じグループへ自動継承されます（チーム共有ディレクトリに有用です）。
* **スティッキービット（Sticky Bit：`1000`、その他 `x` 欄が `t`）：** 全員が書き込み可能な共有ディレクトリ（代表例：`/tmp`、権限 `1777` = `drwxrwxrwt`）に付けると、「ディレクトリ内のファイル削除やリネームは、**そのファイルの所有者か `root` だけ**に限定する」制限が加わります。これにより、`/tmp` で `bob` が `alice` の一時ファイルを勝手に削除するのを防ぎます。

OSカーネルは `setuid` プログラムが安全に一時的な特権昇格と特権放棄を行えるよう、各プロセスのPCB（[3-2節](../3/3-2.md)）に **3つのUID** を保持しています（図5-7-2）。

1. **RUID（Real UID：実UID）：** このプロセスを起動した本来のログインユーザ（誰が実行したか）を表します。
2. **EUID（Effective UID：実効UID）：** OSがファイルアクセスなどの**権限チェックに実際に使うUID**です。通常は RUID と同じですが、`setuid` バイナリを `exec` した瞬間にファイル所有者のUID（例：`0` = `root`）になります。
3. **SUID（Saved Set-User-ID：保存セットUID）：** `exec` 時に昇格した EUID（例：`0`）をカーネルが控えておく枠です。これにより、`setuid` プログラムは普段 `seteuid(RUID)` で実効権限だけを一般ユーザへ落として安全に動き、`/etc/shadow` を書く数行だけ `seteuid(SUID)` で特権へ戻すことができます。また、特権を永久放棄する際、**呼び出し時点で `EUID == 0`（`root`）であれば** `setuid(RUID)` 1回で RUID・EUID・SUID の3つすべてが一般ユーザへ書き換わって特権を永久放棄できます。一方、**非 `root` 所有の `setuid` プログラム（`EUID != 0`）や、すでに `seteuid(RUID)` で降格済みの状態**では `setuid(RUID)` を呼んでも EUID のみ変わり SUID に元の特権が残ってしまうため、環境を問わず確実に3つすべてを書き換えて永久放棄するには Linux 等の **`setresuid(ruid, ruid, ruid)`** を使います。

#### (4) DAC（任意アクセス制御）vs MAC（強制アクセス制御）と最小権限の原則

アクセス制御のポリシー管理方針には、大きく次の2つのパラダイムがあります。

* **DAC（Discretionary Access Control：任意アクセス制御）：** ファイルの所有者が自分の裁量（`chmod` 等）で誰にアクセスを許すかを決められる方式です。伝統的な Unix 権限は DAC です。柔軟で扱いやすい反面、ユーザがうっかり機密ファイルを `chmod 644` にしたり、ユーザ権限で動いたマルウェアがユーザの全ファイルを勝手に外部へ送信・改ざんしたりするのを防げません。
* **MAC（Mandatory Access Control：強制アクセス制御）：** ファイル所有者の裁量を超え、OSカーネル側でシステム全体の厳格なセキュリティポリシーを強制する方式です（代表例：Linux の **SELinux** や **AppArmor**）。たとえば「Webサーバプロセス（`httpd`）は、たとえバグで乗っ取られても `/var/www` 以外のファイル（`/etc/shadow` やユーザのホームディレクトリ）へはアクセスできない」という制約をカーネルが強制します。

これらすべての設計を貫く基本思想が、ジェローム・サルツァーとマイケル・シュローダーが1975年に定式化した **最小権限の原則（Principle of Least Privilege）** です。すなわち、すべてのプログラムとユーザには「自分の仕事を遂行するのに必要最小限の権限だけ」を与え、不要な権限を持たせないことで、バグや侵害が起きた際の被害半径を最小限に封じ込めます。

### 4. 限界と補正（Critique & Adaptation）

#### (1) `setuid` の構造的リスクと Linux ケイパビリティによる細分化

`setuid` は便利ですが、セキュリティの視点からは **「すべてか無か（All-or-Nothing）」の危険な仕組み** です。たとえばネットワークの疎通確認を行う `ping` コマンドは、特殊なネットワークソケット（Raw Socket）を開くたった1つの権限が欲しいだけなのに、古典的なUNIXでは `setuid root` を付けていました。すると、もし `ping` の引数解析に1行でもバグがあると、攻撃者は `EUID = 0`（システム全権）を奪ってマシン全体を乗っ取れてしまいます。

さらに、`setuid` プログラムには環境権限（Ambient Authority）に起因する次の古典的な攻撃パターン（**Confused Deputy 問題** の実例）が常に付きまといます。

1. **環境変数による乗っ取り：** 攻撃者が `PATH` 環境変数を細工したり、`LD_PRELOAD`（[1-5節](../1/1-5.md)）で悪意ある共有ライブラリを読み込ませようとしたりします（補正：動的リンカは `RUID != EUID` のとき `LD_PRELOAD` や `LD_LIBRARY_PATH` を自動的に無視します）。
2. **TOCTOU（Time-of-Check to Time-of-Use）競合：** `setuid root` プログラムが `access("/tmp/f", W_OK)` で「一般ユーザ（`RUID`）が書けるファイルか」を検査した直後、`open("/tmp/f", O_WRONLY)` を `EUID = 0` のまま呼ぶ**ほんの一瞬の隙間**に、攻撃者が `/tmp/f` を `/etc/shadow` へのシンボリックリンクへすり替える攻撃です（補正：`open()` の前に `seteuid(RUID)` で一般権限へ降格させる、シンボリックリンクを辿らない `O_NOFOLLOW` を指定する、さらにパス名ではなく一度開いたFDに対して `openat` / `fstat` で検査・操作する対策を組み合わせます）。

この「`root` が強すぎる」問題に対する現代 Linux の抜本的な補正が、**Linux ケイパビリティ（POSIX Capabilities）** です（図5-7-3）。Linux カーネルはかつての万能な `root` 権限を約40種類の機能別フラグへ分割しました。

* `CAP_NET_BIND_SERVICE`：1024番未満の特権ポート（80番 HTTP 等）を開く権限**だけ**を付与します。
* `CAP_NET_RAW`：`ping` が使う Raw Socket を開く権限**だけ**を付与します。
* `CAP_DAC_OVERRIDE`：ファイルの `rwx` 権限検査を無視して読み書きできる特権です（通常の特権サービスには付与しません）。
* `CAP_SYS_ADMIN`：マウント操作やカーネル設定変更など広範な管理特権です（`root` に近い強い権限のため原則付与を避けます）。
* `CAP_KILL`：他プロセスへシグナルを送る権限**だけ**を付与します。

これにより、`/bin/ping` に `setuid root` を付ける代わりに `CAP_NET_RAW` のみを付与すれば、万が一 `ping` が乗っ取られても攻撃者は `/etc/shadow` を読むことも他ファイルを消すこともできず、最小権限の原則が実現します。

なお、名称が似ているため混同されやすい点に注意が必要です。3-(1) で扱った **オブジェクトケーパビリティ**（および UNIX の FD）は「**特定の対象（ファイル等）と操作権限を 1 つに束ねたチケット**」を指すのに対し、**Linux ケイパビリティ** は「**特定の対象を指定するのではなく、従来の万能な `root` 特権を機能別のフラグ群へ細分化したプロセス属性**」です。どちらも最小権限の実現を目指していますが、対象（客体）と一体化しているか否かという構造が異なります。

#### (2) 伝統的 Unix 9ビットの表現力不足と POSIX ACL・RBAC・サンドボックス

伝統的な Unix の `u/g/o` 9ビットは、「特定ファイルについて `alice` には `rw`、`bob` には `r`、`charlie` には禁止、という複数ユーザの細かな組み合わせ」を1つのグループだけで表現しきれない限界があります。

これに対し、現代のシステムでは次の多層的な補正が組み合わされています。

* **POSIX ACL（拡張ACL：`getfacl` / `setfacl`）：** i-node の拡張属性（xattr）に任意個数の `(ユーザ/グループ, 権限)` エントリを追加し、本来のアクセス制御リストの表現力を取り戻します。
* **RBAC（Role-Based Access Control：ロールベースアクセス制御）：** 企業システムやクラウド（IAM）・データベースにおいて、個人へ直接権限を振るのではなく「開発者」「監査役」「管理者」といった役割（ロール）へ権限を束ね、管理コストと設定ミスを大幅に減らします。
* **プロセス・サンドボックス（`seccomp-bpf`・Linux 名前空間・`cgroup`）：** Webブラウザのレンダラやコンテナ（Docker等）では、ファイル権限だけでなく「そのプロセスが呼んでよいシステムコールの種類そのもの」を **`seccomp`（`seccomp-bpf`）** フィルタで制限し、さらにファイルシステム（マウント名前空間）・PID空間・ネットワークを **名前空間（Namespace）**（および古典的な `chroot`）で隔離し、CPU時間やメモリ上限などの計算資源を **`cgroup`（Control Groups）** で制限することで軽量な隔離環境を構成します。

### 5. 接続と展望（Bridge）：本節の内容が後半のどの部に繋がるか

1. **次節（[5-8節](5-8.md)：メモリ破壊攻撃と多層防御［BOF・ROP・ASLR/NX/カナリア］）：**
    本節で見たアクセス制御や `setuid` は、「プログラムが意図通りに動く」限りは堅固に機能します。しかし、もし `setuid` が付いた特権プログラムやネットワーク待ち受けサーバに **バッファオーバーフロー（BOF）** のようなメモリ破壊バグが潜んでいると、攻撃者はプログラムの制御フローを乗っ取って任意の機械語を実行し、そのプロセスの権限（`EUID = 0` 等）を丸ごと奪い取れます。次節では、[1-3節](../1/1-3.md)のスタックフレーム構造を回収しながら、メモリ破壊攻撃の原理と多層防御（カナリア・NX・ASLR＋PIE・ROP）へ進み、さらに[第5部](../index.md#part-5)の最終節（[5-9節](5-9.md)）でバグを実行前に検出・検証する静的解析と形式手法の入口へ繋ぎます。

2. **[第7部](../index.md#part-7)（[7-7節](../7/7-7.md)：認証・鍵交換とプロトコル保護）：**
    本節で扱ったアクセス制御は「すでに本人確認が済んだ主体に対して、何の操作を許すか（**認可：Authorization**）」の仕組みでした。ネットワーク越しの通信では、まず相手が本当に本人であることを暗号で証明する「**認証（Authentication）**」が前提となり、それを[第7部](../index.md#part-7)の終盤（デジタル署名・Kerberos・TLS）で学びます。

3. **[第8部](../index.md#part-8)（[8-6節](../8/8-6.md)：SQL の権限管理とビュー）：**
    データベースでも本節のアクセス制御行列や RBAC と同じ枠組みが `GRANT` / `REVOKE` 文として提供され、さらに特定の列や行だけを見せる「ビュー（View）」を組み合わせたきめ細かなアクセス制御が行われます。

### 理解度チェック（次節へ進む前の確認）

本節の Unix ディレクトリ権限・`setuid` の TOCTOU 対策・最小権限の多層設計を確認し、次節（[5-8節](5-8.md)）へ繋ぐ問いを置きます。

> **【確認の問い】**
>
> 1. **（ディレクトリ `711`・配下ファイル `644` に対する 3 コマンドの成否トレース）**
>     所有者 `root` のディレクトリ `/dir` の権限が **`711`（`drwx--x--x`）**、その直下にある `root` 所有のファイル `/dir/file` の権限が **`644`（`-rw-r--r--`）** と設定されています。一般ユーザ `bob`（その他ユーザ `o` に該当）が次の 3 つのコマンドを実行したとき、それぞれの**成否**と**理由**を答えてください。
>
>     * (a) `ls /dir`
>     * (b) `cat /dir/file`
>     * (c) `rm /dir/file`
>
> 2. **（`setuid root` プログラムの `access()` → `open()` TOCTOU 攻撃と対策）**
>     `setuid root`（`EUID = 0`）で動作するプログラムが、一般ユーザから受け取ったパス `path`（例：`/tmp/work`）へ結果を書き込む前に、次のような権限検査を行いました。
>
>     ```c
>     if (access(path, W_OK) == 0) {     // 実UID(RUID)に書込権限があるか確認
>         int fd = open(path, O_WRONLY); // 実効UID(EUID=0)でファイルを開く
>         write(fd, data, len);
>     }
>     ```
>
>     * (a) 攻撃者（一般ユーザ）がこのコードの隙を突いて `/etc/shadow` を上書きする **TOCTOU 競合攻撃** の手順を説明してください（これが **Confused Deputy 問題** の一種と言える理由も添えてください）。
>     * (b) この攻撃を防ぐ実装上の対策として、**`seteuid(RUID)`** による実効権限の一時降格、および **`O_NOFOLLOW`**（や `openat`＋`fstat`）がそれぞれどのように機能するか説明してください。
>
> 3. **（ポート 80 番 Web サーバの最小権限多層設計）**
>     外部からの HTTP 要求を特権ポート（80 番）で待ち受け、`/var/www` 配下の静的ファイルを配信する Web サーバを最小権限で運用したいとします。`setuid root` のまま動かし続ける設計の問題点を踏まえ、次の 3 つの機構を組み合わせたときの役割分担を説明してください（あわせて、ここで使う **Linux ケイパビリティ** と FD のような **オブジェクトケーパビリティ** の構造的な違いも 1 文で述べてください）。
>
>     * ① `CAP_NET_BIND_SERVICE`
>     * ② `chroot` または Linux マウント名前空間（Mount Namespace）
>     * ③ `seccomp`（`seccomp-bpf`）
