### 前節（5-6）の確認問題の解答

前節の最後に提示した3つの問いの解答を確認します。問3がそのまま本節（アクセス制御モデル）の導入になります。

1. **停電タイミング別のクラッシュリカバリ判定：**

    * **(a) ①ログデータ書込が半分終わった直後（②コミット点の前）に停電した場合：**
        ディスク上のログヘッダは `n == 0` のままです。起動時リカバリ（`recover_from_log`）は `n == 0` を見てログ領域の書きかけデータを完全に無視し、何もせず通常起動します。本体ブロックはまだ1バイトも書き換えられていないため、ファイルシステムは一貫した **「作成前」** の状態になります。

    * **(b) ③本体反映が半分終わった直後に停電し、さらにリカバリの途中で2回目の停電が起きて3回目に起動した場合：**
        ②のコミット点を通過済みのため、ログヘッダには `n > 0` と全変更ブロックがディスク上に残っています。3回目の起動時にもログヘッダが依然として `n > 0` のままなので、リカバリがログ領域から全ブロックを本体へ最初からコピーし直し（REDO）、すべて完了した最後にログヘッダへ `n = 0` を書き込みます。物理ブロックの上書きは**べき等**（何度繰り返しても最終結果が同じ）であるため、ファイルシステムは完全に一貫した **「作成後」** の状態へ復旧します。

2. **Ordered モード（`data=ordered`）が性能と安全性を両立できる理由：**
    Ordered モードは、ログへ書き込む対象を「メタデータのみ」に絞ることで、ファイルのデータ本体をディスクへ1回しか書き込まずに済ませます（Data モードの2回書き込みより高速）。同時に、「**データ本体を本来のディスク位置へ書き終えてから、メタデータのログをコミットする**」という書き込み順序を厳格に強制するため、メタデータが確定した時点では必ず新しいデータ本体がディスク上に揃っており、Writeback モードのような「古いゴミデータの露出」を防げます。

3. **複数ユーザが共有するマシンで「他人のファイル」を守り、特権操作を安全に行う仕組み（本節への接続）：**
    OSは「誰（主体）が、どの資源（客体）へ、何の操作を許されるか」を規定する **アクセス制御モデル（ACL・ケイパビリティ・Unix 権限）** を備えています。さらに一般ユーザが自分のパスワードを変更する瞬間だけ一時的に管理者権限で `/etc/shadow` を書き換えるような処理には、プログラム実行時だけ実効権限を切り替える **`setuid`**（および現代の **Linux ケイパビリティ**）の仕組みが使われます。

## 5-7. アクセス制御モデル（ACL・ケイパビリティ・Unix権限と `setuid`）

### 1. 動機（Why）：なぜ仮想記憶の隔離だけでは足りず、「権限の設計モデル」が必要なのか

[第3部](../index.md#part-3)では仮想記憶によってプロセス同士のメモリを隔離し、[5-4](5-4.md)〜[5-6節](5-6.md)ではディスク上のデータを電源断から守るファイルシステムの仕組みを整えました。しかし、1台のLinuxサーバやPCを複数の人間（`alice`, `bob`, 管理者 `root`）や、複数の常駐サービス（Webサーバ、データベース、メールサーバ）で共有するとき、メモリ隔離だけでは防げない新たなセキュリティ課題が現れます。

1. **永続資源の保護と共有の両立：**
    `alice` の秘密鍵ファイルは `bob` から完全に読めなくしたい一方で、プロジェクトの設計書は同じチームのメンバーだけが読み書きでき、さらに標準コマンド `/bin/ls` は全員が実行できるようにしたい。このように、資源ごとにきめ細かく「誰に何を許すか」を制御する枠組み（**認可：Authorization**）が必要です。

2. **「普段は低権限、特定の瞬間だけ特権」というジレンマ：**
    たとえば、すべてのユーザのパスワードハッシュが収められた `/etc/shadow` ファイルは、管理者 `root` しか読み書きできません。もし一般ユーザ `alice` に `/etc/shadow` への直接書き込みを許せば、`alice` は他人のパスワードまで勝手に書き換えられてしまいます。かといって一切触らせなければ、`alice` は自分自身のパスワード変更すらできません。「`passwd` プログラムの厳格な手順を通るとき**だけ**、一時的に特権で `/etc/shadow` を更新させる」という安全な権限昇格の仕組みが求められます。

本節では、アクセス制御の理論的な出発点である **アクセス制御行列** から **ACL** と **ケイパビリティ** の2大モデルを対比したうえで、Unix の伝統的な権限（`rwx` と **`setuid`**）の実装と、その構造的な危うさを補う現代の防御機構（Linux ケイパビリティ・MAC）までを整理します。

---

### 2. 具体例と動作イメージ（Toy Model）

理論の分類に入る前に、2つの小さな例で「ACLとケイパビリティの違い」および「`setuid` による権限切替」を具体的に確かめます。

#### 実験A：3人のユーザと3つのファイルを管理する「アクセス制御行列」

システム上に3人の主体（**Subject**：`alice`, `bob`, `root`）と、3つの客体（**Object**：`alice.txt`, `shared.txt`, `/etc/shadow`）があるとします。誰が何をしてよいか（`r`: 読取、`w`: 書込、`x`: 実行）をすべて1枚の表に書き出したものが **アクセス制御行列（Access Control Matrix）** です。

| 主体（Subject）＼ 客体（Object） | `alice.txt` | `shared.txt` | `/etc/shadow` |
| :--- | :---: | :---: | :---: |
| **`alice`** | `r, w` | `r, w` | （なし） |
| **`bob`** | （なし） | `r` | （なし） |
| **`root`** | `r, w` | `r, w` | `r, w` |

現実のシステムではユーザ数が数千、ファイル数が数百万に及ぶため、この巨大なスカスカの表をそのままメモリやディスクへ保存することはできません。そこで、表を **「縦（列）に切り分けて各ファイル側へ持たせる」** か、**「横（行）に切り分けて各ユーザ／プロセス側へ持たせる」** かの2通りの実装が生まれます。

* **列で切る $\implies$ ACL（アクセス制御リスト）：** `shared.txt` の側に「`alice: r,w`、`bob: r`、`root: r,w`」という入場者名簿を貼り付ける方式です（空港の搭乗者名簿チェックに近いです）。
* **行で切る $\implies$ ケイパビリティ（Capability：権限証票）：** `bob` の側に「`shared.txt` を `r` できる偽造不能なチケット」を持たせる方式です（映画館の入場チケットや部屋の物理鍵に近いです）。

#### 実験B：一般ユーザ `alice` が `passwd` を実行する瞬間の権限変化

一般ユーザ `alice`（ユーザID：`UID = 1000`）が、自分のパスワードを変更するため `/usr/bin/passwd` を実行する流れを追ってみます。

1. `alice` のシェルは `UID = 1000` で動いています。このままでは `/etc/shadow`（所有者 `root`：`UID = 0`、権限 `rw-------`）を開こうとしても OS に拒否されます。
2. `/usr/bin/passwd` の実行ファイルには、所有者が `root`（`0`）であり、かつ **`setuid` ビット**（`ls -l` で `-rwsr-xr-x` と表示される **`s`**）が立っています。
3. シェルが `fork()` して子プロセスが `exec("/usr/bin/passwd")` を実行した瞬間、OSカーネルは `setuid` ビットを検知し、そのプロセスの **実効UID（EUID）** だけを `1000` からファイル所有者の **`0`（`root`）** へ一時昇格させます（元のユーザを示す **実UID：RUID** は `1000` のまま残ります）。
4. `passwd` はまず `RUID = 1000`（`alice` 本人）の現在のパスワードを照合し、正しければ `EUID = 0` の権限で `/etc/shadow` の `alice` の行**だけ**を安全に書き換えて終了します。

> **【コラム：実は身近なケイパビリティ — UNIXのファイル記述子（FD）と `open()` 時の権限検査】**

> 「ケイパビリティは特殊な研究用OSだけの概念だ」と思われがちですが、実は[5-2節](5-2.md)と[5-3節](5-3.md)で学んだ **UNIX のファイル記述子（FD）そのものが、OSカーネルによって保護されたケイパビリティ** として機能しています。
>
> * プロセスが `open("secret.txt", O_RDONLY)` を呼ぶとき、OSカーネルは i-node の **ACL（Unix権限）** を検査し、許可された場合だけ「`readable = 1, writable = 0`」という権限情報を含んだ `struct file` へのハンドル（FD番号）をプロセスのFDテーブルへ発行します。
> * 以降の `read(fd, ...)` では、OSは毎回ファイル名やACLを再検査せず、**「有効な読取用FD（偽造不能なチケット）を持っていること」**だけでアクセスを許可します。
> * さらに、特権を持つ親プロセスが `secret.txt` を `O_RDONLY` で開いたあと、特権を捨てた子プロセスへそのFDだけを継承（または[5-3節](5-3.md)の UNIX ドメインソケットでFD渡し）すれば、子プロセスはファイルシステム全体へ一切アクセスできないまま、**渡されたその1ファイルの読み出しだけ**を安全に実行できます。このように現代のUNIX/Linuxは、「ファイルシステム層に ACL、オープン後のプロセス層にケイパビリティ（FD）」を組み合わせたハイブリッド設計をとっています。

#### (2) Unix の伝統的権限モデル（`rwx` 9ビットと8進表記）

1970年代のUNIXは、i-node（[5-4節](5-4.md)）のメタデータを小さく保つため、完全な可変長 ACL ではなく、主体を **所有者（User / Owner：`u`）**、**所属グループ（Group：`g`）**、**その他全員（Other：`o`）** の3区分に圧縮し、各区分に `r`（4）・`w`（2）・`x`（1）の3ビット、合計 **9ビット（8進数3桁）** の権限モデルを採用しました。

ここで実務上よく誤解されるのが、**通常ファイルとディレクトリで `r`, `w`, `x` の意味が異なる**点です。

| 権限ビット | 8進数 | 通常ファイルに対する意味 | ディレクトリに対する意味 |
| :---: | :---: | :--- | :--- |
| **`r`** | `4` | ファイルの中身を読み出せる（`read`） | ディレクトリ内のファイル名一覧を取得できる（`ls`） |
| **`w`** | `2` | ファイルの中身を書き換えられる（`write`） | そのディレクトリ内でファイルの**作成・削除（`unlink`）・名前変更**ができる |
| **`x`** | `1` | プログラムとして実行できる（`exec`） | そのディレクトリを**通過・検索（`cd` や配下パスへの到達）**できる |

特に重要なのがディレクトリの `w` と `x` です。**あるファイルを削除（`unlink`）できるかどうかは、そのファイル自身の `w` 権限ではなく、そのファイルを含む親ディレクトリの `w` 権限と `x` 権限で決まります**（ディレクトリというテーブルから1行消す操作だからです）。また、ディレクトリの `r` がなくても `x` さえあれば、正確なファイル名を知っている配下のファイルを開くことができます。

#### (3) 特殊権限ビット（`setuid`・`setgid`・Sticky Bit）と 3 つの UID

Unix 権限の9ビットの上位には、さらに **3ビットの特殊権限**（合計12ビット＝8進数4桁）が設けられています。

* **`setuid`（`4000`、所有者 `x` 欄が `s`）：** 実行可能ファイルに付けると、実行中だけプロセスの**実効UID（EUID）**がファイル所有者のUIDへ切り替わります（実験Bの `/usr/bin/passwd` や `sudo`）。
* **`setgid`（`2000`、グループ `x` 欄が `s`）：** 実行ファイルでは実効GIDが切り替わり、ディレクトリに付けると配下に新規作成されるファイルのグループが親ディレクトリと同じグループへ自動継承されます（チーム共有ディレクトリに有用です）。
* **スティッキービット（Sticky Bit：`1000`、その他 `x` 欄が `t`）：** 全員が書き込み可能な共有ディレクトリ（代表例：`/tmp`、権限 `1777` = `drwxrwxrwt`）に付けると、「ディレクトリ内のファイル削除やリネームは、**そのファイルの所有者か `root` だけ**に限定する」制限が加わります。これにより、`/tmp` で `bob` が `alice` の一時ファイルを勝手に削除するのを防ぎます。

OSカーネルは `setuid` プログラムが安全に一時的な特権昇格と特権放棄を行えるよう、各プロセスのPCB（[3-2節](../3/3-2.md)）に **3つのUID** を保持しています（図5-7-2）。

1. **RUID（Real UID：実UID）：** このプロセスを起動した本来のログインユーザ（誰が実行したか）を表します。
2. **EUID（Effective UID：実効UID）：** OSがファイルアクセスなどの**権限チェックに実際に使うUID**です。通常は RUID と同じですが、`setuid` バイナリを `exec` した瞬間にファイル所有者のUID（例：`0` = `root`）になります。
3. **SUID（Saved Set-User-ID：保存セットUID）：** `exec` 時に昇格した EUID（例：`0`）をカーネルが控えておく枠です。これにより、`setuid` プログラムは普段 `seteuid(RUID)` で一般権限へ落として安全に動き、`/etc/shadow` を書く数行だけ `seteuid(SUID)` で特権へ戻し、不要になったら `setuid(RUID)` で3つすべてを一般ユーザへ戻して**特権を永久放棄**できます。

#### (4) DAC（任意アクセス制御）vs MAC（強制アクセス制御）と最小権限の原則

アクセス制御のポリシー管理方針には、大きく次の2つのパラダイムがあります。

* **DAC（Discretionary Access Control：任意アクセス制御）：** ファイルの所有者が自分の裁量（`chmod` 等）で誰にアクセスを許すかを決められる方式。伝統的な Unix 権限は DAC です。柔軟で扱いやすい反面、ユーザがうっかり機密ファイルを `chmod 644` にしたり、ユーザ権限で動いたマルウェアがユーザの全ファイルを勝手に外部へ送信・改ざんしたりするのを防げません。
* **MAC（Mandatory Access Control：強制アクセス制御）：** ファイル所有者の裁量を超え、OSカーネル側でシステム全体の厳格なセキュリティポリシーを強制する方式（代表例：Linux の **SELinux** や **AppArmor**）。たとえば「Webサーバプロセス（`httpd`）は、たとえバグで乗っ取られても `/var/www` 以外のファイル（`/etc/shadow` やユーザのホームディレクトリ）へは絶対にアクセスできない」という制約をカーネルが強制します。

これらすべての設計を貫く基本思想が、ジェローム・サルツァーとマイケル・シュローダーが1975年に定式化した **最小権限の原則（Principle of Least Privilege）** です。すなわち、すべてのプログラムとユーザには「自分の仕事を遂行するのに必要最小限の権限だけ」を与え、不要な権限を一切持たせないことで、バグや侵害が起きた際の被害半径を最小限に封じ込めます。

### 4. 限界と補正（Critique & Adaptation）

#### (1) `setuid` の構造的リスクと Linux ケイパビリティによる細分化

`setuid` は便利ですが、セキュリティの視点からは **「すべてか無か（All-or-Nothing）」の危険な仕組み** です。たとえばネットワークの疎通確認を行う `ping` コマンドは、特殊なネットワークソケット（Raw Socket）を開くたった1つの権限が欲しいだけなのに、古典的なUNIXでは `setuid root` を付けていました。すると、もし `ping` の引数解析に1行でもバグがあると、攻撃者は `EUID = 0`（システム全権）を奪ってマシン全体を完全に乗っ取れてしまいます。

さらに、`setuid` プログラムには次の古典的な攻撃パターン（**Confused Deputy 問題** の実例）が常に付きまといます。

1. **環境変数による乗っ取り：** 攻撃者が `PATH` 環境変数を細工したり、`LD_PRELOAD`（[1-5節](../1/1-5.md)）で悪意ある共有ライブラリを読み込ませようとしたりします（補正：動的リンカは `RUID != EUID` のとき `LD_PRELOAD` や `LD_LIBRARY_PATH` を自動的に無視します）。
2. **TOCTOU（Time-of-Check to Time-of-Use）競合：** `setuid` プログラムが `access("/tmp/f", W_OK)` で「一般ユーザが書けるファイルか」を検査した直後、`open("/tmp/f", O_WRONLY)` を呼ぶ**ほんの一瞬の隙間**に、攻撃者が `/tmp/f` を `/etc/shadow` へのシンボリックリンクへすり替える攻撃です（補正：パス名ではなく、一度開いたFDに対して操作する `openat` / `fstat` を使います）。

この「`root` が強すぎる」問題に対する現代 Linux の抜本的な補正が、**Linux ケイパビリティ（POSIX Capabilities）** です（図5-7-3）。Linux カーネルはかつての万能な `root` 権限を約40種類の細かい権限フラグへ分割しました。

* `CAP_NET_BIND_SERVICE`：1024番未満の特権ポート（80番 HTTP 等）を開く権限**だけ**を付与します。
* `CAP_NET_RAW`：`ping` が使う Raw Socket を開く権限**だけ**を付与します。
* `CAP_KILL`：他プロセスへシグナルを送る権限**だけ**を付与します。

これにより、`/bin/ping` に `setuid root` を付ける代わりに `CAP_NET_RAW` のみを付与すれば、万が一 `ping` が乗っ取られても攻撃者は `/etc/shadow` を読むことも他ファイルを消すこともできず、最小権限の原則が実現します。

#### (2) 伝統的 Unix 9ビットの表現力不足と POSIX ACL・RBAC・サンドボックス

伝統的な Unix の `u/g/o` 9ビットは、「特定ファイルについて `alice` には `rw`、`bob` には `r`、`charlie` には禁止、という複数ユーザの細かな組み合わせ」を1つのグループだけで表現しきれない限界があります。

これに対し、現代のシステムでは次の多層的な補正が組み合わされています。

* **POSIX ACL（拡張ACL：`getfacl` / `setfacl`）：** i-node の拡張属性（xattr）に任意個数の `(ユーザ/グループ, 権限)` エントリを追加し、本来のアクセス制御リストの表現力を取り戻します。
* **RBAC（Role-Based Access Control：ロールベースアクセス制御）：** 企業システムやクラウド（IAM）・データベースにおいて、個人へ直接権限を振るのではなく「開発者」「監査役」「管理者」といった役割（ロール）へ権限を束ね、管理コストと設定ミスを大幅に減らします。
* **プロセス・サンドボックス（`seccomp-bpf`・Linux 名前空間）：** Webブラウザのレンダラやコンテナ（Docker等）では、ファイル権限だけでなく「そのプロセスが呼んでよいシステムコールの種類そのもの」を `seccomp` フィルタで制限し、さらにファイルシステムやPID空間を名前空間（Namespace）で丸ごと隔離します。
