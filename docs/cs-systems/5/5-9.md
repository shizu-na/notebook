### 前節（5-8）の確認問題の解答

前節の最後に提示した3つの問いの解答を確認します。実行時の多層防御や動的テストだけでは境界バグの不在を保証できないため、本節ではコードを実行前に解析・検証する静的解析と形式手法へ進みます。

1. **整数オーバーフロー境界チェックの突破値構成と安全な修正：**

    * **(a) 最大の正常 `count` 値と、境界チェックを突破する最小の不正 `count` 値：**

        * **正常な最大値：** $32 \times \text{count} + 16 \le 4{,}096 \iff 32 \times \text{count} \le 4{,}080 \iff \text{count} \le 127.5$ より、最大の正常値は **`127`**（このとき `total = 4080`）です。
        * **突破する最小の不正値：** $2^{32} = 2^{27} \times 32$ なので、`count` $= 2^{27} - 1$（`0x07FFFFFF`）までは `total = 2^{32} - 16` となりオーバーフローせず拒否されます。一方、**`count = 0x08000000`（$2^{27} = 134{,}217{,}728$）** では $2^{27} \times 32 + 16 = 2^{32} + 16 \equiv \mathbf{16} \pmod{2^{32}}$ へラップアラウンドし、`16 > 4096`（偽）となってチェックをすり抜け、わずか **`total = 16` バイト** しか確保されません。

    * **(b) オーバーフロー前の安全な検査コード：**

        ```c
        if (count > (4096 - 16) / 32) {   // すなわち count > 127
            return -1;
        }
        uint32_t total = count * 32 + 16;
        ```

2. **3 つの防御設定環境に対する攻撃可否の診断：**

    * **① NX のみ有効（カナリアなし・ASLR/PIE なし）：**
        スタック上の**シェルコード注入**は NX（`X = 0`）によってページフォルトで阻止されます。しかし配置アドレスが固定でカナリアもないため、情報漏洩なしでも既存の `X = 1` コード片を使う **ROP 攻撃でそのまま突破**できます。

    * **② NX ＋ スタックカナリア有効（ASLR/PIE なし）：**
        シェルコードは NX で阻止され、素朴な BOF による ROP は戻り番地の手前で**スタックカナリアが壊れて `__stack_chk_fail()` で阻止**されます。ただし、**情報漏洩バグを使って実行時のカナリア値を読み出し**、同じ値を上書きし直せばカナリア検査をすり抜け、固定アドレスの ROP チェーンで突破され得ます。

    * **③ NX ＋ スタックカナリア ＋ ASLR/PIE すべて有効：**
        シェルコードは NX で、連続破壊はカナリアで、アドレス固定の ROP は ASLR/PIE でそれぞれ阻止されます。しかし、**情報漏洩バグによってカナリア値と `libc`（または `.text`）の実測アドレスの両方を漏洩**できれば、ベースアドレスを逆算してガジェット番地を再計算した ROP チェーンを構成することで突破され得ます（そのためシャドウスタック等の CFI や、メモリ安全言語・静的検証によるバグ根絶が重要になります）。

3. **x86-64 ROP ガジェット連鎖のトレースとカナリア最下位バイト `0x00` の役割：**

    * **(a) スタック配置と 3 ステップトレース：**
        戻り番地の位置（低位側）から高位アドレス側へ向かって **`G` → `S` → `F`**（`+8(%rbp)` に `G`、`+16(%rbp)` に `S`、`+24(%rbp)` に `F`）の順に並べます。

        1. **脆弱関数の `ret`：** スタックトップの `G` をポップして `%rip ← G`（`pop %rdi; ret` へジャンプ）し、`%rsp` は `+8` 進んで `S` を指します。
        2. **ガジェットの `pop %rdi`：** スタックトップの `S` をポップして第 1 引数レジスタ **`%rdi ← S`（`"/bin/sh"`）** へ格納し、`%rsp` は `+8` 進んで `F` を指します。
        3. **ガジェットの `ret`：** スタックトップの `F` をポップして `%rip ← F` へジャンプし、`%rdi = S` の状態で **`system("/bin/sh")`** が実行されます。

    * **(b) カナリア最下位バイトに `0x00` を置く理由：**
        `strcpy()` や `printf("%s", ...)` のような C 文字列関数はヌルバイト `0x00` を文字列終端とみなして処理を止めます。カナリアの配列 `buf` に最も近い最下位バイトを `0x00` にしておくことで、文字列系の読み出しバグでカナリア値をそのまま漏洩しにくくするとともに、`strcpy()` の入力途中に `0x00` を混ぜてカナリア値を元の値どおりに上書き再現する攻撃を封じられます。

## 5-9. 静的解析と形式手法の入口（モデル検査・SAT/SMT・有界モデル検査）

### 1. 動機（Why）：「テストはバグの存在を示せても、不在を証明できない」

前節（[5-8節](5-8.md)）では、メモリ破壊攻撃に対する実行時の多層防御（カナリア・NX・ASLR＋PIE・CFI）と、開発時の動的検査（ASan・TSan・ファジング）を整理しました。これらは実用上欠かせない防波堤ですが、OSカーネルや暗号ライブラリ、並行ロックアルゴリズムのような高信頼システムでは、**「実際に動かして運悪く踏む前に、バグの構造や反例を機械的に見つけ出し、可能な範囲で安全性を数学的に裏付けたい」**という要求が生じます。

計算機科学者エドガー・ダイクストラの有名な言葉に、**「テストはバグの『存在』を示すことはできるが、バグの『不在』を証明することはできない」**があります。[4-1節](../4/4-1.md)で確認した通り、並行プログラムのインターリービングは簡単に数兆通りへ膨らみますし、32ビット整数の入力だけでも約43億通り存在するため、人間が用意したテストケースを通過しただけでは境界バグや競合バグの不在は保証できません。

本節では[第5部](../index.md#part-5)の締めくくりとして、プログラムを実行する前にコードや仕様を機械的に検証する次の **2つのアプローチ** を整理します。

1. **静的解析（Static Analysis）の構造的・定量的手法：** [2-7節](../2/2-7.md)の制御フローグラフ（CFG）とデータフロー解析を発展させ、**プログラム依存グラフ（PDG）によるプログラムスライシング**で変数の影響経路を絞り込み、**McCabe のサイクロマチック数**でテストすべき構造複雑度を定量化します。
2. **形式手法（Formal Methods）の入口：** システムの状態遷移やプログラムの意味を論理式・数学モデルへ落とし込み、**モデル検査**、**SAT / SMT ソルバを用いた有界モデル検査（BMC）**、および **定理証明** によって、反例入力の自動発見や安全性の厳密な検証を行う原理と限界を確認します。

---

### 2. 具体例と動作イメージ（Toy Model）

抽象的なグラフ定義や論理式に入る前に、2つの短いCコードを使って「静的解析がどうコードを読み解くか」と「有界モデル検査（BMC）がどう境界バグの反例入力を自動発見するか」を手計算で確かめます。

#### 実験A：短いC関数に対するプログラムスライシングとサイクロマチック数の手計算

次の8行のC関数 `calc_fee()` を考えます（会員割引あり／なしの合計金額 `sum` を計算しつつ、無関係な監査カウンタ `log_cnt` も数えています）。

```c
int calc_fee(int price, int is_member, int n) {
    1: int sum = 0;
    2: int log_cnt = 0;              // 監査用カウンタ（sum には影響しない）
    3: for (int i = 0; i < n; i++) { // ループ条件判定（分岐①）
    4:     if (is_member)            // 会員判定（分岐②）
    5:         sum += price - 10;
           else
    6:         sum += price;
    7:     log_cnt++;                // 監査用カウンタ更新
       }
    8: return sum;
}
```

このコードに対して、静的解析の2つの代表的な問いを手計算してみます。

1. **「行8の `return sum;` の値が異常なとき、どの行だけを見ればよいか（後方スライス）」：**

    * 行8が参照する `sum` の値を直接書き換え得るのは **行1・行5・行6** です（**データ依存**）。
    * 行5と行6が実行されるかどうかを決めるのは **行4（`if (is_member)`）** です（**制御依存**）。
    * 行4が何回実行されるかを決めるのは **行3（`for` ループ）** です（**制御依存**）。
    * 一方、**行2（`log_cnt = 0`）と行7（`log_cnt++`）** は、`sum` の計算へデータも制御も一切繋がっていません。
    * したがって、注目点 `(行8, sum)` の **後方スライス** は **`{行1, 行3, 行4, 行5, 行6, 行8}`** となり、`log_cnt` まわりの2行を機械的に除外できます（図5-9-1左）。

2. **「この関数の分岐構造はどれほど複雑で、独立な基本経路が何本あるか（サイクロマチック数）」：**

    * `calc_fee` の制御フローグラフ（CFG：[2-7節](../2/2-7.md)）を基本ブロック単位で描くと、頂点は `N1`（初期化：`行1・2`＋`i=0`）、`N2`（`i < n ?`）、`N3`（`is_member ?`）、`N4`（`行5`）、`N5`（`行6`）、`N6`（`行7`＋`i++`）、`N7`（`return sum`）の **$N = 7$ 個** になります。
    * 遷移辺は `N1→N2`, `N2→N3`, `N2→N7`, `N3→N4`, `N3→N5`, `N4→N6`, `N5→N6`, `N6→N2`（ループ戻り辺）の **$E = 8$ 本** です（図5-9-1右）。
    * 単一関数なので連結成分数 $P = 1$ を公式 $V(G) = E - N + 2P$ に当てはめると、

        $$
        V(G) = 8 - 7 + 2 \times 1 = \mathbf{3}
        $$

    * これは二値分岐の数（`i < n` と `is_member` の2個）に $1$ を足した値（$2 + 1 = 3$）と一致し、次の **3本の独立な基本経路**（①ループ0回：`N1→N2→N7`、②会員側：`N1→N2→N3→N4→N6→N2→N7`、③非会員側：`N1→N2→N3→N5→N6→N2→N7`）が CFG の基底をなす（したがって最大 3 本のテストで全分岐を網羅できる）ことを示しています。

#### 実験B：有界モデル検査（BMC）が off-by-one 境界バグの反例を自動発見する流れ

次に、長さ4の配列 `a[4]`（有効添字は `0, 1, 2, 3`）へ先頭から値を埋める短いC関数を考えます。

```c
void fill(int a[4], int n) {
    if (n < 0 || n > 4) return;    // 0 <= n <= 4 に制限しているつもり
    for (int i = 0; i <= n; i++) { // バグ：i < n とすべきところを i <= n にした
        a[i] = i;                  // 境界検査：0 <= i < 4 を満たす必要がある
    }
}
```

もし開発者が通常の単体テストで `n = 0, 1, 2, 3` を試しても、添字 `i` は最大でも `3` に収まるため**すべてのテストが正常通過してしまいます**。ところが `n = 4` の境界条件だけは、5周目（`i = 4`）で `a[4]` へ境界外書き込み（off-by-one バグ）を起こします。

**有界モデル検査（BMC）**は、このプログラムをテスト入力で動かす代わりに、ループ展開上限（たとえば $k = 5$ 回）を設定して **論理式（SMT 式）** へ変換します。

1. **入口の前提条件（パス制約）：** `if (n < 0 || n > 4) return;` を通過してループへ入る条件は $0 \le n \le 4$ です。
2. **ループの $k = 5$ 回展開と各回の境界違反条件：**

    * $i = 0$ 周目：実行条件 $0 \le n$、境界違反条件 $\neg(0 \le 0 < 4)$（常に偽）
    * $i = 1, 2, 3$ 周目：同様に $0 \le i < 4$ は常に真のため違反しません。
    * **$i = 4$ 周目：** 実行条件 $4 \le n$、境界違反条件 $\neg(0 \le 4 < 4)$（**真**）

3. **「エラーが起きる入力 $n$ が存在するか？」の論理式 $\Phi$ を組み立てる：**
    まず、展開したステップ $i = 0, 1, 2, 3, 4$ の**いずれかで配列外アクセス（$i \ge 4$、すなわち $\neg(0 \le i < 4)$）が成立する論理和 $\bigvee$** として全体の違反条件を組み立てます。

    $$
    \Phi(n) \;\equiv\; (0 \le n \le 4) \;\land\; \bigvee_{i=0}^{4} \bigl((i \le n) \land \neg(0 \le i < 4)\bigr)
    $$

    このうち $i = 0, 1, 2, 3$ の各項は $\neg(0 \le i < 4)$ が常に偽となるため消去され、最終的に次の論理式へ簡約されます。

    $$
    \Phi(n) \;\equiv\; (0 \le n \le 4) \;\land\; \bigl((4 \le n) \land \neg(0 \le 4 < 4)\bigr)
    $$

4. **SMT ソルバへ渡す：** ソルバは $\Phi(n)$ を真にする整数 $n$ が存在するかを自動判定し、即座に **`SAT`（充足可能）** と答え、具体的な**反例（Counterexample）** **`n = 4`（5周目 `i = 4` で `a[4]` が境界外）** を出力します。

逆に、プログラマがバグを `i < n` に修正すれば、5周目の実行条件は $4 < n$ となり、前提 $0 \le n \le 4$ と矛盾するため、ソルバは **`UNSAT`（充足不能）** を返します。これにより、**$k = 5$ 回の展開範囲内で境界外アクセスを起こす入力 $n$ は1つも存在しない**ことが機械的に確認されます。

### 3. 構造・アルゴリズム・実装（What）

#### (1) 静的解析の定量的・構造的手法（PDG・スライシング・サイクロマチック数）

[2-7節](../2/2-7.md)で学んだ通り、コンパイラは最適化のためにプログラムを **制御フローグラフ（CFG）** へ変換し、「どの代入がどの参照に届くか」を追う **データフロー解析（到達定義・生存変数解析）** を行います。静的解析ツールは、この同じ基盤をバグ検出・影響分析・コード品質の定量化へ応用しています。

1. **プログラム依存グラフ（PDG：Program Dependence Graph）：**
    プログラムの各文を頂点とし、次の2種類の有向辺を重ね合わせたグラフです（図5-9-1左）。

    * **データ依存辺（Data Dependence Edge）：** 文 $s_1$ が変数 $v$ を定義（代入）し、途中で別の上書きを受けずに文 $s_2$ がその $v$ を参照し得るとき、$s_1 \to_{\text{data}} s_2$ を張ります（[2-7節](../2/2-7.md)の到達定義解析から機械的に求まります）。
    * **制御依存辺（Control Dependence Edge）：** 条件分岐文 $s_1$ の真偽結果によって文 $s_2$ が実行されるかどうかが直接決まるとき、$s_1 \to_{\text{ctrl}} s_2$ を張ります。

2. **プログラムスライシング（Program Slicing）：**
    PDG 上でグラフ探索（到達可能頂点の収集）を行うだけで、巨大なコードベースから目的に関係する文だけを自動抽出できます。

    * **後方スライス（Backward Slice）：** 注目点 `(行p, 変数v)` から PDG の辺を**逆向き**に辿って到達できる全文の集合です。「なぜこの行で変数が不正な値になったか」という **デバッグ・原因の絞り込み** に使います（実験Aの `(行8, sum)` では `{行1, 行3, 行4, 行5, 行6, 行8}` が抽出されました）。
    * **前方スライス（Forward Slice）：** ある文 `(行p, 変数v)` から PDG の辺を**順向き**に辿って到達できる全文の集合です。「この行を書き換えたら、プログラムのどこまで影響が波及するか」という **変更影響範囲の特定・リファクタリング安全性確認** に使います（実験Aで `行2` の `log_cnt` を変更しても、前方スライスは `{行2, 行7}` に閉じるため `return sum` へ影響しないことが一目で分かります）。

3. **McCabe のサイクロマチック数（Cyclomatic Complexity）：**
    トーマス・マッケイブ（1976年）が提案した、CFG の位相構造からコードの分岐複雑度を定量化する指標です（図5-9-1右）。グラフ理論のオイラーの公式に基づき、辺数 $E$、頂点数 $N$、連結成分数 $P$（単一関数では $P = 1$）に対して次式で定義されます。

    $$
    V(G) = E - N + 2P
    $$

    * 単一関数で各分岐が二値判定（`if`、`while`、`for`、`&&`、`||`、`?:`）からなる場合、**$V(G) = (\text{分岐判定の個数}) + 1$** と一致します（実験Aでは $E = 8, N = 7, P = 1$ より $8 - 7 + 2 = 3$、分岐判定2個 $+ 1 = 3$）。
    * $V(G)$ は、CFG のすべての経路を線形結合で表すための **線形独立な基本経路（基底）の本数** です。したがって、**分岐網羅（ブランチカバレッジ）を達成するために必要な最小テストケース数の上限**を与えます（1 本の実行経路が独立した複数の分岐の真偽を同時に通れるため、分岐網羅に必要な最小テスト数は $V(G)$ 以下になり得ます）。同時に、関数が複雑すぎないか（実務では一般に $V(G) \le 10$ を1つの目安とし、超過する関数は分割を検討します）を監視する品質指標として静的解析ツールに組み込まれています。

#### (2) 形式手法（Formal Methods）の柱：モデル検査・SAT/SMT と BMC・定理証明

静的解析は構文やグラフ構造から高速に異常や複雑度を検出できますが、「複数の変数値やスレッドの実行順が絡み合った複雑な仕様を満たすか」までは保証できません。この壁を越える数学的検証アプローチが **形式手法（Formal Methods）** であり、大きく次のアプローチへ分かれます。

1. **モデル検査（Model Checking）：状態遷移系の自動網羅探索**

    * **仕組み：** システムの振る舞いを有限の状態遷移グラフ（オートマトン）としてモデル化し、満たすべき仕様を **時相論理（LTL：線形時相論理等）** で記述します。時相論理では、時間軸に沿った性質を表す演算子として **$\Box$（常に：Always / Globally、以降のすべての状態で成り立つ）** と **$\Diamond$（いつか必ず：Eventually / Finally、将来のある時点で必ず成り立つ）** を用います。たとえば[4-1節](../4/4-1.md)の並行性では、**安全性（Safety）**を「常に2プロセスが同時にクリティカルセクションへ入らない：$\Box \neg(\text{cs}_0 \land \text{cs}_1)$」、**活性（Liveness）**を「入ろうと試みれば、いつか必ず入れる：$\Box(\text{try}_0 \to \Diamond \text{cs}_0)$」と書き表します。
    * **強み：** ツール（**SPIN**、**TLA+** 等）が到達可能なすべての状態とインターリービングを自動探索し、仕様に違反する経路が1つでもあれば**具体的な反例トレース（バグを再現する最短の実行順）を自動出力**します。[4-2節](../4/4-2.md)の Peterson アルゴリズムや分散合意プロトコル、通信プロトコルの設計検証で大きな威力を発揮します。

2. **SAT / SMT ソルバと有界モデル検査（BMC：Bounded Model Checking）：**

    * **SAT / SMT ソルバ：** **SAT ソルバ**は命題論理式（ブール変数と AND/OR/NOT）を真にする割当が存在するか（充足可能性）を高速に判定するエンジンです。これを拡張した **SMT（Satisfiability Modulo Theories）ソルバ**（Z3 等）は、固定幅ビットベクトル（32/64ビット整数演算やオーバーフロー）、配列、線形算術といった理論を組み込んだ論理式を直接解くことができます。
    * **有界モデル検査（BMC）：** C言語などの実際のソースコードに対し（代表ツール：**CBMC**）、ループ展開回数や実行ステップ数に上限 $k$ を設けてプログラムを **静的単一代入（SSA：Static Single Assignment、各変数への代入がちょうど1回だけになるようバージョン番号を振り分ける中間表現、[2-7節](../2/2-7.md)）形式**へ展開し、「パス制約 $\land$ 仕様違反条件」という SMT 論理式へエンコードしてソルバへ渡します（図5-9-2）。実験Bで見たように、配列境界外アクセス・ゼロ除算・整数オーバーフロー・アサーション違反が起きる具体入力を**人手でテストを書かずに自動で発見**できます。

3. **定理証明（Theorem Proving）：演繹的証明型**

    * **仕組み：** システムの仕様と実装を数学の論理体系（**Coq** / **Lean** / **Isabelle** などの証明支援系：Proof Assistant）の上で定式化し、人間の証明方針と機械の厳密な証明検査器を組み合わせて、「あらゆる入力・無限の状態に対しても性質が成り立つ」ことを数学の定理として演繹的に証明します。
    * **実例：** [3-1節](../3/3-1.md)コラムで触れたマイクロカーネル **seL4** は、約1万行のCコード実装が抽象仕様と一致し、バッファオーバーフローやヌルポインタ参照が起きないことが Isabelle/HOL によって機械的に証明されています。また、Cコンパイラ **CompCert** も、最適化によってプログラムの意味が保存されることが Coq で証明されています。

> **【コラム：形式検証は万能策ではない：「仕様の曖昧さをあぶり出す工学的道具」】**
>
> 形式手法を学ぶと「形式検証を通したプログラムには一切バグがない」と誤解されがちですが、形式検証が証明できるのはあくまで **「実装（またはモデル）が、人間が書き下した形式仕様を満たしていること」** だけです。もし形式仕様そのものに抜け漏れがあったり、ハードウェアのキャッシュタイミング経由のサイドチャネル漏洩のようにモデル化していない物理層に問題があったりすれば、証明済みのコードでも想定外の挙動は起こり得ます。
>
> それでも実務（AWS の分散ストレージ設計での TLA+ 活用など）で形式手法が高く評価される理由は、**「自然言語では曖昧なまま放置されがちな不変条件や例外経路を数式として書き出す過程そのものが、設計段階の致命的な欠陥を早期にあぶり出す」**点にあります。形式検証はすべてのバグを自動証明する万能策ではなく、重大欠陥の芽を設計・実装の初期段階で摘み取る工学的道具として位置づけられます。

### 4. 限界と補正（Critique & Adaptation）

#### (1) 静的解析の理論的限界：偽陽性と偽陰性のトレードオフ

[2-5節](../2/2-5.md)で触れた計算理論の基本定理（**停止性問題**および **ライスの定理**）により、「任意のプログラムが実行時にバッファオーバーフローやヌルポインタ参照を起こすか否かを、誤りなく常に自動判定するアルゴリズム」は数学的に存在しません。そのため、すべての実用的な静的解析ツールは次の **トレードオフ** を避けられません。

* **偽陽性（False Positive：安全なのに「バグの恐れあり」と警告する）：** 見逃しをゼロに近づける（健全性を保つ）ため保守的に近似すると、実際には起こり得ない経路まで警告してしまいます。警告が大量に鳴り続けると、開発者が警告を無視する「警告疲れ」を招きます。
* **偽陰性（False Negative：バグがあるのに見逃す）：** 開発現場で使いやすいよう偽陽性を減らすヒューリスティックに振ると、複雑なポインタ別名（エイリアス）や関数跨ぎの条件で発生する重大なバグを見逃してしまいます。

#### (2) 形式手法の計算上・運用上の壁：状態空間爆発・有界性・人的コスト

形式手法にも明確な現実的限界があります。

* **状態空間爆発問題（State Explosion Problem）：** モデル検査では、変数のビット数や並行プロセス数が少し増えるだけで、取り得る全状態数が $2^n$ と指数関数的に爆発し、メモリと計算時間が尽きて探索が終了しなくなります。
* **BMC の有界性（Boundedness）ゆえの制約：** 有界モデル検査は展開上限 $k$ 以内の実行経路しか論理式に含めないため、**ループ回数 $k$ を超えた先に潜むバグは見逃し得ます**。たとえば実験Bでもし上限を $k = 4$（`i = 0, 1, 2, 3` の4周分）に設定していれば、5周目（`i = 4`）で発火する `n = 4` の境界外書き込みを検出できずに `UNSAT` が出てしまいます（実務では、展開末尾で「ループ継続条件が偽であること（上限 $k$ を超える反復が残っていないこと）」を自動検査する **巻き戻しアサーション［unwinding assertion］** や、数学的帰納法と組み合わせる $k$-帰納法などで補います）。
* **定理証明の人的コスト：** seL4 や CompCert のような厳密な機械的証明には、実装コードの何十倍もの証明スクリプトと高度な専門知識・数年単位の工数が必要です。

#### (3) 実用上の補正：階層的保証（Layered Assurance）

以上の限界を踏まえ、現実の大規模システムでは「アプリケーション全体を定理証明する」のではなく、**コストとリスクに応じて検証手法を層状に組み合わせる「階層的保証」**が採られています。

* **システムの中核（小さく致命的な境界）：** マイクロカーネル、暗号プリミティブ、分散合意プロトコル、OS のロックやファイルシステム設計などには **モデル検査（SPIN / TLA+）・BMC・定理証明** を集中投入します。
* **広大な周辺コードベース：** 残りのアプリケーション層や周辺ドライバには、**メモリ安全言語（Rust 等）**の採用に加え、CI パイプラインでの **静的解析（サイクロマチック数監視・Linter）・サニタイザ（ASan / TSan）・ファジング**、そして本番環境での **実行時多層防御（[5-8節](5-8.md)）** を重ねて全体を守ります。

> **【確認の問い】**
>
> 1. **（サイクロマチック数 $V(G) = 4$ の計算・基本経路の列挙とスライシングの比較）**
>     次の C 関数 `classify()` について、(a)・(b) に答えてください。
>
>     ```c
>     int classify(int x, int y) {
>         1: int r = 0;
>         2: if (x > 0) {           // 分岐①
>         3:     if (y > 0) r = 1;  // 分岐②
>                else       r = 2;
>            }
>         4: while (x > 10) {       // 分岐③
>         5:     x -= 10;
>            }
>         6: return r;
>     }
>     ```
>
>     * (a) この関数の CFG の頂点数 $N$・辺数 $E$・連結成分数 $P$ から **McCabe のサイクロマチック数 $V(G) = 4$** を導き、線形独立な **4 本の基本経路**（具体入力例と通過する分岐の組合せ）を列挙してください（あわせて、分岐網羅に必要な最小テスト数と $V(G)$ の関係も 1 文で述べてください）。
>     * (b) PDG における **後方スライス** と **前方スライス** の役割の違いを比較し、注目点 `(行6, r)` の後方スライスに `while (x > 10) { x -= 10; }`（行 4〜5）が含まれない理由、および `(行5, x)` の前方スライスがどこに閉じるかを説明してください。
>
> 2. **（有界モデル検査［BMC］の有界性トレースと巻き戻しアサーションの役割）**
>     長さ 3 の配列 `a[3]`（有効添字 `0, 1, 2`）に対する次の C 関数に有界モデル検査（BMC）を適用します。
>
>     ```c
>     void fill3(int a[3], int n) {
>         if (n < 0 || n > 3) return;
>         for (int i = 0; i <= n; i++) {   // バグ：i <= n
>             a[i] = i;                    // 境界条件：0 <= i < 3
>         }
>     }
>     ```
>
>     * (a) ループ展開上限を **$k = 3$**（`i = 0, 1, 2` の 3 周分）に設定したときと、**$k = 4$**（`i = 0, 1, 2, 3` の 4 周分）に設定したときのそれぞれについて、BMC が生成する論理式（パス制約 $\land$ 各ステップの境界違反の論理和 $\bigvee$）と SMT ソルバの判定結果（`SAT` / `UNSAT`、および `SAT` の場合の具体的な反例）をトレースしてください。
>     * (b) $k = 3$ でバグを見逃す危険を防ぐために実用 BMC ツールが展開末尾へ挿入する **巻き戻しアサーション（Unwinding Assertion）** は何を検査しており、この例で $k = 3$ のときどのような判定を下すでしょうか。
>
