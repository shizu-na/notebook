### 前節（5-2）の確認問題の解答

前節の最後に提示した3つの問いの解答を確認します。問3がそのまま本節（プロセス間通信とI/O多重化）の導入になります。

1. **3層ファイル管理構造とオフセット共有の区別（`data.txt` へ `"AA"` と `"BB"` を書き込み）：**

    * **(a) 親が `open()` した後に `fork()` した場合：**
        カーネル内に生成される `struct file` は **1個だけ** であり、親と子のFDテーブルが同じ1個の `struct file`（と現在オフセット `off`）を共有します。したがって、先に書いた側が `off` を `0 → 2` へ進め、後から書く側はオフセット `2` から追記するため、ファイルの中身は **`"AABB"` または `"BBAA"`（4バイト）** になります。

    * **(b) 2つの独立したプロセスが別々に `open()` した場合：**
        `open()` ごとに独立した `struct file` が **2個** 生成され、どちらも初期オフセット `off = 0` を別々に持ちます。したがって、後から書いた側が先頭オフセット `0` を上書きしてしまい、ファイルの中身は **`"AA"` または `"BB"`（2バイト）** になります。

2. **`stdio` バッファリングと `fflush` vs `fsync`：**

    * **(a) `stderr` がデフォルトで無バッファリングである理由：**
        プログラムがエラーメッセージを出力した直後にクラッシュ（`SIGSEGV` 等）したとき、メッセージがユーザ空間のバッファに溜まったまま消えてしまうのを防ぎ、確実に端末やログへ即時出力させるためです。

    * **(b) `fflush(fp)` だけでは電源断に耐えられない理由と必要なシステムコール：**
        `fflush(fp)` はユーザ空間の `stdio` バッファを `write()` でカーネル空間のバッファキャッシュ（RAM上）へ渡すだけであり、物理ディスクへの書き出し完了までは待たないため、直後の停電でデータが消失し得ます。物理ディスクへの永続化を確実にするには **`fsync(fd)`** システムコールが必要です。

3. **ファイルを経由せずプロセス同士・別マシン同士を繋ぎ、多数接続を同時に待つ仕組み（本節への接続）：**
    OSは[5-2節](5-2.md)のファイル記述子（FD）抽象をさらに拡張し、カーネル内メモリ上のリングバッファでプロセス同士を繋ぐ **パイプ（`pipe`）**、ネットワーク越しの通信口を表す **ソケット（`socket`）**、そして多数のFDの読み書き可能状態を1スレッドで一括監視する **I/O多重化（`select` / `poll` / `epoll`）** を提供しています。

## 5-3. プロセス間通信（パイプ・FIFO・ソケット・I/O多重化）

### 1. 動機（Why）：仮想記憶で隔離されたプロセス同士を、どうやって速く安全に繋ぐのか

[第3部](../index.md#part-3)で確認した通り、OSは仮想記憶（多段ページテーブル）によって各プロセスを厳格に隔離しています。プロセスAはプロセスBのメモリへ一切触れることができません。しかし現実のシステムでは、独立した複数のプロセスが協調して1つの仕事をする場面が不可欠です。

* シェルで `ls | grep .c | wc -l` のように、前のコマンドの出力を次のコマンドの入力へ流し込みます。
* Webブラウザやデータベースクライアントが、同じマシン上（あるいはインターネットの向こう側）のサーバプロセスへ要求を送って応答を受け取ります。

もしこのやり取りを「プロセスAがいったん一時ファイルへ書き出し、プロセスBがそのファイルをディスクから読む」方法で済ませようとすると、不要なディスクI/Oが発生するだけでなく、「Aがまだ書き終わっていないのにBが読んでしまう」同期の調整も煩雑になります。

そこでOSは、**プロセス間通信（IPC：Inter-Process Communication）** の仕組みを提供し、しかも[5-2節](5-2.md)で学んだ **ファイル記述子（FD）の統一インターフェース（`read` / `write` / `close`）** の上へ自然に統合しました。さらにネットワークサーバのように何千ものクライアント接続を同時に扱う場面では、1本のFDでブロックして止まってしまわないための **I/O多重化** が必要になります。

本節では、**無名パイプのカーネル実装**、**各種IPC（FIFO・共有メモリ等）の比較**、**ソケットAPIの抽象構造**、そして **I/O多重化（`select`・`poll`・`epoll`）** を順に整理します。

---

### 2. 具体例と動作イメージ（Toy Model）

データ構造の解説に入る前に、2つの小さな具体例で「シェルのパイプ配線」と「複数接続を同時に待つ難しさ」を確かめます。

#### 実験A：シェルが `ls | grep foo` を組み立てる裏側

端末で `ls | grep foo` と入力すると、シェルは `pipe(int p[2])` システムコールを1回呼び出します。`pipe(p)` はカーネル内に1本のデータ通り道を作り、**読み出し専用のFD `p[0]`** と **書き込み専用のFD `p[1]`** という2つのFDを返します。

続いてシェルは2回 `fork()` を行い、2つの子プロセスへ次のように配線を繋ぎ替えます（図5-3-1右）。

1. **左の子（`ls` 担当）：** `dup2(p[1], 1)` で自分の標準出力（FD `1`）をパイプの書き込み端へ差し替え、不要になった `p[0]` と `p[1]` を両方 `close()` してから `exec("ls")` を実行します。
2. **右の子（`grep` 担当）：** `dup2(p[0], 0)` で自分の標準入力（FD `0`）をパイプの読み出し端へ差し替え、不要になった `p[0]` と `p[1]` を両方 `close()` してから `exec("grep", "foo")` を実行します。
3. **親シェル自身：** 親が持ち続けている **`p[0]` と `p[1]` の両方を必ず `close()`** してから、2つの子の終了を `wait()` で待ちます。

ここで重要な細部が、**「親シェルや右の子が、使わない書き込み端 `p[1]` を必ず `close()` しなければならない」**点です。もし親シェルが `p[1]` を閉じ忘れると、左の `ls` が処理を終えて終了しても、カーネルからは「まだ書き込み端を開いているプロセス（親シェル）が残っている」と見えるため、`grep` の `read(0, ...)` が EOF（`0`）を受け取れず**永遠に待ち続けてデッドロック**します。

#### 実験B：チャットサーバが2人のクライアントを同時に待てない問題

次に、クライアントA（FD `4`）とクライアントB（FD `5`）の2人が同時に接続しているサーバプログラムを考えます。もしサーバが1スレッドで素朴に次のように書いたらどうなるでしょうか。

```c
// 失敗例：ブロッキング read を順番に呼ぶ
while (1) {
    n = read(fd_A, buf, sizeof(buf));  // A が発言するまでここで完全に停止する
    handle(buf, n);
    n = read(fd_B, buf, sizeof(buf));  // B がいくら発言しても、Aが黙っている限り届かない
    handle(buf, n);
}
```

`fd_A` の `read()` が `SLEEPING` 状態で止まっているあいだ、クライアントBからどれだけメッセージが届いても一切処理できません。かといって「クライアント1人ごとに `fork()` やスレッドを作る」方式では、接続数が 10,000 人になった瞬間にスレッドのスタックメモリとコンテクストスイッチのコストが破綻します。

これを解決するのが、**「FD `4` と FD `5`（あるいは10,000本のFDすべて）をOSカーネルへまとめて預け、『どれか1本でも読み書き可能になったら起こしてほしい』と一括待機する」** I/O多重化の仕組みです。

### 3. 構造・アルゴリズム・実装（What）

#### (1) 無名パイプ（Pipe）のカーネル実装（xv6モデル）

[5-2節](5-2.md)で見た通り、パイプもカーネル内では通常ファイルと同じ `struct file`（`type = FD_PIPE`）として扱われます。2つの `struct file`（読取り用・書込み用）が、カーネルメモリ上に確保された1つの `struct pipe` を共有する構造です（図5-3-1左）。

ここで、**[4-5節](../4/4-5.md)で学んだ「有限バッファ生産者・消費者問題」がそのままOSカーネルの実装として回収されます**。xv6 の `struct pipe` の中核は次の通りです。

```c
#define PIPESIZE 512   // Linux では標準 64 KiB

struct pipe {
    struct spinlock lock;   // パイプ状態を守るスピンロック
    char data[PIPESIZE];    // 固定長のリングバッファ
    uint nread;             // これまでに読み出された総バイト数
    uint nwrite;            // これまでに書き込まれた総バイト数
    int  readopen;          // 読み出し端が1つ以上開いているか (1/0)
    int  writeopen;         // 書き込み端が1つ以上開いているか (1/0)
};
```

リングバッファ内の現在の未読データ量は `nwrite - nread` バイトです。

* **`pipewrite(pi, addr, n)`（生産者）：**

    * `lock` を獲得し、バッファが満杯（`nwrite == nread + PIPESIZE`）のあいだは読み手を `wakeup(&pi->nread)` で起こしつつ `sleep(&pi->nwrite, &pi->lock)` で眠ります。
    * 空きができれば `data[nwrite++ % PIPESIZE]` へ1バイトずつ書き込み、最後に読み手を `wakeup(&pi->nread)` で起こします。
    * **読み手が全員閉じた場合（`readopen == 0`）：** 行き先のない書き込みのため即座にエラー（POSIXでは **`SIGPIPE` シグナル**を送り、無視されていれば `EPIPE` エラーを返します）で中断します。

* **`piperead(pi, addr, n)`（消費者）：**

    * `lock` を獲得し、バッファが空（`nread == nwrite`）かつ **書き込み端がまだ開いている（`writeopen == 1`）** あいだは `sleep(&pi->nread, &pi->lock)` で眠ります。
    * データがあれば `data[nread++ % PIPESIZE]` から読み出し、書き手を `wakeup(&pi->nwrite)` で起こして読んだバイト数を返します。
    * バッファが空かつ **すべての書き込み端が閉じた（`writeopen == 0`）** 瞬間に、ループを抜けて **`0`（EOF）** を返します。

#### (2) 主なプロセス間通信（IPC）の比較

無名パイプは `fork()` でFDを継承する**親子・兄弟プロセス間**でしか使えません。用途やプロセス間の関係に応じて、OSは次の主要なIPC機構を提供しています。

| IPC 方式 | 通信範囲 | 方向・データ単位 | 特徴と主な用途 |
| :--- | :--- | :--- | :--- |
| **無名パイプ（`pipe`）** | 親子・兄弟プロセス | 単方向・バイトストリーム | 最も軽量。シェルのパイプライン（`a \| b`） |
| **名前付きパイプ（FIFO）** | 同一ホスト上の任意プロセス | 単方向・バイトストリーム | `mkfifo` でファイルシステム上に名前（パス）を持つパイプ |
| **共有メモリ（`shm_open` + `mmap`）** | 同一ホスト上の任意プロセス | 双方向・任意メモリ構造 | **カーネル経由のコピーがゼロ（最速）**。同期（セマフォ・ミューテックス）はアプリ側で別途必要 |
| **UNIXドメインソケット** | 同一ホスト上の任意プロセス | 双方向・ストリーム／データグラム | パス名で接続。TCP/IPのヘッダ処理不要で高速。**FDそのものを別プロセスへ渡せる** |
| **ネットワークソケット** | 同一ホスト・**別マシン** | 双方向・ストリーム（TCP）／データグラム（UDP） | IPアドレス＋ポート番号で世界中のプロセスと通信可能 |

#### (3) ソケット（Socket）抽象とクライアント／サーバの基本フロー

1980年代の BSD UNIX で導入された **ソケット（Socket）** は、「ネットワーク越しの別マシン上のプロセスとの通信」を、そのまま[5-2節](5-2.md)の **ファイル記述子（FD）** の抽象化へ統合した広く普及したAPI設計です。

TCP のような接続型（ストリーム型）ソケットでクライアントとサーバが通信する手順は、次の決まったシステムコール列で進みます（図5-3-2）。

1. **サーバ側の準備：**

    * `sfd = socket(AF_INET, SOCK_STREAM, 0)`：通信端点となるソケットを作成し、FD番号を得ます。
    * `bind(sfd, &addr, len)`：ソケットに自マシンの IP アドレスとポート番号（例：`8080`、[0-2節](../0/0-2.md)のネットワークバイトオーダ `htons(8080)` へ変換）を結びつけます。
    * `listen(sfd, backlog)`：接続待ち受け状態へ移行し、着信待ちキューの大きさを設定します。
    * `cfd = accept(sfd, ...)`：クライアントからの接続が来るまで `SLEEPING` で待機し、接続が確立すると**そのクライアントとの1対1通信専用の新しいFD `cfd`** を返します（元の待ち受け用 `sfd` は引き続き次のクライアントの着信待ちに使い続けます）。

2. **クライアント側の接続：**

    * `fd = socket(...)` でソケットを作成し、`connect(fd, &server_addr, len)` でサーバのIP＋ポートへ接続を要求します。

3. **双方向データ通信と切断：**

    * 接続が確立すれば、あとは通常ファイルやパイプとまったく同じ **`read(cfd, ...)` / `write(cfd, ...)`**（または `recv` / `send`）で双方向にバイト列をやり取りし、終わったら **`close()`** で閉じます。

#### (4) I/O 多重化（`select`・`poll`・`epoll`）の進化

実験Bの「1スレッドで数千本の接続（FD）を同時に監視する」課題に対し、OSは **I/O多重化（I/O Multiplexing）** システムコールを進化させてきました（図5-3-3）。

1. **`select()` / `poll()`（古典的な全件走査型：$O(N)$）：**

    * 呼び出しのたびに、監視したい全 $N$ 個のFD集合（`select` は上限1024個程度のビットマップ、`poll` は任意長の配列 `struct pollfd[]`）を**ユーザ空間からカーネル空間へ丸ごとコピー**します。
    * カーネルは $N$ 個すべてのFDの状態を先頭から順に走査し、1つでも準備ができていれば返ります。なければ全FDの待機キューへ登録して眠ります。
    * 復帰後、ユーザ側も「$N$ 個のうちどれが準備できたか」を再び配列の先頭から **$O(N)$ で全走査**して探す必要があります。
    * 接続数 $N = 10{,}000$ に対して実際に発言したクライアントが数人しかいない場合でも、毎回 10,000 個分のコピーと走査が走るため性能が急落します。

2. **`epoll()`（Linuxのイベント駆動型：$O(1)$、BSD/macOS では `kqueue`）：**

    * **登録と待機を分離する：** 最初に `epoll_create1()` でカーネル内に監視インスタンスを作り、`epoll_ctl(epfd, EPOLL_CTL_ADD, fd, ...)` で監視対象のFDをカーネル内の**赤黒木（Red-Black Tree）**へ1回だけ登録しておきます（毎回 $N$ 個コピーする必要がありません）。
    * **コールバックによるレディリスト通知：** 登録されたFDにネットワークパケットやパイプのデータが到着すると、デバイスドライバ／プロトコルスタックの割り込み処理がコールバックを起動し、**準備が完了したそのFDだけをカーネル内の「レディリスト（連結リスト）」へ $O(1)$ で追加**します。
    * **`epoll_wait()`：** ユーザが `epoll_wait()` を呼ぶと、カーネルは全 $N$ 個を一切走査せず、**レディリストに入っている $k$ 個（準備完了済みのFDだけ）**をユーザ空間へ返します。計算量は総接続数 $N$ ではなく、実際にイベントが起きた数 $k$ にしか比例しません（$O(k)$、1イベントあたり **$O(1)$**）。

> **【コラム：レベルトリガ（LT）vs エッジトリガ（ET）とノンブロッキングI/O】**
>
> `epoll` には、イベントを通知する条件として2つのモードがあります。
>
> * **レベルトリガ（Level-Triggered：LT、デフォルト）：** 「受信バッファに未読データが1バイトでも残っている状態」であれば、`epoll_wait()` を呼ぶたびに何度でも通知される。`select` / `poll` と同じ扱いやすい挙動。
> * **エッジトリガ（Edge-Triggered：ET、`EPOLLET`）：** 「空だったバッファに新しくデータが届いた瞬間（状態の立ち上がり変化）」に**1回だけ**通知される。もしそのとき一部しか読み切らずに再び `epoll_wait()` へ入ると、次の新データが来るまで二度と通知されずに停滞する。
>
> そのためエッジトリガを使うときは、必ず対象FDを **`O_NONBLOCK`（ノンブロッキングモード）** に設定したうえで、`read()` が `EAGAIN`（もう手元にデータがない）を返すまで **`while` ループで一気に読み切る** のが鉄則です。余計な再通知システムコールを減らせるため、Nginx や Redis といった超高速サーバで広く活用されています。

### 4. 限界と補正（Critique & Adaptation）

#### (1) パイプで起きる2つの典型障害：双方向デッドロックと `SIGPIPE`

無名パイプは簡潔ですが、バッファ容量が有限（xv6 で 512 B、Linux で 64 KiB）であるため、実務では次の2つの落とし穴に注意が必要です。

1. **双方向パイプによるデッドロック：** プロセスAとプロセスBを2本のパイプ（A→B と B→A）で双方向に繋いだとき、両方が同時に 64 KiB を超える大量のデータを `write()` し始めると、両方のパイプバッファが満杯になって双方が `write()` の中で眠ってしまい、誰も `read()` を呼ばず永久にデッドロックします（補正：ノンブロッキングI/O＋`poll`/`epoll` で読み書きを多重化します）。
2. **`SIGPIPE` によるサーバの突然死：** ネットワークサーバが、すでに切断されたクライアントのソケットへ `write()` を呼ぶと、OSはプロセスへ `SIGPIPE` シグナルを送り、デフォルト動作で**サーバプロセス全体が即座に強制終了**してしまいます。補正として、実用のネットワークサーバでは起動時に必ず `signal(SIGPIPE, SIG_IGN)` で `SIGPIPE` を無視（または `send()` に `MSG_NOSIGNAL` を指定）し、`write()` の戻り値 `-1`（`errno == EPIPE`）として通常のエラー処理で静かに接続を閉じます。

#### (2) C10K 問題とイベント駆動サーバの限界（ワーカースレッド併用と `io_uring`）

1999年にダン・ケーゲルが提起した **C10K 問題（1台のサーバで同時に1万クライアントをどう捌くか）** は、従来の「1接続＝1プロセス／1スレッド」モデルから、本節の **`epoll` / `kqueue` によるシングルスレッド・イベント駆動（Reactor パターン）** への転換によって突破されました。

しかし、イベント駆動モデルにも明確な限界があります。

* **CPUバウンド処理によるイベントループの停滞：** 1本のイベントループスレッドの中で、重い暗号計算や画像変換、あるいはブロックするディスクI/O（注意：Linux の `epoll` は通常のディスクファイルに対して常に「準備完了」を返し、実際のディスク読込みではブロックします）を実行すると、その間すべてのクライアント応答が止まります。
* **補正：** ネットワークI/Oの多重化は `epoll` ループへ任せつつ、重い計算やディスクI/Oは背後の**ワーカースレッドプール**へオフロードするハイブリッド構成をとるか、さらに近年はネットワークもディスクファイルも統一的に完全非同期で処理できる Linux の **`io_uring`**（[5-1節](5-1.md)のVirtIOと似たユーザ／カーネル間リングバッファ共有）へ移行する動きが進んでいます。

### 理解度チェック（次節へ進む前の確認）

本節のパイプのクローズ規則、`select`/`poll` と `epoll` の違いを確認し、次節（[5-4節](5-4.md)）へ繋ぐ問いを置きます。

> **【確認の問い】**
>
> 1. **（無名パイプの書き込み端クローズ忘れと `SIGPIPE`）**
>     シェルが `pipe(p)` を呼んで `ls | grep foo` を実行する場面を考えます。
>
>     * (a) 親シェルが不要な書き込み端 `p[1]` を `close()` し忘れた場合、`ls` が正常終了した後も `grep` が終了せず永久に止まってしまうのはなぜでしょうか。`writeopen` と EOF の関係から説明してください。
>     * (b) 逆に、読み出し側の `grep` が途中で異常終了してすべての読み出し端が閉じた状態で、書き込み側のプロセスがパイプへ `write()` を呼ぶとOSはどのような反応をするでしょうか。
>
> 2. **（`select` / `poll` と `epoll` のスケーラビリティの差）**
>     同時に $10{,}000$ 本のクライアントソケットが接続されており、そのうち実際にデータが届いたのは $2$ 本だけだとします。この状況で `poll()` と `epoll_wait()` の処理コスト（計算量）が大きく異なる理由を、「カーネルへの登録方式」と「レディリスト」の2語を使って簡潔に説明してください。
>
> 3. **（次節への伏線：巨大なファイルを物理ディスクのセクタ群へどう並べて管理するか）**
>     本節までで、メモリ上のパイプやネットワークソケットをFDとして読み書きする仕組みが整いました。では、電源を切っても消えない **HDD や SSD** の上に、サイズが数バイトから数ギガバイトまでばらばらで、しかも後からどんどん追記・削除される多数の「通常ファイル」を格納するには、ディスク上のブロックをどのようなデータ構造（**i-node** 等）で割り当てて管理すればよいでしょうか。
