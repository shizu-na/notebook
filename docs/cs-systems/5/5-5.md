### 前節（5-4）の確認問題の解答

前節の最後に提示した3つの問いの解答を確認します。問3がそのまま本節（ディレクトリ・リンク・VFSとバッファキャッシュ）の導入になります。

1. **HDD のランダム読み出し時間の手計算（$10{,}000\text{ rpm}$、平均シーク $4.0\text{ ms}$）：**

    * **(a) 1回転時間と平均回転待ち時間：**
        1分（$60{,}000\text{ ms}$）あたり $10{,}000$ 回転なので、1回転にかかる時間は $\dfrac{60{,}000\text{ ms}}{10{,}000} = \mathbf{6.0\text{ ms}}$ です。平均回転待ち時間はそのちょうど半分（半回転分）のため **$\mathbf{3.0\text{ ms}}$** になります。

    * **(b) 1回あたりの平均アクセス時間：**
        シーク時間と平均回転待ち時間を足して $4.0 + 3.0 = \mathbf{7.0\text{ ms}}$ です（データ転送時間は $0\text{ ms}$ とみなしています）。

2. **i-node の最大ファイルサイズ計算（ブロックサイズ $4\text{ KiB}$、ブロック番号 $4\text{ B}$）：**

    * **(a) 1枚の間接ブロックに格納できるブロック番号の個数：**
        $\dfrac{4{,}096\text{ B}}{4\text{ B}} = \mathbf{1{,}024\text{ 個}}$

    * **(b) 最大ファイルサイズとその内訳：**

        * 直接ブロック（12本）：$12 \times 4\text{ KiB} = \mathbf{48\text{ KiB}}$
        * 単一間接ブロック（1本）：$1{,}024 \times 4\text{ KiB} = \mathbf{4\text{ MiB}}$
        * 二重間接ブロック（1本）：$1{,}024 \times 1{,}024 \times 4\text{ KiB} = \mathbf{4\text{ GiB}}$
        
        合計は **$4\text{ GiB} + 4\text{ MiB} + 48\text{ KiB}$**（およそ **$4.004\text{ GiB}$**）になります。

3. **i-node に「ファイル名」が入っていない理由と、ディスクアクセスを減らすキャッシュ（本節への接続）：**
    UNIX系ファイルシステムでは「ファイルの実体（i-node）」と「人間が読む名前」を意識的に切り離し、**ディレクトリ**という特殊なファイルの中に `(ファイル名, i-node番号)` の対応表を並べて管理しています。これにより1つの i-node に複数の別名（ハードリンク）を付けられます。また、毎回ディスクへ読み書きする遅さを隠蔽するため、OSカーネルはRAM上に **バッファキャッシュ（LRU）** を置いて頻繁に使うブロックを記憶しています。

## 5-5. ディレクトリ・リンク・VFSとバッファキャッシュ（LRU）

### 1. 動機（Why）：なぜ「名前」「実体」「物理媒体」を切り離し、さらにRAM上にキャッシュを挟むのか

前節（[5-4節](5-4.md)）で、ディスク上のファイル実体が **i-node**（メタデータと多段ブロック番号表）によって管理されていることを確認しました。しかし、i-node だけでは普段私たちが使っているファイルシステムとしてまだ3つの重要な要素が欠けています。

1. **人間が使う「階層的な名前」と i-node の結びつけ：**
    人間は「i-node 番号 `42` のファイルを開け」とは指示せず、`/home/user/main.c` のような階層的なパス名を指定します。もしファイル名を i-node の中へ直接書いてしまうと、1つのファイルに複数の別名を付けたり、異なるディレクトリ間でファイルを移動したりする設計が窮屈になります。

2. **異種ファイルシステムの統一的な扱い：**
    現代の1台のコンピュータには、内蔵SSD（ext4 や APFS）、差し込んだUSBメモリ（FAT32）、さらにプロセス情報をファイルのように見せる仮想ファイルシステム（Linux の `/proc`）など、**内部構造がまったく異なる複数のファイルシステム**が同時に繋がります。アプリケーションが媒体ごとの違いを意識せず1つの統一されたディレクトリ木として扱える抽象層（**VFS**）が必要です。

3. **ミリ秒単位のディスク遅延の隠蔽と並行アクセス保護：**
    `/home/user/main.c` を開くだけでも、ルートディレクトリ・`home`・`user`・`main.c` の i-node とデータブロックを何度も読む必要があります。毎回物理ディスク（HDDなら約 $7\text{〜}10\text{ ms}$）へアクセスしていてはシステム全体が使い物にならず、さらに複数プロセスが同じブロックを同時に読み書きすればデータが破損します。

本節では、**ディレクトリと2種類のリンク（ハードリンク／シンボリックリンク）**、**VFS（仮想ファイルシステム）とマウント**、そして xv6 モデルに基づく **バッファキャッシュ（LRU と2段階ロック）** の3つを順に整理します。

---

### 2. 具体例と動作イメージ（Toy Model）

データ構造の細部に入る前に、2つの小さな実験で「パス名解決のステップ」と「2種類のリンクの決定的な違い」を確かめます。

#### 実験A：パス名 `/usr/bin/ls` を先頭から1段ずつ辿る（名前解決 `namei`）

OSカーネルが `open("/usr/bin/ls", O_RDONLY)` を受け取ったとき、どのようにして目的の i-node 番号へ辿り着くのかを追ってみます。UNIX系ファイルシステムでは、ルートディレクトリ `/` の i-node 番号はあらかじめ固定値（xv6 では **`1`**、Linux ext4 では `2`）と決まっています。

1. 先頭が `/` なので、固定の **ルート i-node `1`** を開きます（相対パスなら現在プロセスのカレントディレクトリ `p->cwd` から始めます）。
2. i-node `1` のデータブロックを読み、中身の一覧から名前 `"usr"` を探して **i-node `12`** を見つけます。
3. i-node `12`（ディレクトリ）のデータブロックを読み、中身から名前 `"bin"` を探して **i-node `25`** を見つけます。
4. i-node `25`（ディレクトリ）のデータブロックを読み、中身から名前 `"ls"` を探して **i-node `42`**（通常ファイル）に到達します。

このように、ディレクトリとは特別な隠しデータではなく、**「`(名前, i-node番号)` のペアがずらりと並んだ普通のデータブロックを持つ i-node」** に過ぎません。

#### 実験B：ハードリンクとシンボリックリンクで、元のファイルを `rm` したときの差

あるファイル `a.txt`（i-node 番号 `42`、中身は `"hello"`）に対して、2種類のリンクを作成してから元の `a.txt` を削除（`rm a.txt`）してみます。

```sh
ln    a.txt hard.txt   # ① ハードリンクを作成
ln -s a.txt sym.txt    # ② シンボリックリンクを作成
rm    a.txt            # ③ 元の名前 a.txt を削除
```

この直後に `cat hard.txt` と `cat sym.txt` を実行すると、結果は真っ二つに分かれます。

* **`cat hard.txt`：** 正常に **`"hello"`** が読めます。`a.txt` も `hard.txt` も対等に「i-node `42` を指す名前」の1つに過ぎず、`rm a.txt` は i-node `42` のリンク数（`nlink`）を $2 \to 1$ に減らしただけだからです。
* **`cat sym.txt`：** **`No such file or directory` エラー**になります。`sym.txt` は別の i-node（例：`99`）を持っており、その中身に `"a.txt"` という**ただのパス文字列**が書かれているだけなので、`a.txt` が消えた瞬間にリンク切れ（Dangling Link）になるのです。

### 3. 構造・アルゴリズム・実装（What）

#### (1) ディレクトリの内部構造と名前解決

xv6 のディレクトリエントリ（`struct dirent`）は、わずか 16 バイトの単純な固定長構造体です。

```c
#define DIRSIZ 14

struct dirent {
    ushort inum;          // i-node 番号（0 なら空きスロット）
    char   name[DIRSIZ];  // ファイル名（最大 14 文字）
};
```

ディレクトリ用の i-node は `type == T_DIR` が設定されており、そのデータブロックにはこの `struct dirent` が配列状に並んでいます。すべてのディレクトリは、作成時に必ず自分自身を指す **`.`** と親ディレクトリを指す **`..`** の2つのエントリを含みます（ルートディレクトリ `/` だけは `.` も `..` も自分自身を指します）。

ファイル削除を行うシステムコール名が `delete` や `remove` ではなく **`unlink(path)`**（リンクを切る）である理由は、まさにこの構造にあります。

#### (2) ハードリンク vs シンボリックリンクと「ファイルが本当に消える瞬間」

実験Bで確認した2種類のリンクの構造を対比します（図5-5-1）。

| 比較項目 | ハードリンク（`ln` / `link()`） | シンボリックリンク（`ln -s` / `symlink()`） |
| :--- | :--- | :--- |
| **実体の構造** | 同じ i-node 番号を別名でディレクトリへ登録 | 新しい専用 i-node を作り、データ本体へ**リンク先パス文字列**を保存 |
| **元ファイル削除後** | 他の名前が残っていればデータは無傷で読める | 参照先パスが消えるためリンク切れになる |
| **ファイルシステム跨ぎ** | **不可**（i-node 番号は同一FS内でのみ一意） | **可能**（別ディスク・別パーティションも指定可） |
| **ディレクトリへのリンク** | **原則禁止**（ディレクトリ木に循環ループが生じるため） | **可能**（OSがループ深さ上限 `ELOOP` で検知） |

ここで、UNIXファイルシステムの洗練された仕様である **「ファイルの物理ブロックが本当に解放される条件」** を押さえておきます。OSは各 i-node について、次の **2種類の参照カウンタ** を管理しています。

1. **ディスク上のハードリンク数（`nlink`）：** ディレクトリから名前で指されている数です。
2. **メモリ上のオープン参照数（`ref`）：** 現在 `open()` して開いているプロセスやカーネル内参照の数です。

あるファイルに対して `unlink()` が呼ばれて **`nlink` が `0` になっても、もし別プロセスがそのファイルを `open()` したまま（`ref > 0`）であれば、OSはまだデータブロックと i-node を解放しません**。そのプロセスは名前が消えた後も最後まで正常に `read()` / `write()` を続けられ、最後のプロセスが `close()` して **`nlink == 0` かつ `ref == 0`** になった瞬間に初めてディスク上のブロックが回収されます（一時ファイルを `open()` 直後に `unlink()` しておけば、プロセスがクラッシュしても絶対にディスクへゴミを残さない安全な一時ファイルパターンとして実務で広く使われます）。

#### (3) VFS（仮想ファイルシステム）とマウント

異なる種類のファイルシステム（ext4、FAT32、NFS、`/proc` 等）を1つの統一されたディレクトリツリーとして透過的に扱うため、Linux や BSD のカーネルはファイルシステムの上層に **VFS（Virtual File System：仮想ファイルシステム）** という抽象インターフェース層を設けています（図5-5-2）。

VFS はC言語の構造体と関数ポインタ表を用いて、オブジェクト指向のポリモーフィズム（多態性）を実現します。主要なのは次の4つの抽象オブジェクトです。

* **`superblock`：** マウントされた1つのファイルシステム全体の情報（ブロックサイズ、ルート位置、マウント操作表）を保持します。
* **`inode`：** 個々のファイル／ディレクトリのメタデータと操作関数表（`create`, `lookup`, `unlink` 等）を保持します。
* **`dentry`（Directory Entry）：** パス名の構成要素（例：`"usr"`, `"bin"`, `"ls"`）と `inode` の対応をメモリ上にキャッシュする構造体です。
* **`file`：** プロセスが `open()` した1つのオープン状態（[5-2節](5-2.md)の `struct file`：`read`, `write`, `lseek` 等の関数ポインタ表）を表します。

USBメモリなどを接続して `mount("/dev/sdb1", "/mnt/usb", "vfat", ...)` を実行すると、VFS は既存のツリー上の空ディレクトリ `/mnt/usb` の `dentry` に「ここからは別ファイルシステム（FAT32）のルートへ繋ぎ替える」という**マウントポイント**を登録します。するとアプリが `/mnt/usb/photo.jpg` を開いたとき、`/` と `mnt` は ext4 のドライバが解決し、`usb` を跨いだ瞬間から VFS が自動的に FAT32 のドライバへ処理を切り替えてくれるのです。

#### (4) バッファキャッシュ（Buffer Cache）の設計と実装（xv6 の LRU ＋ 2段階ロック）

名前解決やファイル読み書きのたびに遅いディスク（[5-1節](5-1.md)の VirtIO / HDD / SSD）へ直接アクセスしていては性能が出ません。そこでOSカーネルは、ファイルシステム層とディスクドライバ層のあいだに **バッファキャッシュ（Buffer Cache）** を挟みます。

バッファキャッシュは、次の **2つの重要な責務** を同時に担います。

1. **高速化（キャッシュ）：** 最近読み書きされたディスクブロックのコピーをRAM上に保持し、同じブロックへの再アクセス（スーパーブロック、ルートディレクトリ、よく使う i-node 等）でディスクI/Oを省きます。
2. **同期（単一コピーの保証）：** 同一のディスクブロック `(dev, blockno)` に対して、カーネルのメモリ上に**常に高々1個しかバッファコピーが存在しない**ことを保証し、複数プロセスが同じブロックを同時に書き換えて壊すのを防ぎます。

xv6 のバッファキャッシュ（`bio.c`）は、固定個数（例：`NBUF = 30` 個）の `struct buf` を **環状二重連結リスト（LRU順）** で繋いで管理しています（図5-5-3）。

```c
struct buf {
    int valid;              // ディスクから読み込み済みか (1/0)
    int disk;               // VirtIO ドライバへI/O要求中か
    uint dev;               // デバイス番号
    uint blockno;           // ディスク上のブロック番号
    struct sleeplock lock;  // このブロックの内容を守る長時間用スリープロック
    uint refcnt;            // 現在このバッファを参照しているプロセス数（PIN数）
    struct buf *prev;       // LRU 二重連結リストの前の要素
    struct buf *next;       // LRU 二重連結リストの次の要素
    uchar data[BSIZE];      // ディスクブロック1枚分の実データ（1024 B）
};
```

ここで、**[4-4節](../4/4-4.md)で学んだ「スピンロックとスリープロックの使い分け」がそのまま実務設計として回収されます**。`bread(dev, blockno)`（ブロック読込）と `brelse(b)`（ブロック解放）は、次の2段階ロックで動きます。

1. **`bget(dev, blockno)` による検索・確保：**

    * まず全体を守る短いスピンロック **`bcache.lock`** を `acquire()` します。
    * リストを先頭から走査し、目的の `(dev, blockno)` がすでにあれば（**キャッシュヒット**）、`b->refcnt++` してから `bcache.lock` を解放し、ブロック専用の **`acquiresleep(&b->lock)`** を獲得して返します。
    * 見つからなければ（**キャッシュミス**）、リストの**末尾（最も長く使われていない：LRU側）から逆順**に走査し、現在誰も使っていない（**`b->refcnt == 0`**）空きブロックを1つ見つけて再利用（`dev`, `blockno` を付け替え、`valid = 0`, `refcnt = 1`）し、`bcache.lock` を解放してから `acquiresleep(&b->lock)` を獲得して返します。

2. **`bread()` でのディスク読込：**

    * `b->valid == 0` なら、`b->lock`（スリープロック）を保持したまま `virtio_disk_rw(b, 0)` を呼んで安全に `sleep` しながらディスクから読み込み、`b->valid = 1` にして返します。

3. **`brelse(b)` での解放と LRU 先頭への移動（MRU更新）：**

    * `releasesleep(&b->lock)` でブロックのスリープロックを解放し、`bcache.lock` を握って `b->refcnt--` します。
    * もし **`b->refcnt == 0`** になったら、そのブロックを環状リストから外して **`head` の直後（MRU：最も最近使われた側）** へ繋ぎ直します。

> **【コラム：Linux の「ページキャッシュとバッファキャッシュの統合」と `dcache`】**
>
> 初期の UNIX や xv6 では、「ファイルの読み書き用キャッシュ（バッファキャッシュ）」と「`mmap` で仮想メモリへマップしたファイル用のページ（ページキャッシュ：[3-7節](../3/3-7.md)）」が別々に管理されていました。しかし両者が分離していると、同じファイルに対して片方のプロセスが `write()` し、もう片方が `mmap` で読んだときに**メモリ上に同じデータが二重に載って内容が不整合になる**という問題が起きます。
>
> そこで現代の Linux（カーネル 2.4 以降）では、両者を **統合ページキャッシュ（Unified Page Cache）** として完全に一本化しました。通常ファイルの `read()`/`write()` も `mmap` も、すべて同じ物理RAMページを共有するため、二重コピーも不整合も起きません。さらに、名前解決（`/usr/bin/ls` 等）のたびに毎回ディレクトリブロックを走査するコストを省くため、VFS層に直近のパス解決結果をハッシュ表で記憶する **`dcache`（dentry キャッシュ）** も備えており、頻出パスの名前解決をマイクロ秒未満で完了させています。

### 4. 限界と補正（Critique & Adaptation）

#### (1) 線形走査ディレクトリの限界とハッシュ木（HTree / B木）による補正

xv6 のような単純なディレクトリ実装では、`struct dirent` を配列に並べているだけなので、あるディレクトリに $N$ 個のファイルがあると、ファイル検索（`lookup`）に毎回 **$O(N)$ の線形走査** がかかります。ファイルが100個なら一瞬ですが、Webキャッシュやメールサーバのように**1つのディレクトリに 10 万個のファイル**が置かれると、1回の `open()` ごとに数万エントリをなめる羽目になりシステム全体が急激に遅くなります。

これに対する現代ファイルシステム（ext4、XFS、APFS、NTFS）の補正が、ディレクトリ内部のインデックス構造化です。たとえば Linux の **ext4** は、ファイル名からハッシュ値を計算して定数深さの木で管理する **HTree（ハッシュ $\text{B}$ 木）** をディレクトリへ導入し、数百万ファイルが入っていても $O(\log N)$（実質2〜3ブロック読込）で検索できるよう改善しています。また、xv6 の `bcache` 自体も全30ブロックを1本のスピンロックと1本のリストで線形走査していますが、実システムではブロック番号の**ハッシュバケットごとにロックとリストを分割**して検索 $O(1)$ とマルチコア並列性を確保します。

#### (2) LRU キャッシュの「シーケンシャルスキャン汚染」と 2Q / Active-Inactive リスト

LRU（最も長く使われていないものを追い出す）は時間的局所性に対して非常に優れた置換アルゴリズムですが、**「巨大なファイルを1回だけ先頭から末尾まで連続読み出し（バックアップや `grep -r` 等）する」**ワークロードに極端に弱いという有名な弱点があります（**シーケンシャルスキャン汚染：Scan Resistance の欠如**）。

たとえばキャッシュ容量が $4\text{ GiB}$ のマシンで、よく使う重要なデータベース索引（$1\text{ GiB}$）がキャッシュに温まっていたとします。そこへ $10\text{ GiB}$ のバックアップファイルを1回だけ読み込むと、二度と使われないバックアップのデータが次々と MRU 端へ押し込まれ、**大切な $1\text{ GiB}$ の索引データがすべて LRU 端からキャッシュ外へ追い出されてしまいます**。

この限界に対する Linux ページキャッシュや DBMS の補正が、キャッシュを「**Inactive（まだ1回しか参照されていない候補リスト）**」と「**Active（2回以上参照されて定着したホットリスト）**」の2本に分ける **2Q / Active-Inactive リスト（あるいは ARC）** です。1回限りのスキャンデータは Inactive リストを素通りしてすぐ追い出され、Active リストに昇格した本当に熱いデータ群を汚染から守ります。

#### (3) ライトバック（遅延書き戻し）とクラッシュ時の不整合（次節への動機）

バッファキャッシュ上でブロックを書き換えたとき、毎回即座にディスクへ書き込む（ライトスルー）と遅いため、実用OSはダーティなブロックをメモリ上に溜めて後でまとめて書き戻す（**ライトバック / 遅延書き戻し**）ことで高い性能を出します。

ところが、ファイルの作成や削除といった操作は、実は **複数のディスクブロックへの書き換え**（例：①空きビットマップの更新、②i-node の更新、③親ディレクトリへのエントリ追加）の組み合わせで成り立っています。もしこの3つの書き込みのうち**2つ目までがディスクへ書かれた直後に停電（クラッシュ）**が起きると、「空きビットマップ上は使用中になっているのに、どのディレクトリからも指されていない迷子ブロック」や「中身がゴミのままディレクトリに登録された破損ファイル」が生まれ、ファイルシステム全体が壊れてしまいます。この深刻な問題を解決するのが、次節（[5-6節](5-6.md)）で学ぶ **ジャーナリング（ログとクラッシュリカバリ）** です。
