### 前節（5-1）の確認問題の解答

前節の最後に提示した3つの問いの解答を確認します。問3の抽象化設計がそのまま本節（ファイル抽象とバッファリング）の導入になります。

1. **10 Gbps 環境における割り込みライブロックの定量評価と対策比較：**

    * **(a) 割り込み処理上限と起きる現象：**
        1秒（$10^6\ \mu\text{s}$）あたり1回の割り込みに $2\ \mu\text{s}$ かかるため、1コアが処理できる割り込み回数の上限は

        $$
        \frac{10^6\ \mu\text{s}}{2\ \mu\text{s}} = \mathbf{500{,}000\text{ 回/秒（50万回/秒）}}
        $$

        です。到着率（約 $1{,}488$ 万パケット/秒）は処理上限の約 $30$ 倍（約 $29.8$ 倍）に達するため、CPU時間のほぼ $100\%$ が割り込みの入口・出口処理だけで埋め尽くされ、アプリケーションがほとんど進まない **割り込みライブロック（割り込みストーム）** に陥ります。

    * **(b) 割り込み結合（Coalescing）とハイブリッド制御（NAPI）の比較：**

        * **割り込み結合（割り込み合体）：** NIC 側で一定パケット数または一定タイマ時間が経過するまで割り込みを1回にまとめます。高負荷時の割り込み回数を減らせる一方で、低負荷時に1パケットだけ到着した場面でもタイマ満了まで待たされるため応答遅延（レイテンシ）が悪化しやすいトレードオフがあります。
        * **ハイブリッド制御（NAPI 等）：** 平常時は通常の割り込み駆動で最初の1パケットを即座に処理するため低負荷時の遅延が小さく、割り込み直後に NIC 割り込みを一時マスクしてポーリングへ切り替え、リングバッファに溜まった複数パケットをバッチ処理で吸い上げたのち割り込みへ戻ります。低負荷時の低遅延と高負荷時の高スループットを両立できます。

2. **VirtIO ディスクドライバと MMIO・PLIC の 3 バグ診断：**

    * **(a) `__sync_synchronize()`（メモリバリア）の削除：**
        CPU のアウトオブオーダ実行やストアバッファの影響で、MMIO の `QUEUE_NOTIFY` 書き込みが RAM 上の `desc[]` や `avail` リングへの書き込みより先にデバイス側へ観測され得ます。その結果、VirtIO デバイスが未初期化または古いディスクリプタ内容を読み出して誤ったセクタ・物理アドレスへ DMA 転送を行ってしまいます。

    * **(b) MMIO 領域をキャッシュ有効メモリのままにした場合：**
        状態レジスタの読み込みが CPU キャッシュ上の古い値にヒットし続けるため、UART ポーリングループ等がハードウェアの状態変化を検知できずに無限ループへ陥ります。また、制御レジスタへの書き込みがライトバックキャッシュに滞留し、デバイスへコマンドが即座に届かなくなります。

    * **(c) `plic_complete(irq)` の呼び忘れ：**
        PLIC が「その `irq` の割り込み処理がまだ進行中である」とみなし続けるため、同じデバイスからの2回目以降の割り込みが CPU コアへ配送されなくなります。結果として、次のディスク I/O 要求を出したプロセスが `sleep()` したまま永久に起床できなくなります。

3. **キャラクタデバイスとブロックデバイスの対比と抽象化設計（本節への接続）：**

    * **(a) ハードウェア制御の違い：**

        * **UART（キャラクタデバイス）：** 1バイト（文字）単位の逐次ストリームであり、過去の位置へ戻るランダムアクセスはできません。転送量が小さいためポーリングや1文字単位の割り込みで制御します。
        * **VirtIO ディスク（ブロックデバイス）：** セクタ／ブロック（$512\text{ B}$〜$4\text{ KiB}$）単位の転送であり、任意のセクタ番号へのランダムアクセスが可能です。大量データ転送の CPU 負荷を避けるため、DMA と共有リングバッファ（ディスクリプタ・Available/Used リング）で非同期に処理します。

    * **(b) OS カーネル側に必要な抽象化：**
        デバイス固有の制御手順を隠蔽し、すべての対象を「順序付きバイト列の読み書き」という共通インターフェースで扱えるよう、プロセス側の識別子からデバイスドライバの関数ポインタ表へ動的に振り分ける間接参照層（本節で学ぶ **ファイル記述子テーブル・`struct file`・`devsw[]`**）が必要になります。

## 5-2. ファイル抽象・低レベルI/Oと標準I/Oライブラリのバッファリング

### 1. 動機（Why）：なぜ多様なデバイスを「ただのバイト列」へ統一し、なぜ2段階でバッファリングするのか

前節（[5-1節](5-1.md)）で見た通り、ハードウェアの最下層にあるデバイスは実に多様です。UART は1文字ずつレジスタへ書き込む文字型デバイスであり、VirtIO ディスクはセクタ単位でリングバッファへDMA要求を積むブロック型デバイスです。

もしアプリケーションが「画面へ出すときは UART 専用命令」「ファイルへ書くときはディスク専用命令」と個別に呼び分ける設計だったとしたら、プログラムの再利用性は失われ、[3-2節](../3/3-2.md)で見たシェルのリダイレクト（`ls > out.txt`：画面出力をそのままファイルへ切り替える仕組み）も実現できません。

そこでUNIX系OSが掲げた中核的な設計哲学が **「Everything is a File（すべてはファイルである）」** です。ディスク上の通常ファイルも、キーボード・画面も、プロセス間通信のパイプも、すべて**「開いて（`open`）、バイト列を読み書きし（`read`/`write`）、閉じる（`close`）」**という共通のインターフェースへ統一します。

ところが、この統一システムコール（低レベルI/O）をそのまま直接呼び出すと、もう1つの現実的な壁にぶつかります。[3-1節](../3/3-1.md)で確認した通り、システムコール1回には特権モード切替やレジスタ退避という重いオーバーヘッドがかかります。もしプログラムが1文字出力するたびに毎回 `write(1, &c, 1)` を呼んでいたら、処理時間の大半がモード切替で消えてしまいます。

本節では、多様なI/Oを1つの抽象へ束ねるカーネル内の **3層ファイル管理構造** と、低レベルI/Oシステムコールの仕様を押さえたうえで、システムコール回数を大幅に減らすユーザ空間の **標準I/Oライブラリ（`stdio`）のバッファリング** の仕組みと落とし穴を整理します。

---

### 2. 具体例と動作イメージ（Toy Model）

データ構造の整理に入る前に、2つの小さな実験で「バッファリングの効果」と「カーネル内のオフセット共有」を確かめます。

#### 実験A：$1\text{ MiB}$ を1バイトずつ書くときのシステムコール回数（`write` vs `fputc`）

$1\text{ MiB}$（$1{,}048{,}576$ バイト）のデータを、ループで1バイトずつファイルへ書き出す2つのCコードを比べてみます。

```c
// パターン1：低レベルI/O（システムコールを毎回直接呼ぶ）
for (int i = 0; i < 1048576; i++) {
    write(fd, &c, 1);           // 毎回 ecall / syscall でカーネルへ遷移する
}

// パターン2：標準I/Oライブラリ（ユーザ空間バッファ 4 KiB を経由）
for (int i = 0; i < 1048576; i++) {
    fputc(c, fp);               // 通常はユーザ空間配列へ1バイト書くだけ
}
```

* **パターン1（低レベル `write`）：** システムコールの発行回数はちょうど **1,048,576 回** です。仮に1回のシステムコールに $0.5\ \mu\text{s}$ かかるとすると、純粋なモード切替だけで **約 $0.52\text{ 秒}$** を消費します。
* **パターン2（標準I/O `fputc`）：** `fputc` はユーザ空間に用意された $4\text{ KiB}$（$4{,}096\text{ B}$）のバッファ配列へ1バイトずつ書き込み、バッファが満杯になった瞬間だけまとめて `write(fd, buf, 4096)` を1回呼びます。システムコールの発行回数は

    $$
    \frac{1{,}048{,}576}{4{,}096} = \mathbf{256\text{ 回}}
    $$

    となり、**システムコール回数が 4,096 分の 1**（モード切替の合計時間は約 $0.13\text{ ミリ秒}$）まで大幅に削減されます。

#### 実験B：`fork()` 後に親と子が同じファイルへ書き込むと「上書きせず追記になる」理由

次に、親プロセスがファイル `log.txt` を開いてから `fork()` し、親が `"AA"`、子が `"BB"` をそれぞれ `write()` で書き込むプログラムを考えます。

```c
int fd = open("log.txt", O_WRONLY | O_CREAT | O_TRUNC, 0644);
if (fork() == 0) {
    write(fd, "BB", 2);   // 子プロセス
} else {
    write(fd, "AA", 2);   // 親プロセス
}
```

このプログラムを実行すると、ファイルの中身は（スケジューリング順に応じて）`"AABB"` または `"BBAA"` のどちらか4バイトになり、**後から書いた側が先頭オフセット `0` を上書きして `"AA"` や `"BB"` の2バイトだけに潰れてしまうことはありません**。

なぜ親と子の書き込み位置（ファイルオフセット）が自動的に連動しているのでしょうか。もしオフセットが「各プロセスのFDテーブルの中」に直接保存されていたら、`fork()` でコピーされた瞬間に親も子も独立した `off = 0` を持つことになり、互いに先頭を上書きし合ってしまうはずです。そうならない理由は、カーネル内部に **プロセス間で共有される「オープンファイルテーブル」という中間層** が挟まっており、さらに個々の `read()` / `write()` の内部でオフセット更新がカーネルのロックによって排他保護されているからです。なお、単一の `read()` や `write()` の内部更新は保護される一方で、**`lseek()` と `read()`（または `write()`）を2回のシステムコールに分けて呼ぶ場合**には、2呼び出しのあいだに別プロセス・別スレッドがオフセットを動かしてしまう **TOCTOU 競合** が起き得ます（対策は 4-(2) で整理します）。

### 3. 構造・アルゴリズム・実装（What）

#### (1) カーネル内の3層ファイル管理構造（FDテーブル・オープンファイル・実体）

UNIX系OS（Linux および xv6 モデル）は、開かれたファイルを次の **3層の間接参照構造** で管理しています（図5-2-1）。

1. **第1層：プロセスごとのファイル記述子テーブル（`p->ofile[]`）**
    各プロセスのPCB（[3-2節](../3/3-2.md)）が持つポインタ配列です。配列の添字 `0, 1, 2, 3, ...` がユーザ空間から見える **ファイル記述子（FD：File Descriptor）** という小さな非負整数です（慣習として `0`＝標準入力、`1`＝標準出力、`2`＝標準エラー出力）。

2. **第2層：カーネル共通のオープンファイルテーブル（`struct file`）**
    `open()` システムコールを1回呼ぶたびにカーネル内へ1個作られる構造体です。ここには次の情報が収められます。

    * `type`：対象の種類（通常ファイル `FD_INODE`、デバイス `FD_DEVICE`、パイプ `FD_PIPE` 等）を保持します。
    * `readable` / `writable`：読み書きの許可フラグです。
    * **`off`（現在オフセット）：** 次に読み書きするバイト位置を保持します。
    * **`ref`（参照カウント）：** この `struct file` を指しているFDの総数です。`close()` のたびに1減り、`0` になった瞬間に解放されます。

3. **第3層：ファイル・デバイスの実体**

    * 通常ファイルならファイルシステムの管理構造体（i-node：[5-4節](5-4.md)）を指します。
    * デバイスならデバイスドライバの関数ポインタ表 **`devsw[major]`**（例：`devsw[CONSOLE].read = consoleread`、`devsw[CONSOLE].write = consolewrite`）を指します。

この3層構造によって、実験Bの仕組みと「すべてはファイル」のポリモーフィズムが同時に説明できます。

* **`fork()` や `dup()`：** 同じ `struct file` へのポインタを複製し、`ref` を $+1$ するだけなので、親と子で現在オフセット `off` が自然に共有されます。
* **別々に `open()` した場合：** たとえ同じ `log.txt` であっても、2つの独立した `struct file`（別々の `off`）が作られるため、プロセスAが先頭を読んでいる間にプロセスBが末尾を読むといった独立アクセスが可能です。
* **デバイスごとの振り分け（ディスパッチ）：** ユーザが `write(fd, buf, n)` を呼ぶと、カーネルの `filewrite(f, buf, n)` は `f->type` を調べ、`FD_DEVICE` なら `devsw[f->major].write()`（[5-1節](5-1.md)の UART ドライバ等）、`FD_INODE` ならファイルシステムへの書込み、`FD_PIPE` ならパイプへの書込みへと自動的に振り分けます。

#### (2) 低レベルI/Oシステムコールと「ショートカウント（部分読書き）」

POSIX の低レベルI/O（非バッファI/O）を構成する基本システムコールは、次の6つです。

* `int open(const char *path, int flags, mode_t mode)`：ファイルを開き、空いている最小のFD番号を返します。
* `ssize_t read(int fd, void *buf, size_t count)`：最大 `count` バイトを `buf` へ読み込み、実際に読んだバイト数（EOFなら `0`、エラーなら `-1`）を返します（`ssize_t` は符号付きサイズ型であり、エラー時の `-1` を表現するために符号なしの `size_t` ではなく符号付き型が使われます）。
* `ssize_t write(int fd, const void *buf, size_t count)`：最大 `count` バイトを書き込み、実際に書いたバイト数を返します。
* `off_t lseek(int fd, off_t offset, int whence)`：現在オフセット `off` を任意位置へ移動します。
* `int close(int fd)`：自プロセスのFDスロットを解放し、`struct file` の `ref` を $-1$ します。
* `int dup(int oldfd)` / `dup2(int oldfd, int newfd)`：同じ `struct file` を指す別名のFDを作ります（`dup2` は `newfd` がすでに開いていれば先に閉じてから複製します。リダイレクトやパイプ接続の要です）。

ここで実務上重要な仕様が、**ショートカウント（Short Count：要求より少ないバイト数での正常復帰）** と **シグナル割り込み（`EINTR`：[4-7節](../4/4-7.md)）** の区別です。たとえば `read(fd, buf, 1000)` を呼んだとき、ファイル末尾付近であったり、端末やパイプ・ネットワークソケットに今ちょうど 120 バイトしか届いていなかったりすると、`read()` はエラーにせず **`120`** を返します。また、ブロック中に非同期シグナルの割り込みを受けた場合の挙動は進捗によって分かれます。**1バイトも読み込む前にシグナルを受けた場合は `-1` を返して `errno = EINTR` を設定**しますが、**途中まで（例：120バイト）読み込んだ後にシグナルを受けた場合はエラーにせず「読めた分だけのショートカウント（`120`）」を返します**。したがって、低レベルI/Oで確実に `n` バイトを読み書きするには、`-1` かつ `errno == EINTR` ならリトライし、正の値が返れば進捗を加算しながら残りバイト数が `0` になるまで `while` ループで繰り返すラッパー関数（`read_all` / `write_all`）を書くのが定石です。

#### (3) 標準I/Oライブラリ（`stdio`）と3つのバッファリングモード

実験Aで確認した通り、低レベルI/Oを直接使うとシステムコール回数の増加やショートカウント処理の煩雑さが負担になります。これを解決するのが、C言語の標準ライブラリ（`<stdio.h>`）がユーザ空間に提供する **標準I/O（`FILE *`, `fopen`, `fread`, `fwrite`, `printf`, `fgets`, `fflush`, `fclose`）** です。

`FILE` 構造体の正体は、カーネルのFD番号 `fd` に加えて、ユーザ空間のヒープ上に確保された **バッファ配列（通常 $4\text{ KiB} \sim 8\text{ KiB}$）**、現在の読み書きポインタ、残りバイト数、エラー／EOFフラグをまとめたユーザ空間の構造体です。

`stdio` は出力先の性質に応じて、次の **3種類のバッファリングモード** を自動的に使い分けます（`setvbuf()` で明示変更も可能です）。

| バッファリングモード | いつ `write()` システムコールを発行するか | デフォルトの対象 |
| :--- | :--- | :--- |
| **完全バッファリング**（`_IOFBF`） | バッファが満杯になったとき、または `fflush()` / `fclose()` / 正常 `exit()` 時 | ディスク上の通常ファイル、リダイレクトされた `stdout` |
| **行バッファリング**（`_IOLBF`） | **改行文字 `\n`** が出力されたとき、またはバッファ満杯・フラッシュ時 | 端末（ターミナル）に繋がっている `stdout` |
| **無バッファリング**（`_IONBF`） | バッファに溜めず、**即座に** `write()` を発行する | **`stderr`（標準エラー出力）** |

`stderr` だけが無バッファリングに設定されている理由は明快です。プログラムがエラーメッセージを出力した直後にクラッシュ（`SIGSEGV` 等）したとき、もしメッセージがユーザ空間のバッファに溜まったまま消えてしまったら、原因究明の手掛かりを失ってしまうからです。

> **【コラム：なぜ `printf("hello\n")` の直後に `fork()` すると `"hello"` が2回出力されることがあるのか】**
>
> C言語の有名な落とし穴に、次のわずか3行のプログラムがあります。
>
> ```c
> int main(void) {
>     printf("hello\n");   // 端末では行バッファ、ファイル出力では完全バッファ
>     fork();
>     return 0;
> }
> ```
>
> このプログラムを端末上でそのまま `./a.out` と実行すると、`hello` は **1回** だけ表示されます。ところが、出力をファイルへリダイレクトして `./a.out > out.txt` と実行すると、`out.txt` の中には **`hello` が2行（2回）** 書き込まれます（図5-2-3）。
>
> 理由は、標準I/Oのバッファリングモードの切替と `fork()` の仕様にあります。
>
> 1. 端末へ繋いだときは**行バッファリング**のため、`printf("hello\n")` の `\n` を見た瞬間に `fork()` より前に `write()` で出力が完了し、バッファは空になります。
> 2. しかしファイルへリダイレクトした瞬間、`stdout` は**完全バッファリング**へ切り替わります。そのため `printf("hello\n")` の直後、`"hello\n"` はまだ `write()` されず、**親プロセスのユーザ空間の `stdio` バッファの中に溜まったまま**です。
> 3. その状態で `fork()` を呼ぶと、**ユーザ空間のメモリ（未出力の `stdio` バッファごと）が子プロセスへ丸ごと複製**されます。そして `main` から `return 0`（＝`exit(0)`）するときに、親と子の両方が自分のバッファに残っていた `"hello\n"` をそれぞれ `write()` してしまい、2回出力されるのです。
>
> この事故を防ぐ実務上の基本原則は2つです。第1に、**`fork()` を呼ぶ直前に `fflush(stdout)`（または `fflush(NULL)`）でバッファを空にしておく**こと（あるいは低レベル `write()` を直接使うこと）です。第2に、子プロセスが `exec()` に失敗して終了するときは、親の未出力バッファを二重フラッシュしないよう `exit()` ではなく **`_exit()`**（[4-7節](../4/4-7.md)）を使うことです。

### 4. 限界と補正（Critique & Adaptation）

#### (1) `fflush()` と `fsync()` の混同、および2重バッファリングのバイパス

図5-2-2に示した通り、通常のファイル書き込みには「ユーザ空間の `stdio` バッファ」と「カーネル空間のページキャッシュ／バッファキャッシュ（[5-5節](5-5.md)）」の **2重のバッファ** が存在します。

* **`fflush(fp)`：** ユーザ空間のバッファを `write()` システムコールでカーネルへ渡すだけです。直後に電源が落ちると、カーネルのRAM上に留まっていたデータは**消失**します。
* **`fsync(fd)`：** カーネルのページキャッシュにある未書き戻し（ダーティ）データを、物理ディスク（SSD/HDD）の不揮発性媒体へ確実に書き出させて完了を待ちます。

データベースやファイルシステムのジャーナル（[5-6](5-6.md)・[9-8節](../9/9-8.md)）のように停電時もデータを失えないシステムでは、`fflush`（または `write`）の後に必ず **`fsync()`** を呼びます。また、DBMS自身がメモリ上に巨大な専用バッファプールを管理している場合は、OSのページキャッシュとデータが2重にRAMへ載る無駄とコピーコストを避けるため、カーネルキャッシュを素通りしてディスクとユーザ空間メモリを直接DMA転送する **`O_DIRECT`** フラグ（図5-2-2下部の破線経路、あるいは[3-7節](../3/3-7.md)の `mmap`）を補正として用います。ただし `O_DIRECT` を利用する場合は、ユーザ空間バッファの先頭アドレス・ファイルオフセット・転送サイズのすべてをディスクのセクタサイズ（例：$512\text{ B}$ や $4\text{ KiB}$）の整数倍に揃える**アライメント制約**があるほか、OSのキャッシュを飛ばしても**ディスク機器自身に内蔵された揮発性の書き込みキャッシュを不揮発媒体へフラッシュするために依然として `fsync()` 等が必要**である点に注意が必要です。

#### (2) `lseek` ＋ `read`/`write` の非アトミック性と `pread` / `pwrite`・`O_APPEND`

複数のスレッド（あるいは `fork` 後の親子）が同じ `struct file`（オフセット `off`）を共有しているとき、あるスレッドが「`lseek(fd, 100, SEEK_SET)` → `read(fd, buf, 50)`」を実行しようとすると、[4-1節](../4/4-1.md)で見た **TOCTOU 競合状態** が起きます。`lseek` で `off = 100` に合わせた直後、`read` を呼ぶ前に別スレッドが `lseek(fd, 500, SEEK_SET)` でオフセットを動かすと、意図しない位置を読んでしまうのです。

これに対するPOSIXの補正が次の2つです。

1. **`pread(fd, buf, count, offset)` / `pwrite(fd, buf, count, offset)`：** オフセット位置の指定と読み書きを**1回のシステムコールで不可分に実行**し、しかも共有されている現在オフセット `off` を動かしません。マルチスレッドで同じファイルを並列ランダムアクセスするDBMS等に不可欠です。
2. **`O_APPEND` フラグ：** `open()` 時に `O_APPEND` を指定しておくと、毎回の `write()` の内部でカーネルがロックを握ったまま「現在のファイル末尾へ移動＋書き込み」を不可分に行うため、複数プロセスが同時に1つのログファイルへ追記しても互いに上書きし合うことがありません。

#### (3) 「すべてはファイル」抽象化の限界と `ioctl`

「すべてはバイト列」という統一抽象化は強力ですが、すべてのデバイス操作が `read` / `write` に収まるわけではありません。たとえばシリアル端末（UART）の通信速度（ボーレート）を変更する、ターミナルの画面の行数・列数を取得する、CD-ROMトレイを開ける、といった**制御操作（メタ操作）**は、単純なバイト列の読み書きには当てはまりません。

この限界に対するUNIXの補正が、デバイス固有の制御コマンドを送るための汎用システムコール **`ioctl(int fd, unsigned long request, ...)`（I/O Control）** です。統一された `read`/`write` の一貫した抽象化を保ちつつ、どうしても収まらないデバイス固有機能だけを `ioctl` という1つの専用口へ逃がすことで、全体のシンプルさと実用性を両立させています。

>         printf("A");
>         write(1, "B", 1);
>         printf("C\n");
>         ```
>
>     * (b) マルチスレッドで同じファイル記述子 `fd`（同一の `struct file`）を共有しているとき、スレッドごとに `lseek(fd, offset, SEEK_SET)` → `read(fd, buf, len)`（または `write`）を実行する設計にはどのような競合バグ（TOCTOU）が起きるでしょうか。また、「任意位置への並列読み書き」と「ファイル末尾への安全な追記」のそれぞれについて、適切な POSIX の解決策を答えてください。
>
> 2. **（ショートカウントと `EINTR` を誤認する素朴な `read()` コードの診断と修正）**

>
>     ```c
>     char buf[1000];
>     ssize_t n = read(fd, buf, 1000);
>     if (n < 0) { /* エラー処理 */ }
>     process_1000_bytes(buf);
>     ```
>
>     * (a) 到着データが分割されていた場合（ショートカウント）およびブロック中に非同期シグナルの割り込みを受けた場合（`EINTR`）に、このコードがそれぞれどのように誤動作するか説明してください（1 バイトも読む前にシグナルを受けた場合と、途中まで読んだ後に受けた場合の違いも区別してください）。

>
> 3. **（`dup2` と `close` 連続操作後の FD テーブルと参照カウントのトレース）**

>
>     ```c
>     int fd1 = open("a.txt", O_RDWR);   // FD 3 を取得
>     int fd2 = open("b.txt", O_RDWR);   // FD 4 を取得
>     dup2(fd1, 1);                      // 操作①
>     dup2(fd2, fd1);                    // 操作②
>     close(fd2);                        // 操作③
>     ```
