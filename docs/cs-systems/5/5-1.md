### 前節（4-7）の確認問題の解答

前節の最後に提示した3つの問いの解答を確認します。これで[第4部](../index.md#part-4)（並行性制御と同期）が完結し、本節からは CPU と主記憶の外側へ広がる[第5部](../index.md#part-5)（I/O・ファイルシステム・IPCとシステム保護）へ進みます。

1. **シグナルハンドラのコードレビュー（3つの危険なバグと修正方針）：**

    * **① 共有フラグ `int stop_flag = 0;`：** `volatile` と `sig_atomic_t` が付いていません。メインループ側の `while (!stop_flag)` がコンパイラ最適化でレジスタへ固定されて無限ループ化したり、アーキテクチャによっては読み書きが途中で分断されたりする危険があります。**`static volatile sig_atomic_t stop_flag = 0;`** へ修正します。
    * **② `printf("Shutting down...\n");`：** `printf` は `stdout` の内部ミューテックスや共有バッファを使う非同期シグナル非安全関数です。メイン処理の `printf` 実行中に `SIGINT` が割り込むと、同一スレッド上でロックを待ち合う**自己デッドロック**やバッファ破損を起こします。ハンドラ内ではフラグを立てるだけにとどめ（即時出力がどうしても必要なら非同期シグナル安全な `write()` を使い）、ログ出力はメインループ側へ移します。
    * **③ `exit(1);`：** `exit()` は終了時に `stdio` バッファのフラッシュや `atexit` 登録関数を呼び出すため非同期シグナル非安全です。ハンドラから即時終了したい場合はカーネルへ直接終了を依頼する **`_exit(1)`** を使うか、通常はフラグだけ立ててメインループ側で安全に後片付けを行ってから終了します。

2. **安全な `SIGCHLD` ハンドラと `volatile sig_atomic_t` の落とし穴：**

    * **(a) `while (waitpid(-1, NULL, WNOHANG) > 0)` と `errno` 退避・復元を省いた場合の不具合：**
        標準の POSIX シグナルは 1 ビットの `pending` フラグで管理されるため、ハンドラ実行中やブロック中に複数の子プロセスが同時終了すると複数の `SIGCHLD` が 1 回分に結合（Coalesce）されます。`while` ループを省くと 2 人目以降の子プロセスが回収されずゾンビのまま残ります。また、`errno` の退避・復元を省くと、メイン処理のシステムコールが失敗して `errno` を検査する直前にハンドラが割り込んだ際、ハンドラ内の `waitpid()` が `errno`（例：`ECHILD`）を上書きしてメイン側のエラー判定を壊してしまいます。

    * **(b) `volatile sig_atomic_t child_count` に対する `child_count++` / `child_count--` の安全性：**
        **安全ではありません。** `volatile sig_atomic_t` が保証するのは単一スレッドとハンドラ間の「単純な代入・読出し」のみであり、`child_count++` と `child_count--` は[4-1節](../4/4-1.md)の通り「読出し→加減算→書戻し」の3ステップ（RMW）に分解されます。メイン側が `child_count` を読み出した直後・書き戻す前に `SIGCHLD` が割り込んで `child_count--` を実行すると、メイン側の書戻しでデクリメントが上書き消失します。修正するには、メイン側で `child_count++`（および関連ジョブ表の更新）を行う区間を **`sigprocmask(SIG_BLOCK, ...)` / `SIG_SETMASK`** で囲んで `SIGCHLD` の配送を一時ブロックします。

3. **マルチスレッドサーバにおける安全な `SIGTERM` 終了設計：**

    * **非同期シグナルハンドラ方式が不適切な2つの理由：** ① プロセス宛ての `SIGTERM` はブロックしていない**どのスレッドへ配送されるか不定**であり、割り込まれたスレッドが保持中のミューテックスや `stdout` ロックと自己デッドロックする危険があるためです。② ハンドラ内からは `printf` や通常のミューテックス・条件変数といった非同期シグナル非安全関数を安全に呼べず、複数ワーカーへのクリーンな終了通知とログ出力が困難なためです。
    * **安全な設計（`sigwait` 専用スレッドパターン）：** ① `main()` の冒頭で**ワーカースレッドを1本も生成する前**に `pthread_sigmask(SIG_BLOCK, &set, NULL)` で `SIGTERM` をブロックし、生成される全4本のワーカースレッドへブロック設定を継承させます。② シグナル処理専用の1スレッドを起動し、`sigwait(&set, &sig)` で同期的に `SIGTERM` を待ち受けます。③ `sigwait()` から戻った専用スレッドは非同期割り込み文脈ではないため、通常のミューテックス・条件変数で全ワーカーへ安全に停止通知を送り、合流後に `printf` で統計ログを出力して終了できます。

## 5-1. I/Oの仕組み（MMIO・ポーリング・割り込み・DMA・PLIC・VirtIO）

### 1. 動機（Why）：CPUと主記憶の外側にある「遅くて多様なデバイス」をどう操るのか

[第3部](../index.md#part-3)と[第4部](../index.md#part-4)を通じて、CPUと主記憶（RAM）の上で複数のプロセスやスレッドを仮想化・同期する仕組みが揃いました。しかし、CPUとRAMだけで完結する計算機は、外から入力を受け取ることも、計算結果を画面へ表示することも、データを電源オフ後もディスクへ保存することもできません。

キーボード、ディスプレイ、SSD/HDD、ネットワークカード（NIC）といった **I/O デバイス（入出力機器）** をOSカーネルから制御するとき、次の3つの物理的な壁に直面します。

1. **インターフェースの多様さ：** シリアル端末（UART）、ディスク、ネットワーク機器はそれぞれ内部構造も制御手順も異なります。CPUからこれらへどうやってコマンドを送り、状態を読み取るのかという共通の接続方式が必要です。
2. **CPUとの桁違いの速度差：** [0-7節](../0/0-7.md)で確認した通り、CPUの1クロックは約 $0.3\text{〜}0.5\text{ ns}$ ですが、SSDのアクセスは数十マイクロ秒、HDDやキーボード入力はミリ秒〜秒のオーダーです。CPUがデバイスの完了を待ち続けたら、数百万〜数億サイクルもの計算能力が無駄になります。
3. **大量データ転送の負荷：** ディスクから $1\text{ MiB}$ のファイルを読み込むとき、CPUが `ld`/`sd` 命令で1ワードずつデバイスからRAMへ運び続けたら、その間CPUは他のプロセスをほとんど実行できません。

本節では、これら3つの壁を乗り越えるハードウェアとOSの協調機構として、**MMIO（Memory-Mapped I/O）**、**ポーリング vs 割り込み（と RISC-V の PLIC）**、**DMA（Direct Memory Access）**、そして xv6（RISC-V）のディスクドライバで使われる **VirtIO** のリングバッファ構造を順に整理します。

---

### 2. 具体例と動作イメージ（Toy Model）

全体構造の解説に入る前に、2つの小さな実験で「デバイスへの1文字出力」と「大量データ転送の2方式」の違いを確かめます。

#### 実験A：UART（シリアル端末）へ `'A'` を1文字出力する MMIO とポーリング

RISC-V（QEMU `virt` マシン上の xv6 モデル）では、画面・キーボードに繋がるシリアル通信装置 **UART（16550互換）** の制御レジスタ群が、物理アドレス **`0x10000000`** からの数バイトに割り当てられています（[3-8節](../3/3-8.md)の図3-8-2左端）。

* `0x10000000`（`THR`：送信保持レジスタ）：ここへ1バイト書き込むと、その文字が端末へ送信されます。
* `0x10000005`（`LSR`：ライン状態レジスタ）：第5ビット（`0x20`）が `1` なら「送信バッファが空で次の1文字を書ける」、`0` なら「前の文字をまだ送信中（ビジー）」であることを示します。

このとき、OSカーネルのC言語コードから端末へ文字 `'A'` を1文字送る処理は、**普通のメモリアクセスとまったく同じポインタ読み書き**として書けます。

```c
#define UART0 0x10000000L
#define Reg(offset) ((volatile unsigned char *)(UART0 + (offset)))

void uart_putc_sync(int c) {
    // 1. 送信可能（LSR の第5ビットが 1）になるまで待つ（ポーリング）
    while ((*Reg(5) & (1 << 5)) == 0)
        ;
    // 2. 送信レジスタへ1バイト書き込むと、ハードウェアが文字を出力する
    *Reg(0) = c;
}
```

ここで、**[2-7節](../2/2-7.md)で学んだ `volatile` の伏線がそのまま回収されます**。もし `volatile` を付け忘れて `-O2` でコンパイルすると、コンパイラは `*Reg(5)` が普通のメモリだとみなして `while` ループの外へ読み出しを追い出し、ハードウェアが送信完了しても永遠にループを抜けられなくなります。さらに、`volatile` はコンパイラの最適化を抑止するだけであるため、CPUキャッシュによる読み書きの吸収や並べ替えを防ぐには、OSが **MMIO 領域のページテーブル属性をキャッシュ無効（Uncacheable / Device メモリ）に設定しておくこと** も必須条件になります（キャッシュが有効なままだと、状態レジスタの読み込みがキャッシュ上の古い値を返し続けてしまいます）。

#### 実験B：ディスクから $4\text{ KiB}$ を読むときの「PIO（CPU手運び）」vs「DMA（専用回路へ委託）」

次に、ストレージ（ディスク）から $4\text{ KiB}$（$4{,}096$ バイト）のブロックを主記憶 RAM へ読み込む場面を比べてみます。

* **PIO（Programmed I/O：CPUが直接運ぶ方式）：**
    64ビット環境（RISC-V RV64 等）でCPUがデバイスのデータレジスタから8バイト（64ビット）ずつ `ld` で読み、RAMへ `sd` で書くループを $4{,}096 / 8 = 512$ 回繰り返します。転送中ずっとCPUコアが拘束され、もし $100\text{ MiB}$ 読み込めばCPU時間が大量に奪われます。

* **DMA（Direct Memory Access：専用回路へ任せる方式）：**
    CPUはディスク側の **DMAコントローラ** に対し、「セクタ番号 `10` の $4{,}096$ バイトを、物理RAMの `0x8010_0000` 番地へ転送せよ」という**わずか数十バイトの指示書（ディスクリプタ）**だけを渡して即座に手を離します。その後、CPUは別のユーザプロセスを自由に実行し、DMAコントローラが裏側でバス経由でRAMへ直接 $4{,}096$ バイトを運び終えた瞬間に**完了割り込みを1回だけ**CPUへ送ります。

### 3. 構造・アルゴリズム・実装（What）

#### (1) デバイスへのアクセス方式：MMIO（Memory-Mapped I/O）

CPUが外部デバイスの制御レジスタ（状態確認・コマンド発行・データ読み書き）へアクセスする方式には、歴史的に2種類あります。

1. **ポートマップド I/O（Port-Mapped I/O / 独立I/O空間）：** 通常のメモリ空間とは別にI/O専用のアドレス空間を設け、専用の機械語命令（x86の `in` / `out` 命令）でアクセスする方式です。
2. **メモリマップド I/O（MMIO：Memory-Mapped I/O）：** 実験Aのように、物理アドレス空間の一部を主記憶 RAM ではなく**各デバイスの制御レジスタ群へ割り当てる**方式です。

RISC-V や ARM は MMIO のみを採用しており、現代の x86-64 でも PCIe デバイス（NVMe SSD、GPU、高速NIC）の制御はほぼすべて MMIO で行われます。MMIO には次の2つの大きな利点があります。

* 専用のI/O命令が不要で、通常のロード／ストア命令（`ld`/`sd`）だけで任意のデバイスを操作できます。
* [3-5節](../3/3-5.md)の**ページテーブル（PTEの `U=0`）の保護機構をそのまま流用**し、「S-mode のOSカーネルだけがデバイス領域へアクセスでき、U-mode のアプリからはアクセスできない」隔離と、キャッシュ無効（Uncacheable / Device）属性の指定をハードウェアで自動強制できます。

CPUが発行した物理アドレスは、チップ内の**メモリコントローラ／インターコネクト（バス）**によって判定され、`0x80000000` 以降なら主記憶 DRAM へ、`0x10000000` なら UART チップへ、`0x10001000` なら VirtIO ディスクへと自動的に振り分けられます（図5-1-1左）。

#### (2) ポーリング vs 割り込み駆動 I/O と PLIC（割り込みコントローラ）

デバイスへコマンドを出したあと、処理完了を知る方法には **ポーリング（Polling）** と **割り込み駆動 I/O（Interrupt-Driven I/O）** の2つがあります。

* **ポーリング（実験A）：** CPUが `while` ループで状態レジスタを繰り返し読み続けて完了を待ちます。実装が単純で、数マイクロ秒以内で終わる高速デバイスやパニック時の緊急出力（`printf`）には有効ですが、低速なキーボードやディスクで使うとCPU時間を浪費します。
* **割り込み駆動 I/O：** CPUはコマンドを出したら即座に別プロセス（または `sleep`）へ移り、デバイス側が処理を終えた瞬間に電気信号（割り込み要求：IRQ）を送ってCPUのトラップハンドラ（[3-1](../3/3-1.md)・[3-6節](../3/3-6.md)）を呼び出します。

マルチコアCPUに多数のデバイス（UART、複数のディスク、NIC、USB等）が接続された環境で、どのデバイスからの割り込みをどのCPUコアへ届けるかを調停する専用ハードウェアが、RISC-V の **PLIC（Platform-Level Interrupt Controller：x86-64の APIC に相当）** です（図5-1-1右）。

xv6 のカーネルが PLIC 経由で外部割り込みを処理する手順は、次の4ステップの決まったプロトコルで進みます。

1. **起動時の設定（`plicinit` / `plicinithart`：[3-8節](../3/3-8.md)）：** 各デバイスの割り込み番号（例：UART = `10`、VirtIO ディスク = `1`）に優先度を設定し、各CPUコアの S-mode で受け取る割り込みを有効化します。
2. **割り込み発生と取得（`claim`）：** デバイスが PLIC へ信号を送ると、PLIC は割り込み受付可能なCPUコアの1つへ外部割り込み（`scause = 0x8000...0009`）を通知します。PLIC の `SCLAIM` レジスタは **CPUコア（RISC-V では hart）ごとに独立した MMIO アドレス**として用意されており、割り込みハンドラ `devintr()` は自コア用の `SCLAIM` レジスタを読むことで**「どの番号のデバイスが割り込みを起こしたか（`irq`）」**を取得します。この読み出しにより、他のCPUコアへ同じ割り込みが重複配送されるのを防ぎます。
3. **デバイスドライバの呼び出し：** `irq == UART0_IRQ` なら `uartintr()`、`irq == VIRTIO0_IRQ` なら `virtio_disk_intr()` を実行してデータ回収や `wakeup()` を行います。
4. **完了通知（`complete`）：** 処理が終わったら、取得した `irq` 番号を同じ自コア用の `SCLAIM` レジスタへ書き戻すことで、PLIC に「この割り込みの処理が完了したので、次の割り込みを受け付けてよい」と通知します。

#### (3) DMA（Direct Memory Access）のデータ転送フロー

実験Bで対比した **DMA（Direct Memory Access）** は、ディスクやNICのように一度に数 KiB〜数 MiB を転送する高速デバイスで不可欠な仕組みです（図5-1-2）。

DMAを用いたディスク読み込みは、次の4ステップで実行されます。

1. **CPUによる指示（MMIO）：** OSドライバが、読み込み元のディスクセクタ番号、転送先の**物理メモリアドレス**、転送バイト数をデバイス（DMAコントローラ）へ設定し、開始を通知します。
2. **CPUの解放（`sleep`）：** CPUは即座にI/O要求元プロセスを `SLEEPING` にし、別の `RUNNABLE` プロセスを実行します。
3. **DMAによる直接転送：** DMAコントローラがシステムバスの利用権を得て、CPUコアを一切経由せず、デバイスと主記憶 RAM のあいだで直接データを転送します。
4. **完了割り込みと起床（`wakeup`）：** 全バイトの転送が終わった時点で、DMAコントローラが PLIC 経由でCPUへ**1回だけ割り込み**を送ります。割り込みハンドラが待機中のプロセスを `wakeup` して完了します。

#### (4) 現代のリングバッファ型ドライバ：VirtIO ディスクの仕組み（xv6 モデル）

現実の高速ストレージ（NVMe）や仮想化環境（QEMU/KVM の標準インターフェース **VirtIO**）では、CPUとデバイスがRAM上の **共有リングバッファ（Virtqueue）** を介して複数のDMA要求をパイプライン状にやり取りします。

xv6 の VirtIO ディスクドライバ（`virtio_disk.c`）では、RAM上に次の3つのデータ構造を配置し、MMIOの通知レジスタ1つだけでデバイスと協調します（図5-1-3）。

1. **ディスクリプタテーブル（`desc[]`）：** DMA転送の1要素を表す配列です。各エントリに「物理アドレス `addr`」「バイト長 `len`」「方向フラグ（読込／書込）」「次のディスクリプタ番号 `next`」が入ります。ディスクの1回の読み書き要求は、①ヘッダ（読込か書込か＋セクタ番号）、②データバッファ本体（$1{,}024\text{ B}$ 等）、③ステータス結果1バイト（デバイスが成功時に `0` を書く）の **3つのディスクリプタを連結リスト状に繋いで** 1セットにします。
2. **Available リング（`avail`：ドライバ → デバイス）：** OSドライバが「新しく用意したリクエストの先頭ディスクリプタ番号」を書き込んでデバイスへ提出するリングです。
3. **Used リング（`used`：デバイス → ドライバ）：** デバイスがDMA転送を完了したリクエストの番号を書き戻すリングです。

`virtio_disk_rw(buf, write)` の実行フローは、[4-4節](../4/4-4.md)で学んだスピンロックと `sleep`/`wakeup` の代表的な実用例になっています（引数 `buf` はディスク1ブロック分のRAMバッファを管理するカーネル構造体 `struct buf` であり、詳細は[5-5節](5-5.md)で扱います）。

1. `acquire(&disk.vdisk_lock)` でドライバの排他ロックを獲得し、3個の空きディスクリプタを確保してヘッダ・データ・ステータスを設定します。
2. 先頭ディスクリプタ番号を `avail` リングへ追記し、`__sync_synchronize()`（メモリバリア：RAM上のディスクリプタが確実にデバイスから見えるようにする）を挟んでから、**MMIOの `QUEUE_NOTIFY` レジスタへ書き込んでデバイスを起動**します。
3. `buf->disk = 1;` として、`while (buf->disk == 1) sleep(buf, &disk.vdisk_lock);` で眠り、CPUを他プロセスへ譲ります（[4-4節](../4/4-4.md)で見た通り、`sleep()` は内部で `vdisk_lock` を一旦解放してから眠り、起床時に再獲得するため、`vdisk_lock` を保持したまま呼び出しても自己デッドロックは起きません）。
4. デバイスがDMA転送を終えて `used` リングへ結果を書き込み、PLIC 経由で割り込みを起こすと、`virtio_disk_intr()` が `disk.vdisk_lock` を獲得して `used` リングを確認し、`buf->disk = 0; wakeup(buf);` で要求元プロセスを起こします。

> **【コラム：割り込みコンテクストの制約と「トップハーフ／ボトムハーフ」分離】**
>
> [4-4節](../4/4-4.md)で確認した通り、外部割り込みで呼び出される**割り込みハンドラ（割り込みコンテクスト）**には厳しい制約があります。現在たまたまCPU上で動いていた無関係なプロセスの実行を横取りして走っているため、**割り込みハンドラの中で `sleep()` を呼んで眠ることは厳禁**であり、また割り込みを長時間禁止したまま重い処理をすると、タイマ割り込みや他デバイスの応答が取りこぼされてしまいます。
>
> そのため Linux などの実用OSでは、デバイス割り込みの処理を次の2段階へ分割する **トップハーフ（Top Half）／ボトムハーフ（Bottom Half）** 設計をとります。
>
> * **トップハーフ（ハードウェア割り込みハンドラ）：** 割り込み発生直後に即座に実行される最小限の処理です。デバイスの状態確認、受信データのキューへの退避、PLIC への完了通知など、数マイクロ秒で終わる緊急処理だけを行って即座に割り込みから抜けます。
> * **ボトムハーフ（遅延処理：SoftIRQ / Tasklet / Workqueue）：** トップハーフが終わって割り込みが再許可されたあとに、受信パケットのTCP/IPプロトコル解析やファイルシステムへの後処理といった重い処理を、通常のスケジューリングのもとで実行します。
>
> この2段階分離により、システム全体の応答性（割り込み遅延の最小化）と複雑なプロトコル処理の両立を実現しています。

### 4. 限界と補正（Critique & Adaptation）

#### (1) 高速デバイスにおける「割り込みストーム」とポーリングへの回帰（NAPI）

ここまでの議論では、「ポーリングはCPUの無駄で、割り込み駆動が常に優れている」ように見えました。ところが、**10 Gbps / 100 Gbps の高速ネットワークカード（NIC）や NVMe SSD** が普及した現代のサーバでは、この常識が逆転します。

たとえば 10 Gbps のイーサネット NIC に最小サイズのフレーム（プリアンブルやフレーム間隔を含め 84 バイト＝672 ビット）が連続到着する場合、到着率は **毎秒 1,000 万パケット以上（約 1,488 万パケット/秒、約 67.2 ナノ秒に 1 回）** に達します。もし1パケットごとに割り込みを発生させたら何が起きるでしょうか。1回の割り込み処理（トラップ遷移・レジスタ退避・PLIC操作・復帰）には数マイクロ秒かかるため、**CPU時間のほぼ 100% が割り込みの入口と出口の処理だけで埋め尽くされ、肝心のアプリケーションがほとんど進まない状態（割り込みライブロック／割り込みストーム）**に陥ります。

この限界に対する現代OSの補正は、次の2つの組み合わせです。

1. **割り込み結合（割り込み合体：Interrupt Coalescing）：** デバイス側でパケットが一定数（例：32個）溜まるか、一定時間（例：50マイクロ秒）経つまで割り込みを1回にまとめます。
2. **ハイブリッド制御（Linux の NAPI 等）：** 通信量が少ない平常時は**割り込み駆動**で省電力かつ低遅延に待機し、最初の1発目の割り込みが来たら**一時的にそのNICの割り込みをマスク（禁止）してポーリングへ切り替え**、リングバッファに溜まったパケットを一気にバッチ処理で吸い上げます。リングが空になったら再び割り込みを有効化して待機へ戻ります。さらに低遅延が求められる金融・通信分野では、OSカーネルの割り込み自体をバイパスしてユーザ空間から専用コアで常時ポーリングする **DPDK** や、ユーザ空間とカーネル空間の共有リングバッファでシステムコールや割り込みを省く Linux の非同期 I/O 機構 **`io_uring`（`IOPOLL` モード）** も活用されます。

#### (2) DMA の2つの落とし穴：キャッシュ一貫性と DMA 攻撃（IOMMU による補正）

DMAはCPUを介さず主記憶 RAM へ直接読み書きするため、次の2つの構造的な問題が生じます。

1. **CPUキャッシュとの不整合：** [0-7節](../0/0-7.md)で見た通り、CPUの書き込みはライトバック方式でL1/L2キャッシュに留まっていることがあります。もしCPUがDMAバッファへ書き込んだデータがまだRAMへ吐き出されていないのにデバイスがDMAでRAMを読めば古いデータが出てしまい、逆にデバイスがDMAでRAMへ新データを書いたのにCPUキャッシュに古い値が残っていればCPUが古い値を読んでしまいます。補正として、アーキテクチャがハードウェアでキャッシュコヒーレントなDMAを提供するか、OSドライバ側でDMAの前後に対象領域のキャッシュフラッシュ／無効化を実行します。
2. **DMA 攻撃と IOMMU による保護：** DMAコントローラは物理アドレスを直接指定してRAMのどこへでも読み書きできます。つまり、悪意ある（またはバグのある）PCIeデバイスやThunderbolt機器が接続されると、**CPUのページテーブル保護（[3-5節](../3/3-5.md)）を素通りしてOSカーネルの秘密メモリを盗み見たり書き換えたりできる（DMA攻撃）**リスクがあります。これに対する現代ハードウェアの補正が **IOMMU（I/O Memory Management Unit）** です。IOMMU は「デバイス専用のMMU・ページテーブル」としてバス上に置かれ、デバイスが発行するDMAアドレスを検証・変換することで、OSが許可したバッファ領域以外の物理RAMへのDMAアクセスをハードウェアで遮断します。

### 理解度チェック（次節へ進む前の確認）

本節の MMIO・PLIC・DMA・VirtIO・割り込みライブロック対策を確認し、次節（[5-2節](5-2.md)）へ繋ぐ問いを置きます。

> **【確認の問い】**
>
> 1. **（10 Gbps 環境における割り込みライブロックの定量評価と対策比較）**
>     10 Gbps イーサネット NIC に最小サイズのフレームが約 **$1{,}488$ 万パケット/秒**（約 $67.2\text{ ns}$ に 1 回）で連続到着しており、1 回の割り込み処理（トラップ遷移・レジスタ退避・PLIC 操作・復帰）に **$2\ \mu\text{s}$** かかるとします。
>
>     * (a) 「1 パケット＝1 割り込み」の純粋な割り込み駆動方式では、1 コアが 1 秒間に処理できる割り込み回数の上限は何回であり、到着率に対してどのような状態に陥るでしょうか（計算式と現象名を含めて答えてください）。
>     * (b) この問題に対する 2 つの対策である **割り込み結合（割り込み合体：Interrupt Coalescing）** と **ハイブリッド制御（Linux の NAPI 等）** について、それぞれの仕組みと、低負荷時の応答遅延（レイテンシ）および高負荷時の処理効率における違いを比較してください。
>
> 2. **（VirtIO ディスクドライバと MMIO・PLIC の 3 バグ診断）**
>     xv6 の VirtIO ディスクドライバおよび MMIO・PLIC の実装において、次の 3 つのバグをそれぞれ単独で混入させた場合、どのような誤動作や障害が起きるか原因とともに説明してください。
>
>     * (a) `avail` リングへの追記と `QUEUE_NOTIFY`（MMIO 書込）の間にある `__sync_synchronize()`（メモリバリア）を削除した。
>     * (b) UART や VirtIO の MMIO 物理アドレス領域に対して、ページテーブル属性をキャッシュ無効（Uncacheable / Device）にせず通常のキャッシュ有効メモリのままにした。
>     * (c) 外部割り込みハンドラ `devintr()` の末尾で `plic_complete(irq)` を呼び忘れた。
>
> 3. **（キャラクタデバイスとブロックデバイスの対比と抽象化設計）**
>     本節で扱った **UART（シリアル端末）** と **VirtIO ディスク** を例にとり、次の 2 点に答えてください。
>
>     * (a) データの転送単位、ランダムアクセスの可否、および典型的なデータ転送方式（ポーリング／1文字割り込み vs DMA＋共有リングバッファ）の観点から、両者のハードウェア制御の違いを整理してください。
>     * (b) このように制御手順が大きく異なる多様なデバイスを、アプリケーション側から共通の読み書き操作で扱えるようにするには、OS カーネルの側にどのような間接参照や抽象インターフェースの分離が必要になると考えられるでしょうか。
