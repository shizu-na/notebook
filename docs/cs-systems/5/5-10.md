### 前節（5-9）の確認問題の解答

前節の最後に提示した3つの問いの解答を確認します。本節では[第5部](../index.md#part-5)の締めくくりとして、[3-3節](../3/3-3.md)の OS スレッドと [5-3節](5-3.md)の `epoll` イベント駆動を 1 つに繋ぐ現代言語の非同期実行モデルへ進みます。

1. **サイクロマチック数 $V(G) = 4$ の計算・基本経路の列挙とスライシングの比較：**

    * **(a) $V(G) = 4$ の導出、4 本の基本経路、および分岐網羅との関係：**
        `classify()` の CFG の基本ブロックを `N1`（`r = 0; if (x > 0)`）、`N2`（`if (y > 0)`）、`N3`（`r = 1;`）、`N4`（`r = 2;`）、`N5`（`while (x > 10)`）、`N6`（`x -= 10;`）、`N7`（`return r;`）とすると、頂点数 $N = 7$、遷移辺は `N1→N2`, `N1→N5`, `N2→N3`, `N2→N4`, `N3→N5`, `N4→N5`, `N5→N6`, `N6→N5`, `N5→N7` の $E = 9$、連結成分数 $P = 1$ となります。したがって

        $$
        V(G) = E - N + 2P = 9 - 7 + 2 \times 1 = \mathbf{4}
        $$

        です（二値分岐 `x > 0`・`y > 0`・`x > 10` の 3 個 $+ 1 = 4$ と一致します）。線形独立な 4 本の基本経路の例は次の通りです。

        1. **経路 1（例：`x = 0, y = 0`）：** 分岐①偽・ループ 0 回（`N1 → N5 → N7`）
        2. **経路 2（例：`x = 5, y = 1`）：** 分岐①真・分岐②真・ループ 0 回（`N1 → N2 → N3 → N5 → N7`）
        3. **経路 3（例：`x = 5, y = 0`）：** 分岐①真・分岐②偽・ループ 0 回（`N1 → N2 → N4 → N5 → N7`）
        4. **経路 4（例：`x = 15, y = 1`）：** 分岐①真・分岐②真・ループ 1 回以上（`N1 → N2 → N3 → N5 → N6 → N5 → N7`）

        なお、$V(G) = 4$ は分岐網羅に必要な最小テストケース数の**上限**を与えます（実際、この関数では経路 1・経路 3・経路 4 の 3 本だけで全 9 辺［全分岐の真偽］を網羅できます）。

    * **(b) 後方スライス vs 前方スライスの役割と `classify()` のスライス：**
        **後方スライス**は注目点から依存辺を逆向きに辿って「その変数値へ影響し得る文」を抽出するデバッグ・原因調査に使い、**前方スライス**は順向きに辿って「その文の変更がどこまで波及するか」を調べる変更影響範囲の特定に使います。
        注目点 `(行6, r)` の後方スライスは `{行1, 行2, 行3, 行6}` であり、行 4〜5 の `while (x > 10) { x -= 10; }` は `r` への代入も行 1〜3 の実行制御も行わないため（データ依存も制御依存も繋がらないため）含まれません。また、`(行5, x)` の前方スライスは `{行4, 行5}` に閉じ、`r` や `return r;` には影響しないことが分かります。

2. **有界モデル検査（BMC）の有界性トレースと巻き戻しアサーションの役割：**

    * **(a) $k = 3$ と $k = 4$ における論理式と SMT ソルバの判定結果：**
        入口のパス制約は $0 \le n \le 3$、各ステップ $i$ の境界違反条件は $(i \le n) \land \neg(0 \le i < 3)$ です。

        * **$k = 3$（`i = 0, 1, 2` の 3 周分を展開）：**

            $$
            \Phi_{k=3}(n) \;\equiv\; (0 \le n \le 3) \;\land\; \bigvee_{i=0}^{2} \bigl((i \le n) \land \neg(0 \le i < 3)\bigr)
            $$

            $i = 0, 1, 2$ では常に $0 \le i < 3$ が真（違反条件が常に偽）となるため $\Phi_{k=3}(n)$ は恒偽となり、SMT ソルバは **`UNSAT`** を返します（4 周目に潜むバグを見逃します）。

        * **$k = 4$（`i = 0, 1, 2, 3` の 4 周分を展開）：**

            $$
            \Phi_{k=4}(n) \;\equiv\; (0 \le n \le 3) \;\land\; \bigvee_{i=0}^{3} \bigl((i \le n) \land \neg(0 \le i < 3)\bigr) \;\equiv\; (0 \le n \le 3) \;\land\; (3 \le n)
            $$

            $i = 3$ の項で $\neg(0 \le 3 < 3)$ が真となり $n = 3$ で充足されるため、SMT ソルバは **`SAT`** と判定し、反例 **`n = 3`（4 周目 `i = 3` で `a[3]` へ境界外書込）** を自動出力します。

    * **(b) 巻き戻しアサーション（Unwinding Assertion）の役割と $k = 3$ での判定：**
        巻き戻しアサーションは、展開上限 $k$ の末尾において「ループ継続条件が偽であること（上限 $k$ を超える反復が残っていないこと）」を自動検査します。本例で $k = 3$ とすると、3 周目（`i = 2`）終了後に次のループ継続条件 `3 <= n` が **`n = 3` で真**になるため、巻き戻しアサーションが違反（`SAT`）を報告し、「展開上限 $k = 3$ ではループを最後まで検証し切れておらず安全とは断言できない（$k$ を増やす必要がある）」ことを自動で警告します。

3. **大規模決済システムに対する階層的保証の設計：**

    * **① OS マイクロカーネル・隔離境界層：** コード規模が小さく、突破されるとシステム全体が陥落する最重要核であるため、高い人的コストをかけてでも **定理証明（Coq / Lean / Isabelle 等）** や厳密な **BMC** を集中投入し、メモリ安全性や隔離境界の不変条件を数学的に裏付けます（seL4 の設計思想）。
    * **② 暗号プリミティブ・並行プロトコル／トランザクション状態遷移層：** 稀な境界条件や並行インターリービングが致命的欠陥に直結するため、設計段階の状態遷移（安全性・活性）を **モデル検査（SPIN / TLA+）** で網羅検証し、具体的な実装の整数オーバーフローや境界バグを **SMT ベースの BMC（CBMC 等）** で自動探索します（重要な暗号核には定理証明も活用します）。
    * **③ 広大な業務 Web アプリケーション層：** 数百万行規模で仕様変更やリリース頻度が高いため、全体を定理証明・モデル検査するのは人的コストや状態爆発の面で非現実的です。したがって **メモリ安全言語** の採用を基本としつつ、CI パイプラインで **静的解析（サイクロマチック数監視・Linter）・ユニットテスト＋サニタイザ（ASan / TSan）・カバレッジ誘導型ファジング** を常時回し、本番環境では **実行時多層防御（[5-8節](5-8.md)の ASLR/PIE・NX・カナリア・最小権限サンドボックス）** を重ねて全体を守ります。

## 5-10. 非同期実行モデルとイベントループ（スレッド・コルーチン・M:Nスケジューリング）

### 1. 動機（Why）：なぜ OS スレッドだけでは数万〜数百万の並行タスクを捌けないのか

[3-3節](../3/3-3.md)で学んだ OS スレッド（カーネルスレッド）を使えば、プログラマはネットワーク通信やディスク I/O を普通の関数呼び出しのように上から下へ素直に記述できます。ところが、チャットサーバや API ゲートウェイのように**同時に 10 万本のクライアント接続を待ち受ける**現代のシステムでは、「1 接続 ＝ 1 OS スレッド」のモデルは 2 つの物理的な壁に突き当たります。

1. **メモリ消費の壁：**
    OS スレッドを 1 本作るたびに、ユーザ空間スタック（Linux 既定で仮想 $8\text{ MiB}$、実際に触ったページだけでも数十 $\text{KiB}$）に加えて、カーネル空間のスタック（$8\text{〜}16\text{ KiB}$）とスレッド管理構造体が消費されます。10 万接続を張るだけで数 $\text{GiB}$ 〜数十 $\text{GiB}$ のメモリがスレッド管理だけで消えてしまいます。

2. **カーネル遷移とコンテクストスイッチの壁：**
    OS スレッドが `read()` でブロックして別スレッドへ切り替わるたびに、システムコールによる特権モード遷移（[3-1節](../3/3-1.md)）、レジスタ退避、OS スケジューラの実行キュー操作が発生します。さらに多数のスレッドが交互に走ると CPU キャッシュと TLB が頻繁に汚染され、肝心の業務処理より切替コストの方が支配的になります。

一方で、[5-3節](5-3.md)で学んだ **`epoll` によるシングルスレッド・イベントループ** を使えば、1 本の OS スレッドだけで 10 万本のソケットを軽量に監視できます。しかし、生の `epoll` とノンブロッキング I/O で複雑な処理を書こうとすると、「リクエストを読む → DB へ問い合わせる → 外部 API を呼ぶ → 結果を返す」という 1 本の流れがバラバラの**コールバック関数**へ分断され、状態管理・ループ・エラー処理が非常に読みにくくなりバグの温床になります（**コールバック地獄**）。

この **「OS スレッドのような素直な逐次コードの書きやすさ」** と **「`epoll` イベントループの高い軽量性・高並列性」** を両立させるために現代のプログラミング言語とランタイムが生み出した仕組みが、**非同期実行モデル（コルーチン・`async/await`・M:N スケジューリング）** です。本節では、その内部構造を OS・コンパイラの知識と結びつけて解き明かします。

### 2. 具体例と動作イメージ（Toy Model）

ランタイムの全体構造に入る前に、2 つの小さな実験で「メモリの桁違いの差」と「`async/await` が裏側で何へ変換されているか」を確かめます。

#### 実験A：10 万本の同時待機タスクが消費するメモリ量の比較

10 万人のクライアントが WebSocket や HTTP Keep-Alive でサーバへ同時接続し、大半が次のメッセージ到着を待っている状況を想定します。

* **1:1 OS スレッドモデル（POSIX `pthread` 等）：**
    仮想スタックを最小限に抑えても、カーネルスタック $16\text{ KiB}$ ＋ ユーザスタック実使用 $16\text{ KiB}$ ＋ 管理構造体で 1 本あたり少なくとも約 $32\text{〜}64\text{ KiB}$ を消費します。$100{,}000 \text{ 本} \times 32\text{ KiB} \approx \mathbf{3.05\text{ GiB}}$ 以上が「何もせず待っているだけ」のタスクのために固定消費され、カーネルのスケジューラ管理対象も 10 万個に膨らみます。

* **軽量ユーザ空間タスク（M:N コルーチン／`async/await`）：**

    * **Go の goroutine（スタックフル）：** 初期スタックがわずか **$2\text{ KiB}$** のため、$100{,}000 \text{ 本} \times 2\text{ KiB} \approx \mathbf{195\text{ MiB}}$ に収まります。
    * **Rust の `async` タスク（スタックレス）：** 専用スタックを持たず、`await` を跨いで生存する局所変数だけを詰めた構造体（例：約 $200\text{ B}$）になるため、$100{,}000 \text{ 本} \times 200\text{ B} \approx \mathbf{19.1\text{ MiB}}$ で収まり、OS スレッドは CPU コア数と同じわずか **4〜8 本** で足ります。

#### 実験B：`async/await` 関数がコンパイラによって「状態機械」へ変換される仕組み

次の `async` 関数は、見た目には普通の同期コードと同じように上から下へ書かれています。

```rust
// 開発者が書くコード（同期コードのように素直に読める）
async fn handle_client(sock: Socket) -> Result {
    let req = sock.read().await;        // 中断点 ①：データ到着待ち
    let res = query_db(req).await;      // 中断点 ②：DB 応答待ち
    sock.write(res).await;              // 中断点 ③：送信完了待ち
    return Ok;
}
```

実はコンパイラ（Rust / C# / C++20 / JavaScript エンジン等）は、この関数をコンパイル時に **[2-7節](../2/2-7.md)の生存変数解析** を使って解析し、**「`await` 地点で分割された有限状態機械（ステートマシン）と `poll()` 関数」** へ自動変換します。

```c
// コンパイラが内部生成する等価なステートマシン構造体（概念図）
struct HandleClientFuture {
    enum { START, WAIT_READ, WAIT_DB, WAIT_WRITE, DONE } state;
    Socket sock;          // 全 await を跨いで生存する変数だけを保持
    Request req;          // 中断点 ①〜② で生存
    Response res;         // 中断点 ②〜③ で生存
};

PollResult poll(struct HandleClientFuture *f, Waker *w) {
    switch (f->state) {
    case START:
        /* 非同期 read を登録し、準備未完なら state = WAIT_READ にして Pending を返す */
    case WAIT_READ:
        /* 読込完了なら req を取り出し、query_db を開始して state = WAIT_DB へ */
    case WAIT_DB:
        /* DB 応答完了なら res を取り出し、write を開始して state = WAIT_WRITE へ */
    case WAIT_WRITE:
        /* 書込完了なら state = DONE にして Ready(Ok) を返す */
    }
}
```

`await` に到達して I/O の準備がまだできていないとき、このタスクは OS スレッドをブロックせず、**自分の現在状態 `state` を構造体へ保存しただけで `Pending` を返して即座に制御をイベントループへ戻します**（なお実際の Rust コンパイラ等では、生存期間が重ならない状態ごとの変数をタグ付き共用体 `enum` として同じメモリ領域へ重ねることで、構造体サイズをさらに圧縮します）。このおかげで、人間はコールバック地獄を書かずに済み、実行時は `epoll` によるノンブロッキング駆動と同じ軽量さで動くのです。

### 3. 構造・アルゴリズム・実装（What）

#### (1) 並行実行モデルの 3 系統（1:1・イベントループ・M:N）

OS スレッドとアプリケーション上の論理的なタスク（接続・リクエスト処理）をどう対応づけるかによって、現代の実行モデルは大きく 3 系統に分類されます（図5-10-1）。

| モデル | 対応関係 | 切替の主体 | 特徴と代表例 |
| :--- | :---: | :--- | :--- |
| **1. 1:1 モデル（OS スレッド）** | タスク 1 ： OS スレッド 1 | OS カーネル（プリエンプティブ） | 既存のブロッキング I/O や C ライブラリと完全互換。マルチコアを自動活用できるが、数万本規模でメモリと切替コストが重くなる（C `pthread`, 従来の Java Thread）。 |
| **2. シングルスレッド・イベントループ** | タスク $M$ ： OS スレッド 1 | ユーザ空間（`epoll` + 協調的） | ロック不要で競合状態が起きにくく非常に軽量。ただし 1 コアしか使えず、CPU 重処理で全体が止まる（Node.js, Redis, Nginx ワーカープロセス）。 |
| **3. M:N モデル（ユーザ空間スケジューラ）** | タスク $M$ ： OS スレッド $N$<br>（$N \approx$ CPU コア数） | ユーザ空間ランタイム ＋ `epoll` | 数十万タスクを省メモリで管理しつつ、$N$ 個の CPU コアすべてを並列活用できる現代の主流（Go goroutine, Rust Tokio, Java Virtual Threads, Erlang BEAM）。 |

#### (2) スタックフル・コルーチン vs スタックレス・コルーチン（`async/await`）

途中で処理を一時停止（サスペンド）し、後から続きを再開（レジューム）できる関数・タスクを一般に **コルーチン（Coroutine）** と呼びます。コルーチンの実装方式は、中断時の状態をどこへ保存するかによって次の 2 種類に大きく分かれます。

| 比較項目 | スタックフル・コルーチン（Stackful） | スタックレス・コルーチン（Stackless） |
| :--- | :--- | :--- |
| **中断時の状態保存** | タスクごとに**専用の小さなコールスタック**を割り当て、callee-saved レジスタと `sp` をユーザ空間で切り替える（[3-3節](../3/3-3.md)の `swtch()` と同型） | コンパイラが `await` ごとに分割した**有限状態機械（構造体）**を生成し、生存変数だけをその構造体へ保存する（実験B） |
| **メモリ効率（1 タスク）** | 数 $\text{KiB}$（例：Go は初期 $2\text{ KiB}$、必要時に動的拡張） | 数十〜数百バイト（最小限・スタック不要） |
| **関数呼び出しの自由度** | 普通の同期関数の深い呼び出し先からでも自由に中断できる（関数カラーリングなし） | `async` 関数の中からしか `await` できない（**関数カラーリング**が生じる：4-(2)で詳述） |
| **代表言語・実装** | Go（goroutine）, Java Virtual Threads, Lua | Rust（`async/await`）, JavaScript/TS, Python `asyncio`, C++20 |

スタックレス `async/await` がイベントループ（`epoll` / `kqueue`）と協調して動く全体の仕組みを図5-10-2に示します。

1. **エグゼキュータ（Executor：実行キュー）：** 実行可能なタスク（Future）を取り出し、`poll(future, waker)` を呼び出します。
2. **リアクタ（Reactor：`epoll` 監視役）：** タスクがノンブロッキングの `read()` を試みて `EAGAIN`（データ未到着）を受け取ると、その FD とこのタスクを起こすためのハンドル（**Waker**）をリアクタ（`epoll`）へ登録し、`Pending` を返して OS スレッドを空けます。
3. **イベント起床と再実行：** ネットワークからパケットが届くと、`epoll_wait()` が該当 FD の準備完了を検知し、登録されていた **Waker** を呼んでそのタスクをエグゼキュータの実行キューへ戻します。再び `poll()` が呼ばれたタスクは、保存していた `state` から続きを再開します。

#### (3) M:N スケジューラの心臓部：ワークスティーリング（Go の G-M-P モデル）

複数の CPU コアすべてを使い切る M:N ランタイム（Go ランタイムや Rust の Tokio マルチスレッド実行器など）では、全ワーカーがたった 1 本の「グローバル実行キュー」を共有するとロック競合が激しくなり、[4-1節](../4/4-1.md)の Amdahl の法則でスケールしなくなります。

そこで Go ランタイムは、次の 3 要素からなる **G-M-P モデル** と **ワークスティーリング（Work Stealing）** を採用しています（図5-10-3）。

* **G（Goroutine）：** ユーザ空間の軽量タスクです（初期スタック $2\text{ KiB}$＋プログラムカウンタ等）。
* **M（Machine）：** OS カーネルがスケジュールする実体の OS スレッドです。
* **P（Processor）：** CPU コア数と同数（`GOMAXPROCS` 個）用意される論理実行コンテクストであり、**各 P が自分専用のローカル実行キュー（LRQ）** を持ちます。

**ワークスティーリングと非同期 I/O 連携の動作：**

1. **ロックレスに近い高速実行：** 各 OS スレッド M は 1 つの P に紐づき、原則として **P 自身のローカルキュー（LRQ）** から G を取り出して実行します。他コアとロックを奪い合わないため高速です。
2. **ワークスティーリング（仕事盗み）：** ある P0 のローカルキューが空になると、P0 はアイドルになる前にグローバルキューを確認し、さらに空なら **別の忙しい P1 のローカルキューから待機中の G の半分を盗んで（Steal）** 自分のコアで実行します。これによりマルチコア全体の負荷が自律的に均等化されます。
3. **ネットワークポーラ（`epoll`）による非ブロック化：** ある G がソケットの `read()` でデータ待ちに入ると、ランタイムはその G を P から外して **ネットワークポーラ（裏側で `epoll_wait` を回す機構）** へ預け、OS スレッド M は即座にローカルキューの次の G を実行し続けます。一方、G が通常のブロッキングシステムコール（C ライブラリ呼び出しやディスク I/O 等）に入った場合は、ランタイムが P をその M から切り離して別の待機中 M へ付け替えることで、他の G の進行を止めないよう工夫されています。

> **【コラム：協調的スケジューリングの限界と「ユーザ空間プリエンプション」への回帰】**
>
> 初期のユーザ空間スレッドやコルーチンは、タスクが `await` や I/O 呼び出しに到達したときにだけ自発的に CPU を譲る **協調的スケジューリング（Cooperative Scheduling）** でした。しかし協調的モデルには、「たった 1 つのタスクが `for (;;)` のような関数呼び出しも `await` も含まない重い計算ループに入ると、同じ OS スレッド上の他タスクやガベージコレクタが永久に動けなくなる」という、[3-3節](../3/3-3.md)で見た協調的 OS とまったく同じ弱点があります。
>
> そこで Go 1.14（2020年）では、ランタイムの監視スレッドが「10 ミリ秒以上 CPU を占有している G」を検知すると、その M（OS スレッド）宛てに **[4-7節](../4/4-7.md)で学んだ非同期 POSIX シグナル（`SIGURG`）** を送り、シグナルハンドラ内でスタック上のレジスタ退避フレームを書き換えて強制的に別 G へ切り替える **非同期プリエンプション** を導入しました。OS がタイマ割り込みで行った歴史的な進化が、そのままユーザ空間ランタイムの中でも繰り返されているのです。

### 4. 限界と補正（Critique & Adaptation）

非同期実行モデルと M:N スケジューラは I/O バウンドな高並列システムで強力な武器になりますが、使い方を誤ると OS スレッド以上に分かりにくい性能劣化や障害を招きます。

#### (1) イベントループ／非同期ワーカーの凍結（ブロッキング呼び出しと CPU バウンド処理）

非同期ランタイムの前提は、**「個々のタスクが 1 回の `poll()` で CPU を占有する時間はごく短い（マイクロ秒〜ミリ秒未満）こと」** です。もし `async` 関数の中でうっかり次のような処理を直接書いてしまうと、そのタスクを実行している OS スレッド全体が凍結し、同じスレッド（または P）に相乗りしている数千件の無関係なリクエストが一斉にタイムアウトします。

* 同期的なブロッキングライブラリ（例：通常のディスクファイル `read()`、同期 DB ドライバ、スレッドを眠らせる `sleep()`）の呼び出し。
* 長時間かかる CPU バウンド計算（パスワードのストレッチング、巨大 JSON のパース、画像リサイズ等）。

**補正：** ブロッキング I/O や重い CPU 計算は、非同期ランタイムが別途用意する **専用のブロッキング用 OS スレッドプール（例：Rust Tokio の `spawn_blocking`、Node.js の `libuv` スレッドプール / Worker Threads）** へ明示的に逃がします。また、通常のディスクファイル I/O を非同期化するには [5-1](5-1.md)・[5-3節](5-3.md)で触れた **`io_uring`** を利用する構成も広がっています。

#### (2) 関数カラーリング問題と構造化並行性（Structured Concurrency）

スタックレス `async/await` には、同期関数（`fn foo()`）と非同期関数（`async fn bar()`）という「2 色の関数」が言語内で分断される **関数カラーリング問題（Function Coloring）** があります。末端の 1 関数を非同期化しただけで、それを呼び出す上位の関数チェーンすべてへ `async` / `.await` を伝播させなければなりません。

また、タスク生成が非常に軽量なあまり、あちこちでタスクを放り投げ（`go f()` や `tokio::spawn(...)`）すると、親リクエストがエラーやタイムアウトで終了した後も子タスクが裏側で走り続けてメモリやソケットをリークする問題が起きやすくなります。

**補正：** 近年は、子タスクの寿命を必ず親のレキシカルスコープ（ブロック構造）の内側へ閉じ込め、親がエラーやキャンセルで抜けるときは全子タスクを確実にキャンセルして終了を待つ **構造化並行性（Structured Concurrency：Java の `StructuredTaskScope`、Python `asyncio.TaskGroup`、Go の `errgroup` 等）** が標準的な設計指針になっています。

#### (3) 無制限タスク生成とバックプレッシャ（Backpressure）の欠如

10 万本のタスクを簡単に生成できるからといって、クライアントからのリクエストを受け付けるたびに上限なくタスクを生成し続けると、後段のデータベースや外部 API が遅延した瞬間に、未完了のタスクとリクエストボディが RAM 上へ際限なく積み上がり、最終的に OS の **OOM Killer（[3-7節](../3/3-7.md)）** によってプロセス全体が強制終了します。

**補正：** 受付口に [4-5節](../4/4-5.md)の **有界キュー（Bounded Channel）** や **セマフォによる同時実行数上限** を設け、上限に達したら新規タスクの生成を止めるか即座に過負荷エラー（HTTP `503` / `429`）を返して呼び出し側へ減速を伝える **バックプレッシャ（背圧制御）** を設計に組み込むことが不可欠です。

>
>     * (a) 1 本あたり実質 $40\text{ KiB}$ を消費する 1:1 OS スレッドモデルと、1 タスクあたり $2\text{ KiB}$ のスタックフル・コルーチン（Go 等）および $256\text{ B}$ のスタックレス `async` タスク（Rust 等）について、10 万本分のタスク管理メモリ消費量をそれぞれ概算比較してください。
>     * (b) スタックフル・コルーチンとスタックレス・コルーチン（`async/await`）について、中断時の状態保存方法と「関数カラーリング」の有無の違いを説明してください。
>
> 2. **（非同期サーバにおける 2 つの実務障害診断）**
>     CPU 4 コア上で 4 本の OS スレッドを動かす M:N 非同期サーバ（`epoll` ベース）において、次の 2 つの実装ミスがそれぞれ引き起こす障害と適切な修正策を答えてください。
>
>     * (a) ある HTTP エンドポイントの `async` ハンドラ内で、500 ms かかる同期的な画像変換処理（CPU バウンド）やブロッキング型の外部ライブラリ呼び出しをそのまま実行した。
>     * (b) リクエストを受け取るたびに同時実行数制限なし（無制限）で新規タスクを生成して後段 DB へ投げる設計にしたところ、DB が一時的に遅延した瞬間にサーバプロセス全体が OOM Killer で落ちた。
>
> 3. **（[第6部](../index.md#part-6)への伏線：共有ネットワーク回線の多重化方式）**
>     本節までで、1 台のサーバ内で 10 万本のソケットを効率よく捌く仕組みが整いました。ここで視点をサーバの外側（ネットワーク）へ広げ、多数のコンピュータ同士を接続することを考えます。$N$ 台のホストをすべて 1 対 1 の専用ケーブルで直結できないため、途中の交換機で 1 本の幹線リンクを共有（多重化）する必要があります。Web 閲覧のように「一瞬だけ通信して残り 90% の時間は無音（バースト的）」なトラヒックを多数収容するとき、通信開始前に帯域を固定予約する方式（回線交換）と、データを小包へ分けて送りたいときだけ流し込む方式（パケット交換）では、それぞれどのような利点と代償が生じるでしょうか。
