### 前節（5-7）の確認問題の解答

前節の最後に提示した3つの問いの解答を確認します。前節で設計したアクセス制御や最小権限の枠組みも、プログラム本体にメモリ破壊バグがあると制御フローごと突破され得るため、本節では攻撃原理と実行時の多層防御へ進みます。

1. **ディレクトリ `711`・配下ファイル `644` に対する 3 コマンドの成否トレース（一般ユーザ `bob`＝`o`）：**
    `/dir` の `o` 権限は `--x`（通過のみ）、`/dir/file` の `o` 権限は `r--`（読取のみ）です。

    * **(a) `ls /dir`：失敗（Permission denied）。** ディレクトリ内のファイル名一覧を読み出すには `/dir` 自身の `r` 権限が必要ですが、`o` に `r` が付いていないため拒否されます。
    * **(b) `cat /dir/file`：成功。** `/dir` に `x`（通過・検索）権限があるため、正確なファイル名 `"file"` を指定すれば `/dir` を通過して `/dir/file` へ到達でき、さらに `/dir/file` 自身に `o` の `r` 権限があるため中身を読み出せます。
    * **(c) `rm /dir/file`：失敗（Permission denied）。** ファイル削除（`unlink`）は親ディレクトリ `/dir` のエントリを書き換える操作であり、親ディレクトリ `/dir` に `w` と `x` の両方が必要ですが、`/dir` の `o` には `w` が付いていないため拒否されます。

2. **`setuid root` プログラムの `access()` → `open()` TOCTOU 攻撃と対策：**

    * **(a) TOCTOU 競合攻撃の手順と Confused Deputy 問題との関係：**
        攻撃者は最初に `/tmp/work` として自分が書き込み可能な通常ファイルを用意してプログラムを起動します。`access("/tmp/work", W_OK)` は `RUID` で検査するため成功（`0`）を返しますが、その直後・`open()` が実行される前のわずかな隙間に、攻撃者が `/tmp/work` を削除して `/etc/shadow` へのシンボリックリンクへすり替えます。続く `open()` は **`EUID = 0`（`root` の環境権限）** で実行されるため `/etc/shadow` が開かれて上書きされてしまいます。特権を持つ代理プログラムが攻撃者の指定したパス名へ自身の環境権限を誤適用してしまった点で、典型的な **Confused Deputy 問題** です。

    * **(b) `seteuid(RUID)` と `O_NOFOLLOW` による対策：**

        * **`seteuid(RUID)`：** `open()` を呼ぶ前に実効権限を一般ユーザ `RUID` へ降格させておけば、たとえ `/etc/shadow` へすり替えられてもカーネルの権限検査で `open()` 自体が拒否されます（`access()` による事前チェックを省いて直接開く設計にできます）。
        * **`O_NOFOLLOW`（および `openat`＋`fstat`）：** `open()` に `O_NOFOLLOW` を指定すると対象がシンボリックリンクだった瞬間にオープンを拒否でき、さらに一度開いた FD に対して `fstat()` 等で検査すればパス名の再解決（すり替え）を防げます。

3. **ポート 80 番 Web サーバの最小権限多層設計：**
    `setuid root` のまま動かすと、HTTP パーサ等に 1 箇所バグがあるだけでシステム全権（ファイル破壊・権限奪取）を奪われる All-or-Nothing の危険があります。そこで次の 3 層で被害半径を封じ込めます。

    * **① `CAP_NET_BIND_SERVICE`：** 1024 番未満の 80 番ポートを `bind()` する特権**だけ**を付与し（他の `CAP_DAC_OVERRIDE` や `CAP_SYS_ADMIN` 等は一切持たせない。ポートをバインドした後に放棄してもよい）、全能な `root` 権限を排除します。
    * **② `chroot` / マウント名前空間：** プロセスから見えるファイルシステムのルートを `/var/www` 配下だけに隔離し、万が一侵入されても `/etc/shadow` などのホスト側機密ファイルへ到達できないようにします。
    * **③ `seccomp`（`seccomp-bpf`）：** Web サーバの稼働に必要な最小限のシステムコール（`read`, `write`, `epoll_wait` 等）以外の呼び出し（`execve` によるシェル起動等）をカーネルで遮断します。

    なお、ここで用いる **Linux ケイパビリティ** は「対象を限定せず `root` 特権を機能別フラグへ分割したプロセス属性」であるのに対し、FD のような **オブジェクトケーパビリティ** は「特定の客体（ファイル等）と操作権限を 1 つに束ねたチケット」である点が構造的に異なります。

## 5-8. メモリ破壊攻撃と多層防御（BOF・ROP・ASLR/NX/カナリア）

### 1. 動機（Why）：アクセス制御が堅固でも「プログラムの1行のバグ」で権限が奪われる理由

前節（[5-7節](5-7.md)）では、OSが ACL・ケイパビリティ・Unix 権限・Linux ケイパビリティによって「誰が何の資源へアクセスしてよいか」を厳格に管理していることを見ました。しかし現実のセキュリティ事故の多くは、OSの権限設定ミスだけでなく、**高い権限（`setuid` やネットワーク待ち受けサーバ等）で動いているC/C++プログラム自身のメモリ操作バグ**から引き起こされます。

[2-5節](../2/2-5.md)で触れた通り、C言語は実行速度とハードウェア直結の自由度を優先し、配列アクセス `buf[i]` の境界チェックを実行時に自動挿入しません。さらに、[0-1節](../0/0-1.md)で確認した固定幅整数のオーバーフローがサイズ計算に紛れ込むと、プログラマが書いたはずの境界チェック自体がすり抜けられてしまいます。その結果、[1-3節](../1/1-3.md)のスタックフレーム構造、[1-4節](../1/1-4.md)の「命令とデータは同じビット列である」という性質、そして[3-5節](../3/3-5.md)の仮想記憶レイアウトが絡み合い、**外部からの入力1つでプログラムの制御フローを乗っ取る「メモリ破壊攻撃」**が成立してしまいます。

本節では、実行時のシステム保護の中核となる **メモリ破壊攻撃と多層防御（Defense in Depth）** の攻防を整理します。

1. **攻撃の原理（スタック BOF と整数オーバーフロー）：** [1-3節](../1/1-3.md)のスタックフレーム上で戻り番地が上書きされる仕組み（実験A）と、[0-1節](../0/0-1.md)の整数オーバーフローによって境界チェックが回避される仕組み（実験B）を具体的に追います。
2. **実行時の多層防御とコード再利用攻撃（ROP）：** コンパイラ・OS・CPUハードウェアの協調による防御の4本柱（**スタックカナリア・NXビット［W^X］・ASLR＋PIE・Full RELRO／CFI**）と、NX をくぐり抜ける **Return-to-libc / ROP** の攻防を整理します。
3. **実行時防御の限界と開発時の補正：** 情報漏洩やヒープ破壊（Use-After-Free）といった多層防御の死角と、開発時の動的検査ツール（**ASan・TSan・ファジング**）およびメモリ安全言語による根本対策を確認します。

### 2. 具体例と動作イメージ（Toy Model）

防御機構の全体像に入る前に、2つの短いCコードで「バッファオーバーフローが制御フローを奪う瞬間」と「境界チェックを書いても整数オーバーフローですり抜けられる瞬間」をメモリ番地・数値レベルで追ってみます。

#### 実験A：1行の `strcpy` で戻り番地を上書きする（x86-64 スタックフレーム）

次の脆弱なC関数 `greet()` を考えます（[1-3節](../1/1-3.md)の x86-64 System V AMD64 ABI を例にとりますが、戻り番地 `ra` をスタックへ退避する RISC-V でも本質は同じです）。

```c
void secret_admin_shell(void) {
    // 本来は呼ばれないはずの特権処理（非 PIE 実行ファイルの例：0x0000000000401196）
    execve("/bin/sh", ...);
}

void greet(const char *user_input) {
    char buf[16];            // スタック上に 16 バイトの局所配列を確保
    strcpy(buf, user_input); // 危険：長さを検査せず '\0' までコピーする
}
```

`greet()` のプロローグが実行された直後のスタックフレームを、低位アドレス（下）から高位アドレス（上）へ並べると次の配置になっています（図5-8-1左）。

* `rbp - 16` 〜 `rbp - 1`：`buf[0]` 〜 `buf[15]`（16バイト）
* `rbp + 0` 〜 `rbp + 7`：退避された呼び出し元の `%rbp`（8バイト）
* **`rbp + 8` 〜 `rbp + 15`：戻り番地（Return Address、8バイト）**

ここで重要なのは、**スタック自体は高位から低位へ伸びるのに対し、配列 `buf[0], buf[1], ...` への書き込みは低位から高位（戻り番地の方向）へ進む**という向きの一致です。

ここで1つ細かなバイト配置に注意します。`strcpy()` は文字列終端のヌルバイト **`0x00`** を検出した時点でコピーを終了するため、64ビット非 PIE 実行ファイルのアドレス `0x0000000000401196`（リトルエンディアンで `96 11 40 00 00 00 00 00`）の上位5バイトにある `0x00` をそのまま並べても4バイト目以降へはコピーが進みません。ところが、非 PIE の64ビット実行ファイルでは、`rbp + 8` に元から置かれていた正規の戻り番地（例：`0x0000000000401234`）も上位5バイトがもともとすべて `0x00` です。そのため攻撃者は `user_input` として次の **27バイト＋終端ヌル1バイト（計28バイト書込）** を渡すだけで目標アドレスへ飛ばせます。

1. 先頭 **16バイト**：`'A'` $\times 16$（`buf[0..15]` を埋めます）
2. 次の **8バイト**：`'B'` $\times 8$（保存された `%rbp` を上書きします）
3. 最後の **3バイト** `0x96, 0x11, 0x40` と文字列終端の **1バイト** `0x00`：リトルエンディアン配置のため、`rbp + 8` 〜 `rbp + 10` の下位3バイトが `96 11 40` に書き換わり、4バイト目（`rbp + 11`）へ `strcpy()` の終端 `0x00` が書かれてコピーが止まります。上位4バイト（`rbp + 12` 〜 `rbp + 15`）は元から `0x00` のまま残るため、戻り番地全体が正確に **`0x0000000000401196`** へすり替わります。

直後に `greet()` のエピローグが `leave; ret` を実行すると、CPUはスタックトップから偽造された `0x401196` をポップして `%rip` へ読み込み、**一度も呼び出していないはずの `secret_admin_shell()` へジャンプしてしまいます**。

なお、途中に `0x00` を含む複数の64ビットアドレスをスタック上へ連続配置する **ROP チェーン**（後述 3-(2)）を送り込む場合は、`strcpy()` では最初の `0x00` でコピーが止まってしまうため、`read()` や `memcpy()` のようにヌルバイトを含めて指定バイト数そのままコピーする**バイナリ入力系のバッファオーバーフロー脆弱性**が前提になります。また、`secret_admin_shell()` のような都合のよい関数が存在しない場合でも、古典的な攻撃では `buf` の中に攻撃者自身の機械語（**シェルコード：Shellcode**、例：`/bin/sh` を起動する `execve` システムコール列）を埋め込み、戻り番地を `buf` の先頭アドレスへ書き換えることで任意のプログラムを実行させることができました。

#### 実験B：整数オーバーフローによる境界チェック回避とヒープ破壊

`strcpy()` のような危険な関数を使わず、プログラマが丁寧にサイズ上限のチェックを書いたつもりでも、[0-1節](../0/0-1.md)で学んだ**固定幅整数のラップアラウンド（$\bmod\ 2^{32}$）**によってメモリ破壊が起きる典型例を見ます。

ネットワークパケットから受け取った32ビット符号なし整数 `count` 個ぶんのレコード（1個あたり 16 バイト）を格納するため、最大 $64\text{ KiB}$（$65{,}536\text{ B}$）までに制限してメモリを確保する関数を考えます。

```c
#include <stdint.h>
#include <stdlib.h>

// 1要素 16 バイトの配列を count 個ぶん確保したい（最大 64 KiB まで許可）
void *alloc_items(uint32_t count) {
    uint32_t total = count * 16;   // 32ビット符号なし乗算でオーバーフローし得る
    if (total > 65536) {           // 「64 KiB 超は拒否」の境界チェック
        return NULL;
    }
    return malloc(total);          // 呼び出し元が count 個ぶん書き込むと溢れる
}
```

ここで、攻撃者が `count` として **`0x10000001`**（$2^{28} + 1 = 268{,}435{,}457$）を送ったとします。

1. `count * 16` の数学的な積は $(2^{28} + 1) \times 2^4 = 2^{32} + 16$（16進で `0x100000010`）になります。
2. しかし `uint32_t` は下位32ビットしか保持できないため、上位ビットが切り捨てられて `total` は $2^{32} + 16 \equiv \mathbf{16} \pmod{2^{32}}$ に丸め込まれます。
3. 次の境界チェック `if (total > 65536)` は `16 > 65536`（偽）と評価されて**チェックをすり抜けます**。
4. `malloc(16)` はヒープ上に**たった16バイト（1要素ぶん）**しか確保しません。ところが呼び出し元は「`count` 個ぶん確保に成功した」と信じて後続のデータを書き込み続けるため、直後のヒープ管理領域や隣接オブジェクトを破壊する **ヒープ・バッファオーバーフロー** が発生します。

このように、境界チェックは「乗算や加算をした結果」ではなく、演算前に上限を割って比較する（`if (count > 65536 / 16) return NULL;`）か、オーバーフロー検査付きの確保関数（`calloc()` や `__builtin_mul_overflow()`）を使わなければ回避されてしまいます。

### 3. 構造・アルゴリズム・実装（What）

#### (1) 多層防御（Defense in Depth）の 4 本柱

実験Aのような古典的バッファオーバーフロー攻撃を防ぐため、現代のコンピュータは「1つの防御が突破されても次の層で止める」**多層防御**を、コンパイラ・OS・CPUハードウェアの3層協調で構築しています。

1. **スタックカナリア（Stack Canary / Stack Smashing Protector：コンパイラ層）**

    * **仕組み：** コンパイラ（GCC/Clang の `-fstack-protector-strong`）が、局所配列を持つ関数のプロローグで、**`buf` と「保存 `%rbp`・戻り番地」のちょうど間**に、起動時にOSが生成した予測不能なランダム値（**カナリア値**）を書き込んでおきます（図5-8-1右）。
    * **検知：** エピローグで `ret` を実行する直前に、スタック上のカナリア値が元の秘密値と一致しているかを照合します。バッファオーバーフローで戻り番地まで連続上書きすると**途中のカナリア値が必ず壊れる**ため、一致しなければ即座に `__stack_chk_fail()` を呼んでプロセスを強制終了させ、`ret` による乗っ取りを阻止します（炭鉱の毒ガスを早期検知するカナリア鳥が名前の由来です）。
    * なお、カナリア値の最下位1バイト（低位アドレス＝配列 `buf` に最も近い側）には意図的にヌル文字 **`0x00`** を含める工夫があり、`strcpy()` のような文字列関数による読み出し・書き換えをカナリアの入口で遮断します。

2. **NX ビット / DEP（実行禁止保護・W^X：ハードウェア MMU ＋ OS 層）**

    * **仕組み：** [3-5節](../3/3-5.md)で学んだページテーブルエントリ（PTE）の実行許可ビット `X`（x86-64 では NX: No-Execute ビット）を活用し、**「書き込み可能なページは実行禁止、実行可能なページは書き込み禁止（W^X：Write XOR Execute）」**をハードウェアで強制します。
    * **効果：** スタックやヒープは `R=1, W=1, X=0` に設定されるため、仮に攻撃者が `buf` へシェルコード（機械語）を書き込んで戻り番地を `buf` へ向けたとしても、CPUがスタック上の命令をフェッチした瞬間にMMUがページフォルト例外を起こして即座にプロセスを停止させます。これにより、古典的な「コード注入攻撃（シェルコード実行）」は無力化されました。

3. **ASLR（Address Space Layout Randomization）＋ PIE（OS ＋ リンカ層）**

    * **仕組み：** プログラムを起動するたびに、OSカーネルが**スタック、ヒープ、共有ライブラリ（`libc.so`）、さらに [1-5節](../1/1-5.md)の PIE（位置独立実行ファイル）であれば実行ファイル本体の `.text` セクションの仮想アドレスまでランダム化**して配置します。
    * **効果：** 攻撃者が戻り番地を書き換えられても、飛び先となる `secret_admin_shell` や `libc` 関数のアドレスが実行のたびに変わるため、当てずっぽうのジャンプが失敗してクラッシュに終わります。

4. **Full RELRO（[1-5節](../1/1-5.md)）と CFI（Control-Flow Integrity：制御フロー整合性）**

    * **Full RELRO：** 起動時に GOT 全体を読み取り専用（`r--`）へ凍結し、関数ポインタ表の改ざんを防ぎます。
    * **CFI / ハードウェア支援（[1-2節](../1/1-2.md)の Intel CET 等）：** 関数ポインタや間接ジャンプの飛び先を、先頭に `endbr64` 命令が置かれた正当な入口だけにハードウェアで限定する **IBT（Indirect Branch Tracking：間接分岐追跡）** と、通常のスタックとは別の保護領域へ戻り番地の控えを自動保存・照合する **シャドウスタック（Shadow Stack）** によって、制御フロー改ざん自体をハードウェアで遮断します。

#### (2) 防御と攻撃の進化：NX を突破する Return-to-libc と ROP

NX ビット（W^X）の導入によって「攻撃者が新しい機械語をスタックへ持ち込むこと」はできなくなりました。しかし攻撃者は発想を転換し、**「新しいコードを持ち込まずに、すでに `X=1`（実行可能）でメモリ上に存在している正規のコード（`libc` やプログラム本体）を悪用する」** **コード再利用攻撃（Code Reuse Attack）** へ進化させました（図5-8-2）。

* **Return-to-libc（ret2libc）：** スタックへシェルコードを置く代わりに、すでにメモリにマップされている `libc` の `system()` 関数へ制御を移して `system("/bin/sh")` を実行させる手法です。32ビット x86 では引数をスタックへ積むだけで済みましたが、[1-3節](../1/1-3.md)で確認した **x86-64 の呼び出し規約（System V AMD64 ABI）では第1引数をレジスタ `%rdi` で渡す**ため、単に `system()` へ飛ぶだけでは引数が渡りません。そこで、スタックトップの値を `%rdi` へ取り込んで次のアドレスへ戻る短い命令片 **`pop %rdi; ret`** を先頭に挟み、スタック上へ `[addr(pop %rdi; ret)]` → `[addr("/bin/sh")]` → `[addr(system)]` の順に並べて実行します（図5-8-3）。
* **ROP（Return-Oriented Programming：リターン指向プログラミング）：** この発想を一般化し、既存の `.text` や `libc` の中から末尾が `ret` 命令で終わる2〜3命令の小さな断片（**ガジェット：Gadget**）を多数探し出し、それらのアドレスをスタック上へ鎖（**ROP チェーン**）のように並べる手法です。各ガジェットの `ret` が次のガジェットのアドレスをスタックからポップして次々と連鎖実行するため、1バイトも新しい機械語を書き込まずに任意の計算やシステムコール呼び出しを構成できます。

この ROP に対抗するのが、上で挙げた **ASLR＋PIE**（ガジェットのアドレス自体を分からなくする）と、**シャドウスタック・CFI**（`ret` の戻り先が本来の `call` 元と一致するか検証する）です。

> **【コラム：なぜ `gets()` は C11 で廃止され、現代は Rust のようなメモリ安全言語へ移行しているのか】**
>
> かつてC言語の標準ライブラリには、標準入力から1行読み込む **`gets(char *buf)`** という関数が存在しました。しかし `gets()` は**バッファサイズを引数にとらない**ため、入力が `buf` より1バイトでも長ければ必ずバッファオーバーフローを起こす危険な仕様であり、1988年の世界初の大規模インターネットワーム（モリスワーム）の感染経路にもなりました。その結果、`gets()` は **C11 規格で標準ライブラリから削除** され、サイズ上限を受け取る `fgets()` や `snprintf()` の利用が必須となりました。
>
> しかし、大規模なC/C++コードベース（OSカーネルやブラウザ等）の脆弱性統計を見ると、どれほど熟練した開発者がレビューしても、深刻なセキュリティ脆弱性の **約 70%** が依然としてバッファオーバーフローや解放後使用（Use-After-Free）といった**メモリ安全性バグ**に起因しています。そのため近年は、実行時の多層防御（ASLR/NX等）で対症療法を重ねるだけでなく、**Rust** のように「配列の境界チェック」と「所有権・借用チェッカによるコンパイル時のメモリライフタイム検証（[2-5節](../2/2-5.md)）」を言語仕様へ組み込み、メモリ破壊バグ自体を構造的に排除する動きが Linux カーネルや Windows・Android 開発へ広がっています。

### 4. 限界と補正（Critique & Adaptation）

#### (1) 多層防御の死角：情報漏洩による ASLR 突破とヒープ破壊

スタックカナリア・NX・ASLR をすべて有効にしても、攻撃がゼロになるわけではありません。

* **情報漏洩（Information Leak）による ASLR・カナリア突破：** たとえば `printf(user_input)` のような書式文字列バグや、未初期化メモリの読み出しバグによって、プログラムがスタック上のカナリア値や `libc` のアドレスをたった1回画面へ漏らしてしまうと、攻撃者はその実測値からカナリア値をそのまま書き戻しつつ ASLR のランダム配置を逆算し、正確に ROP チェーンを組み立てられます。
* **ヒープ破壊（Use-After-Free / Double Free）と整数オーバーフロー：** スタックカナリアが守るのはスタックの戻り番地だけです。実験Bの整数オーバーフローに起因するヒープ・バッファオーバーフローや、`malloc()` で確保したヒープ領域を `free()` で解放した後も古いポインタ（ダングリングポインタ）を使い続ける **Use-After-Free（解放後使用）**、同じ領域を2回解放する **Double Free（二重解放）** によってヒープ上の関数ポインタやオブジェクトを書き換えられる攻撃には、スタックカナリアは効きません。

#### (2) 動的検査ツール・メモリ安全言語による補正と、動的検証の本質的限界

多層防御は「バグが残っていても悪用を難しくする」防波堤ですが、バグの根本原因を消すわけではありません。そのため実務では、開発・テスト段階と設計段階の両面で次の補正を組み合わせています。

* **サニタイザによる実行時監視：** コンパイル時に検査コードを埋め込み、テスト実行中に異常を即座に検知します。

    * **AddressSanitizer（ASan）：** スタック・ヒープ双方の境界外アクセスと Use-After-Free を高速に検知します。
    * **UndefinedBehaviorSanitizer（UBSan）：** 符号付き整数オーバーフローやシフト量超過などの未定義動作を検知します。
    * **ThreadSanitizer（TSan）：** [4-1節](../4/4-1.md)で扱ったマルチスレッドのデータ競合を検知します。

* **カバレッジ誘導型ファジング（AFL / libFuzzer）：** プログラムの分岐カバレッジを計測しながら何百万もの異常入力を自動生成し、ASan と組み合わせて境界チェック漏れやクラッシュを引き起こす入力を自動探索します。
* **メモリ安全言語の採用：** 新規開発やパーサ・ドライバなどの攻撃対象面では、Rust 等のメモリ安全言語を採用して境界外アクセスや Use-After-Free をコンパイル時に構造的に防ぎます。

しかし、ここにも越えられない壁が残ります。実行時の多層防御も、ASan やファジングなどの動的テストも、**「実際に動かした入力や実行経路でバグが顕在化したこと」を検知できても、「試していない境界条件や稀な並行インターリービングにバグが存在しないこと」は証明できません**。この限界に挑むため、次節（[5-9節](5-9.md)）ではプログラムを実行する前にコードの構造や状態空間を機械的・数学的に検証する **静的解析と形式手法** へ進みます。

### 理解度チェック（次節へ進む前の確認）

本節の整数オーバーフロー構成・多層防御マトリクス・x86-64 ROP 連鎖とカナリアの仕組みを確認し、次節（[5-9節](5-9.md)）へ繋ぐ問いを置きます。

> **【確認の問い】**
>
> 1. **（整数オーバーフロー境界チェックの突破値構成と安全な修正）**
>     次の C コードは、1 要素 32 バイトのレコードを `count` 個とヘッダ 16 バイトを確保する際、合計サイズを 4,096 バイト以下に制限する意図で書かれています。
>
>     ```c
>     int alloc_records(uint32_t count) {
>         uint32_t total = count * 32 + 16;   // 32ビット符号なし演算
>         if (total > 4096) {
>             return -1;
>         }
>         void *p = malloc(total);
>         ...
>     }
>     ```
>
>     * (a) 本来許可される最大の正常 `count` 値はいくつでしょうか。また、`total > 4096` の境界チェックをすり抜けてしまう**最小の不正な `count` 値**（16 進数および 10 進数）と、そのときの `total` の値を求めてください。
>     * (b) この脆弱性を防ぐため、`count * 32 + 16` を計算する**前**に上限を検査する安全なコードへ書き直してください。
>
> 2. **（3 つの防御設定環境に対する攻撃可否の診断）**
>     ある 64 ビットプログラムに、`read()` によるスタック・バッファオーバーフロー脆弱性と、スタック上の任意位置の内容を画面へ出力できる情報漏洩バグの 2 つがあるとします。次の 3 つの防御設定環境それぞれについて、**シェルコード注入・ROP 攻撃・情報漏洩の併用**がどのように阻止または突破されるか診断してください。
>
>     * ① **NX のみ有効**（カナリアなし・ASLR/PIE なし）
>     * ② **NX ＋ スタックカナリア有効**（ASLR/PIE なし）
>     * ③ **NX ＋ スタックカナリア ＋ ASLR/PIE すべて有効**
>
> 3. **（x86-64 ROP ガジェット連鎖のトレースとカナリア最下位バイト `0x00` の役割）**
>
>     * (a) NX 有効・ASLR 無効の x86-64 環境で、スタック上の戻り番地以降を書き換えて `system("/bin/sh")` を実行したいとします。`pop %rdi; ret` ガジェットの番地を `G`、文字列 `"/bin/sh"` の番地を `S`、`system()` 関数の番地を `F` とするとき、戻り番地の位置から高位アドレス側へどのような順序で 3 つの 8 バイト値を並べればよいでしょうか。`%rsp`・`%rip`・`%rdi` の変化を 3 ステップでトレースしてください。
>     * (b) スタックカナリアの 8 バイト乱数値の最下位バイト（配列 `buf` に最も近い側）に、意図的にヌルバイト **`0x00`** を配置する理由を、`strcpy()` などの C 文字列関数の挙動と結びつけて説明してください。
