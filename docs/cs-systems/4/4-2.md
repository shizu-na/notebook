### 前節（4-1）の確認問題の解答

前節の最後に提示した3つの問いの解答を確認します。問3-(b) がそのまま本節（ソフトウェア相互排除の系譜）のアルゴリズム0の導入になります。

1. **インターリービングによる最終値の範囲（2スレッド各3回、計6回の `count++`）：**

    * **(a) 最大値・最小値と `1` にならない理由：**

        * **最大値：`6`**（すべての加算が重ならず順に実行された場合です）。
        * **最小値：`2`**（直感に反して、片方の実行回数 `3` よりも小さい `2` が生じ得ます）。
        * **最小値が `1` にならない理由：** どの `sd` 命令も `1` 以上の値を書き込むため、一度でも `sd` が実行された後はメモリ上の `count` が `0` に戻ることはありません。さらに、最後に `sd` を実行するスレッドはその前に自身の1回目・2回目の `sd` を必ず完了しているため、3回目の `ld` が読み出す値は必ず `1` 以上になり、最終書き込みは必ず `2` 以上になります。

    * **(b) 最小値 `2` が生じる具体的な実行順の例：**

        1. スレッドA（1回目）：`count`（`0`）を `ld` で読み出して一時停止します。
        2. スレッドB（1回目）：`0` を読み出し、`+1` して `1` を書き込みます（`count = 1`）。
        3. スレッドB（2回目）：`1` を読み出し、`+1` して `2` を書き込みます（`count = 2`）。
        4. スレッドA（1回目再開）：手元の `0` に `+1` して `1` を書き込みます（`count` が `1` へ上書きされます）。
        5. スレッドB（3回目）：`count`（`1`）を `ld` で読み出して一時停止します。
        6. スレッドA（2回目・3回目）：`1 → 2`、`2 → 3` と連続して完了します（`count = 3`）。
        7. スレッドB（3回目再開）：手元の `1` に `+1` して **`2`** を書き込みます（`count` が `2` へ上書きされて終了します）。

2. **並行障害の診断と Amdahl の法則による設計判断：**

    * **(a) 障害種別・原因・修正策：**

        * **① デッドロック：** スレッド間で `A → B` と `B → A` の逆順にロックを取り合うため循環待機（Coffman の第4条件）が成立します。口座IDの昇順でロックを獲得する**ロック順序付け**で予防できます。
        * **② ライブロック：** 双方のロック解放と再試行が同調し、状態変化と CPU 消費が続くのに前進しません。再試行間隔にランダムな待ち時間（バックオフ）を入れるか、そもそもロック順序付けで競合を解消します。

    * **(b) Amdahl の法則による比較：**

        * **案A（$1 - p = 0.20,\; p = 0.80,\; N = 16$）：**

          $$S_A(16) = \frac{1}{0.20 + \dfrac{0.80}{16}} = \frac{1}{0.20 + 0.05} = \frac{1}{0.25} = \mathbf{4.0\text{ 倍}}$$

          （コア数を無限に増やしても $1/0.20 = 5.0$ 倍が上限です）。

        * **案B（$1 - p = 0.04,\; p = 0.96,\; N = 8$）：**

          $$S_B(8) = \frac{1}{0.04 + \dfrac{0.96}{8}} = \frac{1}{0.04 + 0.12} = \frac{1}{0.16} = \mathbf{6.25\text{ 倍}}$$

        * 半分のコア数であっても直列部分を削る**案B**の方が大幅に高速であり、案Aの無限コア上限（$5.0$ 倍）すら上回ります。

3. **共有データ構造の破壊と素朴なロック変数の破綻：**

    * **(a) `kalloc()` で同一ページ `P0` を重複取得する最小4ステップ（初期 `kmem.freelist = P0`、`P0->next = P1`）：**

        1. コア0が `(1) r_0 = kmem.freelist` を実行し、`r_0 = P0` を取得します。
        2. コア0が `(2)` を実行する前に、コア1も `(1) r_1 = kmem.freelist` を実行し、`r_1 = P0` を取得します。
        3. コア0が `(2) kmem.freelist = P0->next`（`= P1`）を実行し、`P0` を返します。
        4. コア1も `(2) kmem.freelist = P0->next`（`= P1`）を実行し、同じく **`P0`** を返してしまいます。

    * **(b) `while (lock == 1) {}` 直後に `lock = 1;` と書く方式が破綻する理由：**
        `lock == 0` の確認と `lock = 1` の書き込みが別命令に分かれているため、スレッド0が `lock == 0` を確認してループを抜けた直後、`lock = 1` を書く前にスレッド1も `lock == 0` を確認してしまい、両方が同時にクリティカルセクションへ入ってしまいます。

## 4-2. ソフトウェア相互排除の系譜（アルゴリズム0〜4からDekker・Petersonへ）

### 1. 動機（Why）：なぜわざわざ「失敗作（アルゴリズム0〜4）」から順番に辿るのか

前節（[4-1節](4-1.md)）で、並行プログラムの入口／出口プロトコルが満たすべき3大条件として、**①安全性（相互排除）**、**②活性（進行性：デッドロック・ライブロックの不在）**、**③公平性（有界待機：飢餓の不在）**を定義しました。

ここで素朴な疑問が湧きます。「CPUに特別なロック命令が一切ないと仮定して、**普通の共有変数（メモリへの単純な読み書き）だけ**で、この3条件をすべて満たすことはできるのでしょうか？」

実は、この問題は1960年代の計算機科学者たちを悩ませた古典的な難問でした。十分に正しいと考えて提案されたアルゴリズムの多くが、後から巧妙なインターリービングの反例（デッドロックやライブロック、相互排除の破綻）を見つけられて次々と覆された歴史があります。

本節では、最初から完成形を暗記するのではなく、**アルゴリズム0からアルゴリズム4までの5つの素朴な試みが「それぞれどの条件で、どの瞬間に破綻するのか」**を1つずつ検証したうえで、歴史的な解である **Dekker（デッカー）のアルゴリズム** と **Peterson（ピーターソン）のアルゴリズム** へ到達します。この失敗の系譜を辿ることが、並行バグを見抜く目を養う近道になります。

---

### 2. 具体例と動作イメージ（Toy Model）

プログラムのコードに入る前に、2人の利用者（スレッド0とスレッド1）が**「1人しか入れない鍵のない共有会議室（クリティカルセクション）」**を、ドアの外のメモ用紙だけで譲り合って使う状況を想像してみます。

#### 実験A：ドアの外のメモだけで起きる2つのすれ違い

* **すれ違い1（確認してから札を掛ける）：**
    利用者0が「ドアに『使用中』の札が掛かっていない」と確認して、自分のポケットから札を取り出している**ほんの一瞬の隙間**に、利用者1も「札がない」と確認して入室してしまいます。結果、**2人が同時に会議室へ入って鉢合わせ（相互排除の破綻）**します。

* **すれ違い2（先に札を掛けてから相手を確認する）：**
    それなら「まず自分の『入りたい』旗を上げてから、相手の旗を見る」ルールに変えます。すると、2人がまったく同じタイミングで自分の旗を上げた場合、どちらも「相手が旗を上げているから待とう」とドアの前で固まり、**永遠に誰も入れない（デッドロック）**ことになります。

「見てから立てる」と衝突し、「立ててから見る」と睨み合いになります。このジレンマを突破する鍵が、**「意思表示（`flag`）」と「順番の譲り合い（`turn`）」の2つを組み合わせる**という発想です。

---

### 3. 構造・アルゴリズム・実装（What）

以下では、2つのスレッド（自分＝$i \in \{0, 1\}$、相手＝$j = 1 - i$）が共有変数だけを使って相互排除を行う系譜を順に検証します（まずは単一変数のロード／ストア自体は途中で分断されず、かつ各スレッドのメモリ読み書きが記述順通りに即時反映される理想的な共有メモリモデルを仮定します）。

#### (1) 失敗の系譜：アルゴリズム 0 〜 アルゴリズム 4

それぞれの試みと、破綻する決定的なインターリービングを整理します（図4-2-1）。

* **アルゴリズム 0（単一の共有ロック変数 `int lock = 0;`）：**

    ```c
    while (lock == 1) { }   // (1) 空くまで待つ
    lock = 1;               // (2) 使用中と記録
    /* クリティカルセクション */
    lock = 0;
    ```

    * **破綻（安全性違反：相互排除の失敗）：** `(1)` の確認と `(2)` の書き込みが1つの不可分な操作ではないため、スレッド0が `lock == 0` を確認してループを抜けた直後、`lock = 1` を書く前にスレッド1も `lock == 0` を確認してしまい、両方が同時にCSへ入ります（実験Aのすれ違い1と同じ、**チェックと使用の隙間［TOCTOU］**）。

* **アルゴリズム 1（厳格な交互実行 `int turn = 0;`）：**

    ```c
    while (turn != i) { }   // 自分の番になるまで待つ
    /* クリティカルセクション */
    turn = j;               // 終わったら相手へ番を渡す
    ```

    * **破綻（活性違反：進行性の失敗）：** `turn` は `0` か `1` のどちらか1つしか取れないため、**相互排除は満たします**。しかし、「0 → 1 → 0 → 1」と厳密に交互にしか入れないため、スレッド0がCSを終えて `turn = 1` にしたあと、スレッド1が残余セクションで長時間休んでいる（あるいは終了した）と、スレッド0は二度とCSへ入れなくなります。

* **アルゴリズム 2（2つの意思表示フラグ `flag[2]`：見てから立てる）：**

    ```c
    while (flag[j] == 1) { } // (1) 相手が希望していなければ進む
    flag[i] = 1;             // (2) 自分の旗を立てる
    /* クリティカルセクション */
    flag[i] = 0;
    ```

    * **破綻（安全性違反：相互排除の失敗）：** アルゴリズム0と同じ理由で、両スレッドが同時に `(1)` で相手の旗が `0` であることを確認してから `(2)` を実行すると、2人同時にCSへ入ってしまいます。

* **アルゴリズム 3（2つの意思表示フラグ `flag[2]`：先に立ててから見る）：**

    ```c
    flag[i] = 1;             // (1) 先に自分の旗を立てる
    while (flag[j] == 1) { } // (2) 相手が旗を立てていたら待つ
    /* クリティカルセクション */
    flag[i] = 0;
    ```

    * **破綻（活性違反：デッドロック）：** 先に自分の旗を立てるため、**相互排除は満たします**。しかし、スレッド0が `flag[0] = 1`、スレッド1が `flag[1] = 1` を同時に実行すると、互いに相手の旗が `1` なのを見て `while` ループから永久に出られなくなります（実験Aのすれ違い2）。

* **アルゴリズム 4（衝突したら一時的に旗を下ろして譲る）：**

    ```c
    flag[i] = 1;
    while (flag[j] == 1) {
        flag[i] = 0;         // 衝突したので一旦旗を下ろす
        /* 少し待つ */
        flag[i] = 1;         // 再度旗を立て直す
    }
    /* クリティカルセクション */
    flag[i] = 0;
    ```

    * **破綻（活性違反：ライブロックおよび飢餓）：** 互いに譲り合うため静止したデッドロックは避けられますが、2スレッドが同じタイミングで「旗を立てる → 相手を見る → 旗を下ろす → 立て直す」を繰り返すインターリービングが存在し、CPUを消費しながら永遠にどちらもCSへ入れない **ライブロック** に陥ります（また、片方だけがタイミング悪く譲り続ける**飢餓**も起こり得ます）。

#### (2) Dekker のアルゴリズム（1965年）：歴史上初のソフトウェア解

アルゴリズム3とアルゴリズム4が失敗した根本原因は、**2つのスレッドが完全に左右対称な動きをしてしまうこと**にあります。そこでオランダの数学者テオドルス・デッカー（Th. J. Dekker）は、アルゴリズム3の意思表示フラグ `flag[2]` に、アルゴリズム1の **`turn`（どちらに優先権があるか）を「衝突したときの審判役」としてだけ組み合わせる**ことで、歴史上初の3条件を満たすアルゴリズムを完成させました（エドガー・ダイクストラによって1965年に公表）。

```c
// Dekker のアルゴリズム（スレッド i、相手 j = 1 - i）
flag[i] = 1;                     // 1. まず自分の入場意思を宣言
while (flag[j] == 1) {           // 2. 相手も入りたい場合だけ衝突処理へ
    if (turn == j) {             // 3. 相手の番なら、自分だけ一時的に旗を下ろす
        flag[i] = 0;
        while (turn == j) { }    //    相手の終了を待つ
        flag[i] = 1;             //    自分の番が来たら再び旗を立てる
    }
}
/* クリティカルセクション */
turn = j;                        // 4. 退場時に優先権を相手へ渡す
flag[i] = 0;                     // 5. 自分の旗を下ろす
```

衝突が起きたとき、`turn` が示す優先側だけは旗を下げずに待ち続け、非優先側だけが旗を下ろして引き下がります。これにより対称性が破れ、相互排除・進行性・有界待機の3条件すべてを満たします（Dekker の厳密な証明は入れ子構造がやや煩雑なためここでは省略し、次のより簡潔な Peterson のアルゴリズムで3条件の厳密な証明を行います）。

#### (3) Peterson のアルゴリズム（1981年）と3条件の証明

Dekker のアルゴリズムは正しいものの、入れ子の `while` と `if` がやや煩雑です。それから16年後の1981年、ゲイリー・ピーターソン（Gary L. Peterson）は、わずか3行の入口プロトコルと1行の出口プロトコルだけで同じ3条件をすべて満たす簡潔なアルゴリズムを発見しました。

```c
// Peterson のアルゴリズム（共有変数：int flag[2] = {0, 0}; int turn = 0;）
// スレッド i（0 または 1）、相手 j = 1 - i
flag[i] = 1;                            // (1) 自分が入りたいと宣言
turn = j;                               // (2) 「お先にどうぞ」と相手へ番を譲る
while (flag[j] == 1 && turn == j) { }   // (3) 相手も希望 かつ 相手の番なら待つ
/* クリティカルセクション */
flag[i] = 0;                            // (4) 退場時に旗を下ろす
```

この数行のコードが、なぜ3大条件をすべて満たすのかを論理的に証明します（図4-2-2）。

1. **安全性（相互排除）の証明（背理法）：**
    スレッド0とスレッド1が**同時にクリティカルセクション（CS）内にいる**と仮定します。

    * 両スレッドが CS 内にいる以上、スレッド0は `(1) flag[0] = 1` と `(2) turn = 1` を、スレッド1は `(1) flag[1] = 1` と `(2) turn = 0` をそれぞれ完了し、`flag[0] = 1, flag[1] = 1` のまま保たれています。
    * 共有変数 `turn` への2つの書き込み（スレッド0の `turn = 1` とスレッド1の `turn = 0`）は、逐次一貫性のもとで必ずどちらかが先、どちらかが後になります。対称性より、**スレッド1の方が後から `turn = 0` を書き込んだ**（スレッド0の `turn = 1` が先だった）とします。
    * 各スレッド内でのプログラム実行順序と `turn` の書き込み順序を繋ぐと、次の4要素の先行関係（$\prec$）が成り立ちます。

      $$\text{T0: }\texttt{flag[0]=1} \;\prec\; \text{T0: }\texttt{turn=1} \;\prec\; \text{T1: }\texttt{turn=0} \;\prec\; \text{T1: }\texttt{while評価}$$

    * 推移律より、スレッド1が `(3)` の `while (flag[0] == 1 && turn == 0)` を評価する時点では、スレッド0はすでに `flag[0] = 1` を書き終えており（かつ CS 内にいるので `0` には戻していない）、しかも `turn` はスレッド1自身が最後に書き込んだ `0` のままです（スレッド0はすでに `turn = 1` を終えているため再上書きしない）。
    * したがって、スレッド1の待機条件 `flag[0] == 1 && turn == 0` は**必ず真**となり、スレッド1は `while` ループを抜けられません。これは「両方が同時に CS 内にいる」という仮定に矛盾します。よって相互排除は厳密に成立します。

2. **活性（進行性・デッドロック／ライブロック不在）の証明：**
    （各スレッドの CS は有限時間で終了し、スケジューラの弱公平性により `(1)` と `(2)` の間で永久停止しないことを前提とします。）

    * もしスレッド $j$ が残余セクションにいるなら `flag[j] == 0` なので、スレッド $i$ は `while` 条件が偽になり直ちに入場できます（アルゴリズム1の欠点を克服）。
    * もし両方が同時に `while` ループで足止めされるとしたら、`turn == 1`（スレッド0が待つ条件）と `turn == 0`（スレッド1が待つ条件）が同時に成り立つ必要がありますが、`turn` は同時に2つの値を持てないため不可能です。先に `turn` を書いた側が必ずループを抜けて前進します。

3. **公平性（有界待機・飢餓の不在）の証明：**

    * スレッド0が `while (flag[1] == 1 && turn == 1)` で待っている間に、スレッド1が CS を終えて `flag[1] = 0` にしたとします。
    * もしスレッド0が動く前にスレッド1がすぐ次の周回に入り、`flag[1] = 1` の直後に **`turn = 0`** と書き換えた瞬間に、スレッド0の待機条件 `turn == 1` が偽へ反転します。逆にスレッド1側は `flag[0] == 1 && turn == 0` が真になって止まります。
    * したがって、スレッド0が待たされる回数は**高々1回（相手の1回分）**に厳密に抑えられ、飢餓は決して起きません。

> **【コラム：$N$ スレッドへの拡張：Lamport（ランポート）のパン屋のアルゴリズム（Bakery Algorithm）】**
>
> Dekker や Peterson は「2スレッド専用」のアルゴリズムですが、1974年にレスリー・ランポート（Leslie Lamport）は、任意の $N$ スレッド間で普通の共有変数だけで相互排除・進行性・公平性を満たす **パン屋のアルゴリズム（Bakery Algorithm）** を考案しました。
>
> 発想は、混雑したパン屋や銀行の窓口にある**整理券発券機**と同じです。
>
> 1. CSへ入りたいスレッド $i$ は、現在他の全員が持っている整理券番号の最大値 $+ 1$ を自分の番号 `number[i]` として取ります。
> 2. もし2つのスレッドが同時に発券機を引いて**まったく同じ整理券番号**を取ってしまった場合は、**「スレッドID（$i$）が小さい方を優先する」**という辞書式順序 `(number[i], i) < (number[j], j)` で勝敗を一意に決めます。
> 3. 自分より優先度の高い（番号が小さい）スレッドがすべてCSを終えるまで待ってから入場し、退場時に `number[i] = 0` に戻します。
>
> パン屋のアルゴリズムは「番号を計算している途中に他スレッドが未確定の `number[i] = 0` を読んで追い抜く」のを防ぐフラグ（`choosing[i] = 1`）まで考慮して設計されており、ハードウェアのアトミック命令を一切使わずに任意の $N$ スレッドのFIFOに近い公平な相互排除を実現できます。

### 4. 限界と補正（Critique & Adaptation）

Peterson のアルゴリズムは理想的な共有メモリモデルの上では数学的に成り立ちます。ところが、**現代のマルチコアPCやスマートフォン上で、上のC言語コードをそのまま実行すると、実は相互排除が破綻して2スレッドが同時にクリティカルセクションへ入ってしまう**ことがあります。なぜ数学的証明が現実のハードウェアで崩れるのでしょうか。

#### (1) 現代のマルチコアCPUにおける破綻：ストアバッファによる「Store-Load 並べ替え」

Peterson の証明には、**「各スレッドのメモリ書き込みと読み込みが、ソースコードに書いた順番通りに他コアへ観測される（逐次一貫性：Sequential Consistency）」**という暗黙の前提が置かれていました。

しかし、現代の高性能CPU（x86-64、ARM、RISC-V）は、[0-7節](../0/0-7.md)で見たキャッシュ無効化の待ち時間を隠蔽するために、各コアとキャッシュのあいだに **ストアバッファ（Store Buffer）** という小さな書き込み一時置き場を備えています。すると、次の現象が起きます（図4-2-3）。

1. スレッド0（コア0）が `flag[0] = 1; turn = 1;` を実行します。これらの書き込みはいったん**コア0自身のストアバッファ**に溜められ、まだ共有キャッシュ（他コアから見える場所）へは反映されていません。
2. コア0はストアバッファの反映を待たず、直後の `while` ループの読み込み **`load flag[1]` を追い越して先に実行**します（**Store-Load 並べ替え**）。この時点ではコア1の書き込みもまだ反映されていないため、コア0は **`flag[1] == 0`** と読みます。C言語の `&&` は短絡評価（[2-6節](../2/2-6.md)）なので、左辺が偽になった時点で `turn` を確認することすらなくループを抜け、**そのまま CS へ突入します**。
3. 同じ瞬間に、コア1も `flag[1] = 1; turn = 0;` を自分のストアバッファへ積んだまま、追い越して **`load flag[0]`** を実行して **`flag[0] == 0`** を読み、**同じく CS へ突入します**。

さらに、コンパイラ自身の最適化（[2-7節](../2/2-7.md)）によっても、`flag[i] = 1` と `flag[j]` の読み込みの順序が入れ替えられたり、`while (flag[j] == 1)` がレジスタへキャッシュされて無限ループ化したりする危険があります。

#### (2) ビジーウェイトの非効率性とハードウェア支援への移行

さらに、ソフトウェア相互排除アルゴリズムには実用上の制約が2つ残ります。

1. **ビジーウェイト（スピン待ち）によるCPUと電力の浪費：** `while (flag[j] == 1 && turn == j) { }` は待機中ずっとCPUコアを100%回し続けるため、CSが長い場合や単一コア環境では非効率です。
2. **多スレッド環境でのスケーラビリティ不足：** パン屋のアルゴリズムのように $N$ スレッドへ拡張できても、入場のたびに全 $N$ スレッドの配列を走査する $O(N)$ コストがかかり、動的にスレッド数が増減する現代のOSには向きません。

これらの限界を根本から解決するため、現代のCPUは「確認と書き込みの隙間（TOCTOU）」をハードウェアの1命令で不可分に閉じる **アトミック命令（Swap・CAS等）** と、メモリ順序を制御する **メモリバリア** を備えています。次節（[4-3節](4-3.md)）では、そのハードウェア支援の仕組みへ進みます。

### 理解度チェック（次節へ進む前の確認）

本節の失敗パターン・Peterson のアルゴリズムの成立条件・実機ハードウェアでの破綻原因を確認し、次節（[4-3節](4-3.md)）へ繋ぎます。

> **【確認の問い】**
>
> 1. **（Peterson のアルゴリズムのバグ変種を診断する）**
>     Peterson のアルゴリズムの入口プロトコルで、`turn = j;`（相手へ譲る）を誤って **`turn = i;`（自分へ番を設定する）** と書いてしまいました。
>
>     ```c
>     flag[i] = 1;
>     turn = i;                               // ← 本来は turn = j;
>     while (flag[j] == 1 && turn == j) { }
>     ```
>
>     このコードでは「安全性（相互排除）・活性（進行性）・公平性（有界待機）」のどれが破綻するでしょうか。最小の反例インターリービングを示して証明してください。
>
> 2. **（Peterson のアルゴリズムにおける順序の厳密性）**
>     正しい Peterson のアルゴリズムの入口プロトコルは、① `flag[i] = 1;` → ② `turn = j;` → ③ `while (flag[j] == 1 && turn == j) {}` の順です。もし誤って ① と ② の順番を逆にして、**`turn = j;` を先に書き、その後で `flag[i] = 1;` を書く**ように変えてしまった場合、**相互排除が破綻する具体的なインターリービング**（スレッド0とスレッド1の実行順）を1つ示してください。
>
> 3. **（実機 CPU とコンパイラ最適化による破綻の境界）**
>     本節4-(1)および[2-7節](../2/2-7.md)の知識をもとに、次の2つに答えてください。
>
>     * (a) ストアバッファを備えるマルチコアCPUで Peterson のアルゴリズムを守るには、`flag[i] = 1` と `turn = j` の間ではなく、**`turn = j` と `while` ループの読み込みの間**にメモリ順序の保証（バリア）が必要なのはなぜでしょうか。
>     * (b) 仮に CPU ハードウェアが完全な逐次一貫性（並べ替えゼロ）だったとしても、C コンパイラの最適化によって Peterson のアルゴリズムが壊れ得る具体的な変換を1つ挙げてください。
