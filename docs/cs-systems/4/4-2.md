### 前節（4-1）の確認問題の解答

前節の最後に提示した3つの問いの解答を確認します。問3がそのまま本節（ソフトウェア相互排除の系譜）の導入になります。

1. **インターリービングによる最終値の範囲（2スレッド各2回、計4回の `count++`）：**

    * **(a) 最大値と最小値：**

        * **最大値：`4`**（すべての加算が重ならず順に実行された場合）
        * **最小値：`2`**（どのスレッドの2回目の加算も、自身の1回目が `1` 以上を書き込んだ後に行われるため、2回目が読み出す値は必ず `1` 以上になり、最終書き込みが `1` になることはありません）

    * **(b) 最小値 `2` が生じる具体的な実行順の例：**

        1. スレッドA（1回目）：`count`（`0`）を読み出して一時停止。
        2. スレッドB（1回目）：`count`（`0`）を読み出し、`+1` して `1` を書き込む。
        3. スレッドB（2回目）：`count`（`1`）を読み出し、`+1` して `2` を書き込む（B完了）。
        4. スレッドA（1回目再開）：手元の `0` に `+1` して `1` を書き込む（ここで `count` が `1` へ上書きされる）。
        5. スレッドA（2回目）：`count`（`1`）を読み出し、`+1` して **`2`** を書き込む（最終値 `2`）。

2. **デッドロック・ライブロック・飢餓の区別と Amdahl の法則：**

    * **(a) 障害の対応：**

        * CPUを100%消費して動き続けているのにシステム全体が前進しない状態：**ライブロック**
        * 全体は前進しているのに特定スレッドだけ永遠に順番が来ない状態：**飢餓（スターベーション）**

    * **(b) Amdahl の法則による高速化倍率（直列部分 $1 - p = 0.2 \implies p = 0.8$）：**

        * $N = 4$ コア時：$S(4) = \dfrac{1}{0.2 + \dfrac{0.8}{4}} = \dfrac{1}{0.2 + 0.2} = \dfrac{1}{0.4} = \mathbf{2.5\text{ 倍}}$
        * コア数無限大（$N \to \infty$）の上限：$S(\infty) = \dfrac{1}{0.2} = \mathbf{5.0\text{ 倍}}$

3. **ハードウェアの特殊命令なしで相互排除は作れるか（本節への接続）：**
    メモリ操作がプログラムの記述順通りに他スレッドへ見える（逐次一貫性）という前提のもとでは、普通の共有変数（`flag[2]` と `turn`）の読み書きだけでも、安全性・活性・公平性の3条件をすべて満たすアルゴリズム（Dekker・Peterson）を構成できます。本節では、素朴な失敗作から完全解へ至る思考の系譜を辿ります。

## 4-2. ソフトウェア相互排除の系譜（アルゴリズム0〜4からDekker・Petersonへ）

### 1. 動機（Why）：なぜわざわざ「失敗作（アルゴリズム0〜4）」から順番に辿るのか

前節（[4-1節](4-1.md)）で、並行プログラムの入口／出口プロトコルが満たすべき3大条件として、**①安全性（相互排除）**、**②活性（進行性：デッドロック・ライブロックの不在）**、**③公平性（有界待機：飢餓の不在）**を定義しました。

ここで素朴な疑問が湧きます。「CPUに特別なロック命令が一切ないと仮定して、**普通の共有変数（メモリへの単純な読み書き）だけ**で、この3条件をすべて満たすことはできるのでしょうか？」

実は、この問題は1960年代の計算機科学者たちを大いに悩ませた古典的な難問でした。「これで完璧だ」と思って提案されたアルゴリズムの多くが、後から巧妙なインターリービングの反例（デッドロックやライブロック、相互排除の破綻）を見つけられて次々と覆された歴史があります。

本節では、最初から完成形を暗記するのではなく、**アルゴリズム0からアルゴリズム4までの5つの素朴な試みが「それぞれどの条件で、どの瞬間に破綻するのか」**を1つずつ検証したうえで、歴史的な完全解である **Dekker（デッカー）のアルゴリズム** と **Peterson（ピーターソン）のアルゴリズム** へ到達します。この失敗の系譜を辿ることこそが、並行バグを見抜く目を養う最短経路になります。

---

### 2. 具体例と動作イメージ（Toy Model）

プログラムのコードに入る前に、2人の利用者（スレッド0とスレッド1）が**「1人しか入れない鍵のない共有会議室（クリティカルセクション）」**を、ドアの外のメモ用紙だけで譲り合って使う状況を想像してみます。

#### 実験A：ドアの外のメモだけで起きる2つのすれ違い

* **すれ違い1（確認してから札を掛ける）：**
    利用者0が「ドアに『使用中』の札が掛かっていないな」と確認して、自分のポケットから札を取り出している**ほんの一瞬の隙間**に、利用者1も「札がないな」と確認して入室してしまう。結果、**2人が同時に会議室へ入って鉢合わせ（相互排除の破綻）**します。

* **すれ違い2（先に札を掛けてから相手を確認する）：**
    それなら「まず自分の『入りたい』旗を上げてから、相手の旗を見る」ルールに変えます。すると、2人がまったく同じタイミングで自分の旗を上げた場合、どちらも「相手が旗を上げているから待とう」とドアの前で固まり、**永遠に誰も入れない（デッドロック）**ことになります。

「見てから立てる」と衝突し、「立ててから見る」と睨み合いになる。このジレンマを突破する鍵が、**「意思表示（`flag`）」と「順番の譲り合い（`turn`）」の2つを組み合わせる**という発想です。

### 3. 構造・アルゴリズム・実装（What）

以下では、2つのスレッド（自分＝$i \in \{0, 1\}$、相手＝$j = 1 - i$）が共有変数だけを使って相互排除を行う系譜を順に検証します（まずはメモリ読み書きが記述順通りに即時反映される理想的な共有メモリモデルを仮定します）。

#### (1) 失敗の系譜：アルゴリズム 0 〜 アルゴリズム 4

それぞれの試みと、破綻する決定的なインターリービングを整理します（図4-2-1）。

* **アルゴリズム 0（単一の共有ロック変数 `int lock = 0;`）：**
    ```c
    while (lock == 1) { }   // (1) 空くまで待つ
    lock = 1;               // (2) 使用中と記録
    /* クリティカルセクション */
    lock = 0;
    ```

    * **破綻（安全性違反：相互排除の失敗）：** `(1)` の確認と `(2)` の書き込みが1つの不可分な操作ではないため、スレッド0が `lock == 0` を確認してループを抜けた直後、`lock = 1` を書く前にスレッド1も `lock == 0` を確認してしまい、両方が同時にCSへ入ります（実験Aのすれ違い1と同じ、**チェックと使用の隙間［TOCTOU］**）。

* **アルゴリズム 1（厳格な交互実行 `int turn = 0;`）：**
    ```c
    while (turn != i) { }   // 自分の番になるまで待つ
    /* クリティカルセクション */
    turn = j;               // 終わったら相手へ番を渡す
    ```

    * **破綻（活性違反：進行性の失敗）：** `turn` は `0` か `1` のどちらか1つしか取れないため、**相互排除は完全に満たします**。しかし、「0 → 1 → 0 → 1」と厳密に交互にしか入れないため、スレッド0がCSを終えて `turn = 1` にしたあと、スレッド1が残余セクションで長時間休んでいる（あるいは終了した）と、スレッド0は二度とCSへ入れなくなります。

* **アルゴリズム 2（2つの意思表示フラグ `flag[2]`：見てから立てる）：**
    ```c
    while (flag[j] == 1) { } // (1) 相手が希望していなければ進む
    flag[i] = 1;             // (2) 自分の旗を立てる
    /* クリティカルセクション */
    flag[i] = 0;
    ```

    * **破綻（安全性違反：相互排除の失敗）：** アルゴリズム0とまったく同じ理由で、両スレッドが同時に `(1)` で相手の旗が `0` であることを確認してから `(2)` を実行すると、2人同時にCSへ入ってしまいます。

* **アルゴリズム 3（2つの意思表示フラグ `flag[2]`：先に立ててから見る）：**
    ```c
    flag[i] = 1;             // (1) 先に自分の旗を立てる
    while (flag[j] == 1) { } // (2) 相手が旗を立てていたら待つ
    /* クリティカルセクション */
    flag[i] = 0;
    ```

    * **破綻（活性違反：デッドロック）：** 先に自分の旗を立てるため、**相互排除は満たします**。しかし、スレッド0が `flag[0] = 1`、スレッド1が `flag[1] = 1` を同時に実行すると、互いに相手の旗が `1` なのを見て `while` ループから永久に出られなくなります（実験Aのすれ違い2）。

* **アルゴリズム 4（衝突したら一時的に旗を下ろして譲る）：**
    ```c
    flag[i] = 1;
    while (flag[j] == 1) {
        flag[i] = 0;         // 衝突したので一旦旗を下ろす
        /* 少し待つ */
        flag[i] = 1;         // 再度旗を立て直す
    }
    /* クリティカルセクション */
    flag[i] = 0;
    ```

    * **破綻（活性違反：ライブロック）：** 互いに譲り合うため静止したデッドロックは避けられますが、2スレッドがまったく同じタイミングで「旗を立てる → 相手を見る → 旗を下ろす → 立て直す」を繰り返すインターリービングが存在し、CPUを100%使いながら永遠にどちらもCSへ入れない **ライブロック** に陥ります。

#### (2) Dekker のアルゴリズム（1965年）：歴史上初のソフトウェア完全解

アルゴリズム3とアルゴリズム4が失敗した根本原因は、**2つのスレッドが完全に左右対称な動きをしてしまうこと**にあります。そこでオランダの数学者テオドルス・デッカー（Th. J. Dekker）は、アルゴリズム3の意思表示フラグ `flag[2]` に、アルゴリズム1の **`turn`（どちらに優先権があるか）を「衝突したときの審判役」としてだけ組み合わせる**ことで、歴史上初の完全解を完成させました（エドガー・ダイクストラによって1965年に公表）。

```c
// Dekker のアルゴリズム（スレッド i、相手 j = 1 - i）
flag[i] = 1;                     // 1. まず自分の入場意思を宣言
while (flag[j] == 1) {           // 2. 相手も入りたい場合だけ衝突処理へ
    if (turn == j) {             // 3. 相手の番なら、自分だけ一時的に旗を下ろす
        flag[i] = 0;
        while (turn == j) { }    //    相手の終了を待つ
        flag[i] = 1;             //    自分の番が来たら再び旗を立てる
    }
}
/* クリティカルセクション */
turn = j;                        // 4. 退場時に優先権を相手へ渡す
flag[i] = 0;                     // 5. 自分の旗を下ろす
```

衝突が起きたとき、`turn` が示す優先側だけは旗を下げずに待ち続け、非優先側だけが旗を下ろして引き下がります。これにより対称性が完全に破れ、デッドロックもライブロックも起きず、相互排除・進行性・有界待機の3条件すべてを満たします。

#### (3) Peterson のアルゴリズム（1981年）と3条件の厳密な証明

Dekker のアルゴリズムは正しいものの、入れ子の `while` と `if` がやや煩雑です。それから16年後の1981年、ゲイリー・ピーターソン（Gary L. Peterson）は、わずか4行の入口プロトコルと1行の出口プロトコルだけで同じ3条件を完全に満たす、驚くほど簡潔なアルゴリズムを発見しました。

```c
// Peterson のアルゴリズム（共有変数：int flag[2] = {0, 0}; int turn = 0;）
// スレッド i（0 または 1）、相手 j = 1 - i
flag[i] = 1;                            // (1) 自分が入りたいと宣言
turn = j;                               // (2) 「お先にどうぞ」と相手へ番を譲る
while (flag[j] == 1 && turn == j) { }   // (3) 相手も希望 かつ 相手の番なら待つ
/* クリティカルセクション */
flag[i] = 0;                            // (4) 退場時に旗を下ろす
```

このたった数行のコードが、なぜ3大条件をすべて満たすのかを論理的に証明してみます（図4-2-2）。

1. **安全性（相互排除）の証明（背理法）：**
    スレッド0とスレッド1が**同時にクリティカルセクションへ入った**と仮定します。

    * どちらも直前で `flag[0] = 1` および `flag[1] = 1` を実行済みなので、両者が `while` ループを突破した瞬間の決定打は `turn` の値しかありません。
    * 共有変数 `turn` はスレッド0が `turn = 1` を、スレッド1が `turn = 0` をそれぞれ1回ずつ書き込みますが、メモリ上の最終値は `0` か `1` の**どちらか一方だけ**です。
    * 対称性より、スレッド1の方が後から `turn = 0` を書き込んだ（すなわちスレッド0の `turn = 1` が先だった）とします。
    * すると、スレッド1が `(3)` の `while (flag[0] == 1 && turn == 0)` を評価する時点では、スレッド0はすでに `(1) flag[0] = 1` を終えており、かつ `turn` は今スレッド1自身が書いた `0` のまま（スレッド0はすでに `turn = 1` を書き終えた後なので、もう `turn` を変えない）です。
    * したがって、スレッド1の待機条件 `flag[0] == 1 && turn == 0` は**必ず真**となり、スレッド1は `while` ループを抜けられません。これは「両方が同時に入った」という仮定に矛盾します。よって相互排除は厳密に成立します。

2. **活性（進行性・デッドロック／ライブロック不在）の証明：**

    * もしスレッド $j$ が残余セクションにいるなら `flag[j] == 0` なので、スレッド $i$ は `while` 条件が偽になり即座に入場できます（アルゴリズム1の欠点を克服）。
    * もし両方が同時に `while` ループで足止めされるとしたら、`turn == 1`（スレッド0が待つ条件）と `turn == 0`（スレッド1が待つ条件）が同時に成り立つ必要がありますが、`turn` は同時に2つの値を持てないため不可能です。先に `turn` を書いた側が必ずループを抜けて前進します。

3. **公平性（有界待機・飢餓の不在）の証明：**

    * スレッド0が `while (flag[1] == 1 && turn == 1)` で待っている間に、スレッド1がCSを終えて `flag[1] = 0` にしたとします。
    * もしスレッド0が動く前にスレッド1が猛スピードで次の周回に入り、`flag[1] = 1` の直後に **`turn = 0`** と書き換えた瞬間に、スレッド0の待機条件 `turn == 1` が偽へ反転します。逆にスレッド1側は `flag[0] == 1 && turn == 0` が真になって止まります。
    * したがって、スレッド0が待たされる回数は**高々1回（相手の1回分）**に厳密に抑えられ、飢餓は決して起きません。

> **【コラム：$N$ スレッドへの拡張：Lamport（ランポート）のパン屋のアルゴリズム（Bakery Algorithm）】**
>
> Dekker や Peterson は「2スレッド専用」のアルゴリズムですが、1974年にレスリー・ランポート（Leslie Lamport）は、任意の $N$ スレッド間で普通の共有変数だけで相互排除・進行性・公平性を満たす **パン屋のアルゴリズム（Bakery Algorithm）** を考案しました。
>
> 発想は、混雑したパン屋や銀行の窓口にある**整理券発券機**と同じです。
>
> 1. CSへ入りたいスレッド $i$ は、現在他の全員が持っている整理券番号の最大値 $+ 1$ を自分の番号 `number[i]` として取ります。
> 2. もし2つのスレッドが同時に発券機を引いて**まったく同じ整理券番号**を取ってしまった場合は、**「スレッドID（$i$）が小さい方を優先する」**という辞書式順序 `(number[i], i) < (number[j], j)` で勝敗を一意に決めます。
> 3. 自分より優先度の高い（番号が小さい）スレッドがすべてCSを終えるまで待ってから入場し、退場時に `number[i] = 0` に戻します。
>
> パン屋のアルゴリズムは「番号を計算している途中に他スレッドが未確定の `number[i] = 0` を読んで追い抜く」のを防ぐフラグ（`choosing[i] = 1`）まで考慮して設計されており、ハードウェアのアトミック命令を一切使わずに任意の $N$ スレッドのFIFOに近い公平な相互排除を実現できます。

### 4. 限界と補正（Critique & Adaptation）

Peterson のアルゴリズムは数学的に完璧に見えます。ところが、**現代のマルチコアPCやスマートフォン上で、上のC言語コードをそのまま実行すると、実は相互排除が破綻して2スレッドが同時にクリティカルセクションへ入ってしまう**ことがあります。なぜ数学的証明が現実のハードウェアで崩れるのでしょうか。

#### (1) 現代のマルチコアCPUにおける破綻：ストアバッファによる「Store-Load 並べ替え」

Peterson の証明には、**「各スレッドのメモリ書き込みと読み込みが、ソースコードに書いた順番通りに他コアへ観測される（逐次一貫性：Sequential Consistency）」**という暗黙の前提が置かれていました。

しかし、現代の高性能CPU（x86-64、ARM、RISC-V）は、[0-7節](../0/0-7.md)で見たキャッシュ無効化の待ち時間を隠蔽するために、各コアとキャッシュのあいだに **ストアバッファ（Store Buffer）** という小さな書き込み一時置き場を備えています。すると、次の現象が起きます（図4-2-3）。

1. スレッド0（コア0）が `flag[0] = 1; turn = 1;` を実行します。これらの書き込みはいったん**コア0自身のストアバッファ**に溜められ、まだ共有キャッシュ（他コアから見える場所）へは反映されていません。
2. コア0はストアバッファの反映を待たず、直後の `while` ループの読み込み **`load flag[1]` を追い越して先に実行**します（**Store-Load 並べ替え**）。この時点ではコア1の書き込みもまだ反映されていないため、コア0は **`flag[1] == 0`** と読んでしまい、**そのままCSへ突入します**。
3. まったく同じ瞬間に、コア1も `flag[1] = 1; turn = 0;` を自分のストアバッファへ積んだまま、追い越して **`load flag[0]`** を実行して **`flag[0] == 0`** を読み、**同じくCSへ突入します**。

さらに、コンパイラ自身の最適化（[2-7節](../2/2-7.md)）によっても、`flag[i] = 1` と `flag[j]` の読み込みの順序が入れ替えられたり、`while (flag[j] == 1)` がレジスタへキャッシュされて無限ループ化したりする危険があります。

#### (2) ビジーウェイトの非効率性とハードウェア支援への移行

さらに、ソフトウェア相互排除アルゴリズムには実用上の制約が2つ残ります。

1. **ビジーウェイト（スピン待ち）によるCPUと電力の浪費：** `while (flag[j] == 1 && turn == j) { }` は待機中ずっとCPUコアを100%回し続けるため、CSが長い場合や単一コア環境では非常に非効率です。
2. **多スレッド環境でのスケーラビリティ不足：** パン屋のアルゴリズムのように $N$ スレッドへ拡張できても、入場のたびに全 $N$ スレッドの配列を走査する $O(N)$ コストがかかり、動的にスレッド数が増減する現代のOSには向きません。

これらの限界を根本から解決するため、現代のCPUは「確認と書き込みの隙間（TOCTOU）」をハードウェアの1命令で不可分に閉じる **アトミック命令（Swap・CAS等）** と、メモリ順序を制御する **メモリバリア** を備えています。次節（[4-3節](4-3.md)）では、そのハードウェア支援の仕組みへ進みます。

### 理解度チェック（次節へ進む前の確認）

本節の失敗パターンと Peterson のアルゴリズムの成立条件を手計算で確認し、次節（[4-3節](4-3.md)）へ繋ぐ問いを置きます。

> **【確認の問い】**
>
> 1. **（アルゴリズム1とアルゴリズム3の反例トレース）**
>     本節3-(1)の5つの失敗作のうち、次の2つがそれぞれ「どの性質に違反し、どのような状況で破綻するか」を簡潔に説明してください。
>
>     * (a) アルゴリズム1（`while (turn != i) {}`）
>     * (b) アルゴリズム3（`flag[i] = 1; while (flag[j] == 1) {}`）
> 2. **（Peterson のアルゴリズムにおける順序の厳密性）**
>     Peterson のアルゴリズムの入口プロトコルは、① `flag[i] = 1;` → ② `turn = j;` → ③ `while (flag[j] == 1 && turn == j) {}` の順です。もし誤って ① と ② の順番を逆にして、**`turn = j;` を先に書き、その後で `flag[i] = 1;` を書く**ように変えてしまった場合、**相互排除が破綻する具体的なインターリービング**（スレッド0とスレッド1の実行順）を1つ示してください。
>
> 3. **（次節への伏線：メモリ順序逆転と1命令のアトミック操作）**
>     本節4-(1)で見た通り、現代のマルチコアCPUではストアバッファによって `flag[i] = 1` の書き込みと `flag[j]` の読み込みの順序が逆転し、Peterson のアルゴリズムが壊れることがあります。また、普通の共有変数だけでは多スレッド（$N$ 個）への拡張が煩雑です。では、CPUハードウェアが提供する「読出しと書込みを1命令で不可分に行う命令（**アトミック命令**）」と「順序逆転を防ぐ命令（**メモリバリア**）」は、どのような仕組みで動作するのでしょうか。
