### 前節（4-2）の確認問題の解答

前節の最後に提示した3つの問いの解答を確認します。問3がそのまま本節（ハードウェアのアトミック命令とメモリ一貫性モデル）の導入になります。

1. **アルゴリズム1とアルゴリズム3の反例トレース：**

    * **(a) アルゴリズム1（`while (turn != i) {}`）：** **活性（進行性）に違反**します。`0 → 1 → 0 → 1` と厳密に交互にしかクリティカルセクションへ入れないため、スレッド0が退場して `turn = 1` にした後、スレッド1が残余セクションで長時間休んでいる（あるいは終了した）と、スレッド0は二度と入場できなくなります（相互排除自体は保たれます）。
    * **(b) アルゴリズム3（`flag[i] = 1; while (flag[j] == 1) {}`）：** **活性（デッドロックの不在）に違反**します。スレッド0が `flag[0] = 1`、スレッド1が `flag[1] = 1` を同時に実行すると、互いに相手の旗が `1` であると観測して `while` ループから永久に出られなくなります（相互排除自体は保たれます）。

2. **Peterson のアルゴリズムで `turn = j` と `flag[i] = 1` の順序を逆にした場合の破綻：**
    `turn = j;` を先に書き、その後で `flag[i] = 1;` を書くように変えると、次のインターリービングで相互排除が破綻します。

    1. スレッド0が `turn = 1` を実行した直後、`flag[0] = 1` を書く前に中断されます。
    2. その間にスレッド1が `turn = 0` → `flag[1] = 1` を実行し、`while (flag[0] == 1 && turn == 0)` を評価します。この時点で `flag[0]` はまだ `0` なので、スレッド1は即座にクリティカルセクションへ入場します。
    3. 続いてスレッド0が再開して `flag[0] = 1` を立て、`while (flag[1] == 1 && turn == 1)` を評価します。`turn` はすでにスレッド1によって `0` へ上書きされているためループを抜け、**両スレッドが同時にクリティカルセクションへ入場**してしまいます。

3. **メモリ順序逆転と1命令のアトミック操作（本節への接続）：**
    現代のマルチコアCPUは、「読み込み・変更・書き込み（Read-Modify-Write）」をキャッシュコヒーレンシの排他調停によって1命令で不可分に実行する **アトミック命令（`amoswap` / CAS / LL-SC）** と、ストアバッファやアウトオブオーダー実行によるメモリ順序の逆転を必要な箇所で禁止する **メモリバリア（フェンス／Acquire・Release）** を備えています。本節ではこれらのハードウェア基盤を整理します。

## 4-3. ハードウェアのアトミック命令（Swap・CAS）とメモリ一貫性モデル

### 1. 動機（Why）：なぜソフトウェアだけでは相互排除を完結できないのか

前節（[4-2節](4-2.md)）で確認した通り、Dekker や Peterson のアルゴリズムは「すべてのメモリアクセスがプログラム記述順に全コアへ即座に見える」という理想的な前提（逐次一貫性）のもとでは、通常の読み書き命令だけで相互排除を達成できました。しかし、実用的なシステムと現代のマルチコアCPUにおいては、ソフトウェアのみの相互排除には次の3つの構造的な限界があります。

1. **ハードウェアの並べ替えによる破綻：** 現代のCPUはストアバッファやアウトオブオーダー実行を備えており、独立した書き込みと読み込みの順序を入れ替えます。通常のロード／ストア命令だけでは、コア間でのメモリ操作の順序を保証できません。
2. **スレッド数 $N$ への拡張コスト：** Peterson のアルゴリズムは2スレッド専用です。$N$ スレッドへ拡張したアルゴリズム（パン屋のアルゴリズム等）は、ロック獲得のたびに $O(N)$ 個の共有配列を走査する必要があり、スレッド数が増えるほどオーバーヘッドが線形に悪化します。
3. **読み取りと書き込みの分断：** 競合状態の根本原因は、「現在の値を読み取る（Load）」「条件を確認して新しい値を決める（Modify）」「メモリへ書き戻す（Store）」という一連の処理が別々の命令に分かれており、その隙間に他コアが割り込める点にあります。

この問題を根本から解決するために、現代のCPUはハードウェアレベルで次の2つの機能を提供しています。

* **アトミックな Read-Modify-Write（RMW）命令：** 読み込み・変更・書き込みを1つの不可分な操作として実行し、他コアの割り込みを物理的に禁止します。
* **メモリ一貫性モデルとメモリバリア（フェンス）：** 異なるコア間でメモリ操作がどの順序で観測されるかを定義し、必要な箇所で並べ替えを禁止します。

### 2. 具体例と動作イメージ（Toy Model）

ハードウェアの内部機構に入る前に、2つの小さな例で `amoswap` と `CAS` の動きを手で追ってみます。

#### 実験A：`amoswap` による最小のスピンロック

RISC-V（RV64GC の `A` 拡張）には、メモリ上の値とレジスタの値を不可分に交換する `amoswap.w` 命令があります。

```text
amoswap.w rd, rs2, (rs1)
  動作（全体が1つの不可分操作）:
    temp     = mem[rs1]
    mem[rs1] = rs2
    rd       = temp
```

共有変数 `lock` を `0`（解放状態）で初期化し、獲得時に `1` を書き込むことを考えます。スレッドA（コア0）とスレッドB（コア1）が完全に同じタイミングで `amoswap.w t0, t1, (a0)`（`t1 = 1`, `a0 = &lock`）を発行したとします。

```text
初期状態: lock = 0

時刻 | コア0（スレッドA）                  | コア1（スレッドB）                  | メモリ (lock)
-----+-------------------------------------+-------------------------------------+--------------
t1   | amoswap.w t0, 1, (&lock) 発行       | amoswap.w t0, 1, (&lock) 発行       | 0
     | → ハードウェアがコア0を先に調停     | → コア0の完了まで待機               |
t2   | 旧値 0 を t0 に取得、1 を書込完了   | （待機中）                          | 1
t3   | t0 == 0 なのでロック獲得成功        | 調停を獲得: 旧値 1 を t0 に取得、   | 1
     | クリティカルセクションへ進入        | 1 を書込完了                        |
t4   | （クリティカルセクション実行中）    | t0 == 1 なので獲得失敗 → 再試行     | 1
```

ハードウェアがメモリ（キャッシュライン）への排他アクセスを調停するため、2つの `amoswap` が同時に実行されても必ず直列化されます。結果として、**旧値 `0` を受け取れるのは厳密に1スレッドだけ**であり、もう1つは必ず `1` を受け取ります。これにより、スレッド数 $N$ がいくつであっても $O(1)$ の命令で相互排除が成立します。

#### 実験B：CAS（Compare-And-Swap）によるロックフリー加算

ロックを使わずに共有カウンタ `count` を安全にインクリメントする手法として、**CAS（Compare-And-Swap）** があります。CAS は以下の3引数をとり、不可分に比較と交換を行う抽象操作です。

```c
// ハードウェアが不可分に実行する等価ロジック
bool CAS(int *addr, int expected, int new_val) {
    if (*addr == expected) {
        *addr = new_val;
        return true;   // 期待値と一致したので更新成功
    }
    return false;      // 他者が書き換えていたので更新失敗
}
```

これを使うと、ロックを一切持たないカウンタ加算は次のように書けます。

```c
void atomic_inc(int *count) {
    int old, next;
    do {
        old  = *count;          // 1. 現在値を読む
        next = old + 1;         // 2. 次の値を計算する
    } while (!CAS(count, old, next)); // 3. 変わっていなければ更新、変わっていればやり直し
}
```

初期値 `count = 10` に対してスレッドAとスレッドBが同時に `atomic_inc` を実行したトレースを追います。

1. スレッドA・Bともに `old = 10`, `next = 11` を計算します。
2. スレッドAの `CAS(&count, 10, 11)` が先に調停を勝ち取り、`*count == 10` が成立して `count` が `11` になり `true` を返して終了します。
3. スレッドBの `CAS(&count, 10, 11)` が実行されますが、現在の `*count` はすでに `11` であり `expected (10)` と一致しないため `false` を返します。
4. スレッドBはループを再実行し、今度は `old = 11`, `next = 12` を計算して `CAS(&count, 11, 12)` に成功します。最終結果は `12` となり、更新消失は起きません。

### 3. 構造・アルゴリズム・実装（What）

#### (1) ハードウェアのアトミック命令の2大方式

現代のISAが提供するアトミック命令は、大きく **単一命令型（AMO / LOCKプレフィックス）** と **予約ペア型（LL/SC）** の2方式に分類されます。RISC-V の `A` 拡張（Atomic Extension）はこの両方を備えています。

| 方式 | RISC-V（`A` 拡張）の例 | x86-64 の例 | 特徴 |
| :--- | :--- | :--- | :--- |
| **単一RMW命令** | `amoswap.w`, `amoadd.w`, `amoand.w` | `LOCK XCHG`, `LOCK XADD`, `LOCK CMPXCHG` | 1命令で完結。メモリコントローラやキャッシュ側で直接演算（Near-Memory / Cache Atomic）しやすく高競合に強い。 |
| **LL/SC ペア** | `lr.w`（Load-Reserved）＋ `sc.w`（Store-Conditional） | （なし。`CMPXCHG` を使用） | 2命令のペアで任意のRMW（CASや複雑な条件更新）を合成可能。ARM（`LDXR`/`STXR`）も同方式。 |

RISC-V における **LL/SC（Load-Reserved / Store-Conditional）** の動作は以下の通りです。

* **`lr.w rd, (rs1)`：** アドレス `rs1` から32ビット値を読み込み、同時にそのアドレスを含むキャッシュラインに対して予約（Reservation）をハードウェアに登録します。
* **`sc.w rd, rs2, (rs1)`：** `lr.w` の実行後、**一度も予約が破棄されていなければ** `rs2` を `(rs1)` へ書き込み、`rd` に `0`（成功）を返します。もしその間に他コアが同じキャッシュラインへ書き込んだり、割り込み・コンテクストスイッチが発生したりして予約が失われていれば、書き込みを行わず `rd` に非ゼロ値（通常 `1`：失敗）を返します。

たとえば、RISC-V で CAS（`*a0 == a1` なら `a2` を書き込む）を `lr.w`/`sc.w` で実装すると次のようになります。

```asm
# a0: addr, a1: expected, a2: new_val
# 戻り値 a0: 1=成功, 0=失敗
cas:
    lr.w  t0, (a0)        # 現在値を読み込み、キャッシュラインを予約
    bne   t0, a1, fail    # expected と不一致なら失敗へ
    sc.w  t1, a2, (a0)    # 予約が有効なら new_val を書き込み（成功時 t1 = 0）
    bnez  t1, cas         # 予約が破棄されていたら最初から再試行
    li    a0, 1
    ret
fail:
    li    a0, 0
    ret
```

#### (2) キャッシュコヒーレンシによるアトミック性の実現

古典的なマルチプロセッサでは、アトミック命令の実行中にシステムバス全体をロック（**バスロック**）して他コアのメモリアクセスを止めていました。しかし、コア数が増えるとバスロックはシステム全体の性能を著しく低下させます。

現代のマルチコアCPUは、[0-7節](../0/0-7.md)で触れたキャッシュコヒーレンシプロトコル（MESI など）を利用してアトミック性を実現しています。あるコアが `amoswap` や `LOCK CMPXCHG` を実行するとき、CPUは以下の手順を踏みます。

1. 対象アドレスのキャッシュラインを **Modified（排他変更可）** 状態で取得するため、他コアへ無効化要求（RFO: Read-For-Ownership）を送ります。
2. ラインが自コアのキャッシュ上で排他状態になった後、Read-Modify-Write 処理が終わるまで、他コアからのそのラインに対するスヌープ要求（読み書き要求）への応答を一時的に保留します（**キャッシュロック**）。
3. 処理完了後に保留を解除します。

この仕組みにより、無関係なアドレスへアクセスしている他コアを一切止めることなく、対象キャッシュライン単位で厳密なアトミック性を保証できます。

#### (3) メモリ一貫性モデル（Memory Consistency Model）

アトミック命令で1変数の操作を不可分にしても、「クリティカルセクション内の通常データの読み書き」と「ロック変数の読み書き」の順序がCPUによって入れ替えられると、データ保護は破綻します。

複数コアから見たメモリ操作の観測順序に関するハードウェアの仕様を **メモリ一貫性モデル** と呼びます。メモリアクセスの並べ替えには、先行命令と後続命令の組み合わせにより **4種類**（Load-Load, Load-Store, Store-Store, Store-Load）があります。

| モデル名 | 代表アーキテクチャ | 許容される並べ替え | 特徴 |
| :--- | :--- | :--- | :--- |
| **逐次一貫性（SC）** | （理論モデル） | なし（すべて禁止） | 最も直感的だが、ストアバッファや投機的ロードを無効化する必要があり性能が低い。 |
| **TSO（Total Store Order）** | x86-64, SPARC | **Store → Load のみ** | ストアバッファによる先読みだけを許容。多くの並行バグが起きにくいが、ハードウェアの電力・回路コストが高い。 |
| **弱順序（Weak / Relaxed）** | RISC-V（RVWMO）, ARM | **4種類すべて** | ハードウェアの最適化自由度と電力効率が高い。順序保証が必要な箇所ではソフトウェアが明示的にバリアを挿入する。 |

#### (4) メモリバリア（フェンス）と Acquire / Release セマンティクス

x86-64（TSO）では Load-Load・Load-Store・Store-Store の並べ替えが起きないため通常の読み書きでもロックの順序が保たれやすいのに対し、弱順序モデル（RISC-V RVWMO 等）では4種類すべての並べ替えが許容されるため、ロックの獲得・解放を正しく機能させるにはメモリバリア（フェンス）によって明示的に並べ替えを制限する必要があります。

RISC-V では、汎用的な完全フェンス命令 `fence rw, rw`（この命令より前のすべての読み書きが完了するまで、後のすべての読み書きを開始させない。次節[4-4節](4-4.md)の xv6 実装では `__sync_synchronize()` として利用）に加え、AMO命令自体に軽量な片道バリアである **Acquire（`.aq`）** と **Release（`.rl`）** のフラグを付与できます。

```text
  [ ロック獲得: amoswap.w.aq ]  ──→ Acquire バリア（下から上への追い越しを禁止）
      ↓                                ▲
      │  クリティカルセクション内の     │ ✕ 外（上）へ漏れてはならない
      │  共有データの読み書き           │
      │                                ▼ ✕ 外（下）へ漏れてはならない
  [ ロック解放: amoswap.w.rl ]  ──→ Release バリア（上から下への追い越しを禁止）
```

* **Acquire セマンティクス（獲得・`.aq`）：** この命令より**後**にあるすべての読み書きが、Acquire 命令より**前**へ並べ替えられることを禁止します。これにより、「ロックを獲得する前にクリティカルセクション内の共有データを先読みしてしまう」事態を防ぎます。
* **Release セマンティクス（解放・`.rl`）：** この命令より**前**にあるすべての読み書きが、Release 命令より**後**へ並べ替えられることを禁止します。これにより、「共有データの更新が他コアに見える前にロックが解放されてしまう」事態を防ぎます。

このように、Acquire と Release は対になって「クリティカルセクション内のメモリ操作を内側に閉じ込める」役割を果たします。なお、ロックの外側にある操作が内側に移動することは安全性（相互排除）を損なわないため禁止されず、完全フェンス（`fence rw, rw`）よりも性能上のオーバーヘッドを抑えられます。

> **【コラム：CASの盲点「ABA問題」と対策】**
>
> CAS は「現在の値が期待値 `A` と一致しているか」だけを比較するため、値が **`A → B → A`** と変化して元に戻った場合でも「変化しなかった」と誤認します。これを **ABA問題** と呼びます。
>
> 典型例はロックフリーな単方向連結リスト（スタック）の `pop` 操作です。
>
> 1. スタックが `Top -> A -> B -> C` の状態のとき、スレッド1が `pop` を開始し、`old_top = A`、`next = B` を読み取った直後に中断されます。
> 2. その間にスレッド2が `A` を pop し、さらに `B` も pop してメモリ解放（または再利用）したあと、`A` を再び push します。この時点でスタックは `Top -> A -> C`（`B` はすでに無効）となっています。
> 3. 再開したスレッド1が `CAS(&Top, A, B)` を実行します。現在の `Top` はたまたま `A` なので CAS は成功してしまい、`Top` がすでに解放済みの不正ノード `B` を指してデータ構造が破壊されます。
>
> **対策：**
>
> * **タグ付きポインタ（Tagged Pointer / Double-Width CAS）：** ポインタの上位未使用ビットや隣接ワードに単調増加するバージョンカウンタを埋め込み、`(A, v=1)` と `(A, v=2)` を別物として区別します。
> * **LL/SC の活用：** LL/SC は「値の一致」ではなく「予約後にメモリが書き換えられたか」をハードウェアで監視するため、値が `A` に戻っても `sc` は失敗し、原理的にABA問題が発生しません。

### 4. 限界と補正（Critique & Adaptation）

ハードウェアのアトミック命令を使えば「正しさ（安全性）」は確保できますが、実装の仕方によってはマルチコア環境で深刻な性能劣化を引き起こします。

#### (1) キャッシュライン・ピンポンと TTAS による補正

実験Aで示した単純な `amoswap` スピンロック（Test-and-Set: TAS）を多数のコアで同時に競合させると、性能が大きく悪化します。ロック解放を待っているすべてのコアがループのたびに `amoswap`（書き込みを伴う命令）を発行するため、各コアがキャッシュラインの排他権（`Modified` 状態）を奪い合い、キャッシュラインがインターコネクト上を頻繁に往復する（**キャッシュライン・ピンポン**）ためです。

**補正（Test-and-Test-and-Set: TTAS）：**
ループの内側でいきなり `amoswap` を連打するのではなく、まずは通常のロード命令（読み取り専用）で `lock == 0` になるのを待ちます。

```c
void lock_ttas(volatile int *lock) {
    while (1) {
        // 1. 通常のロードで待機（全待機コアが Shared 状態でキャッシュヒットし続ける）
        while (*lock != 0) {
            // バスやインターコネクトにトラフィックを一切発生させない
        }
        // 2. 0 に見えたときだけアトミック命令で獲得を試みる
        if (__sync_lock_test_and_set(lock, 1) == 0) {
            return;
        }
    }
}
```

TTAS では、待機中のすべてのコアがロック変数のキャッシュラインを **Shared（共有）** 状態で保持し、自コアの L1 キャッシュにヒットし続けるため、インターコネクトの帯域を消費しません。ロック保持者が `0` を書き込んだ瞬間にだけ無効化が通知され、そのとき初めて各コアが `amoswap` を試行します。

#### (2) 偽共有（False Sharing）

キャッシュコヒーレンシは変数単位ではなく **キャッシュライン単位（一般に 64 バイト）** で管理されます。そのため、論理的には完全に独立した2つの変数がたまたま同じ 64 バイトのキャッシュライン上に隣接して配置されると、2つのコアがそれぞれの変数を更新するたびにキャッシュライン全体の無効化と転送が連鎖します。これを **偽共有（False Sharing）** と呼びます。

```text
[ 同一の 64 バイトキャッシュライン ]
+-------------------+-------------------+---------------------------+
| core0_counter (8B)| core1_counter (8B)| ... 残り 48 バイト ...    |
+-------------------+-------------------+---------------------------+
        ▲                   ▲
   Core 0 が更新       Core 1 が更新  → 論理的には無関係なのに Modified/Invalid が往復
```

**補正：** 複数コアから高頻度に書き込まれる独立した変数（コアごとの統計カウンタやロック構造体など）は、`_Alignas(64)` / `alignas(64)`（C11）や明示的なパディング配列を用いて、別々のキャッシュラインへ分離配置します。

#### (3) LL/SC のスプリアス失敗とライブロック

LL/SC（`lr.w` / `sc.w`）は柔軟でABA問題にも強いですが、`lr` と `sc` の間に長い命令列や他のメモリアクセスを挟むと、キャッシュ追い出しやタイマ割り込み、偽共有による他コアの書き込みによって予約が破棄されます（**スプリアス失敗**）。また、2つのコアが同時に `lr` を発行して互いに予約を潰し合い続ける **ライブロック** が起きる可能性もあります。そのため、RISC-V 仕様では `lr`/`sc` の間に置く命令を最小限（最大16命令程度の単純な算術・分岐命令のみで、他のロード／ストアを含めないこと）に制限することで、前進性（Forward Progress）を保証しています。

### 理解度チェック（次節へ進む前の確認）

本節の TTAS のキャッシュ状態遷移・Acquire/Release バリア・偽共有の対策を確認し、次節（[4-4節](4-4.md)）へ繋ぐ問いを置きます。

> **【確認の問い】**
>
> 1. **（TTAS のキャッシュ状態遷移）**
>     コア0が TTAS スピンロックを保持しており、コア1とコア2がロック解放を待っている状態を考えます。MESI プロトコルにおいて、(a) コア1・2が内側の `while (*lock != 0)` ループを回っている間、各コアのキャッシュラインはどの状態にあるでしょうか。(b) コア0が `*lock = 0` を書き込んだ直後、コア1・2のキャッシュラインはどう遷移するでしょうか。
>
> 2. **（Acquire / Release の欠落）**
>     ある共有データ `data` をロック `lock` で保護しています。ロック解放時に Release バリア（`.rl`）を付け忘れ、通常のストア命令で `lock = 0` を書き込んだ場合、弱順序モデル（RISC-V RVWMO）のCPU上でどのようなデータ不整合が起き得るか、命令の並べ替えの観点から説明してください。
>
> 3. **（偽共有のメモリ配置）**
>     64ビット環境（キャッシュラインサイズ 64 バイト）において、`struct counter { uint64_t val; };` の配列 `struct counter counters[4];` を用意し、4つのCPUコアがそれぞれ `counters[cpu_id].val++` を1億回実行したところ、1コア実行時より遅くなりました。この原因を説明し、C言語の構造体定義を修正して問題を解消してください。
