### 前節（4-6）の確認問題の解答

前節の最後に提示した3つの問いの解答を確認します。問3がそのまま本節（シグナルと非同期シグナル安全性）の導入になります。

1. **Mesa式モニタで `while` ではなく `if` を使ったときの破綻：**
    バッファが空（`count == 0`）の状態から、次のインターリービングでデータ破壊が起きます。

    1. 消費者 C1 が `get()` へ入り、`count == 0` なので `cond_wait(&not_empty, &mtx)` で `mtx` を解放して眠る。
    2. 生産者 P が `put()` へ入り、データを1個入れて `count = 1` にし、`cond_signal(&not_empty)` を呼んで C1 を `RUNNABLE` にしたあと、`mutex_unlock(&mtx)` で退場する。
    3. 起こされた C1 が `mtx` を再獲得する直前に、別の消費者 C2 が横入りして `mtx` を獲得し、唯一の1個を取り出して `count = 0` に戻して退場する。
    4. 続いて `mtx` を再獲得した C1 は、`if` で書かれていると条件を再検査せずそのまま空のバッファから不正なデータを読み出してしまう。

2. **誰も待機していないときの `sem_signal` と `cond_signal` の違い：**

    * **(a) セマフォの `sem_signal(&s)`：** セマフォは内部に整数カウンタ（状態）を持つため、誰も待っていなくてもカウンタが $+1$ されて記憶されます。したがって、直後に別スレッドが `sem_wait(&s)` を呼ぶと、カウンタを $-1$ して**眠らずに即座に通過**します。
    * **(b) 条件変数の `cond_signal(&cv)`：** 条件変数は記憶を持たない（状態レスな）待機キューです。誰も待っていないときに `cond_signal` を呼んでも**通知は空振りして消滅**します。したがって、直後に別スレッドが `cond_wait(&cv, &mtx)` を呼ぶと（共有状態変数によるガードがない限り）そのまま眠りにつきます。

3. **単一スレッドでも起きる「非同期シグナル」による自己デッドロック（本節への接続）：**
    スレッドが1本しかなくても、`malloc()` が内部のヒープ管理用ミューテックスを保持している途中で `SIGINT` などの非同期シグナルが届くと、同じスレッド自身の実行が一時中断され、同じスタック上でシグナルハンドラが走り出します。そのハンドラの中で再び `malloc()` や（内部で `malloc`／ロックを使う）`printf()` を呼ぶと、**すでに自分自身が握っているロックの解放を自分自身で永遠に待ち続ける自己デッドロック**に陥ります。

## 4-7. シグナルと非同期割り込みにおける競合・非同期シグナル安全性

### 1. 動機（Why）：なぜ「スレッドを1本しか使っていないプログラム」でも並行性の競合が起きるのか

[4-1節](4-1.md)から[4-6節](4-6.md)まで、複数のスレッドやCPUコアが共有メモリへ同時アクセスするときに起きる競合状態と、それを制御する同期プリミティブ（アトミック命令・スピンロック・スリープロック・セマフォ・モニタ・条件変数）を体系的に見てきました。

ここで、「それならマルチスレッドを使わず、単一スレッドの素朴なCプログラムを書いていれば、競合状態やデッドロックとは無縁でいられるのではないか」と思えるかもしれません。

しかし、UNIX系OS（Linux等）上で動くユーザプログラムには、**スレッドを1本しか作っていなくても非同期に割り込んでくる並行処理の仕組み**が存在します。それが **POSIX シグナル（Signal）** です。

* ユーザが端末で `Ctrl+C` を押した（`SIGINT`）。
* [3-2節](../3/3-2.md)で `fork()` した子プロセスが終了した（`SIGCHLD`）。
* タイマが満了した（`SIGALRM`）、あるいは別プロセスから停止要求が届いた（`SIGTERM`）。

これらはハードウェアの割り込み（[3-1節](../3/3-1.md)）をOSがソフトウェア的に抽象化してユーザプロセスへ届ける「**ソフトウェア割り込み**」です。シグナルハンドラを登録しておくと、メイン処理がどの1命令を実行している最中であっても強制的に中断され、同じスレッドの文脈でハンドラ関数が割り込み実行されます。

その結果、[4-4節](4-4.md)で見た「OSカーネル内でのスピンロックと割り込みハンドラの自己デッドロック」とまったく同じ構造の問題が、ユーザ空間のプログラムでも発生します。本節では[第4部](../index.md#part-4)の締めくくりとして、シグナルの配送メカニズム、**非同期シグナル安全性（Async-Signal-Safety）**の条件、そして実務で安全にシグナルを扱う設計パターンを整理します。

### 2. 具体例と動作イメージ（Toy Model）

仕組みの細部に入る前に、単一スレッドプログラムで実際に起きる2つの代表的なシグナル事故を追ってみます。

#### 実験A：ハンドラ内で `printf()` や `malloc()` を呼んで起きる自己デッドロック

次のCプログラムは、「`Ctrl+C`（`SIGINT`）が押されたらメッセージを表示して終了フラグを立てる」という、初学者や実務でもつい書いてしまいがちなコードです。

```c
#include <signal.h>
#include <stdio.h>
#include <stdlib.h>

void handler(int sig) {
    printf("Caught signal %d\n", sig);    // 危険：非同期シグナル安全ではない
    exit(1);                              // 危険：exit() も非同期シグナル非安全（本来は _exit() を使用）
}

int main(void) {
    signal(SIGINT, handler);
    while (1) {
        char *p = malloc(1024);           // ヒープ管理ロックを獲得・解放しながら動作
        printf("working...\n");           // 標準出力ロックを獲得・解放しながら動作
        free(p);
    }
}
```

このプログラムは99%のケースでは普通に動いてしまいます。しかし、メインループの `printf("working...\n")` が**標準出力 `stdout` の内部ミューテックスを保持しているまさにその一瞬**に `Ctrl+C` が押されると、次の連鎖で完全にフリーズします（図4-7-1）。

1. `main` の `printf` が `stdout` のロックを獲得し、バッファへ文字を書き込んでいる途中で `SIGINT` が到着します。
2. OSは `main` の実行を中断し、同じスレッド上で `handler()` を呼び出します。
3. `handler()` が `printf("Caught signal...")` を呼び、内部で**同じ `stdout` のロックを獲得しようとしてブロック**します。
4. しかし、ロックを解放できるのは中断された `main` 側の `printf` だけであり、`main` が再開できるのは `handler()` が終了して戻った後だけです。

こうして、スレッドが1本しか存在しないのに**自己デッドロック**が成立します。たとえロックを使っていない単純な静的バッファであっても、更新途中でハンドラが割り込めばデータ構造が壊れます。[4-4節](4-4.md)で見た「カーネル内の `acquire(&cons.lock)` とキーボード割り込み `consoleintr()` の自己デッドロック」と完全に同型の現象です。

#### 実験B：複数の `SIGCHLD` が同時に届くと「1回分に潰れる」現象

[3-2節](../3/3-2.md)の最後で触れた通り、親プロセスが子プロセスを3つ `fork()` し、子が終了するたびに届く `SIGCHLD` ハンドラの中で `waitpid(-1, NULL, WNOHANG)` を**1回だけ**呼んでゾンビを回収するコードを書いたとします。

```c
// 失敗例：ハンドラ内で waitpid を 1 回しか呼ばない
void sigchld_handler(int sig) {
    waitpid(-1, NULL, WNOHANG);   // 2人目以降の子がゾンビのまま残ることがある
}
```

もし子プロセス1が終了して `SIGCHLD` ハンドラを実行している最中に、**子プロセス2と子プロセス3がほぼ同時に終了**すると、標準のPOSIXシグナルは回数カウンタではなく**1ビットの保留フラグ**で管理されているため、2発分の `SIGCHLD` が**1ビットの「保留あり（`1`）」へ合体（結合：Coalesce）**されてしまいます。その結果、ハンドラはあと1回しか呼ばれず、3人目の子プロセスが永久にゾンビとして取り残されます。

### 3. 構造・アルゴリズム・実装（What）

#### (1) POSIX シグナルの配送メカニズム（ビットマスクとシグナルフレーム）

OSカーネルがユーザプロセスへシグナルを届ける仕組みは、**「送信（保留ビットを立てる）」**と**「配送（ユーザ空間へ戻る瞬間にハンドラへ迂回させる）」**の2段階に分かれています（図4-7-2）。

カーネルは各プロセス（およびスレッド）のPCB内に、シグナル番号（1〜31等）ごとに対応する **2本のビットマスク** を保持しています。

1. **`pending`（保留ビットマスク）：** まだプロセスへ配送されていない到着済みシグナルの集合です。シグナル $k$ が送られると、カーネルは `pending` の $k$ ビット目を `1` にセットします（すでに `1` ならそのまま上書きされるため、実験Bの結合が起きます）。
2. **`blocked`（ブロック／マスクビットマスク）：** 現在一時的に配送を保留（遅延）するようプロセス自身が指定しているシグナルの集合です。

カーネルがシステムコールやタイマ割り込みの処理を終えて、**S-mode から U-mode のユーザプロセスへ復帰（`usertrapret` / `sret`）する直前**に、カーネルはビット演算

$$
\text{deliverable} = \text{pending} \;\mathbin{\&}\; (\sim \text{blocked})
$$

を評価します。ここに `1` のビットがあれば、その最小のシグナル番号 $k$ について `pending` ビットを `0` に戻し、次の手順でハンドラを起動します。

1. **ユーザスタック上へのシグナルフレーム構築：** カーネルは現在のユーザレジスタ群（元の復帰先 `sepc` や汎用レジスタ、`blocked` マスク）を、ユーザプロセスのスタック上（x86-64では[1-3節](../1/1-3.md)の Red Zone 128バイトを飛び越えた先）へ退避します。
2. **ハンドラへの迂回：** ユーザへの復帰先 `sepc` を登録済みの **`handler(k)` の先頭アドレス**へ差し替え、さらにハンドラの戻り番地（`ra` 等）に **トランポリン用の `sigreturn` システムコール** を仕込んで U-mode へ戻ります。
3. **`sigreturn` による元の処理への復帰：** ユーザ空間で `handler(k)` が実行を終えて `ret` すると、自動的に `sigreturn` システムコールが呼ばれます。通常の関数リターンだけでは中断時点の caller-saved を含む全レジスタと元の `blocked` マスクを復元できないため、カーネルへ一度戻ってユーザスタック上のシグナルフレームから一括復元し、中断された元の命令へ復帰します。

#### (2) 再入可能性（Reentrancy）と非同期シグナル安全関数

実験Aのように、ある関数の実行途中でシグナルハンドラが割り込み、同じ関数（または同じ内部状態を共有する別関数）が入れ子で呼び出されても壊れない性質を **再入可能（Reentrant）** と呼びます。

POSIX規格では、シグナルハンドラの内部から安全に呼び出せる関数を **非同期シグナル安全（Async-Signal-Safe）関数** として厳格にリストアップしています。

| 分類 | 代表的な関数 | 安全／危険の理由 |
| :--- | :--- | :--- |
| **非同期シグナル安全**（ハンドラ内で呼べる） | **`write`**, **`read`**, **`_exit`**, **`waitpid`**, **`kill`**, **`sigaction`**, **`sigprocmask`** | 主にカーネルへの薄いシステムコールラッパーであり、ユーザ空間の共有静的バッファやユーザ空間ロックを使わないため。 |
| **非同期シグナル非安全**（ハンドラ内で厳禁） | **`printf`**, **`malloc`**, **`free`**, **`exit`**, **`pthread_mutex_lock`**, **`strtok`** | ユーザ空間に共有の静的データ構造（ヒープ管理リスト・`FILE` バッファ等）と内部ミューテックスを持ち、途中割り込みで自己デッドロックやデータ破壊を起こすため。 |

ここで混同しやすいのが、**スレッド安全（Thread-Safe）と非同期シグナル安全の違い**です。`printf()` や `malloc()` は内部でミューテックスを使っているため「マルチスレッドから同時に呼んでも安全な（スレッド安全な）」関数です。しかし、**ミューテックスを使っているからこそ、同一スレッドへ割り込むシグナルハンドラから呼ぶと自己デッドロックを起こす（非同期シグナル非安全になる）**のです。また、通常の `exit()` は `stdio` のバッファフラッシュを行うため危険であり、ハンドラから即座に終了したい場合はカーネルへ直接終了を依頼する **`_exit()`** を使います。

#### (3) 安全なシグナル処理の 3 大設計パターン

では、現実のプログラムではシグナルをどう処理すれば安全なのでしょうか。実務で確立されている3つの定石パターンを整理します（図4-7-3）。

1. **パターン1：`volatile sig_atomic_t` フラグ方式（最も基本）**
    シグナルハンドラの中では複雑な処理や `printf`・`malloc` を一切行わず、**「専用の整数フラグを `1` に立てるだけ」**で即座に終わります。実際の後片付けやログ出力は、メインループ側でフラグを定期的に確認して行います。
    ```c
    static volatile sig_atomic_t stop_requested = 0;

    void handler(int sig) {
        stop_requested = 1;   // 1命令の不可分書込だけをして即座に終了
    }
    ```
    ここで **`volatile`**（[2-7節](../2/2-7.md)：メインループの `while (!stop_requested)` が最適化で無限ループ化するのを防ぐ）と、**`sig_atomic_t`**（単一スレッドとハンドラの間で読み書きが途中で分断されないことがC規格で保証された整数型）の両方を必ず付けます。

2. **パターン2：`sigprocmask()` によるクリティカルセクションの保護（`push_off`/`pop_off` と同型）**
    メイン側とシグナルハンドラが共有するデータ構造（例：ジョブ一覧リスト）をメイン側が更新する短い区間だけ、**`sigprocmask(SIG_BLOCK, &mask, &oldmask)`** で対象シグナル（`SIGCHLD` 等）の配送を一時的にブロックし、更新が終わったら `SIG_SETMASK` で元へ戻します。これは、[4-4節](4-4.md)でカーネルがスピンロックの前後で `push_off()` / `pop_off()` によってハードウェア割り込みを禁止した設計と完全に同じ原理です。
    また、実験Bの `SIGCHLD` の結合に対しては、ハンドラ内で `while (waitpid(-1, NULL, WNOHANG) > 0) {}` と**回収できるゾンビが尽きるまでループする**ことで取りこぼしを防ぎます。

3. **パターン3：Self-Pipe Trick / `signalfd` / `sigwait` による「同期イベント化」**
    `select` や `poll`/`epoll`（[5-3節](../5/5-3.md)）でI/Oを待っているサーバプログラムでは、ハンドラ内から非同期シグナル安全な **`write()` で自分自身のパイプへ1バイト書き込む（Self-Pipe Trick）** ことで、非同期のシグナルを通常のファイル読出しイベントへ変換してメインループで安全に処理できます。Linux固有の **`signalfd()`** や、マルチスレッド環境での **`sigwait()`**（後述）も同じ「非同期を同期へ変換する」発想です。

> **【コラム：低速システムコールの中断（`EINTR`）と `SA_RESTART`】**
>
> プロセスが `read()` や `accept()`、`wait()` のような完了まで時間のかかるシステムコール（低速システムコール）の中で `SLEEPING` している最中に、捕獲対象のシグナルが届くと何が起きるでしょうか。
>
> カーネルはシグナルを配送するためにプロセスを途中で起こし、ハンドラを実行させます。ハンドラから戻ったあと、中断された `read()` は自動的には再開されず、戻り値 **`-1`**、エラー番号 **`errno = EINTR`（Interrupted System Call）** を返して失敗することがあります。
>
> これを放置すると、たとえば端末サイズ変更（`SIGWINCH`）や子プロセス終了（`SIGCHLD`）が届いただけでファイル読み込みが予期せずエラー終了してしまいます。実務では、① `sigaction()` で **`SA_RESTART`** フラグを立ててカーネルに可能な限りシステムコールを自動再実行させること、② それでも一部のシステムコール（タイムアウト付き `poll` や `connect` 等）は `EINTR` を返すため、呼び出し側で `while ((n = read(...)) < 0 && errno == EINTR) {}` と再試行ループを書くこと、の2段構えで対処します。

### 4. 限界と補正（Critique & Adaptation）

#### (1) `errno` の破壊とハンドラ内での退避・復元

非同期シグナル安全なシステムコール（`write()` や `waitpid()`）だけを使ってハンドラを書いていても、見落としやすい細部があります。それは、スレッドごとのグローバル変数 **`errno`** の上書きです。

メイン処理でシステムコールが失敗して `errno = ENOENT` がセットされ、直後に `if (errno == ENOENT)` を検査しようとした**まさにその瞬間**にシグナルハンドラが割り込み、ハンドラ内の `waitpid()` が `errno = ECHILD` へ書き換えてしまうと、メイン側のエラー判定が壊れてしまいます。

**補正：** シグナルハンドラの中でシステムコールを1回でも呼ぶ場合は、必ず**ハンドラの先頭で `int saved_errno = errno;` と退避し、末尾で `errno = saved_errno;` と復元する**のが鉄則です。

```c
void sigchld_handler(int sig) {
    int saved_errno = errno;                 // 1. 元の errno を退避
    while (waitpid(-1, NULL, WNOHANG) > 0)   // 2. 結合された全ゾンビをループ回収
        ;
    errno = saved_errno;                     // 3. 元の errno を復元
}
```

#### (2) 古い `signal()` の移植性問題と `sigaction()` の利用

歴史的な経緯により、古い `signal(SIGINT, handler)` 関数はOSの系統（System V 系 vs BSD 系）によって、「1回ハンドラが呼ばれるとデフォルト動作へリセットされるか」「ハンドラ実行中に同じシグナルがブロックされるか」「`SA_RESTART` が有効か」といった挙動がバラバラでした。現代のPOSIXプログラミングでは `signal()` を使わず、これらのフラグを明示的に指定できる **`sigaction()`** を常に使用します。

#### (3) マルチスレッド環境でのシグナル配送と `sigwait` 専用スレッドパターン

シグナルはもともと「1プロセス＝1スレッド」の1970年代UNIXで設計された仕組みであり、現代のマルチスレッドプログラムとは相性が良くありません。

* シグナルハンドラの設定（どの関数を呼ぶか）は**プロセス全体で1つ共有**されます。
* 一方、`blocked`（シグナルマスク）は**スレッドごとに独立**して持ちます。
* 外部からプロセス宛てに `SIGINT` や `SIGTERM` が届いたとき、そのシグナルをブロックしていない**どのスレッドへ配送されるかは不定**です。

そのため、マルチスレッドプログラムで非同期シグナルハンドラを直接使うと制御が非常に煩雑になります。この限界に対する実務の標準的な補正が、**「全スレッドでシグナルをブロックし、専用の1スレッドだけが `sigwait()` で同期的に受け取る」**パターンです。

1. `main()` の冒頭で新しいスレッドを1本も作る**前**に、**`pthread_sigmask(SIG_BLOCK, &set, NULL)`** で `SIGINT`/`SIGTERM` 等をブロックします（以降に生成される全ワーカースレッドは、このブロック設定を自動的に継承します）。
2. シグナル処理専用の1スレッドを起動し、その中で **`sigwait(&set, &sig)`** をループ呼び出しします。
3. こうすれば非同期割り込みが一切起きなくなり、専用スレッドは `sigwait()` から戻った直後に **`printf` も `malloc` も通常のミューテックスも条件変数もすべて安全に呼び出して**、全ワーカースレッドへクリーンな終了通知を送ることができます。

### 理解度チェック（次節へ進む前の確認）

本節の非同期シグナル安全性・`SIGCHLD` の結合・`errno` 保護を確認し、[第5部](../index.md#part-5)（I/O・ファイルシステムとシステム保護）へ繋ぐ問いを置きます。

> **【確認の問い】**
>
> 1. **（スレッド安全と非同期シグナル安全の違い）**
>     C標準ライブラリの `malloc()` や `printf()` は、マルチスレッドから同時に呼んでも壊れない「スレッド安全な」関数として実装されています。それにもかかわらず、なぜシグナルハンドラの内部からこれらを呼び出すと危険（非同期シグナル非安全）なのでしょうか。単一スレッドで起きる具体的な現象（自己デッドロック）に沿って説明してください。
>
> 2. **（安全な `SIGCHLD` ハンドラの3つの要点）**
>     子プロセスの終了を回収する `SIGCHLD` ハンドラを安全に書くとき、次の3つの工夫がそれぞれ何を防ぐために必要か簡潔に答えてください。
>
>     * (a) ハンドラ内で `waitpid(-1, NULL, WNOHANG)` を1回だけでなく **`while` ループ**で呼ぶ理由。
>     * (b) ハンドラの先頭と末尾で **`errno` を退避・復元**する理由。
>     * (c) メイン側と共有するフラグ変数へ **`volatile sig_atomic_t`** を付ける理由。
> 3. **（[第5部](../index.md#part-5)への伏線：CPUの外側にあるディスクやネットワーク機器とどうデータをやり取りするか）**
>     第3〜4部では、CPUと主記憶（RAM）の上で複数のプロセスやスレッドを安全に仮想化・同期する仕組みを学びました。では、CPUの外側に繋がっているキーボード、ディスプレイ、ディスク（SSD/HDD）、ネットワークカードといった **I/O デバイス** に対して、OSカーネルはどのようなアドレス空間・割り込みコントローラ・データ転送方式（DMA）を使ってデータをやり取りしているのでしょうか。
