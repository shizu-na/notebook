### 前節（4-4）の確認問題の解答

前節の最後に提示した3つの問いの解答を確認します。

1. **`push_off` / `pop_off` の境界条件と交差解放：**

    * **(a) 元が割り込み禁止状態（`intr_get() == 0`）での安全な保持：**
        `acquire(&A)` 内の `push_off()` が `noff` を `0 → 1` に増やす際、`old = intr_get()` で得た `0` を `mycpu()->intena = 0` に記録します。その後 `release(&A)` 内の `pop_off()` で `noff` が `1 → 0` に戻っても、`if (c->noff == 0 && c->intena)` が偽となるため `intr_on()` は呼ばれず、元の割り込み禁止状態が正しく維持されます。

    * **(b) 交差解放（`acq(A) → acq(B) → rel(A) → rel(B)`）のトレースと方式比較：**
        初期状態（`intr_get() == 1`, `noff == 0`）からの推移は次の通りです。

        * `acquire(&A)` 完了：`noff = 1`, `intena = 1`（割込 OFF）
        * `acquire(&B)` 完了：`noff = 2`（割込 OFF）
        * `release(&A)` 完了：`noff = 1`（まだ B を保持しているため割込 OFF を維持）
        * `release(&B)` 完了：**`noff = 0`** かつ `intena == 1` となり、**ここで初めて `intr_on()` が呼ばれます**。

        もし「ロック構造体ごとに取得前の割り込み状態を保存する設計」にすると、`A` に `1`、`B` に `0` が保存され、先に `release(&A)` を呼んだ時点で `A` が保存していた `1` へ戻してしまい、**まだロック B を保持中なのに割り込みが許可されて自己デッドロックする**バグが生じます。CPU ごとのネスト深さ `noff` で管理するからこそ、解放順が入れ替わっても安全です。

2. **`acquiresleep()` の実装バグ診断：**

    * **(a) `while (lk->locked)` を `if (lk->locked)` にした場合の破綻（3プロセス P0, P1, P2）：**

        1. P0 がスリープロックを保持中（`lk->locked == 1`）に、P1 が `acquiresleep()` を呼んで `sleep(lk, &lk->lk)` で眠ります。
        2. P0 が `releasesleep()` を呼び、`lk->locked = 0` にして `wakeup(lk)` で P1 を `RUNNABLE` にします。
        3. P1 が CPU をもらって再開する直前に、別コアの P2 が `acquiresleep()` へ割り込み、`lk->locked == 0` を見て **`lk->locked = 1` に設定しクリティカルセクションへ入場**します。
        4. 直後に再開した P1 は `if` の直後へ戻るため条件を再検査せず、そのまま `lk->locked = 1` を上書きして入場してしまい、**P2 と P1 が同時にクリティカルセクションへ入る相互排除破綻**が起きます。

    * **(b) `acquiresleep()` 末尾の `release(&lk->lk)` を書き忘れた場合の2つの障害：**

        1. 内部スピンロック `lk->lk` を握ったままになるため自コアの `noff == 1`（割り込み禁止）が解除されず、その後の長時間処理でタイマ割り込みが止まったり、`sleep()` を呼んだ瞬間に `sched()` の `noff != 1` 検査でパニックしたりします。
        2. 他のコアが `acquiresleep()` を呼んでも（さらには保持者自身が `releasesleep()` で `acquire(&lk->lk)` を呼んでも）内部スピンロックを獲得できず、自己デッドロック／永久膠着に陥ります。

3. **スピンロックとスリープロックの設計選定：**

    * **(a) 5 ms のディスク I/O 待ちを含むブロックキャッシュ保護 → スリープロック：** 数ミリ秒の待機中にスピンロックを握り続けると CPU を浪費し割り込みも止まってしまいます。そもそもスピンロック保持中の `sleep()` は厳禁であるため、割り込みを許可したまま眠れるスリープロックを選びます。
    * **(b) 割り込みハンドラ `consoleintr()` と `sys_read()` 共有の 128 B リングバッファ → スピンロック：** 割り込みハンドラはプロセスではないため `sleep()`（スリープロック）を使えません。操作も極短時間のメモリ読み書きであり、スピンロックの割り込み禁止（`push_off`）により同一コア上の自己デッドロックを防げます。

## 4-5. セマフォと古典的同期問題（生産者消費者・Readers-Writers・哲学者）

### 1. 動機（Why）：なぜ「0/1 のロック」だけでは複雑な協調パターンを書きにくいのか

前節（[4-4節](4-4.md)）で、スピンロックとスリープロック、および `sleep`/`wakeup` によって「クリティカルセクションへ同時に入れるのを1スレッドに制限する（相互排除）」仕組みが完成しました。

しかし、実際のOSやアプリケーションで必要になる同期は、単純な1対1の排他制御だけではありません。次のような**複数スレッド間の協調（Coordination）**が至るところに現れます。

1. **個数制限と生産・消費の同期：** 最大 $N$ 個まで入るキューに対し、空きがある間だけ生産者が投入し、データが1個以上ある間だけ消費者が取り出すように制御します。
2. **読取り共有と書込み排他の両立：** データベースや設定キャッシュのように、複数の読者（Reader）は同時に読めるようにして性能を稼ぎつつ、書き手（Writer）がいるときだけは全員を締め出します。
3. **複数資源の同時獲得とデッドロック回避：** 複数の共有資源を同時に必要とするスレッド群が、循環待機に陥らず安全に処理を進められるようにします。

これらをすべて生のロックと `sleep`/`wakeup` だけで毎回ゼロから組むと、カウンタ管理や Lost Wakeup のミスが起きやすくなります。そこで1965年、エドガー・ダイクストラ（Edsger W. Dijkstra）は、**「整数カウンタ1つと、2つの不可分操作（`wait` と `signal`）だけで、相互排除も個数制御も順序同期もすべて統一的に記述できる」**抽象プリミティブである **セマフォ（Semaphore）** を考案しました。

本節では、セマフォの動作原理と内部実装を押さえたうえで、並行プログラミングの設計パターンと典型的なバグ（デッドロック・飢餓）が凝縮された **3つの古典的同期問題**（有限バッファ生産者・消費者、Readers-Writers、食事する哲学者）をセマフォで解き明かします。

---

### 2. 具体例と動作イメージ（Toy Model）

厳密な実装に入る前に、2つの小さな例でセマフォの直感的な振る舞いを確かめます。

#### 実験A：残り台数を数える「駐車場のゲート（計数セマフォ）」

定員2台の小さな駐車場があり、入口に残り空き台数を示すカウンタ `S`（初期値 **`2`**）があると想像してください。

* 車が駐車場へ入ろうとするときは **`wait(S)`** を呼びます。空きがあれば `S` を `1` 減らしてそのまま入場し、空きがなければ（`S <= 0`）ゲートの待機列でエンジンを切って眠ります（`SLEEPING`）。
* 車が駐車場から出るときは **`signal(S)`** を呼びます。`S` を `1` 増やし、待機列で眠っている車があれば1台を起こして入場させます。

スレッド A, B, C の3台が順番に到着したときのカウンタ `S` の推移を追ってみます。

1. 初期状態：`S = 2`（待機列は空です）。
2. スレッド A が `wait(S)` $\implies$ `S` が $2 \to 1$ になり、A は即座に入場します。
3. スレッド B が `wait(S)` $\implies$ `S` が $1 \to 0$ になり、B も即座に入場します。
4. スレッド C が `wait(S)` $\implies$ `S` がすでに `0`（または $0 \to -1$ 実装）のため、**C はブロックして待機列で眠ります**。
5. スレッド A が作業を終えて `signal(S)` $\implies$ 待機列の先頭にいた **C が起こされて入場**します。

特に初期値を **`S = 1`**（定員1台）に設定すれば、そのまま相互排除ロック（**二値セマフォ**）として機能します。

#### 実験B：初期値 `0` のセマフォによる「順序同期（先行制約）」

セマフォのもう1つの強力な使い方が、**初期値を `0` にして「処理Aが終わってから処理Bを実行する」順序を保証する**パターンです。

```c
// 共有セマフォ：sem_t done; init(&done, 0);

// スレッド A（先に実行してほしい側）      // スレッド B（Aの完了を待つ側）
prepare_data();                         wait(&done);      // 完了を待つ
signal(&done);   // 準備完了を通知      use_data();       // 準備済みデータを使う
```

ここで、2つのインターリービングを両方確認してみましょう。

* **スレッド B が先に `wait(&done)` へ到達した場合：** `done == 0` なので B は待機列で眠ります。後から A が `prepare_data()` を終えて `signal(&done)` を呼ぶと B が起こされ、`use_data()` へ進みます。
* **スレッド A が先に `signal(&done)` を呼び終えていた場合：** `done` のカウンタが **`0` から `1` へ増えて記憶**されます。後から B が `wait(&done)` を呼ぶと、`done == 1` を `0` へ減らして**眠らずに即座に通過**します。

前節（[4-4節](4-4.md)）の素朴な `wakeup` は「先に呼ばれると通知が空振りして消える（Lost Wakeup）」弱点がありましたが、セマフォは**過去の `signal` の回数を整数カウンタの中に蓄えて記憶してくれる**ため、順序同期で通知が失われることがありません。

---

### 3. 構造・アルゴリズム・実装（What）

#### (1) セマフォの定義・不変条件・弱い／強いセマフォ

初期値 $k \ge 0$ のセマフォ $s$ について、これまでに完了した `sem_wait`（$P$ 操作）の回数を $\#P_{\text{完了}}(s)$、`sem_signal`（$V$ 操作）の回数を $\#V(s)$ とすると、セマフォは常に次の **セマフォ不変条件（Semaphore Invariant）** を保ちます。

$$
s.\text{value} = k + \#V(s) - \#P_{\text{完了}}(s) \ge 0 \quad \Longleftrightarrow \quad \#P_{\text{完了}}(s) \le k + \#V(s)
$$

この単純な不等式が、相互排除（$k=1$ で同時入場数 $\#P_{\text{完了}} - \#V \le 1$）、個数制限（$k=N$）、および順序同期（$k=0$ で完了済み `wait` が `signal` 回数を超えない）のすべての正当性の根拠になります。

また、複数のスレッドが待機しているときに `sem_signal` が誰を起こすかによって、セマフォは次の2種類に区別されます。

* **弱いセマフォ（Weak Semaphore）：** 待機中のスレッドの中から**任意の1つ**を選びます（あるいはブロードキャストで全員を起こして競争させます）。実装は単純ですが、特定のスレッドが永遠に選ばれない**飢餓**が起こり得ます。
* **強いセマフォ（Strong Semaphore）：** 待機スレッドを **FIFO（先入れ先出し）キュー** で管理し、最も長く待っていた先頭スレッドを起こします。これにより有界待機（飢餓の不在）が保証されます。

前節（[4-4節](4-4.md)）の部品（スピンロック＋ブロードキャスト型 `sleep`/`wakeup`）から素朴な弱いセマフォを組み立てると、わずか十数行で実装できます。

```c
struct semaphore {
    int value;             // 利用可能な資源の残り個数（0以上）
    struct spinlock lk;    // value への操作を不可分にする内部スピンロック
};

void sem_wait(struct semaphore *s) {   // P操作（down）
    acquire(&s->lk);
    while (s->value == 0) {
        sleep(s, &s->lk);              // 資源がなければロックを引き継いで眠る
    }
    s->value -= 1;                     // 資源を1つ確保
    release(&s->lk);
}

void sem_signal(struct semaphore *s) { // V操作（up）
    acquire(&s->lk);
    s->value += 1;                     // 資源を1つ返却（または通知を蓄積）
    wakeup(s);                         // 待機中のスレッドを起こす（FIFO キューなら先頭1個＝強いセマフォ）
    release(&s->lk);
}
```

（※上のコードは xv6 の `sleep`/`wakeup` に合わせて `value >= 0` を保つ非負方式です。一方、専用 FIFO 待機キューへ直接スレッドを繋いで `signal` で先頭1個だけを起こす実用OSの強いセマフォでは、先に `s->value--` を行って負数になったとき待機キューへ入れる実装をとることも多く、その場合 `|value|` がそのまま待機スレッド数を表します。）

> **【コラム：セマフォの語源と、なぜ操作名が `P` と `V` なのか】**
>
> 「セマフォ（Semaphore）」とは、もともと鉄道の線路脇に立てられ、腕木の角度で「この先の区間へ列車が入ってよいか（進行／停止）」を知らせる**腕木信号機**のことです。単線区間に2台の列車が同時に入って正面衝突（競合状態）しないように制御する役割が、まさにクリティカルセクションの排他制御と重なるため、ダイクストラがこの名前を付けました。
>
> また、古典的な教科書や論文では `wait` と `signal` の代わりに **`P(S)`** と **`V(S)`** という記号が使われます。これは英語ではなくダイクストラの母国語である**オランダ語**の頭文字に由来します。
>
> * **`P`：** *Proberen*（試す・検査する）または *Passering*（通過） $\implies$ 資源を取れるか試して減らす（`wait` / `down`）
> * **`V`：** *Verhogen*（増やす）または *Vrijgave*（解放） $\implies$ 資源を増やして解放する（`signal` / `up`）

#### (2) 古典問題①：有限バッファ生産者・消費者問題（Bounded-Buffer）

OSのパイプ（[5-3節](../5/5-3.md)）やキーボード入力バッファ、Webサーバのリクエストキューなど、計算機システムで最も頻繁に現れるのが **有限バッファ生産者・消費者問題** です。

容量 $N$ 個のリングバッファ `buf[N]` を共有し、**生産者（Producer）**は空きがあるときだけデータを投入し、**消費者（Consumer）**はデータがあるときだけ取り出します。これは次の **3本のセマフォ** で解けます（図4-5-1左）。

* `empty`（初期値 **$N$**）：バッファ内の**空きスロット数**を数える計数セマフォです。
* `full`（初期値 **$0$**）：バッファ内の**格納済みデータ数**を数える計数セマフォです。
* `mutex`（初期値 **$1$**）：リングバッファの読み書き位置（`in`, `out`）を守る相互排除セマフォです。

```c
// 生産者（Producer）                   // 消費者（Consumer）
void producer(Item item) {              Item consumer(void) {
    sem_wait(&empty);  // ① 空きを待つ      sem_wait(&full);   // ① データを待つ
    sem_wait(&mutex);  // ② 排他獲得        sem_wait(&mutex);  // ② 排他獲得
    buf[in] = item;                         Item item = buf[out];
    in = (in + 1) % N;                      out = (out + 1) % N;
    sem_signal(&mutex);// ③ 排他解放        sem_signal(&mutex);// ③ 排他解放
    sem_signal(&full); // ④ データ+1通知    sem_signal(&empty);// ④ 空き+1通知
}                                       }
```

ここで重要な設計上の教訓が、**「`sem_wait` を呼ぶ順番（①と②の順序）」**です（図4-5-1右）。もし生産者側でうっかり `sem_wait(&mutex)` を先に呼んでから `sem_wait(&empty)` を呼ぶように逆に書いてしまうと、次の手順で**即座にデッドロック**します。

1. バッファが満杯（`empty == 0`）の状態で、生産者が先に `sem_wait(&mutex)` に成功して `mutex` を握ります。
2. 続けて生産者が `sem_wait(&empty)` を呼びますが、`empty == 0` のため **`mutex` を握ったまま眠りにつきます**。
3. 消費者がデータを取り出して空きを作ろうと `sem_wait(&full)` を通過し、`sem_wait(&mutex)` を呼びますが、生産者が `mutex` を離さないため**消費者も眠ってしまいます**。
4. 生産者は消費者が `empty` を増やすのを待ち、消費者は生産者が `mutex` を離すのを待ち合い、永久に停止します。

なお、対照的に出口側の **`sem_signal(&mutex)` と `sem_signal(&full)`（③と④）の順序を逆にしてもデッドロックやデータ破壊は起きません**（どちらもブロックしない操作のためです）。ただし、先に `sem_signal(&full)` を呼ぶと起こされた消費者がまだ解放されていない `mutex` にぶつかって即座に再ブロックする無駄が生じ得るため、元の通り `mutex` を先に解放する順序の方が性能面で優れます。

**鉄則：** 相互排除ロック（`mutex`）の獲得は、必ず「資源待ち（`empty` / `full`）を通過した**後**」に行い、ロックの保持区間（スコープ）を最小限に保ちます。

#### (3) 古典問題②：Readers-Writers 問題と「書き手飢餓」の解消

共有データ（設定テーブルやキャッシュなど）へのアクセスは、多くのシステムで「9割が読み取り、1割が書き込み」です。読み取り同士は互いにデータを壊さないため、普通の排他ロックで読者まで1人ずつ順番待ちさせると並列度が大きく落ちます。

そこで、**「読者（Reader）は何人でも同時入場可、書き手（Writer）は完全排他（他の読者も書き手も0人）」**を実現するのが **Readers-Writers 問題（読者・書き手問題）** です。

最も基本的な **読者優先（First Readers-Writers）** の解法では、書き手との排他用セマフォ `rw_mutex = 1`、読者人数カウンタ `read_count = 0`、および `read_count` 自身を守る `mutex = 1` を使います。

```c
// 読者（Reader：読者優先版）            // 書き手（Writer）
sem_wait(&mutex);                       sem_wait(&rw_mutex);
read_count++;                           /* データを排他的に書き換える */
if (read_count == 1)                    sem_signal(&rw_mutex);
    sem_wait(&rw_mutex); // 最初の読者だけ書き手を締め出す
sem_signal(&mutex);

/* 共有データを並列に読み取る */

sem_wait(&mutex);
read_count--;
if (read_count == 0)
    sem_signal(&rw_mutex); // 最後の読者だけ書き手を解放する
sem_signal(&mutex);
```

このアルゴリズムは **「照明スイッチの比喩（Lightswitch パターン）」** と呼ばれます。部屋に入る最初の1人だけが電気を点け（`wait(rw_mutex)`）、2人目以降の読者は素通りして並列に読み、部屋を出る最後の1人だけが電気を消して（`signal(rw_mutex)`）書き手へ部屋を明け渡します（なお、ここでは読者が `mutex` を保持したまま `sem_wait(&rw_mutex)` を呼んでいますが、書き手は `mutex` を獲得せず `rw_mutex` のみを扱うため、生産者・消費者問題のような循環待機によるデッドロックは発生しません）。

しかし、この素朴な読者優先版には **書き手の飢餓（Writer Starvation）** という明確な欠点があります（図4-5-2左）。読者1が読んでいる間に読者2が入り、読者1が出る前に読者3が入る……と読者が途切れず到着し続けると、`read_count` が一度も `0` にならず、**書き手が永遠に `rw_mutex` を獲得できません**。

この飢餓を解消する補正が、入口に **回転木戸セマフォ `turnstile = 1`** を1本追加する **公平（飢餓なし）Readers-Writers 解法** です（図4-5-2右）。ただし重要な前提として、この公平性が保証されるのは **`turnstile` が強いセマフォ（FIFO 待機キュー）として実装されている場合** です（3-(1) のブロードキャスト型のような弱いセマフォでは、後続の読者が `turnstile` の獲得競争で書き手を追い抜き続けて再び飢餓が起こり得ます）。

```c
// 公平版 Readers-Writers（turnstile = 1 は FIFO の強いセマフォが前提）
// 読者（Reader）                        // 書き手（Writer）
sem_wait(&turnstile);                    sem_wait(&turnstile);   // 後続の読者・書き手を足止め
sem_signal(&turnstile);                  sem_wait(&rw_mutex);    // 既存の全読者の退場を待つ
sem_wait(&mutex);                        /* データを排他的に書き換える */
if (++read_count == 1)                   sem_signal(&rw_mutex);
    sem_wait(&rw_mutex);                 sem_signal(&turnstile); // 回転木戸を解放
sem_signal(&mutex);
/* 共有データを並列に読み取る */
sem_wait(&mutex);
if (--read_count == 0)
    sem_signal(&rw_mutex);
sem_signal(&mutex);
```

書き手が到着して `turnstile` を握った瞬間、後続の新規読者はすべて `turnstile` の手前で足止めされます。あとは現在すでに読み取り中の読者たちが出終えて `read_count == 0` になった瞬間に、書き手が確実に順番を獲得できるのです。

#### (4) 古典問題③：食事する哲学者の問題（Dining Philosophers）

ダイクストラが1965年に考案した **食事する哲学者の問題** は、「複数のスレッドが複数の排他資源を同時に必要とするときに起きるデッドロックと、その回避策」を端的にモデル化した古典問題です。

円卓に5人の哲学者（$P_0 \sim P_4$）が座り、隣り合う哲学者のあいだに合計5本のフォーク（セマフォ `fork[0]`〜`fork[4]`、初期値 `1`）が置かれています。各哲学者は「思考」と「食事」を繰り返し、食事をするには自分の**左側のフォーク `fork[i]`** と**右側のフォーク `fork[(i+1) % 5]`** の**両方**を同時に手に取る必要があります（図4-5-3左）。

* **素朴な実装（全員が「左 → 右」の順で取る）：**
    もし5人全員がほぼ同時に左側のフォークを取ってしまうと、`fork[0]`〜`fork[4]` のすべてが `0` になります。次に全員が右側のフォークを取ろうとして待ち始め、資源獲得順序グラフに $f_0 \to f_1 \to f_2 \to f_3 \to f_4 \to f_0$ という閉路が生まれ、**循環待機（Coffman の4条件すべて成立）による完全なデッドロック**に陥ります。

このデッドロックを防ぐ代表的な3つの解決策は、そのまま実システムの並行設計パターンに対応します。

1. **非対称な資源獲得順序（ロック順序付け：最も実用的）：**
    $P_0 \sim P_3$ は「左 → 右（小さい番号 → 大きい番号）」の順に取るのに対し、**最後の1人 $P_4$ だけ「右（`fork[0]`） → 左（`fork[4]`）」の順（同じく小さい番号 → 大きい番号）**で取るようにします（図4-5-3右）。全員が必ず**フォーク番号の昇順**で獲得するため、ロック獲得順序グラフに閉路（循環待機）が原理的に発生しなくなります。[4-1節](4-1.md)および[4-4節](4-4.md)で述べた「グローバルなロック順序規約」そのものです。

2. **同時着席人数の制限（計数セマフォ `room = 4`）：**
    円卓に同時に食事を試みられる人数を、初期値 $N - 1 = 4$ の計数セマフォで制限します。鳩の巣原理より、5本のフォークに対して最大4人しか手を出さないなら、必ず少なくとも1人は両側のフォークを揃えて食事を終えられるためデッドロックしません。

3. **2本同時の原子獲得（状態配列＋個別セマフォ：Tanenbaum の解法）：**
    各哲学者の状態（`THINKING` / `HUNGRY` / `EATING`）を1つの `mutex` で守り、「左右の隣人がどちらも `EATING` でないときだけ2本まとめて確保する」方式です。保持と待機（Coffman の条件②）を崩してデッドロックを防ぎますが、左右の隣人が交互に食べ続けると中央の哲学者が飢餓する可能性は残ります。

### 4. 限界と補正（Critique & Adaptation）

セマフォは理論的に強力で表現力が高い反面、大規模な実務ソフトウェアで直接セマフォを多用するとバグが混入しやすいという構造的な弱点があります。

#### (1) セマフォの構造的な弱点（誤用のしやすさと所有権の不在）

1. **「相互排除」と「条件同期」の区別がコード上で消える：**
    有限バッファ問題で見た通り、`mutex`（排他制御）と `empty`/`full`（条件・個数同期）はまったく異なる役割なのに、セマフォではどちらも同じ `sem_wait` / `sem_signal` で書かれます。そのため `wait` の順序を1行入れ替えただけで静かにデッドロックし、1箇所 `signal` を書き忘れるだけでシステム全体が止まります。

2. **ロック所有権（Ownership）が存在しない：**
    セマフォの `sem_signal(S)` は、**過去に `sem_wait(S)` を呼んでいないまったく無関係なスレッドからでも自由に呼び出せてしまいます**（実際、順序同期では別スレッドが `signal` を呼ぶのが前提です）。これは便利な反面、排他ロック用途では「誰がロックを保持しているか」をOSが把握できないことを意味します。その結果、[3-3節](../3/3-3.md)で触れた **優先度逆転を防ぐ「優先度継承」を二値セマフォへは適用できない** という実務上の大きな限界が生じます。

#### (2) 構造化同期プリミティブ（モニタ・条件変数・ミューテックス）への補正

これらの限界に対する言語・OS設計上の補正は、次の2つの分離と構造化です。

1. **所有権を持つミューテックス（Mutex）の分離：** 相互排除には二値セマフォではなく、**「ロックした本人（スレッド）しかアンロックできない」**所有権付きのミューテックスを用います。これにより誤った解放の検知や優先度継承が可能になります。
2. **モニタ（Monitor）と条件変数（Condition Variable）によるカプセル化：** 共有データ・相互排除ロック・条件待ちの仕組みを1つのモジュール（オブジェクト）へまとめ、プログラマが `wait`/`signal` の順序ミスを起こしにくくします。これが次節（[4-6節](4-6.md)）の主題です。

### 5. 接続と展望（Bridge）：本節の内容が後半のどの部に繋がるか

1. **次節（[4-6節](4-6.md)：モニタと条件変数［Hoare式 IRR vs Mesa式 non-IRR］）：**
    本節4-(2)で提起した「セマフォの誤用しやすさと所有権不在」を解決する高水準の同期構造である **モニタと条件変数** へ進み、有限バッファ問題をより安全に書き直したうえで、`signal` 直後の制御権の扱い（Hoare式とMesa式の違い）を整理します。

2. **[第5部](../index.md#part-5)（[5-3](../5/5-3.md)・[5-5節](../5/5-5.md)：パイプとバッファキャッシュ）：**
    本節の有限バッファ生産者・消費者問題は、[第5部](../index.md#part-5)で扱うUNIXの **パイプ（`pipe`）** のカーネル内リングバッファの動作そのものです。

3. **[第9部](../index.md#part-9)（[9-6節](../9/9-6.md)：データベースの共有ロック S・排他ロック X とデッドロック）：**
    本節の Readers-Writers 問題における「複数読者の共有＋書き手の排他」という構造は、[第9部](../index.md#part-9)のデータベース並行制御（2PL）における **共有ロック（Sロック）と排他ロック（Xロック）の互換行列** へそのまま発展します。また、食事する哲学者の循環待機は、DBMSの待機グラフ（Wait-For Graph）によるデッドロック検出へ直結します。

>
>     * (a) 消費者側で `sem_wait(&mutex)` と `sem_wait(&full)` の順序を逆にした場合、バッファが空（`full == 0`）の状態からどのようにデッドロックが発生するか手順を追って説明してください。
>     * (b) 一方、生産者側で出口の `sem_signal(&mutex)` と `sem_signal(&full)` の順序を逆にした場合、デッドロックやデータ破壊は起きるでしょうか。また性能面ではどちらの順序が望ましいか答えてください。
>
> 2. **（Readers-Writers 問題のクリティカルセクション縮小バグ）**

>
>     ```c
>     sem_wait(&mutex);
>     read_count++;
>     sem_signal(&mutex);          // ← 先に mutex を解放してしまった
>     if (read_count == 1)
>         sem_wait(&rw_mutex);
>     ```

>     書き手 W と2人の読者 R1, R2 の3スレッドが動くとき、**書き手 W が書き込み中なのに読者が同時に共有データへ侵入してしまう**具体的なインターリービングを1つ示してください。
