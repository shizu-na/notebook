### 前節（3-8）の確認問題の解答

前節の最後に提示した3つの問いの解答を確認します。問3がそのまま[第4部](../index.md#part-4)（並行性制御と同期）の導入になります。

1. **リンカスクリプト `kernel.ld` が果たす2つの役割：**

    * **(a) `.bss` セクション直後のシンボル `end`：**
        カーネル自身のコードと静的データ（`.text`〜`.bss`）が物理メモリのどこで終わるかをC言語コードへ伝える境界印です。`kinit()` はこの `end` 番地から物理RAM上限 `PHYSTOP` までを空きページとしてフリーリストへ登録し、カーネル自身を上書きしないように保護します。

    * **(b) `ALIGN(0x1000)` で4 KiB境界へ揃える `trampoline`（`trampsec`）：**
        ユーザページテーブルとカーネルページテーブルの双方で、同一仮想アドレスに1ページ単位で共有マップする（[3-6節](../3/3-6.md)）ため、ちょうど $4\text{ KiB}$ のページ先頭から始まり1ページに収まるよう配置を強制します。

2. **M-mode からの降格とマルチコア起動時の同期：**

    * **(a) `call main` ではなく `mret` で S-mode へ移行する理由：**
        通常の関数呼び出し `call` では特権モードが変わらず M-mode のままになってしまいます。RISC-V では M-mode から S-mode へ直接降格する命令がないため、`mstatus.MPP` に S-mode、`mepc` に `main` のアドレスをセットしてトラップ復帰命令 **`mret`** を実行することで、権限降格とジャンプを原子的に行います。

    * **(b) `started` に `volatile` と `__sync_synchronize()` を併用する理由：**
        `volatile` はコンパイラが待機ループ `while (started == 0);` を最適化で消去・移動するのを防ぎますが、CPUハードウェア自身によるメモリ書き込み順序の逆転は防げません。`__sync_synchronize()`（メモリバリア）を併用することで、コア0が行った `kinit` や `kvminit` の全書き込みが他コアから確実に観測できるようになってから `started = 1` が見えることを保証します。

3. **2つのCPUコアが同時に共有カウンタを `+1` したら何が起きるか（本節への接続）：**
    C言語の1行 `count = count + 1;` は、CPUの機械語レベルでは「メモリからレジスタへ読出し（`ld`）→ レジスタで `+1`（`addi`）→ メモリへ書戻し（`sd`）」という3命令に分解されます。コア0が読み出した古い値 `0` に `+1` している間にコア1も同じ古い値 `0` を読み出してしまうと、両方が結果 `1` を上書きしてしまい、1回分の加算が消滅します。これが本節で学ぶ**競合状態（Race Condition）**です。

## 4-1. 競合状態・クリティカルセクションと安全性・活性・公平性

### 1. 動機（Why）：なぜ単一スレッドでは100%正しいコードが、並行実行した瞬間に壊れるのか

[第3部](../index.md#part-3)（[3-1](../3/3-1.md)〜[3-8節](../3/3-8.md)）を通じて、OSが1台のコンピュータの上で複数のプロセスやスレッドを切り替えながら動かし、さらに複数のCPUコアを一斉に稼働させる仕組みが揃いました。

しかし、複数の実行主体（CPUコア、スレッド、割り込みハンドラ）が**同じメモリ領域を共有**して読み書きし始めた瞬間、単一スレッドのプログラミングでは決して起きなかった奇妙なバグが発生します。

* 銀行口座へ1万円ずつ2回入金したのに、残高が1万円しか増えません。
* [3-4節](../3/3-4.md)で見た物理ページのフリーリスト `kmem.freelist` へ2つのコアが同時に `kfree()` を呼んだら、1ページ分のメモリが永久に行方不明になります。
* テスト環境では1万回動かしても1回も失敗しなかったのに、本番サーバで負荷が高まったときだけ月に1度クラッシュします。

これらの原因は、高級言語で「1つの操作」に見える処理が、CPUレベルでは複数の機械語命令に分かれており、その**命令の途中で別のスレッドや割り込みが割り込んで実行順が入り混じる（インターリービング）**ことにあります。

本節では、[第4部](../index.md#part-4)の土台として、競合状態が起きる物理的なメカニズムを小さな例で可視化したうえで、並行プログラムの「正しさ」を議論するための厳密な語彙（**クリティカルセクション・安全性・活性・公平性・デッドロック・ライブロック・飢餓**）を整理します。

### 2. 具体例と動作イメージ（Toy Model）

抽象的な定義に入る前に、実際にシステムプログラミングで最も頻繁に遭遇する2つの破壊パターンを手計算で追ってみます。

#### 実験A：`count = count + 1` で起きる「更新の消失（Lost Update）」

メモリ上の共有変数 `count` の初期値が `0` であるとします。スレッドA（コア0）とスレッドB（コア1）が、どちらも次の1行を1回ずつ実行します。

```c
count = count + 1;
```

期待する最終結果は当然 `2` です。しかし、[1-1節](../1/1-1.md)で確認した通り、RISC-V（ロード・ストアアーキテクチャ）ではこの1行が次の3命令へ翻訳されます（x86-64の `addq $1, count(%rip)` であっても、内部では読出し・加算・書戻しのマイクロオペレーションに分かれ、特別なロック指定がなければ同じ現象が起きます）。

```asm
ld   t0, 0(a0)      # (1) メモリ [count] の値を自コアのレジスタ t0 へ読出し
addi t0, t0, 1      # (2) レジスタ t0 に 1 を加算
sd   t0, 0(a0)      # (3) レジスタ t0 の値をメモリ [count] へ書戻し
```

ここで、2つのスレッドの命令が次のように交互に入り混じって実行されたとします（図4-1-1）。

1. **時刻1：** スレッドAが `(1) ld` を実行し、メモリから `0` を自分のレジスタ `t0` へ読みます（`t0_A = 0`）。
2. **時刻2：** スレッドAが書き戻す前に、スレッドBが `(1) ld` を実行し、同じくメモリから **`0`** を自分のレジスタ `t0` へ読みます（`t0_B = 0`）。
3. **時刻3：** スレッドAが `(2) addi` で `t0_A = 1` とし、`(3) sd` でメモリへ `1` を書き戻します（`count = 1`）。
4. **時刻4：** スレッドBが `(2) addi` で `t0_B = 1` とし、`(3) sd` でメモリへ **`1`** を書き戻します（`count = 1`）。

スレッドAの更新結果がスレッドBによって上書きされて消え、最終結果は `2` ではなく **`1`** になってしまいました。このように、複数の更新が重なって片方が消滅する現象を **更新の消失（Lost Update）** と呼びます。

#### 実験B：連結リスト（3-4節の `kfree`）への同時挿入で起きるポインタ破壊

競合状態は単純な数値カウンタだけでなく、データ構造を根本から破壊します。[3-4節](../3/3-4.md)で見た xv6 の物理ページ解放 `kfree()` を思い出してください。

```c
// 保護なしの kfree()
r->next = kmem.freelist;   // (1) 現在の先頭を読む
kmem.freelist = r;         // (2) 先頭を自分へ付け替える
```

現在 `kmem.freelist` がページ `P0` を指している状態で、コア0がページ `A` を、コア1がページ `B` を同時に解放しようとしたとします。

1. コア0が `(1)` を実行し、`A->next = P0` と設定します。
2. コア0が `(2)` を実行する前に、コア1も `(1)` を実行し、`B->next = P0` と設定します。
3. コア0が `(2)` で `kmem.freelist = A` と書き、直後にコア1が `(2)` で `kmem.freelist = B` と上書きします。

すると、最終的なフリーリストは `kmem.freelist → B → P0` となり、**ページ `A` はどこからも指されなくなって永久に消失（メモリリーク）**します。逆に2コアが同時に `kalloc()` で先頭を取り出せば、**同じ1枚の物理ページ `P0` を2つの別プロセスへ同時に貸し出してしまう**という致命的なメモリ破壊に発展します。

### 3. 構造・アルゴリズム・実装（What）

#### (1) 並行性（Concurrency）と並列性（Parallelism）、およびインターリービング

議論を正確にするため、よく混同される2つの言葉を区別しておきます。

* **並行性（Concurrency）：** 複数の処理が論理的に同時進行し得る構造（時間的に重なり合って進むこと）。**CPUコアが1個しかなくても**、[3-3節](../3/3-3.md)のタイマ割り込みによるプリエンプションでスレッドAの `ld` と `sd` のあいだにスレッドBへ切り替われば、実験Aとまったく同じ更新消失が起きます。
* **並列性（Parallelism）：** 複数のCPUコア上で、物理的にまったく同じナノ秒に複数の命令を同時実行すること。

どちらの場合も、システム全体の振る舞いは「複数スレッドの個別の機械語命令を1本の時間軸上へ交互に並べた実行列」としてモデル化できます。この命令の入り混じりを **インターリービング（Interleaving）** と呼びます。並行プログラムが正しいとは、「人間が期待する都合の良い1通りの実行順」ではなく、**「起こり得るすべてのインターリービングに対して正しい結果を保つこと」**を意味します。

#### (2) 競合状態・データ競合・クリティカルセクション問題

ここで関連する3つの専門用語を定義します。

* **競合状態（Race Condition）：** プログラムの実行結果が、複数スレッドや割り込みの**実行タイミングやインターリービングの順序に依存して変わってしまう**欠陥。
* **データ競合（Data Race）：** 複数のスレッドが同期なしに同じメモリアドレスへ同時にアクセスし、そのうち少なくとも1つが書き込みである状態（C11/C++11 規格ではデータ競合自体が未定義動作とされます）。
* **クリティカルセクション（Critical Section：臨界領域）：** 共有変数や共有データ構造（`count` や `kmem.freelist`）へアクセスするコード区間であり、**複数のスレッドが同時にその区間の中へ入ってはならない領域**。

クリティカルセクションを安全に守るための一般的なプログラム構造は、次の4区間のループとして表されます。

```c
while (1) {
    entry_protocol();      // 1. 入口プロトコル（入場許可を待つ・ロック獲得）
    /* クリティカルセクション */  // 2. 共有データの読み書き（同時に最大1スレッド）
    exit_protocol();       // 3. 出口プロトコル（退場を通知・ロック解放）
    /* 残余セクション */        // 4. 共有データに触らない通常の独立処理
}
```

#### (3) 並行アルゴリズムの正しさを測る3大性質：安全性・活性・公平性

では、「良い `entry_protocol()` と `exit_protocol()`」とはどのような条件を満たすべきでしょうか。たとえば、`entry_protocol()` の中身を `while (1) {}`（誰も絶対に中に入れない）とすれば、2つのスレッドが同時にクリティカルセクションへ入る事故は二度と起きませんが、プログラムは1ミリも進みません。

並行性理論では、アルゴリズムの正当性を次の **3つの性質** で厳密に評価します（図4-1-2）。

1. **安全性（Safety）：「悪いことは決して起きない（Nothing bad ever happens）」**

    * **相互排除（Mutual Exclusion）：** 任意の時刻において、クリティカルセクション内にいるスレッド数は**最大1個**であること。
    * データの不変条件（例：銀行の総残高、連結リストの整合性）が壊れないこと。
    * 安全性の違反は、「ある有限のステップ数で悪い状態へ到達した」という**1つの反例（トレース）**で即座に証明できます。

2. **活性（Liveness）：「良いことがいつか必ず起きる（Something good eventually happens）」**

    * **進行性（Progress）：** クリティカルセクション内に誰もいない状態で、入場を希望するスレッドが1つ以上あるなら、**有限時間内にそのうちいずれか1つが必ず入場できる**こと（外側の残余セクションで止まっている無関係なスレッドに入場を妨げられないこと）。
    * デッドロックやライブロックが起きずに処理が前進し続けること。

3. **公平性（Fairness）と有界待機（Bounded Waiting）：**

    * **有界待機（飢餓の不在：Starvation-freedom）：** あるスレッドが入場を要求してから実際に許可を得るまでの間に、他のスレッドが割り込んで先にクリティカルセクションへ入れる回数に**有限の上限**があること。
    * スケジューラの前提としても、「実行可能なスレッドはいつか必ずCPUを割り当てられる（弱公平性）」などの条件が置かれます。

#### (4) 活性と公平性が破綻する3つの典型障害：デッドロック・ライブロック・飢餓

安全性を守ろうとしてロックや待機を導入すると、今度は活性や公平性が壊れる3つの典型的な障害に遭遇します（図4-1-3）。

1. **デッドロック（Deadlock：膠着状態）：**
    複数のスレッドが、互いに相手が保持している資源（ロック）の解放を待ち合い、**全員がブロック状態のまま永久に1ステップも進めなくなる状態**です。たとえば、スレッドAがロック1を握ったままロック2を待ち、同時にスレッドBがロック2を握ったままロック1を待つとデッドロックになります。デッドロックは、次の **Coffman の4条件** がすべて同時に成立したときに発生します（裏返せば、このうち1つでも崩せばデッドロックを予防できます）。

    * ① **相互排除：** 資源を同時に1スレッドしか使えません。
    * ② **保持と待機（Hold and Wait）：** すでに資源を1つ握ったまま、追加の資源を待ちます。
    * ③ **非横取り（No Preemption）：** 他人が握っている資源を強制的に奪えません。
    * ④ **循環待機（Circular Wait）：** 待ち関係のグラフに閉路（サイクル：$A \to B \to A$）が存在します（実務で最もよく使う予防策は、全ロックにグローバルな番号を振り、常に昇順で獲得させることでこの④を断つ「ロック順序付け」です）。

2. **ライブロック（Livelock）：**
    スレッドはブロックして停止しているわけではなく、**CPUを使って活発に動き続けているのに、互いに状態を譲り合って元の状態を行き来し続け、本来の仕事が1ミリも進まない状態**です。細い廊下で向かい合った2人が、同時に右へ避け、同時に左へ避け、を繰り返して永遠にすれ違えない状況と同じです。

3. **飢餓（Starvation：スタベーション）：**
    システム全体としては他のスレッドが順調にクリティカルセクションへ出入りして仕事が進んでいるのに、**特定のスレッド（例：優先度の低いスレッドやタイミングが悪いスレッド）だけが永遠に順番をもらえず待ち続ける状態**です。

> **【コラム：ハイゼンバグ（Heisenbug）：デバッグ用 `printf` を入れた瞬間に消える並行バグ】**
>
> 並行プログラムのバグを調査しようとして、怪しい箇所へ `printf("count=%d\n", count);` のようなログ出力を入れた途端、**それまで何度も再現していた競合バグがピタリと消えてしまう**現象がよく起きます。物理学者ハイゼンベルクの不確定性原理（観測行為自体が対象の状態を変えてしまう）にちなみ、こうしたバグを **ハイゼンバグ（Heisenbug）** と呼びます。
>
> 理由は明快です。`printf` は内部で標準出力のロックを獲得し、さらにシステムコール（`write`）を実行するため、スレッドの実行タイミングを数マイクロ秒〜数ミリ秒単位で大きく遅らせます。その結果、偶然重なっていた2スレッドのクリティカルセクションのタイミングがずれてしまい、**バグが直ったわけでもないのに表面上だけ再現しなくなる**のです。したがって、並行バグの調査では `printf` による場当たり的な確認に頼らず、ロック設計の論理検証や、後述する動的解析ツール（ThreadSanitizer 等）を用いることが基本になります。

### 4. 限界と補正（Critique & Adaptation）

#### (1) テストによる検証の限界（インターリービングの組合せ爆発）

単一スレッドのプログラムなら、代表的な入力に対するユニットテストを通せば高い信頼性が得られます。しかし並行プログラムでは、**同じ入力を与えてもスレッド間のインターリービングの総数が組合せ爆発を起こす**ため、テストだけで安全性を証明することはできません。

たとえば、それぞれ $m$ 命令を実行する $n$ 個のスレッドが同時に動くとき、合計 $nm$ ステップの並べ方 $(nm)!$ 通りのうち、各スレッド内部の $m$ 命令の順序は固定されている（各 $m!$ 通りを区別しない）ため、起こり得るインターリービングの総数は多項係数

$$
\frac{(nm)!}{(m!)^n}
$$

通りです。わずか $n = 2$ スレッド・各 $m = 5$ 命令でも $\frac{10!}{5!5!} = 252$ 通り、各 $m = 10$ 命令になれば $\frac{20!}{10!10!} = \mathbf{184{,}756\text{ 通り}}$、3スレッド・各10命令では **約 $5.6 \times 10^{12}$ 通り** に達します。そのうちたった1通りだけで壊れる競合バグを、ランダムなテスト実行だけで確実に見つけ出すことは不可能です。

これに対する実務上の補正は、①そもそも共有可変状態を減らす（メッセージパッシングや不変データの活用）、②ロックの規則（データとロックの対応付け、ロック獲得順序）を設計規約として徹底する、③実行時のメモリアクセス履歴からデータ競合を自動検出する **ThreadSanitizer（TSan）** や、小規模な状態空間を網羅検証する **モデル検査（[5-9節](../5/5-9.md)）** を併用することです。

#### (2) 粗粒度ロックの限界と Amdahl の法則（直列化部分の壁）

「競合が怖いから、プログラム全体やカーネル全体をたった1つの巨大なロック（**粗粒度ロック / Big Kernel Lock**）で丸ごと囲ってしまえば安全ではないか」と考えるかもしれません。確かに安全性は簡単に満たせますが、それではマルチコアCPUの性能をまったく活かせません。

プログラム全体のうち、並列化できる部分の割合を $p$（$0 \le p \le 1$）、ロック等によって**必ず1コアずつ順番にしか実行できない直列部分の割合**を $(1 - p)$ とします。CPUコア数を $N$ 個に増やしたときの理論上の最大高速化倍率 $S(N)$ は、ジーン・アムダールが示した **Amdahl（アムダール）の法則** で上から抑えられます。

$$
S(N) = \frac{1}{(1 - p) + \dfrac{p}{N}}
$$

たとえば、クリティカルセクションによる直列部分が全体のわずか **$10\%$（$1 - p = 0.1,\; p = 0.9$）** 残っているだけで、コア数を $N = 16$ 個へ増やしても

$$
S(16) = \frac{1}{0.1 + \dfrac{0.9}{16}} = \frac{1}{0.15625} = \mathbf{6.4\text{ 倍}}
$$

にしかならず、仮にコア数を無限大（$N \to \infty$）へ増やしても $\frac{1}{0.1} = \mathbf{10\text{ 倍}}$ を絶対に超えられません。

したがって並行システムの設計では、**「ロックの粒度を細かくして（例：テーブル全体ではなく行単位・バケット単位、あるいはコアごとの独立フリーリスト）クリティカルセクションを極力短く保つ」**ことと、**「ロックを増やしすぎた結果として生じるデッドロックや管理複雑性を制御する」**ことのバランスが常に問われます。
