### 前節（4-5）の確認問題の解答

前節の最後に提示した3つの問いの解答を確認します。問3-(b) で確認したセマフォの所有権不在と誤用しやすさの克服が、そのまま本節（モニタと条件変数）の導入になります。

1. **有限バッファ問題における `wait` 逆転 vs `signal` 逆転：**

    * **(a) 消費者側で `wait(mutex)` と `wait(full)` を逆にした場合のデッドロック（初期 `full == 0`）：**

        1. 消費者が先に `sem_wait(&mutex)` を呼び、`mutex` を獲得します（`mutex: 1 → 0`）。
        2. 続けて消費者が `sem_wait(&full)` を呼びますが、`full == 0` のため **`mutex` を握ったまま眠ります**。
        3. 生産者がデータを投入しようと `sem_wait(&empty)` を通過し、`sem_wait(&mutex)` を呼びますが、消費者が `mutex` を離さないため**生産者も眠ってしまいます**。
        4. 消費者は生産者が `full` を増やすのを待ち、生産者は消費者が `mutex` を離すのを待ち合い、永久に停止します。

    * **(b) 生産者側で `signal(mutex)` と `signal(full)` を逆にした場合：**
        `sem_signal` はブロックしない操作のため、**デッドロックもデータ破壊も起きません**。ただし、`sem_signal(&full)` を先に呼ぶと起こされた消費者が即座に `sem_wait(&mutex)` へ到達し、まだ生産者が `mutex` を解放し終えていないために再びブロックする（余計なコンテクストスイッチが増える）可能性があるため、`sem_signal(&mutex)` を先に呼ぶ順序の方が性能面で望ましいです。

2. **Readers-Writers 問題で `if (read_count == 1)` を `mutex` の外へ出した場合の破綻：**
    書き手 W がすでに `rw_mutex` を保持してデータを書き換えている最中（`read_count == 0`）に、次のインターリービングで相互排除が破綻します。

    1. 読者 R1 が `sem_wait(&mutex)` を取り、`read_count` を `0 → 1` に増やして `sem_signal(&mutex)` で解放します。その後 `read_count == 1` を確認し、`sem_wait(&rw_mutex)` で W の完了を待ってブロックします。
    2. W がまだ書き込みを終える前に、読者 R2 が到着して `sem_wait(&mutex)` を取り、`read_count` を `1 → 2` に増やして `sem_signal(&mutex)` を解放します。
    3. R2 は `if (read_count == 1)` を評価しますが、すでに `read_count == 2`（偽）となっているため **`sem_wait(&rw_mutex)` を素通りして共有データの読み取りを開始**してしまいます。結果として、書き手 W と読者 R2 が同時に共有データへアクセスする競合状態が発生します。

3. **哲学者問題の同時着席制限と二値セマフォの限界：**

    * **(a) `room` 初期値 `5`・`4`・`3` の比較：**
        フォークが5本しかないため、隣接しない哲学者しか同時に2本確保できず、**同時に食事できる最大人数はいずれの設定でも 2 人**（$\lfloor 5/2 \rfloor = 2$）です。デッドロック可能性については、`room = 5` では5人全員が左フォークを持って**デッドロックし得ます**が、`room = 4` および `room = 3` では鳩の巣原理により少なくとも1人が必ず2本揃えられるため**デッドロックしません**（`room = 3` は `room = 4` と比べて、食事を待つために1本目のフォークを握る人数をさらに抑えるだけです）。

    * **(b) 二値セマフォに優先度継承を適用できない理由：**
        セマフォには「どのスレッドがロックを所有しているか」という所有権の概念がなく、誰からでも `sem_signal` を呼べる仕様になっています。そのため、高優先度スレッドが `sem_wait` でブロックしたときに、OS が「どの低優先度スレッドの優先度を一時的に引き上げるべきか」を特定できません。

## 4-6. モニタと条件変数（Hoare式 IRR vs Mesa式 non-IRR）

### 1. 動機（Why）：なぜセマフォではなく「モニタと条件変数」が現代の標準になったのか

前節（[4-5節](4-5.md)）で学んだセマフォは、整数カウンタ1つだけで相互排除・個数制限・順序同期のすべてを表現できる強力なプリミティブでした。しかし、前節の最後で確認した通り、大規模なプログラムでセマフォを直接使い続けると次の2つの問題が深刻化します。

1. **排他制御と条件待ちが混ざり、わずかなミスでデッドロックする：**
    有限バッファ問題で `sem_wait(&mutex)` と `sem_wait(&empty)` を1行入れ替えただけで即座にデッドロックしたように、プログラマがすべての関数・すべての分岐経路で `wait` と `signal` の対称性と順序を手動で守り続けるのは困難です。

2. **共有データと同期機構が分離している：**
    セマフォは単なる独立した変数であるため、「どの共有変数がどのセマフォで守られているのか」が言語構文やモジュール構造として強制されません。うっかりロックなしで共有変数へアクセスしてもコンパイラは気づけません。

この課題を解決するため、1970年代にパー・ブリンチ・ハンセン（Per Brinch Hansen）とトニー・ホーア（C. A. R. Hoare）が提唱した高水準の同期構造が **モニタ（Monitor）** です。

モニタの基本思想は、オブジェクト指向のカプセル化と同じです。**「共有データ、それを操作する手続き群、相互排除ロック（ミューテックス）、そして条件待ちの仕組み（条件変数）を1つのモジュールへ閉じ込め、同時に入れるスレッドを自動的に最大1つに制限する」**ことで、安全な並行プログラミングを構造的に支えます。本節では、モニタと条件変数の動作原理、および設計上の分岐点である **Hoare式（IRR）** と **Mesa式（non-IRR）** の違いを解き明かします。

---

### 2. 具体例と動作イメージ（Toy Model）

抽象的な仕様に入る前に、前節と同じ「有限バッファ生産者・消費者問題」をモニタ＋条件変数で書き直し、さらに `signal` 直後の振る舞いの違いを小さなシナリオで確かめます。

#### 実験A：モニタと条件変数で書く有限バッファ（Pthreads / C言語風）

容量 $N$ のリングバッファを、1本の相互排除ロック `mtx`（ミューテックス）と、2本の **条件変数（Condition Variable）** `not_full`（満杯でないことを待つ）・`not_empty`（空でないことを待つ）で保護します。

```c
// モニタに相当する共有構造体（データ ＋ ロック ＋ 条件変数）
struct bounded_buf {
    int buf[N];
    int in, out, count;      // 共有データ
    mutex_t mtx;             // モニタ入口の相互排除ロック
    cond_t  not_full;        // 「空きができる」のを待つ条件変数
    cond_t  not_empty;       // 「データが入る」のを待つ条件変数
};

void put(struct bounded_buf *b, int item) {
    mutex_lock(&b->mtx);                      // モニタへ入場
    while (b->count == N) {                   // 満杯なら待機
        cond_wait(&b->not_full, &b->mtx);     // ロックを離して眠り、起きたら再獲得
    }
    b->buf[b->in] = item;
    b->in = (b->in + 1) % N;
    b->count++;
    cond_signal(&b->not_empty);               // 空待ちの消費者を起こす
    mutex_unlock(&b->mtx);                    // モニタから退場
}

int get(struct bounded_buf *b) {
    mutex_lock(&b->mtx);
    while (b->count == 0) {                   // 空なら待機
        cond_wait(&b->not_empty, &b->mtx);
    }
    int item = b->buf[b->out];
    b->out = (b->out + 1) % N;
    b->count--;
    cond_signal(&b->not_full);                // 満杯待ちの生産者を起こす
    mutex_unlock(&b->mtx);
    return item;
}
```

前節のセマフォ版と比べてみてください。排他制御（`mtx`）は常に手続きの入口と出口に固定され、条件待ち（`cond_wait`）は「共有状態 `count == N` や `count == 0` を普通の条件式で直接書いて待つ」だけになっています。`wait` の順序逆転によるデッドロックが構造的に起きにくく、コードの意図も一目で読めます。

#### 実験B：`cond_signal` の直後に「割り込みスレッド」が来たとき何が起きるか

ここで、上の `get()` 関数で **`while (b->count == 0)` の代わりに `if (b->count == 0)` と書いてしまった** と仮定し、バッファが空（`count == 0`）の状態で次の3スレッドが動くシナリオを追ってみます。

1. **消費者 C1：** `get()` に入り、`count == 0` なので `cond_wait(&not_empty, &mtx)` で眠ります（`mtx` は自動的に解放されます）。
2. **生産者 P：** `put()` に入り、データを1個入れて `count = 1` にし、`cond_signal(&not_empty)` を呼んで C1 を起こし、`mutex_unlock(&mtx)` で退場します。
3. **消費者 C2（横入り）：** 起こされた C1 が実際にCPUをもらって `mtx` を再獲得する**ほんの一瞬前に**、別の消費者 C2 が `get()` へ到着して `mtx` を獲得します。`count == 1` なので C2 はデータを1個取り出し、`count = 0` に戻して退場します。
4. **消費者 C1（起床・再開）：** ようやく `mtx` を再獲得して `cond_wait` から戻ってきた C1 は、すでに **`count == 0`（バッファが空）になっている**にもかかわらず、もし `if` で書いていたら条件を再検査せずにそのままバッファからゴミデータを読み出してしまい、データ構造が破壊されます。

このシナリオこそが、次に学ぶ **Hoare式（横入りを構造的に禁止する設計）** と **Mesa式（横入りを許容し、`while` で再検査する設計）** の分岐点になります。

#### (1) モニタの内部構造：入口キューと条件変数キュー

言語レベルで提供されるモニタ（Java の `synchronized` メソッドや、C/Rust でミューテックス＋条件変数を構造体へまとめたもの）の内部は、次の3つの要素で構成されます（図4-6-1）。

1. **入口キュー（Entry Queue）：** モニタの相互排除ロック（`mtx`）が空くのを待っているスレッドの列です。モニタの中で実行できるスレッドは常に最大1つに制限されます。
2. **共有データと手続き群：** 入口ロックを獲得したスレッドだけが読み書きできる状態変数とメソッド群です。

#### (2) 条件変数のセマンティクス：セマフォとの決定的な違い

条件変数（`cond_t`）はセマフォと操作名（`wait` と `signal`）が似ているため初学者が最も混同しやすい概念ですが、動作の原理には **決定的な違い** があります。

* **セマフォは「整数カウンタ（記憶）」を持つ：** 誰も待っていないときに `sem_signal()` を呼ぶとカウンタが $+1$ されて記憶され、後から来た `sem_wait()` は眠らずにすぐ通過できます。
* **条件変数は「記憶を持たない（状態レス）」：** 条件変数の実体は単なる待機キューです。**誰も `cond_wait()` で待っていないときに `cond_signal()` を呼んでも、その通知は何もせず空振りして消滅します**。

だからこそ、条件変数は単独では使えず、必ず「**共有状態変数（例：`count`）**」と「**それを守るミューテックス（`mtx`）**」の3点セットで運用します。

* **`cond_wait(&cv, &mtx)`：** 必ず `mtx` をロックした状態で呼び出します。内部で不可分に `mtx` を解放して `cv` の待機キューで眠り、起こされて戻る前に再び `mtx` を獲得し直してから呼び出し元へ返ります。
* **`cond_signal(&cv)`：** `cv` で眠っているスレッドがあればそのうち**1つ**を起こします（いなければ何もしません）。
* **`cond_broadcast(&cv)`：** `cv` で眠っている**すべて**のスレッドを一斉に起こします。

（※実は、前々節 [4-4節](4-4.md)で実装した xv6 カーネルの `sleep(chan, lk)` と `wakeup(chan)` は、カーネル内部における条件変数の仕組みそのものでした。）

#### (3) Hoare式（IRR）vs Mesa式（non-IRR）の決定的な違い

モニタの中でスレッド P（起こす側）が `cond_signal(&cv)` を呼んだとき、待機キューにスレッド C1（起こされる側）が眠っていたとします。この瞬間、モニタの排他実行権（ロック）を持てるのは最大1スレッドだけなので、**「P と C1 のどちらが先にモニタの中で実行を続けるか」**という設計上の選択が生じます。これが有名な **Hoare式** と **Mesa式** の対比です（図4-6-2）。

1. **Hoare式（Signal-and-Wait / IRR：Immediate Resumption Requirement［即時再開要件］）：**

    * `cond_signal(&cv)` を呼んだ瞬間に、起こす側 P は即座に実行を中断してモニタ内の「緊急キュー（Urgent Queue）」へ退避し、**ロックと実行権をそのまま起こされた側 C1 へ直接手渡します**。
    * C1 は割り込み（横入り）を一切許さず即座に動き出すため、P が直前に整えた条件（`count > 0`）が**確実に真のまま保証**されます。したがって、C1 側は `while` ではなく **`if (count == 0) cond_wait(...);`** と書くことができます。
    * C1 がモニタを退場（または再び `wait`）すると、通常の入口キューより優先度の高い緊急キューにいた P が再開されます（なお、P の無駄な再開を省くため `signal` を必ずモニタ手続きの末尾に制限する **Hansen 式［Signal-and-Return］** も知られています）。

2. **Mesa式（Signal-and-Continue / non-IRR［非即時再開］）：**

    * 1970年代後半にゼロックス PARC の Mesa 言語で採用された方式です。`cond_signal(&cv)` を呼んでも、**起こす側 P はロックを手放さずそのままモニタ内の残りの処理を実行し続けます**。
    * 起こされた側 C1 は、即座に動くのではなく単に `SLEEPING` から `RUNNABLE`（入口キュー）へ移されるだけです。
    * P が `mutex_unlock` したあと、実験Bのように**入口キューの先頭にいた別スレッド C2 が先にロックを取って条件を崩す可能性**があるため、C1 は起きた直後に条件がまだ真であるとは限りません。したがって、Mesa式では必ず **`while (count == 0) cond_wait(...);`** とループで条件を再検査する決まりになっています。

| 比較項目 | Hoare式（IRR / Signal-and-Wait） | Mesa式（non-IRR / Signal-and-Continue） |
| :--- | :--- | :--- |
| **`signal` 直後の実行者** | **起こされた側 C1** が即座にロックを引き継ぐ | **起こす側 P** がそのまま実行を継続する |
| **`wait` 復帰時の条件保証** | 真であることが厳密に保証される（横入り不可） | 保証されない（他スレッドの横入り・偽起床あり） |
| **待機側のコード記述** | `if (!cond) wait();` で正しい | **必ず `while (!cond) wait();`** で再検査が必要 |
| **コンテクストスイッチ** | `signal` のたびに即時切替＋復帰で2回発生しがち | P が終わるまで切替不要でオーバーヘッドが小さい |
| **`broadcast` との相性** | 同時に1スレッドへしか渡せないため不向き | 全待機スレッドを `RUNNABLE` にするだけで自然に対応 |
| **主な採用例** | 理論モデル・一部の教育用言語 | **POSIX (`pthread`), Java, C++, Rust, Go, Linux, xv6** |

> **【コラム：なぜ現代の実用システムはすべて Mesa式を選んだのか】**
>
> 理論上は「`if` で書けて間違いにくい」Hoare式の方が美しく見えます。それにもかかわらず、POSIX スレッド（`pthread_cond_t`）、Java（`Object.wait`/`notify`）、C++（`std::condition_variable`）、Rust（`Condvar`）、Go（`sync.Cond`）に至るまで、**現代の主要な言語とOSは例外なく Mesa式を採用しています**。理由は実務上の3つの強みにあります。
>
> 1. **余計なコンテクストスイッチの削減：** 生産者が `signal` した直後に `unlock` して終わるケースが大半です。Hoare式のようにわざわざ P を途中で止めて C1 へ切り替え、C1 が終わったあとに「P の `unlock` 1行だけを実行するため」にもう1回 P へ戻すのは大きな無駄になります。
> 2. **マルチコア環境との親和性：** 現代のマルチコアCPUでは、P を強制停止せずそのまま `unlock` まで進ませ、別コアのスケジューリング柔軟性を活かす方が効率的です。Hoare式のように「1コアずつ厳密にバトンを手渡す」モデルはマルチコアのスケジューリング制約を重くします。
> 3. **防御的プログラミングの習慣化：** Mesa式で常に `while (!条件)` と書く習慣を徹底すれば、横入りだけでなくOSやハードウェア都合で起きる **偽の起床（Spurious Wakeup）** や `broadcast` による一斉起床にもそのまま耐えられる堅牢なコードになります。

### 4. 限界と補正（Critique & Adaptation）

モニタと条件変数はセマフォの弱点を大きく改善しましたが、実際の設計では次の3つの構造的な落とし穴と補正を押さえておく必要があります。

#### (1) 入れ子モニタ問題（Nested Monitor Problem）

あるモニタ A のロック `mtx_A` を保持したまま、別のモニタ B の手続きを呼び出し、その中でモニタ B の条件変数で `cond_wait(&cv_B, &mtx_B)` に入ってしまった場合を考えます（図4-6-3）。

1. `cond_wait(&cv_B, &mtx_B)` が自動的に解放するのは**内側のモニタ B のロック `mtx_B` だけ**であり、**外側のモニタ A のロック `mtx_A` は握ったまま**眠りにつきます。
2. もし、モニタ B の条件を満たして `cond_signal(&cv_B)` を呼ぶためのスレッド T2 が、まずモニタ A の手続きを経由して（すなわち `mtx_A` を獲得してから）モニタ B へ入ろうとすると、T2 は入口で `mtx_A` の解放を待って止まってしまいます。
3. 結果として、T1 は T2 が `cv_B` を起こすのを待ち、T2 は T1 が `mtx_A` を離すのを待ち合い、**デッドロック**に陥ります。

これを **入れ子モニタ問題（Nested Monitor Problem）** と呼びます。

#### (2) `signal` による「誤ったスレッドの起床」と `broadcast`（カバーリング条件）

実験Aの有限バッファ問題で、もし `not_full` と `not_empty` の2本に分けず、**たった1本の条件変数 `cv`** だけで生産者と消費者の両方を待たせ、`cond_signal(&cv)`（1スレッドだけ起こす）を使ったら何が起きるでしょうか。

1. バッファが空（容量 $N = 1$）の状態で、消費者 C1 と C2 の2人が同じ `cv` で眠っています。
2. 生産者 P がデータを1個入れて `count = 1` にし、`cond_signal(&cv)` を呼んで C1 を `RUNNABLE` にします。
3. C1 が動き出す前に、**生産者 P が続けて2個目を入れようとして `put()` へ入り、満杯（`count == 1`）のため同じ `cv` で眠りにつきます**（この時点で `cv` には C2 と P が眠っています）。
4. 続いて C1 が動いてデータを取り出し（`count = 0`）、「空きができた」と `cond_signal(&cv)` を呼んだとき、同じ `cv` で眠っていた生産者 P ではなく、**もう1人の消費者 C2 を起こしてしまう**ことがあります。
5. 起こされた C2 は `while (count == 0)` を見てまた眠りにつき、C1 も次の周回で空のバッファを見て眠ります。**生産者 P は誰も起こしてくれないため、`{P, C1, C2}` 全員が眠ったままデッドロック**します。

この問題に対する補正は2通りです。

* **基本の補正（条件変数の分離）：** 実験Aのように、待つ条件の種類ごとに専用の条件変数（`not_full` と `not_empty`）を明確に分けます。
* **一般的な補正（カバーリング条件と `cond_broadcast`）：** たとえば可変サイズのアロケータで「スレッドAは $100\text{ B}$ 空くのを待ち、スレッドBは $10\text{ B}$ 空くのを待つ」のように、条件が連続値で個別の条件変数に分けられない場合は、解放時に **`cond_broadcast(&cv)`** で全員を起こし、各スレッドが自分の `while (free_bytes < my_need)` で再判定する（カバーリング条件：Covering Condition）設計をとります。

#### (3) 条件変数の「状態レス」による Lost Wakeup 防止の徹底

条件変数はセマフォと違い過去の `signal` を記憶しないため、もし生産者側が `mtx` のロックを解放した**後**で状態変数 `count` を変更すると、消費者が `count == 0` を確認して `cond_wait` へ入る隙間に更新と通知がすり抜け、[4-4節](4-4.md)で見た Lost Wakeup が再発します（なお、状態変数 `count` の更新自体を `mtx` の中で完了していれば、POSIX 仕様上 `mutex_unlock` 直後に `cond_signal` を呼んでも Lost Wakeup は起きませんが、条件変数の破棄競合を防ぎコードの見通しを保つため通常はロック内で `cond_signal` を呼びます）。**「条件式に現れるすべての共有変数の読み書きは、必ず `cond_wait` に渡すのと同じミューテックスの保護下で行う」**ことが絶対条件です。

>
> 2. **（ミューテックスと条件変数によるセマフォの実装）**
>     ミューテックス `mtx`、条件変数 `cv`、および整数変数 `value` を使って、非負計数セマフォの `sem_wait()` と `sem_signal()` をそれぞれ数行の擬似コードで実装してください。また、Mesa 式環境において `sem_wait()` 内で `if (value == 0)` ではなく **`while (value == 0)`** を使わなければならない理由を説明してください。
>
> 3. **（可変サイズアロケータとカバーリング条件）**
>     空きバイト数 `free_bytes` を管理する可変サイズアロケータで、`alloc(bytes)` が `while (free_bytes < bytes) cond_wait(&cv, &mtx);` で待機し、`free_mem(bytes)` がメモリを返却するとします。`free_mem()` で `cond_broadcast` ではなく **`cond_signal`** を使ったときに進行が止まってしまう具体例（初期 `free_bytes`、スレッド A・B の要求量、返却量）を1つ構成し、なぜ `cond_broadcast`（カバーリング条件）が必要か説明してください。
