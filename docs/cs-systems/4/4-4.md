### 前節（4-3）の確認問題の解答

前節の最後に提示した3つの問いの解答を確認します。

1. **TTAS のキャッシュ状態遷移（MESIプロトコル）：**

    * **(a) 内側の `while (*lock != 0)` ループを回っている間：**
        コア1とコア2はロック変数に対して読み取り専用のロード命令しか発行しないため、両コアのキャッシュラインは **`Shared (S)` 状態** のまま自コアの L1 キャッシュにヒットし続けます（コア0も読み出された時点で `Shared` 状態になります）。これにより、バスやインターコネクトに無効化トラフィックが一切発生しません。

    * **(b) コア0が `*lock = 0` を書き込んだ直後：**
        コア0が書き込みのために排他権（RFO：Read-For-Ownership）を要求し、他コアへ無効化メッセージ（Invalidate）を送ります。その結果、コア0のキャッシュラインは **`Modified (M)` 状態** になり、コア1・2のキャッシュラインは **`Invalid (I)` 状態** へ遷移します。直後にコア1・2でキャッシュミスが起きて新しい値 `0` を読み込み、`amoswap` による獲得競争へ移行します。

2. **Acquire / Release バリアの欠落によるデータ不整合（RISC-V RVWMO）：**
    弱順序モデルのCPUでは、クリティカルセクション内の共有データへの書き込み（`data = new_val`）と、ロック解放の通常ストア（`lock = 0`）の間に Release バリア（`.rl`）がないと、ハードウェアによって **Store-Store 並べ替え** が起き得ます。すると、`data = new_val` が他コアから見えるようになる**より前に** `lock = 0` が他コアへ観測されてしまい、直後にロックを獲得した別コアが `data` の古い値を読み出してしまうデータ不整合が発生します。

3. **偽共有（False Sharing）の原因と構造体定義の修正：**

    * **原因：** `uint64_t` は 8 バイトのため、`counters[0]`〜`counters[3]` の合計 32 バイトすべてが**同一の 64 バイト・キャッシュライン**上に並びます。論理的には4コアが別々の要素を更新しているのに、キャッシュコヒーレンシは 64 バイトのライン単位で管理されるため、毎回の加算で他コアのラインを無効化し合う「キャッシュライン・ピンポン（偽共有）」が発生して大幅に遅くなります。
    * **修正例（C11 の `_Alignas` または明示パディングで各要素を64バイト境界へ分離）：**
      ```c
      struct counter {
          _Alignas(64) uint64_t val;   // または uint64_t val; char pad[56];
      };
      ```

## 4-4. スピンロック（割り込み禁止の理由）とスリープロック（`sleep`/`wakeup`）

### 1. 動機（Why）：なぜアトミック命令だけではOSカーネルのロックは完成しないのか

前節（[4-3節](4-3.md)）で、ハードウェアのアトミック命令（`amoswap` / CAS）と Acquire / Release メモリバリアを組み合わせることで、マルチコア環境でも正しく相互排除を行える基本的なスピンロック（TAS / TTAS）を組み立てました。

しかし、このスピンロックを実際のOSカーネル（RISC-V版 xv6 モデル）へそのまま持ち込むと、すぐに次の2つの深刻な壁に突き当たります。

1. **同じCPUコア上の「割り込みハンドラ」との自己デッドロック：**
    OSカーネルでは、通常のシステムコール処理と外部デバイスからの割り込みハンドラが同じデータ構造（コンソールバッファやディスク要求キュー等）を共有します。もしコア0がスピンロックを握ったまま割り込みを受け、その割り込みハンドラが同じロックを獲得しようとすると、自コア自身が永久にスピンし続けてシステムが凍結します。

2. **長時間の待機（ディスクI/O等）におけるCPU浪費と割り込み停止の矛盾：**
    スピンロックは待機中ずっとCPUコアを100%回し続け、しかもデッドロック防止のため保持中は割り込みを禁止します。もしディスクの読み書き完了（数ミリ秒＝数百万サイクル）を待つあいだずっとスピンロックを握り続けたら、そのCPUコアは他のプロセスへ切り替えることすらできず完全に止まってしまいます。

したがってOSカーネルは、用途の異なる次の **2種類のロック** を使い分ける必要があります。

* **スピンロック（Spinlock）：** 数十〜数百命令で終わる**短時間**のクリティカルセクション用です。割り込みを禁止して高速に排他制御します。
* **スリープロック（Sleeplock）と `sleep`/`wakeup`：** ディスクI/O待ちなどの**長時間**の待機用です。待っているあいだプロセスを `SLEEPING` 状態へ移してCPUを別プロセスへ譲ります。

本節では、xv6（RISC-V）の実際のカーネル実装に沿って、スピンロックの割り込み禁止管理から、Lost Wakeup を防ぐ `sleep`/`wakeup` の精緻なロック引き継ぎ手順、そしてスリープロックの構成までを1ステップずつ解き明かします。

---

### 2. 具体例と動作イメージ（Toy Model）

コードの詳細に入る前に、OSカーネルで実際に起きる2つの代表的な事故（**割り込み自己デッドロック**と **Lost Wakeup**）を小さなシナリオで追ってみます。

#### 実験A：割り込みを禁止せずにスピンロックを握ると起きる「自己デッドロック」

CPUコアが1個（コア0）の環境で、コンソール入出力を保護するスピンロック `cons.lock` を考えます。

1. プロセスAが `write()` システムコールでカーネルへ入り、画面へ文字を出力するため `acquire(&cons.lock)` でロックを獲得します（`cons.lock.locked = 1`）。
2. ロックを保持してバッファを操作している**まさにその途中**で、ユーザがキーボードを押して**外部割り込み**が発生します。
3. コア0は現在の `write()` の実行を強制中断し、同じコア0上で割り込みハンドラ `consoleintr()` を開始します。
4. `consoleintr()` は入力文字をバッファへ入れるため、`acquire(&cons.lock)` を呼び出します。
5. `cons.lock.locked` はすでに `1` なので、`consoleintr()` は解放を待って **`while (amoswap(...) != 0)` でスピンし続けます**。
6. しかし、`cons.lock` を解放できるのは中断された `write()` だけであり、`write()` が再開できるのは `consoleintr()` が終わって `sret` で戻った後だけです。

こうして、別コアとの競合ではなく**自分自身のコア上で永久に膠着（自己デッドロック）**してしまいます。これが、スピンロックを獲得する**直前に必ず自コアの割り込みを禁止しなければならない**根本理由です。

#### 実験B：素朴な `sleep` / `wakeup` で起きる「目覚まし時計の聞き逃し（Lost Wakeup）」

次に、ディスクI/O待ちのように長い待機でCPUを譲るため、[3-2節](../3/3-2.md)の `SLEEPING` 状態を使った素朴な `sleep(chan)` と `wakeup(chan)` を考えてみます（`chan` は「何を待っているか」を表す任意の識別アドレス＝待機チャネルです）。

生産者（コア1）がデータを1個作って `count = 1` にし、消費者（コア0）が `count == 0` のあいだ眠って待つとします。もし `sleep(chan)` がロックを受け取らずに単独で動作すると、次の隙間が生まれます。

```c
// 失敗例：ロックを引き継がない素朴な消費者コード
acquire(&buf_lock);
while (count == 0) {
    release(&buf_lock);   // (1) ロックを持ったまま眠れないので先に解放
                          //     ← ここに致命的な隙間がある
    sleep(&buf);          // (2) 自分の状態を SLEEPING にして CPU を譲る
    acquire(&buf_lock);
}
```

1. 消費者（コア0）が `count == 0` を確認し、`(1)` で `buf_lock` を解放した直後にタイミングよく中断されます。
2. その瞬間に生産者（コア1）が `buf_lock` を獲得し、データを入れて `count = 1` にし、`wakeup(&buf)` を呼んでロックを解放します。
3. `wakeup(&buf)` はプロセス表を見て `SLEEPING` 状態のプロセスを起こそうとしますが、消費者はまだ `(2)` を実行していないため `RUNNING` のままであり、**`wakeup` は誰にも届かず空振り**します。
4. 直後に消費者（コア0）が `(2) sleep(&buf)` を実行して `SLEEPING` 状態に入ります。すでにデータは届いており生産者はもう `wakeup` を呼ばないため、**消費者は永遠に目覚めません**。

この古典的かつ重要な並行バグを **Lost Wakeup（起床通知の喪失）** と呼びます。

### 3. 構造・アルゴリズム・実装（What）

#### (1) xv6 スピンロックの実装：`acquire` / `release` と `push_off` / `pop_off`

実験Aの自己デッドロックを防ぐには「ロック獲得前に割り込みを禁止し、解放後に割り込みを許可する」必要があります。ところが、ここで1つ繊細な問題が生じます。カーネル内では「ロックAを握った状態で、さらに関数を呼んでロックBを握る」という**ロックの入れ子（ネスト）**が頻繁に起きるのです。

もし `release(&B)` の末尾で無条件に `intr_on()`（割り込み許可）を呼んでしまうと、**まだ外側のロックAを保持している最中なのに割り込みが許可されてしまい**、再び自己デッドロックの危険に晒されます。

そこで xv6 では、各CPUコア固有の管理構造体 `struct cpu` に次の2つのフィールドを持たせ、**ネスト回数管理付きの割り込み禁止関数 `push_off()` / `pop_off()`** を用意します（図4-4-1）。

* `int noff;`：現在入れ子になっている `push_off()` の深さ（初期値 `0`）。
* `int intena;`：`noff` が `0` から `1` へ増えた瞬間（一番外側）に、もともと割り込みが許可されていたか否かを記憶するフラグ。

```c
void push_off(void) {
    int old = intr_get();    // 現在の sstatus.SIE（割り込み許可状態）を取得
    intr_off();              // ハードウェアの割り込みを禁止
    if (mycpu()->noff == 0)
        mycpu()->intena = old;   // 一番外側の元の状態だけを記録
    mycpu()->noff += 1;
}

void pop_off(void) {
    struct cpu *c = mycpu();
    c->noff -= 1;
    if (c->noff == 0 && c->intena)
        intr_on();           // ネストが完全に 0 に戻り、元が許可だったときだけ再許可
}
```

この `push_off` / `pop_off` と前節のアトミック命令・メモリバリアを組み合わせたものが、xv6 のスピンロック `acquire()` / `release()` の完成形です。

```c
void acquire(struct spinlock *lk) {
    push_off();                           // 1. 割り込み禁止（自己デッドロック防止）
    if (holding(lk))                      // 2. 自コアが既に保持中（lk->locked && lk->cpu == mycpu()）なら検知
        panic("acquire");
    while (__sync_lock_test_and_set(&lk->locked, 1) != 0)
        ;                                 // 3. amoswap.w.aq で 1 を書き込み旧値 0 を待つ
    __sync_synchronize();                 // 4. Acquire バリア（CS内の先行読出を禁止）
    lk->cpu = mycpu();                    // デバッグ用：保持しているCPUコアを記録
}

void release(struct spinlock *lk) {
    if (!holding(lk))
        panic("release");
    lk->cpu = 0;
    __sync_synchronize();                 // 1. Release バリア（CS内の書込完了を保証）
    __sync_lock_release(&lk->locked);     // 2. amoswap.w.rl で 0 を書いてロック解放
    pop_off();                            // 3. ネストが 0 になれば元の割り込み状態へ復元
}
```

#### (2) Lost Wakeup を完全に防ぐ xv6 の `sleep(chan, lk)` と `wakeup(chan)`

実験Bの Lost Wakeup が起きた根本原因は、「条件 `count == 0` を守るロック `lk` を解放してから、`p->state = SLEEPING` を設定するまで」のあいだに**どのロックも守っていない隙間**が空いたことでした。

xv6 は、**条件保護ロック `lk` を `sleep(chan, lk)` の第2引数として引き渡し、`sleep` の内部で「自プロセスのロック `p->lock` へバトンリレーする」**ことで、この隙間を完全に0ナノ秒へ閉じます（図4-4-2）。

```c
// 正しい消費者側の呼び出し方
acquire(&buf_lock);
while (count == 0) {
    sleep(&buf, &buf_lock);   // buf_lock を保持したまま sleep へ渡す
}
/* データを取り出す */
release(&buf_lock);
```

`sleep(void *chan, struct spinlock *lk)` と `wakeup(void *chan)` の実装は次の通りです。

```c
void sleep(void *chan, struct spinlock *lk) {
    struct proc *p = myproc();

    // 核心：先に p->lock を獲得してから、条件保護ロック lk を解放する
    acquire(&p->lock);
    release(lk);

    // ここから p->lock に守られた状態で安全に眠りにつく
    p->chan  = chan;
    p->state = SLEEPING;
    sched();                  // 3-3節の swtch() でスケジューラへCPUを譲る

    // wakeup で起こされてここへ戻ってきたときの後片付け
    p->chan = 0;
    release(&p->lock);
    acquire(lk);              // 元の条件保護ロックを取り直して呼び出し元へ戻る
}

void wakeup(void *chan) {
    for (struct proc *p = proc; p < &proc[NPROC]; p++) {
        if (p != myproc()) {
            acquire(&p->lock);
            if (p->state == SLEEPING && p->chan == chan)
                p->state = RUNNABLE;
            release(&p->lock);
        }
    }
}
```

なぜこれで Lost Wakeup が数学的に絶対に起きないのかを確認しましょう。生産者側も `acquire(&buf_lock); count = 1; wakeup(&buf); release(&buf_lock);` のように**同じ条件保護ロック `buf_lock` を保持した状態**で状態更新と `wakeup` を行います（あるいは `release(&buf_lock)` 直後に `wakeup` を呼びます）。

* 消費者が `sleep` の中で **`release(lk)` を呼ぶより前**は、消費者が `lk` を握っているため、生産者は `count = 1` に更新して `wakeup` を呼ぶことができません。
* 消費者が **`release(lk)` を呼んだ瞬間**には、すでに消費者は **`p->lock` を握っています**。そのため、生産者が直後に `lk` を獲得して `wakeup(&buf)` を呼んでも、`wakeup` 内の `acquire(&p->lock)` で待たされます。
* 消費者が `p->state = SLEEPING` にして `sched()` で自プロセスのカーネルスタックを完全に離れ、スケジューラ側で `release(&p->lock)` した直後に、`wakeup` が `p->lock` を獲得し、**確実に `SLEEPING` 状態の消費者を見つけて `RUNNABLE` へ起こします**（もし `sched()` の前に `p->lock` を離すと、別コアの `wakeup` が即座に消費者を `RUNNABLE` にして起動してしまい、2つのコアが同じカーネルスタックを同時に使って破壊する事故が起きるため、解放は必ずスケジューラ側で行います）。

つまり、「条件の検査」から「`SLEEPING` 状態の確定」までの全期間において、**`lk` と `p->lock` の少なくとも一方が常に握られ続けている（オーバーラップしている）**ため、通知がすり抜ける隙間が完全に消滅するのです。

#### (3) スリープロック（`sleeplock`）の構築とスピンロックとの使い分け

ここまでのスピンロックと `sleep`/`wakeup` を組み合わせると、**「保持したまま割り込みを許可し、ディスクI/Oなどで眠ることもできる長時間用ロック（スリープロック：カーネル版ミューテックス）」**がわずか数行で作れます。

```c
struct sleeplock {
    uint locked;           // 1 なら保持中
    struct spinlock lk;    // 上の locked フラグ自体を守るための内部スピンロック
    char *name;
    int pid;               // 現在ロックを保持しているプロセスの PID
};

void acquiresleep(struct sleeplock *lk) {
    acquire(&lk->lk);              // 短い内部スピンロックを獲得
    while (lk->locked) {           // 誰かが保持中なら
        sleep(lk, &lk->lk);        // CPUを譲って SLEEPING に入る
    }
    lk->locked = 1;
    lk->pid = myproc()->pid;
    release(&lk->lk);              // 内部スピンロックはすぐ解放（割込は許可に戻る）
}

void releasesleep(struct sleeplock *lk) {
    acquire(&lk->lk);
    lk->locked = 0;
    lk->pid = 0;
    wakeup(lk);                    // 待っているプロセスを起こす
    release(&lk->lk);
}
```

内部スピンロック `lk->lk` は `locked` フラグの検査と書き換えの一瞬だけ握ってすぐ解放するため、**スリープロック本体（`lk->locked == 1`）を保持している間は割り込みが許可されたまま**になり、そのままディスクの読み書きで `sleep` したりタイマ割り込みで他プロセスへ切り替えたりしても完全に安全です。

| 比較項目 | スピンロック（`spinlock`） | スリープロック（`sleeplock`） |
| :--- | :--- | :--- |
| **待機中の動作** | CPUを100%回してビジーウェイト | `SLEEPING` 状態へ移りCPUを他プロセスへ譲る |
| **適した保持時間** | 極短時間（数十〜数百命令、メモリ操作のみ） | 長時間（ディスクI/Oやファイル操作をまたぐ区間） |
| **保持中の割り込み** | **禁止**（`push_off` による自己デッドロック防止） | **許可**（内部スピンロックは即解放されるため） |
| **保持中の `sleep` / `yield`** | **厳禁**（割り込み禁止のまま手放すと破綻） | **可能**（I/O待ちで安全に眠れる） |
| **割り込みハンドラからの利用** | **可能** | **不可**（割り込みハンドラはプロセスではないため眠れない） |
| **所有権の単位** | CPUコア（`lk->cpu`） | プロセス（`lk->pid`） |

> **【コラム：ユーザ空間の「ハイブリッドロック」：Linux の `futex`（Fast Userspace Mutex）】**
>
> ユーザ空間のマルチスレッドプログラム（Cの `pthread_mutex_lock` や Rust の `Mutex`）でも、「待っている間はOSに眠らせてもらいたい（スリープロックの利点）」と同時に、「競合が起きていない通常時は高速に通過したい」という要求があります。もし毎回カーネルへシステムコールを発行してロックを取っていたら、[3-1節](../3/3-1.md)で見たモード切替のコストが毎回かかってしまいます。
>
> そこで現代の Linux が提供しているのが **`futex`（Fast Userspace Mutex）** です。`futex` は、ユーザ空間の共有整数変数 `state` に対する**2段階のハイブリッド戦略**をとります。
>
> 1. **高速経路（競合なし：99%のケース）：** ユーザ空間でハードウェアの CAS（[4-3節](4-3.md)）を1回実行し、`state` を `0 → 1` に変えられれば**システムコールを1回も呼ばずに**ロック獲得完了。解放時も `1 → 0` に戻すだけで完了します。
> 2. **低速経路（競合発生時のみ）：** CAS に失敗して他スレッドが保持中だと分かったときだけ、`futex(FUTEX_WAIT, &state, expected)` システムコールを呼んでOSカーネルの待機キューへ `SLEEPING` に入ります。このときカーネル内部でも Lost Wakeup を防ぐため、「`state == expected` がまだ成り立っているか」をカーネル内ロックのもとで再検査してから眠らせます。
>
> このように「競合ゼロならユーザ空間だけで完結、競合時だけカーネルへ眠る」構造が、現代の高速なミューテックス実装の標準になっています。

### 4. 限界と補正（Critique & Adaptation）

#### (1) ロックの獲得順序（Lock Ordering）とスピンロック保持中の `sleep` 禁止

スピンロックやスリープロックを導入しても、複数のロックを同時に握る場面では [4-1節](4-1.md)の **循環待機によるデッドロック** が常に隣り合わせです。たとえば、プロセスAがロック `L1` → `L2` の順に獲得し、プロセスBが `L2` → `L1` の順に獲得しようとすると即座にデッドロックします。

さらに、**スピンロックを保持したまま `sleep()` や `yield()` を呼ぶこと**も厳禁です。スピンロック保持中は割り込みが禁止されているため、その状態でCPUを手放すとタイマ割り込みが二度と起きなくなったり、他コアがロック待ちで永遠にスピンしたりします。

これらに対するカーネル実装上の補正は次の2点です。

1. **グローバルなロック順序規約（Lock Ordering）：** 「常に親ディレクトリ → 子ファイル」「常に条件ロック `lk` → プロセスロック `p->lock`」のように、カーネル全体でロック獲得の順序を厳格に定め、循環待機を構造的に排除します。
2. **実行時アサーションによる強制検査：** xv6 の `sched()` では、コンテクストスイッチ直前に `if (mycpu()->noff != 1) panic("sched locks");` と検査し、「`p->lock` 以外のスピンロックを1つでも握ったまま眠ろうとしたバグ」を即座に検出して停止させます。

#### (2) `wakeup` の「サンダリング・ハード問題」と `while` ループ再検査

xv6 の `wakeup(chan)` は、チャネル `chan` で眠っている**すべてのプロセスを一斉に `RUNNABLE` へ起こす**（ブロードキャスト型）実装です。この単純な設計には、規模が大きくなると2つの課題が現れます（図4-4-3）。

1. **サンダリング・ハード（Thundering Herd：暴走する群れ）問題：**
    1つのスリープロック（や接続待ちソケット）の解放を 100 個のプロセスが待っているとき、`wakeup()` が 100 個全員を一斉に起こすと、全CPUコアが 100 個のプロセスを次々スケジュールしてロックを奪い合い、勝った1個以外の **99 個がまた即座に `SLEEPING` へ戻る**という莫大なコンテクストスイッチの無駄が発生します。

2. **`if` ではなく必ず `while` で条件を再検査する理由：**
    `acquiresleep()` のコードをよく見ると、`if (lk->locked)` ではなく **`while (lk->locked)`** で `sleep()` を囲んでいます。なぜなら、自分が `wakeup` で起こされて再びCPUをもらうまでのあいだに、**別のスレッドが割り込んで先に `lk->locked = 1` を奪っている可能性**（あるいは同じチャネルを共有する無関係な通知で起こされる **偽の起床：Spurious Wakeup**）があるからです。`if` で書いてしまうと、他人が保持中のロックへ2人目が突入して相互排除が破綻します。

サンダリング・ハードに対する現代OS（Linux等）の補正は、プロセス表全体を走査する代わりに**待機チャネルごとに専用の待機キュー（Wait Queue）を持ち、排他的な資源待ちでは先頭の1スレッドだけを起こす（`wake_up_one`）**設計へ発展させることです。

### 理解度チェック（次節へ進む前の確認）

本節の `push_off`/`pop_off`、Lost Wakeup の防止手順、およびロックの使い分けを確認し、次節（[4-5節](4-5.md)）へ繋ぐ問いを置きます。

> **【確認の問い】**
>
> 1. **（`push_off` / `pop_off` のネスト管理のトレース）**
>     割り込みが許可されている状態（`intr_get() == 1`、`noff == 0`）の CPU コア 0 が、順に `acquire(&A)` → `acquire(&B)` → `release(&B)` → `release(&A)` を実行します。各関数の完了直後における `mycpu()->noff` の値と、実際にハードウェアの割り込みが再許可（`intr_on()`）されるタイミングを答えてください。
>
> 2. **（Lost Wakeup を防ぐロックのバトンリレー）**
>     xv6 の `sleep(chan, lk)` の内部では、必ず「**先に `acquire(&p->lock)` してから `release(lk)` する**」順序をとります。もしこの2行の順番を逆にして「先に `release(lk)` してから `acquire(&p->lock)` する」と書いてしまった場合、どのようなインターリービングで Lost Wakeup が発生するでしょうか。生産者（別コア）の動きとあわせて簡潔に説明してください。
>
> 3. **（次節への伏線：0/1 ロックから「残り個数」を数える同期プリミティブへ）**
>     本節のスピンロックとスリープロックは、クリティカルセクションへ同時に入れる数を「最大1スレッド」に制限する二値（0か1）の排他制御でした。では、「最大 $N$ 個までデータが入る有限バッファに対して、空きがある間だけ生産者が書き込み、データがある間だけ消費者が取り出す」といった**資源の個数や順序の同期**を簡潔に表現するには、どのような同期プリミティブ（**セマフォ**）を使えばよいでしょうか。
