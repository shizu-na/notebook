### 前節（2-3）の確認問題の解答

前節の最後に提示した3つの問いの解答を確認します。問1で見た「共通接頭辞を持つ規則を左括り出ししなければならない」という $\text{LL}(1)$ の窮屈さが、そのまま本節（上向き構文解析・LR法）の動機へ繋がります。

1. **非 $\text{LL}(1)$ 文法の衝突証明と左括り出しによる $\text{LL}(1)$ 化：**

    * **(a) $\text{LL}(1)$ でないことの証明：**
        2つの規則の右辺はどちらも終端記号 $\text{id}$ で始まるため、$\varepsilon$ を導出せず選択集合は次のようになります。

        * $\text{director}(S \to \text{id}\,\texttt{=}\,E) = \text{first}(\text{id}\,\texttt{=}\,E) = \{\text{id}\}$ です。
        * $\text{director}(S \to \text{id}\,\texttt{(}\,E\,\texttt{)}) = \text{first}(\text{id}\,\texttt{(}\,E\,\texttt{)}) = \{\text{id}\}$ です。

        両者の交わりは $\{\text{id}\} \cap \{\text{id}\} = \{\text{id}\} \neq \emptyset$ となり、先頭トークン `id` を1個見ただけでは2規則を区別できないため、このままでは **$\text{LL}(1)$ 文法ではありません**。

    * **(b) 左括り出しによる書き換えと再検証：**
        共通の先頭記号 $\text{id}$ をくくり出して新しい非終端記号 $S'$ を導入すると、等価な文法は次のようになります。

        $$
        S \to \text{id}\,S', \qquad S' \to \texttt{=}\,E \;\mid\; \texttt{(}\,E\,\texttt{)}
        $$

        $S'$ の2規則の選択集合は $\text{director}(S' \to \texttt{=}\,E) = \{\texttt{=}\}$ と $\text{director}(S' \to \texttt{(}\,E\,\texttt{)}) = \{\texttt{(}\}$ であり、交わりは $\{\texttt{=}\} \cap \{\texttt{(}\} = \emptyset$ となるため、**$\text{LL}(1)$ 文法**になります。

2. **$\varepsilon$ 伝播が2段階起きる文法の $\text{first}$・$\text{follow}$・$\text{director}$ 集合と $\text{LL}(1)$ 判定：**

    * **(a) $\text{first}$ 集合と $\text{follow}$ 集合：**

        * $\text{first}(A) = \{\texttt{a},\; \varepsilon\}$、$\text{first}(B) = \{\texttt{b},\; \varepsilon\}$ です。
        * $\text{first}(S)$ は $A$ も $B$ も $\varepsilon$ になり得るため後ろの `c` まで伝播し、かつ `c` は $\varepsilon$ にならないため $\text{first}(S) = \{\texttt{a},\; \texttt{b},\; \texttt{c}\}$ となります（$\varepsilon$ は含みません）。
        * $\text{follow}(S) = \{\texttt{\$}\}$ です。
        * $\text{follow}(B) = \{\texttt{c}\}$ です（規則 $S \to A B \texttt{c}$ で $B$ の直後に `c` があるため）。
        * $\text{follow}(A)$ は規則 $S \to A B \texttt{c}$ で $A$ の直後に $B\texttt{c}$ が続き、$\varepsilon \in \text{first}(B)$ なので `c` も含まれて $\text{follow}(A) = \text{first}(B\texttt{c}) = \{\texttt{b},\; \texttt{c}\}$ となります。

    * **(b) $\text{director}$ 集合と $\text{LL}(1)$ 判定：**

        * **$A$ の2規則：** $\text{director}(A \to \texttt{a}) = \{\texttt{a}\}$、$\text{director}(A \to \varepsilon) = \text{follow}(A) = \{\texttt{b},\; \texttt{c}\}$ であり、交わりは $\emptyset$ です。
        * **$B$ の2規則：** $\text{director}(B \to \texttt{b}) = \{\texttt{b}\}$、$\text{director}(B \to \varepsilon) = \text{follow}(B) = \{\texttt{c}\}$ であり、交わりは $\emptyset$ です。

        すべての分岐で選択集合が互いに素であるため、この文法は **$\text{LL}(1)$ 文法です**。

3. **右結合べき乗演算子 `^` の再帰下降設計と C 言語の `typedef` 問題：**

    * **(a) べき乗演算子 `^` の階層と `parse_P()` の実装：**
        乗算 $T$ より優先順位が高く因子 $F$ より低い位置へ非終端記号 $P$ を挿入し、階層を $E \to T \to P \to F$ とします（$T$ の中では `parse_F()` の代わりに `parse_P()` を呼びます）。`^` は**右結合**であるため、`while` ループではなく**右再帰**（規則 $P \to F \texttt{\^} P \mid F$）で次のように書きます。

        ```c
        Node *parse_P(void) {
            Node *lhs = parse_F();
            if (tok == '^') {
                next_tok();
                Node *rhs = parse_P();   // 右側を先に再帰でまとめる → 右結合
                return new_bin('^', lhs, rhs);
            }
            return lhs;
        }
        ```

        これにより `2 ^ 3 ^ 2` は内側の呼び出しで `3 ^ 2 = 9` が先に組み上がり、外側で `2 ^ (3 ^ 2) = 512` となります。

    * **(b) `A * B;` のあいまいさと Lexer Hack：**
        `A` が `typedef` された型名なら「型 `A` へのポインタ変数 `B` の宣言」、通常の変数名なら「`A` と `B` の乗算式」になり、トークン列の形 `[ID(A)] [*] [ID(B)] [;]` だけでは区別できません。実用 C コンパイラは解析途中で記号表を参照し、`typedef` 登録済みの識別子だけを `TYPE_NAME` という別トークンとして字句解析器から返す **Lexer Hack** によって解決しています。

## 2-4. 構文解析②：上向き解析（$\text{SLR}(1)$・$\text{LR}(1)$・$\text{LALR}(1)$）

### 1. 動機（Why）：なぜ「判断を後ろへ遅らせる」だけで、扱える文法が大きく広がるのか

前節（[2-3節](2-3.md)）で学んだ再帰下降構文解析（$\text{LL}(1)$）は実装が素直で分かりやすい反面、**「まだ入力の先頭1トークンしか見ていない段階で、これから使う生成規則を決め打ちしなければならない」**という窮屈さを抱えていました。その結果、自然な左再帰 $E \to E \texttt{+} T$ がそのまま使えず、共通接頭辞を持つ規則も書き換え（左括り出し）が必要になりました。

これに対して発想を逆転させ、**「どの規則を使うかの判断を、右辺のトークンを最後まで読み終えるまで遅らせる」**のが **上向き（ボトムアップ）構文解析**、その代表格である **LR構文解析** です（`L` は左から右へ読む Left-to-right、`R` は**最右導出の逆順** Reverse rightmost derivation［左側から完成した部品を順に下から上へまとめていくと、逆再生したときに右から展開する最右導出と一致すること］を意味します）。

LR構文解析には、実用上の大きな強みが3つあります。

1. **左再帰をそのまま書ける：** $E \to E \texttt{+} T \mid T$ のように自然な文法のまま、左結合のASTを歪みなく組み立てられます。
2. **表現できる文法クラスが $\text{LL}(1)$ より大幅に広い：** 先頭が共通する規則も、右辺を読み進めて違いが現れた時点で自然に判別できます。
3. **線形時間 $O(n)$ で解析でき、文法ファイルから自動生成できる：** Yacc や Bison といったパーサ生成系（文法定義からパーサのソースコードを自動生成する**コンパイラ・コンパイラ**）の基盤アルゴリズムとして広く使われています。

本節では、小さな加算式文法を題材に、LR構文解析器のスタック動作（シフトと還元）から始め、$\text{LR}(0)$ オートマトンによる **$\text{SLR}(1)$ 構文解析表**の構成、そして文脈精度を高めた **$\text{LR}(1)$** と実用圧縮版の **$\text{LALR}(1)$** への発展を順に辿ります。

---

### 2. 具体例と動作イメージ（Toy Model）

自動生成アルゴリズムに入る前に、まずは完成した解析表を使って、LR構文解析器が数式 `1 + 2` をどのように「下から上へ」組み立てていくかを最後まで手計算で追ってみます。

#### 実験A：左再帰のままの式文法で `1 + 2` をシフト＆還元する

次の左再帰を含む小さな式文法を考えます。元の開始記号 $E$ は規則 $(1)$ の右辺にも現れるため、$E$ への還元が「入力全体の受理」なのか「まだ外側の式の一部」なのかを一意に区別できるよう、右辺に一度も現れない新しい開始記号 $S'$ と規則 $(0)\; S' \to E$ を付け足した **拡大文法（Augmented Grammar）** を用意します。`num` は数値トークン（`1` や `2`）を表します。

$$
\begin{aligned}
(0)\quad S' &\to E \\
(1)\quad E  &\to E \texttt{+} T \\
(2)\quad E  &\to T \\
(3)\quad T  &\to \text{num}
\end{aligned}
$$

LR構文解析器（ドライバ）は、**スタック**（状態番号と文法記号を交互に積む）と **構文解析表**（`ACTION` 表と `GOTO` 表）だけを使って、次の4種類の動作を繰り返します（図2-4-1）。

* **シフト（`s` $k$）：** 入力の先頭トークンを1個読み込んでスタックへ積み、状態 $k$ へ移ります。
* **還元（`r` $m$）：** 規則 $(m): A \to \alpha$ の右辺の記号数 $|\alpha|$ 個分の「記号と状態番号の組」をスタック頂上からポップします。次に、露出したスタック頂上の状態番号 $s$ と左辺の非終端記号 $A$ を使って `GOTO[s, A]` を引き、$A$ とその新状態番号をスタックへプッシュします。
* **受理（`acc`）：** 入力全体が正しく構文解析されたとして正常終了します。
* **エラー（空欄）：** 文法違反として構文エラーを報告します。

後述する手順で作成したこの文法の解析表（次項に全表を掲載）を用いて、入力 `num + num $`（`1 + 2 $`）をトレースします。

| ステップ | スタック（底 → 頂上） | 残りの入力 | 参照セル・動作 | 実行内容（木への反映） |
| :---: | :--- | ---: | :--- | :--- |
| 1 | `0` | `num + num $` | `ACTION[0, num] = s3` | `num`(1) をシフトし状態 `3` へ |
| 2 | `0 num 3` | `+ num $` | `ACTION[3, +] = r3` | $T \to \text{num}$ で還元 → `GOTO[0, T] = 2` |
| 3 | `0 T 2` | `+ num $` | `ACTION[2, +] = r2` | $E \to T$ で還元 → `GOTO[0, E] = 1` |
| 4 | `0 E 1` | `+ num $` | `ACTION[1, +] = s4` | `+` をシフトし状態 `4` へ |
| 5 | `0 E 1 + 4` | `num $` | `ACTION[4, num] = s3` | `num`(2) をシフトし状態 `3` へ |
| 6 | `0 E 1 + 4 num 3` | `$` | `ACTION[3, $] = r3` | $T \to \text{num}$ で還元 → `GOTO[4, T] = 5` |
| 7 | `0 E 1 + 4 T 5` | `$` | `ACTION[5, $] = r1` | $E \to E \texttt{+} T$ で還元 → `GOTO[0, E] = 1` |
| 8 | `0 E 1` | `$` | `ACTION[1, $] = acc` | **受理**（構文木が完成） |

還元された規則をステップ順に並べると $(3) \to (2) \to (3) \to (1)$ です。これを逆から辿ると、

$$
E \xRightarrow{(1)} E \texttt{+} T \xRightarrow{(3)} E \texttt{+} \text{num} \xRightarrow{(2)} T \texttt{+} \text{num} \xRightarrow{(3)} \text{num} \texttt{+} \text{num}
$$

となり、ちょうど**最右導出の逆順**になっていることが分かります。

### 3. 構造・アルゴリズム・実装（What）

#### (1) $\text{LR}(0)$ 項の閉包と `goto` 演算によるオートマトン構築

実験Aのドライバ自体はどんな文法でも同じコードで動きます。核心は、**「与えられた文法から、どうやって `ACTION` 表と `GOTO` 表を自動生成するか」**です。

その土台となる概念が **$\text{LR}(0)$ 項（LR(0) item）** です。これは、生成規則の右辺のどこかに点「$\cdot$」を1個打ったもので、**「右辺のうち点の左側まではすでにスタック上へ読み込み終わり、これから点の右側が来るのを待っている」**という進捗状況を表します。たとえば規則 $E \to E \texttt{+} T$ からは、次の4つの $\text{LR}(0)$ 項が作れます。

$$
[E \to \cdot E \texttt{+} T], \quad [E \to E \cdot \texttt{+} T], \quad [E \to E \texttt{+} \cdot T], \quad [E \to E \texttt{+} T \cdot]
$$

点が右端まで到達した項 $[E \to E \texttt{+} T \cdot]$ は、「右辺全体を読み終えたので、今すぐ $E$ へ還元できる」ことを意味します。

ここで、[2-2節](2-2.md)の部分集合構成法（$\varepsilon$-閉包と状態遷移）と同じ発想で、2つの演算を定義します。

1. **閉包演算 $\text{closure}(I)$：** 項集合 $I$ の中に、点の直後に非終端記号 $B$ がある項 $[A \to \alpha \cdot B \beta]$ が含まれていれば、「これから $B$ を読み始める可能性がある」ため、$B$ のすべての生成規則 $B \to \gamma$ について $[B \to \cdot \gamma]$ を $I$ へ追加します（変化しなくなるまで繰り返します）。元の項を**カーネル項**、閉包で追加された項を**閉包項**と呼びます。
2. **遷移演算 $\text{goto}(I, X)$：** 項集合 $I$ の中で、点の直後に記号 $X$（終端または非終端）があるすべての項について点を $X$ の右へ1つ進め、その集合の $\text{closure}$ をとります。

実験Aの拡大文法に対し、初期状態 $I_0 = \text{closure}(\{[S' \to \cdot E]\})$ から `goto` で到達可能なすべての状態集合を列挙すると、次の **6状態の決定性有限オートマトン（$\text{LR}(0)$ オートマトン）** が機械的に得られます（図2-4-2）。理論的には、この $\text{LR}(0)$ オートマトンは「正しい構文解析の途中でスタック上に現れ得る記号列（**活性接頭辞：Viable Prefix**）」の全体を受理するDFAになっており、[2-2節](2-2.md)の有限オートマトン理論がそのまま構文解析器の心臓部へ繋がっています。

* **$I_0$：** $\{ [S' \to \cdot E],\; [E \to \cdot E \texttt{+} T],\; [E \to \cdot T],\; [T \to \cdot \text{num}] \}$
* **$I_1 = \text{goto}(I_0, E)$：** $\{ [S' \to E \cdot],\; [E \to E \cdot \texttt{+} T] \}$
* **$I_2 = \text{goto}(I_0, T)$：** $\{ [E \to T \cdot] \}$
* **$I_3 = \text{goto}(I_0, \text{num})$：** $\{ [T \to \text{num} \cdot] \}$
* **$I_4 = \text{goto}(I_1, \texttt{+})$：** $\{ [E \to E \texttt{+} \cdot T],\; [T \to \cdot \text{num}] \}$
* **$I_5 = \text{goto}(I_4, T)$：** $\{ [E \to E \texttt{+} T \cdot] \}$（なお $\text{goto}(I_4, \text{num}) = I_3$）

#### (2) $\text{SLR}(1)$ 構文解析表の構成

図2-4-2の $\text{LR}(0)$ オートマトンから、次の4規則で **$\text{SLR}(1)$（Simple LR(1)）構文解析表** を埋めます。

1. **シフト：** 状態 $I_i$ に終端記号 $a$ の遷移 $\text{goto}(I_i, a) = I_j$ があれば、`ACTION[i, a] = s` $j$ とします。
2. **還元（$\text{follow}$ 集合の利用）：** 状態 $I_i$ に右端ドットの項 $[A \to \alpha \cdot]$（規則番号 $m$、ただし $A \neq S'$）があれば、[2-3節](2-3.md)で定義した **$\text{follow}(A)$ に属するすべての終端記号 $a$ に対してのみ** `ACTION[i, a] = r` $m$ とします。
3. **受理：** 状態 $I_i$ に $[S' \to E \cdot]$ があれば、`ACTION[i, $] = acc` とします。
4. **`GOTO`：** 非終端記号 $A$ の遷移 $\text{goto}(I_i, A) = I_j$ があれば、`GOTO[i, A] =` $j$ とします。

この文法では $\text{follow}(E) = \{ \texttt{+},\; \texttt{\$} \}$、$\text{follow}(T) = \{ \texttt{+},\; \texttt{\$} \}$ であるため、実験Aで使った解析表全体が次のように一意に埋まります（どのセルにも衝突がありません）。

| 状態 | `ACTION`: `num` | `ACTION`: `+` | `ACTION`: `$` | `GOTO`: $E$ | `GOTO`: $T$ |
| :---: | :---: | :---: | :---: | :---: | :---: |
| **0** | `s3` | | | `1` | `2` |
| **1** | | `s4` | `acc` | | |
| **2** | | `r2` | `r2` | | |
| **3** | | `r3` | `r3` | | |
| **4** | `s3` | | | | `5` |
| **5** | | `r1` | `r1` | | |

#### (3) $\text{SLR}(1)$ から $\text{LR}(1)$、そして実用標準の $\text{LALR}(1)$ へ

$\text{SLR}(1)$ は状態数が小さく簡潔ですが、還元してよい条件に「文法全体で $A$ の後ろに現れ得る記号すべて（$\text{follow}(A)$）」を使うため、**現在の文脈ではあり得ない先読み記号に対しても還元を登録してしまい、無用な衝突を起こす**ことがあります。

典型例が、代入文を表す次の小さな文法です（`*` はポインタ参照、`=` は代入）。

$$
S \to L \texttt{=} R \;\mid\; R, \qquad L \to \texttt{*} R \;\mid\; \text{id}, \qquad R \to L
$$

* 初期状態から代入の左辺に置ける式（**左辺値**、[2-6節](2-6.md)）$L$ を読んだ直後の状態 $I_2$ には、$[S \to L \cdot \texttt{=} R]$（次が `=` ならシフト）と $[R \to L \cdot]$（還元）が同居します。
* ここで $\text{follow}(R)$ を計算すると、規則 $L \to \texttt{*} R$ のあとに `=` が来得る（例：`*x = y`）ため、$\texttt{=} \in \text{follow}(R)$ となります。
* その結果、$\text{SLR}(1)$ では状態 $I_2$ の先読み `=` のセルに「`=` をシフト」と「$R \to L$ で還元」の両方が入ってしまい、**衝突が発生して解析できません**。
* しかし文脈を見れば、入力先頭の $L$ を $R$ へ還元したとき（$S \to R$）、その直後に `=` が続くことはありません（後ろに来得るのは入力末尾 `$` だけです）。

この精密な文脈を捉えるのが **$\text{LR}(1)$（正準 LR(1)：Canonical LR(1)）** です。$\text{LR}(1)$ では、各項の後ろに「この項が還元される文脈で本当に後ろに来得る1文字の先読み記号」をペアで持たせます。閉包演算では、項 $[A \to \alpha \cdot B \beta,\; a]$ が含まれているとき、$B$ の各規則 $B \to \gamma$ と **$\text{first}(\beta a)$ に属するすべての終端記号 $b$** に対して $[B \to \cdot \gamma,\; b]$ を追加します。

上の例で初期項 $[S' \to \cdot S,\; \texttt{\$}]$ の閉包をとると、$[S \to \cdot R,\; \texttt{\$}]$ から $[R \to \cdot L,\; \texttt{\$}]$（ここでは $\beta = \varepsilon,\; a = \texttt{\$}$ なので先読みは `$` のみ）が導かれます。すると $L$ を読んだ状態 $I_2$ には $[R \to L \cdot,\; \texttt{\$}]$ が入るため、`$` のときだけ $R \to L$ で還元し、`=` のときは迷わずシフトするため、衝突が解消します。

しかし、$\text{LR}(1)$ には大きな実用上の欠点があります。先読み記号のわずかな違いだけで別々の状態として区別するため、C言語のような実用言語では**状態数が数千個に膨れ上がり、構文解析表が数MBにも肥大化する**のです。

そこで考案されたのが、Yacc / Bison などのパーサ生成系で標準採用されている **$\text{LALR}(1)$（Look-Ahead LR(1)）** です（図2-4-3）。

* **$\text{LALR}(1)$ の仕組み：** $\text{LR}(1)$ オートマトンにおいて、先読み記号を除いた本体（**コア：$\text{LR}(0)$ 項の集合**）が一致する状態同士（つまり「今どこまで読んだか［進捗＝コア］」が同じで「次にどの文字で還元するか［先読みメモ］」だけ違う2状態）を1つに合併し、先読みメモ欄の和集合をとります。
* **効果：** 解析表の**状態数は $\text{SLR}(1)$ と同じ（コンパクト）**に抑えられながら、表現力は $\text{LR}(1)$ に非常に近く、C言語やSQLなど現実のプログラミング言語のほとんどをカバーできます。

なお、$\varepsilon$-規則を含む一般の $\text{LL}(1)$ 文法まで考慮すると、すべての $\text{LL}(1)$ 文法は $\text{LR}(1)$ に収まる（$\text{LL}(1) \subset \text{LR}(1)$）一方で、$\text{SLR}(1)$ や $\text{LALR}(1)$ には含まれない $\text{LL}(1)$ 文法も存在します（$\text{LL}(1) \not\subset \text{SLR}(1)$ かつ $\text{LL}(1) \not\subset \text{LALR}(1)$、図2-4-3左）。

> **【コラム：ぶらぶら `else` と演算子優先順位宣言（`%left` / `%right` / `%prec`）の衝突裁定規則】**
>
> [2-3節](2-3.md)で登場した「ぶらぶら `else`（`if (c1) if (c2) s1; else s2;`）」をそのまま素朴なLR文法で書くと、内側の `if (c2) s1` を読み終えて次に `else` を先読みした状態で、次の2つの動作が同じセルにぶつかります。
>
> * **シフト：** `else` をスタックへ読み込み、内側の `if (c2)` に結びつけます。
> * **還元：** いったん `if (c2) s1` を1つの文 $S$ へ還元して確定させ、後続の `else` を外側の `if (c1)` に結びつけます。
>
> Yacc や Bison などのパーサ生成系では、あいまいな文法で **シフト／還元衝突** が起きたときのデフォルト動作を **「常にシフトを優先する」** と定めています。この1つの規則により、文法を複雑に書き換えなくても「`else` は必ず最も内側の `if` に結びつく」というC言語の仕様が自動的に満たされます（文法自体を無曖昧化したい場合は、`else` が完結した `matched_stmt` と未対応の `unmatched_stmt` の2系統に規則を倍増させて書き換える古典手法もありますが、文法が煩雑になるため実務ではシフト優先が多用されます）。
>
> さらに、演算子優先順位宣言（`%left`：左結合、`%right`：右結合、`%nonassoc`：連続禁止、`%prec`：単項マイナス等へ明示的に優先順位を付与）を併用すると、実験Aのように非終端記号を階層化せず、簡潔なあいまい文法 $E \to E \texttt{+} E \mid E \texttt{*} E$ のまま衝突を裁定できます。Bison は衝突時に**「還元候補の規則の右辺に現れる最後の終端記号の優先順位」と「現在の先読みトークンの優先順位」**を比較し、先読みの方が高ければシフト、規則側が高ければ還元、同順位なら `%left` なら還元・`%right` ならシフトを選びます。
>
> ただし、デフォルトのシフト優先に頼りすぎると意図しない文法バグまで黙って握り潰してしまう危険があるため、実務の文法ファイルでは `%expect 1`（ぶらぶら `else` の1件だけシフト／還元衝突を許容し、それ以外が出たらビルドエラーにする）のように期待件数を明示して検証するのが定石です。

### 4. 限界と補正（Critique & Adaptation）

#### (1) LR 構文解析の2種類の衝突（シフト／還元衝突・還元／還元衝突）

LR構文解析表を構成したとき、1つのセル `ACTION[i, a]` に複数の異なる動作が入ってしまう状態を **衝突（Conflict）** と呼び、次の2種類があります。

1. **シフト／還元衝突（Shift/Reduce Conflict）：** 同じ状態・同じ先読み記号に対して、「さらにトークンを読み込む（シフト）」と「ここまでの記号列をまとめる（還元）」の2択が競合する状態です。演算子の優先順位不足やぶらぶら `else`、あるいは $\text{SLR}(1)$ の精度不足で発生します。
2. **還元／還元衝突（Reduce/Reduce Conflict）：** 同じ状態・同じ先読み記号に対して、「規則 $m_1$ で還元する」と「別の規則 $m_2$ で還元する」が競合する状態です。多くの場合、文法設計そのもののあいまいさ（同じ文字列を2通りの非終端記号として解釈できてしまう等）を示しており、文法の見直しが必要です。

#### (2) $\text{LALR}(1)$ 合併による還元／還元衝突と、一般化LR（GLR）への補正

$\text{LR}(1)$ から $\text{LALR}(1)$ へ同一コアの状態を合併するとき、数学的に次の重要な性質が成り立ちます。

* **シフト／還元衝突は新たに生まれない：** 合併前の両状態は同じ $\text{LR}(0)$ コアを持つため、シフト可能な記号は共通です。もし合併後にシフト／還元衝突が起きるなら、合併前の片方の $\text{LR}(1)$ 状態でもすでに同じ衝突が起きていたはずです。
* **還元／還元衝突は稀に新たに生じ得る：** たとえば状態 $I_a$ に $[A \to \alpha \cdot,\; c],\; [B \to \beta \cdot,\; d]$ があり、状態 $I_b$ に $[A \to \alpha \cdot,\; d],\; [B \to \beta \cdot,\; c]$ があるとき、合併前は衝突していませんが、合併すると $c, d$ の両方で $A$ と $B$ の**還元／還元衝突**が生じます。

また、$\text{LALR}(1)$ や $\text{LR}(1)$ であっても、C++のように「文脈や数トークン先まで読まないと構文が確定しない言語」では衝突を完全には避けられません。この限界に対する補正として、衝突が起きた地点だけ一時的にスタックを分岐させて両方の解釈を並列に進め、後ろのトークンで不正になった枝を捨てる **GLR（Generalized LR）構文解析** や、[2-3節](2-3.md)コラムで触れた**手書きの再帰下降パーサ＋先読み**が実務で使い分けられています。

> **【コラム：DeRemer-Pennello 法による $\text{LALR}(1)$ の直接構築】**
>
> 本文では理解しやすくするため「まず巨大な $\text{LR}(1)$ オートマトンを作ってからコア合併する」手順で $\text{LALR}(1)$ を説明しましたが、実際の Bison などが巨大な $\text{LR}(1)$ 状態を丸ごとメモリへ展開するわけではありません。実用ツールでは、まず小さな **$\text{LR}(0)$ オートマトンだけを構築**し、その状態グラフの上で先読み記号の伝播関係をデータフロー計算（**DeRemer-Pennello アルゴリズム**、1982年）で直接求めることで、最初から $\text{SLR}(1)$ 並みのメモリ使用量で $\text{LALR}(1)$ 表を生成します。

> **【コラム：疎な構文解析表の圧縮技法（デフォルト還元と行変位法）】**
>
> 完成した `ACTION`/`GOTO` 表は数百状態 $\times$ 数百トークンの疎な2次元配列（大半のセルが空欄＝エラー）になります。そのまま格納すると数十〜数百KBを消費しキャッシュ効率も落ちるため、Bison は次の2つの圧縮技法を使います。
>
> * **デフォルト還元：** ある状態で最も頻出する還元動作を1つだけ別配列 `yydefact[state]` に逃がし、表本体からそのセルを消去します。
> * **行変位法（Row Displacement / Comb Compression）：** 空欄だらけの各行を少しずつ横にずらしながら1本の1次元配列へ重ねて詰め込み、`yypact[state] + token` の1回の加算と正当性チェック表 `yycheck` の参照だけで元の2次元表を高速に復元します。
