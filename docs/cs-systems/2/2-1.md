### 前節（1-6）の確認問題の解答

前節の最後に提示した3つの問いの解答を確認します。問3がそのまま第2部（コンパイラと言語処理系）の導入になります。

1. **ULEB128 による可変長整数符号化の手計算（`200`）：**
    10進数の `200` は2進数で $\texttt{11001000}_2$（8ビット）です。下位から7ビットずつ分割します。
    * 下位7ビット：$\texttt{1001000}_2$（10進数で $64 + 8 = 72$）
    * 上位7ビット：$\texttt{0000001}_2$（10進数で $1$）

    下位側から並べ、継続する1バイト目のMSBに `1`、最後の2バイト目のMSBに `0` を付けます。
    * **1バイト目：** $\texttt{1\_1001000}_2 = \mathbf{\texttt{0xC8}}$（MSB=`1`：後ろにバイトが続く）
    * **2バイト目：** $\texttt{0\_0000001}_2 = \mathbf{\texttt{0x01}}$（MSB=`0`：ここで終了）

    検算すると $72 + 1 \times 2^7 = 72 + 128 = 200$ となり一致します。

2. **ソフトウェア・ブレークポイントの動作原理：**

    * **(a) 元の1バイトを復元したうえで `%rip` を `1` 減らす理由：**
        CPUが `int 3`（`0xCC`、1バイト）を実行してトラップを起こした時点で、`%rip` はすでに1バイト先の「元の命令の2バイト目」を指しています。元の先頭1バイトだけを復元して再開すると命令の途中から誤って解釈してしまうため、`%rip` を `1` 戻して元の命令の先頭から正しく実行し直す必要があります。

    * **(b) 1命令だけシングルステップ実行してから `0xCC` を埋め戻す理由：**
        元の1バイトへ戻したまま通常再開してしまうと、`0xCC` が消えたままになり、ループなどで同じ場所を2回目以降に通過したときに止まらなくなります。そのため、元の1命令だけを実行させて通過直後に再び `0xCC` を埋め戻す手順が不可欠です。

3. **高級言語から機械語への翻訳パイプライン（本節への接続）：**
    コンパイラは、人間が書いたテキスト（文字列）からいきなり機械語を生成するのではなく、「単語への切り出し（字句解析）→ 文法構造の木への変換（構文解析）→ 型と名前の検査（意味解析）→ 中間表現（IR）の生成 → 最適化 → ターゲット機械語の生成」という独立した複数のフェーズへ分割して翻訳を進めます。本節ではその全体地図を整理します。

## 2-1. コンパイラの全体構造・中間表現（IR）と実行方式（VM・JIT）

### 1. 動機（Why）：なぜソースコードからいきなり機械語へ変換せず、多段階のフェーズと「中間表現」を挟むのか

第0部と第1部では、CPUが実行する機械語・レジスタ・スタックフレーム・ELFバイナリの仕組みを見てきました。ここからは視点を180度反転させ、**「人間が書くC言語などの高級言語を、どうやって第1部で見たような機械語命令列へ自動翻訳しているのか」**という言語処理系（コンパイラ）の内部へ入ります。

初めてコンパイラを想像すると、「C言語のテキストを1行ずつ読んで、対応するx86-64命令をそのまま書き出せばよいのではないか」と思えるかもしれません。しかし、現実のプログラミング言語とCPUのあいだには、単純な1対1変換を阻む3つの大きな隔たりがあります。

1. **構造の複雑さ：** `y = a + b * (c - d);` のような入れ子の数式や、何重にもネストした `if`・`while`・関数定義・型チェックを、単なる文字列の走査だけで一度に正しく処理しようとするとプログラムが破綻します。
2. **言語とCPUの組み合わせ爆発：** 世界には C、C++、Rust、Go、Fortran のように多様なプログラミング言語があり、一方でターゲットとなるCPUも x86-64、ARM64、RISC-V など複数存在します。$M$ 個の言語から $N$ 種類のCPUへ直接翻訳器を書くと、**$M \times N$ 個の独立したコンパイラ**（さらにそれぞれに最適化器）を開発・保守しなければなりません。
3. **実行方法の多様さ：** すべての言語がC言語のように事前コンパイルされるわけではありません。Pythonのように1行ずつ解釈するものや、JavaやJavaScriptのように仮想機械や実行時コンパイルを使うものなど、「いつ翻訳するか」によってトレードオフが変わります。

本節では、コンパイラを「フロントエンド」「中間表現（IR）」「バックエンド」へ分割するアーキテクチャの全体像を掴み、さらに4つの代表的なプログラム実行方式を比較します。

各段階で何が行われているかを順に見てみます。

1. **字句解析（Lexical Analysis）：** 空白を取り除き、文字の並びを最小の意味単位である **トークン** の列（`ID(y)`, `=`, `ID(x)`, `+`, `NUM(3)`, `*`, `NUM(2)`, `;`）へ切り出します。
2. **構文解析（Syntax Analysis）：** 文法規則に従い、「`+` より `*` の方が結合が強い」ことを反映した木構造（**抽象構文木：AST**）を組み立てます。
3. **意味解析（Semantic Analysis）：** 変数 `x` や `y` が事前に宣言されているか、型が矛盾していないか（たとえば `int` と構造体を足そうとしていないか）を検査します。
4. **中間表現（IR）生成：** 木構造を、特定のCPUに依存しない単純な1ステップずつの命令列（例：`t1 = 3 * 2; t2 = x + t1; y = t2;`）へ平坦化します。
5. **最適化（Optimization）：** `3 * 2` は定数同士なのでコンパイル時に `6` へ計算してしまい（定数畳み込み）、不要な一時変数 `t1, t2` を消去して `y = x + 6;` へ簡約します。
6. **コード生成・レジスタ割当（Code Generation）：** ターゲットCPU（たとえばx86-64）の具体的なレジスタへ変数を割り当て、1-2節で見た `leal 6(%rdi), %eax` のような機械語を出力します。

### 3. 構造・アルゴリズム・実装（What）

#### (1) フロントエンド・中間表現（IR）・バックエンドの3層分離

実験Aの6ステップは、大きく **フロントエンド（Frontend）**、**ミドルエンド／中間表現（IR）**、**バックエンド（Backend）** の3つに分離されます。

* **フロントエンド（ソース言語に依存・CPUに非依存）：** 字句解析・構文解析・意味解析・IR生成を担当します。C言語やRustといったソース言語の文法と型ルールだけを知っていればよく、最終的なCPUがx86-64かRISC-Vかを知る必要はありません。
* **中間表現（IR：Intermediate Representation）とミドルエンド最適化（両方に非依存）：** どの言語でも表現でき、どのCPUへも変換しやすい共通の抽象命令形式です。定数畳み込みや不要コード削除、ループ最適化といった**言語にもCPUにも依存しない最適化**を、このIR上で1回だけ実装します。
* **バックエンド（CPUに依存・ソース言語に非依存）：** IRを入力とし、ターゲットCPU固有の命令選択、レジスタ割当、命令スケジューリング（0-6節のロード・ユースハザード回避など）を行ってアセンブリや機械語を出力します。

なお、IRの代表的な形式としては、実験Aの `t1 = 3 * 2` のように「1命令あたり最大3つのアドレス（結果1つ＋入力2つ）しか書かない」**3番地コード（Three-Address Code）** や、各変数への代入をプログラム中で必ず1回に制限してデータフロー解析を容易にする **SSA形式（Static Single Assignment：静的単一代入形式）** が広く用いられます。

| 実行方式 | 仕組みと代表例 | 長所 | 短所 |
| :--- | :--- | :--- | :--- |
| **事前コンパイラ（AOT）** | 実行前に全体をターゲットCPUの機械語へ翻訳（C, C++, Rust, Go） | 実行速度が非常に速く、実行時のメモリ消費も小さい | CPU・OSごとに別バイナリが必要。ビルド待ち時間がある |
| **インタプリタ** | ソースコード（またはAST）を1文ずつ解釈しながら直接実行（シェルスクリプト等） | ビルド不要で即座に試せる。対話実行が容易 | 同じループを回るたびに毎回解釈コストがかかる |
| **仮想機械（VM）＋バイトコード** | ソースを架空の単純CPU向け命令（**バイトコード**）へ事前変換し、各環境上のVMが解釈実行（CPython, 初期Java） | 配布するバイトコードがCPUに依存せず高い移植性を持つ | VMの解釈ループのオーバーヘッドがありネイティブより遅い |
| **JIT コンパイラ**（Just-In-Time） | VMやインタプリタで動かしつつ、実行頻度の高い箇所だけを実行時にネイティブ機械語へ翻訳（JVM HotSpot, V8 JavaScript, PyPy） | 移植性と高速な実行を両立でき、実行時情報も最適化に使える | 起動直後のウォームアップ遅延、コンパイラ常駐によるメモリ増 |

> **【コラム：コンパイラを自分自身の言語で書く「ブートストラップ（セルフホスティング）」】**
>
> GCC（Cコンパイラ）は C/C++ で書かれており、Rust のコンパイラ `rustc` は Rust 自身で書かれています。このように「言語 $L$ のコンパイラを、言語 $L$ 自身で記述してコンパイルできる状態」を **セルフホスティング（Self-hosting）** と呼びます。
>
> すると「最初の1個目のコンパイラはどうやってコンパイルしたのか？（鶏と卵問題）」という疑問が湧きます。この問題を解決する手順が **ブートストラップ（Bootstrap：自分の靴紐を引っ張って持ち上げる比喩）** です。
>
> 1. まず、すでに動く別の言語（アセンブリや既存のCコンパイラ）を使って、言語 $L$ のごく小さなサブセットだけを翻訳できる最小コンパイラ $C_0$ を作ります。
> 2. 次に、言語 $L$ の最小サブセットを使って、より高機能なコンパイラ $C_1$ を書き、$C_0$ でコンパイルして動かします。
> 3. 以降、$C_1$ を使ってさらに完全なコンパイラ $C_2$ をコンパイルし、最終的には「$C_n$ 自身を $C_n$ でコンパイルしても同じバイナリが再現される」状態へ育て上げます。
>
> なお、ケン・トンプソンがチューリング賞記念講演（1984年 *Reflections on Trusting Trust*）で示した通り、コンパイラのバイナリ自体に「特定のプログラム（例：`login`）やコンパイラ自身をコンパイルするときだけ裏口を埋め込む」細工が潜んでいると、ソースコードを読んでも一切痕跡が見えないという著名なセキュリティ上の教訓も、このセルフホスティング構造から生まれています。

### 4. 限界と補正（Critique & Adaptation）

#### (1) AOT コンパイラの限界：実行時情報の不在

CやRustなどの事前コンパイラ（AOT：Ahead-Of-Time）は、コンパイル時にじっくり時間をかけて高度な最適化を行える反面、**「実際にプログラムが動くときの具体的な入力・分岐頻度・動的な型」を知らない**という構造的な限界を持ちます。

たとえば、オブジェクト指向言語で親クラスの参照経由でメソッドを呼ぶとき、実行時には99%が特定の子クラス `A` であっても、AOTコンパイラは別の子クラス `B` が来る可能性を排除できないため、関数呼び出しをインライン展開（中身を直接埋め込む高速化）できません。また、分岐のどちら側が頻繁に通るかも静的には推測に留まります。

#### (2) JIT コンパイラによる補完と、JIT 自身のトレードオフ

**JITコンパイラ**は、このAOTの限界を正面から補完します。プログラムをまず軽量なインタプリタや簡易コンパイラで動かし、裏側で実行回数や実際の型を計測（プロファイリング）します。そして何度も繰り返し呼ばれる箇所（**ホットスポット**）を見つけた瞬間に、実行時プロファイルをもとに「今は99%が型 `A` だから、`A` 専用にインライン展開した高速な機械語を生成する（もし稀に型 `B` が来たら安全な汎用経路へ退避＝デオプティマイズする）」という **投機的最適化** をメモリ上で行います。

しかし、JITにも明確な弱点があります。

* **ウォームアップ遅延：** 起動直後はインタプリタ実行やコンパイル処理自体が走るため、短命なCLIコマンドなどではAOTより遅くなります。
* **メモリ消費の増大：** 実行時にコンパイラ本体、プロファイル情報、生成した機械語をすべてRAM上へ保持し続ける必要があります。

そのため実務では、AOT側でも「テスト実行で集めたプロファイルを次のコンパイルへ渡す **PGO（Profile-Guided Optimization）**」を取り入れ、逆にJVMやJavaScriptエンジン側でも「起動を速くする多段階コンパイル（Tiered Compilation）」や事前AOT化（GraalVM Native Image等）を取り入れるなど、AOTとJITの利点を組み合わせる補正が進んでいます。

本節の3層構造（フロントエンド・IR・バックエンド）と4つの実行方式の特徴を確認し、次節（2-2節）へ繋ぐ問いを置きます。

> **【確認の問い】**
>
> 1. **（共通中間表現 IR の開発コスト削減効果）**
>     現在、5つのプログラミング言語（C, C++, Rust, Swift, Fortran）と、4種類のCPUアーキテクチャ（x86-64, ARM64, RISC-V, WebAssembly）をサポートしたいとします。
>     * (a) 共通の中間表現（IR）を使わず、言語とCPUを直接結ぶコンパイラを作る場合、合計何本の翻訳器が必要になるでしょうか。
>     * (b) 共通の中間表現（IR）を1つ導入してフロントエンドとバックエンドを分離した場合、合計何本で済むでしょうか。また、ここに新しいCPUを1種類追加するとき、それぞれ何本の新規開発が必要になりますか。
>
> 2. **（AOT コンパイラと JIT コンパイラの使い分け）**
>     次の2つの用途について、AOTコンパイラとJITコンパイラのどちらが適している傾向があるか、理由（ウォームアップ遅延・メモリ消費・実行時プロファイル）とあわせて簡潔に説明してください。
>     * (a) コマンドラインから呼び出され、数ミリ秒で処理を終えて即座に終了する小型のシステムユーティリティ。
>     * (b) 一度起動したら何日も動き続け、実行時にさまざまな型のデータが流れてくる大規模なWebアプリケーションサーバ。
>
> 3. **（次節への伏線：ただの文字の並びをどうやって「単語」に切り出すか）**
>     本節の実験Aでは、ソースコードの文字列 `"y = x + 3 * 2;"` を最初にトークン列 `[ID(y)] [=] [ID(x)] [+] [NUM(3)] [*] [NUM(2)] [;]` へ切り分けました。では、`if`（予約語）と `ifdef`（識別子）、あるいは `=` と `==` のように先頭が重なる記号を、1文字ずつ左から読みながら迷わず $O(n)$ で高速に切り出すには、どのような数学モデルとアルゴリズムを使えばよいでしょうか。
