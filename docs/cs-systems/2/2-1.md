### 前節（1-6）の確認問題の解答

前節の最後に提示した3つの問いの解答を確認します。これで[第1部](../index.md#part-1)（機械語・ABI・バイナリとリンク）が完結し、本節からは高級言語を機械語へ翻訳・最適化する[第2部](../index.md#part-2)（コンパイラと言語処理系）へ進みます。

1. **ULEB128 の復号と SLEB128 による負数の符号化：**

    * **(a) ULEB128 `0xE5 0x03` の復号：**

        * **1バイト目 `0xE5`**（2進数 `1110_0101`）：MSB（継続ビット）が `1`（次バイトあり）、下位7ビットは `110_0101`（$0\text{x}65 = 101$）です。
        * **2バイト目 `0x03`**（2進数 `0000_0011`）：MSB が `0`（終端）、下位7ビットは `000_0011`（$0\text{x}03 = 3$）です。
        * リトルエンディアン順に $128$ 進数として結合すると、$101 + 3 \times 128 = 101 + 384 = \mathbf{485}$ となります。

    * **(b) SLEB128 による `-10` の1バイト符号化：**
        1バイト SLEB128 が表せる範囲は7ビット2の補数の $-64 \sim +63$ であり、$-10$ は1バイトに収まります。7ビット2の補数で $-10$ は $128 - 10 = 118 = 64 + 32 + 16 + 4 + 2$ より `111_0110` です。最終バイトのため MSB（ビット7）に `0` を付けると、2進数 **`0111_0110`**、16進数 **`0x76`** になります。
        検算として最終バイトの**ビット6（`0x40`）が `1`** であるため上位ビットがすべて `1` で符号拡張され、$-64 + 32 + 16 + 4 + 2 = -10$ へ正しく復元されます。

2. **ソフトウェア・ブレークポイントの再開制御とウォッチポイントの性能境界：**

    * **(a) `%rip` を `1` 減らし忘れた場合の挙動：**
        `0xCC`（1バイト）実行時点で `%rip` は `0x112b` へ進んでいます。`0x112a` の元のバイト `0x48` を復元しただけで `%rip -= 1` を忘れると、CPU は **`0x112b`** から **`89 e5 ...`** のバイト列を実行してしまいます。64ビット演算を指定する REX.W プレフィックス `0x48` が欠落したため 32ビット命令 `movl %esp, %ebp` として誤解釈され、`%rbp` の上位32ビットがゼロクリアされてスタックフレームが破壊されます（一般にも命令途中のバイト列を誤解釈して `SIGILL` や `SIGSEGV` でクラッシュします）。

    * **(b) マルチスレッドでの取り逃しとアウトオブライン実行：**
        スレッドAを1命令だけ進めるために `.text` 上の `0xCC` を一時的に元の命令へ戻している短い隙間に、別コアで走るスレッドBが同じ番地を通過すると、ブレークポイントに気づかず素通りしてしまいます。これを防ぐため、現代のデバッガは `.text` 上の `0xCC` を消さずに残したまま、元の1命令だけを別の退避領域へコピーしてスレッドAにシングルステップ実行させる**アウトオブライン実行（Out-of-line Single Stepping）**を用います。

    * **(c) 5個目のウォッチポイントで極端に遅くなる理由：**
        x86-64 CPU がハードウェアとして備えるデバッグアドレスレジスタは **`DR0`〜`DR3` の4個**に限られます。4個までは CPU ハードウェアが通常速度のまま監視できますが、5個目を追加するとハードウェア枠を超え、デバッガが**ソフトウェア・ウォッチポイント**（1命令ごとにシングルステップ停止してメモリ値を検査する方式）へフォールバックするため、数百倍〜数千倍の速度低下が起きます。

3. **インラインアセンブラの契約違反とコンパイラ最適化事故（本節への接続）：**

    * **(a) `calc(5, 5)` で `%1 = %2 = %0 = %edi` が割り当てられた場合の動作と修正：**
        初期値 `%edi = 5` から3命令を順に追うと、① `movl %edi, %edi`（`%edi = 5`）、② `shll $1, %edi`（`%edi = 10`：入力 `%2` である `b` も同時に `10` へ上書きされる）、③ `addl %edi, %edi`（`%edi = 10 + 10 =` **`20`**）となり、正しい `15` ではなく **`20`** が返ります。修正するには出力制約に早期破壊修飾子 `&` を付けて **`"=&r" (out)`** とし、出力 `%0` にどの入力とも異なる物理レジスタを割り当てさせます。

    * **(b) `volatile` や `"memory"` を省いたときの最適化事故：**
        コンパイラは `asm` 文字列の中身を解釈せず、入出力制約と破壊リストだけを信じて最適化します。**`volatile`** を省くと、`rdtsc` の戻り値が使われない場合に命令自体が丸ごと削除されたり、ループ外へ移動・共通部分式統合されたりして正しい時間計測が壊れます。また破壊リストの **`"memory"`** を省くと、コンパイラが `asm` ブロックの前後にまたがって通常のメモリ読み書きを並べ替えたり、ロック獲得前にレジスタへキャッシュした古いメモリ値を使い回したりして並行制御が破綻します。

## 2-1. コンパイラの全体構造・中間表現（IR）と実行方式（VM・JIT）

### 1. 動機（Why）：なぜソースコードからいきなり機械語へ変換せず、多段階のフェーズと「中間表現」を挟むのか

[第0部](../index.md#part-0)と[第1部](../index.md#part-1)では、CPUが実行する機械語・レジスタ・スタックフレーム・ELFバイナリの仕組みを見てきました。ここからは視点を反転させ、**「人間が書くC言語などの高級言語を、どうやって[第1部](../index.md#part-1)で見たような機械語命令列へ自動翻訳しているのか」**という言語処理系（コンパイラ）の内部へ入ります。

初めてコンパイラを想像すると、「C言語のテキストを1行ずつ読んで、対応するx86-64命令をそのまま書き出せばよいのではないか」と思えるかもしれません。しかし、現実のプログラミング言語とCPUのあいだには、単純な1対1変換を阻む3つの大きな隔たりがあります。

1. **構造の複雑さ：** `y = a + b * (c - d);` のような入れ子の数式や、何重にもネストした `if`・`while`・関数定義・型チェックを、単なる文字列の走査だけで一度に正しく処理しようとするとプログラムが破綻します。
2. **言語とCPUの組み合わせ爆発：** 世界には C、C++、Rust、Go、Fortran のように多様なプログラミング言語があり、一方でターゲットとなるCPUも x86-64、ARM64、RISC-V など複数存在します。$M$ 個の言語から $N$ 種類のCPUへ直接翻訳器を書くと、**$M \times N$ 個の独立したコンパイラ**（さらにそれぞれに最適化器）を開発・保守しなければなりません。
3. **実行方法の多様さ：** すべての言語がC言語のように事前コンパイルされるわけではありません。Pythonのように1行ずつ解釈するものや、JavaやJavaScriptのように仮想機械や実行時コンパイルを使うものなど、「いつ翻訳するか」によってトレードオフが変わります。

本節では、コンパイラを「フロントエンド」「ミドルエンド（中間表現：IR）」「バックエンド」へ分割するアーキテクチャの全体像を掴み、さらに4つの代表的なプログラム実行方式を比較します。

各段階で何が行われているかを順に見てみます。

1. **字句解析（Lexical Analysis）：** 空白を取り除き、文字の並びを最小の意味単位である **トークン** の列（`ID(y)`, `=`, `ID(x)`, `+`, `NUM(3)`, `*`, `NUM(2)`, `;`）へ切り出します。
2. **構文解析（Syntax Analysis）：** 文法規則に従い、「`+` より `*` の方が結合が強い」ことを反映した木構造（**抽象構文木：AST**）を組み立てます。
3. **意味解析（Semantic Analysis）：** 変数 `x` や `y` が事前に宣言されているか、型が矛盾していないか（たとえば `int` と構造体を足そうとしていないか）を検査します。
4. **中間表現（IR）生成：** 木構造を、特定のCPUに依存しない単純な1ステップずつの命令列（例：`t1 = 3 * 2; t2 = x + t1; y = t2;`）へ平坦化します。
5. **最適化（Optimization）：** `3 * 2` は定数同士なのでコンパイル時に `6` へ計算します（**定数畳み込み**：`t1 = 6; t2 = x + t1; y = t2;`）。次に、`t1 = 6` を参照先へ展開して `t2 = x + 6; y = t2;` とし、さらに `t2` の代入も畳んで不要な一時変数 `t1, t2` を消去し（**コピー伝播**）、`y = x + 6;` へ簡約します（なお、`a + 0` を `a` に変えるような**代数簡約**もこの段階で行われます）。
6. **コード生成・レジスタ割当（Code Generation）：** ターゲットCPU（ここではx86-64）の具体的なレジスタへ変数を割り当てます。[1-2節](../1/1-2.md)で見たアドレス計算命令の流用により `leal 6(%rdi), %eax` の1命令で出力が完了します。ここで64ビット表記の `%rdi` と32ビット表記の `%eax` が混在しているのは、x86-64のアドレス計算構文 `(...)` がベースレジスタに64ビット幅を要求する一方、命令の接尾辞 `l` と出力先 `%eax` によって下位32ビット（`int` 幅）の加算結果のみを取り出し、上位32ビットをゼロ拡張しているためです。

### 3. 構造・アルゴリズム・実装（What）

#### (1) フロントエンド・ミドルエンド（中間表現 IR）・バックエンドの3層分離

実験Aの6ステップは、図2-1-1に示した通り大きく **フロントエンド（Frontend）**、**ミドルエンド／中間表現（IR）**、**バックエンド（Backend）** の3つに分離されます。

* **フロントエンド（ソース言語に依存・CPUに非依存）：** 字句解析・構文解析・意味解析・IR生成を担当します。C言語やRustといったソース言語の文法と型ルールだけを知っていればよく、最終的なCPUがx86-64かRISC-Vかを知る必要はありません。
* **中間表現（IR：Intermediate Representation）とミドルエンド最適化（両方に非依存）：** どの言語でも表現でき、どのCPUへも変換しやすい共通の抽象命令形式です。定数畳み込みや不要コード削除、ループ最適化といった**言語にもCPUにも依存しない最適化**を、このIR上で1回だけ実装します。
* **バックエンド（CPUに依存・ソース言語に非依存）：** IRを入力とし、IRの抽象演算をターゲットCPUの具体的な機械語命令へ対応づける**命令選択（Instruction Selection）**、レジスタ割当、命令スケジューリング（[0-6節](../0/0-6.md)のロード・ユースハザード回避など）を行ってアセンブリや機械語を出力します。

この3層分離がもたらす設計上の効果は明確です（図2-1-2）。

$M$ 個の言語と $N$ 種類のCPUをサポートするとき、直接変換では $M \times N$ 本の翻訳器が必要ですが、共通のIRを1つ挟むことで必要な実装数は **$M + N$ 本** へ削減されます。現代の代表的なコンパイラ基盤である **LLVM**（Clang・Rust・Swift などが共有する LLVM IR）や **GCC**（高水準な木寄りIRの **GIMPLE** と、レジスタ寄りの低水準IRである **RTL**）は、この構造によって新しい言語と新しいCPUの双方へ迅速に対応しています。もっとも現実には、構造体の値渡しやポインタ幅などターゲット固有のABI規約をフロントエンド側で事前に降格（lowering）せざるを得ない側面もあります（詳細は下記コラム）。

なお、IRの代表的な形式としては、実験Aの `t1 = 3 * 2` のように「1命令あたり最大3つのアドレス（結果1つ＋入力2つ）しか書かない」**3番地コード（Three-Address Code）** や、**SSA形式（Static Single Assignment：静的単一代入形式）** が広く用いられます。SSA形式とは、`x = 1; x = x + 2;` のような再代入を `x1 = 1; x2 = x1 + 2;` のように**代入のたびに別の番号を振る形式**で、すべての値の出どころがプログラム中で1箇所に特定されるため、変数の値の流れを追跡する**データフロー解析**（[2-7節](2-7.md)）や最適化が大幅に簡潔になります（分岐の合流点を扱う $\phi$ 関数は[2-7節](2-7.md)コラムで回収します）。

> **【コラム：共通IRは本当に完全なターゲット非依存か？（データレイアウトと ABI 降格）】**
>
> 図2-1-2の「$M + N$ 構造」は明快な理想ですが、実務のC/C++コンパイラ（Clang + LLVM 等）では、フロントエンドが完全にターゲットCPUを知らずに済むわけではありません。代表的な壁が **データレイアウトと ABI 降格（ABI Lowering）** です。
>
> * **型サイズとアラインメント（`TargetDataLayout`）：** C言語の `sizeof(long)` や構造体パディング（[0-2節](../0/0-2.md)）、プリプロセッサの `#ifdef __x86_64__` は、フロントエンドの構文・意味解析の段階でターゲットCPUとOSの仕様を知っていなければ確定できません。そのため LLVM IR の先頭には、エンディアンや各型のアラインメントを記した `target datalayout` 文字列が埋め込まれます。
> * **構造体値渡しの ABI 規約：** [1-3節](../1/1-3.md)の System V AMD64 ABI では、16バイト以下の構造体を値渡しするとき、メンバ型に応じて2本の汎用レジスタや **XMMレジスタ**（浮動小数点演算や並列演算に使う専用レジスタ）へ分割して渡します。一方、Windows x64 や ARM64 では規則が大きく異なります。LLVM IR はこれらのABI詳細を自動では抽象化しきれないため、Clang や `rustc` などのフロントエンド側が「x86-64向けなら `{i64, i64}` の2整数へ分解して渡す」といったターゲット依存の降格処理を自ら実装しています。

さらに近年は、単一の低水準IR（LLVM IR）だけでは機械学習のテンソル演算や高水準なループ並列化といったドメイン固有の情報を途中で失ってしまうという課題に対し、高水準のドメイン専用IRから低水準のLLVM IRまで**複数階層のIR（Dialect）を段階的に降格していく基盤（MLIR：Multi-Level IR）**へと設計が発展しています。

| **事前コンパイラ（AOT）** | 実行前に全体をターゲットCPUの機械語へ翻訳（C, C++, Rust, Go） | 実行速度が速く、実行時のメモリ消費も小さい | CPU・OSごとに別バイナリが必要。ビルド待ち時間がある |
| **インタプリタ** | ソースコード（またはAST）を1文ずつ解釈しながら直接実行（シェルスクリプト等） | ビルド不要で即座に試せる。対話実行が容易 | 同じループを回るたびに毎回解釈コストがかかる |
| **仮想機械（VM）＋バイトコード** | ソースを架空の単純CPU向け命令（**バイトコード**）へ事前変換し、各環境上のVMが解釈実行（CPython, 初期Java） | 配布するバイトコードがCPUに依存せず高い移植性を持つ | VMの解釈ループのオーバーヘッドがありネイティブより遅い |
| **JIT コンパイラ**（Just-In-Time） | VMやインタプリタで動かしつつ、実行頻度の高い箇所だけを実行時にネイティブ機械語へ翻訳（JVM HotSpot, V8 JavaScript, PyPy） | 移植性と高速な実行を両立でき、実行時情報も最適化に使える | 起動直後のウォームアップ遅延（インタプリタ実行や動的コンパイルの待ち時間、4-(2)参照）、コンパイラ常駐によるメモリ増 |

> **【コラム：コンパイラを自分自身の言語で書く「ブートストラップ（セルフホスティング）」と Trusting Trust】**
>
> GCC（Cコンパイラ）は C/C++ で書かれており、Rust のコンパイラ `rustc` は Rust 自身で書かれています。このように「言語 $L$ のコンパイラを、言語 $L$ 自身で記述してコンパイルできる状態」を **セルフホスティング（Self-hosting）** と呼びます。
>
> すると「最初の1個目のコンパイラはどうやってコンパイルしたのか？（鶏と卵問題）」という疑問が湧きます。この問題を解決する手順が **ブートストラップ（Bootstrap：自分の靴紐を引っ張って持ち上げる比喩）** です。コンパイラの関係を図示する **T-diagram（T字図）** では、「ソース言語 $S$ をターゲット言語 $T$ へ変換し、実装言語 $I$ で書かれたコンパイラ」を $(S \to T)_I$ のように表します。ターゲットCPUの機械語を $M$ として、手順をこの記法で追ってみます。
>
> 1. まず、すでに動く別の言語（アセンブリや既存のCコンパイラ）を使って、言語 $L$ のごく小さなサブセット $L_0$ だけを翻訳できる最小コンパイラ $(L_0 \to M)_{\text{C}}$ を書き、既存のCコンパイラで実行可能なバイナリ $C_0 = (L_0 \to M)_M$ を作ります。別CPU向けの実行ファイルを生成する**クロスコンパイル**でも、ホスト機上で動くコンパイラを使ってターゲット機向けのバイナリを段階的に生成します。
> 2. 次に、言語 $L$ の最小サブセット $L_0$ を使ってより高機能なコンパイラ $(L \to M)_{L_0}$ を書き、先ほどの $C_0 = (L_0 \to M)_M$ でコンパイルして実行可能版 $C_1 = (L \to M)_M$ を得ます。
> 3. 実務の GCC や `rustc` のビルドでは、正当性を検証する **3段階ブートストラップ（3-stage bootstrap）** が行われます。既存のコンパイラで新コンパイラのソース $(L \to M)_L$ をビルドして **Stage 1** のバイナリ $(L \to M)_M^{(1)}$ を作り、Stage 1 で同じソース $(L \to M)_L$ をビルドして **Stage 2** の $(L \to M)_M^{(2)}$ を作り、さらに Stage 2 で同じソースをビルドして **Stage 3** の $(L \to M)_M^{(3)}$ を作ります。ここで **Stage 2 と Stage 3 のバイナリがバイト単位で完全に一致すれば**、新しいコンパイラ自身のバグや既存コンパイラの癖が混入していない（不動点に達した）と確認できます。
>
> なお、ケン・トンプソンがチューリング賞記念講演（1984年 *Reflections on Trusting Trust*）で示した通り、コンパイラのバイナリ自体に「特定のプログラム（例：`login`）やコンパイラ自身をコンパイルするときだけ裏口を埋め込む」細工が潜んでいると、ソースコードを読んでも痕跡が見えないというセキュリティ上の教訓も、このセルフホスティング構造から生まれています。
>
> この問題に対する現実的な防御策として知られているのが、デイビッド・ウィーラーが提案した **Diverse Double-Compiling（DDC）** です。怪しいコンパイラ $A$ のソースコードを、系統の異なる信頼できる別コンパイラ $B$（たとえば GCC に対して Clang や TinyCC）でコンパイルし、その結果得られたバイナリでさらに $A$ 自身をコンパイルして出力バイナリを比較することで、バイナリ潜伏型の裏口を検出できます。さらに根本的な取り組みとして、人間が全バイトを目視検証できる数百バイトの最小16進アセンブラ（`hex0`）から段階的にCコンパイラ（GCC）までをソースのみから再構築する **bootstrappable（Bootstrappable Builds）** プロジェクトも進められています。

### 4. 限界と補正（Critique & Adaptation）

#### (1) AOT コンパイラの限界：実行時情報の不在

CやRustなどの事前コンパイラ（AOT：Ahead-Of-Time）は、コンパイル時に時間をかけて高度な最適化を行える反面、**「実際にプログラムが動くときの具体的な入力・分岐頻度・動的な型」を知らない**という構造的な限界を持ちます。

たとえば、オブジェクト指向言語で親クラスの参照経由でメソッドを呼ぶとき、実行時には99%が特定の子クラス `A` であっても、AOTコンパイラは別の子クラス `B` が来る可能性を排除できないため、関数呼び出しをインライン展開（中身を直接埋め込む高速化）できません。また、分岐のどちら側が頻繁に通るかも静的には推測に留まります。

#### (2) JIT コンパイラによる補完と、JIT 自身のトレードオフ

**JITコンパイラ**は、このAOTの限界を補完します。プログラムをまず軽量なインタプリタや簡易コンパイラで動かし、裏側で実行回数や実際の型を計測（プロファイリング）します。そして何度も繰り返し呼ばれる箇所（**ホットスポット**）を見つけると、実行時プロファイルをもとに「よく来るパターン専用の近道を作り、想定外が来たときだけ元の安全な手順へ戻る」という **投機的最適化** をメモリ上で行います。具体的には、「今は99%が型 `A` だから、`A` 専用にインライン展開した高速な機械語を生成し、稀に型 `B` が来たら安全な汎用経路へ退避（**デオプティマイズ**）する」という仕組みです（図2-1-3下段）。

しかし、JITにも明確な弱点があります。

* **ウォームアップ遅延：** 起動直後はインタプリタ実行やコンパイル処理自体が走るため、短命なCLIコマンドなどではAOTより遅くなります。
* **メモリ消費の増大：** 実行時にコンパイラ本体、プロファイル情報、生成した機械語をすべてRAM上へ保持し続ける必要があります。

そのため実務では、AOT側でも「テスト実行で集めたプロファイルを次のコンパイルへ渡す **PGO（Profile-Guided Optimization）**」を取り入れ、逆にJVMやJavaScriptエンジン側でも「最初は軽量なインタプリタや簡易JITですばやく起動し、実行回数が増えた関数だけを段階的に高度な最適化JITへ引き上げる **多段階コンパイル（Tiered Compilation）**」や事前AOT化（GraalVM Native Image等）を取り入れるなど、AOTとJITの利点を組み合わせる補正が進んでいます。

本節の3層構造（フロントエンド・ミドルエンド・バックエンド）、共通IRの限界、AOT/JITのトレードオフ、および6フェーズの変換を確認します。

> **【確認の問い】**
>
> 1. **（共通中間表現 IR のコスト削減効果とターゲット非依存性の限界）**
>     現在、5つのプログラミング言語（C, C++, Rust, Swift, Fortran）と、4種類のターゲット環境（x86-64, ARM64, RISC-V, WebAssembly［ブラウザ等で動く仮想ISA］）をサポートしたいとします。

>     * (a) 共通の中間表現（IR）を使わない直接変換（$M \times N$）と、共通 IR を1つ導入した3層分離（$M + N$）では、合計何本の翻訳器が必要になるでしょうか。また、新しい CPU を1種類追加するとき、それぞれ何本の新規開発が必要になりますか。
>     * (b) 共通 IR を導入しても、現実の C/C++ フロントエンドがターゲット CPU や OS の仕様から完全には独立できない理由を、本節コラムの内容（`sizeof(long)` や構造体値渡しの ABI 降格）に沿って簡潔に説明してください。
>
> 2. **（サーバレス［FaaS］環境における AOT と JIT の課題と補正）**

>
>     * (a) この環境で、純粋な AOT コンパイラのみを使う場合と、純粋な JIT コンパイラのみを使う場合では、それぞれどのような弱点・課題が問題になりやすいでしょうか。
>     * (b) それらの弱点を補うために実務で導入されている補正手法（AOT 側の PGO、JIT 側の多段階コンパイルや事前 AOT 化）がそれぞれどのように働くかを簡潔に説明してください。
>
> 3. **（6フェーズの変換トレースとエラー検出段階の判定）**
>     変数 `a` と `z` が `int` 型で宣言済み（x86-64 では引数 `a` が `%rdi` の下位32ビット、返り値 `z` が `%eax` に置かれる前提）であるとし、文 `int z = (a + 0) + 2 * 5;` を本節のコンパイルパイプラインへ通します。

>     * (a) 実験A（図2-1-1）にならい、①字句解析（トークン列）→ ②構文解析（AST の構造）→ ③意味解析 → ④IR 生成（3番地コード）→ ⑤IR 最適化（定数畳み込み・代数簡約・コピー伝播）→ ⑥x86-64 コード生成の6段階での変換結果を順に示してください。
