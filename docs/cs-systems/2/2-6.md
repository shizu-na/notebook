### 前節（2-5）の確認問題の解答

前節の最後に提示した3つの問いの解答を確認します。問3がそのまま本節（コード生成）の導入になります。

1. **静的スコープとスタック型記号表のトレース：**
    大域スコープ（`v = 1`：宣言A）を底として、ブロック `{` に入るたびに新しいハッシュ表が `push` され、`}` を抜けるたびに `pop` されます。
    * **① `int a = v;`：** `main` スコープに `v` がないため底の大域スコープから**宣言A（値 `1`）**が見つかります（`a = 1`）。
    * **② `a += v;`：** 宣言B（`v = 2`）のスコープの上へさらに宣言C（`v = 3`）のスコープが積まれているため、最上段の**宣言C（値 `3`）**が見つかります（`a = 1 + 3 = 4`）。
    * **③ `a += v;`：** 内側ブロックを抜けて宣言Cのスコープが `pop` されたため、現在の最上段である**宣言B（値 `2`）**が見つかります（`a = 4 + 2 = 6`）。最終的な返り値は **`6`** です。

2. **C言語の暗黙の型変換の挙動（`unsigned int len = 0; int idx = -1;`）：**

    * **(a) `idx < len` の評価結果：**
        通常の算術型変換により、同じ32ビット幅の `int` と `unsigned int` の演算では符号あり側の `idx` が `unsigned int` へ変換されます。`-1` のビット列 `0xFFFFFFFF` が符号なし整数 **`4,294,967,295`** と解釈されるため、`4,294,967,295 < 0` は**偽（`0`）**になります。

    * **(b) 実務上の対策と現代言語の設計方針：**
        C言語ではコンパイラの警告オプション（`-Wsign-compare` や `-Wsign-conversion`）を有効にして混在を早期発見するのが基本の補正です。一方、GoやRustなどの現代のシステム言語では、異なる数値型同士の暗黙の型変換自体を禁止し、明示的なキャストを必須にする設計へ改めています。

3. **型とオフセットが確定したASTから機械語を書き出す方法（本節への接続）：**
    注釈付きASTを**後順序（postorder：左の子 → 右の子 → 親）**で再帰的に走査し、部分式の計算結果をCPUのスタックへ積みながら演算を進める**スタック機械方式**を使うと、任意の深さに入れ子になった式や制御文からx86-64アセンブリを系統的に出力できます。本節ではその具体的な生成規則を組み立てます。

## 2-6. コード生成：スタック機械・制御文・短絡評価と関数呼び出し

### 1. 動機（Why）：なぜASTからいきなりレジスタを駆使せず、まず「スタック機械」でコード生成を組み立てるのか

前節（[2-5節](2-5.md)）までで、ソースコードは字句解析・構文解析・意味解析を経て、すべてのノードに型情報とメモリ配置（オフセット）が紐づいた**注釈付きAST**になりました。いよいよここから、x86-64のアセンブリ命令列を出力する **コード生成（Code Generation）** のフェーズに入ります。

ここで最初にぶつかる壁が、**「入れ子の式の途中結果をどこに一時保存するか」**という問題です。たとえば `(a + b) * (c - d) + (e * f)` のような式を計算するとき、`a + b` の答えが出たあと、`c - d` を計算している間ずっと `a + b` の値をどこかに覚えておかなければなりません。もし式の入れ子が20重になれば、x86-64の汎用レジスタ16本だけでは足りなくなってしまいます。

そこで、コンパイラのコード生成を理解する第一歩として広く用いられるのが、**「部分式の計算結果はすべてスタックへ積み、演算するときだけスタック頂上から2個取り出して計算し、結果を再びスタックへ積む」**という **スタック機械（Stack Machine）方式** です。

スタック機械方式には、「式の深さがいくら深くなってもレジスタ不足の心配が一切なく、ASTの各ノードに対する生成規則が数行の再帰関数で完結する」という高い見通しの良さがあります。本節では、この素直なコード生成器を使って、式・左辺値と代入・ポインタ演算・制御文・短絡評価・関数呼び出しのすべてをx86-64アセンブリへ翻訳する手順を確立します（なお、スタック機械の速度面の限界を解決する最適化とレジスタ割当は、続く[2-7](2-7.md)・[2-8節](2-8.md)で扱います）。

```asm
popq  %rdi          # 先に取り出すのが右辺 (d = 4)
popq  %rax          # 後に取り出すのが左辺 (c = 10)
subq  %rdi, %rax    # AT&T記法：%rax = %rax - %rdi = 10 - 4 = 6
pushq %rax          # 結果 6 をスタック頂上へ戻す
```

### 3. 構造・アルゴリズム・実装（What）

ここからは、C言語の主要な構文要素をx86-64アセンブリへ翻訳する規則を、**①左辺値と右辺値・代入**、**②ポインタ演算と配列**、**③制御文（`if`/`while`）**、**④論理演算子の短絡評価**、**⑤関数呼び出し（ABI準拠）** の5つに分けて整理します。

#### (1) 左辺値（アドレス）と右辺値（値）の区別・代入文

C言語の代入文 `x = y + 1;` を見ると、左側の `x` と右側の `y` はどちらも同じ変数ノードですが、コード生成で欲しいものが異なります。

* **右辺値（R-value）：** 変数 `y` の**中身（箱の中に入っている数値）**が欲しい。
* **左辺値（L-value）：** 書き込み先である変数 `x` の**メモリアドレス（値を入れる箱の場所そのもの）**が欲しい。

この違いを統一的に処理するため、コード生成器には式を評価する関数 **`gen_expr(node)`（値をスタックへ積む）** に加えて、アドレスを計算する補助関数 **`gen_lval(node)`（アドレスをスタックへ積む）** の2つを用意します（図2-6-2）。

図2-6-2の通り、`gen_lval` を1つ独立させるだけで、単なる変数への代入 `x = 5` だけでなく、ポインタ経由の代入 `*p = 5` やアドレス演算子 `&x`（`gen_lval(x)` を呼ぶだけ）がすべて同じ枠組みで統一的に処理できます。ここで `gen_lval(*p)` が `gen_expr(p)` をそのまま呼ぶ理由は具体番地で考えると明快です。たとえばポインタ変数 `p` 自身が番地 `0x1000` に置かれ、その中身として `x` の番地 `0x2000` が入っているとき、`*p = 5` で書き込みたい先は `0x1000` ではなく `p` の中身である `0x2000` だからです。なお、C言語では `a = b = 5;` のように代入自体が「代入された値」を持つ式であるため、メモリへ書き込んだ後に `pushq %rdi` で値をスタックへ残して不変条件を守ります。

#### (2) ポインタ演算のスケーリングと配列アクセス（Array Decay）

[2-5節](2-5.md)の型検査で確認した通り、`int *p;` に対するポインタ加算 `p + i` は単なるアドレスへの `+ i` ではなく、`p + i * sizeof(int)`（4バイト単位のスケーリング）を意味します。コード生成器はASTに注釈された型情報を見て、左辺が `Ptr(T)` なら右辺の整数へ `imulq $sizeof(T), %rdi`（または2のべき乗サイズなら左シフト `shlq $2, %rdi`）を挟んでから加算します。

配列の添字アクセス `a[i]` はC言語の仕様上 `*(a + i)` と等価であるため、構文解析や意味解析の段階で `Deref(PtrAdd(a, i))` というASTへ展開しておけば、上記の `gen_lval` とポインタ加算の規則で統一的に処理できます。ただし1点だけ重要な例外があります。`int a[10];` のような**配列型変数を右辺値として `gen_expr(a)` で評価するとき**です。通常の変数と同じように `gen_lval(a)` の直後に `movq (%rax), %rax` でロードしてしまうと、配列先頭の値（`a[0]` など先頭8バイトの中身）を読んでしまい、アドレスではなくなってしまいます。そのため、C言語の **配列からポインタへの自動変換（Array Decay）** に従い、ノードの型が `Array(T, n)` のときはロード命令を省略して先頭要素のアドレス（`gen_lval(a)` の結果そのまま）をスタックへ残す例外処理を入れます。

#### (3) 比較演算子・制御文（`if-else`・`while`）と一意ラベルの生成

制御文の条件式に現れる比較演算子（`<`, `<=`, `==`, `!=` など）は、[1-2節](../1/1-2.md)で見た条件フラグと `setcc` 命令を使って、真偽値 `1`（真）または `0`（偽）をスタックへ積むコードを生成します。たとえば `a < b` のコード生成は次のようになります。

```asm
# a < b の比較演算（スタックへ 0 または 1 を積む）
    <gen_expr(a)>
    <gen_expr(b)>
    popq   %rdi             # 右辺 b
    popq   %rax             # 左辺 a
    cmpq   %rdi, %rax       # a - b を計算してフラグ更新
    setl   %al              # 符号ありで a < b なら %al = 1、そうでなければ 0
    movzbq %al, %rax        # 上位56ビットをゼロ拡張して64ビット値 0/1 にする
    pushq  %rax
```

`if` や `while` のような制御文は、こうして得られた条件式の真偽値を受け取り、コンパイラ内部の連番カウンタ（`label_seq++`）で他の文と重複しない一意なローカルラベル（`.L_else_1`, `.L_end_1` 等。[1-4節](../1/1-4.md)で見た通り `.L` 始まりはELFの記号表に載らず軽量です）を自動発行してアセンブリを出力します。

```asm
# if (cond) then_stmt else else_stmt
    <gen_expr(cond)>       # 条件式を評価してスタックへ積む
    popq  %rax
    cmpq  $0, %rax         # 0 (偽) か判定
    je    .L_else_1        # 偽なら else 節へジャンプ
    <gen_stmt(then_stmt)>  # 真のときの本体
    jmp   .L_end_1         # else 節を飛び越す
.L_else_1:
    <gen_stmt(else_stmt)>  # 偽のときの本体
.L_end_1:
```

`while (cond) body` も同様に、先頭に `.L_begin_2:`、末尾に `.L_end_2:` を置き、条件式が `0` なら `.L_end_2` へ抜け、本体実行後に `jmp .L_begin_2` で先頭へ戻ります。なお、ループ内で `break` や `continue` が出てきたときは、「現在いる最も内側のループの終了ラベル／開始ラベル」をスタックで管理しておき、そこへの `jmp` を出力します。

#### (4) 論理演算子 `&&` / `||` の短絡評価（Short-Circuit Evaluation）

C言語の論理AND `E1 && E2` や論理OR `E1 || E2` は、ビット演算 `&` / `|` のように左右を両方評価してから演算するのではなく、**必ず左辺 `E1` を先に評価し、その結果だけで全体の真偽が確定したら右辺 `E2` を一切評価しない（短絡評価）**という厳格な仕様があります。

たとえば `if (p != NULL && p->val > 0)` のようなコードは、`p == NULL` のときに右辺 `p->val` を評価せずに飛び越してくれるからこそ、ヌルポインタ参照でクラッシュせずに安全に動きます。したがって、`&&` や `||` は通常の二項演算ではなく、**`if` 文と同じ分岐ラベル構造**としてコード生成します（図2-6-3）。

#### (5) System V AMD64 ABI に準拠した関数呼び出しのコード生成

関数呼び出し `foo(arg1, arg2, ..., argk)` のコード生成は、[1-3節](../1/1-3.md)で確認した System V AMD64 ABI のルールをそのまま実装します。

1. **実引数の評価と一時退避：** 第7引数以降がある場合は、[1-3節](../1/1-3.md)のABIに従い、先に第 $k$ 引数から第7引数までを右から左の順で評価してスタックへ積んでおきます。続いて第1〜第6引数 `arg1`〜`arg6` を順に `gen_expr` で評価し、スタックへ積んでいきます。直接 `%rdi` へ入れずに一度スタックへ積むのは、`arg2` の評価中に別の関数呼び出しが含まれていた場合に `%rdi` が上書きされるのを防ぐためです。
2. **第1〜第6引数のレジスタ設定（逆順ポップ）：** `arg1`〜`arg6` の順に積んでいるため、スタック頂上には最後の実引数（最大で第6引数）が乗っています。したがって、**逆順（`%r9, %r8, %rcx, %rdx, %rsi, %rdi` の順）に `popq` で取り出して**レジスタへ設定します（第7引数以降は、ちょうどスタック頂上側に第7引数が来る形でそのまま残ります）。
3. **16バイト境界の調整と `%al` 設定：** `call` 実行直前の `%rsp` が16の倍数になるよう調整し（後述 4-(2)）、可変長引数関数（`printf` 等）に備えて `movb $0, %al`（浮動小数点引数の個数）を設定します。
4. **呼び出しと後片付け・結果のプッシュ：** `call foo` を実行し、第7引数以降のスタック渡し分（および16バイト境界の調整分）があれば `addq` で片付けたうえで、返り値レジスタ `%rax` をスタック頂上へ `pushq %rax` して式の不変条件を満たします。

> **【コラム：なぜC言語では `f(g(), h())` の評価順序が未規定なのか（Unspecified vs 未定義動作 UB）】**
>
> `E1 && E2` のような短絡演算子では「左から右」という評価順序が厳格に定められていますが、C言語の関数呼び出し `f(g(), h())` や二項演算 `g() + h()` では、**「`g()` と `h()` のどちらを先に呼び出すか」は規格上未規定（Unspecified Behavior）** になっています。
>
> ここで C11 以降の規格が定義する **順序関係（Sequenced-before）** に沿って、**未規定動作（Unspecified）**と**未定義動作（Undefined Behavior：UB）**の違いを正確に区別しておく必要があります。
>
> * **未規定動作（例：`f(g(), h())`）：** `g()` と `h()` のどちらが先に呼ばれるかはコンパイラ次第ですが、必ず「`g()`→`h()`」か「`h()`→`g()`」のどちらかの正当な結果になります。
> * **未定義動作（例：`f(i++, i++)`）：** 2つの引数の間に順序関係がないのに、**同一の変数 `i` に対して複数の書き込み（または書き込みと読み出し）**を行っています。これは規格上 **未定義動作（UB）** であり、どちらかの順で評価されることすら保証されません。
>
> なぜC言語は評価順序を「常に左から右」に固定しなかったのでしょうか。理由は**コンパイラの最適化の自由度**にあります。第1に、[2-8節](2-8.md)のコラムで触れる通り、複雑な部分式を先に評価した方が消費するレジスタ数を減らせることがあります。第2に、ABIの規約上、スタック渡しする引数は右から左へ積んだ方が操作を省ける場合もあります。
>
> 一方、この自由度は実務でバグの原因にもなります。たとえば C++14 以前の `f(new A(), new B())` では、コンパイラが「`new A()` を確保 → `new B()` を確保 → `A` のコンストラクタ実行 → `B` のコンストラクタ実行」のように引数の評価を途中で混ぜて（インターリーブして）実行することが許されていたため、もし `new B()` が例外を投げると確保済みの `A` が解放されずメモリリークが起きました。こうした教訓から **C++17** では、添字 `a[b]` やシフト `a << b` などの評価順序を左→右へ固定し、関数引数同士も順序自体は未規定のまま「ある引数の評価を完了してから次の引数へ移る（インターリーブ禁止）」規則へ強化されています（JavaやGoでは安全性と予測可能性を優先し、左から右の評価順を全面的に規定しています）。

### 4. 限界と補正（Critique & Adaptation）

本節で組み立てたスタック機械方式のコード生成器は、主要なC言語の式・制御文・関数呼び出しから正しいアセンブリを出力できます。しかし、実用コンパイラとして見ると次の2つの課題があります。

#### (1) スタック機械方式の性能上の限界（次節以降の最適化・レジスタ割当の動機）

実験Aで `(a + b) * (c - d)` を計算したときの命令数を数えてみてください。わずか3回の算術演算（`+`, `-`, `*`）を行うためだけに、**`pushq` を7回、`popq` を6回（合計13回のメモリアクセス）** も発行しています。

[0-7節](../0/0-7.md)で確認した通り、レジスタ間の演算は1サイクル未満で終わるのに対し、スタックへの読み書きはL1キャッシュにヒットしても毎回メモリアクセスを伴い、命令数もロード・ストアの依存連鎖も大幅に増えます。これが「純粋なスタック機械は実装が簡潔な反面、生成コードが大幅に遅くなる」理由です。

この限界に対する補正が、続く[2-7節](2-7.md)・[2-8節](2-8.md)の主役である **最適化**（連続する `pushq %rax; popq %rax` の削除などのぞき穴最適化、データフロー解析）と、**レジスタ割当**（変数をスタックではなくCPUの汎用レジスタへ直接配置する技術）です。現代の実用コンパイラ（GCC・LLVM）は、まず仮想レジスタを無限に使える3番地コード（IR）を生成し、最適化を施してから有限の物理レジスタへ割り当てます。

> **【コラム：スタック機械（JVM / WebAssembly）vs レジスタ機械（Lua / Dalvik）】**
>
> ネイティブCPU向けのAOTコンパイラではスタック機械は遅いため使われませんが、[2-1節](2-1.md)で見た**仮想機械（VM）のバイトコード設計**では、JVM・WebAssembly（Wasm）・CPython・CLR（.NET）など現代の主流VMの多くが依然として**スタック機械**を採用しています。一方で、Lua 5 や Android の Dalvik/ART は**レジスタ機械**（仮想レジスタ番号を命令に含める方式）を採用しています。両者には明確なトレードオフがあります。
>
> * **スタック機械の利点（コンパクトな命令長と検証の容易さ）：** `iadd` のようにオペランド指定が不要なため1命令が1バイト程度で済み、ネットワーク配信する WebAssembly や Java バイトコードのサイズを小さく保てます。また、実CPUのレジスタ本数（x86-64の16本 vs ARM64の32本）に一切依存せず、バイトコード検証もスタック深さと型の追跡だけで済みます。JITコンパイラが実行時にネイティブ機械語へ翻訳するとき、スタック上のやり取りはそのままレジスタ割当（[2-8節](2-8.md)）へ変換されるため、最終的な実行速度のハンデも解消されます。
> * **レジスタ機械の利点（インタプリタ実行時のディスパッチ回数削減）：** JITを使わずインタプリタで解釈実行する場合、スタック機械は `push a; push b; add; pop c` の4命令をディスパッチする必要がありますが、レジスタ機械なら `add r3, r1, r2` の1命令で済むため、インタプリタの分岐予測ミス（[0-5節](../0/0-5.md)）と解釈ループのオーバーヘッドを大幅に減らせます。

#### (2) 式文の余剰スタック値の破棄と、16バイト境界の動的／静的整合

スタック機械を実装するときに必ず踏む2つの実務的な細部と補正を押さえておきます。

1. **式文（Expression Statement）でのスタックリーク防止：**
    C言語では `x = 1;` や `printf("hi\n");` のように、式の末尾に `;` を付けただけの「式文」が頻繁に現れます。`gen_expr` の不変条件により、式を評価した直後はスタック頂上に結果の値が1個残っています。もし式文の終わりにそれを片付けないと、`for` ループで100万回 `x = x + 1;` を回しただけでスタックに8MB分のゴミが溜まってスタックオーバーフローを起こします。そのため、すべての式文の末尾には必ず **`addq $8, %rsp`**（または `popq %rax`）を1命令出力して余剰値を破棄します。

2. **式の途中からの関数呼び出しにおける16バイト境界の確保：**
    `1 + foo()` のように、すでに左辺の `1` をスタックへ `pushq` した状態で `foo()` を呼ぶと、その瞬間の `%rsp` が16の倍数から8バイトずれていることがあります。[1-3節](../1/1-3.md)で確認した通り、`%rsp` が16バイト境界でないまま `printf` 等を呼ぶとSSE命令でクラッシュします。

    * **静的補正：** コンパイラ側で現在のスタック深さ（`push`/`pop` の増減回数）をカウントしておき、`call` の直前に奇数回なら `subq $8, %rsp` を挟み、`call` 終了直後に `addq $8, %rsp` で元へ戻します。
    * **動的補正：** 呼び出し直前に `%rsp` の下位4ビットを検査し、8バイトずれている経路だけ `subq $8, %rsp` を実行します。このとき、**`call` から戻った直後に「調整した経路だけ `addq $8, %rsp` で元に戻す」復元処理**を必ず対にします（戻し忘れると `%rsp` が8バイトずれたままになり、直後の `popq` や関数復帰が破損します）。

        ```asm
            movq  %rsp, %rax
            andq  $15, %rax         # %rsp % 16 を確認
            jnz   .L_call_align_1   # 8バイトずれていれば調整経路へ
            movb  $0, %al
            call  foo               # 16バイト整合済み：そのまま呼ぶ
            jmp   .L_call_end_1
        .L_call_align_1:
            subq  $8, %rsp          # 16バイト境界へ調整
            movb  $0, %al
            call  foo
            addq  $8, %rsp          # 調整した経路だけ必ず 8 バイト復元する
        .L_call_end_1:
            pushq %rax              # 返り値をスタックへ積む
        ```
