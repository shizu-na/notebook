### 前節（2-6）の確認問題の解答

前節の最後に提示した3つの問いの解答を確認します。スタック機械方式のコード生成で生じる冗長な命令列やメモリアクセス過多を体系的に削るのが、本節（コード最適化とデータフロー解析）の主題になります。

1. **スタック機械のトレースと左辺値アドレスの区別：**

    * **(a) `10 - (3 + 2)` のスタック推移とポップ順：**
        スタック（底 → 頂上）は `[10]` $\to$ `[10, 3]` $\to$ `[10, 3, 2]` $\to$（`3 + 2` を計算）$\to$ `[10, 5]` $\to$（`10 - 5` を計算）$\to$ **`[5]`** と推移します。最後の引き算では後から積んだ右辺が先に取り出されるため、1回目の `popq %rdi` が **`5`**、2回目の `popq %rax` が **`10`** になります（`subq %rdi, %rax` で $10 - 5 = 5$）。

    * **(b) `gen_lval(*p)` と `gen_lval(p)` が積むアドレス：**
        `gen_lval(p)` は変数 `p` 自身の格納場所である **`0x1000`** をスタックへ積みます。一方、`gen_lval(*p)` は `gen_expr(p)` を呼ぶため、`p` の中身である変数 `x` のアドレス **`0x2000`** をスタックへ積みます。

2. **論理OR `E1 || E2` の短絡評価アセンブリと真偽値正規化：**

    * **(a) `E1 || E2` の短絡評価 x86-64 アセンブリ：**

        ```asm
            <gen_expr(E1)>
            popq  %rax
            cmpq  $0, %rax
            jne   .L_true_1     # E1 が非0（真）なら E2 を評価せず短絡
            <gen_expr(E2)>
            popq  %rax
            cmpq  $0, %rax
            jne   .L_true_1     # E2 が非0（真）なら 1 を積む
            pushq $0            # 両方偽のとき 0 を積む
            jmp   .L_end_1
        .L_true_1:
            pushq $1            # 結果を常に 1 へ正規化
        .L_end_1:
        ```

    * **(b) `E1 = 5` をそのまま積まず `pushq $1` を実行する理由：**
        C 言語の規格では、論理演算子 `||` および `&&` の評価結果は元のオペランド値ではなく、**必ず整数 `1`（真）または `0`（偽）へ正規化される**と定められているためです。たとえば `int r = (5 || 0);` の値は `5` ではなく `1` でなければならず、`E1` の値をそのまま残すと規格違反の誤った計算結果になってしまいます。

3. **関数呼び出しコード生成における2つの実装バグ診断：**

    * **(a) `foo(a, bar(99))` で第1引数 `a` を直接 `%rdi` へ設定した場合のバグ：**
        第2引数 `bar(99)` を呼び出す際、System V AMD64 ABI に従って `bar` の第1引数 `99` が **`%rdi` へ書き込まれます**（さらに `bar` の実行中にも caller-saved である `%rdi` は自由に上書きされます）。その結果、`foo` を呼ぶ直前には `%rdi` にあったはずの `a` が `99`（あるいは別のゴミ値）へ破壊されており、`foo` へ誤った第1引数が渡ってしまいます。

    * **(b) `addq $8, %rsp` 忘れ、および第7引数プッシュ後の `subq $8, %rsp` のバグ：**
        調整経路で `addq $8, %rsp` を出力し忘れると、関数から戻った後も `%rsp` が8バイト下へずれたままになります。すると直後の `pushq %rax` や外側の式の `popq`、さらには関数エピローグでのスタック復元がすべて8バイトずつ食い違い、誤った計算や戻り番地破損によるクラッシュを引き起こします。また、第7引数をスタックへ積んだ**後**に `subq $8, %rsp` を挟むと、呼び出し先が `8(%rsp)` にあると期待する第7引数が `16(%rsp)` へずれてしまい、ABI 違反で引数が正しく読めなくなります。

## 2-7. コード最適化①：のぞき穴最適化・CFG/データフロー解析と `volatile`

### 1. 動機（Why）：なぜコンパイラは元のコードをそのまま訳さず、安全に変形して高速化するのか

前節（[2-6節](2-6.md)）で組み立てたスタック機械方式のコード生成器は、どんなCプログラムでも正しく機械語へ翻訳できました。しかし、生成されたアセンブリをそのまま実行すると、1回の足し算のたびに何度もスタックへ `pushq`/`popq` を繰り返し、手書きのアセンブリに比べて数倍も遅くなってしまいます。

また、人間が読みやすさや保守性を優先して書いたコードには、次のような冗長さが自然に含まれます。

* 定数同士の計算（例：`buf_size = 1024 * 4;` や配列の要素サイズ計算）
* ループの中で毎回同じ値になる計算（例：`for (i = 0; i < n; i++) a[i] = x * y + i;` の `x * y`）
* デバッグ用の無効な分岐（例：`if (0) { ... }` のように実行されないコード）

もしプログラマが毎回これらを手作業で展開・書き換えようとすると、ソースコードの可読性が失われ、バグの温床になります。そこで現代のコンパイラは、**「人間は分かりやすく安全なコードを書き、機械的な高速化はコンパイラが自動で引き受ける」**という役割分担を実現するために、**コード最適化（Code Optimization）**のフェーズを備えています。

ただし、最適化には必ず守るべき原則があります。それは、**「プログラムの観測可能な振る舞い（結果・入出力・副作用）を変えてはならない（意味の保存）」**という制約です。本節では、小さな命令パターンの置換（のぞき穴最適化）から、グラフ理論を用いた体系的な解析（CFGとデータフロー解析）、そして最適化の前提が崩れる境界条件（複数ポインタが同じ番地を指す**エイリアシング**［4-(1)参照］と `volatile`）までを整理します。

### 2. 具体例と動作イメージ（Toy Model）

理論的な枠組みに入る前に、2つの小さな例で「局所的な命令の無駄」と「プログラム全体を見渡さないと消せない無駄」の違いを確かめます。

#### 実験A：のぞき穴（Peephole）を覗くだけで消せる冗長な命令列

前節のスタック機械方式の生成コードを簡略化した例として、単純な式 `x = a * 8 + 0;` に対して次のような冗長な命令列が出力されたとします。

```asm
# 最適化前（素朴なスタック機械の出力例）
    movq  -8(%rbp), %rax    # a をロード
    pushq %rax              # (1) スタックへ積む
    popq  %rax              # (2) 直後に同じレジスタへ戻す
    imulq $8, %rax          # (3) コストの大きい乗算命令
    addq  $0, %rax          # (4) 0 を足しても値は変わらない
    movq  %rax, -16(%rbp)   # x へストア
```

ここで、命令列の上を「2〜3命令だけが見える小さな窓（のぞき穴：Peephole）」でスライドさせながら眺めるだけで、次の3つの無駄が即座に見つかります。

1. **`pushq %rax; popq %rax` の相殺：** 積んだ直後に同じレジスタへ戻す操作は何もしないのと同じであるため削除します。
2. **`imulq $8, %rax` の軽量化：** 2のべき乗（$8 = 2^3$）の乗算は、より高速な左ビットシフト **`shlq $3, %rax`** へ置き換えられます（**強度削減：Strength Reduction**）。
3. **`addq $0, %rax` の削除：** `0` を足しても結果が変わらない（`x + 0 = x`）ため削除します（**代数簡約：Algebraic Simplification**）。

結果として、上の6命令はわずか3命令（`movq -8(%rbp), %rax; shlq $3, %rax; movq %rax, -16(%rbp)`）へ縮みます。

#### 実験B：ループの前後を見渡して初めて見つかる最適化

次に、次の短いCコード（中間表現の3番地コード風に書いたもの）を見てみます。

```c
t1 = 3 * 4;              // 定数同士の演算 → 12 へ畳み込み可能
i  = 0;
while (i < n) {
    t2 = x * y;          // ループ内で x も y も変わらない（ループ不変）
    a[i] = t2 + t1;      // t1 は常に 12 だと分かる（定数伝播）
    i = i + 1;
}
```

ここでは、たった2〜3命令の「のぞき穴」だけを見ても `t2 = x * y` をループの外へ出してよいかは判断できません。「ループ内のどの経路を通っても、`x` と `y` が一度も書き換えられない」という**制御フロー全体の情報**を確認して初めて、`t2 = x * y + 12;` をループの前へ1回だけ移動し、ループ本体を `a[i] = t2;` だけに単純化できるのです。

### 3. 構造・アルゴリズム・実装（What）

#### (1) 最適化のスコープと代表的な基本変換

コンパイラの最適化は、解析する範囲（スコープ）の広さによって3段階に分かれます。

1. **局所最適化（Local Optimization）：** 途中に分岐や合流を含まない1本の直線コード（後述の**基本ブロック**）の中だけで行う最適化です。
2. **大域最適化（Global / Intraprocedural Optimization）：** 1つの関数全体の制御フロー（`if` や `while` の分岐・合流）をまたいで行う最適化です。
3. **関数間最適化（Interprocedural Optimization, IPO）：** 複数の関数をまたぐ最適化です（小さな関数を呼び出し元へ直接展開する**インライン展開**や、リンク時にファイル横断で最適化する **LTO：Link-Time Optimization** など）。

これらの中で頻繁に組み合わされる代表的な基本変換を整理しておきます。

| 最適化手法 | 変換の例（前 → 後） | 狙い |
| :--- | :--- | :--- |
| **のぞき穴最適化**（Peephole） | `pushq %rax; popq %rax` → 削除 | 隣接する数命令の冗長パターンを機械語直前で除去 |
| **定数畳み込み**（Constant Folding） | `t1 = 3 * 4` → `t1 = 12` | 定数同士の計算をコンパイル時に済ませる |
| **定数伝播**（Constant Propagation） | `t1 = 12; y = x + t1` → `y = x + 12` | 定数と確定した変数の参照を直接定数へ置換 |
| **強度削減**（Strength Reduction） | `x * 8` → `x << 3` | 重い演算（乗除算）を軽い演算（シフト・加算）へ置換 |
| **共通部分式除去**（CSE） | `a = x + y; b = x + y` → `t = x + y; a = t; b = t` | 値が変わらない同じ式の再計算を防ぐ |
| **デッドコード削除**（DCE） | 結果が使われない代入・到達不能な `if (0)` 節の削除 | 実行時間とコードサイズの両方を削減 |

#### (2) 基本ブロック（Basic Block）と制御フローグラフ（CFG）

関数全体をまたぐ大域最適化を厳密に行うため、コンパイラはまず中間表現（IR）の命令列を **基本ブロック（Basic Block）** へ分割し、それらを遷移の矢印で結んだ**有向グラフ**（頂点を向きのある矢印で結んだグラフ）である **制御フローグラフ（CFG：Control Flow Graph）** を構築します（※[2-3節](2-3.md)の文脈自由文法も英語略称が CFG ですが、最適化の文脈では制御フローグラフを指します）。

**基本ブロック**とは、「先頭に入ったら末尾まで合流も分岐もなく一本道で通り抜ける極大な直線命令列」（先頭以外から途中へジャンプして入ることはなく、末尾以外から途中へ分岐して出ることもない命令のかたまり）です。つまり、基本ブロックの先頭命令が実行されたら、末尾の命令まで必ず上から順番に1回ずつ実行されることが保証されます。

命令列から基本ブロックの境界（先頭命令＝**リーダ：Leader**）を見つける手順は、次の3規則で機械的に決まります。

1. 関数の最初の命令はリーダです。
2. ジャンプ命令（条件付き・無条件）の**飛び先ラベルにある命令**はリーダです。
3. ジャンプ命令の**すぐ次の命令**はリーダです。

各リーダから「次のリーダの直前」までを1つの基本ブロックとして束ね、あるブロックの末尾から次のブロックの先頭へ制御が移り得るときに有向辺を張ると、CFGが完成します（図2-7-1）。

#### (3) データフロー解析（Dataflow Analysis）の枠組み

CFGが構築できると、コンパイラは「ある地点でどの変数の定義が有効か」「どの式の値がすでに計算済みか」といった性質を、**データフロー方程式**を反復計算することで機械的に求められます。代表例として **到達定義解析（Reaching Definitions）** の仕組みを確認します（図2-7-2）。

ある代入文 $d$（例：`d1: x = 1`）がプログラムの地点 $p$ に **到達する（reach）** とは、$d$ から $p$ へ至るCFG上の経路が少なくとも1本存在し、その途中で `x` が別の値で上書き（殺害：kill）されないことを指します。

各基本ブロック $B$ に対して、あらかじめ静的に求まる2つの集合と、解析によって求める2つの集合を定義します。

* **$\text{GEN}[B]$：** ブロック $B$ の中で生成され、$B$ の出口まで上書きされずに生き残る定義の集合です。
* **$\text{KILL}[B]$：** ブロック $B$ の中で変数が上書きされることによって無効化される、他のブロックの定義の集合です。
* **$\text{IN}[B]$ / $\text{OUT}[B]$：** ブロック $B$ の入口／出口に到達している定義の集合です。

すると、全ブロック間の関係は次の2本の方程式で表されます（前向き・和集合型データフロー）。

$$
\text{IN}[B] = \bigcup_{P \in \text{pred}(B)} \text{OUT}[P], \qquad \text{OUT}[B] = \text{GEN}[B] \cup \bigl(\text{IN}[B] \setminus \text{KILL}[B]\bigr)
$$

ここで $\text{pred}(B)$ はCFG上でブロック $B$ へ直接矢印が入っている先行ブロック全体の集合です。ループがあるため一見循環定義に見えますが、最初にすべての $\text{OUT}[B] = \emptyset$ と初期化し、「前のブロックから届いた代入履歴を受け取り、上書き分（`KILL`）を消して新規分（`GEN`）を足して次へ渡すバケツリレー」を、**どのブロックの $\text{OUT}[B]$ も変化しなくなる安定状態（不動点）に収束するまで**反復します。

伝達関数 $f_B(X) = \text{GEN}[B] \cup (X \setminus \text{KILL}[B])$ と和集合演算 $\cup$ は入力が増えれば出力も減らない（**単調増加**）性質を持ち、かつプログラム中の定義文の総数は有限であるため、集合の要素が増え続ける回数には上限があり**必ず有限回で停止**します。こうして得られる解は、CFG上のあらゆる経路を網羅した**最小不動点（安全側の保守的近似）**です。なお、到達定義解析（前向き・和集合 $\cup$）、次節の生存解析（後ろ向き・和集合 $\cup$）、利用可能式解析（前向き・積集合 $\cap$）など多様なデータフロー解析は、すべて **束・半格子（Semilattice）** と **タルスキー（Tarski）の不動点定理**（「有限の高さを持つ半格子上で単調な伝達関数を反復すれば、最小または最大不動点へ必ず有限回で収束する」）という共通の数学的枠組みで統一されています。

実際に、図2-7-1の4つの基本ブロック（代入文を `d1: s = 0`, `d2: i = 0`, `d3: t = x * y`, `d4: s = s + t`, `d5: i = i + 1` と命名）に対して `GEN`/`KILL` と不動点反復を手計算してみます（各反復では `B1 → B2 → B3 → B4` の順に計算し、同一反復内で更新された最新の `OUT` を後続ブロックへ即座に反映する **Gauss-Seidel 順** で進めます）。

| ブロック | 先行 $\text{pred}$ | $\text{GEN}[B]$ | $\text{KILL}[B]$ | 反復1の $\text{IN}$ / $\text{OUT}$ | 反復2の $\text{IN}$ / $\text{OUT}$ | 反復3（収束確認） |
| :---: | :---: | :---: | :---: | :--- | :--- | :--- |
| **B1** | $\emptyset$ | $\{d_1, d_2\}$ | $\{d_4, d_5\}$ | $\text{IN}: \emptyset$<br>$\text{OUT}: \{d_1, d_2\}$ | $\text{IN}: \emptyset$<br>$\text{OUT}: \{d_1, d_2\}$ | 変化なし |
| **B2** | $\{B1, B3\}$ | $\emptyset$ | $\emptyset$ | $\text{IN}: \{d_1, d_2\}$<br>$\text{OUT}: \{d_1, d_2\}$ | $\text{IN}: \{d_1, d_2, d_3, d_4, d_5\}$<br>$\text{OUT}: \{d_1, d_2, d_3, d_4, d_5\}$ | 変化なし |
| **B3** | $\{B2\}$ | $\{d_3, d_4, d_5\}$ | $\{d_1, d_2\}$ | $\text{IN}: \{d_1, d_2\}$<br>$\text{OUT}: \{d_3, d_4, d_5\}$ | $\text{IN}: \{d_1, d_2, d_3, d_4, d_5\}$<br>$\text{OUT}: \{d_3, d_4, d_5\}$ | 変化なし |
| **B4** | $\{B2\}$ | $\emptyset$ | $\emptyset$ | $\text{IN}: \{d_1, d_2\}$<br>$\text{OUT}: \{d_1, d_2\}$ | $\text{IN}: \{d_1, d_2, d_3, d_4, d_5\}$<br>$\text{OUT}: \{d_1, d_2, d_3, d_4, d_5\}$ | 変化なし |

反復2で後退辺 `B3 → B2` を通じて $\{d_3, d_4, d_5\}$ が `B2` と `B4` へ流れ込み、反復3で全ブロックが変化しなくなって収束します。この結果から、出口 `B4`（`return s`）に到達する `s` の定義は `d1`（0回ループ時）と `d4`（1回以上ループ時）の2つであり、一方 `B3` で参照される `x, y` にはループ内の定義が一切到達していない（ループ不変である）ことが機械的に分かります。

> **【コラム：SSA形式と $\phi$ 関数（[2-1節](2-1.md)の伏線回収）】**
>
> [2-1節](2-1.md)で「代入のたびに別番号を振る **SSA形式（静的単一代入形式）**」を紹介しました。直線コードなら `x1 = 1; x2 = x1 + 2;` で済みますが、`if` 文やループで複数の経路が合流する地点ではどうなるでしょうか。
>
> ```text
> if (cond) { x1 = 10; } else { x2 = 20; }
> x3 = phi(x1, x2);   // 直前にどちらのブロックから来たかに応じて x1 または x2 を選ぶ
> y  = x3 + 1;
> ```
>
> このように合流点の先頭に仮想的な選択命令である **$\phi$（ファイ）関数** を配置することで、任意のCFGを「すべての変数がプログラム中でちょうど1回だけ定義される」SSA形式へ変換できます（図2-7-3）。SSA形式の最大の利点は、到達定義解析のような $O(|B|\cdot|D|)$ のビットベクタ反復を毎回回さなくても、**すべての変数の参照箇所から定義箇所へのリンク（Def-Useチェイン）が直接1対1に定まる**点にあり、定数伝播やデッドコード削除、後述の GVN（大域値番号付け）が大幅に高速化・単純化されます。

#### (4) ループ最適化：ループ不変コード移動とループ展開

プログラムの実行時間の大半はループの中で消費されるため、CFG上の「後退辺（ループ本体からループ判定へ戻る辺）」を検出してループを重点的に最適化します。

* **ループ不変コード移動（LICM：Loop-Invariant Code Motion）：** 実験Bや図2-7-1の `t = x * y` のように、到達定義解析の結果「`x` と `y` の定義がすべてループの外側にしかなく、ループ内で一度も書き換わらない」と確認できた式を、ループ入口の直前へ移動して計算回数を $n$ 回から1回へ減らします。ただし、ループが1回も実行されない場合（例：`n <= 0`）に備え、**ゼロ除算・不正メモリアクセス・C言語の符号あり整数オーバーフローなどの未定義動作（UB）といった例外や副作用を起こし得る式は、無条件にループ外へ移動できません**（安全に実行できることが保証された場合のみ移動します）。
* **ループ展開（Loop Unrolling）：** ループ本体をたとえば4回分並べて書き出し、カウンタ加算 `i += 4` と終了判定の分岐回数を4分の1へ減らします。[0-5節](../0/0-5.md)で見た**制御ハザード（分岐命令の実行回数）を削減**し、さらに命令スケジューリング（[0-6節](../0/0-6.md)）の余地を広げる効果があります。

> **【コラム：最適化の「順序問題（Phase Ordering Problem）」と LLVM パイプライン】**
>
> コンパイラには定数伝播、共通部分式除去、インライン展開、ループ不変コード移動、デッドコード削除など数十種類もの1変換単位（**最適化パス**）が組み込まれています。ここで悩ましいのが、**「どの順番で最適化を適用するかによって、最終的なコードの速さが大きく変わる」**という **順序問題（Phase Ordering Problem）** です。
>
> たとえば次のコードで、**インライン展開 → 定数伝播 → デッドコード削除** が連鎖する様子を見てみます。
>
> ```c
> int helper(int flag, int x) { return flag ? x * 2 : x + 1; }
> int f(int x) { return helper(0, x); }
> // ① インライン展開後: return (0 ? x * 2 : x + 1);
> // ② 定数伝播＋DCE後:  return x + 1;  （分岐も乗算も消滅）
> ```
>
> 逆にループ展開を先にやりすぎるとコードが膨張してインライン展開の閾値を超えてしまうこともあります。そのため LLVM の `-O2` パイプラインでは、まずフロントエンドがスタック変数（`alloca`）として出力した局所変数をSSA仮想レジスタへ昇格させる **`mem2reg`（または `SROA`）を最序盤に実行**し、後続の解析が効く土台を整えたうえで、`InstCombine`（のぞき穴的簡約）→ `SimplifyCFG`（制御フロー簡約）→ `Inline`（インライン展開）→ `SROA` → `GVN`（大域値番号付けによるCSE）→ `LICM` のように重要なパスを段階的・反復的に適用する構成をとっています。また近年では、あらゆるプログラムに対する固定順序の限界を超える試みとして、強化学習や機械学習を用いてインライン判定やパス順序を最適化する **MLGO（LLVM での実導入）** や **CompilerGym** のような研究・実務応用も進んでいます。

### 4. 限界と補正（Critique & Adaptation）

データフロー解析と最適化は強力ですが、現実のCプログラムやハードウェアを相手にする場面では、次の4つの重要な限界と補正を押さえておく必要があります。

#### (1) ポインタ・エイリアシング（Aliasing）の壁と `restrict`・自動ベクトル化（SIMD化）

次のC関数を見てください。

```c
void add_twice(int *a, int *b) {
    *a += *b;
    *a += *b;
}
```

一見すると `*b` の値は変わらないので、`*b` を1回だけレジスタへ読み込み、`*a += 2 * (*b);` に最適化できそうです。しかし、コンパイラは**この最適化を行えません**。なぜなら、呼び出し元が **`add_twice(&x, &x)` のように `a` と `b` へ同じ変数のアドレスを渡す可能性**があるからです。もし `a == b`（初期値 `x = 5`）なら、1行目で `x` が `10` になり、2行目で `10 + 10 = 20` になるのが正解ですが、先の最適化をすると `5 + 2 * 5 = 15` と誤った答えになってしまいます。

このように、複数のポインタが同じメモリ番地を指し得る現象を **エイリアシング（Aliasing：別名参照）** と呼びます。コンパイラは安全を最優先するため、ポインタ経由の書き込みがあるたびに「他のポインタが指す値も書き換わったかもしれない」と保守的に仮定し、レジスタへのキャッシュを諦めて毎回メモリから再ロードします。

エイリアシングは、ループの **自動ベクトル化（SIMD化：1命令で4〜8要素の配列演算を並列処理する高速化）** も大きく阻害します。たとえば `for (int i = 0; i < n; i++) c[i] = a[i] + b[i];` において、出力先 `c` と入力 `a` が重なっている（例：`c == a + 1`）と、ある反復での書き込みが次の反復の読み込みへ依存してしまい、4要素同時計算では結果が壊れます。そのためコンパイラは重複しないと証明できない限り SIMD 化を見送るか、実行時の重複チェック分岐を挿入します。

この限界に対するC99以降の補正が **`restrict` 修飾子**（`void add_twice(int *restrict a, int *restrict b)`）です。プログラマが「この関数の範囲内では、`a` と `b` が指すメモリ領域は重ならない」とコンパイラへ明示的に約束することで、安全な再ロード削減や自動ベクトル化（SIMD化）を有効にできます。

#### (2) コンパイラから見えない外部変化と `volatile` 修飾子

組み込みシステムやOSカーネル、割り込み処理では、次のようなフラグ待ちループがよく書かれます。

```c
int ready = 0;   // 別の割り込みハンドラやハードウェア機器が 1 に書き換える想定

void wait_device(void) {
    while (ready == 0) {
        // 何もしないで待つ
    }
}
```

この関数を通常の最適化オプション（`-O2`）でコンパイルすると、最適化器は次のような変形を行います。CFGとデータフロー解析の目には、`wait_device` のループ本体の中に **`ready` を書き換える命令が1つも存在しない** ように見えるからです。そこで最適化器はループ不変コード移動を適用し、`ready` の読み出しをループの外へ追い出してしまいます（図2-7-4）。

```c
// -O2 最適化後の等価な姿：ready が最初 0 なら、二度とメモリを見ず無限ループになる
if (ready == 0) {
    while (1) { }
}
```

これに対するC言語の補正が **`volatile` 修飾子**（`volatile int ready = 0;`）です。`volatile` はコンパイラに対し、**「この変数はコンパイラの知らない外部要因（ハードウェアのデバイスレジスタや割り込みハンドラなど）で値が変化し得る。アクセスをレジスタへキャッシュしたり、削除・ループ外移動・順序変更したりせず、ソースに書かれた通りに毎回必ずメモリから読み書きせよ」**と命令する制約です。

ここで実務上重要な注意点があります。**`volatile` が抑止するのは「コンパイラの最適化」だけ**であり、マルチコアCPUのハードウェア側で起きる次の2つの問題は防げません。

1. **メモリ順序の逆転：** マルチコアCPUのキャッシュや命令の追い越し実行（アウトオブオーダ実行、[0-6節](../0/0-6.md)）によって、別コアから観測される読み書きの順序が入れ替わる現象は止められません。
2. **不可分性（アトミック性）の欠如：** `count++` のような「読出 → 加算 → 書戻」の途中で別コアが割り込んで値が失われる現象も防げません。

したがって、`volatile` はメモリ空間に割り当てられたハードウェア機器の制御レジスタ（**MMIO**）や同一スレッド内のシグナルハンドラ用フラグなど限定的な用途に使い、マルチスレッド間の同期には必ず[第4部](../index.md#part-4)（[4-3節](../4/4-3.md)）で学ぶ**アトミック型（`<stdatomic.h>`）やロック（排他制御）**を用いる必要があります。

#### (3) 未定義動作（UB）を前提とした最適化の注意点

最適化器は「C言語の規格で**未定義動作（Undefined Behavior, UB）**とされている事象は実行時に起きない」と仮定して変換を行います。たとえば [0-1節](../0/0-1.md)で触れた「符号あり整数のオーバーフロー」が起きないと仮定するため、

```c
int is_overflow(int x) {
    return (x + 1) < x;   // 符号あり整数 x でオーバーフローを検出しようとする誤ったコード
}
```

のような関数を `-O2` でコンパイルすると、コンパイラは「数学的に $x + 1 < x$ は常に偽（UBが起きない前提）」と判断し、**関数全体を `return 0;`（定数0を返すだけ）へ丸ごと最適化して消去**します。安全にオーバーフローを判定するには、実際に加算してUBを起こす前に **`return x == INT_MAX;`**（一般の加算なら `b > 0 && a > INT_MAX - b`）と事前チェックするか、GCC/Clang の組み込み関数 **`__builtin_add_overflow(x, 1, &res)`**（C23 標準 `<stdckdint.h>` の `ckd_add`）を用います。また、ポインタ `p` を一度逆参照 `*p` した後に `if (p == NULL)` と書いても、「もし `p` が `NULL` なら前の行ですでにUBなので、ここに来た時点で `p` は非NULL」とみなして `NULL` チェックが削除されます。最適化と共存するには、UBに依存しない安全な判定順序を書くことが不可欠です。

#### (4) 最適化によるデバッグ困難化とプロファイリングに基づく集中（80/20 の法則）

最適化が進むほど、コード生成と運用のあいだには次の2つの実務的なトレードオフも生じます。

* **最適化とデバッグの困難化（[1-6節](../1/1-6.md)との接続）：** 命令の並べ替え・インライン展開・定数畳み込み・不要変数削除が適用されると、機械語命令と元のソースコード行・局所変数の1対1対応が崩れます。そのため `-O2` でビルドしたバイナリをデバッガで追うと、ステップ実行の行番号が前後したり変数が `<optimized out>` として観測できなくなったりします。実務では開発時のデバッグ用に `-O0` やデバッグ体験を損ねない最適化のみを施す `-Og` を使い、リリースビルドで `-O2` 等へ切り替えます。
* **プロファイリングと 80/20 の法則：** 経験上、プログラムの実行時間の大半（おおよそ80%）はコード全体のごく一部（おおよそ20%のループや関数＝ホットスポット）で費やされます。実行頻度の低い処理にまで無闇にループ展開やインライン展開を施すとコードサイズが肥大化し、かえって命令キャッシュ（[0-7節](../0/0-7.md)）のヒット率低下を招きます。そのため、プロファイリングによる計測結果をもとにホットスポットへ最適化を集中させる設計（[2-1節](2-1.md)の PGO や JIT のホットスポット検出）が重要です。

### 理解度チェック（次節へ進む前の確認）

本節の基本ブロック分割と到達定義解析、エイリアシング・UB最適化の診断、および LICM の安全性条件と `volatile` の限界を確認します。

> **【確認の問い】**
>
> 1. **（基本ブロック分割・到達定義解析と定数伝播の可否判定）**
>     次の6行の3番地コード（`cond` は外部引数とします）を考えます。
>
>     ```text
>     1: d1: a = 5
>     2: d2: x = 10
>     3: if cond goto L1
>     4: d3: x = 20
>     5: L1: y = a + 1
>     6:     z = x + 1
>     ```
>
>     * (a) リーダの3規則に従って基本ブロック `B1, B2, B3` へ分割し、変数 `a, x` の定義 `d1, d2, d3` に着目して各ブロックの `GEN`, `KILL`, `IN`, `OUT` を求めてください（ループがないため1パスで収束します）。
>     * (b) 求めた `IN[B3]` の結果をもとに、5行目の `a` と6行目の `x` について、それぞれ定数伝播によって定数へ置換できるか否かを理由とあわせて判定してください。
>
> 2. **（エイリアシング・`restrict` と未定義動作 UB による最適化の診断）**
>     次の2つの C 関数を `-O2` で最適化する場面を考えます。
>
>     ```c
>     void f(int *p, int *q) { *p = 1; *q = 2; printf("%d\n", *p); }
>     int g(int *p) { int v = *p; if (p == NULL) return -1; return v; }
>     ```
>
>     * (a) 関数 `f` で、コンパイラは `printf` に渡す `*p` を定数 `1` へ置き換えられるでしょうか。また、引数へ `restrict` を付けると最適化の可否はどう変わりますか。
>     * (b) 関数 `g` を `-O2` でコンパイルすると、2つ目の文 `if (p == NULL) return -1;` が丸ごと削除されることがあります。なぜそのような最適化が起きるのか、未定義動作（UB）の前提に沿って説明してください。
>
> 3. **（ループ不変コード移動 LICM の反例と `volatile` の限界）**
>
>     * (a) 次のループにおいて、式 `100 / k` はループ内で `k` が書き換わらないため一見ループ不変に見えます。
>
>         ```c
>         for (int i = 0; i < n; i++) {
>             a[i] = 100 / k + i;
>         }
>         ```
>
>         しかし、この式を無条件にループ直前へ移動（LICM）するとプログラムの振る舞いが壊れる具体的な入力 `(n, k)` の組を1つ挙げ、なぜ壊れるかを説明してください。
>
>     * (b) マルチスレッド環境で複数コアから共有変数に対して `count++` を実行するとき、`volatile int count;` としても安全な同期にならない2つの理由（ハードウェア側の制約）を挙げてください。
