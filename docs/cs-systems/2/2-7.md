### 前節（2-6）の確認問題の解答

前節の最後に提示した3つの問いの解答を確認します。問3がそのまま本節（コード最適化とデータフロー解析）の導入になります。

1. **スタック機械による引き算のコード生成とトレース（`10 - (3 + 2)`）：**

    * **(a) スタックの推移（底 → 頂上）：**
        `[10]` $\to$ `[10, 3]` $\to$ `[10, 3, 2]` $\to$（`3 + 2` を計算）$\to$ `[10, 5]` $\to$（`10 - 5` を計算）$\to$ **`[5]`**

    * **(b) 最後の引き算でポップされる値：**
        先に左辺 `10`、後から右辺 `5` が積まれているため、1回目の `popq %rdi` で取り出されるのは右辺の **`5`**、2回目の `popq %rax` で取り出されるのは左辺の **`10`** です（`subq %rdi, %rax` で $10 - 5 = 5$）。

2. **短絡評価と式文のスタック管理：**

    * **(a) `if (n != 0 && total / n > 10)` が安全に動く理由：**
        `&&` のコード生成では、左辺 `n != 0` の評価結果が `0`（偽）だった瞬間に `.L_false` ラベルへ条件分岐（`je`）して `0` を積みます。右辺 `total / n > 10` の機械語命令列そのものを飛び越すため、`n == 0` のときに除算命令が一切実行されず安全です。

    * **(b) 式文の末尾で余剰スタック値を破棄し忘れた場合の問題：**
        `gen_expr` は評価結果をスタック頂上へ1個（8バイト）残します。式文の末尾で `addq $8, %rsp` を出力し忘れると、ループが1周するたびにスタックポインタ `%rsp` が8バイトずつ下がり続け、やがて確保されたスタック領域を使い切って**スタックオーバーフロー（Segmentation Fault）**を引き起こします。

3. **無駄な `push`/`pop` や不変な計算をどう削るか（本節への接続）：**
    コンパイラは、命令列の局所的なパターンを書き換える**のぞき穴最適化**から始め、さらにプログラムを**基本ブロック**と**制御フローグラフ（CFG）**へ分解して変数の定義と使用を体系的に追跡する**データフロー解析**を行うことで、プログラムの意味を変えずに無駄な命令やメモリアクセスを安全に削除・変形します。

## 2-7. コード最適化①：のぞき穴最適化・CFG/データフロー解析と `volatile`

### 1. 動機（Why）：なぜコンパイラは元のコードをそのまま訳さず、安全に変形して高速化するのか

前節（2-6節）で組み立てたスタック機械方式のコード生成器は、どんなCプログラムでも正しく機械語へ翻訳できました。しかし、生成されたアセンブリをそのまま実行すると、1回の足し算のたびに何度もスタックへ `pushq`/`popq` を繰り返し、手書きのアセンブリに比べて数倍も遅くなってしまいます。

また、人間が読みやすさや保守性を優先して書いたコードには、次のような冗長さが自然に含まれます。

* 定数同士の計算（例：`buf_size = 1024 * 4;` や配列の要素サイズ計算）
* ループの中で毎回同じ値になる計算（例：`for (i = 0; i < n; i++) a[i] = x * y + i;` の `x * y`）
* デバッグ用の無効な分岐（例：`if (0) { ... }` のように絶対に実行されないコード）

もしプログラマが毎回これらを手作業で展開・書き換えようとすると、ソースコードの可読性が失われ、バグの温床になります。そこで現代のコンパイラは、**「人間は分かりやすく安全なコードを書き、機械的な高速化はコンパイラが自動で引き受ける」**という役割分担を実現するために、**コード最適化（Code Optimization）**のフェーズを備えています。

ただし、最適化には絶対に破ってはならない鉄則があります。それは、**「プログラムの観測可能な振る舞い（結果・入出力・副作用）を一切変えてはならない（意味の保存）」**という制約です。本節では、小さな命令パターンの置換（のぞき穴最適化）から、グラフ理論を用いた体系的な解析（CFGとデータフロー解析）、そして最適化の前提が崩れる境界条件（エイリアシングと `volatile`）までを整理します。

### 2. 具体例と動作イメージ（Toy Model）

理論的な枠組みに入る前に、2つの小さな例で「局所的な命令の無駄」と「プログラム全体を見渡さないと消せない無駄」の違いを確かめます。

#### 実験A：のぞき穴（Peephole）を覗くだけで消せる冗長な命令列

前節のスタック機械方式で、単純な式 `x = a * 8 + 0;` をそのまま翻訳すると、次のような冗長な命令列が出力されます。

```asm
# 最適化前（素朴なスタック機械の出力例）
    movq  -8(%rbp), %rax    # a をロード
    pushq %rax              # (1) スタックへ積む
    popq  %rax              # (2) 直後に同じレジスタへ戻す
    imulq $8, %rax          # (3) コストの大きい乗算命令
    addq  $0, %rax          # (4) 0 を足しても値は変わらない
    movq  %rax, -16(%rbp)   # x へストア
```

ここで、命令列の上を「2〜3命令だけが見える小さな窓（のぞき穴：Peephole）」でスライドさせながら眺めるだけで、次の3つの無駄が即座に見つかります。

1. **`pushq %rax; popq %rax` の相殺：** 積んだ直後に同じレジスタへ戻す操作は何もしないのと同じ（削除）。
2. **`imulq $8, %rax` の軽量化：** 2のべき乗（$8 = 2^3$）の乗算は、より高速な左ビットシフト **`shlq $3, %rax`** へ置き換え可能（**強度削減：Strength Reduction**）。
3. **`addq $0, %rax` の削除：** $x + 0 = x$ より不要（**代数簡約：Algebraic Simplification**）。

結果として、上の6命令はわずか3命令（`movq -8(%rbp), %rax; shlq $3, %rax; movq %rax, -16(%rbp)`）へ縮みます。

#### 実験B：ループの前後を見渡して初めて見つかる最適化

次に、次の短いCコード（中間表現の3番地コード風に書いたもの）を見てみます。

```c
t1 = 3 * 4;              // 定数同士の演算 → 12 へ畳み込み可能
i  = 0;
while (i < n) {
    t2 = x * y;          // ループ内で x も y も変わらない（ループ不変）
    a[i] = t2 + t1;      // t1 は常に 12 だと分かる（定数伝播）
    i = i + 1;
}
```

ここでは、たった2〜3命令の「のぞき穴」だけを見ても `t2 = x * y` をループの外へ出してよいかは判断できません。「ループ内のどの経路を通っても、`x` と `y` が一度も書き換えられない」という**制御フロー全体の情報**を確認して初めて、`t2 = x * y + 12;` をループの前へ1回だけ移動し、ループ本体を `a[i] = t2;` だけに単純化できるのです。

### 3. 構造・アルゴリズム・実装（What）

#### (1) 最適化のスコープと代表的な基本変換

コンパイラの最適化は、解析する範囲（スコープ）の広さによって3段階に分かれます。

1. **局所最適化（Local Optimization）：** 途中に分岐や合流を含まない1本の直線コード（後述の**基本ブロック**）の中だけで行う最適化。
2. **大域最適化（Global / Intraprocedural Optimization）：** 1つの関数全体の制御フロー（`if` や `while` の分岐・合流）をまたいで行う最適化。
3. **関数間最適化（Interprocedural Optimization, IPO）：** 複数の関数をまたぐ最適化（小さな関数を呼び出し元へ直接展開する**インライン展開**や、リンク時にファイル横断で最適化する **LTO：Link-Time Optimization** など）。

これらの中で頻繁に組み合わされる代表的な基本変換を整理しておきます。

| 最適化手法 | 変換の例（前 → 後） | 狙い |
| :--- | :--- | :--- |
| **のぞき穴最適化**（Peephole） | `pushq %rax; popq %rax` → 削除 | 隣接する数命令の冗長パターンを機械語直前で除去 |
| **定数畳み込み**（Constant Folding） | `t1 = 3 * 4` → `t1 = 12` | 定数同士の計算をコンパイル時に済ませる |
| **定数伝播**（Constant Propagation） | `t1 = 12; y = x + t1` → `y = x + 12` | 定数と確定した変数の参照を直接定数へ置換 |
| **強度削減**（Strength Reduction） | `x * 8` → `x << 3` | 重い演算（乗除算）を軽い演算（シフト・加算）へ置換 |
| **共通部分式除去**（CSE） | `a = x + y; b = x + y` → `t = x + y; a = t; b = t` | 値が変わらない同じ式の再計算を防ぐ |
| **デッドコード削除**（DCE） | 結果が使われない代入・到達不能な `if (0)` 節の削除 | 実行時間とコードサイズの両方を削減 |

#### (2) 基本ブロック（Basic Block）と制御フローグラフ（CFG）

関数全体をまたぐ大域最適化を厳密に行うため、コンパイラはまず中間表現（IR）の命令列を **基本ブロック（Basic Block）** へ分割し、それらを遷移の矢印で結んだ有向グラフである **制御フローグラフ（CFG：Control Flow Graph）** を構築します（※2-3節の文脈自由文法も英語略称が CFG ですが、最適化の文脈では制御フローグラフを指します）。

**基本ブロック**とは、「先頭（入口）以外から途中へジャンプして入ることはなく、末尾（出口）以外から途中へ分岐して出ることもない、極大な直線命令列」です。つまり、基本ブロックの先頭命令が実行されたら、末尾の命令まで必ず上から順番に1回ずつ実行されることが保証されます。

命令列から基本ブロックの境界（先頭命令＝**リーダ：Leader**）を見つける手順は、次の3規則で機械的に決まります。

1. 関数の最初の命令はリーダです。
2. ジャンプ命令（条件付き・無条件）の**飛び先ラベルにある命令**はリーダです。
3. ジャンプ命令の**すぐ次の命令**はリーダです。

各リーダから「次のリーダの直前」までを1つの基本ブロックとして束ね、あるブロックの末尾から次のブロックの先頭へ制御が移り得るときに有向辺を張ると、CFGが完成します（図2-7-1）。

#### (3) データフロー解析（Dataflow Analysis）の枠組み

CFGが構築できると、コンパイラは「ある地点でどの変数の定義が有効か」「どの式の値がすでに計算済みか」といった性質を、**データフロー方程式**を反復計算することで機械的に求められます。代表例として **到達定義解析（Reaching Definitions）** の仕組みを確認します（図2-7-2）。

ある代入文 $d$（例：`d1: x = 1`）がプログラムの地点 $p$ に **到達する（reach）** とは、$d$ から $p$ へ至るCFG上の経路が少なくとも1本存在し、その途中で `x` が別の値で上書き（殺害：kill）されないことを指します。

各基本ブロック $B$ に対して、あらかじめ静的に求まる2つの集合と、解析によって求める2つの集合を定義します。

* **$\text{GEN}[B]$：** ブロック $B$ の中で生成され、$B$ の出口まで上書きされずに生き残る定義の集合。
* **$\text{KILL}[B]$：** ブロック $B$ の中で変数が上書きされることによって無効化される、他のブロックの定義の集合。
* **$\text{IN}[B]$ / $\text{OUT}[B]$：** ブロック $B$ の入口／出口に到達している定義の集合。

すると、全ブロック間の関係は次の2本の方程式で表されます（前向き・和集合型データフロー）。

$$
\text{IN}[B] = \bigcup_{P \in \text{pred}(B)} \text{OUT}[P], \qquad \text{OUT}[B] = \text{GEN}[B] \cup \bigl(\text{IN}[B] \setminus \text{KILL}[B]\bigr)
$$

ここで $\text{pred}(B)$ はCFG上でブロック $B$ へ直接矢印が入っている先行ブロック全体の集合です。ループがあるため一見循環定義に見えますが、最初にすべての $\text{OUT}[B] = \emptyset$ と初期化し、**どのブロックの $\text{OUT}[B]$ も変化しなくなる（不動点に収束する）まで**式を繰り返し適用すると、集合は単調増加かつ有限なので必ず有限回で厳密な解へ収束します。

#### (4) ループ最適化：ループ不変コード移動とループ展開

プログラムの実行時間の大半はループの中で消費されるため、CFG上の「後退辺（ループ本体からループ判定へ戻る辺）」を検出してループを重点的に最適化します。

* **ループ不変コード移動（LICM：Loop-Invariant Code Motion）：** 実験Bや図2-7-1の `t = x * y` のように、到達定義解析の結果「`x` と `y` の定義がすべてループの外側にしかなく、ループ内で一度も書き換わらない」と確認できた式を、ループ入口の直前へ移動して計算回数を $n$ 回から1回へ減らします。
* **ループ展開（Loop Unrolling）：** ループ本体をたとえば4回分並べて書き出し、カウンタ加算 `i += 4` と終了判定の分岐回数を4分の1へ減らします。0-5節で見た**制御ハザード（分岐命令の実行回数）を削減**し、さらに命令スケジューリング（0-6節）の余地を広げる効果があります。

> **【コラム：最適化の「順序問題（Phase Ordering Problem）」】**
>
> コンパイラには定数伝播、共通部分式除去、インライン展開、ループ不変コード移動、デッドコード削除など数十種類もの最適化パスが組み込まれています。ここで悩ましいのが、**「どの順番で最適化を適用するかによって、最終的なコードの速さが大きく変わる」**という **順序問題（Phase Ordering Problem）** です。
>
> たとえば、ある関数を**インライン展開**したことで初めて引数が定数 `0` だと分かり、そこから**定数伝播**が連鎖して `if (0)` が消え（**デッドコード削除**）、さらに残ったコードから新しい共通部分式が現れる、といった連鎖が頻繁に起きます。逆にループ展開を先にやりすぎるとコードが膨張してインライン展開の閾値を超えてしまうこともあります。あらゆるプログラムに対して常に最良の適用順序を見つける一般的なアルゴリズムは知られていないため、GCCやLLVMでは長年の経験則とベンチマークに基づき、重要な最適化パスを少しずつ順番を変えて複数回反復適用するパイプライン構成をとっています。

### 4. 限界と補正（Critique & Adaptation）

データフロー解析と最適化は強力ですが、現実のCプログラムやハードウェアを相手にする場面では、次の3つの重要な限界と補正を押さえておく必要があります。

#### (1) ポインタ・エイリアシング（Aliasing）の壁と `restrict`

次のC関数を見てください。

```c
void add_twice(int *a, int *b) {
    *a += *b;
    *a += *b;
}
```

一見すると `*b` の値は変わらないので、`*b` を1回だけレジスタへ読み込み、`*a += 2 * (*b);` に最適化できそうです。しかし、コンパイラは**この最適化を行えません**。なぜなら、呼び出し元が **`add_twice(&x, &x)` のように `a` と `b` へ同じ変数のアドレスを渡す可能性**があるからです。もし `a == b`（初期値 `x = 5`）なら、1行目で `x` が `10` になり、2行目で `10 + 10 = 20` になるのが正解ですが、先の最適化をすると `5 + 2 * 5 = 15` と誤った答えになってしまいます。

このように、複数のポインタが同じメモリ番地を指し得る現象を **エイリアシング（Aliasing：別名参照）** と呼びます。コンパイラは安全を最優先するため、ポインタ経由の書き込みがあるたびに「他のポインタが指す値も書き換わったかもしれない」と保守的に仮定し、レジスタへのキャッシュを諦めて毎回メモリから再ロードします。

この限界に対するC99以降の補正が **`restrict` 修飾子**（`void add_twice(int *restrict a, int *restrict b)`）です。プログラマが「この関数の範囲内では、`a` と `b` が指すメモリ領域は絶対に重ならない」とコンパイラへ明示的に約束することで、安全な最適化と高速化を解放できます。

#### (2) コンパイラから見えない外部変化と `volatile` 修飾子

組み込みシステムやOSカーネル、割り込み処理では、次のようなフラグ待ちループがよく書かれます。

```c
int ready = 0;   // 別の割り込みハンドラやハードウェア機器が 1 に書き換える想定

void wait_device(void) {
    while (ready == 0) {
        // 何もしないで待つ
    }
}
```

この関数を通常の `-O2` でコンパイルすると、最適化器は重大な変形を行います。CFGとデータフロー解析の目には、`wait_device` のループ本体の中に **`ready` を書き換える命令が1つも存在しない** ように見えるからです。そこで最適化器はループ不変コード移動を適用し、`ready` の読み出しをループの外へ追い出してしまいます（図2-7-3）。

```c
// -O2 最適化後の等価な姿：ready が最初 0 なら、二度とメモリを見ず無限ループになる
if (ready == 0) {
    while (1) { }
}
```

これに対するC言語の補正が **`volatile` 修飾子**（`volatile int ready = 0;`）です。`volatile` はコンパイラに対し、**「この変数はコンパイラの知らない外部要因（ハードウェアのデバイスレジスタや割り込みハンドラなど）で値が変化し得る。アクセスをレジスタへキャッシュしたり、削除・ループ外移動・順序変更したりせず、ソースに書かれた通りに毎回必ずメモリから読み書きせよ」**と命令する制約です。

ここで実務上非常に重要な注意点があります。**`volatile` は「コンパイラの最適化を抑止する」だけであり、マルチコアCPUのキャッシュやアウトオブオーダ実行によるメモリアクセス順序の逆転、および読み書きの不可分性（アトミック性）は一切保証しません**。したがって、`volatile` はハードウェアのデバイスレジスタ（MMIO）や同一スレッド内のシグナルフラグなど限定的な用途に使い、マルチスレッド間の同期には必ず第4部（4-3節）で学ぶ**アトミック型（`<stdatomic.h>`）やロック**を用いる必要があります。

#### (3) 未定義動作（UB）を前提とした最適化の注意点

最適化器は「C言語の規格で**未定義動作（Undefined Behavior, UB）**とされている事象は実行時に絶対に起きない」と仮定して変換を行います。たとえば 0-1節で触れた「符号あり整数のオーバーフロー」が起きないと仮定するため、

```c
int is_overflow(int x) {
    return (x + 1) < x;   // 符号あり整数 x でオーバーフローを検出しようとする誤ったコード
}
```

のような関数を `-O2` でコンパイルすると、コンパイラは「数学的に $x + 1 < x$ は常に偽（UBが起きない前提）」と判断し、**関数全体を `return 0;`（定数0を返すだけ）へ丸ごと最適化して消去**します。また、ポインタ `p` を一度逆参照 `*p` した後に `if (p == NULL)` と書いても、「もし `p` が `NULL` なら前の行ですでにUBなので、ここに来た時点で `p` は絶対に非NULL」とみなして `NULL` チェックが削除されます。最適化と共存するには、UBに依存しない安全な判定順序を書くことが不可欠です。

### 5. 接続と展望（Bridge）：本節の内容が後半のどの部に繋がるか

1. **次節（2-8節：コード最適化② 生存解析・干渉グラフとグラフ彩色によるレジスタ割当）：**
    本節で導入したCFGとデータフロー方程式を「後ろ向き」に適用する**生存解析（Liveness Analysis）**から干渉グラフを作り、スタック機械の最大の弱点だったメモリアクセス過多を解消する**レジスタ割当**へ進みます。

2. **第4部（4-3・4-7節：メモリ一貫性モデルとシグナル）：**
    本節4-(2)で注意喚起した「`volatile` だけではマルチコア環境のスレッド間同期が壊れる理由」を、ハードウェアのストアバッファとメモリバリアの観点から解明します。また、シグナルハンドラとのフラグ共有（`sig_atomic_t`）にも直結します。

3. **第5部（5-1節：MMIOとデバイスドライバ）：**
    OSカーネルがメモリ空間にマップされたハードウェアレジスタ（MMIO）を読み書きするとき、なぜ必ず `volatile` ポインタ経由でアクセスするのかを実例で確認します。

4. **第9部（9-4節：DBMSの問合せ最適化）：**
    「観測可能な結果（意味）を変えずに、コストの低い実行計画へ等価変換する」という本節の設計思想は、データベースにおける関係代数の等価変換（Selection Pushdown等）と完全に同型です。

>     popq  %rax
>     imulq $16, %rax
>     addq  $0, %rax
>     movq  %rax, -16(%rbp)
>     ```
>
> 2. **（`volatile` の役割と限界）**
>     デバイスからの完了通知を待つループ `while (status == 0) {}` について、次の2点に答えてください。
>     * (a) 変数 `status` に `volatile` を付けずに `-O2` でコンパイルすると、最適化器はどのような理由でどのようなコードへ変形してしまうでしょうか。
>     * (b) マルチコア環境で別スレッドと共有するカウンタ変数に `volatile` を付けただけでは、なぜ安全な同期（排他制御や順序保証）の代わりにならないのでしょうか。
>
> 3. **（次節への伏線：有限個のレジスタへ多数の変数をどう割り当てるか）**
>     本節の最適化で無駄な計算は減りましたが、変数が20個ある関数を物理レジスタが限られたCPU（たとえば利用可能なレジスタが数本〜十数本）で動かすとき、すべての変数を同時にレジスタへは置けません。しかし、「前半でしか使われない変数 `a`」と「後半でしか使われない変数 `b`」であれば、同じ1本のレジスタを使い回せるはずです。コンパイラはどの変数同士が同時に生きているかをどう判定し、レジスタを割り当てているのでしょうか。
