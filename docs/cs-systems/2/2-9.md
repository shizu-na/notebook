### 前節（2-8）の確認問題の解答

前節の最後に提示した3つの問いの解答を確認します。本節では[第2部](../index.md#part-2)の締めくくりとして、コンパイルされたプログラムが実行時にヒープメモリを自動管理する **実行時ランタイムとガベージコレクション（GC）** の内部構造へ進みます。

1. **4頂点閉路 $C_4$ に対する $k = 2$ Chaitin-Briggs と楽観的彩色のトレース：**

    * **(a) 初期次数と潜在的スピル後の縮約順：**
        4頂点閉路 $C_4$（辺：`(a, b)`, `(b, c)`, `(c, d)`, `(d, a)`）では、初期状態ですべての頂点の次数が $\deg(a) = \deg(b) = \deg(c) = \deg(d) = \mathbf{2}$ です。レジスタ本数 $k = 2$ に対して次数が $2$ 未満の頂点が1つもないため、縮約（Simplify）が即座に停止します。ここで潜在的スピル（Potential Spill）として頂点 `a` を選んでスタックへ積みグラフから除くと、残った経路 `b - c - d` で `b` と `d` の次数が `1`（$< 2$）に下がります。以降、`b`（次数1）→ `c`（次数1）→ `d`（次数0）の順に縮約でき、スタックの並び（底 → 頂上）は **`a → b → c → d`** になります（`d` から先に縮約する `a → d → c → b` 等でも同様に完了します）。

    * **(b) 選択・彩色（Select）で実スピルゼロになる過程：**
        スタック頂上から順にポップして `{R1, R2}` の2色を割り当てます。

        1. `d` をポップ：彩色済みの隣接頂点がないため **`d → R1`** とします。
        2. `c` をポップ：隣接する `d` が `R1` のため **`c → R2`** とします。
        3. `b` をポップ：隣接する `c` が `R2` のため **`b → R1`** とします。
        4. 潜在的スピル候補の `a` をポップ：隣接する `b` と `d` の両方が偶然同じ色 **`R1`** になっているため、もう1色の **`R2`** が空いており **`a → R2`** と塗れます。

        以上より **`a, c → R2`、`b, d → R1`** となり、潜在的スピル候補だった `a` を実際にメモリへ退避することなく（実スピルゼロで）2彩色に成功します。

2. **スピルコスト重み付け $\text{cost}/\deg$ と `call` 跨ぎ変数の事前彩色：**

    * **(a) $\text{cost}(v) / \deg(v)$ の比較計算とスピル候補の選択：**

        * **変数 `x`（二重ループ内 $d = 2$、重み $10^2 = 100$）：** 定義1回＋参照1回＝計2回のアクセスがあるため $\text{cost}(x) = 2 \times 100 = 200$ となり、次数 $\deg(x) = 4$ で割ると $\text{cost}(x) / \deg(x) = 200 / 4 = \mathbf{50}$ です。
        * **変数 `y`（ループ外 $d = 0$、重み $10^0 = 1$）：** 定義1回＋参照4回＝計5回のアクセスがあるため $\text{cost}(y) = 5 \times 1 = 5$ となり、次数 $\deg(y) = 2$ で割ると $\text{cost}(y) / \deg(y) = 5 / 2 = \mathbf{2.5}$ です。

        $2.5 < 50$ より、評価値が小さいループ外変数 **`y`** をスピル候補に選ぶべきです。

    * **(b) 事前彩色ノードと干渉辺による callee-saved 自動割当の仕組み：**
        物理レジスタ自身を、あらかじめ自分の色が固定されて縮約もスピルもできない**事前彩色ノード（Precolored Nodes）**として干渉グラフへ加えておきます。関数呼び出し `call foo` をまたいで生存する変数 $v$ に対して、すべての caller-saved レジスタの事前彩色ノードへ干渉辺を張っておけば、グラフ彩色の通常ルールだけで caller-saved レジスタがすべて除外され、自動的に **callee-saved レジスタ（`%rbx, %r12`〜`%r15`）** へ割り当てられます。

3. **Ershov 数による評価順の最適化と JIT における線形走査法：**

    * **(a) `a + (b + (c + d))` の Ershov 数とレジスタ本数の比較：**
        葉ノードはすべて $E(a) = E(b) = E(c) = E(d) = 1$ です。最内側の `c + d` は左右の子の Ershov 数が等しい（$l = r = 1$）ため $E(c + d) = 1 + 1 = \mathbf{2}$ となります。1段上の `b + (c + d)` は左右が異なる（$l = 1,\; r = 2$）ため $E(b + (c + d)) = \max(1, 2) = \mathbf{2}$、最外側の `a + (b + (c + d))` も同様に $\max(1, 2) = \mathbf{2}$ です。左から右へ素朴に評価すると 4 本同時に必要になりますが、Ershov 数の大きい右側から先に評価すると `c + d` を計算して空いたレジスタへ `b`, `a` を順に読み込めるため **2 本** だけで完結します。

    * **(b) JIT で線形走査法が採用される理由と生存区間の穴（Lifetime Hole）の弱点：**
        Chaitin-Briggs のグラフ彩色法は干渉グラフ構築と再彩色に最悪 $O(|V|^2)$ 以上を要するため実行時コンパイル遅延が重すぎますが、**線形走査法**は $O(|V| \log |V|)$ で高速に動作するため JIT で広く採用されます。ただし単純な線形走査法では分岐で変数が一時的に使われない**生存区間の穴（Lifetime Hole）**を連続区間として保守的に扱うため、穴の期間だけ他変数へレジスタを貸し出せずスピルが増えやすい弱点があります。

## 2-9. 実行時メモリ管理とガベージコレクション（GC）

### 1. 動機（Why）：なぜ手動の `malloc` / `free` はバグの温床になり、多くの言語が「自動メモリ管理（GC）」を選ぶのか

[2-1節](2-1.md)から [2-8節](2-8.md)までを通じて、ソースコードが字句解析・構文解析・意味解析・最適化・レジスタ割当を経て高速な機械語へ変換される過程を学びました。しかし、言語処理系の責務はコンパイルが終わった瞬間に完了するわけではありません。プログラムが**実行中（ランタイム）にヒープメモリをどう確保し、使い終わったオブジェクトをいつ安全に解放するか**というメモリ管理の設計が、言語の安全性と性能を大きく左右します。

C 言語や従来の C++ のように、プログラマが手動で `malloc()` と `free()` を対にして呼び出す **手動メモリ管理** では、規模が大きくなるほど次の 3 大バグを避けることが非常に困難になります。

1. **メモリリーク（Memory Leak）：** 使い終わったオブジェクトへ `free()` を呼び忘れ、プロセスが長時間稼働するうちに RAM を食い尽くして停止します。
2. **解放後参照（Use-After-Free：UAF）：** まだ別のポインタが指しているのに先に `free()` してしまい、後からその領域へ別のデータが入った状態で読み書きしてデータ破壊や任意コード実行脆弱性（[5-8節](../5/5-8.md)）を招きます。
3. **二重解放（Double Free）：** 同じポインタへ `free()` を 2 回呼んでヒープ管理構造（フリーリスト）を破壊します。

そこで Java、Go、Python、JavaScript、C#、Ruby などの現代の多くの言語では、実行時ランタイムが「もうプログラムから到達できない不要なオブジェクト（ゴミ＝Garbage）」を自動判定して回収する **ガベージコレクション（GC：Garbage Collection）** を採用しています。

本節では、GC の 2 大アプローチである **参照カウント** と **トレーシング GC（マーク＆スイープ・コピー GC・世代別 GC）** の内部アルゴリズム、そして現代の低遅延 GC を支える **三色マーキングとライトバリア**、さらに GC を使わずに安全性を達成する **Rust の所有権モデル** との設計対比までを整理します。

---

### 2. 具体例と動作イメージ（Toy Model）

アルゴリズムの体系に入る前に、2 つの小さな実験で「参照カウントの落とし穴」と「世代別仮説の威力」を確かめます。

#### 実験A：なぜ「参照カウント」だけでは循環参照（リング）を回収できないのか

オブジェクトごとに「現在いくつのポインタから指されているか」を数える **参照カウント（Reference Counting）** を考えます。

1. 関数内で 2 つのノード `A` と `B` をヒープに確保し、ローカル変数 `p` が `A` を指し、さらに `A.next = B`、`B.next = A` と互いに指し合わせた（循環参照）とします。この時点の参照カウントは **`A: 2`**（`p` と `B` から）、**`B: 1`**（`A` から）です。
2. 関数が終了し、スタック上のローカル変数 `p` が消滅しました。`p` からの参照が消えたため `A` のカウントが $2 \to 1$ に減ります。
3. ところが、プログラムのどこからも `A` と `B` へ辿り着けなくなった（孤立した）にもかかわらず、**`A` のカウントは `1`（`B` から）、`B` のカウントも `1`（`A` から）のまま `0` にならず、メモリリークが発生** します。

この「孤立した循環参照」を見抜くには、局所的なカウントではなく、「スタックや大域変数（**ルート集合：Root Set**）から実際にポインタを辿って到達できるか」を大域的に調べる **トレーシング GC** が必要になります。

#### 実験B：なぜ「ほとんどのオブジェクトは生まれてすぐ死ぬ」性質（世代別仮説）が GC を大きく高速化できるのか

Web サーバが 1 件の HTTP リクエストを処理する場面を想像してください。リクエストをパースするあいだに一時的な文字列や JSON オブジェクトが 10,000 個生成されますが、5 ミリ秒後にレスポンスを返した瞬間、そのうち **9,990 個（99.9%）は即座に不要** になります。一方、起動時に読み込んだ設定オブジェクトやキャッシュなどの長寿オブジェクトは、何時間経っても生き続けます。

この経験則（**弱い世代別仮説：Weak Generational Hypothesis**）を活かし、ヒープを「生まれたての **若世代（Young Generation）**」と「何度も生き残った **旧世代（Old Generation）**」へ分け、普段は小さな若世代だけを掃除すれば、毎回ヒープ全体（数 GiB）を走査せずに 99% のゴミを数ミリ秒で回収できます。

### 3. 構造・アルゴリズム・実装（What）

#### (1) 参照カウント（Reference Counting）の仕組みと長短

**参照カウント** は、各オブジェクトのヘッダに整数カウンタを持ち、ポインタ代入 `x = y` のたびに代入先 `y` のカウントを $+1$、上書きされた旧参照先のカウントを $-1$ し、カウントが `0` になった瞬間にそのオブジェクトを即座に解放する方式です（Python［CPython］の主機構、Swift の ARC、C++ の `std::shared_ptr` 等）。

* **長所：** 不要になった瞬間に**即座に解放される**ため、長い全体停止（Stop-The-World）が起きにくく、実装も単純です。
* **短所：** ① 実験Aの**循環参照を単体では回収できない**（CPython は別途トレーシング型の循環検出 GC を併用、Swift では弱参照 `weak` で開発者が環を断ちます）、② ポインタ代入のたびにカウンタ増減の書き込みが発生し、マルチスレッド環境ではアトミック命令（[4-3節](../4/4-3.md)）と同一カウンタへのキャッシュライン競合（[0-7節](../0/0-7.md)）で性能が大きく落ちます、③ 巨大な木構造の根のカウントが `0` になると連鎖解放で一時停止が起きることがあります。

#### (2) トレーシング GC の基本 3 アルゴリズム

**トレーシング GC（Tracing GC）** は、スタック上の局所変数・CPU レジスタ・大域変数からなる **ルート集合（Root Set）** を出発点として、ポインタ参照の有向グラフを辿り、**到達可能（Reachable）なオブジェクトだけを「生存」とみなし、到達不能なものをすべて一括回収** します（循環参照もルートから到達不能なら確実に回収されます）。基本方式は次の 3 つです（図2-9-1）。

1. **マーク＆スイープ（Mark-and-Sweep）：**

    * **Mark フェーズ：** ルートから DFS / BFS で到達可能な全オブジェクトを辿り、ヘッダのマークビットを `1` に立てます。
    * **Sweep フェーズ：** ヒープ全体を先頭から末尾まで線形走査し、マークが `0` のオブジェクトをフリーリストへ返却し、`1` のマークを次回用に `0` へ戻します。
    * **特徴：** オブジェクトを移動させないためポインタ書き換えが不要ですが、回収後に空き領域が虫食い状になる **外部断片化（[3-4節](../3/3-4.md)）** が進行し、確保速度が低下します。

2. **コピー GC（Copying GC / Cheney のアルゴリズム）：**

    * ヒープを同じ大きさの 2 領域（**From 空間** と **To 空間**）へ半分に分け、普段は From 空間の先端ポインタをずらすだけで高速に新規確保（**バンプポインタ割当：$O(1)$**）します。
    * From 空間が満杯になったら、ルートから到達可能な**生存オブジェクトだけ**を To 空間の先頭から隙間なくコピーして詰め直し（同時にコピー元へ転送アドレスを記して参照ポインタを書き換え）、From と To の役割を入れ替えます。
    * **特徴：** 計算量が「ヒープ全体」ではなく **生存オブジェクト数のみに比例** するため、実験Bのように $10{,}000$ 個中 $10$ 個（$0.1\%$）しか生き残らない若世代ではコピー対象がごくわずかとなり非常に高速で、**外部断片化もゼロ** になります。代償は、利用可能なメモリ空間が半分（50%）に限られる点です。

3. **マーク＆コンパクト（Mark-and-Compact）：**

    * Mark フェーズで生存オブジェクトを特定したあと、同じヒープ領域内で生存オブジェクトを片側へ隙間なく詰め直し（コンパクション）、参照ポインタをすべて更新します。
    * **特徴：** コピー GC のようにメモリを半分遊ばせる無駄がなく、かつ断片化も解消できますが、複数パスの走査とポインタ書き換えを伴うため 1 回あたりの処理コストは最も重くなります（主に長寿の旧世代で使われます）。

#### (3) 世代別 GC（Generational GC）とライトバリア（Remembered Set）

実験Bの「弱い世代別仮説」を実装したのが、JVM（HotSpot）や V8（JavaScript）で中核となる **世代別 GC** です（図2-9-2左）。

* **若世代（Young Generation：Eden ＋ Survivor 空間）：** 新しいオブジェクトはすべて Eden にバンプポインタで高速確保され、満杯になると **Minor GC（コピー GC）** が走ります（新規割当用の Eden と、生存オブジェクトの退避に使う 2 つの Survivor 空間［From/To］に分けることで、単純な 2 分割より空間の無駄を小さく抑えています）。実験Bのように大部分のオブジェクトはその場で回収され、数回の Minor GC を生き残った少数のオブジェクトだけが旧世代へ **昇格（Promotion）** します。
* **旧世代（Old Generation）：** 長寿オブジェクトが格納され、ここが満杯になったときだけ低頻度の **Major / Full GC（マーク＆スイープ／コンパクト）** が走ります。

ここで 1 つ見落としやすい難問が生じます。Minor GC で若世代だけを掃除するとき、**「旧世代にあるオブジェクト `oldObj` が、若世代のオブジェクト `youngObj` を指している（旧 $\to$ 若の世代間参照）」** 場合、もし旧世代を一切スキャンしなければ `youngObj` を誤ってゴミとして回収してしまいます。かといって毎回巨大な旧世代全体をスキャンしては世代別 GC の意味がなくなります。

この問題を解決するのが **ライトバリア（Write Barrier）＋ 記憶集合（Remembered Set / Card Table）** です。コンパイラはポインタの書き込み `oldObj.field = youngObj` を行う機械語の直後に数命令の小さなフック（ライトバリア）を自動挿入し、「旧世代から若世代への参照が書かれたメモリ区画（512 B 単位の**カードテーブル**）」にダーティ印（`1`）を付けます。Minor GC の際は旧世代全体ではなく**ダーティ印の付いたわずかなカードだけ**を追加ルートとして調べれば、安全かつ高速に若世代だけを回収できます。

#### (4) 停止時間（STW）を削る「三色マーキング（Tri-color Marking）」と並行 GC

初期のトレーシング GC は、GC が動いているあいだアプリケーションの全スレッドを一時停止させる **STW（Stop-The-World）** 方式でした。ヒープが数十 GiB に達すると STW が数秒間続き、Web API のタイムアウトやゲームのコマ落ちを引き起こします。

現代の低遅延 GC（Go の並行 GC、JVM の G1 / ZGC / Shenandoah 等）は、**アプリケーションスレッド（ミューテータ）を動かしたまま、裏側で並行してマークを進める並行 GC（Concurrent GC）** を採用しています。その理論的基盤がダイクストラらの **三色抽象（Tri-color Marking）** です（図2-9-2右）。

全オブジェクトを次の 3 色に分類してマーキングを進めます。

* **白（White）：** 未訪問（最後まで白のまま残ればゴミとして回収される）。
* **灰（Gray）：** 到達済みだが、そのオブジェクトが持つ子ポインタの探索がまだ終わっていない（作業キューに入っている状態）。
* **黒（Black）：** 到達済みかつ、すべての子ポインタを訪問し終えた（完了）。

マーキング中にアプリケーションが並行してポインタを書き換えると、「**すでに完了した黒オブジェクト `A` から未訪問の白オブジェクト `C` へ新しい参照を張り、同時に灰オブジェクト `B` から `C` への元の参照を消す**」操作が起きた瞬間に、生きているはずの `C` が誰からも辿られず白のまま誤回収されるバグが生じます。これを防ぐため、並行 GC でもポインタ書込み時に **ライトバリア** を挟み、新しく参照された白（挿入バリア：Dijkstra 方式）または参照を切られた白（削除バリア：SATB 方式）を強制的に **灰（探索キュー）へ塗る** ことで、生きている白オブジェクトが探索経路から取り残される事態を防ぎ、STW 停止時間を **1 ミリ秒未満** まで抑えています。

> **【コラム：GC も手動 `free()` も不要にした第 3 の道：Rust の所有権と RAII】**
>
> これまで「手動 `free()` は速いが危険（C/C++）」「GC は安全だがランタイムのメモリ消費・STW 遅延がある（Java/Go）」という二項対立が一般的でした。この対立に対する第 3 の選択肢が、C++ の **RAII（Resource Acquisition Is Initialization：変数のスコープ終了時にデストラクタで自動解放）** をコンパイル時の型システムへ統合した **Rust の所有権（Ownership）と借用（Borrowing）モデル（[2-5節](2-5.md)）** です。
>
> Rust では「すべてのヒープ値には常にただ 1 人の所有者（Owner）が存在し、所有者がスコープを抜けた瞬間にコンパイラが自動的に `free` 相当の解放コードを挿入する」という規則をコンパイル時に静的に検証します。これにより、**実行時の GC オーバーヘッド（STW やメモリ余剰）を伴わずに、Use-After-Free・Double Free・データ競合をコンパイル時に排除し、通常のスコープ内ヒープ確保における解放忘れ（メモリリーク）も防げます**（ただし循環参照を含むグラフ構造では、参照カウント `Rc`/`Arc` だけではリークし得るため、弱参照 `Weak` やインデックス配列を使い分ける設計が必要です）。

### 4. 限界と補正（Critique & Adaptation）

#### (1) GC の 3 すくみ（スループット・一時停止時間・メモリ消費量）

GC の設計には、次の 3 つをすべて同時に最大限まで満たすことはできない **GC トリレンマ** が存在します。

* **スループット（CPU 効率）：** ライトバリアを減らして STW でまとめて処理するほど総スループットは上がりますが、1 回の停止時間が長くなります。
* **低遅延（短い一時停止時間）：** 並行 GC（ZGC / Go GC）で STW を $1\text{ ms}$ 未満に抑えるには、ライトバリア／リードバリアや並行マーク用スレッドの CPU 消費が増えます。
* **省メモリ（フットプリント）：** GC はヒープ使用量が上限に近づくほど頻繁に起動して CPU を消費するため、実効データの **2 倍〜3 倍のヒープ余裕** を与えないと急激に性能が劣化します（逆にコンテナのメモリ上限［cgroup の `memory.max` 等］を小さく絞りすぎると GC スラッシングが起きます）。

#### (2) GC は「メモリ」しか管理しない（ファイル記述子・DB 接続の明示解放）

GC が自動回収してくれるのはあくまで **ヒープメモリ** です。ファイル記述子（FD：[5-2節](../5/5-2.md)）、ネットワークソケット、データベース接続といった OS カーネル側の有限資源の解放を GC のファイナライザ（回収時フック）任せにすると、メモリに余裕があるあいだは GC が走らず、先に FD 上限（`EMFILE`）に達してシステムがクラッシュします。

* **補正：** メモリ以外の OS 資源は必ず Java の `try-with-resources`、Python の `with`、Go の `defer`、C# の `using` のように、**スコープ脱出時に決定的かつ即座に `close()` する構文** で明示解放するのが実務上の基本です。

>     * (a) ヒープ上にノード `A`, `B`, `C` があり、スタック変数 `p` が `A` を指し、さらに `A → B → C → B`（`B` と `C` が相互参照）という参照関係があるとします。`p` がスコープを抜けて消滅した直後に、① `A`, `B`, `C` の参照カウントがそれぞれいくつになり、どのノードが解放されてどのノードがリークするかを追ってください。② また、トレーシング GC を使わずに参照カウント方式のままこのリークを防ぐには、`B → C` と `C → B` の参照をどう変更すればよいですか。
>     * (b) 総容量 $200\text{ MiB}$ の領域に対して、① 生存率 $1\%$ の若世代、② 生存率 $80\%$ の旧世代、それぞれへ**コピー GC** を適用するとどのような問題（利用可能空間やコピー量）が生じるか比較し、世代別 GC が若世代にコピー GC、旧世代にマーク＆スイープ／コンパクトを組み合わせる理由を説明してください。
>
> 2. **（並行 GC の三色マーキング誤回収トレースと、外部資源管理の誤解検証）**
>
>     * (a) 並行 GC のマーク途中で、オブジェクトが `A（黒）→ B（灰）→ C（白）` と繋がっているとします。アプリケーションスレッドが並行して「① `A.ref = C` を書き込む → ② `B.ref = null` で元の参照を消す」を実行した直後に GC がマークを完了すると、もし**ライトバリアが無効**だった場合、`C` はどのような扱いになりますか。また、ライトバリアを有効にするとどの色遷移によってこのバグが防がれますか。
>     * (b) ある開発者が「Java や Python には GC があるから、開いたファイルや DB 接続を閉じ忘れても、オブジェクトが不要になれば GC が自動で閉じてくれるので障害にはならない」と考えています。本節 4-(2) の内容に基づき、なぜこの考えが誤りかを説明し、実務上の正しい対処法を述べてください。
>
> 3. **（[第3部](../index.md#part-3)への伏線：単一プロセス内の安全性の先にある「複数プロセス間の隔離」）**
>     本節までで、コンパイラとランタイム（GC や所有権）によって 1 つのプログラム内部のメモリ安全性を高める仕組みが整いました。しかし、1 台のコンピュータ上で複数の独立したプログラム（エディタ、Web ブラウザ、C 言語プログラムなど）を同時に動かすとき、もし OS による保護がなく各アプリが CPU や物理メモリ・ディスクを直接操作できるとしたら、どのような破綻が起き得るでしょうか（メモリ・CPU・I/O デバイスの 3 つの観点から考えてみてください）。また、それらをソフトウェアの約束事だけでなくハードウェアレベルで強制するには、CPU 側にどのような機能が必要になるでしょうか。
