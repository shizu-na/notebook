### 前節（2-7）の確認問題の解答

前節の最後に提示した3つの問いの解答を確認します。前節の到達定義解析（前向きデータフロー）とちょうど逆向きにデータフロー方程式を解く**生存解析**から、本節のレジスタ割当へ進みます。

1. **基本ブロック分割・到達定義解析と定数伝播の可否判定：**

    * **(a) 基本ブロック分割と `GEN` / `KILL` / `IN` / `OUT`：**
        リーダの3規則より、1行目（先頭）、4行目（条件分岐の直後）、5行目（ジャンプ先ラベル `L1`）の3箇所がリーダになり、3つの基本ブロックへ分割されます（辺は `B1 → B2`, `B1 → B3`, `B2 → B3`）。定義 `d1, d2, d3` に対する各集合は次の通りです。

        | ブロック | 命令範囲 | 先行 $\text{pred}$ | $\text{GEN}$ | $\text{KILL}$ | $\text{IN}$ | $\text{OUT}$ |
        | :---: | :--- | :---: | :---: | :---: | :---: | :---: |
        | **B1** | 1〜3行目 | $\emptyset$ | $\{d_1, d_2\}$ | $\{d_3\}$ | $\emptyset$ | $\{d_1, d_2\}$ |
        | **B2** | 4行目 | $\{B1\}$ | $\{d_3\}$ | $\{d_2\}$ | $\{d_1, d_2\}$ | $\{d_1, d_3\}$ |
        | **B3** | 5〜6行目 | $\{B1, B2\}$ | $\emptyset$ | $\emptyset$ | $\{d_1, d_2, d_3\}$ | $\{d_1, d_2, d_3\}$ |

    * **(b) 5行目の `a` と6行目の `x` に対する定数伝播の可否：**

        * **5行目の `a`（置換可能）：** `IN[B3]` に含まれる `a` の定義は `d1`（`a = 5`）の1つだけであるため、安全に定数 `5` へ置換できます（定数畳み込みで `y = 6` になります）。
        * **6行目の `x`（置換不可）：** `IN[B3]` には `d2`（`x = 10`）と `d3`（`x = 20`）の異なる2つの定義が到達しており、実行時の `cond` によって値が変わるため定数へ置換できません。

2. **エイリアシング・`restrict` と未定義動作 UB による最適化の診断：**

    * **(a) 関数 `f` の `*p` 置換と `restrict` の効果：**
        通常のポインタ引数では呼び出し元が `f(&x, &x)` のように `p == q` を渡す可能性（**エイリアシング**）を排除できず、`*q = 2;` が `*p` を上書きし得るため、コンパイラは `*p` を定数 `1` へ置き換えられません（毎回メモリから再ロードします）。引数へ `restrict`（`int *restrict p, int *restrict q`）を付けると `p` と `q` の指す領域が重ならないことが保証されるため、`*p` を定数 `1` へ安全に置き換えられます。

    * **(b) 関数 `g` で `if (p == NULL)` が削除される理由：**
        1つ目の文 `int v = *p;` でポインタ `p` を逆参照しているため、もし `p == NULL` だったならその時点で C 言語の**未定義動作（UB）**が発生しています。最適化器は「UB は実行時に起きない」と仮定するため、2つ目の文に到達した時点で `p` は必ず非 `NULL` であると推論し、`if (p == NULL) return -1;` を到達不能なデッドコードとして削除してしまいます。

3. **ループ不変コード移動 LICM の反例と `volatile` の限界：**

    * **(a) `100 / k` の無条件移動が壊れる反例：**
        入力 **`(n, k) = (0, 0)`**（一般に `n <= 0` かつ `k = 0`）が反例です。元のコードでは `i < 0` が初回から偽なのでループ本体が1回も実行されず、除算は起きずに正常終了します。しかし `100 / k` を無条件にループ直前へ移動すると、`n = 0` のときでも必ず `100 / 0` が実行されてしまい、ゼロ除算例外（クラッシュ）を起こして振る舞いが壊れます。

    * **(b) `volatile` がマルチスレッド `count++` の同期に不十分な2つの理由：**
        `volatile` が抑止するのはコンパイラの最適化だけであり、ハードウェア側で起きる次の2つを防げないためです。

        1. **メモリ順序の逆転：** マルチコア CPU のキャッシュやストアバッファ・アウトオブオーダ実行によって、別コアから観測される読み書きの順序が入れ替わる現象を止められません。
        2. **不可分性（アトミック性）の欠如：** `count++` の「読出し → 加算 → 書戻し」の途中で別コアが割り込んで更新が失われる競合を防げません。

## 2-8. コード最適化②：生存解析・干渉グラフとグラフ彩色によるレジスタ割当

### 1. 動機（Why）：なぜ「スタック機械の遅さ」を解消する鍵がグラフ理論の彩色問題にあるのか

[2-6節](2-6.md)で組み立てたスタック機械方式のコード生成器は、計算途中の値をすべてメモリ上のスタックへ読み書きしていました。しかし [0-7節](../0/0-7.md)で確認した通り、CPU内部の汎用レジスタへのアクセス（$< 0.5\text{ ns}$）は、主記憶へのアクセスに比べて大幅に高速であり、L1キャッシュと比べてもレイテンシが短く命令数も削減できます。したがって、コンパイラが生成する機械語の性能を左右する最も重要な最適化の1つが、**「可能な限り多くの変数と一時値を、メモリではなくCPUの物理レジスタへ配置する」**という **レジスタ割当（Register Allocation）** です。

ところが、現実のプログラムには1つの関数の中に数十個もの局所変数や中間値（仮想レジスタ）が登場するのに対し、CPUが持つ物理レジスタの本数は限られています（x86-64の汎用レジスタは16本、スタックポインタ等を除くと自由に使えるのはさらに少なくなります）。

ここで発想の転換が起きます。関数の中に変数が20個あっても、**20個すべてが「同じ瞬間に」値を保持している必要はほとんどありません**。関数の前半でしか使われない変数 `a` と、後半で初めて計算される変数 `d` であれば、同じ1本の物理レジスタ `%rax` を時間差で使い回しても計算結果は壊れません。

つまりレジスタ割当は、次の2つの問いに分解されます。

1. **どの変数とどの変数が「同じ瞬間に生きていて、同じレジスタを共有できないか」をどう特定するか（生存解析と干渉グラフ）。**
2. **その制約を満たしながら、限られた $k$ 本の物理レジスタへどう割り当て、どうしても入りきらない変数だけをどうメモリへ逃がすか（グラフ彩色とスピル）。**

本節では、[第2部](../index.md#part-2)の締めくくりとして、データフロー解析と離散数学のグラフ理論が実用のコンパイラ最適化へ直結する仕組みを、小さな手計算例から順に組み立てます。

### 2. 具体例と動作イメージ（Toy Model）

一般的なアルゴリズムに入る前に、5個の変数 `a, b, c, d, e` を使う6行の3番地コードを題材に、後ろ向きに生存区間を調べ、**3本のレジスタ（`R1, R2, R3`）だけでメモリアクセスゼロに収まる**過程を手計算で確かめます。

#### 実験A：5変数のコードから生存区間と干渉グラフを作る

次の6行のコード（1つの基本ブロック）を考えます。

```text
1: a = 1
2: b = a + 2
3: c = b + 3
4: d = a + c
5: e = d + b
6: return e
```

ある地点で変数 $x$ が **生存している（live）** とは、「その地点で $x$ が持っている値が、**将来のどこかの命令で上書きされる前に読み出される可能性がある**」ことを意味します。変数がいつまで生きているかは「未来の参照」から決まるため、**コードの末尾（6行目）から先頭（1行目）へ向かって後ろ向きに**辿ります。

各命令 $s$ の直前（`IN`）と直後（`OUT`）で生存している変数の集合は、末尾から1行ずつ遡りながら次の式で機械的に計算できます（一般のCFGへの拡張は3-(1)で定式化します）。

$$
\text{OUT}[s] = \text{IN}[\text{次の命令}], \qquad \text{IN}[s] = \text{use}[s] \cup \bigl(\text{OUT}[s] \setminus \text{def}[s]\bigr)
$$

この式を6行目から1行目へ順に適用してみましょう。

| 行 | 命令 | 参照 (`use`) | 定義 (`def`) | 命令直前 `IN` | 命令直後 `OUT` | この行で生じる干渉（`def` と `OUT` の他変数） |
| :-: | :--- | :---: | :---: | :---: | :---: | :--- |
| 6 | `return e` | `{e}` | `{}` | `{e}` | `{}` | なし |
| 5 | `e = d + b` | `{b, d}` | `{e}` | `{b, d}` | `{e}` | なし |
| 4 | `d = a + c` | `{a, c}` | `{d}` | `{a, b, c}` | `{b, d}` | **`(b, d)`** |
| 3 | `c = b + 3` | `{b}` | `{c}` | `{a, b}` | `{a, b, c}` | **`(a, c)`, `(b, c)`** |
| 2 | `b = a + 2` | `{a}` | `{b}` | `{a}` | `{a, b}` | **`(a, b)`** |
| 1 | `a = 1` | `{}` | `{a}` | `{}` | `{a}` | なし |

この表を眺めると、次の特徴が見えてきます（図2-8-1。図中の「次数」とは、その頂点に繋がる辺の本数＝同時に生きる相手の個数を表します）。

* 3行目の直後では `{a, b, c}` の3変数が**同時に生存**しているため、`a, b, c` は互いに異なる3本のレジスタへ置かなければなりません（三角形の干渉）。
* 一方、`a` と `c` は4行目で読み出されたのを最後に二度と使われないため、4行目で生まれる **`d` は `a` とも `c` とも同時に生きていません**。`d` が同時に生きている相手は `b` だけです。
* さらに5行目で生まれる **`e` は誰とも同時に生きていない**ため、すでに役目を終えた `b` や `d` のレジスタをそのまま上書きして使えます。

### 3. 構造・アルゴリズム・実装（What）

#### (1) 生存解析（Liveness Analysis）：後ろ向きデータフロー方程式

分岐やループを含む一般の制御フローグラフ（CFG）上で全変数の生存集合を求めるには、前節（[2-7節](2-7.md)）の到達定義解析と**ちょうど逆向き（後ろ向き）のデータフロー方程式**を解きます。

各基本ブロック $B$ に対し、次の2つの静的な集合を用意します。

* **$\text{USE}[B]$：** ブロック $B$ の中で、定義（代入）される**より前**に参照される変数の集合です。
* **$\text{DEF}[B]$：** ブロック $B$ の中で定義（代入）される変数の集合です。

ブロック $B$ の出口で生存している変数の集合 $\text{OUT}[B]$ は、後続ブロック $\text{succ}(B)$ のいずれかの入口で生存している変数の和集合になります。また、入口で生存している集合 $\text{IN}[B]$ は、出口から遡って $B$ 内で上書きされた変数を除き、$B$ 内で先に参照される変数を加えたものです。

$$
\text{OUT}[B] = \bigcup_{S \in \text{succ}(B)} \text{IN}[S], \qquad \text{IN}[B] = \text{USE}[B] \cup \bigl(\text{OUT}[B] \setminus \text{DEF}[B]\bigr)
$$

前節と同様に、すべての $\text{IN}[B] = \emptyset$ から始めて不動点へ収束するまで反復計算することで、ループを含む任意のCFGでも厳密な生存集合が求まります。基本ブロックの境界での `OUT[B]` が決まれば、あとは実験Aのように各ブロック内部を末尾の命令から1行ずつ遡って命令単位の `OUT` を計算します。

#### (2) 干渉グラフと $k$-彩色問題への帰着（NP完全性）

生存解析の結果から、辺に向きのないグラフ（**無向グラフ**）である **干渉グラフ（Interference Graph）** $G = (V, E)$ を構築します。

* **頂点集合 $V$：** 関数内のすべての変数（仮想レジスタ）です。
* **辺集合 $E$：** ある命令で変数 $x$ が定義（`def`）されたとき、その命令の直後 $\text{OUT}$ に生存しているすべての変数 $y \neq x$ との間に無向辺 $(x, y)$ を張ります。理由は明快で、定義命令が $x$ のレジスタへ新しい値を書き込んだ瞬間に、その直後も生きている変数 $y \in \text{OUT}$ と同じレジスタだと $y$ の値を上書きして壊してしまうためです（※代入命令 `x = y` の場合は値が同一なので辺 $(x, y)$ を省く最適化もあります）。

なお、実験Aのように分岐やループを含まない単一の基本ブロックでは、各変数の生存区間が命令番号の数直線上で1本の連続区間になるため、干渉グラフはグラフ理論における**区間グラフ（Interval Graph）**となり多項式時間で最適彩色が求まります。しかし、分岐やループを含む一般の関数では生存区間が複数箇所へ飛び地状に広がるため、干渉グラフは一般の無向グラフになります。

ここで、CPUが使える物理レジスタの本数を $k$ 本とします。各変数へ物理レジスタを重複なく割り当てる問題は、**「同時に使われるため同じレジスタを共有できない変数同士を線で結び、隣同士が必ず異なる色になるように $k$ 色で塗り分ける地図の塗り分けパズル」**、すなわちグラフ理論の **$k$-彩色問題（Graph $k$-Coloring）** に帰着されます。

ところが計算理論において、一般のグラフが $k$ 色（$k \ge 3$）で彩色可能かを判定する問題は **NP完全問題**（変数の数が増えると厳密な最適解を探す計算時間が爆発的に増えてしまう難問）であることが証明されています。つまり、変数が何百個もある大きな関数に対して「常に最良の彩色を厳密に求める高速な（多項式時間の）アルゴリズム」は、計算理論上の未解決予想 $\text{P} \neq \text{NP}$ のもとで存在しません。そこで実用コンパイラでは、厳密最適ではないが実務上ほぼ最良の解を高速に見つける実用的な近似手順（**ヒューリスティック**）を用います。

#### (3) Chaitin-Briggs のアルゴリズム（縮約・選択・スピル）

GCC の IRA/LRA をはじめとするグラフ彩色ベースのアロケータの理論的基礎となっているのが、グレゴリー・チャイティン（Gregory Chaitin, 1981年）が提案し、プレストン・ブリッグス（Preston Briggs）らが改良した **縮約（Simplify）と選択（Select）に基づくグラフ彩色アルゴリズム** です。

このアルゴリズムの核心は、次の簡潔なグラフ理論の補題にあります。

> **【縮約の補題】** 干渉グラフ $G$ の中に、隣接する頂点数（次数）が $k$ 未満（$\deg(v) < k$）である頂点 $v$ が存在するとする。このとき、$v$ を一時的に取り除いた残りのグラフ $G \setminus \{v\}$ が $k$ 色で彩色可能であれば、元のグラフ $G$ も必ず $k$ 色で彩色可能である。

理由は1行で分かります。$v$ の隣にいる頂点は最大でも $k - 1$ 個しかないため、残りのグラフをどう $k$ 色で塗ったとしても、$v$ を元へ戻したときに**少なくとも1色は隣と被らない空き色が必ず残っている**からです。

これを繰り返す手順は次の4フェーズで進みます（図2-8-2）。

1. **Build（構築）：** 生存解析を行い、干渉グラフを構築します。
2. **Simplify（縮約）：** 次数が $k$ 未満の頂点 $v$ を1つ見つけ、グラフから一時的に削除して**スタックへ積みます**。頂点を1つ消すと隣接頂点の次数が1ずつ減るため、連鎖的に他の頂点も次数 $< k$ になっていきます。グラフが空になるまで繰り返します。
3. **Potential Spill（潜在的スピル）：** まだグラフに頂点が残っているのに、**すべての残存頂点の次数が $k$ 以上**になって縮約が止まった場合、メモリへ逃がしても影響が最も小さそうな頂点 $u$ を1つ選び、スピル候補としてスタックへ積んでグラフから取り除き、Simplify へ戻ります（「今は色が足りなさそうだが、塗り戻し時に隣同士が同じ色を使っていれば空き色が出るかもしれないので、本当にメモリへ追い出すかは最後に塗るまで保留にする」のが Briggs の楽観的彩色です）。
4. **Select（選択と彩色）：** スタックの頂上から頂点を1つずつポップしてグラフへ戻しながら、すでに塗られた隣接頂点と重複しない色（レジスタ）を割り当てます。

    * すべての頂点に色を塗れれば**割当成功**です。
    * もしある頂点 $u$ に塗れる空き色が1色もなかった場合（**Actual Spill：実スピル**）、変数 $u$ をスタックフレーム（メモリ）へ割り当て、$u$ の定義直後にストア命令、参照直前にロード命令を挿入したコードへ書き換えて、最初から（Buildから）やり直します。

実験Aの5変数グラフに対し、レジスタ数 $k = 3$（`R1, R2, R3`）で実行してみます。初期状態では `b` の次数は `3`（`a, c, d` と隣接）で $3 \not< 3$ ですが、まず次数 `0` の `e` と次数 `1` の `d` を取り除くと、辺 `(b, d)` が消えて **`b` の次数が `3 → 2`（$< 3$）へ下がります**。これにより図2-8-2左の通り **`e → d → a → c → b`** の順に全頂点を縮約でき、スタックから戻しながら彩色することで **`b, e → R1`、`c, d → R2`、`a → R3`** というメモリアクセスゼロの割当が得られます。

一方、レジスタ数を $k = 2$（`R1, R2`）へ減らすと、`e, d` を除いた後の三角形 `{a, b, c}` で全頂点の次数が $2 \not< 2$ となり詰まるため、1変数をスピルしてメモリへ退避します。ここでは2〜5行目にまたがって生存し最も次数が高い（次数3）変数 **`b`** をメモリスロット `[slot_b]` へスピルしてコードを書き換えます（図2-8-2右）。

```text
# b をメモリスロット [slot_b] へスピルした書き換え後
1:  a = 1
2a: t_b1 = a + 2
2b: store t_b1 -> [slot_b]   # 定義直後にメモリへ退避
3:  c = t_b1 + 3             # 直後の参照は t_b1 をそのまま利用（直後に t_b1 は終了）
4:  d = a + c                # ここで a, c が終了し、b はメモリ上にある
5a: t_b2 = load [slot_b]     # 離れた5行目の参照直前にメモリから復元
5b: e = d + t_b2
6:  return e
```

書き換え後の各行で後ろ向き生存解析を検算すると、各命令直後の生存集合は順に `1: {a}`、`2a: {a, t_b1}`、`2b: {a, t_b1}`、`3: {a, c}`、`4: {d}`、`5a: {d, t_b2}`、`5b: {e}`、`6: {}` となり、**最大同時生存数が 3 から 2 へ減少**しています。干渉辺は `(a, t_b1)`, `(a, c)`, `(d, t_b2)` の3本だけになり、再彩色によって **`a, d, e → R1`、`t_b1, c, t_b2 → R2`** の2色割当に成功します。なお、ここで `b` ではなく3〜4行目のごく短い区間しか生きていない `c` をスピルしてしまうと、書き換え後も `a, b` と一時変数の3変数が同時生存したまま残り干渉が減らないという落とし穴があります（このように短い生存区間をスピルしても干渉解消に繋がらないため、長い生存区間や高次数の変数を優先してスピル対象に選びます）。

なお、実用アルゴリズムではさらに **合体（Coalescing）** という工夫も組み込みます。コード中に `x = y` というコピー命令があり、かつ `x` と `y` の間に干渉辺がなければ、2つの頂点を1つに合体させて**同じ物理レジスタを割り当て、`mov` 命令そのものを消去する**ことができます。

> **【コラム：式の評価順序と必要レジスタ数（Ershov 数 / Sethi-Ullman の考え方）】**
>
> [2-6節](2-6.md)のコラムで、「C言語は `g() + h()` の左右どちらを先に評価するかを規定しておらず、コンパイラが最適化しやすい順番を選べる」と述べました。その代表的な恩恵の1つが、**評価順序の工夫による必要レジスタ数の削減**です。
>
> 標準的なロード・ストア型CPU（各変数をまずレジスタへ読み込んでから演算する前提）で、右へ深く入れ子になった加算式 **`a + (b + (c + d))`** を考えます。
>
> * **左（軽い側）から右へ素朴に評価すると：** まず `a` を `R1`、`b` を `R2`、`c` を `R3`、`d` を `R4` へ読み込み、奥から順に `R3 = R3 + R4` → `R2 = R2 + R3` → `R1 = R1 + R2` と足し合わせるため、**合計4本**のレジスタを同時に消費します。
> * **右（深い・重い側）から先に評価すると：** まず `c` を `R1`、`d` を `R2` へ読んで `R1 = R1 + R2`（`c + d`）を計算します。この時点で `R2` が空くため、そこへ `b` を読み込んで `R1 = R2 + R1`（`b + (c + d)`）を計算し、再び空いた `R2` へ `a` を読み込んで `R1 = R2 + R1` を計算します。これにより、**ちょうど2本**のレジスタだけで完結します（必要レジスタ数が4本から2本へ半減します）。
>
> このように、ASTの各部分木に「その部分木の計算に必要な最小レジスタ数（**Ershov数**／Sethi-Ullman数）」をボトムアップに計算しておき、**常に必要なレジスタ数が多い側（重い側）の子から先に評価する**手法（Sethi-Ullman アルゴリズム）によって、スピルを最小限に抑えることができます。標準ロード・ストアモデルにおける Ershov 数 $E(v)$ は次の再帰式で定まります（葉ノードは $E(v) = 1$、左右の子の Ershov 数を $l, r$ とします）。
>
> $$
> E(v) = \begin{cases} \max(l, r) & (l \neq r \text{ のとき}) \\ l + 1 & (l = r \text{ のとき}) \end{cases}
> $$
>
> `a + (b + (c + d))` へ当てはめると、葉はすべて $E(a)=E(b)=E(c)=E(d)=1$ です。最内側の `c + d` は $l = r = 1$ なので $E(c+d) = 1 + 1 = 2$ となります。その1段上の `b + (c + d)` は $l = 1,\; r = 2$（左右が異なる）なので $E(b+(c+d)) = \max(1, 2) = 2$、最外側の `a + (b + (c + d))` も $l = 1,\; r = 2$ より $E(a+(b+(c+d))) = \max(1, 2) = \mathbf{2}$ となり、式全体が2本で評価できることが正確に導かれます。
>
> なお計算理論上、**木（AST）に対しては線形時間で最小レジスタ数の評価順序が求まりますが、共通部分式を共有する DAG（有向非巡回グラフ）へ一般化した瞬間に問題は NP完全になる**ことが知られています（**Bruno-Sethi の定理**、1976年）。また、現代のアウトオブオーダ実行CPU（[0-6節](../0/0-6.md)）はISA上の論理レジスタよりはるかに多い物理レジスタファイル（数百本）とレジスタリネーミングを備えていますが、論理レジスタ不足による不要なスピル命令（メモリアクセス）の発生自体を抑える意義は依然として大きく残っています。

### 4. 限界と補正（Critique & Adaptation）

理論上のグラフ彩色を現実のCPUや多様な実行環境へ適用すると、次の3つの現実的な制約と補正が現れます。

#### (1) 物理レジスタ固有の制約（事前彩色と `call` をまたぐ生存区間）

グラフ彩色の基本モデルでは「どの色（レジスタ）も完全に対等」と仮定しています。しかし現実のx86-64やRISC-VのABI（[1-3節](../1/1-3.md)）では、特定のレジスタに特別な役割が固定されています。

* 関数の第1引数は `%rdi`、返り値は `%rax`、符号あり除算命令 `idivq` の入力・出力は `%rax` と `%rdx` に固定されています。
* 関数呼び出し `call foo` を実行すると、caller-saved レジスタ（`%rax, %rcx, %rdx, %rsi, %rdi, %r8`〜`%r11`）の中身がすべて破壊されます。

コンパイラはこの現実の制約を、グラフ彩色の枠組みへ統合しています。

1. **事前彩色ノード（Precolored Nodes）：** 物理レジスタ自身を「あらかじめ自分の色が塗られていて、スピルも縮約もできない特別な頂点」として干渉グラフへ入れておきます。
2. **`call` 命令をまたぐ変数の自動振り分け：** たとえば `%rax` の色が固定された頂点をグラフへ混ぜて `call` をまたぐ変数 $v$ と辺で結んでおけば、「隣と同じ色は塗れない」という通常ルールだけで自動的に `%rax` を避けられます。同様に、すべての caller-saved レジスタの事前彩色ノードへ干渉辺を張ることで、彩色アルゴリズムが自動的に **callee-saved レジスタ（`%rbx, %r12`〜`%r15`）**へ $v$ を割り当ててくれます（[1-3節](../1/1-3.md)のABIの役割分担が、グラフ彩色によって自動的に実現されます）。

#### (2) スピル候補の選び方（ループ深度による重み付け）

縮約が詰まってスピル候補を1つ選ばなければならないとき、単純に「次数が最大の頂点」を選んでしまうと、100万回回る多重ループの最内側で毎周参照される変数をメモリへ追い出してしまい、実行速度が大きく低下する恐れがあります。

そのため実用コンパイラでは、各変数 $v$ について「ループのネスト深さ $d$ にある参照・定義ほど $10^d$ 倍の重みを付けた総アクセス回数（**スピルコスト** $\text{cost}(v)$）」を見積もり、

$$
\frac{\text{cost}(v)}{\deg(v)}
$$

が**最も小さい頂点**（「あまり頻繁に使われないのに、多くの他変数と干渉して邪魔をしている変数」）を優先的にスピル候補へ選ぶヒューリスティックで補正します。

#### (3) グラフ彩色の計算コストと、線形走査法（Linear Scan）・現代の実装

Chaitin-Briggs のグラフ彩色は高品質な機械語を生成しますが、干渉グラフの構築と反復再彩色に最悪 $O(|V|^2)$ 以上の時間とメモリを消費します。コンパイル時間に余裕があるAOTコンパイラの最適化ビルド（GCC の IRA/LRA による `-O2`/`-O3` 等）では有効ですが、**プログラムの実行中に数ミリ秒以内で機械語を生成しなければならない JITコンパイラ（[2-1節](2-1.md)の JVM HotSpot や V8 等）**では重すぎます。

この限界に対する補正として広く採用されているのが、**線形走査レジスタ割当（Linear Scan Register Allocation）** です（図2-8-3）。

* **仕組み：** 複雑な干渉グラフを作らず、各変数の生存区間を1次元の命令番号上の区間 `[start, end]` として単純に表現します。区間を `start`（開始位置）の昇順に並べ、先頭から1回なめるだけ（$O(|V| \log |V|)$）で、現在アクティブな区間集合に空きレジスタを貪欲に割り当てます。
* **スピル判定：** アクティブな区間が $k$ 本を超えたら、最も終了位置 `end` が遠くにある区間を1本選んでスピルします。

単純な線形走査法は、分岐やループの途中で変数が一時的に使われない区間（**生存区間の穴：Lifetime Holes**）があっても `[start, end]` の1本の連続区間として穴を潰して保守的に扱うため、その間に別変数へレジスタを貸し出せずグラフ彩色より精度が数%ほど劣る場合があります。しかし、**割当の実行速度が数倍〜10倍以上速い**ため、JITコンパイラやデバッグ時の高速コンパイル（最適化なし `-O0` や軽量最適化 `-O1`）の標準手法として定着しています。また、現代の **Clang/LLVM のデフォルト割当器（`RAGreedy`）** は、グラフ彩色ではなく、この線形走査・区間ベースのアプローチを優先度キューと区間分割で高度化した方式を採用しています（詳細は下記コラム）。

> **【コラム：実コンパイラのレジスタ割当（GCC IRA vs LLVM `RAGreedy`）と SSA 干渉グラフの弦グラフ定理】**
>
> 現代の2大C/C++コンパイラである GCC と Clang/LLVM は、レジスタ割当に異なるアプローチを採用しています。
>
> * **GCC（IRA / LRA）：** 領域ベース（ループ階層ごと）に Chaitin-Briggs 系のグラフ彩色を行う **IRA（Integrated Register Allocator）** と、命令固有のレジスタ制約を局所的に解決する **LRA（Local Register Allocator）** を組み合わせています。
> * **LLVM（`RAGreedy`）：** 従来の単純な線形走査を発展させた **Greedy Register Allocator（`RAGreedy`）** が `-O2`/`-O3` のデフォルトです。`RAGreedy` は巨大な干渉グラフを作らず、生存区間を重要度・長さ順の優先度キューから取り出しながら、割り当てられない場合は優先度の低い既存区間を追い出す（Eviction）、生存区間をループ内外で細かく切り分ける（**ライブレンジ分割：Live Range Splitting**）、定数や単純なアドレス計算ならメモリへ退避せず使う直前に再計算する（**再物質化：Rematerialization**）といった手法で、グラフ彩色に匹敵するコード品質と高いコンパイル速度を両立しています。
>
> さらに理論面でも重要な発見があります。一般のプログラムの干渉グラフに対する $k$-彩色問題はNP完全ですが、[2-1](2-1.md)・[2-7節](2-7.md)で学んだ **SSA形式のプログラムから作られる干渉グラフは必ず「弦グラフ（Chordal Graph：長さ4以上のすべての閉路に弦があるグラフ）」になる**ことが証明されています（Hack et al., 2006年）。弦グラフの最小彩色数は最大クリーク（同時に生きる変数の最大数）に一致し、**多項式時間で厳密な最適彩色が求まります**。このため現代のコンパイラ研究では、「まずSSA形式のままスピルだけを決定し、その後に最適彩色と $\phi$ 関数の除去を行う」という **SSAベースレジスタ割当** が大きな潮流となっています。

> **【確認の問い】**

> 1. **（4頂点閉路 $C_4$ に対する $k = 2$ Chaitin-Briggs と楽観的彩色のトレース）**
>     4つの変数 `a, b, c, d` の干渉グラフが4頂点閉路 $C_4$（辺：`(a, b)`, `(b, c)`, `(c, d)`, `(d, a)`）になっており、使える物理レジスタは $k = 2$ 本（`R1, R2`）であるとします。
>
>     * (a) 初期状態で全頂点の次数がいくつになるかを確認し、縮約（Simplify）で止まったあと潜在的スピル（Potential Spill）として頂点 `a` を選んでスタックへ積んだ場合の、残りの縮約手順（スタックの底 → 頂上の並び）を示してください。
>     * (b) スタック頂上から順にポップして選択・彩色（Select）を行ったとき、潜在的スピル候補だった `a` が実際にはメモリへスピルされず 2 彩色に成功する（Briggs の楽観的彩色）過程を、各頂点の色割当とともに示してください。
>
> 2. **（スピルコスト重み付け $\text{cost}/\deg$ と `call` 跨ぎ変数の事前彩色）**
>
>     * (a) ある関数内に、二重ループ（ネスト深さ $d = 2$、重み $10^2$）の内側で定義1回・参照1回が行われ次数が `4` の変数 `x` と、ループ外（ネスト深さ $d = 0$、重み $10^0$）で定義1回・参照4回が行われ次数が `2` の変数 `y` があるとします。本節 4-(2) の評価式 $\text{cost}(v) / \deg(v)$ を計算し、どちらをスピル候補に選ぶべきかを答えてください。
>     * (b) グラフ彩色レジスタ割当において、関数呼び出し `call foo` をまたいで生存する変数が、特別な場合分けコードなしで自動的に callee-saved レジスタ（`%rbx, %r12`〜`%r15`）へ割り当てられる仕組みを、事前彩色ノードと干渉辺の観点から説明してください。
>
> 3. **（Ershov 数による評価順の最適化と JIT における線形走査法）**
>
>     * (a) 標準的なロード・ストアモデルで加算式 `a + (b + (c + d))` の各部分木の Ershov 数（葉 $= 1$）を求め、左から右へ素朴に評価した場合（4本）と、Ershov 数の大きい側から先に評価した場合（2本）とで必要なレジスタ本数がどう変わるかを、レジスタ使用手順とともに説明してください。
>     * (b) AOT コンパイラの最適化ビルドで用いられるグラフ彩色法に対し、JIT コンパイラで**線形走査法（Linear Scan）**が広く採用される理由（計算量と実行時コンパイル遅延）、および単純な線形走査法が分岐で生じる**生存区間の穴（Lifetime Hole）**で不利になり得る理由を簡潔に説明してください。
