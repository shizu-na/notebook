### 前節（2-4）の確認問題の解答

前節の最後に提示した3つの問いの解答を確認します。構文解析で AST が構築された後、次のステップとして名前と型を検証する本節（意味解析）へ進みます。

1. **$\text{SLR}(1)$ 構文解析表の3ステップトレースと左結合の確認（`1 + 2 + 3 $`）：**

    * **(a) スタック `0 E 1 + 4 T 5`、残り入力 `+ num $` からの3ステップ：**

        | ステップ | 参照セル・動作 | 更新後のスタック（底 → 頂上） | 残り入力 |
        | :---: | :--- | :--- | ---: |
        | ① | `ACTION[5, +] = r1`（$E \to E\texttt{+}T$ で3組ポップ → `GOTO[0, E] = 1`） | `0 E 1` | `+ num $` |
        | ② | `ACTION[1, +] = s4`（2つ目の `+` をシフト） | `0 E 1 + 4` | `num $` |
        | ③ | `ACTION[4, num] = s3`（`num`(3) をシフト） | `0 E 1 + 4 num 3` | `$` |

    * **(b) 左結合 `(1 + 2) + 3` になる理由：**
        2つ目の `+` をシフトして右側の `+ 3` へ進む前のステップ①で、すでにスタック上にある `1 + 2`（$E\texttt{+}T$）を先に1つの非終端記号 $E$ へ還元してまとめるためです。後からシフトされる `+ 3` はそのまとまった `(1 + 2)` を左の子とする親ノードになり、自然に左結合の木が組み上がります。

2. **$\text{LALR}(1)$ コア合併による還元／還元衝突とシフト／還元衝突の性質：**

    * **(a) 合併後の項集合と発生する衝突：**
        $I_a$ と $I_b$ は同じ $\text{LR}(0)$ コア $\{[A \to \texttt{x}\cdot],\; [B \to \texttt{x}\cdot]\}$ を持つため、合併して先読みの和集合をとると次の項集合になります。

        $$
        I_{ab} = \bigl\{\, [A \to \texttt{x}\cdot,\; \texttt{c}/\texttt{d}],\; [B \to \texttt{x}\cdot,\; \texttt{c}/\texttt{d}] \,\bigr\}
        $$

        これにより、先読み `c` のセルと先読み `d` のセルの両方で「$A \to \texttt{x}$ による還元」と「$B \to \texttt{x}$ による還元」が競合する**還元／還元衝突（Reduce/Reduce Conflict）**が新たに発生します。

    * **(b) 新たなシフト／還元衝突が決して生まれない理由：**
        合併後の状態 $I_{ab}$ で先読み記号 $a$ に対してシフト／還元衝突が起きたと仮定します。シフト動作が存在するなら、共通の $\text{LR}(0)$ コアの中に $[X \to \alpha \cdot a \beta]$ の形のシフト項が含まれており、これは合併前のすべての $\text{LR}(1)$ 状態（$I_a$ と $I_b$ の両方）に共通して存在します。また、還元動作 $[Y \to \gamma \cdot,\; a]$ が合併後に存在するなら、合併前の少なくとも一方の状態（$I_a$ または $I_b$）にその還元項が元々含まれていたはずです。するとその元の状態の時点で、同じ先読み $a$ に対するシフト項と還元項がすでに同居しており、合併前からシフト／還元衝突が存在したことになります。したがって、合併前にシフト／還元衝突がなければ合併後に新たに生まれることはありません。

3. **演算子優先順位宣言 `%left` によるあいまい文法の衝突裁定：**

    * **(a) 先読み `*` と `+` のそれぞれの選択：**
        還元候補の規則 $E \to E \texttt{+} E$ の右辺に現れる最後の終端記号は `+` です。先読みが **`*`** のときは先読み側（`*`）の方が規則側（`+`）より高優先順位のため**シフト**が選ばれます。先読みが **`+`** のときは規則側と先読み側が同順位であり、`%left '+'`（左結合）が指定されているため**還元**が選ばれます。

    * **(b) 入力 `1 + 2 * 3` と `1 + 2 + 3` の解析結果：**
        `1 + 2 * 3` では `1 + 2` の後に `*` をシフトして `2 * 3` を先にまとめるため `1 + (2 * 3)` となり、`1 + 2 + 3` では2つ目の `+` の手前で `1 + 2` を先に還元するため `(1 + 2) + 3` として正しく解析されます。

## 2-5. 意味解析：静的スコープ・記号表と型システム・暗黙変換

### 1. 動機（Why）：なぜ構文解析だけでは足りず、名前と型を検査するフェーズが必要なのか

前節（[2-3](2-3.md)・[2-4節](2-4.md)）までの字句解析と構文解析によって、ソースコードはトークン列を経て**抽象構文木（AST）**へ変換されました。しかし、構文解析が保証しているのは「プログラムが文法規則に沿った形をしている」ことだけです。次の3つのCコード片は、いずれも構文解析を問題なく通過して構文上の誤りがないASTになります。

```c
x = y + 1;                  // 問題1：変数 y はそもそも宣言されているか？
int a = 1; int a = 2;       // 問題2：同じ範囲内で a を二重定義していないか？
int *p = "hello" + 3.14;    // 問題3：文字列と小数の加算、さらに int* への代入は許されるか？
```

これらが誤りかどうかを判定するには、構文木の中で離れた場所にある「変数の宣言」を覚えておき、参照箇所と照らし合わせる必要があります。左辺が1記号だけの文脈自由文法（CFG）では、こうした「離れた箇所どうしの対応（文脈依存の制約）」を原則として表現できません。

そこでASTを構築した直後に走るフェーズが **意味解析（Semantic Analysis）** です。意味解析には大きく2つの役割があります。

1. **意味エラーの検出：** 未宣言変数の使用、二重定義、型の不一致、引数の個数や型の誤り、ループ外での `break` などをコンパイル時に見つけて報告します。
2. **後段（コード生成）のための注釈付け：** 同じ `a + b` というASTノードであっても、`int` 同士の加算、`double` 同士の加算、ポインタ `int *` と整数 `int` の加算（要素サイズ4倍のスケーリングが必要）では、生成すべき機械語命令がまったく異なります。意味解析はASTの各ノードへ**型情報や変数の配置情報（スタックオフセット等）**を紐づけ、次節のコード生成へ橋渡しします。

本節では、スコープを管理する**記号表**の仕組み、複合型を表す**型木と型検査**、さらに静的／動的型付けやC言語の**暗黙の型変換**、そして静的解析の理論的限界までを整理します。

### 2. 具体例と動作イメージ（Toy Model）

データ構造の一般論に入る前に、2つの小さな例で「入れ子スコープでの名前解決」と「型による意味の変化」を確かめます。

#### 実験A：入れ子ブロックと名前の覆い隠し（シャドーイング）

次のCプログラムで、①〜③の3箇所に現れる変数 `x` はそれぞれどの宣言を指しているでしょうか。

```c
int x = 10;             // 宣言(A)：大域変数 x (int)
int main(void) {
    int y = x + 1;      // ① 大域の x (= 10) を参照 → y = 11
    {
        double x = 2.5; // 宣言(B)：内側ブロックの x (double)
        double z = x;   // ② 内側の x (= 2.5) を参照（外側の x を覆い隠す）
    }
    return x;           // ③ 内側ブロックを抜けたので、再び大域の x (= 10) を参照
}
```

C言語をはじめとする現代のほとんどのプログラミング言語では、**「ある名前がどの宣言を指すかは、実行時の呼び出し経路ではなく、ソースコード上の入れ子構造（字句構造）だけで静的に決まる」**という **静的スコープ（Static Scope / レキシカルスコープ）** を採用しています。これと対照的なのが、実行時の呼び出し元を遡って変数を探す **動的スコープ（Dynamic Scope）** です。たとえば大域変数 `int x = 10;` と関数 `int f(void) { return x; }` があるとき、別の関数 `void g(void) { int x = 20; f(); }` から `f()` を呼ぶと、静的スコープでは `f` が書かれた場所から見える `10` を返しますが、動的スコープ（初期のLispやBashの局所変数など）では呼び出し元 `g` の `20` が参照されます。静的スコープの方が、関数の意味を呼び出し元に依存せずソースコード単体から予測できるため、現代の言語の標準となっています。

実験Aを上から順に追うと、ブロック `{` に入った瞬間に新しい名前空間が1段積まれ、内側の `double x` が外側の `int x` を一時的に覆い隠します（**シャドーイング：Shadowing**）。そしてブロック `}` を抜けた瞬間に内側の名前空間が丸ごと破棄され、再び外側の `int x` が見えるようになります。この「最後に入ったブロックから最初に出る（後入れ先出し：**LIFO：Last-In First-Out**）」振る舞いは、そのまま**スタック構造**と一致します。

#### 実験B：同じ `+` ノードが型によって3通りの機械語へ分かれる

AST上に同じ二項演算ノード `Add(a, b)` があっても、意味解析で `a` と `b` の型を調べると、後段へ渡すべき処理内容が次のように分岐します。

* `int a; int b;` の場合は、通常の整数加算（x86-64 の `addl`）を行います。結果の型は `int` です。
* `double a; int b;` の場合は、まず `b` を `int` から `double` へ変換するノード（`IntToDouble(b)`）を AST へ自動挿入したうえで浮動小数点加算（`addsd`）を行います。結果の型は `double` です。
* `int *a; int b;` の場合はポインタ演算であり、32ビットの符号あり整数 `b` が負の値（例：`a + (-1)`）でもアドレス計算が壊れないよう、まず `movslq %esi, %rsi` で `b` を64ビットへ符号拡張したうえで、`sizeof(int) = 4` 倍のスケーリング加算（`leaq (%rdi, %rsi, 4), %rax`）を行います（`long b` のように元々64ビット幅なら符号拡張は不要です）。結果の型は `int *` です。
* `int *a; int *b;` の場合は、ポインタ同士の加算が意味を持たないため**型エラー**としてコンパイルを中止します。

このように、意味解析はプログラムの正誤を検証する役割と同時に、あいまいな演算子 `+` の意味を確定させて後段の翻訳へ引き渡す役割も担っています。

### 3. 構造・アルゴリズム・実装（What）

#### (1) 静的スコープとスタック型記号表（Symbol Table）

コンパイラが変数・関数・型などの宣言情報を登録・検索するためのデータ構造が **記号表（Symbol Table）** です。各エントリには、識別子名、種類（変数／関数／型名）、データ型、スコープの深さ、そしてコード生成で使う配置情報（局所変数なら `%rbp` からのオフセット、大域変数ならELFラベル名）などが記録されます。

入れ子になった静的スコープを扱う最も標準的な実装が、名前から登録情報をほぼ $O(1)$ で引ける連想配列である**ハッシュ表のスタック（スコープ・スタック）** です（図2-5-1）。

1. **ブロック開始（`{`）：** 新しい空のハッシュ表をスタックの頂上へ積みます（`enter_scope`）。
2. **宣言（例：`double x = 2.5;`）：** **スタックの一番上（現在のスコープ）だけ**を調べます。すでに同名 `x` があれば「二重定義エラー」とし、なければ現在のハッシュ表へ登録します（外側のスコープに同名があってもエラーにならず、シャドーイングになります）。
3. **参照（例：`x`）：** スタックの**頂上（最も内側）から底（大域スコープ）へ向かって順に検索**し、最初に見つかったエントリを返します。底まで探しても見つからなければ「未宣言エラー」とします。
4. **ブロック終了（`}`）：** スタック頂上のハッシュ表をポップして破棄します（`leave_scope`）。

また、現実のプログラミング言語の記号表には、次の2つの実用的な設計要素が組み込まれています。

* **名前空間（Namespace）の分離：** C言語では「通常の識別子（変数・関数・`typedef` 名）」「構造体・共用体・列挙体のタグ名（`struct node` の `node`）」「`goto` ラベル名」「各構造体ごとのメンバ名」の4つが、用途ごとの別々の名簿（名前空間）として管理されます。そのため `struct node node;` のように構造体タグと変数に同じ名前を付けても衝突しません。
* **前方参照（Forward Reference）とプロトタイプ宣言：** 関数 `f` が関数 `g` を呼び、同時に `g` も `f` を呼ぶ（相互再帰）場合、上から1回だけ読む（1パス）コンパイラでは先に現れた `f` の中で `g` が未定義になってしまいます。C言語ではヘッダやファイル先頭に **`int g(int);`（関数プロトタイプ宣言）** を置いて先に記号表へ型情報だけ登録させることで解決しています。一方、Java・Go・Rust などのより新しい言語では、ソース全体からまずトップレベルの関数・型宣言だけを収集する「2パス名前解決」を行うため、プロトタイプ宣言が不要になっています。

> **【コラム：文字列リテラルの集約（インターニング）と書き換え禁止、およびELFリンカのサフィックス共有】**
>
> プログラムの中で `"error\n"` や `"%d\n"` のような同じ文字列リテラルが複数の関数に何度も登場することは珍しくありません。多くのCコンパイラは、意味解析の段階で記号表（文字列プール）を用いて**内容が同じ文字列リテラルを1つにまとめて共有（インターニング：String Interning）**し、実行ファイルの `.rodata` セクションへ1個分だけ配置してメモリを節約します。
>
> ここで、もし次のコードのように文字列リテラルの先頭文字を書き換えられたら何が起きるでしょうか。
>
> ```c
> char *p = "hello";
> char *q = "hello";
> p[0] = 'H';   // 未定義動作。Linuxでは通常 Segmentation Fault で終了する
> ```
>
> もし書き換えが許されてしまうと、記号表で共有されている無関係な `q` の中身まで `"Hello"` に化けてしまい、深刻なバグになります。だからこそC言語の規格では文字列リテラルの書き換えを**未定義動作**とし、OSとELF（[1-4節](../1/1-4.md)）は `.rodata` を**読み取り専用（`r--`）**のメモリページへ配置して、書き換えようとした瞬間にハードウェア例外で強制停止させる安全設計をとっています。
>
> なお、この点には言語やツールチェインによる興味深い違いがあります。
>
> * **C と C++ の型設計の差：** C言語では歴史的互換性のため文字列リテラルの型は `char[N]`（非 `const`）のままであり、`char *p = "hello";` がコンパイルエラーにならず実行時UBになります。一方、C++ では型を **`const char[N]`** と厳格化したため、`const` なしの `char *` への代入自体をコンパイル時に型エラーとして弾きます。
> * **ELF リンカによる翻訳単位横断のサフィックス共有：** GCC や Clang は文字列リテラルを `SHF_MERGE | SHF_STRINGS` フラグ付きのセクション（`.rodata.str1.1`）へ出力します。リンカ（`ld`/`lld`）は複数の `.o` ファイルを結合する際、内容が一致する文字列だけでなく **`"hello"` と `"lo"` のように末尾（サフィックス）が一致する文字列同士も重ねて1つに共有**し、バイナリサイズをさらに削減します。
> * **実行時インターニング：** Java の `String.intern()` や Python の一部識別子文字列では実行時にも文字列プールを共有しますが、動的に大量の文字列を登録するとハッシュ表管理や、不要になったメモリを自動回収する仕組みである**ガベージコレクション（GC）**の負荷が増えるトレードオフがあります。

#### (2) 型表現（型木：Type Tree）とボトムアップの型検査

単純な `int` や `double` だけなら列挙型（`enum`）で表現できますが、C言語や現代の言語には「`int` へのポインタの配列」「`int` と `char *` を受け取り `int` を返す関数へのポインタ」のように、型をいくらでも入れ子にできる **複合型** があります。

コンパイラ内部では、こうした複合型を、既存の型を包んで新しい型を作る枠組み（**型構成子：Type Constructor**）を組み合わせた木構造である **型木（Type Tree）** として表現します（図2-5-2左）。

* **葉ノード（基本型）：** `Int`, `Char`, `Double`, `Void` などの基本型です。
* **内部ノード（型構成子）：**

    * `Ptr(T)`：型 `T` へのポインタ型を表します。
    * `Array(T, n)`：要素型 `T`・要素数 `n` の配列型を表します。
    * `Struct(field1: T1, field2: T2, ...)`：構造体型を表します（[0-2節](../0/0-2.md)のアラインメント規則に従って各メンバのオフセットと全体サイズをここで計算して確定させます）。
    * `Func((T1, T2, ...) -> Ret)`：引数型リストと返り値型を持つ関数型を表します。

型検査（Type Checking）は、構築されたASTを**葉から根へ向かって（ボトムアップ／後順序）**走査しながら、各部分式の型を確定し、親ノードの規則に合うかを検証する処理です（図2-5-2右）。このとき「2つの型が等しいか」を判定する基準には、**名前的等価性（Nominal Equivalence）** と **構造的等価性（Structural Equivalence）** の2種類があります。C言語では、`struct A { int x; };` と `struct B { int x; };` は中身が同一でも定義名が異なるため別型とみなす**名前的等価性**を構造体・共用体に採用する一方、ポインタ・配列・関数型は型木の構造が一致すれば等しいとみなす**構造的等価性**で判定します（なお `typedef` は新しい型を作らず、既存の型への別名を記号表へ登録するだけです）。

#### (3) 静的型付け・動的型付けと型推論

プログラミング言語の型システムは、「いつ型を検査するか」と「型を誰が書くか」の2軸で整理できます。

| 分類 | 代表言語 | 仕組みと特徴 | 長所・短所 |
| :--- | :--- | :--- | :--- |
| **静的型付け**（明示的） | C, Java | コンパイル時にすべての変数・式の型を検査して確定する | 実行前に型バグを排除でき、実行時の型タグ不要で高速。記述量が増えやすい |
| **動的型付け** | Python, Ruby, JavaScript | 変数ではなく実行時の「値」に、その値が整数か文字列かを示す識別子（**型タグ**）を持たせ、演算のたびに検査する | 柔軟で素早く書ける。実行時まで型エラーに気づけず、型チェックの実行時コストがある |
| **静的型付け＋型推論** | Rust, Go, OCaml, Haskell | コンパイル時に静的に型検査しつつ、文脈から明らかな型注釈をコンパイラが自動推論する | 記述の簡潔さと、静的型付けの安全性・高速性を両立できる（エラー原因箇所が分かりにくくなる場合あり） |

> **【コラム：型推論（Hindley-Milner）の直感：型変数と単一化による方程式の解法】**
>
> Rust や OCaml、Haskell では、変数の型をいちいち書かなくてもコンパイラが静的に型を確定してくれます。この仕組みの理論的土台が **Hindley-Milner（ヒンドリー＝ミルナー）型推論** です。発想は中学数学の連立方程式によく似ています。
>
> 1. **型変数の割り当て：** 型が書かれていない変数や式の引数に、未知数となる仮の型変数 $\alpha, \beta, \gamma$ を振ります。たとえば `fn add_one(x) { return x + 1; }` なら、`x` の型を $\alpha$、返り値の型を $\beta$ と置きます。
> 2. **制約（型方程式）の収集：** ASTを走査して式から制約を集めます。`x + 1` では `1` が `int` であり、`+` は同じ数値型同士を受け取って同じ型を返すため、「$\alpha = \text{int}$」「$\beta = \text{int}$」という方程式が得られます。
> 3. **単一化（Unification）：** 集めた方程式を代入・照合して解きます。すべての型変数に矛盾のない解が見つかれば型が確定し、`int` と `string` が等しくなるような矛盾が出ればコンパイル時の型エラーとして報告されます。また、たとえば `fn id(x) { return x; }` のように $\beta = \alpha$ という制約だけが残って未知の型変数が消えない場合は、任意の型を受け取って同じ型を返す多相関数（$\alpha \to \alpha$、ジェネリクス）として最も一般的な型が自動導出されます。

### 4. 限界と補正（Critique & Adaptation）

#### (1) C言語の暗黙の型変換（整数拡張・通常の算術型変換）による直感とのズレ

型検査を厳格に行うと、`double d = 1.5; int i = 2; double x = d + i;` のような日常的な式で毎回キャストを書かなければならず煩雑です。そこでC言語は、異なる数値型同士を演算するときにコンパイラが自動で型を揃える **暗黙の型変換（Implicit Type Conversion）** を導入しました。

1. **整数拡張（Integer Promotion）：** `char` や `short` のような `int` より狭い整数型は、演算の前に自動的に `int` へ拡張されます。
2. **通常の算術型変換（Usual Arithmetic Conversions）：** 二項演算で左右の型が異なるとき、表現範囲の広い型へ揃えます（概略順は `int` → `unsigned int` → `long` → `unsigned long` → `float` → `double` ですが、実際の変換先は処理系のビット幅に依存します。たとえば64ビット Linux の LP64 では `long` が64ビットで `unsigned int`［32ビット］の全値を表現できるため両者の演算は符号あり `long` になりますが、32ビット ILP32 では `long` と `unsigned int` が同じ32ビット幅のため `unsigned long` へ変換されます）。

しかし、この便利な規則には[0-1節](../0/0-1.md)でも触れた重大な注意点があります。**同じビット幅の `int`（符号あり）と `unsigned int`（符号なし）を混ぜると、符号あり側が強制的に符号なしへ変換される**という仕様です（図2-5-3）。

このように、暗黙の型変換は書きやすさと引き換えに意図しないバグを生みやすいため、C言語の実務ではコンパイラの警告オプション（`-Wsign-compare` 等）を厳格に有効化し、GoやRustといった現代のシステムプログラミング言語では**異なる数値型同士の暗黙変換を全面的に禁止し、明示的な型変換だけを許す**設計へ補正されています。

#### (2) 静的解析の理論的限界（停止性問題と実行時チェックの併用）

意味解析や静的型チェックは強力ですが、**「コンパイル時の静的解析だけで、プログラムのあらゆるバグを漏れなく誤検知もなく検出することは数学的に不可能である」**という根本的な限界があります。

アラン・チューリングが証明した **停止性問題（Halting Problem）** により、「任意のプログラムと入力を受け取り、それが有限時間で停止するか無限ループするかを常に正しく判定するアルゴリズム」は存在しません。さらにその一般化である **ライスの定理**（「プログラムが実行時に何をするか」という非自明な性質を、ソースコードだけからあらゆるプログラムに対して漏れも誤検知もなく判定する万能チェッカは作れない、という計算理論の定理）により、「実行時にゼロ除算が起きないか」「配列の添字 `a[i]` が決して範囲外に出ないか」「ヌルポインタ参照が起きないか」を漏れも誤検知もなく静的に判定することも不可能です。

たとえば配列境界検査の不可能性は、停止性問題から1ステップで帰着できます。もし任意のプログラムで配列範囲外アクセスが起きるかを漏れも誤検知もなく判定できるチェッカが存在すれば、**配列を使わない任意の計算 `P()`** に対して「`int a[10]; P(); a[100] = 0;`」を検査させるだけで、`a[100] = 0` に到達するか否か＝`P()` が停止するか否かを判定できてしまい、停止性問題の決定不能性に矛盾するからです。

したがって、現実の言語設計では次の2方向の補正を組み合わせています。

1. **実行時チェックの併用：** 配列アクセス `a[i]` の境界検査やゼロ除算検査など、静的に保証しきれない箇所には実行時の検査コードを自動挿入します（Java, Go, Rust 等。C言語は速度優先で省略したため、[第5部](../index.md#part-5) [5-8節](../5/5-8.md)のバッファオーバーフロー攻撃の温床になりました）。
2. **保守的な静的制約の導入：** Rustの**所有権・借用チェッカ**（メモリの所有者や参照の有効期間をコンパイル時に追跡する仕組み）のように、「実際には安全かもしれない一部の書き方まで一律エラーにして見逃しを防ぐ」という**保守的な方針**をとる代わりに、通過したプログラムについてはメモリ安全性や**データ競合**（複数スレッドが同期なしに同じメモリへ同時書き込みするバグ）の不在をコンパイル時に確実に保証する設計です。

### 理解度チェック（次節へ進む前の確認）

本節の静的スコープと動的スコープの違い、複合型の型木と処理系依存の暗黙変換、および静的解析の限界を確認します。

> **【確認の問い】**
>
> 1. **（静的スコープ vs 動的スコープとシャドーイングの規則）**
>     次の C 風プログラムを考えます。
>
>     ```c
>     int x = 10;
>     int get_x(void) { return x; }
>     int main(void) {
>         int sum = 0;
>         {
>             int x = 20;
>             sum = x + get_x();
>         }
>         return sum;
>     }
>     ```
>
>     * (a) C 言語のような**静的スコープ（レキシカルスコープ）**で評価した場合と、**動的スコープ**で評価した場合とで、`main` 関数の返り値 `sum` はそれぞれいくつになるでしょうか。それぞれの名前解決の仕組みとあわせて答えてください。
>     * (b) 同じ変数名 `x` の再宣言が「内側のブロック `{ int x = 20; }`（シャドーイング）」では許されるのに、「同じブロック内での二重定義 `int x = 1; int x = 2;`」ではエラーになる理由を、スタック型記号表の検索範囲から説明してください。
>
> 2. **（複合型の型木比較と処理系依存の暗黙変換）**
>
>     * (a) C 言語の2つの宣言 `int *a[4];`（`int` へのポインタを4個持つ配列）と `int (*p)[4];`（`int` 4個の配列へのポインタ）について、それぞれの**型木（Type Tree）**を `Ptr`, `Array`, `int` の入れ子表記（例：`Ptr(Array(int, 4))`）で書き分けて比較してください。
>     * (b) `unsigned int u = 1;` と `long s = -2;` に対する比較式 `s < u` を評価したとき、64ビット Linux（LP64：`int`=32ビット、`long`=64ビット）と 32ビット環境（ILP32：`int`=32ビット、`long`=32ビット）で真偽が逆転する理由を、通常の算術型変換の規則に沿って説明してください。
>
> 3. **（ヌルポインタ参照の静的判定不能性と現実言語の2つの補正）**
>
>     * (a) 「任意のプログラムが実行時にヌルポインタ参照を起こすか否かを、漏れも誤検知もなくコンパイル時に判定する静的チェッカ」が存在しないことを、停止性問題からの帰着によって説明してください（ヒント：ポインタ参照を含まない任意の計算 `P()` を用いてコード片を構成してください）。
>     * (b) この理論的限界に対して、Java や Go の「実行時チェックの併用」と、Rust の「保守的な静的制約」では、安全性・表現力・実行コストのトレードオフがどう異なるかを簡潔に比較してください。
