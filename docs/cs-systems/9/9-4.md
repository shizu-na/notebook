### 前節（9-3）の確認問題の解答

前節の最後に提示した3つの問いの解答を確認します。問3がそのまま本節（問合せ最適化）の導入になります。

1. **2-pass 同時ソートマージ結合と GRACE ハッシュ結合のメモリ上限比較（$M = 22$ ページ、$B(R) = 1{,}000$、$B(S) = 400$）：**

    * **(a) 2-pass 同時マージ版ソートマージ結合のラン本数と可否：**
        Pass 1 で生成されるソート済みランの本数は、$R$ が $\lceil 1{,}000 / 22 \rceil = \mathbf{46\text{ 本}}$、$S$ が $\lceil 400 / 22 \rceil = \mathbf{19\text{ 本}}$ で、合計 **$46 + 19 = 65\text{ 本}$** になります。一方、Pass 2 では出力バッファ 1 ページを除く **$M - 1 = 21\text{ 本}$** までのランしか同時に 1 パスでマージできません。$65 > 21$ であるため、$M = 22$ ページでは **2-pass 同時マージ版ソートマージ結合は実行できません**（途中に追加のマージパスが必要です）。

    * **(b) GRACE ハッシュ結合のパーティション数・サイズ・可否と総 I/O コスト：**
        Pass 1 では出力用に $M - 1 = \mathbf{21\text{ 個}}$ のパーティションを作成します。均等分割を仮定すると、小さい表 $S$ の 1 パーティションあたりのページ数は $\lceil 400 / 21 \rceil = \mathbf{20\text{ ページ}}$（$400 = 21 \times 19 + 1$ より 19〜20 ページ）となり、Pass 2 で $R_i$ の入力用 1 ページ＋出力用 1 ページを除いたメモリ上限 **$M - 2 = 20\text{ ページ}$** に収まります（2-pass で実行可能です）。これは、GRACE ハッシュ結合の 2-pass 成立条件が小さい表 $S$ のみ（$B(S) \le (M - 1)(M - 2) = 21 \times 20 = 420$ ページ）で決まり、大きい表 $R$ のサイズに上限がないためです。総ディスク I/O コストは $3\bigl(B(R) + B(S)\bigr) = 3 \times (1{,}000 + 400) = \mathbf{4{,}200\text{ ページ I/O}}$ です。

2. **非クラスタ索引の選択率逆転とハッシュ結合におけるデータスキュー：**

    * **(a) $s = 5\%$ でのページ I/O 比較と誤解の反証：**
        全表シーケンシャルスキャンは選択率 $s$ によらず常に **$B(R) = 10{,}000\text{ ページ}$** の連続読込みで完了します。一方、$T(R) = 1{,}000{,}000$ 行の $5\%$ にあたる $50{,}000$ 行が該当する場合、非クラスタ索引で 1 行ごとにヒープ表へ少なくとも 1 回のランダムページ I/O が起きると合計 **$50{,}000\text{ 回}$ 以上**（葉ノード探索を含めればさらに多く）のランダム I/O が発生します。I/O 回数だけで全表走査の 5 倍以上に増えるうえ、1 回あたりの遅延も連続 I/O よりランダム I/O の方が大きいため、「索引があれば常に索引を使うべき」というのは誤りであり、選択率が高い条件では全表スキャン（または中間帯のビットマップヒープスキャン）の方が高速です。

    * **(b) 極端なデータスキュー（$S$ の $30\% = 120$ ページが同一キー値）が起きたときの破綻と回避策：**
        同じキー値はハッシュ関数 $h_1$ で必ず同じパーティション $S_i$ へ集まるため、$S_i$ のサイズが少なくとも $120$ ページ以上に膨れ上がり、Pass 2 のメモリ上限 $M - 2 = 20$ ページを大幅に超えてメモリ溢れを起こします。しかも単一キー値への集中は別のハッシュ関数で再帰パーティショニングしても分割できないため、実システムでは溢れたそのバケット $(R_i, S_i)$ だけを **Block Nested-Loop Join（BNLJ）へフォールバック** して処理します。

3. **3 表の結合順序と選択の適用位置による中間結果サイズの差（本節への接続）：**

    * **① 各段階の中間結果の行数見積り：**

        * **手順 1（`((Students ⋈ Enroll) ⋈ Courses)` の後に `dept = 'CS'`）：** `Students`（$10^5$ 行）と `Enroll`（$10^6$ 行）の結合で **$10^6$ 行** が生まれ、続く `Courses`（$1{,}000$ 行）との結合でも **$10^6$ 行** の中間結果となり、最後の絞り込みで `'CS'` の $2\% = 20{,}000$ 行になります（中間結果の合計は **$2{,}000{,}000$ 行**）。
        * **手順 2（$\bigl(\sigma_{\text{dept}=\text{'CS'}}(\text{Courses}) \bowtie \text{Enroll}\bigr) \bowtie \text{Students}$）：** 先に `Courses` を `dept = 'CS'` で絞り込むことで **$20$ 行** になり、これと `Enroll` を結合した中間結果は全体の $2\%$ の **$20{,}000$ 行** へ抑えられ、最後に `Students` と結合して最終結果 $20{,}000$ 行を得ます（中間結果の合計は **$20 + 20{,}000 = 20{,}020$ 行** で、手順 1 の約 100 分の 1 です）。

    * **② コストが減る理由と多表結合の探索の難しさ：**
        `dept = 'CS'` の絞り込みを結合より先に適用して中間タプル数・ページ数を小さく保ったことで、後続の結合でメモリに収まりやすくなり、読み書きするページ数が大きく減るためです。ただし結合するテーブルが 5 つ・10 個と増えると結合順序・選択位置・Join アルゴリズムの組合せ数が急激に増大するため、手計算や総当たりでは選び切れず、本節の **問合せ最適化器** が等価変換ルールとコスト見積り・動的計画法などで効率よく探索します。

## 9-4. 問合せ最適化（等価変換・Selection Pushdown・コストベースと NP 完全性）

### 1. 動機（Why）：なぜ「同じ SQL」でも実行計画の選び方 1 つで速度が 1,000 倍変わるのか

[8-1節](../8/8-1.md)で学んだ通り、リレーショナルデータベースが半世紀以上にわたり標準として広く使われ続けている最大の理由は、利用者が「どうやってデータを取り出すか（How）」を書くことなく、**「どんな条件のデータが欲しいか（What）」だけを宣言的言語 SQL で書けばよい**点にあります。

しかし、この宣言的な便利さの裏側には、重い責務が DBMS 側へ課されています。前節まで（[9-2](9-2.md)・[9-3節](9-3.md)）で見た通り、たった 1 本の SQL クエリを実行するにも、DBMS の手元には膨大な選択肢があるからです。

* 各テーブルを「全表シーケンシャルスキャン」で読むか、「$\text{B}^+$ 木索引スキャン」で読むか。
* 選択（$\sigma$）や射影（$\pi$）を結合（$\bowtie$）の前に行うか、後に行うか。
* 5 つのテーブル $R_1 \bowtie R_2 \bowtie R_3 \bowtie R_4 \bowtie R_5$ をどの組み合わせ・順番で結合するか。
* 各結合に Block Nested-Loop・Index Nested-Loop・Sort-Merge・Hash Join のどれを割り当てるか。

最悪の実行計画を選べば **数時間** かかるクエリが、最良の実行計画を選べば **数ミリ秒** で終わることは珍しくありません。一方で、結合するテーブル数 $n$ が増えると可能な実行計画の総数は階乗や指数を超えて爆発するため、すべての計画を総当たりで試すこともできません（**結合順序の最適化問題は一般に NP 困難**であり、対応する決定問題「コスト $K$ 以下の計画が存在するか」は **NP 完全** です）。

この「宣言的な What」と「物理的な最速の How」のあいだを数ミリ秒で繋ぐ DBMS の中核機構が **問合せ最適化器（Query Optimizer）** です。本節では、**ルールベース等価変換**、**統計情報によるカーディナリティ推定とコストベース最適化（CBO）**、そして IBM System R で確立された **動的計画法と左深木探索** の仕組みを整理します。

---

### 2. 具体例と動作イメージ（Toy Model）

理論の枠組みに入る前に、2つの小さな数値例で「計画による大きなコスト差」と「探索空間の組合せ爆発」を確かめます。

#### 実験A：3 表の結合で「順番と押し下げ」が中間結果サイズを 100 倍変える

次の 3 つのテーブルを結合し、`dept = 'CS'` の科目を履修した学生の氏名を求める SQL を考えます。

* `Students(sid, sname)`：10 万行（$T = 10^5$）
* `Enroll(sid, cid)`：100 万行（$T = 10^6$、1 人平均 10 科目履修）
* `Courses(cid, dept)`：1,000 行（$T = 1,000$、全 50 学科が均等で `'CS'` は **20 科目**）

次の 2 つの論理計画（同じ最終結果を返す等価な関係代数木）の中間タプル数を比べてみましょう。

* **計画 1（素朴な実行：結合してから絞り込む）：**

    $$\sigma_{\text{dept}=\text{'CS'}}\Bigl((\text{Students} \bowtie \text{Enroll}) \bowtie \text{Courses}\Bigr)$$

    1. まず `Students`（10 万行）と `Enroll`（100 万行）を結合 $\implies$ 中間結果 **100 万行**。
    2. 次に `Courses`（1,000 行）と結合 $\implies$ 中間結果 **100 万行**。
    3. 最後に `dept = 'CS'` で絞り込む $\implies$ 最終結果 2 万行（100 万行 $\times 20/1000$）。
    * **中間結果の合計：200 万行**。

* **計画 2（Selection Pushdown ＋ 小さい結果から先に結合）：**

    $$\text{Students} \bowtie \Bigl(\text{Enroll} \bowtie \sigma_{\text{dept}=\text{'CS'}}(\text{Courses})\Bigr)$$

    1. まず `Courses`（1,000 行）へ `dept = 'CS'` を先に適用（**Selection Pushdown**）$\implies$ **20 行**。
    2. 次に `Enroll` と結合（20 行のハッシュ表へ `Enroll` を通す等の方法で該当行だけを抽出）$\implies$ 中間結果 **2 万行**。
    3. 最後に `Students` と結合 $\implies$ 最終結果 2 万行。
    * **中間結果の合計：20,020 行（約 2 万行、計画 1 の約 100 分の 1）**。

#### 実験B：結合するテーブル数 $n$ と「結合木の総数」の爆発

$n$ 個のテーブルを 2 つずつ順番に結合するとき、括弧の付け方（木の形）とテーブルの並べ順の組み合わせが何通りあるかを計算してみます（物理的な結合アルゴリズムは外側・内側の左右入力で非対称なため、$R_1 \bowtie R_2$ と $R_2 \bowtie R_1$ を区別して数えます）。

* **一般の二分木（茂み木：Bushy Tree、例：$(R_1 \bowtie R_2) \bowtie (R_3 \bowtie R_4)$ も含む）：**
    $n$ 枚の葉を持つ二分木（$n - 1$ 個の結合ノード）の形はカタラン数 $C_{n-1} = \dfrac{(2n-2)!}{n!(n-1)!}$ 通りあり、そこへ $n$ 個のテーブルを配置する順列 $n!$ 通りを掛けると $\dfrac{(2n - 2)!}{(n - 1)!}$ 通りになります。

* **左深木（Left-Deep Tree、例：$(((R_1 \bowtie R_2) \bowtie R_3) \bowtie R_4)$ に限定）：**
    木の形を「右の子が常に 1 枚の基底テーブル」に固定すると、テーブルの順列の数そのままの $n!$ 通りになります。

| テーブル数 $n$ | 左深木の数（$n!$） | 一般の茂み木の数（$\frac{(2n-2)!}{(n-1)!}$） |
| :---: | ---: | ---: |
| $n = 3$ | $6$ 通り | $12$ 通り |
| $n = 5$ | $120$ 通り | $1{,}680$ 通り |
| $n = 8$ | $40{,}320$ 通り | $17{,}297{,}280$ 通り（約 1,730 万） |
| $n = 10$ | $3{,}628{,}800$ 通り（約 363 万） | **$17{,}643{,}225{,}600$ 通り（約 176 億）** |

しかも各結合ごとに 4 種類の Join アルゴリズム（[9-3節](9-3.md)）と各表のアクセス方法（全表走査／各種索引）の選択が掛け算で増えるため、わずか 10 テーブルの `JOIN` でも総当たり探索は現実時間では不可能です。

### 3. 構造・アルゴリズム・実装（What）

#### (1) 問合せ最適化の 2 段階アーキテクチャ（論理計画 → 物理計画）

現代の RDBMS（PostgreSQL, MySQL, Oracle, System R 等）の問合せ最適化器は、次の 2 段階（**ルールベース変換** と **コストベース最適化**）を組み合わせて動作します（図9-4-1）。

1. **論理計画の生成とルールベース最適化（RBO：Rule-Based Optimization）：**
    パーサが SQL から構築した初期の **論理問合せ計画（関係代数木）** に対し、データの中身やサイズを見なくても「ほぼ常に有利になる」関係代数の等価変換規則（Selection Pushdown 等）を適用して木を書き換える。

2. **物理計画の列挙とコストベース最適化（CBO：Cost-Based Optimization）：**
    書き換えられた論理計画に対し、**システムカタログの統計情報** を参照しながら、各ノードへ具体的なアクセス手法（全表走査 vs $\text{B}^+$ 木索引）と結合アルゴリズム（Hash Join / Sort-Merge / INLJ 等）を割り当てた **物理問合せ計画** の候補を動的計画法で探索し、推定総コスト（ディスク I/O ＋ CPU コスト）が最小となる 1 本を問合せ実行エンジン（[9-3節](9-3.md)）へ渡す。

#### (2) ルールベース最適化：関係代数の等価変換規則

関係代数が満たす以下の数学的恒等式（等価変換規則）を適用することで、最終結果を変えずに中間データ量を大幅に削減します。

1. **選択の分解（連言分解）：** $\sigma_{p_1 \land p_2}(R) \equiv \sigma_{p_1}(\sigma_{p_2}(R))$
2. **選択の交換律：** $\sigma_{p_1}(\sigma_{p_2}(R)) \equiv \sigma_{p_2}(\sigma_{p_1}(R))$
3. **選択の押し下げ（Selection Pushdown）：** 条件 $p$ が $R$ の属性だけを参照するなら、結合より先に $R$ へ適用する。

    $$\sigma_{p}(R \bowtie S) \;\equiv\; \sigma_{p}(R) \bowtie S$$

    （条件が $p_R \land p_S$ に分解できるなら $\sigma_{p_R \land p_S}(R \bowtie S) \equiv \sigma_{p_R}(R) \bowtie \sigma_{p_S}(S)$ として両側へ押し下げます。なお [8-2節](../8/8-2.md)で確認した通り、この等価性は内部結合 $\bowtie$ で成り立ち、`LEFT JOIN` の右表［`NULL` 補完側］への無条件の押し下げは一般には非等価になります。）

4. **射影の早期適用（Projection Pushdown）：** 結合や最終出力に不要な列を早い段階で切り落とし、1 タプルあたりのバイト幅を縮めてバッファプールへより多くの行を載せる。

    $$\pi_{L}(R \bowtie S) \;\equiv\; \pi_{L}\bigl(\pi_{L_R}(R) \bowtie \pi_{L_S}(S)\bigr)$$

    （ただし $L_R, L_S$ には最終出力列 $L$ に含まれる属性に加えて、結合で参照する**結合キー属性**も含める必要があります。）

5. **結合の交換律と結合律（結合順序の自由度）：**

    $$R \bowtie S \;\equiv\; S \bowtie R, \qquad (R \bowtie S) \bowtie T \;\equiv\; R \bowtie (S \bowtie T)$$

    この 2 法則があるからこそ、CBO が「どのペアから先に結合するか」を自由に組み替えられます。

6. **選択と直積の結合化：** $\sigma_{\theta}(R \times S) \equiv R \bowtie_{\theta} S$（素朴な直積を作らず、ハッシュ結合や索引結合へ変換します）。

#### (3) コストベース最適化（CBO）：統計情報とカーディナリティ推定

ルールベース変換で木を整えたあと、CBO が「計画 A と計画 B のどちらが速いか」を比較するには、実際にクエリを実行する**前**に、各演算子が出力する推定行数（**カーディナリティ推定：Cardinality Estimation**）を見積もる必要があります。

DBMS は **システムカタログ** に各テーブルの軽量な **統計情報（Statistics）** を保存しています（定期的に `ANALYZE` コマンドやバックグラウンド処理でサンプリング収集します）。

* $T(R)$：テーブル $R$ の総タプル（行）数。
* $B(R)$：テーブル $R$ の総ページ数。
* $V(R, A)$：属性 $A$ に現れる**異なる値（一意な値）の個数**（NDV：Number of Distinct Values）。
* $\min(R, A),\; \max(R, A)$：属性 $A$ の最小値・最大値、および値の偏りを捉える **ヒストグラム（等幅／等深ヒストグラム）**。

これらを用いて、各条件を満たす割合（**選択率：Selectivity** $s \in [0, 1]$）と出力行数 $T_{\text{out}}$ を次のように推定します（図9-4-2）。

* **等値条件 `A = c`（一様分布仮定：$c$ が $R.A$ に現れる値の 1 つであり、出現頻度が均等と仮定）：**

    $$s = \frac{1}{V(R, A)}, \qquad T(\sigma_{A = c}(R)) \approx \frac{T(R)}{V(R, A)}$$

* **範囲条件 `A > c`（一様分布仮定、またはヒストグラム参照；$\min(R, A) \le c \le \max(R, A)$）：**

    $$s = \frac{\max(R, A) - c}{\max(R, A) - \min(R, A)}$$

* **複合条件 `p1 AND p2`・`p1 OR p2`・`NOT p1`（独立性仮定）：**

    * $s(p_1 \land p_2) = s(p_1) \times s(p_2)$
    * $s(p_1 \lor p_2) = s(p_1) + s(p_2) - s(p_1)s(p_2) = 1 - \bigl(1 - s(p_1)\bigr)\bigl(1 - s(p_2)\bigr)$
    * $s(\neg p_1) = 1 - s(p_1)$

* **等結合 $R \bowtie_{R.A = S.A} S$（包含仮定）：**
    異なる値の少ない側の全キー値が大きい側に含まれると仮定します。たとえば $V(R, A) \le V(S, A)$ なら $R$ の各タプルが $S$ のある 1 つのキー値と一致する確率は $\frac{1}{V(S, A)}$ であり、逆に $V(S, A) \le V(R, A)$ なら $R$ の値が $S$ の値域に入る確率 $\frac{V(S, A)}{V(R, A)}$ と一致確率 $\frac{1}{V(S, A)}$ の積 $\frac{1}{V(R, A)}$ になります。したがってどちらの場合も、任意のタプル対 $(r, s) \in R \times S$ で $r.A = s.A$ となる確率は $\dfrac{1}{\max(V(R, A),\, V(S, A))}$ となり、次式が得られます。

    $$T(R \bowtie S) \;\approx\; \frac{T(R) \cdot T(S)}{\max\bigl(V(R, A),\; V(S, A)\bigr)}$$

    特に $S.A$ が主キー（$V(S, A) = T(S)$）で $R.A$ が外部キーのとき、この式は自動的に $T(R \bowtie S) \approx T(R)$ となり直感と一致します。

**実験Aの数値回収と I/O コストの比較：**
上の推定式へ 2 節（実験A）の統計値を当てはめると、中間結果とページ I/O コストの差を最適化器が事前に見抜けることが分かります。いま 1 ページあたり $100$ 行が格納されているとし、作業メモリを $M = 102$ ページ（[9-3節](9-3.md)の記号に準拠）と設定します。

* カタログ統計：$T(\text{Students}) = 10^5,\; B(\text{Students}) = 1{,}000,\; V(\text{Students}, \text{sid}) = 10^5$、$T(\text{Enroll}) = 10^6,\; B(\text{Enroll}) = 10{,}000,\; V(\text{Enroll}, \text{cid}) = 1{,}000$、$T(\text{Courses}) = 1{,}000,\; B(\text{Courses}) = 10,\; V(\text{Courses}, \text{cid}) = 1{,}000,\; V(\text{Courses}, \text{dept}) = 50$。
* **計画 2 の推定行数と I/O コスト：**

    1. $C' = \sigma_{\text{dept}=\text{'CS'}}(\text{Courses})$ の推定行数は $T(C') \approx 1{,}000 / 50 = \mathbf{20\text{ 行}}$（$1$ ページ未満）。`Courses` を $10$ ページ読み、メモリ上に $1$ ページ分のハッシュ表を作ります。
    2. $E' = \text{Enroll} \bowtie C'$ の推定行数は $V(C', \text{cid}) = 20$、$V(\text{Enroll}, \text{cid}) = 1{,}000$ より、

        $$T(E') \approx \frac{10^6 \times 20}{\max(1{,}000,\; 20)} = \mathbf{20{,}000\text{ 行}}\text{（約 } 200\text{ ページ）}$$

        `Enroll` の $10{,}000$ ページを $1$ 回走査しながらハッシュ表を引く（1-pass Hash Join）ため I/O は $10{,}000$ 回です。

    3. 最後の $E' \bowtie \text{Students}$ は $T \approx \dfrac{20{,}000 \times 10^5}{10^5} = \mathbf{20{,}000\text{ 行}}$。$E'$（$200$ ページ）を $100$ ページ単位のブロックで流しつつ `Students`（$1{,}000$ ページ）と Block Nested-Loop Join すると $2 \times 1{,}000 = 2{,}000$ I/O となり、合計 **$10 + 10{,}000 + 2{,}000 = 12{,}010$ ページ I/O** で完了します（最終結果の出力 I/O は共通のため除外）。

* **計画 1 の推定コスト：**
    先に `Students`（$1{,}000$ ページ）と `Enroll`（$10{,}000$ ページ）を結合すると、どちらも $M - 2 = 100$ ページに収まらないため 2-pass の GRACE Hash Join（[9-3節](9-3.md)）が必要になり、それだけで $3(1{,}000 + 10{,}000) = 33{,}000$ I/O を消費します。さらに $100$ 万行をパイプラインで `Courses`（$10$ ページ）と結合しても合計 **$33{,}010$ ページ I/O**（計画 2 の約 $2.7$ 倍の I/O と $100$ 倍の中間タプル数；中間結果をディスクへ書き出せばさらに増加）となり、CBO は計画 2 を選びます。

#### (4) 結合順序最適化の計算複雑性と System R（Selinger）の動的計画法

実験Bで確認した通り、$n$ テーブルの結合順序を最適化する問題は一般に **NP 困難**（対応する決定問題「コスト $K$ 以下の計画が存在するか」は **NP 完全**）です。1979年、IBM System R の開発チーム（パトリシア・セリンジャー［Patricia Selinger］ら）は、現代の商用 RDBMS の雛形となった **「左深木への探索空間限定 ＋ 動的計画法（DP）」** という代表的な最適化アルゴリズムを確立しました（図9-4-3）。

1. **探索空間の限定①：左深木（Left-Deep Tree）のみを探索する**

    * **左深木** とは、すべての結合ノードにおいて「右の子（内側表）が必ず元の基底テーブル 1 枚である」ような結合木（$(((R_1 \bowtie R_2) \bowtie R_3) \bowtie R_4)$）です（図9-4-3左）。
    * 左深木には 2 つの大きな利点があります。第 1 に探索空間が茂み木から大幅に縮むこと。第 2 に、[9-3節](9-3.md)のイテレータモデル（Volcano モデル）において、左の子から流れてくる中間タプルをディスクへ書き出さず（マテリアライズせず）、**そのままパイプラインで次の Index Nested-Loop Join や Hash Join へ流し込める** ためメモリ効率が非常に高いことです。

2. **探索空間の限定②：不要な直積（Cartesian Product）を原則除外する**

    * 共通の結合条件を持たないテーブル同士の結合（直積）は、結合グラフが非連結で他に選択肢がない場合を除き探索から除外します。

3. **ボトムアップ動的計画法（DP：計算量 $O(n \, 2^n)$）：**

    * **ステップ 1（サイズ 1 の部分集合）：** 各単一テーブル $\{R_i\}$ について、全表走査および各索引スキャンのコストを評価し、最安のアクセス計画を DP 表へ保存します。
    * **ステップ 2（サイズ $k = 2, 3, \dots, n$ の部分集合）：** $k$ 個のテーブルからなる部分集合 $S$ ごとに、$S$ から 1 表 $R_j$ を抜いた残り $(S \setminus \{R_j\})$ の「すでに求まっている最安計画」と $R_j$ を各種 Join アルゴリズムで結合するコストをすべて評価し、**$S$ を作る最安の 1 本だけを DP 表へ残します（最適性の原理：劣る計画は即座に枝刈りします）**。サイズ $k$ の部分集合 $\binom{n}{k}$ 個ごとに最大 $k$ 通りを調べるため、全体の比較回数は $\sum_{k=2}^{n} \binom{n}{k} k = n(2^{n-1}-1) = O(n \, 2^n)$ に抑えられます（茂み木まで許す DP の $O(3^n)$ より高速です）。
    * **興味深い順序（Interesting Orders）の例外保持：** たとえば `ORDER BY a` があるクエリでは、単純に最安な Hash Join（未ソート出力）より少しコストが高い Sort-Merge Join（`a` 順ソート済み出力）の方が、最終的な `ORDER BY` の外部ソートを丸ごと省けて全体では最安になることがあります。そのため System R の DP では、各部分集合 $S$ について「全体の最安計画」だけでなく、**「クエリ中の `JOIN` / `GROUP BY` / `ORDER BY` に役立つ特定のソート順（Interesting Order）ごとの最安計画」** も別枠で保持します（保持する順序の種類数を $r$ とすると計算量は $O(r \, n \, 2^n)$ になります）。

### 4. 限界と補正（Critique & Adaptation）

#### (1) カーディナリティ推定の破綻（独立性仮定の崩壊と統計の陳腐化）

現代の問合せ最適化器が「ひどく遅い計画」を選んでしまう最大の原因は、コスト計算式そのものではなく、**カーディナリティ推定（中間行数の見積り）の大幅な外れ**にあります。

1. **属性間の相関（独立性仮定の破綻）：**
    自動車テーブル（100 万台）で、`maker = 'Toyota'`（選択率 $0.1$）かつ `model = 'Prius'`（選択率 $0.01$）という条件を考えます。独立性仮定 $s(p_1 \land p_2) = 0.1 \times 0.01 = 0.001$ をそのまま使うと、最適化器は「1,000 台しかヒットしない」と見積もります。しかし現実には Prius は 100% Toyota 製なので、実際のヒット数は $10{,}000$ 台（**見積りの 10 倍**）です。この誤差が結合を 3 段、4 段と経るごとに掛け算で増幅し、「本当は 100 万行あるのに 10 行だと誤認して Index Nested-Loop Join を選び、100 万回のランダム I/O で遅延する」事故が起きます。

2. **統計情報の陳腐化：** テーブルへ大量のデータを `INSERT` した直後、カタログの古い統計情報（まだ 100 行しかない記録）のままクエリを計画してしまう事故です。

* **補正：** 定期的な自動統計収集（PostgreSQL の `autovacuum` / `ANALYZE`）に加え、相関の強い複数列の同時分布を記録する **拡張統計（多次元統計：`CREATE STATISTICS`）** を導入します。

#### (2) 多表結合（$n > 12$）における DP の限界とヒューリスティック切替

System R の動的計画法は計算量 $O(n \, 2^n)$ で済むため、$n = 8 \sim 12$ テーブル程度までは数ミリ秒で完了します。しかし、自動生成された BI ツールの SQL などで **$n = 20$ テーブルの `JOIN`** が飛んでくると、$2^{20} \approx 105\text{ 万}$ もの部分集合エントリを作る羽目になり、最適化だけでメモリと時間が尽きます。

* **補正：** PostgreSQL では、結合テーブル数が閾値（デフォルト `geqo_threshold = 12`）を超えると自動的に DP を打ち切り、**遺伝的アルゴリズム（GEQO）** や貪欲法などの確率的・近似的探索へ切り替えて計画時間の上限を守ります。

#### (3) 静的計画の限界と適応的問合せ実行（AQE）・`EXPLAIN ANALYZE`

どれだけ統計を磨いても、クエリ実行前に行数を 100% 当てることは不可能です。そのため現代の分散分析エンジン（Spark SQL 等）や最新 RDBMS（SQL Server, Oracle 等）では、**実行途中で実際の中間行数を観測し、「見積りより 100 倍多かったら、その場で Nested-Loop から Hash Join へ計画を動的に切り替える」適応的問合せ実行（AQE：Adaptive Query Execution）** が導入されています。

また開発者の実務では、遅い SQL を見つけたとき推測で書き換えるのではなく、必ず **`EXPLAIN ANALYZE`** を実行して「最適化器が**推定した行数（Estimated Rows）**」と「実際に処理された**実測行数（Actual Rows）**」のズレを確認するのが性能チューニングの基本手順です。

本節のカーディナリティ推定・Selection Pushdown・左深木 DP の仕組みを確認し、次節（[9-5節](9-5.md)）へ繋がる課題を体験する問いを置きます。

> **【確認の問い】**
>
> 1. **（統計情報によるカーディナリティ推定と結合の I/O コスト比較）**
>     次の統計情報を持つ 2 つのテーブル $R(A, B)$ と $S(B, C)$ を考えます（作業用バッファは $M = 50$ ページとします）。
>
>     * $T(R) = 10{,}000$ 行、$B(R) = 200$ ページ、$V(R, A) = 100$、$V(R, B) = 500$
>     * $T(S) = 2{,}000$ 行、$B(S) = 40$ ページ、$V(S, B) = 2{,}000$（$B$ は $S$ の主キー）
>
>     * (a) 選択 $\sigma_{A = 42}(R)$ の推定行数、および選択を先に押し下げた結合 $\sigma_{A = 42}(R) \bowtie S$ の推定行数を求めてください（一様分布・包含仮定）。また、先に $R \bowtie S$ を計算してから $\sigma_{A = 42}$ を適用する場合の推定行数と最終値が一致することを検算し、両者の中間行数を比べてください。
>     * (b) 選択なしの結合 $R \bowtie S$ を 1-pass Hash Join（[9-3節](9-3.md)：構築側 $\le M - 2$ ページ）で実行する場合、$R$ と $S$ のどちらをハッシュ表の構築側（内側）に選ぶべきか判定し、そのときのディスク I/O 回数を求めてください。
>
> 2. **（Interesting Orders の判断と独立性仮定の破綻）**
>
>     * (a) クエリ `SELECT * FROM A JOIN B ON A.x = B.x ORDER BY A.x` に対し、部分集合 $\{A, B\}$ の結合候補として計画 $P_1$（Hash Join：コスト $1{,}000$、出力は未ソート）と計画 $P_2$（Sort-Merge Join：コスト $1{,}400$、出力は `A.x` 昇順）が得られ、未ソート結果への最終 `ORDER BY A.x` の外部ソートコストが $800$ であるとします。DP が各部分集合で単一の最安計画だけを残した場合と、**Interesting Orders** を別枠で残した場合とで、選ばれる計画と最終コストがどう変わるか計算してください。
>     * (b) $100$ 万行の表 `Employees(id, dept, is_manager)` において、`dept = 'Sales'` の選択率が $0.2$、`is_manager = TRUE` の選択率が $0.1$ であり、実際には管理職の $80\%$ が営業部（`'Sales'`）に属しているとします。独立性仮定による推定行数と実際の行数を比較し、この誤差が物理計画（索引走査 vs 全表走査など）の選択をどう誤らせるか説明してください。
>
> 3. **（次節への伏線：単一クエリを最適化しても防げない同時実行の矛盾）**
>     本節の最適化器によって、口座テーブル `Accounts(id, balance)` に対するすべての単一 SQL が最速の索引プランで実行できるようになったとします。いま初期残高がともに $10$ 万円の口座 $A, B$ に対し、送金処理 $T_1$ が 2 本の更新（$A$ を $8$ 万円へ更新し、続けて $B$ を $12$ 万円へ更新）を実行するあいだに、残高合計を求める参照処理 $T_2$ が $A$ と $B$ を順に読み取ったとします。各 SQL 単体の実行計画が最適であっても、$T_1$ と $T_2$ の操作が交錯するとどのような矛盾が生じ、さらにその直後に $T_1$ がエラーで中断した場合に何が問題になるでしょうか。
