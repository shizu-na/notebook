### 前節（9-6）の確認問題の解答

前節の最後に提示した3つの問いの解答を確認します。問3がそのまま本節（TO・OCC・MVCC とスナップショット）の導入になります。

1. **ロッキング定理の条件トレースと基本 2PL・Strict 2PL の検証：**

    * **(a) $S_A$ で破られている条件と先行グラフの閉路：**
        $S_A$ では読み書き前のロック取得・終了時解放（**正規**）と排他・共有の同時保持禁止（**合法**）は守られていますが、$T_1$ が $U_1(A)$ でロックを解放したあとに $X_1(B)$ を獲得し、$T_2$ も $U_2(A)$ のあとに $S_2(B)$ を獲得しているため、**二相（Two-Phase）** の条件が破られています。データ $A$ の $W_1(A) \to R_2(A)$（WR 競合）から $T_1 \to T_2$、データ $B$ の $R_2(B) \to W_1(B)$（RW 競合）から $T_2 \to T_1$ の辺が張られ、有向閉路 **$T_1 \to T_2 \to T_1$** が生じます。

    * **(b) 基本 2PL への修正と Strict 2PL が必要な理由：**
        $T_1$ が $X_1(A)$ と $X_1(B)$ の両方を獲得したあとに $U_1(A), U_1(B)$ を解放し、そのあとに $T_2$ が $S_2(A), S_2(B)$ を獲得するように修正すると、$T_1$ の最終獲得時刻 $LP(T_1)$（$X_1(B)$ の時点）は $U_1(A), U_1(B)$ より前であり、$T_2$ の獲得より必ず早いため **$LP(T_1) < LP(T_2)$** となり、直列スケジュール **$T_1 \to T_2$** と競合等価になります。ただし基本 2PL のまま $T_1$ がコミット前に $U_1(A)$ を解放し、$T_2$ が未コミットの $A$ を読んだ（あるいは別トランザクションが $A$ へ上書きした）直後に $T_1$ がアボートすると、**ダーティリード・連鎖アボート・ダーティライトによる UNDO 破損** が起きるため、X ロックを終了まで保持する **Strict 2PL** が必要になります。

2. **Wait-Die / Wound-Wait の双方向判定と `READ COMMITTED` の誤解検証：**

    * **(a) $T_1(TS=10\text{：古い})$ と $T_2(TS=20\text{：若い})$ の衝突判定と時刻印引継ぎの理由：**

        * **① $T_1$（古い）が $T_2$（若い）の保持ロックを要求した場合：** Wait-Die では $T_1$ が待ち（**Wait**）、Wound-Wait では $T_1$ が $T_2$ を強制アボートしてロックを奪います（**Wound**）。
        * **② $T_2$（若い）が $T_1$（古い）の保持ロックを要求した場合：** Wait-Die では $T_2$ が自らアボートしてやり直し（**Die**）、Wound-Wait では $T_2$ が待ちます（**Wait**）。
        * **元の古い時刻印を引き継ぐ理由：** 再起動のたびに新しい大きい時刻印を振り直すと、そのトランザクションは後続の新しいトランザクションより常に「若い」ままになり、何度もアボートされ続けて完了できない**飢餓（Starvation）** が起きるためです。

    * **(b) `READ COMMITTED` 下での主張の反証と対策：**
        この主張は**誤り**です。ロックベースの `READ COMMITTED` では `SELECT balance` の読取り直後に短期 S ロックを即座に解放するため、2 つのトランザクションが同時に残高 $10$ 万円を読んで `balance >= 60000` の条件を通過したあと、順番に X ロックを取って引落しを実行し、二重引落しや更新消失を起こせます。対策は、① **`SELECT balance FROM Accounts WHERE id = 1 FOR UPDATE;`** として読取り時点から行へ X ロックを保持するか、② **`UPDATE Accounts SET balance = balance - 60000 WHERE id = 1 AND balance >= 60000;`** の 1 文にまとめて X ロック解放後の最新コミット値で条件を再評価させることです。

3. **相互ブロックの解消と、スナップショット読取りの新しい矛盾（本節への接続）：**

    * **(a) Strict 2PL で読取りと書込みが互いに待たされる理由：**
        Strict 2PL（SS2PL）では $T_1$ が読み取った $100$ 万行（`id = 500` を含む）に終了まで S ロックを保持し続けるため、互換行列で S と非互換な X ロックを要求する $T_2$ は $T_1$ の完了まで待たされます。逆に $T_2$ が先に `id = 500` の X ロックを保持しているあいだは、X と非互換な S ロックを要求する $T_3$ も待たされます。

    * **(b) スナップショット読取りで生じる矛盾：**
        $T_1$ と $T_2$ は互いに同じ開始時点（$A, B$ とも当直中）を読んで別々の行（$T_1$ は $A$、$T_2$ は $B$）を非番へ更新するため、書き込み対象が重ならず両方とも確定できてしまいます。その結果、**当直医が 0 人になり「常に 1 人以上残す」制約が破られる（書き込みスキュー）** という、直列実行（$T_1 \to T_2$ でも $T_2 \to T_1$ でも必ず 1 人は残る）とは等価でない矛盾が発生します。本節では、このようなスナップショット分離（MVCC）の仕組みと、直列化可能性を取り戻す **SSI** などを詳しく解説します。

## 9-7. 時刻印・楽観的・多版並行制御（TO・OCC・MVCC とスナップショット）

### 1. 動機（Why）：なぜ悲観的ロック（2PL）だけでは現代の高並列ワークロードを捌き切れないのか

前節（[9-6節](9-6.md)）で学んだ **Strict 2PL** は、共有ロック（S）と排他ロック（X）によって競合直列化可能性（CSR）と厳格性（Strict）を動的に保証できる堅牢な方式です。しかし、実際の高負荷システムで純粋な 2PL だけを運用すると、次の 3 つの構造的なボトルネックに直面します。

1. **「読み取り」と「書き込み」の相互ブロック：**
    Strict 2PL では、ある分析クエリが `Orders` テーブルの 100 万行を 5 秒かけて集計しているあいだ S ロックが掛かり続けるため、通常の注文更新（X ロック）が 5 秒間すべて待たされます。逆に、更新トランザクションが X ロックを握っている行は、参照だけの画面ですらブロックされます。

2. **ロック管理とデッドロックのオーバーヘッド：**
    すべての行アクセスごとに中央のロックテーブル（ハッシュ表）へラッチを掛けてロックを獲得・解放する処理は、それ自体がマルチコア CPU 上で激しいラッチ競合とキャッシュ無効化（[0-7節](../0/0-7.md)）を引き起こします。さらに 2PL ではデッドロックが不可避なため、待機グラフの巡回やアボート処理も必要になります。

3. **競合が滅多に起きないワークロードでの過剰防衛：**
    読み取りが 95% を占める Web サービスや、ユーザごとに別々の行を触るシステムでは、実際にはほとんど競合しないにもかかわらず、毎回「衝突するかもしれない」と悲観的にロックを取り続けるのは大きな無駄です。

これらの壁を乗り越えるために、データベース研究では **ロック待ちに頼らない 3 つのアプローチ** が発展しました。

* **時刻印順序付け方式（TO：Timestamp Ordering）：** ロックを使わず、開始時刻の順番（時刻印）に従って直列化順序を事前に固定します。
* **楽観的並行制御（OCC：Optimistic Concurrency Control）：** 競合しない前提でロックなしのまま最後まで処理を進め、コミット直前に一括検証します。
* **多版並行制御（MVCC：Multi-Version Concurrency Control）：** データの過去バージョンを複数保持し、読み取りと書き込みが互いにブロックし合わないようにします。

本節では、これら 3 方式のアルゴリズムとトレードオフを順に整理し、理論モデルである **MVTO** を経て、現代の主要 RDBMS（PostgreSQL・MySQL InnoDB 等）を支える **MVCC とスナップショット分離（SI / SSI）** の構造を解き明かします。

### 2. 具体例と動作イメージ（Toy Model）

厳密なアルゴリズムに入る前に、2 つの小さなシナリオで「ロックなしで整合性を守る発想」と「多版（MVCC）の仕組み」を確かめます。

#### 実験A：「先にルールで縛る（2PL・TO）」vs「終わる直前にチェックする（OCC）」

図書館の蔵書検索・貸出システムに例えてみます。

* **悲観的制御（2PL）：** 誰かが本棚の 1 冊を手に取るとき、必ず受付で鍵（ロック）を借りて本棚に施錠します。返却するまで他の人はその本を覗き見ることすらできません。
* **時刻印方式（TO）：** 入館時に整理券番号（時刻印 $TS = 10, 20, \dots$）を配ります。「番号 10 の人は番号 20 の人より必ず先に仕事をしたことにする」と決めておき、もし番号 10 の人が後から来て「すでに番号 20 が書き換えた後のページ」を読もうとしたら、「順番が逆転した」と判断して即座に番号 10 をやり直し（アボート）させます。
* **楽観的制御（OCC）：** 誰も鍵を掛けずに、本の内容を自分のメモ帳（プライベート作業領域）へコピーして自由に編集します。最後に受付へ提出する瞬間（コミット直前）だけ、「自分がコピーした後に誰かが原本を書き換えていないか」を一括チェックし、誰も触っていなければそのまま原本へ反映し、誰かが先に書き換えていたら自分のメモを破棄してやり直します。

#### 実験B：残高合計クエリ $T_2$ と送金 $T_1$ が「待たずに」共存する（MVCC）

[9-5節](9-5.md)・[9-6節](9-6.md)で登場した、口座 $A$（10 万円）と口座 $B$（10 万円）のシナリオ（初期状態は過去のトランザクション `TX 5` が作成済み）を **MVCC（多版並行制御）** で動かしてみます。

1. 時刻 `t = 10` に残高合計クエリ $T_2$ が開始します（$T_2$ のスナップショット基準時刻 ＝ **`10`**）。
2. 時刻 `t = 12` に送金 $T_1$（トランザクション ID `12`）が始まり、口座 $A$ を 10 万円 $\to$ 8 万円へ更新して、口座 $B$ を 10 万円 $\to$ 12 万円へ更新します。このとき MVCC では **元の「10 万円」の行をそのまま上書きして消さず、古い版（Version 1：`TX 5` が作成）を残したまま新しい版（Version 2：`TX 12` が作成）を追記** します。なお、$T_1$ が未コミットのあいだ（たとえば `t = 13`）に別トランザクションが読みに来ても、Version 2 はまだ未確定のため依然として Version 1 だけが見えます。
3. 時刻 `t = 15` に $T_1$ がコミットします（Version 2 が確定）。
4. その直後（時刻 `t = 16`）に、まだ動いていた $T_2$ が $A$ と $B$ を読みに来ます。$T_2$ は自分の開始時点（`t = 10`）で確定していたバージョンだけを見るため、$A$ も $B$ もともに古い Version 1（10 万円と 10 万円）を **ロック待ちゼロで読み出し、矛盾のない合計 20 万円を返します**。
5. 一方、時刻 `t = 20` に新しく始まった $T_3$ は $T_1$ のコミット後なので、確定済みの Version 2（8 万円と 12 万円）を読み出し、同じく矛盾のない合計 20 万円を返します。

このように、**古いバージョンを残しておくだけで、読み取りと書き込みが互いにブロックせず、しかも一貫したスナップショットを読める** のが MVCC の本質です。

### 3. 構造・アルゴリズム・実装（What）

#### (1) 時刻印順序付け方式（TO：Timestamp Ordering）とトーマスの書き込み規則

**時刻印順序付け方式（Basic TO）** は、各トランザクション $T_i$ が開始した瞬間に単調増加する一意の時刻印 $TS(T_i)$ を割り当て、**「等価な直列順序が必ず開始時刻印の昇順（$TS(T_1) < TS(T_2) < \dots$）になる」** ように、ロックを一切使わず実行時に強制する方式です（図9-7-1左）。

DBMS は各データ項目 $X$ ごとに、次の 2 つのメタデータを記録します（初期値は $0$）。

* **`R-TS(X)`（読出し時刻印）：** これまでに $X$ を正常に読み出したトランザクションの中で最大の時刻印。
* **`W-TS(X)`（書込み時刻印）：** これまでに $X$ へ正常に書き込んだトランザクションの中で最大の時刻印。

トランザクション $T_i$ が $X$ へアクセスするたびに、次の規則で「未来のトランザクションに追い越されていないか」を検査します。

1. **$T_i$ が $R_i(X)$（読出し）を要求したとき：**

    * もし **$TS(T_i) < \text{W-TS}(X)$** なら：すでに自分より**未来（若い）**トランザクションが $X$ を上書きしてしまっており、自分が読むべき過去の値が失われている $\implies$ **$T_i$ をアボート**して新しい時刻印で再起動します。
    * そうでなければ（$TS(T_i) \ge \text{W-TS}(X)$）：読出しを許可し、$\text{R-TS}(X) \leftarrow \max\bigl(\text{R-TS}(X),\; TS(T_i)\bigr)$ と更新します。

2. **$T_i$ が $W_i(X)$（書込み）を要求したとき（検査順に注意）：**

    * **① もし $TS(T_i) < \text{R-TS}(X)$ なら：** すでに自分より未来のトランザクションが $X$ の古い値を読んでしまっており、今さら過去の値を書き換えると整合性が崩れる $\implies$ **$T_i$ をアボート**します。
    * **② そうでなく（$TS(T_i) \ge \text{R-TS}(X)$ であり）、もし $TS(T_i) < \text{W-TS}(X)$ なら：** すでに自分より未来のトランザクションが $X$ を上書き済みです。

        * **基本 TO：** **$T_i$ をアボート**します。
        * **トーマスの書き込み規則（Thomas Write Rule）：** 「$\text{R-TS}(X) \le TS(T_i) < \text{W-TS}(X)$ であれば、$T_i$ と $\text{W-TS}(X)$ の間のどのトランザクションも $X$ を読んでおらず、過去の書き込みは未来の書き込みに上書きされて消えるだけである」と判断できるため、**アボートせず $W_i(X)$ を静かに無視（$X$ も $\text{W-TS}(X)$ も更新せず続行）** できます。これにより CSR より広い **VSR（ビュー直列化可能：[9-5節](9-5.md)）** なスケジュールまで受理できます。

    * **③ そうでなければ（$TS(T_i) \ge \text{R-TS}(X)$ かつ $TS(T_i) \ge \text{W-TS}(X)$）：** 書込みを許可し、$X$ の値を更新して $\text{W-TS}(X) \leftarrow TS(T_i)$ と更新します。

**基本 TO とトーマスの書き込み規則の対比（ミニトレース）：**
初期値 $X = 10$（$\text{R-TS} = 0, \text{W-TS} = 0$）に対し、$T_1(TS=10)$ と $T_2(TS=20)$ が `R1(X)` $\to$ `W2(X=30)` $\to$ `W1(X=20)` の順に要求したとします。

1. `R1(X)`：$10 \ge \text{W-TS}(0)$ より許可、$\text{R-TS}(X) \leftarrow 10$。
2. `W2(X=30)`：$20 \ge \text{R-TS}(10)$ かつ $20 \ge \text{W-TS}(0)$ より許可、$X \leftarrow 30$、$\text{W-TS}(X) \leftarrow 20$。
3. `W1(X=20)`：まず $10 < \text{R-TS}(10)$ は**偽**（$T_1$ 自身の読出しであり未来の読者はいない）、次に $10 < \text{W-TS}(20)$ が**真**です。よって **基本 TO では $T_1$ がアボート** になりますが、**トーマスの書き込み規則** を適用すると `W1(X=20)` を無視して $X = 30$ のまま $T_1$ も続行でき、直列スケジュール $T_1 \to T_2$ とビュー等価（VSR）な結果になります。

TO 方式は「待ち（ブロック）」が存在しないため **デッドロックが原理的に起きない** ことが美点です。一方で、基本 TO には次の 2 つの弱点があり、実システムでは補正が必要です。

* **非厳格性（ダーティリード可能）：** $W_i(X)$ を即座に本体へ書くと、$T_i$ のコミット前に若い $T_j$ が読んで連鎖アボートが起き得ます。そのため書き込みをコミットまでローカルバッファへ留める（あるいは未コミット書込み完了まで読者を待機させる）補正で Strict に保ちます。
* **長寿命トランザクションの飢餓：** 長いトランザクション $T_{\text{long}}$ が他の処理を進めているあいだに、次々と到着する短いトランザクションがホットな項目 $X$ を更新して $\text{W-TS}(X)$ を押し上げると、$T_{\text{long}}$ は $X$ に触れるたびにアボートし、新しい時刻印でやり直しても再び後続の短いトランザクションに追い越されて飢餓（Starvation）に陥りやすくなります。

#### (2) 楽観的並行制御（OCC：Optimistic Concurrency Control）

1981年に Kung と Robinson が提案した **楽観的並行制御（OCC）** は、「トランザクション同士の競合は滅多に起きない」という楽観的な仮定に基づき、実行中のロック獲得・時刻印更新のオーバーヘッドを排除します。各トランザクションは次の **3 フェーズ** で進行します（図9-7-1右）。

1. **Read フェーズ（読出し・ローカル作業）：**
    データベースからロックなしでデータを読み込み、すべての書き込み変更はデータベース本体へ直接書かず、そのトランザクション専用の **プライベート作業空間（ローカルバッファ）** へ一時記録します。読み込んだ項目集合を **Read Set（$RS(T_i)$）**、書き込んだ項目集合を **Write Set（$WS(T_i)$）** として記録しておきます。

2. **Validation フェーズ（コミット直前の検証）：**
    トランザクション $T_i$ がコミットしようとするとき、競合の有無を一括検証します。検証には、検証時刻と対象相手の違いにより **後向き検証** と **前向き検証** の 2 つの流儀があります。

    * **後向き検証（Backward Validation：Kung-Robinson 型）：**
        $T_i$ が Validation へ入った時点で直列化順序の番号 $TS(T_i)$ を割り当て、**自分より先に Validation へ入った完了済み・並行実行中のトランザクション $T_j$（$TS(T_j) < TS(T_i)$）** との間で、次の 3 条件のいずれかが成り立てば合格（Valid）とします。

        * **条件 1：** $T_j$ が $T_i$ の Read フェーズ開始より前に完全に Write フェーズを終えている（そもそも実行時間が重なっていない）。
        * **条件 2：** $T_j$ が $T_i$ の Write フェーズ開始前に Write フェーズを終えており、かつ **$WS(T_j) \cap RS(T_i) = \emptyset$**（$T_j$ が書き換えたデータを $T_i$ は 1 つも読んでいない）。
        * **条件 3：** $T_j$ が $T_i$ より先に Validation を終えて Write フェーズと重なっているが、**$WS(T_j) \cap RS(T_i) = \emptyset$ かつ $WS(T_j) \cap WS(T_i) = \emptyset$**（Write 順序も衝突しない）。
        いずれも満たせない場合は、**検証中の $T_i$ 自身をアボート** してプライベート作業空間を破棄します（過去の $WS(T_j)$ を一定期間保持しておく必要があります）。

    * **前向き検証（Forward Validation）：**
        これからコミットしようとする $T_i$ が、**現在まだ Read フェーズを実行中のすべての稼働中トランザクション $T_a$** に対して検証を行います（$T_i$ を $T_a$ より前、すなわち $T_i \to T_a$ の順に直列化します）。具体的には、すべての稼働中 $T_a$ について

        $$WS(T_i) \cap RS(T_a) = \emptyset$$

        が成り立てば合格です（$T_i$ がこれから書き換えるデータを、Read 中の $T_a$ がすでに古い値として読んでしまっていないことの確認）。Validation と Write を排他的に（あるいは同時書込み衝突を防ぎつつ）行えば過去の $WS$ を保存する必要がなく、しかも衝突時に「検証側の $T_i$ を諦める」か「Read 途中の $T_a$ を早期アボートする」かを柔軟に選択できます。

3. **Write フェーズ（本体への一括反映）：**
    検証に合格した場合だけ、プライベート作業空間の変更内容（$WS(T_i)$）をデータベース本体へ書き込んでコミットします（読み取り専用トランザクションは Write フェーズが不要です）。

#### (3) 多版並行制御の理論モデル：MVTO（多版時刻印順序付け）

単一バージョンしか持たない基本 TO では、すでに未来のトランザクションが書き換えた後へ古いトランザクションが読みに来るとアボートになってしまいました。そこで「データ項目 $X$ ごとに複数のバージョン $\langle X_1, X_2, \dots \rangle$ を保持する」ことで読み取りのアボートをなくした理論モデルが、1978年に Reed が提案した **MVTO（Multi-Version Timestamp Ordering）** です。

MVTO では、各バージョン $X_k$ に **作成時刻印 $\text{W-TS}(X_k)$**（その版を書き込んだトランザクションの時刻印）と **最大読出し時刻印 $\text{R-TS}(X_k)$**（その版を読んだトランザクションの中で最大の時刻印、作成時は $\text{W-TS}(X_k)$ に初期化）を持たせます。時刻印 $TS(T_i)$ を持つ $T_i$ が $X$ にアクセスするときは、まず **「$\text{W-TS}(X_k) \le TS(T_i)$ を満たす中で最大の $\text{W-TS}(X_k)$ を持つバージョン $X_k$」** を選び、次のように処理します。

1. **$T_i$ が $R_i(X)$（読出し）を要求したとき：**
    選んだバージョン $X_k$ の値をそのまま読み出し、$\text{R-TS}(X_k) \leftarrow \max\bigl(\text{R-TS}(X_k),\; TS(T_i)\bigr)$ と更新します。初期版 $X_0$（$\text{W-TS}(X_0)=0$）が存在する限り、**読み取り操作は決してアボートせず、ブロックもされません**。

2. **$T_i$ が $W_i(X)$（書込み）を要求したとき：**

    * もし **$TS(T_i) < \text{R-TS}(X_k)$** なら：すでに自分より未来のトランザクション $T_j$（$TS(T_j) = \text{R-TS}(X_k)$）が $X_k$ を読んでしまっているため、時刻印順 $T_i \to T_j$ で $T_j$ が読むべき値を後から割り込ませることはできません $\implies$ **$T_i$ をアボート**します。
    * そうでなく **$TS(T_i) = \text{W-TS}(X_k)$** なら：$T_i$ 自身が作った版の再更新なので、$X_k$ をそのまま上書きします。
    * そうでなければ（$TS(T_i) \ge \text{R-TS}(X_k)$ かつ $TS(T_i) > \text{W-TS}(X_k)$）：**新しいバージョン $X_{\text{new}}$ を新規作成**し、$\text{W-TS}(X_{\text{new}}) = \text{R-TS}(X_{\text{new}}) = TS(T_i)$ とします。

基本 TO のミニトレース `R1(X)` $\to$ `W2(X=30)` $\to$ `W1(X=20)` に MVTO を当てはめると、`R1(X)` は初期版 $X_0$ を読んで $\text{R-TS}(X_0) = 10$ にし、`W2(X=30)` は新版 $X_{20}=30$ を作ります。続く `W1(X=20)` は $\text{W-TS} \le 10$ の $X_0$ に対して $TS(T_1)=10 \ge \text{R-TS}(X_0)=10$ を満たすためアボートせず、**中間の版 $X_{10}=20$ を履歴へ挿入して続行** できます（後に $T_2$ が読んでも $X_{20}=30$ を読むため矛盾しません）。なお、未コミット版を読んだ後の連鎖アボートを防ぐため、実務上の MVTO では作成元トランザクションのコミットを待ってから自らのコミットを確定させるなどの回復可能性制御と組み合わせます。

#### (4) 実用上の MVCC とスナップショット分離（Snapshot Isolation）

MVTO の多版管理の思想を、固定の時刻印ではなく「トランザクションの開始時点における確定状態の静止画（スナップショット）」という形で実用化したものが、現代の主要 RDBMS（PostgreSQL, MySQL InnoDB, Oracle, SQL Server, CockroachDB 等）で中核技術となっている **多版並行制御（MVCC）** と **スナップショット分離（SI）** です（図9-7-2）。

MVCC の核心は、**「1 つの論理的なタプル（行）に対して、複数の物理バージョン（世代）を同時に保持する」** 点にあります。各物理バージョンには、その版がどのトランザクションによって生まれ・無効化されたかを表すメタデータが付与されます（PostgreSQL ではタプルヘッダの `xmin`［作成トランザクション ID］と `xmax`［削除・更新トランザクション ID］、MySQL InnoDB では最新行から **Undo ログ** へ遡るポインタ連鎖として実装されます）。

* **MVCC の基本動作：**

    1. **更新（`UPDATE`）と削除（`DELETE`）：** 既存の行を直接上書きせず、古い版の削除・更新トランザクション ID（`xmax`）に自分のトランザクション ID を刻印し、新しい内容を持つ**新バージョン**（`xmin = 自 TX ID`）を追記してバージョンチェーンで繋ぎます。
    2. **読出し（`SELECT`）：** トランザクション $T_i$ が読み取りを行うとき、ロックを取らず、**「自分のスナップショット時点（`REPEATABLE READ` 等の SI ではトランザクション開始後最初の問合せ時点、`READ COMMITTED` では各 SQL 文の開始時点）ですでにコミット済みの `xmin` を持ち、かつその時点でコミット済みの `xmax` によって無効化されていない最新のバージョン」** をバージョンチェーンから選んで読みます。そのため図9-7-2のように、未コミットの `TX 25` が書き込んだ Version 3 や `xmax = 25` による無効化は無視され、Version 2 が安全に見えます。

これにより、MVCC では次の基本原則が成立します。

> **【MVCC の基本原則】**
> **読み取りは書き込みをブロックせず、書き込みも読み取りをブロックしない。**
> （Readers never block Writers, and Writers never block Readers.）

特に、トランザクション開始時点のデータベース全体の一貫したスナップショットを終了まで見続け、書き込み同士の競合だけは「最初にコミットした側が勝ち（**First-Committer-Wins**：同じ行を並行更新した組は先発のみ確定し、後発はアボート）」とする隔離レベルを **スナップショット分離（SI：Snapshot Isolation）** と呼びます（PostgreSQL や InnoDB 等の実用実装では、更新対象の行へ X ロックを取って後発書込みを先発の終了まで待たせたうえで衝突判定を行う **First-Updater-Wins** として実装されます）。

> **【コラム：なぜ現代の主要 RDBMS は「MVCC ＋ 2PL のハイブリッド」を採用しているのか】**
>
> [9-6節](9-6.md)で 2PL を、本節で TO・OCC・MVCC を学びましたが、現実の PostgreSQL や MySQL（InnoDB）や Oracle の中身を覗くと、どれか 1 つを純粋に使っているのではなく、**「MVCC と Strict 2PL のハイブリッド」** になっています。
>
> * **通常の読み取り（`SELECT`）：** **MVCC（スナップショット）** を使い、S ロックを一切取らずに高速かつノンブロッキングで読み取ります。
> * **書き込み同士の衝突（`UPDATE` / `DELETE` / `SELECT ... FOR UPDATE`）：** 同じ行を同時に更新しようとする 2 つの書き込みトランザクションの間だけは、**Strict 2PL（行単位の X ロック）** で調停します。
>
> もし書き込み同士まで純粋な OCC で衝突のたびにアボートさせると高競合時に再試行が溢れ、逆に読み取りまで純粋な 2PL で S ロックを取ると分析クエリが更新を止めてしまいます。「**読み取りは MVCC でブロックせず、書き込み同士は 2PL の行ロックで確実に保護する**」というハイブリッド構成こそが、実戦を経て定着した RDBMS 並行制御の標準的な設計です。

### 4. 限界と補正（Critique & Adaptation）

#### (1) スナップショット分離（SI）の盲点：書き込みスキュー（Write Skew）と SSI

MVCC に基づくスナップショット分離（SI）は、[9-5節](9-5.md)で挙げた読取・書込み異常（更新消失・ダーティリード・非再現リード・ファントムリード）をすべて防げるため、かつては「これで完全な `SERIALIZABLE` がロックなしで実現できた」と誤解されていました（実際、一部の商用 RDBMS では `SERIALIZABLE` を指定しても長らく SI として実装されていました）。

しかし 1995年、Berenson らが **「スナップショット分離は真の直列化可能性（SERIALIZABLE）ではない」** ことを示す決定的な反例である **書き込みスキュー（Write Skew）** を明らかにしました（図9-7-3）。

**【2 人の当直医問題（Write Skew の典型例）】**
病院の当直表 `OnCall(doc, status)` に、Alice（当直中）と Bob（当直中）の 2 人が登録されており、病院の業務不変条件として **「常に最低 1 人は当直中（`COUNT(*) >= 1`）でなければならない」** とします。

1. Alice（$T_1$）と Bob（$T_2$）が、ちょうど同時に体調を崩して「自分が休んでももう 1 人残っているか」を確認するトランザクションを開始します（両者とも同じスナップショット「Alice=ON, Bob=ON（計 2 人）」を見ます）。
2. $T_1$ は「まだ 2 人いるから大丈夫」と判断し、**Alice の行だけ** を `status = 'OFF'` へ更新してコミットします（$RS(T_1) = \{\text{Alice}, \text{Bob}\}$, $WS(T_1) = \{\text{Alice}\}$）。
3. 同時に $T_2$ も同じスナップショットから「まだ 2 人いるから大丈夫」と判断し、**Bob の行だけ** を `status = 'OFF'` へ更新してコミットします（$RS(T_2) = \{\text{Alice}, \text{Bob}\}$, $WS(T_2) = \{\text{Bob}\}$）。
4. **なぜ SI で素通りするのか：** $T_1$ が書き換えたのは **Alice の行**、$T_2$ が書き換えたのは **Bob の行** であり、**書き込み集合同士（$WS(T_1) \cap WS(T_2) = \emptyset$）がまったく重なっていない** ため、SI の書き込み衝突チェック（First-Committer-Wins）を両方とも通過してしまいます。
5. **結果：** 病院の当直医が **0 人** になり、どの直列スケジュール（$T_1 \to T_2$ でも $T_2 \to T_1$ でも必ず 1 人は残る）とも一致しない整合性崩壊が起きます。

**書き込みスキューに対する 2 つの補正：**

1. **SSI（Serializable Snapshot Isolation：PostgreSQL 9.1+ の `SERIALIZABLE`）：**
    MVCC のノンブロッキング性能を保ったまま完全な直列化可能性を保証するアルゴリズムです（Cahill ら、2008年）。あるトランザクション $T_i$ が読み取った古いバージョン（または検索範囲）を、並行する別トランザクション $T_j$ が後から上書き（または挿入）した関係（**rw-反依存［rw-antidependency］：$T_i \xrightarrow{rw} T_j$**）があると、等価な直列順序では必ず $T_i$ が $T_j$ より先にならなければなりません。

    * 上の 2 人の当直医問題では、$T_1$ が読んだ `Bob=ON` を $T_2$ が更新するため **$T_1 \xrightarrow{rw} T_2$** が生じ、同時に $T_2$ が読んだ `Alice=ON` を $T_1$ が更新するため **$T_2 \xrightarrow{rw} T_1$** も生じます。
    * SSI は互いにブロックしない軽量な追跡ロック（**SIREAD ロック**）で各トランザクションの読出しを記録し、**危険な 2 連続の rw-反依存（$T_{\text{in}} \xrightarrow{rw} T_{\text{pivot}} \xrightarrow{rw} T_{\text{out}}$、上の例では $T_1 \xrightarrow{rw} T_2 \xrightarrow{rw} T_1$）** を検知したときだけ一方をアボートさせます（十分条件を用いた検知のため、ごく稀に擬陽性によるアボートが起きる点には注意が必要です）。

2. **明示的ロック（`SELECT ... FOR UPDATE`）：**
    `REPEATABLE READ`（SI）のまま業務ルールを守りたい場合は、確認クエリを `SELECT * FROM OnCall WHERE status = 'ON' FOR UPDATE;` と書いて全当直行へ X ロックを掛けることで、2 人の処理が同時に進むのを防ぎます。

#### (2) MVCC のガベージコレクション（古いバージョンの肥大化と `VACUUM`）

MVCC は更新のたびに古いバージョンを残し続けるため、**もうどのアクティブなトランザクションからも参照されなくなった古いバージョン（Dead Tuples：死んだタプル）** を放置すると、ディスク容量とインデックスが際限なく膨張し、検索速度が大きく低下します。

* **補正（ガベージコレクション）：**

    * **PostgreSQL：** バックグラウンドプロセス **`autovacuum`（`VACUUM`）** が定期的にページを走査し、現在稼働中の最古のトランザクションより前に削除・更新が確定した死んだタプルを回収して空き領域へ戻します（さらに 32 ビットトランザクション ID が一周して過去と未来が逆転するのを防ぐ凍結処理も担います）。
    * **MySQL InnoDB：** 最新行だけをテーブル本体へ上書きし、古いバージョンは専用の **Undo ログ領域** へ逃がして、不要になった古い Undo ログをパージスレッドが回収します。

* **運用の注意点：** たった 1 本でも「`BEGIN` したまま何時間も放置された長寿命トランザクション」が存在すると、それより新しい古いバージョンを 1 つも回収できなくなり、データベース全体が急速に肥大化します。

### 5. 接続と展望（Bridge）：本節の内容が後半のどの部に繋がるか

1. **次節（[9-8節](9-8.md)：障害回復［DO-UNDO-REDO・WAL・page LSN と CLR のべき等性・チェックポイント］）：**
    [9-6節](9-6.md)（悲観的 2PL）と本節（TO・OCC・MVTO・MVCC）をもって、ACID の **I（分離性：並行性制御）** の主要アーキテクチャが揃いました。次節では、残る **A（原子性）** と **D（持続性）** を突然の停電やクラッシュから守り抜く **WAL（Write-Ahead Logging）と ARIES リカバリ** へ進みます。

2. **[第3部](../index.md#part-3)（[3-7節](../3/3-7.md) CoW）・[第5部](../index.md#part-5)（[5-6節](../5/5-6.md) CoW ファイルシステム）との構造的回収：**
    「既存データをその場で破壊的に上書きせず、古い版を残したまま新しい版を別に書き出すことで、読み取りとの競合をなくし一貫したスナップショットを提供する」という MVCC の思想は、仮想記憶の Copy-on-Write や ZFS/APFS の CoW ファイルシステムと同型の設計パターンです。

### 理解度チェック（次節へ進む前の確認）

本節の時刻印方式（TO・Thomas・MVTO）・OCC・MVCC と書き込みスキューを確認し、次節（[9-8節](9-8.md)：障害回復と WAL）へ繋ぐ問いを置きます。

> **【確認の問い】**
>
> 1. **（基本 TO・トーマスの書き込み規則・MVTO の手動トレース比較）**
>     データ項目 $X$（初期版 $X_0 = 10$、初期 $\text{R-TS} = \text{W-TS} = 0$）に対して、時刻印 $TS(T_1) = 10$ の $T_1$ と $TS(T_2) = 20$ の $T_2$ が、次の順に操作を要求したとします：
>     `R1(X)` $\to$ `W2(X = 30)` $\to$ `W1(X = 20)` $\to$ `R2(X)`（ただし `W1(X = 20)` で $T_1$ がアボートしない場合は `R2(X)` まで続行します）。
>
>     * (a) **基本 TO** で先頭から処理したとき、どの操作で何が起きるか（$\text{R-TS}(X), \text{W-TS}(X)$ の変化を含め）トレースしてください。
>     * (b) 同じ操作列を **トーマスの書き込み規則** を有効にした TO で処理した場合と、**MVTO** で処理した場合で、`W1(X = 20)` の扱いがどう変わるか（および `R2(X)` が読む最終的な値）を比較してください。
>
> 2. **（書き込みスキューに対する OCC 検証 vs スナップショット分離［SI］）**
>     「2 人の当直医問題」（初期状態：`Alice = ON, Bob = ON`）で、$T_1$ が両行を読んだうえで `Alice` を `OFF` に更新し、$T_2$ も両行を読んだうえで `Bob` を `OFF` に更新するとします。
>
>     * (a) $T_1$ と $T_2$ の Read Set（$RS$）および Write Set（$WS$）をそれぞれ書き出し、$T_1$ が先に Validation・Write を完了した直後に $T_2$ が **楽観的並行制御（OCC：後向き検証）** の Validation フェーズへ入った場合、$T_2$ は合格するかアボートされるかを検証条件の式で示してください。
>     * (b) 同じ操作列が、**スナップショット分離（SI）** では両方コミットできてしまい（書き込みスキュー）、OCC では防げる理由を、両者が衝突検査で比較している集合の違いから説明してください。
>
> 3. **（次節への伏線：バッファプールとクラッシュが交錯したときの 2 つの矛盾）**
>     [9-6](9-6.md)・9-7節で同時実行中の複数トランザクションを隔離する仕組みが揃いました。しかし [9-1節](9-1.md)で学んだ通り、トランザクションが書き換えたページはまず揮発性の RAM（バッファプール）上に置かれます。
>
>     * (a) 停電時の矛盾を防ぐため、「未コミットの変更を含むページは絶対にディスクへ追い出さず、かつコミットの瞬間に変更した全ページを必ずディスクへ書き戻す」という素朴な方針をとった場合、**巨大な更新トランザクションの実行** と **複数ページ更新の I/O 性能（[5-4節](../5/5-4.md)）** でそれぞれどのような深刻な限界が生じるでしょうか。
>     * (b) 逆に「空き枠確保のために未コミットページも先出ししてよい」「コミット時もデータページ本体をすぐには書き戻さなくてよい」と緩めた場合、停電直後のディスク上にはどのような 2 種類の矛盾が残り得るでしょうか。
