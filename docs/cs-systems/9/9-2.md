### 前節（9-1）の確認問題の解答

前節の最後に提示した3つの問いの解答を確認します。問3がそのまま本節（索引構造と LSM-Tree）の導入になります。

1. **スロッテッド・ページのバイト境界トレースとコンパクション：**

    * **(a) `T1` 削除直後の状態：**

        * `T0`（$120\text{ B}$）挿入後：`upper = 8192 - 120 = 8072`、`slot[0] = (8072, 120)`、`lower = 24 + 4 = 28`。
        * `T1`（$300\text{ B}$）挿入後：`upper = 8072 - 300 = 7772`、`slot[1] = (7772, 300)`、`lower = 32`。
        * `T2`（$80\text{ B}$）挿入後：`upper = 7772 - 80 = 7692`、`slot[2] = (7692, 80)`、`lower = 36`。
        * `T1` 削除直後は、`lower = 36`、`upper = 7692`、`slot[0] = (8072, 120)`、`slot[1] = (0, 0)`（空き印）、`slot[2] = (7692, 80)` です。`upper - lower` で表される連続空き領域は $7692 - 36 = \mathbf{7{,}656\text{ B}}$ となります（これとは別に `7772..8071` に $300\text{ B}$ の空き穴が孤立しています）。

    * **(b) コンパクション後の状態と TID が不変である理由：**
        `T2`（$80\text{ B}$）を `T0`（`8072..8191`）の直前 `7992..8071` へ移動すると、新しい `upper` は $8072 - 80 = \mathbf{7992}$、**`slot[2] = (7992, 80)`**、連続空き領域は $7992 - 36 = \mathbf{7{,}956\text{ B}}$（$300\text{ B}$ 分が回復）になります。外部の索引が記憶しているのはページ内の直接バイトオフセットではなく、**`TID = (page_id, 2)`** という不変の論理識別子であり、書き換えるのはページ内部の `slot[2]` のオフセット値だけであるため、外部索引を変更せずに済みます。

2. **バッファプールの `pin_count`・`dirty` ビットとスキャン汚染：**

    * **(a) ステップ ④ と ⑥ の挙動：**

        * **ステップ ④（`FetchPage(P4)`）：** この時点で 3 フレームすべてが `pin_count == 1 > 0`（使用中）であるため追い出し可能な犠牲フレームが存在せず、空きができるまで**待機（またはエラー）**となります。
        * **ステップ ⑥（⑤ で `P1` に続いて `P2` をアンピンした後の `FetchPage(P4)`）：** キャッシュミスとなり、置換リスト（`pin_count == 0` の候補 `P1`, `P2`）から LRU に従って先にアンピンされた `P1`（フレーム `F0`）が犠牲に選ばれます。`P1` は **`dirty == 1`** であるため、まず WAL 規則に従って対応ログがディスクへ永続化されていることを確認したうえで **`P1` をディスクへフラッシュ（書戻し）** し、ページテーブルから `P1` を削除して `F0` へ `P4` を読み込みます（`pin=1, dirty=0`）。

    * **(b) スキャン汚染と LRU-2 / Midpoint Insertion による防御：**
        単純 LRU では 1 回限りの `S1..S5` が次々と MRU 側へ入るため、容量 3 フレームの LRU 端から `P_root` が追い出されてしまいます（スキャン汚染）。これに対し **LRU-2** は「過去 2 回目の参照時刻」を比較するため、1 回しか参照されていない `S_i`（2 回目の参照時刻 $-\infty$）が 10 回参照された `P_root` を追い出せません。また **Midpoint Insertion** では新規ページが中間点（Old 先頭）へ挿入されるため、再参照されない `S_i` は Young 領域へ昇格せず Old 領域を素通りし、Young 領域の `P_root` が保護されます。

3. **固定長ページ単位の I/O と 1,000 万行の検索コスト（本節への接続）：**

    * **(a) ヒープファイル全走査のページ読込み回数：**
        索引がない場合、最悪で全 **$200{,}000$ 回**、一様位置なら平均で約 **$100{,}000$ 回**（$(200{,}000 + 1)/2$）のページ読込みが必要です。

    * **(b) 素朴な二分探索のページ読込み回数と無駄：**
        $10^7$ 件を半分ずつ絞り込む二分探索では、$2^{23} = 8{,}388{,}608 < 10^7 < 2^{24} = 16{,}777{,}216$ より最大で **約 $24$ 回**（終盤で同一ページに収まる数ステップを除いても 15〜20 回程度）のページ読込みが発生します。$8\text{ KiB}$ のページを丸ごと 1 枚読み込んでいるにもかかわらず、そのうち「たった 1 組のキー」を比較するだけで別のページへ飛んでしまい、1 ページに入れられる数百個分の分岐情報を活かせていない点が非効率です。1 ページの容量に合わせて分岐数を増やす **$\text{B}^+$ 木** がこの無駄を解消します。

## 9-2. 索引構造（動的ハッシュ・B木・$\text{B}^+$木）と LSM-Tree の対比

### 1. 動機（Why）：なぜ通常の二分探索木では遅く、ディスク専用の索引構造が必要なのか

前節（[9-1節](9-1.md)）で、テーブルの各行（タプル）を固定長ページ（$8\text{ KiB}$ や $16\text{ KiB}$）の中へ収め、`TID = (page_id, slot_num)` で指し示し、バッファプールへ読み込む土台が整いました。

しかし、ページをただ並べただけの **ヒープファイル（Heap File）** に 1 億行のデータが入っているとき、`SELECT * FROM Students WHERE sid = 2026001;` を実行すると、最悪で先頭から末尾まですべてのページ（数百万ページ）を順番に読み込む **$O(N)$ の全件走査（Full Table Scan）** になり、数秒〜数十秒かかってしまいます。

本の巻末にある「索引（インデックス）」のように、検索キー（`sid`）から目的の `TID` へ直接飛びたいところです。ここでアルゴリズムの基礎を思い出すと、「赤黒木や AVL 木のような**平衡二分探索木**を使えば $O(\log_2 N)$ で探せるのではないか」と思えるかもしれません。

ところが、ディスクや SSD 上のデータベースで平衡二分探索木をそのまま使うと、[5-4節](../5/5-4.md)で学んだストレージの物理特性によって深刻な性能問題が起きます。

1. **木の高さ（ディスク I/O 回数）が大きすぎる：**
    1 億行（$N = 10^8$）を二分探索木（分岐数 $2$）に入れると、木の高さは $\log_2(10^8) \approx \mathbf{27\text{ 段}}$ になります。1 段降りるたびに離れたディスクページへランダムアクセスすると、HDD なら $27 \times 9\text{ ms} \approx 240\text{ ms}$ もかかり、1 ページ（$8\text{ KiB}$）にたった 1 ノード（数十バイト）しか入らず空間も浪費します。

2. **範囲検索とランダム書き込みのトレードオフ：**
    完全一致検索（`sid = 2026001`）だけでなく、範囲検索（`age BETWEEN 20 AND 25`）や大量のランダム挿入（ログ収集・IoT 書き込み）をどう高速化するかによって、最適なデータ構造は大きく異なります。

本節では、ディスクのページ単位 I/O に最適化された索引構造である **動的ハッシュ（Extendible Hashing）**、**B木・$\text{B}^+$木**、そして書き込み特化型の **LSM-Tree** の仕組みとトレードオフを整理します。

---

### 2. 具体例と動作イメージ（Toy Model）

細部のアルゴリズムに入る前に、たった 1 つの計算で「$\text{B}^+$ 木の浅さ」を確かめます。

#### 実験A：1 億行の検索に必要なディスク I/O 回数（二分木 vs $\text{B}^+$ 木）

1 ページのサイズを $8\text{ KiB}$（$8{,}192\text{ B}$）、検索キー（`BIGINT`）が $8\text{ B}$、子ページ番号（ポインタ）または `TID` が $8\text{ B}$ だとします。1 組の「キー＋ポインタ（葉ではキー＋`TID`）」は合計 $16\text{ B}$ です。

すると、ページヘッダを除いた $8{,}000\text{ B}$ 強の領域の中に、**たった 1 枚の $8\text{ KiB}$ ページ（1 ノード）だけで約 $500\text{ 本}$ もの枝（分岐数＝ファンアウト $F \approx 500$）** を詰め込むことができます。各ノード（内部ノードおよび葉ノード）が平均 70%（1 ノードあたり分岐数・収容件数 $F \approx 350$）埋まっているとして、木の高さごとに収容できる最大キー数を計算してみましょう。

* **高さ 1（ルート兼葉が 1 枚）：** $350$ 件
* **高さ 2（ルート → 葉）：** $350^2 = 122{,}500$ 件（約 12 万件）
* **高さ 3（ルート → 内部 → 葉）：** $350^3 = 42{,}875{,}000$ 件（約 4,287 万件）
* **高さ 4（ルート → 内部 → 内部 → 葉）：** $350^4 \approx \mathbf{1.50 \times 10^{10}}$ 件（**約 150 億件**）

二分探索木なら 27〜34 回もディスク I/O が必要だった 1 億〜150 億件の検索が、分岐数をページサイズに合わせて増やした多木（$\text{B}^+$ 木）なら、**わずか高さ 3〜4 段**で到達できます。しかもルートノードと上位段は [9-1節](9-1.md)のバッファプール（RAM）に留まり続けるため、**実際のディスク I/O は 1〜2 回程度**で完了します。

### 3. 構造・アルゴリズム・実装（What）

#### (1) 静的ハッシュの限界と動的ハッシュ（Extendible Hashing）

範囲検索が不要で **完全一致検索（`WHERE id = 123`）** だけを最速 **$O(1)$** で行いたいときに使うのが **ハッシュ索引** です。

素朴な **静的ハッシュ（Static Hashing）** では、あらかじめ固定個数 $M$ 個のバケット（ページ）を用意し、`hash(key) % M` 番目のバケットへ格納します。しかしデータベースの行数が後から 10 倍に増えると、バケットが溢れて長いオーバーフローページ連鎖ができ、検索が $O(N)$ へ劣化します。かといって $M$ を 2 倍にして全バケットを作り直す（リハッシュ）と、数億行の再配置でシステムが長時間止まってしまいます。

この問題を「溢れた 1 バケットだけを局所的に分割する」ことで解決するのが **動的ハッシュ（Extendible Hashing：拡張可能ハッシュ）** です（図9-2-1）。

* **2 層の間接参照構造：**

    1. **ディレクトリ配列：** サイズ $2^d$（$d$ を **グローバル深さ：Global Depth** と呼びます）のポインタ配列です。ハッシュ値の下位（または上位）$d$ ビットを添字としてバケットを指します（図9-2-1 では下位ビット参照の例を示します）。
    2. **バケット（ディスクページ）：** 各バケットは自分自身のビット精度である **ローカル深さ（Local Depth：$k \le d$）** を持ちます。$k < d$ のバケットは、複数のディレクトリエントリから共有して指されます（たとえば $d = 2, k = 1$ で下位ビットのみ区別するとき、`00` と `10` が同じバケットを指します）。

* **バケットが満杯になったときの分割ルール：**

    * **ケース 1（$k < d$ のとき）：** ディレクトリ配列は広げず、溢れたバケットだけを 2 つに分割して両方のローカル深さを $k + 1$ に上げ、ディレクトリ上の該当ポインタだけを付け替えます（**ディスク上で書き換えるバケットは新旧 2 ページだけです**）。
    * **ケース 2（$k == d$ のとき）：** もうビット精度が足りないため、ディレクトリ配列のサイズだけを 2 倍（$d \leftarrow d + 1$）にしてから溢れたバケット 1 つだけを分割します。ディレクトリは小さなポインタ配列なのでメモリ上で高速に 2 倍化でき、**他の満杯でないバケットのディスクページは一切動かさずに済みます**（※なお、同じバケットの全キーが次のビットでも片方に偏った場合は再度分割を繰り返し、ハッシュ値が同一の重複キーだけでバケットが溢れた場合にのみ例外的にオーバーフローページを繋ぎます）。

ただし、ハッシュ索引には **「範囲検索（`age >= 20 AND age <= 30`）や並べ替え（`ORDER BY`）に一切使えない」** という構造的な弱点があります（ハッシュ関数がキーの大小順序を完全にバラバラにしてしまうためです）。そのため、RDBMS のデフォルト索引として広く使われるのは次に学ぶ **$\text{B}^+$ 木** です。

#### (2) B木 vs $\text{B}^+$木：なぜ RDBMS は B木ではなく「$\text{B}^+$木」を採用するのか

1970年にルドルフ・バイヤーらが考案した **B木（B-Tree）** は、1 ノードをちょうどディスク 1 ページサイズに合わせ、すべての葉ノードがルートから**常に同じ深さ（完全平衡）**を保つ多木（1 ノードあたり最大 $m$ 本の子ポインタ＝ $m - 1$ 個のキーを持てる $m$ 分木）です。ルート以外の各内部ノードは常に最低半分（$\lceil m/2 \rceil$ 本以上の子＝ $\lceil m/2 \rceil - 1$ 個以上のキー）を保持するため、データの挿入・削除を繰り返しても木が偏って細長くなることがありません。実験Aの $8\text{ KiB}$ ページ（1 組 $16\text{ B}$）なら 1 ノードに約 $500$ 本の枝が収まり、平均 70% 充填（$F \approx 350$）でも高さ 3 で $350^3 \approx 4{,}287\text{ 万}$ 件、高さ 4 で $350^4 \approx 150\text{ 億}$ 件に到達できます。

現代のほぼすべての RDBMS（PostgreSQL, MySQL InnoDB, SQLite, Oracle）が採用しているのは、B木をさらに改良した **$\text{B}^+$ 木（B+ Tree）** です。B木と $\text{B}^+$ 木には、次の **2 つの決定的な違い** があります（図9-2-2）。

1. **データ実体（あるいは TID）を「葉ノードだけ」に置く：**

    * 元の **B木** では、ルートや内部ノード（非葉ノード）にもキーと一緒にタプル本体や TID を格納するため、1 ページに入るキーの個数（分岐数＝ファンアウト）が減って木が高くなりがちです。
    * **$\text{B}^+$ 木** では、内部ノードには道案内用の「キーと子ページ番号」だけをぎっしり詰め込み、実際の TID（またはタプル本体）はすべて最下層の **葉ノード** にだけ置きます。これにより分岐数 $F$ が大きくなり、木の高さが最小限（3〜4 段）に抑えられます。

2. **すべての葉ノードを横方向の「双方向連結リスト」で繋ぐ：**

    * 範囲検索 `WHERE key BETWEEN 20 AND 50` を実行するとき、$\text{B}^+$ 木はまずルートから 3〜4 ホップで開始値 `20` を含む葉ノードへ降り、**あとはルートへ戻ることなく、葉ノードの横方向ポインタを辿って `50` まで一直線にシーケンシャル走査**するだけで完了します（元の B木では何度も親ノードへ上がったり降りたりする中順序走査が必要でした）。

**$\text{B}^+$ 木の挿入（分割）と削除（統合）の動作：**

* **挿入と分割（Split）：** キーを葉ノードへ挿入して満杯になったら、葉を半分ずつ 2 ページへ分割し、右側の最小キーの**コピー**を親の内部ノードへ押し上げます（元の B木と異なり、葉のすべてのキーを残すためコピーを上げます）。もし親の内部ノードも満杯なら中央のキーをさらに上の親へ**移動**させて分割が連鎖し、ルートが分割された瞬間にだけ木の高さが 1 段増えます（**ボトムアップに成長するため、常に完全平衡が保たれます**）。
* **削除と借用／統合（Merge）：** 削除によって葉ノードのエントリ数が半分未満になったら、隣の兄弟ノードからエントリを 1 個借りる（再分配）か、兄弟と合体（マージ）して親の境界キーを削除します（なお実用 DBMS では削除後の再挿入を見込み、完全に空になるまで統合を遅らせることも多くあります）。

#### (3) クラスタ索引（一次索引）vs 非クラスタ索引（二次索引）とカバリングインデックス

$\text{B}^+$ 木の葉ノードの先に「実際の行データ」がどう並んでいるかによって、索引は 2 種類に分類されます。

* **クラスタ索引（Clustered Index / 一次索引）：**
    テーブルのタプル本体そのものが、**索引キー（通常は主キー）の順序通りに物理ディスクページへ並んで格納されている**索引です（MySQL InnoDB は主キー $\text{B}^+$ 木の葉ノード自体にタプル本体を格納する「索引構成表」です）。物理的な並び順は 1 通りしか持てないため、**1 テーブルにつき最大 1 個**しか作れません。範囲検索でページを連続読み込みできるため高速です。

* **非クラスタ索引（Non-Clustered Index / 二次索引）：**
    主キー以外の列（例：`Students.name` や `Students.dept_id`）に後から追加する索引です。葉ノードにはキーと **TID**（または InnoDB のようにクラスタ索引の主キー値）だけが格納されます。したがって、二次索引で `TID`（または主キー値）を見つけたあと、さらにヒープファイル（または主キー $\text{B}^+$ 木）へ **もう 1 回以上のアクセス（ルックアップ）** を行って残りの列を取り出す必要があります。

* **カバリングインデックス（Covering Index / Index-Only Scan）：**
    もしクエリが必要とするすべての列が二次索引自身に含まれている場合（例：`INDEX(dept_id, name)` に対して `SELECT name FROM Students WHERE dept_id = 'CS'`）、葉ノードを読むだけで答えが揃うため、**テーブル本体へのランダムアクセスを完全に 0 回へ省く**ことができます。

#### (4) 書き込みの壁を超える LSM-Tree（Log-Structured Merge-Tree）

$\text{B}^+$ 木は読み取りと範囲検索に適した構造ですが、IoT センサーデータ、チャットメッセージ、アクセスログのように **毎秒何十万件ものランダムな `INSERT` / `UPDATE` が降り注ぐワークロード** では弱点が露呈します。ランダムなキーを $\text{B}^+$ 木へ挿入するたびに、ディスク上のあちこちの葉ページをランダムに書き換え、満杯になればページ分割が連鎖して **膨大なランダム書き込み I/O** が発生するからです。

[5-4節](../5/5-4.md)で確認した通り、HDD でも SSD（書き込み増幅）でも、**ランダム書き込みよりシーケンシャル追記（Sequential Append）の方が桁違いに高速** です。この物理特性を最大限に活かし、**「すべてのランダム書き込みを、メモリ上のソート＋ディスクへのシーケンシャル追記へ変換する」** データ構造が **LSM-Tree（Log-Structured Merge-Tree）** です（RocksDB, LevelDB, Apache Cassandra, HBase 等の中核エンジン：図9-2-3）。

LSM-Tree の書き込みと読み取りは、次のコンポーネントの連携で動作します。

1. **書き込み（ランダム I/O ゼロ）：**
    新しい `(key, value)` が来ると、まず停電耐性のためにディスク末尾の **WAL（追記ログ）** へシーケンシャルに書き、同時に RAM 上の平衡木である **MemTable**（赤黒木やスキップリスト）へソート順で挿入して即座に完了を返します。

2. **フラッシュ（Flush → SSTable 生成）：**
    MemTable が一定サイズ（例：$64\text{ MiB}$）に達したら、それを書き込み禁止（Immutable）へ切り替え、キー順にソートされたまま **ディスクへ 1 回の大きなシーケンシャル書き込み** として書き出します。この不変（一度書いたら絶対に上書きしない）のソート済みファイルを **SSTable（Sorted String Table）** と呼びます。

3. **コンパクション（Compaction：階層マージ）：**
    SSTable は時間が経つにつれて多数溜まっていきます（削除されたキーには「削除済み」の印である **Tombstone［墓石］** レコードが追記されます）。このままでは読み取り時に調べるファイル数が増えすぎるため、バックグラウンド処理がすでにキー順にソート済みの古い複数 SSTable を k-way マージして 1 つの大きな新 SSTable へ統合し、上書きされた古い値や Tombstone を掃除します（**Level 0 → Level 1 → Level 2 ...** と下位レベルほど容量が 10 倍ずつ大きくなる **Leveled Compaction** では、L0 内の SSTable 同士はキー範囲が重複し得る一方、L1 以降の同一レベル内ではキー範囲の重複がないよう整理されます）。

4. **読み取りとブルームフィルタ（Bloom Filter）：**
    `GET(key)` が来たら、最新データから順に **MemTable → L0 SSTable 群 → L1 → L2 ...** と探していきます。
    ここで「そもそもその SSTable の中に `key` が入っていないのに毎回ディスクを読みに行く無駄」を削るのが、各 SSTable に添えて RAM 上へキャッシュされる超小型の確率的ビット配列 **ブルームフィルタ（Bloom Filter）** です。ブルームフィルタは $m$ ビットの配列（初期値 `0`）と $k$ 個の独立なハッシュ関数を用い、登録時に $k$ か所のビットを `1` に立てます。検索時に $k$ か所のうち **1 つでも `0` があればそのキーは 100% 確実に存在しない**（偽陰性ゼロ）と即判定できます（すべて `1` でも別キーのビットと衝突したわずかな偽陽性の可能性はありますが、無関係な SSTable のディスク I/O をほぼすべてスキップできます）。

> **【コラム：索引は「タダ」ではない — 索引を増やしすぎたときに起きる書き込み増幅とキャッシュ圧迫】**
>
> 「索引を貼れば `SELECT` が速くなるなら、テーブルの全 20 列すべてに $\text{B}^+$ 木インデックスを貼ってしまえばよいのではないか」と考える人は少なくありません。しかし、実務でむやみに索引を増やすと、システム全体の性能が逆に低下します。
>
> 1. **書き込みコストの線形増大：** 1 個のテーブルに 10 本の索引が張られていると、たった 1 行の `INSERT` や `DELETE`（あるいは索引列の `UPDATE`）を実行するたびに、テーブル本体に加えて **10 本すべての $\text{B}^+$ 木のページを探して更新・分割・WAL 記録** しなければなりません。
> 2. **バッファプールとストレージの圧迫：** 巨大な索引群がディスク容量だけでなく、有限な RAM 上のバッファプール（[9-1節](9-1.md)）を圧迫し、よく使うデータページを追い出してキャッシュヒット率を下げてしまいます。
>
> したがって実務では、実際のスロークエリログと `EXPLAIN`（実行計画）をもとに、「よく `WHERE` や `JOIN` や `ORDER BY` に使われ、かつ絞り込み効果（選択性）が高い列」だけを厳選して最小限の索引を設計するのが基本です。

### 4. 限界と補正（Critique & Adaptation）

#### (1) $\text{B}^+$ 木 vs LSM-Tree の 3 大トレードオフ（読み・書き・空間増幅）

データベースのストレージエンジン設計では、**読み取り増幅（Read Amplification：1 件の論理読取で実際に何倍のページ／SSTable を読むか）**、**書き込み増幅（Write Amplification：1 回の論理書込で実際に何倍のバイト数をディスクへ書くか）**、**空間増幅（Space Amplification：論理データ量に対する実ファイル消費量の倍率）** の 3 つを同時に最小化することはできないという経験則（RUM 予想）が知られています。

| 比較項目 | $\text{B}^+$ 木（更新型：In-place Update） | LSM-Tree（追記型：Out-of-place Append） |
| :--- | :--- | :--- |
| **読み取り・範囲検索** | **高速**（常に 1 本の木を 3〜4 ホップ辿るだけ） | やや不利（複数レベルの SSTable を確認する必要あり。Bloom Filter で補正） |
| **ランダム大量書き込み** | 不利（ページ単位のランダム更新＋分割で書き込み増幅大） | **高速**（MemTable＋WAL のシーケンシャル追記で完了） |
| **空間効率（ディスク容量）** | ページ内空き（平均 30% 程度）が残る | コンパクション前は旧値・墓石が重複するが、圧縮率は高い |
| **バックグラウンド負荷** | 予測可能・安定している | コンパクション実行時にディスク I/O スパイク（レイテンシ悪化）が起き得る |
| **主な採用例** | PostgreSQL, MySQL (InnoDB), SQLite, Oracle | RocksDB, LevelDB, Cassandra, CockroachDB (Pebble) |

#### (2) 複合索引の「最左プレフィックス原則」と、索引が逆効果になる選択率

複数列を組み合わせた $\text{B}^+$ 木索引 **`INDEX(a, b, c)`** を作ったとき、キーは「まず `a` 順、同じ `a` なら `b` 順、同じ `(a, b)` なら `c` 順」という**辞書式順序**で葉ノードに並びます。そのため、

* `WHERE a = 1` や `WHERE a = 1 AND b = 2` は先頭から一致するため索引が効きます（ただし `WHERE a = 1 AND c = 3` のように途中の `b` が抜けると、`a = 1` の絞り込みにしか索引を使えません）。
* しかし **`WHERE b = 2`**（先頭の `a` を指定しない条件）では電話帳を「下の名前だけ」で引くのと同じになり、この複合索引を原則として使えません（**最左プレフィックス原則：Leftmost Prefix Rule**）。

また、性別（`male` / `female`）のように**テーブル全体の 50% がヒットするような選択率の低い条件**に二次索引を使うと、葉ノードからヒープファイルへのランダム I/O が大量に発生し、**最初からヒープファイル全体をシーケンシャルスキャンした方が何倍も速い**という逆転現象が起きます。この「索引を使うべきか、全表走査すべきか」をコスト計算で自動判断するのが、次々節（[9-4節](9-4.md)）の問合せ最適化器です。

#### (3) $\text{B}^+$ 木へのマルチスレッド同時アクセスと「ラッチ結合（Latch Crabbing）」

複数スレッドが同時に 1 本の $\text{B}^+$ 木へ `INSERT`（ノード分割）と `SELECT` を実行すると、木構造が壊れます。もしルートノードに 1 本の排他ラッチを掛け続けると [4-1節](../4/4-1.md)の Amdahl の法則で並列性が低下します。

これに対する補正が **ラッチ結合（Latch Crabbing / Latch Coupling）** です。木を上から下へ降りるとき、次のように操作種別に応じてラッチをバトンリレー（[4-4節](../4/4-4.md)の `sleep` のロック引き継ぎと同型）で渡します。

* **検索（`SELECT`）：** 親の S ラッチを握ったまま子の S ラッチを獲得したら、即座に親の S ラッチを解放して下へ降ります。
* **挿入・削除（`INSERT` / `DELETE`）：** 親の X ラッチを握ったまま子の X ラッチを獲得し、**子ノードが「分割も統合も絶対に起きない安全な状態（挿入なら空きあり、削除なら半分超が埋まっている）」だと確認できた瞬間に、保持していた上位の親ラッチ群をすべて解放**します。これにより、ルート付近の競合を抑えつつ木構造の整合性を守れます。

> 2. **（複合索引の誤用の反証と $\text{B}^+$ 木 vs LSM-Tree の比較）**
>
>     * (a) 1,000 万行のテーブル `Orders(order_id, status, created_at)` に対し、複合 $\text{B}^+$ 木索引 `INDEX(status, created_at)` を張りました（全行の $80\%$ は `status = 'SHIPPED'` です）。開発者が「① `WHERE created_at >= '2026-01-01'` の検索もこの複合索引だけで高速化できる」「② `WHERE status = 'SHIPPED'` も索引がある以上、全表走査より必ず速い」と主張しました。それぞれの誤りを**最左プレフィックス原則**と**選択率・ランダム I/O** の観点から反論してください。
>     * (b) 大量のランダム `PUT` が発生するログ収集システムでは $\text{B}^+$ 木より **LSM-Tree** が有利になりやすい理由をディスク I/O パターンの違いから説明し、逆に LSM-Tree を採用することで新たに発生する 2 つの運用・性能上の負担（読み取り側とバックグラウンド処理）を挙げてください。
