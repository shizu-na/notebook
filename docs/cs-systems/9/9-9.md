### 前節（9-8）の確認問題の解答

前節の最後に提示した3つの問いの解答を確認します。問3がそのまま最終節（分散システムへの展望と全10部の総括）の導入になります。

1. **ARIES の 3 フェーズ（Analysis・REDO・UNDO）と `pageLSN` / CLR の手動トレース：**

    * **(a) Analysis フェーズの結果（ATT と DPT）：**
        `LSN 10` から末尾まで走査すると、`T1` は `LSN 30` で `COMMIT` して勝者（ATT から除外）となり、`T2` だけが未確定の敗者として残ります。各ページが最初にダーティになった LSN は `Page A` が `10`、`Page B` が `20` です（`LSN 40, 50` ではすでに DPT に登録済みなので `recLSN` は更新されません）。

        * **ATT（敗者 TX）：** `{ T2: lastLSN = 50 }`
        * **DPT（ダーティページ）：** `{ Page A: recLSN = 10,  Page B: recLSN = 20 }`

    * **(b) REDO フェーズ（`min recLSN = 10` から末尾まで）：**

        * `LSN 10`（`Page A`）：ディスク上の `pageLSN(A) = 10 >= 10` $\implies$ **スキップ**（`A = 200`, `pageLSN = 10`）。
        * `LSN 20`（`Page B`）：ディスク上の `pageLSN(B) = 50 >= 20` $\implies$ **スキップ**（`B = 50`, `pageLSN = 50`）。
        * `LSN 40`（`Page A`）：ディスク上の `pageLSN(A) = 10 < 40` $\implies$ **REDO 実行**（`A = 300`, `pageLSN = 40`）。
        * `LSN 50`（`Page B`）：ディスク上の `pageLSN(B) = 50 >= 50` $\implies$ **スキップ**（`B = 50`, `pageLSN = 50`）。
        * **REDO 完了時点：** `Page A = 300`（`pageLSN = 40`）、`Page B = 50`（`pageLSN = 50`）。

    * **(c) UNDO フェーズで出力される CLR の並びと最終値：**
        敗者 $T_2$ の `lastLSN = 50` から `prevLSN` を逆順に辿って取り消し、CLR を追記します。

        1. `LSN 50` を取消 $\implies$ **`CLR(T2, Page B = 100, UndoNextLSN = 40)`**（`B = 100`）。
        2. `LSN 40` を取消 $\implies$ **`CLR(T2, Page A = 200, UndoNextLSN = 20)`**（`A = 200`）。
        3. `LSN 20` を取消 $\implies$ **`CLR(T2, Page B = 500, UndoNextLSN = NULL)`**（`B = 500`、続けて $T_2$ の `END` を記録）。
        * **最終値：** **`Page A = 200`**, **`Page B = 500`**（勝者 $T_1$ の変更は保持され、敗者 $T_2$ の変更はすべて取り消されます）。

2. **WAL の 2 規則の欠落と、UNDO 途中の再クラッシュに対する CLR：**

    * **(a) 各規則を省略した場合の破綻：**

        * **規則②（`COMMIT` 応答前の WAL `fsync`）を省略した場合：** アプリへ `COMMIT` 成功を返した直後、ログがまだ RAM 上に留まったまま停電すると、再起動時の WAL に `COMMIT`（や更新ログ）が残っておらず、確定したはずの変更が失われる（または未確定とみなされて UNDO される）ため **持続性（D）が破綻** します。
        * **規則①（ダーティページ追出し前の WAL `fsync`）を省略した場合：** 未コミットの変更を含むページが先にディスクへ書き出され、その変更前イメージ（UNDO 情報）を含む WAL がまだ RAM にある状態で停電すると、再起動後に未コミットの書き込みを取り消す手掛かりがなくなり **原子性（A）が破綻** します。

    * **(b) 2 回目停電で `LSN 50` が重複取り消しされない理由：**
        3 回目の起動時の Analysis で $T_2$ の最新記録として `LSN 60 (CLR)` が読み込まれます。REDO フェーズでは `pageLSN(B) = 60 >= 60` によりスキップ（未反映でも `CLR` により `B = 100` に復元）されます。続く UNDO フェーズでは、`LSN 60` が `CLR` であるため自身は取り消さず **`UndoNextLSN = 40` へ直接ジャンプして `LSN 50` を飛び越す** ため、同じ UNDO が二重に適用されることは決してありません。

3. **単一マシンの WAL が「東京と大阪の 2 台」では足りなくなる理由（本節への接続）：**
    東京へ先に `COMMIT` を送ってローカル WAL へ永続化した直後、大阪へ `COMMIT` を送る前にネットワーク分断・大阪サーバのクラッシュ・制約違反アボートが起きると、東京のローカル WAL はすでに `COMMIT` を確定済みのため取り消せず、大阪には入金されないまま **「東京だけ 2 万円減少・大阪は増えず」という原子性（All-or-Nothing）の破綻** が起きます。各ノードのローカル WAL は自ノード単独の永続性しか守れないため、ノード間で事前に準備確認と決定を揃える分散合意プロトコル（本節の **2 相コミット**）が必要になります。

## 9-9. 分散システムへの展望と全10部の総括（2相コミット・CAP定理の入口）

### 1. 動機（Why）：なぜ「1台のマシンで正しく動いた OS と DB」が、2台に分けた瞬間に別次元の難問になるのか

[第0部](../index.md#part-0)から前節（[9-8節](9-8.md)）までを通じて、1 台のコンピュータの内部で電気信号から CPU パイプライン、コンパイラ、OS、ファイルシステム、並行性制御、そして ACID 特性を守る RDBMS（2PL / MVCC / ARIES）までがどう噛み合って動くかを一通り整理しました。

しかし、現代のインターネットサービス（クラウド、決済基盤、SNS、検索エンジン）は、もはや 1 台のサーバには収まりません。次の 2 つの避けられない理由から、システムを **複数台のマシンへ分散** させる必要が生じます。

1. **物理容量と性能の上限（スケールアウトの必然性）：** 1 台のサーバに積める CPU コア数・RAM 容量・SSD 容量には物理的な上限があります。ペタバイト級のデータや毎秒数百万リクエストを捌くには、データを複数台へ分割配置する **シャーディング（Sharding：水平分割）** が不可欠です。
2. **耐障害性と地理的遅延の壁（レプリケーションの必然性）：** [9-8節](9-8.md)の最後で確認した通り、1 台のサーバの SSD が物理破損したり、データセンター全体が停電・地震で被災したりすれば、ローカルの WAL ごとデータが消滅します。データを複数台・複数地域へ複製する **レプリケーション（Replication）** によって初めて高い可用性と災害耐性が得られます。

ところが、第6〜7部で学んだ **「遅延・パケット欠損・回線分断が起きるネットワーク」** の上へ複数台のデータベースを広げた瞬間、単一マシンでは存在しなかった **3 つの根本的な壁** が立ちはだかります。

* **共有時計の不在：** 各サーバのクロックはわずかにズレるため、「どちらのイベントが先に起きたか」の絶対的な共通時刻が存在しません。
* **部分故障（Partial Failure）：** 単一マシンなら「全体が動くか、全体が止まるか」の二択ですが、分散システムでは「10 台のうち 1 台だけが遅い・落ちた」状態が日常的に起きます。
* **停止と遅延の区別不能性：** 相手サーバから 5 秒間返事がないとき、「相手がクラッシュして停止した」のか、「相手は生きているが途中のルータが混雑してパケットが遅れているだけ」なのかを、ネットワーク越しには原理的に区別できません。

本節では、単一マシンの集大成（第0〜9部）から **分散システム** の世界へ踏み出す入口として、**2 相コミット（2PC）** と **CAP 定理**、さらに **合意アルゴリズム（Paxos / Raft）と結果整合性** を整理し、最後に **全10部・全76節を貫く横断構造** を総括します。

### 2. 具体例と動作イメージ（Toy Model）

理論の定式化に入る前に、2 つの小さなシナリオで「分散原子性の難しさ」と「ネットワーク分断時の二者択一」を確かめます。

#### 実験A：東京 DB と大阪 DB をまたぐ送金トランザクションのジレンマ

銀行の口座 $A$（10 万円）が **東京サーバ（ノード1）**、口座 $B$（10 万円）が **大阪サーバ（ノード2）** に分かれて格納されているとします。口座 $A$ から口座 $B$ へ 2 万円を送金するトランザクションを考えます。

前節の問い 3 で見た通り、アプリが素朴に「東京へ `COMMIT` を送り、続いて大阪へ `COMMIT` を送る」と、東京が `COMMIT` に成功して 2 万円引いた直後に大阪が「残高上限エラー」または「停電」でアボートしたとき、**東京からは 2 万円消えたのに大阪には 2 万円増えない** という原子性（A）の崩壊が起きます。

これを防ぐには、「まず両方のサーバへ『本当にコミットできる準備ができているか（ロックも WAL も済んだか）』と事前確認し、**全員が『YES（準備完了）』と答えたときだけ**『全員コミットせよ』と号令をかける」という **2 段階の合意手順（2 相コミット）** が必要になります。

#### 実験B：東京と大阪の間の海底ケーブルが切断された瞬間の選択（CAP 定理の直感）

今度は、同じ口座 $A$（初期残高 10 万円）のコピー（レプリカ）を、災害対策のために **東京サーバ** と **大阪サーバ** の両方に置いて同期しているとします。

ある瞬間、東京と大阪を結ぶ幹線ネットワークが完全に切断されました（**ネットワーク分断：Partition**）。両サーバ自身は元気に動いていますが、互いに 1 パケットも通信できません。このまさに分断中に、東京のユーザから「口座 $A$ を 10 万円 $\to$ 15 万円へ更新せよ」という書き込み要求が届きました。

システム設計者には、次の **2 つに 1 つの選択肢** しか残されていません（図9-9-2）。

1. **選択 1（一貫性 C を守る $\implies$ 可用性 A を諦める）：**
    大阪サーバへ変更を伝えて同意を得られないため、東京サーバは **エラーを返して書き込み要求を拒否（または分断が直るまで停止）** します。これで「東京は 15 万円、大阪は古い 10 万円」という食い違い（不整合）は絶対に起きませんが、サービスは一時停止します（**CP 型**）。

2. **選択 2（可用性 A を守る $\implies$ 強い一貫性 C を諦める）：**
    サービスを止めないため、東京サーバは単独で 15 万円への更新を受け付けて「成功」と返します。しかしその瞬間、大阪サーバへアクセスした別ユーザには古い **10 万円** が見えてしまい、両ノードの間でデータが一時的に矛盾します（**AP 型**）。

切れたケーブルの向こうへ情報を瞬時に届けることは物理的にできないため、**ネットワーク分断が起きた瞬間に強い一貫性 C と可用性 A の両方を同時に満たすことは不可能** なのです。

### 3. 構造・アルゴリズム・実装（What）

#### (1) 分散トランザクションの原子性：2 相コミット（2PC）と状態遷移・ブロッキング問題

実験Aの「複数ノード（参加者：Participant）にまたがるトランザクションを、全員コミットするか全員アボートするか（All-or-Nothing）で統一する」標準プロトコルが **2 相コミット（2PC：Two-Phase Commit）** です。調整役である **コーディネータ（Coordinator）** と各参加者ノードがローカルの WAL（[9-8節](9-8.md)）へ状態を永続化しながら、次の 2 フェーズで状態遷移を進めます（図9-9-1）。

* **第 1 相：投票フェーズ（Prepare / Voting Phase）**

    1. コーディネータ（初期状態 `INIT`）は、すべての参加者へ **`PREPARE`** メッセージを送信して待機状態（`WAIT`）へ移ります。
    2. 各参加者（`INIT`）は、ローカルのロック保持とデータ変更の WAL 永続化を完了させ、確実にコミットできる状態になったら **`PREPARED` レコードを自身の WAL へ `fsync`** して不確定状態（**`PREPARED` 状態**）へ入り、コーディネータへ **`VOTE_COMMIT`（YES）** を返します（制約違反や障害で無理な場合は自身の WAL へ `ABORT` を書いて即ローカルアボートし、**`VOTE_ABORT`（NO）** を返します）。

* **第 2 相：決定フェーズ（Commit / Decision Phase）**

    3. コーディネータは、**すべての参加者から `VOTE_COMMIT` が揃った場合のみ**、自身の WAL へ **`COMMIT` レコードを `fsync`** し（これが分散トランザクション全体の確定点です）、`COMMIT` 状態へ遷移して全参加者へ **`GLOBAL_COMMIT`** を送信します。1 台でも `VOTE_ABORT`（または無応答タイムアウト）があれば、WAL へ `ABORT` を書いて全参加者へ **`GLOBAL_ABORT`** を送ります。
    4. 各参加者は指示に従ってローカルで `COMMIT`（または UNDO による `ABORT`）を WAL へ記録してロックを解放し、コーディネータへ **`ACK`** を返します（全員の `ACK` を受け取ったコーディネータは `END` を記録して完了します）。

**2PC における障害の種類とブロッキング問題：**

* **参加者が投票前に停止した場合（ブロックしない）：** 参加者が `VOTE_COMMIT` を返す前にクラッシュまたは通信断になると、コーディネータはタイムアウトを検知して `GLOBAL_ABORT` を決定できるため、システム全体が止まることはありません（停止した参加者が `PREPARED` 後に落ちて復旧したときは、自 WAL から `PREPARED` を読んでコーディネータへ決定を問い合わせます）。
* **参加者が `PREPARED` の状態でコーディネータが停止した場合（無期限ブロッキング）：** 図9-9-1右の通り、参加者が `VOTE_COMMIT`（YES）を返してから `GLOBAL_COMMIT / ABORT` を受け取るまでの **`PREPARED`（不確定：In-Doubt）期間** にコーディネータがクラッシュすると深刻な問題が起きます。たとえ東京と大阪の参加者同士が通信して「双方とも `PREPARED` 状態である」と確認できたとしても、**「コーディネータが自身の WAL へ `COMMIT` を書き終えた直後に落ちて復旧後に `GLOBAL_COMMIT` を送ってくるのか、それとも `COMMIT` を書く前に落ちて復旧後に `ABORT` するのか」** を参加者側から知る術がありません。そのため、参加者は勝手にコミットもアボートもできず、**コーディネータが復旧して WAL を読み直すまで対象データの X ロックを握りしめたまま無期限に停止（ブロッキング）** してしまいます。これが 2PC が単一障害点（コーディネータ）に弱い **ブロッキングプロトコル** と呼ばれる理由です。

#### (2) CAP 定理（Brewer の予想・Gilbert & Lynch の証明）

2000年にエリック・ブリューワー（Eric Brewer）が予想し、2002年にセス・ギルバートとナンシー・リンチが数学的に定式化・証明した **CAP 定理（CAP Theorem）** は、分散データストアが満たし得る 3 つの性質の根本的な限界を示します（図9-9-2）。

* **C：一貫性（Consistency / 厳密には線形化可能性［Linearizability］）：**
    どのノードへ読み取り要求を送っても、必ず「直前の最新書き込みの結果（または最新順序に矛盾しない結果）」が返り、あたかも単一コピーのデータベースが存在するかのように振る舞う性質（ACID の C［スキーマ・業務不変条件］とは別概念である点に注意します）。

* **A：可用性（Availability）：**
    故障していないすべてのノードへ送られた要求は、無限に待たされたりエラーになったりせず、必ず有効な（エラーでない）応答を返す性質。

* **P：分断耐性（Partition Tolerance）：**
    ノード間のネットワークメッセージが任意に遅延・欠損・分断（Partition）されても、システム全体が動作を継続できる性質。

> **【CAP 定理】**
> ノード間のネットワーク分断（**P**）が発生し得る非同期分散システムにおいては、強い一貫性（**C**：線形化可能性）と完全な可用性（**A**）を**同時に**満たすことは不可能である。すなわち、**分断（P）が発生したとき、システムは C と A のどちらか一方を選ばざるを得ない**。

現実の広域ネットワークではケーブル断線やスイッチ故障、BGP 異常による **分断（P）の発生をゼロにすることは物理的に不可能** です。したがって「C・A・P の 3 つから好きな 2 つを選ぶ（P を捨てて CA を選ぶ）」のではなく、正確には **「分断が起きていない平常時は C と A の両立が可能だが、ネットワーク分断（P）が起きた瞬間に、一貫性を優先して一部リクエストを拒否する（CP 型）か、エラーを返さず古い値でも応答を返して可用性を優先する（AP 型）かを事前に設計で決めておく必要がある」** というのが CAP 定理の正確な意味です。

### 4. 限界と補正（Critique & Adaptation）

#### (1) FLP 不可能性と、実用的な合意アルゴリズムの入口（Paxos / Raft・結果整合性・PACELC）

[7-2節](../7/7-2.md)の **二つの軍隊問題**（メッセージ紛失があるときの合意不可能性）と双璧をなす分散システム理論の限界が、1985年に Fischer・Lynch・Paterson が証明した **FLP 不可能性定理** です。「メッセージ遅延に上限がない完全非同期ネットワークでは、たとえ**たった 1 台のノードが停止故障（クラッシュ）する可能性があるだけでも**、安全性を保ったまま、すべての正常ノードが有限時間内に必ず合意へ達する（終了する）決定論的アルゴリズムは存在しない」という厳しい限界を示しています。

しかし現実の分散システム（Google Spanner, CockroachDB, etcd, TiDB 等）は、この理論限界に対して次の工学的補正で実用的な分散合意とレプリケーションを実現しています（ここでは分散システムの入口として考え方の骨格だけを整理します）。

1. **過半数（クォーラム：Quorum）に基づく合意アルゴリズム（Paxos / Raft）：**
    2PC のように「全ノードの同意＋単一コーディネータ」に依存すると 1 台落ちただけでブロックします。そこで **Paxos** や **Raft** といった合意アルゴリズムは、$2f + 1$ 台（例：3 台または 5 台）のレプリカ群で **過半数（$f + 1$ 台）のノードが複製ログ（WAL）へ永続化した時点でコミット確定** とします（Raft はさらに明示的なリーダー選出と任期番号［Term］でアルゴリズムを理解しやすく整理し、Multi-Paxos も安定したリーダーを置いて高スループット化します）。

    * **なぜ実用化できるのか：** 安全性の不変条件（異なる値が同時に合意されない）は非同期下でも常に守りつつ、FLP の壁は「ランダム化したタイムアウトによるリーダー再選出（ネットワークが安定した期間に合意を完了させる）」という部分的同期の仮定で回避しています。
    * **利点と CAP 上の位置づけ：** 過半数同士（たとえば 5 台中の任意の 3 台と別の 3 台）は必ず少なくとも 1 台の共通ノードを含むため一貫性が保たれ、最大 $f$ 台の故障に耐えます（2PC のコーディネータ自身を Raft グループで冗長化すれば 2PC の単一障害点によるブロッキングも防げます）。ただしネットワーク分断で過半数に満たない少数派へ孤立したノード側は書き込みを受け付けられないため、CAP 分類上は **CP 型** です。

2. **結果整合性（Eventual Consistency）と CRDT：**
    ショッピングカートや SNS の「いいね」数のように厳密な線形化可能性が不要な用途では、AP 型として「新たな更新が止まれば、いずれすべてのレプリカが同じ状態へ収束する（結果整合性）」モデルを採用し、同時更新の衝突を数学的に自動マージできるデータ構造（**CRDT：Conflict-free Replicated Data Type**）で補正します。

3. **平常時のトレードオフを捉える PACELC 定理：**
    CAP 定理は「分断（P）が起きた異常時」の話だけですが、ダニエル・アバディが提唱した **PACELC 定理**（2012年）は、「分断時（**P**）は **A** か **C** かの選択になり、**そうでなく平常時（E：Else）であっても、遅延（L：Latency）と一貫性（C：Consistency）のトレードオフが常に存在する**」という現実の設計指針を与えています（たとえば東京の更新をロンドンまで同期待ちすれば低遅延 L が犠牲になり、待たずに返せば強い一貫性 C が緩みます）。

#### 横断視点 1：全階層に繰り返し現れる「5 つの普遍的な設計パターン」

#### 横断視点 2：物理的制約の中で「抽象化と実装上の工夫」はどう噛み合っているか

計算機システムの各層は、下層の物理的制約を隠蔽して使いやすい「抽象（幻想）」を上位へ提供し、同時に物理制約のもとで性能を引き出す実装上の工夫を備えています。

* **物理・バイナリ層（第0〜2部）：** ゲート遅延やメモリ速度差という物理制約のもとで、CPU は 5 段パイプライン・フォワーディング・セット連想キャッシュで「1 サイクル 1 命令・高速単一メモリ」という抽象を支え、コンパイラと ABI は型・スタック・PIC/GOT によって機械語と高級言語を安全に橋渡しします。
* **OS・並行性・I/O 層（第3〜5部）：** OS は特権モード・コンテクストスイッチ・多段ページテーブル・コピーオンライトによって「各プロセスが CPU と広大なメモリを独占する」抽象を作り出し、CAS・メモリバリア・スピンロック／スリープロック・i-node・ジャーナリングで共有と永続化を保護します。
* **ネットワーク・DB 層（第6〜9部）：** 誤りや輻輳が起きるベストエフォートの物理網の上に TCP/TLS が「信頼できる安全なバイトストリーム」を築き、関係モデル・SQL・$\text{B}^+$ 木・問合せ最適化・2PL/MVCC・WAL（ARIES）が「非手順的な 1 文で安全かつ高速に永続データを扱える」抽象を完成させます。

#### 横断視点 3：「素朴な理想モデル」が現実で破綻したときに、システムはどう補正してきたか

どの階層でも、最初は美しい理論モデル（シングルサイクル CPU、逐次一貫性メモリ、素朴な FIFO キャッシュ、平文の通信プロトコル、ロックなしの同時実行）から出発し、**現実の物理制約（光速・熱雑音・電力の壁・停電・悪意ある攻撃・ランダムな負荷集中）によって破綻する瞬間** にこそ、現代の計算機システムの洗練された工夫（フォワーディング、メモリバリア、Clock-Sweep / 2Q、AIMD / QUIC、TLS 1.3、MVCC / SSI、ARIES）が生み出されてきました。

新しい技術や未知の障害に直面したとき、「これはどの層の抽象化が破れているのか」「キャッシュ・間接参照・ログ・待ち行列・一貫性のどの普遍パターンに当てはまるか」と問い直す視点を持てば、特定の製品やバージョンが変わっても、現代の計算機システムを自分の頭で深く読み解くことができます。

1. **2 相コミット（2PC）の障害タイミング別トレースとブロッキング問題：**

    * **(a) $P_2$ が投票前にクラッシュした場合（ブロックしない）：**
        $C$ は $P_2$ からの応答タイムアウトを検知した時点で「全員一致の `VOTE_COMMIT` が揃わなかった」と判断し、自身の WAL へ `ABORT` を記録して **`GLOBAL_ABORT`** を決定し、$P_1$ へ送信します。$P_1$ はそれを受け取ってローカルで UNDO アボートし、保持していた X ロックを即座に解放できるため、システム全体はブロックしません。

    * **(b) 両参加者が `PREPARED` になった後に $C$ がクラッシュした場合（ブロックする）：**
        $P_1$ と $P_2$ が「双方とも `PREPARED` である」と確認できても、**$C$ が「自身の WAL へ `COMMIT` を書き終えた直後（送信前）に落ちた」のか、「まだ決定を WAL へ書く前（復旧後に `ABORT` になる可能性あり）に落ちた」のかを参加者側から判別できません**。勝手な判断は他ノードや復旧後の $C$ と矛盾するリスクがあるため、ACID の分離性を保つべく X ロックを解放できず、$C$ の復旧まで無期限にブロックします。

2. **CAP 定理の正確な解釈とクォーラム・PACELC 定理：**

    * **(a) 5 台構成の 3 台 vs 2 台分断における CP 型の挙動：**
        CP 型では、過半数（3 台以上）を確保できる **3 台側（$N_1, N_2, N_3$）** だけがリーダーを維持して書き込みを受理し、過半数に届かない **2 台側（$N_4, N_5$）** はエラーを返して書き込みを拒否します（可用性 A の一部を犠牲）。5 台中の過半数（3 台以上）の部分集合を 2 つとると必ず少なくとも 1 台の共通ノード（$3 + 3 - 5 = 1$ 台以上）を含むため、分断の片側だけで過半数合意した更新が別の過半数と衝突して分岐することはなく、一貫性（C）が保たれます。

    * **(b) 平常時における PACELC と第0・4部との類推：**
        CAP 定理は分断時（P）の二者択一ですが、PACELC 定理が示す通り分断のない平常時（E）でも、強い一貫性（C）を保つには東京からロンドン（RTT $150\text{ ms}$）の同意を待ってから応答する必要があり遅延（L）が増大します。逆に低遅延（L）で即答して非同期に送ると一時的に古い値が読め得ます。これは、CPU 内の MESI コヒーレンシで他コアの無効化応答を待つか（SC）、ストアバッファを挟んで非同期化するか（緩和モデル）のトレードオフと同型です。

3. **全10部の横断総括（間接参照の具体対比と「抽象化の破れ」の診断）：**

    * **(a) 各層における 1 段の間接参照（代表例）：**

        * **第1〜5部（例）：** ① **GOT / PLT（[1-5節](../1/1-5.md)）**：機械語中の呼び出し先参照を固定したまま、共有ライブラリのロードアドレス（ASLR）を実行時に解決する。② **多段ページテーブル（[3-5節](../3/3-5.md)）**（または **i-node［[5-4節](../5/5-4.md)］・FD テーブル［[5-2節](../5/5-2.md)］**）：連続した仮想アドレス（またはファイル名／FD 番号）を固定したまま、物理フレームやディスクブロックを不連続に配置・保護する。
        * **第6〜9部（例）：** ① **DNS / ARP / NAT（[6-6](../6/6-6.md)・[7-5節](../7/7-5.md)）**：人間向けのドメイン名や論理 IP を固定したまま、変化する IP や MAC アドレスへ変換する。② **スロッテッドページの TID と $\text{B}^+$ 木（[9-1](9-1.md)・[9-2節](9-2.md)）**：外部索引が持つ `TID = (page_id, slot_num)` を固定したまま、ページ内コンパクションでタプルの物理オフセットを自由に移動する。

    * **(b) 2 つのトラブルの診断と補正策：**

        * **(i) [0-7節](../0/0-7.md)の False Sharing（偽共有）：** 論理的には別変数でも物理的に同じ **CPU キャッシュライン（例：64 B）** に同居しているため、MESI プロトコルによるキャッシュライン無効化がコア間で往復している状態です。**補正策：** 構造体にパディングを入れて要素ごとに別のキャッシュラインへ離します。
        * **(ii) [9-7節](9-7.md)の書き込みスキュー（Write Skew）：** SI の衝突判定が $WS \cap WS$（同一行の書込み競合）しか検査せず、相手が読んだ別行を書き換える関係を見逃しているためです。**補正策：** 連続する `rw`-反依存を検知する **SSI（`SERIALIZABLE`）** を使うか、確認読出し時に **`SELECT ... FOR UPDATE`** で明示的な行ロックを取ります。
