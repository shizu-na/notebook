### 前節（9-7）の確認問題の解答

前節の最後に提示した3つの問いの解答を確認します。問3がそのまま本節（障害回復と WAL）の導入になります。

1. **基本 TO・トーマスの書き込み規則・MVTO の手動トレース比較（`R1(X)` $\to$ `W2(X=30)` $\to$ `W1(X=20)` $\to$ `R2(X)`）：**

    * **(a) 基本 TO でのトレース（初期値 $X = 10$、$\text{R-TS} = \text{W-TS} = 0$）：**

        1. `R1(X)`（$TS=10$）：$10 \ge \text{W-TS}(0)$ なので許可され、$X=10$ を読み出して $\text{R-TS}(X) \leftarrow 10$ となります。
        2. `W2(X=30)`（$TS=20$）：$20 \ge \text{R-TS}(10)$ かつ $20 \ge \text{W-TS}(0)$ なので許可され、$X \leftarrow 30$、$\text{W-TS}(X) \leftarrow 20$ となります。
        3. `W1(X=20)`（$TS=10$）：まず $10 < \text{R-TS}(10)$ は偽ですが、次に $10 < \text{W-TS}(20)$ が真となります。よって基本 TO では **$T_1$ がアボート** され、$X$ は $30$ のまま残ります（その後の `R2(X)` は $30$ を読みます）。

    * **(b) トーマスの書き込み規則と MVTO の比較：**

        * **トーマスの書き込み規則：** `W1(X=20)` で $\text{R-TS}(10) \le 10 < \text{W-TS}(20)$ が成り立つため、$T_1$ をアボートせず **`W1(X=20)` だけを静かに無視して続行** します（$X = 30$, $\text{W-TS}(X) = 20$ のまま）。続く `R2(X)` は $20 \ge \text{W-TS}(20)$ より **$30$** を読みます。
        * **MVTO：** `R1(X)` は初期版 $X_0=10$ を読んで $\text{R-TS}(X_0)=10$ にし、`W2(X=30)` は新版 $X_{20}=30$ を作ります。続く `W1(X=20)` では $\text{W-TS} \le 10$ の最新版 $X_0$ に対して $10 \ge \text{R-TS}(X_0)=10$ を満たすためアボートせず、**中間の版 $X_{10}=20$（$\text{W-TS}=10, \text{R-TS}=10$）を新規作成** して続行します。続く `R2(X)` は $\text{W-TS} \le 20$ の最新版である $X_{20}$ から **$30$** を読みます。

2. **書き込みスキューに対する OCC 検証 vs スナップショット分離（SI）：**

    * **(a) OCC（後向き検証）での判定：**
        $T_1$ と $T_2$ はともに両行（`Alice` と `Bob`）を読んで一方だけを更新するため、

        $$RS(T_1) = \{\text{Alice}, \text{Bob}\}, \quad WS(T_1) = \{\text{Alice}\}, \qquad RS(T_2) = \{\text{Alice}, \text{Bob}\}, \quad WS(T_2) = \{\text{Bob}\}$$

        となります。$T_1$ が先に Validation・Write を完了した直後に $T_2$ が Validation へ入ると、両者の実行時間は重なっているため条件 1 は不成立であり、条件 2（または 3）は **$WS(T_1) \cap RS(T_2) = \emptyset$** を要求します。しかし実際には $WS(T_1) \cap RS(T_2) = \{\text{Alice}\} \neq \emptyset$ となるため、**$T_2$ は Validation で不合格（アボート）** となります。

    * **(b) SI で素通りし OCC で防げる理由：**
        スナップショット分離（SI）の衝突判定（First-Committer-Wins）は **書き込み集合同士の重なり（$WS(T_1) \cap WS(T_2)$）** しか見ないため、更新行が Alice と Bob で別々なら両方コミットされてしまいます。これに対し OCC は **先行の書き込み集合と後続の読出し集合の交わり（$WS(T_1) \cap RS(T_2)$）** を検査するため、読んだ前提が書き換えられた事実を捉えて書き込みスキューを確実に防げます。

3. **バッファプールとクラッシュが交錯したときの限界と 2 つの矛盾（本節への接続）：**

    * **(a) 追い出し禁止（NO-STEAL）＋即時書出し（FORCE）の限界：**
        未コミットページの追い出しを禁止すると、バッファプール容量を超える巨大トランザクションが実行不能になります。またコミットのたびに変更全ページをディスクへ書き出すと、複数ページへのランダム `fsync` I/O が発生してスループットが大きく低下します。

    * **(b) 緩めた場合に停電直後のディスクへ残る 2 つの矛盾：**
        コミット済みの $T_1$ が更新した $A=200$ がまだ RAM に残ったまま停電するとディスクに古い $A=100$ が残り（持続性の破綻 $\implies$ **REDO** が必要）、逆に未コミットの $T_2$ が更新した $B=100$ が先にディスクへ追い出されて停電すると未確定値が永続化されてしまいます（原子性の破綻 $\implies$ **UNDO** が必要）。

## 9-8. 障害回復（DO-UNDO-REDO・WAL・page LSN と CLR のべき等性・チェックポイント）

### 1. 動機（Why）：なぜ「コミットのたびに全データページをディスクへ書く」素朴な方式では遅すぎるのか

[9-5](9-5.md)〜[9-7節](9-7.md)を通じて、複数のトランザクションを安全に同時実行する並行性制御（ACID の **I：分離性**）のアーキテクチャが揃いました。本節では、ACID 特性の残る 2 本柱である **A（原子性：Atomicity）** と **D（持続性：Durability）** を、突然の停電・OS クラッシュ・ディスク故障から守り抜く **障害回復マネージャ（Recovery Manager）** の仕組みを解き明かします。

データベースで発生し得る障害は、影響範囲によって次の 3 種類に分類されます。

1. **トランザクション障害：** デッドロックによる強制アボート、制約違反、アプリからの `ROLLBACK` 発行（1 トランザクションのみ取り消します）。
2. **システム障害（クラッシュ）：** 停電、OS カーネルパニック、DBMS プロセスの異常終了です。**揮発性の RAM（バッファプール）の内容がすべて消滅** しますが、不揮発性のディスク上のデータは残ります。
3. **媒体障害（メディア障害）：** ディスク自体の物理破損です（バックアップ＋アーカイブ WAL ログの再生、あるいはレプリケーションで復旧します）。

ここで最も設計が難しいのが **システム障害（停電）** です。[9-1節](9-1.md)で学んだ通り、DBMS は高速化のために RAM 上に **バッファプール** を持ち、更新されたページ（ダーティページ）をしばらくメモリ上に留めます。ここで、もし素朴に「停電しても壊れないように、① 未コミットのダーティページはディスクへ追い出さず（**NO-STEAL**）、② コミットの瞬間に変更した全データページを即座にディスクへ書き出す（**FORCE**）」とすれば、障害回復は不要になります。

しかし、この素朴な **NO-STEAL / FORCE** 方針は、現実の DBMS では **著しく遅く、メモリ容量の壁にも突き当たります**。

* **NO-STEAL の限界：** 1 億行を一括更新する巨大トランザクションが走ると、変更したページがバッファプールに収まり切らなくなり、実行自体が不可能になります。
* **FORCE の限界：** 1 回のコミットのたびに、テーブルや複数 $\text{B}^+$ 木に散らばった 10 枚のダーティページをディスクのあちこちへ **ランダム書き込み** で `fsync` しなければならず、スループットが大きく落ち込みます。

そこで現代のほぼすべての高性能 RDBMS（PostgreSQL, MySQL InnoDB, Oracle, SQL Server 等）は、正反対の **STEAL / NO-FORCE** 方針を採用し、**ランダムなデータページの代わりに「シーケンシャルな追記ログ（WAL）」だけを先にディスクへ確定させる** という発想で、高い性能と障害耐性を両立させています。

---

### 2. 具体例と動作イメージ（Toy Model）

アルゴリズムの細部に入る前に、2 つの小さなシナリオで「なぜ REDO と UNDO の両方が必要になるのか」と「リカバリ途中の 2 回目クラッシュの難しさ」を確かめます。

#### 実験A：停電の瞬間にディスクへ残された「2 つの矛盾」

ある銀行データベースで、次の 2 つのトランザクションが動いていた直後に突然停電したとします。

* **$T_1$（コミット済み）：** 口座 $A$ を `100 → 200` に更新し、`COMMIT` が成功してユーザへ「完了」と返答しました。しかし **NO-FORCE** のため、ダーティページ $A$ はまだバッファプール（RAM）に留まっており、ディスク上の $A$ は古い **`100`** のままでした。
* **$T_2$（未コミット）：** 口座 $B$ を `500 → 100` に書き換えましたが、まだ `COMMIT` していません。しかしバッファプールが満杯になったため **STEAL** によって追い出され、ディスク上の $B$ はすでに未確定の **`100`** で上書きされていました。

停電から再起動した直後、ディスクの中身は `(A = 100, B = 100)` となっています。本来あるべき正しい状態は **`(A = 200, B = 500)`** です。

* $T_1$（コミット済み）の変更 `A = 200` をディスクへやり直して復元する操作 $\implies$ **REDO（再実行：持続性 D の回復）**
* $T_2$（未コミット）の変更 `B = 100` を古い値 `500` へ巻き戻して取り消す操作 $\implies$ **UNDO（取消し：原子性 A の回復）**

つまり、**STEAL が UNDO を必要とし、NO-FORCE が REDO を必要とする** のです（図9-8-1）。

#### 実験B：もし「UNDO を実行している最中」にもう一度停電したら

リカバリ処理は、[5-6節](../5/5-6.md)のファイルシステム・ジャーナリングでも確認した通り、**リカバリの途中で再び停電しても何度でも安全にやり直せる「べき等性（Idempotency）」** を持たなければなりません。

もし $T_2$ が「`B` に `+50` を足す」といった論理的な差分更新を行っていて、1 回目のリカバリで UNDO（`-50`）をディスクへ適用した直後に 2 回目の停電が起きたとします。もし再起動後の 2 回目のリカバリが「すでに UNDO 済みである」という記録を持たずに同じ UNDO をもう 1 回実行してしまうと、`B` から合計 `100` 引かれてデータが破壊されます。

この難題を解決する仕組みが、本節の中心となる **`pageLSN`** と **補償ログレコード（CLR）** です。

### 3. 構造・アルゴリズム・実装（What）

#### (1) バッファプール管理の 4 方針と WAL（Write-Ahead Logging）の 2 大規則

バッファプールのフラッシュ方針と必要な回復操作の対応は、次の 2×2 の表で整理されます（図9-8-1左）。

| バッファ管理方針 | **NO-FORCE**（コミット時にデータページ強制書出しない） | **FORCE**（コミット時に全データページ強制書出する） |
| :--- | :--- | :--- |
| **NO-STEAL**（未コミットページを追出さない） | REDO 必要 / UNDO 不要 | 回復不要（最遅・大 TX 不可） |
| **STEAL**（未コミットページの追出し許可） | **REDO 必要 / UNDO 必要（現代 DBMS の標準：最速）** | REDO 不要 / UNDO 必要 |

**STEAL / NO-FORCE** を安全に成立させるための基本規則が、**WAL（Write-Ahead Logging：先行書き込みログ）プロトコル** です（図9-8-1）。すべてのログレコードには単調増加する一意の通し番号 **LSN（Log Sequence Number）** が振られ、各ログレコードには `(LSN, TX ID, prevLSN［同一 TX の直前ログ］, 種類［UPDATE/COMMIT/ABORT/CLR/END］, 対象 page_id, 変更前イメージ［UNDO 用］, 変更後イメージ［REDO 用］)` が記録されます。

WAL は次の **2 つの規則** を厳守することで、STEAL と NO-FORCE の両方の安全性を保証します。

1. **WAL 規則（STEAL の安全保証＝UNDO の保証）：**
    バッファプール上のダーティページ $P$ をディスクへ書き出す（フラッシュする）**より必ず前に**、そのページ $P$ に対して行われたすべての変更のログレコード（特に変更前イメージ＝UNDO 情報）を、ディスク上のログファイルへ `fsync` して永続化しておかなければなりません（$\text{pageLSN}(P) \le \text{flushedLSN}$。ここで $\text{pageLSN}(P)$ はページ $P$ へ適用済みの最新ログ番号、$\text{flushedLSN}$ はディスクへ永続化済みの最大ログ番号です）。

2. **コミット時強制ログ規則（NO-FORCE の安全保証＝REDO の保証）：**
    トランザクション $T_i$ の `COMMIT` が成功してアプリへ完了応答を返す**より必ず前に**、$T_i$ のすべての変更ログレコードおよび **`COMMIT` ログレコード** をディスク上のログファイルへ `fsync` して永続化しなければなりません。

データページへの書き込みはディスク上のあちこちへのランダム I/O ですが、ログファイルへの書き込みは末尾への **1 本のシーケンシャル追記** だけで済むため、コミットのたびに `fsync` しても桁違いに高速です（さらに複数トランザクションのコミットログを 1 回の `fsync` へ束ねる **グループコミット** で一層高速化されます）。

#### (2) DO-UNDO-REDO プロトコルと ARIES の 3 フェーズ回復アルゴリズム

1992年に IBM の C. Mohan らが発表した **ARIES（Algorithms for Recovery and Isolation Exploiting Semantics）** は、現代の商用・オープンソース RDBMS の障害回復の標準設計図です。これは、通常運転時の変更とログ書込みを行う **DO**、クラッシュ時の履歴再現を行う **REDO**、そして未確定変更を取り消す **UNDO** からなる **DO-UNDO-REDO プロトコル** に基づいています。

ARIES の特徴は、**「クラッシュ直前の物理状態をまず完全に再現し（Repeating History）、そのあとで未コミットのトランザクションだけを巻き戻す」** という 3 フェーズ構成にあります（図9-8-2）。

1. **フェーズ 1：解析フェーズ（Analysis Phase：チェックポイントから末尾へ前向き走査）**

    * 最新の完了済みチェックポイント（後述する `END_CHECKPOINT` 内のスナップショット）から表を復元したうえで、そのチェックポイントの開始位置（`BEGIN_CHECKPOINT`）から WAL の末尾までを前向きにスキャンし、クラッシュ瞬間のシステム状態を次の 2 つのメモリ表へ再構築します。

        * **ATT（Active Transaction Table：稼働中トランザクション表）：** クラッシュ時点で `COMMIT` もロールバック完了（`END`）もしていなかった未確定トランザクション（**敗者：Loser**）と、各 TX の最新 LSN（`lastLSN`）のリストです（`COMMIT` レコードを見つけた TX は勝者として ATT から除かれますが、`ABORT` 途中で `END` に達していない TX は敗者として残ります）。
        * **DPT（Dirty Page Table：ダーティページ表）：** クラッシュ時にバッファプール上で未フラッシュだった可能性があるページと、そのページを最初にダーティにした LSN（**`recLSN`**）のリストです（チェックポイント後にそのページが最初に更新・CLR 適用されたときに `recLSN` が登録されます）。

2. **フェーズ 2：REDO フェーズ（履歴の繰り返し：DPT の最小 `recLSN` から末尾へ前向き走査）**

    * DPT の中で最小の `recLSN`（`min recLSN`）からログ末尾までを前向きに辿り、**コミット済み（勝者）だけでなく未コミット（敗者）や CLR の変更も含めて、ディスクへ未反映のログをすべて再実行** します（Repeating History）。
    * 対象ページ $P$ を変更する各更新ログ（`UPDATE` または `CLR`）について、もし **$P$ が DPT に含まれない** か、**$\text{LSN} < \text{DPT}[P].\text{recLSN}$** であれば「クラッシュ前にすでにディスクへ反映済みである」と確定できるため、ディスクからページを読まずにスキップします。
    * そうでなければディスクからデータページ $P$ を読み込み、ヘッダに刻まれた **`pageLSN(P)`（[9-1節](9-1.md)）** とログの LSN を比較します。

        $$\text{pageLSN}(P) \ge \text{ログの LSN}$$

        であれば、「このログ（およびそれより新しいログ）の変更はクラッシュ前にすでにディスクへ反映済みである」と即座に分かるため **REDO をスキップ** します。$\text{pageLSN}(P) < \text{ログの LSN}$ のときだけ変更後イメージを再適用し、$\text{pageLSN}(P) \leftarrow \text{ログの LSN}$ へ更新します。

3. **フェーズ 3：UNDO フェーズ（敗者の取り消し：末尾から先頭へ後ろ向き走査）**

    * 解析フェーズで見つけたすべての未確定トランザクション（ATT に残った敗者）について、まだ取り消すべき LSN 群の中から常に **最大の LSN** を選びながら（各 TX の `prevLSN` または `CLR` の `UndoNextLSN` を辿って）後ろ向きに変更を取り消し（変更前イメージへ戻し）、取り消すたびに後述の **CLR（補償ログレコード）** を WAL へ書き出して `pageLSN` を更新します。先頭（`NULL`）へ到達した TX ごとに `END` レコードを書き、すべての敗者の UNDO が終われば回復完了です。

#### (3) `pageLSN` と補償ログレコード（CLR）による「再クラッシュ耐性とべき等性」

実験Bで提起した **「UNDO フェーズの途中で 2 回目の停電が起きたらどうなるか」** を確実に解決するのが **補償ログレコード（CLR：Compensation Log Record）** です（図9-8-3）。

たとえば、ある敗者トランザクション $T_2$ が `LSN 10: X (1→2), prevLSN = NULL` と `LSN 20: B (500→100), prevLSN = 10` を実行した直後に 1 回目の停電が起きたとします（`LSN 30` に勝者 $T_1$ の `COMMIT` が挟まっていたとします）。UNDO フェーズで $T_2$ の `LSN 20` を取り消して `Page B` を `500` へ戻すとき、ARIES はその UNDO 操作自体を **通常のログと同じように WAL の末尾へ新しいレコード `CLR` として追記** します。

* **`CLR` の中身：** `(LSN = 40, TX = T2, type = CLR, target = Page B, REDO内容 = 500へ戻す, UndoNextLSN = 10)`
* **`UndoNextLSN` ポインタ：** 次に UNDO すべき $T_2$ のログ番号（ここでは `LSN 20` の `prevLSN` であった `LSN 10`）を指します。
* **CLR 自体は決して UNDO しない（REDO 専用ログ）：**
    もし `LSN 40 (CLR)` を WAL へ書いて `Page B` を戻した直後、`LSN 10` を取り消す前に **2 回目の停電** が起きても、3 回目の起動時には次の流れで矛盾なく回復します。

    1. **REDO フェーズ：** `CLR (LSN 40)` も普通の REDO 対象として扱われるため、`Page B` に `500` が反映されていなければ確実に `500` へ復元されます（すでに反映済みなら `pageLSN >= 40` でスキップされます）。
    2. **UNDO フェーズ：** 後ろ向きに辿って `CLR (LSN 40)` に出会った瞬間、**`LSN 20` を丸ごと飛び越して `UndoNextLSN = 10` へ直接ジャンプ** します。

これにより、**同じ UNDO 操作が二度と重複実行されず、リカバリの途中で何回停電が繰り返されても、前回の UNDO の進捗を 1 ステップも無駄にせず必ず有限回で正しい状態へ収束（完全なべき等性）** します。

#### (4) チェックポイント（静止 vs ファジー）とシャドウページング

もしデータベースが 1 年間連続稼働したあとに停電したとき、WAL ファイルの先頭（1 年前のログ）から末尾まで全部スキャンして REDO していたら、再起動だけで何日もかかってしまいます。そこで、定期的に「ここより前の古い変更はすでにディスクのデータページへ反映済みである」という区切り印を打つ仕組みが **チェックポイント（Checkpoint）** です。

1. **静止チェックポイント（Quiescent / Sharp Checkpoint：素朴な方式）：**

    * 新規トランザクションの受付を一時停止し、現在稼働中の全トランザクションが終わるのを待ち、全ダーティページをディスクへフラッシュしてから `CHECKPOINT` レコードを WAL へ書きます。
    * **弱点：** チェックポイント取得中にシステム全体がフリーズしてしまい、24時間無停止のサービスでは使えません。

2. **ファジーチェックポイント（Fuzzy Checkpoint：ARIES の標準）：**

    * **トランザクションを止めずに処理を進めます**。`BEGIN_CHECKPOINT` をログへ書き、その間のメモリ上の **ATT（稼働中 TX 表）と DPT（ダーティページ表）のスナップショットだけ** を `END_CHECKPOINT` レコードとして WAL へ書き出します（完了後にマスターレコードが `BEGIN_CHECKPOINT` の LSN を指すよう更新します）。
    * なお、スナップショットだけを記録しても古いダーティページがメモリに残ったままだと `min recLSN` が前進しないため、バックグラウンドのフラッシュ処理（チェックポインタ）が最も古い `recLSN` を持つダーティページを非同期にディスクへ書き戻し続けることと連動して、クラッシュ時の解析・REDO 開始位置を数分前まで大幅に短縮します。

なお、WAL ログを一切使わない障害回復の別アプローチとして **シャドウページング（シャドウイングとも呼ばれます：Shadow Paging）** もあります（SQLite の古いモードや [5-6節](../5/5-6.md)コラムの CoW ファイルシステム［ZFS / Btrfs / APFS］と同型の発想）。元のデータページを直接上書きせず、コピー先の空きページへ書き込んで新しいページテーブルを作り、コミット時にルートポインタ 1 個だけを切り替える方式です。単純ですが、複数トランザクションの同時更新が難しく、連続配置（クラスタリング）が崩れて断片化しやすい弱点があるため、汎用 OLTP RDBMS では WAL（ARIES）が標準となっています。

> **【コラム：[第5部](../index.md#part-5)（[5-6節](../5/5-6.md)）のファイルシステム・ジャーナリングと、本節の DB の WAL は同じ原理】**
>
> [5-6節](../5/5-6.md)で学んだファイルシステムの **ジャーナリング（xv6 の `log.c` や Linux ext4）** と、本節の **DBMS の WAL（ARIES）** を見比べてみてください。OS とデータベースという別々の領域で扱われますが、その中心にある設計原理は同じです。
>
> > **「ディスク上のあちこちへ散らばるランダムな本体更新を行う前に、まずシーケンシャルな追記ログ領域へ確定記録を残し、クラッシュ時はべき等なログ再生で一貫状態を復元する。」**
>
> ただし、データベースの方が 1 段階だけ複雑な理由は **「1 枚の 8 KiB ページの中に複数トランザクションの行が同居し、片方がコミット、もう片方がアボート（STEAL）し得る」** 点にあります。ファイルシステムのジャーナリング（No-Steal・物理ブロック丸ごと REDO のみ）から、データベースの ARIES（STEAL/NO-FORCE・行単位の REDO ＋ UNDO ＋ `pageLSN` ＋ CLR）へと、要求される並行性の高さに応じて同じ原理が精緻に拡張された構造が見えてきます。

### 4. 限界と補正（Critique & Adaptation）

#### (1) ディスクの部分書き込み（Torn Page：引き裂かれたページ）への補正

WAL の REDO ログを小さく高速に保つため、多くの DBMS はページ全体（$8\text{ KiB}$）ではなく「オフセット 240 番地の 8 バイトだけ変更」という **物理論理ログ（差分ログ）** を記録します。

ところがここに、OS（$4\text{ KiB}$）やストレージ（$512\text{ B}$ セクタ）とのサイズ差に由来する深刻な物理障害が潜んでいます。DBMS が $8\text{ KiB}$ や $16\text{ KiB}$ のダーティページをディスクへフラッシュしている**まさに真ん中で停電**すると、前半の $4\text{ KiB}$ だけが新データで後半の $4\text{ KiB}$ が古いデータのまま混ざった **部分書き込み（Torn Page：引き裂かれたページ）** が生じます。この壊れたページへ差分ログだけを REDO しても元の正しいページには戻りません。

* **補正（Full Page Writes / Doublewrite Buffer）：**

    * **PostgreSQL（`full_page_writes`）：** チェックポイント後に**最初に**あるページを書き換えるときだけは、差分ではなく **8 KiB のページ丸ごとのイメージ** を WAL へ書き出します。直近のチェックポイント完了後にフラッシュされたページで Torn Page が起きても、WAL 内の最初の丸ごとイメージで無傷のページを上書き修復してから後続の差分ログを REDO できます。
    * **MySQL InnoDB（Doublewrite Buffer）：** ダーティページを本来の場所へランダム書き込みする前に、まず専用の連続領域（ダブルライトバッファ）へまとめてシーケンシャル書き出しして `fsync` したうえで本体へ書きます。停電で本体ページが引き裂かれても、ダブルライトバッファから無傷の $16\text{ KiB}$ ページをコピーして復元できます。

#### (2) 単一ノード障害回復の限界：媒体障害・データセンター被災とレプリケーション（次節への動機）

WAL と ARIES は、単一サーバ上での停電やプロセス異常終了に対して高い確実性で原子性と持続性を保証します。しかし、**サーバの SSD 自体が物理的に破損したり、データセンター全体が停電・災害で失われたり**すれば、ローカルディスク上の WAL ごと消滅してしまいます。

これを乗り越えるには、WAL ログのストリームをネットワーク（第6〜7部）越しに別マシン・別地域のスタンバイサーバへ継続的に転送して複製する **レプリケーション（Streaming Replication）** や、複数ノードにまたがる **分散トランザクション（2 相コミット）** が必要になります。いよいよ最終節となる次節（[9-9節](9-9.md)）で、単一マシンから分散システムへの展望と、全10部の総括を行います。

### 理解度チェック（最終節へ進む前の確認）

本節の STEAL / NO-FORCE・WAL 2 規則・ARIES（`pageLSN` と CLR）の仕組みを確認し、最終節（[9-9節](9-9.md)）へ繋ぐ問いを置きます。

> **【確認の問い】**
>
> 1. **（ARIES の 3 フェーズ［Analysis・REDO・UNDO］と `pageLSN` / CLR の手動トレース）**
>     初期状態が `A = 100`, `B = 500` のデータベースで、次の 5 本の WAL レコード（`LSN 50` まで永続化済み、チェックポイントなし）が記録された直後に停電しました：
>
>     * `LSN 10`: `T1 UPDATE Page A (100 -> 200), prevLSN = NULL`
>     * `LSN 20`: `T2 UPDATE Page B (500 -> 100), prevLSN = NULL`
>     * `LSN 30`: `T1 COMMIT, prevLSN = 10`
>     * `LSN 40`: `T2 UPDATE Page A (200 -> 300), prevLSN = 20`
>     * `LSN 50`: `T2 UPDATE Page B (100 -> 50), prevLSN = 40`
>     再起動直後のディスク上のデータページは、`Page A` が `(値 = 200, pageLSN = 10)`、`Page B` が `(値 = 50, pageLSN = 50)` でした。
>
>     * (a) **Analysis フェーズ**（`LSN 10` から末尾まで走査）の結果として得られる **ATT（敗者 TX と `lastLSN`）** と **DPT（ダーティページと `recLSN`）** を答えてください。
>     * (b) **REDO フェーズ**で `LSN 10, 20, 40, 50` のそれぞれについて、`pageLSN` との比較から **REDO が実行されるかスキップされるか** と、REDO 完了時点での `Page A`・`Page B` の値を答えてください。
>     * (c) **UNDO フェーズ**で出力されるすべての **CLR（対象ページ・復元値・`UndoNextLSN`）** の並びと、回復完了後の最終的な `Page A`・`Page B` の値を答えてください。
>
> 2. **（WAL の 2 規則の欠落と、UNDO 途中の再クラッシュに対する CLR）**
>
>     * (a) ある開発者が「ダーティページ追出し前の WAL `fsync`（規則①）」は実装したものの、「`COMMIT` 完了応答前の WAL `fsync`（規則②）」だけを省略してログを RAM に溜めたまま `COMMIT` 成功を返したとします。直後に停電が起きるとどのような不整合が生じるでしょうか。また逆に、規則②だけを守って規則①を省略した場合はどうでしょうか。
>     * (b) 問 1 の UNDO フェーズで `LSN 50` を取り消す `LSN 60 (CLR: T2, Page B = 100, UndoNextLSN = 40)` を WAL へ書き、`Page B`（`pageLSN = 60`）をディスクへ反映した直後に **2 回目の停電** が起きたとします。3 回目の起動時に `LSN 50` が二度と重複取り消しされない理由を、`pageLSN` と `UndoNextLSN` の働きから説明してください。
>
> 3. **（最終節への伏線：単一マシンの WAL が「東京と大阪の 2 台」では足りなくなる理由）**
>     本節までで、1 台のサーバ上の DBMS が停電やプロセス障害に対して原子性（All-or-Nothing）と持続性を守る仕組みが揃いました。では、口座 $A$ を持つ東京サーバと口座 $B$ を持つ大阪サーバの 2 台がネットワーク（第6〜7部）越しに結ばれており、**それぞれのマシン内部に完全な WAL と ARIES が動いている** 状態を考えます。この環境で $A \to B$ への 2 万円送金を 1 つのトランザクションとして実行しようとして、「東京へ先に `COMMIT` を送って完了させてから、次に大阪へ `COMMIT` を送る」という素朴な手順をとると、どのようなタイミングで障害や通信断が起きたときに原子性が破綻し、なぜ各サーバのローカル WAL だけでは防げないのでしょうか。
