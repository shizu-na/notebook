### 前節（8-7）の確認問題の解答

前節の最後に提示した3つの問いの解答を確認します。問3がそのまま[第9部](../index.md#part-9)（DBMS の内部構造・トランザクションと分散への展望）の導入になります。

1. **行指向 vs 列指向の I/O 量定量比較と 4 次元データキューブの組合せ数：**

    * **(a) 行指向と列指向の読込データ量および OLTP 不向きの理由：**

        * **① 読込データ量と倍率：** 行指向ストレージは 1 行あたり全 50 列（$400\text{ B}$）を丸ごと読み込むため、$400\text{ B} \times 10^8\text{ 行} = 4 \times 10^{10}\text{ B} = \mathbf{40\text{ GB}}$ です。これに対し列指向ストレージは必要な 2 列（計 $4 + 4 = 8\text{ B}$）だけを読み込むため、$8\text{ B} \times 10^8\text{ 行} = 8 \times 10^8\text{ B} = \mathbf{0.8\text{ GB}}$ となり、読込量は行指向の $1/50$（**$50\text{ 倍}$ の差**）に抑えられます。
        * **② 列指向が OLTP に不向きな理由：** 全 50 列が別々の列ブロック（または列ファイル）へ分かれて格納されているため、1 行を `INSERT`／`UPDATE` するだけで 50 か所すべてへ分散して書き込む**書き込み増幅**が発生します。また、特定 1 行の全 50 列を取得するポイントルックアップでも 50 か所から断片を集めて 1 行を再構成しなければならず非効率になります。

    * **(b) 4 次元データキューブの事前計算すべき集計粒度数：**

        * **① 各軸に階層がない場合：** 各軸について「個別値」と「全合計（`ALL`）」の 2 通りを選べるため、$2^4 = \mathbf{16\text{ 通り}}$ です。
        * **② 各軸の階層レベル数が $L = (2, 1, 2, 3)$ の場合：** 各軸 $i$ ごとに $(L_i + 1)$ 通りの粒度があるため、$\prod_{i=1}^{4}(L_i + 1) = (2 + 1)(1 + 1)(2 + 1)(3 + 1) = 3 \times 2 \times 3 \times 4 = \mathbf{72\text{ 通り}}$ です。

2. **ORDB 単独 vs ポリグロット永続化の判断と、グラフ DB 分散の難しさ：**

    * **(a) 3 つのシステム要件に対する構成判断：**

        1. **ORDB 単独（PostgreSQL ＋ JSONB / PostGIS 等）：** 注文・在庫管理の ACID トランザクションを保ったまま、半構造化のスペック情報は JSONB（GIN 索引）で、店舗の近傍検索は PostGIS（GiST / R 木索引）で単一 DB 内に収められ、複数 DB 間の同期や運用複雑性を増やさずに済むためです。
        2. **専用 DB の併用（ポリグロット永続化：OLTP 用 RDB ＋ 列指向 DWH / OLAP、または HTAP）：** 毎秒数千件の決済（行指向 OLTP）と数十億行の多次元集計（列指向 OLAP）では物理配置も負荷特性も相反するため、WAL ベースの CDC 等で列指向 DWH へ準リアルタイム連携（あるいは HTAP でレプリカ分離）して OLTP のロック・I/O 競合を防ぎます。
        3. **専用 DB の併用（ポリグロット永続化：グラフ DB）：** 数千万ノード規模での 5〜6 ホップ探索を RDB の自己 `JOIN` で行うと、1 ホップごとに全体索引 $O(\log \vert E \vert)$ を引き直すコストと中間結果が急増して低遅延を満たせません。インデックスフリー隣接で 1 ホップ $O(1)$ で辿れるグラフ DB を併用します。

    * **(b) グラフ DB の分散分割が難しい理由：**
        グラフを複数サーバへ水平分割すると、同じサーバ内に収まらずサーバ境界を跨ぐ辺（**エッジカット**）が必ず生じます。頂点数を均等に保ちながらエッジカット数を最小化する「均衡グラフ分割問題」は NP 困難であるうえ、エッジカットを辿るたびにローカルの直接ポインタ参照（$O(1)$）がネットワーク往復通信へ置き換わるため、グラフ DB 本来の低遅延な多段探索の優位が崩れてしまいます。

3. **固定長 $8\text{ KiB}$ ページにおける可変長レコード管理の課題（本節への接続）：**
    ① **ページ内部の空き領域（断片化）：** 行の削除や長さ変更を繰り返すとページ途中に細切れの空き隙間が散在し、空き容量の合計は十分でも連続領域が足りず新しい大きな行を格納できなくなります。② **行識別子（RID / TID）の維持：** 空き隙間を詰めるために残りの行をページ内でずらして配置し直す（コンパクションする）と、外部の索引などがページ内の直接バイトオフセットを記録していた場合、移動した行を指すすべての索引ポインタが壊れて書き換えが必要になります。本節では、この問題を 1 段の間接参照で解決する **スロッテッド・ページと TID**、および **バッファプール** の仕組みを整理します。

## 9-1. ページ編成（スロット配列・TID）とバッファプール（LRU・PIN）

### 1. 動機（Why）：なぜ「固定長ページ」「スロット間接参照」「自前のバッファプール」が DBMS の最下層を支えるのか

[第8部](../index.md#part-8)（[8-1](../8/8-1.md)〜[8-7節](../8/8-7.md)）を通じて、関係データモデル・関係代数・正規化・SQL・OLAP という「データベースの論理世界（What）」を学びました。ここからの **[第9部](../index.md#part-9)** では、DBMS の内部へ踏み込み、第0〜7部で培ったハードウェア・OS・並行性制御・ネットワークの知識を合流させて、「DBMS が物理ディスクと RAM の上で実際にどうやってデータを格納・検索・最適化し、同時実行と障害から ACID 特性を守るか（How）」を解き明かします。

最下層の **ストレージエンジン** を設計しようとすると、次の 3 つの物理的・構造的な壁に直面します。

1. **バイト単位ではなく「固定長ページ単位」の I/O が必須：**
    [5-4節](../5/5-4.md)で確認した通り、HDD や SSD は 1 バイトずつ読み書きできず、セクタ／ブロック単位でアクセスします。またランダムアクセス遅延（HDD で数 $\text{ms}$、SSD でも数十 $\mu\text{s}$）は RAM（約 $100\text{ ns}$）より桁違いに遅いため、DBMS はテーブル全体を **$4\text{ KiB} \sim 16\text{ KiB}$（システムによっては最大 $64\text{ KiB}$）の固定長ページ（Page）** に区切って読み書きします（PostgreSQL は $8\text{ KiB}$、MySQL InnoDB は $16\text{ KiB}$ が標準です）。

2. **可変長タプルの削除・更新と「外部ポインタ破壊」のジレンマ：**
    `VARCHAR` などの可変長文字列を含む行（タプル）をページの中へ並べたとき、途中の行が削除されたり長くなったりすると空き隙間（ページ内断片化）が生じます。隙間を詰めるために行をページ内でずらす（コンパクションする）と、もし外部の索引（[9-2節](9-2.md)で詳述する $\text{B}^+$ 木などの検索用木構造）がその行の「ページ内バイトオフセット」を直接記憶していた場合、**すべての索引ポインタが壊れてしまいます**。

3. **OS のページキャッシュ（[5-5節](../5/5-5.md)）があるのに、なぜ DBMS 自身が RAM キャッシュを持つのか：**
    OS カーネルはすでにディスクブロックを RAM へキャッシュしてくれます。それにもかかわらず、主要な RDBMS はほぼ例外なく、自分自身のプロセス空間内に専用の **バッファプール（Buffer Pool）** を自前で構築します。

本節では、これら 3 つの壁を解決する **スロッテッド・ページと TID（タプル ID）**、および **バッファプールマネージャ（PIN / UNPIN・ダーティページ・置換制御）** の仕組みを整理します。

### 2. 具体例と動作イメージ（Toy Model）

データ構造の細部に入る前に、2 つの小さな思考実験で「素朴な配置の破綻」と「スロッテッド・ページの間接参照」を確かめます。

#### 実験A：ページ先頭から素朴にタプルを詰めると、1 行削除で何が起きるか

$8\text{ KiB}$（$8{,}192\text{ B}$）のページ（Page #5）がすでにほぼ埋まっており、末尾近くに連続空き領域が $100\text{ B}$ だけ残った状態で、手前に 3 つの可変長タプル `T0`（$100\text{ B}$）、`T1`（$200\text{ B}$）、`T2`（$150\text{ B}$）が並んでいるとします。外部の索引には「`T2` は Page #5 のオフセット値（先頭からの直接バイト位置）にある」と直接アドレスを記録したとします。

ここで中間の `T1`（$200\text{ B}$）が `DELETE` されました。

* **そのまま穴を放置すると：** $200\text{ B}$ の穴が残ります。あとから $250\text{ B}$ の新タプル `T3` を挿入しようとしたとき、ページ内の空き合計は $200 + 100 = 300\text{ B}$ あり十分収まるはずなのに、`200 B` の穴にも `100 B` の空き領域にも入らず**外部断片化**（[3-4節](../3/3-4.md)と同型の隙間による領域不足）が起きます。
* **穴を詰めて `T2` を $200\text{ B}$ 分ずらすと：** 外部の索引が持っている「`T2` の直接バイトオフセット」というポインタがすべて古い場所を指して壊れてしまいます。もし `T2` を指す索引が 5 個あれば、ページ内を 1 回整理するたびに 5 個の $\text{B}^+$ 木すべてを探し出して書き直す膨大な処理が必要になります。

#### 実験B：目次（スロット配列）と本体（タプル）を「両端から向かい合わせ」に伸ばす

そこで DBMS が採用した解決策が、**1 段の間接参照（Indirection）** です。

* ページの**先頭側**（ヘッダの直後）には、「`slot[0]`, `slot[1]`, `slot[2]` はページ内の何バイト目から何バイト分か」という小さな配列（**スロット配列**）を下向き（アドレス増加方向）に伸ばします。
* ページの**末尾側（$8{,}192\text{ B}$ 目）** から先頭へ向かって、実際のタプル本体を上向き（アドレス減少方向）に詰めて配置します。たとえば空のページ末尾から順に `T0`（$100\text{ B}$ → `8092..8191`）、`T1`（$200\text{ B}$ → `7892..8091`）、`T2`（$150\text{ B}$ → `7742..7891`）と詰めます。
* 外部の索引が記憶するのはバイトオフセットではなく、**「`(ページ番号, スロット番号)`」という不変の論理識別子（TID / RID）** だけにします（例：`T2` の TID は `(Page 5, Slot 2)`）。

この構造なら、`T1` が削除されたあとで `T2`（$150\text{ B}$）をページ末尾側の `T0` の隣（`7942..8091`）へずらして空き領域を 1 箇所へ集めても（**ページ内コンパクション**）、書き換えるのは **そのページ内部の `slot[2]` のオフセット値（`7742 → 7942` のたった 2〜4 バイト）だけ** で完結します。外部の索引が持つ TID `(Page 5, Slot 2)` は一切変更せずに済みます。

### 3. 構造・アルゴリズム・実装（What）

#### (1) スロッテッド・ページ（Slotted Page）と TID（Tuple ID）の内部構造

現代のほぼすべての行指向 RDBMS（PostgreSQL、MySQL InnoDB、SQLite 等）が採用している標準的なページレイアウトが **スロッテッド・ページ（Slotted Page）** です（図9-1-1）。

1. **ページヘッダ（Page Header：先頭 24 バイト程度）：**

    * **`pageLSN`（Log Sequence Number）：** このページを最後に更新した WAL ログ（変更内容を先にディスクへ追記記録する仕組み、[9-8節](9-8.md)で詳述）の通し番号です。クラッシュリカバリ時に「このページがすでに最新か、REDO（再実行による復元）が必要か」を判定する基準になります。
    * **チェックサム（Checksum）：** ディスク故障によるサイレントデータ破損を検知する符号です。
    * **`lower` / `upper` ポインタ：** スロット配列の末尾位置（`lower`）と、タプル領域の先頭位置（`upper`）を保持します。この間の `upper - lower` バイトが連続した空き領域（Free Space）となります。

2. **スロット配列（Slot Array / Line Pointers：先頭から下へ成長）：**
    各スロットは `(offset, length)` のペア（通常 4 バイト程度）です。実験Bの数値を当てはめると、`T0` 格納時に `upper = 8192 - 100 = 8092`、`slot[0] = (8092, 100)` となり、`lower` は $24 \to 28$ へ進みます。同様に `T1`・`T2` を挿入すると `slot[1] = (7892, 200)`、`slot[2] = (7742, 150)`、`lower = 36`、`upper = 7742` となります。
    削除されたタプルのスロットには「空き（`offset = 0` 等）」の印を付けます（先頭 $0\text{..}23$ バイト目はページヘッダが占めているため、有効なタプルの `offset` は必ず $0$ より大きく、衝突しません）。なお、空きスロットを別の新タプル用に再利用するのは、元の行を指していたすべての索引エントリが削除・回収された後に行います。

3. **タプルデータ領域（Tuple Data：末尾から上へ成長）：**
    新しいタプルを挿入するとき、空き領域から `length` バイト分だけ `upper` を引き下げて本体を書き込み、スロット配列の末尾（`lower`）へ `(upper, length)` を追記します（なお、タプルを先頭から、スロット配列を末尾から逆向きに伸ばす実装流儀もありますが、両側から中央の空き領域へ向かい合わせて伸ばす本質は同じです）。空き領域が両側から挟み撃ちで縮まり、`upper - lower` が不足したとき（コンパクション後も収まらないとき）がページ満杯です。実験Bで `T1` を削除してコンパクションすると、`T2` が `7942..8091` へ移動して `upper = 7942`、`slot[2] = (7942, 150)` となり、元の $200\text{ B}$ の穴が `upper - lower` の連続空き領域へ回収されます。

タプルを一意に指し示す **TID（Tuple ID / RID：Record ID）** は **`(page_id, slot_num)`** の 2 つ組（例：32 ビットページ番号 ＋ 16 ビットスロット番号）で表されます。

また、1 つのタプル（行）の内部レイアウトも、[0-2節](../0/0-2.md)のアラインメント制約を意識して効率よく設計されています。

* **タプルヘッダ：** トランザクションの可視性情報（MVCC［多版並行制御：1 行の複数バージョンを管理する仕組み、[9-7節](9-7.md)で詳述］で使う作成・削除トランザクション ID）と、どの列が `NULL` かを 1 列 1 ビットで記録する **NULL ビットマップ** を持ちます。
* **属性データ部：** `INT`（$4\text{ B}$）や `BIGINT`（$8\text{ B}$）などの固定長列をアラインメント境界に揃えて配置し、可変長列（`VARCHAR` 等）には先頭に長さヘッダ（あるいはタプル先頭からのオフセット）を付けて後ろへ並べます。

#### (2) バッファプールマネージャ（Buffer Pool Manager）の構造と動作

ディスク上にある何百万枚ものページを毎回ディスク I/O していては性能が出ないため、DBMS は起動時に主記憶（RAM）上に固定メモリ領域を確保し、ページサイズ（例：$8\text{ KiB}$）の枠である **フレーム（Frame）** の配列へ分割します。これが **バッファプール（Buffer Pool）** です（図9-1-2）。

バッファプールマネージャは、次の 3 つのメタデータ構造を管理します。

1. **ページテーブル（Page Table：ハッシュ表）：**
    現在バッファプールに載っている `page_id → frame_id` の対応を $O(1)$ で検索するハッシュ表です（※OS の仮想記憶ページテーブルと同じ名前ですが、こちらは DBMS 内のソフトウェアハッシュ表です）。

2. **フレーム記述子（Frame Metadata）：**
    各フレームごとに次の状態を保持します。

    * **`pin_count`（ピン留めカウンタ）：** 現在そのページを参照・処理しているトランザクション（スレッド）の数です。**`pin_count > 0` のフレームは絶対に追い出し（Eviction）の対象にしてはなりません**（[5-5節](../5/5-5.md)の xv6 バッファキャッシュの `refcnt` と完全に同型です）。
    * **`dirty` ビット（ダーティフラグ）：** メモリ上でタプルの挿入・更新・削除が行われ、ディスク上の内容より新しくなっているかを示します（`1` なら追い出し時に必ずディスクへ書き戻す必要があります）。
    * **ラッチ（Latch）：** そのページのメモリ構造を複数スレッドの同時アクセスから守る短時間の排他／共有ロック（[4-4](../4/4-4.md)・[4-5節](../4/4-5.md)の Readers-Writers ロックに相当）です。

3. **置換リスト（Replacer）：**
    `pin_count == 0` になった追い出し候補フレームを管理するリスト（LRU や Clock-Sweep 等）です。

あるクエリ実行スレッドが `page_id = 42` を要求（**`FetchPage(42)`**）したときの処理フローは次の通りです。

1. **キャッシュヒット時：**
    ページテーブルに `42 → Frame 1` が見つかれば、`Frame 1` の **`pin_count` を $+1$（PIN 固定）** してそのメモリアドレスを即座に返します（ディスク I/O ゼロ）。

2. **キャッシュミス時：**

    * まず空きフレームを探します。空きがなければ置換リストから **`pin_count == 0`** の犠牲フレーム（Victim）を 1 つ選びます（もし全フレームが `pin_count > 0` なら空きを待つかエラーになります）。
    * 選ばれた犠牲フレームの **`dirty == 1`** であれば、上書きする前に必ずその内容をディスクへ書き戻します（**フラッシュ：Flush**。ただし [9-8節](9-8.md)の WAL 規則により、**対応するログが先にディスクへ永続化されていること** を確認してからフラッシュします）。
    * ページテーブルから古い `page_id` を消し、ディスクから `page_id = 42` をそのフレームへ読み込み、`page_id = 42, pin_count = 1, dirty = 0` に設定して返します。

3. **使用終了時（`UnpinPage(42, is_dirty)`）：**
    スレッドがそのページを使い終わったら `UnpinPage` を呼びます。書き込みを行ったなら `dirty = 1` に立て、**`pin_count` を $-1$** します。`pin_count` がちょうど `0` になった瞬間に、そのフレームは置換リストへ戻され追い出し可能になります。

> **【コラム：なぜ DBMS は OS のページキャッシュ（[5-5節](../5/5-5.md)）を使わず、自前のバッファプールを持つのか】**
>
> [3-7節](../3/3-7.md)（`mmap`）や [5-5節](../5/5-5.md)（統合ページキャッシュ）で学んだ通り、Linux などの OS カーネルはディスク上のファイルを自動的に RAM へキャッシュしてくれます。では、なぜ MySQL（InnoDB）や Oracle、SQL Server といった主要 DBMS は、わざわざ `O_DIRECT`（[5-2節](../5/5-2.md)）で OS のページキャッシュをバイパスし、実装コストをかけてまで自前のバッファプールを管理するのでしょうか（PostgreSQL のように OS キャッシュと併用する設計でも、核となる共有バッファは自前で持ちます）。理由は 3 つあります。
>
> 1. **WAL による厳密なフラッシュ順序制御（[9-8節](9-8.md)）：** データベースのクラッシュリカバリ（WAL 規則）では、「ダーティなデータページをディスクへ書き戻す**より必ず前に**、その変更を記録したログレコードをディスクへ永続化しなければならない」という厳格な順序制約があります。OS のページキャッシュはカーネルの都合で任意のタイミングでダーティページを裏から書き戻してしまうため、WAL 規則を破ってデータベースを破損させる危険があります。
> 2. **ワークロード固有の置換・先読み知識：** OS は「あるページが $\text{B}^+$ 木のルートノード（長く保持したいページ）なのか、1 回限りの全表スキャン（すぐ捨ててよいページ）なのか」を知りません。DBMS 自身のバッファプールなら、SQL の実行計画（[9-3](9-3.md)・[9-4節](9-4.md)）に基づいて最適な置換方針と先読み（プリフェッチ）を制御できます。
> 3. **二重キャッシュとシステムコール／ページフォルトの回避：** `mmap` に頼るとページフォルト発生時にスレッド全体が OS にブロックされて制御を失い、通常の `read`/`write` だと OS キャッシュと DB バッファの両方に同じデータが二重に載って RAM を浪費します。

### 4. 限界と補正（Critique & Adaptation）

#### (1) 単純な LRU の「シーケンシャルスキャン汚染」と LRU-K / Clock-Sweep

[5-5節](../5/5-5.md)の OS バッファキャッシュでも確認した通り、単純な LRU（最も長く使われていないページを追い出す）は、「1 回の巨大な全表走査（`SELECT * FROM BigTable`）が、これまで温めていた重要な $\text{B}^+$ 木のルートやホットなページをすべてキャッシュ外へ追い出してしまう（シーケンシャルフラッディング／スキャン汚染）」という弱点を持ちます。

これに対する現代 DBMS の代表的な補正が次の 3 つです（図9-1-3）。

1. **LRU-K（特に LRU-2）：**
    最後に参照された時刻だけでなく、「過去 $K$ 回目の参照時刻（$K = 2$ なら 2 回前）」を記録して比較します。1 回しか参照されていないスキャンページは 2 回目の履歴がない（$-\infty$）ため、2 回以上使われているホットなページを追い出すことができません。

2. **MySQL InnoDB の Midpoint Insertion（2 領域 LRU）：**
    LRU リストを「Young 領域（上位 5/8）」と「Old 領域（下位 3/8）」に分割し、新しくディスクから読み込んだページは先頭ではなく中間点（Old の先頭）へ挿入します。一定時間（例：1 秒）以上経ってから再参照されたページだけを Young 領域へ昇格させることで、1 回限りのスキャンデータを Old 領域だけで素通りさせます。

3. **PostgreSQL の Clock-Sweep ＋ リングバッファ：**
    [3-7節](../3/3-7.md)の Clock アルゴリズムを拡張し、各フレームに参照回数カウンタ（`usage_count`：最大 5）を持たせ、時計針が回るたびに `-1` して `0` になったページを追い出します。さらに巨大な全表スキャンには、バッファプール全体を使わせずわずか **$256\text{ KiB}$ の小さな専用リングバッファ** だけを使い回させることで、スキャン汚染を物理的に遮断します。

#### (2) 更新によるタプル肥大化・巨大列（オーバーフローページ）への補正

スロッテッド・ページには、次の 2 つの境界ケースがあります。

1. **更新でタプルが長くなり元のページに入り切らなくなった場合：**
    `UPDATE` で `VARCHAR` 列が長くなり、ページ内コンパクションをしても同じページに収まらないとき、タプルを別の空きページ（例：`Page 99, Slot 4`）へ引っ越します。しかし元の TID `(Page 5, Slot 2)` を変えると全索引の書き換えになるため、元の場所に「移動先 `(Page 99, Slot 4)` への転送ポインタ（Forwarding Pointer）」を残す（あるいは [9-7節](9-7.md)の MVCC のように新バージョン行を別場所へ追記する）補正を行います。

2. **1 ページ（$8\text{ KiB}$）を超える巨大な列（長文テキストや JSONB）の場合：**
    スロッテッド・ページ 1 枚には収まらないため、タプル本体の中には小さなポインタだけを置き、実データ本体を専用の **オーバーフローページ**（PostgreSQL では **TOAST：The Oversized-Attribute Storage Technique**、圧縮＋分割格納）へ逃がす補正を行います。

#### (3) 「ラッチ（Latch）」と「ロック（Lock）」の厳格な区別

[第9部](../index.md#part-9)を進めるうえで重要な用語の区別を押さえておきます。DBMS の内部には、役割がまったく異なる 2 種類の排他制御が存在します。

* **ロック（Lock：[9-6節](9-6.md)）：** 論理的なデータ（行やテーブル）を他のトランザクションから守る仕組みです。トランザクションのコミット／アボートまで長時間保持され、デッドロック検出やロールバックの対象になります。
* **ラッチ（Latch：本節）：** バッファプールのページテーブルやスロッテッド・ページの `lower` / `upper` ポインタといった **DBMS 内部の物理メモリ構造** を、複数スレッドの同時書き換えから守る超短時間（ナノ秒〜マイクロ秒）の同期機構です（[4-4](../4/4-4.md)・[4-5節](../4/4-5.md)のスピンロックや Readers-Writers ロックで実装されます）。ロールバックは不要であり、獲得順序の規約でデッドロックを回避します。

### 5. 接続と展望（Bridge）：本節の内容が後半のどの部に繋がるか

2. **第1・3・5部との構造的回収：**
    [1-5節](../1/1-5.md)の GOT/PLT、[3-5節](../3/3-5.md)の多段ページテーブル、[5-4節](../5/5-4.md)の i-node に続き、本節のスロッテッド・ページ（TID $\to$ スロット配列 $\to$ 物理オフセット）は、計算機システム全体を貫く **「1 段の間接参照（Indirection）で物理移動の自由度を得る」** パターンの 4 つ目の実例です。またバッファプールの `pin_count` と `dirty` ビットは、[5-5節](../5/5-5.md)の xv6 バッファキャッシュの `refcnt` とライトバックの直系の発展形です。

### 理解度チェック（次節へ進む前の確認）

本節のスロッテッド・ページと TID のオフセット計算・バッファプールの PIN と置換トレースを確認し、次節（[9-2節](9-2.md)：索引構造）へ繋ぐ問いを置きます。

> **【確認の問い】**
>
> 1. **（スロッテッド・ページのバイト境界トレースとコンパクション）**
>     $8\text{ KiB}$（$8{,}192\text{ B}$）のスロッテッド・ページ（図9-1-1）において、先頭 $24\text{ B}$（`0..23`）をページヘッダ、各スロットを $4\text{ B}$ とします。空のページ（`lower = 24`, `upper = 8192`）へ順に `T0`（$120\text{ B}$）、`T1`（$300\text{ B}$）、`T2`（$80\text{ B}$）を挿入したあと、`T1` を削除しました。
>
>     * (a) `T1` 削除直後の `lower`、`upper`、各スロット `slot[0]`〜`slot[2]` の `(offset, length)`、および `upper - lower` で表される連続空き領域のバイト数を求めてください。
>     * (b) この状態からページ内コンパクションを行って `T2` を末尾側（`T0` の隣）へ詰めたとき、新しく更新される `upper`、`slot[2]` の値、連続空き領域のバイト数をそれぞれ求め、外部の索引が保持している `T2` の TID `(page_id, 2)` を変更せずに済む理由を説明してください。
>
> 2. **（バッファプールの `pin_count`・`dirty` ビットとスキャン汚染）**
>
>     * (a) 容量 3 フレーム（`F0, F1, F2`）の空のバッファプール（置換方針は単純な LRU）に対し、次の ①〜⑥ を順に実行しました。ステップ ④ と ⑥ でそれぞれ何が起きるか（ヒット／ミス、追い出し対象、ディスクへのフラッシュの有無と前提規則、あるいは待機・失敗）を答えてください。
>         `① FetchPage(P1)` → `② FetchPage(P2)` → `③ FetchPage(P3)` → `④ FetchPage(P4)` → `⑤ UnpinPage(P1, dirty=True)` に続いて `UnpinPage(P2, dirty=False)` → `⑥ FetchPage(P4)`
>
>     * (b) この 3 フレームの単純 LRU バッファプールに、索引のルートページ `P_root` がすでに 10 回参照された状態で常駐しています。そこへ全表スキャンで 5 枚のページ `S1..S5` を 1 回ずつ順に `FetchPage` して即 `UnpinPage(..., False)` すると `P_root` はどうなるでしょうか。また、**LRU-2**（または **Midpoint Insertion**）はこの問題をどのように防ぐか説明してください。
>
> 3. **（次節への伏線：固定長ページ単位の I/O と 1,000 万行の検索コスト）**
>     $10^7$ 行（1,000 万行）の学生テーブルが $8\text{ KiB}$ のスロッテッド・ページ群（1 ページに平均 $50$ 行格納、計 $200{,}000$ ページ）としてヒープファイルに格納されているとします。
>
>     * (a) 索引のないこのヒープファイルから `WHERE sid = 2026001` の 1 行を探すとき、最悪および平均でおよそ何回のページ読込みが必要になるでしょうか。
>     * (b) そこで「全 $10^7$ 行分の `(sid, TID)` を別ファイルにキー順で並べて、通常の二分探索（中央の 1 件を読んで大小比較し、探索範囲を半分に絞る）をすればよい」と考えたとします。本節で学んだ通りストレージ I/O が **$8\text{ KiB}$ ページ単位** で行われる前提の下では、この素朴な二分探索でも 1 件の検索に最大およそ何回のページ読込み（$\lceil \log_2(10^7) \rceil$ 程度）が発生し、1 回の I/O で読み込んだ $8\text{ KiB}$ ページの活用という点でどのような無駄が残るでしょうか。
