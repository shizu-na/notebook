### 前節（9-2）の確認問題の解答

前節の最後に提示した3つの問いの解答を確認します。問3がそのまま本節（問合せ実行アルゴリズム）の導入になります。

1. **動的ハッシュの局所分割トレースと $\text{B}^+$ 木の高さ見積り：**

    * **(a) バケット A が溢れたときの局所分割：**

        * **① ディレクトリ拡張の要否：** バケット A のローカル深さは $k = 1$、グローバル深さは $d = 2$ で $k < d$ を満たすため、ディレクトリ配列を 2 倍に拡張する**必要はありません**（$d = 2$ のまま維持）。
        * **② 分割後のローカル深さと振り分け先：** 分割後の新バケット `A0`, `A1` のローカル深さはいずれも $k = 1 + 1 = \mathbf{2}$ になります。ハッシュ値の下位 2 ビットで振り分けると、`8`（下位 `00`）と `4`（下位 `00`）が **`A0`（`[8, 4]`）** へ入り、`6`（下位 `10`）が **`A1`（`[6]`）** へ入ります。ディレクトリは `00` が `A0`、`10` が `A1` を指すよう書き換えられ、バケット B（`01`）・C（`11`）は変更不要です。

    * **(b) $\text{B}^+$ 木の高さ 3 での収容件数（$4{,}000\text{ B}$ 有効領域、1 組 $16\text{ B}$）：**

        * **① 満杯時の最大件数 $F$：** $4{,}000 \div 16 = \mathbf{250\text{ 件}}$。
        * **② $60\%$ 充填時の平均件数：** $250 \times 0.6 = \mathbf{150\text{ 件}}$。
        * **③ 高さ 3 で格納できる概算最大レコード数：** $150^3 = \mathbf{3{,}375{,}000\text{ 件}}$（約 $337.5\text{ 万件}$）。

2. **複合索引の誤用の反証と $\text{B}^+$ 木 vs LSM-Tree の比較：**

    * **(a) `INDEX(status, created_at)` に関する 2 つの主張への反論：**

        * **① `WHERE created_at >= '2026-01-01'` への反論：** 複合索引は辞書式順序（まず `status`、同じ `status` の範囲内でのみ `created_at` 順）で並んでいます。先頭列 `status` の指定がないと `created_at` の値は葉ノード全体へ散在するため、**最左プレフィックス原則**によりこの索引だけでは高速に範囲絞り込みができません。
        * **② `WHERE status = 'SHIPPED'` への反論：** 全行の $80\%$（$800\text{ 万行}$）が該当する選択率の高い（絞り込みが弱い）条件で非クラスタ索引を使うと、葉ノードからテーブル本体へのランダムアクセスが最大数百万回発生し、最初からテーブル全体をシーケンシャルスキャンする方がはるかに高速になります。

    * **(b) LSM-Tree が書き込みで有利な理由と新たな負担：**
        ランダム `PUT` をディスク上の離れたページへのランダム更新にする $\text{B}^+$ 木と異なり、LSM-Tree は WAL へのシーケンシャル追記と RAM 上の MemTable 挿入だけで書き込みを完了させ、後からソート済みの不変ファイル SSTable として一括シーケンシャル書出しするため高速です。一方で、① 読み取り時に MemTable と複数レベルの SSTable 群を確認する必要があり読み取り増幅が起きやすい点（Bloom Filter で軽減）、② バックグラウンドで定期的に Compaction（k-way マージ）が走る際に I/O・CPU 負荷によるレイテンシスパイクが生じ得る点、が新たな負担になります。

3. **バッファプールに収まらない 2 表の結合と並べ替えの課題（本節への接続）：**

    * **(a) メモリ一括読込みができない理由：**
        $R$（$1{,}000$ ページ）と $S$（$500$ ページ）はいずれも作業用バッファプール（$M = 100$ ページ）より大きく、テーブル全体を RAM 上のハッシュ表や $\text{B}^+$ 木として保持できません。OS の仮想記憶スワップに頼るとスラッシングで極端に低速化します。

    * **(b) 素朴な手順の読込み回数と改善の方向性：**
        $S$ の 500 ページを読みつつ 1 ページごとに $R$ の全 $1{,}000$ ページを読み直すと、合計 $500 + 500 \times 1{,}000 = \mathbf{500{,}500\text{ 回}}$ のディスク読込みが発生します。これを減らすには、① 空いている $M$ ページ分のバッファを使って $S$ を大きな塊ごとにまとめて読み、$R$ の走査回数を減らす工夫や、② ディスク上の一時領域にソート済み断片やハッシュ値ごとの小ファイルとして小分けに書き出し、メモリに収まる単位同士で処理する工夫（外部アルゴリズム）が必要です。これが本節の主題です。

## 9-3. 問合せ実行アルゴリズム（1-pass・外部マージソート・各種 Join）

### 1. 動機（Why）：なぜ通常のメモリ内アルゴリズム（クイックソート等）では巨大テーブルを処理できないのか

前節（[9-1](9-1.md)・[9-2節](9-2.md)）までで、DBMS がデータを固定長ページへ格納し、バッファプール（RAM 上に $M$ フレーム）へキャッシュし、$\text{B}^+$ 木や動的ハッシュで特定の行へアクセスする下層ストレージエンジンが完成しました。

しかし、実際の SQL クエリは「主キー 1 件の検索」だけではありません。次のような巨大な集合全体に対する演算が日常的に実行されます。

```sql
SELECT s.name, e.grade
FROM Students AS s JOIN Enrollments AS e ON s.sid = e.sid
ORDER BY e.grade;
```

もし `Students` が $10\text{ GiB}$、`Enrollments` が $50\text{ GiB}$ あるのに対し、このクエリに割り当てられた作業用バッファプール（RAM）が **$1\text{ GiB}$ しかない** としたらどうなるでしょうか。

* アルゴリズムの教科書でおなじみのクイックソートやメモリ内ハッシュ表をそのまま動かそうとしても、そもそもデータが RAM に入り切りません。
* 無理やり OS の仮想記憶スワップ（[3-7節](../3/3-7.md)）に頼れば、ランダムアクセスのたびにディスクとのページ入れ替え（**スラッシング**）が頻発し、数分で終わるはずの処理が何日も終わらなくなります。

したがって、DBMS の **問合せ実行エンジン（Execution Engine）** は、CPU の比較回数よりもはるかに重い **「ディスク I/O 回数（読み書きするページ総数）」** を最小化するように専用設計された **外部メモリ（Out-of-Core）アルゴリズム** を用います。本節では、DBMS の実行パイプライン構造（イテレータモデル）を押さえたうえで、**1-pass 演算**、**2-pass 外部マージソート**、そして **4 大結合（Join）アルゴリズム** の仕組みと I/O コストを比較します。

---

### 2. 具体例と動作イメージ（Toy Model）

各アルゴリズムの厳密なコスト式に入る前に、2 つの小さな数値実験で「外部ソートの仕組み」と「結合アルゴリズムによる I/O 回数の差」を確かめます。

#### 実験A：メモリがたった $3$ ページしかなくても、$6$ ページのファイルをソートできる

作業用バッファプールが **$M = 3$ ページ** しか使えない極小マシン上で、未ソートのデータが入った **$6$ ページ** のテーブルを昇順に並べ替えたいとします。1 度には 3 ページしか RAM に載らないのに、どうすれば全体をソートできるでしょうか。

答えは **2 段階（2-pass）の外部マージソート** です（図9-3-1）。

1. **Pass 1（ソート済みランの生成）：**

    * 最初の $3$ ページを RAM へ読み込み、メモリ内でクイックソートして、ソート済みの塊（**ラン：Run 0**、3 ページ）としてディスクへ書き出します。
    * 残りの $3$ ページを RAM へ読み込み、メモリ内でソートして **ラン 1**（3 ページ）としてディスクへ書き出します。

2. **Pass 2（2-way マージ）：**

    * 3 ページのメモリのうち、**2 ページを入力バッファ**（ラン 0 の先頭 1 ページ用、ラン 1 の先頭 1 ページ用）、**残り 1 ページを出力バッファ** に割り当てます。
    * 2 つの入力バッファの先頭要素を比べて小さい方を出力バッファへ移します。出力バッファが 1 ページ満杯になったらディスクへ書き出し、どちらかの入力バッファが空になったらそのランの次の 1 ページをディスクから補充します。
    * これを最後まで繰り返せば、**わずか 3 ページの RAM だけで 6 ページ全体がソート** されます（総ディスク I/O は Pass 1 で読 $6$ ＋書 $6$、Pass 2 で読 $6$ ＋書 $6$ の計 $24$ ページ）。

#### 実験B：同じ 2 テーブルの結合で「アルゴリズムの違い」が I/O 回数を数千倍変える

$B(R) = 1{,}000$ ページ（タプル数 $T(R) = 100{,}000$ 行）のテーブル $R$ と、$B(S) = 500$ ページ（$T(S) = 50{,}000$ 行）のテーブル $S$ を、作業用バッファ **$M = 102$ ページ** を使って等結合 $R \bowtie S$ するとき、アルゴリズムによって必要なディスク I/O 回数（読み書きページ数）がどれほど変わるか比べてみましょう（最終結果の書き出しコストは全方式共通なので除外します）。

* **素朴なタプル単位ネストループ結合（Tuple Nested-Loop）：**
    $R$ の 1 行ごとに $S$ の全 500 ページを読み直す $\implies 1{,}000 + 100{,}000 \times 500 = \mathbf{50{,}001{,}000\text{ I/O}}$（実行が現実的ではありません）。

* **ブロック・ネストループ結合（Block Nested-Loop、$S$ を外側）：**
    $S$ を 100 ページずつまとめてメモリへ載せ、その都度 $R$ を 1 回走査する $\implies 500 + (500 / 100) \times 1{,}000 = \mathbf{5{,}500\text{ I/O}}$（約 **9,091 分の 1** に削減）。

* **GRACE ハッシュ結合（2-pass Hash Join）：**
    両表をハッシュ分割して書き出し、対応バケット同士を結合する $\implies 3 \times (1{,}000 + 500) = \mathbf{4{,}500\text{ I/O}}$。

アルゴリズムとバッファの使い方を変えるだけで、同じハードウェアの上でディスク I/O 回数が桁違いに縮まります。

### 3. 構造・アルゴリズム・実装（What）

#### (1) 問合せ実行の I/O コストモデルとイテレータモデル（Volcano モデル）

本節のコスト解析では、次の記号を用います。

* $B(R)$：テーブル $R$ が占めるディスクページ総数（I/O 単位）。
* $T(R)$：テーブル $R$ に含まれるタプル（行）の総数。
* $M$：この演算に割り当てられたバッファプールの利用可能フレーム（ページ）数。
* **コストの定義：** ディスクから読み込む、またはディスクへ書き出す **ページ I/O の総回数**（最終結果の出力 I/O は全アルゴリズム共通のため慣例として含めません）。

また、[8-2節](../8/8-2.md)の関係代数木（例：$\pi_{\text{name}}(\sigma_{\text{bldg}=\text{'Bldg-A'}}(\text{Students} \bowtie \text{Depts}))$）を実際に DBMS 上で動かす標準的なソフトウェアアーキテクチャが **イテレータモデル（Volcano モデル / パイプライン実行）** です。

すべての演算子（Scan, Filter $\sigma$, Project $\pi$, Join $\bowtie$, Sort 等）が、共通の 3 メソッド **`Open()`**・**`Next()`**・**`Close()`** を実装します。最上位の親演算子が子演算子の `Next()` を呼ぶと、子がさらに孫の `Next()` を呼んでタプルを **1 行ずつ上へ吸い上げる（プル型）** 構造です。これにより、選択や射影のような演算では中間テーブル全体をディスクへ書き出す（マテリアライズする）ことなく、メモリ上を流れ作業（パイプライン）で処理できます。

#### (2) 1-pass アルゴリズム（各ページを 1 回読むだけで完了する演算）

入力テーブルをディスクから **ちょうど 1 回読み込むだけ（コスト $B(R)$）** で完了する操作を **1-pass アルゴリズム** と呼びます。

* **タプル単位の単項演算（選択 $\sigma$・射影 $\pi$）：**
    必要なメモリはわずか $M \ge 1$ ページ（入力 1 ページずつ処理して即座に親へ渡します）。コストは常に $B(R)$ です。

* **メモリ内に収まる重複排除（$\delta$）・集約（$\gamma$：`GROUP BY`）：**
    異なるグループ（または重複しない値）の総数が $M - 1$ ページ以内に収まるなら、メモリ上のハッシュ表（または平衡木）へ順次集計しながら 1 回スキャンするだけで完了します。コストは $B(R)$ です。

* **片方の表がメモリに収まる結合（1-pass Hash Join）：**
    小さい方の表 $S$ が $B(S) \le M - 2$ ページに収まるなら（残り 2 ページを $R$ の入力用と出力用に使用）、$S$ 全体をメモリ上のハッシュ表へ読み込み、続いて大きい表 $R$ を 1 ページずつスキャンしてハッシュ表を引くだけで結合が完了します。コストは最小限の $B(R) + B(S)$ です。

#### (3) 2-pass 外部マージソート（External Merge Sort）

`ORDER BY`、重複排除（`DISTINCT`）、巨大な `GROUP BY`、そして後述のソートマージ結合の基盤となるのが **2-pass 外部マージソート（2PMMS：Two-Phase Multiway Merge Sort）** です（図9-3-1）。

1. **Pass 1（ソート済みラン生成）：**

    * テーブル $R$ を先頭から $M$ ページずつメモリへ読み込み、メモリ内でソートして「ソート済みラン（長さ $M$ ページ）」としてディスクへ書き出します。
    * 作成されるランの個数は $K = \left\lceil \dfrac{B(R)}{M} \right\rceil$ 本です。
    * **I/O コスト：** 全ページを 1 回読んで 1 回書くため $2 B(R)$。

2. **Pass 2（$K$-way マージ）：**

    * $M$ ページのメモリのうち、$K$ ページを各ランの先頭 1 ページ用の入力バッファ、残りの 1 ページを出力バッファに使います。
    * 最小ヒープ（優先度付きキュー）で $K$ 本のランの先頭要素から最小値を $O(\log K)$ で取り出し続け、ソート済みの出力を生成します。
    * **I/O コスト：** 全ページを 1 回読むため $B(R)$（最終結果をディスクへ書き出すなら $+ B(R)$ で計 $4 B(R)$、パイプラインで親演算子へそのまま流すなら合計 $3 B(R)$）。

**1 回の 2-pass でソートできる最大テーブルサイズ：**
Pass 2 で全 $K$ 本のランを同時に 1 パスでマージするためには、出力バッファ 1 ページを除いた $M - 1$ ページ以内に $K$ 本の入力バッファが収まる必要があります（$K \le M - 1$）。各ランの長さは $M$ ページなので、

$$
B(R) \;\le\; M \times (M - 1) \;\approx\; M^2
$$

実験Aの $M = 3$ の例では $3 \times (3 - 1) = 6$ ページとなり、まさに 2-pass の上限と一致していることが確認できます。この $M^2$ による収容能力の拡大は大きく、たとえば 1 ページ $= 8\text{ KiB}$、作業用バッファが $M = 1\text{ GiB} = 131{,}072$ ページあれば、2-pass 外部マージソートは $131{,}072 \times 131{,}071 \times 8\text{ KiB} \approx \mathbf{128\text{ TiB}}$（約 $141\text{ TB}$）もの巨大テーブルを、わずか 2 パスでソートできます（※万一 $B(R) > M(M - 1)$ の場合も、Pass 2 以降で $(M - 1)$ 本ずつまとめる多段マージ［3-pass 以上］で $M(M - 1)^{p - 1}$ ページまで処理できます）。

#### (4) 4 大 Join（結合）アルゴリズムの動作と I/O コスト

データベースの中で計算コストが高く性能を左右するのが 2 つのテーブル $R$ と $S$ の **結合演算（$R \bowtie S$）** です。ここでは $B(S) \le B(R)$（$S$ の方が小さい表）として、4 大結合アルゴリズムの仕組みと I/O コストを比較します（図9-3-2, 図9-3-3）。

1. **ブロック・ネストループ結合（Block Nested-Loop Join：BNLJ）**

    * **仕組み：** 小さい表 $S$ を **外側（Outer）** に選び、メモリの大部分である **$(M - 2)$ ページ分の塊（ブロック）** をまとめて RAM へ読み込みます（残り 2 ページは内側表 $R$ の入力用と結果出力用）。その状態で大きい表 $R$ を 1 ページずつ全走査し、メモリ上の $S$ の塊と一致するペアを出力します（メモリ上の $S$ の塊にハッシュ表を張っておくと CPU 比較も高速です）。これを $S$ の末尾まで繰り返します。
    * **I/O コスト：**

        $$
        B(S) + \left\lceil \frac{B(S)}{M - 2} \right\rceil B(R)
        $$

    * **強み：** 結合条件が等号（`=`）でなくても、**任意の $\theta$-結合（`<`, `!=`, 範囲重複条件など）** に使える汎用的な方式です。

2. **索引ネストループ結合（Index Nested-Loop Join：INLJ）**

    * **仕組み：** 外側表 $R$ を 1 回スキャンし、各タプル $r \in R$ の結合キーを使って、内側表 $S$ にあらかじめ張られた **$\text{B}^+$ 木索引** を引いて一致する行だけを取り出します。
    * **I/O コスト：** $B(R) + T(R) \times C_{\text{index}}$（$C_{\text{index}}$ は $\text{B}^+$ 木探索＋本体取得の $1\text{〜数 I/O}$）。
    * **強み：** `WHERE` 条件によって外側表 $R$ が **数行〜数十行** へ絞り込まれている OLTP クエリでは、巨大な内側表 $S$ を全走査せずに済むため **最も高速** です。

3. **ソートマージ結合（Sort-Merge Join：SMJ）**

    * **仕組み：** $R$ と $S$ の両方を結合キーで **外部マージソート** したあと、2 本のポインタを先頭から同時に進めてマージ（突き合わせ）しながら一致ペアを出力します（図9-3-2左）。
    * **I/O コスト：**

        * 素直に両表を 2-pass ソートしてディスクへ書き出してからマージする場合：$5\bigl(B(R) + B(S)\bigr)$。
        * **最適化版（2-pass 同時マージ）：** Pass 1 で $R$ と $S$ それぞれのソート済みラン（ラン本数の合計 $\lceil B(R)/M \rceil + \lceil B(S)/M \rceil \le M - 1$、すなわちおおむね $B(R) + B(S) \lesssim M^2$）を作り、Pass 2 で両表の全ランを**同時に 1 パスでマージしながらそのまま結合結果を出力**すれば、コストは $3\bigl(B(R) + B(S)\bigr)$ まで縮みます。
        * 両表がすでに主キー $\text{B}^+$ 木等でソート済みならソート不要で $B(R) + B(S)$ です。

    * **強み：** 出力結果が自動的に結合キー順になるため、`ORDER BY` を兼ねられます。重複キーが多すぎなければ安定して高速です（重複キーが極端に多い場合は同一キー群同士の全組合せ出力でポインタ巻き戻しが発生します）。

4. **GRACE ハッシュ結合（GRACE Hash Join：2-pass 等結合の代表的手法）**

    * **仕組み：** 等結合（`R.a = S.a`）において、「同じ結合キーを持つタプル同士は、必ず同じハッシュ値になる」という性質を利用します（図9-3-2右）。

        * **Pass 1（パーティション分割フェーズ）：** 入力 1 ページ＋出力 $(M - 1)$ ページのメモリを使い、ハッシュ関数 $h_1(\text{key})$ で表 $R$ を $(M - 1)$ 個の小さなパーティション $R_0, \dots, R_{M-2}$ へ分割してディスクへ書き出します。同じ $h_1$ で表 $S$ も $S_0, \dots, S_{M-2}$ へ分割して書き出します（I/O：$2(B(R) + B(S))$）。
        * **Pass 2（プローブ結合フェーズ）：** 同じ番号のペア $(R_i, S_i)$ 同士しか結合し得ません。各 $i = 0, \dots, M-2$ ごとに、小さい方の $S_i$（サイズが $M - 2$ ページ以下）を丸ごとメモリへ読み込んで**$h_1$ とは独立な別のハッシュ関数 $h_2$** でメモリ内ハッシュ表を作ります（同じパーティション内の行は $h_1$ の値が揃っているため、$h_2$ を変えないと 1 バケットへ衝突してしまいます）。続いて $R_i$ を 1 ページずつ読みながらハッシュ表を $O(1)$ で引いて結合します（I/O：$B(R) + B(S)$）。

    * **I/O コスト：** 合計 $3\bigl(B(R) + B(S)\bigr)$（端数ページの丸めを除く理想値）。
    * **必要メモリ条件：** 小さい表 $S$ の 1 パーティションがメモリに収まればよいため、$\dfrac{B(S)}{M - 1} \le M - 2 \implies \mathbf{B(S) \lesssim M^2}$ です（2-pass 同時マージ SMJ が $B(R) + B(S) \lesssim M^2$ を要するのに対し、GRACE ハッシュ結合は大きい表 $R$ のサイズに上限がありません）。
    * **さらに高速な Hybrid Hash Join：** Pass 1 でメモリに余裕があれば、最初のパーティション $S_0$ をディスクへ書き出さず最初からメモリ上に残しておくことで、I/O コストを $3(B(R)+B(S))$ から最小 $B(R)+B(S)$ へ近づけられます。

#### (5) 4 大 Join アルゴリズムの総合比較表

| Join アルゴリズム | 典型的なディスク I/O コスト | 対応する結合条件 | 最も適した場面 |
| :--- | :--- | :--- | :--- |
| **Block Nested-Loop** | $B(S) + \lceil B(S)/(M-2) \rceil B(R)$ | **任意の** $\theta$（`<, !=` 可） | 等号以外の複雑な条件、あるいは超小規模表 |
| **Index Nested-Loop** | $B(R) + T(R) \times C_{\text{index}}$ | 等号・範囲（索引依存） | 外側表 $R$ が `WHERE` でごく少数行に絞られているとき |
| **Sort-Merge Join** | $3(B(R)+B(S))$（既ソートなら $B(R)+B(S)$） | 等号（範囲も応用可） | 入力がすでにソート済み、または出力に `ORDER BY` があるとき |
| **GRACE / Hybrid Hash** | $3(B(R)+B(S))$（メモリ収容なら $B(R)+B(S)$） | **等号（`=`）のみ** | 索引がなく未ソートの大規模 2 表の等結合 |

> **【コラム：なぜ Nested-Loop Join では「小さい表を外側」にするだけで I/O が大きく減るのか】**
>
> Block Nested-Loop Join のコスト式 $B(\text{outer}) + \left\lceil \dfrac{B(\text{outer})}{M - 2} \right\rceil B(\text{inner})$ をよく見ると、$R$ と $S$ のどちらを外側（outer）に置くかで結果が変わることが分かります。
>
> $B(R) = 1{,}000$ ページ、$B(S) = 100$ ページ、利用可能メモリ $M = 102$ ページ（つまり 1 ブロック $= M - 2 = 100$ ページ）で比べてみましょう。
>
> * **小さい表 $S$ を外側に置いた場合：**
>     $S$ の 100 ページが丸ごと 1 回でメモリに載るため、内側 $R$ はたった 1 回スキャンするだけです。
>
> $$
> \text{コスト} = 100 + \left\lceil \frac{100}{100} \right\rceil \times 1{,}000 = \mathbf{1{,}100\text{ I/O}}
> $$
>
> * **大きい表 $R$ を外側に置いた場合：**
>     $R$ を 100 ページずつ 10 回に分けて読み込み、そのたびに内側 $S$（100 ページ）を 10 回も読み直します。
>
> $$
> \text{コスト} = 1{,}000 + \left\lceil \frac{1{,}000}{100} \right\rceil \times 100 = \mathbf{2{,}000\text{ I/O}}
> $$
>
> 単純に外側と内側を入れ替えただけでディスク I/O がほぼ半減しました。「小さい表を外側（ビルド側）にして、大きい表の内側走査回数を最小化する」という原則は、Block Nested-Loop でも Hash Join でも共通する基本原則です。

### 4. 限界と補正（Critique & Adaptation）

#### (1) 索引検索が全表走査より遅くなる「選択率の逆転現象」

[9-2節](9-2.md)でも触れた通り、「`WHERE` 条件の列に $\text{B}^+$ 木の二次索引（非クラスタ索引）が張られていれば、常に索引を使った方が速い」というのは誤解です（図9-3-3左）。

$B(R) = 10{,}000$ ページ（$T(R) = 1{,}000{,}000$ 行）のテーブルから、条件を満たす行の割合（**選択率：$s$**）が変化したときのコストを比べてみましょう。

* **全表シーケンシャルスキャン：** 選択率 $s$ に関係なく常に $10{,}000$ ページの連続読み込みです（HDD でも SSD でも高速）。
* **非クラスタ索引（二次索引）スキャン：** ヒットした $s \times 1{,}000{,}000$ 行それぞれについて、葉ノードの TID からヒープファイル上のバラバラなページへ**ランダム I/O** が発生します。仮に $s = 10\%$（10 万行ヒット）だと、最大 **10 万回のランダム I/O** が発生し、全表スキャン（1 万ページの連続 I/O）より何倍も遅くなってしまいます。

**補正：** 次節（[9-4節](9-4.md)）のコストベース最適化器が選択率 $s$ を見積もり、おおむね $s$ が数%以下なら索引スキャン、それ以上なら全表スキャンへ切り替えます。また中間帯では、先に二次索引からヒットした全 TID を集めてページ番号順にソート（ビットマップ化）してからヒープファイルを 1 回だけ昇順スキャンする **ビットマップヒープスキャン（PostgreSQL 等）** によってランダム I/O をシーケンシャル I/O へ変換します。

#### (2) ハッシュ結合における「データスキュー（Skew）」と再帰パーティショニング

GRACE ハッシュ結合は、ハッシュ関数 $h_1$ がデータを全 $(M - 1)$ バケットへ均等に散らすことを前提としています。しかし現実の業務データには、たとえば「顧客 ID の 40% が特定の 1 社（大口顧客）や `NULL` に集中している」ような激しい偏り（**データスキュー：Skew**）が珍しくありません。

もし特定のパーティション $S_i$ だけが巨大化して $M - 2$ ページに収まらなくなると、Pass 2 でメモリ溢れが起きます。

* **補正：** 溢れたパーティション $S_i$ だけを別のハッシュ関数でさらに細分割（再帰パーティショニング）するか、どうしても単一キー値そのものがメモリに入り切らない極端なスキューに対しては、その 1 バケットだけ安全に **Block Nested-Loop Join へフォールバック** します（同一キー値はどのハッシュ関数をかけても同じバケットへ集まるため、再帰ハッシュ分割では解消できないからです）。

#### (3) SSD・大容量 RAM 時代の CPU ボトルネックと「ベクトル化実行・JIT コンパイル」

ここまでは「ディスク I/O が唯一のボトルネック」という古典的モデルで解析してきました。しかし、NVMe SSD と数百 GiB の RAM を搭載し、ワーキングセットの大半がバッファプールへ載る現代のサーバでは、**Volcano モデル（`Next()` を 1 行ごとに仮想関数呼び出しする方式）の CPU オーバーヘッド** が新たなボトルネックとして浮上しています（図9-3-3右）。1 億行を処理するだけで `Next()` の間接関数呼び出しが数億回も発生し、CPU の命令キャッシュや分岐予測器（[0-5節](../0/0-5.md)）を圧迫するからです。

この限界に対する現代 DBMS（DuckDB, ClickHouse, Snowflake, PostgreSQL 11+ 等）の代表的な補正が次の 2 つです。

1. **ベクトル化実行（Vectorized Execution）：**
    `Next()` で 1 行ずつ返すのをやめ、**1,024 行などの小さなバッチ（列指向ベクトル）単位** で一気に受け渡します。関数呼び出し回数が約 1,000 分の 1 に減少し、CPU の **SIMD 命令** で複数行を並列処理できます。

2. **クエリの JIT コンパイル（[2-1節](../2/2-1.md)の回収）：**
    SQL の実行計画（関係代数木）をインタプリタ的に解釈実行するのではなく、**LLVM を使ってクエリ専用のネイティブ機械語ループへ実行時コンパイル（JIT）** してから一気に走らせます（PostgreSQL の LLVM JIT や Hyper / Umbra 等）。

### 理解度チェック（次節へ進む前の確認）

本節の外部マージソート・各種 Join のメモリ上限と I/O コスト・選択率逆転・スキュー対策を確認し、次節（[9-4節](9-4.md)：問合せ最適化）へ繋ぐ問いを置きます。

> **【確認の問い】**
>
> 1. **（2-pass 同時ソートマージ結合と GRACE ハッシュ結合のメモリ上限比較）**
>     作業用バッファプールが **$M = 22$ ページ** の環境で、索引のない未ソートのテーブル $R$（$B(R) = 1{,}000$ ページ）と $S$（$B(S) = 400$ ページ）を等結合 $R \bowtie S$ します（最終結果の出力書き込みコストは除外します）。
>
>     * (a) 2-pass の **同時マージ版ソートマージ結合**（Pass 1 で $R$ と $S$ のソート済みランを作り、Pass 2 で両表の全ランを 1 パスで同時にマージしながら結合）を行おうとすると、Pass 1 で生成される $R$ と $S$ のラン本数の合計は何本になるでしょうか。このラン合計数を Pass 2 で同時にマージできるラン本数の上限（$M - 1$）と比較し、$M = 22$ で 2-pass 同時マージ結合が可能かどうか判定してください。
>     * (b) 同じ $M = 22$ ページ、$B(R) = 1{,}000$、$B(S) = 400$ に対して **GRACE ハッシュ結合** を実行する場合、Pass 1 で作成されるパーティション数（$M - 1$）と、均等分割を仮定したときの $S$ の 1 パーティションあたりのページ数 $\lceil B(S)/(M-1) \rceil$ を求め、Pass 2 のメモリ上限（$M - 2$ ページ）に収まるか判定したうえで、総 I/O コストを求めてください。
>
> 2. **（非クラスタ索引の選択率逆転とハッシュ結合におけるデータスキュー）**
>
>     * (a) $B(R) = 10{,}000$ ページ・$T(R) = 1{,}000{,}000$ 行のテーブルに対し、`WHERE col = 'X'` を満たす行の割合（選択率）が $s = 5\%$（$50{,}000$ 行ヒット）だとします。`col` 列には非クラスタ $\text{B}^+$ 木索引が張られているとして、仮に 1 行の取得あたり少なくとも 1 回のヒープ表へのランダムページ I/O がかかると見積もったとき、素朴な索引スキャンと全表シーケンシャルスキャンのページ I/O 回数を比較し、「索引があれば常に索引を使うべきだ」という誤解を反証してください。
>     * (b) 問 1(b) の GRACE ハッシュ結合において、もし実際のデータでは結合キーの $30\%$（$S$ の $120$ ページ分）がすべて**同一の単一キー値**（例：`NULL` や大口顧客 ID）に集中していた場合（データスキュー）、Pass 2 でどのような破綻が起きるでしょうか。また、同じキー値が原因で再帰ハッシュ分割でも解消できないとき、実システムはどの Join アルゴリズムへフォールバックして乗り切るでしょうか。
>
> 3. **（次節への伏線：3 表の結合順序と選択の適用位置による中間結果サイズの差）**
>     次の 3 つのテーブルを結合して、`dept = 'CS'` である科目の履修者一覧を求めたいとします。
>
>     * `Students(sid, sname)`：$10^5$ 行
>     * `Enroll(sid, cid)`：$10^6$ 行（1 人平均 10 科目を履修）
>     * `Courses(cid, dept)`：$1{,}000$ 行（全 50 学科が均等で、`'CS'` の科目は全体の $2\%$＝$20$ 行）
>
>     次の 2 通りの手順を比較し、① 手順 1 と手順 2 の各段階で生成される**中間結果の行数（タプル数）**を見積もってください。また、② なぜ同じ結果を返すにもかかわらず手順 2 の方が結合の I/O コストを大幅に減らせるのか、さらに結合するテーブルが 5 つ・10 個と増えたときに最適手順を手計算で選ぶのがなぜ困難になるのかを簡潔に答えてください。
>
>     * **手順 1：** まず `Students ⋈ Enroll` を実行し、その結果に `Courses` を結合してから、最後に `dept = 'CS'` で絞り込む。
>     * **手順 2：** まず `Courses` を `dept = 'CS'` で絞り込み、その結果と `Enroll` を結合してから、最後に `Students` を結合する。
